### Major: correction — the dispatch lock does have a TTL; the real defect is that 60s is shorter than one batch, so the lock expires mid-batch and the worker then deletes its successor's lock
File: `app/webhooks/delivery.py` — `_acquire_lock` / `run_worker` `finally` block
What is wrong: The already-reported titles say the lock has "no TTL" and can "wedge dispatch permanently", but `_acquire_lock` does call `redis_client.expire(LOCK_KEY, 60)`; the unreported defect is the opposite one — a batch can take far longer than 60s (per delivery: up to 5 × `REQUEST_TIMEOUT` 30s plus `2+4+8+16` = 30s of `time.sleep`, i.e. ~180s, and because the sleep is blocking those 100 gathered deliveries run effectively serially), so the lock lapses while the batch is still running, a second worker legitimately acquires it, and the first worker's unconditional `finally: await redis_client.delete(LOCK_KEY)` then deletes the *second* worker's lock.
What breaks in production: Two or more workers dispatch concurrently and each deletes the other's lock, so `_claim_batch` races on the same due rows and customers receive duplicate POSTs — the permanent-wedge window that was reported is in fact only the crash between `set` and `expire`, and the lock-stealing above is the failure that actually happens on every batch longer than a minute.
Fix: Replace `_acquire_lock`/`finally` with a fenced lock: acquire with a single `SET LOCK_KEY <random-token> NX EX <ttl>` (atomic, closing the reported check-then-act window too), keep the token in a local, renew it from a heartbeat task while the batch runs, and release only via a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can never delete a lock it does not own. Set the TTL from the measured worst case rather than a guess: `ttl >= MAX_ATTEMPTS * REQUEST_TIMEOUT + sum(backoff_for(i) for i in 1..MAX_ATTEMPTS-1)` per delivery, and assert that arithmetic in a test so raising `MAX_ATTEMPTS` or `REQUEST_TIMEOUT` reds the build. Preserve the property the current code does get right — the lock is released promptly on the happy path, so do not "fix" this by removing the release and relying on expiry alone. Red-prove per clause: (a) drop the `NX` and assert a test where two acquires overlap reds; (b) replace the compare-and-delete with a plain `delete` and assert the "worker A must not release worker B's lock" test reds; (c) shrink the TTL below the computed floor and assert the arithmetic test reds. Allow side that must stay green: a single worker still acquires, runs a batch, and releases, and a worker whose predecessor crashed still acquires after the TTL elapses. Boundary: at exactly `ttl` seconds the lock is considered expired and re-acquirable, and the outgoing holder's compare-and-delete must be a no-op — a tie between renewal and expiry resolves in favour of the new holder.

### Major: the webhook enqueue sits downstream of an unguarded in-process subscriber loop, so any unrelated subscriber failure silently cancels webhook delivery
File: `app/events/dispatcher.py` — `dispatch`, the `for subscriber in SUBSCRIBERS.get(...)` loop placed before the `enqueue_for_event` block
What is wrong: The new `enqueue_for_event` call was appended after `await subscriber(envelope)`, which has no `try`/`except`, so any subscriber raising aborts `dispatch` before the enqueue and before `return event_id` — the author wrapped their own call in `try`/`except`, which shows failure at this layer was anticipated, but placed it behind a loop that has no such guard.
What breaks in production: An unrelated internal subscriber (an analytics hook, a cache warmer) throwing turns off customer-visible webhooks for every event of that type while the event row is already committed, and because the event is committed there is nothing to retry from — the outbound delivery is simply never created.
Fix: Decouple the two consumers: move the `enqueue_for_event` block above the subscriber loop (it is the durable, customer-facing consumer and must not depend on in-process ones), and wrap each subscriber invocation individually in `try`/`except Exception` with a per-subscriber `log.exception`, so one failing subscriber does not cancel its siblings either. Preserve what the current code does correctly — `dispatch` must still return `event_id` and must still propagate nothing from the best-effort consumers to the caller — and do not "fix" this by broadening the existing `except Exception` around the enqueue, which would hide the failure rather than order it. Red-prove per clause: (a) register a subscriber that raises and assert `enqueue_for_event` was still called and `dispatch` still returned `event_id` — reverting the reorder must red this; (b) register two subscribers where the first raises and assert the second still ran — removing the per-subscriber `try` must red this; (c) allow side that must stay green: with all subscribers healthy, every subscriber runs exactly once, in order, and exactly one enqueue happens. Boundary: an event type present in `WEBHOOK_EVENT_TYPES` but with zero registered subscribers must still enqueue, and an event type with subscribers but not in `WEBHOOK_EVENT_TYPES` must still run them — neither path may become conditional on the other after the reorder.

### Major: the documented retry policy makes 429 and 408 permanent failures, so implementing the doc as written drops deliveries the receiver explicitly asked us to retry
File: `docs/webhooks.md` — "Retries" section, "a 4xx is permanent and we stop immediately"
What is wrong: The published contract classifies the entire 4xx range as permanent, but `429 Too Many Requests` and `408 Request Timeout` are precisely the codes a receiver returns to request a later retry; the implementation currently retries all non-2xx, so the fix that other reviewers are asking for — make `deliver` honour the documented policy — would, taken literally, convert every rate-limited receiver into permanent data loss.
What breaks in production: A customer endpoint under load returns 429, we mark the delivery `failed_permanent` on the first attempt, and the event is dropped with no retry and no operator signal — the failure is silent and is worst exactly when the receiver is busiest.
Fix: Correct the doc and the code together to a three-way classification rather than a 2xx/4xx split: 2xx → `delivered`; 408, 429, and 5xx, timeouts and connection errors → retry with backoff; every other 4xx → `failed_permanent`. Honour `Retry-After` when present on a 429 by scheduling `next_attempt_at` at that instant, clamped to `[BASE_DELAY_SECONDS, MAX_RETRY_DELAY]` so a hostile or mistaken header cannot park a delivery indefinitely, and add the jitter the doc already promises. Preserve the property the current wording protects — a genuinely rejected delivery (400, 401, 404, 410) must still stop immediately and must not consume all 5 attempts. Red-prove per clause, one mutation each: 429 → asserted retried (move 429 into the permanent set and the test reds); 400 → asserted permanent after one attempt (move it into the retry set and the attempt-count assertion reds); an out-of-range `Retry-After` → asserted clamped (remove the clamp and the bound assertion reds). Route the unparseable `Retry-After` case explicitly to the default backoff with a WARN that names it, so "header could not be read" is not spelled the same as "no header". Boundary: state that 428 and 431 fall on the permanent side and that `Retry-After: 0` means "retry at the next poll", not "retry immediately in-process".
