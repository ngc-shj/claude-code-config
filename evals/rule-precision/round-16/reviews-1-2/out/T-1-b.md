### Critical: nothing ever starts `run_worker`, so no enqueued delivery is ever sent
File: `app/webhooks/delivery.py` — `run_worker`, and the diff's file list as a whole
What is wrong: `run_worker` is created by this diff and has no caller anywhere in it — no `asyncio.run`/`__main__` block, no ASGI startup hook, no CLI command, no process/supervisor definition among the eight changed files — and because the symbol did not exist before this commit, no pre-existing caller outside the diff can reference it either.
What breaks in production: `dispatch` writes `webhook_deliveries` rows that stay `pending` forever, so `docs/webhooks.md`'s "we POST every subscribed event to it" is false for every customer from the first deploy, and the failure is silent — the API returns 201, the deliveries endpoint shows scheduled attempts, and nothing is ever sent.
Fix: Add the missing runtime unit and wire it: `app/webhooks/worker.py` with `if __name__ == "__main__": asyncio.run(run_worker())`, plus an entry in the same process definition file that already declares the API process (Procfile / compose service / k8s Deployment — whichever this repo uses), and have `run_worker` verify its dependencies at start (`await redis_client.ping()` and one DB round-trip) before entering the loop. Allow side to pin: an integration test that inserts one `pending` row, runs `run_worker` as a task against an `httpx.MockTransport` endpoint, and asserts the row reaches `delivered` within two poll intervals — this must pass. Red-prove separately, by execution: (1) remove the entrypoint registration from the process definition → the deploy smoke check that greps for the worker process must fail; (2) make `_claim_batch` return `[]` → the `delivered` assertion must fail; (3) make the startup dependency check raise → the worker must exit non-zero, not loop. Fail loudly: an unreachable Redis or DB at start must log ERROR and exit non-zero so the supervisor restarts and the alert fires — "no deliverable rows" and "cannot reach the queue" must not both be spelled as a quiet `await asyncio.sleep(poll_interval)`. Preserve: do not "fix" this by delivering inline from `dispatch` — the `webhook_deliveries` table, the retry columns and the lock exist precisely to keep delivery off the request path. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (`<=`, as written), and two rows sharing that timestamp must order deterministically by `(next_attempt_at, id)`.

### Major: `deliver` dereferences the endpoint without a null check — the same unchecked `session.get` already flagged in `_finish`, at a second site
File: `app/webhooks/delivery.py` — `deliver`, `endpoint = session.get(m.WebhookEndpoint, delivery.endpoint_id)`
What is wrong: R3 cross-cutting — the prior reviews reported the unchecked `session.get` in `_finish` but not this one, and `endpoint` is passed straight to `send_once`, which reads `endpoint.signing_secret` and `endpoint.url`; the migration's `ON DELETE CASCADE` on `webhook_deliveries.endpoint_id` means an endpoint deleted between `_claim_batch` and `deliver` yields `None` here.
What breaks in production: the resulting `AttributeError` is not an `httpx.HTTPError`, so it escapes `deliver`'s own `except` clause and propagates out of the `asyncio.gather` in `run_worker`, aborting the whole claimed batch and leaving up to 100 rows stranded in `in_flight` with no reaper.
Fix: In `deliver`, treat a missing endpoint as terminal rather than exceptional — `if endpoint is None: log.error("delivery %s: endpoint %s is gone", delivery.id, delivery.endpoint_id); _finish(delivery.id, "failed_permanent", delivery.attempts + 1, None, "endpoint deleted"); return` — and apply the same guard in `_finish` (`row = session.get(...)`; `if row is None: log.error(...); return`), because under the cascade the delivery row is gone too and the terminal write must not itself raise. This fix must not be written to depend on the already-reported `return_exceptions=True` change to `gather`; each site closes independently. Allow side to pin: the existing `test_send_once_posts_the_signed_payload` path — a delivery whose endpoint still exists is still POSTed and still reaches `delivered`. Red-prove separately, by execution: (1) delete the endpoint row, run `deliver`, assert the delivery reaches `failed_permanent` — red today with `AttributeError`; (2) call `_finish` with an id that does not exist and assert it returns without raising — red today. Fail loudly: both guards log at ERROR with the delivery id; do not downgrade to `debug` or to a bare `return`, or the stranded-endpoint case becomes invisible. Preserve: the retry loop's existing classification of `httpx.HTTPError` as retryable must not be widened to bare `Exception` — that would swallow programming errors as retryable failures. Boundary and tie: the deletion landing exactly between the claim commit and `session.get` is the case under test; both the endpoint lookup and the subsequent `_finish` lookup must be `None`-tolerant, since the cascade removes both rows.

### Major: a raising in-process subscriber skips the webhook enqueue entirely for an already-committed event
File: `app/events/dispatcher.py` — `dispatch`, the `for subscriber in SUBSCRIBERS.get(...)` loop preceding the new `if envelope.type in WEBHOOK_EVENT_TYPES:` block
What is wrong: the new enqueue block was placed *after* an unguarded `await subscriber(envelope)` loop, so any subscriber raising means `enqueue_for_event` is never reached — and the author's own `try/except Exception` around the enqueue shows the post-commit path was known to need protection, but the protection was put on the wrong side of the hazard.
What breaks in production: the `Event` row is already committed when a subscriber fails, so the event exists in the database and in the audit trail while zero `webhook_deliveries` rows are created — a permanent, unlogged, unretryable customer-visible gap that the "delivery is at-least-once" contract in `docs/webhooks.md` promises cannot happen.
Fix: Move the webhook enqueue block to immediately after the `with session_scope()` block and before the subscriber loop (both are post-commit side effects, and the durable one must not be gated by the in-process one), and wrap each subscriber call individually — `for subscriber in ...: try: await subscriber(envelope) except Exception: errors.append(...)` — re-raising a grouped error after the loop so one bad subscriber no longer silences the rest. Allow side to pin: an event with a healthy subscriber must still invoke that subscriber exactly once and still create its delivery rows. Red-prove separately, by execution: (1) register a subscriber that raises, dispatch an `invoice.paid` event, assert `webhook_deliveries` has a row — red today; (2) register two subscribers where the first raises, assert the second was still called — red today; (3) assert the raised subscriber error still surfaces to `dispatch`'s caller — red if the fix is written as a bare swallow. Fail loudly: the collected subscriber failures must be re-raised or logged at ERROR with the event id; do not fix this by converting subscriber errors into a silent `log.debug`. Preserve: `dispatch` must still return `event_id` and must still call every subscriber for the type — the reordering changes only which side effect runs first, not the set. Boundary and tie: an event type that is in `WEBHOOK_EVENT_TYPES` *and* has subscribers is the tie case both assertions must cover; an event type in neither set must still commit and return its id unchanged.

### Major: the dispatch lock's 60s TTL is shorter than the batch it protects, so the ownership bug is the normal path, not a race
File: `app/webhooks/delivery.py` — `_acquire_lock` (`expire(LOCK_KEY, 60)`) and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: this is a correction to the already-reported "released without ownership" item, which understates it — one `deliver` can consume up to `2+4+8+16 = 30s` of `time.sleep` plus five `REQUEST_TIMEOUT`s (150s), and because `time.sleep` is blocking the `asyncio.gather` over `BATCH_SIZE = 100` deliveries is fully serialized, so a batch's worst case is hours against a 60-second TTL.
What breaks in production: the lock expires mid-batch on essentially every non-trivial batch, a second worker acquires it and claims rows concurrently, and then the first worker's unconditional `finally: delete` removes the *second* worker's lock — so the mutual exclusion the design depends on is absent by default rather than under a rare interleaving, and duplicate deliveries become routine.
Fix: Make acquisition atomic and ownership explicit — `token = uuid4().hex`; `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)`; release via a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) — and make the TTL exceed the batch's real wall-clock bound, which requires the already-reported removal of the in-process `time.sleep` retry loop so a batch is bounded by one `REQUEST_TIMEOUT` (30s) of genuinely concurrent requests; set `LOCK_TTL_SECONDS = 120` and add a heartbeat that re-`expire`s while the batch runs. Allow side to pin: a single worker must still acquire, process a full batch, release, and re-acquire on the next poll with no added latency. Red-prove separately, by execution: (1) revert to `get`-then-`set` → a test starting two workers against a fake Redis must show both acquiring, and must go red; (2) revert the compare-and-delete to an unconditional `DEL` → a test where A's lock has expired and B holds it must assert B's token survives A's `finally`, and must go red; (3) set the TTL below the batch bound → an assertion that the lock is still held when the batch ends must go red. Fail loudly: a Redis error inside `_acquire_lock` currently propagates and kills the worker loop; catch it, log ERROR, and return `False` — never let an exception or a `None` reply be read as "lock is free", because that is a fail-open into concurrent dispatch. Preserve: the poll/backoff loop and the single-active-dispatcher property must remain — do not remove the lock in favour of "let both workers run", which is what the `in_flight` claim was never made atomic enough to support. Boundary and tie: a batch finishing at exactly the TTL boundary must not delete a lock it no longer owns — the token comparison, not the clock, decides — and two workers presenting the same token cannot occur because the token is per-acquisition, not per-worker.

### Major: the hot dispatch query has no index — `webhook_endpoints` gets none, while both new indexes went to `webhook_deliveries`
File: `migrations/0042_webhook_delivery.sql` — `CREATE TABLE webhook_endpoints` (no index) vs `idx_webhook_deliveries_status` / `idx_webhook_deliveries_event`
What is wrong: R3 cross-cutting — the prior reviews reported the missing/ill-fitting indexes on `webhook_deliveries` only, but `enqueue_for_event` filters `WebhookEndpoint.org_id == org_id AND active IS TRUE` and `list_webhook_endpoints` filters `org_id`, and neither column is indexed anywhere in the migration.
What breaks in production: every dispatched `invoice.paid` / `invoice.payment_failed` / `subscription.updated` event runs a sequential scan of the whole `webhook_endpoints` table on the synchronous request path, so dispatch latency grows linearly with total customer count rather than with the org's own endpoints.
Fix: Add `CREATE INDEX idx_webhook_endpoints_org ON webhook_endpoints (org_id, active);` to the same migration. Allow side to pin: `list_webhook_endpoints`, which does *not* filter on `active`, must still return inactive endpoints — that is why this is a two-column b-tree and not `... (org_id) WHERE active`, which would leave the list route back on a sequential scan. Red-prove separately, by execution: (1) seed ~10k endpoints across orgs, `EXPLAIN` the enqueue query and assert the plan contains no `Seq Scan on webhook_endpoints` — red before the index; (2) `EXPLAIN` the list query and assert the same — red if the partial-index variant is chosen instead. Fail loudly: if the plan check cannot run because no PostgreSQL instance is available, the check must error rather than skip — a skipped plan assertion reports the same green as a satisfied one. Preserve: leave `idx_webhook_deliveries_status` in place; this finding adds an index, it does not reshuffle the ones already under discussion. Boundary and tie: rows with `active = false` sit inside this index and are filtered by the scan, so flipping an endpoint inactive does not move it out of the list route's reach.

### Major: endpoint registration is unattributed — nothing records which user pointed the org's event stream at a URL
File: `migrations/0042_webhook_delivery.sql` — `CREATE TABLE webhook_endpoints`; `app/api/routes/settings.py` — `create_webhook_endpoint`
What is wrong: the table stores `org_id`, `url`, `signing_secret`, `active` and `created_at` but no actor column, and the route logs nothing, so a registration that redirects every `invoice.*` and `subscription.updated` payload to an arbitrary external host leaves no record of who created it.
What breaks in production: after a data-exfiltration incident the only forensic artifact is a URL and a timestamp — the responder cannot identify the compromised account, cannot scope the blast radius to that user's other actions, and the `ON DELETE CASCADE` from `organizations` removes even that if the org is deleted.
Fix: Add `created_by BIGINT NOT NULL REFERENCES users (id)` to `webhook_endpoints` in this migration and to `WebhookEndpoint` in `app/webhooks/models.py`, populate it from `user.id` in `create_webhook_endpoint`, and emit a structured audit log line at creation (`org_id`, `created_by`, `endpoint_id`, `url` — never `signing_secret`, whose logging is already reported separately). Allow side to pin: a normal creation must still return 201 and the endpoint body; the new NOT NULL column must not break it. Red-prove separately, by execution: (1) create an endpoint and assert the persisted row's `created_by` equals the caller's id — red today (column absent); (2) drop the audit log line and assert the caplog record is present — red; (3) assert the audit record does *not* contain the secret — red if the whole `endpoint.to_dict()` is logged. Fail loudly: if `user.id` is unavailable the insert must fail with a 500 rather than writing a NULL or a sentinel actor — an unattributable endpoint must not be creatable. Preserve: do not fix this by removing the route or by making the response leaner; the 201 body and the endpoint list contract stay as they are (their secret-exposure defect is a separate, already-reported finding). Boundary and tie: two endpoints created by the same user for the same URL are legal and must both persist — attribution is additive, not a uniqueness constraint.

### Minor: is there a role or permission gate these settings routes should sit behind?
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `Depends(current_user)`
What is wrong: the route authenticates but does not authorize beyond membership, so on the evidence in the diff any authenticated member of an org can register an egress endpoint for that org's entire event stream — but whether the codebase has a role model that `current_user` already carries is not something this diff shows.
What breaks in production: if no role gate exists, a single low-privilege compromised account is sufficient to establish a persistent, signed feed of every invoice and subscription event to an attacker-controlled host.
Closing answer: point at an existing admin/owner dependency (e.g. an `require_role` dep used by other mutating settings routes) that this route should also declare, or confirm that org membership is the intended authorization level for egress configuration.

### Minor: `webhook_deliveries.event_id` has no foreign key, unlike every other relation in the migration
File: `migrations/0042_webhook_delivery.sql` — `event_id BIGINT NOT NULL`
What is wrong: `org_id` and `endpoint_id` both carry `REFERENCES ... ON DELETE CASCADE`, but `event_id` — which `docs/webhooks.md` names as the customer's dedup key — is an unconstrained integer, so a delivery can reference an event row that does not exist or was purged.
What breaks in production: deliveries survive their source event, and a reconciliation that joins deliveries back to events silently drops or mismatches rows with no error.

### Minor: `list_deliveries` returns 200 with `[]` for an endpoint id that does not exist, while its sibling in the same file 404s
File: `app/api/routes/settings.py` — `list_deliveries` vs `get_profile`
What is wrong: `get_profile` raises `HTTPException(404, "organization not found")` for a missing row, but `list_deliveries` conflates "no such endpoint" with "no deliveries yet" into the same empty 200.
What breaks in production: a customer polling a mistyped or deleted endpoint id sees a permanently empty delivery list and concludes deliveries are not being attempted, rather than that the endpoint is gone.
