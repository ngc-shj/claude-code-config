### Major: the worker this feature depends on is introduced with no startup wiring and no boot check
File: app/webhooks/delivery.py — `run_worker` (and the diff's file list)
What is wrong: `run_worker` is a brand-new coroutine in a brand-new file and nothing in the change references it — not `app/events/dispatcher.py`, not `app/api/routes/settings.py`, not `tests/webhooks/test_delivery.py` (which imports only `MAX_ATTEMPTS`, `backoff_for`, `send_once`) — and the change adds no process/entrypoint artifact, so no pre-existing deployment file can name a symbol that did not exist before this commit.
What breaks in production: `dispatch` writes `webhook_deliveries` rows forever and nothing ever claims them, so the docs' "we POST every subscribed event" silently no-ops and the defect surfaces only as a customer support ticket days later.
Fix: add the entrypoint in this change — a module that calls `asyncio.run(run_worker())` — plus the background-process entry in whatever supervisor manifest the repo already uses, and a boot smoke test that starts that entrypoint against a real Postgres and Redis, enqueues one delivery, and asserts the row reaches a terminal status within a bounded 30s wait. Deny/allow pairing: the API process must still boot green with no worker configured (worker absence must not break `dispatch`), and that case is asserted alongside the smoke test. Red-prove each clause separately by execution: (i) point the entrypoint at a misspelled coroutine — the smoke test reds at import; (ii) make `_claim_batch` return `[]` unconditionally — the smoke test reds on the bounded wait rather than hanging; (iii) stop Redis before start — the entrypoint must exit non-zero with a named error. Fail loudly: "cannot reach Redis/DB" must not be spelled the same as "no work" — `run_worker` logs and exits non-zero so the supervisor restarts it, rather than looping silently. Preserve: keep the `poll_interval` parameter so the smoke test can run fast. Boundary: the 30s wait is inclusive, and a second concurrently started worker must not make the assertion pass twice (see the lock finding). If a supervisor entry for this worker already exists outside the diff, naming it in the PR closes this finding.

### Major: a failing in-process subscriber skips the webhook enqueue entirely
File: app/events/dispatcher.py — `dispatch`, the `for subscriber in SUBSCRIBERS...` loop and the block placed after it
What is wrong: the new enqueue block was appended after an unguarded `await subscriber(envelope)` loop, so any subscriber raising propagates out of `dispatch` after the event row has already been committed, and the webhook enqueue never runs at all — a different failure mode from the already-reported swallowed `enqueue_for_event` exception, because here the try/except is never entered.
What breaks in production: one unrelated in-process subscriber bug drops every outbound webhook for every affected event, with no delivery row, no retry, and no log line mentioning webhooks.
Fix: enqueue first, then iterate subscribers with a per-subscriber `try/except` that logs the subscriber's name at error and continues, aggregating failures and re-raising after the loop. Deny/allow pairing: an event whose subscribers all succeed must still return the same `event_id` and create byte-identical delivery rows — pin that case. Red-prove each clause separately: (i) a subscriber that raises — assert the delivery rows exist AND the aggregated error still propagates; (ii) an empty subscriber list — rows still enqueued; (iii) `enqueue_for_event` raising — the subscriber loop still runs. Fail loudly: do not convert this into a silent swallow; the per-subscriber handler logs with the subscriber name and `event_id`, and the aggregate is re-raised. Preserve: subscriber exceptions must remain observable to callers — the point of the fix is ordering, not suppression. Boundary: when both a subscriber and the enqueue fail, the enqueue failure is the one that must name itself in the log, because it is the one with no retry path.

### Major: the Redis lock is acquired with two commands, so a crash between them wedges dispatch forever, and its TTL is shorter than one batch
File: app/webhooks/delivery.py — `_acquire_lock`, `run_worker`
What is wrong: correcting the reported title "can wedge with no TTL" — a TTL is set (`await redis_client.expire(LOCK_KEY, 60)`), but it is a second round trip after `set`, so a crash in between leaves a key with no expiry (that, not the absent TTL, is the permanent-wedge path), and 60s is below the worst-case wall time of a single delivery (`MAX_ATTEMPTS` 5 × `REQUEST_TIMEOUT` 30s + 2+4+8+16s of backoff = 180s), so the lock expires mid-batch on exactly the slow-endpoint runs it exists to serialize.
What breaks in production: a worker killed between `set` and `expire` blocks all webhook delivery until someone deletes the key by hand, and on slow endpoints two or three workers run concurrently and each `finally` deletes a lock it no longer owns.
Fix: replace the pair with one atomic `SET LOCK_KEY <per-worker-token> NX EX <ttl>`, release via a Lua compare-and-delete on that token, and stop relying on Redis for correctness by making the DB claim authoritative: `_claim_batch` selects `WHERE status='pending' AND next_attempt_at <= now() ORDER BY next_attempt_at, id FOR UPDATE SKIP LOCKED LIMIT 100` and flips to `in_flight` in the same transaction. Set the TTL above 180s or renew it while the batch runs. Deny/allow pairing: a single worker on an empty queue must still acquire, find nothing, release, and sleep — the NX path must not fail closed when the previous holder's key merely expired. Red-prove each clause separately: (i) revert to GET-then-SET and run two workers — the duplicate-claim assertion reds; (ii) delete the token comparison in release — the "worker A does not delete worker B's key" assertion reds; (iii) assert `TTL(LOCK_KEY) > 0` immediately after acquisition — reds against the current two-command version if the process dies between them; (iv) drop `SKIP LOCKED` — the two-worker test reds on the same delivery row being sent twice. Fail loudly: if Redis is unreachable, `_acquire_lock` must log a named error and the worker must not proceed as though it held the lock. Preserve: the poll-interval backoff when the lock is held. Boundary: `next_attempt_at` exactly equal to `now()` is claimed (`<=`, inclusive), and two rows sharing a `next_attempt_at` are broken by `id`.

### Major: the enqueue hot path has no index to use on `webhook_endpoints`
File: migrations/0042_webhook_delivery.sql — `CREATE TABLE webhook_endpoints` (no index statements) vs app/webhooks/delivery.py — `enqueue_for_event`
What is wrong: `enqueue_for_event` filters `org_id == org_id AND active IS TRUE` on every dispatched event, and the migration creates two indexes on `webhook_deliveries` but none on `webhook_endpoints` — Postgres does not index a REFERENCES column automatically — so this is a distinct gap from the already-reported missing deliveries indexes.
What breaks in production: every `invoice.paid`, `invoice.payment_failed` and `subscription.updated` event runs a sequential scan over the whole tenant-wide endpoints table inside the dispatch path, so dispatch latency grows linearly with total customer count rather than with the org's own endpoints.
Fix: add `CREATE INDEX idx_webhook_endpoints_org ON webhook_endpoints (org_id, active);` to the same transaction in `migrations/0042_webhook_delivery.sql` (safe without CONCURRENTLY only because the table is created empty in this same migration — say so in a comment). Deny/allow pairing: endpoint creation must not regress — pin that the INSERT plan is unchanged, alongside pinning that the enqueue query's plan is an Index Scan. Red-prove each clause separately: (i) drop the index — the EXPLAIN assertion on the enqueue query reds with `Seq Scan on webhook_endpoints`; (ii) build it as a partial index with the inverted predicate (`WHERE NOT active`) — the same assertion reds, proving the assertion reads the predicate and not merely the index name. Fail loudly: if EXPLAIN cannot be executed (no DB in the test environment) the check must error and name itself, never skip to green. Preserve: leave the two existing deliveries indexes in place; this is additive. Boundary: an org with zero endpoints must return an empty result through the index rather than erroring, and an endpoint row with `active = NULL` cannot occur because the column is `NOT NULL` — state that in the migration comment so the partial-index variant is not introduced later.

### Major: nothing projects the internal event payload into the public webhook body
File: app/webhooks/delivery.py — `enqueue_for_event` (`payload=payload`) and `send_once` (`json=delivery.payload`); app/events/dispatcher.py — `dispatch` passing `payload=envelope.payload`
What is wrong: the object handed to in-process subscribers is posted verbatim to customer-controlled URLs with no projection, allowlist, or version marker, so the public contract described in `docs/webhooks.md` is defined by whatever any internal producer happens to put in `EventEnvelope.payload`.
What breaks in production: a field added to an internal `invoice.paid` payload is published to every subscribed third-party endpoint the moment it merges — an unreviewed data-egress change and an unversioned breaking change to a documented API, with no place in the code where either would be caught.
Fix: add an explicit outbound renderer in `app/webhooks/` — `render(event_id, event_type, occurred_at, payload) -> dict` returning `{"id", "type", "created_at", "api_version", "data"}` where `data` is a per-event-type field allowlist — have `enqueue_for_event` store the rendered body in `WebhookDelivery.payload`'s place (keep the raw payload in a separate column so redelivery stays possible), and have `send_once` post exactly the stored bytes. Document the shape in `docs/webhooks.md`. Deny/allow pairing: the `{"id": "evt_1", "type": "invoice.paid", "amount_cents": 4200}` fixture in `tests/webhooks/test_delivery.py` must still arrive with `amount_cents` intact — pin that as the success case beside the exclusion cases. Red-prove each clause separately: (i) add an extra key to the internal payload — the contract test asserting the outbound key set reds; (ii) delete a documented key from the renderer — the same test reds on a different assertion; (iii) call `render` with an event type that has no allowlist entry — it must raise a named error, and the test reds if it falls back to the raw payload. Fail loudly: an unknown event type is a refusal, never a passthrough. Preserve: do not drop the raw payload from storage — redelivery and support debugging depend on it; project at render time. Boundary: a documented key whose value is absent is omitted rather than emitted as `null`, and a key present in both the allowlist and the raw payload always takes the raw value.

### Minor: `event_id` carries no foreign key while `endpoint_id`, three lines above, does
File: migrations/0042_webhook_delivery.sql — `webhook_deliveries.event_id`
What is wrong: within one `CREATE TABLE`, `endpoint_id` is declared `REFERENCES webhook_endpoints (id) ON DELETE CASCADE` while `event_id BIGINT NOT NULL` references nothing, so the column the docs make the customer's dedup key has no integrity guarantee and no declared lifecycle.
What breaks in production: deliveries can outlive or precede the event row they name, and support cannot join a customer's reported `event_id` back to the event.
Fix: add `REFERENCES events (id)` with an explicit ON DELETE policy chosen deliberately (RESTRICT if delivery history must not be silently lost), or add a comment stating why events are intentionally unreferenced (e.g. partitioning) so the asymmetry is not read as an oversight.

### Minor: is there an authorization or audit requirement on webhook endpoint creation?

### Minor: the deliveries table has no retention path and stores a full payload copy per endpoint
File: migrations/0042_webhook_delivery.sql — `webhook_deliveries.payload JSONB NOT NULL`; app/webhooks/delivery.py — `enqueue_for_event`
What is wrong: one row per endpoint per event, each holding a complete JSONB copy of the payload plus (per the already-reported unbounded `response_body`) the response text, with no TTL, prune job, or partitioning introduced anywhere in the change.
What breaks in production: the table grows without bound in proportion to events × endpoints and eventually dominates the database, with the first symptom being backup and vacuum time rather than an application error.
Fix: either store the payload once and reference the event row, or add a retention job and a `created_at` index to support it, and document the retention window in `docs/webhooks.md` next to the deliveries endpoint.
