### Major: the URL guard is a prefix match on the scheme, so cleartext `http://` (and any `http*` scheme) is accepted while the docs promise HTTPS-only
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: `startswith("http")` judges the notation rather than testing membership, so `http://`, `httpx://` and `httpfoo://` all pass, while `docs/webhooks.md` states "Only `https://` URLs are accepted" — R47 (surface-form adjudication where the URL parser defines the meaning) plus R49 (a claim stronger than the implementation).
What breaks in production: an endpoint registered as `http://hooks.example.com/acme` receives every invoice and subscription payload, plus the live HMAC signature header, in cleartext over the public internet, and any on-path observer can both read the customer's billing data and replay the request verbatim.
Fix: replace the prefix test with exact membership — `if parsed.scheme != "https" or not parsed.netloc:` — and if plain HTTP is genuinely intended, change `docs/webhooks.md` in the same commit instead of leaving the two disagreeing; wrap the `urlparse` call so that a value it refuses (or one yielding an empty scheme) raises the same 422 with a message naming the scheme actually seen, so "could not parse" is never spelled the same as "not https"; preserve the accept side explicitly — `https://hooks.example.com/acme` must still return 201 and still store the URL verbatim (no normalisation, no lowercasing of the path), pinned by its own test; state the boundary: `urlparse` lowercases the scheme, so `HTTPS://…` falls on the accept side, a bare `hooks.example.com/acme` (empty scheme) falls on the reject side, and two endpoints differing only in scheme remain two distinct rows rather than a conflict; red-prove the three clauses with three separate runs — (i) revert `!=` to `startswith` and watch only the `http://`-rejected assertion redden, (ii) change the constant to `"http"` and watch only the https-accepted assertion redden, (iii) make the parse-failure branch fall through and watch only the malformed-URL refusal redden.
This is the scheme axis; the already-reported SSRF finding is the host/redirect axis, and fixing either one leaves the other open.

### Major: `deliver` dereferences the endpoint row without checking it exists, and the resulting `AttributeError` is not an `httpx.HTTPError`
File: `app/webhooks/delivery.py` — `deliver`, `endpoint = session.get(m.WebhookEndpoint, delivery.endpoint_id)`
What is wrong: `session.get` returns `None` when the endpoint row is gone, and the only `except` in the retry loop catches `httpx.HTTPError`, so the `NoneType` dereference inside `send_once` escapes uncaught — the same missing-row dereference already reported in `_finish`, at a second site nobody named (R3 cross-cutting).
What breaks in production: the migration in this same diff declares `org_id … ON DELETE CASCADE`, so deleting an organisation removes its endpoints while a batch is mid-flight; the raised `AttributeError` propagates through `asyncio.gather`, out of the `try/finally` in `run_worker`, and kills the worker, abandoning the sibling coroutines and stranding every row in that batch in `in_flight`.
Fix: after the lookup, branch on `endpoint is None` and call `_finish(delivery.id, "failed_permanent", delivery.attempts, None, "endpoint deleted")` before returning, so a vanished endpoint is a terminal outcome rather than an exception; add `return_exceptions=True` to the `asyncio.gather` in `run_worker` and log each returned exception with its delivery id, so an unforeseen error in one delivery fails loudly and by name without taking its siblings or the worker down; do not achieve this by broadening the `except` in `deliver` to bare `Exception` — that would hide the transport-error classification the retry loop depends on, and the behaviour to preserve is that `httpx.HTTPError` still routes to a retry rather than to a permanent failure; boundary: a delivery whose endpoint disappears at exactly the moment of lookup is failed, not retried, and two deliveries for the same missing endpoint each get their own terminal row rather than one of them being silently dropped; red-prove separately — (i) a test whose fake session returns `None` for the endpoint must assert the delivery row reaches `failed_permanent`, and reverting the `is None` branch must redden that and only that; (ii) a test where one of three gathered deliveries raises must assert the other two still complete, and removing `return_exceptions=True` must redden that assertion alone; (iii) a test that a `httpx.ConnectError` still produces a retry must stay green through both mutations, which is what shows the fix did not simply swallow everything.

### Major: the per-endpoint `active` kill switch has no write path — nothing can ever set it to `False`
File: `app/webhooks/models.py` — `WebhookEndpoint.active`; `app/api/routes/settings.py` — `create_webhook_endpoint` (`active=True`); `app/webhooks/delivery.py` — `enqueue_for_event` (`.filter(… m.WebhookEndpoint.active.is_(True))`)
What is wrong: the column is created with `DEFAULT TRUE`, written only as the literal `True` at creation, and read as a filter predicate, but the diff adds no update or delete route for `webhook_endpoints` — a brand-new table, so no pre-existing route can write it either (R41: declared capability with no backing path; the reported `webhooks_enabled` finding is a different column on a different table).
What breaks in production: a customer whose signing secret or endpoint URL is compromised has no way to stop delivery — the docs tell them the secret "cannot be read back", so they cannot rotate it either, and support's only recourse is a manual `UPDATE` against production.
Fix: add `PATCH /v1/settings/webhook-endpoints/{endpoint_id}` accepting `{"active": bool}` and `POST /v1/settings/webhook-endpoints/{endpoint_id}/rotate-secret` returning the new secret exactly once, both loading the row with `.filter(org_id == user.org_id, id == endpoint_id)` and raising 404 (not 403) when that yields nothing, so a cross-tenant id is indistinguishable from a missing one; make `deliver` re-read `endpoint.active` after the claim and terminate the delivery as `failed_permanent` with detail `"endpoint deactivated"` rather than sending, since deactivation must also stop deliveries already queued; preserve the allow side — an endpoint with `active=True` must still receive its queued deliveries unchanged after the re-check is added, and rotation must not invalidate a signature already computed for an in-flight attempt (the in-flight attempt uses the secret it read; the next attempt uses the new one); fail loudly if the row cannot be loaded at all — a `session.get` returning `None` in the PATCH handler is a 404, never a silent 200; boundary: `active=False` at exactly the moment of the claim falls on the do-not-send side, and two concurrent PATCHes to the same row settle by last-write-wins on a single column, not by a read-modify-write of the whole endpoint; red-prove in three runs — deleting the tenancy predicate reddens the cross-org 404 test, deleting the `active` re-check in `deliver` reddens the deactivated-endpoint test, and deleting the rotation handler reddens the rotate test while the active-endpoint delivery test stays green throughout.

### Major: the delivery status vocabulary is written out in three places with no single source, and has already drifted
File: `app/webhooks/models.py` — `STATUSES`; `app/webhooks/delivery.py` — the literals `"pending"`, `"in_flight"`, `"delivered"`, `"failed_permanent"`; `migrations/0042_webhook_delivery.sql` — `CHECK (status IN (…))`
What is wrong: `STATUSES` is defined and referenced by nothing (not by the `Column`, not by any validator, not by the migration), while `delivery.py` spells each state as a bare literal and the SQL re-lists them a third time — R2, and the already-reported CHECK-versus-code mismatch is the drift this duplication produced, not a separate cause.
What breaks in production: the next state added or renamed will again land in two of the three places, and because the SQL copy is the only enforcing one, the failure surfaces as a constraint violation on a write path rather than at import or test time.
Fix: make `models.STATUSES` the single source — bind it to the column with `Column(String(20), nullable=False, default=STATUSES[0])` plus an explicit `Enum`/`CheckConstraint` derived from `STATUSES` in the model's `__table_args__`, replace every literal in `delivery.py` with a reference (`STATUS_PENDING`, `STATUS_IN_FLIGHT`, … named members of that tuple), and generate the migration's `CHECK` list from the same tuple or add a test that reads the migration file and asserts its `IN (…)` set equals `set(STATUSES)`; confirm meaning-equality before collapsing, per R2 — these four strings name delivery lifecycle states and nothing else in the diff reuses those bytes for another concept, so the merge is safe here; do not "fix" this by deleting the unused `STATUSES` constant, which would remove the only place the intended vocabulary is written down; preserve the allow side — every status the code writes today must still satisfy the constraint after the change, so the migration's list gains `failed_permanent` rather than the code losing it; boundary: a status string differing only in case or whitespace is rejected, and a row already holding the old `failed` value (none exist, since the table is new in this migration) would need a data fix before the constraint is tightened; red-prove in three runs — adding a fifth member to `STATUSES` without touching the SQL must redden the migration-parity test, writing a literal `"failed"` in `_finish` must redden a status-round-trip test, and removing the `CheckConstraint` must redden an invalid-status insert test.

### Major: the two new tables index none of the columns the new queries actually filter on
File: `migrations/0042_webhook_delivery.sql` — `CREATE INDEX idx_webhook_deliveries_status`, `CREATE UNIQUE INDEX idx_webhook_deliveries_event`
What is wrong: the migration creates no index on `webhook_endpoints (org_id)`, which `enqueue_for_event` and `list_webhook_endpoints` both filter on, and none on `webhook_deliveries (endpoint_id)`, which `list_deliveries` filters on and which the `ON DELETE CASCADE` from `webhook_endpoints` must scan — this is a different gap from the reported claim-query index, which concerns `(status, next_attempt_at)`.
What breaks in production: every dispatched event of the three subscribed types runs a sequential scan of `webhook_endpoints` on the request path, and the deliveries listing plus any endpoint or organisation deletion scans the whole `webhook_deliveries` table, which this diff gives no retention policy and therefore grows without bound.
Fix: add `CREATE INDEX idx_webhook_endpoints_org ON webhook_endpoints (org_id);` and `CREATE INDEX idx_webhook_deliveries_endpoint ON webhook_deliveries (endpoint_id, created_at DESC, id DESC);` inside the existing transaction, the second matching the listing's filter and its ordering in one structure; keep the existing `idx_webhook_deliveries_status` — it is not made redundant, since the claim query filters on status without an endpoint id — so this is an addition, not a replacement of what is there; verify the allow side by running `EXPLAIN` on both new queries before and after and asserting the plan moves from `Seq Scan` to `Index Scan` while the returned row set is byte-identical, which is the property the index must not change; boundary: with `created_at` ties (two deliveries enqueued for the same event in the same statement share it to microsecond precision), the trailing `id DESC` is what makes the order total, so a page cut through equal `created_at` values neither repeats nor skips a row; fail loudly rather than silently degrading — if the migration runs against a database where `CREATE INDEX` is refused, the surrounding `BEGIN/COMMIT` must abort the whole migration rather than leaving the tables indexed halfway; red-prove separately — dropping each of the two new indexes in turn must redden its own `EXPLAIN`-plan assertion, and dropping the trailing `id DESC` must redden a pagination test that inserts two rows with an identical `created_at` and asserts two distinct pages.

### Minor: correction — the documented "a 4xx is permanent and we stop immediately" rule would permanently drop deliveries to any consumer that rate-limits
File: `docs/webhooks.md` — the Retries section
What is wrong: a previous reviewer reported that the code retries 4xx against the documented policy; the correction is that the documented policy is itself the wrong target, because `429 Too Many Requests` and `408 Request Timeout` are 4xx codes that explicitly ask the sender to try again.
What breaks in production: implementing the doc literally would mark every delivery to a temporarily rate-limited customer endpoint `failed_permanent` on first response, converting a momentary backpressure signal into permanent data loss with no retry path.
Fix: state the exception in `docs/webhooks.md` and implement it — retry on 408 and 429 (honouring `Retry-After` when present, clamped to the existing `MAX_ATTEMPTS` budget) and treat every other 4xx as permanent; pin the allow side with a test that a `429` response leads to a second attempt and a `400` does not, and red-prove the two clauses in separate runs by removing `429` from the retryable set (reddens the retry test) and by adding `400` to it (reddens the permanent test).

### Minor: the create endpoint's request schema bounds neither the URL length nor the event-type list, and accepts unknown fields
File: `app/api/routes/settings.py` — `EndpointIn`
What is wrong: `url: str` and `event_types: list[str] = []` carry no `max_length`/`max_items` and the model does not forbid extra fields, so an authenticated caller controls the size of what lands in the `TEXT` and `JSONB` columns (RS3 — a type annotation is not validation).
What breaks in production: an authenticated caller can store multi-megabyte URLs and event-type lists in `webhook_endpoints`, and `enqueue_for_event` then walks that list per endpoint on every dispatched event.
Fix: give `EndpointIn` `model_config = ConfigDict(extra="forbid")`, `url: str = Field(max_length=2048)` and `event_types: list[str] = Field(default_factory=list, max_length=32)` with each member length-bounded; keep the allow side pinned — the documented example body `{"url": "https://hooks.example.com/acme", "event_types": ["invoice.paid"]}` must still return 201 unchanged; boundary: a URL of exactly 2048 characters is accepted and 2049 is rejected with 422.

### Minor (question): is `app/webhooks/` reachable once packaged, given that the diff adds no `__init__.py` for it?
File: `app/webhooks/` — new modules `models.py`, `signing.py`, `delivery.py`; `tests/webhooks/test_delivery.py`
What is wrong: the diff creates a new package directory with no `__init__.py`, which imports fine as a PEP 420 namespace package but is excluded by `setuptools.find_packages` — I cannot see the project's `pyproject.toml`/`setup.py` in this change, so I am asking rather than asserting.
What breaks in production: if the build uses `find_packages` rather than `find_namespace_packages` or a src-layout wheel that copies the tree wholesale, the module is absent from the installed artifact and `app/events/dispatcher.py`'s new top-level `from app.webhooks import delivery as webhook_delivery` raises `ImportError` at startup while every local test passes.
What would close it: confirming that the packaging config uses `find_namespace_packages`, an explicit `packages` list that will be updated, or a non-setuptools backend (hatch/poetry) that includes the directory — or that sibling packages such as `app/events/` likewise have no `__init__.py`.
