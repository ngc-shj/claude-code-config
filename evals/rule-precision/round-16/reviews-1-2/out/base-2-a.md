### Critical: `list_deliveries` has no tenancy filter — any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(...)` on `WebhookDelivery.endpoint_id == endpoint_id`
What is wrong: The query is scoped only by the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while the sibling handler `list_webhook_endpoints` two lines above does filter on `org_id`, so the tenancy predicate was written for one route and dropped on the other.
What breaks in production: Any logged-in customer can enumerate `endpoint_id` values and read other tenants' delivery rows; `WebhookDelivery.to_dict()` exposes `event_id`, `event_type`, `status` and `response_status` for events belonging to organizations the caller has no relationship with, which is a cross-tenant data breach reportable under the same terms as a database leak.
Fix: Resolve the endpoint first and scope it to the caller — inside the same `session_scope`, `endpoint = session.query(WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`; if it is `None`, `raise HTTPException(status_code=404, ...)` (404, not 403, so the route does not confirm existence of another tenant's id), and only then run the delivery query with `WebhookDelivery.endpoint_id == endpoint.id`. Preserve the allow side and pin it: a test where the endpoint belongs to the caller's org must still return the rows, with the same ordering and `limit` semantics the current code has — a fix that 404s unconditionally satisfies the deny test alone. Red-prove the two clauses separately: (1) delete the `org_id` term and confirm the cross-tenant test goes from 404 to 200-with-rows; (2) delete the `one_or_none()` None-check and confirm the unknown-id test goes from 404 to 200-with-empty-list. Route the third outcome loudly: a caller whose session has no `org_id` must raise, never fall through to an unfiltered query — "could not determine the tenant" must not be spelled the same as "no rows". Boundary and tie: an endpoint whose `org_id` equals the caller's org is IN; a soft-deleted or `active=False` endpoint still belonging to the caller stays IN (deliveries remain inspectable after an endpoint is disabled), and two endpoints can never share an id because it is the primary key.

### Critical: `GET /webhook-endpoints` returns every endpoint's `signing_secret`, contradicting the documented "cannot be read back" control
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` is the single serializer shared by the create route (where returning the secret once is intended) and the list route, so `docs/webhooks.md`'s claim that "the response is the only place the signing secret appears — it cannot be read back afterwards" is false as implemented (R49: a claim stronger than the implementation).
What breaks in production: Any read-scoped session or leaked read-only API credential harvests every endpoint's HMAC key in one request, after which the attacker can forge signed events indistinguishable from ours, and customers who followed the doc's advice have no reason to rotate.
Fix: Split the serializer — make `to_dict()` omit `signing_secret` entirely, and add a separate `to_dict_with_secret()` used only by `create_webhook_endpoint`; the list route keeps calling `to_dict()`. Cross-cutting check: `to_dict()` on `WebhookEndpoint` has exactly two call sites in this diff (`create_webhook_endpoint`, `list_webhook_endpoints`) — both are covered by this split, and `WebhookDelivery.to_dict()` carries no secret. Preserve the allow side and pin it: the create route's 201 response must still contain the secret with the `whsec_` prefix intact — a fix that strips the secret everywhere breaks the only path by which a customer can ever obtain it, which is precisely the "do not fix by deleting what made the feature useful" failure. Red-prove each clause separately: (1) re-add `signing_secret` to `to_dict()` and confirm the list-route test asserting `"signing_secret" not in body[0]` goes red; (2) point the create route at `to_dict()` and confirm the create-route test asserting the secret is present goes red. Fail loudly on the third outcome: if a future serializer is added and the endpoint model gains another secret-bearing column, an explicit allowlist of keys inside `to_dict()` (rather than a denylist of what to strip) makes the unknown column default to not-serialized. Boundary: the create response is the one and only emission; a re-read of the same endpoint immediately after creation is already past the boundary and must not include it.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random.choice` draws from the Mersenne Twister, a non-cryptographic PRNG whose internal state is fully recoverable from 624 observed outputs, and this function is the sole source of the HMAC key for every endpoint.
What breaks in production: An attacker who obtains a handful of secrets — their own endpoint's secret, plus any leaked through the disclosure finding above — can recover the generator state and predict every other tenant's signing secret, letting them forge webhook events that verify against the victim's own verification code.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and `import secrets` (drop the now-unused `random`, `string`, and `_ALPHABET` — leave nothing that can be reintroduced by a later import). Rename `SECRET_BYTES` to match its new meaning: `token_urlsafe(32)` consumes 32 bytes of entropy and emits 43 characters, so the existing assertion `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` in `test_new_signing_secret_has_prefix_and_length` must be updated to the emitted length, not deleted — deleting it is the "fix by removing the assertion" failure. Preserve the allow side and pin it: the `whsec_` prefix test must still pass, and a new test asserting 1000 generated secrets are pairwise distinct must stay green. Red-prove each clause separately: (1) revert to `random.choice` seeded with `random.seed(0)` and confirm a determinism test (two secrets generated after identical seeding are equal) goes red under `secrets` and green under `random` — that is the assertion that names the defect; (2) truncate the entropy argument to 4 and confirm the length assertion goes red. Fail loudly: `secrets.token_urlsafe` raises rather than degrading if the OS entropy source is unavailable, and no `try`/`except` may convert that into a fallback — an unavailable CSPRNG must abort endpoint creation, not silently produce a weak key. Boundary: existing rows created before this change carry weak secrets and are not repaired by it — ship a one-off rotation for endpoints whose `created_at` precedes the deploy, and say so in `docs/webhooks.md`.

### Critical: `verify` compares signatures with `==` (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: Python's `str.__eq__` short-circuits on the first differing byte, so the comparison of an HMAC digest leaks its matching prefix length through timing.
What breaks in production: An attacker with network access to any consumer that calls `verify` (this is the reference implementation we ship and the one our own inbound paths would reuse) can recover a valid signature byte-by-byte and replay or forge events without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)` — `hmac` is already imported. Preserve the allow side and pin it: `test_verify_accepts_signature_produced_by_sign` must stay green, and a new test must confirm a signature differing only in its final character is rejected (the case `==` would also reject, so it is not the proof — see the mutation below). Red-prove each clause separately: (1) revert to `==` and confirm a test asserting `verify` is called through `hmac.compare_digest` (patch `hmac.compare_digest` with a spy and assert it was invoked with both operands) goes red — a pure behavioural test cannot discriminate the two implementations, so the assertion must be on the call path, per RT5; (2) swap the operand order to `compare_digest(signature, expected)` and confirm the spy test still names both operands. Fail loudly: `compare_digest` raises `TypeError` on a non-`str`/`bytes` argument — do not wrap it in an `except TypeError: return False`, because a caller passing a JSON object where a signature string was expected must abort rather than be told "signature invalid". Boundary and tie: operands of unequal length are rejected by `compare_digest` without leaking the length differential; a `signature` of `""` and an `expected` of `""` cannot both occur because `sign` always emits `sha256=` plus 64 hex characters.

### Critical: the signature is computed over different bytes than the request body carries (R40)
File: `app/webhooks/delivery.py` — `send_once`, `sign(endpoint.signing_secret, delivery.payload)` paired with `client.post(..., json=delivery.payload, ...)`
What is wrong: `signing.serialize` produces `json.dumps(payload, sort_keys=True)` with Python's default `", "`/`": "` separators, while httpx serializes the `json=` argument itself with its own encoder and its own separator and key-ordering choices, so the HMAC is taken over a byte string that is not the one transmitted.
What breaks in production: Every customer who implements verification as `docs/webhooks.md` instructs — HMAC over the raw request body — computes a different digest than we sent, so every delivery fails verification and the entire webhook product silently does not work for any integrator who actually checks signatures; the retry loop then hammers each endpoint five times per event.
Fix: Serialize once and send those exact bytes: in `send_once`, compute `body = serialize(delivery.payload).encode()`, sign that byte string, and post it with `client.post(endpoint.url, content=body, headers=headers)` where `headers` still sets `Content-Type: application/json` — never `json=`, which re-serializes. Codebase-awareness evidence: `signing.serialize` already exists in this diff and is the only canonicalizer; `send_once` currently bypasses it for the wire path while `sign` uses it for the MAC path, which is the divergence. Preserve the allow side and pin it: `test_send_once_posts_the_signed_payload`'s existing assertions (`content-type` is `application/json`, the decoded body's `type` is `invoice.paid`) must stay green — the fix must not turn the body into a form encoding or a string-wrapped blob. Red-prove each clause separately, and this requires a NEW test the current suite does not contain: (1) a round-trip test that takes `captured["body"]` verbatim from the `MockTransport` handler and asserts `hmac.new(SECRET.encode(), captured["body"], sha256).hexdigest()` equals the hex in the captured `X-Acme-Signature` header — mutate `serialize` to drop `sort_keys` and confirm this test goes red for a payload with out-of-order keys, which requires the fixture payload to have at least two keys in non-sorted order; (2) revert `content=body` back to `json=delivery.payload` and confirm the same test goes red. Fail loudly: if `serialize` raises on a non-JSON-serializable payload the delivery must be marked `failed_permanent` with that reason, not silently posted unsigned. Boundary and tie: two payloads that differ only in key order must produce the identical MAC after canonicalization, and the test fixture must contain such a pair so the tie is exercised rather than assumed.

### Critical: the signature does not cover the timestamp, so the documented replay window enforces nothing
File: `app/webhooks/signing.py` — `sign`, `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `docs/webhooks.md` states the signature is "the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`", but the implementation MACs the body alone and returns the timestamp as an unauthenticated sidecar; `verify` correspondingly discards the timestamp (`_, expected = sign(...)`) and never checks freshness.
What breaks in production: A captured request can be replayed indefinitely by rewriting `X-Acme-Timestamp` to the current second — the signature still validates — so the five-minute window the doc tells customers is "what stops a captured request from being replayed" stops nothing, and every consumer that trusts the doc is exposed to unlimited replay of, for example, an `invoice.paid` event.
Fix: Make the signed message the documented one — in `sign`, `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` where `body` is the exact bytes posted (shared with the fix above); change `verify(secret, payload, signature)` to `verify(secret, timestamp, body, signature, tolerance_seconds=300)`, which recomputes the MAC over `f"{timestamp}."` plus `body` and rejects when `abs(int(time.time()) - int(timestamp)) > tolerance_seconds`. Preserve the allow side and pin it: a request signed one second ago must still verify, and a request signed exactly 300 seconds ago must verify (see boundary below) — a fix that rejects everything passes the replay test alone. Red-prove each clause separately: (1) keep the timestamp out of the MAC input and confirm a test that signs at T, rewrites the header to T+3600, and asserts `verify` is False goes red; (2) remove the tolerance check and confirm a test that signs at T-3600 with the ORIGINAL timestamp header intact asserts False and goes red; (3) note that clause (1) and clause (2) need separate mutations because either alone leaves the other's test green. Fail loudly: a `timestamp` that is absent or non-integer must raise or return False explicitly with a distinct log line — "the header could not be parsed" must not be spelled the same as "the signature did not match". Boundary and tie: define the window as inclusive (`<= 300` accepts) and state it in `docs/webhooks.md`; a timestamp in the future beyond the same tolerance must also be rejected, since clock-skew symmetry is what makes an attacker-chosen future timestamp useless.

### Critical: endpoint URLs are unvalidated against internal targets and the client follows redirects (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `run_worker`, `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The check accepts any scheme merely beginning with `http` (`httpx://`, `httpfoo://` pass), accepts plaintext `http://` despite `docs/webhooks.md` stating "Only `https://` URLs are accepted", and applies no host restriction at all, while `follow_redirects=True` means even a host that passed validation can bounce the request to a different one at delivery time.
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://localhost:6379/` and our worker issues authenticated-looking POSTs from inside the production network, returning the response body to the attacker through `WebhookDelivery.response_body`; with `follow_redirects=True` even a correctly-validated `https://evil.example.com` can 302 to the metadata service on every attempt.
Fix: Validate at the schema layer, not in the handler body — change `EndpointIn.url` from `str` to `pydantic.HttpUrl` with `allowed_schemes={"https"}` (or a validator that rejects any scheme other than exactly `https`), and add an egress check that resolves the hostname and rejects any address in a private, loopback, link-local, or unique-local range using `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`. Set `follow_redirects=False` on the `httpx.AsyncClient` in `run_worker` and treat a 3xx as a non-2xx failure so it flows through the existing retry/permanent-failure path. Because DNS can be re-resolved between validation and delivery (the check-then-use interval), re-apply the address check inside the worker at connect time rather than relying on the create-time check alone. Preserve the allow side and pin it: a genuine public `https://hooks.example.com/acme` must still validate at create time and still deliver in `test_send_once_posts_the_signed_payload`, whose `FakeEndpoint.url` is already `https://` — a fix that rejects all hosts passes every SSRF test and ships a dead feature. Red-prove each clause separately: (1) restore `scheme.startswith("http")` and confirm a test posting `{"url": "http://hooks.example.com/x"}` and asserting 422 goes red; (2) remove the private-address check and confirm a test posting `http s://metadata.internal` resolving to `169.254.169.254` and asserting 422 goes red; (3) set `follow_redirects=True` again and confirm a `MockTransport` test whose handler returns a 302 to a private address asserts the delivery was not followed and goes red. Fail loudly: a hostname that does not resolve, or a resolver error, must reject the registration with an explicit "could not resolve" message — an unresolvable host must not be treated as "not private, therefore allowed". Boundary and tie: a host resolving to BOTH a public and a private address is rejected (any private address in the answer set disqualifies it), and `https` on a non-443 port is allowed since the constraint is the address, not the port.

### Critical: the migration's status CHECK constraint does not contain the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint permits `'failed'`, but `app/webhooks/models.py`'s `STATUSES` tuple and `app/webhooks/delivery.py`'s `deliver` both use `'failed_permanent'`, so the status vocabulary is written in three places and one of them disagrees.
What breaks in production: The first delivery to exhaust its attempts raises a `CheckViolation` inside `_finish`, so the row never leaves `in_flight`, the exception propagates out of `deliver` into `asyncio.gather`, and the worker's batch aborts — the permanent-failure path, which is the one that runs whenever a customer endpoint is down, is the path that cannot commit.
Fix: Change the migration's constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))`, and remove the duplication that allowed the drift: have the constraint generated from, or asserted against, `models.STATUSES` — `STATUSES` is currently defined and never referenced anywhere in the diff, which is exactly the dead-shared-constant shape (R2). Add a test that opens a session, asserts `set(STATUSES)` equals the set parsed out of the live constraint definition (`pg_get_constraintdef`), and fails when either side changes alone. Preserve the allow side and pin it: inserting each of the four legal statuses must still succeed — a fix that drops the CHECK entirely makes every failing test pass and removes the only thing that would have caught this. Red-prove each clause separately: (1) revert the constraint to `'failed'` and confirm the constraint-vs-`STATUSES` test goes red naming the missing member; (2) delete `'in_flight'` from `STATUSES` and confirm the same test goes red naming the extra member — the two mutations must redden different assertions (missing-from-DB vs missing-from-code), not one combined "sets differ". Fail loudly: if the constraint cannot be read (no DB in the test environment), the test must error, not skip — a skipped constraint test is the "examined nothing spelled the same as found nothing" failure. Boundary: `'failed'` is not a legal value in either direction after this change; if any row already carries it, the migration must `UPDATE ... SET status = 'failed_permanent' WHERE status = 'failed'` before adding the constraint.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `app/webhooks/delivery.py`'s `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index permits only one row per `event_id` across the whole table.
What breaks in production: The moment an organization registers a second endpoint (or a second endpoint subscribes to the same event type), the `session.add_all(rows)` flush raises a `UniqueViolation`, which `app/events/dispatcher.py` catches and downgrades to `log.warning` — so ALL webhooks for that event are dropped for ALL endpoints including the first, silently, with no retry and no dead-letter row.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the pair that actually expresses the at-least-once/deduplicate-on-`event_id` contract stated in `docs/webhooks.md` — one attempt record per endpoint per event. Preserve the allow side and pin it: enqueuing one event for three endpoints must produce three rows (a test asserting `enqueue_for_event(...) == 3` and three persisted rows), and re-enqueuing the same `(endpoint_id, event_id)` must still be rejected — a fix that simply drops the unique index passes the fan-out test and removes the idempotency guarantee the doc promises. Red-prove each clause separately: (1) revert to the single-column index and confirm the three-endpoint fan-out test goes red with a `UniqueViolation`; (2) drop the index entirely and confirm a duplicate-enqueue test (same endpoint, same event, called twice) goes red by finding two rows where it asserts one. Fail loudly: `enqueue_for_event` must let an integrity error propagate to a distinct log level and a dead-letter record rather than returning a count — see the dispatcher swallowing finding below. Boundary and tie: two different endpoints of the SAME org with the SAME event id are two rows and must both persist; the same endpoint retried for the same event is one row and the second insert must be rejected, not upserted, so a retry does not reset `attempts`.

### Critical: `time.sleep` inside an async coroutine blocks the event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async def` and is scheduled via `asyncio.gather`, but its retry pause uses the blocking `time.sleep` rather than `await asyncio.sleep`, so the pause stops the entire event loop instead of yielding it.
What breaks in production: With a batch of up to `BATCH_SIZE = 100` deliveries gathered together, a single failing endpoint freezes every other in-flight delivery and any other coroutine in the process for up to 2+4+8+16 = 30 seconds, and because the gathered tasks then execute serially rather than concurrently the worker's throughput collapses to one endpoint at a time while the 60-second Redis lock expires underneath it.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)`; `asyncio` is already imported at the top of this file. The same class of blocking call is present elsewhere in the diff and must be addressed with it: `enqueue_for_event` and `_claim_batch` are `async def` but perform synchronous `session_scope()` DB work with no thread offload, and `_finish` is a synchronous DB function called from within `async def deliver` — each blocks the loop for the duration of its query. Run these through `asyncio.to_thread(...)` (or an async session), or document explicitly that the worker process runs nothing else. Preserve the allow side and pin it: the retry delays must remain the documented 2/4/8/16 seconds — `test_backoff_grows_exponentially` must stay green, and the fix must not shorten the waits to make the test fast, which would be repairing the symptom by deleting the behaviour. Red-prove each clause separately: (1) restore `time.sleep` and confirm a test that gathers two `deliver` calls against a `MockTransport` returning 500 (with `BASE_DELAY_SECONDS` patched down and an `asyncio.wait_for` timeout bounding the test so a blocked loop surfaces as a failure rather than a hang) goes red on wall-clock elapsed time; (2) remove the thread offload from `_claim_batch` and confirm a test asserting the loop remains responsive during a claim goes red. Fail loudly: bound the whole `deliver` call with `asyncio.wait_for` so a hung endpoint that neither errors nor completes surfaces as a timed-out delivery rather than an indefinitely `in_flight` row. Boundary: the final attempt (`attempt >= MAX_ATTEMPTS`) must not sleep at all before returning — the current code already returns before the sleep, and that must be preserved.

### Major: `deliver` and `_claim_batch` use ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` outside the `with`), `deliver` (`endpoint = session.get(...)` then `endpoint.url` / `endpoint.signing_secret` outside the `with`)
What is wrong: Both functions carry SQLAlchemy instances out of their `session_scope()` block and then read attributes from them, whereas every other DB use in this diff (`enqueue_for_event`, `_finish`, the three route handlers) completes all attribute access inside the block.
What breaks in production: Under SQLAlchemy's default `expire_on_commit=True`, every attribute of a committed instance is expired at commit, so the first read outside the block (`row.status` is written inside, but `delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.url`, `endpoint.signing_secret` are all read outside) raises `DetachedInstanceError` and the worker cannot deliver anything at all. What would close this: `session_scope` being configured with `expire_on_commit=False`; that configuration is not in this diff, so if it holds, this reduces to a durability concern rather than an outright failure.
Fix: Do not hand ORM instances across the session boundary — have `_claim_batch` return plain value objects (a dataclass or dict of `id`, `endpoint_id`, `payload`, `attempts`) built inside the block, and have `deliver` read the endpoint's `url` and `signing_secret` into locals inside its own block before use. Preserve the allow side and pin it: `_claim_batch` must still mark the claimed rows `in_flight` and still return them in `next_attempt_at` order, and `deliver` must still post to the endpoint's real URL — a fix that returns ids only and re-queries per row inside `send_once` reintroduces a per-delivery round trip and loses the batch claim's atomicity, so state which you chose. Red-prove each clause separately: (1) an integration test (real session, not a `FakeDelivery`) that calls `_claim_batch` and then reads every field `deliver` reads — revert to returning ORM rows and confirm it goes red with `DetachedInstanceError` rather than passing; (2) revert `deliver`'s endpoint locals and confirm the same test's endpoint-field read goes red. Note that neither mutation can be proven against the current suite, whose `FakeEndpoint` and `FakeDelivery` are plain classes with no session at all — that mock/reality gap is a separate finding below. Fail loudly: if `session.get(m.WebhookEndpoint, delivery.endpoint_id)` returns `None` (the endpoint was deleted between enqueue and delivery), `deliver` must mark the delivery `failed_permanent` with that reason, not raise `AttributeError` on `endpoint.signing_secret`. Boundary: a delivery claimed in the same transaction in which its endpoint is deactivated must be treated as claimed-then-cancelled, and the code must state which side wins.

### Major: `_acquire_lock` is a non-atomic check-then-set and the release is unowned
File: `app/webhooks/delivery.py` — `_acquire_lock` (`get` then `set` then `expire`) and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: Three separate defects in one primitive — the `get`/`set` pair has a race window in which two workers both observe an empty key and both proceed; `set` and `expire` are two round trips, so a crash between them leaves a key with no TTL; and the release deletes `LOCK_KEY` unconditionally with no ownership token.
What breaks in production: Two workers claim overlapping batches and every customer receives duplicate webhooks; a crash between `set` and `expire` wedges the entire delivery pipeline permanently with no recovery path short of manual Redis surgery; and because a batch of 100 deliveries with up to 30 seconds of retry sleeps each routinely exceeds the 60-second TTL, worker A's `finally` regularly deletes the lock worker B is actively holding.
Fix: Make acquisition a single atomic operation with the TTL attached — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and make release conditional on the token via a Lua `CAS`-delete (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`), so a worker can only release the lock it holds. Because the batch can outlive the TTL, add a heartbeat that extends the TTL while the token still matches, and abandon the batch when the extension fails. Preserve the allow side and pin it: a single worker with no contender must still acquire the lock on the first poll and must still release it so the next iteration acquires again — a fix that never acquires passes every mutual-exclusion test and stops all delivery. Red-prove each clause separately: (1) revert to `get`-then-`set` and confirm a test launching two `_acquire_lock` coroutines concurrently against a fake Redis that yields between calls asserts exactly one `True` and goes red; (2) drop `ex=60` and confirm a TTL-presence assertion goes red; (3) replace the CAS-delete with an unconditional `delete` and confirm a test where worker B holds the lock and worker A releases asserts B's token survives and goes red. Fail loudly: a Redis connection error in `_acquire_lock` must return `False` and log at error level — it must never fall through to "no key found, therefore acquire", which is the fail-open direction. Boundary and tie: `nx=True` decides the tie at the server, so exactly one of two simultaneous callers wins; a token that has expired and been re-acquired by another worker must cause the original holder's CAS-delete to be a no-op rather than an error.

### Major: `in_flight` is a non-terminal state with no exit on the crash path (R38)
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_claim_batch`'s filter `status == "pending"`
What is wrong: A row transitions to `in_flight` at claim time and leaves it only via `_finish` on the success or exhausted-attempts path; there is no reaper, no timeout, and the claim query selects only `pending`, so any row whose worker crashes, is killed, or loses the lock mid-batch is unreachable forever.
What breaks in production: A single worker restart during a batch permanently strands up to 100 customer deliveries in `in_flight`, and because `docs/webhooks.md` promises at-least-once delivery, those events are lost with no operator-visible signal beyond a stuck row count.
Fix: Add a claim deadline — set `next_attempt_at = now + lease_seconds` alongside `status = "in_flight"` at claim time, and widen `_claim_batch`'s filter to `(status == "pending" OR (status == "in_flight" AND next_attempt_at <= now)) AND next_attempt_at <= now`, so an expired lease is reclaimed by the next poll. Bound `attempts` so a row that is reclaimed repeatedly still reaches `failed_permanent` rather than cycling forever. Preserve the allow side and pin it: a delivery currently being worked on (lease not yet expired) must NOT be reclaimed by a second poll — a fix that reclaims everything on every poll turns at-least-once into at-least-N-times. Red-prove each clause separately: (1) revert the lease write and confirm a test that claims a batch, simulates a crash, advances the clock past the lease, and asserts the row is re-claimed goes red; (2) remove the `next_attempt_at <= now` term from the reclaim branch and confirm a test asserting a fresh `in_flight` row is not reclaimed goes red. Fail loudly: a row whose `attempts` exceeds `MAX_ATTEMPTS` while still `in_flight` must be moved to `failed_permanent` with an explicit "lease expired without result" detail, never left for the next poll. Boundary and tie: a lease expiring at exactly `now` is reclaimable (inclusive `<=`), and two workers reaching the same expired row are separated by the row-level lock the claim `UPDATE` takes — state that the claim must be a single `UPDATE ... RETURNING` rather than a `SELECT` followed by attribute assignment, which is what the current code does and which has no such protection.

### Major: the persisted retry schedule is never used — retries are an in-process loop
File: `app/webhooks/delivery.py` — `deliver`'s `while True` loop, and `m.WebhookDelivery.next_attempt_at` / `attempts` which no code path ever advances between attempts
What is wrong: The schema and the claim query are built around rescheduling (`next_attempt_at`, `attempts`, `status = 'pending'`), but `deliver` instead loops in memory with sleeps and writes the row exactly once, at the terminal outcome, so the persisted retry machinery is dead.
What breaks in production: Any process restart, deploy, or OOM kill during the up-to-30-second retry loop loses every in-progress retry with no record of how many attempts were made, and `list_deliveries`' documented "when the next attempt is scheduled" field is a lie — `next_attempt_at` never moves after enqueue.
Fix: Replace the loop with a single attempt per claim: on a retryable failure, write `status = "pending"`, `attempts = attempt`, `next_attempt_at = now + backoff_for(attempt)` and return; on success or exhaustion, call `_finish` as today. `run_worker`'s poll loop then performs the retries by re-claiming due rows, which is what `_claim_batch`'s `next_attempt_at <= now` filter was already written for. Codebase-awareness evidence: `backoff_for` already exists and is already exported and tested; this fix moves its result into the row rather than into a sleep, and does not reimplement it. Preserve the allow side and pin it: the observable retry cadence must remain 2/4/8/16 seconds and the cap must remain 5 attempts — `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` must both stay green. Red-prove each clause separately: (1) revert to the in-process loop and confirm a test that fails a delivery once, asserts `attempts == 1` and `status == "pending"` and `next_attempt_at` advanced by 2 seconds, goes red; (2) drop the `attempts = attempt` write and confirm a test that fails five successive claims and asserts `failed_permanent` goes red by looping forever — bound that test with a timeout so the missing increment surfaces as a failure rather than a hang. Fail loudly: a delivery whose endpoint row has disappeared must be marked `failed_permanent`, not rescheduled indefinitely. Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal condition (the fifth attempt is made, the sixth is not), which matches the current code and the doc's "at most 5 times"; two rows with an identical `next_attempt_at` are both due and the claim's ordering must break the tie on the primary key — see the ordering finding below.
