### Critical: the signature is computed over different bytes than the request body carries
File: `app/webhooks/delivery.py` — `send_once`, with `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (spaces after separators, keys sorted) while the request body is produced independently by `client.post(..., json=delivery.payload)`, which httpx serializes with `separators=(",", ":")` and insertion order, so the digest in `X-Acme-Signature` is an HMAC of a byte string that never goes on the wire.
What breaks in production: every receiver that follows `docs/webhooks.md` and HMACs the raw request body computes a different digest and rejects 100% of deliveries, and the failures look like customer misconfiguration rather than a producer bug.
Fix: make the serialized body the single source of both the signature and the request — in `send_once` compute `body = signing.serialize(delivery.payload).encode()` once, sign that exact `bytes` object, and send it with `client.post(endpoint.url, content=body, headers=headers)`; change `sign()` to take `bytes` so no second encoding can be introduced, and delete the `json=` path so the divergence cannot reappear. Preserve the properties that made the current code useful: `Content-Type: application/json` stays on the request, and `serialize()` keeps `sort_keys=True` so a receiver that re-serializes for logging still gets a stable form. Pin the allow side and the deny side: one test asserts `signing.verify_raw(SECRET, captured["body"], captured["headers"][SIGNATURE_HEADER])` is True for the byte string the MockTransport actually received (allow), and one asserts it is False after flipping a single byte of `captured["body"]` (deny). Red-prove each clause separately by running it: (i) revert `content=body` to `json=delivery.payload` — the allow test must red naming a signature mismatch; (ii) revert `sign()` to re-serialize internally — the same test must red; (iii) drop the byte-flip mutation's effect by comparing prefixes instead of the whole digest — the deny test must red. Fail loudly rather than silently when the check cannot run: if `serialize()` raises (non-JSON-serializable payload), `send_once` must raise a named `PayloadNotSerializable` and `deliver` must mark the row `failed_permanent` with that reason — an unencodable payload must not be spelled the same way as a delivered one. Boundary and tie: the signed region is exactly the bytes of the request body with no trailing newline, and two payloads that serialize to identical bytes intentionally produce identical signatures — the timestamp (see next finding) is what separates them.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window cannot be enforced
File: `app/webhooks/signing.py` — `sign`
What is wrong: the docs state the signature is `HMAC-SHA256("{timestamp}.{raw_request_body}")` and instruct receivers to reject requests older than five minutes, but `sign()` MACs the body alone and returns the timestamp as an unauthenticated side value.
What breaks in production: an attacker who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to the current second, so the five-minute window customers are told is their replay defence provides none (R49: the claim is strictly stronger than the implementation).
Fix: change the signed input to `f"{timestamp}.".encode() + body` exactly as documented, keep `timestamp` in the returned tuple, and add `MAX_SKEW_SECONDS = 300` plus a `verify(secret, timestamp, body, signature)` that rejects when `abs(now - int(timestamp)) > MAX_SKEW_SECONDS` before any digest work. Do not fix this by relaxing the doc — the five-minute window is the control customers were told to rely on, and it must survive the change. Pair deny with allow: a signature produced at `now` still verifies (allow), a valid signature replayed at `now + 301` is rejected (deny), and a valid body whose `timestamp` header was changed to `now` is rejected (deny) — that last case is the one that is green today. Red-prove each clause by execution: (i) drop the `f"{timestamp}."` prefix — the header-rewrite test reds; (ii) widen `MAX_SKEW_SECONDS` to 10**9 — the replay test reds; (iii) hardcode `verify` to return True — the wrong-secret test reds. Fail loudly: a non-numeric or absent `X-Acme-Timestamp` must raise/return a named `MalformedTimestamp` rejection, never fall through to a digest comparison, so "could not evaluate the window" is not spelled like "inside the window". Boundary and tie: skew is rejected at strictly greater than 300 seconds (exactly 300 is accepted, in both directions), and two requests sharing one timestamp second are both accepted — the window is a bound on age, not a uniqueness claim, so receivers still need the per-event dedup key (see the payload finding below).

### Critical: HMAC comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the recomputed digest is compared to the caller-supplied signature with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: an attacker who can submit signatures against this helper recovers a valid digest byte-by-byte from response-time differences, defeating signature verification wherever this helper is used to authenticate an inbound request.
Fix: replace with `hmac.compare_digest(expected, signature)`, comparing the full `sha256=<hex>` strings after an explicit length/prefix check that itself uses a fixed-shape rejection. Do not "fix" it by removing `verify` from the module — it is the reference implementation the docs point customers at, and it must keep returning a bool for the same arguments. Pair deny with allow: a signature produced by `sign` for the same secret and body still returns True; a signature from another secret returns False; a signature of the correct length that differs only in the last hex character returns False. Red-prove each by execution: (i) revert to `==` — add a timing assertion or, more reliably, assert `verify.__code__.co_names` contains `compare_digest` in a guard test and mutate to see it red; (ii) delete the length check — feed a truncated signature and assert the rejection is still False rather than an exception; (iii) hardcode True — all three deny cases red. Fail loudly: a `signature` that is not a `str` of the expected `sha256=` + 64 hex form is rejected by a named branch, not by an exception escaping to the caller as a 500. Boundary and tie: signatures of unequal length are rejected before comparison (never passed to `compare_digest` where the length itself leaks), and two distinct secrets that produce the same digest for one body is a collision the scheme already treats as impossible — no tie-break is needed.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is 32 characters drawn with `random.choice`, i.e. the Mersenne Twister, whose internal state is recoverable from a modest amount of observed output and which is not seeded for unpredictability.
What breaks in production: an attacker who obtains their own endpoint's secret (they legitimately get one) and can observe or provoke further generations can reconstruct the generator state and forge signatures for other organizations' endpoints, turning the whole signing scheme into decoration.
Fix: use `secrets.token_urlsafe(32)` prefixed with `SECRET_PREFIX` and delete the `random`/`string` imports and `_ALPHABET` so the weak path cannot be called again; rename `SECRET_BYTES` to `SECRET_ENTROPY_BYTES` since the current name claims bytes while the code counted characters. Preserve what made the old value useful: the `whsec_` prefix and a fixed, documented length, because `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` and customer key-management tooling both key off them — update that test's length expectation to the new encoded length rather than dropping the assertion. Pair deny with allow: a generated secret still starts with `SECRET_PREFIX` and has the documented length (allow), and 1000 generations produce 1000 distinct values (deny of the degenerate constant implementation). Red-prove each by execution: (i) revert to `random.choice` — a guard test asserting the module does not import `random` reds; (ii) return a fixed constant — the uniqueness test reds; (iii) drop the prefix — the prefix test reds. Fail loudly: if `secrets` is unavailable the module must fail at import with a named error rather than falling back to `random`. Boundary and tie: 32 bytes of entropy is the floor, not the target — state it as `>= 32` in the test so a later widening does not red, and two endpoints colliding on a secret is a 2^-256 event the uniqueness test treats as a failure, not as an accepted tie.

### Critical: the deliveries endpoint is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters on `endpoint_id` only, while every sibling route in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) constrains rows by `user.org_id` — the tenancy predicate was not propagated to the new route (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` values and read another organization's delivery history — event types, event ids, delivery status and upstream response codes — a cross-tenant data leak reachable with a single incrementing integer.
Fix: join through `WebhookEndpoint` and filter on both, e.g. `.join(m.WebhookEndpoint, m.WebhookDelivery.endpoint_id == m.WebhookEndpoint.id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)`, and return 404 (not 403) when the endpoint exists but belongs to another org so the route does not confirm existence. Do not fix this by removing the endpoint-id path parameter — per-endpoint inspection is the feature. Pair deny with allow: a caller listing deliveries for an endpoint their own org owns still receives the rows (allow — this is the case a naive "always 404" fix silently kills), and a caller passing another org's endpoint id receives 404 with an empty body (deny). Per RT8, the deny test must assert the absence of the data, not only the status: assert the response body contains no delivery ids at all. Red-prove each clause by execution: (i) delete the `org_id` filter — the cross-tenant test reds; (ii) change the join to an outer join — the cross-tenant test reds; (iii) hardcode 404 — the same-org test reds. Fail loudly: an `endpoint_id` that does not exist at all and one that exists in another org must take the same named 404 branch, and a session whose `user.org_id` is None must raise rather than match all rows. Boundary and tie: an endpoint whose `active` flag is False still belongs to its org and remains listable by that org; ownership is decided by `org_id` equality only, with no tie possible since an endpoint has exactly one owner. Cross-cutting check performed: the tenancy predicate is present in the other three routes in this file and absent only here; `enqueue_for_event` filters by `org_id` correctly.

### Critical: the unique index on `event_id` makes any org with two endpoints receive nothing
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so the second row of the same event violates the unique index, and `session.add_all` fails as a unit.
What breaks in production: the moment an organization registers a second endpoint, every event insert raises `IntegrityError`, the dispatcher swallows it as a warning, and **all** webhook deliveries for that org stop — including the ones for the first endpoint, which would otherwise have worked.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the code actually needs (one delivery per endpoint per event) and which also gives the idempotency the docs promise. Do not fix this by dropping uniqueness entirely — the index is what stops a re-dispatched event from double-delivering, and that property must be preserved. Pair deny with allow: an event fanning out to two endpoints of one org inserts two rows and both are delivered (allow), and re-running `enqueue_for_event` with the same `event_id` for the same endpoint inserts no second row (deny) — implement the deny with `ON CONFLICT DO NOTHING` at the insert so the retry path is not an exception path. Red-prove each by execution against a real Postgres, not a mock: (i) revert to the single-column index — the two-endpoint test reds with a unique violation; (ii) drop the index — the re-dispatch test reds with two rows; (iii) remove `ON CONFLICT DO NOTHING` — the re-dispatch test reds with an `IntegrityError` instead of a clean no-op. Fail loudly: an `IntegrityError` that is not the expected conflict must propagate rather than be counted as a successful enqueue. Boundary and tie: `event_id` is unique per event row so `(endpoint_id, event_id)` is total; two endpoints of the same org sharing an `event_id` is the legitimate case the new index must admit.

### Critical: the migration's CHECK constraint rejects the terminal status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the code's terminal failure status is `failed_permanent` (also the spelling in `models.py::STATUSES`) but the constraint only admits `failed` — the enum spelling diverges across the three places it is written (R2/R3, and R40 producer-vs-strict-consumer).
What breaks in production: the final attempt of every failing delivery raises a constraint violation inside `_finish`, so the row never leaves `in_flight`, the retry budget is silently voided, and the operator-facing delivery list shows a permanently in-flight row for every dead endpoint.
Fix: make the constraint read from one definition — set `STATUSES` in `app/webhooks/models.py` as the single source, generate the `CHECK` list from it in the migration (or, minimally, correct the migration to `'failed_permanent'`), and replace the four string literals in `delivery.py` with references to that constant. Do not fix by dropping the CHECK — the constraint is what makes an unknown status impossible, and that must survive. Pair deny with allow: a delivery that exhausts `MAX_ATTEMPTS` is persisted with status `failed_permanent` and is readable back (allow), and an attempt to persist `"failed"` or any other unlisted string is rejected by the database (deny). Red-prove each by execution against a real database: (i) revert the migration spelling — the exhaustion test reds with a check violation; (ii) point `delivery.py` at a literal `"failed"` — the same test reds; (iii) remove the CHECK — the unknown-status test reds. Fail loudly: `_finish` must raise on an unknown status rather than writing it, and must not swallow the database error. Boundary and tie: `STATUSES` is the closed set — adding a member requires a migration in the same PR, and the transition `in_flight -> failed_permanent` is terminal with no further writes permitted.

### Critical: the signing secret is readable back from the list endpoint, contradicting the documented contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns it for every endpoint, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (R49: the doc declares an enforceable boundary the code does not implement).
What breaks in production: any principal with read access to settings can harvest every endpoint secret for the org and forge signed events into the customer's system, and customers who trusted the doc will not have rotated a secret they believe was never re-exposed.
Fix: remove `signing_secret` from `to_dict()` and add a separate `to_dict_with_secret()` used only by the 201 response of `create_webhook_endpoint`; add a `POST /webhook-endpoints/{id}/rotate-secret` route as the sole other place a secret is returned. Do not fix by editing the doc to match the code — the "write-once secret" property is the security claim the whole scheme rests on, and the code must be brought up to it. Pair deny with allow: the create response still contains the secret exactly once so a customer can store it (allow — a blanket redaction breaks onboarding), and the list response for the same endpoint contains no `signing_secret` key at all (deny). Red-prove each by execution: (i) re-add `signing_secret` to `to_dict()` — the list test reds; (ii) strip it from the create path — the create test reds; (iii) assert on `!= None` instead of key absence — mutate the value to `""` and confirm the test reds only under the key-absence form. Fail loudly: a serializer that encounters an endpoint row with no secret must raise, not emit `null`, so "secret missing" is not spelled like "secret withheld". Boundary and tie: exactly one response body in the API's lifetime carries the secret per creation or rotation; a second read of the same endpoint by the same caller returns the redacted shape. Cross-cutting check performed: `WebhookDelivery.to_dict` carries no secret material, and `list_api_keys` already returns only a `prefix` — this route is the sole deviation from a redaction pattern the file otherwise follows.

### Critical: endpoint URL validation admits SSRF, and redirect following widens it
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, and `app/webhooks/delivery.py` — `run_worker`'s `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the check is `parsed.scheme.startswith("http")`, which accepts `httpfoo://`, accepts plain `http://` despite the doc's "Only `https://` URLs are accepted", and constrains the host not at all — so `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:6379/` is a valid endpoint, and `follow_redirects=True` lets even a public host redirect the worker to those targets after validation passed (RS3 boundary validation; RS5 untrusted parameter fed to a privileged primitive).
What breaks in production: any authenticated customer turns the delivery worker into a request forwarder inside the production network, reading cloud metadata credentials or driving internal services, with the response body helpfully persisted into `response_body` and readable through the deliveries endpoint.
Fix: validate at the schema level with a Pydantic `HttpUrl`-derived field constrained to `scheme == "https"` (exact equality, not `startswith`), resolve the host at creation and at each send, and reject any address in loopback / link-local / RFC 1918 / unique-local / multicast / reserved ranges via `ipaddress.ip_address(...).is_global`; set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure with a named reason. Do not fix by validating only at creation — DNS rebinding makes the creation-time answer worthless, so the check must also run against the address actually connected to (an `httpx` transport hook or a pre-connect resolve). Preserve what made the feature useful: a legitimate public HTTPS endpoint on a non-standard port must still be accepted. Pair deny with allow: `https://hooks.example.com:8443/acme` is accepted and delivered to (allow), and each of `http://hooks.example.com`, `httpfoo://x`, `https://127.0.0.1/`, `https://169.254.169.254/`, `https://[::1]/`, and a public host whose DNS answer is `10.0.0.5` are rejected at creation with 422 (deny). Red-prove each clause by execution: (i) revert to `startswith("http")` — the `httpfoo://` and `http://` cases red; (ii) delete the `is_global` check — the metadata-address case reds; (iii) restore `follow_redirects=True` — a MockTransport returning a 302 to `http://169.254.169.254/` must red a test asserting no second request was issued. Fail loudly: a hostname that does not resolve, or a resolver error, must produce a named 422 `UnresolvableEndpointHost` rather than being admitted on the grounds that no bad address was seen — "could not check" must not be spelled like "checked and clean". Boundary and tie: the scheme comparison is exact string equality against `"https"`, the port is unrestricted, and a host resolving to both a global and a private address is rejected (any private answer denies).

### Critical: the delivered body carries no event id or type, so the documented dedup key does not exist on the wire
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`payload=payload`) and `send_once` (`json=delivery.payload`), against `docs/webhooks.md` "delivery is at-least-once, so deduplicate on `event_id`"
What is wrong: the row stores and the request sends the bare `envelope.payload`, which contains no `event_id` and no `event_type`; the only place those fields appear in a payload is the test's `FakeDelivery.payload = {"id": "evt_1", "type": "invoice.paid", ...}`, a fixture that invents a wire shape production never produces (R40 producer/consumer shape, RT1 mock-reality divergence).
What breaks in production: receivers cannot deduplicate at-least-once deliveries as instructed and cannot route by event type without inspecting the payload's ad-hoc contents, so a retried delivery is processed twice — for `invoice.paid` that means a duplicate fulfilment.
Fix: send an envelope rather than the raw payload — `{"id": f"evt_{delivery.event_id}", "type": delivery.event_type, "created_at": <iso8601>, "data": delivery.payload}` — built by one function in `delivery.py` used by both the signer and the sender, and update `docs/webhooks.md` to name the field receivers must dedupe on (`id`). Do not fix by changing the doc to say "dedupe on whatever your payload contains" — at-least-once delivery without a stable idempotency key on the wire is the defect, not the documentation. Pair deny with allow: a delivered request body parses to an object whose `id` and `type` match the delivery row and whose `data` equals the original `envelope.payload` byte-for-byte (allow), and two sends of the same delivery row produce the identical `id` (deny of a per-send random id). Red-prove each by execution: (i) revert to `json=delivery.payload` — the envelope test reds on the missing `id`; (ii) build `id` from `uuid4()` — the stable-id test reds; (iii) nest `data` one level deeper — the byte-equality assertion on `data` reds. Fail loudly: an envelope that cannot be built because `event_type` is null must raise a named error and mark the delivery `failed_permanent`, never send a partial envelope. Boundary and tie: `id` is unique per `(endpoint_id, event_id)` pair — the same event fanned to two endpoints carries the same `id`, which is correct because the receivers are different systems, and a receiver seeing that `id` twice must treat the second as a duplicate.

### Critical: `time.sleep` inside the async delivery loop blocks the whole worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: a synchronous sleep is called from a coroutine, so it blocks the event loop rather than yielding — and it is reached from `asyncio.gather` over a batch of up to `BATCH_SIZE = 100` deliveries.
What breaks in production: one endpoint that times out stalls every other delivery in the batch for up to 2+4+8+16 = 30 seconds serially, and because the batch can hold 100 such rows the run exceeds the 60-second lock TTL, after which a second worker claims the same rows and delivers them again.
Fix: replace with `await asyncio.sleep(delay)`, and remove the in-process retry loop entirely in favour of rescheduling (see the next finding) so the worker never holds a coroutine open across a backoff. Preserve the behaviour that made the loop useful: the retry budget of `MAX_ATTEMPTS` and the exponential shape of `backoff_for` must still be observed end to end. Pair deny with allow: a delivery that succeeds on the first attempt completes without any sleep (allow), and a batch containing one slow endpoint still completes the other 99 deliveries within the poll interval (deny of the blocking implementation) — assert the second by measuring that the fast deliveries' completion timestamps are not ordered behind the slow one. Red-prove each by execution: (i) revert to `time.sleep` — the concurrency test reds because the fast deliveries complete only after the slow one; (ii) drop the `MAX_ATTEMPTS` bound — a bounded test with an always-failing endpoint must red rather than hang (bound the loop in the test so the mutation reds instead of never terminating); (iii) make `backoff_for` constant — the growth test reds. Fail loudly: a negative or non-finite delay must raise rather than be passed to `asyncio.sleep`. Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal comparison, so attempt 5 is the last one performed and there is no sleep after it; two deliveries scheduled for the same instant run concurrently with no ordering guarantee between them.

### Critical: ORM rows are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after `with session_scope()` exits), `deliver` (`endpoint` fetched in a closed session, then `endpoint.url`/`endpoint.signing_secret` read in `send_once`), and `run_worker` (`deliver(client, d)` over the returned rows)
What is wrong: `session_scope()` commits and closes on exit, so with SQLAlchemy's default expire-on-commit every attribute access on those instances triggers a refresh against a dead session.
What breaks in production: the first real batch raises `DetachedInstanceError` before any HTTP request is made, so the worker delivers nothing at all and — because `asyncio.gather` has no `return_exceptions` — the exception escapes `run_worker` and kills the loop.
Fix: stop passing ORM instances across session boundaries — have `_claim_batch` return plain dataclasses or tuples of the fields the send path needs (`id`, `endpoint_id`, `attempts`, `payload`, `event_id`, `event_type`, `url`, `signing_secret`) selected in one query that joins `WebhookEndpoint`, and have `deliver` take that value object. Do not fix by setting `expire_on_commit=False` globally — that hides the boundary rather than removing it and leaves stale rows in every other caller of `session_scope`. Preserve the behaviour that made the current shape useful: the claim must still mark rows `in_flight` inside the same transaction that reads them. Pair deny with allow: a batch of two claimable rows is delivered end to end against a MockTransport with no session touched after the claim (allow), and an attempt to access an attribute not selected into the value object fails at type-check/attribute time rather than by silently re-querying (deny). Red-prove each by execution: (i) return ORM instances again — the end-to-end test reds with `DetachedInstanceError`; (ii) drop `endpoint` from the join — the send test reds on a missing `url`; (iii) move the `in_flight` write outside the claim transaction — a concurrency test asserting a row is claimed once reds. Fail loudly: a claimed row whose endpoint row is missing (deleted between enqueue and claim) must be marked `failed_permanent` with a named reason, not skipped silently. Boundary and tie: rows are claimed where `next_attempt_at <= now` inclusive, and two rows with the same `next_attempt_at` are both claimable — see the ordering finding for the tie-break.

### Critical: the dispatch lock is non-atomic to acquire, released without ownership, and can wedge with no TTL
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: the acquire is a `get` followed by a separate `set` (two workers both observe an empty key and both proceed), the TTL is a third round trip so a crash between `set` and `expire` leaves a key that never expires, and the release deletes the key unconditionally even when the current worker no longer owns it after a TTL expiry (R5 read-then-write race; R38 persisted fail-closed wedge with no reset path).
What breaks in production: the common case is duplicate deliveries of every event in a batch — for `invoice.paid` that is a duplicate customer-side fulfilment — and the tail case is a permanently held lock that stops all webhook delivery until an operator manually deletes a Redis key nobody has documented.
Fix: acquire with a single atomic `SET key <random-token> NX EX 60`, release with a compare-and-delete Lua script that deletes only when the stored value equals this worker's token, and renew the TTL while a batch is in flight instead of assuming 60 seconds is enough. Add an operator-facing reset path — a documented command and a metric on lock age — so the wedge is recoverable and observable. Do not fix by removing the lock — mutual exclusion is what stops the duplicate deliveries; and do not fix by shortening the TTL alone, which trades a wedge for more frequent double-claims. Pair deny with allow: a single worker acquires, delivers, and releases, and the next poll acquires again (allow — a compare-and-delete bug that never releases fails exactly here), and two concurrently started workers result in exactly one claiming the batch (deny). Red-prove each by execution against a real Redis: (i) revert to `get`-then-`set` — the two-worker test reds with both claiming; (ii) revert to an unconditional `delete` — a test where worker A's TTL expires and worker B acquires must red when A's release removes B's lock; (iii) drop the `EX` — a test asserting `TTL(key) > 0` immediately after acquire reds. Fail loudly: a Redis error during acquire must be treated as "not acquired" and logged at error with the exception, never as acquired; a release that finds a foreign token must log at error rather than proceed quietly. Boundary and tie: the lock is held for at most the TTL and renewed at half of it; when two workers race, the one whose `SET NX` returns OK wins and the loser sleeps `poll_interval` rather than retrying immediately.

### Critical: the test suite cannot fail on any of the signing defects above
File: `tests/webhooks/test_delivery.py` — `FakeEndpoint`, `FakeDelivery`, `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`

### Minor (question): is there a shared rate limiter the three new routes should be registered with?
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: none of the three new routes carries a rate-limit dependency, but neither do the pre-existing `get_profile` and `list_api_keys` in the same file, so the diff gives no evidence either way about whether limiting is applied at a layer outside it (RS2, recorded as a question per Finding Floor clause 2).
What breaks in production: if limiting is per-route rather than global, `create_webhook_endpoint` is an unauthenticated-cost amplifier and `list_deliveries` is a cheap way to sweep the deliveries table.
What would close it: pointing at the middleware or gateway that applies a limit to `/v1/settings/*`; if there is none, this becomes a Major with the same fix shape as the endpoint-cap finding.

### Minor: `SECRET_BYTES` names bytes but counts characters

## Cross-cutting verification performed

- **Tenancy predicate** (`org_id == user.org_id`): present in `get_profile`, `list_api_keys`, `list_webhook_endpoints`, and in `enqueue_for_event`; absent only in `list_deliveries` — reported Critical.
- **Timezone-aware `now`**: `models._now()`, `_claim_batch`, `_finish` and `dispatch` all use aware UTC; `enqueue_for_event`'s `datetime.utcnow()` is the single divergent site — reported Major.
- **Status literals**: three independent spellings (`models.STATUSES`, the four literals in `delivery.py`, the migration `CHECK`), diverging at `failed_permanent`/`failed` — reported Critical.
- **Credential comparison**: `verify`'s `==` is the only credential comparison in the diff; no second unguarded site exists.
- **Timestamp column type**: all four datetime columns in the migration are `TIMESTAMP` while all four ORM columns declare `timezone=True` — the mismatch is uniform, so the fix must touch all four.
- **Secret exposure**: `WebhookEndpoint.to_dict` is the only serializer emitting secret material; `WebhookDelivery.to_dict` and `list_api_keys` are clean.

## Codebase awareness

- `app/webhooks/models.py` already provides `_now()` (aware UTC) and `STATUSES`; `delivery.py` reimplements both inline — `datetime.now(timezone.utc)` at three sites, `datetime.utcnow()` at a fourth, and four bare status strings. The remedies above adopt the existing helpers rather than adding new ones (R1).
- `app/webhooks/signing.py` already provides `serialize()` as the canonical body encoder, and `send_once` bypasses it by handing the dict to httpx's own encoder — the duplication is the direct cause of the top Critical, which is precisely R1's "adopting the shared helper is necessary and not sufficient" case inverted: the helper exists and the call site declined to use it.
- `app/api/routes/settings.py` already demonstrates the redaction pattern (`list_api_keys` returns `prefix`, never the key) and the tenancy pattern; both new-route findings are failures to reuse a pattern already present in the same file, not requests for new infrastructure.
