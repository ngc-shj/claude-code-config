### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters on `WebhookDelivery.endpoint_id == endpoint_id` only, with no join back to `WebhookEndpoint.org_id == user.org_id`, while both siblings in the same file (`list_api_keys`, `list_webhook_endpoints`) do filter on `user.org_id` — the tenancy predicate was propagated to two of three new/adjacent readers (R3).
What breaks in production: any authenticated user can walk `endpoint_id` 1..N and read other organizations' delivery rows, and `WebhookDelivery.to_dict` plus `response_body` expose those tenants' event types, statuses and upstream response text.
Fix: in `list_deliveries`, join `WebhookEndpoint` and filter `WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id`; when the join yields no endpoint row, raise `HTTPException(404)` rather than returning `[]`, so "endpoint not yours" and "endpoint has no deliveries" are not spelled the same. Pin both sides: a test where the owning user reads an endpoint with 2 deliveries and gets 2 rows (the allow case — a fix that always 404s must fail this), and a test where a second org's user gets 404 and, per RT8, that no delivery row is serialized in the body. Red-prove each clause separately by execution: (i) delete the `org_id` predicate → the cross-tenant test must red naming the leaked row count; (ii) delete the `WebhookEndpoint.id == endpoint_id` predicate → the owner test must red on rows belonging to a second endpoint of the same org. Boundary and tie: an endpoint that exists but is `active=False` still belongs to the org and MUST remain readable (deliveries for a deactivated endpoint are exactly what an operator inspects); an `endpoint_id` that does not exist at all returns the same 404 as one owned by another org, so existence is not disclosed. Preserve the existing behaviour the fix must not delete: the `limit`, the ordering, and the `to_dict` shape stay as they are.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister PRNG, which is seeded from process state and fully reconstructible from ~624 observed outputs — this is key material for the HMAC that authenticates every outbound event.
What breaks in production: an attacker who registers a handful of endpoints in their own org observes enough generator output to recover the internal state, predict the secrets minted for other tenants, and forge signed `invoice.paid` events into those tenants' systems.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`; drop `random`, `string` and `_ALPHABET` if unused elsewhere), and rename `SECRET_BYTES` to mean what it now is — bytes of entropy, not characters. Keep the allow side pinned: the existing `test_new_signing_secret_has_prefix_and_length` must be updated to the new length rather than deleted, and a test asserting 1000 generated secrets are pairwise distinct must still pass — a fix that returns a constant satisfies "uses `secrets`" and must fail here. Red-prove per clause: (i) revert to `random.choice` with a fixed `random.seed(0)` in the test process → a test asserting two secrets generated across two seeded runs differ must red; (ii) drop the prefix → the prefix assertion reds. Fail loudly rather than silently weaken: do not add a `try: import secrets / except: random` fallback — if `secrets` is unavailable the process must not start. Boundary and tie: `SECRET_BYTES = 32` is the floor, not a target; state that a secret shorter than 32 bytes is rejected at construction, and that two endpoints of the same org must never share a secret (each `create_webhook_endpoint` call mints its own).

### Critical: signature comparison in `verify` is not constant-time (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==` on `str`, which short-circuits on the first differing byte, and no constant-time helper appears on the line.
What breaks in production: `verify` is the reference implementation shipped for this signing scheme and is exercised by the tests as the contract, so any internal or customer-side use of it leaks the expected digest byte-by-byte through response timing, letting an attacker forge a signature without the secret.
Fix: `return hmac.compare_digest(expected, signature)` (`hmac` is already imported), and guard the shape first — if `signature` does not start with `"sha256="` or is not the expected length, return `False` before comparing, so a malformed header cannot vary the comparison length. Pair deny with allow: `test_verify_accepts_signature_produced_by_sign` must still pass (a `return False` body satisfies "constant-time" and must fail this test), alongside the existing wrong-secret rejection. Red-prove per clause by execution: (i) swap `compare_digest` back to `==` → a test that asserts `verify.__code__.co_names` contains `compare_digest`, or a lint rule pinned to this file, reds; (ii) remove the prefix/length pre-check → a test passing `signature="sha256="` must red. Fail loudly: a `secret` of `""` or `None` must raise, not return `False`, so "could not check" is not spelled like "did not match". Boundary and tie: state that the comparison is over the full `sha256=<64 hex>` string including the prefix, and that a signature equal in every byte except case is rejected (hex is emitted lowercase).

### Critical: the MAC is computed over bytes that are neither transmitted nor documented
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` and does not include the timestamp, while `send_once` transmits the body via `client.post(json=delivery.payload)`, which httpx serializes with its own separators and without `sort_keys` — and `docs/webhooks.md` tells customers the preimage is `"{timestamp}.{raw_request_body}"`.
What breaks in production: every customer who implements the documented verification rejects every delivery (three different byte strings are in play — signed, sent, documented), and because the timestamp is outside the MAC an attacker who captures one request can replay it forever by rewriting `X-Acme-Timestamp`, so the "five minute window" the docs sell as replay protection does not exist.
Fix: make the signed bytes and the wire bytes the same object. In `signing.sign`, take the already-serialized body: `def sign(secret: str, body: bytes) -> tuple[str, str]` computing `timestamp = str(int(time.time()))` and `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`; in `send_once`, compute `body = serialize(delivery.payload).encode()` once, pass it to `sign`, and send it with `client.post(endpoint.url, content=body, headers=headers)` so the transmitted bytes are the signed bytes; update `verify` to the same `(secret, body, timestamp, signature)` signature. Preserve what made the feature useful: `serialize`'s `sort_keys=True` stays, `Content-Type: application/json` stays, and the header names are unchanged — customers already integrated against the header names must not be broken. Pin the allow side: a round-trip test that captures the ACTUAL request bytes from `httpx.MockTransport` and feeds them through `verify` must pass (R40's actual-producer-output-through-actual-consumer requirement, not two mocked shapes). Red-prove each clause separately: (i) revert `content=body` to `json=delivery.payload` → the round-trip test reds because the transmitted bytes differ from the signed ones; (ii) drop `f"{timestamp}."` from the preimage → a test that verifies with a *different* timestamp and expects `False` reds; (iii) reorder the payload keys before serializing → the sort-keys test reds. Fail loudly: if `serialize` raises on a non-JSON-serializable payload the delivery must be marked `failed_permanent` with the exception text, never sent unsigned. Boundary and tie: define the replay window as `abs(now - timestamp) <= 300` seconds — exactly 300 is accepted, 301 rejected — and state it in `docs/webhooks.md` beside the corrected preimage; two deliveries signed in the same second are independent and neither invalidates the other.

### Critical: the signing secret is returned on every endpoint read
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict` includes `"signing_secret": self.signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so the secret is served on every `GET /v1/settings/webhook-endpoints` — directly contradicting `docs/webhooks.md`, which states the create response "is the only place the signing secret appears — it cannot be read back afterwards" (R29: a documented control the change does not implement; R49: a claim stronger than the implementation).
What breaks in production: the HMAC key for every endpoint is copied into browser caches, proxy logs, CDN entries and any support tooling that dumps the settings API, and the customer-side rotation story the docs promise is false because the secret was never write-once.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` build its 201 body explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the value returned by `new_signing_secret()` (bind it to a local before constructing the row) — one reveal, at creation, with no path from a read handler to the column. Pair deny with allow: a test asserting the 201 body DOES contain `signing_secret` (a fix that strips it everywhere breaks the only way a customer can ever configure verification, and must fail this test) alongside a test asserting `GET /webhook-endpoints` contains no key matching `secret` for any element. Red-prove each clause: (i) re-add the key to `to_dict` → the list-response test reds naming the leaked key; (ii) drop it from the create body → the 201 test reds. Fail loudly: the list assertion must iterate the parsed JSON keys and fail on an empty endpoint list rather than passing vacuously — "no endpoints to check" must not read as "no secrets leaked". Boundary and tie: state that a re-registration of the same URL mints a NEW secret and does not return the old one, and that the column stays populated (the delivery path still reads it server-side).

### Critical: any http(s) host is accepted and redirects are followed — SSRF into the internal network
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://169.254.169.254/…`, `http://127.0.0.1:6379/`, any RFC1918 address and even a scheme like `httpx://`, while the worker's client is built with `follow_redirects=True`, so an endpoint that passes any host check at creation can 302 the signed POST anywhere; `docs/webhooks.md` claims "Only `https://` URLs are accepted" (RS3 Critical — an unvalidated externally-supplied value reaching an interpreter, here the HTTP client's connection target).
What breaks in production: a tenant registers an internal URL and the worker POSTs attacker-chosen JSON to cloud metadata, an unauthenticated Redis, or an internal admin API from a trusted network position, and returns the response body to that tenant through `list_deliveries`.
Fix: validate at the schema boundary, not in the handler body — give `EndpointIn.url` a `pydantic.HttpUrl`-typed field plus a validator that rejects any scheme other than `https`, resolves the host and rejects addresses in loopback / link-local / private / unique-local / reserved ranges via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`, and caps the URL at 2048 chars; set `follow_redirects=False` on the worker's `AsyncClient` and treat a 3xx as a permanent failure with the `Location` recorded; re-check the resolved address at delivery time (DNS rebinding makes a creation-time check alone insufficient — the name resolved at creation is not the address connected to later, R51). Preserve the feature: customer endpoints on public hosts, including non-standard ports and paths with query strings, must still be accepted — pin that with a test registering `https://hooks.example.com:8443/acme?x=1` and expecting 201, so a validator that rejects everything fails. Red-prove each clause separately: (i) drop the scheme check → `http://hooks.example.com` must red with 422; (ii) drop the private-range check → `https://localhost/x` and `https://169.254.169.254/` must red; (iii) set `follow_redirects=True` again → a `MockTransport` test returning 302 to `http://127.0.0.1/` must red on the delivery being marked delivered. Fail loudly: DNS resolution failure at creation is a 422 that names the host, never a silent accept. Boundary and tie: `0.0.0.0` and IPv6-mapped IPv4 (`::ffff:127.0.0.1`) fall on the reject side, a public address that also appears in a customer's own private range is judged on the resolved address only, and the docs must be corrected to match whichever set is enforced.

### Critical: the migration's CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", …)`
What is wrong: the schema allows `'failed'` while `app/webhooks/models.py:STATUSES` and `deliver`'s exhaustion branch both use `'failed_permanent'` — the enum spelling diverges across the storage boundary (R40 / R3), and `STATUSES` itself is declared but never enforced anywhere.
What breaks in production: every delivery that exhausts its 5 attempts raises a check-constraint violation inside `_finish`, the update rolls back, the row stays `in_flight` forever, and the failure is invisible because `deliver` returns immediately after the failed `_finish`.
Fix: change the migration's CHECK list to exactly `('pending', 'in_flight', 'delivered', 'failed_permanent')` — matching `models.STATUSES` — and make `STATUSES` the single source by declaring the column as `Column(Enum(*STATUSES, name="webhook_delivery_status"))` or by adding a test that reads the CHECK list out of `information_schema` and asserts set equality with `STATUSES`, so the two cannot drift again. Pair the sides: the drift test must PASS on the corrected pair (an assertion that always fails is not a guard), and an integration test must show a delivery that exhausts attempts ends with `status == "failed_permanent"` and a non-null `response_status` or `response_body`. Red-prove per clause: (i) revert one spelling in the migration → the set-equality test reds naming both sets; (ii) change `_finish`'s exhaustion argument to `"failed"` → the exhaustion integration test reds on the persisted value. Fail loudly: if `information_schema` returns no CHECK for the column, the test must fail as "constraint not found", not pass. Boundary and tie: `attempts == MAX_ATTEMPTS` is the terminal case and `attempts == MAX_ATTEMPTS - 1` still retries; a row already `delivered` must never be moved to `failed_permanent` by a late-arriving `_finish`.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint for the same `event_id`, so the unique index permits at most one delivery per event across the whole table, and the second row of the same `add_all` violates it.
What breaks in production: any organization with two subscribed endpoints gets an `IntegrityError` on the whole insert, the dispatcher's blanket `except Exception` downgrades it to a `log.warning`, and NO endpoint receives the event — a total, silent loss of every webhook for those tenants.
Fix: replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — which is also the idempotency key `enqueue_for_event` needs if `dispatch` is ever retried — and add `ON CONFLICT DO NOTHING` semantics to the insert (`session.execute(insert(...).on_conflict_do_nothing(index_elements=["endpoint_id", "event_id"]))`) so a re-dispatch of the same event does not raise. Pin both directions: a test with one org and two active endpoints asserting `enqueue_for_event` returns 2 and persists 2 rows (the allow case — dropping the unique index entirely also passes any "no error" assertion, so this must be paired), and a test calling `enqueue_for_event` twice with the same `event_id` asserting the row count stays 2. Red-prove per clause: (i) restore the single-column unique index → the two-endpoint test reds with an integrity error; (ii) remove the conflict clause → the double-call test reds. Fail loudly: `enqueue_for_event` must stop swallowing — see the dispatcher finding below — so a constraint failure surfaces rather than being logged at warning. Boundary and tie: an endpoint deactivated between the two calls contributes no new row and its existing row is untouched; two endpoints of DIFFERENT orgs that somehow share an `event_id` are distinct rows under the composite key.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is fanned out with `asyncio.gather`, but the retry backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, and `time` is imported for exactly this call.
What breaks in production: a single failing endpoint freezes the whole loop for 2+4+8+16 = 30 seconds per delivery, and because a batch is 100 rows the "concurrent" gather degrades to strictly serial — one bad customer stalls every other tenant's webhooks, and any API served on the same loop stops responding.
Fix: `await asyncio.sleep(delay)` (`asyncio` is already imported); remove the now-unused `time` import from `delivery.py` (`signing.py` keeps its own). Do not fix this by deleting the backoff — the delay between attempts is the behaviour that protects a struggling customer endpoint and must be preserved. Pair the sides: a test asserting the delay actually elapses (patch `asyncio.sleep` with an async spy and assert it was awaited with 2, 4, 8, 16 in order — a fix that removes the sleep entirely must fail this), and a concurrency test running two `deliver` calls where one fails and one succeeds, asserting the successful one completes while the other is still backing off. Red-prove per clause: (i) restore `time.sleep` → the concurrency test reds because the second delivery cannot finish first; (ii) drop the `await` on `asyncio.sleep` → the spy test reds on a never-awaited coroutine (run with `-W error::RuntimeWarning`). Fail loudly: an unexpected exception type inside the retry loop must mark the row rather than escape silently. Boundary and tie: the sleep happens only when `attempt < MAX_ATTEMPTS` — the fifth attempt does not sleep before returning — and two deliveries scheduled for the same instant both proceed rather than one starving.

### Critical: ORM instances are used after their session closes
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (reads `endpoint.signing_secret` / `endpoint.url` after the `with` block)
What is wrong: both functions load ORM objects inside a `session_scope()` block and then read attributes after the block has exited; the same module's `_finish` demonstrates the correct pattern by re-fetching by id inside a fresh scope, so the codebase-aware path already exists in this diff and is not used here.
What breaks in production: under SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and the detached instance raises `DetachedInstanceError` on first access — `run_worker` dies on its very first non-empty batch, and because the batch rows were already flipped to `in_flight` they are never reclaimed.
Fix: stop passing ORM objects across scope boundaries. Have `_claim_batch` return plain data — a list of `dataclass`/`dict` snapshots of `(id, endpoint_id, attempts, payload)` built inside the scope — and have `deliver` take that snapshot plus an endpoint snapshot loaded in its own `with session_scope()` block, mirroring `_finish`. Pin both sides: a test that runs `_claim_batch` against a real (or SQLite-backed) session and then reads every field of every returned item OUTSIDE the scope must pass (an implementation that returns empty lists also never raises, so pair it with an assertion that the claimed count equals the seeded count), and an assertion that the claimed rows are persisted as `in_flight` when read back in a new session. Red-prove per clause: (i) return the ORM rows again → the outside-the-scope field read reds with `DetachedInstanceError`; (ii) remove the `row.status = "in_flight"` write → the read-back assertion reds. Fail loudly: if the endpoint referenced by a claimed delivery no longer exists, `deliver` must mark the row `failed_permanent` with a named reason, not `AttributeError` on `None` (`session.get` returns `None`). Boundary and tie: a batch of exactly `BATCH_SIZE` rows is fully claimed and the `BATCH_SIZE + 1`-th is left for the next poll; two workers claiming the same instant must not both receive the same row — see the locking finding.

### Critical: the signature test cannot fail when the signature is wrong
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: the test asserts only that the header *starts with* `sha256=` and that the timestamp is digits — it never recomputes the MAC over `captured["body"]`, so it passes unchanged under the preimage defect above, and `FakeEndpoint`/`FakeDelivery` are hand-written doubles whose fields diverge from the real `WebhookEndpoint`/`WebhookDelivery` (no `endpoint_id`, no `status`), which is the RT1/RT9 divergence that hides a security control.
What breaks in production: the suite is green while every customer's verification fails and replay protection does not exist — the one test that looks like signing coverage is structurally blind to the only thing that matters.
Fix: assert the control, not its shape — in the handler capture `request.content` and `request.headers`, then assert `signing.verify(SECRET, captured["body"], captured["headers"][signing.TIMESTAMP_HEADER], captured["headers"][signing.SIGNATURE_HEADER])` is `True`, using the production `verify` (RT5: the test call path must include the production primitive) and the real `WebhookEndpoint`/`WebhookDelivery` classes constructed unsaved rather than bespoke fakes. Pair deny with allow: the positive case above, plus a negative case that flips one byte of `captured["body"]` and asserts `verify` returns `False` — a `verify` that returns `True` unconditionally must fail the second, and one that returns `False` unconditionally must fail the first. Red-prove each clause by execution, one mutation each: (i) change `send_once` to sign a constant string → the positive assertion reds; (ii) change `verify` to `return True` → the tampered-body assertion reds; (iii) drop the timestamp from the preimage → a test verifying with a shifted timestamp reds. Fail loudly: if the signature header is absent the test must fail with "header missing", not `KeyError` swallowed by a `.get(...)` default. Boundary and tie: keep the existing content-type and payload assertions — they are not what is wrong here and must not be deleted in the rewrite; a payload whose keys are supplied in a different order must produce the identical signature (the `sort_keys` contract), and that is a third case worth pinning.

### Major: the `webhooks_enabled` kill switch is added and never consulted
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: the migration introduces an org-level flag that defaults to disabled, but no code in the diff reads it — `enqueue_for_event` filters only on `org_id` and `active`, so the declared capability has no backing path (R41) and the control fails open.
What breaks in production: every organization receives webhooks the moment an endpoint exists, including the ones the flag says are switched off, so the operator lever intended to stop a runaway or compromised integration does nothing.
Fix: join the flag into the endpoint query — `.join(Organization, Organization.id == m.WebhookEndpoint.org_id).filter(Organization.webhooks_enabled.is_(True), …)` — and mirror it in `create_webhook_endpoint` by returning `403` when the caller's org has the flag off, so registration and delivery agree. Pair deny with allow: an org with the flag ON and one active endpoint must still get exactly 1 delivery row (a fix that filters everything out also "respects the flag"), and an org with the flag OFF must get 0 rows AND, per RT8, no outbound POST attempted. Red-prove per clause: (i) drop the `webhooks_enabled` predicate → the flag-off test reds on a non-zero row count; (ii) drop the `active` predicate → an inactive-endpoint test reds. Fail loudly: if the organization row is missing, `enqueue_for_event` must raise rather than treat the absent flag as enabled. Boundary and tie: the flag is evaluated at enqueue time, not at send time — a flag turned off after enqueue does not retroactively cancel already-queued rows, and that must be stated in `docs/webhooks.md`.

### Major: `in_flight` is a non-terminal state with no reset path, and retry progress is never persisted
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`
What is wrong: `_claim_batch` flips rows to `in_flight` and only `_finish` moves them out, while `deliver` holds all retry state in the local `attempt` variable and never updates `attempts` or `next_attempt_at` between tries; `_claim_batch` selects `status == "pending"` only, so nothing ever reclaims an `in_flight` row (R38 case 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: a worker restart, deploy, OOM kill, or any of the crashes above during the 30-second retry window strands every claimed delivery in `in_flight` permanently — the events are silently never delivered and no query surfaces them.
Fix: persist each attempt instead of holding it in memory — after a failed attempt write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next poll pick the row up, so the retry state machine lives in the row rather than in a coroutine; add a reclaim predicate to `_claim_batch` (`or (status == "in_flight" and updated_at < now - LEASE_SECONDS)`) with an explicit `LEASE_SECONDS` constant, and `updated_at` set at claim time. Pair deny with allow: a test that a row still inside its lease is NOT reclaimed by a second worker (a reclaim that fires immediately re-delivers everything twice and must fail this), and a test that a row whose lease has expired IS reclaimed with `attempts` preserved. Red-prove per clause: (i) remove the lease predicate → the expired-lease reclaim test reds; (ii) remove the `updated_at` write at claim → the within-lease test reds because every row looks stale; (iii) revert to the in-memory loop → a test that kills the coroutine mid-retry and asserts the row is re-claimable reds. Fail loudly: a row that exceeds `MAX_ATTEMPTS` through reclaims must land in `failed_permanent`, never loop forever. Boundary and tie: `updated_at == now - LEASE_SECONDS` exactly is treated as expired (reclaimable), and two workers whose leases expire in the same instant must not both claim — that requires `FOR UPDATE SKIP LOCKED` on the claim query, which also removes the dependence on the Redis lock.

### Major: the Redis lock is non-atomic, can lose its TTL, and is deleted by whoever finishes first
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act race so two workers can both acquire; `set` followed by a separate `expire` leaves a window where a crash between the two calls yields a lock with no TTL; and the `finally` deletes the key unconditionally, including a lock a *different* worker acquired after this one's TTL lapsed.
What breaks in production: either duplicate concurrent delivery of every batch (double-charging a customer's downstream automation) or, after an ill-timed crash, a permanently held lock that stops all webhook delivery until someone deletes the key by hand — a persisted fail-closed wedge with no reset path (R38 case 2).
Fix: make acquisition a single atomic operation with a fencing token — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`) so only the holder releases; drop the separate `expire`. Pair deny with allow: a test that a second `_acquire_lock` while the first is held returns `False` (the deny side), and a test that after the holder releases, the next `_acquire_lock` returns `True` (the allow side — a lock that never releases passes the first test alone). Red-prove per clause: (i) revert to `get`-then-`set` → a test issuing two concurrent acquisitions and asserting exactly one succeeds reds; (ii) drop `ex=` → a test asserting `ttl(LOCK_KEY) > 0` immediately after acquire reds; (iii) replace the compare-and-delete with a plain `delete` → a test where worker B holds the lock and worker A's `finally` runs, asserting B still holds it, reds. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise and the worker must log an error and back off — an exception swallowed into `False` is indistinguishable from "someone else holds it" and hides an outage. Boundary and tie: `LOCK_TTL_SECONDS` must exceed the worst-case batch duration (`BATCH_SIZE` × the full retry ladder) or the lease expires mid-batch — state the computed value; two workers presenting the same token is impossible by construction and must be asserted.
