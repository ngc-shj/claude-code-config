# Review — F10-webhooks.diff (second pass: what the prior reviewers missed)

Routing: digest → R41/R32 (§1), R41 (§2), R57/R38 (§3), R2 (§8), R47/R49 (§6), R3 cross-cutting (§7, §10). Targeted extraction was conclusive; `common-rules.md` was not read in full.

### Critical: nothing starts `run_worker`, so no delivery is ever attempted
File: `app/webhooks/delivery.py` — `run_worker` (and the diff's file list as a whole)
What is wrong: `app/webhooks/delivery.py` is a `new file`, so no pre-existing supervisor, entrypoint or config can reference `run_worker`, and the only importer added in this change — `app/events/dispatcher.py` — imports the module solely to call `enqueue_for_event`, while `tests/webhooks/test_delivery.py` imports `MAX_ATTEMPTS, backoff_for, send_once` and never the worker.
What breaks in production: `enqueue_for_event` inserts rows that stay `status='pending'` forever while the API answers 201 and `GET .../deliveries` shows a queue that never drains — the whole documented retry pipeline is dead on arrival, and the failure is silent because the enqueue path reports success.
Fix: add the runtime entry point in this change — a `python -m app.webhooks.worker` module (or an app-lifespan task) that calls `asyncio.run(run_worker())` — plus the process definition that launches it, and have `run_worker` emit a declared ready signal (`log.info("webhook worker ready poll_interval=%s batch=%s", ...)`) once the Redis and DB connections have been opened, before entering the loop. Preserve the existing in-process `enqueue_for_event` call path — the fix is to add the consumer, not to move enqueueing into the worker. Pin both directions with a boot smoke test in the deployment shape: (a) with Redis and Postgres reachable, the ready line appears and a seeded `pending` row reaches `delivered`; (b) with `REDIS_URL` pointing at a closed port, the process exits non-zero with a message naming Redis — "could not connect" must not be spelled the same as "nothing due". Red-prove each separately: delete the entry-point registration → (a) times out waiting for the ready line; make the ready log unconditional (emitted before the connections open) → (b) passes while the process is broken, which is the mutation that must red. Boundary: state what two replicas do at startup — with the claim fixed per the finding below, both may run and each claims a disjoint id set; a delivery due at exactly `next_attempt_at == now()` is claimed by whichever replica commits first, never both.

### Major: an endpoint can never be deactivated, and `deliver` never re-checks `active`
File: `app/webhooks/models.py` — `WebhookEndpoint.active`; `app/api/routes/settings.py` — the three new routes; `app/webhooks/delivery.py` — `deliver`
What is wrong: `active` is written only by `create_webhook_endpoint`, which hardcodes `active=True`, the change adds no PATCH/DELETE route, and `deliver` re-loads the endpoint with `session.get(m.WebhookEndpoint, delivery.endpoint_id)` and reads `endpoint.url` / `endpoint.signing_secret` without consulting `active` — the flag is honoured only in `enqueue_for_event`.
What breaks in production: a customer whose endpoint URL or signing secret is compromised has no way to stop delivery, and even an operator flipping the column by hand does not stop rows already enqueued or the up-to-5-attempt loop already running, so payloads keep flowing to an endpoint the owner has revoked.
Fix: add `DELETE /v1/settings/webhook-endpoints/{endpoint_id}` that loads the row with the same `org_id == user.org_id` predicate `list_webhook_endpoints` already uses (reuse that filter — do not add a second tenancy idiom) and sets `active=False`; and in `deliver`, after the `session.get`, add `if endpoint is None or not endpoint.active: _finish(delivery.id, "failed_permanent", attempt, None, "endpoint disabled"); return`, repeating the `active` read at the top of each retry iteration so a deactivation mid-retry stops the next attempt. Preserve the current behaviour for live endpoints: an `active` endpoint must still deliver, and deactivation must not delete delivery history — the listing route is the audit trail. Red-prove separately: (a) delete the route → the revocation test 404s; (b) drop the `active` check in `deliver` → a delivery whose endpoint was deactivated after claim still POSTs; (c) drop the per-iteration re-read → a deactivation between attempt 1 and 2 still POSTs. Fail loudly: a `DELETE` for an endpoint id belonging to another org returns 404, and a delivery whose endpoint row is missing terminates as `failed_permanent` rather than being skipped silently. Boundary: an endpoint deactivated exactly between claim and send is not sent (the check runs after the load, before the POST); requests already on the wire are not recalled, and the response is still recorded.

### Major: `_claim_batch` is not an atomic claim — fixing the Redis lock does not stop double delivery
File: `app/webhooks/delivery.py` — `_claim_batch`
What is wrong: the batch is claimed by a plain `SELECT ... WHERE status='pending'` followed by per-row `row.status = "in_flight"`, so the emitted UPDATEs are keyed by primary key with no `WHERE status='pending'` predicate, no `FOR UPDATE SKIP LOCKED`, and no uniqueness constraint in the migration to fall back on — two sessions that read before either commits both claim the same rows.
What breaks in production: two workers (or one worker after the 60s `LOCK_KEY` TTL expires mid-batch, which it can, since a single `deliver` can hold the loop for 2+4+8+16s of sleeps plus five 30s HTTP timeouts) POST the same payload twice; this is a correction to the already-reported lock findings, because replacing `_acquire_lock` with a correct `SET NX EX` still leaves the claim itself racy and still expires while work is in flight.
Fix: delete `LOCK_KEY`, `_acquire_lock` and the `finally: redis_client.delete(LOCK_KEY)` block, and make the database the mutual exclusion: `UPDATE webhook_deliveries SET status='in_flight', attempts = attempts + 1, updated_at = now() WHERE id IN (SELECT id FROM webhook_deliveries WHERE status='pending' AND next_attempt_at <= :now ORDER BY next_attempt_at, id FOR UPDATE SKIP LOCKED LIMIT :batch) RETURNING id`, returning ids (not ORM instances) and re-loading each row inside the delivering transaction. Preserve the batching and the due-time filter — the fix must not degrade to one row per poll, and must not drop the `next_attempt_at <= now` predicate that makes scheduling work. Red-prove each clause separately: remove `SKIP LOCKED` → two concurrent claims return overlapping id sets; remove `AND status='pending'` from the inner select → an `in_flight` row is re-claimed; remove `ORDER BY ... , id` → the tie test below fails. Fail loudly: an empty `RETURNING` set means "nothing due" and must be distinguishable from a DB error, which must propagate rather than be returned as an empty batch. Boundary and tie: `<= :now` claims a delivery due at exactly `now`; rows sharing a `next_attempt_at` are ordered by `id`, giving the total order the claim needs, and each id is returned to exactly one claimer.

### Major: the whole delivery path does synchronous DB I/O inside coroutines, so the 100-way `gather` is serial and the event loop stalls
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `_claim_batch`, `_finish`, `run_worker`
What is wrong: `enqueue_for_event` and `_claim_batch` are `async def` whose entire bodies are a blocking `with session_scope()`, and `_finish` is a plain sync function called from inside `deliver`, which `run_worker` fans out `BATCH_SIZE=100` wide via `asyncio.gather` — none of these ever yield, so the reported `time.sleep` is one instance of a wider pattern rather than the whole of it.
What breaks in production: the gather provides no concurrency at all for the claim/finish halves, and because `dispatch()` awaits `enqueue_for_event` inline, every `invoice.paid` request blocks the API's event loop for the duration of the endpoint query and the fan-out insert.
Fix: keep `session_scope` (it is the codebase's transaction helper — do not introduce a second session idiom) but stop calling it from the loop thread: make `_claim_batch`, `_finish` and the body of `enqueue_for_event` ordinary sync functions and invoke them as `await asyncio.to_thread(...)` from the async callers. Preserve the fan-out: the fix must keep `asyncio.gather` over the batch, since removing the concurrency would also make the symptom disappear without fixing it. Pin both sides: (a) a single delivery still completes end-to-end and writes its terminal row; (b) a test that schedules a 1s-blocking delivery and a concurrent no-op coroutine asserts the no-op completes in well under 1s. Red-prove separately: revert `_finish` to a direct call → (b) reds; revert `enqueue_for_event` to a direct call → the dispatcher-latency assertion reds. Fail loudly: exceptions raised inside `to_thread` must propagate to the caller, not be swallowed into a "no rows" return. Boundary: `asyncio.to_thread`'s default executor is bounded (40 threads by default) while `BATCH_SIZE` is 100 — either lower `BATCH_SIZE` to the pool bound or size the executor explicitly, and say which, because at exactly the bound the excess deliveries queue rather than error.

### Major: the migration indexes neither of the two access paths it creates
File: `migrations/0042_webhook_delivery.sql` — index section
What is wrong: the only indexes created are `idx_webhook_deliveries_status` and `UNIQUE (event_id)`, while `enqueue_for_event` filters `webhook_endpoints` by `org_id`, `list_webhook_endpoints` filters by `org_id`, `list_deliveries` filters by `endpoint_id` and orders by `created_at`, and Postgres does not index the `endpoint_id` foreign key that `ON DELETE CASCADE` must traverse.
What breaks in production: every dispatched `invoice.paid` sequential-scans `webhook_endpoints` inside the request path (blocking it, per the finding above), and both the deliveries listing and any endpoint deletion sequential-scan a table that grows by one row per event per endpoint.
Fix: add `CREATE INDEX idx_webhook_endpoints_org ON webhook_endpoints (org_id) WHERE active;` and `CREATE INDEX idx_webhook_deliveries_endpoint ON webhook_deliveries (endpoint_id, created_at DESC, id DESC);` in the same migration. Preserve write throughput: do not replace the claim-path index work with these — they are additive, and the claim predicate still needs its own covering index. Pin both directions: `EXPLAIN` on the `enqueue_for_event` query and on the `list_deliveries` query must show `Index Scan` after and `Seq Scan` before; inserts and the cascade delete must still succeed. Red-prove separately: drop each index and re-run its own `EXPLAIN` assertion — one mutation per index, reddening a different assertion. Fail loudly: if the `EXPLAIN` assertion runs against an empty table Postgres will prefer a seq scan regardless, so the check must seed enough rows to make the plan meaningful and must error (not skip) when the table is empty. Boundary and tie: the trailing `id DESC` gives `list_deliveries` a total order at equal `created_at`, which is the key the already-reported R57 finding needs, so the two fixes must land together.

### Major: `http://` endpoints are accepted, and the scheme test is a prefix match — the docs promise https-only
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `parsed.scheme.startswith("http")`; `docs/webhooks.md` — "Only `https://` URLs are accepted."
What is wrong: `startswith("http")` admits `http`, and also any scheme merely beginning with those four characters, while the shipped documentation states the control is https-only — a claim strictly stronger than the check (R49), decided on the notation rather than on the resolved scheme (R47).
What breaks in production: a customer registering an `http://` endpoint has every payload and the live `X-Acme-Signature` header transmitted in cleartext, so an on-path observer reads the customer's invoice data and can replay the captured request verbatim.
Fix: replace the condition with `if parsed.scheme != "https" or not parsed.netloc:` and keep the 422 detail aligned to the doc wording ("url must be an https URL"); this is the transport check only — the SSRF/host-allowlist work reported separately is a different predicate and must not be folded into it. Preserve the successful path: the documented `https://hooks.example.com/acme` must still return 201 with the secret in the body. Red-prove each clause separately: revert to `startswith` → the `httpsx://host/x` case passes; drop the `!= "https"` tightening → the `http://host/x` case passes; drop the `netloc` check → `https:///path` passes. Fail loudly: wrap the `urlparse` call so a value it rejects (`ValueError` on a malformed IPv6 literal) returns 422 rather than propagating as a 500 — "could not parse" must deny, not error out ambiguously. Boundary and tie: `urlparse` lower-cases the scheme, so `HTTPS://…` compares equal and is accepted; `https` with an empty `netloc` is rejected; the comparison is exact equality, so no future scheme is admitted by prefix.

### Major: the unchecked `session.get` reported at `_finish` has a second, unreported instance in `deliver`, and `gather` abandons the batch when it raises
File: `app/webhooks/delivery.py` — `deliver` (`endpoint = session.get(...)`) and `run_worker` (`asyncio.gather(*[deliver(client, d) for d in batch])`)
What is wrong: the cross-cutting check on the already-reported "`_finish` dereferences a row it did not confirm exists" finds the identical pattern in `deliver`, where `session.get(m.WebhookEndpoint, delivery.endpoint_id)` may return `None` and is immediately passed to `send_once`, and the `gather` has no `return_exceptions=True`, so the resulting `AttributeError` propagates out of `run_worker`.
What breaks in production: one delivery whose endpoint row was cascade-deleted kills the worker and leaves the other 99 rows of the batch stranded in the non-terminal `in_flight` state, converting a single missing row into a total outage of the pipeline.
Fix: guard both sites in the same change — in `deliver`, `if endpoint is None: _finish(delivery.id, "failed_permanent", delivery.attempts + 1, None, "endpoint deleted"); return`; in `_finish`, `if row is None: log.warning("delivery %s vanished before finish", delivery_id); return`; and pass `return_exceptions=True` to the `gather`, logging each returned exception with its delivery id. Preserve the crash-visibility that the current code accidentally provides: the per-delivery exception must still be logged at `error` with a stack trace, so the fix does not trade a loud outage for a silent one. Pin both sides: (a) a batch containing one orphaned delivery still delivers the other rows and marks the orphan terminal; (b) a batch of healthy rows is unaffected — same count delivered as before. Red-prove separately: remove the `deliver` guard → (a) reds with `AttributeError`; remove `return_exceptions=True` → (a) reds with the sibling rows left `in_flight`; remove the `_finish` guard → the vanished-row test reds. Boundary: a row deleted between the claim and `_finish` takes the log-and-return path, and a row deleted between claim and `deliver` takes the terminal path — neither is retried.

### Major: `STATUSES` is dead, and the status vocabulary is spelled out four times in two different alphabets
File: `app/webhooks/models.py` — `STATUSES`; `app/webhooks/delivery.py` — the `"pending"`/`"in_flight"`/`"delivered"`/`"failed_permanent"` literals; `migrations/0042_webhook_delivery.sql` — the `CHECK` constraint
What is wrong: `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` is declared and referenced by nothing — the model column is `String(20)` with a bare `default="pending"`, `delivery.py` writes bare literals, and the migration re-enumerates the set with `'failed'` instead of `'failed_permanent'`; this duplication is the mechanism behind the already-reported CHECK mismatch, so correcting the SQL string alone leaves four independent copies and the next status added drifts the same way.
What breaks in production: the vocabularies drift again on the next status (`dead_letter`, `cancelled`), and because the CHECK is the only enforcement, the drift surfaces as an `IntegrityError` at write time on the delivery path rather than at review time.
Fix: make `STATUSES` the single source — bind the column to it (`Column(String(20), nullable=False, default="pending")` plus `CheckConstraint(status.in_(STATUSES))` on `__table_args__`), replace the literals in `delivery.py` with module-level names derived from it (`STATUS_PENDING`, `STATUS_IN_FLIGHT`, …), and correct the migration's `CHECK` to the same four values. Confirm meaning-equality before sharing: these four literals name one concept (the delivery lifecycle) and must not be merged with any similarly-spelled constant elsewhere, e.g. `WebhookEndpoint.active`. Preserve the constraint: the fix is to align the CHECK, not to drop it — an unconstrained column would also make the symptom disappear. Pin both sides with one test: every member of `STATUSES` inserts successfully, and the migration's ghost value `'failed'` is rejected by the database. Red-prove separately: revert the migration string → the `failed_permanent` insert reds; delete the model `CheckConstraint` → the `'failed'` rejection reds. Fail loudly: the test must fail, not skip, when the constraint cannot be introspected (table absent, wrong dialect) — "examined nothing" must not read as "found nothing". Boundary: renaming a member requires a migration in the same change, and the test comparing `set(STATUSES)` to the constraint's parsed value list is what ties the two together.

### Minor: the signing-secret test pins the character/byte defect, so the CSPRNG fix will red it
File: `tests/webhooks/test_delivery.py` — `test_new_signing_secret_has_prefix_and_length`
What is wrong: the assertion `len(secret) == len(signing.SECRET_PREFIX) + signing.SECRET_BYTES` holds only because `new_signing_secret` emits `SECRET_BYTES` alphabet *characters*, so the test encodes the already-reported naming defect as a requirement.
What breaks in production: nothing at runtime, but the fix for the CSPRNG finding turns this green test red, which invites the fix to be reverted or the constant to be re-fudged rather than corrected. Fix: rename the constant to `SECRET_ENTROPY_BYTES`, switch the generator to `secrets.token_hex(SECRET_ENTROPY_BYTES)`, and change this assertion to `len(secret) == len(SECRET_PREFIX) + 2 * SECRET_ENTROPY_BYTES`, so the test states the hex-expansion relationship instead of the accidental one.

### Minor: response bodies also reach the application log, a third copy the storage fix will not bound
File: `app/webhooks/delivery.py` — `deliver`, `detail = f"HTTP {response.status_code}: {response.text}"` and the following `log.warning`
What is wrong: the cross-cutting check on the already-reported "response bodies are stored unbounded" finding shows the same unbounded value is also passed to `log.warning("delivery %s failed (%s), retrying in %ss", ...)`, so it is written to the log on every failed attempt as well as to the column.
What breaks in production: a misbehaving endpoint returning a multi-megabyte error page has that body written to the log four times per delivery, so a fix that truncates only `WebhookDelivery.response_body` leaves the log-volume and log-content exposure untouched. Fix: truncate once at the point of construction (`detail = f"HTTP {response.status_code}: {response.text[:1024]}"`) so both the stored column and the log line inherit the bound, and keep the status code un-truncated since it is the diagnostic the docs promise the listing endpoint returns.
