### Critical: the signature is computed over different bytes than the ones sent, so no receiver can ever verify it
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (keys sorted, `", "`/`": "` separators) while the request body is produced independently by `client.post(..., json=delivery.payload)`, which httpx serializes compactly and in insertion order, and the `X-Acme-Timestamp` value is never fed into the MAC even though `docs/webhooks.md` states the signature is HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`.
What breaks in production: every customer who implements the documented verification rejects 100% of our webhooks, and because the timestamp is outside the MAC an attacker who captures one request can rewrite the timestamp header freely, so the documented five-minute replay window is unenforceable even after the body mismatch is fixed.
Fix: make one byte string the single source for both the MAC and the wire — in `send_once` compute `body = signing.serialize(delivery.payload).encode()`, call a `sign(secret, body)` that returns `timestamp, "sha256=" + hmac.new(secret.encode(), f"{timestamp}.".encode() + body, sha256).hexdigest()`, and send `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})`; change `verify(secret, body, timestamp, signature)` to take the same raw bytes plus the timestamp and reject when `abs(now - int(timestamp)) > 300`. Preserve what the current code got right and must not be dropped: `serialize`'s `sort_keys=True` (it is what makes the digest reproducible for a receiver that re-serializes) and the `sha256=` prefix the docs and `test_sign_returns_timestamp_and_prefixed_digest` pin. Allow side that must still succeed and must be pinned: a round-trip test that captures `request.content` from `httpx.MockTransport` and asserts `signing.verify(SECRET, captured["body"], captured["headers"][TIMESTAMP_HEADER], captured["headers"][SIGNATURE_HEADER])` is `True` — actual producer output through the actual verifier, per R40, not two independently mocked shapes. Red-prove each clause separately by executing one mutation per clause: (a) revert `content=body` to `json=delivery.payload` — the round-trip assertion must go red; (b) drop `f"{timestamp}."` from the MAC input — a test asserting that two `sign` calls one second apart over the identical payload differ must go red; (c) set the verifier's window to accept any timestamp — a test signing with `time.time() - 600` must go red. Fail loudly when the check cannot run: `verify` must raise on a signature that is not `sha256=<64 hex>` and on a non-integer timestamp rather than returning `False`, so "malformed header" is not spelled the same as "wrong signature". Boundary and tie: the window is inclusive — `abs(skew) == 300` verifies, `301` does not; two requests sharing the same second both verify, since the timestamp is an authenticity input and not a uniqueness key.

### Critical: any authenticated user can read any organization's webhook deliveries
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` with no join back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling routes added in the same file (`create_webhook_endpoint`, `list_webhook_endpoints`) do scope to `user.org_id` — the tenancy pattern was propagated to two of three new routes (R3).
What breaks in production: an authenticated tenant enumerating small integers reads other organizations' delivery rows, and since `WebhookDelivery.to_dict` exposes `event_type` and the route is documented as returning "the most recent attempts for an endpoint belonging to your organization", cross-tenant billing-event metadata leaks under a contract that claims it cannot.
Fix: join the tenancy predicate into the same query — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the response does not disclose whether the id exists. Do not fix this by removing the route or by dropping `endpoint_id` from the path; the feature the docs sell is per-endpoint inspection and it must keep working. Deny side and allow side both pinned: one test where user B requests user A's `endpoint_id` asserts 404 **and** that the response body is `[]`/absent rather than merely asserting the status (RT8 — status without the payload assertion is vacuous), and one test where the owning user requests their own `endpoint_id` asserts 200 with the expected delivery ids. Red-prove by executing two separate mutations: delete the `org_id` clause (cross-tenant test must go red) and change the returned status to 403 with the row still serialized (the payload assertion must go red). Fail loudly: an `endpoint_id` that resolves to no row after the join must raise `HTTPException(404)`, never fall through to an empty list produced by a query that errored. Boundary and tie: the caller's own endpoint id is the inclusive-allow case; an endpoint that exists but belongs to another org and an endpoint that does not exist must be indistinguishable in status, body, and timing.

### Critical: registered endpoint URLs are unvalidated, and the worker follows redirects — SSRF into the internal network
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plain `http://`, admits any scheme literally prefixed `http` (`urlparse("httpfoo://x").scheme == "httpfoo"` passes), and performs no host or address check, while `docs/webhooks.md` asserts "Only `https://` URLs are accepted"; the delivery client then follows redirects, so even an allowed host can bounce the request to a link-local address (RS3, and R49 — the doc claims an enforceable boundary the code does not implement).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://127.0.0.1:6379/` and our worker issues authenticated-looking POSTs into our own network from a trusted source address, with the response body captured verbatim into `WebhookDelivery.response_body` and readable through the deliveries API — a full read-side SSRF exfiltration channel.
Fix: replace the `startswith` test with an explicit whitelist check at the boundary — `parsed.scheme == "https"` (exact equality, not prefix), non-empty `parsed.hostname`, no userinfo, and a resolution check that rejects when any address `socket.getaddrinfo(hostname, 443)` returns is private, loopback, link-local, multicast, or reserved (`ipaddress.ip_address(a).is_global` is False) — then set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a non-retryable permanent failure. Re-resolve and re-check at send time rather than trusting the stored URL, because DNS rebinding makes the registration-time result stale (R51). Do not fix by deleting the deliveries API's `response_body` field — the diagnostic value it provides is the feature; the fix is to stop the request reaching an internal target. Allow side that must still succeed and be pinned: `https://hooks.example.com/acme` (the URL already used in the docs and in `tests/webhooks/test_delivery.py::FakeEndpoint`) still registers with 201 and still delivers. Red-prove by three separate executed mutations: (a) revert to `scheme.startswith("http")` — a test posting `httpfoo://x/` and `http://x/` must go red; (b) remove the address check — a test posting `https://localhost/` must go red; (c) restore `follow_redirects=True` — a `MockTransport` handler returning `302` to `http://169.254.169.254/` with an assertion that no second request was issued must go red. Fail loudly: when `getaddrinfo` raises or times out, reject the registration with 422 naming "hostname could not be resolved" — an unresolvable host must not be spelled the same as a safe one. Boundary and tie: a hostname resolving to both a global and a private address is rejected (any-private-rejects, not all-private-rejects), and a URL whose host is a bare IPv6 literal is subject to the same check.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice` over `string.ascii_letters + string.digits`, and `random` is a Mersenne Twister seeded from process state, not a CSPRNG; additionally `SECRET_BYTES = 32` is used as a character count, so the constant's name misstates what it controls.
What breaks in production: an attacker who observes enough output from the same process — trivially, by registering endpoints in a loop and reading back the secrets, which this API currently returns (see the next finding) — can recover the MT19937 state and predict every other tenant's signing secret, letting them forge webhooks that our own documented verification accepts as genuine.
Fix: generate with the CSPRNG — `secrets.token_urlsafe(SECRET_BYTES)` prefixed with `SECRET_PREFIX`, and rename the constant to `SECRET_ENTROPY_BYTES = 32` so the name states the property (raw entropy) rather than the encoded length. Do not fix by only lengthening the `random`-based string; length does not repair predictability, and the visible symptom (short secret) is not the defect. Preserve what `test_new_signing_secret_has_prefix_and_length` was pinning — the `whsec_` prefix must survive — but replace its length assertion, which is satisfied by any constant string, with two assertions: 1000 generated secrets are pairwise distinct, and each decodes to `SECRET_ENTROPY_BYTES` of entropy. Allow side pinned: a secret produced by `new_signing_secret` still round-trips through `sign`/`verify`. Red-prove by executing one mutation per clause: replace the body with `SECRET_PREFIX + "a" * 32` (the distinctness assertion must go red, and note that the current test stays GREEN under this mutation — that is the evidence the existing test is decorative), and shorten the entropy to 4 bytes (the entropy-length assertion must go red). Fail loudly: `secrets` is stdlib and cannot be absent, but if the generator is ever made pluggable, an unavailable source must raise at import rather than fall back to `random`. Boundary and tie: two secrets colliding is the failure the distinctness assertion names; at 32 bytes the collision probability is negligible, which is precisely why a collision in the test means the CSPRNG was replaced.

### Critical: the signing secret is returned on every endpoint read, contradicting the documented one-time-disclosure contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret` and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (RS4; R49 — a claim stronger than the implementation).
What breaks in production: the secret that authenticates every webhook we send is served on a GET, so it lands in browser history, proxy and CDN logs, API-client transcripts and any support screenshot, and anyone with read access to the settings API — a scope customers reasonably grant to read-only integrations — can forge events for that tenant.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` alone disclose it, by returning `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable it already holds; add a `POST /webhook-endpoints/{id}/rotate-secret` returning the new secret once, since removing read-back without a rotation path leaves a customer who lost the secret with no recovery. Do not fix by keeping the field and redacting it in the route — `to_dict` is the shared serializer and the next call site will leak it again; removing it at the source is what makes the class closed. Allow side pinned: a test asserting the 201 response from `create_webhook_endpoint` DOES contain `signing_secret` (the feature must keep working), alongside the deny-side test asserting the 200 from `list_webhook_endpoints` does not. Red-prove by two separate executed mutations: re-add the key to `to_dict` (the list-response assertion must go red) and drop the merge in the create route (the create-response assertion must go red). Fail loudly: rotation must fail closed with a 5xx if the new secret cannot be persisted, never return a secret that was not written. Boundary and tie: during rotation both the old and the new secret must verify for one skew window, and after that window only the new one — otherwise every in-flight retry signed with the old secret is rejected.

### Critical: the signature and full header set are written to the application log at INFO
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: the whole `headers` dict, including `X-Acme-Signature`, is logged for every attempt at INFO level, and `_finish` additionally stores the customer's entire `response.text` into `WebhookDelivery.response_body` with no size cap or redaction.
What breaks in production: shipped and indexed logs become a store of valid signatures for replayable payloads (and, once the timestamp is folded into the MAC per the first finding, a replay of exactly that request), while unbounded `response_body` lets a hostile or merely verbose endpoint write megabytes of arbitrary content per attempt into our primary database.
Fix: log the endpoint id, the delivery id and the HTTP status only — `log.info("POST endpoint=%s delivery=%s", endpoint.id, delivery.id)` — never the header mapping; and truncate before persisting: `row.response_body = detail[:2048]` with a `"…(truncated)"` marker so the truncation is visible rather than silent. Do not fix by lowering the log level to DEBUG; DEBUG is enabled in incident response, which is exactly when the log is most widely read. Preserve the diagnostic value the line was there for — the allow side pinned by a test is that a failed delivery still records a non-empty `response_body` and still names the endpoint in the log. Red-prove by two executed mutations: restore `headers=%s` (a test asserting the emitted log record contains neither the secret nor the `sha256=` value must go red) and remove the slice (a test posting a 100 KB response body and asserting the stored length is 2048 plus the marker must go red). Fail loudly: if `response.text` cannot be decoded, store `"<undecodable body>"` rather than an empty string, so "no body" and "body we could not read" are not spelled the same. Boundary and tie: a body of exactly 2048 characters is stored whole with no marker; 2049 is truncated and marked.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`; `app/webhooks/models.py` — `STATUSES`
What is wrong: the status vocabulary is hardcoded in three places and they disagree — the migration allows `'failed'`, while `models.STATUSES` and the only writer in `delivery.py` use `'failed_permanent'` (R2 value duplicated across places, R3 the change propagated to two of the three).
What breaks in production: the first permanently-failed delivery raises a check-constraint violation inside `_finish`, the transaction aborts, the row stays `in_flight` forever, and because `_claim_batch` only selects `pending` the delivery is never retried and never reported as failed — a silent permanent loss on the exact path meant to record failure.
Fix: make one definition authoritative and derive the others from it — keep `models.STATUSES` as the source, write the migration constraint from that same tuple (`CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`), and add a startup/CI assertion that the constraint's enumerated set equals `set(STATUSES)` so the next divergence fails the build rather than a delivery. Do not fix by widening the constraint to accept any text; the constraint is what makes an unknown status visible. Allow side pinned: an integration test that drives a delivery to permanent failure asserts the row is readable afterwards with `status == "failed_permanent"` and `attempts == MAX_ATTEMPTS`; the deny side asserts that writing `"failed"` raises. Red-prove by two executed mutations: revert the constraint to `'failed'` (the permanent-failure integration test must go red with a check-violation the failure output names) and add `"bogus"` to `STATUSES` without touching the migration (the set-equality assertion must go red). Fail loudly: the set-equality check must error if it cannot read the constraint definition from the database, rather than skipping and reporting pass. Boundary and tie: `attempts == MAX_ATTEMPTS` is the inclusive terminal case (`>=` in `deliver` is correct); at `MAX_ATTEMPTS - 1` the row must still be retryable.

### Critical: the unique index on `event_id` alone makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint for a single `event_id` and `session.add_all`s them, but the index declares `event_id` globally unique, so any org with two subscribed endpoints inserts two rows with the same `event_id`.
What breaks in production: the flush raises a unique-violation, the whole `session_scope` rolls back so NOT EVEN the first endpoint gets a delivery row, and because `dispatch` wraps the call in `except Exception: log.warning(...)` the event is silently dropped for every customer who registered a second endpoint.
Fix: the uniqueness the design actually needs is per endpoint per event — replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which both permits fan-out and gives `enqueue_for_event` the idempotency key the docs' "deduplicate on `event_id`" line presumes. Do not fix by dropping uniqueness altogether; the index is what prevents a re-dispatched event from double-enqueuing, and that protection must be preserved. Allow side pinned: a test with two active endpoints on one org asserts `enqueue_for_event` returns 2 and that both rows exist; deny side: calling `enqueue_for_event` twice with the same `event_id` asserts the second call inserts nothing and raises no error (use `ON CONFLICT DO NOTHING`/`session.merge` semantics rather than letting the violation escape). Red-prove by two executed mutations: restore the single-column index (the two-endpoint test must go red on a unique violation) and remove the conflict handling (the double-enqueue test must go red). Fail loudly: `enqueue_for_event` must re-raise any integrity error that is not this conflict, so "already enqueued" and "database rejected the write" are distinguishable. Boundary and tie: two endpoints of the SAME org and one endpoint subscribed via an empty `event_types` plus one via an explicit list are the two tie cases the pair `(endpoint_id, event_id)` must keep distinct.

### Critical: `_claim_batch` returns ORM rows whose session has already closed
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`
What is wrong: the rows are loaded and mutated inside `with session_scope() as session:` and then returned after the block exits, so under SQLAlchemy's default `expire_on_commit=True` they come back expired and detached; `deliver` then reads `delivery.attempts`, `delivery.payload` and `delivery.id` from them.
What breaks in production: the first attribute access raises `DetachedInstanceError`, `asyncio.gather` (called without `return_exceptions=True`) propagates it out of `run_worker`, and the worker dies after having already flipped up to 100 rows to `in_flight` — those deliveries are then unreachable by any later poll, so the queue silently drains into a dead state on the very first tick.
Fix: stop passing ORM identities across the session boundary — have `_claim_batch` return plain values (`list[tuple[int, int, dict]]` of `delivery_id`, `endpoint_id`, `payload`, plus `attempts`) read inside the session, and have `deliver` take those values; claim atomically in one statement with `UPDATE webhook_deliveries SET status='in_flight' WHERE id IN (SELECT id FROM webhook_deliveries WHERE status='pending' AND next_attempt_at <= now() ORDER BY next_attempt_at, id LIMIT :n FOR UPDATE SKIP LOCKED) RETURNING id, endpoint_id, attempts, payload`, which also removes the read-then-write TOCTOU between the SELECT and the status write (R5). Do not fix by setting `expire_on_commit=False` and keeping detached instances; that hides the boundary error and leaves the claim non-atomic. Allow side pinned: a test asserting a single worker claims and delivers a pending row end-to-end (status becomes `delivered`, `attempts == 1`); deny side: two concurrent `_claim_batch` calls against the same pending set return disjoint id sets. Red-prove by two executed mutations: return the ORM objects again (the end-to-end test must go red naming `DetachedInstanceError`) and drop `FOR UPDATE SKIP LOCKED` (the disjointness test must go red — and bound it with a statement timeout so a lock wait fails rather than hangs). Fail loudly: if the claiming statement returns no rows because the table is locked or the query errored, `run_worker` must log at ERROR and back off, never treat it as an empty queue. Boundary and tie: `next_attempt_at <= now()` is inclusive at exactly now, and rows tying on `next_attempt_at` are ordered by `id` so the claim order is total (R57).

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's short-circuiting string equality instead of `hmac.compare_digest`, and this is the reference verifier we ship and that `docs/webhooks.md` tells customers to mirror with "a constant-time comparison" (RS1; R49 — the doc claims the property the code omits).
What breaks in production: any internal caller of `verify` — and any customer who copies it, which is the function's stated purpose — leaks the correct digest byte by byte through response timing, letting an attacker forge a signature without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with the arguments encoded to bytes so the comparison is over a fixed-width value, and update `docs/webhooks.md` to point at this implementation as the reference rather than describing it in prose. Do not fix by removing `verify` because "customers implement their own"; it is what the tests and the docs stand on, and deleting it removes the only executable statement of the contract. Allow side pinned: `test_verify_accepts_signature_produced_by_sign` must still pass, and — because that test is currently an identity over `sign` and would stay green under almost any mutation — add one that verifies against a signature computed by an independently written expected value (a literal hex digest checked in from a known secret/payload/timestamp triple), per RT1. Red-prove by two executed mutations: restore `==` (a test asserting `verify.__code__.co_names` contains `compare_digest` goes red — a structural check is used here deliberately, since a timing assertion is flaky and would be a blind gate under RT7) and flip one character of the literal expected digest (the independent-value test must go red). Fail loudly: `verify` must raise `ValueError` on a signature of the wrong length or shape rather than returning `False`, so a malformed header is not reported as a failed authentication. Boundary and tie: a signature equal to `expected` except for case must be rejected, since `hexdigest()` is lowercase and the comparison is over exact bytes.

### Critical: `deliver` blocks the event loop with `time.sleep` inside an async function
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: the retry loop calls the blocking `time.sleep` rather than `await asyncio.sleep`, inside a coroutine that `run_worker` launches 100 at a time under `asyncio.gather`.
What breaks in production: the first retrying delivery freezes the entire event loop for up to 16 seconds — every other delivery in the batch, the Redis lock refresh, and anything else sharing the loop stall behind it, so one slow customer endpoint takes down the whole worker's throughput and the 60-second lock expires while work is still running.
Fix: replace with `await asyncio.sleep(delay)`, and — better, because a 5-attempt in-process loop also loses all progress if the process restarts — do not retry in-process at all: on a retryable failure, write `attempts = attempt`, `status = "pending"` and `next_attempt_at = now() + backoff_for(attempt)` and return, letting the next poll pick it up. Do not fix by shrinking the delays to keep the block short; the backoff schedule the docs publish (2s/4s/8s/16s) is the behaviour that must be preserved. Allow side pinned: a test asserting a delivery that fails once and succeeds on the second poll ends `delivered` with `attempts == 2`; deny side: a delivery failing `MAX_ATTEMPTS` times ends `failed_permanent` and is not re-claimed. Red-prove by three executed mutations, each run singly: restore `time.sleep` (a test asserting two concurrent `deliver` calls complete in under the sum of their delays must go red — bound it with `asyncio.wait_for` so a regression fails rather than hangs); set `next_attempt_at = now()` on the retry write (a test asserting the row is not claimable immediately must go red); make the permanent branch write `status = "pending"` (the not-re-claimed assertion must go red). Fail loudly: if the retry write itself fails, log at ERROR and leave the row `in_flight` for the reaper below rather than swallowing it. Boundary and tie: at `attempt == MAX_ATTEMPTS` the delivery is permanent (inclusive); rows whose `next_attempt_at` ties are ordered by `id`.

### Major: `in_flight` is a non-terminal state with no timeout and no recovery path
File: `app/webhooks/delivery.py` — `_claim_batch` (sets `in_flight`), `_finish` (only exit)
What is wrong: a row leaves `in_flight` only when `_finish` runs on the success or permanent-failure path, so a worker crash, a deploy, an OOM kill, or any exception escaping `deliver` strands the row, and `_claim_batch` selects only `status == "pending"` — nothing anywhere returns an `in_flight` row to the queue (R38 mode 1: the async transition has no failure-exit and no bounded timeout).
What breaks in production: every worker restart permanently orphans up to `BATCH_SIZE` deliveries with no alert and no operator affordance, and the count grows monotonically across the service's life.
Fix: add a claim deadline — a `claimed_at TIMESTAMPTZ` column set when the row goes `in_flight`, and a reaper in `run_worker`'s loop that runs `UPDATE webhook_deliveries SET status='pending', next_attempt_at=now() WHERE status='in_flight' AND claimed_at < now() - interval '5 minutes'`, logging at WARNING with the count reclaimed so the condition is visible rather than silent. Do not fix by removing the `in_flight` state and claiming rows implicitly; the state is what stops two workers delivering the same row. Allow side pinned: a row claimed 10 seconds ago is NOT reclaimed while its delivery is still running (otherwise the reaper causes the duplicate deliveries it was added to prevent); deny side: a row claimed 6 minutes ago is reclaimed and subsequently delivered. Red-prove by two executed mutations: remove the `claimed_at` predicate (the still-running-row test must go red) and remove the reaper (the stale-row test must go red). Fail loudly: if the reaper's update errors, `run_worker` logs ERROR and continues polling rather than exiting silently. Boundary and tie: a row whose `claimed_at` is exactly the 5-minute threshold is NOT reclaimed (strict `<`), which must exceed `REQUEST_TIMEOUT` (30s) plus the full retry schedule so the deadline can never fire on live work.

### Major: the dispatch lock is check-then-act, and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by `set` is not atomic, so two workers polling simultaneously both observe an absent key and both acquire; the separate `set` then `expire` leaves a window where a crash between them creates a permanent lock; and `delete(LOCK_KEY)` releases whatever lock is currently held, including one a different worker acquired after the 60-second expiry fired mid-batch.
What breaks in production: concurrent workers claim overlapping batches and deliver the same event twice or more, and a batch that outlives the 60-second TTL has its successor's lock deleted, so the mutual exclusion degrades to none precisely under the load that made batches slow.
Fix: acquire with a single atomic call carrying a unique owner token and the TTL together — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = secrets.token_hex(16)` — and release only if still owned, via the compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`); refresh the TTL periodically while a batch runs. Do not fix by lengthening the TTL alone; a longer TTL trades duplicate delivery for a longer outage after a crash, and the mutual exclusion the lock provides must be preserved in both directions. Allow side pinned: a single worker that acquires, finishes, and releases can immediately re-acquire on the next tick; deny side: a second worker's `_acquire_lock` returns `False` while the first holds it, and a worker whose token no longer matches does NOT delete the key. Red-prove by three executed mutations: revert to `get`-then-`set` (a test issuing two concurrent `_acquire_lock` calls and asserting exactly one `True` must go red); drop `ex=60` (a test asserting `ttl(LOCK_KEY) > 0` must go red); revert the release to plain `delete` (a test where worker B holds the lock and worker A releases, asserting the key survives, must go red). Fail loudly: a Redis error in `_acquire_lock` must return `False` and log at ERROR — an unreachable Redis must read as "cannot claim the lock", never as "the lock is free". Boundary and tie: two workers submitting `SET NX` in the same millisecond — exactly one wins, and the loser sleeps `poll_interval` rather than proceeding.

### Major: `dispatch` records the event, then swallows the enqueue failure
File: `app/events/dispatcher.py` — `dispatch`, the `except Exception as exc: log.warning(...)` around `enqueue_for_event`
What is wrong: the event row is committed by its own `session_scope` before the webhook enqueue is attempted, and any failure of that enqueue — including the unique-violation described above — is caught, logged at WARNING and discarded, with `dispatch` still returning the event id as success (R9: the side effect is outside the transaction that made it owed, with no compensating record).
What breaks in production: an event exists in the database with no corresponding delivery row and nothing to reconcile from, so the customer never receives a webhook for a paid invoice and no query can distinguish "delivered" from "never enqueued".
Fix: make the enqueue derivable rather than fire-and-forget — either write the delivery rows in the SAME transaction as the `Event` insert (both are DB writes; there is no reason for two scopes), or keep the split and add a reconciliation query that finds `events` of a `WEBHOOK_EVENT_TYPES` type with no `webhook_deliveries` row and enqueues them, run from the same worker loop. Narrow the `except Exception` to the specific recoverable errors and re-raise the rest. Do not fix by deleting the try/except so a webhook failure fails the whole `dispatch`; in-process subscribers have already run by that point and must not be rolled back. Allow side pinned: a healthy `dispatch` still returns the event id and still enqueues one row per subscribed endpoint; deny side: a `dispatch` whose enqueue fails leaves an event that the reconciliation query finds, asserted by querying it — not merely by asserting a log line was emitted. Red-prove by two executed mutations: widen the except back to bare `Exception` with no reconciliation (the reconciliation test must go red) and make the reconciliation query join on the wrong column (it must go red naming zero rows found). Fail loudly: reconciliation that cannot run (DB unreachable) must log ERROR and leave the cursor untouched rather than reporting an empty backlog. Boundary and tie: an event enqueued in the same transaction and one enqueued by reconciliation must both produce exactly one row per `(endpoint_id, event_id)` — the unique index above is what makes the tie safe.

### Major: `webhooks_enabled` is added by the migration and read by nothing
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: the column declares a per-organization feature gate defaulting to FALSE, but no code in the diff references it — `enqueue_for_event` filters only on `org_id` and `active` — so the declared capability has no backing path (R41).
What breaks in production: the flag is either a dead column that misleads every future reader into believing the feature is gated, or, if operations relies on it, a gate that silently does nothing and ships webhooks for every organization from day one, including any that were meant to be excluded.
Fix: wire the flag at the single enqueue chokepoint — join `Organization` in `enqueue_for_event` and return 0 when `webhooks_enabled` is false — and additionally reject `create_webhook_endpoint` with 403 for a disabled org, so the flag holds in both the registration and the delivery direction; if the gate is not wanted, drop the column in the same migration rather than leaving it. Do not fix by defaulting it TRUE to "make it work"; the fail-closed default is the property to preserve. Allow side pinned: an org with `webhooks_enabled = TRUE` still gets one delivery row per subscribed endpoint; deny side: an org with FALSE gets zero rows, asserted by querying `webhook_deliveries`, not by asserting the return value alone (RT8). Red-prove by two executed mutations: remove the join predicate (the disabled-org row-count assertion must go red) and invert it (the enabled-org assertion must go red). Fail loudly: if the organization row cannot be loaded, `enqueue_for_event` raises rather than treating the missing row as enabled. Boundary and tie: an org toggled from TRUE to FALSE while deliveries are already `pending` — state which side those fall on; the recommendation is that already-enqueued rows still deliver and only new enqueues are blocked, and that must be asserted.

### Major: none of the three new routes has rate limiting
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: three new public endpoints are added with no limiter and no per-org cap on endpoint count (RS2); `create_webhook_endpoint` in particular is an unbounded write that each time multiplies the fan-out of every future event.
What breaks in production: a caller loops on `POST /webhook-endpoints` and every subsequent event enqueues one delivery row and one outbound HTTP request per registered endpoint, turning a cheap authenticated call into an amplification attack on our own worker and on whatever hosts the URLs point at.
Fix: apply the project's existing limiter dependency to all three routes (`grep -r` for the decorator or `Depends` already used on `list_api_keys`' router — if none exists this is a question, not an assertion, see the Minor below), and independently enforce a hard cap of N active endpoints per organization inside `create_webhook_endpoint`, returning 409 when exceeded. Do not fix by rate-limiting only the write route; `list_deliveries` with an unbounded `limit` is the cheapest way to read a lot of JSONB. Allow side pinned: a normal caller making one create and a handful of reads is never limited, asserted by a test making N-1 calls and expecting 200s; deny side: call N+1 returns 429 AND no endpoint row was inserted (status alone is vacuous per RT8). Red-prove by two executed mutations: remove the limiter (the 429 assertion must go red) and let the handler insert before the cap check (the row-count assertion must go red). Fail loudly: if the limiter's backing store is unreachable, deny with 503 rather than allowing through. Boundary and tie: the Nth call succeeds and the (N+1)th is refused; two calls arriving in the same window with the counter at N-1 must not both succeed.

### Major: `limit` on the deliveries route has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: the validator constrains only the lower bound, so `?limit=100000000` is accepted and the query materializes that many rows, each carrying a JSONB `payload` and a `TEXT` `response_body` (RS3).
What breaks in production: a single request holds a database connection while loading and serializing gigabytes, exhausting the pool and taking the whole settings API down with it.
Fix: `limit: int = Query(50, ge=1, le=200)` so the bound is enforced at the schema layer where FastAPI returns 422, not deep in the handler, and add keyset pagination (`before_id`) rather than raising the ceiling. Do not fix by clamping silently inside the handler — a silently-clamped 100000 reads as success and hides the caller's mistake; a 422 names it. Allow side pinned: `limit=200` still returns 200 with up to 200 rows; deny side: `limit=201` returns 422 and executes no query. Red-prove by two executed mutations: remove `le=200` (the 422 test must go red) and lower it to 199 (the `limit=200` allow test must go red). Fail loudly: a non-integer `limit` must 422 rather than falling back to the default. Boundary and tie: 200 is accepted and 201 refused; with `created_at` ties at a page edge, see the ordering finding below.

### Major: `enqueue_for_event` writes a naive `utcnow()` into a timezone-aware column, and the migration declares the columns without a timezone
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); `app/webhooks/models.py` — `_now`, `DateTime(timezone=True)`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP NOT NULL`
What is wrong: three layers disagree — `models._now()` is the aware helper the file already provides and `_claim_batch`/`_finish` use `datetime.now(timezone.utc)`, while `enqueue_for_event` reimplements it with the naive `datetime.utcnow()`; and every SQL column is `TIMESTAMP` (without time zone) under models that declare `timezone=True` (R1: the helper already exists in the change and the new code bypasses it; R16: schema and model parity).
What breaks in production: comparing the naive value against the aware `now` in `_claim_batch` raises `TypeError` on a `TIMESTAMPTZ` column, or, on the `TIMESTAMP` column the migration actually creates, silently compares local-time and UTC values — so on a non-UTC database server deliveries become claimable hours early or hours late.
Fix: use `m._now()` in `enqueue_for_event` (the helper is in the same package, imported as `m`), and change every timestamp column in the migration to `TIMESTAMPTZ NOT NULL DEFAULT now()` so the schema matches `DateTime(timezone=True)`. Do not fix by making the models naive; the aware representation is what makes cross-region correctness checkable. Allow side pinned: a delivery enqueued with `next_attempt_at = now()` is claimed on the immediately following poll, asserted under a session whose `TimeZone` is set to something other than UTC; deny side: one enqueued with `now() + 60s` is not claimed. Red-prove by two executed mutations: restore `datetime.utcnow()` (the non-UTC-session claim test must go red) and revert the column type to `TIMESTAMP` (the same test must go red for a different, named reason — run them singly so the two reds are distinguishable). Fail loudly: reject a naive datetime at the model boundary with a validator that raises, rather than coercing it. Boundary and tie: `next_attempt_at <= now()` is inclusive at exactly now.

### Major: `docs/webhooks.md` describes four behaviours the implementation does not have
File: `docs/webhooks.md` — the "Registering an endpoint", "Verifying the signature" and "Retries" sections
What is wrong: the doc states (a) "Only `https://` URLs are accepted" against a `startswith("http")` check, (b) the signature covers `"{timestamp}.{raw_request_body}"` against a `sign` that MACs the body only, (c) "backoff is exponential with jitter" against a purely deterministic `backoff_for`, and (d) "a 4xx is permanent and we stop immediately" against a `deliver` loop that retries every non-2xx up to `MAX_ATTEMPTS`; the secret read-back claim is covered separately above (R29 rationale/derived-claim accuracy, R49 claim stronger than the implementation).
What breaks in production: customers build verification and alerting against a contract the service does not honour — their signature checks fail, their 4xx responses are hammered five times each, and the absent jitter synchronizes retries from every endpoint of a shared outage into a thundering herd.
Fix: bring the code to the doc for (a), (b) and (c) — the https whitelist and timestamp-in-MAC changes are specified in the Critical findings above, and `backoff_for` becomes `timedelta(seconds=BASE_DELAY_SECONDS**attempt * (1 + random.random() * 0.25))` — and add a `4xx` branch in `deliver` that calls `_finish(..., "failed_permanent", ...)` immediately for `400 <= code < 500` except `408` and `429`, which are retryable. Where a doc statement is aspirational rather than implemented, change the doc in the same commit rather than leaving it; do not fix by deleting the retry/verification documentation, since it is the only published contract customers can build against. Allow side pinned: a 500 is still retried (the jitter test asserts the delay lies within `[base, base*1.25]`, not that it equals a constant, so the schedule the doc publishes is preserved), and a 429 is still retried; deny side: a 404 response ends the delivery at `attempts == 1` with `status == "failed_permanent"`. Red-prove by three executed mutations run singly: remove the jitter factor (the interval assertion must go red — assert the interval, not a sampled value, so the test is not flaky); remove the 4xx branch (the `attempts == 1` assertion must go red); add 429 to the permanent set (the 429-retried assertion must go red). Fail loudly: a response with no status code (transport error) must take the retryable path explicitly rather than falling through the 4xx comparison. Boundary and tie: 400 and 499 are permanent, 500 is retryable, and 408/429 are the named exceptions on the permanent side of that boundary.

### Major: the new delivery, worker and enqueue code ships with no tests
File: `tests/webhooks/test_delivery.py` — imports only `MAX_ATTEMPTS`, `backoff_for`, `send_once`
What is wrong: `enqueue_for_event`, `deliver`, `run_worker`, `_acquire_lock`, `_claim_batch` and `_finish` are all new production symbols with no test covering them, so the retry loop, the terminal-state transitions, the lock, and the batch claim are entirely unexercised (RT6); the retry path in particular is where five of this review's Critical findings live.
What breaks in production: every defect above — the blocking sleep, the detached rows, the status-constraint violation, the swallowed enqueue failure — is invisible to a green suite, so the first signal is customers reporting missing webhooks.
Fix: add `tests/webhooks/test_worker.py` covering, against a real in-memory/containerized Postgres rather than mocks (the constraint violation is only reachable through a real database — a mocked session cannot validate the CHECK): `enqueue_for_event` fan-out to two endpoints and the event-type filter including the empty-list-means-all case; `deliver` on success, on retryable failure, and on permanent failure asserting the persisted `status`/`attempts`/`response_status`; `_acquire_lock` mutual exclusion; and one full `run_worker` tick with `httpx.MockTransport`. Do not fix by asserting call counts on a mocked `session` — that is the mock-reality divergence (RT1) that would let all four defects through. Allow side pinned: each test names the case that must SUCCEED (delivered on 200, re-claimed after backoff) alongside the failure case. Red-prove each of the six behaviours by its own executed mutation, one per test, and confirm each red names the assertion that failed. Fail loudly: if the database fixture cannot start, the suite must ERROR, not skip — a skipped integration test reports the same green as a passing one, and that is exactly how this class ships. Boundary and tie: assert `attempts == MAX_ATTEMPTS` (not `>=`) on the permanent path, and assert the row is not re-claimable at that boundary.

### Major: the existing signing tests cannot fail for the defects they appear to cover
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign`, `test_send_once_posts_the_signed_payload`, `test_new_signing_secret_has_prefix_and_length`
What is wrong: the verify test computes both sides with `sign`, so it is an identity that stays green under any change to `serialize` or to the MAC input (RT1); the `send_once` test asserts only that the header starts with `sha256=` and never recomputes the HMAC over the captured body, which is the single assertion that would have caught the producer/signer serialization split; and the secret test's length assertion stays green if the generator is replaced by a constant string (RT7 — the guards are structurally blind).
What breaks in production: the suite reads as coverage of the signing contract while proving nothing about it, so the Critical signature defect above ships with a green build and a reviewer's confidence.
Fix: replace the identity with independently written expected values — check in a fixed `(secret, payload, timestamp)` triple and its literal expected hex digest, assert `sign` reproduces it, and assert `verify` accepts it; in `test_send_once_posts_the_signed_payload` recompute the HMAC over `captured["body"]` and the captured timestamp header and assert equality; in the secret test assert pairwise distinctness across 1000 generations. Do not fix by deleting the weak tests — keep the prefix and `sha256=`-shape assertions, which pin real parts of the contract, and add the missing ones beside them. Allow side pinned: the newly strengthened tests must pass against the corrected implementation before any mutation is attempted. Red-prove each separately by execution: flip one hex character of the checked-in digest (the reproduce assertion reds); revert `content=body` to `json=` (the recomputation assertion reds); replace `new_signing_secret`'s body with a constant (the distinctness assertion reds, and record that the ORIGINAL length assertion stayed green under that same mutation — that observation is the evidence for this finding). Fail loudly: if the fixture triple cannot be loaded, the test errors rather than falling back to a generated one. Boundary and tie: the literal digest is exactly 64 hex characters after the `sha256=` prefix, and a value differing only in case must fail.

### Minor: deliveries are ordered by a non-unique wall-clock column
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc()).limit(limit)`
What is wrong: `created_at` has no uniqueness and the whole point of `enqueue_for_event` is to insert several rows in one statement, so a batch shares a timestamp and the order among them is undefined (R57).
What breaks in production: two calls with the same `limit` return different subsets at the page edge, so an operator diagnosing a delivery failure can see a row appear and disappear between refreshes.
Fix: order by `(created_at DESC, id DESC)` and carry both in any future cursor; `id` is `BIGSERIAL` and not caller-nameable, so it supplies the total order. The same pattern exists on the pre-existing `list_api_keys` in this file (`ApiKey.created_at.desc()`) and is in scope — apply the tie-break there too.

### Minor: `_finish` dereferences a row it does not check for existence
File: `app/webhooks/delivery.py` — `_finish`, `row = session.get(...)` then `row.status = status`
What is wrong: `session.get` returns `None` for a deleted row and the next line dereferences it unconditionally; the endpoint's `ON DELETE CASCADE` makes this reachable whenever a customer deletes an endpoint mid-flight.
What breaks in production: an `AttributeError` escapes `deliver`, and via the un-guarded `asyncio.gather` takes down the worker mid-batch.
Fix: return early with a WARNING naming the delivery id when `row is None`.

### Minor: `enqueue_for_event` accepts arbitrary strings as `event_types`
File: `app/api/routes/settings.py` — `EndpointIn.event_types: list[str] = []`
What is wrong: nothing validates the values against a known set, and `dispatcher.WEBHOOK_EVENT_TYPES` is the actual (three-element) universe of deliverable types, so a typo or a subscription to any other type is accepted and silently never matches.
What breaks in production: a customer subscribes to `invoice.payed`, sees a 201, and never receives an event, with no signal anywhere that the subscription is dead.
Fix: validate `event_types` against `WEBHOOK_EVENT_TYPES` in the pydantic model and 422 on an unknown value; note this also makes the docs' "An empty `event_types` subscribes the endpoint to every event type we emit" accurate, since "every type we emit" is currently that same three-element set and the doc reads as though it were open-ended.

### Minor: the delivery table lacks the index its two hot queries need
File: `migrations/0042_webhook_delivery.sql` — `CREATE INDEX idx_webhook_deliveries_status`
What is wrong: `_claim_batch` filters on `(status, next_attempt_at)` and orders by `next_attempt_at`, and `list_deliveries` filters on `endpoint_id` and orders by `created_at`, but the only index is on `status` alone — a low-cardinality column the planner will decline to use.
What breaks in production: both queries degrade to sequential scans as the table grows, and the claim query holds the batch lock longer each poll.
Fix: replace with `CREATE INDEX ON webhook_deliveries (status, next_attempt_at)` and add `CREATE INDEX ON webhook_deliveries (endpoint_id, created_at DESC, id DESC)`.

What is wrong: the diff shows no limiter and no shared URL validator, but the change is not the system — a router-level dependency or middleware outside this diff could already supply both, in which case the RS2 finding above is satisfied and the SSRF finding's remedy should adopt the existing validator rather than write a new one (R1).

## Codebase awareness

- `app/webhooks/signing.serialize` already exists as the canonical serializer and `sign` uses it; `send_once` reimplements serialization by delegating to httpx's `json=` parameter (`return await client.post(endpoint.url, json=delivery.payload, headers=headers)`) — the duplication is the bug, and the fix is to route both through `serialize`.
- `app/webhooks/models._now()` already exists as the aware-now helper in the same package that `delivery.py` imports as `m`; `enqueue_for_event` reimplements it as `datetime.utcnow()` with different semantics.
- `app/webhooks/signing.verify` already exists and is the documented reference verifier, but no code path and no test exercises it against a signature taken from an actual request — the recommended round-trip test uses it rather than adding a second verifier.
- `app/webhooks/models.STATUSES` already exists as the status vocabulary; the migration's CHECK list is a hand-written second copy rather than derived from it.
