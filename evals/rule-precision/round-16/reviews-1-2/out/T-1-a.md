### Major: a raising in-process subscriber skips the webhook enqueue entirely
File: app/events/dispatcher.py — `dispatch`, the `for subscriber in SUBSCRIBERS.get(...)` loop placed before the `if envelope.type in WEBHOOK_EVENT_TYPES:` block
What is wrong: the subscriber loop has no exception handling and runs *after* the event row is committed but *before* the webhook enqueue, so any subscriber that raises propagates out of `dispatch` and the enqueue block is never reached.
What breaks in production: an unrelated in-process subscriber failing (a Slack notifier, a metrics sink) silently costs the customer every webhook for that event, and unlike the already-reported swallowed-enqueue case there is not even a `log.warning` naming the lost delivery — the event is committed, no delivery row exists, and the failure is attributed to the subscriber.
Fix: in `dispatch`, move the `enqueue_for_event` block to immediately after the `with session_scope()` block that assigns `event_id`, ahead of the subscriber loop, and wrap each subscriber call in its own `try/except Exception` that logs `subscriber %s failed for event %s` and continues — so neither side can suppress the other. Preserve, and say so in the change: subscriber exceptions must still be visible (log at `error` and re-raise a collected `ExceptionGroup` after the loop, not swallowed) and `dispatch` must still return `event_id`. Red-prove each clause separately by execution: (a) register a subscriber that raises and assert one `WebhookDelivery` row per matching active endpoint is still created; (b) make `enqueue_for_event` raise and assert the subscriber still ran and its side effect is observable; (c) delete the per-subscriber `except` and assert (a) turns red. Pin the allow side: with all subscribers healthy and one active endpoint, the dispatch still produces exactly one delivery row and one `dispatching ...` log line — a fix that simply drops the subscriber loop passes every other clause. Fail loudly when the enqueue itself cannot run: replace the terminal `except Exception: log.warning(...)` with a write to a durable outbox row (or re-raise after the event transaction is made to include the delivery rows), so "enqueued nothing" is never spelled the same as "enqueued zero endpoints". Boundary and tie: an event whose org has zero matching endpoints and an event whose enqueue failed must be distinguishable in the log and in the outbox — they currently produce the identical observable.

### Major: the new worker is a long-running artifact with no invocation, no readiness signal, and no exit
File: app/webhooks/delivery.py — `run_worker`
What is wrong: `run_worker` is the only drain for the `pending` rows `enqueue_for_event` writes, yet nothing in the change invokes it, it emits no ready signal, and its `while True` has no cancellation or shutdown path — the only observable it produces before the first delivery is a lock write.
What breaks in production: if the deployment shape does not already start this coroutine, `webhook_deliveries` accumulates `pending` rows forever while `docs/webhooks.md` promises "we POST every subscribed event to it", and because the worker prints nothing on boot there is no signal an operator can alert on to notice that it never started (R32/R41).
Fix: add an explicit entrypoint in this change (`python -m app.webhooks.delivery` via an `if __name__ == "__main__": asyncio.run(run_worker())`, plus the deployment/process entry the repo uses for its other long-running processes), and have `run_worker` log a single declared ready line — `log.info("webhook worker ready (batch=%s, poll=%ss)", BATCH_SIZE, poll_interval)` — before entering the loop, so the pass/fail check is `grep` on that line. Add graceful shutdown: catch `asyncio.CancelledError` around the batch, release the lock, and reset the batch's rows from `in_flight` back to `pending` before re-raising. Preserve: the poll/backoff behaviour and the `poll_interval` parameter must survive — do not fix this by inlining the loop into request handling. Red-prove separately by execution: (a) boot the entrypoint against an empty table and assert the ready line appears within one poll interval; (b) insert one due row, boot, and assert it reaches `delivered` — then revert the entrypoint wiring and assert (b) reds; (c) cancel the task mid-batch and assert no row remains `in_flight`. Pin the allow side: the worker must still exit 0 on SIGTERM rather than only proving it can be killed. Fail loudly: if the redis client or the DB is unreachable at boot, log and exit non-zero rather than looping silently on `_acquire_lock` — "cannot run" must not look like "nothing to do". Boundary: a row whose `next_attempt_at` is exactly `now` is due and must be claimed by this batch, not the next.
Question that would close the entrypoint half of this finding: if the service manifest outside this change already runs `app.webhooks.delivery:run_worker`, the wiring clause is answered and only the ready-signal and shutdown clauses stand.

### Major: the dispatch lock's TTL is shorter than a batch's worst-case runtime, so two workers run concurrently and each deletes the other's lock
File: app/webhooks/delivery.py — `_acquire_lock` (`expire(LOCK_KEY, 60)`) and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: a single `deliver` call can run for roughly 5 × `REQUEST_TIMEOUT` (150s) plus the 2+4+8+16s of `time.sleep`, i.e. ~180s, so the 60s TTL expires while the batch is still in flight; a second worker then acquires the lock, and the first worker's unconditional `finally` delete removes the *second* worker's lock, cascading to a third.
What breaks in production: under any batch that hits timeouts, several workers dispatch simultaneously with no mutual exclusion at all, so the lock provides the appearance of serialization while delivering nothing of the kind.
Correction to what was already reported: the titles state the lock has "no TTL" and "can wedge dispatch permanently". That is wrong about the code — `expire(LOCK_KEY, 60)` is present. The permanent-wedge window is only the crash between `set` and `expire`; the routine failure is the opposite one, expiry *too early*, which the existing titles do not describe.
Fix: replace `_acquire_lock` with a single atomic `SET LOCK_KEY <token> NX EX <ttl>` where `<token>` is a per-worker `uuid4()`, and release with the compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete a lock it still owns. Set `ttl` from the worst case the code actually admits — `MAX_ATTEMPTS * REQUEST_TIMEOUT + sum(backoff_for(i) for i in range(1, MAX_ATTEMPTS))` — and renew it from the loop at `ttl/3` while the batch runs, rather than hardcoding a second magic number. Preserve: a crashed worker must still release within `ttl`; do not fix this by removing the expiry. Red-prove each clause separately by execution: (a) acquire in worker A, attempt acquire in worker B, assert `False`; (b) let the TTL lapse in A and assert A's release is a no-op that leaves B's lock intact; (c) kill A without release and assert B acquires after `ttl`. Pin the allow side: a single worker with no contention must still acquire on every poll — a fix that always returns `False` satisfies every other clause. Fail loudly: if redis is unreachable, `_acquire_lock` must raise rather than return `False` forever, so "cannot check the lock" is not spelled like "someone else holds it". Boundary and tie: two workers whose `SET NX` land in the same millisecond — exactly one must win, and the loser must not delete.

### Major: registering an egress endpoint is authorized at the same level as reading a profile
File: app/api/routes/settings.py — `create_webhook_endpoint`, `user: CurrentUser = Depends(current_user)`
What is wrong: this is the first state-changing route in the file, and it grants a caller the power to have every future `invoice.paid` / `invoice.payment_failed` / `subscription.updated` payload for the whole organization POSTed to a URL the caller chooses — yet it is guarded by exactly the same dependency as the read-only `get_profile` and `list_api_keys` in the same hunk, with no role, scope, or permission check.
What breaks in production: any authenticated member of an organization, including the lowest-privileged one, can stand up a permanent, self-service copy of the organization's billing event stream to an external host, and because the endpoint is created by the same call that returns the signing secret there is no second party in the loop.
Fix: gate `create_webhook_endpoint` behind the organization-admin/owner check the codebase already uses for privileged settings mutations (the same dependency that guards API-key creation), and record `created_by_user_id` on `WebhookEndpoint` plus an audit log line naming the actor, the org, and the URL. Preserve: the route must still succeed for an admin with a valid HTTPS URL and still return 201 with the secret — do not fix this by making the route unreachable. Red-prove each clause separately by execution: (a) a non-admin member posting a valid body gets 403 and no `webhook_endpoints` row exists afterwards (assert the row count, not only the status — a status-only assertion passes against a handler that 403s after inserting); (b) an admin posting the same body gets 201 and exactly one row; (c) remove the role dependency and assert (a) reds. Fail loudly: if the role of the caller cannot be resolved (missing membership row), return 403, not 200 — an unresolvable principal must not fall through to the permissive branch. Boundary and tie: a user holding the role in a *different* organization than `user.org_id` must be denied; state that the check is on the membership for `user.org_id`, not on any role the user holds anywhere.
Question that would close this: if the product has no role model at all and every member is intentionally an admin, the role clause is answered and the audit-log and `created_by_user_id` clauses still stand.

### Major: the endpoint lookup on the synchronous dispatch path has no supporting index
File: migrations/0042_webhook_delivery.sql — `CREATE TABLE webhook_endpoints` (no index on `org_id`) versus `enqueue_for_event` in app/webhooks/delivery.py
What is wrong: the migration indexes `webhook_deliveries` twice but creates no index on `webhook_endpoints (org_id)`, while `enqueue_for_event` runs `WHERE org_id = ? AND active IS TRUE` on that table for every dispatched event and `list_webhook_endpoints` runs the same predicate per request — the same "index the hot query" pattern the author applied to the deliveries table was not propagated to the endpoints table (R3).
What breaks in production: because `dispatch` awaits `enqueue_for_event` inline, every `invoice.paid` in the system pays a sequential scan over all endpoints of all organizations, so event-dispatch latency degrades with total customer count rather than with the customer's own endpoint count.
Fix: add `CREATE INDEX idx_webhook_endpoints_org_active ON webhook_endpoints (org_id) WHERE active;` to the same migration, matching the predicate `enqueue_for_event` uses; keep the plain `(org_id)` shape rather than a partial index if the listing route must also serve inactive endpoints — `list_webhook_endpoints` does not filter on `active`, so the non-partial `CREATE INDEX idx_webhook_endpoints_org ON webhook_endpoints (org_id);` is the form that serves both call sites and is the one to ship. Preserve: the existing `idx_webhook_deliveries_status` must stay; this is an addition, not a re-shuffle. Red-prove each clause separately by execution: (a) `EXPLAIN` the `enqueue_for_event` predicate on a seeded table and assert `Index Scan` appears where `Seq Scan` did; (b) `EXPLAIN` the `list_webhook_endpoints` predicate and assert the same index is chosen; (c) drop the index and assert both assertions red. Pin the allow side: an org with zero endpoints must still return an empty list rather than erroring, and the migration must still apply forward on an empty database. Fail loudly: if the migration runner cannot create the index (name collision), it must abort the transaction rather than log and continue — the `BEGIN/COMMIT` already present gives this, so do not move the statement outside it. Boundary: an endpoint row with `active = FALSE` must be excluded by `enqueue_for_event` and included by the listing route; the non-partial index keeps both correct.

### Minor: correction — the deliveries route has no pagination at all, not broken pagination
File: app/api/routes/settings.py — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: the already-reported titles describe pages that "skip and repeat rows" and a cursor built on a non-unique key, but the route exposes no cursor and no offset — it can only ever return the newest `limit` rows, so older deliveries are unreachable through the API entirely; the non-total ordering on `created_at` additionally makes even that top-N unstable across two identical calls.
What breaks in production: a customer debugging a delivery that failed an hour ago cannot retrieve it once `limit` newer attempts exist, and `docs/webhooks.md`'s "returns the most recent attempts" is the only reason this is not also a contract breach.
Fix (optional at Minor): add a keyset cursor over `(created_at, id)` — accept `before_created_at` and `before_id`, order by `created_at DESC, id DESC`, and include both fields in `WebhookDelivery.to_dict()` so the client can build the next cursor; a row sharing `created_at` with the cursor is included only when its `id` is strictly lower, which is the tie rule that makes the page boundary total.

### Minor: `webhook_deliveries` stores a full copy of every payload with no retention path
File: migrations/0042_webhook_delivery.sql — `payload JSONB NOT NULL`, `response_body TEXT` on `webhook_deliveries`
What is wrong: the table stores one full copy of the event payload per endpoint per event plus the response body, and the change adds no pruning job, partitioning, or retention column — the only deletion path is the `ON DELETE CASCADE` from `webhook_endpoints`.
What breaks in production: the table grows without bound at (events × active endpoints) and becomes the largest table in the database, with no operational path to trim it that does not involve deleting customers' endpoints.
Fix (optional at Minor): store `event_id` and read the payload from the `events` table at send time instead of duplicating it, or add a scheduled `DELETE FROM webhook_deliveries WHERE status IN ('delivered','failed_permanent') AND updated_at < now() - interval '30 days'` with a supporting index on `(status, updated_at)`; a row whose `updated_at` is exactly at the boundary is retained.
