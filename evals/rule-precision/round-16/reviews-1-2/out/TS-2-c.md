### Major: `UNIQUE (event_id)` does not lose the second endpoint — it loses *every* delivery for the event, silently (correction)
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`; `app/webhooks/delivery.py` — `enqueue_for_event`; `app/events/dispatcher.py` — the `except Exception` around `enqueue_for_event`
What is wrong: The already-reported "fan-out to a second endpoint is impossible" understates the defect — `enqueue_for_event` builds all rows in one list and `session.add_all(rows)` inside a single `session_scope()`, so the unique violation aborts the whole transaction rather than dropping one row, and the dispatcher's blanket `except Exception` then converts the `IntegrityError` into a `log.warning`.
What breaks in production: An organization with two or more matching active endpoints receives **zero** webhooks for every event — not "one of two" — and the only trace is a warning line, so the feature reads as working for single-endpoint test tenants and is totally dead for the multi-endpoint customers who paid for it.
Fix: Replace `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)` with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, and mirror it on the model as `__table_args__ = (UniqueConstraint("endpoint_id", "event_id"),)` so DDL and ORM cannot drift again. Insert via `postgresql.insert(WebhookDelivery).values(rows).on_conflict_do_nothing(index_elements=["endpoint_id", "event_id"])` so a redelivered event is idempotent per endpoint instead of aborting its peers. *Preserve*: the at-most-one-row-per-(endpoint,event) guarantee the original index was reaching for — do not fix this by deleting the unique index. *Allow side, pinned*: one event with three matching active endpoints inserts exactly three rows and `enqueue_for_event` returns `3`; *deny side*: calling `enqueue_for_event` twice for the same `event_id` still leaves three rows. *Boundary and tie*: two endpoints of the same org with byte-identical `url` each get their own row (the key is `endpoint_id`, not `url`); an endpoint deleted and recreated gets a fresh id and therefore a fresh row, which is the intended behaviour and must be asserted. *Fail loudly*: change the dispatcher handler to `log.exception("webhook enqueue failed for event %s", event_id)` and increment a `webhook_enqueue_failed` counter — "enqueued nothing" must not be spelled the same as "enqueued". *Red-prove by execution, one mutation per clause*: (a) revert the index to `(event_id)` → the three-endpoint test reds with `IntegrityError`; (b) remove `on_conflict_do_nothing` → the double-dispatch test reds; (c) revert the handler to `log.warning` without the counter → the "enqueue failure is observable" assertion reds.

### Major: `deliver` dereferences the endpoint without checking it exists, and the resulting `AttributeError` kills the worker and abandons the rest of the batch
File: `app/webhooks/delivery.py` — `deliver` (`endpoint = session.get(m.WebhookEndpoint, delivery.endpoint_id)`) and `run_worker` (`await asyncio.gather(*[deliver(client, d) for d in batch])`)
What is wrong: `session.get` returns `None` when the endpoint row is gone (the migration's `ON DELETE CASCADE` on `endpoint_id` means a customer deleting an endpoint removes the rows a batch already claimed into memory), and the resulting `AttributeError` in `send_once` is not an `httpx.HTTPError`, so it escapes `deliver`'s `except`, escapes `asyncio.gather` (called without `return_exceptions=True`), and propagates out of `run_worker`'s `while True`.
What breaks in production: One customer deleting an endpoint mid-batch terminates the single dispatcher process permanently and leaves every other delivery in that batch stranded in `in_flight` with its coroutine orphaned mid-request — all webhooks for all organizations stop until someone restarts the worker.
Fix: In `deliver`, immediately after the load, fail closed: `if endpoint is None: log.error("delivery %s references missing endpoint %s", delivery.id, delivery.endpoint_id); _finish(delivery.id, "failed_permanent", delivery.attempts, None, "endpoint no longer exists"); return`. Add `return_exceptions=True` to the `asyncio.gather` call and log every returned exception with its delivery id. Add a `except Exception as exc:` arm *inside* `deliver`'s loop that routes the delivery to a terminal `_finish` rather than raising. *Preserve*: `httpx.HTTPError` must keep its existing retry path — do not collapse the two arms, or the fix removes the retry behaviour that made the feature useful. *Allow side, pinned*: a healthy delivery sharing the batch with the broken one still reaches `delivered` and the worker's `while True` survives to the next poll. *Deny side*: the delivery with the missing endpoint ends `failed_permanent`, never left `in_flight`. *Fail loudly*: the missing-endpoint and unexpected-exception paths both write a named `response_body` and log at `error` — an unrunnable attempt must not be recorded the same way as a successful one. *Boundary and tie*: the interval between `_claim_batch` committing `in_flight` and `deliver` loading the endpoint is the boundary; a row deleted inside it is finalized by this guard, and if two workers race the same row the loser's `_finish` is a last-writer-wins overwrite of the same terminal status. *Red-prove, one mutation per clause*: (a) delete the `None` guard → the missing-endpoint test reds with `AttributeError`; (b) delete `return_exceptions=True` → the "one failing delivery does not abandon its batch peers" test reds; (c) widen the new `except Exception` to swallow `httpx.HTTPError` too → the "connection error is retried up to `MAX_ATTEMPTS`" test reds.

### Major: `active` is consulted only at enqueue time, so deactivating an endpoint does not stop queued or retrying deliveries
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`m.WebhookEndpoint.active.is_(True)`) is the only reader of `active`; `_claim_batch` filters on `WebhookDelivery.status`/`next_attempt_at` only, and `deliver`/`send_once` never re-check it
What is wrong: The `active` flag is a decision taken at enqueue and never re-bound to the object the effectful POST actually uses (R51), and the interval between the two is unbounded — the delivery sits `pending` until `next_attempt_at`, then retries for up to `2+4+8+16` seconds of sleeps plus five 30-second request timeouts.
What breaks in production: A customer who discovers their endpoint is compromised, or whose secret has leaked, deactivates it and still watches signed payloads keep arriving — the only kill switch the API exposes for a single endpoint does not actually stop delivery, and the org-level `webhooks_enabled` column is read by nothing either.
Fix: Re-check at the moment of use in two places. In `_claim_batch`, join the endpoint and add `m.WebhookEndpoint.active.is_(True)` to the filter so deactivated endpoints' `pending` rows are never claimed. In `deliver`, after loading the endpoint and before the first `send_once`, add `if not endpoint.active: log.info("delivery %s skipped: endpoint %s deactivated", delivery.id, endpoint.id); _finish(delivery.id, "failed_permanent", delivery.attempts, None, "endpoint deactivated"); return`, and repeat the check at the top of each retry iteration so a deactivation mid-retry takes effect on the next attempt. *Preserve*: keep the `active` filter in `enqueue_for_event` — it keeps the queue small; this is a second check at the point of use, not a replacement, and removing it is not the fix. *Allow side, pinned*: an endpoint that is active throughout still delivers on the happy path and a re-activated endpoint's still-`pending` rows are claimed again on the next poll (this is the case a fix that always denies would break). *Deny side*: deactivating between two attempts stops the next one. *Boundary and tie*: the check is at attempt start, so an attempt already on the wire completes and is recorded — state that in the docs; a deactivation landing exactly between the `_claim_batch` commit and the `deliver` check is caught by the second guard, which is why both are needed. *Red-prove, one mutation per clause*: (a) drop the `deliver` check → "deactivating between attempts stops the retry" reds; (b) drop the `_claim_batch` join → "a deactivated endpoint's pending rows are not claimed" reds; (c) invert the `deliver` check to `if endpoint.active: return` → the happy-path delivery test reds, pinning the allow side.

### Major: the scheme guard is a prefix match on notation, and it admits plaintext `http://` that `docs/webhooks.md` promises is rejected
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: `docs/webhooks.md` states "Only `https://` URLs are accepted", but the guard tests a string *prefix* of the parsed scheme rather than the scheme itself, so `http://…` (plaintext) is accepted and so is any scheme spelled with an `http` prefix (`httpz://`, `http-evil://`) — a surface-form adjudication where the URL parser and the transport define the meaning (R47), paired with a doc claim stronger than the implementation (R49). This is distinct from the already-reported SSRF finding, which is about which *hosts* are reachable; this is about the *transport* and the false guarantee written next to it.
What breaks in production: A customer who registers `http://hooks.example.com` gets every event payload and its live `X-Acme-Signature` sent in cleartext across the network, where a passive observer can read the business data and replay the captured request verbatim (the timestamp is not covered by the MAC), while the documentation tells that customer plaintext was impossible.
Fix: Replace the prefix test with equality on the parsed scheme — `if parsed.scheme != "https" or not parsed.netloc: raise HTTPException(422, "url must be an https:// URL")` — and reject a URL carrying userinfo (`parsed.username or parsed.password`), since `send_once` logs `endpoint.url` and those credentials would land in the application log. Where a non-production deployment genuinely needs plaintext, gate it on an explicit config allow-list of hostnames rather than loosening the scheme test. In `docs/webhooks.md`, declare the class per R49: the scheme check is an *enforceable boundary* (equality against the parser's own output), while the destination check is at best a *best-effort tripwire* until the SSRF finding is closed — name that gap in the doc rather than leaving the reader to infer (a). *Preserve*: the documented example `https://hooks.example.com/acme` must still be accepted and `event_types` handling is untouched — do not fix this by deleting the endpoint-creation route's flexibility wholesale. *Fail loudly*: a URL `urlparse` cannot decompose (raises `ValueError`) must return 422 with a distinct detail string, not fall through to acceptance — "could not parse" must not be spelled the same as "parsed and allowed". *Boundary and tie*: `HTTPS://hooks.example.com` is accepted because `urlparse` lower-cases the scheme; `https:/nohost` has an empty `netloc` and is rejected; `https://user:pw@host` falls on the reject side by the userinfo rule above. *Red-prove, one mutation per clause*: (a) `http://hooks.example.com` → expect 422 (reds against the current `startswith`); (b) `httpz://hooks.example.com` → expect 422; (c) `https://hooks.example.com/acme` → expect 201, the allow-side pin that a fix rejecting everything would fail; (d) `https://u:p@hooks.example.com` → expect 422.

### Major: the migration creates no index for the deliveries listing query and leaves both foreign keys unindexed
File: `migrations/0042_webhook_delivery.sql` — the only indexes created are `idx_webhook_deliveries_status` and `idx_webhook_deliveries_event`
What is wrong: `list_deliveries` queries `WHERE endpoint_id = ? ORDER BY created_at DESC LIMIT ?` and `enqueue_for_event` queries `webhook_endpoints WHERE org_id = ? AND active`, but no index covers either, and the two `REFERENCES … ON DELETE CASCADE` columns (`webhook_deliveries.endpoint_id`, `webhook_endpoints.org_id`) are unindexed, which PostgreSQL does not create automatically. (This is a different index from the already-reported claim-query one, which concerns `idx_webhook_deliveries_status`.)
What breaks in production: `webhook_deliveries` grows at events × endpoints and is append-only, so the customer-facing deliveries route degrades into a sequential scan plus a full sort of the whole table on every call, and deleting a single endpoint or organization scans the same table while holding row locks — the API route times out and the delete blocks the dispatcher.
Fix: Add to the same migration `CREATE INDEX idx_webhook_deliveries_endpoint_created ON webhook_deliveries (endpoint_id, created_at DESC, id DESC);` and `CREATE INDEX idx_webhook_endpoints_org ON webhook_endpoints (org_id, active);`. Because this migration also creates the tables, plain `CREATE INDEX` inside the transaction is correct here; any follow-up index added to a populated table must use `CREATE INDEX CONCURRENTLY` outside a transaction block. *Preserve*: leave `idx_webhook_deliveries_status` in place — it is the claim query's index and dropping it is not part of this fix. *Allow side, pinned*: `EXPLAIN (ANALYZE)` of the listing query against a seeded table shows `Index Scan using idx_webhook_deliveries_endpoint_created` with no `Sort` node, and the query still returns the same rows in the same order as before the index (an index that changes the result set is not a fix). *Deny side*: deleting an endpoint with 10k deliveries completes without a `Seq Scan` on `webhook_deliveries` in the cascade plan. *Fail loudly*: assert on the `EXPLAIN` plan in a migration test rather than on wall-clock time — a timing assertion that passes on an empty table is "examined nothing" spelled as "found nothing". *Boundary and tie*: `created_at` is not unique (fan-out inserts every row for one event in a single statement, so they share a timestamp), which is why the trailing `id DESC` is in the index — it gives the ordering a total order (R57) so a keyset page boundary cut through equal `created_at` values can neither skip nor repeat a row. *Red-prove, one mutation per clause*: (a) drop the deliveries index → the `EXPLAIN`-plan assertion reds with `Seq Scan`; (b) drop `id DESC` from the index and page through rows sharing one `created_at` → the "no row appears twice across pages" assertion reds; (c) drop `idx_webhook_endpoints_org` → the endpoint-lookup plan assertion reds.

### Minor: the migration takes `ACCESS EXCLUSIVE` on `organizations` inside the same transaction as the table creations, with no lock timeout
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE;` between `BEGIN;` and `COMMIT;`
What is wrong: The `ALTER` needs an `ACCESS EXCLUSIVE` lock on the busiest table in the schema and holds it until `COMMIT`, and because no `lock_timeout` is set the statement waits behind any open transaction while every query arriving after it queues behind the waiter.
What breaks in production: A single long-running read on `organizations` during deploy turns this migration into a lock convoy that stalls `get_profile` and every other org-scoped route — including the two other routes added in this very diff — for as long as the blocking transaction runs.
Fix: Set `SET LOCAL lock_timeout = '3s';` immediately after `BEGIN;` so the migration fails fast and retries rather than queueing, and move the `ALTER TABLE organizations` into its own transaction after the `CREATE TABLE` statements so a lock wait does not also hold the new tables uncommitted. The column already carries a `DEFAULT`, so on PostgreSQL 11+ the rewrite cost is zero and only the lock acquisition is at issue.

### Minor: `STATUSES` is declared and never used, which is why the status vocabulary is spelled three different ways (root cause of a reported finding)
File: `app/webhooks/models.py` — `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")`
What is wrong: The constant is exported by the new module and referenced nowhere in the diff, while `delivery.py` re-spells the same four values as bare literals (`"pending"` in `_claim_batch`, `"in_flight"`, `"delivered"`, `"failed_permanent"` in `deliver`) and the migration spells the fourth one differently again as `'failed'` (R2). The already-reported "CHECK constraint rejects the status the code writes" is the symptom; the absent single source of truth is the mechanism, and fixing only the CHECK leaves the next status addition free to drift the same way.
What breaks in production: The next status value added to one of the three spellings and not the others reproduces the same insert-time failure, which surfaces as swallowed webhook loss rather than as a migration error.
Fix: Derive the DDL constraint and the code from one definition — reference `STATUSES` from `WebhookDelivery` via `Enum(*STATUSES, name="webhook_delivery_status")` (or a `CheckConstraint` in `__table_args__` built from `STATUSES`), have `delivery.py` use named members instead of literals, and add a test that asserts the set the model declares equals the set the migration's CHECK permits so the two cannot diverge silently.

### Minor: `test_backoff_grows_exponentially` pins exact delays, which will red when the documented jitter is added
File: `tests/webhooks/test_delivery.py` — `@pytest.mark.parametrize("attempt,seconds", [(1, 2), (2, 4), (3, 8), (4, 16)])`
What is wrong: The test asserts `backoff_for(attempt).total_seconds() == seconds` exactly, encoding the absence of the jitter that `docs/webhooks.md` promises ("backoff is exponential with jitter").
What breaks in production: Nothing at runtime, but whoever implements the documented jitter sees four red tests and reads them as a regression, which is how the doc/code divergence gets closed in the wrong direction — by editing the doc instead of the backoff.
Fix: Assert the interval rather than the point — `assert base <= backoff_for(attempt).total_seconds() <= base * 1.5` with `base = 2 ** attempt` — so the test constrains growth without forbidding jitter, and name the tolerance bound in the test's name.
