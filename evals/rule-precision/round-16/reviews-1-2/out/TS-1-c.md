### Major: the only exception `deliver` handles is `httpx.HTTPError`, and both `_finish` calls sit outside the `try`, so the row stays `in_flight` forever
File: `app/webhooks/delivery.py` — `deliver` (the `try:` / `except httpx.HTTPError` block, and the two `_finish(...)` calls)
What is wrong: the `try` covers only `send_once`, and `except httpx.HTTPError` catches only transport errors, so every other exception raised on that path — `session.get(m.WebhookEndpoint, delivery.endpoint_id)` returning `None` and then `endpoint.signing_secret` raising `AttributeError` inside `send_once`; `DetachedInstanceError` on the same access because the `session_scope()` around that `get` has already closed; `TypeError` from `json=delivery.payload` when the JSONB round-trips a value httpx cannot encode; and the `IntegrityError` that `_finish(delivery.id, "failed_permanent", ...)` is *guaranteed* to raise against the migration's `CHECK (status IN (..., 'failed'))` — escapes `deliver` entirely without ever reaching a `_finish` call.
What breaks in production: the delivery that raised is left in `in_flight`, which `_claim_batch` never selects again (it filters `status == "pending"`), so that event is silently never delivered and never retried — and because the raise propagates out of `asyncio.gather`, the other 99 deliveries in the same batch that had already been flipped to `in_flight` by `_claim_batch` are abandoned in the same unrecoverable state.
Correction to the reported list: "one failing delivery aborts the batch" names the `asyncio.gather` mechanism, and the obvious remedy for it — `return_exceptions=True` — does *not* fix this. It stops the sibling coroutines from being cancelled but still leaves the raising row in `in_flight` with no terminal write, because the failure never reaches `_finish`. The list's `in_flight`-has-no-sweeper findings describe the symptom; this is a second, deterministic producer of it that a sweeper alone would paper over on every single `failed_permanent` delivery.
Fix: in `deliver`, widen the guarded region to the whole attempt and make the terminal write unconditional. (a) Fetch the endpoint inside `deliver`'s loop with an explicit absence check — `endpoint = session.get(m.WebhookEndpoint, delivery.endpoint_id)`; `if endpoint is None or not endpoint.active: _finish(delivery.id, "failed_permanent", attempt, None, "endpoint missing or inactive"); return` — and read `endpoint.url` / `endpoint.signing_secret` into locals *inside* that `session_scope`, so nothing detached is dereferenced later. (b) Change `except httpx.HTTPError as exc` to `except Exception as exc` with `status_code, detail = None, f"{type(exc).__name__}: {exc}"`, keeping the existing `httpx.HTTPError` branch first so transport errors still record their own message — do not delete the narrower branch or the `detail` text, since that string is what makes a failed delivery diagnosable in the deliveries listing. (c) Wrap the whole body of `deliver` in `try/finally`, and in the `finally` write a terminal status if none was written: `if not finished: _finish(delivery.id, "failed_permanent", attempt, None, "worker aborted: <exc class>")`, and log that branch at ERROR with the delivery id — an exception the worker cannot classify must be spelled differently from a clean permanent failure, never as silence. (d) Pass `return_exceptions=True` to the `asyncio.gather` in `run_worker` so one row cannot cancel its siblings, and log every returned exception. Allow side that must still pass: a 2xx response still writes `status="delivered"` with `response_status=200` and returns after one attempt, and a 500 followed by a 200 still writes `delivered` with `attempts=2` — pin both. Boundary: `attempt >= MAX_ATTEMPTS` must remain the tie — attempt 5 writes `failed_permanent` and does *not* sleep; attempt 4 sleeps and retries. Red-prove each clause separately by execution, one mutation each: (a) make `session.get` return `None` and assert the row is `failed_permanent`, not `in_flight`; (b) make the transport raise `ValueError` and assert the same; (c) make `_finish` itself raise on the first call and assert the ERROR log fires and the batch's other rows still finish; (d) make one of two gathered deliveries raise and assert the other still reaches `delivered`. Each mutation must redden a different assertion. Note this fix does not remove the need for the `CHECK`-constraint fix already reported — until the constraint admits `failed_permanent`, clause (c) converts a crash into a permanent ERROR log on every exhausted delivery rather than a correct terminal write.

### Major: a raising in-process subscriber skips the webhook enqueue entirely, after the event has already been committed
File: `app/events/dispatcher.py` — `dispatch`, the `for subscriber in SUBSCRIBERS.get(envelope.type, ()): await subscriber(envelope)` loop preceding the new `if envelope.type in WEBHOOK_EVENT_TYPES:` block
What is wrong: the new webhook enqueue was appended *after* the pre-existing unguarded subscriber loop, so any subscriber that raises propagates out of `dispatch` before `enqueue_for_event` is ever called — and unlike the enqueue itself, that path has no `try/except` at all, so it is not even reached by the (separately reported) swallowing handler.
What breaks in production: the `Event` row is already committed by the time the subscriber loop runs, so an unrelated in-process subscriber — an analytics hook, a cache invalidator — failing on one event permanently drops the customer-visible webhook for that event, with no delivery row, no retry, and nothing in the log tying the missing webhook to the subscriber that failed. This is R4/R9: the mutation is committed and its notification side-effect is sequenced behind unrelated work that can abort it.
Fix: move the `if envelope.type in WEBHOOK_EVENT_TYPES:` block to immediately after the `with session_scope()` block that produces `event_id`, ahead of the subscriber loop, and independently guard each subscriber: `for subscriber in ...: try: await subscriber(envelope) except Exception: log.exception("subscriber %s failed for event %s", subscriber, event_id)`. Do not delete the existing enqueue `try/except` while doing this — reordering does not make the enqueue infallible, and the separately-reported requirement to persist a retryable record instead of swallowing still applies to it. Allow side to pin: an event whose subscribers all succeed still produces exactly the same delivery rows and still returns `event_id`; and a subscriber that raises now still lets `dispatch` return `event_id` normally. Boundary and tie: for an event type in `WEBHOOK_EVENT_TYPES` with zero registered endpoints, the reorder must be a byte-identical no-op (`enqueue_for_event` returns 0, no rows, no log noise). Red-prove by execution, one mutation per clause: (i) register a subscriber that raises and assert the delivery rows still exist — this must fail against the current ordering; (ii) register a subscriber that raises and assert `dispatch` still returns the event id; (iii) register two subscribers where the first raises and assert the second still ran.

### Major: the dispatch lock's 60s TTL is unconditionally shorter than the batch it protects
File: `app/webhooks/delivery.py` — `_acquire_lock` (`await redis_client.expire(LOCK_KEY, 60)`) against `run_worker` / `deliver`
What is wrong: the lock's TTL is a fixed 60 seconds while the work it serialises has no bound anywhere near it — `BATCH_SIZE = 100` deliveries, `REQUEST_TIMEOUT = 30.0`, `MAX_ATTEMPTS = 5`, and a blocking `time.sleep` in `deliver` that serialises the `asyncio.gather` so the batch runs one delivery at a time; a single slow endpoint costs up to `5 × 30s` of timeouts plus `2+4+8+16 = 30s` of backoff, so one row can hold the lock for ~3 minutes and a full batch for hours.
What breaks in production: the lock expires while the first worker is still mid-batch, a second worker enters and starts claiming, and when the first worker finally reaches its `finally: await redis_client.delete(LOCK_KEY)` it deletes the *second* worker's lock, admitting a third — so under any real endpoint latency the mutual exclusion the lock exists to provide is absent for essentially the whole run, not just in a rare window.
Correction to the reported list: "the dispatch lock ... can wedge with no TTL" is factually wrong about the code — `_acquire_lock` does call `expire(LOCK_KEY, 60)`. The genuine TTL defect is the opposite of a wedge: the TTL is too *short* for the critical section, so the lock releases itself mid-batch. (A wedge is still reachable, but only in the narrow window where the process dies between the `set` and the `expire`.) A fix written against the list's description — "add a TTL" — would leave this defect in place untouched.
Fix: replace the check-then-act pair with a single atomic acquire that carries a unique owner token and a TTL derived from the work, and release only if still owned. Concretely: `token = uuid4().hex`; `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)`; define `LOCK_TTL_SECONDS` from the actual worst case rather than a constant guess — `BATCH_SIZE * (MAX_ATTEMPTS * REQUEST_TIMEOUT + sum(backoff_for(i).total_seconds() for i in range(1, MAX_ATTEMPTS)))` — and, because that number is hours, renew it from `run_worker` on a heartbeat (`await redis_client.expire(LOCK_KEY, LOCK_TTL_SECONDS)` every `LOCK_TTL_SECONDS // 3`) so a dead worker's lock still expires. Release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) rather than the unconditional `delete`, so a worker can never drop a successor's lock. Do not delete the TTL to solve the expiry — an untimed lock trades this defect for a permanent wedge on worker crash. Fail loudly when the check cannot run: if the Redis call raises or returns something other than `True`/`None`, treat it as *not acquired*, log at ERROR, and sleep — "could not determine lock state" must not be spelled the same as "lock is free". Allow side to pin: a single worker with a free lock still acquires on the first poll and still processes a batch end to end; and after that worker exits cleanly the next `_acquire_lock` still succeeds (the compare-and-delete must actually delete when the token matches). Boundary and tie: two workers calling `_acquire_lock` at the same instant — exactly one gets `True` from `SET NX`, the other must take the sleep branch and must not renew or delete. Red-prove each clause by execution: (i) two concurrent `_acquire_lock` calls, assert exactly one `True`; (ii) worker A acquires, expire the key manually, worker B acquires, then run A's release — assert B's token still holds the key; (iii) stub the Redis client to raise and assert the ERROR log fires and no batch is claimed.

### Major: `webhook_endpoints` gets no index on `org_id`, and `enqueue_for_event` filters on it for every dispatched event
File: `migrations/0042_webhook_delivery.sql` — `CREATE TABLE webhook_endpoints` (both `CREATE INDEX` statements target `webhook_deliveries`), against `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: the migration creates two indexes and both are on `webhook_deliveries`; `webhook_endpoints` is left with only its primary key, yet `enqueue_for_event` runs `WHERE org_id = ? AND active IS TRUE` against it on every `invoice.paid` / `invoice.payment_failed` / `subscription.updated` dispatch, and `list_webhook_endpoints` runs the same `org_id` predicate on every settings page load.
What breaks in production: every billing event pays a sequential scan of the whole cross-tenant endpoints table inside the request path (`dispatch` is awaited by the caller), so the cost of dispatching one org's event grows with the number of endpoints every *other* org has registered — and since nothing caps endpoints per org, one customer registering aggressively degrades event dispatch for all of them.
Cross-cutting check: the same index pattern is missing in exactly one place and present in none — the diff indexes `webhook_deliveries (status)` and `webhook_deliveries (event_id)` but nothing on `webhook_endpoints`, even though `org_id` is the only column either new query filters on. The codebase already demonstrates the tenant-scoped query shape being indexed elsewhere in this same file's context: `list_api_keys` in `app/api/routes/settings.py` filters `ApiKey.org_id == user.org_id` with `.order_by(ApiKey.created_at.desc())`, the identical access pattern.
Fix: add `CREATE INDEX idx_webhook_endpoints_org_active ON webhook_endpoints (org_id) WHERE active;` to `migrations/0042_webhook_delivery.sql`, inside the existing `BEGIN;`/`COMMIT;`. Use the partial form so the index tracks only rows `enqueue_for_event` can select; keep `org_id` as the leading column so `list_webhook_endpoints` (which does *not* filter on `active`) is not served by it and instead gets a plain `(org_id)` index — if you would rather carry one index, drop the `WHERE active` predicate and index `(org_id, active)`, which serves both queries at the cost of indexing deactivated rows. Do not "fix" this by narrowing `enqueue_for_event`'s query to skip the `active` filter; that filter is the only thing that stops a deactivated endpoint from receiving events. Allow side to pin: `EXPLAIN` on `SELECT ... FROM webhook_endpoints WHERE org_id = $1 AND active` must show an index scan *and* return the identical row set it returns today — assert row-for-row equality on a fixture with active and inactive endpoints across two orgs, not just the plan. Boundary and tie: an org with zero endpoints must still return an empty list and must not error; an org whose endpoints are all inactive must return empty, not all of them. Red-prove separately: (i) drop the index and assert the plan assertion reds; (ii) flip one endpoint to `active = false` and assert it disappears from the result — this reddens if the predicate were dropped in the name of index use.

### Minor: `list_webhook_endpoints` has no bound at all, while its sibling route in the same file got one
File: `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: the sibling route added in the same commit, `list_deliveries`, takes `limit: int = Query(50, ge=1)`, but `list_webhook_endpoints` calls `.all()` with no limit, no offset, and no ordering.
What breaks in production: an org with a large number of registered endpoints (nothing in the change caps that) gets the entire set serialised into one response on every settings page load, and because there is no `order_by` the row order is whatever the planner returns, so the list reshuffles between refreshes.
Cross-cutting note: this is the same unbounded-result pattern the list already flags on `list_deliveries`' missing *ceiling* — but there the bound exists and is merely open-ended upward, whereas here it is absent entirely, and no reported finding names this route.

### Minor: the deliveries listing returns no attempt timestamp, so "most recent attempts" cannot be read from it
File: `app/webhooks/models.py` — `WebhookDelivery.to_dict`
What is wrong: `to_dict` returns `next_attempt_at` but omits both `created_at` and `updated_at`, while `list_deliveries` orders by `created_at.desc()` and `docs/webhooks.md` promises "the most recent attempts for an endpoint ... including the response status we saw and when the next attempt is scheduled".
What breaks in production: a customer debugging a missed webhook sees an ordered list with no timestamp on any row — and for a terminal `delivered` / `failed_permanent` row, `next_attempt_at` still holds the enqueue-time value, so the one timestamp present is actively misleading about when the attempt happened.

### Minor (question): is there a retention or archival job for `webhook_deliveries` that this migration should hook into?
File: `migrations/0042_webhook_delivery.sql` — `CREATE TABLE webhook_deliveries` (`payload JSONB NOT NULL`, `response_body TEXT`)
What is wrong: the table stores a full copy of the event payload per endpoint per event plus the response body, is written on every billing event, and the migration adds no partitioning, no retention column, and no TTL — but a retention job living outside this diff would close it.
What breaks in production: if no such job exists, the table grows without bound with the largest columns in the schema, and `idx_webhook_deliveries_status` — a low-cardinality index over every historical row — degrades the worker's claim query as terminal rows accumulate. What would close this: pointing at an existing retention or partition-management job that already covers new tables, or naming the retention window this table is expected to keep.
