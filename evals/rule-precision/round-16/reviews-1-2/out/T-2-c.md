### Critical: nothing in the change ever starts `run_worker`, so every enqueued delivery sits in `pending` forever
File: `app/webhooks/delivery.py` — `run_worker` (and `docs/webhooks.md`, "Retries")
What is wrong: `run_worker` is a brand-new symbol in a brand-new module, and the change wires no caller for it — the only new importer of `app.webhooks.delivery` is `app/events/dispatcher.py`, which calls `enqueue_for_event` and nothing else; there is no `if __name__ == "__main__"` guard, no console-script/entrypoint declaration, and no service or process declaration anywhere in the eight changed files.
What breaks in production: the feature ships in the "declared but never backed" shape of R41 (Critical: the declared path never worked at all) — `POST /webhook-endpoints` succeeds, `dispatch()` writes delivery rows, `docs/webhooks.md` promises "we POST every subscribed event", and not one request is ever sent, while `webhook_deliveries` grows without bound and the deliveries endpoint reports `pending` forever.
Note on grounding: a pre-existing supervisor cannot be the missing wiring, because the module and the symbol it would name are created by this diff.
Fix: add the deployment shape in this commit — an `async def main()` in `app/webhooks/delivery.py` under `if __name__ == "__main__": asyncio.run(main())` that logs a declared R32 ready signal (`log.info("webhook worker ready (poll=%s, batch=%s)", poll_interval, BATCH_SIZE)`) *before* entering the loop, plus the process declaration alongside the existing API process so the artifact actually boots in its deployed shape. Allow side: a boot smoke test must assert both that the ready line appears within 10s **and** that one enqueued delivery against a local receiver reaches `status="delivered"` — a worker that boots and delivers nothing must not read as green. Red-prove each clause separately by execution: (a) remove the process declaration → the ready-signal grep fails; (b) stub `_claim_batch` to return `[]` → the end-to-end `delivered` assertion reds while the ready line still appears; (c) point the worker at an unreachable Redis → assert the named failure below, not a silent idle. Fail loudly: at boot, probe Redis and the DB and, on failure, log `webhook worker: dependency unreachable (%s)` and exit non-zero — "cannot reach Redis" must not be spelled the same as "no deliveries due", which is exactly what today's `_acquire_lock`-returns-false path would do. Do not fix by deleting what makes it useful: do not call `run_worker()` from a FastAPI startup hook, which runs one worker per API replica and multiplies the contention in the next finding — keep the worker a separate process. Boundary and tie: when N replicas boot at the same instant exactly one acquires `LOCK_KEY` and the losers must idle at `poll_interval`, never exit; state that in the smoke test with N=2.

### Major: `deliver` dereferences the endpoint row without checking it exists — the same defect already reported in `_finish`, at a location with a worse blast radius
File: `app/webhooks/delivery.py` — `deliver`, `endpoint = session.get(m.WebhookEndpoint, delivery.endpoint_id)`
What is wrong: cross-cutting check of the reported `_finish` null-dereference finds the identical unchecked `session.get` in `deliver`, and it is also missing the `active` predicate that `enqueue_for_event` applies at enqueue time (`m.WebhookEndpoint.active.is_(True)`), so a row deleted or deactivated between enqueue and claim reaches `send_once` as `None`.
What breaks in production: `None.signing_secret` raises `AttributeError`, which is not an `httpx.HTTPError` and so escapes the `try`, propagates out of `asyncio.gather`, kills the worker for good, and leaves the whole claimed batch stranded in `in_flight` — a strictly larger failure than the reported `_finish` case, which at least happens after the request went out.
Fix: guard the load and route it to a terminal state — `if endpoint is None or not endpoint.active: _finish(delivery.id, "failed_permanent", delivery.attempts, None, "endpoint missing or inactive"); return` — and pass `return_exceptions=True` to the `asyncio.gather` in `run_worker`, logging each returned exception, so one poisoned delivery cannot take the batch down. Allow side: an existing, `active=True` endpoint must still deliver and still land `delivered`; pin it with the MockTransport shape already present in `tests/webhooks/test_delivery.py::test_send_once_posts_the_signed_payload`, extended to call `deliver`. Red-prove each clause separately: (a) delete the `is None` branch and run a case whose `endpoint_id` has no row → the assertion that the row reaches `failed_permanent` reds with `AttributeError`; (b) delete the `not endpoint.active` clause and run with `active=False` → reds; (c) delete `return_exceptions=True` and run a batch of two where one raises → the "the healthy delivery still reaches `delivered`" assertion reds. Fail loudly: the guard writes a distinguishable `response_body` detail and logs at warning — "endpoint vanished" must not be recorded the same way as a `delivered` row with an empty body. Do not fix by deleting what made it visible: do not widen `except httpx.HTTPError` to a bare `except Exception` around `send_once` — that swallows the same `AttributeError` into the retry loop and re-hides it; the row must reach a terminal state. Boundary and tie: the endpoint deleted *exactly* between `_claim_batch` and this `session.get` is the boundary case — the row is already `in_flight`, so the branch must move it to a terminal state; two workers racing the same delivery id must both converge on `failed_permanent`, so make the `_finish` write idempotent (last writer wins on the same value).

### Major: one global lock plus an in-process retry ladder means a single dead endpoint stalls every tenant's webhooks for minutes
File: `app/webhooks/delivery.py` — `run_worker` / `deliver` / `LOCK_KEY`, `MAX_ATTEMPTS`, `REQUEST_TIMEOUT`
What is wrong: `_claim_batch` takes up to `BATCH_SIZE = 100` rows across *all* organizations ordered only by `next_attempt_at`, `deliver` then runs the entire 5-attempt ladder inline before releasing its slot, and `run_worker` serializes all of this behind one global `LOCK_KEY` — so worst-case batch wall-clock is `5 x REQUEST_TIMEOUT (30s) + (2+4+8+16)s = 180s`, against a lock TTL of 60s set in `_acquire_lock`.
What breaks in production: one customer whose endpoint black-holes connections fills the batch with its own backlog and every other tenant's `invoice.paid` webhook waits three minutes behind it, while the 60s TTL expires two thirds of the way through every such batch so the mutual exclusion the lock exists to provide is simply absent for the remainder (distinct from the reported lock-atomicity defect: this one fires with a perfectly atomic lock).
Fix: make `deliver` perform exactly one attempt and return the row to the queue — on a retryable failure write `status="pending"`, `attempts=attempt`, `next_attempt_at=_now() + backoff_for(attempt)` and return, deleting the `while True` loop and the `time.sleep` with it; cap per-endpoint occupancy in `_claim_batch` so no single `endpoint_id` takes more than `BATCH_SIZE // 10` slots; and set `LOCK_TTL = ceil(BATCH_SIZE / CONCURRENCY) * REQUEST_TIMEOUT` with that derivation in a comment, refreshed once per iteration. Allow side: a batch holding one timing-out endpoint and one healthy endpoint must still deliver the healthy one within a single `poll_interval` — assert both the healthy row's `delivered` status and the elapsed wall clock. Red-prove each clause separately: (a) remove the per-endpoint cap, queue 100 rows for the dead endpoint plus one healthy row → the elapsed-time assertion reds; (b) restore the inline `while True` retry → the same assertion reds for a different reason (the slot is held, not the batch composition); (c) set `LOCK_TTL` below the derived budget → a test asserting the worker still owns the lock at batch end reds. Fail loudly: check lock ownership before the `finally` deletes it (store a per-worker token as the value and delete only on match) and log `webhook worker: lost lock mid-batch` — losing the lock must be reported, not silently papered over by deleting whatever key is there. Do not fix by deleting what made the feature useful: `MAX_ATTEMPTS = 5` and the 2/4/8/16 ladder must be preserved exactly as `docs/webhooks.md` states — moving retries onto the queue must not quietly change the schedule, and `backoff_for` stays the single source for it. Boundary and tie: a row whose `next_attempt_at` equals `now` is claimable (keep `<=`), and ties on equal `next_attempt_at` break on `id` so the per-endpoint cap selects deterministically rather than by planner whim.

### Major: `STATUSES` is declared as the status vocabulary and then used by nothing — the four literals are spelled out at five sites, which is how the CHECK constraint drifted (R2)
File: `app/webhooks/models.py` — `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")`
What is wrong: the tuple has no reader anywhere in the change, while the same values are re-typed as bare literals in `WebhookDelivery.status`'s `default="pending"`, `_claim_batch`'s `== "pending"` filter and `row.status = "in_flight"`, `deliver`'s `_finish(..., "delivered", ...)` and `_finish(..., "failed_permanent", ...)`, and the migration's `CHECK (status IN (...))`.
What breaks in production: the already-reported CHECK/code mismatch (`'failed'` vs `failed_permanent`) is the first symptom of this duplication rather than an isolated typo, and with no shared definition the next status added will drift the same way — the next `INSERT` violating the constraint takes down the delivery worker with an `IntegrityError` at write time.
Fix: define `PENDING = "pending"`, `IN_FLIGHT = "in_flight"`, `DELIVERED = "delivered"`, `FAILED_PERMANENT = "failed_permanent"` in `app/webhooks/models.py`, derive `STATUSES` from them, import and use them at every write and filter site in `delivery.py`, and add a schema-parity test that parses the `CHECK (status IN (...))` clause out of `migrations/0042_webhook_delivery.sql` and asserts its value set equals `set(models.STATUSES)`. Meaning check before merging (R2's own clause): all five sites name the same concept — the delivery row's lifecycle state — so consolidation is correct here; do **not** pull `WebhookEndpoint.active` or the dispatcher's `WEBHOOK_EVENT_TYPES` into the same constant set, since those are different concepts that merely live nearby. Allow side: every member of `STATUSES` must still be insertable — a test that writes each one against the real migrated schema (not a fake) must pass, which is also what proves the constraint was widened rather than narrowed. Red-prove each clause separately: (a) add a bogus member to `STATUSES` → the parity test reds; (b) change `_finish`'s literal to a string outside `STATUSES` → the insert test reds; (c) revert the migration's list to the current `'failed'` spelling → the parity test reds. Fail loudly: if the parity test cannot locate or parse a `CHECK` clause in the migration file, it must fail with "status CHECK constraint not found in 0042", never skip — "examined nothing" must not be spelled like "found nothing". Do not fix by deleting what made the defect visible: keep `in_flight` inside the constraint; narrowing the CHECK to the terminal statuses would make the parity test pass while breaking the claim path. Boundary and tie: the constraint is over the exact set, so adding a fifth state requires the constant and a migration in the same commit — say so beside `STATUSES`.

### Major: the two hottest new query predicates have no index — `webhook_endpoints(org_id)` and `webhook_deliveries(endpoint_id)`
File: `migrations/0042_webhook_delivery.sql` — the index block (`idx_webhook_deliveries_status`, `idx_webhook_deliveries_event`)
What is wrong: the migration creates exactly two indexes, both on `webhook_deliveries` and neither covering `endpoint_id`, and creates none at all on `webhook_endpoints` beyond the primary key, while `enqueue_for_event` filters `webhook_endpoints` on `(org_id, active)`, `list_webhook_endpoints` filters it on `org_id`, and `list_deliveries` filters `webhook_deliveries` on `endpoint_id` and sorts on `created_at DESC` (this is separate from the already-reported claim-query index defect, which concerns `status`/`next_attempt_at`).
What breaks in production: every dispatched `invoice.paid`/`invoice.payment_failed`/`subscription.updated` event sequentially scans the whole endpoint table on the synchronous request path, the deliveries route scans and sorts an unbounded, ever-growing table per call, and both `ON DELETE CASCADE` paths scan the child table per deleted parent, so an organization delete locks the deliveries table for the duration.
Fix: add to the same migration `CREATE INDEX idx_webhook_endpoints_org_active ON webhook_endpoints (org_id) WHERE active;` and `CREATE INDEX idx_webhook_deliveries_endpoint_created ON webhook_deliveries (endpoint_id, created_at DESC, id DESC);`. Allow side, measured not assumed: run `EXPLAIN (ANALYZE, BUFFERS)` for both queries against a table seeded to production scale and require `Index Scan` in each plan, and pin the write side too — the `POST /webhook-endpoints` and delivery-insert latencies must be re-measured after, since the fix adds index maintenance to the enqueue path this feature runs per event. Red-prove each index separately by execution: drop `idx_webhook_endpoints_org_active` → the endpoint-lookup plan assertion reds; drop `idx_webhook_deliveries_endpoint_created` → the listing plan assertion reds; two indexes, two mutations, two distinct failing assertions. Fail loudly: the plan harness must fail with "insufficient rows to plan" when the seeded table is small enough that the planner prefers a sequential scan regardless — a green from an empty table is the classic way this check reports success without having run. Do not fix by deleting what worked: keep `idx_webhook_deliveries_status` (or fold it into the corrected claim index deliberately and say so) — dropping it as "redundant" while the claim query still filters on `status` deoptimizes the worker. Boundary and tie: the `(created_at DESC, id DESC)` composite also gives the listing a total order, so a page cut through rows sharing a `created_at` value neither skips nor repeats — the ordering defect itself is already reported, and this index is what makes the corrected `ORDER BY` cheap rather than a sort of the whole table.

### Major: the URL check is a prefix match on the scheme, so plaintext `http://` — and any scheme merely beginning with "http" — is accepted against the documented HTTPS-only guarantee
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: `startswith("http")` is a surface-form test where `urlparse` and then httpx define the meaning (R47) — it admits `http` (cleartext), and also `httpfoo://`, `https-evil://` and any other scheme sharing the prefix — while `docs/webhooks.md` states "Only `https://` URLs are accepted", a claim stronger than the code (R49); this is the scheme axis, distinct from the already-reported host/redirect SSRF findings. Related, at the same predicate: `parsed.netloc` includes userinfo, so `https://user:secret@hooks.example.com` is accepted and those credentials are then written verbatim into the `log.info("POST %s headers=%s", endpoint.url, headers)` line in `send_once`.
What breaks in production: a customer (or any authenticated user in the org) can register an `http://` endpoint and every invoice and subscription payload, together with a currently valid signature header, crosses the network in cleartext where an on-path observer can read it and — since the timestamp is not covered by the MAC, as already reported — replay it verbatim.
Fix: replace the prefix test with set membership against the documented set and use the parsed host rather than the raw authority — `ALLOWED_SCHEMES = frozenset({"https"})` (with the `docs/webhooks.md` sentence cited beside it) and `if parsed.scheme.lower() not in ALLOWED_SCHEMES or not parsed.hostname or parsed.username or parsed.password: raise HTTPException(422, "url must be an https:// URL without embedded credentials")`. Allow side: the doc's own example `https://hooks.example.com/acme` must still return 201, and so must an https URL carrying a non-default port and a path — pin both, or the remedy is unmeasured in the direction that gets it reverted. Red-prove each clause separately: (a) `http://hooks.example.com` → 422 (reds if the scheme set is widened back to a prefix test); (b) `httpfoo://hooks.example.com` → 422 (this is precisely the input today's `startswith` admits, and it reds against no other clause); (c) `https://user:secret@hooks.example.com` → 422, plus an assertion that no stored `url` contains `@` (reds if only the scheme clause is implemented). Fail loudly: a value `urlparse` cannot decompose into a scheme and a host must be denied with the same 422 rather than falling through the predicate — an unparseable URL is the "cannot decide" case and it denies. Do not fix by deleting what made the feature useful: do not narrow this to a host allowlist or a suffix match, which would break every legitimate customer host; the scheme is the axis being closed here, and the internal-target problem is the separately reported one. Boundary and tie: the comparison is case-folded so `HTTPS://` is accepted, and where the doc and the code disagree the doc wins — if plaintext `http` must be supported for some tier, `docs/webhooks.md` changes in the same commit rather than the check quietly staying loose.

### Minor: model column types drift from the DDL beyond the already-reported timezone mismatch
File: `app/webhooks/models.py` — `WebhookDelivery.event_type` (`String(100)`), `created_at` / `updated_at`
What is wrong: `event_type` is declared `String(100)` against a DDL column of `TEXT`, and `created_at`/`updated_at` are nullable in the model against `NOT NULL` in the DDL, so the model's declared constraints are enforced by neither layer.

### Minor (question, per Finding Floor clause 2): is `app/webhooks/` intended as an implicit namespace package?
