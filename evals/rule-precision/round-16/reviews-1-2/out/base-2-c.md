### Critical: the bytes that are signed are not the bytes that are sent, so no customer can verify a delivery
File: `app/webhooks/signing.py` — `sign` / `serialize`, together with `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` computes the HMAC over `json.dumps(payload, sort_keys=True)` (spaces after `,` and `:`, keys sorted) while `send_once` hands the dict to `client.post(..., json=delivery.payload)`, which serializes it with httpx's own encoder (compact separators, insertion order), so the digest in `X-Acme-Signature` is a MAC of a string the receiver never sees.
What breaks in production: every customer following `docs/webhooks.md` ("HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`") computes a different digest and rejects 100% of deliveries, and the only in-repo test that would notice — `test_verify_accepts_signature_produced_by_sign` — re-serializes through the same `serialize()` on both sides, so it is an identity and stays green (R40 round-trip clause; RT1 identity clause).
Fix: make the signed string and the transmitted body the same object. In `signing.py` add `def canonical_body(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, change `sign` to take and return that body (`body = canonical_body(payload); mac = hmac.new(secret.encode(), b"%s.%s" % (timestamp.encode(), body), hashlib.sha256)`), and change `send_once` to `client.post(endpoint.url, content=body, headers={...})` with an explicit `Content-Type: application/json` — never `json=`, which re-encodes. Preserve, and pin, the allow side: `test_send_once_posts_the_signed_payload` must still see a 200, a `sha256=`-prefixed header and a body that parses as the same JSON object — assert `json.loads(captured["body"]) == FakeDelivery.payload` so the fix cannot be "stop sending a body". Red-prove each clause separately by execution: (i) revert `separators` alone and assert the recomputed-from-`captured["body"]` HMAC no longer matches the captured header; (ii) revert the timestamp prefix alone and assert the same; (iii) swap `content=body` back to `json=payload` alone and assert the same. The round-trip assertion must fail loudly rather than silently skip: if `captured` is empty (the handler never ran) the test must raise `AssertionError("transport handler never invoked")`, so "examined nothing" is not spelled like "found nothing". Boundary and tie: a payload with duplicate-after-sorting keys is impossible in a dict, but non-ASCII keys must be pinned — add a case with a `"é"` key and assert `ensure_ascii` behaviour is identical on both sides, since that is exactly where the two encoders differ next.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign` / `verify`
What is wrong: `sign` returns a timestamp but MACs only the payload, so an attacker who captures one delivery can replay it with any `X-Acme-Timestamp` they choose and the signature still verifies, and `verify` never accepts or checks a timestamp at all.
What breaks in production: the "reject requests whose timestamp is more than five minutes old — that window is what stops a captured request from being replayed" guarantee in `docs/webhooks.md` is unimplementable by any receiver (R49: a claim stronger than the implementation), so a captured `invoice.paid` can be replayed indefinitely against a customer's ledger.
Fix: bind the timestamp into the MAC as in the previous finding (`"{timestamp}.{body}"`) and give `verify` the signature it documents: `def verify(secret, body: bytes, timestamp: str, signature: str, *, max_age_seconds: int = 300) -> bool` which returns False when `abs(int(time.time()) - int(timestamp)) > max_age_seconds`, when `timestamp` is not an integer, and when the digest differs. Do not fix this by widening `max_age_seconds` or by dropping the timestamp from the header — the header is what makes the window checkable and must be preserved. Pair deny with allow: a signature produced by `sign` and verified in the same second must still return True, and one at exactly `max_age_seconds` must still return True. Red-prove each clause separately: (i) hand `verify` a timestamp of `now - 301` and assert False; (ii) hand it a timestamp of `now + 301` (clock skew forward) and assert False; (iii) hand it `"not-a-number"` and assert False rather than an uncaught `ValueError`; (iv) flip one hex character of the digest and assert False. Fail loudly when the check cannot run: a missing or empty `timestamp` argument must return False, never be treated as "no timestamp to check, so pass". Boundary and tie: state in the docstring that the comparison is `<= max_age_seconds` (inclusive) and that skew is checked in both directions, so a receiver whose clock is ahead does not silently reject every delivery.

### Critical: signature comparison is not constant-time (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the recomputed digest is compared to the caller-supplied signature with Python's `==`, which short-circuits on the first differing byte.
What breaks in production: an attacker who can submit candidate signatures learns the correct digest byte by byte from response-time differences and then forges deliveries that pass verification, which is the whole security value of the feature.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str`/`bytes` of the same type first (`compare_digest` raises `TypeError` on mixed `str`/`bytes`, and on non-ASCII `str`). Do not delete the `sha256=` prefix that makes the algorithm visible — strip it from both sides before comparing rather than dropping it from the header. Pair deny with allow: keep `test_verify_accepts_signature_produced_by_sign` green (a genuine signature must still authenticate) alongside `test_verify_rejects_a_signature_made_with_another_secret`. Red-prove each clause separately by execution: (i) mutate `compare_digest` back to `==` and assert a new test that asserts `verify` never uses `==` — e.g. an assertion on `inspect.getsource(signing.verify)` containing `compare_digest` — goes red; (ii) pass a signature of a different length and assert `verify` returns False rather than raising; (iii) pass a non-ASCII `str` signature and assert it returns False rather than propagating `TypeError`. Fail loudly when the check cannot run: a `None` or absent signature argument must return False and log at WARNING, not raise. Boundary and tie: `compare_digest` is not length-hiding, so state in the docstring that the signature length is public (it is fixed at 71 characters) and that this is intended.

### Critical: signing secrets are generated with the `random` module, not a CSPRNG (R1)
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, which is a non-cryptographic PRNG whose full internal state is recoverable from 624 observed outputs, and the code reimplements a security primitive the standard library already provides (`secrets`) — the R1 "duplicated behaviour is a security control" case.
What breaks in production: an attacker who obtains a few of their own issued secrets (self-service signup makes this free) can reconstruct the generator state and derive other tenants' signing secrets, letting them forge webhooks into any customer's endpoint.
Fix: `import secrets` and `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`; delete `import random`, `import string` and `_ALPHABET`, and rename or re-document `SECRET_BYTES = 32` so it means bytes of entropy rather than output characters (`token_urlsafe(32)` returns 43 characters). Do not weaken the existing test to make it pass — `test_new_signing_secret_has_prefix_and_length` must be updated to assert the new, larger length and must keep asserting the `whsec_` prefix, since that prefix is what lets secret scanners find leaked secrets. Pair deny with allow: the create endpoint must still return a usable secret that `sign`/`verify` round-trip successfully — add that assertion so "generate nothing" cannot pass. Red-prove each clause separately: (i) revert to `random.choice` and assert a new test that `secrets` is the module used (`inspect.getsource(signing.new_signing_secret)` contains `secrets.`) goes red; (ii) truncate the output by one character and assert the length test goes red; (iii) drop the prefix and assert the prefix test goes red. Fail loudly: no fallback to `random` if `secrets` is unavailable — let the `ImportError` propagate at module load rather than degrade silently. Boundary and tie: state the minimum acceptable entropy (256 bits) beside the constant so the next person who "shortens the secret for readability" has the floor in front of them.

### Critical: `list_deliveries` has no tenancy filter, so any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id`, taken straight from the path, with no join back to `WebhookEndpoint.org_id == user.org_id` — the sibling route `list_webhook_endpoints` added in the same diff does filter on `org_id`, so this is the missed location for the tenancy pattern the change itself establishes (cross-cutting check: `create_webhook_endpoint` scopes correctly, `list_webhook_endpoints` scopes correctly, `list_deliveries` does not).
What breaks in production: enumerating integer `endpoint_id` values dumps every other tenant's delivery history, and `WebhookDelivery.to_dict()` exposes `event_type` and `event_id` for events the caller has no rights to — a cross-tenant data breach reachable from any valid API key.
Fix: join and filter in the same query — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. Pair deny with allow (RT10): add both a test that org B gets 404 for org A's `endpoint_id` **and** a test that org A gets its own rows back, so a fix that denies everyone cannot pass. Assert the mutation, not only the status (RT8): the denial test must assert the response body is empty of any of org A's delivery ids, not merely that the code is 404. Red-prove each clause separately: (i) delete the `org_id` filter alone and assert the cross-tenant test reddens; (ii) delete the join alone and assert the same test reddens with a different message; (iii) change the 404 to 403 alone and assert the existence-disclosure test reddens. Fail loudly when the check cannot run: if `user.org_id` is None the handler must raise 401, never fall through to an unfiltered query. Boundary and tie: an endpoint that exists but belongs to another org and an endpoint that does not exist must produce byte-identical responses.

### Critical: the signing secret is returned by the list endpoint, contradicting the documented "cannot be read back" guarantee
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, used by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally includes `"signing_secret"`, and the same method serves both the create response (where the secret is intended) and the list response (where `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: every caller of `GET /v1/settings/webhook-endpoints` — including read-only API keys, logs, browser caches and any support tool that mirrors the response — receives live HMAC keys for all endpoints, so the documented containment story is false and secret rotation gives no benefit (R49: a claim stronger than the implementation).
Fix: remove `"signing_secret"` from `to_dict()` and have `create_webhook_endpoint` construct its response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}`, so the secret is emitted at exactly one call site. Do not fix this by deleting the create-time disclosure — the secret must still be returned once, or the feature is unusable. Pair deny with allow: one test asserting `"signing_secret" not in` any element of the list response, and one asserting `"signing_secret"` **is** present and `whsec_`-prefixed in the 201 create response. Red-prove each clause separately: (i) re-add the key to `to_dict()` alone and assert the list test reddens; (ii) drop the merge in the create handler alone and assert the create test reddens. Fail loudly: add a serialization test that iterates the model's declared columns and fails on any newly added column whose name matches `secret|token|key` unless it is explicitly allow-listed, so the next secret-bearing column cannot leak silently. Boundary and tie: state that the secret is returned only on the 201 response and never on any 200, and that a re-create (rotation) is the only way to obtain a new one.

### Critical: endpoint URLs are unrestricted and redirects are followed, giving authenticated SSRF into the internal network
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, and `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: validation is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts plain `http://`, accepts any scheme merely beginning with "http", and applies no destination policy at all, while the delivery client follows redirects — so `http://169.254.169.254/latest/meta-data/` or a public URL that 302s to it is a valid endpoint (RS3: validated for shape, never for the semantic property that matters).
What breaks in production: any signed-up user turns the delivery worker into a request proxy that reaches cloud metadata services, internal admin ports and localhost, and the response body is stored in `response_body` and readable back through `list_deliveries` — a full read-SSRF with exfiltration, and it silently contradicts `docs/webhooks.md` ("Only `https://` URLs are accepted").
Fix: replace the check with an explicit policy in one helper, `app/webhooks/urlpolicy.py::assert_deliverable(url)`, that requires `parsed.scheme == "https"` (exact equality, not `startswith`), requires a hostname, resolves it and rejects any address in a private, loopback, link-local, reserved or multicast range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`, and rejects a userinfo component; set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure; and call the same helper again in `send_once` immediately before the POST, because DNS can be re-pointed between registration and delivery (a TOCTOU the registration-time check alone cannot close — R51). Do not close the hole by disabling deliveries to external hosts generally: the allow case that must keep working is a genuine public HTTPS endpoint, pinned by a test that `https://hooks.example.com/acme` is accepted and delivered. Red-prove each clause separately: (i) revert `==` to `startswith` alone and assert an `httpfoo://` case reddens; (ii) revert to `follow_redirects=True` alone and assert a handler returning a 302 to `http://127.0.0.1/` reddens; (iii) remove the private-range check alone and assert the `169.254.169.254` case reddens; (iv) remove the second call in `send_once` alone and assert a rebinding fixture (registration resolves public, delivery resolves loopback) reddens. Fail loudly when the check cannot run: a DNS resolution failure must reject the registration with 422 and mark the delivery `failed_permanent`, never be treated as "could not check, so allow". Boundary and tie: name where the boundary values fall — IPv6-mapped IPv4 (`::ffff:127.0.0.1`) is rejected, a host resolving to *both* a public and a private address is rejected, and port 443 is not special-cased.

### Critical: the migration's CHECK constraint rejects the status the code actually writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, versus `app/webhooks/models.py` — `STATUSES` and `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the DDL enumerates `'failed'` while both the model's `STATUSES` tuple and the only writer spell it `'failed_permanent'` — an enum spelling that was propagated to two of the three places it exists (R3, security-adjacent in that it governs whether a failed delivery is ever recorded).
What breaks in production: every delivery that exhausts `MAX_ATTEMPTS` raises `CheckViolation` inside `_finish`, so the row stays `in_flight` forever, the failure is never recorded, and the exception escapes `deliver` through `asyncio.gather` and kills `run_worker` — one bad endpoint stops all webhook delivery.
Fix: change the DDL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive it from one source: build the constraint string in the migration from the same list the model exports, or add a startup assertion `assert set(STATUSES) == set(row for row in <constraint introspection>)` that fails at boot. Do not "fix" it by changing `_finish` to write `'failed'` and leaving `STATUSES` untouched — that just moves the third divergent spelling. Pair deny with allow: one test that writing `'failed_permanent'` **succeeds** against a real migrated database, and one that writing `'bogus'` is rejected — the second is what proves the constraint still constrains. Red-prove each clause separately: (i) revert the DDL alone and assert the success test reddens with a `CheckViolation`; (ii) drop the CHECK entirely and assert the `'bogus'` test reddens. Fail loudly when the check cannot run: the parity test must fail — not skip — when no database is reachable, so a CI environment without Postgres cannot report green. Boundary and tie: state that `STATUSES` is the single source of truth and that adding a member requires a migration in the same PR.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint for the same `event_id`, so any organization with two active subscribed endpoints violates the index on `session.add_all(rows)`.
What breaks in production: the whole batch insert fails, the dispatcher's `except Exception` swallows it into a WARNING, and the org receives **zero** webhooks — not one, zero — with no error surfaced to the customer or to the caller.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`, which is the idempotency key the docs' "deduplicate on `event_id`" actually needs (per-endpoint, not global), and add the composite `CREATE INDEX idx_webhook_deliveries_due ON webhook_deliveries (status, next_attempt_at)` that `_claim_batch`'s `WHERE status = ... AND next_attempt_at <= ... ORDER BY next_attempt_at` requires — the existing single-column `status` index does not serve it. Do not drop uniqueness altogether: the duplicate-suppression property must be preserved, so pin it with a test that re-running `enqueue_for_event` for the same `(endpoint, event)` inserts no second row. Pair deny with allow: one test that two endpoints in one org each receive a row for the same event (this must now SUCCEED), one test that the same endpoint cannot receive two rows for the same event. Red-prove each clause separately: (i) revert to the single-column unique index alone and assert the two-endpoint test reddens with a unique violation; (ii) drop the index entirely and assert the duplicate-suppression test reddens. Fail loudly: `enqueue_for_event` must use `ON CONFLICT DO NOTHING` and report the count of rows actually inserted, so a suppressed duplicate is distinguishable from a failed insert. Boundary and tie: an event matching zero endpoints must return 0 and be logged as such, not be indistinguishable from an error.

### Critical: `time.sleep` inside the async retry loop blocks the event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` for up to `BATCH_SIZE = 100` deliveries, but its backoff uses the blocking `time.sleep` instead of `await asyncio.sleep`, so a single retrying delivery freezes the entire loop.
What breaks in production: with backoffs of 2+4+8+16s each delivery can hold the loop for 30s and the batch serializes rather than runs concurrently, so the 60s `LOCK_KEY` TTL expires mid-batch, a second worker acquires the lock and re-sends the same `in_flight` rows, and every other coroutine in the process (health checks included) stalls.
Fix: `await asyncio.sleep(delay)`. Separately, stop sleeping in-process at all for anything past the first retry: set `row.next_attempt_at = now + backoff_for(attempt)` and `row.status = "pending"` in `_finish`-style persistence and return, letting `_claim_batch` pick it up — that is what `next_attempt_at` exists for, and it makes the retry survive a worker restart. Do not fix by shortening the backoff to hide the stall; the documented 2/4/8/16 schedule must be preserved. Pair deny with allow: assert that a first-attempt 200 still completes with no sleep at all, so a fix that always defers cannot pass. Red-prove each clause separately: (i) revert to `time.sleep` alone and assert a test that gathers two deliveries and asserts total wall time < the sum of their delays reddens; (ii) remove the `next_attempt_at` rescheduling alone and assert a test that a retried delivery is claimable by a fresh `_claim_batch` reddens. Fail loudly when the check cannot run: the concurrency test must fail rather than skip if the event loop policy prevents it, and must not use a bare `sleep` as its oracle (a wall-clock assertion with a hard upper bound, not a race window). Boundary and tie: state that `attempt == MAX_ATTEMPTS` schedules no further attempt and that the comparison is `>=`, so the tie at exactly 5 attempts is a permanent failure and not a sixth try.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`) and `deliver` (reads `endpoint.signing_secret` / `endpoint.url` after its `with` block)
What is wrong: both functions let SQLAlchemy instances escape the session that loaded them and then read attributes off them; under SQLAlchemy's default `expire_on_commit=True` every such read triggers a refresh on a closed session and raises `DetachedInstanceError`, and `session.get(m.WebhookEndpoint, ...)` returning `None` for a deleted endpoint gives an `AttributeError` on the very next line.
What breaks in production: the worker raises on the first delivery of every batch, the exception propagates through `asyncio.gather` (which is called without `return_exceptions=True`) and out of `run_worker`, so the worker process dies and all rows stay `in_flight`.
Fix: stop passing ORM objects across session boundaries — have `_claim_batch` return plain values (`[(row.id, row.endpoint_id, row.attempts, row.payload) for row in rows]`) read while the session is open, and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside its own `with` block, raising a named `EndpointGone` when `session.get` returns `None` and marking the delivery `failed_permanent`. Pass `return_exceptions=True` to `asyncio.gather` and log each exception, so one bad delivery cannot take the worker down. Do not fix by disabling `expire_on_commit`: that hides the lifetime bug rather than removing it, and the detachment would still bite on any lazy-loaded relationship added later. Pair deny with allow: assert a normal delivery still completes end to end through `_claim_batch` → `deliver` → `_finish` against a real session. Red-prove each clause separately: (i) re-introduce the returned ORM instance alone and assert an end-to-end test reddens with `DetachedInstanceError`; (ii) delete the `None` check alone and assert a deleted-endpoint test reddens; (iii) remove `return_exceptions=True` alone and assert a test that a second delivery still completes when the first raises reddens. Fail loudly when the check cannot run: `EndpointGone` must be logged at ERROR with the delivery id, never swallowed. Boundary and tie: an endpoint deleted between claim and send is a permanent failure, and a delivery whose endpoint row is merely `active=False` is also permanent — say which, so the two do not diverge later.

### Major: the delivery lock is neither atomic nor safely released, and a crash between `set` and `expire` wedges the feature permanently
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: acquisition is a get-then-set with a window between the two calls (two workers both observe an empty key and both proceed), the TTL is applied by a separate `expire` call so a crash in between leaves a key with no expiry, and the `finally` deletes `LOCK_KEY` unconditionally — including a lock a *different* worker acquired after this one's TTL lapsed (R38 part 2: a persisted fail-closed state with no reset path).
What breaks in production: either two workers dispatch the same batch simultaneously and customers get duplicates beyond the documented at-least-once expectation, or a single unlucky crash leaves an eternal lock and webhook delivery stops entirely with no automatic recovery and no alert.
Fix: make acquisition one atomic command with a fencing token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`) so a worker can only delete its own lock; extend the TTL from the batch loop while work is in flight. Do not remove the lock to avoid the wedge — mutual exclusion is the behaviour being preserved. Pair deny with allow: one test that a second `_acquire_lock` while the first holds it returns False, and one that after the holder releases, the next `_acquire_lock` returns True — the second is what proves the fix does not lock everyone out forever. Red-prove each clause separately: (i) revert to get-then-set alone and assert a test issuing two interleaved acquisitions reddens; (ii) drop `ex=60` alone and assert a TTL assertion (`ttl(LOCK_KEY) > 0` immediately after acquire) reddens; (iii) revert to unconditional `delete` alone and assert a test where worker B holds the lock and worker A's `finally` runs reddens. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must return False and log ERROR (fail closed — do not dispatch), and that path needs its own assertion so "Redis down" is not spelled like "lock free". Boundary and tie: name what happens when the TTL expires at exactly the moment the holder finishes — the compare-and-delete makes it a no-op, and the batch's rows are recovered by the `in_flight` reaper below rather than double-sent silently.

### Major: `in_flight` is a non-terminal state with no reaper, so any interruption strands a delivery forever
File: `app/webhooks/delivery.py` — `_claim_batch` (sets `row.status = "in_flight"`) and `_finish` (the only writer that leaves it)
What is wrong: rows enter `in_flight` before the network call but only leave it on the success or permanent-failure path inside `_finish`, and `_claim_batch` selects `status == "pending"` exclusively — so a worker crash, a redeploy, an OOM kill or any exception before `_finish` leaves the row unreachable by every future claim (R38 part 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: every worker restart silently orphans up to `BATCH_SIZE` deliveries; the customer never receives them, `list_deliveries` shows them stuck at `in_flight`, and nothing retries or alerts.
Fix: add a bounded timeout and a reset path — stamp `claimed_at` when moving to `in_flight`, and have `_claim_batch` also select rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`, resetting them to `pending`; emit a metric/log line for every reclaimed row so the condition is visible rather than merely healed. Do not implement this by widening the claim to all statuses, which would re-send `delivered` rows — the terminal states must stay terminal. Pair deny with allow: one test that an `in_flight` row older than the lease **is** reclaimed, and one that an `in_flight` row claimed one second ago is **not** (so a fix that reclaims everything, duplicating live sends, cannot pass). Red-prove each clause separately: (i) delete the lease predicate alone and assert the reclaim test reddens; (ii) delete the age comparison alone and assert the "not yet expired" test reddens; (iii) include `delivered` in the reclaim set alone and assert a test that a delivered row is never re-sent reddens. Fail loudly when the check cannot run: if `claimed_at` is NULL on a legacy row, treat it as expired and log at WARNING rather than skipping the row silently. Boundary and tie: a row whose `claimed_at` is exactly `now - 5 minutes` is reclaimed (inclusive `<=`), and two workers racing to reclaim the same row are resolved by a conditional `UPDATE ... WHERE status = 'in_flight' AND claimed_at = <observed>` returning a rowcount, not by read-then-write.

### Major: 4xx responses are retried, contradicting the documented retry policy, and the backoff has no jitter
File: `app/webhooks/delivery.py` — `deliver` (`status_code = response.status_code; detail = ...` then fall through to the retry) and `backoff_for`, versus `docs/webhooks.md` "Retries"
What is wrong: the loop retries every non-2xx status up to `MAX_ATTEMPTS`, but the docs state "a 4xx is permanent and we stop immediately"; and the docs state "backoff is exponential with jitter" while `backoff_for` returns exactly `2**attempt` with no jitter at all (R29: the rationale attached to the published contract is not what the code does).
What breaks in production: a customer endpoint returning 401 or 410 is hammered five times per event instead of once, and because every delivery of a given attempt number wakes at the identical second, a recovering endpoint is hit by a synchronized thundering herd of the whole backlog.
Fix: branch on the class — `if 400 <= response.status_code < 500 and response.status_code not in (408, 429): _finish(delivery.id, "failed_permanent", attempt, response.status_code, detail); return` — and add jitter, `backoff_for(attempt) * random.uniform(0.5, 1.5)` computed with `secrets`-independent `random` (jitter is not a security value), keeping the deterministic `backoff_for` as the base so `test_backoff_grows_exponentially` stays meaningful. Pair deny with allow: one test that a 404 stops after exactly one attempt, and one that a 500 and a `ConnectError` each still retry to `MAX_ATTEMPTS` — the second is what stops the fix from making every failure permanent. Fail loudly when the check cannot run: an unexpected status (1xx, 3xx with redirects disabled) must be recorded as `failed_permanent` with the code in `response_status`, never fall through to an unlabelled retry. Boundary and tie: state which side 408 and 429 fall on (retryable) and that 400–499 is inclusive at both ends.

### Major: the delivered payload carries no event id or type, so the documented deduplication key is not on the wire
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`payload=payload`) and `send_once` (`json=delivery.payload`), versus `docs/webhooks.md` "delivery is at-least-once, so deduplicate on `event_id`"

Do not fix by editing the docs to drop the deduplication advice — at-least-once delivery is unchanged and the receiver still needs the key. Pair deny with allow: one test that the POSTed body contains `id`/`type`/`data` derived from a real `WebhookDelivery` row, and one that the customer payload under `data` is byte-identical to what `dispatch` was given (so wrapping does not mangle it). Red-prove each clause separately: (i) drop `id` from the envelope alone and assert the envelope test reddens; (ii) drop the header alone and assert the header test reddens; (iii) mutate one value inside `data` alone and assert the passthrough test reddens. Fail loudly when the check cannot run: if `event_id` is NULL the delivery must be marked `failed_permanent` with a named reason rather than shipped without an id. Boundary and tie: state that the envelope is versioned (`"version": 1`) and that `data` is the only field customers may treat as open-ended, so the next added field is not a breaking change.

### Major: the webhook enqueue is outside the event's transaction and its failure is swallowed
File: `app/events/dispatcher.py` — the `try/except Exception: log.warning(...)` block around `webhook_delivery.enqueue_for_event`
What is wrong: the `Event` row commits in its own `session_scope`, the delivery rows are inserted in a second, later transaction inside `enqueue_for_event`, and any failure of the second is caught and downgraded to a WARNING — so a crash, a DB blip or the unique-index violation above leaves a committed event with no delivery rows and nothing that ever reconciles the two (R9/R5: the "persist and its side effect are atomic" invariant does not hold across the split).
What breaks in production: webhooks are silently dropped for events that the system considers successfully dispatched, which is precisely the at-least-once guarantee the docs sell, and the only trace is a WARNING line no one alerts on.
Fix: use the outbox pattern — insert the `WebhookDelivery` rows in the **same** `session_scope` as the `Event` row (pass the session into `enqueue_for_event`), so either both commit or neither does, and let the failure propagate rather than catching it; the worker's existing `pending` claim already provides the asynchrony that the fire-and-forget call was reaching for. Do not fix by removing the `try/except` alone and leaving the two transactions split, and do not preserve the current behaviour by re-raising into the caller's request path — the point is that the delivery rows become part of the event's atomic unit. Pair deny with allow: one test that a forced failure in `enqueue_for_event` rolls back the `Event` row too (assert the mutation, not only the log line — RT8), and one that a normal `dispatch` commits both the event and one row per subscribed endpoint. Red-prove each clause separately: (i) restore the separate `session_scope` inside `enqueue_for_event` alone and assert the rollback test reddens; (ii) restore the `except Exception` alone and assert the same test reddens with a different message; (iii) remove the per-endpoint fan-out alone and assert the row-count test reddens. Fail loudly when the check cannot run: if the webhooks module cannot be imported, `dispatch` must fail at import time, not degrade to "no webhooks today". Boundary and tie: an event with zero matching endpoints commits with zero delivery rows and is not an error; an event whose fan-out partially fails commits nothing.

### Major: delivery request headers, including the live signature, are logged at INFO
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: the entire header dict is formatted into an INFO log line on every attempt, which puts the `X-Acme-Signature` value — a valid, and (per the timestamp finding above) non-expiring, authentication token for that exact payload — into whatever log sink the service ships to.
What breaks in production: anyone with log-read access, including third-party log vendors and support staff, can replay a captured delivery to the customer's endpoint with a signature that verifies, and the volume also makes the logs an index of every customer's endpoint URLs and event cadence.

Do not fix by lowering the level to DEBUG: debug logging is enabled in incidents, which is exactly when the secret would leak. Pair deny with allow: one test asserting the emitted record contains the delivery id, and one asserting no emitted record contains the signature value (use `caplog` and assert the signature string is absent from `caplog.text`). Red-prove each clause separately: (i) restore `headers=%s` alone and assert the "no signature in logs" test reddens; (ii) remove the delivery id alone and assert the traceability test reddens. Fail loudly when the check cannot run: if `caplog` captures no records the test must fail with "no log records captured", not pass by vacuous absence — this is the exact case where "examined nothing" reads as "found nothing". Boundary and tie: state the redaction rule as a header-name allow-list (`Content-Type`, `User-Agent`, `X-Acme-Timestamp`) so a future header defaults to redacted rather than to logged.

### Major: `limit` on `list_deliveries` has an inclusive lower bound but no upper bound (RS3)
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: the query parameter is validated only for `ge=1`, so `?limit=100000000` is accepted and passed straight to `.limit()` on a table whose only index is on `status` — the ordering column `created_at` is unindexed.
What breaks in production: a single request materializes the entire delivery history into Python dicts, exhausting the worker's memory and the database's sort buffers, and it is reachable by any authenticated caller.
