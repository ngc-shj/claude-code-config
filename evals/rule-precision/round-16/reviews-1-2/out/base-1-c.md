### Critical: `list_deliveries` reads any organization's deliveries (missing tenancy filter)
File: `app/api/routes/settings.py` — `list_deliveries`, the `session.query(...).filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters only on the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while the sibling route `list_webhook_endpoints` added in the same hunk does apply exactly that org filter — the tenancy pattern was propagated to one of the two new read routes and not the other (R3, security-relevant).
What breaks in production: Any authenticated user can enumerate `endpoint_id` values and read other tenants' delivery history — event ids, event types, response statuses and schedules for organizations they do not belong to.
Fix: Join the delivery query to its endpoint and scope it, `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and return `404` (not `403`) when the endpoint exists but belongs to another org so the route does not confirm existence. Preserve the behaviour that makes the route useful: the owning org must still receive its own rows in `created_at DESC` order with the same `to_dict()` shape. Pin both directions and red-prove each separately — (a) mutation: drop the `org_id` predicate, the cross-tenant test must go red asserting `404`; (b) mutation: replace the `org_id` predicate with a constant-false clause, the owner test must go red asserting its own N rows are returned. Boundary/tie: an endpoint whose `org_id` equals the caller's is IN (allowed); a delivery whose endpoint row is missing (endpoint deleted, delivery not yet cascaded) is OUT — route it to `404`, never to an unscoped fallback, so "cannot resolve the owner" is not spelled the same as "found nothing".

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice`, a Mersenne-Twister PRNG whose internal state is recoverable from a modest amount of observed output, so the secrets are predictable rather than unguessable.
What breaks in production: An attacker who obtains a few secrets (or who can register endpoints and read back their own secrets — see the `to_dict` finding) can reconstruct the generator state and forge valid signatures for every other tenant's webhook traffic, defeating the entire signing scheme.
Fix: Replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX` (`import secrets`; delete the now-unused `random`, `string`, `_ALPHABET`), and rename `SECRET_BYTES` usage so the constant means bytes of entropy rather than output characters. Do not fix by deleting what made this visible: the existing `test_new_signing_secret_has_prefix_and_length` assertion on the prefix must be kept, and its length assertion updated to `len(secrets.token_urlsafe(32))` rather than removed. Pair deny with allow: assert (a) two successive calls differ and the prefix is present (allow side still works), and (b) that `random.seed(0)` followed by two calls still produces different secrets — red-prove by reverting to `random.choice`, which makes (b) fail deterministically. Fail loudly: if `SECRET_BYTES < 32`, raise at import rather than emitting a short secret. Boundary/tie: 32 bytes is the accepted floor; a configured value of exactly 32 passes, 31 raises.

### Critical: `verify` compares signatures with `==` (not constant-time) and never covers the timestamp
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The credential comparison uses `==` instead of `hmac.compare_digest` (RS1), and `sign` computes the MAC over `serialize(payload)` alone, so the `X-Acme-Timestamp` header is not authenticated at all despite `docs/webhooks.md` telling integrators the MAC covers `"{timestamp}.{raw_request_body}"`.
What breaks in production: The byte-wise short-circuit in `==` leaks the correct prefix to a remote attacker who can retry, and because the timestamp is outside the MAC an attacker replaying a captured request can freely rewrite `X-Acme-Timestamp` to `now`, so the five-minute replay window the docs sell as the anti-replay control enforces nothing.
Fix: Change `sign` to compute `hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` over the exact transmitted body, change `verify` to take the timestamp explicitly (`verify(secret, timestamp, body, signature, *, max_age=300)`), compare with `hmac.compare_digest`, and reject when `abs(now - int(timestamp)) > max_age`. Preserve what made the feature useful: `verify` must still accept a signature that `sign` just produced for the same body. Red-prove each clause with its own mutation — (a) revert to `==` and assert a dedicated test that `verify` calls `compare_digest` (patch-and-assert on the module symbol) goes red; (b) alter one timestamp byte and assert the signature check goes red; (c) set the timestamp to `now - 301` and assert the age check goes red while the signature is still valid, proving the two clauses are independent. Fail loudly: a non-numeric or absent timestamp returns `False`, it does not skip the age check. Boundary/tie: age exactly `300` is accepted, `301` is rejected; a timestamp exactly `now` in the future is accepted, future skew beyond `max_age` is rejected.

### Critical: the signature is computed over different bytes than the request body carries
File: `app/webhooks/delivery.py` — `send_once`, `sign(endpoint.signing_secret, delivery.payload)` followed by `client.post(..., json=delivery.payload, ...)`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` (via the change's own `signing.serialize`) while httpx serialises the same dict independently with its own separator and key-order rules, so the signed byte string and the transmitted byte string are two different producer shapes for one strict consumer (R40).
What breaks in production: Every customer who implements verification the way `docs/webhooks.md` documents it — HMAC over the raw request body — computes a different digest and rejects 100% of our deliveries, a silent total-path failure that our own tests cannot see because `test_send_once_posts_the_signed_payload` only checks the header's prefix and length.
Fix: Serialise once and send those exact bytes: `body = serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, ts, body)`, `client.post(endpoint.url, content=body, headers={...,"Content-Type": "application/json"})` — the existing `signing.serialize` helper is the canonical form and must be the single producer, not re-derived by the HTTP client. Preserve the behaviour under test: the request must still arrive with `Content-Type: application/json` and a body that parses to the original payload. Red-prove with an actual-output-through-actual-consumer round trip (R40's required test shape): capture `request.content` in the `MockTransport` handler and assert `signing.verify(SECRET, captured_timestamp, captured_body, captured_signature)` is true; mutating `serialize` to `json.dumps(payload)` (no `sort_keys`) or reverting to `json=` must turn that assertion red. Fail loudly: a payload that is not JSON-serialisable must raise before the POST, not send an unsigned request. Boundary/tie: an empty payload `{}` must still produce `b"{}"` and verify, not an empty body.

### Critical: the migration's status CHECK constraint does not admit the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py::deliver` writing `"failed_permanent"` and `app/webhooks/models.py::STATUSES`
What is wrong: The SQL enum spells the terminal failure `failed` while both the model's `STATUSES` tuple and `_finish(delivery.id, "failed_permanent", ...)` spell it `failed_permanent` — one enum, two spellings across the producer/consumer boundary (R40, R3).
What breaks in production: Every delivery that exhausts its retries raises an `IntegrityError` on the terminal write, so the row is left in `in_flight` forever and the worker's `gather` propagates the exception, taking down the batch — permanently failing endpoints wedge the whole dispatch loop.
Fix: Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the SQL list from `models.STATUSES` in a test rather than restating it (R2): add a test that reads the constraint's admitted values and asserts set equality with `STATUSES`. Preserve the constraint's purpose — do not fix by dropping the CHECK. Red-prove separately: (a) remove `failed_permanent` from the SQL list and the set-equality test reds; (b) add a bogus `'oops'` to `STATUSES` and the same test reds from the other side, proving it is not one-directional. Fail loudly: the test must fail, not skip, when the migration file cannot be parsed. Boundary/tie: `in_flight` is admitted by both sides and must remain so; a status not in either set is rejected by the database, which is the intended behaviour.

### Critical: the unique index on `event_id` alone makes multi-endpoint orgs impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: Uniqueness is declared on `event_id` by itself, but `enqueue_for_event` inserts one row per matching endpoint for a single event id, so the second row of any fan-out violates the index.
What breaks in production: The moment an organization registers a second endpoint, every event's enqueue raises, and because `app/events/dispatcher.py` swallows that exception into a `log.warning`, deliveries are silently dropped for both endpoints with no error surfaced to anyone.
Fix: Replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — that is the idempotency key the docs' "deduplicate on `event_id`" guidance actually needs per endpoint. Preserve the deduplication the index was there to provide: a redelivery of the same event to the same endpoint must still be rejected. Red-prove each clause: (a) insert two rows with the same `event_id` and different `endpoint_id` — must succeed, and reverting to the single-column index makes it red; (b) insert two rows with identical `(endpoint_id, event_id)` — must raise, and dropping the index makes that red. Fail loudly: `enqueue_for_event` must let a genuine uniqueness violation propagate (see the dispatcher finding) rather than logging it. Boundary/tie: exactly one row per `(endpoint_id, event_id)`; two endpoints sharing one event id is the allowed case that this index must not block.

### Critical: `WebhookEndpoint.to_dict()` returns the signing secret on every list call
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry
What is wrong: The single serializer used by both `create_webhook_endpoint` and `list_webhook_endpoints` emits the secret, directly contradicting `docs/webhooks.md`'s claim that the creation response "is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation, relied on as a boundary).
What breaks in production: `GET /v1/settings/webhook-endpoints` hands every caller with read access — and every log, proxy cache, browser history and support screenshot of that response — the key that forges signatures for that tenant, and the doc's assurance means integrators will not treat the list response as secret material.
Fix: Split the serializers: `to_dict()` drops `signing_secret`, and a separate `to_dict_with_secret()` is called only from the `create_webhook_endpoint` 201 path; store the secret hashed or in the secrets manager if it is not needed in plaintext for signing, otherwise keep it column-level encrypted. Preserve the feature: creation must still return the secret once, or customers can never verify anything. Red-prove each clause independently: (a) assert `create` response contains `signing_secret` — restoring the shared serializer keeps it green, deleting the create-path branch reds it; (b) assert `list` response does NOT contain `signing_secret` for an endpoint whose secret is set to a known sentinel — reverting `to_dict` reds it. Fail loudly: if `to_dict_with_secret` is called with an endpoint whose secret is unset, raise rather than returning a key-less body. Boundary/tie: exactly one response — the 201 — carries the secret; every other representation of the same row, including the deliveries route, must not.

### Critical: endpoint URL validation admits non-HTTPS and internal targets, and the client follows redirects
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`, with `app/webhooks/delivery.py::run_worker` constructing `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The check adjudicates the URL's surface form rather than its resolved destination (R47) — `startswith("http")` accepts `http`, and any scheme merely beginning with those four characters, while `docs/webhooks.md` states "Only `https://` URLs are accepted" — and nothing rejects `127.0.0.1`, `169.254.169.254`, or a hostname that resolves there, with redirects followed to boot.
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/` (or an external URL that 302s there) and our worker POSTs signed, authenticated-from-inside requests to cloud metadata and internal services, returning the response body into `response_body` where the tenant reads it back — a full SSRF-with-exfiltration primitive.
Fix: Validate at the schema level with pydantic (`url: HttpUrl` on `EndpointIn`) plus an explicit `parsed.scheme == "https"` equality check, resolve the hostname at registration and at send time and reject any address in a private/loopback/link-local/reserved range, and set `follow_redirects=False` so a redirect is a delivery failure rather than a new destination. Preserve the feature: a public `https://hooks.example.com/acme` must still register and receive deliveries. Red-prove each clause with its own mutation — (a) `http://hooks.example.com` returns 422 (reverting to `startswith` reds it); (b) `https://127.0.0.1/x` returns 422 (removing the range check reds it); (c) a handler returning `302` to an internal host marks the delivery failed instead of following (restoring `follow_redirects=True` reds it). Fail loudly: DNS resolution failure at registration must return 422 with a named reason, not fall through to "no private address found". Boundary/tie: scheme is compared for equality, so `https` is in and everything else including `https+foo` is out; an address exactly at a private range edge (`10.0.0.0`, `172.31.255.255`) is out.

### Critical: `deliver` calls the blocking `time.sleep` inside an async worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: A coroutine that is gathered with up to `BATCH_SIZE` siblings blocks the event loop with `time.sleep` instead of `await asyncio.sleep`, and the retry is looped in-process rather than rescheduled through the `next_attempt_at` column the schema and `backoff_for` exist to serve.
What breaks in production: One slow endpoint freezes the entire process — every other in-flight delivery, and any other coroutine sharing the loop — for up to 30 seconds per delivery, so a batch of failing endpoints stalls dispatch for minutes and the redis lock's 60-second TTL expires while the work is still running, letting a second worker claim the same rows.
Fix: Replace the in-process retry loop with a reschedule: on a retryable failure, write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting `_claim_batch` pick the row up when it is due; keep `await asyncio.sleep` only for the worker's idle poll. Preserve what the loop provided: the total attempt budget must still be `MAX_ATTEMPTS`, and `backoff_for` must still yield 2/4/8/16 seconds, so the existing `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` stay green unchanged. Red-prove each clause: (a) a failing endpoint leaves the row `pending` with `next_attempt_at` advanced by exactly `backoff_for(attempt)` — reverting to the inline loop reds it; (b) a delivery at `attempts == MAX_ATTEMPTS - 1` that fails transitions to `failed_permanent` — off-by-one mutations red it; (c) a gathered batch of one slow and one fast delivery completes the fast one first — restoring `time.sleep` reds it. Fail loudly: a delivery whose endpoint row has vanished must be marked terminally with a named reason, not silently retried. Boundary/tie: attempt number exactly `MAX_ATTEMPTS` is the last attempt made and transitions to terminal; it is not a further reschedule.

### Critical: the worker uses ORM objects after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), and `deliver` (loads `endpoint` in a `with` block, then reads `endpoint.signing_secret`/`endpoint.url` outside it)
What is wrong: Both functions hand detached SQLAlchemy instances across the session boundary and then read attributes that the default `expire_on_commit=True` has expired, so the first access after the `with` block triggers a lazy refresh with no session bound.
What breaks in production: `send_once` raises `DetachedInstanceError` on `endpoint.signing_secret` for every delivery — the feature does not work at all — and because `asyncio.gather` is called without `return_exceptions`, the exception escapes `run_worker`'s `try/finally` and kills the worker process after it has already flipped the batch to `in_flight`.
Fix: Keep the unit of work inside one session: have `_claim_batch` return plain data (`list[tuple[int, int, str, dict, int]]` of delivery id, endpoint id, url, payload, attempts) selected with a `SELECT ... FOR UPDATE SKIP LOCKED` in the same transaction that sets `in_flight`, and have `deliver` receive those values rather than an ORM row; alternatively set `expire_on_commit=False` on the session factory and re-attach explicitly. Preserve the claim semantics: a row claimed by one worker must still be invisible to another. Red-prove each clause: (a) a delivery whose endpoint exists is POSTed with that endpoint's secret — reverting to the detached read reds it with `DetachedInstanceError`; (b) two concurrent `_claim_batch` calls return disjoint id sets — dropping `SKIP LOCKED` reds it; (c) `asyncio.gather(..., return_exceptions=True)` plus a per-delivery `except` keeps the worker alive when one delivery raises — removing the handler reds it. Fail loudly: a claimed row whose endpoint was deleted must be marked terminal with a named reason, not skipped silently. Boundary/tie: a row with `next_attempt_at` exactly equal to `now` is due and IS claimed (`<=`), matching the current predicate.

### Critical: the redis lock is non-atomic and can wedge dispatch permanently
File: `app/webhooks/delivery.py` — `_acquire_lock`, the `get` then `set` then `expire` sequence
What is wrong: The check and the acquire are three separate round trips, so two workers can both observe an empty key and both acquire, and the TTL is set in a second call after the key already exists — a crash in that window leaves a key with no expiry (R38: a persisted fail-closed wedge with no reset path).
What breaks in production: Concurrently, both workers claim overlapping batches and customers receive duplicate deliveries; on the crash path the lock key survives forever and `run_worker` spins on `await asyncio.sleep(poll_interval)` without ever dispatching again — webhook delivery stops silently and never self-heals.
Fix: Make acquisition a single atomic operation with the TTL included — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — where `token` is a per-worker `secrets.token_hex()` fencing value, and release with a compare-and-delete Lua script so a worker never deletes a lock that expired and was re-acquired by someone else (the current `finally: redis_client.delete(LOCK_KEY)` does exactly that). Preserve the allow side: a single worker must still acquire on every idle poll and dispatch. Red-prove each clause: (a) two sequential acquires without release — the second returns `False`, and removing `nx=True` reds it; (b) after `LOCK_TTL_SECONDS` with a fake clock, acquisition succeeds again, and dropping `ex=` reds it (the wedge); (c) worker A's release after B has acquired leaves B's token in place, and reverting to unconditional `delete` reds it. Fail loudly: a redis error during acquire must raise or return `False` with a logged reason — it must not be indistinguishable from "lock free". Boundary/tie: the holder's own re-acquire attempt is denied (no reentrancy), and a lock whose TTL has elapsed exactly is free.

### Major: deliveries can be wedged in `in_flight` with no reaper or timeout
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`, and `_finish` is the only writer that leaves it
What is wrong: `in_flight` is entered unconditionally at claim time but exited only on the success or permanent-failure paths inside `deliver`, so any crash, restart, deploy, or the `DetachedInstanceError` above strands rows in a non-terminal state with no timeout and no recovery path (R38 clause 1).
What breaks in production: After the first worker restart mid-batch, up to 100 deliveries are permanently invisible to `_claim_batch` (which selects only `status == "pending"`) and the customer never receives those events, with nothing alerting on it.
Fix: Add a `claimed_at` column and a reaper that, at the start of each poll, resets rows with `status = 'in_flight' AND claimed_at < now() - INTERVAL '5 minutes'` back to `pending` with `attempts` unchanged, and log the count reset at WARNING so the condition is visible. Preserve the claim's purpose: a row currently being worked (claimed under 5 minutes ago) must NOT be reset, or the reaper itself causes duplicates. Red-prove each clause: (a) a row claimed 6 minutes ago is reset and redelivered — removing the reaper reds it; (b) a row claimed 1 minute ago is not touched — removing the age predicate reds it; (c) the reset preserves `attempts` so the budget is not refreshed — a mutation zeroing `attempts` reds a test asserting the row terminates after the original `MAX_ATTEMPTS`. Fail loudly: if the reaper query errors, the worker must log at ERROR and skip the poll rather than continue as if nothing were stuck. Boundary/tie: a row claimed at exactly the 5-minute mark is NOT yet reset (`<` not `<=`), so the in-progress delivery keeps ownership.

### Major: 4xx responses are retried and backoff has no jitter, contradicting the published contract
File: `app/webhooks/delivery.py` — `deliver`'s retry branch (`status_code = response.status_code` with no 4xx test) and `backoff_for`
What is wrong: `docs/webhooks.md` states "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx status identically and `backoff_for` returns a deterministic `2**attempt` (R29/R49: the prose describes a control the code does not implement).
What breaks in production: A customer endpoint returning 404 or 401 is hammered five times per event, and because every failing delivery in a batch retries on the same deterministic schedule, retries arrive as synchronised thundering herds against an endpoint that is already down.
Fix: Branch on the status class — `4xx` other than `408` and `429` goes straight to `_finish(..., "failed_permanent", ...)`; `429`, `5xx`, timeouts and connection errors reschedule — and add jitter as `timedelta(seconds=BASE_DELAY_SECONDS**attempt * random.uniform(0.5, 1.5))`. Preserve the documented ladder: the pre-jitter values must remain 2/4/8/16, so `test_backoff_grows_exponentially` becomes an assertion on the base and a separate bound check `0.5*base <= actual <= 1.5*base`. Red-prove each clause: (a) a 404 response yields `failed_permanent` after exactly one attempt — removing the 4xx branch reds it; (b) a 429 response reschedules — including 429 in the permanent set reds it; (c) two calls to `backoff_for(3)` differ while both stay inside the bound — removing jitter reds the first assertion and the bound test guards against jitter that is too wide. Fail loudly: an unrecognised status class (1xx, 3xx with redirects disabled) must be recorded as a named failure, not silently treated as retryable. Boundary/tie: `400` is permanent, `408` and `429` are retryable, `500` is retryable; status exactly `299` is success and `300` is not.

### Major: the dispatcher swallows every enqueue failure, so events are silently lost
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: A bare `except Exception` around the enqueue converts every failure — the uniqueness violation above, a DB outage, a bug — into a warning line, and the enqueue runs after the event's `session_scope` has committed, so there is no transaction linking the persisted event to its delivery rows (R5/R9).
What breaks in production: `docs/webhooks.md` promises at-least-once delivery, but any enqueue failure drops the event permanently with no queue, no retry and no signal beyond a log line nobody alerts on — exactly the silent-loss mode the `failed`/`failed_permanent` and unique-index defects trigger on day one.
Fix: Write the delivery rows in the same transaction as the `Event` insert (pass the open session into `enqueue_for_event`), so the event and its fan-out commit or roll back together; if the enqueue must stay out-of-band, replace the swallow with an outbox row committed alongside the event and a reconciler that enqueues from it. Preserve the recovery the `except` was reaching for: a webhook failure must still not lose the event itself. Red-prove each clause: (a) force the delivery insert to raise and assert no `Event` row is committed either — the current code leaves the event and reds this; (b) a successful dispatch commits exactly one event and N delivery rows — dropping the enqueue call reds it; (c) assert the log is emitted at ERROR with the event id when the transaction rolls back — downgrading to `warning` reds it. Do not fix by widening the `except` or by dropping the log. Boundary/tie: an org with zero active endpoints commits the event and zero delivery rows — that is success, not an error path.

### Major: `enqueue_for_event` writes a naive `utcnow()` into a timezone-aware column, bypassing the module's own helper
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`
What is wrong: The change already defines `app/webhooks/models.py::_now()` returning `datetime.now(timezone.utc)` and uses aware times everywhere else (`_claim_batch`'s `now`, `_finish`'s `updated_at`), but this one call site reimplements it with the naive, deprecated `datetime.utcnow()` (R1: reimplementation of a shared helper present in the same change).
What breaks in production: The claim predicate `next_attempt_at <= now` compares a naive stored value against an aware one — on Postgres with a `timestamptz` column the naive value is coerced using the server timezone, so on any non-UTC server deliveries become due hours early or late, and in any code path that compares them in Python it raises `TypeError`.
Fix: Call the existing helper — `next_attempt_at=m._now()` — and add a lint or test that asserts no `datetime.utcnow(` appears under `app/webhooks/`. Preserve the intent: a newly enqueued delivery must still be immediately due, i.e. claimable by the very next `_claim_batch`. Red-prove each clause: (a) a row enqueued now is returned by `_claim_batch` — mutating `_now()` to return `now + 1h` reds it; (b) the stored value has a non-`None` `tzinfo` — reverting to `utcnow()` reds it; (c) the grep/lint test reds when `datetime.utcnow(` is reintroduced. Boundary/tie: a delivery whose `next_attempt_at` equals `now` exactly is due and IS claimed, matching `<=`.

### Major: the migration declares naive `TIMESTAMP` columns while the models declare `DateTime(timezone=True)`
File: `migrations/0042_webhook_delivery.sql` — `created_at`, `next_attempt_at`, `updated_at` (all `TIMESTAMP NOT NULL`) vs `app/webhooks/models.py` `Column(DateTime(timezone=True), ...)`
What is wrong: The schema the database enforces is `timestamp without time zone` while SQLAlchemy binds and returns aware datetimes, so the offset is discarded on write and fabricated on read (R3: the aware-time decision was propagated to the models and not to the migration).
What breaks in production: On any deployment whose database session timezone is not UTC, `next_attempt_at` is stored shifted, retries fire at the wrong wall-clock time, and `to_dict()["next_attempt_at"].isoformat()` reports a time that never corresponds to when the attempt happens.
Fix: Change all three columns to `TIMESTAMPTZ NOT NULL` (and `now()` remains correct as the default), in the same migration since it has not shipped. Preserve the defaults: `created_at`/`updated_at` must still populate without an explicit value. Red-prove each clause: (a) a round-trip test writes an aware datetime in a non-UTC zone and reads back the same instant — reverting the column type reds it; (b) `DEFAULT now()` still populates on an insert omitting the column — dropping the default reds it. Fail loudly: the round-trip test must run against a real Postgres (or fail as an error), not a SQLite substitute where both types collapse. Boundary/tie: a value at exactly `00:00` on a DST transition day must round-trip to the same instant, which is precisely what the naive type cannot guarantee.

### Major: signature headers are written to the application log
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: The formatted `headers` dict includes `X-Acme-Signature` and `X-Acme-Timestamp`, so every delivery writes a valid signature for a known payload into logs that are shipped and indexed.
What breaks in production: Anyone with log-read access — a broader group than anyone with database access — can replay a captured delivery to the customer endpoint with a valid signature, and because the timestamp is currently outside the MAC that replay is not even time-bounded.
Fix: Log only the non-sensitive fields — `log.info("POST %s delivery=%s event=%s", endpoint.url, delivery.id, delivery.event_type)` — and drop the header dump entirely. Preserve the diagnostic value the line was added for: the destination and the delivery identity must still appear, so an operator can still correlate a delivery to a request. Red-prove: assert with `caplog` that no emitted record contains the value of `SIGNATURE_HEADER` or the secret, and reintroducing `headers=%s` reds it; separately assert the delivery id IS present, so a fix that deletes the log line altogether also reds. Boundary/tie: the URL is logged in full; if endpoint URLs are treated as customer secrets elsewhere, log only its scheme and host.

### Major: `list_deliveries` accepts an unbounded `limit`
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: The query parameter has a lower bound but no upper bound, so `limit` is validated only for positivity and passes straight into `.limit(limit)` (RS3: a boundary parameter that is type-checked but not range-checked).
What breaks in production: A caller requesting `?limit=100000000` makes Postgres materialise and the app serialise the entire delivery table for that endpoint, exhausting memory and blocking the connection pool — a trivial one-request denial of service.
Fix: Change the declaration to `limit: int = Query(50, ge=1, le=200)` so FastAPI rejects out-of-range values at the schema boundary with a 422 rather than clamping silently deep in the handler. Preserve the default behaviour: an unspecified `limit` must still return 50. Red-prove each clause: (a) `?limit=201` returns 422 — removing `le` reds it; (b) `?limit=200` returns 200 with up to 200 rows — setting `le=199` reds it, proving the boundary is inclusive; (c) no `limit` returns 50 rows — changing the default reds it. Fail loudly: a non-integer `limit` must 422, never fall back to the default. Boundary/tie: 200 is accepted, 201 is rejected; 1 is accepted, 0 is rejected.

### Major: `_finish` dereferences a possibly-absent row and stores an unbounded response body
File: `app/webhooks/delivery.py` — `_finish`, `row = session.get(...)` followed immediately by `row.status = status`, and `row.response_body = detail`
What is wrong: `session.get` returns `None` for a deleted delivery and the code assigns through it without a guard, and `detail` carries `response.text` in full with no size cap before it is written to a `TEXT` column.
What breaks in production: A delivery whose endpoint (and cascaded rows) was deleted mid-flight raises `AttributeError` inside the gathered task and kills the worker, and a misbehaving endpoint returning a multi-megabyte error page has that page persisted per attempt and re-served through the deliveries API, bloating the table and the response.
Fix: Guard the lookup — `if row is None: log.warning("delivery %s vanished before finish", delivery_id); return` — and truncate with an explicit marker, `row.response_body = detail[:RESPONSE_BODY_MAX] + ("…[truncated]" if len(detail) > RESPONSE_BODY_MAX else "")` with `RESPONSE_BODY_MAX = 2048`. Do not fix by deleting the truncation marker: the stored value must still say when it was cut, or an operator reads a truncated body as the whole response. Red-prove each clause: (a) call `_finish` for a nonexistent id — must return without raising, and removing the guard reds it; (b) a 3000-character body is stored at 2048 plus the marker — removing the cap reds it; (c) a 2048-character body is stored verbatim with no marker — an off-by-one cap reds it. Boundary/tie: a body of exactly `RESPONSE_BODY_MAX` characters is stored untruncated and unmarked; 2049 is truncated.

### Major: only three event types can ever reach a webhook, contradicting the documented "every event type"
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES` vs `app/webhooks/delivery.py::enqueue_for_event`'s `if not endpoint.event_types` branch and `docs/webhooks.md`
What is wrong: The dispatcher gates enqueue on a hardcoded three-element set while both the endpoint model's `event_types` filter and the docs say an empty `event_types` "subscribes the endpoint to every event type we emit" — the set of deliverable events is defined in two places with different membership (R12/R2).
What breaks in production: A customer who registers an endpoint with no `event_types` receives only `invoice.paid`, `invoice.payment_failed` and `subscription.updated`, and every future event type added to `SUBSCRIBERS` silently fails to deliver until someone remembers to edit this set — a gap with no test and no error.
Fix: Derive the deliverable set from one source — either drop `WEBHOOK_EVENT_TYPES` and enqueue for every dispatched type (letting the per-endpoint `event_types` filter do the selection, which is what the docs describe), or keep the allowlist and correct the docs to enumerate it. Preserve the filtering the set provided: an endpoint that subscribed to a specific list must still receive only those types. Red-prove each clause: (a) an endpoint with empty `event_types` receives a newly added event type — keeping the hardcoded set reds it; (b) an endpoint subscribed to `["invoice.paid"]` does not receive `subscription.updated` — removing the per-endpoint filter reds it; (c) a test asserts the docs' enumeration equals the code's set if the allowlist is kept, so the two cannot drift. Boundary/tie: an endpoint with `event_types == []` is "all types"; the change must not let a `None` value take a different branch from `[]` — the model default is `list`, so pin both.

### Major: the new worker and enqueue paths ship with no tests

### Major: `webhooks_enabled` is added to `organizations` but nothing reads it

### Minor: the delivery-claim index does not cover the claim query's sort
File: `migrations/0042_webhook_delivery.sql` — `CREATE INDEX idx_webhook_deliveries_status ON webhook_deliveries (status)`
What is wrong: `_claim_batch` filters on `status` and `next_attempt_at` and orders by `next_attempt_at`, but the index covers `status` alone, so the planner sorts the whole matching set on every poll.
