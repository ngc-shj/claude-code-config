### Critical: the signature is computed over different bytes than the ones sent, and does not cover the timestamp
File: `app/webhooks/signing.py` — `sign()`, used by `app/webhooks/delivery.py::send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted) while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes with its own compact separators and no key sorting, and the timestamp is returned as a header but never fed into the MAC — so the digest authenticates a byte string the receiver never sees and binds nothing to the time of signing.
What breaks in production: every customer who implements `docs/webhooks.md` ("HMAC-SHA256 of `{timestamp}.{raw_request_body}`") computes a mismatching digest and rejects 100% of our webhooks, and the documented five-minute replay window is unenforceable because an attacker can rewrite `X-Acme-Timestamp` freely without invalidating the signature.
Fix: change `sign` to take the exact bytes that will be sent — `def sign(secret: str, body: bytes, timestamp: str | None = None) -> tuple[str, str]` computing `hmac.new(secret.encode(), f"{ts}.".encode() + body, hashlib.sha256)` — and have `send_once` build `body = serialize(delivery.payload).encode()` once, pass it as `client.post(endpoint.url, content=body, headers=...)`, and sign that same object; give `verify(secret, body, timestamp, signature)` the mirror signature and add a `max_age_seconds: int = 300` freshness check. Preserve, and do not "fix" by deleting: the request must still arrive as a JSON document with `Content-Type: application/json`, and `verify` must keep comparing a real digest rather than being loosened to compare payload dicts. Pair deny with allow: the allow case that must still pass is a round-trip test that takes the bytes MockTransport actually captured plus the captured `X-Acme-Timestamp` and asserts `signing.verify(SECRET, captured_body, captured_ts, captured_sig) is True` (actual producer output through the actual consumer, R40); the deny case is the same bytes with one byte flipped. Red-prove each clause separately by execution, one mutation apiece: (i) revert `content=body` to `json=payload` — the round-trip assertion must red; (ii) drop the `f"{ts}."` prefix — a test asserting that re-signing with `ts+1` yields a different digest must red; (iii) set the fixture timestamp to `now-301` — the freshness assertion must red. Fail loudly rather than silently: `sign` raises `TypeError` if `body` is not `bytes`, and `verify` raises `ValueError` (not returns `False`) when the signature header is absent or is not `sha256=` + 64 hex characters, so "could not check" is never spelled the same as "did not match". Boundary and tie: a timestamp exactly `max_age_seconds` old is ACCEPTED and `max_age_seconds + 1` is rejected; two deliveries signed within the same clock second produce identical timestamps, which is correct because `event_id` is what disambiguates them for the receiver.

### Critical: the unique index on `event_id` alone makes a second endpoint impossible, and the failure is swallowed
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so any org with two subscribed endpoints violates the unique index on the second row, and `session.add_all(rows)` flushes them in one transaction so the first row rolls back with it.
What breaks in production: an org that registers a second endpoint stops receiving webhooks on *both* endpoints, and because `dispatcher.dispatch` wraps the call in `except Exception: log.warning(...)` the only trace is a warning line — no delivery row, no retry, no alert.
Fix: replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the idempotency key the code actually needs (one attempt-record per endpoint per event), and change `enqueue_for_event` to `INSERT ... ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a redelivered event is a no-op rather than an error. Preserve the property the original index was reaching for: re-dispatching the same `event_id` must still not duplicate rows — do not fix this by deleting the uniqueness constraint. Pair deny with allow: the allow case that must still succeed is two active endpoints in one org both receiving a row for one `event_id`; the deny case is calling `enqueue_for_event` twice with the same `(event_id, endpoint)` and asserting the row count stays at 1 and `attempts` is unchanged. Red-prove separately: (i) restore the single-column unique index — the two-endpoint allow test must red; (ii) drop the `ON CONFLICT` clause — the double-enqueue test must red with `IntegrityError`. Fail loudly: remove the blanket `except Exception` in `dispatcher.dispatch` (see the separate finding) so a constraint violation cannot be reported as an ordinary quiet run. Boundary and tie: an org with exactly zero matching endpoints inserts zero rows and `enqueue_for_event` returns `0` — that is a success, not a failure, and the caller must not treat `0` as an error.

### Critical: the migration's status CHECK constraint does not admit the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py::deliver` writing `"failed_permanent"`
What is wrong: the code's own vocabulary (`app/webhooks/models.py::STATUSES` and the `_finish(delivery.id, "failed_permanent", ...)` call) contains `failed_permanent`, which the CHECK constraint rejects, and `STATUSES` is declared but never referenced so nothing reconciles the two spellings (R40 producer-vs-strict-consumer; R55 in the sense that `failed` is a representable value that means something else).
What breaks in production: the terminal write for every exhausted delivery raises `CheckViolation`, the `_finish` transaction rolls back, and the row is left in `in_flight` forever — the deliveries that failed are exactly the ones whose failure is never recorded, so the `/deliveries` inspection endpoint shows them as still in progress indefinitely.
Fix: make the database constraint derive from the single Python source of truth — change the CHECK to `status IN ('pending', 'in_flight', 'delivered', 'failed_permanent')` and add an assertion in `_finish` (`if status not in m.STATUSES: raise ValueError(f"unknown delivery status {status!r}")`) plus a test that iterates `m.STATUSES` and writes each value to a real row, so a future addition to the tuple reds until the migration is updated. Preserve: `failed_permanent` must remain distinguishable from `pending` — do not fix this by widening the column to unconstrained text or by renaming the code's status to `failed` in isolation, which would leave `STATUSES` still unenforced. Pair deny with allow: the allow case is every member of `STATUSES` inserting successfully; the deny case is `_finish(id, "retrying", ...)` raising `ValueError` before it reaches the database. Red-prove separately: (i) revert the CHECK to the old four values — the `STATUSES` round-trip test must red on `failed_permanent`; (ii) delete the `ValueError` guard — the unknown-status test must red. Fail loudly: the guard raises rather than logging and continuing, so an unmappable status is never written as `pending`. Boundary and tie: the transition at exactly `attempt == MAX_ATTEMPTS` is the one that writes `failed_permanent` (attempt 5 is the last attempt, not the first rejected one); a row already in a terminal status that `_finish` is called on again must be a no-op, not a downgrade back to `in_flight`.

### Critical: `list_deliveries` performs no tenancy check, so any authenticated user reads any org's event payloads
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id`, an attacker-supplied path parameter, and never joins back to `WebhookEndpoint.org_id == user.org_id` — while the two sibling routes added in the same file, `create_webhook_endpoint` and `list_webhook_endpoints`, both scope on `user.org_id`, so this is the one site the pattern was not propagated to (R3, security-relevant).
What breaks in production: enumerating integer `endpoint_id` values dumps other organizations' delivery history — and via `WebhookDelivery.to_dict` their `event_type`, `event_id`, and response statuses for billing events like `invoice.paid` — a cross-tenant data breach reachable by any account holder.
Fix: add the join and the predicate — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)` — and raise `HTTPException(404)` (not 403) when the endpoint does not resolve within the caller's org, so the response does not confirm the existence of other orgs' endpoint ids. Preserve: the endpoint must keep returning the caller's own deliveries in `created_at desc` order with the `limit` semantics intact — do not fix this by removing the route or by returning an empty list unconditionally, which would satisfy the deny side and destroy the feature. Pair deny with allow: the allow case that must still succeed is the owning org receiving its own rows for an endpoint it created; the deny case is an org-B user requesting an org-A endpoint id and getting 404 with an empty body. Red-prove each clause separately by execution: (i) delete the `org_id` conjunct — the cross-tenant deny test must red; (ii) delete the join — the owning-org allow test must red (the query no longer resolves); (iii) change the 404 to a 403 — the existence-oracle assertion (`response.status_code == 404` for both a nonexistent id and a foreign id) must red. Fail loudly: `user.org_id` being `None` must raise rather than matching rows with a NULL comparison, so an unauthenticated-but-routed request cannot read everything. Boundary and tie: an endpoint that exists, belongs to the caller, and has zero deliveries returns `200 []` — that case must not be collapsed into the 404 branch, or a legitimate empty history reads as a missing endpoint.

### Critical: the signing secret is returned by the list endpoint, contradicting the security property the docs promise
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`), surfaced by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict` embeds the plaintext signing secret in every serialization, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` hands the secret back on demand — while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (RS4 Critical: an exploitable credential in a served artifact; R29/R49: a documented control stronger than the implementation).
What breaks in production: any token, log sink, browser cache, or support screenshot that touches the list endpoint captures the credential that authenticates every webhook we send, letting the holder forge events (including `invoice.paid`) into the customer's system, and the documentation actively discourages the customer from rotating because it tells them the value is unreadable.
Fix: remove `signing_secret` from `to_dict`, and return it exactly once at the creation site — `return {**endpoint.to_dict(), "signing_secret": secret}` in `create_webhook_endpoint`, where `secret = new_signing_secret()` is held in a local — so the read paths structurally cannot emit it; add a `POST /webhook-endpoints/{id}/rotate-secret` route (org-scoped like the fixed `list_deliveries`) as the supported way to obtain a new one, since the docs' promise is only honest if rotation exists. Preserve: the creating caller must still receive the secret in the 201 body — do not fix this by never returning it, which would make the feature unusable. Pair deny with allow: the allow case is the 201 response containing a `signing_secret` matching `^whsec_`; the deny case is `GET /webhook-endpoints` returning objects whose key set does not contain `signing_secret` at all (assert on the key, not on the value, so a `None` placeholder does not pass). Red-prove each separately: (i) re-add the key to `to_dict` — the list-endpoint key-absence assertion must red; (ii) drop the `{**..., "signing_secret": secret}` merge — the 201 allow assertion must red; (iii) point the rotate route at another org's endpoint — the tenancy assertion must red. Fail loudly: a `to_dict` call on an endpoint whose `signing_secret` is unexpectedly `None` must not silently emit an endpoint that appears secretless; keep the column `nullable=False` and let the read fail. Boundary and tie: after rotation, deliveries already signed with the previous secret and still in `pending`/`in_flight` must be re-signed with the current secret at send time (`send_once` reloads the endpoint, so state this explicitly), and the tie case — two rotations within one second — is resolved by the endpoint row, not by the timestamp.

### Critical: signing secrets are generated with `random`, a predictable non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, which is the Mersenne Twister — a deterministic generator whose full internal state is recoverable from a modest run of its outputs and which is not seeded as key material.
What breaks in production: an attacker who obtains a few secrets (their own registered endpoints are enough, and `create_webhook_endpoint` has no rate limit) can reconstruct the generator state and derive other tenants' signing secrets, then forge signed `invoice.paid` events into those tenants' systems — the signature control the whole feature rests on is defeated without touching our infrastructure.
Fix: use the cryptographic source the standard library already provides — `import secrets` and `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, deleting the `random`/`string`/`_ALPHABET` imports outright rather than leaving them as a fallback (R1(d): the duplicate must go, not be kept as a wrapper). Note the behaviour change this causes at the call site (R1(b)): `token_urlsafe(32)` returns roughly 43 characters, not 32, so the existing `test_new_signing_secret_has_prefix_and_length` assertion `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` must be rewritten to assert entropy-bearing length (`>= len(SECRET_PREFIX) + 40`) — the constant `SECRET_BYTES` now means bytes of entropy, so rename it `SECRET_ENTROPY_BYTES` and state that in the diff, or the column width and the test both encode the old meaning. Preserve: the `whsec_` prefix must remain, because the docs and any customer-side secret-manager keying rely on it. Pair deny with allow: the allow case is that a freshly generated secret still verifies a payload signed with it end to end; the deny case is a uniqueness/entropy assertion — 1,000 generated secrets are all distinct and none is a prefix of another. Red-prove separately: (i) replace `secrets.token_urlsafe` with a constant string — the uniqueness test must red; (ii) drop the prefix — the `startswith(SECRET_PREFIX)` test must red; (iii) truncate to 8 characters — the minimum-length assertion must red. Fail loudly: do not wrap the call in a try/except that falls back to `random` if anything raises; an unavailable entropy source must propagate as an exception and fail endpoint creation. Boundary and tie: a secret of exactly the minimum accepted length passes and one character shorter fails, and two endpoints of the same org must never share a secret — assert that explicitly, since the endpoint is the key's scope.

### Critical: signature verification uses `==` instead of a constant-time comparison
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: the shipped verification primitive compares an HMAC digest with Python's `==`, which short-circuits on the first differing byte (RS1); `docs/webhooks.md` tells customers to "Compare it against your own computation using a constant-time comparison", so the implementation contradicts the guidance it ships alongside.
What breaks in production: an attacker who can submit candidate signatures against this function recovers the expected digest byte by byte from response-time differences, and — because the same module is the reference customers are pointed at — the weakness is replicated into every integration that copies it.
Fix: `import hmac` is already present; change the body to `return hmac.compare_digest(expected, signature)` and give `verify` the timestamp-aware signature from the first finding so the freshness check and the comparison live in one place. Preserve: `verify` must still return `True` for a genuine signature and `False` for a forged one — do not fix this by removing `verify` or by making it raise on every mismatch, which would break the documented customer-side flow. Pair deny with allow: the allow case is the existing `test_verify_accepts_signature_produced_by_sign` (kept, and extended to run against the bytes actually sent); the deny case is `test_verify_rejects_a_signature_made_with_another_secret` plus a new one-byte-flip case, which is the input nearest the boundary — a wholly different string is admitted by a broken comparison too. Red-prove each separately: (i) revert to `==` and assert via `hmac.compare_digest` being patched to record its calls that the production path invokes it — that assertion must red; (ii) delete the one-byte-flip deny fixture's expectation — it must red against a comparison loosened to `expected[:8] == signature[:8]`, which is the one-step loosening this code admits. Fail loudly: `compare_digest` raises `TypeError` on a non-`str`/`bytes` argument — let it, rather than catching and returning `False`, so a caller passing a parsed JSON object gets an error instead of a silent rejection that reads as a bad signature. Boundary and tie: two signatures of equal length that differ only in the final byte must both take the same time and return `False`; the empty-string signature must return `False`, not raise.

### Critical: arbitrary user-supplied URLs are fetched by a server-side worker with redirects followed (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only validation is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://` (contradicting `docs/webhooks.md`, "Only `https://` URLs are accepted"), admits any scheme whose name merely begins with `http` (`httpx:`, `httpfoo:`), and imposes no restriction on the host — so `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:6379/`, or an external host that 302-redirects into the private range all become fetch targets for a worker running inside our network (RS3: a boundary check that does not constrain the value's sink; R1: `pydantic` is already imported here and ships `AnyHttpUrl`, so the scheme check is a hand-rolled reimplementation of a validated helper).
What breaks in production: any customer can turn our delivery worker into a proxy for reading cloud instance-metadata credentials or reaching internal services, and the request carries a POST body they control.
Fix: replace the hand-rolled check with a typed field on the existing model — `url: HttpUrl` on `EndpointIn`, then reject any `url.scheme != "https"` — and add a `_assert_public_host(url)` guard that resolves the hostname with `socket.getaddrinfo` and rejects every resolved address for which `ipaddress.ip_address(addr).is_private or .is_loopback or .is_link_local or .is_reserved` is true; set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure, since a redirect re-introduces exactly the host the guard just checked. Delete the `urlparse`-based check rather than keeping it alongside (R1(d)), and note the behaviour change (R1(b)): existing `http://` endpoints, if any exist, stop validating — that is the intended tightening, and the migration path is to reject them at rotation time with a named error. Preserve: a legitimate public HTTPS endpoint on a non-standard port must still be accepted — do not fix this by allowlisting a fixed set of hostnames, which turns the feature off. Pair deny with allow: the allow case adjacent to the boundary is `https://hooks.example.com:8443/acme` resolving to a public address (accepted); the deny cases are `http://hooks.example.com/acme` (scheme), `httpx://hooks.example.com/` (the near-miss the current `startswith` admits), `https://169.254.169.254/` (address class), and a public host whose DNS resolves to `10.0.0.5` (resolution, not spelling). Red-prove each clause separately by execution: (i) relax `!= "https"` back to `startswith("http")` — the `httpx://` deny test must red; (ii) delete the `_assert_public_host` call — the DNS-to-private-address deny test must red; (iii) restore `follow_redirects=True` — a delivery test whose MockTransport returns a 302 to `http://127.0.0.1/` must red. Fail loudly: when `getaddrinfo` raises or returns nothing, reject with `HTTPException(422, "endpoint host could not be resolved")` — an unresolvable host must not fall through to accepted, and "could not check" must not be spelled like "checked and clean". Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv6 `::1`/`fc00::/7` are on the deny side and must be enumerated explicitly; a host resolving to *both* a public and a private address is denied (any-private wins), and state that the registration-time check does not survive DNS rebinding — the same guard therefore runs again in `send_once` immediately before the POST.

### Critical: `time.sleep` inside an `async def` blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered 100-at-a-time by `run_worker`, but its retry pause is the synchronous `time.sleep`, which parks the whole thread rather than yielding, so the `asyncio.gather` runs the batch strictly serially and the retry sequence (2+4+8+16 = 30 s per delivery) accumulates across the batch.
What breaks in production: one failing endpoint stalls every other org's deliveries behind it, and because the worker's Redis lock is set with a 60 s expiry (`_acquire_lock`) while a single batch can block for far longer, the lock expires mid-batch and a second worker claims and re-sends the same rows — turning a latency bug into duplicate charges-notification traffic at customers.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (the `asyncio` import is already present), and stop holding an in-process retry loop at all: on a retryable failure, write `status="pending"`, `attempts=attempt`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)`, then `return` — letting the poller pick the row up — so a worker restart does not lose the schedule the `next_attempt_at` column exists to hold. Preserve the behaviour the loop provided: the total attempt budget stays at `MAX_ATTEMPTS` and the delays stay the documented 2/4/8/16 s — do not fix this by removing the backoff or by shrinking the attempt count. Pair deny with allow: the allow case is a delivery whose first attempt returns 200 completing with `status="delivered"` and no sleep at all; the deny case is a delivery whose attempt returns 500 being rescheduled with `next_attempt_at` strictly in the future and `status` back to `pending`, with the worker demonstrably free to serve another delivery in the interval (assert two deliveries complete in wall-clock time under the single backoff delay). Red-prove each separately: (i) restore `time.sleep` — the concurrency assertion must red on elapsed time; (ii) delete the `next_attempt_at` update — the reschedule assertion must red because the row becomes immediately re-claimable; (iii) delete the `status="pending"` write — the poller test must red by never re-picking the row. Fail loudly: if `_finish`/reschedule cannot write (the row vanished, the constraint rejected the status), raise rather than returning, so a delivery that could not be recorded is not indistinguishable from one that succeeded. Boundary and tie: at exactly `attempt == MAX_ATTEMPTS` the row goes terminal and is NOT rescheduled; a row whose `next_attempt_at` is exactly `now` is claimable (the filter is `<=`), and two rows with identical `next_attempt_at` are ordered by `id` (see the ordering finding) so neither is starved at the `LIMIT` cut.

### Critical: the only signature test asserts the header's shape, never that the signature verifies the body
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: the test captures `request.content` and the headers but asserts only `startswith("sha256=")` on the signature and `.isdigit()` on the timestamp, so it never runs the production verification primitive over the bytes that were actually transmitted (RT5: the test's call path excludes the primitive it advertises; RT1: the assertions are satisfied by any 71-character string).
What breaks in production: this is precisely the test that would have caught the sign-versus-send byte mismatch above, and a green suite certifies "posts the signed payload" while no payload was ever verified — a hardcoded `"sha256=" + "0"*64` passes it.
Fix: add `assert signing.verify(SECRET, captured["body"], captured["headers"][signing.TIMESTAMP_HEADER], captured["headers"][signing.SIGNATURE_HEADER])` to this test, feeding the transport's captured bytes (actual producer output) through the actual consumer primitive — the round-trip R40 requires — and add a companion asserting the same call returns `False` when one byte of `captured["body"]` is flipped. Preserve: keep the existing `content-type` and `json.loads(body)["type"]` assertions — the fix must not replace payload-shape coverage with signature coverage. Pair deny with allow: the allow case is the untouched captured triple verifying `True`; the deny case is the one-byte-flipped body verifying `False` — the nearest failing input, not a wholly different payload that any broken comparison also rejects. Red-prove each clause separately by execution: (i) change `send_once` to sign `serialize(payload)` while sending `json=payload` (the current defect) — the `verify` assertion must red; (ii) make `sign` ignore the timestamp argument — a third assertion, that re-verifying with `int(ts)+1` returns `False`, must red; (iii) make `verify` `return True` unconditionally — the flipped-body deny assertion must red. Fail loudly: assert the two headers are present with `signing.SIGNATURE_HEADER in captured["headers"]` before verifying, so a missing header fails as "header absent" rather than as `verify` receiving `None`. Boundary and tie: a payload that serializes to zero-length content and a payload containing a non-ASCII string must both round-trip (the encoding of the signed bytes is the tie that breaks silently), and a timestamp exactly at the freshness limit verifies while one second past it does not.

### Major: the `webhooks_enabled` flag is added to the schema and never consulted
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: the column is created defaulting to `FALSE`, but nothing in `app/events/dispatcher.py`, `app/webhooks/delivery.py`, or `app/api/routes/settings.py` reads it, and `WebhookEndpoint.active` is the only gate `enqueue_for_event` applies — a declared capability with no backing path (R41).
What breaks in production: operators and support tooling will read `webhooks_enabled = FALSE` as "this org is not receiving webhooks" while the org in fact receives every subscribed event, so an incident kill-switch that appears to exist does nothing when someone flips it.
Fix: wire the flag at the single choke point — in `enqueue_for_event`, join `Organization` and add `Organization.webhooks_enabled.is_(True)` to the filter, and reject `POST /webhook-endpoints` with `HTTPException(409, "webhooks are not enabled for this organization")` when the flag is false. Preserve: an org with the flag on and an active endpoint must still enqueue exactly as it does today — do not fix this by dropping the column, because the migration's `DEFAULT FALSE` means the operational expectation of an off-switch already exists. Pair deny with allow: the allow case is `webhooks_enabled = TRUE` plus `active = TRUE` producing a row; the deny cases are each single axis flipped off (flag off/active on, flag on/active off) — the axis combination matters because the two gates are independent (RT10 clause 2), and the fourth cell (both off) should be stated as covered by the first two rather than left unclaimed. Red-prove separately: (i) delete the `webhooks_enabled` conjunct — the flag-off deny test must red; (ii) delete the `active` conjunct — the inactive-endpoint deny test must red; (iii) invert the flag default in the fixture — the allow test must red. Fail loudly: if the `Organization` row does not resolve, raise rather than defaulting the flag to `True`; an org whose record cannot be read must not be treated as enabled. Boundary and tie: the migration sets every existing org to `FALSE`, so the deploy of this change is itself the moment webhooks turn off for everyone — the backfill (`UPDATE organizations SET webhooks_enabled = TRUE WHERE ...`) must be part of the same migration or the rollout is a silent outage; state which population is backfilled.

### Major: the dispatcher's hardcoded event-type set is a second, unreconciled subscription gate
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/api/routes/settings.py` — `EndpointIn.event_types`

Fix: add a `claimed_at TIMESTAMPTZ` column set when a row enters `in_flight`, and have the worker reclaim before each batch — `UPDATE webhook_deliveries SET status='pending', claimed_at=NULL WHERE status='in_flight' AND claimed_at < now() - interval '10 minutes'` — with the interval defined as a named constant strictly greater than `REQUEST_TIMEOUT` so a slow-but-live delivery is never reclaimed underneath itself. Preserve: `in_flight` must still prevent two concurrent workers from picking the same row within the window — do not fix this by deleting the status and relying on the lock alone, which is what the lock finding shows is unreliable. Pair deny with allow: the allow case is a row `in_flight` for less than the interval NOT being reclaimed (a live delivery is left alone); the deny case is a row `in_flight` past the interval being reset to `pending` and re-delivered. Red-prove separately: (i) delete the reclaim statement — the stranded-row test must red; (ii) set the interval below `REQUEST_TIMEOUT` — the live-delivery allow test must red by reclaiming a delivery still in flight; (iii) delete the `claimed_at` write — the reclaim query must red by matching nothing. Fail loudly: log at WARNING with the reclaimed row count on every non-zero reclaim, so a repeatedly crashing worker is visible rather than being smoothed over by the recovery. Boundary and tie: a row whose `claimed_at` is exactly the interval old is NOT reclaimed (strict `<`), and a reclaimed row must not have its `attempts` counter incremented — the attempt never completed, and double-counting it shortens the budget for a delivery that was never actually tried.

### Minor: does `session_scope` leave the returned ORM instances usable after the block exits?
File: `app/webhooks/delivery.py` — `_claim_batch` returns `rows` after the `with session_scope()` block; `deliver` then reads `delivery.attempts`, `delivery.payload`, `delivery.id`, and `send_once` reads `endpoint.signing_secret` and `endpoint.url` from an object loaded in a separate, already-closed session
What is wrong: the change reads attributes off ORM instances after the session that loaded them has exited, which under the common SQLAlchemy default (`expire_on_commit=True`, session closed on exit) raises `DetachedInstanceError` on first access — but `app/db.session_scope` is not part of this diff, so I cannot confirm its commit/expire/close semantics.
What breaks in production: if the default holds, every batch raises on the first attribute access and no webhook is ever delivered; if `session_scope` keeps the session open or disables expiry, the code is correct as written.
Closing answer: show that `session_scope` constructs its session with `expire_on_commit=False` and does not close it on exit (or that these objects are re-attached before use). If it does not, the fix is to return plain values from `_claim_batch` — a list of `(id, endpoint_id, event_id, attempts, payload)` tuples or a dataclass — rather than ORM instances, which also removes the cross-session `endpoint` load in `deliver`.

### Minor: `_finish` assumes the delivery row still exists
File: `app/webhooks/delivery.py` — `_finish()`, `row = session.get(m.WebhookDelivery, delivery_id)` followed immediately by `row.status = status`
What is wrong: `session.get` returns `None` for a missing primary key, and the endpoint's `ON DELETE CASCADE` means a customer deleting an endpoint mid-flight removes its delivery rows, so `row` can legitimately be `None`.
What breaks in production: the terminal write raises `AttributeError: 'NoneType' object has no attribute 'status'` inside the gathered coroutine, which — given `asyncio.gather` without `return_exceptions=True` — propagates out of `run_worker`'s `try` and, combined with the `batch` binding defect above, takes the worker down.
Fix: guard with `if row is None: log.info("delivery %s vanished before finish", delivery_id); return`, and pass `return_exceptions=True` to the `asyncio.gather` in `run_worker` so one delivery's failure cannot abort its siblings.

### Minor: the poller's index does not cover its predicate

### Minor: the 201 response is built before the transaction commits
