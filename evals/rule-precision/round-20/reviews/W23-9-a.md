### Critical: delivery history endpoint is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, filter `WebhookDelivery.endpoint_id == endpoint_id`
What is wrong: the query filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can read any other tenant's delivery rows by incrementing the integer id.
What breaks in production: an authenticated customer enumerates `endpoint_id` and reads other organizations' webhook payloads — `WebhookDelivery.payload` is the full event body (`invoice.paid` amounts, subscription state), so this is a cross-tenant data breach reachable from the public API with a valid session.
Fix: join the ownership predicate into the query rather than checking it afterwards — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookDelivery.endpoint_id == WebhookEndpoint.id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id, ...)` — and raise `HTTPException(404)` (not 403) when the join yields nothing, so a foreign id is indistinguishable from a missing one. This is the same predicate `list_webhook_endpoints` already applies (`WebhookEndpoint.org_id == user.org_id`) — reuse that expression, do not add a second parallel ownership check (R48). Deny/allow pairing (Remedy Floor 1): the owning org's request for its own endpoint must still return its rows, asserted with a spy or a returned-id assertion, not merely a 200. Red-prove each clause separately (Floor 2): (a) delete the `org_id` term → the foreign-org test must red on rows returned, (b) delete the `WebhookEndpoint.id == endpoint_id` term → the owner test must red on rows from a sibling endpoint. Fail loudly (Floor 3): if `user.org_id` is `None` (unauthenticated dependency degraded), deny with a named error rather than letting `org_id == None` match rows. Preserve (Floor 4): the endpoint must still return `to_dict()` for legitimate owners — do not "fix" this by removing the route. Boundary and tie (Floor 5): an endpoint whose row was soft-deleted or whose `active` is `False` still belongs to its org and must remain readable; two orgs can never share an `endpoint_id` because it is the primary key, so there is no tie case.

### Critical: the HMAC is computed over bytes that are not the bytes sent on the wire
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted) while `send_once` transmits the body via `client.post(..., json=delivery.payload)`, which httpx serializes independently with its own separators and insertion key order — and the timestamp is never mixed into the MAC at all, despite `docs/webhooks.md` specifying `HMAC("{timestamp}.{raw_request_body}")`.
What breaks in production: every receiver that follows the published verification recipe computes a different digest and rejects 100% of deliveries, and because the timestamp is outside the MAC an attacker who captures one request can replay it forever with a freshened `X-Acme-Timestamp` — the documented five-minute replay window is unenforceable.
Fix: make one byte string authoritative. Change `sign(secret, body_bytes: bytes) -> tuple[str, str]` to take the exact serialized body and compute `hmac.new(secret.encode(), f"{timestamp}.".encode() + body_bytes, hashlib.sha256)`; in `send_once`, build `body = serialize(delivery.payload).encode()` once, pass it as `content=body` (not `json=`) with an explicit `Content-Type: application/json`, and sign that same `body`. `verify(secret, body_bytes, timestamp, signature)` must take the raw received bytes and the received timestamp, reject when `abs(now - int(timestamp)) > 300`, and compare with `hmac.compare_digest` (see the RS1 finding below). Deny/allow pairing (Floor 1): a round-trip test must assert that the signature in the captured request headers verifies against `captured["body"]` verbatim — the allow case — alongside a case where one byte of the body is flipped and verification fails. Red-prove separately (Floor 2): (a) restore `json=delivery.payload` → the round-trip assertion reds on digest mismatch; (b) drop the `f"{timestamp}."` prefix → a replay test that reuses an old body with a fresh timestamp must red; (c) widen the 300s window to `sys.maxsize` → the stale-timestamp test must red. Fail loudly (Floor 3): a non-numeric, absent, or out-of-range `X-Acme-Timestamp` must raise a named `SignatureError`, never fall through to `False` indistinguishably from a wrong key. Preserve (Floor 4): `serialize`'s `sort_keys=True` is what makes the body reproducible for the receiver — keep it; do not "fix" the mismatch by deleting `serialize` and signing whatever httpx happened to emit. Boundary and tie (Floor 5): a timestamp exactly 300s old is accepted (`<=`), 301s is rejected; document that side in `docs/webhooks.md` so receivers implement the same edge.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is the Mersenne Twister, whose full 19937-bit state is recoverable from 624 consecutive outputs and which is seeded predictably per process, so the "secret" is not unguessable; it also yields only ~190 bits over an alphanumeric alphabet despite the constant being named `SECRET_BYTES = 32`.
What breaks in production: an attacker who observes enough generated secrets (or who can create endpoints in a trial account to harvest them) can predict other tenants' signing secrets and forge webhook deliveries that every customer's verifier accepts as authentic — the signature stops being an authenticity control.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` imports, so the module cannot regress to a non-CSPRNG source; rename nothing else, since `SECRET_BYTES` now correctly means bytes of entropy. Existing rows are compromised: add a one-off migration step that regenerates `signing_secret` for every existing `webhook_endpoints` row and a changelog note telling customers to re-read their secret. Deny/allow pairing (Floor 1): the allow case is that `new_signing_secret()` still returns a value starting with `SECRET_PREFIX` that `sign`/`verify` round-trip successfully — pin it, so a fix that returns a constant or raises still fails. Red-prove separately (Floor 2): (a) revert to `random.choice` → a test asserting `secrets.token_urlsafe` is on the call path (patch `secrets.token_urlsafe` and assert it was called) must red; (b) return a fixed string → a test asserting 1000 successive calls are all distinct must red. Note the existing `test_new_signing_secret_has_prefix_and_length` is green under the broken implementation and is therefore not evidence — it asserts prefix and length only. Fail loudly (Floor 3): do not wrap the generation in a try/except that falls back to `random`; if the OS entropy source is unavailable, `secrets` raises and endpoint creation must return 500 rather than issue a weak secret. Preserve (Floor 4): the `whsec_` prefix is what lets customers recognize the value in their own secret manager — keep it. Boundary and tie (Floor 5): `token_urlsafe(32)` returns 43 characters, so `test_new_signing_secret_has_prefix_and_length`'s `== len(SECRET_PREFIX) + SECRET_BYTES` assertion must be updated to a `>=` entropy-floor check in the same change, not deleted.

### Critical: signature comparison is not constant time (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, leaking the length of the matching prefix through timing.
What breaks in production: this function is the reference verifier shipped in this repo — anything inside the product that verifies an inbound signature with it (and any customer who copies it, which `docs/webhooks.md` implicitly invites by describing the scheme) is byte-at-a-time forgeable by an attacker who can measure response latency, defeating the signature entirely.
Fix: `return hmac.compare_digest(expected, signature)` — `hmac` is already imported, so no new dependency; note that `docs/webhooks.md` already tells customers "Compare it against your own computation using a constant-time comparison", so the shipped implementation contradicts its own published guidance (R49: a claim stronger than the implementation). Deny/allow pairing (Floor 1): keep `test_verify_accepts_signature_produced_by_sign`'s allow direction and add the deny direction against a signature differing only in its final byte, so a fix that always returns `False` still fails. Red-prove separately (Floor 2): (a) revert to `==` → a test that asserts `hmac.compare_digest` is on the call path (monkeypatch it and assert invocation) must red; (b) return `True` unconditionally → the wrong-secret test must red. Fail loudly (Floor 3): `compare_digest` raises `TypeError` on mixed str/bytes — normalize both operands to `str` at the top of `verify` and let a non-string `signature` argument raise a named `SignatureError` rather than returning `False`, so "malformed header" is not spelled the same as "bad signature" in the caller's logs. Preserve (Floor 4): `verify` must keep accepting a genuine signature — do not fix by making the function stricter about anything other than the comparison primitive. Boundary and tie (Floor 5): `compare_digest` is constant-time only for equal-length inputs and leaks length; reject any `signature` whose length is not `len("sha256=") + 64` before comparing, and state that a length mismatch is a deny.

### Critical: the signing secret is readable back on every list call and written to the application log
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`); `app/api/routes/settings.py` — `list_webhook_endpoints`; `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: `to_dict()` unconditionally serializes `signing_secret`, and `list_webhook_endpoints` calls it, so `GET /v1/settings/webhook-endpoints` returns every secret in plaintext — directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards") — while `send_once` logs the full header dict at INFO, putting the computed signature into the log stream on every delivery.
What breaks in production: any actor with a read-only API token, and anyone with access to shipped logs or an APM trace, obtains material sufficient to forge deliveries; because the docs assert the secret is unreadable, customers will not have rotated it and no alarm fires.
Fix: split the serializer — `to_dict()` drops `signing_secret` entirely, and a separate `to_dict_with_secret()` is called only from `create_webhook_endpoint`'s 201 response, so the create path is the single site that can emit it (this is the "only one adjudicator" shape, R48). In `send_once`, log `endpoint.url` and `delivery.id` only: `log.info("POST %s delivery=%s", endpoint.url, delivery.id)` — never the header dict. Add an explicit rotation route (`POST /webhook-endpoints/{id}/rotate-secret`) so the docs' "store it yourself" contract is livable. Deny/allow pairing (Floor 1): assert the create response *does* contain `signing_secret` (the allow case that a blanket redaction would break) and that the list response does not, keyed on the literal string, so a fix that redacts everywhere still fails. Red-prove separately (Floor 2): (a) re-add `signing_secret` to `to_dict()` → the list-response test must red; (b) restore the header log line → a caplog test asserting the secret/signature substring is absent from captured records must red. Fail loudly (Floor 3): if `to_dict_with_secret` is called from any module other than the create route, that is a lint/architecture failure, not a silent pass — add a test that greps the call sites and fails naming the offending file. Preserve (Floor 4): do not fix by deleting the list endpoint or by dropping `url`/`active`/`event_types` from `to_dict()`; the list response must remain useful. Boundary and tie (Floor 5): an endpoint created and listed in the same request cycle must still hide the secret in the list projection — the boundary is the response serializer, not the request's recency.

### Critical: the status CHECK constraint rejects the value the code writes on permanent failure
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the migration enumerates `'failed'` while both `STATUSES` in the model and the only writer in `delivery.py` use `'failed_permanent'`, so the terminal-failure write violates the constraint.
What breaks in production: the first delivery that exhausts `MAX_ATTEMPTS` raises `IntegrityError` inside `_finish`, the row stays `in_flight` forever, and if the exception escapes `deliver` it takes down the `asyncio.gather` for the whole batch — the retry system fails exactly when it is needed.
Fix: change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive it rather than restating it: build the SQL fragment from `models.STATUSES` in a generated-migration test that fails when the two lists diverge (R3/R18 — the enum exists in three places; the model's `STATUSES` is the existing shared definition the migration reimplements). Deny/allow pairing (Floor 1): assert that inserting each member of `STATUSES` succeeds (the allow side — a constraint tightened to reject everything would otherwise pass) and that an unknown value like `'oops'` is rejected. Red-prove separately (Floor 2): (a) remove one member from the DDL list → the per-member insert test reds naming that member; (b) drop the CHECK entirely → the `'oops'` rejection test reds. Fail loudly (Floor 3): if the sync test cannot read the migration file (renamed, moved), it must fail with "migration file not found", never skip — an unreadable subject is not a pass. Preserve (Floor 4): keep the CHECK; do not resolve the divergence by deleting the constraint so both spellings are accepted. Boundary and tie (Floor 5): `'failed_permanent'` is 16 characters against the model's `String(20)` and the DDL's `TEXT` — state that 20 is the cap and that any future status name must fit it, or widen both together.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness is on `event_id` alone, but `enqueue_for_event` creates one `WebhookDelivery` row per matching endpoint for a single event, so any org with two subscribed endpoints inserts two rows with the same `event_id`.
What breaks in production: `session.add_all(rows)` raises `UniqueViolation` on flush for every org with more than one endpoint, and because `dispatch` wraps the call in `except Exception: log.warning(...)`, the failure is swallowed — those orgs silently receive no webhooks at all, with only a warning line as evidence.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the docs' "deduplicate on `event_id`" advice actually needs — per-endpoint at-most-once, not per-event. Deny/allow pairing (Floor 1): assert that one event fanned out to two endpoints of the same org inserts two rows (the allow case the current index breaks) and that re-enqueueing the same `(endpoint_id, event_id)` pair is rejected. Red-prove separately (Floor 2): (a) revert to the single-column index → the two-endpoint fan-out test reds on `UniqueViolation`; (b) drop the index → the duplicate-enqueue test reds by inserting twice. Fail loudly (Floor 3): `enqueue_for_event` must translate the `UniqueViolation` from a genuine duplicate into an explicit "already enqueued, skipping" outcome and re-raise anything else, so a real constraint problem is not indistinguishable from idempotent re-delivery. Preserve (Floor 4): keep uniqueness — do not fix the fan-out by dropping the index, which is what makes at-least-once delivery deduplicable. Boundary and tie (Floor 5): two endpoints of *different* orgs subscribed to the same event are also two rows and must be permitted; the tie on `(endpoint_id, event_id)` is exactly the retry case, which must update the existing row rather than insert a second.

### Critical: endpoint URL validation admits plaintext and internal targets, and redirects are followed (RS3)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http://` (contradicting `docs/webhooks.md`'s "Only `https://` URLs are accepted") and any scheme merely prefixed with `http`, no check rejects loopback / link-local / RFC1918 hosts, and the worker follows redirects — so a caller-supplied URL becomes a server-side request to an arbitrary target of the caller's choosing.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or a public host that 302s there) and the worker POSTs to it and stores the response in `WebhookDelivery.response_body`, which the caller then reads back via `GET .../deliveries` — a full SSRF-to-credential-exfiltration chain with a built-in read channel; separately, plaintext `http` puts every event payload on the wire in the clear.
Fix: validate in the pydantic schema, not in the handler body — `url: HttpUrl` with a field validator that requires `scheme == "https"`, rejects a `netloc` that resolves to a loopback / link-local / private / reserved address (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved` over every A/AAAA record), and rejects userinfo and non-default ports outside an allowlist. Set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure; re-check the resolved address at connect time via a pinned-resolution transport, because DNS re-resolution between validation and delivery is the rebinding window (R51). Cap and redact `response_body` before storing it (see the related Major below). Deny/allow pairing (Floor 1): assert that a legitimate public `https://hooks.example.com/acme` still validates and still delivers — a validator that denies everything otherwise satisfies every other clause. Red-prove separately (Floor 2): (a) remove the scheme check → an `http://` registration test reds; (b) remove the private-range check → a `https://127.0.0.1/` registration test reds; (c) set `follow_redirects=True` → a test whose handler returns a 302 to a private address reds on the request being issued. Fail loudly (Floor 3): when DNS resolution fails or times out during validation, return 422 naming "endpoint host could not be resolved" — an unresolvable host must not be admitted on the grounds that no private address was seen. Preserve (Floor 4): the feature is customer-supplied endpoints; do not fix by hardcoding an allowlist of hostnames. Boundary and tie (Floor 5): a host resolving to both a public and a private address must be rejected (any-private denies), and `0.0.0.0`/`::`/IPv4-mapped IPv6 forms must be normalized before the range test, since those are the spellings that bypass a naive string check (R47).

### Critical: `time.sleep` inside the async retry loop blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather`, but the backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, so the coroutine holds the event loop for the whole delay.
What breaks in production: one failing endpoint stalls every other concurrent delivery — a batch of 100 rows each retrying to `MAX_ATTEMPTS` serializes into `100 × (2+4+8+16) = 3000` seconds of frozen loop, during which the 60-second `LOCK_KEY` expiry lapses and a second worker starts re-delivering the same rows.
Fix: `await asyncio.sleep(delay)`; `asyncio` is already imported. Since the retry loop then holds the row `in_flight` for minutes, restructure it to persist the next attempt instead of sleeping in-process — on a retryable failure call `_finish(delivery.id, "pending", attempt, status_code, detail)` with `next_attempt_at = now + backoff_for(attempt)` and return, letting the next `_claim_batch` pick it up; that also removes the lock-expiry race above. Deny/allow pairing (Floor 1): assert that a delivery which succeeds on the first attempt still completes without any sleep at all — a fix that always defers would otherwise pass. Red-prove separately (Floor 2): (a) restore `time.sleep` → a test that runs two `deliver` coroutines concurrently and asserts total wall time is less than the sum of their delays must red; (b) remove the `next_attempt_at` advance → a test asserting the retried row is not immediately re-claimable must red. Fail loudly (Floor 3): if `backoff_for` is handed a negative or absurd attempt count the delay must raise rather than compute a zero-second retry storm. Preserve (Floor 4): the retry budget itself — `MAX_ATTEMPTS == 5` and the exponential shape — must be preserved; do not fix the blocking by removing retries. Boundary and tie (Floor 5): `attempt >= MAX_ATTEMPTS` is the terminal boundary, so attempt 5 is the last one *tried* and yields four sleeps; state that explicitly, since the docs' "at most 5 times" and the test's four parametrized rows currently encode it only by coincidence.

### Critical: no test binds the transmitted signature to the transmitted body (RT5)
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`
What is wrong: the send test captures both `headers` and `body` but asserts only that the signature header *starts with* `sha256=`, never that it verifies against the captured body; and `test_verify_accepts_signature_produced_by_sign` is an identity — `verify` calls `sign` internally, so it cannot fail for any input.
What breaks in production: the suite is fully green against a signature scheme that no receiver can validate (see the serialization Critical above) — the fixture payload `{"id": ..., "type": ..., "amount_cents": ...}` even has a non-sorted key order, so the mismatch is present in the very data the test captures and still goes undetected.
Fix: add `assert signing.verify(SECRET, captured["body"], captured["headers"][signing.TIMESTAMP_HEADER], captured["headers"][signing.SIGNATURE_HEADER])` operating on the raw captured bytes and the received timestamp, so the test's call path reaches the production `sign` output as it appears on the wire; and rewrite the verify tests to compare against an independently computed expected digest (`hmac.new(SECRET.encode(), b"<ts>." + body, sha256).hexdigest()` written out in the test) rather than against `sign`'s own output, per RT1's "assert against an independently written expected value". Deny/allow pairing (Floor 1): keep the passing case above and add a case where a single byte of `captured["body"]` is mutated before verification and the assertion must be `False`. Red-prove separately (Floor 2): (a) change `serialize` to drop `sort_keys` → the wire-verification assertion reds; (b) remove the timestamp from the MAC → the independently-computed-digest assertion reds; (c) make `verify` return `True` unconditionally → the mutated-body assertion reds. Fail loudly (Floor 3): if the mock transport is never invoked (handler not called), the test must fail on an explicit `assert captured, "transport handler never ran"` rather than passing over an empty dict. Preserve (Floor 4): keep the existing content-type and payload-shape assertions — the new assertion is added, not substituted. Boundary and tie (Floor 5): state which timestamp the test uses (the header value, not a freshly generated one), because re-deriving `int(time.time())` inside the assertion is exactly the tie that would make it pass across a second boundary and fail one time in a thousand.

### Major: ORM objects are used after their session scope has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (reads `endpoint.signing_secret` after the `with` block)
What is wrong: both functions return or retain SQLAlchemy instances past the end of their `session_scope()` block and then read attributes off them (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret`, `endpoint.url`).
What breaks in production: under the default `expire_on_commit=True` every attribute is expired at commit, so the first read on the detached instance raises `DetachedInstanceError` and the worker delivers nothing at all — a total-path failure that the current suite cannot see because no test calls `_claim_batch`, `deliver`, or `run_worker`.
Fix: stop passing ORM instances across the boundary — have `_claim_batch` return plain dataclasses or tuples (`DeliveryJob(id, endpoint_id, payload, attempts)`) materialized inside the session, and have `deliver` load the endpoint's `url` and `signing_secret` into a value object inside its own `session_scope()` before use. Deny/allow pairing (Floor 1): assert a happy-path delivery end-to-end against a real (SQLite/Postgres) session — the allow case — as well as asserting no attribute access happens post-scope. Red-prove separately (Floor 2): (a) return the ORM rows again from `_claim_batch` → the end-to-end test reds with `DetachedInstanceError`; (b) drop `signing_secret` from the value object → the signature assertion reds. Fail loudly (Floor 3): if `session.get(WebhookEndpoint, delivery.endpoint_id)` returns `None` (endpoint deleted mid-flight), mark the delivery `failed_permanent` with a named reason rather than raising `AttributeError` on `None.signing_secret`. Preserve (Floor 4): keep batch claiming — do not fix by loading one row at a time in the request path. Boundary and tie (Floor 5): a row claimed by this batch and concurrently deleted is the tie; define that as a permanent failure, not a retry.

### Major: the dispatch lock is not atomic and expires before a batch can finish
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `get` then a separate `set`, which two workers interleave freely; the `expire` is a third round trip so a crash between `set` and `expire` leaves the key with no TTL forever; and the `finally` deletes `LOCK_KEY` unconditionally even if the 60-second TTL already lapsed and another worker now owns it.
What breaks in production: two workers claim overlapping batches and POST the same event twice to customer endpoints, or one crash wedges the key permanently and all delivery stops with no alarm.
Fix: use a single atomic `SET LOCK_KEY <token> NX EX 60` where `<token>` is a per-worker uuid, and release with a compare-and-delete Lua script that deletes only when the stored value equals this worker's token; renew the TTL from a heartbeat task while the batch runs, or (better, given the previous finding) shorten the critical section by persisting retries instead of sleeping through them. Deny/allow pairing (Floor 1): assert a single worker still acquires the lock and processes its batch — a `SET NX` that always fails would otherwise satisfy every other clause. Red-prove separately (Floor 2): (a) revert to `get`-then-`set` → a test driving two `_acquire_lock` calls against a fake Redis with an interleave point must red on both returning `True`; (b) replace the compare-and-delete with a plain `delete` → a test where worker A's TTL has expired and worker B holds the lock must red on A deleting B's key. Fail loudly (Floor 3): when Redis is unreachable, `_acquire_lock` must raise and the worker must back off, never return `True` on the grounds that no lock was found. Preserve (Floor 4): the 60-second TTL exists so a crashed worker does not wedge delivery — keep a bounded TTL, do not fix the expiry race by removing it. Boundary and tie (Floor 5): a renewal arriving exactly at the TTL boundary must be treated as expired (fail-closed), and the token comparison is what breaks the tie between two workers that both believe they hold it.

### Major: `in_flight` is a non-terminal state with no recovery path (R38)
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `run_worker`
What is wrong: rows are moved to `in_flight` at claim time and are only ever moved out by a successful `_finish` in the same process; a worker crash, a redeploy, an `IntegrityError` from the CHECK constraint above, or an exception escaping `asyncio.gather` strands them, and nothing ever re-claims a row that is not `pending`.
What breaks in production: every worker restart permanently orphans whatever was in flight — customers silently lose those events, and the loss is invisible because `_claim_batch` only ever queries `status == "pending"`.
Fix: add a `claimed_at TIMESTAMPTZ` column set at claim time and a reaper that returns rows with `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` to `pending` with `next_attempt_at = now()`, incrementing `attempts` so the reaped row still respects `MAX_ATTEMPTS`; run the reaper from `run_worker` before each claim. Deny/allow pairing (Floor 1): assert a row claimed 10 seconds ago is *not* reaped (the allow case a too-aggressive reaper would break) alongside one claimed 10 minutes ago that is. Red-prove separately (Floor 2): (a) remove the age predicate → the fresh-claim test reds on a live row being stolen; (b) remove the `attempts` increment → a test asserting a repeatedly-reaped row eventually reaches `failed_permanent` reds by looping forever (bound the loop so it reds rather than hangs). ### Major: naive and timezone-aware datetimes are mixed across the enqueue/claim boundary, and the DDL disagrees with the model
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`) vs `_claim_batch` (`now = datetime.now(timezone.utc)`); `app/webhooks/models.py` (`DateTime(timezone=True)`) vs `migrations/0042_webhook_delivery.sql` (`TIMESTAMP NOT NULL`)

Fix: change all four columns in the migration to `TIMESTAMPTZ` to match `DateTime(timezone=True)`, and replace `datetime.utcnow()` with the module's existing `_now()` helper from `app/webhooks/models.py` (the change already contains this helper — `delivery.py` reimplements it inline, R1). Deny/allow pairing (Floor 1): assert a row enqueued with `next_attempt_at = now` *is* claimed immediately (the allow case) as well as one an hour in the future being skipped, both run under a non-UTC session timezone. Red-prove separately (Floor 2): (a) restore `datetime.utcnow()` → the non-UTC claim test reds; (b) revert a column to `TIMESTAMP` → a test asserting `information_schema.columns.data_type == 'timestamp with time zone'` reds. Fail loudly (Floor 3): reject a naive datetime at the model boundary with a validator that raises naming the field, so a future naive write fails at the call site rather than being silently localized. Preserve (Floor 4): the scheduling semantics must survive — do not fix the skew by widening the claim predicate's tolerance. Boundary and tie (Floor 5): a row whose `next_attempt_at` equals `now` exactly is claimed (`<=`), and ties on equal `next_attempt_at` order arbitrarily — the `ORDER BY next_attempt_at` has no tiebreak, so add `, id` to make paging and claiming deterministic (R57).

### Major: the retry policy contradicts its own published documentation (R49)
File: `app/webhooks/delivery.py` — `deliver`, `backoff_for`; `docs/webhooks.md` — "Retries"
What is wrong: the docs state backoff is "exponential with jitter" and that "a 4xx is permanent and we stop immediately", but `backoff_for` is a bare `2**attempt` with no jitter (pinned to exact values by `test_backoff_grows_exponentially`) and `deliver` retries every non-2xx response including 400/401/404 up to `MAX_ATTEMPTS`.
What breaks in production: a customer endpoint returning 401 after a credential rotation is hammered five times per event across every queued delivery, and with no jitter all deliveries claimed in the same batch retry in lockstep — a synchronized thundering herd against one host, which is precisely what the documented jitter was there to prevent.
Fix: classify the response before retrying — treat `400 <= code < 500 and code not in (408, 425, 429)` as `failed_permanent` immediately, honour `Retry-After` on 429, and add jitter as `backoff_for(attempt) * random.uniform(0.5, 1.5)` (jitter is not a security value, so `random` is correct here, unlike `new_signing_secret`). Update `test_backoff_grows_exponentially` to assert the range rather than the exact value, in the same change. Deny/allow pairing (Floor 1): assert a 500 and a timeout *are* still retried — the allow side a blanket "4xx-and-up is permanent" fix would break — alongside a 404 that is not. Red-prove separately (Floor 2): (a) remove the 4xx classification → the 404 test reds by observing a second request; (b) remove the 408/429 exclusions → the 429 retry test reds; (c) remove the jitter multiplier → a test asserting two consecutive `backoff_for` results differ reds. Fail loudly (Floor 3): a response with no status code (transport-level error) must route to the retryable branch explicitly, not fall through the classifier's else. Preserve (Floor 4): keep `MAX_ATTEMPTS` and the exponential base — do not "fix" the herd by flattening the backoff. Boundary and tie (Floor 5): 400 is permanent and 399/500 are retryable; state 429 and 408 as named exceptions on the permanent side of that boundary so the next reader does not re-derive them.

### Major: webhook enqueue failures are swallowed, so the event is lost with only a warning
File: `app/events/dispatcher.py` — `dispatch`, `except Exception as exc: log.warning(...)`
What is wrong: `enqueue_for_event` is called after the event's `session_scope()` has already committed, and any failure — the `UniqueViolation` from the single-column index above, a DB blip, a serialization error — is caught by a bare `except Exception` and downgraded to a WARNING with no retry, no dead-letter row, and no signal to the caller.
What breaks in production: the event is durably recorded while its webhook rows are not, so the customer never receives the notification and no reconciliation path exists — a silent, permanent divergence between `events` and `webhook_deliveries` (Remedy Floor 4's shape inverted: the error handling deletes exactly the signal that would have made the defect visible).
Fix: make enqueue part of the same transaction as the event insert — move the `enqueue_for_event` call inside the `with session_scope()` block so the delivery rows commit atomically with the `Event` row (this is the transactional-outbox shape the `webhook_deliveries` table already implements; the change reimplements half of it). If it must stay outside, replace the bare catch with a narrow `except (OperationalError, IntegrityError)` that writes a durable retry marker and re-raises everything else at ERROR with `exc_info=True`. Deny/allow pairing (Floor 1): assert the happy path still commits both the event and its delivery rows and still returns `event_id` — a fix that makes `dispatch` raise on every enqueue problem would otherwise pass. Red-prove separately (Floor 2): (a) restore the bare `except Exception: log.warning` → a test injecting an enqueue failure and asserting the event row was rolled back (or the retry marker written) reds; (b) remove the `exc_info=True` → a caplog test asserting the traceback is captured reds. Fail loudly (Floor 3): an enqueue that raises must not leave `dispatch` returning a successful `event_id` to its caller — the failure must be named in the return contract or the exception. Preserve (Floor 4): in-process `SUBSCRIBERS` must keep firing on their existing path; do not fix by moving webhooks in front of them. Boundary and tie (Floor 5): an event whose org has zero matching endpoints legitimately enqueues zero rows — that is success, not failure, and must be distinguished from an enqueue that errored (the count `0` is an in-band sentinel today, R55).

File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`, `if envelope.type in WEBHOOK_EVENT_TYPES`; `app/webhooks/delivery.py` — `enqueue_for_event`'s `if not endpoint.event_types or event_type in endpoint.event_types`; `docs/webhooks.md`

### Major: one failing delivery aborts the whole batch and can leave `batch` unbound
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])` and the trailing `if not batch:`
What is wrong: `gather` without `return_exceptions=True` propagates the first exception and leaves the sibling coroutines running detached with no one awaiting them; and because `batch` is assigned inside the `try` while `if not batch` is read after the `finally`, a raise from `_claim_batch` exits `run_worker` entirely (the worker process stops polling).
What breaks in production: a single malformed row — the `DetachedInstanceError`, the CHECK-constraint `IntegrityError`, an unhandled `httpx` error — kills the delivery worker, and every subsequent event queues up unnoticed because nothing monitors that the loop is still running.
Fix: pass `return_exceptions=True`, then iterate the results and route each exception to `_finish(..., "pending" or "failed_permanent", ...)` with the exception text as `detail`; initialize `batch: list = []` before the `try` and wrap the loop body in a broad `except Exception: log.exception(...); await asyncio.sleep(poll_interval); continue` so the worker survives a bad iteration. Deny/allow pairing (Floor 1): assert a batch where every delivery succeeds still completes and still sleeps only when empty — a fix that swallows results indiscriminately would otherwise pass. Red-prove separately (Floor 2): (a) drop `return_exceptions=True` → a test with one raising delivery among three asserting the other two completed reds; (b) remove the outer `except` → a test making `_claim_batch` raise once and asserting the worker performs a second poll reds. Fail loudly (Floor 3): each swallowed per-delivery exception must be logged at ERROR with the delivery id and `exc_info=True`, and a batch where *every* delivery raised must emit a distinct alarm — "all failed" must not look like "all delivered". Preserve (Floor 4): the crash currently at least stops the worker visibly; the replacement must not become a silent infinite error loop, hence the ERROR-level logging and the distinct all-failed signal. Boundary and tie (Floor 5): an empty batch sleeps `poll_interval`; a non-empty batch loops immediately — keep that distinction explicit, since `if not batch` is currently the only thing preventing a busy-spin.

### Major: the full response body of an untrusted endpoint is stored and returned unbounded
