### Critical: signed bytes are not the bytes sent, and the timestamp is not in the MAC
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, used by `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` and returns a timestamp that is never fed into the MAC, while `send_once` transmits `client.post(..., json=delivery.payload)` — httpx serializes without `sort_keys`, so the signed string differs from the transmitted body for any payload whose keys are not already in sorted order, and `docs/webhooks.md` tells customers to HMAC `"{timestamp}.{raw_request_body}"`, which the server never computes.
What breaks in production: every customer who implements the documented verification gets a permanent mismatch and drops 100% of events, and every customer who instead ignores the timestamp is replayable forever because the unauthenticated `X-Acme-Timestamp` can be rewritten by anyone who captures one request — the five-minute window `docs/webhooks.md` calls "what stops a captured request from being replayed" stops nothing.
Fix: make the signed string the exact transmitted bytes. Add `def canonical_body(payload) -> bytes` in `signing.py` returning `json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`; change `sign(secret, body: bytes, timestamp: str)` to MAC `timestamp.encode() + b"." + body`; change `send_once` to compute `body = canonical_body(delivery.payload)` once and pass `content=body` (not `json=`) with `Content-Type: application/json`, so the signed bytes and the wire bytes are the same object. **Allow side:** a round-trip test must still SUCCEED — take `captured["body"]` from the MockTransport handler in `tests/webhooks/test_delivery.py`, recompute `hmac.new(SECRET.encode(), captured["headers"][signing.TIMESTAMP_HEADER].encode() + b"." + captured["body"], sha256).hexdigest()`, and assert it equals the signature header verbatim; a second test asserts a doc-literal reimplementation (independent of `sign`) also matches. **Red-proof, one mutation per clause, each executed:** (i) drop `sort_keys` from `canonical_body` and confirm the round-trip assertion reddens on a payload with unsorted keys such as `{"b":2,"a":1}`; (ii) remove `timestamp.encode() + b"."` from the MAC and confirm a replay test that reuses a body with a shifted timestamp goes from reject to accept; (iii) revert `content=body` back to `json=payload` and confirm the byte-identity assertion reddens. **Fails loudly:** `sign` raises `TypeError` on a non-`bytes` body and `ValueError` on a non-numeric timestamp rather than signing something else, so "could not canonicalize" is never spelled the same as "signed". **Preserve:** keep `X-Acme-Timestamp` and the `sha256=` prefix on the signature — do not fix this by deleting the timestamp header, which is what makes replay detection possible at all. **Boundary and tie:** state in `docs/webhooks.md` that the receiver rejects `now - timestamp > 300s` and accepts exactly `300s`, and that a timestamp in the future by more than the same 300s is rejected.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is 32 characters drawn with `random.choice`, which is the Mersenne Twister — a non-cryptographic PRNG whose full internal state is recoverable from a modest run of outputs.
What breaks in production: an attacker who registers a handful of their own endpoints and reads back their own secrets (trivial today, see the secret-disclosure finding below) can reconstruct the generator state and derive other tenants' signing secrets, then forge `invoice.paid` webhooks that every customer's verification accepts as genuine.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`, `string`, and `_ALPHABET` imports/module state so the weak generator cannot be reached from this module at all; rename `SECRET_BYTES` to mean what it says (32 bytes of entropy) and update the length assertion accordingly. **Allow side:** the existing `test_new_signing_secret_has_prefix_and_length` must still pass in its prefix clause — pin that `new_signing_secret().startswith(SECRET_PREFIX)` and that two consecutive calls differ, so a fix that returns a constant is rejected. **Red-proof, executed separately:** (i) monkeypatch `secrets.token_urlsafe` to return a fixed string and confirm the "two calls differ" assertion reddens; (ii) add a static check (or a grep test) asserting `"random"` is not imported by `app/webhooks/signing.py`, then re-add the import and confirm that check reddens — the current length-only test cannot redden for this defect, which is why it is not sufficient. **Fails loudly:** if `secrets` is unavailable the module must fail at import rather than fall back to any other generator; there is no degraded path. **Preserve:** keep the `whsec_` prefix and the documented "response is the only place the secret appears" property — do not fix entropy by shortening or truncating the secret. **Boundary and tie:** with `token_urlsafe(32)` the emitted length is 43 characters, so the length assertion must be `len(secret) == len(SECRET_PREFIX) + 43`, not `+ SECRET_BYTES`; state explicitly that two secrets colliding is a 2^-256 event and is not handled specially.

### Critical: `verify()` compares the signature with `==`
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: an HMAC is compared with Python's short-circuiting `==` instead of `hmac.compare_digest`, and `docs/webhooks.md` instructs customers to use "a constant-time comparison" while our own helper does not (RS1).
What breaks in production: any caller reaching this helper over the network leaks the correct signature one byte at a time through response timing, letting an attacker forge a valid signature without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, and have `verify` take the same `(secret, body: bytes, timestamp: str, signature: str)` arguments as the corrected `sign` so it recomputes over the received bytes rather than over a re-serialized dict. **Allow side:** `test_verify_accepts_signature_produced_by_sign` must still pass — a genuine signature must still verify, so a fix that returns `False` unconditionally is rejected. **Red-proof, executed separately:** (i) revert to `==` and confirm a test asserting `compare_digest` is on the call path (patch `hmac.compare_digest` with a counting spy and assert it was called once) reddens; (ii) flip one hex character of a valid signature and confirm `verify` returns `False`. **Fails loudly:** `compare_digest` raises `TypeError` on mixed str/bytes — let it raise rather than catching and returning `False`, so a caller that passes the wrong type gets an error instead of a silent deny that reads as a rejected signature. **Preserve:** keep `verify` returning a bool and keep the negative test `test_verify_rejects_a_signature_made_with_another_secret`. **Boundary and tie:** state that a signature of the wrong length returns `False` (never raises) and that the empty-string signature is a rejection, not a match.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: the query filters on the path parameter alone and never joins to `WebhookEndpoint.org_id == user.org_id`, while all three sibling handlers in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) do scope by `user.org_id` — the shared tenancy pattern already exists in the file and this route omits it (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` and read other organizations' delivery history — event types, timing, and failure detail — a cross-tenant data breach reachable with a single incrementing integer.
Fix: rewrite the query as `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and raise `HTTPException(404)` — not 403 — when the endpoint does not exist or is not the caller's, so the response does not disclose which endpoint ids are real. **Allow side:** pin that the OWNING org still gets its rows: a test where `user.org_id` matches the endpoint's org must return the seeded deliveries, so a fix that always returns `[]` is rejected. **Red-proof, executed separately:** (i) delete the `org_id` clause and confirm the cross-tenant test flips from 404 to 200; (ii) delete the seeded row and confirm the owning-org test reddens on an empty list rather than passing vacuously. **Fails loudly:** when `user.org_id` is `None` the handler must raise rather than fall through to an unfiltered query — an absent subject denies. **Preserve:** the endpoint must keep returning the most recent attempts for the caller's own endpoint; do not fix this by removing the route. **Boundary and tie:** an endpoint that exists but whose `org_id` differs returns 404 identically to one that does not exist, and a soft-deleted/inactive endpoint owned by the caller still returns its history.

### Critical: the signing secret is returned on every read of the endpoint list
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict()` embeds the secret and is used by both `create_webhook_endpoint` and `list_webhook_endpoints`, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards"), and contradicting the file's own precedent where `list_api_keys` returns only `k.prefix` and never the key material (R49: claim stronger than implementation).
What breaks in production: every browser cache, proxy log, and support screenshot of `GET /v1/settings/webhook-endpoints` now carries live signing secrets, and a read-only token that should not be able to forge webhooks can mint valid signatures.
Fix: remove `signing_secret` from `to_dict()`; have `create_webhook_endpoint` build its 201 body as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable returned by `new_signing_secret()`, so the secret exists on exactly one code path. Add a rotation route if read-back is needed rather than leaving it readable. **Allow side:** pin that creation still returns the secret exactly once — assert `"signing_secret" in create_response` — so a fix that strips it everywhere (and leaves customers unable to configure verification) is rejected. **Red-proof, executed separately:** (i) re-add `signing_secret` to `to_dict()` and confirm a test asserting `"signing_secret" not in list_response[0]` reddens; (ii) remove the merge in the create handler and confirm the creation-returns-secret test reddens. **Fails loudly:** the list handler should assert the serialized dict's key set equals a frozen allowlist and raise on any unexpected key, so a future column added to `to_dict()` fails the request rather than silently leaking. **Preserve:** `to_dict()` must keep returning `id`, `url`, `event_types`, and `active` — the fix is redaction of one field, not removal of the serializer. **Boundary and tie:** state that an endpoint created before this change keeps its existing secret (no forced rotation), and that two endpoints of the same org returned in one list response are both redacted.

### Critical: the migration's status CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py:_finish(..., "failed_permanent", ...)` and `app/webhooks/models.py:STATUSES`
What is wrong: the DB is the strict consumer of an enum spelling the producer does not use — Python writes `failed_permanent`, the constraint permits `failed` (R40, enum spelling).
What breaks in production: the first delivery to exhaust `MAX_ATTEMPTS` raises a `CheckViolation`, the update rolls back, the row is left stuck in `in_flight` forever, and the exception propagates out of `deliver` through `asyncio.gather` and kills `run_worker` — one bad customer endpoint takes down webhook delivery for every tenant.
Fix: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive both sides from one source — import `STATUSES` from `app/webhooks/models.py` in a test that asserts the tuple equals the set parsed out of the migration file, so the two cannot drift again. **Allow side:** pin that a legal transition still SUCCEEDS — an integration test that inserts a pending row and calls `_finish(id, "delivered", ...)` must commit and read back `delivered`. **Red-proof, executed separately:** (i) revert the constraint to `'failed'` and confirm a test calling `_finish(id, "failed_permanent", ...)` against a real (not mocked) database reddens with an integrity error; (ii) append a bogus member to `STATUSES` and confirm the migration-parity test reddens. **Fails loudly:** the parity test must fail — not skip — when the migration file cannot be found or parsed, so "examined nothing" is distinguishable from "found nothing". **Preserve:** keep the CHECK constraint; do not fix the mismatch by dropping it, which is what makes an unknown status visible at write time. **Boundary and tie:** name what happens to rows already stuck in `in_flight` — the migration needs a backfill statement, and state whether `in_flight` rows older than the 60s lock TTL are reset to `pending` or left for manual triage.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint, all carrying the same `event_id`, so any org with two subscribed endpoints violates the unique index on the second insert; the index should be on `(endpoint_id, event_id)`.
What breaks in production: the whole `session_scope` transaction in `enqueue_for_event` rolls back, `dispatch` swallows the exception as a `log.warning`, and the org receives **zero** webhooks for that event — a silent total delivery outage for exactly the customers who registered more than one endpoint.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` and keep it unique so the idempotency guarantee the docs promise is enforced by the database rather than by hope. **Allow side:** pin the fan-out that must SUCCEED — a test enqueuing one event for an org with two active endpoints asserts `enqueue_for_event` returns 2 and that two rows exist with distinct `endpoint_id` and equal `event_id`. **Red-proof, executed separately:** (i) restore the single-column unique index and confirm the two-endpoint test reddens with an integrity error; (ii) drop the uniqueness entirely and confirm a test that calls `enqueue_for_event` twice for the same `(endpoint, event)` reddens by finding two rows instead of one. **Fails loudly:** `enqueue_for_event` must catch only the unique-violation on re-enqueue and treat it as "already queued"; every other integrity error must propagate, so a constraint failure is never mistaken for successful deduplication. **Preserve:** keep an index that enforces at-most-once-per-endpoint — do not fix the fan-out by deleting the uniqueness, which is the only thing preventing duplicate deliveries on a retried dispatch. **Boundary and tie:** the second endpoint added to an org *after* an event was enqueued does not receive that event; say so in `docs/webhooks.md`.

### Critical: any http(s) host is accepted as a delivery target and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py:run_worker` — `follow_redirects=True`
What is wrong: the only validation is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts `http://` in plaintext (contradicting `docs/webhooks.md`, "Only `https://` URLs are accepted"), accepts loopback, link-local, and RFC1918 hosts, and the worker then POSTs to them from inside the production network with redirect-following enabled (RS3 boundary validation).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or an external host that 302s there) and our worker fetches cloud instance credentials and stores the response body in `webhook_deliveries.response_body`, where the same customer reads it back through `GET .../deliveries` — a full SSRF-to-credential-exfiltration chain.
Fix: replace the `urlparse` check with a validator on the pydantic model that is already imported in this file — `url: HttpUrl` on `EndpointIn` plus an `@field_validator` that requires `scheme == "https"`, resolves the host with `socket.getaddrinfo`, and rejects when any resolved address satisfies `ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved`; set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a permanent failure; re-check the resolved address at send time (the DNS answer at registration is not the answer at delivery). **Allow side:** pin that a legitimate public HTTPS endpoint still registers and still receives a POST — `https://hooks.example.com/acme` must return 201 and `send_once` must reach the MockTransport handler, so a validator that denies everything is rejected. **Red-proof, executed separately:** (i) register `http://hooks.example.com/x` and confirm the 422 assertion reddens when the scheme check is removed; (ii) point a hostname at `127.0.0.1` and confirm the private-address assertion reddens when the `ipaddress` check is removed; (iii) have the mock transport return a 302 to an internal host and confirm the "delivery marked failed, no second request issued" assertion reddens when `follow_redirects` is set back to `True`. **Fails loudly:** when DNS resolution fails or times out, registration must return 422 and delivery must mark the attempt failed — an unresolvable host must never be treated as "no private address found, therefore allowed". **Preserve:** customers must still be able to register any genuinely public HTTPS endpoint, including one on a non-standard port; do not fix this with a static host allowlist that breaks that. **Boundary and tie:** name the decision for a host resolving to both a public and a private address (deny — any private answer denies), and for `https://` on port 80 (allowed; the scheme, not the port, is the check).

### Critical: `time.sleep()` inside an async coroutine blocks the entire worker
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: a synchronous `time.sleep` is called inside `async def deliver`, which is run under `asyncio.gather` for up to `BATCH_SIZE` (100) concurrent deliveries — it blocks the event loop rather than yielding it.
What breaks in production: one slow endpoint freezes all 100 concurrent deliveries and the poll loop for up to 30 seconds of backoff (2+4+8+16) plus up to five 30-second request timeouts, so the 60-second Redis lock expires mid-batch, a second worker claims rows the first is still holding, and every customer gets duplicate deliveries while throughput collapses to one endpoint at a time.
Fix: replace the in-process retry loop with scheduled retries the schema already models — on a non-2xx or transport error, write `attempts = attempt`, `status = "pending"`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` and `return`, letting `_claim_batch` pick the row up later; delete `import time` from `delivery.py`. This also stops a worker restart from losing in-flight retries. **Allow side:** pin that a first-try success still completes in one pass — the existing `test_send_once_posts_the_signed_payload` path plus a `deliver` test asserting a 200 leaves `status == "delivered"` and issues exactly one request. **Red-proof, executed separately:** (i) assert `"time" not in sys.modules`-style import check or, better, assert `deliver` returns within a strict `asyncio.wait_for` budget while a handler sleeps — restore `time.sleep` and confirm the budget assertion reddens; (ii) make the handler return 500 and assert the row comes back `pending` with `next_attempt_at` advanced by exactly `backoff_for(1)` — hardcode `backoff_for` to zero and confirm it reddens; (iii) assert exactly one HTTP request per `deliver` call and confirm restoring the `while True` loop reddens it. **Fails loudly:** if `_finish`/the reschedule write fails, the worker must log at error and leave the row claimable rather than returning as if the attempt were recorded. **Preserve:** the retry behaviour itself and the `MAX_ATTEMPTS` cap must survive — do not fix the blocking by deleting retries. **Boundary and tie:** the attempt numbered exactly `MAX_ATTEMPTS` is the last one and transitions to `failed_permanent` (it does not get a sixth); a row whose `next_attempt_at` is exactly `now` is claimable.

### Critical: the dispatch lock is not atomic and can be wedged permanently or released by the wrong worker
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` then `expire` is three round trips, so two workers can both observe an empty key and both proceed; a crash between `set` and `expire` leaves a key with no TTL that nothing ever clears (the crashing process never reaches the `finally`); and the `finally` deletes the key unconditionally, including a lock a *different* worker acquired after the TTL expired (R38: persisted fail-closed wedge with no reset path, plus fail-open supersession).
What breaks in production: either every webhook stops forever because a TTL-less lock key wedges the loop and only a manual Redis `DEL` recovers it, or two workers run the same batch concurrently and every customer receives every event twice — both silent, with only a healthy-looking process to show for it.
Fix: acquire with a single atomic call carrying a fenced token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) passing the same token, so a worker can only delete its own lock; renew the TTL from a background task while the batch runs, or size the lease above the worst-case batch duration and state that number. **Allow side:** pin the successful acquisition — a worker with a free key must acquire, run, and release, so a fix that never acquires is rejected. **Red-proof, executed separately:** (i) with the key already held by another token, assert the second acquire returns `False`, then restore the `get`/`set` form and confirm it reddens; (ii) assert the key has a TTL strictly greater than zero immediately after acquisition, then split `set` from `expire` again and confirm it reddens; (iii) hold the key under token A, call the release path with token B, assert the key survives, then restore the unconditional `delete` and confirm it reddens. **Fails loudly:** if Redis is unreachable, `_acquire_lock` must raise or return `False` and the loop must log at error — an exception swallowed into "lock acquired" is the fail-open case, and "cannot check the lock" must not be spelled the same as "lock is free". **Preserve:** single-worker mutual exclusion must survive; do not fix the wedge by removing the lock or by shortening the TTL below the batch duration. **Boundary and tie:** name what happens when the lease expires while the batch is still running (the fenced token makes the late release a no-op, and the row-level `in_flight` claim plus the `(endpoint_id, event_id)` unique index is what prevents the double send) and when two workers race with identical timing (exactly one `SET NX` wins).

### Major: the dispatcher swallows enqueue failure, so events commit with no webhook rows
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning(...)` around `webhook_delivery.enqueue_for_event`
What is wrong: the event row is committed in its own `session_scope`, then the webhook enqueue runs in a separate transaction whose every failure is downgraded to a warning with no retry, no dead-letter, and no signal to the caller (R9/R4).
What breaks in production: any transient DB error — or the unique-index violation above — silently drops the webhook for that event permanently, while `dispatch` returns a successful `event_id` and the customer sees nothing, contradicting the at-least-once guarantee in `docs/webhooks.md`.
Fix: make enqueue part of the same transaction as the event insert (an outbox: insert the `Event` row and the `WebhookDelivery` rows in one `session_scope`, with the worker as the only sender), so a failure rolls back the event rather than orphaning it; if the enqueue must stay separate, remove the blanket `except Exception` and instead record a durable `webhook_enqueue_failed` row plus an error-level log carrying `event_id`, and increment a counter that alerting can page on. **Allow side:** pin the success path — a dispatch of a webhook-eligible event must return the `event_id` AND leave one delivery row per subscribed endpoint, so a fix that makes every dispatch fail is rejected. **Red-proof, executed separately:** (i) make `enqueue_for_event` raise and assert `dispatch` now propagates (or writes the failure row) rather than returning normally — restore the bare `except` and confirm it reddens; (ii) assert the delivery rows and the event row share a transaction by raising after the event insert and confirming neither exists. **Fails loudly:** an enqueue that cannot run at all (module import failure, DB down) must surface as a 5xx or a paging error, never as a warning line. **Preserve:** non-webhook event types must still dispatch and return their id unaffected. **Boundary and tie:** an event whose type is in `WEBHOOK_EVENT_TYPES` but which matches zero endpoints is a success with zero rows, not a failure.

### Minor: the deliveries listing orders on a non-unique key

What is wrong: `created_at` defaults to a single `_now()` value for every row of one `add_all` batch, so rows enqueued together tie and their relative order is undefined (R57).
What breaks in production: two calls to the same URL return different slices at the limit boundary, and any future cursor built on `created_at` will skip or repeat rows; the keyset fix in the `limit` finding above resolves it by carrying `(created_at, id)`.

### Minor: `WebhookDelivery.to_dict` omits `endpoint_id`
File: `app/webhooks/models.py` — `WebhookDelivery.to_dict`
What is wrong: the serialized delivery does not name the endpoint it belongs to, even though the same model is only ever listed per endpoint today.
What breaks in production: nothing now; a future cross-endpoint listing would return rows a client cannot attribute.
