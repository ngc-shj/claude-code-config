### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built with `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, whose internal state is recoverable from a few hundred observed outputs and which is seeded from process state, so secrets issued near each other are predictable.
What breaks in production: an attacker who obtains one org's secret (or who registers enough endpoints of their own to observe the generator) can reconstruct the generator state and forge `X-Acme-Signature` for every other org, so every customer's signature check accepts attacker-authored events.
Fix: replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX` (`import secrets`, drop `random`/`string`/`_ALPHABET`), and rename `SECRET_BYTES` to mean bytes-of-entropy since `token_urlsafe(32)` returns 43 characters. **Allow side that must still pass**: `test_new_signing_secret_has_prefix_and_length` must be updated to `len(secret) == len(SECRET_PREFIX) + len(secrets.token_urlsafe(SECRET_BYTES))` and stay green, and `sign`/`verify` must still round-trip a secret produced by the new generator (`test_verify_accepts_signature_produced_by_sign` seeded with `new_signing_secret()` instead of the literal `SECRET`). **Red-prove separately, by execution**: (i) monkeypatch `secrets.token_urlsafe` to a constant and assert two successive calls to `new_signing_secret` differ — run it, see it red; (ii) drop the `SECRET_PREFIX` concatenation and see the prefix assertion red; (iii) shorten `SECRET_BYTES` to 4 and see a new `assert len(secret) >= 43` red. Three mutations, three distinct failing assertions. **Fail loudly**: if `secrets` is unavailable or `token_urlsafe` raises, let the exception propagate out of `create_webhook_endpoint` as a 500 — do not fall back to `random`; an endpoint must never be created with a secret whose provenance is unknown. **Preserve**: the `whsec_` prefix (customers key their secret managers on it) and the property that the secret is returned exactly once from the create response. **Boundary and tie**: state the minimum accepted length as a named constant and assert `>=` not `==` so a future encoding change does not silently shorten it; two secrets colliding is a 2^-256 event, but add the `UNIQUE` constraint on `webhook_endpoints.signing_secret` so a collision fails the insert rather than making two orgs interchangeable.

### Critical: `GET /webhook-endpoints/{id}/deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so `endpoint_id` is a bare object reference under the caller's control.
What breaks in production: any authenticated user can walk `endpoint_id` from 1 upward and read every other tenant's delivery log — event ids, event types, delivery status and the response codes their systems returned — a cross-tenant data breach reachable with a single incrementing integer.
Fix: join and filter — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. **Codebase awareness / cross-cutting**: the org-scoping idiom already exists three times in this same file — `get_profile` (`session.get(Organization, user.org_id)`), `list_api_keys` (`.filter(ApiKey.org_id == user.org_id)`) and the sibling added in this very diff, `list_webhook_endpoints` (`.filter(WebhookEndpoint.org_id == user.org_id)`); `list_deliveries` is the one added route that does not propagate it (R3, security-relevant → Critical). I checked the rest of the diff for the same shape: `enqueue_for_event` does scope by `org_id`, and `deliver`/`_claim_batch` are worker paths with no caller identity, so `list_deliveries` is the only missed location. **Allow side that must still pass**: a test where the caller's own org owns `endpoint_id` must still receive its rows — pin it, because a fix that filters on `WebhookDelivery.org_id` (a column that does not exist) or that always 404s satisfies the deny test alone. **Red-prove separately, by execution**: (i) delete the `org_id` predicate and see the cross-tenant test go from 404 to 200 — run it; (ii) delete the `endpoint_id` predicate and see the owning-org test return another endpoint's rows; (iii) change the 404 to a 403 and see the enumeration-disclosure assertion red. **Fail loudly**: when `user.org_id` is `None` or absent, deny with 403 rather than letting `org_id == None` render as `IS NULL` and match rows — "no identity" must not spell the same as "no match". **Preserve**: the `created_at desc` ordering and the `limit` behaviour; do not fix this by removing the route. **Boundary and tie**: an endpoint whose `org_id` equals the caller's is allowed (inclusive), one owned by any other org is denied; a delivery whose endpoint row was deleted has no owner and must be denied, not orphan-visible.

### Critical: the HMAC is computed over bytes that are not the bytes sent on the wire
File: `app/webhooks/delivery.py` — `send_once` / `app/webhooks/signing.py` — `sign`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` while the request body is produced independently by `client.post(..., json=delivery.payload)` using httpx's own encoder (insertion order, its own separators), so the signed string and the transmitted body are two different serializations of the same dict — and `docs/webhooks.md` tells customers to HMAC the **raw request body**.
What breaks in production: every customer who implements the documented verification recomputes a MAC over the bytes they received and gets a mismatch, so every delivery is rejected as a forgery and the entire webhook product silently fails at the receiver (R40 — producer wire shape vs strict consumer, same team owning both sides, hidden by mocks).
Fix: serialize once and send the exact signed bytes — `body = serialize(delivery.payload).encode()`, `ts, signature = sign_body(endpoint.signing_secret, body)`, `await client.post(endpoint.url, content=body, headers={...})` with `Content-Type: application/json` set explicitly; refactor `sign` into `sign_body(secret: str, body: bytes)` so no call site can re-serialize, and have `serialize` pin the encoding (`json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`). **Codebase awareness**: `signing.serialize` already exists and is the shared path — `send_once` reimplements serialization by delegating to httpx's `json=` instead of calling it (R1); the fix is adoption of the existing helper, not a new one. **Allow side that must still pass**: extend `test_send_once_posts_the_signed_payload` to recompute `hmac.new(SECRET.encode(), captured["body"], hashlib.sha256).hexdigest()` and assert it equals the header minus `sha256=` — a legitimate delivery must verify byte-for-byte, and this is the assertion the current test is missing entirely. **Red-prove separately, by execution**: (i) reorder the fixture payload's keys and confirm the recomputed-MAC assertion stays green (proves canonicalization); (ii) change `separators` to the default and confirm a test that pins the exact body bytes goes red; (iii) revert `content=body` to `json=delivery.payload` and confirm the recomputed-MAC assertion goes red — that third mutation is the regression guard for this exact defect. **Fail loudly**: if `serialize` raises on a non-JSON-serializable payload, mark the delivery `failed_permanent` with the `TypeError` text rather than sending an unsigned or partially-signed request. **Preserve**: the `sha256=` header prefix and the JSON content type customers already parse. **Boundary and tie**: state that the signed unit is the byte string actually written to the socket, and that an empty payload signs as `{}` — not as the empty string — so a receiver and sender agree on the degenerate case.

### Critical: the timestamp header is not covered by the signature, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign` MACs the payload alone and returns the timestamp as an unauthenticated side value, so `X-Acme-Timestamp` can be rewritten by anyone without invalidating `X-Acme-Signature`.
What breaks in production: an attacker who captures one delivery can replay it forever by resetting the timestamp header to "now" — the five-minute freshness check the docs tell customers to rely on rejects nothing, and it is the only replay defence in the design.
Fix: bind the timestamp into the MAC — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` in the `sign_body` introduced above, matching `docs/webhooks.md` verbatim, and make `verify` take the timestamp and reject when `abs(now - int(timestamp)) > 300`. **Allow side that must still pass**: a signature produced now must verify now (`test_verify_accepts_signature_produced_by_sign`), and one produced 299 seconds ago must still verify — pin both, because a fix that rejects on any clock difference passes every replay test while breaking every real delivery. **Red-prove separately, by execution**: (i) mutate the verifier to ignore the timestamp argument and see the replay test (same body, timestamp advanced by 600s) go from reject to accept; (ii) mutate `sign_body` back to omitting the `f"{timestamp}."` prefix and see a test asserting that two signatures of the same body at different timestamps differ go red; (iii) mutate the window from 300 to 0 and see the 299-second allow case go red. **Fail loudly**: a missing, empty, or non-integer `X-Acme-Timestamp` must raise/reject explicitly in `verify` — never be coerced to 0 (which is always "too old") nor skipped (which is always "fresh"); "could not parse the timestamp" must not be spelled the same as "no timestamp problem". **Preserve**: the two-header layout and the `sha256=` prefix, and keep `verify` exported — it is the reference implementation customers copy. **Boundary and tie**: skew of exactly 300 seconds is accepted (inclusive) and 301 rejected; state that the comparison is two-sided so a receiver whose clock runs ahead does not reject fresh events.

### Critical: signature comparison in the shipped reference verifier is not constant-time
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` compares an HMAC with Python's short-circuiting `==` (RS1), in the very function `docs/webhooks.md` tells customers to model their own verification on while advising them to "use a constant-time comparison".
What breaks in production: the byte-by-byte early exit leaks the correct digest through response-time differences, letting a remote attacker recover a valid signature for a chosen payload one nibble at a time — and every customer who copies this reference inherits the same oracle.
Fix: `return hmac.compare_digest(expected, signature)`. **Cross-cutting verification**: I searched the whole diff for other credential-shaped comparisons — `deliver`'s `200 <= response.status_code < 300` and `_acquire_lock`'s truthiness check are numeric/presence checks that RS1 explicitly suppresses, and no other `==`/`!=` in the diff has a secret, token, hash, signature or digest on either side, so `verify` is the only site. **Allow side that must still pass**: `test_verify_accepts_signature_produced_by_sign` must stay green — `compare_digest` raises `TypeError` on mixed str/bytes, so a careless fix that encodes one side only turns every legitimate verification into an exception. **Red-prove separately, by execution**: (i) revert to `==` and see a test that asserts `verify` is `hmac.compare_digest`-backed (patch `hmac.compare_digest` with a counting spy and assert it was called once) go red; (ii) pass a signature of the same length but one differing character and see the reject assertion hold; (iii) pass a `bytes` signature and see the explicit type guard's `TypeError`/reject assertion fire rather than a stack trace. **Fail loudly**: when `signature` is `None` or not a `str`, return `False` from an explicit branch that logs the reason — do not let `compare_digest`'s `TypeError` escape into a 500 that reads as an availability bug. **Preserve**: the function's `(secret, payload, signature) -> bool` contract that the tests and docs both use; do not "fix" it by deleting `verify`. **Boundary and tie**: `compare_digest` does not hide length, so document that signatures are always 71 characters (`sha256=` + 64 hex) and reject any other length before comparing, making the length check the only length-dependent step.

### Critical: the migration's status CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `webhook_deliveries.status CHECK`
What is wrong: the constraint allows `('pending', 'in_flight', 'delivered', 'failed')` while `app/webhooks/models.py` declares `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` and `deliver` writes the literal `"failed_permanent"` at `_finish(delivery.id, "failed_permanent", ...)` (R2/R42 — the same enum spelled in two places, derived from a supplied list rather than from one primitive).
What breaks in production: the first delivery to exhaust its five attempts raises a `CheckViolation`, `_finish`'s transaction rolls back, the row stays `in_flight` forever, and the exception propagates out of `deliver` into `asyncio.gather` — killing the batch — so a single dead customer endpoint stops the whole delivery worker.
Fix: make the database the single derivation source and the model import it — change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and add a startup assertion that `set(models.STATUSES)` equals the constraint's member set read back from `pg_get_constraintdef`, failing the boot if they diverge. **Cross-cutting verification**: the same two-places-one-enum shape appears once more in this diff — `WEBHOOK_EVENT_TYPES` in `app/events/dispatcher.py` versus the `event_types` values customers post to `create_webhook_endpoint`, which is unconstrained on both sides (reported separately below). **Allow side that must still pass**: inserting each of the four legitimate statuses must succeed — pin all four, because a fix that drops the CHECK entirely satisfies "failed_permanent inserts cleanly" while removing the constraint's whole value. **Red-prove separately, by execution**: (i) insert `status='failed_permanent'` against the pre-fix schema and observe the `CheckViolation`, then against the post-fix schema and observe success; (ii) insert `status='bogus'` post-fix and observe it still raises — proving the constraint was fixed, not deleted; (iii) mutate `models.STATUSES` to add a fifth member and observe the startup parity assertion fail. **Fail loudly**: if the parity assertion cannot read `pg_get_constraintdef` (permission denied, table absent), abort startup with a named error — "could not check the enum" must not report the same as "enums agree". **Preserve**: the existing four-state machine and the `status` index; do not widen the column to unconstrained TEXT. **Boundary and tie**: state that `failed_permanent` and `delivered` are the only terminal states and that a row may not leave either, so a retry racing a permanent failure cannot resurrect it.

### Critical: `UNIQUE INDEX ... (event_id)` makes one event deliverable to at most one endpoint
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`
What is wrong: the unique index is on `event_id` alone, but `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for the same `event_id`, so any org with two subscribed endpoints violates the constraint on `session.add_all`.
What breaks in production: the insert raises `IntegrityError`, which the dispatcher swallows at `except Exception: log.warning(...)`, so an org with two endpoints receives **nothing at all** — not one delivery, since the whole `add_all` rolls back — and the only trace is a warning line.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is the real idempotency key that `docs/webhooks.md`'s "deduplicate on event_id" advice needs, per endpoint — and make `enqueue_for_event` insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a redelivered event is idempotent rather than fatal. **Allow side that must still pass**: an org with two active endpoints subscribed to the same event must produce exactly two rows — pin that count, because dropping the unique index altogether also makes the insert succeed while losing the idempotency guarantee the docs promise. **Red-prove separately, by execution**: (i) revert to the single-column index and see the two-endpoint test go red with `IntegrityError`; (ii) call `enqueue_for_event` twice with the same `event_id` and assert the row count stays at two — remove `DO NOTHING` and see it go red; (iii) enqueue two different `event_id`s to one endpoint and assert two rows, so the constraint is not over-tight. **Fail loudly**: an `IntegrityError` that is not the expected conflict must propagate, not be folded into `DO NOTHING`; and the dispatcher's swallow (see below) must be narrowed so "enqueue failed" is visible as an error, never as an ordinary log line. **Preserve**: at-least-once semantics and the per-event dedupe key customers are told to use. **Boundary and tie**: name the tie explicitly — two endpoints of the same org for one event are two distinct rows; the same endpoint re-enqueued for one event is one row, and the second attempt is a no-op rather than an update.

### Critical: outbound deliveries have no destination restriction and follow redirects (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint` / `app/webhooks/delivery.py` — `run_worker`
What is wrong: the only URL check is `parsed.scheme.startswith("http") and parsed.netloc` — which accepts plain `http://`, and any scheme literally beginning with those four characters — with no host restriction, while the worker's client is built with `follow_redirects=True`.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/` and the worker POSTs authenticated-looking JSON into the cloud metadata service, internal admin ports or Redis, with the reachable-or-not result observable through the `response_status` returned by the deliveries endpoint; the redirect follow means even an https host that passes registration can bounce the request to a link-local address at delivery time (RS3 — a boundary check that admits an off-policy value, with the sink being an HTTP client rather than a sanitizer).
Fix: validate with an allow-list, not a prefix test — require `parsed.scheme == "https"` (which is what `docs/webhooks.md` already promises: "Only `https://` URLs are accepted"), require a non-empty hostname, reject userinfo (`@`) and non-default ports outside `{443}`, resolve the hostname and reject when any resolved address is private, loopback, link-local, multicast or reserved (`ipaddress.ip_address(a).is_global` is False), and set `follow_redirects=False` on the `AsyncClient` so a 3xx is recorded as a delivery failure rather than followed; re-run the address check at send time inside a custom transport so DNS rebinding between registration and delivery cannot reintroduce it. **Cross-cutting verification**: `create_webhook_endpoint` is the only place in the diff that accepts a URL, and `run_worker`'s client is the only egress client — both need the change, and fixing only the registration check leaves the rebinding and redirect paths open. **Allow side that must still pass**: `https://hooks.example.com/acme` — the exact URL in `docs/webhooks.md` and in `FakeEndpoint` — must still register and still be delivered to; pin it, because an allow-list fix that resolves DNS at registration time will reject every host in a test environment without stubbing. **Red-prove separately, by execution**: (i) register `http://hooks.example.com/` and see the 422 assertion fire, then `https://` and see it pass; (ii) register a hostname stubbed to resolve to `127.0.0.1` and see the private-address rejection fire; (iii) point the mock transport at a handler returning `302` to `http://169.254.169.254/` and assert the delivery is recorded failed and no second request was made. **Fail loudly**: when name resolution fails or times out, reject registration with an explicit 422 naming the resolution failure and mark a send-time resolution failure as a retryable delivery error — "could not check the address" must never fall through to "address is fine". **Preserve**: legitimate customer endpoints on non-standard-but-public hosts (make the port policy configurable rather than hard-denying), and keep `follow_redirects` behaviour documented so customers know a 3xx is not followed. **Boundary and tie**: `is_global` is the boundary — a public IPv4 that CNAMEs to a private one is denied at send time, and a host resolving to both a public and a private address is denied (all resolved addresses must pass, not any).

### Critical: `time.sleep` inside an `async def` blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, retry loop
What is wrong: the retry backoff uses the blocking `time.sleep(delay)` inside a coroutine, so the thread's event loop stops entirely for the duration instead of yielding.
What breaks in production: `run_worker` fans a 100-row batch into `asyncio.gather`, so one failing endpoint freezes all 99 siblings and every other task on that loop — including any HTTP handlers sharing the process — for 2+4+8+16 = 30 seconds of sleep plus up to 5×30 s of request timeout, and because the sleeps are serialized across the gathered coroutines a batch of failures stalls the service for minutes.
Fix: stop retrying in-process and reschedule instead — on a retryable failure, write `status='pending'`, `attempts=attempt`, `next_attempt_at = now + backoff_for(attempt)` via `_finish` and return, letting the next poll pick the row up; if an in-process retry is kept for any reason it must be `await asyncio.sleep(delay)`. **Cross-cutting verification**: `time` is imported in `delivery.py` solely for this call and in `signing.py` for `time.time()` (non-blocking, correct); `run_worker` and `_acquire_lock` already use `await asyncio.sleep`/awaited redis calls, so `deliver` is the only blocking site in the diff. **Allow side that must still pass**: a delivery that succeeds on its first attempt must still complete without any sleep at all and be marked `delivered` — pin the elapsed time of the happy path at under a millisecond, because converting to a reschedule model can accidentally add a poll interval to every success. **Red-prove separately, by execution**: (i) run two `deliver` coroutines under `asyncio.gather` against a handler that fails once then succeeds, and assert wall-clock is ~1 backoff not ~2 — restore `time.sleep` and watch it go red; (ii) assert `next_attempt_at` after a retryable failure equals `now + backoff_for(1)`, and mutate `backoff_for` to a constant to see it red; (iii) assert `attempts` is persisted after each failure by re-reading the row, and remove the `attempts=` write to see it red. **Fail loudly**: if `_finish` cannot persist the reschedule (row missing, DB error) the worker must log at error and re-raise rather than returning as if the retry were scheduled — a lost reschedule is a permanently undelivered event, and it must not read as success. **Preserve**: the documented 5-attempt cap and the growing backoff shape — do not fix the stall by shortening or removing the backoff. **Boundary and tie**: `attempt >= MAX_ATTEMPTS` is the terminal boundary (the 5th attempt is made, the 6th is not); a row whose `next_attempt_at` is exactly `now` is due and must be claimed by the `<=` predicate already in `_claim_batch`.

### Major: the Redis lock is non-atomic in both directions — double-claim and a permanent wedge
File: `app/webhooks/delivery.py` — `_acquire_lock` / `run_worker`
What is wrong: `_acquire_lock` does GET-then-SET (two round trips, so two workers can both observe an empty key and both proceed) and `SET` is followed by a separate `expire`, so a crash or connection drop between the two leaves `LOCK_KEY` with no TTL; nothing else in the diff ever clears it (R38 — a persisted fail-closed state with no reset path).
What breaks in production: the first defect delivers every event twice to every endpoint; the second stops all webhook delivery permanently across every worker and every restart, recoverable only by someone manually deleting a Redis key nobody has documented.
Fix: acquire atomically with a fenced token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a compare-and-delete Lua script that only deletes when the stored value equals `token`, so an expired lock reacquired by a second worker is never deleted by the first; set `LOCK_TTL_SECONDS` above the worst-case batch duration derived from `MAX_ATTEMPTS`, `REQUEST_TIMEOUT` and `backoff_for`, and renew it periodically while the batch runs. **Allow side that must still pass**: a single worker must still acquire, run a batch and release, and must be able to reacquire on the next poll — pin a two-iteration run, because a fix that never releases (or that always fails `nx=True`) makes the deny test pass while stopping delivery entirely. **Red-prove separately, by execution**: (i) run two `_acquire_lock` calls concurrently against a real or fake Redis and assert exactly one returns True — revert to GET-then-SET and see it red; (ii) assert `ttl(LOCK_KEY) > 0` immediately after acquisition and mutate the call to drop `ex=` to see it red; (iii) have worker A acquire, force-expire the key, let worker B acquire, then run A's release and assert B's token survives — remove the compare-and-delete and see it red. **Fail loudly**: if Redis is unreachable, `_acquire_lock` must raise (or return False and log at error) rather than returning True; "cannot tell whether another worker holds the lock" must not be spelled the same as "no other worker holds it". **Preserve**: the single-writer property the lock exists for — do not fix the wedge by removing the lock or by having the release path delete unconditionally. **Boundary and tie**: a lock whose TTL expires exactly as its holder finishes is the tie case — the fenced token is what decides it, and the holder's release must be a no-op in that case rather than deleting the new holder's lock.

### Major: `run_worker` dies on the first `_claim_batch` error and never restarts
File: `app/webhooks/delivery.py` — `run_worker`
What is wrong: `batch` is assigned inside the `try` but read after the `finally` at `if not batch`, so any exception from `_claim_batch` or `asyncio.gather` unwinds through `finally`, releases the lock, and then — on the next iteration path — the loop has already propagated the original exception out of `run_worker` entirely; and if the exception is caught upstream and the loop re-entered, `batch` is unbound, raising `NameError`.
What breaks in production: one transient database error terminates the delivery worker process, and because nothing in the diff supervises or restarts it, deliveries accumulate in `pending` indefinitely with no alert.
Fix: initialise `batch: list[m.WebhookDelivery] = []` before the `try`, wrap the body in `except Exception: log.exception("webhook batch failed"); await asyncio.sleep(poll_interval); continue` so the loop survives, and emit a metric/error log on every caught iteration so the failure is observable. **Allow side that must still pass**: a normal iteration that claims and delivers rows must still exit the sleep-skip branch immediately (a non-empty batch must not sleep) — pin it, because an over-broad `except` that also swallows `CancelledError` makes the worker unkillable; re-raise `asyncio.CancelledError` explicitly. **Red-prove separately, by execution**: (i) patch `_claim_batch` to raise and assert `run_worker` completes two iterations — remove the `except` and see it red with the original exception; (ii) remove the `batch = []` initialisation with the `except` in place and see the `NameError` surface; (iii) cancel the task and assert it actually stops — swallow `CancelledError` and see that assertion red. **Fail loudly**: the caught exception must be logged with `log.exception` (traceback) and counted, not reduced to a warning string — a silently retried loop is indistinguishable from a healthy one. **Preserve**: the poll-interval backoff on an empty batch and the lock release in `finally`. **Boundary and tie**: an empty batch and a failed claim must be distinguishable — sleep in both cases, but count only the second as an error, so a quiet queue is never confused with a broken one.

### Major: deliveries are wedged in `in_flight` with no failure exit and no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` / `deliver`
What is wrong: `_claim_batch` writes `status = "in_flight"` and commits, but the only transitions out are `_finish`'s `delivered`/`failed_permanent` on the success and exhaustion paths — a worker crash, a `CheckViolation`, an OOM kill, or a deploy mid-batch leaves rows in `in_flight` forever, and `attempts` is never persisted between retries so a restart loses the count (R38 non-terminal transient state: an async transition with no failure-exit and no bounded timeout).
What breaks in production: every worker restart permanently strands up to `BATCH_SIZE` deliveries that no query will ever pick up again — they are invisible to the `status == "pending"` claim predicate — so customers silently miss events with no error anywhere.

File: `app/webhooks/delivery.py` — `deliver`, `_finish(..., response.text)` / `app/webhooks/models.py` — `response_body`
What is wrong: the full response body is persisted into an unbounded `TEXT` column on both the success and failure paths.
What breaks in production: an endpoint that returns a large HTML error page writes megabytes per attempt into `webhook_deliveries`, bloating the table and any log line built from `detail`; truncate to a stated limit (e.g. 4 KB) before persisting.

### Minor: the claim query's index does not match its predicate
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_status`
What is wrong: `_claim_batch` filters on `status` **and** `next_attempt_at` and orders by `next_attempt_at`, but the only index is on the low-cardinality `status` alone; `webhook_endpoints` has no index on `org_id` despite both new list routes and `enqueue_for_event` filtering on it.
What breaks in production: the claim degrades to a sort over every pending row as the table grows, so the worker's poll gets slower exactly as the backlog gets larger — replace with `(status, next_attempt_at)` and add `webhook_endpoints (org_id)`.

### Minor: `list_deliveries` orders on a non-unique key
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc())`
What is wrong: `created_at` ties for rows inserted in the same `add_all` — which is the normal case, since `enqueue_for_event` inserts one row per endpoint in a single statement — so the order among tied rows is undefined (R57).
What breaks in production: today it only makes the listing non-deterministic between calls, but the moment a keyset cursor is added on this column it will skip or repeat rows across page boundaries; add `.order_by(created_at.desc(), id.desc())` now and make any future cursor carry both.

### Minor (question): does `session_scope` commit and expire on exit?
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`
What is wrong: the detached-instance finding above rests on `session_scope` committing (and hence expiring) on block exit, which is what its name and the `session.flush()`-then-read-inside-the-block idiom in `create_webhook_endpoint` imply, but `app/db` is not in the diff.
What breaks in production: if `session_scope` uses `expire_on_commit=False` and keeps instances alive, the reads outside the block work and that finding drops to a latent hazard rather than a total failure; the answer that closes it is the `sessionmaker(...)` configuration in `app/db` — the returning of ORM instances across the scope boundary is worth changing either way.
