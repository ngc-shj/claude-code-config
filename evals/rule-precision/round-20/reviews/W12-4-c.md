### Critical: `list_deliveries` has no tenancy predicate — any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never constrains the endpoint to `user.org_id`, while the two sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) both filter on `user.org_id`, so the tenancy predicate was propagated to two of three new/adjacent read paths and dropped on the third.
What breaks in production: Any customer can enumerate integer endpoint ids and read other organizations' delivery rows — which carry `event_type` and, via the `payload` column the same row holds, invoice and subscription data — and `docs/webhooks.md` advertises this endpoint as returning attempts "for an endpoint belonging to your organization", so the disclosure is silent and contradicts the published contract.
Fix: Join `WebhookDelivery` to `WebhookEndpoint` and add `WebhookEndpoint.org_id == user.org_id` to the filter (or resolve the endpoint first and raise 404 when its `org_id` differs), reusing the exact predicate shape `list_webhook_endpoints` already uses in this file rather than writing a third variant. Pair the deny side with the allow side: pin a test where an org-B user requesting an org-A endpoint id gets 404 and zero rows, and pin the case that must still SUCCEED — the owning org still gets its own deliveries, newest first, honouring `limit`. Red-prove each clause separately by execution: (i) delete the `org_id` term and observe the cross-org test go red, (ii) make the handler unconditionally 404 and observe the owner test go red — two mutations, two different assertions. Fail loudly when the check cannot run: an unresolvable `endpoint_id`, or a `user` with no `org_id`, must raise 404 explicitly and must never fall through to the unfiltered query — "endpoint not found" must not be spelled the same as "no filter applied". Do not fix by deleting what made the feature useful: keep the endpoint, the `limit` parameter and the documented ordering. Name the boundary and the tie: `endpoint.org_id == user.org_id` is the allow side; a nonexistent id and an id owned by another org must return a byte-identical 404 body, so the response cannot be used as an existence oracle.

### Critical: the signing secret is returned by the endpoint-list API, contradicting the documented "cannot be read back" control
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (consumed by `list_webhook_endpoints` in `app/api/routes/settings.py`)
What is wrong: `to_dict()` includes `"signing_secret"`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so the secret is readable on every GET — while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: The webhook signature stops being an authenticity control the moment any read-scoped credential (a low-privilege API key, a leaked session, a support tool, an HTTP access log with response bodies) can fetch the secret and forge signed events; the doc's claim is the reason integrators are told to trust the signature, so a control was described as stronger than it is (R49) and no other control was built behind it.
Fix: Remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` construct its 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` so exactly one call site emits it; add a redacted fingerprint (`secret_last4` or an HMAC-of-secret id) to `to_dict()` if the UI needs to distinguish endpoints. Pair deny with allow: assert the GET response body contains no key or value matching `whsec_`, AND assert the case that must still succeed — the POST 201 body still returns the full usable secret, since an endpoint whose secret is never shown once is unusable. Red-prove separately by execution: (i) re-add the field to `to_dict()` and watch the list-redaction test redden, (ii) drop the secret from the create response and watch the create test redden. Fail loudly when the check cannot run: if a rotation or admin path ever needs the plaintext, it must call a named `reveal_signing_secret()` that logs an audit record, rather than any code path silently inheriting `to_dict()`. Do not fix by deleting what made the defect visible: keep `docs/webhooks.md`'s claim and make the code satisfy it — do not weaken the doc to match the code. Name the boundary and the tie: the create response is the single point of disclosure; two endpoints of the same org must be distinguishable in the list response without either secret appearing, which is what the fingerprint field is for.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister general-purpose PRNG, which is not cryptographically secure and whose internal state is recoverable from a modest number of observed outputs.
What breaks in production: An attacker who obtains one or a few secrets (their own endpoint's secret is handed to them at creation — see the disclosure finding above) can recover the generator state and predict the secrets issued to other organizations, forging `X-Acme-Signature` on events those customers then act on, such as marking an invoice paid.
Fix: Replace the body with `secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, delete the `random`/`string`/`_ALPHABET` machinery outright rather than leaving it as an unreferenced fallback) and rename `SECRET_BYTES` so the unit it names is the unit it means. Pair deny with allow: pin that the module no longer references `random` (assert via `inspect.getsource` or a lint rule, not by reading the diff), AND pin the allow case that must still hold — the returned value still starts with `SECRET_PREFIX`, is URL-safe, and round-trips through `sign`/`verify`. Red-prove each clause separately by execution: (i) swap `secrets` back to `random` and watch the CSPRNG assertion redden, (ii) drop `SECRET_PREFIX` and watch the prefix assertion redden, (iii) generate 10_000 secrets and assert zero collisions, then hard-code a constant return and watch that assertion redden — the existing `test_new_signing_secret_has_prefix_and_length` passes for `"whsec_" + "a"*32` and therefore red-proves nothing about entropy. Fail loudly when the check cannot run: if `secrets` is unavailable the module must raise at import, never fall back to `random`. Do not fix by deleting what made the feature useful: the prefix and the fixed-length property that clients may already match on must be preserved. Name the boundary and the tie: state the minimum entropy the secret must carry (≥128 bits) and assert the encoded length that delivers it, so the next change to `SECRET_BYTES` cannot silently cross below it.

### Critical: the signed bytes are not the transmitted bytes, so no customer following the documented scheme can ever verify a signature
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)`, but `send_once` passes `json=delivery.payload` to httpx, which re-serializes the dict with its own `json.dumps` settings (no `sort_keys`, and separator/escaping defaults that differ across httpx versions), so the MAC covers a byte string the receiver never sees.
What breaks in production: Every integrator that implements the documented verification — HMAC over the raw request body — computes a different digest and rejects 100% of our webhooks; this is R40's exact shape (producer and consumer owned by different teams with no round-trip test), and the failure is total and silent on our side because we only observe the customer's non-2xx and retry it five times.
Fix: Serialize once and send the bytes you signed: compute `body = serialize(delivery.payload).encode()`, sign `body`, and pass `content=body` with an explicit `Content-Type: application/json` header to `client.post` — never `json=` alongside a separately-computed MAC. Pair deny with allow: add a round-trip test that feeds the ACTUAL request bytes captured by `httpx.MockTransport` into `signing.verify`, and pin the allow case — a payload whose keys are already sorted, and one whose keys are not (`{"id":…, "type":…, "amount_cents":…}` from the existing `FakeDelivery`, which is unsorted), must BOTH verify. Red-prove each clause separately by execution: (i) revert `content=` to `json=` and watch the round-trip assertion redden on the unsorted payload, (ii) remove `sort_keys=True` from `serialize` and watch the sorted/unsorted equivalence assertion redden, (iii) mutate one byte of the captured body and watch verification redden. Fail loudly when the check cannot run: if the payload is not JSON-serializable, raise before the POST rather than sending an unsigned or mismatched request. Do not fix by deleting what made the defect visible: keep `serialize` as the single canonical encoder — do not "fix" this by loosening the docs to say the digest covers the parsed object, which no HTTP receiver can reconstruct. Name the boundary and the tie: state explicitly that the signed unit is the exact octet sequence of the request body, and that two payloads differing only in key order produce different bodies and therefore different signatures.

### Critical: the timestamp is not covered by the MAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign` (and its `verify` counterpart)
What is wrong: `sign` returns `timestamp` as a separate header value but HMACs only `serialize(payload)`, whereas `docs/webhooks.md` states the signature is "the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`" and that the five-minute timestamp check "is what stops a captured request from being replayed".
What breaks in production: An attacker who captures one delivery can replay it indefinitely by rewriting `X-Acme-Timestamp` to the current second — the signature still validates because the timestamp is outside the MAC — so the anti-replay control the documentation credits does not exist, and a captured `invoice.paid` can be replayed to a customer's endpoint at will.
Fix: Make the signed input `f"{timestamp}.".encode() + body` in `sign`, and change `verify` to take the timestamp explicitly (`verify(secret, timestamp, body, signature)`) so a caller structurally cannot omit it; reject a timestamp outside ±300s inside `verify`. Pair deny with allow: pin that a replayed request with a rewritten timestamp fails verification, AND pin the allow case — a request whose timestamp is 299s old still verifies, so the fix does not simply deny everything. Red-prove each clause separately by execution: (i) drop the `f"{timestamp}."` prefix and watch the replay test redden, (ii) remove the ±300s bound and watch the stale-timestamp test redden, (iii) shift the clock by 301s and confirm the freshness assertion — and only that assertion — reddens. Fail loudly when the check cannot run: a missing or non-numeric `X-Acme-Timestamp` must be a rejection that names itself, never a fall-through to payload-only verification. Do not fix by deleting what made the defect visible: preserve the documented header names and the `sha256=` prefix that integrators already parse; do not fix by removing the replay paragraph from the docs. Name the boundary and the tie: state which side of the window the boundary falls on (a timestamp exactly 300s old is accepted, 301s rejected) and that the comparison uses the receiver's clock, so clock skew is the integrator's stated tolerance rather than an unspecified edge.

### Critical: `verify` compares signatures with `==` instead of a constant-time comparison
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The shipped reference verifier compares an attacker-supplied signature to the expected digest with Python's short-circuiting string equality, which returns after the first differing byte (RS1).
What breaks in production: Any inbound path that calls `verify` — which is what the function exists for, and the only behaviour the docs describe on the receiving side — leaks the expected digest one byte at a time under timing measurement, letting an attacker construct a valid signature without ever knowing the secret; the change simultaneously instructs integrators to "compare it against your own computation using a constant-time comparison", so we ship advice we do not follow.
Fix: `return hmac.compare_digest(expected, signature)`, with `hmac` already imported in this module. Pair deny with allow: pin that a signature differing only in its last hex character is rejected, AND pin that the signature produced by `sign` for the same secret and body is accepted, so the constant-time swap has not turned the verifier into an always-deny. Red-prove each clause separately by execution: (i) revert to `==` and watch a source-level assertion (`compare_digest` appears in `verify`) redden, (ii) invert the return and watch the accept-case test redden, (iii) pass a signature of a different length and confirm rejection rather than an exception. Fail loudly when the check cannot run: a `signature` that is `None` or non-`str` must raise or return `False` explicitly rather than reaching `compare_digest` and raising `TypeError` deep in the caller. Do not fix by deleting what made the defect visible: keep `verify` exported and keep the docs' constant-time instruction — the fix is to make the shipped helper an example worth copying. Name the boundary and the tie: `compare_digest` still leaks length, so document that the comparison is over the fixed 71-character `sha256=<64 hex>` form and reject anything of another length before comparing.

### Critical: `UNIQUE (event_id)` allows only one delivery row per event, so any org with two endpoints receives nothing
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` in `app/webhooks/delivery.py` creates one `WebhookDelivery` per matching endpoint and inserts them with a single `session.add_all(rows)`, but the unique index permits exactly one row per `event_id` across all endpoints.
What breaks in production: For any organization with two or more active matching endpoints the batch insert violates the index, the whole `enqueue_for_event` transaction rolls back, `dispatch` swallows the failure into `log.warning`, and that organization receives zero webhooks for every event — a total, silent feature failure for exactly the customers most likely to notice, with the event row already committed so there is nothing to reconcile against.
Fix: Replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which still gives the per-endpoint idempotency the retry design needs and matches the docs' "deduplicate on `event_id`" advice at the endpoint scope where it is true. Pair deny with allow: pin that enqueuing the same `event_id` twice for the same endpoint is rejected (or upserted, if you choose `ON CONFLICT DO NOTHING`), AND pin the allow case — one event fanning out to three endpoints of the same org creates three rows and all three are claimable. Red-prove each clause separately by execution: (i) restore the single-column unique index and watch the fan-out test redden, (ii) drop the unique index entirely and watch the duplicate-rejection test redden. Fail loudly when the check cannot run: `enqueue_for_event` must not report success by returning `len(rows)` computed before the flush — flush inside the scope and let an integrity error propagate to a named failure, and see the separate finding on `dispatch`'s blanket `except Exception`. Do not fix by deleting what made the defect visible: keep a uniqueness constraint; removing it to make the insert pass would trade a loud failure for duplicate customer-visible deliveries. Name the boundary and the tie: state that an endpoint deleted and recreated gets a new `endpoint_id` and therefore may legitimately receive an already-delivered `event_id` again, which is the tie the two-column key resolves and the one-column key silently forbids.

### Critical: `http://` endpoints are accepted despite the documented HTTPS-only rule
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`
What is wrong: `startswith("http")` admits `http`, `https`, and any scheme with that prefix (`httpx`, `httpfoo`), while `docs/webhooks.md` states "Only `https://` URLs are accepted" — a surface-form prefix test standing in for an exact-membership check.
What breaks in production: Signed invoice and subscription payloads, and the `X-Acme-Signature` header derived from the customer's secret, are transmitted in cleartext to any registered `http://` host where a network observer can read the payload and replay the request verbatim (the signature is replayable — see the timestamp finding), and the httpx client's `follow_redirects=True` means even an `https://` registration can be downgraded to plaintext by the customer's own redirect.
Fix: Reject on exact membership — `if parsed.scheme != "https" or not parsed.netloc: raise HTTPException(422, …)` — and set `follow_redirects=False` on the `httpx.AsyncClient` in `app/webhooks/delivery.py` so an in-flight redirect cannot undo the registration-time decision. Pair deny with allow: pin that `http://…`, `httpfoo://…`, `https:///nohost` and a bare hostname are all 422, AND pin the allow case that must still SUCCEED — `https://hooks.example.com/acme` with a port and a query string is accepted, and a 200 from that host still marks the delivery `delivered`. Red-prove each clause separately by execution: (i) restore `startswith("http")` and watch the `http://` rejection test redden, (ii) restore `follow_redirects=True` and watch a MockTransport test that 301s to `http://` redden, (iii) reject everything and watch the https allow-case redden. Fail loudly when the check cannot run: a URL `urlparse` cannot parse must 422 with a message naming the field, never fall through to the `netloc` check. Do not fix by deleting what made the feature useful: keep accepting non-default ports and paths; the constraint is the scheme, not the shape of the host. Name the boundary and the tie: state that the comparison is on the lowercased scheme (`HTTPS://` normalises to `https` in `urlparse`) and that redirects are not followed at all, so there is no "first hop was https" partial credit.

### Critical: no destination restriction on outbound delivery — the worker is a confused deputy for SSRF
File: `app/webhooks/delivery.py` — `send_once` / `run_worker` (`follow_redirects=True`); `app/api/routes/settings.py` — `create_webhook_endpoint`
What is wrong: The only validation applied to a customer-supplied URL is the scheme/netloc check in `create_webhook_endpoint`; nothing rejects loopback, link-local, or RFC1918 destinations, and `follow_redirects=True` lets a validated public host redirect the request into the internal network at delivery time.
What breaks in production: Any customer can register `https://169.254.169.254/latest/meta-data/…` or an internal service address and have our worker POST to it from inside the perimeter with our egress identity, and the response status and body are then written to `webhook_deliveries.response_body` by `_finish` — turning the SSRF into a readable one, since the delivery row is retrievable through `list_deliveries` (which, per the first finding, is not even org-scoped).
Fix: Resolve the hostname at registration and again immediately before each POST, and reject any resolution that lands in loopback/link-local/private/reserved space using `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`; pin the connection to the resolved address (or use an httpx transport that re-checks on connect) so the DNS answer that was validated is the one used, and set `follow_redirects=False`. Pair deny with allow: pin that `http://127.0.0.1`, `https://169.254.169.254`, `https://10.0.0.5` and a public host that redirects to a private one are all refused, AND pin the allow case — a normal public HTTPS endpoint still receives the POST and still marks `delivered`. Red-prove each clause separately by execution: (i) remove the private-range predicate and watch the metadata-address test redden, (ii) remove the pre-POST re-resolution and watch a DNS-rebinding test (resolver returning public then private) redden, (iii) restore `follow_redirects=True` and watch the redirect test redden. Fail loudly when the check cannot run: a hostname that does not resolve, or a resolver error, must mark the delivery failed with a named reason — never proceed on the assumption that an unresolvable name is harmless. Do not fix by deleting what made the feature useful: customers on non-standard ports and behind CDNs must still work; the constraint is the resolved address, not the hostname's shape. Name the boundary and the tie: state which side CGNAT (`100.64.0.0/10`) and IPv6 ULA (`fc00::/7`) fall on, and that a name resolving to several addresses is refused unless every address passes.

### Critical: `time.sleep` inside the async retry loop blocks the event loop for the whole batch
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async def` and is run through `asyncio.gather` over a batch of up to `BATCH_SIZE = 100`, but the backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, so a single retrying delivery halts the entire event loop.
What breaks in production: One slow or failing customer endpoint stalls every other delivery in the batch and every other coroutine on that loop for up to 2+4+8+16 = 30 seconds, and because the sleeps serialize rather than overlap a batch of 100 failing endpoints wedges the process for tens of minutes — long past the 60-second lock TTL, so a second worker claims the same rows and duplicates the deliveries.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (the module already imports `asyncio`, and the `while True` retry loop should additionally be replaced by rescheduling — see the `next_attempt_at` finding — so the backoff never holds a coroutine at all). Pair deny with allow: pin, with a monotonic-clock assertion, that two concurrently-gathered failing deliveries complete in roughly one backoff period rather than two, AND pin the allow case — a single delivery that succeeds on the first attempt still returns without any added latency. Red-prove each clause separately by execution: (i) restore `time.sleep` and watch the concurrency-timing assertion redden, (ii) set the delay to zero and confirm the timing assertion is measuring the sleep and not the transport. Fail loudly when the check cannot run: the timing test must assert against a clock it controls (`asyncio` event-loop time or a patched sleep spy), not a wall-clock `sleep` tolerance — a test that needs a real sleep to pass is reporting the race rather than pinning it. Do not fix by deleting what made the feature useful: the exponential spacing must be preserved; the fix is where the process waits, not whether it waits. Name the boundary and the tie: state the total wall-clock ceiling a single delivery may occupy (`MAX_ATTEMPTS` attempts × `REQUEST_TIMEOUT` + the backoff sum) and assert the worker respects it, since that ceiling is what must stay under the distributed lock's TTL.

### Critical: the Redis "lock" is not atomic, has a window with no TTL, and is released without ownership
File: `app/webhooks/delivery.py` — `_acquire_lock`, and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` followed by `set` is check-then-act with no atomicity, `set` and `expire` are two round-trips so a crash between them leaves a key with no TTL, and `run_worker` deletes `LOCK_KEY` unconditionally without proving it still owns it.
What breaks in production: Two workers pass the check in the same instant and claim the same rows (`_claim_batch` uses a plain `SELECT … LIMIT` with no `FOR UPDATE SKIP LOCKED`), producing duplicate customer POSTs; and a process killed between `set` and `expire` leaves a TTL-less key that every future worker sees as held, permanently halting all webhook delivery with no reset path (R38 persisted fail-closed wedge) until an operator manually deletes the key — a state nothing in the change can clear.
Fix: Acquire with a single atomic call carrying both the token and the expiry — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker whose lease expired cannot free its successor's lock; add `.with_for_update(skip_locked=True)` to `_claim_batch` so correctness does not rest on the lock alone. Pair deny with allow: pin that a second `_acquire_lock` while the first holds returns `False`, AND pin the two allow cases that must still SUCCEED — the holder's own release actually frees the key, and after `LOCK_TTL_SECONDS` a new worker can acquire (proving the fix did not create a permanent lock). Red-prove each clause separately by execution: (i) revert to `get`-then-`set` and watch a concurrent-acquire test redden, (ii) drop `ex=` and watch a TTL assertion (`ttl(LOCK_KEY) > 0`) redden, (iii) replace the compare-and-delete with a plain `delete` and watch a test where worker A releases after its lease expired and B holds the key redden. Fail loudly when the check cannot run: a Redis error in `_acquire_lock` must return `False` and log a named failure, never `True` — an unreachable coordinator must stop the worker, not un-serialize it. Do not fix by deleting what made the feature useful: the worker must still make progress after a crash, which is what the TTL is for; do not fix the wedge by removing the lock. Name the boundary and the tie: state that `LOCK_TTL_SECONDS` must exceed the worst-case batch wall-clock ceiling named in the `time.sleep` finding, and what happens when a batch runs exactly to the TTL — the compare-and-delete makes that case a no-op release rather than a stolen lock.

### Major: 4xx responses are retried five times, contradicting the documented permanent-failure rule
File: `app/webhooks/delivery.py` — `deliver`, the `if 200 <= response.status_code < 300` branch
What is wrong: Every non-2xx response falls through to the retry path, while `docs/webhooks.md` states "a 4xx is permanent and we stop immediately".
What breaks in production: A customer endpoint that has been decommissioned (410), moved (404), or is rejecting our payload shape (400) receives five POSTs per event with 30 seconds of held backoff each, multiplying load on a customer that has already told us to stop and consuming worker capacity that pending deliveries need.
Fix: Branch explicitly — 2xx marks `delivered`; 408 and 429 are retryable; every other 4xx calls `_finish(delivery.id, "failed_permanent", attempt, status_code, detail)` and returns without a further attempt; 5xx, timeouts and connection errors retry. Pair deny with allow: pin that a 404 produces exactly one HTTP request and a `failed_permanent` row, AND pin the allow cases that must still SUCCEED — a 500 is retried up to `MAX_ATTEMPTS`, and a 429 is retried rather than being swept into the permanent bucket. Red-prove each clause separately by execution: (i) remove the 4xx branch and watch the single-request assertion redden, (ii) add 500 to the permanent set and watch the retry-count assertion redden, (iii) add 429 to the permanent set and watch the 429 case redden — three mutations, three assertions. Fail loudly when the check cannot run: a response with no status (a transport-level failure) must take the retry path explicitly rather than falling into the permanent branch by default. Do not fix by deleting what made the defect visible: keep the docs' statement and make the code match; a "retry everything" simplification would discard the customer signal the status code carries. Name the boundary and the tie: state which side 408 and 429 fall on and that 3xx is unreachable once `follow_redirects=False` (see the SSRF finding), so it must be classified explicitly rather than left to the `else`.

### Major: the documented jitter does not exist, and the test pins its absence

Pair deny with allow: pin that with 150 rows sharing one `next_attempt_at`, two successive claims cover all 150 with no row claimed twice and none omitted, AND pin the allow case — a row whose `next_attempt_at` is in the future is still not claimed, so the ordering change did not widen the selection predicate. Red-prove each clause separately by execution: (i) remove the `id` tie-break and watch the coverage assertion redden under a database that returns tied rows in a stable order, (ii) drop the `status == "pending"` filter and watch the future-row assertion redden. Fail loudly when the check cannot run: if `_claim_batch` returns a full `BATCH_SIZE`, log that the queue is saturated so a persistent backlog is visible rather than being inferred from silence. Do not fix by deleting what made the feature useful: keep `next_attempt_at` as the primary sort — scheduling order is the point; `id` is only the tie-break. Name the boundary and the tie: state that `next_attempt_at <= now` is inclusive and that among rows sharing an instant the lower `id` is claimed first — that is the tie this fix names.

### Minor: `event_types` is accepted without validation against the emitted event set
File: `app/api/routes/settings.py` — `EndpointIn.event_types: list[str] = []`
What is wrong: Any list of arbitrary strings is stored into the `JSONB` column and used by `enqueue_for_event`'s `event_type in endpoint.event_types` membership test, with no check against known types and no length cap.
What breaks in production: A customer who typos `invoice.payed` gets an endpoint that is silently subscribed to nothing forever, with no error at registration and nothing in the delivery list to show why.
Fix: Validate the list against the deliverable event-type set derived in the dispatcher finding (a pydantic `field_validator` rejecting unknown members with 422, plus a `max_length` on the list), and pin both sides: `["invoice.paid"]` is accepted and creates a working subscription, `["invoice.payed"]` is 422 naming the unknown value. Red-prove by removing the validator (the 422 assertion reddens) and by rejecting the valid list (the acceptance assertion reddens); an unenumerable event-type set must fail the validator's construction rather than accept everything.

### Minor: `list_deliveries` orders on `created_at` with no tie-break
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc()).limit(limit)`
What is wrong: `created_at` is a wall-clock value with no uniqueness constraint, and the deliveries created for one event by `enqueue_for_event` share an instant, so which of the tied rows appear within `limit` is undefined.
What breaks in production: A customer inspecting deliveries around a burst sees a different, arbitrary subset on each refresh, which makes the endpoint unusable for the reconciliation it is documented for; add `.desc()` on `id` as the tie-break alongside `created_at`.

### Minor: `SECRET_BYTES` names a unit it does not represent
File: `app/webhooks/signing.py` — `SECRET_BYTES = 32`
What is wrong: The constant is used as a count of characters drawn from a 62-symbol alphabet, not a byte count, so the name overstates the entropy to every reader who assumes 32 bytes of randomness.
What breaks in production: A future change that trusts the name — reducing the value, or reusing the constant for a key length — will silently weaken the secret; rename it to `SECRET_LENGTH` (or switch to `token_urlsafe(32)`, per the CSPRNG fix, where 32 genuinely is bytes) and state the entropy in a comment.

### Minor: the migration creates no index for either of the two hot query paths on `webhook_deliveries`
