### Critical: the signing secret is returned by every endpoint read, contradicting the documented "shown once" contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`), reached from `app/api/routes/settings.py` — `create_webhook_endpoint` and `list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally serializes `signing_secret`, so `GET /v1/settings/webhook-endpoints` hands the HMAC key back on every call, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (R49: claim stronger than the implementation).
What breaks in production: any principal who can read the settings API — a scoped-down read-only key, a leaked session, a logged response body, a browser cache — obtains the key that authenticates every outbound webhook, and can forge events into the customer's endpoint indistinguishably from us.
Fix: give `WebhookEndpoint` two serializers — `to_dict()` which omits `signing_secret` entirely, and `to_dict_with_secret()` used only by `create_webhook_endpoint`'s 201 response — and switch `list_webhook_endpoints` to `to_dict()`. Preserve the behaviour that makes the feature usable: the create response MUST still carry the secret (clause 4 — do not fix by removing the only place the customer can obtain it), and add a rotation route later rather than making the secret unobtainable now. Pin both directions (clause 1): `test_create_returns_signing_secret` asserts `"signing_secret" in body` on the 201, and `test_list_never_returns_signing_secret` asserts `"signing_secret" not in e` for every element of the list response. Red-prove each separately by execution (clause 2): mutation A — drop `signing_secret` from the create serializer, run the suite, observe `test_create_returns_signing_secret` red and the list test green; mutation B — point `list_webhook_endpoints` back at `to_dict_with_secret()`, observe only `test_list_never_returns_signing_secret` red. Fail loudly when the check cannot run (clause 3): the list test must assert the response body is a non-empty list first and fail with `"no endpoint rows returned — secret-absence not exercised"`, so a fixture that creates zero endpoints cannot report green by examining nothing. Boundary and tie (clause 5): the boundary is the single create response — for an endpoint created and then immediately listed in the same request cycle the secret is present exactly once (create) and absent thereafter; two endpoints created in the same transaction each carry their own secret in their own 201 and neither appears in any subsequent read.

### Critical: `verify` compares signatures with `==`, and it is the reference implementation we ship
File: `app/webhooks/signing.py` — `verify` (`return expected == signature`)
What is wrong: the signature comparison uses Python's short-circuiting `str.__eq__` instead of `hmac.compare_digest`, which is RS1's exact shape, and the same file's docstring plus `docs/webhooks.md` tell integrators to "compare it against your own computation using a constant-time comparison" — advice this code does not follow.
What breaks in production: an attacker with repeated inbound calls to any surface that reaches `verify` recovers the correct digest byte-by-byte from response-time differences, and every customer who copies our published helper inherits the same oracle on their receiver.
Fix: `import hmac` is already present — change the return to `hmac.compare_digest(expected, signature)`, and change `verify`'s signature to `verify(secret, payload, timestamp, signature)` so it recomputes with the caller's timestamp rather than a fresh one (see the serialization finding below; today `verify` calls `sign`, which mints a new timestamp and discards it). Preserve what made the defect visible (clause 4): keep `verify` exported and keep the existing negative test — do not delete the helper in favour of "callers should compare themselves". Pin both directions (clause 1): `test_verify_accepts_signature_produced_by_sign` must still pass (the valid signature still verifies), alongside `test_verify_rejects_a_signature_made_with_another_secret`. Red-prove each clause separately by execution (clause 2): mutation A — make `sign` return a constant digest, run the suite, observe the reject test red; mutation B — revert `compare_digest` to `==` under a grep-based unit check `test_verify_uses_constant_time_compare` that asserts `"compare_digest" in inspect.getsource(signing.verify)`, and observe that one test red and no other. Fail loudly (clause 3): `verify` must raise `TypeError` when `signature` is not a `str` rather than returning `False`, so a caller passing bytes or `None` gets a named failure instead of a silent deny that reads like a rejected attacker. Boundary and tie (clause 5): equal-length-but-different digests and different-length digests both return `False` from `compare_digest` in the same time class; the tie case — two secrets producing the same digest for the same payload — is a SHA-256 collision and out of scope, state that in the docstring.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret` (`random.choice(_ALPHABET)`)
What is wrong: `random` is the Mersenne Twister, a non-cryptographic PRNG whose internal state is recoverable from 624 observed 32-bit outputs, so consecutive secrets are predictable from each other — and `SECRET_BYTES = 32` is a misnomer, the function emits 32 alphanumeric *characters*.
What breaks in production: an attacker who registers a handful of endpoints in the same process observes enough generator output to predict other tenants' signing secrets and forge signed events to their endpoints, which is total compromise of the only authentication webhooks have.
Fix: replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX`, delete the `random`, `string` imports and `_ALPHABET` outright (R1 clause d — no wrapper left holding the old logic), and rename the constant to `SECRET_ENTROPY_BYTES = 32` so the unit matches. Preserve the property the existing test pins (clause 4): keep the prefix assertion; do not delete `test_new_signing_secret_has_prefix_and_length` — amend its length assertion to `len(secret) > len(SECRET_PREFIX) + 32` since `token_urlsafe` output length is base64-derived, not fixed. Pin both directions (clause 1): `test_new_signing_secret_has_prefix` still passes (valid secrets still generate and still verify end-to-end through `sign`/`verify`), and add `test_secrets_are_unique_across_calls` asserting `len({new_signing_secret() for _ in range(1000)}) == 1000`. Red-prove each separately by execution (clause 2): mutation A — return a constant string, observe the uniqueness test red and the prefix test green; mutation B — drop `SECRET_PREFIX`, observe the prefix test red and uniqueness green. Fail loudly (clause 3): add a module-import-time assertion that `SECRET_ENTROPY_BYTES >= 32` raising `RuntimeError` at import, so a future config lowering the entropy fails the process boot with a named error rather than silently issuing weak keys. Boundary and tie (clause 5): the boundary is the entropy floor — exactly 32 bytes passes, 31 raises; two simultaneous calls returning the same value is the tie case, and the uniqueness test's 1000-draw sample is the assertion that it cannot happen.

### Critical: the signature is computed over a different byte string than the one we send, and than the one the docs tell customers to verify
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign` / `serialize`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted) while `client.post(..., json=delivery.payload)` serializes the body itself with httpx's own compact, unsorted encoding, and the docs specify the MAC input as `"{timestamp}.{raw_request_body}"` — three mutually incompatible byte strings, with the timestamp not covered by the MAC at all (R40: producer wire shape vs strict consumer).
What breaks in production: every customer who implements verification exactly as documented rejects 100% of our deliveries, we retry each five times against a receiver that will never accept it, and because the timestamp is outside the MAC the five-minute replay window the docs describe is unenforceable — an attacker replays a captured request with a fresh timestamp and the signature still checks out.
Fix: serialize once and send the bytes we signed — in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, call `sign(endpoint.signing_secret, body)` where `sign` now takes the raw bytes and MACs `f"{timestamp}.".encode() + body`, and post with `content=body` instead of `json=` so httpx never re-encodes; update `verify` to take `(secret, timestamp, raw_body, signature)` and recompute the identical string. Do not fix by relaxing the docs to match the code (clause 4): the timestamp must remain inside the MAC, because that binding is what makes the documented replay window enforceable rather than decorative. Pin both directions (clause 1): `test_delivered_body_verifies_under_the_documented_recipe` captures `request.content` from the `MockTransport` handler, recomputes `hmac.new(SECRET, f"{ts}.".encode() + captured_body, sha256)` in the *test* using the documented recipe written independently of `signing.py`, and asserts it equals the sent header — the allow side; `test_tampered_body_fails_verification` flips one byte of the captured body and asserts verification fails — the deny side. Red-prove each separately by execution (clause 2): mutation A — restore `json=delivery.payload` alongside the signed `content`, observe only the allow-side round-trip test red; mutation B — drop the `f"{timestamp}."` prefix from the MAC input, observe a dedicated `test_signature_covers_the_timestamp` (which re-signs the same body under a different timestamp and asserts the digests differ) red and the body test green; mutation C — return the payload unchanged from `serialize`, observe the tamper test red. Fail loudly (clause 3): `send_once` must raise a named `WebhookSerializationError` when `serialize` raises `TypeError` on a non-JSON-serializable payload, rather than posting an unsigned or partially encoded body — an unserializable payload must abort the delivery with a message naming the field, not degrade to a request that no one can verify. Boundary and tie (clause 5): the boundary is the timestamp freshness window the receiver applies — a request whose timestamp is exactly 300 seconds old is accepted, 301 rejected, and state that inclusively in the docs; the tie case is two deliveries of the same payload signed in the same second, which produce identical signatures by design and are disambiguated by `event_id`, which is why the docs' deduplicate-on-`event_id` instruction must stay.

### Critical: `UNIQUE (event_id)` on `webhook_deliveries` makes multi-endpoint orgs silently lose every webhook
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`, against `app/webhooks/delivery.py` — `enqueue_for_event` (`session.add_all(rows)`)
What is wrong: `enqueue_for_event` builds one delivery row per matching endpoint for a single `event_id`, but the unique index permits only one row per `event_id` across the whole table, so the second row of any multi-endpoint fan-out raises a unique violation that aborts the entire `add_all` transaction.

Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the idempotency key the code actually needs (one attempt record per endpoint per event), and add `ON CONFLICT (endpoint_id, event_id) DO NOTHING` semantics to the insert so a redelivered event is a no-op rather than an error. Preserve the property the unique index existed to give (clause 4): the deduplication guarantee stays — the fix widens the key, it does not drop uniqueness, and `docs/webhooks.md`'s "deduplicate on `event_id`" line must be corrected to `(endpoint_id, event_id)` in the same commit. Pin both directions (clause 1): `test_fanout_creates_one_row_per_active_endpoint` asserts `enqueue_for_event` returns 3 and persists 3 rows for an org with three active endpoints — the allow side that the current schema breaks; `test_redelivering_the_same_event_to_the_same_endpoint_is_a_no_op` asserts the second call adds zero rows. Red-prove each separately by execution (clause 2): mutation A — revert the index to `(event_id)`, run against a real Postgres (not SQLite, which does not enforce it identically), observe the fan-out test red with a unique-violation in the failure output; mutation B — drop the unique index entirely, observe only the dedup test red. Fail loudly (clause 3): remove the bare `except Exception` swallow in `dispatch` (see the separate finding) so an insert that cannot run surfaces — the migration test must also fail with a named error, not skip, when the test database is SQLite and cannot enforce the constraint, so "constraint not exercised" is never spelled the same as "constraint holds". Boundary and tie (clause 5): the boundary is one row per `(endpoint_id, event_id)` pair — the same event to two endpoints is two rows, the same event twice to one endpoint is one; the tie case is two workers enqueuing concurrently, resolved by the database's uniqueness rather than an application read-then-write.

### Critical: user-supplied webhook URLs are fetched with redirects followed and no egress restriction (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(timeout=REQUEST_TIMEOUT, follow_redirects=True)`

Pin both directions (clause 1): `test_public_https_endpoint_is_accepted` asserts a 201 for `https://hooks.example.com/acme`; `test_link_local_is_rejected` asserts 422 for `http://169.254.169.254/`, `test_loopback_is_rejected` for `https://127.0.0.1/`, and `test_redirect_to_internal_is_not_followed` asserts the `MockTransport` sees exactly one request when the handler returns a 302 to `http://127.0.0.1/`. Red-prove each separately by execution (clause 2): mutation A — restore `startswith("http")`, observe only the scheme test red; mutation B — remove the private-address check, observe only the loopback and link-local tests red; mutation C — restore `follow_redirects=True`, observe only the redirect test red. Fail loudly (clause 3): when `getaddrinfo` raises or returns no addresses, reject the registration with 422 and a message naming the resolution failure — an unresolvable host must not fall through to "no private address found, therefore safe". Boundary and tie (clause 5): the boundary is the address classification — `10.0.0.0/8`, `127.0.0.0/8`, `169.254.0.0/16`, `::1` and IPv4-mapped IPv6 forms of each are rejected, the first address outside them is accepted; the tie case is a host resolving to both a public and a private address, which must be rejected, not accepted on the public one.

### Critical: `time.sleep` inside an `async def` blocks the event loop for the whole retry backoff

Fail loudly (clause 3): if the patched clock is not installed (the test's own precondition), the test must assert `sleep_calls` is non-empty and fail with `"no sleep observed — retry path not exercised"` rather than passing on a delivery that succeeded first try. Boundary and tie (clause 5): the boundary is `attempt >= MAX_ATTEMPTS`, evaluated before the sleep, so attempt 5 finishes without a trailing wait and attempt 4 sleeps 16 seconds; the tie is two deliveries whose backoffs expire in the same loop iteration, which is fine once they are awaitable and is the case the interleaving test pins.

### Major: the redis lock is non-atomic, and a crash between `set` and `expire` stops all delivery permanently
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker` (`await redis_client.delete(LOCK_KEY)`)
What is wrong: `get` then `set` is a check-then-act race two workers pass simultaneously, `expire` is a second round-trip so a crash in between leaves `LOCK_KEY` with no TTL, and the unconditional `delete` in `finally` removes whichever worker's lock is currently held once the 60-second TTL has already expired and another worker has taken it (R38: persisted fail-closed wedge with no reset path, plus fail-open supersession).
What breaks in production: the wedge is total and silent — a single crashed worker leaves an immortal lock and every webhook in the system stops being delivered with no alert, and the race in the other direction produces duplicate deliveries to customer endpoints.
Fix: acquire with a single atomic call carrying a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script that deletes only if the stored value equals this worker's token; set `LOCK_TTL_SECONDS` above the worst-case batch duration and refresh it from a background task while the batch runs. Preserve mutual exclusion (clause 4): the fix must not become "drop the lock and rely on the database" — keep the lock, and add `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch` as defence in depth, not as a replacement. Pin both directions (clause 1): `test_second_worker_is_refused_while_lock_held` asserts the second `_acquire_lock()` returns `False`; `test_lock_is_acquirable_after_ttl_expiry` asserts a worker *can* acquire once the key expires — the allow side that a fix which never releases would fail; `test_release_does_not_delete_another_owners_lock` asserts the key survives when a stale worker releases. Red-prove each separately by execution (clause 2): mutation A — drop `nx=True`, observe only the refusal test red; mutation B — drop `ex=`, observe only the TTL-expiry test red (with a fake clock, bounded, so it fails rather than hangs); mutation C — revert to unconditional `delete`, observe only the foreign-release test red. Fail loudly (clause 3): when the redis call raises, `_acquire_lock` must propagate a named `LockUnavailableError` and the worker must refuse to process the batch — an unreachable redis must not be read as "no lock present, proceed", which is exactly how the current `if await redis_client.get(...)` would behave if `get` returned `None` on a degraded client. Boundary and tie (clause 5): the boundary is the TTL instant — a worker whose lock expires at exactly T must not release a lock acquired at T; the compare-and-delete token is what decides the tie, and the batch must abort rather than continue when its own refresh fails.

### Minor: `_finish` dereferences a row it never checks for existence
File: `app/webhooks/delivery.py` — `_finish` (`row = session.get(m.WebhookDelivery, delivery_id)` then `row.status = status`)
What is wrong: `session.get` returns `None` when the row is absent — after a cascade delete of its endpoint, for instance — and the next line assigns to it unconditionally.
What breaks in production: deleting a webhook endpoint while a delivery is in flight raises `AttributeError: 'NoneType'` inside the worker, which per the finding above kills the entire loop.

### Minor: the full response body of an untrusted remote host is stored unbounded
File: `app/webhooks/delivery.py` — `deliver` (`_finish(delivery.id, "delivered", attempt, response.status_code, response.text)`), `app/webhooks/models.py` — `response_body = Column(Text)`
What is wrong: `response.text` is read in full and written to an unbounded `TEXT` column for every attempt, with no size cap on either the read or the write.
What breaks in production: a customer endpoint that returns a multi-megabyte body on every 2xx fills the deliveries table and the worker's memory at one copy per delivery, and stores attacker-controlled content that is later returned through the API.

### Minor: the deliveries index does not match the query that reads them
File: `migrations/0042_webhook_delivery.sql` — `CREATE INDEX idx_webhook_deliveries_status ON webhook_deliveries (status)`, against `app/webhooks/delivery.py` — `_claim_batch`
What is wrong: the claim filters on `status` AND `next_attempt_at` and orders by `next_attempt_at`, but the only index is on `status` alone, whose low cardinality makes it nearly useless as a filter.
What breaks in production: once the table accumulates delivered rows, the worker's poll degrades to a sort over a large heap scan every second, and the composite `(status, next_attempt_at)` index the query wants is absent.

### Minor: nothing deactivates or deletes an endpoint, though the model and docs both imply it
File: `app/api/routes/settings.py` — new routes; `app/webhooks/models.py` — `WebhookEndpoint.active`; `docs/webhooks.md`
What is wrong: `active` is exposed in `to_dict()` and filtered on in `enqueue_for_event`, but no route sets it and none deletes an endpoint, so the flag can only ever be `True`.
What breaks in production: a customer whose signing secret leaks — which, per the first finding, is every customer — has no way to stop deliveries or rotate the key without an operator running SQL by hand.

### Minor (question, per the Finding Floor): does `session_scope` commit, and does `create_webhook_endpoint` return before it does?
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`session.flush()` then `return endpoint.to_dict()` inside the `with`)
What is wrong: the handler returns the serialized endpoint after `flush()` but before the context manager exits, so whether the 201 response can be sent for a transaction that subsequently fails to commit depends on `session_scope`, which this change does not contain.
What breaks in production: if `session_scope` can roll back after `flush()`, a customer receives a 201 with a signing secret for an endpoint that does not exist, and stores a key that will never authenticate anything. What would close this: `session_scope`'s definition showing that an exception at commit propagates before the response is serialized — if it does, this is not a defect.
