### Critical: the HMAC is computed over bytes that are never transmitted, and omits the timestamp the docs say it covers
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, with `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys re-sorted) while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and insertion order — so the signed string and the request body are different byte strings — and the MAC input contains no timestamp although `docs/webhooks.md` tells every integrator to verify `HMAC("{timestamp}.{raw_request_body}")`.
What breaks in production: every correctly-implemented consumer that follows the published doc computes a different digest and rejects 100% of deliveries as forged, and because the timestamp is outside the MAC an intercepted request stays valid forever, defeating the five-minute replay window the doc instructs customers to rely on.
Fix: serialize exactly once and sign exactly what is sent — change `sign()` to take the already-encoded body (`def sign(secret: str, body: bytes) -> tuple[str, str]`), build `signed = f"{timestamp}.".encode() + body`, MAC that, and have `send_once` do `body = serialize(delivery.payload).encode()` then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})`; update `verify()` to the same signature (`verify(secret, body: bytes, timestamp: str, signature: str)`) and correct `docs/webhooks.md` only if the doc's stated construction is changed, not to paper over the code. Allow side to pin: a receiver-side test that takes the exact `captured["body"]` bytes and the `X-Acme-Timestamp` header from a `MockTransport` handler, recomputes `hmac.new(SECRET.encode(), b"%s." % ts + body, sha256).hexdigest()`, and asserts equality with the transmitted `X-Acme-Signature` — this must stay green. Red-prove each clause separately: (i) revert `content=body` to `json=delivery.payload` and add one key to the payload so the separator/order difference bites — the round-trip assertion must red; (ii) drop the `f"{timestamp}."` prefix — the round-trip assertion must red naming the digest mismatch; (iii) change the timestamp by one second between signing and asserting — must red. Fail loudly when the check cannot run: if `serialize()` raises `TypeError` on a non-JSON-serializable payload, let it propagate out of `deliver` into `_finish(..., "failed_permanent", ...)` with the exception text, never a silent skip — "could not sign" must not be spelled the same as "signed". Preserve: `sort_keys=True` determinism (so a re-signed identical payload is byte-identical) and the existing `sha256=` header prefix, which integrators already parse. Boundary and tie: state that the receiver's freshness window is `now - ts <= 300` inclusive at exactly 300 seconds, and that two deliveries signed within the same clock second produce identical timestamps — dedup is on `event_id`, never on the timestamp.

### Critical: `verify()` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: the signature comparison uses Python's short-circuiting `str.__eq__` instead of a constant-time comparison, and `hmac.compare_digest` is already available in the module (`hmac` is imported one line above the reimplementation).
What breaks in production: `verify()` is the function this repo publishes as the reference verifier and will be reused for any inbound-signature path, where byte-at-a-time timing leakage lets an attacker recover a valid digest one nibble at a time and forge requests.
Fix: `return hmac.compare_digest(expected, signature)`, after normalising both to `str`. Allow side to pin: `test_verify_accepts_signature_produced_by_sign` must still pass — a fix that always returns `False` satisfies "no timing leak" and must be excluded. Red-prove separately: (i) mutate back to `==` and assert a static check (`rg 'expected == signature'` in a lint test, or `check-timing-safe.sh`) reds; (ii) mutate the returned value to constant `False` and watch the accept-side test red; (iii) mutate to constant `True` and watch `test_verify_rejects_a_signature_made_with_another_secret` red. Fail loudly: when `signature` is `None` or not a `str`, raise `TypeError` rather than returning `False`, so a caller passing a missing header sees a crash instead of a silent deny that reads as a legitimate rejection. Preserve: the boolean return contract and the `sha256=`-prefixed comparand, so existing callers do not need to strip the prefix. Boundary and tie: `compare_digest` on unequal-length inputs still returns `False` — assert the truncated-signature case explicitly so the length short-circuit is not mistaken for the equality check.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, whose internal state is fully recoverable from 624 consecutive outputs — a hand-rolled reimplementation of `secrets`, which the standard library already provides for exactly this (R1: a shared utility for a security control was reimplemented, and the reimplementation lacks the property the call site needs).
What breaks in production: an attacker who registers a few of their own endpoints observes enough generator output to predict every other tenant's signing secret and forge webhooks that those tenants' systems accept as authentic billing events.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` with `import secrets`, deleting the `random`/`string`/`_ALPHABET` scaffolding; rename `SECRET_BYTES` to match its new meaning (it now genuinely is a byte count, whereas today it counts characters). Allow side to pin: `test_new_signing_secret_has_prefix_and_length` must still pass after being updated to the new length — assert `secret.startswith(SECRET_PREFIX)` and that two consecutive calls differ, so a fix that returns a constant is excluded. Red-prove separately: (i) revert to `random.choice` and assert a static check for `import random` in `app/webhooks/**` reds; (ii) make the function return a fixed literal — the "two calls differ" assertion reds; (iii) drop the prefix — the prefix assertion reds. Fail loudly: if `secrets` cannot produce entropy the underlying `os.urandom` raises, and that must propagate out of `create_webhook_endpoint` as a 500, never be caught and replaced with a fallback generator. Preserve: the `whsec_` prefix that customers' secret managers and any prefix-based scanning already key on. Boundary and tie: `token_urlsafe(32)` yields 43 characters, so update the length assertion to the exact value and state that two secrets colliding is a ~2^-256 event, not something the uniqueness constraint must handle.

### Critical: the deliveries endpoint has no tenancy filter — any authenticated user reads any organization's deliveries
File: `app/api/routes/settings.py` — `list_deliveries()`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query filters on the caller-supplied `endpoint_id` only, with no join back to `WebhookEndpoint.org_id == user.org_id`, even though both sibling routes added in the same file and the same diff (`list_webhook_endpoints`, and `enqueue_for_event` in `delivery.py`) do filter by `org_id` — the tenancy pattern was propagated to two of three new query sites (R3, security-relevant).
What breaks in production: any customer can enumerate integer `endpoint_id` values and read another tenant's delivery history — event ids, event types, delivery status and response codes — a cross-tenant data breach reachable with a single authenticated GET.
Fix: join the parent and scope it — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and raise `HTTPException(404)` (not 403) when the endpoint does not exist or belongs to another org, so the response does not disclose existence. Allow side to pin: a test where the endpoint's owner lists its deliveries and receives all of them — a fix that returns `[]` unconditionally satisfies the deny side and must be excluded. Red-prove separately: (i) delete the `org_id` predicate — the cross-tenant test must red on the leaked rows, not merely on a status code; (ii) delete the `WebhookEndpoint.id == endpoint_id` predicate — the owner-side test reds because deliveries of the owner's *other* endpoint appear; (iii) change 404 to 403 — an assertion on the status reds. Fail loudly: when `user.org_id` is `None` the handler must raise rather than fall through to an unfiltered query, so "no tenant resolved" cannot be spelled the same as "no restriction". Preserve: the existing `order_by(created_at.desc()).limit(limit)` result shape, so the endpoint keeps returning most-recent-first. Boundary and tie: an endpoint that exists but has zero deliveries returns `200 []`, while an endpoint owned by another org returns `404` — these two cases must not be conflated, and the test must assert both.

### Critical: the signing secret is returned on every list call, contradicting the published contract that it can never be read back
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()` (`"signing_secret": self.signing_secret`), consumed by `list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally includes `signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` hands out every endpoint's secret — while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim materially stronger than the implementation, about a control other parties are told to depend on).
What breaks in production: the secret is exposed on a read-only, cacheable, widely-logged GET, so any read-scoped API key, browser cache, or proxy log yields the key that authenticates every webhook this tenant receives — and the doc's promise means integrators will not have treated the list response as secret material.
Fix: make secret exposure opt-in at the single site that legitimately needs it — `def to_dict(self, *, include_secret: bool = False)` returning the secret only when `include_secret=True`, called as `endpoint.to_dict(include_secret=True)` from `create_webhook_endpoint` and unchanged (secret-free) from `list_webhook_endpoints`. Allow side to pin: the create-route test must still find `signing_secret` in the 201 body — a fix that strips the secret everywhere breaks the documented one-time reveal and must be excluded. Red-prove separately: (i) flip the default to `True` — the list-route test asserting `"signing_secret" not in body[0]` reds; (ii) drop `include_secret=True` at the create site — the 201-body test reds; (iii) add the key back under an alias such as `"secret"` — a test asserting the exact key set of the list response reds. Fail loudly: any endpoint row whose `signing_secret` is `None` (a partially-migrated row) must raise at create time rather than return `"signing_secret": null`, which a client would store as a valid empty key. Preserve: the rest of the dict — `id`, `url`, `event_types`, `active` — which the docs' registration example shows. Boundary and tie: state that the secret is present in exactly one response (the 201) and in no other, and that a re-`POST` of the same URL mints a *new* endpoint with a *new* secret rather than returning the existing one.

Fail loudly: if the test cannot locate or parse the migration file it must fail, not skip — a missing file must not be reported as a passing comparison. Preserve: the four legitimate states and the terminal meaning of `delivered` / `failed_permanent`. Boundary and tie: name explicitly that `in_flight` is non-terminal and needs the reaper described in the `in_flight` finding below; the CHECK fix alone does not unwedge rows already stranded by this bug, so the migration must also carry a one-time `UPDATE ... ### Critical: the unique index is on `event_id` alone, so fan-out to a second endpoint always fails
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness key omits `endpoint_id`, so at most one delivery row can ever exist per event, while `enqueue_for_event` inserts one row per matching endpoint.
What breaks in production: any organization with two or more active endpoints hits an `IntegrityError` on every event; the dispatcher's blanket `except Exception: log.warning(...)` swallows it, so the API returns success, the event is persisted, and *no* webhook is delivered to *any* endpoint — a silent total-delivery outage visible only in warning logs.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — this keeps the intended idempotency (one attempt-record per endpoint per event, which is what the doc's "deduplicate on `event_id`" advice presumes) while permitting fan-out. Allow side to pin: an integration test that creates two active endpoints in one org and asserts `enqueue_for_event` returns `2` and both rows are present — a fix that merely drops the unique index satisfies the insert but loses idempotency, so also assert that calling `enqueue_for_event` twice with the same `event_id` still yields exactly two rows. Red-prove separately: (i) revert to the single-column index — the two-endpoint test reds with `IntegrityError`; (ii) drop the index entirely — the re-enqueue idempotency assertion reds with four rows; (iii) reverse the column order — assert the index is used by the claim/dedup query plan, or drop this clause as unfalsifiable rather than claiming it. Fail loudly: `enqueue_for_event` must let `IntegrityError` propagate to the dispatcher and the dispatcher must re-raise or record a dead-letter rather than `log.warning`, so "nothing was enqueued" is never spelled the same as "nothing needed enqueuing". Preserve: the at-least-once contract and the `event_id` value that consumers dedup on. Boundary and tie: state that an endpoint deactivated between two enqueues of the same event yields one row, not two, and that the conflict of a genuine retry is resolved by `ON CONFLICT DO NOTHING`, not by an exception.

### Critical: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returning `rows`, `deliver()` reading `delivery.attempts` / `delivery.payload` / `delivery.id`, and `send_once()` reading `endpoint.signing_secret` / `endpoint.url`
What is wrong: `_claim_batch` returns SQLAlchemy entities from inside `with session_scope() as session:` and `deliver` fetches its `endpoint` in a session that closes on the next line, then reads attributes from both — with the default `expire_on_commit=True` every one of those reads is a refresh against a dead session (R9: work using session-bound objects is launched outside the transaction scope that owns them).
What breaks in production: the first attribute access raises `DetachedInstanceError`, `asyncio.gather` propagates it, and the worker dies on its very first batch — outbound webhooks never deliver at all, while the rows it marked `in_flight` are already stranded.
Fix: detach the data, not the objects — have `_claim_batch` return plain values (a `@dataclass(frozen=True) ClaimedDelivery(id, endpoint_id, payload, attempts)` built inside the session) and have `deliver` load the endpoint's `url` and `signing_secret` into a similar frozen record inside its own session before any network call, so nothing session-bound crosses a `with` boundary. Allow side to pin: an integration test that runs `_claim_batch` against a real (or in-memory) DB with two pending rows and asserts the returned records expose the correct `payload` and `endpoint_id` *after* the session has exited — a fix that returns empty lists satisfies "no DetachedInstanceError" and must be excluded. Red-prove separately: (i) return the ORM rows again — the after-session read reds with `DetachedInstanceError`; (ii) omit `payload` from the record — `send_once` reds on the missing attribute; (iii) set `expire_on_commit=False` as the "fix" instead — assert that the record type, not an ORM entity, is returned, and this reds. Fail loudly: if `session.get(WebhookEndpoint, delivery.endpoint_id)` returns `None` (endpoint deleted mid-flight) `deliver` must call `_finish(..., "failed_permanent", ..., "endpoint deleted")` rather than dereferencing `None` and dying inside `gather` — this is the same unguarded-`None` bug `_finish` itself has when its row is missing. Preserve: the batch ordering and the `in_flight` marking that stops a second worker from re-claiming. Boundary and tie: a row claimed at exactly `next_attempt_at == now` is included (`<=`), and two rows sharing an identical `next_attempt_at` have no defined order today — see the ordering finding below.

### Critical: the retry loop blocks the event loop with `time.sleep`
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)` inside an `async def`
What is wrong: a synchronous `time.sleep` is called from a coroutine, so it parks the entire event loop rather than yielding, and `asyncio` is already imported in the same module (`asyncio.sleep` is used correctly in `run_worker` twenty lines below — the correct primitive is present and was not used at the second site, R3).
What breaks in production: `run_worker` gathers up to `BATCH_SIZE = 100` deliveries concurrently, so one failing endpoint freezes the whole process for up to 2+4+8+16 = 30 seconds per attempt cycle, serialising every other delivery, starving the redis lock heartbeat, and stalling any other coroutine in the same process.
Fix: `await asyncio.sleep(delay)`. Allow side to pin: a test that patches `asyncio.sleep` with an async spy, drives `deliver` through one 500 then a 200, and asserts the delivery ends `delivered` with `attempts == 2` and the spy recorded `2.0` — a fix that removes the sleep entirely also removes the blocking and must be excluded by that recorded delay. Red-prove separately: (i) revert to `time.sleep` — assert with a second coroutine that increments a counter every 10 ms during the retry that the counter advanced; this reds; (ii) delete the sleep call — the spy's recorded-delay assertion reds; (iii) change `backoff_for(attempt)` to `backoff_for(1)` — the spy's `2.0, 4.0` sequence assertion reds. Fail loudly: if `delay` exceeds a ceiling (say 300 s) the delivery must be rescheduled to the DB rather than slept on, and that branch must log at error level naming the delay, so an absurd backoff is never silently waited out. Preserve: the exponential 2/4/8/16 schedule that `test_backoff_grows_exponentially` and `docs/webhooks.md` both pin. Boundary and tie: `attempt >= MAX_ATTEMPTS` short-circuits *before* the sleep, so the fifth failure must never sleep at all — assert that the spy records exactly four delays for a five-attempt exhaustion.

### Critical: no egress restriction on the customer-supplied endpoint URL, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint()` validation, and `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://` (the docs say "Only `https://` URLs are accepted"), admits any scheme merely *beginning* with `http` such as `httpfoo://`, and places no restriction on the host, while the delivery client follows redirects — so a registered URL is a server-side request primitive against the internal network (RS3: an externally-supplied value validated only for shape, then reaching a request-issuing sink).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/`, or registers an external host that 302s to one, and our worker issues authenticated-looking POSTs into the cloud metadata service and internal admin ports — classic SSRF with credential-theft reach, and on plain `http` the signed payload and its signature travel in cleartext.
Fix: validate at the boundary and constrain the client — require `parsed.scheme == "https"` and a non-empty `parsed.hostname`, resolve the host with `socket.getaddrinfo` and reject any address for which `ipaddress.ip_address(addr).is_private or is_loopback or is_link_local or is_reserved or is_multicast`, reject non-default ports outside `{443}` unless allowlisted, set `follow_redirects=False` on the `AsyncClient`, and re-run the same address check inside the worker immediately before the POST (DNS can be rebound between registration and delivery). Allow side to pin: registering `https://hooks.example.com/acme` (the URL in `docs/webhooks.md`) must still return 201 and must still deliver — a fix that rejects everything satisfies the deny side and must be excluded by that case. Red-prove separately: (i) relax to `startswith("https")` — a test registering `httpsfoo://x/` reds; (ii) remove the private-range check — a test registering `https://127.0.0.1/` reds on the 201; (iii) restore `follow_redirects=True` — a `MockTransport` test whose handler returns a 302 to `http://169.254.169.254/` reds because the second request was issued. Fail loudly: when DNS resolution fails or times out, `create_webhook_endpoint` must return 422 naming "endpoint host could not be resolved" and the worker must record `failed_permanent` with that detail — an unresolvable host must not be treated as "not private, therefore allowed". Preserve: the ability to register any legitimate public HTTPS endpoint, including one behind a CDN with multiple A records (check every resolved address, allow only if all are public). Boundary and tie: state which side IPv6-mapped IPv4 (`::ffff:127.0.0.1`) falls on — it must be normalised and rejected — and that a host resolving to both a public and a private address is rejected, not accepted on the public one.

### Critical: `in_flight` is a non-terminal state with no exit, and retry progress is never persisted
File: `app/webhooks/delivery.py` — `_claim_batch()` (`row.status = "in_flight"`) and `deliver()`'s `while True` loop
What is wrong: a claimed row is set to `in_flight` and only ever leaves that state through `_finish` at the end of an in-memory retry loop that can last 30+ seconds and up to 5 HTTP timeouts of 30 s each, and neither `attempts` nor `next_attempt_at` is written between attempts — so any worker restart, deploy, OOM, or the `CheckViolation` above strands the row permanently, since the claim query only ever selects `status == "pending"` (R38 failure mode 1: a transient state whose only exit is the success path, with no failure-exit and no bounded timeout).
What breaks in production: every deploy silently drops the deliveries in flight at that moment, and those rows are invisible to the worker forever — customers lose billing webhooks with no alert and no recovery path other than manual SQL.
Fix: stop looping in memory and make each attempt a persisted transition — on a non-2xx or transport error, write `attempts = attempt`, `status = "pending"`, `next_attempt_at = now + backoff_for(attempt)` and return, letting the next poll re-claim; add a reaper that runs each poll and resets rows with `status = 'in_flight' AND updated_at < now() - interval '5 minutes'` back to `pending` with `attempts` unchanged; set `updated_at` at claim time so the reaper has a clock to measure against (today `_claim_batch` does not touch it). Allow side to pin: a delivery that succeeds on its first attempt must still end `delivered` with `attempts == 1` and must not be re-claimed by a subsequent poll — a fix that resets everything to `pending` satisfies "nothing gets stuck" and must be excluded by that assertion. Red-prove separately: (i) remove the `next_attempt_at` write on the failure path — a test asserting the row is re-claimable only after the backoff reds because it is claimable immediately; (ii) remove the reaper — a test that marks a row `in_flight` with an old `updated_at` and asserts a later poll claims it reds; (iii) remove the `attempts` write — a test driving five polls and asserting the fifth ends `failed_permanent` reds because the counter never advances. Fail loudly: if the reaper's own transaction fails, `run_worker` must log at error level and not proceed to claim, so a broken reaper is never mistaken for "nothing needed reaping". Preserve: the documented at-most-5-attempts limit and the 2/4/8/16 schedule; the reaper must not reset `attempts`, or a flapping endpoint retries forever. Boundary and tie: a row whose `updated_at` is exactly the 5-minute threshold is reaped (`<=`), and a row reaped while its original worker is still alive can produce one duplicate delivery — that is the at-least-once contract the docs already state, and the `(endpoint_id, event_id)` key is what bounds it.

### Critical: no test verifies the signature against the transmitted body, which is exactly why the R40 defect ships green
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload()`, and `test_verify_accepts_signature_produced_by_sign()`
What is wrong: the send test asserts only that the header *starts with* `sha256=` and is 71 characters long, never recomputing the MAC over `captured["body"]`, and the verify test calls `verify()` which itself calls `sign()`, making it a self-consistency tautology that is green for any serialization whatsoever — so the production primitive (the signature a customer will actually check) is never exercised end-to-end (RT5: the test claims to verify a security primitive while bypassing it; RT1: the assertion compares two outputs of the subject rather than an independently written expected value).
What breaks in production: the suite is green while every delivery carries a signature no customer can reproduce, and no future change to `serialize`, to the header set, or to httpx's encoder can be caught by these tests.
Fix: add an independent verifier to the send test — inside the `MockTransport` handler capture `request.content` and `request.headers`, then assert `hmac.compare_digest(request.headers[SIGNATURE_HEADER], "sha256=" + hmac.new(SECRET.encode(), request.headers[TIMESTAMP_HEADER].encode() + b"." + request.content, hashlib.sha256).hexdigest())` — written from `docs/webhooks.md` rather than by calling `signing.sign`; add tests that drive `deliver` through a `MockTransport` sequence (500 then 200; five 500s; a `ConnectError`) and assert the persisted `status`, `attempts` and `next_attempt_at` after each; add a test for `enqueue_for_event` covering an endpoint with `event_types=[]`, one with a matching type, one with a non-matching type, and one `active=False`. Allow side to pin: the happy-path 200 case must still assert `delivered`, so a suite that only asserts failures is excluded. Red-prove separately: (i) change `serialize` to `json.dumps(payload)` without `sort_keys` and reorder a payload key — the independent-verifier assertion must red naming the digest mismatch; (ii) drop `TIMESTAMP_HEADER` from the request — the verifier reds on the missing header; (iii) change `MAX_ATTEMPTS` to 3 — the five-500s test reds on `attempts`; (iv) make `enqueue_for_event` ignore `active` — the inactive-endpoint test reds on the extra row. Fail loudly: if `MockTransport` never invokes the handler, `captured` stays empty and the test must fail on a `KeyError`/explicit `assert captured, "handler never ran"` rather than pass with zero assertions executed. Preserve: the existing signing tests, which correctly pin the prefix, the digest length, and the wrong-secret rejection. Boundary and tie: pin the exhaustion boundary explicitly — the fourth failure retries and the fifth does not — and assert that two deliveries signed within the same second yield different signatures only if their payloads differ.

### Major: naive and timezone-aware datetimes are mixed, and the SQL columns are `TIMESTAMP` while the models declare `timezone=True`
File: `app/webhooks/delivery.py` — `enqueue_for_event()` (`next_attempt_at=datetime.utcnow()`) vs `_claim_batch()` (`now = datetime.now(timezone.utc)`); `migrations/0042_webhook_delivery.sql` — all five `TIMESTAMP` columns vs `app/webhooks/models.py` — `DateTime(timezone=True)`
What is wrong: `datetime.utcnow()` returns a naive value while every other site in the diff uses aware values, and `models.py` already defines a `_now()` helper (`datetime.now(timezone.utc)`) that `delivery.py` reimplements inline in three places and contradicts in a fourth (R1 helper reimplementation, R3 incomplete propagation).
What breaks in production: comparing naive and aware datetimes raises `TypeError` in Python and, once round-tripped through a `TIMESTAMP WITHOUT TIME ZONE` column, silently shifts scheduling by the server's UTC offset — deliveries fire hours early or late, and in a non-UTC deployment the claim query returns nothing at all.
Fix: import `_now` from `app.webhooks.models` and use it at all four sites in `delivery.py` (including `next_attempt_at=_now()`), and change every `TIMESTAMP` in the migration to `TIMESTAMPTZ` with `DEFAULT now()`. Allow side to pin: a row enqueued with `next_attempt_at = _now()` must be claimable by a poll one second later — a fix that makes everything naive is equally consistent and must be excluded by asserting `row.next_attempt_at.tzinfo is not None` after a DB round trip. Red-prove separately: (i) restore `datetime.utcnow()` — a test asserting `tzinfo is not None` on the persisted value reds; (ii) revert one column to `TIMESTAMP` — the same round-trip assertion reds for that column; (iii) run the claim query with the session's `TimeZone` set to `America/New_York` and assert the same rows are returned — reds under the naive schema. Fail loudly: reject at write time (a `CheckConstraint` or an assertion in `_finish`) any datetime whose `tzinfo` is `None`, so a naive value is never silently coerced. Preserve: the existing UTC semantics — no times should shift for an already-UTC deployment. Boundary and tie: a row whose `next_attempt_at` equals `now` exactly is claimed (`<=`), and DST transitions are irrelevant once every stored value is UTC-anchored — say so, because that is the property the change buys.

### Major: the dispatch lock is a non-atomic check-then-set with a TTL shorter than a batch
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by a separate `set` is not atomic, so two workers starting together both observe the key absent and both proceed; the `set` and `expire` are likewise two round trips, so a crash between them leaves the lock held forever; the 60 s TTL is shorter than the worst-case batch (100 deliveries × up to 5 attempts × a 30 s timeout), so the lock expires mid-batch and the `finally` then deletes a lock a *different* worker now owns.
What breaks in production: two workers deliver the same batch simultaneously and, once the lock lapses, the delete-someone-else's-lock path removes mutual exclusion entirely — customers receive duplicated billing webhooks at a rate the `(endpoint_id, event_id)` idempotency key cannot suppress, because both workers already read the same rows.
Fix: use a single atomic call with a token — `token = secrets.token_hex(16)`; `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)`; release with a Lua compare-and-delete that only deletes when the stored value equals `token`; set `LOCK_TTL_SECONDS` above the worst-case batch runtime (`BATCH_SIZE * REQUEST_TIMEOUT` is the bound to state) and renew it periodically from the worker loop; the DB claim should additionally use `SELECT ... FOR UPDATE SKIP LOCKED` so correctness does not depend on the lock at all. Allow side to pin: a single worker must still acquire the lock, run its batch, and release it, so the next poll acquires again — a fix that never acquires satisfies "no double acquisition" and must be excluded. Red-prove separately: (i) drop `nx=True` — a test with two concurrent `_acquire_lock()` calls asserting exactly one `True` reds; (ii) drop the token comparison in release — a test where worker A's lock expired and worker B acquired, then A releases, asserting B's lock still exists, reds; (iii) drop `ex=` — a test asserting the key has a positive TTL reds. Fail loudly: when redis is unreachable, `_acquire_lock` must raise (or return `False` *and* log at error level) rather than returning `True`; "cannot tell whether a lock is held" must never be spelled the same as "no lock is held". Preserve: the poll/sleep cadence and the `finally` release so a lock is never orphaned by an exception. Boundary and tie: a `SET NX` losing by microseconds returns `False` and the loser sleeps `poll_interval` — state that, and state that a lock expiring at exactly the instant of release results in no delete, not a foreign delete.

### Major: webhook enqueue is fire-and-forget after the event transaction has already committed, and every failure is swallowed
File: `app/events/dispatcher.py` — `dispatch()`, the `try/except Exception: log.warning(...)` block
What is wrong: `enqueue_for_event` runs in a transaction of its own after the event's `session_scope()` has closed, and every exception it can raise — the `IntegrityError` from the single-column unique index, a DB outage, the `CheckViolation` above — is caught and downgraded to a warning with no retry, dead-letter, or metric (R9: fire-and-forget crossing a transaction boundary; R4: a mutation site whose notification path can silently no-op).
What breaks in production: the API returns success and the event is durably recorded while the webhook rows silently do not exist, so the customer's system never learns about a paid invoice and nothing in the product surfaces the gap.
Fix: enqueue inside the same transaction as the event insert (move the `enqueue_for_event` call into the `with session_scope()` block and pass the session, so the event and its delivery rows commit atomically), and let any exception propagate so the caller sees a 500 rather than a false success; if a same-transaction insert is unacceptable, write an outbox row in that transaction and have the worker fan it out. Allow side to pin: a successful dispatch must still return the `event_id` and must still fire in-process `SUBSCRIBERS` — a fix that raises on every path is excluded by that case. Red-prove separately: (i) restore the `except Exception` swallow — a test where `enqueue_for_event` raises and the caller asserts the exception propagates reds; (ii) move the enqueue back outside the transaction — a test that forces the enqueue to raise and asserts *no* `Event` row was committed reds; (iii) remove the `envelope.type in WEBHOOK_EVENT_TYPES` guard — a test asserting a non-webhook event creates no delivery rows reds. Fail loudly: keep a distinct log line and metric for "enqueued 0 rows because the org has no active matching endpoint" versus "enqueue failed" — today both are invisible, and the former is legitimate while the latter is an incident. Preserve: the existing `SUBSCRIBERS` notification and the return of `event_id`, which callers depend on. Boundary and tie: an event whose org has exactly zero matching endpoints commits with zero delivery rows and must return normally; that is not an error and must not be routed to the same alert.

### Major: `WEBHOOK_EVENT_TYPES` is a hardcoded three-member allowlist that contradicts the documented subscription model
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES` gate, against `docs/webhooks.md` ("An empty `event_types` subscribes the endpoint to every event type we emit") and `app/webhooks/delivery.py` — `if not endpoint.event_types or event_type in endpoint.event_types`

Red-prove separately: (i) restore the hardcoded set — a test emitting a fourth registered type and asserting a delivery row exists reds; (ii) remove the API validation — a test posting `event_types=["invoice.pad"]` and asserting 422 reds; (iii) make the empty list mean "nothing" — the subscribe-to-all test reds. Preserve: the log line's `webhooks=` field, which is useful — recompute it from the new predicate rather than deleting it. Boundary and tie: state that `event_types=[]` means all and `event_types` absent means the same (the Pydantic default), and that an endpoint whose list is later emptied re-subscribes to everything — that fail-open direction should be an explicit product decision, documented at the API, not an artifact of the empty-list sentinel.

### Major: `limit` on the deliveries route has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries()`, `limit: int = Query(50, ge=1)`
What is wrong: the parameter is validated for its lower bound only, so a caller may pass an arbitrarily large value that flows straight into `.limit(limit)` and then into JSON serialization of every matching row (RS3: an externally-supplied value validated at the boundary for one half of its domain, reaching a query sink).

### Major: no rate limiting on any of the three new routes
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, `list_webhook_endpoints()`, `list_deliveries()`
What is wrong: three new public API routes are added with no rate limiter and no per-org cap on endpoint count (RS2), and the create route mints a fresh secret and an unbounded fan-out target on each call.
What breaks in production: a script creating thousands of endpoints multiplies our outbound traffic by that factor for every event — the platform becomes a traffic amplifier against a third party, and the delivery worker's fixed `BATCH_SIZE = 100` means legitimate tenants' deliveries starve behind the flood.

Preserve: normal interactive use of the settings UI, which is what the cap and the window must be sized against. ### Major: the retry policy in code contradicts the retry policy in the docs on two points
File: `app/webhooks/delivery.py` — `deliver()`'s status handling and `backoff_for()`, against `docs/webhooks.md` "Retries"
What is wrong: the docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", while `deliver` retries *every* non-2xx up to `MAX_ATTEMPTS` and `backoff_for` returns a pure power of two with no jitter (R29: a rationale and a derived claim published to customers that the implementation does not support).
What breaks in production: a customer endpoint returning 401 or 404 is hammered five times per event instead of once, burning our quota and their rate limiter, and the missing jitter means every delivery enqueued by one event retries in lockstep — a synchronized thundering herd against a single customer host after any shared outage.
Fix: branch on the response class — treat `400 <= status < 500` (excluding 408 and 429, which are retryable) as `failed_permanent` immediately, retry 5xx / 408 / 429 / transport errors, and add jitter as `backoff_for(attempt) * random.uniform(0.5, 1.5)` computed at scheduling time; where the doc and the code still differ after this, change the doc in the same commit. Allow side to pin: a 500 must still be retried and a 200 must still be `delivered` — a fix that marks every non-2xx permanent removes retries entirely and is excluded by the 500 case. Red-prove separately: (i) remove the 4xx branch — a test returning 404 and asserting `attempts == 1` and `failed_permanent` reds; (ii) add 429 to the permanent set — a test returning 429 and asserting a retry reds; (iii) remove the jitter multiplier — a test asserting two deliveries scheduled from the same `attempt` receive different `next_attempt_at` values reds. Fail loudly: an unrecognised status (a 3xx once redirects are disabled, a 1xx) must be recorded `failed_permanent` with the status in `response_body`, not fall through to a retry as "not 2xx". Preserve: `MAX_ATTEMPTS == 5` and the 2/4/8/16 base schedule, both of which `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` pin — jitter must be applied outside `backoff_for` so those tests stay meaningful. Boundary and tie: 399 and 400 fall on opposite sides and 500 is retryable — state each explicitly, and state that jitter never pushes a delay below the previous attempt's base delay.

### Major: the request signature is written to the application log, and the full response body is persisted unbounded
File: `app/webhooks/delivery.py` — `log.info("POST %s headers=%s", endpoint.url, headers)` in `send_once()`, and `_finish(..., response.text)` in `deliver()`
What is wrong: the log line serialises the entire header dict including `X-Acme-Signature` and `X-Acme-Timestamp` on every single delivery, and `response.text` is stored into `response_body` with no size cap and no content-type check.
What breaks in production: anyone with log-read access holds a valid signature for a known payload and — because the timestamp is not in the MAC (see the first finding) — can replay that exact request against the customer forever; separately, an endpoint returning a multi-megabyte error page fills the `webhook_deliveries` table and the log pipeline on every attempt.

Red-prove separately: (i) restore the header logging — a test capturing log records and asserting no record contains `SIGNATURE_HEADER` reds; (ii) remove the truncation — a test with a 1 MB body asserting the stored length equals the cap reds; (iii) remove the recorded original length — a test asserting the truncation is discoverable reds. Fail loudly: when the response body is not decodable text, store an explicit marker naming the content-type rather than an empty string, so "no body" and "unreadable body" are distinguishable. Preserve: the existing warning line on retry, which names the delivery id and delay and is genuinely useful for operations. Boundary and tie: a body exactly at the cap is stored untruncated and one character longer is truncated — assert both, and state that the cap is in characters, not bytes, for multi-byte responses.

### Major: `_finish` dereferences a row it never checks
File: `app/webhooks/delivery.py` — `_finish()`, `row = session.get(...)` followed immediately by `row.status = status`
What is wrong: `session.get` returns `None` for a missing primary key and the next line attributes onto it unguarded — reachable whenever an endpoint (and its deliveries, via `ON DELETE CASCADE`) is removed while a delivery is in flight.

## Cross-cutting verification

- **Org scoping** — three new query sites: `list_webhook_endpoints` (scoped), `enqueue_for_event` (scoped), `list_deliveries` (**not scoped** — reported Critical above). No other unscoped site in the diff.
- **`datetime` construction** — `models._now()` is defined and used for four column defaults; `delivery.py` reimplements it inline at `_claim_batch` and `_finish` and contradicts it at `enqueue_for_event` (`datetime.utcnow()`). Four sites, one divergent; reported Major above.
- **Status enum spelling** — `models.STATUSES` and `deliver()` use `failed_permanent`; the migration CHECK uses `failed`. Two of three sites agree; reported Critical above.
- **Sleeping in coroutines** — `run_worker` uses `await asyncio.sleep` at two sites; `deliver` uses `time.sleep` at one. Reported Critical above.
- **URL validation** — validation exists at exactly one site (`create_webhook_endpoint`); there is no second registration path in the diff, but the delivery worker re-uses the stored URL with no re-check, which is the second site the SSRF fix must cover.

## Codebase awareness

- `hmac.compare_digest` — already reachable in `signing.py` (`hmac` imported at line 2); `verify()` reimplements comparison with `==`.
- `secrets` — the standard-library CSPRNG helper for exactly this job; `new_signing_secret()` reimplements it with `random`.
- `asyncio.sleep` — already imported and correctly used twice in `run_worker`; `deliver` reimplements the wait with `time.sleep`.
- `models._now()` — already defined as the module's timestamp helper; `delivery.py` inlines the same expression twice and diverges from it once.
- `serialize()` — already defined in `signing.py` as the canonical encoder; `send_once` bypasses it by delegating serialization to httpx's `json=` parameter, which is the direct cause of the top Critical finding.
