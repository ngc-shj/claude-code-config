### Critical: signing secrets are generated with the `random` module, so every signature is forgeable
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, which is the Mersenne Twister PRNG — non-cryptographic, unseeded from any entropy source the attacker cannot observe, and fully reconstructible from ~624 observed outputs.
What breaks in production: An attacker who registers a handful of their own endpoints recovers the generator state and derives every other tenant's signing secret, letting them forge `X-Acme-Signature` on fabricated `invoice.paid` events delivered to any customer that trusts the signature.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`; drop `random`, `string`, `_ALPHABET`) and rename `SECRET_BYTES` to match its new meaning — it currently names a character count, not bytes, and the existing test asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which is false for base64url of N bytes. Preserve the two behaviours the current code does provide and that the fix must not delete: the `whsec_` prefix (clients grep for it) and a fixed, documented secret length. Pair the deny side with the allow side: assert both that two consecutive calls differ AND that a secret produced by the new generator still round-trips through `sign`/`verify` for a known-literal payload, so a generator that returns a constant and a generator that returns something `verify` cannot consume are both caught. Red-prove each clause separately by execution: (a) stub `new_signing_secret` to return a fixed string → the distinctness assertion reds; (b) stub it to return `SECRET_PREFIX` only → the length assertion reds; (c) stub it to drop the prefix → the prefix assertion reds. Fail loudly when the check cannot run: if `secrets.token_urlsafe` raises (no OS entropy source), let the exception propagate out of endpoint creation as a 500 rather than falling back to any weaker generator — "could not generate a secret" must not be spelled the same as "generated one". Boundary and tie: a secret of exactly `SECRET_BYTES` bytes is accepted; the generator must never emit a shorter one, and two endpoints created in the same request must receive different secrets.

### Critical: `verify` compares signatures with `==`, a non-constant-time comparison (RS1)
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: The HMAC comparison uses Python's `str.__eq__`, which short-circuits on the first differing byte, so the comparison time leaks a prefix-match oracle.
What breaks in production: Any consumer that adopts this shipped `verify` as its verification routine lets a remote caller recover a valid signature byte-by-byte over repeated requests and then deliver forged events as if they came from us.
Fix: `import hmac` is already present — change the return to `hmac.compare_digest(expected, signature)`, and guard the non-`str` case first (`if not isinstance(signature, str): return False`) because `compare_digest` raises `TypeError` on mixed types. Do not fix this by deleting `verify` and telling consumers to write their own; the function's usefulness — a reference verifier we ship — is the behaviour to preserve. Pair the deny side with the allow side: keep `test_verify_accepts_signature_produced_by_sign` green and add a case where a signature differing only in its final hex character is rejected, so a fix that always returns `False` fails. Red-prove each clause separately: (a) mutate `compare_digest` back to `==` → a test asserting `verify.__code__.co_names` contains `compare_digest` reds; (b) mutate the return to `True` → the wrong-secret rejection test reds; (c) pass a non-`str` signature → the type-guard test reds instead of the call raising. Fail loudly when the check cannot run: a `signature` of the wrong length or missing the `sha256=` prefix must return `False` explicitly rather than reaching the comparison. Boundary and tie: signatures of equal length that differ in one byte are rejected; two byte-identical signatures compare equal in time independent of content.

### Critical: the signature is computed over bytes that are never transmitted, and omits the timestamp the docs say it covers (R40)
File: `app/webhooks/signing.py` — `sign`/`serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, sorted keys) while `send_once` transmits the body via `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and unsorted keys, and the timestamp is returned in a header but never fed into the MAC that `docs/webhooks.md` says is over `"{timestamp}.{raw_request_body}"`.
What breaks in production: Every customer who implements verification exactly as documented — HMAC over the raw received body prefixed with the timestamp — computes a digest that never matches, so the entire integration rejects 100% of our deliveries; and because the timestamp is unauthenticated, an attacker who captures one request can replay it forever with a rewritten timestamp header, defeating the five-minute window the docs present as the anti-replay control.
Fix: Make one byte string the single source of truth. Change `serialize` to `json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, change `sign` to take that exact `body: bytes` and return `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, and change `send_once` to build `body = serialize(delivery.payload)` once, pass it as `content=body` (not `json=`) with an explicit `Content-Type: application/json`, and sign that same object — so the signed bytes and the wire bytes are the same variable, not two independent serializations. Update `verify` to take the raw body bytes and the timestamp, reject a timestamp more than 300 seconds from now, and compare with `compare_digest`. Do not fix this by relaxing the doc to match the code: the anti-replay property and the "verify against the raw body" contract are exactly what the fix must preserve. Pair the deny side with the allow side: add a round-trip test that feeds the ACTUAL bytes captured by `httpx.MockTransport` — not a re-serialization — through `verify` and asserts acceptance, alongside a case where one byte of the captured body is flipped and one where the captured timestamp header is incremented, both rejected. Red-prove each clause separately by execution: (a) revert `separators` to the default → the captured-bytes acceptance test reds; (b) drop the `f"{timestamp}."` prefix → the rewritten-timestamp rejection test reds; (c) widen the freshness window to `sys.maxsize` → the stale-timestamp test reds. Fail loudly when the check cannot run: a payload that is not JSON-serializable must raise at `serialize` before any HTTP call, never be signed as a repr. Boundary and tie: a timestamp exactly 300 seconds old is accepted and 301 rejected; two deliveries signed in the same second with identical payloads produce identical signatures, which is why `event_id` must remain the dedup key on the receiver.

### Critical: `list_deliveries` has no tenancy predicate, exposing every organization's event payloads (R3)
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id == endpoint_id` taken straight from the path, with no check that the endpoint belongs to `user.org_id`, while its two siblings in the same file (`list_webhook_endpoints`, `create_webhook_endpoint`) both scope by `user.org_id` — the pattern was propagated to two of three new routes.
What breaks in production: Any authenticated customer can enumerate sequential `BIGSERIAL` endpoint ids and read other tenants' delivery rows, whose `to_dict` exposes `event_type` and status for billing events (`invoice.paid`, `invoice.payment_failed`), a cross-tenant data breach reachable with a `for` loop.
Fix: Join the ownership check into the same query rather than adding a second round trip — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id, ...)` — and raise `HTTPException(404)` (not 403) when the endpoint does not exist or is not the caller's, so the two cases are indistinguishable and the id space is not an oracle. Cross-cutting: `enqueue_for_event` already scopes by `org_id`, and `deliver`'s `session.get(m.WebhookEndpoint, delivery.endpoint_id)` is internal so it needs no predicate — those are the only other endpoint lookups in the diff, and both are correct; this route is the sole miss. Do not fix by removing the route: the documented ability to inspect one's own deliveries is the behaviour to preserve. Pair the deny side with the allow side: one test asserting the owning org gets its rows (a deny-everything fix must red here) and one asserting a foreign org gets 404 with an empty body. Red-prove each clause separately: (a) delete the `org_id` filter → the foreign-org test reds; (b) change 404 to 403 → the indistinguishability test reds; (c) delete the join → the owning-org test reds because the join column is gone. Fail loudly when the check cannot run: an `endpoint_id` that resolves to no row must 404, never return `[]`, so "no such endpoint" is not spelled the same as "endpoint with no deliveries". Boundary and tie: an endpoint whose `org_id` equals the caller's is allowed, and a soft-deleted or inactive endpoint still belongs to its org for read purposes.

### Critical: `WebhookEndpoint.to_dict` returns the signing secret on every read, contradicting the documented one-time disclosure (R49)
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict` unconditionally includes `"signing_secret"`, and `list_webhook_endpoints` returns it for every endpoint, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: The secret is re-served on every settings page load, so it lands in browser caches, proxy logs, HAR files, and support screenshots, and the documented claim causes operators to skip the rotation they would otherwise perform after such exposure — an overstated control that another control was omitted because of.
Fix: Remove `"signing_secret"` from `to_dict` and give the creation path its own serializer — have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` so exactly one call site discloses it; the disclosure then cannot be reintroduced by a new list route reusing `to_dict`. Do not fix by deleting the disclosure entirely: the create response must still return the secret once, or customers can never configure verification. Pair the deny side with the allow side: assert the create response CONTAINS `signing_secret` and that the list response does not, so a fix that strips it everywhere reds. Red-prove each clause separately: (a) re-add `"signing_secret"` to `to_dict` → the list-response test reds; (b) drop the key from the create handler → the create-response test reds; (c) add a third route calling `to_dict` → a test asserting `"signing_secret" not in WebhookEndpoint.to_dict.__code__.co_consts` reds if the key returns to the shared serializer. Fail loudly when the check cannot run: `create_webhook_endpoint` must raise rather than return a 201 if `new_signing_secret()` produced an empty or missing secret. Boundary and tie: the create response is the single disclosure point; two endpoints created in one session each disclose only their own secret.

### Critical: the migration's status CHECK constraint omits the status the code writes (R2)
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` `STATUSES`

Do not fix by dropping the CHECK constraint: the constraint is what makes an unknown status visible at write time and must be preserved. Pair the deny side with the allow side: an integration test inserting each of the four legitimate statuses must succeed, and one inserting `'failed'` must raise — a fix that drops the constraint reds the second, a fix that narrows it reds the first. Red-prove each clause separately: (a) revert the SQL to `'failed'` → the `failed_permanent` insert test reds; (b) add a fifth value to `STATUSES` without migrating → a test comparing `STATUSES` against the constraint's enumerated values reds; (c) delete the constraint → the `'failed'` rejection test reds. Fail loudly when the check cannot run: if the constraint cannot be introspected (no DB in the environment) the test must error, not skip silently. Boundary and tie: exactly the four members of `STATUSES` are accepted; a row already holding a status later removed from `STATUSES` must be caught by the migration that removes it.

### Critical: `UNIQUE INDEX` on `event_id` alone allows only one delivery per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: The uniqueness is on `event_id` only, but `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`.
What breaks in production: The moment any organization registers a second webhook endpoint, `session.add_all(rows)` violates the unique index, the whole enqueue transaction rolls back, and `dispatch`'s bare `except Exception` swallows it as a `log.warning` — so every subscribed customer silently stops receiving webhooks, including the first endpoint that used to work.
Fix: Change it to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);`, which is the idempotency key the code actually needs (one attempt record per event per destination) and matches the docs' "deduplicate on `event_id`" advice given per-endpoint. Do not fix by dropping uniqueness: the index is what makes a re-dispatch of the same event idempotent, and that property must be preserved. Pair the deny side with the allow side: assert that two endpoints of the same org both receive a row for one `event_id` (a fix that keeps the single-column index reds here) and that re-running `enqueue_for_event` for the same event does NOT create duplicate rows for the same endpoint. Red-prove each clause separately: (a) revert to the single-column index → the two-endpoint test reds; (b) drop the index entirely → the re-enqueue idempotency test reds; (c) remove `endpoint_id` from the insert → the insert reds on the NOT NULL constraint. Fail loudly when the check cannot run: `enqueue_for_event` must stop swallowing integrity errors — see the finding on `dispatch`'s bare except below. Boundary and tie: a second endpoint on the same org for the same event inserts successfully; two concurrent enqueues of the same `(endpoint_id, event_id)` must resolve to exactly one row via `ON CONFLICT DO NOTHING`, not to an exception.

### Critical: outbound URLs are unvalidated and redirects are followed, making the worker an SSRF proxy (RS3)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: The only check is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts `http://` (the docs say only `https://` is accepted) and even `httpz://`, applies no allowlist or private-address rejection, and the delivery client then follows redirects, so a public HTTPS URL can bounce the request to `http://169.254.169.254/` or `http://10.0.0.x/`.
What breaks in production: Any authenticated customer turns our delivery worker into a request forwarder against cloud metadata endpoints and internal services, receiving the response body back through `WebhookDelivery.response_body` and the deliveries API — a full read-SSRF with an exfiltration channel.
Fix: Replace the `startswith` test with an explicit `parsed.scheme == "https"` check plus a resolution-time guard: resolve the hostname with `socket.getaddrinfo` and reject any address for which `ipaddress.ip_address(addr).is_private or .is_loopback or .is_link_local or .is_reserved`, rejecting at registration AND re-checking in `send_once` (DNS rebinding makes the registration-time check insufficient on its own), and set `follow_redirects=False` so a 3xx is recorded as a permanent failure rather than chased. Declare the control class per R49: this is a fail-closed verification gate, not an enforceable boundary — a hostname resolving to a public address that proxies inward still passes, and that known bypass belongs next to the check. Do not fix by dropping the deliveries API's `response_body`: the field's diagnostic value is real and the exfiltration is closed by the address guard, not by blinding the operator. Pair the deny side with the allow side: assert `https://hooks.example.com/acme` (public address) registers successfully — a guard that rejects everything is the failure mode that gets this switched off — alongside rejections for `http://`, `httpz://`, `https://localhost`, `https://169.254.169.254`, and a public URL that 302s to a private one. Red-prove each clause separately: (a) revert to `startswith("http")` → the `http://` and `httpz://` rejection tests red; (b) delete the private-address check → the `169.254.169.254` test reds; (c) set `follow_redirects=True` → the redirect-to-private test reds. Fail loudly when the check cannot run: a hostname that fails to resolve must be rejected with a named error, never treated as "no private address found, allow". Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv6 unique-local `fc00::/7` fall on the reject side; a hostname resolving to both a public and a private address is rejected, not accepted on the public one.

### Critical: `time.sleep` inside `async def deliver` blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: A synchronous `time.sleep` is called inside a coroutine that `run_worker` schedules through `asyncio.gather`, so it blocks the loop thread rather than yielding.
What breaks in production: A batch of 100 deliveries is processed strictly serially with up to 30 seconds of blocking sleep each (2+4+8+16), the Redis lock's 60-second TTL expires mid-batch so a second worker claims the same rows and double-delivers, and if the worker shares a process with the API every HTTP request stalls behind the sleep.
Fix: Change the line to `await asyncio.sleep(delay)` — `asyncio` is already imported — and delete the now-unused `import time`. Then make the lock TTL exceed the worst-case batch duration, or better, stop holding one global lock across the whole batch (see the lock finding below). Do not fix by removing the retry delay: the backoff is the behaviour protecting a struggling receiver and must be preserved. Pair the deny side with the allow side: assert that two concurrent `deliver` coroutines whose first attempts both fail complete in roughly one backoff period rather than two (a fix that removes the delay entirely reds a separate assertion that the delay was at least `BASE_DELAY_SECONDS`). Red-prove each clause separately: (a) revert to `time.sleep` → the concurrency test reds because wall time doubles; (b) set `delay = 0` → the minimum-delay assertion reds; (c) remove the `await` keyword → the coroutine-never-awaited warning turns into a failure under `-W error`. Fail loudly when the check cannot run: if `backoff_for` returns a non-positive or non-finite delay, raise rather than sleeping zero, so "no backoff configured" is not spelled the same as "backoff elapsed". Boundary and tie: `attempt == MAX_ATTEMPTS` takes the permanent-failure branch and never sleeps; two deliveries scheduled for the same instant must both proceed rather than serialize.

### Critical: ORM instances are used after their session closes, so the delivery path cannot run at all
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after `with session_scope()` exits), `deliver` (`endpoint` fetched inside a `with` block, read outside it)
What is wrong: Both functions return or retain SQLAlchemy entities past the end of their `session_scope()` block and then read lazily-loaded attributes (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret`, `endpoint.url`), which raises `DetachedInstanceError` once the session is closed and the instances are expired on commit.
What breaks in production: The first real batch raises inside `asyncio.gather`, the exception propagates out of `run_worker`'s `try` (the `finally` releases the lock but does not swallow it), the worker process dies, and every claimed row is left in `in_flight` where `_claim_batch`'s `status == "pending"` filter will never find it again — the queue stops permanently after the first poll.
Fix: Stop passing entities across session boundaries. Have `_claim_batch` return plain data — a list of frozen dataclasses or dicts carrying `id`, `endpoint_id`, `event_id`, `attempts`, and `payload`, read inside the block — and have `deliver` load the endpoint's `url` and `signing_secret` into the same value object inside a single session, so no lazy load ever happens outside a session. Note the codebase already establishes this shape: `WebhookEndpoint.to_dict`/`WebhookDelivery.to_dict` exist as the in-session materialization helper, and `_claim_batch` should use them rather than reimplementing attribute access outside the block. Do not fix by setting `expire_on_commit=False` globally: that hides the boundary rather than removing it, and the fix must preserve the property that a claimed row's state is read from a committed transaction. Pair the deny side with the allow side: an integration test that claims a batch and successfully delivers it must stay green (a fix that returns empty lists reds it), alongside a test asserting `_claim_batch`'s return elements are not SQLAlchemy instances. Red-prove each clause separately: (a) return the ORM rows again → the not-an-ORM-instance assertion reds; (b) drop `payload` from the value object → the delivery test reds with a missing attribute; (c) read `endpoint.url` outside the session in `deliver` → the same detachment error surfaces under a test that closes the session explicitly. Fail loudly when the check cannot run: `deliver` must raise a named error when `session.get(WebhookEndpoint, ...)` returns `None` (deleted endpoint) rather than proceeding to an `AttributeError` on `None`. Boundary and tie: a batch of exactly `BATCH_SIZE` rows and a batch of zero both return valid lists; two workers claiming the same row must not both materialize it — see the lock finding.

### Critical: an enqueue failure is swallowed, so a persisted event is never delivered and never retried (R9)
File: `app/events/dispatcher.py` — `dispatch`, the `except Exception as exc: log.warning(...)` around `webhook_delivery.enqueue_for_event`
What is wrong: The event row is committed in its own transaction and the webhook enqueue runs afterwards in a separate session whose every failure — the unique-index violation above, a DB blip, a detached-instance error — is caught and downgraded to a warning with no outbox row, no retry, and no signal to the caller.
What breaks in production: `docs/webhooks.md` promises at-least-once delivery, but any transient error at enqueue time drops the webhook permanently and silently, so a customer's billing automation misses `invoice.paid` with nothing in the delivery list to explain it.
Fix: Make the enqueue part of the same durable unit as the event: insert the `WebhookDelivery` rows inside the same `session_scope()` that writes the `Event` row, so the delivery record commits atomically with the event and the background worker becomes the only thing that needs retrying — this is the transactional-outbox shape and it removes the fire-and-forget boundary rather than wrapping it. If the enqueue must stay separate, replace the bare `except Exception` with `log.exception` plus a metric and re-raise, so the caller learns the event was not fully processed. Do not fix by widening the `except` or by deleting the warning: the diagnostic must survive, and the behaviour to preserve is that `dispatch` still returns `event_id` on the success path. Pair the deny side with the allow side: assert that a normal dispatch of `invoice.paid` creates both the event row and one delivery row per active endpoint (a fix that always raises reds it), and that a forced enqueue failure leaves NO event row committed rather than an orphan. Red-prove each clause separately: (a) move the delivery insert back outside the transaction → the atomicity test reds because the event survives the induced failure; (b) restore the bare `except` → the propagation test reds; (c) make `enqueue_for_event` a no-op → the delivery-row-count test reds. Fail loudly when the check cannot run: an event type in `WEBHOOK_EVENT_TYPES` with zero matching endpoints must record "0 enqueued" explicitly, so "no endpoints" is not spelled the same as "enqueue skipped". Boundary and tie: an event whose type is exactly a member of `WEBHOOK_EVENT_TYPES` enqueues; two concurrent dispatches of the same `event_id` must resolve to one delivery row per endpoint via the conflict clause.

### Major: `in_flight` is a non-terminal state with no timeout and no reset path (R38)
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `_finish`
What is wrong: `_claim_batch` moves rows to `in_flight`, but the only exits are `_finish`'s success and permanent-failure writes on `deliver`'s happy paths — a worker crash, an unhandled non-`httpx.HTTPError` exception, a container restart, or a lock expiry leaves the row in `in_flight` forever, and the claim query only ever selects `status == "pending"`.
What breaks in production: Every worker restart permanently strands whatever was mid-flight, and the queue silently shrinks over time with no alert, because the stranded rows are neither pending nor terminal.
Fix: Add a `claimed_at TIMESTAMPTZ` column set at claim time, and have `_claim_batch` also select rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`, resetting them to `pending` with `attempts` preserved; wrap `deliver` in a `try/except Exception` that calls `_finish(..., "pending", ...)` with a future `next_attempt_at` so an unexpected exception releases the claim rather than stranding it. Do not fix by removing `in_flight`: the state is what prevents two workers double-delivering, and that property must be preserved. Pair the deny side with the allow side: assert a row claimed 10 minutes ago is re-claimed (a fix that never reclaims reds it) and that a row claimed 10 seconds ago is NOT re-claimed by a second worker. Red-prove each clause separately: (a) delete the reaper predicate → the stale-reclaim test reds; (b) delete the `except` that releases the claim → a test injecting a `ValueError` in `send_once` and then re-polling reds; (c) set the stale interval to 0 → the fresh-claim exclusion test reds. Fail loudly when the check cannot run: a row with `status = 'in_flight'` and a NULL `claimed_at` must be treated as stale and reported, never skipped. Boundary and tie: a row claimed exactly at the 5-minute mark is reclaimed; two workers reclaiming the same stale row must be serialized by a `SELECT ... FOR UPDATE SKIP LOCKED`, so exactly one wins.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` then `expire` is a three-command read-modify-write with no atomicity, so two workers polling simultaneously both observe an empty key and both proceed; and the `finally` deletes the key without checking ownership, so a worker whose lock already expired deletes the lock a second worker legitimately holds.
What breaks in production: Two workers claim overlapping batches and deliver the same event twice to a customer endpoint, and — with the 60-second TTL shorter than a blocking-sleep batch — this is the normal case rather than a race window.
Fix: Acquire with a single atomic command carrying a unique token, `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)`, where `token = uuid4().hex`; release with a Lua compare-and-delete (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so only the owner clears it; and raise `LOCK_TTL_SECONDS` above the worst-case batch wall time once `await asyncio.sleep` replaces `time.sleep`. Do not fix by deleting the lock: single-writer serialization is the property being preserved. Pair the deny side with the allow side: assert a single worker DOES acquire the lock and process a batch (a fix that always returns `False` reds it), and that a second concurrent worker does not. Red-prove each clause separately: (a) revert to `get`-then-`set` → a test issuing two `_acquire_lock` calls against a fake Redis that interleaves reds; (b) drop `ex=` → a test asserting the key has a TTL reds; (c) revert the release to an unconditional `delete` → a test where worker A's lock expired and worker B holds it reds when A's release removes B's token. Fail loudly when the check cannot run: a Redis error during acquire must return `False` (do not run) rather than being caught as "no lock present, proceed". What is wrong: httpx derives the content type from the `json=` argument, so the explicit header is redundant and, if the body construction is later changed to `content=`, the header silently outlives the serializer it described.
What breaks in production: Nothing today; it becomes a live mismatch the moment the body serialization changes, which the R40 fix above requires — at which point the explicit header becomes load-bearing and should be set deliberately alongside `content=`.

### Minor (question, per Finding Floor): is `redis_client` an async client with `nx`/`ex` support?
File: `app/webhooks/delivery.py` — `_acquire_lock`, `from app.cache import redis_client`
What is wrong: The lock fix above assumes `redis_client.set` accepts `nx=`/`ex=` and that a Lua `eval` is available, but `app/cache.py` is not in the diff, so the client's API cannot be confirmed from the change itself.
What breaks in production: If the wrapper exposes only positional `set(key, value)`, the atomic-acquire remedy will not compile as written and needs a `SET ... NX EX` issued through whatever raw-command escape hatch the wrapper provides; confirming that `app/cache.redis_client` is a `redis.asyncio.Redis` (or exposes `set(..., nx=True, ex=...)` and `eval`) closes this.
