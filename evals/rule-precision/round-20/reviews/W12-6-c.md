### Critical: `list_deliveries` has no tenancy predicate — any authenticated user reads any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only `WebhookDelivery.endpoint_id == endpoint_id` taken straight from the path, while its sibling `list_webhook_endpoints` in the same hunk filters `WebhookEndpoint.org_id == user.org_id` — the org predicate was not propagated to the second read route (R3, security-relevant).
What breaks in production: Any authenticated customer can walk `endpoint_id = 1, 2, 3…` and read every other organization's delivery history — event ids, event types, response statuses and schedule — a cross-tenant data breach reachable with a browser and no special tooling.
Fix: Join through the endpoint and scope by org — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` when the endpoint row is absent OR belongs to another org, so the two are indistinguishable and the id space cannot be enumerated. Preserve the feature that made this route useful: the owning org must still receive its own rows, ordered `created_at desc`, so pin an allow case (`org A` sees exactly its N deliveries) beside the deny case (`org B` gets 404 and zero rows). Red-prove each clause separately by execution: (i) delete the `org_id` filter → the cross-tenant test reds; (ii) change the foreign-org branch from 404 to 403 → the enumeration-indistinguishability test reds; (iii) point the request at an id that exists in no table → assert 404, not an empty 200, so "endpoint unresolvable" is not spelled the same as "endpoint has no deliveries". Boundary and tie: an endpoint whose `org_id` is exactly the caller's org is inside; a delivery row whose endpoint was hard-deleted is not reachable at all (the join drops it) and that is the intended outcome.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, whose internal state is recoverable from roughly 624 observed outputs and which is seeded predictably across a process.
What breaks in production: An attacker who registers a handful of endpoints of their own recovers the generator state and predicts the signing secret issued to another organization, letting them forge signed events that a customer's verifier accepts as authentic (RS1/R49 — the whole signing scheme rests on this one call).
Fix: Replace with `secrets.choice(_ALPHABET)` (or `SECRET_PREFIX + secrets.token_urlsafe(32)`) and delete the `random` import so it cannot be reintroduced by autocomplete; rename `SECRET_BYTES = 32` to `SECRET_CHARS`, because it currently counts alphabet characters (~5.95 bits each, not 8) and the name overstates the entropy by a third. Preserve what makes the value usable: the `whsec_` prefix and the exact length the existing `test_new_signing_secret_has_prefix_and_length` asserts, so that test is the pinned allow case and stays green byte-for-byte in shape. Red-prove per clause by execution: (i) stub `secrets.choice` back to `random.choice` under a fixed `random.seed(0)` and assert two fresh secrets from two seeded runs differ — reds; (ii) assert `len(set(new_signing_secret() for _ in range(1000))) == 1000` — reds against any constant-returning implementation; (iii) if `secrets` cannot supply entropy the call must raise, never fall back to `random` — no `except: return random...` path. Boundary and tie: two endpoints must never share a secret; assert distinctness rather than mere non-emptiness, since an empty-string secret is a legal `str` and would otherwise pass.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (sorted keys, `", "`/`": "` separators) while the request body is produced independently by `client.post(..., json=delivery.payload)` (insertion order, `","`/`":"` separators), so the MAC covers a different byte string than the one on the wire — two serializers deciding one predicate (R48/R40), even though `signing.serialize` already exists as the shared serializer this call site bypasses.
What breaks in production: Every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest and rejects 100% of deliveries — a silent total-path failure that no test in this diff can see, because `test_send_once_posts_the_signed_payload` only asserts the header starts with `sha256=`.
Fix: Serialize exactly once and reuse the bytes — `body = serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, body)` (change `sign` to take bytes so the serializer cannot be chosen twice), then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})`; keep `json.dumps(..., sort_keys=True)` as the one canonical form and add `separators=(",", ":")` so it is stable. Preserve the behaviour the `json=` kwarg was giving: the request must still carry `Content-Type: application/json` and the body must still parse to the same object, so the pinned allow case is the existing MockTransport test extended with `assert json.loads(captured["body"]) == FakeDelivery.payload` AND `assert signing.verify(SECRET, captured["body"], captured["headers"][SIGNATURE_HEADER])` computed from the captured raw bytes. Red-prove separately by execution: (i) revert `content=body` to `json=payload` → the verify-from-raw-bytes assertion reds; (ii) drop `sort_keys=True` and feed a payload whose keys are inserted out of order → the canonical-form assertion reds; (iii) if the payload is not JSON-serializable the call must raise before any HTTP request is made, not post an unsigned body. Boundary and tie: a payload of `{}` must still be signed (empty body, non-empty MAC) rather than skipped, and two payloads differing only in key order must produce the identical signature.

### Critical: the timestamp is not covered by the MAC, so the documented replay window stops nothing
File: `app/webhooks/signing.py` — `sign` / `verify`, against `docs/webhooks.md` "Verifying the signature"
What is wrong: The doc states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed", but `sign` MACs the body alone and returns the timestamp as an unauthenticated side value — a claim strictly stronger than the implementation (R49).
What breaks in production: A customer implementing the documented scheme rejects every event; a customer implementing the actual scheme has no replay protection at all, because an attacker who captures one signed delivery can rewrite `X-Acme-Timestamp` to `now` and resend indefinitely with the signature still validating.
Fix: Make the timestamp part of the signed input — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, timestamp, body, signature)` to take the received timestamp, recompute over it, compare with `hmac.compare_digest`, and reject when `abs(now - int(timestamp)) > 300`. Preserve the published header contract: the wire format stays `X-Acme-Timestamp` plus `sha256=<hex>`, so existing receivers keep parsing. Red-prove each clause by execution: (i) sign a payload, mutate only the timestamp header, assert `verify` returns False — reds against the current body-only MAC; (ii) sign with `time.time() - 400` and assert rejection on staleness alone with the MAC still valid — reds against any implementation without the window; (iii) feed a non-numeric or absent timestamp and assert `verify` returns False rather than raising an unhandled `ValueError`, so an unparseable timestamp denies loudly instead of 500-ing the receiver. Boundary and tie: a timestamp exactly 300 seconds old is accepted and 301 is rejected (state it in the doc), and a timestamp in the future by more than the window is rejected too, since clock-skew tolerance must be symmetric or a forward-dated capture never expires.

### Critical: `GET /v1/settings/webhook-endpoints` returns every signing secret, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; consumed by `list_webhook_endpoints` in `app/api/routes/settings.py`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and because `list_webhook_endpoints` reuses that same shared serializer, the secret is returned on every list call — while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49 overstated control; RS4 secret in a readable artifact).
What breaks in production: The credential that authenticates every outbound event is served on a routine GET, so it lands in API access logs, proxy logs, browser history and any client-side cache, and any principal with read access to settings can extract it and forge events indefinitely — while the doc tells customers no such exposure exists.
Fix: Remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` build its 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}`, so the single disclosure site is visible in the route rather than inherited by every caller of the serializer. Preserve what the list route legitimately needs: `id`, `url`, `event_types` and `active` must still be returned, so the pinned allow case is "create returns a `whsec_`-prefixed secret exactly once". Red-prove per clause by execution: (i) assert `"signing_secret" not in GET /webhook-endpoints` body → reds today; (ii) assert `"signing_secret" in POST` response → reds if the create-time disclosure is removed with the rest; (iii) grep-assert in a test that no other route serializes the attribute, so a future third route that forgets fails the check rather than silently re-exposing it. Boundary and tie: an endpoint created and listed in the same request cycle must still hide the secret in the list payload; if a customer loses the secret the recovery path is rotation (a new endpoint or an explicit rotate route), not read-back — say so in the doc.

### Critical: the migration's status CHECK constraint omits the status the code actually writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint allows `'failed'` while `app/webhooks/models.py` `STATUSES` and `delivery.py` `_finish(delivery.id, "failed_permanent", ...)` both use `failed_permanent`; the member set was derived from a hand-written list rather than from one shared primitive (R42/R2), and no writer in the diff ever produces `'failed'`.
What breaks in production: The moment a delivery exhausts its five attempts the `UPDATE` violates the check and raises `IntegrityError`, so the row stays `in_flight` forever and the worker's terminal path is exactly the path that cannot commit — permanent failures are the one case the system cannot record.
Fix: Make one source authoritative: change the constraint to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and generate it from `models.STATUSES` (or assert equality between the two in a test that reads the migration text), rather than editing the literal in one file. Preserve the constraint itself — do not fix this by dropping the CHECK, which is what makes an unknown status impossible. Red-prove each clause by execution: (i) insert `status='failed_permanent'` against the pre-fix schema → reds with `IntegrityError`; (ii) insert `status='bogus'` post-fix → still rejected, proving the constraint was not merely widened; (iii) a sync test that mutates `STATUSES` and asserts the migration comparison reds, so "the two lists agree" cannot pass by never being evaluated. Boundary and tie: the model's column default `'pending'` and the SQL `DEFAULT` must both be members of the same set; if a future status is added it enters `STATUSES` first and the migration is derived, never the reverse.

### Critical: `UNIQUE (event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` in `app/webhooks/delivery.py` builds one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the unique index rejects the second row of every fan-out; the index enforces uniqueness on the wrong key.
What breaks in production: Any organization with two active endpoints gets an `IntegrityError` on flush that rolls back the whole insert, so *zero* deliveries are created — and because `dispatcher.dispatch` swallows the exception with a `log.warning`, the event is silently never delivered to anyone, to be discovered only when a customer reports missing webhooks.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the key that actually backs the documented "deduplicate on `event_id`" guarantee per endpoint. Preserve the idempotency the original index was reaching for: re-running `enqueue_for_event` for the same event must still not create duplicate rows for the same endpoint, so pair the schema change with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` on the insert. Red-prove separately by execution: (i) enqueue one event for an org with two active endpoints and assert two rows exist → reds against the current index; (ii) enqueue the same event twice and assert still two rows → reds if the unique index is simply dropped instead of re-keyed; (iii) assert the second enqueue does not raise, so "already enqueued" is not spelled the same as "enqueue failed". Boundary and tie: an org with exactly one endpoint must still get exactly one row, and two endpoints of *different* orgs subscribed to the same event id each get their own row.

### Critical: `time.sleep` inside an `async def` blocks the whole event loop for the entire backoff
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered 100-wide by `run_worker`, but it retries with the blocking `time.sleep` rather than `await asyncio.sleep`, and it holds the retry loop in-process instead of persisting `next_attempt_at` and returning.
What breaks in production: One failing endpoint freezes the event loop for 2+4+8+16 = 30 seconds per delivery — serializing the whole batch to ~50 minutes and, if the worker shares a process with the FastAPI app, stalling every inbound HTTP request for that entire window while the redis lock's 60-second TTL expires under it and a second worker starts double-delivering.
Fix: Delete the in-process retry loop: attempt once, and on a retryable failure write `attempts = attempt`, `status = 'pending'`, `next_attempt_at = _now() + backoff_for(attempt)` and return, letting `_claim_batch` re-claim it when it is due; if an in-process wait is kept for any reason it must be `await asyncio.sleep(delay)`. Preserve the retry budget that made the feature useful — a delivery must still be attempted up to `MAX_ATTEMPTS` times with the same growing schedule, now spread across polls rather than one blocking loop. Red-prove per clause by execution: (i) a test with a handler returning 500 asserts exactly one HTTP request per `deliver` call and a persisted `next_attempt_at` in the future → reds today; (ii) `asyncio.gather` two deliveries against a slow handler and assert wall-clock is bounded by the slower one rather than their sum → reds against `time.sleep`; (iii) a delivery whose row vanished between claim and finish must log a named error and return, not raise into `gather`. Boundary and tie: at `attempt == MAX_ATTEMPTS` the row goes terminal and is never rescheduled; at `attempt == MAX_ATTEMPTS - 1` it is rescheduled exactly once more, and a row whose `next_attempt_at` equals `now` is claimed (the filter is `<=`).

### Critical: customer-controlled URL with `follow_redirects=True` is an SSRF into the internal network
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only validation is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts `http://` (the doc says "Only `https://` URLs are accepted"), accepts any scheme merely prefixed with `http` such as `httpx://`, and applies no host restriction — and the delivery client then follows redirects, so even an allowlisted host can bounce the request anywhere (RS3, unvalidated boundary value reaching a network sink).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://localhost:6379/`, and the worker POSTs to it from inside the VPC while `_finish` persists the response status and body — turning the webhook system into an authenticated internal-network scanner and credential-exfiltration channel, with the payload also travelling in cleartext for `http://`.
Fix: Validate at the schema boundary with a pydantic type rather than a string prefix — `url: HttpUrl` plus an explicit `if parsed.scheme != "https": raise HTTPException(422, "url must be https")` — then resolve the host and reject any address in a private, loopback, link-local, multicast or reserved range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a delivery failure rather than followed. Preserve the legitimate case: a public `https://hooks.example.com/acme` must still register and still receive deliveries — that is the pinned allow assertion. Red-prove each clause by execution: (i) POST `http://hooks.example.com/x` → 422, reds today; (ii) POST `https://127.0.0.1/x` and `https://169.254.169.254/x` → 422 each, one mutation per range class; (iii) a hostname that does not resolve must 422 with a named reason, not be accepted on the grounds that the check could not run. Boundary and tie: re-resolve at delivery time or pin the resolved address, because a host that is public at registration can be re-pointed to `127.0.0.1` afterwards (DNS rebinding) — state which side of that check the request falls on.

### Critical: no test exercises the verification path a customer actually runs
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`
What is wrong: The signature assertions check only that the header starts with `sha256=` and is 64 hex chars, and `verify` is only ever tested against a signature that `verify` itself recomputes by calling `sign` — so no test ever recomputes the MAC from the bytes on the wire the way `docs/webhooks.md` instructs, which is precisely why the serializer mismatch and the unsigned timestamp above are invisible to a fully green suite (RT5: the test call path never reaches the primitive the customer depends on).
What breaks in production: The signing scheme can be arbitrarily broken — wrong bytes, wrong key input, missing timestamp — while CI stays green, so the defect ships and is discovered only by every customer's verifier rejecting every event at once.
Fix: Add a receiver-side test that captures `request.content` and `request.headers` from `httpx.MockTransport` and recomputes `hmac.new(SECRET.encode(), f"{ts}.".encode() + captured_body, hashlib.sha256).hexdigest()` *independently of `signing.sign`*, asserting it equals the header — an expected value written by hand, not derived from the subject. Preserve the existing coverage: the wrong-secret rejection test stays, since it is the one current assertion with discriminating power. Red-prove each clause separately by execution: (i) change `send_once` back to `json=payload` → the raw-bytes recomputation reds; (ii) drop the timestamp from `sign`'s MAC input → the timestamp-covered assertion reds; (iii) make `sign` return a constant `"sha256=" + "0"*64` → the recomputation reds, whereas today only the wrong-secret test would. Boundary and tie: an empty payload `{}` must still round-trip through the same assertion, and two payloads differing only in key order must yield the same expected digest — pin both, so canonicalization is covered rather than assumed.

### Major: ORM rows are used after their session closes
File: `app/webhooks/delivery.py` — `_claim_batch` return value; `deliver`'s `endpoint` lookup
What is wrong: `_claim_batch` returns `rows` after `with session_scope()` exits, and `deliver` reads `delivery.attempts`, `delivery.payload` and `delivery.id` outside any session; likewise it loads `endpoint` in its own `session_scope` and then reads `endpoint.signing_secret`/`endpoint.url` in `send_once` after that scope has closed.
What breaks in production: With SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit, so the first attribute access raises `DetachedInstanceError` and the worker fails on the first delivery of the first batch — the pipeline never delivers anything, and because `run_worker` has no exception handling the coroutine dies outright.
Fix: Do not pass ORM instances across session boundaries — have `_claim_batch` return plain data (`[(row.id, row.endpoint_id, row.event_type, row.payload, row.attempts) for row in rows]`, materialized inside the session) and have `deliver` open one session that loads the endpoint and delivery together for the duration of the send. Preserve the batching behaviour: the claim must still mark rows `in_flight` and still return at most `BATCH_SIZE` rows in `next_attempt_at` order. Red-prove per clause by execution: (i) an integration test that claims a batch and reads `payload` from the returned value → reds today with `DetachedInstanceError`; (ii) assert the claimed rows' statuses are `in_flight` in a *fresh* session → reds if the mutation is only in-memory; (iii) if the endpoint row is missing (deleted between enqueue and delivery), log a named error and mark the delivery `failed_permanent`, rather than raising `AttributeError` on `None`. Boundary and tie: a row whose `next_attempt_at` equals the claim instant is included, and two workers claiming the same instant must not both see it — see the lock finding below.

### Major: `in_flight` is a non-terminal state with no reaper, and one failure abandons the whole batch
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `run_worker` (`await asyncio.gather(...)`)
What is wrong: Rows enter `in_flight` at claim time and only leave it via `_finish`, so any crash, deploy, or raised exception strands them permanently — `_claim_batch` only ever selects `status == "pending"` — and `asyncio.gather` without `return_exceptions=True` propagates the first exception, abandoning the other 99 claimed rows and killing the `while True` loop since nothing catches it (R38(1): a transient state with no failure exit and no bounded timeout).
What breaks in production: A single transient DB error or one bad endpoint silently drops up to 100 deliveries into a state no code path can ever revisit, and the worker process exits, so delivery stops entirely until someone notices and manually resets rows.
Fix: Add a bounded reclaim — stamp `claimed_at` at claim time and have `_claim_batch` also select `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` — pass `return_exceptions=True` to `gather` and log each returned exception against its delivery id, and wrap the loop body in `try/except Exception: log.exception(...); await asyncio.sleep(poll_interval)` so the worker survives. Preserve the property the `in_flight` marker exists for: a row being sent must not be claimed concurrently by another worker, so the reclaim window must exceed `REQUEST_TIMEOUT`. Red-prove each clause by execution: (i) mark a row `in_flight` with an old `claimed_at` and assert the next `_claim_batch` returns it → reds today; (ii) make one `deliver` raise and assert the other rows in the batch still reach a terminal status → reds without `return_exceptions=True`; (iii) make `_claim_batch` itself raise and assert the worker logs and continues rather than exiting → reds today. Boundary and tie: a row whose `claimed_at` is exactly the reclaim threshold is *not* reclaimed (strict `<`), so an in-flight request at exactly `REQUEST_TIMEOUT` is never double-sent.

### Major: the dispatch lock is a non-atomic check-then-set, and can wedge permanently
File: `app/webhooks/delivery.py` — `_acquire_lock`
What is wrong: `get` then `set` then `expire` are three round trips, so two workers can both observe the key empty and both "acquire"; and because the TTL is set in a separate call, a process that dies between `set` and `expire` leaves a key with no expiry, while `run_worker`'s `finally` deletes the lock unconditionally — including a lock another worker owns.
What breaks in production: Concurrent workers claim overlapping batches and customers receive duplicate events, while the crash-between-set-and-expire case leaves an eternal lock that halts all webhook delivery until an operator manually deletes the redis key (R38 persisted fail-closed wedge with no reset path).
Fix: Acquire atomically with a value that identifies the owner — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only free its own lock; back this with `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch` so correctness does not rest on the lock at all. Preserve the single-dispatcher intent — one worker at a time must still win, and the loser must still sleep rather than spin. Red-prove per clause by execution: (i) two concurrent `_acquire_lock()` calls, assert exactly one returns True → reds today; (ii) worker A acquires, worker B calls the release path, assert the key still holds A's token → reds against the unconditional `delete`; (iii) kill the process after `set` and assert the key still carries a TTL → reds against the separate `expire`. Boundary and tie: the TTL must exceed the longest possible batch, and when both workers hold expired-but-present locks the `SKIP LOCKED` claim decides, so the tie never produces a duplicate send.

### Major: naive and aware datetimes are mixed, and the migration's columns have no time zone
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); `migrations/0042_webhook_delivery.sql` — the four `TIMESTAMP` columns
What is wrong: Every other datetime in the change is timezone-aware (`models._now()`, `_claim_batch`'s `datetime.now(timezone.utc)`, `_finish`'s `updated_at`), but `enqueue_for_event` alone writes naive `datetime.utcnow()` — the one site the aware pattern was not propagated to (R3) — while the migration declares `TIMESTAMP` (without time zone) for columns the models declare as `DateTime(timezone=True)`.
What breaks in production: The `next_attempt_at <= now` comparison mixes naive and aware values (a `TypeError` in Python, or a silent offset once Postgres applies the session `TimeZone` to the naive column), so on any non-UTC database session deliveries are scheduled hours early or late and `created_at DEFAULT now()` drifts from the model's UTC `_now()`.
Fix: Use the module's own helper — `next_attempt_at=m._now()` — and change all four columns to `TIMESTAMPTZ` in the migration so the storage type matches `DateTime(timezone=True)`; there is no need for a new helper, `models._now()` already is the shared one. Preserve the scheduling semantics: a freshly enqueued delivery must still be immediately due, so it is claimed on the very next poll. Red-prove each clause by execution: (i) assert `enqueue_for_event`'s written `next_attempt_at.tzinfo is not None` → reds today; (ii) run `_claim_batch` against a row written by `enqueue_for_event` under `SET TimeZone='America/New_York'` and assert it is claimed → reds against the naive column; (iii) if a row's `next_attempt_at` is NULL the claim must skip it rather than compare `None`. Boundary and tie: a row whose `next_attempt_at` equals `now` to the microsecond is claimed (`<=`), and two rows with identical `next_attempt_at` are ordered by a tiebreaker — add `, id` to the `order_by`, or the `LIMIT 100` page boundary can cut through equal keys and starve rows.

### Major: the documented retry policy is not the implemented one
File: `docs/webhooks.md` — "Retries"; `app/webhooks/delivery.py` — `backoff_for`, `deliver`
What is wrong: The doc promises "exponential with jitter" and "a 4xx is permanent and we stop immediately", but `backoff_for` returns a fixed `2**attempt` with no jitter and `deliver` retries every non-2xx — including 400, 401 and 410 — the full five times (R49: the claim is stronger than the implementation; `test_backoff_grows_exponentially`'s exact equality assertions in fact pin the un-jittered behaviour in place).
What breaks in production: All deliveries that failed together retry in lockstep, so a customer endpoint that comes back from an outage is hit by a synchronized thundering herd, and endpoints returning a permanent 4xx are pounded four extra times each, burning the customer's rate limits and ours.
Fix: Implement both promises — `backoff_for` returns `timedelta(seconds=BASE_DELAY_SECONDS**attempt * random.uniform(0.8, 1.2))` (jitter is not security-sensitive, so `random` is fine here, unlike the secret generator), and `deliver` marks any 4xx other than 408 and 429 `failed_permanent` on the first response. Preserve what the doc's readers rely on: the retry *count* stays at 5 and the median schedule stays ≈2/4/8/16s, so replace the exact-equality backoff test with a bounds assertion rather than deleting it. Red-prove each clause by execution: (i) assert 100 samples of `backoff_for(1)` yield more than one distinct value and all fall in `[1.6, 2.4]` → reds today; (ii) a handler returning 400 asserts exactly one request and `failed_permanent` → reds today; (iii) a handler returning 429 asserts a retry is scheduled → reds if 4xx is made blanket-permanent. Boundary and tie: 429 and 408 are retryable, 499 is not; state that a 3xx (with redirects disabled) counts as a permanent failure.

### Major: the event-type gate is decided in two places, and unknown subscriptions are accepted silently
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: `dispatch` gates on a hardcoded three-element literal set, `enqueue_for_event` gates again on `endpoint.event_types`, and the create route accepts any `list[str]` without checking it against either — three sites deciding one predicate by different data (R48/R4), while `docs/webhooks.md` promises that an empty `event_types` "subscribes the endpoint to every event type we emit".
What breaks in production: A customer subscribing to a real but ungated event such as `invoice.refunded` receives a 201 and then never receives a single delivery, with no error anywhere; and an endpoint with empty `event_types` receives only the three hardcoded types rather than the "every event type" the doc guarantees.
Fix: Put the emitted set in one module (`app/events/registry.py: WEBHOOK_EVENT_TYPES`), import it in the dispatcher for the gate and in `create_webhook_endpoint` to reject unknown members with `HTTPException(422, f"unknown event types: {sorted(unknown)}")`; the dispatcher's set is already the de facto registry, so this is a move, not a new abstraction. Preserve the documented empty-list semantics: an endpoint with `event_types == []` must receive every member of that registry. Red-prove each clause by execution: (i) POST an endpoint with `["invoice.refunded"]` and assert 422 naming the type → reds today (201); (ii) enqueue each registry member for an endpoint with `event_types=[]` and assert one delivery row per member → reds if the empty case is narrowed; (iii) if the registry import fails the dispatcher must raise at import time, not fall back to an empty set that silently disables all webhooks. Boundary and tie: an event type present in the registry but in no endpoint's list produces zero rows and that is correct; adding a type to the registry must not retroactively require re-registration by empty-list subscribers.

### Major: `organizations.webhooks_enabled` is added by the migration and read by nothing
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: The column is created defaulting to FALSE, but no code in the change consults it — `enqueue_for_event` filters only on `org_id` and `active`, and `create_webhook_endpoint` never checks it — so the declared kill switch has no backing path (R41).
What breaks in production: Operators and the migration reviewer both read `DEFAULT FALSE` as "webhooks are off until enabled", while the feature in fact delivers for every organization from the moment it ships; and when an incident calls for switching webhooks off, flipping the column does nothing.
Fix: Make the flag load-bearing — join `Organization` in `enqueue_for_event` and skip enqueueing when `webhooks_enabled` is false, and have `create_webhook_endpoint` return `HTTPException(403, "webhooks are not enabled for this organization")` — or, if the flag was not intended yet, drop the column from the migration rather than shipping an inert one. Preserve the rollout intent: an org with the flag true must still receive every delivery it would have received. Red-prove per clause by execution: (i) set the flag false and assert `enqueue_for_event` returns 0 with no rows written → reds today; (ii) set it true and assert the same event produces one row per matching endpoint → reds if the gate is made unconditional; (iii) if the organization row cannot be loaded, deny and log rather than defaulting to enabled. Boundary and tie: flipping the flag false must not cancel deliveries already queued (state whether in-flight rows drain or are abandoned) — decide it explicitly rather than leaving it to the claim query.

### Major: webhook enqueue runs outside the event's transaction and its failure is swallowed
File: `app/events/dispatcher.py` — `dispatch`, the `try/except Exception: log.warning(...)` block
What is wrong: The `Event` row is committed by its own `session_scope`, and `enqueue_for_event` then opens a second, independent transaction whose failure is caught and reduced to a warning, so "the event happened" and "the event will be delivered" are not atomic (R9) — while `docs/webhooks.md` states "delivery is at-least-once".
What breaks in production: Any failure in the enqueue path — including the `UNIQUE (event_id)` violation above, or a momentary DB blip — permanently drops every webhook for that event with only a WARNING line and no retry, dead-letter, or metric, so the documented at-least-once guarantee is silently untrue and the loss is unrecoverable because nothing records that the enqueue was owed.
Fix: Write the delivery rows in the same transaction as the `Event` insert (pass the open session into `enqueue_for_event`), so either both commit or neither does; if that coupling is unacceptable, persist an outbox row in the event transaction and have the worker turn outbox rows into deliveries, and let the `except` re-raise after incrementing a `webhook_enqueue_failed` counter instead of returning normally. Preserve what the `try` was protecting: a webhook problem must still not break the caller of `dispatch` for non-webhook subscribers — so narrow the catch and keep dispatching to `SUBSCRIBERS`. Red-prove each clause by execution: (i) force `enqueue_for_event` to raise and assert no `Event` row is committed (or that an outbox row exists) → reds today; (ii) assert `SUBSCRIBERS` still run when the webhook path fails → reds if the fix simply lets everything propagate; (iii) assert the failure emits a named error-level signal, so "enqueued nothing" is not spelled the same as "nothing to enqueue". Boundary and tie: an event with zero matching endpoints commits normally with zero rows — that is success, not failure, and the counter must not fire for it.

### Major: the `limit` query parameter has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: The bound is declared asymmetrically — `ge=1` with no `le` — so `?limit=100000000` is accepted and passed straight to `.limit()` (RS3: the boundary validates the value's floor but not the cost it authorizes).
What breaks in production: A single request can force the database to materialize and the app to serialize millions of delivery rows, exhausting memory and stalling the worker sharing that event loop — a one-line denial of service available to any authenticated user.
Fix: Add `le=200` to the `Query(...)` declaration so the schema rejects oversize values with a 422 before any query runs, and keep the default at 50. Preserve the pagination the parameter exists for: `?limit=200` must still return up to 200 rows, and callers wanting more should get a cursor (`before_id`) rather than an unbounded limit. Red-prove per clause by execution: (i) `?limit=100000` → assert 422 → reds today; (ii) `?limit=200` → assert 200 rows returned → reds if the cap is set below the documented maximum; (iii) `?limit=abc` → assert 422 rather than a 500 from the coercion. Boundary and tie: `limit=200` is accepted and `limit=201` is rejected; `limit=0` remains rejected by the existing `ge=1`.

### Major: full response bodies and signed headers are written to logs and to the database unbounded
File: `app/webhooks/delivery.py` — `send_once`'s `log.info("POST %s headers=%s", endpoint.url, headers)`; `deliver`'s `_finish(..., response.text)`
What is wrong: Every delivery logs the complete header dict — including `X-Acme-Signature` and `X-Acme-Timestamp` — at INFO level, and both the success and failure paths persist the customer endpoint's entire `response.text` into `response_body` with no truncation.
What breaks in production: A customer endpoint that returns a large error page writes megabytes per delivery row and bloats the table until the disk fills, while the INFO log stream accumulates a signature for every event — and since the timestamp is not covered by the MAC (see above), a log reader who also has the body can replay any captured delivery.
Fix: Log only what is diagnosable — `log.info("POST %s delivery=%s attempt=%s", endpoint.url, delivery.id, attempt)` — and truncate before persisting: `detail[:2048]` in `_finish`, applied at the single `_finish` call boundary so all four call sites inherit it. Preserve the debuggability the logging was for: the endpoint URL, delivery id, attempt number and response status must all still be recorded, and the truncated body must keep its first 2 KB rather than being dropped. Red-prove each clause by execution: (i) assert the emitted log record contains neither `SIGNATURE_HEADER` nor its value → reds today; (ii) finish a delivery with a 10 MB body and assert the stored `response_body` length is exactly 2048 → reds today; (iii) a response whose body cannot be decoded must store a named placeholder, not raise inside `_finish`. Boundary and tie: a body of exactly 2048 bytes is stored whole and 2049 is cut — mark truncation explicitly (a trailing `…[truncated]`) so a 2048-byte body is not mistaken for a truncated one.

### Major: the delivery worker's production paths have no tests, and the test doubles diverge from the real models
File: `tests/webhooks/test_delivery.py` — imports, `FakeEndpoint`, `FakeDelivery`
What is wrong: The suite imports only `MAX_ATTEMPTS, backoff_for, send_once`, so `enqueue_for_event`, `deliver`, `_claim_batch`, `_finish`, `_acquire_lock` and `run_worker` — every path that carries the Critical and Major defects above — are entirely untested; and `FakeEndpoint`/`FakeDelivery` are hand-written stand-ins whose attributes are class-level constants, so they lack `endpoint_id`, never expire like a detached ORM row, and cannot surface the session-lifetime defect (RT1: a double that returns values fixed before the call; RT6: new production exports with no test diff). `test_max_attempts_matches_documented_limit` compares a constant to a literal and pins no behaviour at all.
What breaks in production: A fully green suite gives no signal about retries, claiming, locking, or the terminal-state transition, so every defect in the worker ships undetected and is discovered as missing customer webhooks.
Fix: Add integration tests against a real session and the real `WebhookEndpoint`/`WebhookDelivery` models — enqueue for a two-endpoint org and assert two rows; claim a batch and assert `in_flight`; run `deliver` against MockTransport handlers returning 200, 500 and 400 and assert the persisted `status`, `attempts` and `next_attempt_at` for each; and replace `test_max_attempts_matches_documented_limit` with one that counts actual HTTP requests until the row goes terminal. Preserve the existing fast unit tests for `signing` — they stay, the new tests are additive. Red-prove each clause by execution: (i) set `MAX_ATTEMPTS = 3` and assert the request-count test reds (today's constant-comparison test would too, but for the wrong reason — the new one names the behaviour in its failure output); (ii) make `_finish` skip the status write and assert the terminal-state test reds; (iii) if no database is available the suite must fail with a named skip-or-error, never pass silently on the fakes. Boundary and tie: assert both the 5th attempt failing (terminal) and the 5th attempt succeeding (delivered), so the retry budget is pinned on the allow side as well as the deny side.
