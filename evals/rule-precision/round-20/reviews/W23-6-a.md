### Critical: `list_deliveries` has no organization filter — any user reads any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id`, taken straight from the path, while every sibling query in the same file (`list_api_keys`, `list_webhook_endpoints`) and in `app/webhooks/delivery.py::enqueue_for_event` filters on `org_id` — so the tenancy predicate was propagated to three of four new query sites and dropped at the fourth (R3, security-relevant).
What breaks in production: Any authenticated user can walk `endpoint_id = 1, 2, 3…` and read other organizations' `invoice.paid` / `subscription.updated` delivery rows, and `docs/webhooks.md` states this route "returns the most recent attempts for an endpoint belonging to your organization", so the documented contract is violated silently with no audit trail.
Fix: Join the tenancy predicate into the query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and when the join yields nothing raise `HTTPException(404)` rather than `403`, so a foreign endpoint id is indistinguishable from a nonexistent one (no existence oracle). Deny/allow pair: pin BOTH a test where the endpoint's owning org is the caller's and rows are returned, and a test where the caller is in another org and the response is 404 with an empty body; red-prove each separately — deleting the `org_id ==` clause must redden only the cross-org test, and deleting the join must redden only the same-org test. Preserve what the route was for: the same-org caller must still get `to_dict()` rows in `created_at DESC` order, so do not "fix" this by removing the route or by requiring an org id in the path. Boundary and tie: an endpoint whose `org_id` is NULL or whose row was cascade-deleted falls on the deny side (404), and if the id is claimed by no endpoint the handler must return 404, not an empty 200 — "endpoint not found" and "no deliveries yet" must not be spelled the same way.

### Critical: the HMAC covers bytes that are never transmitted, and the timestamp is unsigned
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators) while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx encodes with compact separators and insertion key order, and the timestamp is put in a header without being part of the signed material — so the signed string matches neither the wire body nor the `"{timestamp}.{raw_request_body}"` recipe `docs/webhooks.md` publishes (R40 producer/consumer shape, R29 doc claim vs implementation).
What breaks in production: Every customer who implements the documented verification rejects every delivery, and every customer who reverse-engineers our code still fails because the transmitted bytes differ from the signed bytes, while the "reject requests whose timestamp is more than five minutes old" replay defence the docs sell is unenforceable because an attacker can rewrite the unauthenticated timestamp header on a captured request.
Fix: Serialize once and sign exactly what goes on the wire — in `signing.py` add `def signing_input(timestamp: str, body: bytes) -> bytes: return timestamp.encode() + b"." + body`, have `sign(secret, body: bytes)` take the already-encoded body and return `(timestamp, "sha256=" + hmac.new(secret.encode(), signing_input(timestamp, body), hashlib.sha256).hexdigest())`; in `send_once` build `body = serialize(delivery.payload).encode()` and POST `content=body` with an explicit `Content-Type: application/json` header instead of `json=`. Change `verify(secret, timestamp, body, signature)` to recompute over the same `(timestamp, body)` pair. Deny/allow pair: add a round-trip test that captures `request.content` from `httpx.MockTransport` and asserts `signing.verify(SECRET, captured_timestamp, captured_body, captured_signature)` is True (the allow case that must still succeed), alongside one asserting it is False when a single byte of the captured body is flipped and one asserting it is False when the timestamp header is altered. Red-prove each clause separately: re-inserting `json.dumps(..., sort_keys=True)` in `sign` must redden only the round-trip assertion; dropping `signing_input`'s timestamp prefix must redden only the altered-timestamp test; flipping the body byte must redden only that test. Preserve the deterministic key ordering `serialize` gives (it is what lets a consumer recompute over the raw body) — do not fix this by dropping `sort_keys` and hoping the encoders agree. Boundary and tie: the age check belongs to the receiver, but state it in the docs as inclusive — a timestamp exactly 300 seconds old is accepted, 301 rejected — and a request with two `X-Acme-Signature` headers must be rejected outright rather than verified against the first.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` compares an HMAC digest with Python's short-circuiting string equality instead of a constant-time primitive (RS1), in the very helper `docs/webhooks.md` tells integrators to implement with "a constant-time comparison".
What breaks in production: Any caller of `verify` — including inbound flows that later reuse this module — leaks the correct digest byte-by-byte through response timing, letting an attacker forge a signature for an arbitrary payload without the secret.
Fix: `return hmac.compare_digest(expected, signature)`, importing nothing new (`hmac` is already imported). Deny/allow pair: keep the existing `test_verify_accepts_signature_produced_by_sign` as the case that must still return True, and keep `test_verify_rejects_a_signature_made_with_another_secret` as the deny case; add one asserting a signature of the correct length but one differing hex character is rejected. Red-prove: reverting to `==` must not redden any of them (timing is not observable in a unit test), so the clause is enforced instead by a lint/grep gate — add `hooks`/CI check `rg -n '(signature|digest|secret|mac)\s*[!=]=' app/webhooks/` that exits non-zero on a hit, and red-prove THAT gate by re-introducing the `==` line and observing it exit 1 naming the file and line. Fail loudly when the check cannot run: the gate must exit non-zero (not 0) if `rg` is absent or the `app/webhooks/` path does not resolve, so "examined nothing" is not spelled like "found nothing". Preserve the boolean contract of `verify` — do not change it to raise, since call sites branch on the return. Boundary and tie: `compare_digest` raises `TypeError` on non-ASCII `str` input, so the header value must be checked as ASCII before the call and a non-ASCII header must be rejected as invalid rather than crashing the handler.

### Critical: signing secrets are generated with the `random` module
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister PRNG, which is not cryptographically secure and whose internal state is recoverable from a modest number of observed outputs.
What breaks in production: An attacker who registers a handful of endpoints of their own can recover the generator state and predict the signing secret issued to another organization's endpoint, then forge signed `invoice.paid` events that the customer's integration accepts as authentic.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)[:SECRET_BYTES]` — or better, `secrets.token_hex(SECRET_BYTES)` and rename the constant to reflect that it is now bytes of entropy — and delete `import random`, `import string`, and `_ALPHABET` so the weak path cannot be reached again. Existing secrets must be treated as compromised: add a rotation endpoint and a migration that regenerates every row in `webhook_endpoints.signing_secret`. Deny/allow pair: `test_new_signing_secret_has_prefix_and_length` must still pass, so update its length expectation in the same commit if the encoding changes width (the test currently pins `len(SECRET_PREFIX) + SECRET_BYTES`); add an allow-side test asserting two successive calls differ and a deny-side test asserting the returned alphabet contains no character outside the expected set. Red-prove each separately: making the function return a constant must redden only the uniqueness test; restoring `random.choice` must redden a CI gate `rg -n '\brandom\.' app/webhooks/` that exits non-zero, and that gate must itself exit non-zero when `rg` is missing. Preserve the `whsec_` prefix — customer key-management tooling and `test_new_signing_secret_has_prefix_and_length` both key on it. Boundary and tie: state that `SECRET_BYTES` is now bytes of entropy, not characters, and that two endpoints of the same org must never share a secret — the rotation migration must generate per-row, not one value applied by a single `UPDATE`.

### Critical: `to_dict` returns the signing secret on every read of every endpoint
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict` includes `"signing_secret"`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, directly contradicting `docs/webhooks.md`: "The response is the only place the signing secret appears — it cannot be read back afterwards" (R29 / R49 — a claimed control the implementation does not have).
What breaks in production: The webhook signing key is returned on every `GET /v1/settings/webhook-endpoints` and lands in browser caches, proxy logs, API-client history, and any integration that stores list responses, so the secret's blast radius is every principal with read access to the settings API rather than the one-time creation response.
Fix: Remove `"signing_secret"` from `WebhookEndpoint.to_dict()`, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` so the secret is emitted exactly once at creation. Deny/allow pair: pin BOTH a test asserting `POST /v1/settings/webhook-endpoints` response contains a `signing_secret` starting with `whsec_` (the case that must still succeed — without it, deleting the field everywhere passes) and a test asserting `GET /v1/settings/webhook-endpoints` responses contain no key named `signing_secret` and no value starting with `whsec_`. Red-prove each separately: re-adding the field to `to_dict` must redden only the GET test; dropping the explicit merge in the create handler must redden only the POST test. Do not fix by deleting the field from the create response as well — the docs make the creation response the only channel by which a customer can ever obtain the secret. Boundary and tie: `list_deliveries` returns `WebhookDelivery.to_dict()`, which carries no secret today, but the same audit applies if a field is added there; and until the rotation endpoint from the previous finding exists, note in the docs that a lost secret requires deleting and re-registering the endpoint.

### Critical: registration accepts plaintext and internal URLs, and the worker follows redirects — SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker`
What is wrong: The check `parsed.scheme.startswith("http")` admits `http://`, and any scheme that merely begins with those four characters, with no host-level restriction at all, while `httpx.AsyncClient(..., follow_redirects=True)` lets even a legitimate public https endpoint redirect the signed POST anywhere (RS3 — validation done ad hoc in the handler rather than at the schema level, plus a surface-form check standing in for a semantic one).
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:6379/` and our worker POSTs attacker-chosen JSON from inside the VPC — cloud credentials, internal admin APIs, and unauthenticated Redis are all reachable — and plain `http://` endpoints send customers' invoice payloads and our signature in cleartext, which `docs/webhooks.md` explicitly promises will not be accepted ("Only `https://` URLs are accepted").
Fix: Validate at the schema level — declare `url: AnyHttpUrl` on `EndpointIn` (pydantic is already imported) and add a field validator that requires `scheme == "https"` exactly, then resolve the hostname with `socket.getaddrinfo` and reject any address for which `ipaddress.ip_address(addr).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast or .is_unspecified`; set `follow_redirects=False` on the `AsyncClient`, treating a 3xx as a permanent failure; and re-run the same address check inside `send_once` immediately before the POST, because DNS can be re-pointed between registration and delivery. Deny/allow pair: pin `https://hooks.example.com/acme` resolving to a public address as the case that must still return 201 and must still be delivered to (`test_send_once_posts_the_signed_payload` must stay green), and pin deny cases for `http://hooks.example.com`, `httpfoo://evil`, `https://localhost/x`, `https://169.254.169.254/x`, and a 302 from a public host to `http://169.254.169.254/`. Red-prove each separately: relaxing `scheme == "https"` back to `startswith("http")` must redden only the `http://` and `httpfoo://` cases; deleting the address check must redden only the loopback/link-local cases; restoring `follow_redirects=True` must redden only the redirect case. Fail loudly when the check cannot run: a `getaddrinfo` failure must reject the registration with 422 naming DNS resolution as the cause, never fall through to accept. Preserve the ability to register a normal public HTTPS endpoint — do not fix this with an operator allowlist that blocks self-service registration. Boundary and tie: a host resolving to BOTH a public and a private address must be rejected (deny wins over allow), IPv6 must be checked with the same predicates including IPv4-mapped forms, and `0.0.0.0` / `[::]` fall on the deny side.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out fail entirely
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)` permits one delivery row per event across the whole table, but `enqueue_for_event` builds one row per subscribed endpoint and inserts them with a single `session.add_all`.
What breaks in production: The moment an organization has two active endpoints subscribed to the same event, the insert raises `IntegrityError`, the whole `add_all` batch rolls back so NEITHER endpoint gets the event, and the dispatcher's `except Exception: log.warning` swallows it — the customer sees silently missing webhooks with only a warning line to show for it.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — this is also the constraint that actually implements the idempotency `docs/webhooks.md` promises ("delivery is at-least-once, so deduplicate on `event_id`", which must be stated per endpoint) — and have `enqueue_for_event` insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a re-dispatch of the same event is a no-op rather than a 500. Deny/allow pair: pin an integration test where one org with two active endpoints both subscribed to `invoice.paid` gets exactly two rows (the case that must still succeed), and one where `enqueue_for_event` is called twice for the same event and still yields two rows total, not four. Red-prove each separately: reverting the index to `(event_id)` must redden only the two-endpoint test; removing the `ON CONFLICT` clause must redden only the double-dispatch test. Preserve the deduplication the index was added for — do not fix by dropping the unique index outright, which would let a retried dispatch double-deliver. Boundary and tie: two endpoints of DIFFERENT orgs subscribed to the same `event_id` must also both get a row, and the migration must be applied before any code writing a second row per event ships, or the deploy order itself produces the failure.

### Critical: the CHECK constraint rejects the status the code actually writes
File: `migrations/0042_webhook_delivery.sql` — `webhook_deliveries.status CHECK`; `app/webhooks/models.py` — `STATUSES`; `app/webhooks/delivery.py` — `deliver`
What is wrong: The SQL constraint allows `('pending', 'in_flight', 'delivered', 'failed')` while `models.STATUSES` and `deliver`'s exhaustion branch use `'failed_permanent'` — the same enum is spelled in four places (migration, `STATUSES`, `_claim_batch`'s `"pending"`/`"in_flight"` literals, `deliver`'s `"delivered"`/`"failed_permanent"` literals) and one of them diverges (R2 / R40 producer vs strict consumer).
What breaks in production: The first delivery to exhaust its attempts raises a `CheckViolation` inside `_finish`, so the failure is never recorded, the row stays `in_flight` forever, and — because `_claim_batch` selects only `status == "pending"` — that delivery is neither retried nor visible as failed to the customer.
Fix: Make the constraint derive from the one authority: settle on `'failed_permanent'`, change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))`, and replace the bare literals in `_claim_batch`, `deliver` and `_finish` with names imported from `models.STATUSES` (e.g. `STATUS_PENDING`, `STATUS_IN_FLIGHT`, `STATUS_DELIVERED`, `STATUS_FAILED_PERMANENT`) so a future spelling change has exactly one edit site. Deny/allow pair: pin an integration test that drives a delivery to `MAX_ATTEMPTS` against an always-500 transport and asserts the row commits with `status == "failed_permanent"` (must succeed), and a test asserting that writing an unlisted status raises `IntegrityError` (the constraint must still deny). Red-prove each separately: reverting the migration to `'failed'` must redden only the exhaustion test; dropping the CHECK clause must redden only the unlisted-status test. Add a test asserting `set(STATUSES)` equals the set parsed out of the migration file so the two cannot drift again, and red-prove it by editing either side. Preserve the constraint — do not fix this by deleting the CHECK. Boundary and tie: name the terminal set explicitly (`delivered`, `failed_permanent`) and state that `in_flight` is non-terminal and must have a reclaim path (see the `in_flight` finding below); a row already written as `'failed'` by an earlier deploy must be migrated, not left outside the new constraint.

### Critical: `deliver` blocks the event loop with `time.sleep` inside an `async` function
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: The retry backoff uses the synchronous `time.sleep` inside a coroutine, so it blocks the entire event loop rather than yielding.
What breaks in production: One unreachable endpoint stalls the whole worker process for up to 30 seconds (2+4+8+16), `asyncio.gather` over a `BATCH_SIZE` of 100 degrades from concurrent to strictly serial — a batch of failing endpoints takes ~50 minutes — and the 60-second Redis lock expires long before the batch finishes, so a second worker claims and re-sends the same deliveries.
Fix: `await asyncio.sleep(delay)` (`asyncio` is already imported); delete the now-unused `import time` from `delivery.py`. Deny/allow pair: pin a test asserting a batch of N failing deliveries completes in wall-clock time close to the longest single delivery rather than N times it (patch `asyncio.sleep` with an async no-op counting calls, and assert the call count equals the retry count — the allow side is that the retries still HAPPEN), and keep `test_backoff_grows_exponentially` green so the delays themselves are unchanged. Red-prove each separately: restoring `time.sleep` must redden the concurrency assertion; removing the sleep call altogether must redden the call-count assertion. Do not fix by deleting the backoff — the delay between attempts is the feature. Boundary and tie: state that `attempt == MAX_ATTEMPTS` performs no sleep at all (the loop returns first), so the call count is exactly `MAX_ATTEMPTS - 1` for a fully failing delivery, and pin that exact number rather than "greater than zero".

### Major: the dispatch lock is a non-atomic check-then-set with a TTL shorter than the work it guards
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`
What is wrong: `_acquire_lock` does `get` then `set` then `expire` as three separate round-trips, so two workers that both see the key absent both proceed (R5 — a read followed by a write with no atomicity), and the 60-second expiry is unrelated to how long a `BATCH_SIZE`-of-100 batch with retries actually takes.
What breaks in production: Two workers deliver the same financial events concurrently to customer endpoints, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)` deletes whichever lock is current — including one a different worker acquired after the TTL lapsed.
Fix: Replace the three calls with one atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = uuid4().hex`, release only via a Lua compare-and-delete (`if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) end`) so a worker cannot delete another's lock, and renew the TTL between batches; independently, claim rows with `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch` so correctness does not rest on the lock at all. Deny/allow pair: pin a test where a single worker acquires, works, and releases successfully (must still succeed), and one where two concurrent acquisitions against a fake Redis yield exactly one True. Red-prove each separately: reverting to `get`-then-`set` must redden only the concurrency test; removing the token comparison from release must redden a test asserting worker A's release does not delete worker B's lock. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must be caught and treated as "not acquired" plus an error-level log naming Redis, never as acquired. Preserve the poll loop's ability to make progress — do not fix by holding the lock forever. Boundary and tie: state that the lock TTL must exceed the worst-case batch duration (`BATCH_SIZE` × per-delivery worst case) or be renewed, and that a worker whose renewal fails must stop claiming rather than continue unguarded.

### Major: `in_flight` is a non-terminal state with no reclaim path
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`, `_finish`
What is wrong: `_claim_batch` moves rows to `in_flight` and only `_finish` moves them out, while `_claim_batch` selects exclusively `status == "pending"` — so any crash, deploy, unhandled exception, or lock expiry between claim and finish strands rows in `in_flight` permanently, and `attempts` is written only once at the end rather than per attempt (R38 non-terminal transient state).
What breaks in production: Every worker restart silently abandons up to 100 in-flight deliveries which are never retried and never reported as failed, and because `attempts` is not persisted between retries a resumed delivery would restart its count from zero.
Fix: Add a lease: store `claimed_at` (or reuse `updated_at`) when claiming, widen the claim predicate to `status == "pending" OR (status == "in_flight" AND updated_at < now() - LEASE_TIMEOUT)`, persist `attempts` and the next `next_attempt_at` at the END of each failed attempt rather than only on exhaustion, and add a startup sweep that returns stale `in_flight` rows to `pending`. Deny/allow pair: pin a test asserting a row left `in_flight` with `updated_at` older than the lease is re-claimed (the recovery that must work), and one asserting a row `in_flight` for less than the lease is NOT re-claimed (so the fix does not cause concurrent double delivery). Red-prove each separately: removing the `in_flight` arm of the predicate must redden only the first; removing the `updated_at <` age condition must redden only the second. Do not fix by making the worker catch-and-mark-failed on every exception — that would convert a transient restart into a permanent failure for deliveries that never left the queue. Boundary and tie: a row whose `updated_at` is exactly `now() - LEASE_TIMEOUT` falls on the reclaim side, and `LEASE_TIMEOUT` must exceed the worst-case single-delivery duration (`REQUEST_TIMEOUT` × `MAX_ATTEMPTS` plus total backoff ≈ 180s) or a live delivery is reclaimed underneath its own worker.

### Major: ORM rows are mutated in one session and then read and re-read outside it
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`, `send_once`
What is wrong: `_claim_batch` mutates `row.status` and returns the ORM instances after `session_scope()` has exited, and `deliver` likewise reads `endpoint.signing_secret` and `delivery.payload`/`.attempts`/`.id` outside any open session, so every attribute access happens on an instance no session owns.
What breaks in production: With SQLAlchemy's default `expire_on_commit=True` the first attribute access after the scope closes raises `DetachedInstanceError` and no delivery is ever sent; even with `expire_on_commit=False` the values are a snapshot, so `attempt = delivery.attempts` restarts at the stale value on every claim. (What would close the detached-instance half: `session_scope` yielding a session configured `expire_on_commit=False` — the diff does not contain its definition, so that half is a question; the stale-`attempts` half is grounded in the diff as written.)
Fix: Have `_claim_batch` return plain identifiers (`[row.id for row in rows]`) and let `deliver` open its own `session_scope`, load the delivery and its endpoint together, read the fields it needs into locals, and close the session before the HTTP call — this also gives `deliver` a live `attempts` value to increment and persist per attempt. Deny/allow pair: pin an integration test against a real (SQLite or test-Postgres) session asserting a claimed delivery is actually POSTed and marked `delivered` (the path that must work end to end), and one asserting a second `deliver` call for the same id sees the `attempts` value the first call persisted. Red-prove each separately: reverting `_claim_batch` to return ORM instances must redden the first against a default-configured session; removing the per-attempt `attempts` write must redden the second. Do not fix by setting `expire_on_commit=False` globally — that silences the symptom for every model in the application while leaving the snapshot-staleness. Boundary and tie: an id whose row was deleted between claim and load must be skipped with an info log, not crash the batch, and two workers loading the same id must be serialized by the `FOR UPDATE SKIP LOCKED` claim above.

### Major: `enqueue_for_event` writes a naive `utcnow()` into a timezone-aware column, and the migration's columns are not `TIMESTAMPTZ`
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); `migrations/0042_webhook_delivery.sql`
What is wrong: `enqueue_for_event` is the sole site in the new code using naive `datetime.utcnow()` — `models._now()`, `_claim_batch`, `_finish`, and the dispatcher all use aware `datetime.now(timezone.utc)` — and the migration declares `TIMESTAMP` (without time zone) for columns the model declares as `DateTime(timezone=True)`. Codebase awareness: `app/webhooks/models.py::_now()` is the shared helper the change already introduced for exactly this, and `delivery.py` reimplements the timestamp inline in four places instead of importing it (R1).
What breaks in production: `_claim_batch` compares an aware `now` against values inserted naive into a non-`timestamptz` column, so on any deployment whose database session `TimeZone` is not UTC every delivery becomes claimable hours early or hours late, and `WebhookDelivery.to_dict()`'s `next_attempt_at.isoformat()` returns an offset-less string the API documents as a schedule.
Fix: Import `_now` from `app.webhooks.models` and use it at all four sites in `delivery.py`, replacing `datetime.utcnow()` and the three inline `datetime.now(timezone.utc)` calls; change every `TIMESTAMP` in `migrations/0042_webhook_delivery.sql` to `TIMESTAMPTZ` and add a follow-up `ALTER TABLE ... ALTER COLUMN ... TYPE TIMESTAMPTZ USING ... AT TIME ZONE 'UTC'` if the migration has already been applied anywhere. Deny/allow pair: pin a test asserting a row enqueued with `next_attempt_at = _now()` IS claimed immediately (the due-now case that must still succeed), and one asserting a row scheduled one hour ahead is NOT claimed, both executed with the database session set to a non-UTC zone. Red-prove each separately: restoring `datetime.utcnow()` must redden the non-UTC due-now test; reverting the column type must redden the future-scheduled test. Do not fix by making `_claim_batch` compare naive values — that discards the offset information the aware columns exist to carry. Boundary and tie: a delivery whose `next_attempt_at` equals `now` exactly falls on the claim side (`<=`, as written), and this must remain true across a DST transition in the session's configured zone.

### Major: the retry policy contradicts the documented contract on 4xx and on jitter
File: `app/webhooks/delivery.py` — `deliver`, `backoff_for`; `docs/webhooks.md` — "Retries"
What is wrong: The docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx status for all five attempts and `backoff_for` returns a bare `2**attempt` with no jitter — and `test_backoff_grows_exponentially` pins the jitter-free values, so the test enshrines the divergence (R29).
What breaks in production: A customer who deprovisions an endpoint receives four extra POSTs per event returning 404/410, and because every endpoint subscribed to one event retries on the identical schedule, a shared downstream outage produces synchronized retry waves that keep it down.
Fix: In `deliver`, treat `400 <= response.status_code < 500` — excluding `408` and `429`, which are retryable — as terminal: call `_finish(delivery.id, STATUS_FAILED_PERMANENT, attempt, response.status_code, detail)` and return. In `backoff_for`, apply full jitter: `timedelta(seconds=random.uniform(0, BASE_DELAY_SECONDS ** attempt))` using `random` (non-cryptographic use is correct here, unlike the signing secret). Update `test_backoff_grows_exponentially` to assert bounds (`0 <= seconds <= 2 ** attempt`) rather than exact values, and keep a test asserting the upper bound grows monotonically. Deny/allow pair: pin a 500 response still producing `MAX_ATTEMPTS` attempts (the retry behaviour that must survive), and a 404 producing exactly one; plus a 429 producing `MAX_ATTEMPTS`. Red-prove each separately: removing the 4xx branch must redden only the 404 test; adding 429 to the terminal set must redden only the 429 test; removing the jitter must redden a test asserting two calls to `backoff_for(3)` are not always equal. Do not fix by editing the docs to match the code — the 4xx-is-permanent rule is what stops us hammering a deprovisioned endpoint, and it is what customers designed against. Boundary and tie: state which side each edge status falls on — `399` and `400` (400 is terminal), `499` and `500` (500 retries) — and that a delivery terminated on 4xx records the status code so the customer can see why.

### Major: two adjudicators decide "is this endpoint subscribed", and neither validates `event_types`
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/webhooks/delivery.py` — `enqueue_for_event`; `app/api/routes/settings.py` — `EndpointIn.event_types`
What is wrong: `enqueue_for_event` already decides subscription per endpoint (`if not endpoint.event_types or event_type in endpoint.event_types`), and the dispatcher adds a second, coarser gate over a hardcoded three-element set, so the same predicate is answered by two different semantics (R48); meanwhile `EndpointIn.event_types: list[str] = []` accepts any string at the boundary with no membership check (RS3, R42).
What breaks in production: `docs/webhooks.md` promises "an empty `event_types` subscribes the endpoint to every event type we emit", but such an endpoint receives only the three types in the dispatcher's set, and a customer who registers `event_types: ["invoice.pald"]` — or any valid type outside those three — gets a 201 and then silently never receives a single delivery.
Fix: Keep exactly one adjudicator. Move the canonical set into `app/webhooks/models.py` as `WEBHOOK_EVENT_TYPES`, delete the dispatcher's gate so `enqueue_for_event` is the only place subscription is decided (the dispatcher still calls it unconditionally), and add a pydantic validator on `EndpointIn.event_types` rejecting any value not in that set with a 422 naming the unknown type and listing the accepted ones. Red-prove each separately: restoring the dispatcher gate must redden the empty-`event_types` test; inverting the membership condition in `enqueue_for_event` must redden the selective test; removing the validator must redden the 422 test. Do not fix by widening the dispatcher's set and leaving both gates — that leaves the two semantics in place to drift again. Boundary and tie: an endpoint with `event_types: []` and one with the field absent must behave identically (both "all types"), and adding a new event type to the canonical set must not require touching the dispatcher.

### Major: the enqueue is not in the event's transaction and its failure is swallowed
File: `app/events/dispatcher.py` — `dispatch`
What is wrong: The `Event` row commits when its `session_scope` exits, and `enqueue_for_event` then opens a separate session, so a crash or error between the two leaves an event with no delivery rows — and `except Exception: log.warning` makes that outcome indistinguishable from success to every caller (R9, and a swallowed error at a distance from its cause).
What breaks in production: Every enqueue failure — including the `IntegrityError` the `UNIQUE (event_id)` index guarantees for any org with two endpoints — is a permanent, unretried loss of a customer's `invoice.paid` webhook, visible only as a warning line, and `dispatch` still returns the event id as though everything succeeded.
Fix: Make this a transactional outbox — pass the open session into `enqueue_for_event` and insert the `WebhookDelivery` rows inside the SAME `session_scope` as the `Event` row, so event and deliveries commit or roll back together; drop the `try/except` entirely, since a failure must now roll back the event rather than be logged. Where the caller genuinely must not fail on webhook problems, catch only the narrow exception type and increment a counter metric plus an `error`-level log, never `warning`. Deny/allow pair: pin a test asserting a successful dispatch commits both the event row and one delivery row per subscribed endpoint (the path that must still work), and one asserting that when the delivery insert raises, NO event row is committed either. Red-prove each separately: moving the enqueue back outside the scope must redden the atomicity test; removing the enqueue call must redden the first. Do not fix by re-adding a broad `except Exception` around the combined write — that restores exactly the silent-loss behaviour being removed. Boundary and tie: an event with zero matching endpoints must still commit the event and return its id (zero delivery rows is success, not failure), and that case must be pinned so the atomicity fix does not turn "no subscribers" into an error.

### Major: none of the three new routes is rate limited
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: All three new endpoints are added with no rate limiting of any kind (RS2), and `create_webhook_endpoint` places no cap on how many endpoints an organization may register.
What breaks in production: A single tenant can register thousands of endpoints, each of which multiplies every subsequent event into another outbound HTTP request forever, turning our worker into a traffic amplifier aimed at a third party of the tenant's choosing; `list_deliveries` is equally unthrottled over rows carrying full JSONB payloads.
Fix: Apply the project's existing rate-limit dependency to all three routes (grep for an existing limiter before adding one — if none exists, add a shared dependency rather than three inline implementations, per R1), and add a per-org cap in `create_webhook_endpoint`: count active endpoints for `user.org_id` inside the session and raise `HTTPException(409, detail="endpoint limit reached")` at the limit. Deny/allow pair: pin a test where a caller under the limit still gets 201 and a normal-rate list call still gets 200 (the traffic that must keep working), and tests where the N+1st registration returns 409 and where exceeding the request rate returns 429. Red-prove each separately: removing the limiter dependency must redden only the 429 test; removing the count check must redden only the 409 test. Fail loudly when the check cannot run: if the limiter's backing store is unreachable the request must be rejected with 503, not admitted unlimited. Do not fix by making the routes admin-only — self-service registration is the documented feature. Boundary and tie: state the cap as inclusive (the Nth registration succeeds, the N+1st fails) and count only `active=True` endpoints, so a tenant cannot exhaust the cap with soft-deleted rows.

### Major: `limit` on `list_deliveries` has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: The query parameter is bounded below but not above, so any caller may request an arbitrarily large page of rows that each carry a full JSONB `payload`.
What breaks in production: `GET .../deliveries?limit=100000000` materializes the entire delivery history into worker memory and into a single JSON response, taking the API process down for every tenant.
Fix: `limit: int = Query(50, ge=1, le=200)`, and switch the response to keyset pagination on `(created_at DESC, id DESC)` returning a `next_cursor` so callers who need more still can. Red-prove each separately: removing `le=200` must redden the 422 test; breaking the cursor's tie-break must redden the pagination test. Do not fix by hardcoding the limit and removing the parameter — callers need to request smaller pages. Boundary and tie: 200 is accepted and 201 rejected, and the cursor must carry both `created_at` and `id` because `created_at` alone is not a total order (see the Minor below).

### Major: the signature header and full response bodies are written to logs and to the database
File: `app/webhooks/delivery.py` — `send_once` (`log.info("POST %s headers=%s", endpoint.url, headers)`), `deliver`/`_finish` (`response.text`)
What is wrong: `send_once` logs the entire header dict, which includes `X-Acme-Signature` and `X-Acme-Timestamp`, at INFO on every delivery, and `_finish` persists the customer's unbounded `response.text` into `response_body` verbatim.
What breaks in production: Anyone with log access can replay a captured delivery within the receiver's timestamp window using the logged signature, and a customer endpoint returning a multi-megabyte error page writes that page into every delivery row, bloating the table and surfacing the customer's own error content — potentially containing their secrets — in our `GET .../deliveries` responses if it is ever added to `to_dict`.
Fix: Log only what is diagnosable — `log.info("POST %s event=%s delivery=%s", endpoint.url, delivery.event_type, delivery.id)` — and drop the header dict entirely; truncate the stored body with a named constant, `detail = response.text[:MAX_RESPONSE_BODY_CHARS]` where `MAX_RESPONSE_BODY_CHARS = 2048`, appending a `…truncated` marker so the truncation is visible rather than silent. Deny/allow pair: pin a test asserting a short error body is stored intact and remains diagnosable (what truncation must not destroy) and one asserting a 1 MB body is stored at exactly the cap plus the marker; plus a log-assertion test that no emitted record contains the value of `SIGNATURE_HEADER`. Red-prove each separately: restoring the header log must redden the log-assertion test; removing the slice must redden the 1 MB test; lowering the cap below the short body must redden the intact test. Do not fix by removing the delivery log altogether — the URL, event type and delivery id are what makes a failed delivery traceable. Boundary and tie: a body exactly `MAX_RESPONSE_BODY_CHARS` long is stored without the marker, one character longer gets it.

### Major: `_finish` dereferences a possibly-missing row, and one failure kills the worker
File: `app/webhooks/delivery.py` — `_finish`, `run_worker`
What is wrong: `_finish` does `row = session.get(...)` and immediately assigns `row.status` without a None check, and `run_worker` calls `asyncio.gather(...)` without `return_exceptions=True` inside a `while True` whose only handler is a `finally` that releases the lock.
What breaks in production: A delivery whose endpoint was deleted (the migration cascades `webhook_endpoints` → `webhook_deliveries`) makes `_finish` raise `AttributeError`, `gather` propagates it out of the loop, and the worker process exits — every pending delivery for every tenant stops until someone notices the process is gone.
Fix: In `_finish`, guard `if row is None: log.warning("delivery %s vanished before finish", delivery_id); return`. In `run_worker`, pass `return_exceptions=True` to `gather` and iterate the results, logging each `Exception` at error level with the delivery id and incrementing a failure counter, so one bad delivery cannot end the loop; wrap the batch body in `try/except Exception` that logs and continues rather than exits. Deny/allow pair: pin a test asserting a batch of three deliveries where the middle one raises still results in the other two being marked `delivered` (the progress that must survive) and one asserting the raised error is logged at error level with the delivery id. Red-prove each separately: removing `return_exceptions=True` must redden the first; removing the error log must redden the second. Fail loudly when the check cannot run: swallowing the exception silently is not acceptable — the counter and the error log are what distinguish "delivered nothing" from "had nothing to deliver". Do not fix by wrapping `deliver` in a bare `except: pass`, which would hide the very failures this reports. Boundary and tie: a batch where ALL deliveries raise must still release the lock, sleep `poll_interval`, and continue — not spin hot — so the `if not batch` sleep must also run on the all-failed path.
