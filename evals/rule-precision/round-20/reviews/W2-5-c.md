### Critical: the HMAC is computed over a different byte string than the one actually transmitted
File: `app/webhooks/delivery.py` — `send_once`, in combination with `app/webhooks/signing.py:sign`/`serialize`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` while `send_once` sends the body via `client.post(..., json=delivery.payload)`, so httpx re-serializes the dict with its own key order and separators and the receiver — which per `docs/webhooks.md` MACs the raw request body — computes a different digest.

### Critical: the timestamp is not covered by the HMAC, so the documented replay window is not a control
File: `app/webhooks/signing.py` — `sign`, `verify`
What is wrong: `sign` mints a fresh `timestamp` but MACs only the payload, and `verify` throws its recomputed timestamp away (`_, expected = sign(...)`) and never checks the header's age, so an attacker replaying a captured request simply rewrites `X-Acme-Timestamp` to now and the signature still validates — while `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that the five-minute window "is what stops a captured request from being replayed".
What breaks in production: a captured `invoice.paid` request can be replayed indefinitely against every customer that implemented the documented verification, and integrators skipped their own anti-replay measures because our doc declared this one an enforceable boundary (R49: the overstated control is relied on elsewhere).
Fix: change the signed string to `f"{timestamp}.".encode() + body` in `sign`, and give `verify` the signature `verify(secret, timestamp: str, body: bytes, signature: str, *, max_age_seconds: int = 300) -> bool` so it recomputes with the caller-supplied timestamp instead of a new one and rejects when `abs(now - int(timestamp)) > max_age_seconds`. Deny side: a request replayed at `now + 301s`, and a request whose timestamp header is altered without re-signing, must both return False. Allow side that must still succeed and be pinned: a freshly signed request verifies True, and one signed 299 seconds ago still verifies True — clock skew in the customer's favour must not be traded away. Red-prove each clause separately by execution: (i) delete the `f"{timestamp}."` prefix → the tampered-timestamp test reds; (ii) delete the age check → the 301s test reds; (iii) widen `max_age_seconds` to 0 → the 299s allow test reds, proving that test is not vacuous. Fail loudly: a timestamp that is absent, empty, or not parseable as an integer must return False through an explicit branch, never through an uncaught `ValueError` and never through the "no timestamp supplied → skip the age check" path. Do not fix by deleting what made the defect visible or the feature useful: keep `verify` public and keep it exercised by `test_verify_accepts_signature_produced_by_sign`, updated for the new signature, rather than dropping the function. Boundary and tie: state that exactly `max_age_seconds` old is accepted and `max_age_seconds + 1` is rejected, and that two requests sharing one timestamp second are both independently valid (the timestamp is not an idempotency key).

### Critical: signature comparison is not constant-time (RS1)

What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte and therefore leaks the correct digest prefix through response timing.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice`, i.e. the Mersenne Twister, whose internal state is fully recoverable from roughly 624 observed outputs and which is seeded per process.

Red-prove each clause separately by execution: (i) revert to `random.choice` → the no-`random` test reds; (ii) drop the `SECRET_PREFIX` concatenation → the prefix assertion reds; (iii) shorten the length by one → the length assertion reds. Fail loudly: on any platform where `secrets` cannot source entropy the call must propagate the `OSError` rather than degrading to `random`. Do not fix by deleting what made the defect useful: keep the human-readable `whsec_` prefix, which is what lets customers and log scanners recognize the value. Boundary and tie: state that the entropy floor is the alphabet size to the power of `SECRET_CHARS` (62^32, ~190 bits) and that two independently generated secrets colliding is the tie case the uniqueness assertion covers.

### Critical: SSRF — plaintext and internal-network URLs are accepted and redirects are followed

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop

### Major: `in_flight` is a non-terminal state with no timeout and no reset path (R38)

What breaks in production: after the first worker restart, an ever-growing set of paid events is silently never delivered and never reported as failed, and the deliveries endpoint shows them as perpetually in progress.
Fix: add a bounded reclaim — record `claimed_at` (or reuse `updated_at`) when flipping to `in_flight`, and have `_claim_batch` also select `status == 'in_flight' AND updated_at < now() - interval '5 minutes'`, treating the reclaim as an ordinary attempt so `MAX_ATTEMPTS` still bounds it; wrap the `run_worker` loop body in `except Exception` that logs and continues, and use `asyncio.gather(..., return_exceptions=True)` so one delivery's failure cannot cancel its siblings. Deny side: a test that a row left `in_flight` with an old `updated_at` is re-claimed on the next poll, and that one raising `deliver` no longer prevents the others from finishing. Allow side that must still succeed and be pinned: a row currently `in_flight` and freshly claimed (updated seconds ago) must NOT be re-claimed — the reclaim must not become a duplicate-delivery generator. Red-prove each clause separately by execution: (i) remove the staleness predicate → the fresh-row test reds with a duplicate claim; (ii) remove the `updated_at` write → the reclaim test reds; (iii) revert to `gather` without `return_exceptions` → the sibling-completion test reds. Fail loudly: a row reclaimed more than `MAX_ATTEMPTS` times must be marked `failed_permanent` with a reason naming the reclaim, never reclaimed forever. Do not fix by deleting what made the defect visible: keep `in_flight` as a distinct state; collapsing it into `pending` removes the only signal that a worker took the row. Boundary and tie: state that a row whose `updated_at` is exactly at the staleness threshold is not reclaimed (strict `<`), and that two workers reclaiming the same stale row is prevented by the row-level claim, not by the timestamp.

### Major: the dispatch lock is not atomic in either direction
File: `app/webhooks/delivery.py` — `_acquire_lock`, and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does a read-then-write (`get` then `set`), so two workers can both observe an empty key and both proceed; the `set` and `expire` are separate commands, so a crash between them leaves a key with no TTL; and the unconditional `delete` in `finally` removes whatever value is present, including a lock another worker acquired after this one's TTL expired.
What breaks in production: two workers claim overlapping batches and customers receive duplicate deliveries, or — in the crash-between-set-and-expire case — the TTL-less key stops all webhook delivery for every tenant permanently, since nothing in this change ever clears a lock it did not just set.
Fix: make acquisition one atomic command with a fencing token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock; because the lock is advisory and can still expire mid-batch, keep the DB-side claim (`_claim_batch`'s status flip) as the real mutual exclusion and add `WITH FOR UPDATE SKIP LOCKED` to it. Deny side: a test where a second `_acquire_lock` while the first holds the key returns False, and a test where releasing with the wrong token leaves the key intact. Allow side that must still succeed and be pinned: after the holder releases, the next `_acquire_lock` succeeds, and after the 60s TTL a stuck lock is acquirable — recovery must not be traded away for exclusivity. Red-prove each clause separately by execution: (i) drop `nx=True` → the second-acquire test reds; (ii) replace the compare-and-delete with a plain `delete` → the wrong-token test reds; (iii) drop `ex=60` → the TTL-recovery test reds. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise or return False with an error log, never return True — an unavailable coordinator must not read as "no one holds the lock". Do not fix by deleting what made the feature useful: the 60-second TTL must stay; making the lock permanent-until-released is what produces the wedge. Boundary and tie: state that a lock at exactly its TTL boundary is treated as expired and that the DB-level `SKIP LOCKED` claim, not the Redis key, is what makes a lost lock safe.

### Major: naive and aware datetimes are mixed, and the migration's column types contradict the models
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); `migrations/0042_webhook_delivery.sql` — all `TIMESTAMP` columns
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` while `_claim_batch` compares against an aware `datetime.now(timezone.utc)` and `models._now()` is aware, and the migration declares `TIMESTAMP` (without time zone) for every column the models declare as `DateTime(timezone=True)`. Codebase awareness: this change already added `models._now()` as the aware timestamp helper, and `enqueue_for_event` and `_finish` both reimplement it inline instead of calling it (R1).
What breaks in production: on any server whose session `TimeZone` is not UTC the stored `next_attempt_at` is off by the UTC offset, so deliveries fire hours early or hours late, and `WebhookDelivery.to_dict()` returns an `isoformat()` string with no offset that customers will read as local time.
Fix: change the migration's five timestamp columns to `TIMESTAMPTZ` (matching `DateTime(timezone=True)`) and replace both inline timestamp expressions with the existing `m._now()` helper, exporting it as `now()` from `app/webhooks/models.py` so there is exactly one clock in this package. Cross-cutting verification: `_finish` (`datetime.now(timezone.utc)`) and `enqueue_for_event` (`datetime.utcnow()`) are the two sites; the model column defaults already use `_now` and need no change. Deny side: a test asserting `enqueue_for_event`'s stored `next_attempt_at.tzinfo is not None`, run with `TZ=America/New_York`. Allow side that must still succeed and be pinned: `_claim_batch` still claims a row whose `next_attempt_at` is in the past under a non-UTC server timezone — the fix must not make rows uncllaimable by tightening comparison. Red-prove each clause separately by execution: (i) revert to `utcnow()` → the tzinfo test reds; (ii) revert the column to `TIMESTAMP` → a round-trip test asserting the offset survives reds; (iii) run the claim test under a non-UTC `TZ` with the old code → it reds on an off-by-offset boundary. Fail loudly: a naive datetime reaching `_claim_batch`'s comparison must raise rather than be silently coerced. Do not fix by deleting what made the defect visible: keep the `<=` comparison against a real clock rather than switching to a DB-side `now()` that hides the mismatch. Boundary and tie: state that a row whose `next_attempt_at` equals the comparison instant is claimed, and that rows sharing an instant have no defined relative order.

### Major: webhook enqueue is outside the event transaction and its failures are swallowed
File: `app/events/dispatcher.py` — the `try/except Exception: log.warning(...)` block around `webhook_delivery.enqueue_for_event`
What is wrong: the event row is committed by its own `session_scope()` before `enqueue_for_event` opens a second, independent transaction, and every failure of that second transaction — including the unique-index violation described above — is downgraded to a warning, so there is no atomicity between "the event happened" and "we will tell the customer" and no record that the telling was lost.
What breaks in production: a process death, a DB blip, or any constraint violation between the two commits permanently loses the webhook for that event with no row to retry from, which contradicts `docs/webhooks.md`'s "delivery is at-least-once".
Fix: make enqueue part of the same transaction as the event insert — move the `WebhookDelivery` rows into the `with session_scope()` block that writes the `Event` row (an outbox), passing the open session into `enqueue_for_event(session, ...)`, and delete the `except Exception` so an enqueue failure rolls the event back and surfaces to the caller. Deny side: a test where `enqueue_for_event` raises and the `Event` row is asserted absent afterwards. Allow side that must still succeed and be pinned: an event whose type is in `WEBHOOK_EVENT_TYPES` but whose org has zero active endpoints must still commit the `Event` row and return its id — zero matching endpoints is a success, not a failure, and must not be collapsed into the error path. Red-prove each clause separately by execution: (i) re-add the `except Exception` → the rollback test reds; (ii) keep the separate `session_scope` → the same test reds for the transaction-boundary reason; (iii) make zero-endpoint enqueue raise → the allow test reds. Fail loudly: an enqueue failure must propagate a named exception, never a `log.warning` — "we could not enqueue" must not be spelled the same as "there was nothing to enqueue". Do not fix by deleting what made the feature useful: `dispatch` must still return `event_id` and must still notify in-process `SUBSCRIBERS`; those calls stay outside the transaction. Boundary and tie: state that the in-process subscriber loop runs after the commit and that a subscriber raising does not undo the committed event — the two failure domains must be explicitly separated, not both folded into one `try`.

### Major: the dispatcher's hardcoded event-type set contradicts the documented "every event type" subscription, and endpoint `event_types` are never validated
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/api/routes/settings.py` — `EndpointIn.event_types`
What is wrong: `docs/webhooks.md` says an empty `event_types` "subscribes the endpoint to every event type we emit", but `dispatch` only calls `enqueue_for_event` for three hardcoded types, and `EndpointIn` accepts any `list[str]` without checking membership in that set — so a customer who registers `["invoice.refunded"]` or relies on the empty-list default receives nothing and gets no error (R12: the action group and its registry are not cross-checked; RS3: a new request parameter validated nowhere).
What breaks in production: customers silently miss events they believe they subscribed to, and every event type added later is silently non-delivering until someone remembers to edit this set in a second file.
Fix: move the emitted-type registry into `app/webhooks/models.py` as `WEBHOOK_EVENT_TYPES`, import it in both `dispatcher.py` and `settings.py`, and add a pydantic validator on `EndpointIn.event_types` rejecting any member not in it with 422 listing the unknown values; correct `docs/webhooks.md` to say an empty list subscribes to every type in that registry and link the registry. Deny side: a test that `POST /webhook-endpoints` with `["invoice.refunded"]` returns 422 naming the unknown type. Allow side that must still succeed and be pinned: an empty `event_types` still registers and still receives all three current types, and `["invoice.paid"]` still registers — the validator must not reject the documented empty-list default. Red-prove each clause separately by execution: (i) delete the validator → the unknown-type test reds; (ii) delete a member from the registry → a test asserting an endpoint subscribed to it still receives reds; (iii) make the validator reject the empty list → the empty-list allow test reds. Fail loudly: an event type dispatched but absent from the registry must log an error at dispatch time rather than being silently skipped. Do not fix by deleting what made the feature useful: the empty-list "subscribe to everything" behaviour must be preserved. Boundary and tie: state that an endpoint whose `event_types` lists a type twice is not an error, and that adding a type to the registry retroactively enables it for every empty-list endpoint — which is the intended tie and should be documented as such.

### Major: three new public routes with no rate limiting and no per-organization endpoint cap (RS2)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: none of the three new routes carries a rate-limit dependency, and `create_webhook_endpoint` imposes no cap on how many endpoints an organization may register.
What breaks in production: a single tenant can register thousands of endpoints, and because `enqueue_for_event` fans one event out to every active endpoint, each event then costs thousands of outbound POSTs — turning our worker into a DDoS amplifier aimed at a target of the tenant's choosing, and saturating the shared delivery batch so other tenants' events never get claimed.
Fix: attach the existing per-route rate-limit dependency used elsewhere in this API to all three routes (I could not see one in the diff — if the codebase has none, add a per-org token bucket keyed on `user.org_id`), and add an explicit `MAX_ENDPOINTS_PER_ORG` check in `create_webhook_endpoint` that counts the org's active endpoints inside the same session and returns 429 when exceeded. Deny side: a test that the `MAX_ENDPOINTS_PER_ORG + 1`-th create returns 429 and asserts no new row was written — the row count, not just the status (RT8: the denial must be asserted at the mutation, not only at the response). Allow side that must still succeed and be pinned: the `MAX_ENDPOINTS_PER_ORG`-th create still succeeds with 201 and writes its row, and one org hitting its cap does not affect another org's create. Red-prove each clause separately by execution: (i) remove the count check → the 429 test reds; (ii) assert only the status and not the row count, then break the rollback → the test must red, proving the mutation assertion is load-bearing; (iii) set the cap to `N-1` → the allow test reds. Fail loudly: if the count query fails, the create must be refused, not allowed through — an unavailable counter must not read as "under the cap". Do not fix by deleting what made the feature useful: legitimate multi-endpoint fan-out must remain possible; the cap is a bound, not a prohibition. Boundary and tie: state that exactly `MAX_ENDPOINTS_PER_ORG` is allowed and `+1` refused, and that inactive endpoints do or do not count toward it — pick one and pin it.

### Major: the `limit` query parameter has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: `ge=1` bounds the parameter from below but nothing bounds it from above, so a caller can request `?limit=100000000` and drive an unbounded ordered scan over `webhook_deliveries` (RS3: a new request parameter constrained on only one side).
What breaks in production: a single request materializes millions of rows with their JSONB payloads into memory and serializes them, exhausting the worker and the DB connection for every other tenant sharing it.
Fix: change to `Query(50, ge=1, le=200)` so FastAPI rejects out-of-range values at the schema layer with 422 before the handler runs, and back it with the composite index named in the Minor finding below so the bounded query is also cheap. Deny side: a test that `?limit=201` returns 422 and that the handler body never executes (assert no query was issued, e.g. via a spy on the session). Allow side that must still succeed and be pinned: `?limit=200` still returns 200 with up to 200 rows, and omitting the parameter still defaults to 50. Red-prove each clause separately by execution: (i) remove `le=200` → the 422 test reds; (ii) change the default to something other than 50 → the default test reds; (iii) change `le` to `199` → the `limit=200` allow test reds, proving the boundary case is pinned. Fail loudly: a non-integer `limit` must 422 at the schema layer rather than reaching the handler. Do not fix by deleting what made the feature useful: keep `limit` caller-controllable rather than hardcoding 50. Boundary and tie: `limit=200` is accepted and `limit=201` is refused; where more than `limit` rows share the ordering timestamp, the page cut is arbitrary among them (see the R57 Minor below).

### Major: the retry policy contradicts the documented one in two ways
File: `app/webhooks/delivery.py` — `deliver` retry loop, `backoff_for`; `docs/webhooks.md` — "Retries"
What is wrong: the docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", while `deliver` retries every non-2xx response — including 400, 404, 410 and 422 — for the full five attempts, and `backoff_for` returns a fixed `2**attempt` with no jitter at all (R49: a claim stronger than the implementation, on a control customers reason about).
What breaks in production: a customer who deletes their endpoint gets hammered five times per event with no benefit, and because every delivery in a 100-row batch fails and retries on the identical unjittered schedule, all retries land in the same instant — a synchronized thundering herd against whichever endpoint just recovered.
Fix: branch on the status class in `deliver` — `if 400 <= response.status_code < 500 and response.status_code not in (408, 429): _finish(..., "failed_permanent", ...); return` — and add jitter to `backoff_for` as full jitter over the computed interval (`timedelta(seconds=random.uniform(0, BASE_DELAY_SECONDS**attempt))` using the stdlib `random`, which is correct here because this value is not a secret, unlike `new_signing_secret`). Deny side: a test that a 404 response marks the delivery `failed_permanent` with `attempts == 1`, and a test that 100 rows failing together produce distinct `next_attempt_at` values. Allow side that must still succeed and be pinned: a 500 and a `httpx.ConnectError` are both still retried to the full `MAX_ATTEMPTS`, and 429 and 408 are still retried — the tightening must not turn a transient throttle into a permanent failure. Red-prove each clause separately by execution: (i) remove the 4xx branch → the 404 test reds; (ii) remove the 429/408 carve-out → the throttle allow test reds; (iii) remove the jitter → the distinct-timestamps test reds. Fail loudly: a status code outside 100–599 (a malformed response) must be treated as a retryable transport error with a named log line, not fall through the 2xx/4xx/else chain silently. Do not fix by deleting what made the defect visible: `test_backoff_grows_exponentially` must be rewritten to assert the jittered interval's bounds (`0 < delay <= 2**attempt`) rather than deleted, since it is the only test pinning the schedule. Boundary and tie: state that exactly 400 is permanent and exactly 399 and 500 are retryable, and that a jittered delay of exactly 0 is permitted and simply means "retry on the next poll".

### Major: the full signed request headers and the customer's full response body are written to the logs
File: `app/webhooks/delivery.py` — `log.info("POST %s headers=%s", endpoint.url, headers)` in `send_once`, and `log.warning("delivery %s failed (%s), retrying in %ss", delivery.id, detail, delay)` in `deliver`
What is wrong: the first line logs the complete header dict including `X-Acme-Signature`, and the second logs `detail`, which for a non-2xx is `f"HTTP {code}: {response.text}"` — the entire untrusted response body from a customer-controlled host.
What breaks in production: valid per-request signatures land in the log pipeline where anyone with log access can replay them against the customer (compounded by the missing timestamp binding above), and an endpoint returning a multi-megabyte or newline-laden body floods and forges entries in the shared log index.
Fix: log the endpoint id rather than the URL and log only the header names, never their values (`headers=%s`, `sorted(headers)`), and truncate `detail` to a bounded prefix — `detail = f"HTTP {response.status_code}: {response.text[:512]}"` — with the truncation applied once at the point the string is built so both the log line and the `response_body` column inherit it. Cross-cutting verification: `_finish` writes that same unbounded `detail` into `webhook_deliveries.response_body`, so the same truncation must be applied there and is covered by building it once. Deny side: a test asserting the signature value does not appear in captured log output, and a test that a 10 KB response body yields a stored `response_body` of at most 512 characters. Allow side that must still succeed and be pinned: the log line must still identify which delivery and which endpoint failed and with what status, and `response_body` must still contain the beginning of the customer's error message — the truncation must not be a wholesale deletion of the diagnostic. Red-prove each clause separately by execution: (i) restore the full header dict → the signature-absent test reds; (ii) remove the `[:512]` slice → the stored-length test reds; (iii) remove the delivery id from the log line → the identification test reds. Fail loudly: if `response.text` cannot be decoded, log a named "undecodable body" marker rather than an empty string, so an unreadable response is not spelled the same as an empty one. Do not fix by deleting what made the feature useful: keep a per-attempt log line and keep `response_body` populated. Boundary and tie: state that a body of exactly 512 characters is stored whole and 513 is truncated, and that truncation is applied to the stored value and the logged value from the same expression so the two can never disagree.
