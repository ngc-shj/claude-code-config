### Critical: the signature is computed over different bytes than the ones sent on the wire
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` while the request body is produced independently by httpx from `json=delivery.payload` (unsorted keys, httpx's own separators), and the documented signing input `"{timestamp}.{raw_request_body}"` includes a timestamp the code never feeds into the MAC, so the signed string and the transmitted body are two different byte strings.
What breaks in production: every receiver that follows `docs/webhooks.md` and verifies the HMAC over the raw body it received rejects 100% of deliveries, which the sender records as HTTP 401/403 and retries five times per event — a silent total-path failure that also burns the customer's rate limits.
Fix: serialize exactly once and sign the bytes you send — change `sign(secret, body: bytes) -> tuple[str, str]` to compute `mac = hmac.new(secret.encode(), f"{ts}.".encode() + body, hashlib.sha256)`, and change `send_once` to `body = serialize(delivery.payload).encode(); ts, signature = sign(endpoint.signing_secret, body); return await client.post(endpoint.url, content=body, headers=...)` so no second serializer exists. Pin the allow side: a test using `httpx.MockTransport` must take `request.content` verbatim, recompute `hmac(secret, f"{ts}.".encode() + request.content)` with an independently written expression (not by calling `sign`), and assert it equals the `X-Acme-Signature` value — that case must stay green. Red-prove the three clauses separately by execution: (i) drop `sort_keys=True` from `serialize` and observe the byte-equality assertion red; (ii) delete the `f"{ts}."` prefix and observe the doc-derived verifier assertion red; (iii) flip one byte of the payload before posting and observe the recomputed-MAC assertion red. Fail loudly where the check cannot run: if `serialize` raises `TypeError` on a non-JSON-serializable payload, `_finish` the row `failed_permanent` with the encoder message rather than letting the `asyncio.gather` task die unrecorded — "could not encode" must not be spelled like "delivered". Preserve what makes the feature work: keep `Content-Type: application/json` and the sorted-key body so existing JSON parsers on the receiving side are unaffected; do not "fix" this by deleting the sorted-key serialization. Boundary and tie: the timestamp is unix seconds, receivers accept when `now - ts <= 300` (300 exactly accepted), and because `ts` is signed material and not a uniqueness key, two deliveries produced in the same second must both verify.

### Critical: `verify()` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`
What is wrong: the shipped verification helper compares the expected and supplied signature with `expected == signature`, a byte-at-a-time short-circuiting comparison, instead of `hmac.compare_digest` (RS1).
What breaks in production: `verify` is the function this codebase itself will use for any inbound signature check and the one customers copy from, so an attacker with request-timing access can recover a valid signature byte by byte and forge webhook payloads.
Fix: replace the comparison with `return hmac.compare_digest(expected, signature)` and change the signature to `verify(secret, body: bytes, timestamp: str, signature: str) -> bool` so it verifies the same material `sign` now produces. Pair the deny side with the allow side: keep `test_verify_accepts_signature_produced_by_sign` green (a genuine signature must still authenticate) alongside `test_verify_rejects_a_signature_made_with_another_secret`. Red-prove each clause by execution: (i) mutate `compare_digest` back to `==` and assert with a static-check test (`ast` scan of `signing.py`, or `check-timing-safe.sh`) that reds on the equality operator; (ii) mutate one hex character of the signature and observe the reject test red; (iii) pass a `str` where `bytes` is expected and observe the type error surface rather than a silent `False`. Fail loudly: `compare_digest` raises `TypeError` on mixed str/bytes — let that propagate at the boundary instead of wrapping it in `except Exception: return False`, because "could not compare" must not be spelled the same as "signature invalid". Do not remove the existing accept/reject tests to make the new signature fit; update their call sites. Boundary and tie: inputs of unequal length must return `False` without raising, and two distinct secrets that happen to produce the same digest for a payload (collision) are outside the guarantee — state that in the docstring.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice`, the Mersenne Twister PRNG, which is not cryptographically secure and whose 19937-bit state is recoverable from enough observed output (R1 — the stdlib `secrets` module is the existing shared primitive for exactly this, and it is a security control, so Critical).
What breaks in production: an attacker who registers a handful of their own endpoints and observes their secrets can reconstruct the generator state and predict every other tenant's signing secret, letting them forge signed webhooks that those tenants' systems accept as authentic billing events.
Fix: `import secrets` and return `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, deleting the `random`/`string`/`_ALPHABET` code outright rather than leaving it as a wrapper (R1(d)); note the behaviour change at the call site (R1(b)) — the secret body becomes ~43 characters of base64url for `SECRET_BYTES = 32`, so the existing length assertion must be rewritten to `len(secret) == len(SECRET_PREFIX) + len(secrets.token_urlsafe(SECRET_BYTES))` or to a documented minimum-entropy bound, and `SECRET_BYTES` now means bytes of entropy rather than characters. Pair with the allow side: `new_signing_secret()` must still return a value that `create_webhook_endpoint` stores and that `sign`/`verify` round-trip, and the prefix assertion must stay green. Red-prove each clause by execution: (i) replace the body with a constant string and observe a new "1000 draws yield 1000 distinct values" test red — the current length-only test does not red on a constant secret; (ii) shorten `SECRET_BYTES` to 4 and observe a minimum-length assertion red; (iii) drop the prefix and observe the prefix test red. Fail loudly: `secrets` is stdlib and cannot be absent, but if a future config supplies `SECRET_BYTES` from the environment, reject a value below 16 at import with a named exception rather than silently generating a short secret. Boundary and tie: a secret of exactly the minimum length is accepted; two endpoints must never share a secret, so assert distinctness across draws rather than merely non-emptiness.

### Critical: the list endpoint hands the signing secret back to any reader
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns it for every endpoint in the org, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards") (RS4; R49 — the doc claims a confidentiality boundary the implementation does not have).
What breaks in production: any credential that can call the read-only settings list — a lower-privileged member, a leaked read-scoped API key, a browser extension reading the settings page — exfiltrates every signing secret in the organization and can then forge webhooks that downstream systems treat as authentic.
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` so the secret is emitted at exactly one call site; add a rotate route if read-back was the actual requirement, rather than restoring the field. Pair deny with allow: assert that `POST /v1/settings/webhook-endpoints` still returns a `signing_secret` the caller can use to verify a delivery (the creation flow must not be broken by the tightening) while `GET /v1/settings/webhook-endpoints` returns a body in which the substring `whsec_` does not appear. Red-prove each clause separately: (i) re-add the key to `to_dict` and observe the GET-response test red; (ii) delete the explicit merge in the POST handler and observe the create-response test red; (iii) add a second serializer path (e.g. a new admin list route reusing `to_dict`) and observe a repo-wide "no route returns `signing_secret` except create" test red. Fail loudly: if `to_dict` is ever called on an instance whose `signing_secret` is unset, that is a data defect — raise rather than emitting `None`, so "no secret stored" is not spelled like "secret withheld". Do not fix by dropping the deliveries/list feature; both routes must keep returning `id`, `url`, `event_types`, `active`. Boundary and tie: the secret appears in exactly one response, the 201 for the creating request; a repeated `POST` with the same URL creates a second endpoint with its own secret rather than re-revealing the first.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on the path parameter `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while its two sibling routes in the same file (`list_api_keys`, `list_webhook_endpoints`) both filter by `user.org_id` (R3 — incomplete propagation of the tenancy predicate, security-relevant).
What breaks in production: any authenticated user can enumerate integer endpoint ids and read another tenant's delivery history — event ids, event types, delivery status and the response statuses of their private endpoints — a cross-tenant data leak that leaves no trace distinguishable from normal use.
Fix: join the parent row and scope it, e.g. `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and return `404` (not `403`) when the join yields nothing so ids are not oracle-testable. Pair deny with allow: pin both a test where the owning org's user still receives their deliveries in `next_attempt_at`/`created_at` order, and a test where a second org's user receives `404` with an empty body — a fix that always 404s satisfies everything else. Red-prove the clauses separately by execution: (i) delete the `org_id` filter and observe the cross-tenant test red; (ii) delete the `endpoint_id` filter and observe an "only this endpoint's rows" assertion red; (iii) change the deny status to `403` and observe the enumeration-oracle assertion red. Fail loudly: if `user.org_id` is `None` (an unauthenticated or partially-hydrated principal), raise `HTTPException(401)` explicitly rather than letting the filter compare against `NULL` and return an empty list that reads like "no deliveries". Do not fix by removing the route or by dropping the `limit`/ordering behaviour. Boundary and tie: an endpoint owned by the caller with zero deliveries returns `200 []` while an endpoint owned by another org returns `404` — the two must not be spelled the same.

### Critical: any URL is accepted and fetched from inside the network, with redirects followed (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`), `send_once`
What is wrong: the only check on a customer-supplied destination is `parsed.scheme.startswith("http") and parsed.netloc`, so `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:6379/`, or any RFC1918 address is registered and then POSTed to by the worker, with `follow_redirects=True` letting an initially-public host redirect into the same space (RS3 — an unvalidated externally-supplied value reaching a request-issuing sink).
What breaks in production: a customer turns the delivery worker into a confused deputy that reaches cloud metadata and internal admin services from a trusted network position, and the response text is persisted by `_finish` into `response_body`, making it a readable exfiltration channel.
Fix: validate at the schema boundary with a pydantic `HttpUrl`-typed field plus an explicit destination policy — require `scheme == "https"` by exact comparison, resolve the hostname at registration and at each attempt, and reject when any resolved address is in a loopback/link-local/private/reserved range (`ipaddress.ip_address(addr).is_private or .is_loopback or .is_link_local or .is_reserved`); set `follow_redirects=False` and treat a 3xx as a permanent failure. Pair deny with allow: pin that `https://hooks.example.com/acme` (public address) still registers and still delivers, alongside denials for `http://`, `https://127.0.0.1/`, `https://169.254.169.254/`, and a public host that 302s to `http://127.0.0.1/`. Red-prove each clause by execution: (i) remove the private-range check and observe the metadata-address test red; (ii) set `follow_redirects=True` and observe the redirect test red; (iii) relax the scheme check back to `startswith` and observe the `http://` denial red. Fail loudly: when DNS resolution fails or times out, deny the registration and fail the attempt with a named `dns_unresolvable` detail — an unresolvable host must not be spelled the same as an allowed one. Do not close this by removing `response_body` capture, which is what makes deliveries debuggable; bound it instead (see the response-body finding). Boundary and tie: an address exactly at a private range's first or last host is denied, and a hostname resolving to both a public and a private address is denied — any private answer decides.

### Critical: the migration's status CHECK constraint does not include the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `webhook_deliveries.status CHECK`; `app/webhooks/delivery.py` — `_finish(..., "failed_permanent", ...)`
What is wrong: the constraint allows `('pending', 'in_flight', 'delivered', 'failed')` while both `app/webhooks/models.py::STATUSES` and `_finish` use `failed_permanent` (R18/R2 — the status vocabulary is written three times and the three copies disagree).
What breaks in production: the first delivery to exhaust its attempts raises a `CheckViolation` on `_finish`, so the row is never moved out of `in_flight`, the worker task dies inside `asyncio.gather`, and the delivery is retried by no one and reported to no one.
Fix: change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and make `STATUSES` in `models.py` the single source — build the constraint text and the column default from it, and replace the string literals in `delivery.py` with `m.STATUS_DELIVERED` / `m.STATUS_FAILED_PERMANENT` / `m.STATUS_PENDING` / `m.STATUS_IN_FLIGHT` so a fourth copy cannot appear. Pair deny with allow: pin an integration test (real database, not a mock) that writes each member of `STATUSES` successfully and that a write of `'bogus'` raises `IntegrityError`. Red-prove the clauses separately: (i) remove `failed_permanent` from the constraint and observe the permanent-failure write test red; (ii) remove it from `STATUSES` and observe a "every literal used by `delivery.py` is in `STATUSES`" test red; (iii) add `'failed'` back to the code and observe the constraint test red. Fail loudly: if the deployed constraint text and `STATUSES` disagree, a startup assertion querying `pg_constraint` should refuse to boot the worker rather than letting the mismatch surface one attempt at a time. Do not fix by widening the constraint to accept any text — the enumeration is what makes the drift visible. Boundary and tie: `delivered` and `failed_permanent` are the only terminal values; a row already terminal must not be transitioned again, so `_finish` should be a conditional update keyed on `status IN ('pending','in_flight')`.

### Critical: the unique index on `event_id` alone makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`
What is wrong: `CREATE UNIQUE INDEX ... ON webhook_deliveries (event_id)` permits only one delivery row per event, but `enqueue_for_event` inserts one row per active matching endpoint of the org (R40 — the storage contract contradicts the producer's shape).
What breaks in production: any org with two or more active endpoints subscribed to the same event triggers an `IntegrityError` on `session.add_all`, which the dispatcher's blanket `except Exception` downgrades to a `log.warning`, so the whole org silently receives no webhooks at all for that event — including the first endpoint, whose row is rolled back with the batch.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which still gives the per-endpoint idempotency the docs promise ("deduplicate on `event_id`"), and make `enqueue_for_event` use an `ON CONFLICT DO NOTHING` insert so a retried dispatch is a no-op instead of an error. Pair deny with allow: pin that one event with three active endpoints creates exactly three rows (allow side), and that calling `enqueue_for_event` twice for the same `(endpoint_id, event_id)` still leaves three rows (deny side). Red-prove each clause: (i) restore the single-column index and observe the three-endpoint test red; (ii) drop the unique index entirely and observe the double-enqueue test red; (iii) remove `ON CONFLICT DO NOTHING` and observe the double-enqueue test red with an `IntegrityError` rather than a count mismatch. Fail loudly: `enqueue_for_event` must stop swallowing failure by returning `len(rows)` computed before the flush — flush inside the block and return the actual inserted count, so "0 endpoints matched" and "insert failed" are distinguishable to the caller. Do not fix by deleting the unique index, which is what makes at-least-once delivery deduplicable. Boundary and tie: an org with zero matching endpoints inserts zero rows and must return `0` rather than raising, and two endpoints of the same org registered to the same URL are two distinct subjects that each get a row.

### Critical: ORM rows are used after their session closes
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`
What is wrong: `_claim_batch` returns the `WebhookDelivery` instances out of its `with session_scope() as session:` block and `deliver` then reads `delivery.payload`, `delivery.id` and `delivery.attempts` (and `endpoint.url` / `endpoint.signing_secret`, fetched the same way) from instances whose session has already exited — every other `session_scope` user in this diff (the three route handlers, `enqueue_for_event`, `_finish`) consumes its rows inside the block (R5).
What breaks in production: with SQLAlchemy's default `expire_on_commit=True` the first attribute access after the commit raises `DetachedInstanceError`, so the worker's first batch dies before a single request is sent, while the rows it just flipped to `in_flight` stay that way forever.
Fix: have `_claim_batch` return plain data, not ORM instances — select the batch, set `status='in_flight'` and `attempts = attempts + 1` in the same transaction with `SELECT ... FOR UPDATE SKIP LOCKED` so concurrent workers cannot claim the same row, and return a frozen dataclass `ClaimedDelivery(id, endpoint_id, url, signing_secret, payload, attempts)` built inside the block by joining the endpoint (which also removes `deliver`'s second `session.get`). Pair deny with allow: pin that a claimed batch delivers end-to-end against `httpx.MockTransport` with no session open (allow side), and that two concurrent `_claim_batch` calls against one pending row return it to exactly one caller (deny side). Red-prove each clause: (i) return the ORM instance instead of the dataclass and observe the "no attribute access after commit" test red; (ii) drop `SKIP LOCKED` and observe the concurrent-claim test red with both callers returning the row; (iii) drop the `attempts` increment and observe the max-attempts test red. Fail loudly: if the join finds no endpoint for a delivery (a race with endpoint deletion), mark that row `failed_permanent` with a named `endpoint_missing` detail instead of letting `endpoint.url` raise `AttributeError` on `None` and killing the gather task. Do not fix by disabling `expire_on_commit` globally — that hides the same class of defect everywhere else in the app. Boundary and tie: a row whose `next_attempt_at` equals `now` exactly is claimable (`<=`), and ties on `next_attempt_at` are broken by `id` so the ordering is total.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker
File: `app/webhooks/delivery.py` — `deliver` (retry loop), and `run_worker`'s `asyncio.gather`
What is wrong: the retry loop calls the blocking `time.sleep(delay)` from inside a coroutine, so it stalls the event loop rather than yielding, while the surrounding design retries in-process instead of using the `next_attempt_at` column that already exists for scheduling.
What breaks in production: one endpoint that times out serializes the entire batch — with `BATCH_SIZE = 100`, `REQUEST_TIMEOUT = 30` and backoff 2+4+8+16, a single bad endpoint blocks all other deliveries for minutes and holds the 60-second dispatch lock far past its TTL, so throughput collapses to roughly one endpoint at a time.
Fix: make `deliver` perform exactly one attempt and persist the outcome — on a retryable failure, write `status='pending'`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next poll pick it up; delete the `while True` loop and the `time.sleep` import. Pair deny with allow: pin that a 200 still marks the row `delivered` on the first attempt (allow side), and that a 500 leaves the row `pending` with `next_attempt_at` advanced and `attempts == 1` (deny side). Red-prove each clause separately by execution: (i) reintroduce `time.sleep` and observe an "a batch of two slow endpoints completes in under `REQUEST_TIMEOUT`" test red under a mock transport that sleeps asynchronously; (ii) omit the `next_attempt_at` update and observe a "retry is not re-claimed before its backoff elapses" test red; (iii) omit the `attempts` write and observe the fifth-attempt-is-permanent test red. Fail loudly: wrap each `deliver` task so an unexpected exception writes `status='pending'` with the error detail rather than being absorbed by `asyncio.gather`, and use `return_exceptions=False` only if the caller logs the failure — a task that vanished must not look like a delivered one. Do not fix by lowering `BATCH_SIZE` or `REQUEST_TIMEOUT`, which hides the blocking rather than removing it. Boundary and tie: attempt number 5 is the last (`attempt >= MAX_ATTEMPTS` is permanent, so `MAX_ATTEMPTS` attempts happen, not `MAX_ATTEMPTS + 1`), and two rows with identical `next_attempt_at` are ordered by `id`.

### Critical: the dispatch lock is not atomic and is released by whoever finishes first
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: acquisition is a `GET` followed by a separate `SET` and a separate `EXPIRE` (a TOCTOU window between the check and the write, and a window where a crash after `SET` leaves a key with no TTL), and release deletes the key by name without proving the deleter still owns it (R51 — the decision is bound to a name, not to the object).
What breaks in production: two workers starting together both see an empty key and both claim the same batch (double-POSTing financial events), a worker whose batch outlives the 60-second TTL deletes the lock a *different* worker has since taken, and a process killed between `SET` and `EXPIRE` leaves a permanent lock that stops all webhook delivery until someone notices and deletes the key by hand.
Fix: acquire with a single atomic command carrying a unique token and a TTL — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock; renew the TTL from a heartbeat task while the batch runs, and make the batch bounded so it cannot outlive a renewable lease. Pair deny with allow: pin that a single worker acquires, runs and releases successfully (allow side), and that a second worker's `_acquire_lock` returns `False` while the first holds it and that the second worker's release is a no-op against the first worker's token (deny side). Red-prove each clause: (i) drop `nx=True` and observe the mutual-exclusion test red; (ii) drop `ex=` and observe a "key has a TTL after acquisition" assertion red; (iii) replace the compare-and-delete with a plain `delete` and observe the foreign-release test red. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise a named error that the worker logs and backs off on, never `return False` silently forever and never `return True` — "cannot determine the lock state" must not be spelled like "someone else holds it" or like "it is free". Do not fix by removing the lock and relying on `SKIP LOCKED` alone; keep both, since the lock also bounds concurrent outbound load. Boundary and tie: a lease at exactly its TTL is treated as expired by Redis, and two workers presenting different tokens for the same key means the loser must abandon its batch rather than finish it.

### Critical: the replay-protection control described in the docs does not exist in the implementation
File: `docs/webhooks.md` — "Verifying the signature"; `app/webhooks/signing.py` — `sign`
What is wrong: the documentation tells integrators that rejecting requests older than five minutes "is what stops a captured request from being replayed", but the timestamp header is not part of the signed material, so an attacker replaying a captured request simply rewrites `X-Acme-Timestamp` and the signature still verifies (R49 — a claim stronger than the implementation, relied on elsewhere as the boundary).
What breaks in production: every customer who implements exactly the documented verification believes they have replay protection and has none, so a captured `invoice.paid` can be replayed indefinitely to re-trigger fulfilment or provisioning on their side.
Fix: bind the timestamp into the MAC as part of the same change that fixes the serialization mismatch — sign `f"{timestamp}.".encode() + body` — and restate the docs as the exact string signed, with a worked example (secret, timestamp, body bytes, expected hex) that a reader can reproduce. Pair deny with allow: pin that a request with an unmodified timestamp verifies and is inside the window (allow side), and that flipping a single digit of `X-Acme-Timestamp` makes `verify` return `False` (deny side) — the second assertion is the one that currently cannot fail. Red-prove each clause: (i) remove the timestamp from the signed string and observe the tampered-timestamp test red; (ii) remove the freshness comparison from the documented verifier used in tests and observe a "6-minute-old request rejected" test red; (iii) change the documented window without changing the constant and observe a docs-vs-constant test red. Fail loudly: a request missing either header must be rejected with a distinct "missing signature material" outcome rather than falling through to a comparison against an empty string. Do not fix by deleting the five-minute guidance, which is the useful part; make it true. Boundary and tie: a request at exactly 300 seconds of skew is accepted and 301 is rejected, and clock skew is measured against the receiver's clock, so state that receivers should also reject timestamps more than 300 seconds in the future.

### Critical: the only test of the signing path cannot fail when the signature is wrong
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: the test asserts that the signature header merely *starts with* `sha256=` and that the timestamp *is digits*, never recomputing the MAC over `captured["body"]`, so it passes for any signature over any bytes — it is exactly the assertion that would have caught the serialization mismatch above, and it cannot (RT5 — the test claims to verify a security primitive while asserting only its shape).
What breaks in production: the suite reports the signing path as covered while every delivery leaves with a signature no receiver can verify, so the defect ships green.
Fix: extend the test to recompute the expected digest from the captured bytes with an independently written expression — `expected = hmac.new(SECRET.encode(), captured["headers"][signing.TIMESTAMP_HEADER].encode() + b"." + captured["body"], hashlib.sha256).hexdigest()` — and assert `captured["headers"][signing.SIGNATURE_HEADER] == "sha256=" + expected`; do not call `signing.sign` to build the expectation, since that makes the assertion an identity. Pair deny with allow: keep the 200-response and JSON-body assertions green (a correct delivery must still pass) and add a case asserting the header does *not* match when the endpoint's secret differs. Red-prove each clause separately by execution: (i) change `send_once` to post `json=` instead of the signed bytes and observe the digest assertion red; (ii) change `sign` to omit the timestamp prefix and observe it red for a different reason; (iii) change the secret used in the fixture and observe the mismatch case red. Fail loudly: assert the headers are present before indexing them, so a missing header fails with "signature header absent" rather than a `KeyError` that reads like a test bug. Do not fix by deleting the existing shape assertions; add to them. Boundary and tie: an empty payload `{}` must still produce a verifiable signature, and two deliveries signed in the same second differ in signature because the body differs — assert that rather than assuming timestamp uniqueness.

### Major: `in_flight` has no exit path and no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `_finish`
What is wrong: rows are moved to `in_flight` at claim time and only ever leave it via `_finish` on the success or permanent-failure path, so a worker crash, a redeploy, an unhandled exception inside `asyncio.gather`, or the `CheckViolation` described above strands the row in a transient state that no query ever revisits (R38 — non-terminal transient state with no failure-exit and no timeout).
