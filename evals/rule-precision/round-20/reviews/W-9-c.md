### Critical: the signature is computed over bytes that are never sent, and does not cover the timestamp
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, used by `app/webhooks/delivery.py::send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` while `send_once` puts the body on the wire via `client.post(..., json=delivery.payload)`, which serializes with httpx's own encoder (no `sort_keys`, different separators), and the returned `timestamp` is sent in `X-Acme-Timestamp` but never fed into the MAC — so the digest covers neither the transmitted bytes nor the timestamp, contradicting `docs/webhooks.md` ("HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`").
What breaks in production: every customer who implements the documented verification recomputes over the raw body and gets a mismatch, so either 100% of deliveries are rejected or customers are pushed to skip verification, and because the timestamp is outside the MAC an attacker can rewrite `X-Acme-Timestamp` to defeat the documented five-minute replay window on a captured request forever.
Fix: make the signed bytes the transmitted bytes — build `body = serialize(payload).encode()` once in `send_once`, sign `f"{timestamp}.{body}"` with `hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256)`, and send with `client.post(url, content=body, headers={"Content-Type": "application/json", ...})` so no re-encoding can occur between signing and transmission; pin `serialize` to `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` so the byte string is stable across interpreter and library versions. Preserve the two behaviours the current code gets right and do not drop them in the fix: the `sha256=` prefix and the header names stay as documented (customers key off both). Pin the allow side as well as the deny side: a receiver-side test that takes the *actual* `httpx.Request.content` captured from `send_once` and the *actual* `X-Acme-Timestamp` header, recomputes the HMAC independently of `sign()` (written out longhand in the test, not by calling `sign`), and asserts equality — this must stay green (R40's actual-producer-output-through-actual-consumer round trip). Red-prove each clause separately by execution, one mutation per clause: (i) drop `sort_keys` from `serialize` and run with a payload whose keys are inserted out of order — the round-trip assert must red; (ii) revert to `json=` on the post — must red; (iii) remove the timestamp from the MAC input — a separate assertion that changing only the timestamp header changes the signature must red. Fail loudly where the check cannot run: `sign` must raise on a payload `json.dumps` cannot encode (`allow_nan=False`, no `default=str` fallback) rather than emitting a signature over a lossy rendering. Boundary and tie: state that a receiver accepts a timestamp `t` where `now - t <= 300` inclusive, and that two deliveries of the same event in the same second produce identical signatures only when their bodies are byte-identical — which is why the dedup key must be the event id (next finding), not the signature.

### Critical: the delivered body contains no event id or type, so the documented dedup contract is impossible
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`payload=payload`) and `send_once` (`json=delivery.payload`)
What is wrong: the POST body is the bare `EventEnvelope.payload` — `event_id` and `event_type` are stored on the `WebhookDelivery` row and then never transmitted — while `docs/webhooks.md` instructs receivers "delivery is at-least-once, so deduplicate on `event_id`" and the test fixture `FakeDelivery.payload = {"id": "evt_1", "type": "invoice.paid", ...}` asserts an envelope shape that `enqueue_for_event` never produces (RT1 mock-reality divergence: the double is what hides the defect, and `test_send_once_posts_the_signed_payload` asserts `json.loads(body)["type"] == "invoice.paid"` only because the fake supplies a key production does not).
What breaks in production: retries and the at-least-once guarantee make duplicate POSTs routine, and receivers have no id to deduplicate on, so a repeated `invoice.paid` is processed twice — double-shipping, double-crediting, or double-charging on the customer's side.
Fix: give the delivery a stable envelope built in one place — `enqueue_for_event` stores `payload={"id": f"evt_{event_id}", "type": event_type, "created": <occurred_at ISO>, "data": payload}` (or `send_once` wraps at send time; pick one, not both) so the id, the type and the customer data are all on the wire, and update `docs/webhooks.md`'s example body to the shape actually sent. Do not fix this by deleting the doc sentence — the at-least-once guarantee is real and the dedup key is what makes it survivable; name that as the behaviour to preserve. Replace `FakeDelivery` with a real `m.WebhookDelivery` instance constructed by `enqueue_for_event` against an in-memory session, so the test body comes from the production builder rather than from a hand-written literal (RT1: make the double compute its value, never fix it before the call). Allow side to pin: one test asserting the receiver can read `body["id"]` and `body["data"]["amount_cents"]` from `send_once`'s captured content. Red-prove per clause: (i) revert `enqueue_for_event` to `payload=payload` — the id assertion reds; (ii) drop `"type"` from the envelope — the type assertion reds, and only that one. Boundary and tie: two deliveries of the same event to two different endpoints share one `id` by design — say so in the docs, since the receiver's dedup scope is (its own endpoint, id), and see the unique-index finding below.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: `==` on a hex digest short-circuits on the first differing byte, and this is the function the repo offers as the reference verifier (RS1).
What breaks in production: an attacker who can submit candidate signatures recovers a valid digest byte by byte from response-time differences and then forges events for that endpoint.
Fix: `return hmac.compare_digest(expected, signature)`, guarding the non-`str` and `None` cases first so a caller passing a missing header gets a refusal rather than a `TypeError` from `compare_digest`. Preserve the current accept behaviour — the `sha256=` prefix is part of the compared string, do not strip it on one side only. Pin the allow side: `test_verify_accepts_signature_produced_by_sign` must stay green after the change, and add the deny side against a digest differing only in the final byte. Red-prove by execution: revert to `==` and confirm a test asserting `hmac.compare_digest` appears on the call path (e.g. by monkeypatching it to raise) goes red — a timing assertion is not admissible as the proof, it is not reproducible in CI. Fail loudly: a `signature` that is `None`, empty, or not `sha256=<64 hex>` returns `False` via an explicit branch that logs the malformed-header case, so "could not compare" is not spelled the same as "compared and matched". Boundary: a signature of exactly the right length but wrong content is a deny; a correct signature with different case in the hex is a deny (say so, or normalise case on both sides before comparing).

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from a predictable source and its internal state is recoverable from a modest run of observed outputs, so it must never generate key material (the module imports `hashlib`/`hmac` correctly but reaches for `random`, not `secrets`).
What breaks in production: a customer who legitimately holds one or more of their own signing secrets can reconstruct the generator state and derive other tenants' secrets, then forge signed `invoice.paid` events into those tenants' systems.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, delete the `random`/`string`/`_ALPHABET` imports so the unsafe primitive cannot be reached from this module at all), and rename `SECRET_BYTES` to what it now means — actual entropy bytes, not characters. Every existing row's secret is compromised the moment this ships, so the fix must include a rotation path: a migration marking all `webhook_endpoints` rows for re-issue plus the deactivate/rotate route called out in a later finding — do not ship the generator change alone. Preserve what the current code gets right and state it: the `whsec_` prefix stays, because customers may be matching on it. Allow side to pin: `test_new_signing_secret_has_prefix_and_length` must still pass after being updated to the new length (`len(secrets.token_urlsafe(32))` is 43, not 32) — update the assertion to the computed value, do not delete it. Red-prove by execution, one mutation per clause: (i) revert to `random.choice` and confirm a new test asserting `secrets` is on the call path (monkeypatch `secrets.token_urlsafe` to raise) reds; (ii) shorten `SECRET_BYTES` to 8 and confirm a minimum-entropy assertion reds. Fail loudly: if `secrets.token_urlsafe` raises, propagate — never fall back to `random`. Boundary: state the minimum accepted secret length and that a secret at exactly that length is accepted, so the verifier and the generator agree on the tie.

### Critical: `GET /webhook-endpoints` returns every endpoint's signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict` unconditionally includes `"signing_secret"`, so the list route hands back the secret for every endpoint on every call, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards") — a claim stronger than the implementation (R49), and one that customers will rely on when deciding their own storage posture.
What breaks in production: any actor with a session or key scoped to the org — a read-only integration, a support tool, a browser devtools session, or anything that caches or logs API responses — walks away with the key that authenticates all inbound webhooks, and the doc's promise means nobody thinks to rotate.
Fix: remove `"signing_secret"` from `to_dict()` and have `create_webhook_endpoint` alone return it, by building its response as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at the single creation site — the secret then exists in exactly one response shape and the model can no longer leak it into a route added later. Do not fix this by narrowing the doc sentence instead; the doc states the correct contract and the code is what is wrong. Pin the allow side: `create_webhook_endpoint`'s response must still contain a usable `signing_secret` (a test that signs a payload with the returned value and verifies it), otherwise a fix that strips the field everywhere satisfies the deny side and breaks onboarding. Red-prove separately by execution: (i) re-add `"signing_secret"` to `to_dict` — a test asserting `"signing_secret" not in` each element of the list response reds; (ii) remove it from the create response — the sign-and-verify test reds. Fail loudly: the same assertion must run over `list_deliveries`' response too, so a future `to_dict` gaining the field is caught rather than silently shipped. Boundary: an org with zero endpoints returns `[]` and that is a pass, not a vacuous one — assert the non-empty case.

### Critical: `list_deliveries` has no tenancy filter — any user reads any org's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query filters on the path-supplied `endpoint_id` only and never joins to `WebhookEndpoint.org_id == user.org_id`, while the two sibling routes in the same file (`list_api_keys`, `list_webhook_endpoints`) both scope by `user.org_id` — the tenancy pattern exists in the diff and was not propagated to the new route (R3, security-relevant).
What breaks in production: any authenticated customer enumerates small integer endpoint ids and reads other organizations' delivery history — event ids, event types, delivery status and schedule — a cross-tenant data breach reachable with a single `curl`.
Fix: join the tenancy predicate into the query — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the response does not disclose whether the id exists. Authorize in the handler that touches the data, not only wherever the session is established. Pin both sides, since a fix that always denies satisfies the deny side alone: an owning-org request for its own endpoint must still return its deliveries (allow), and a second org's request for that same id must return 404 (deny) — and per RT8 the deny test must assert the response body is empty of any row, not merely that the status is 404. Red-prove each clause by execution: (i) delete the `org_id` filter — the cross-org test reds; (ii) delete the `endpoint_id` filter — a test asserting only the requested endpoint's rows come back reds. Fail loudly: an `endpoint_id` that does not exist at all takes the same 404 path, and that case is asserted, so "no such row" and "not yours" are indistinguishable to the caller but both explicitly tested. Boundary and tie: state that an endpoint owned by the caller's org but `active=False` is still readable (history must survive deactivation), and that ties on `created_at` are broken by `id` — see the ordering finding.

### Critical: any http(s) URL is accepted and followed, giving a full SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check is `parsed.scheme.startswith("http")` and a non-empty netloc, so `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/`, and any RFC1918 address are accepted; `follow_redirects=True` then means even a public host that passes any future allowlist can 302 the worker into the internal network (RS3 — validation belongs at the schema boundary and its sink is what matters).
What breaks in production: a customer registers an internal URL and our worker POSTs attacker-chosen JSON to the cloud metadata service or an unauthenticated internal admin API from inside the trust boundary, with the response status recorded for them to read back.
Fix: validate at the schema level with a pydantic `HttpUrl`-typed field constrained to `https` only (matching the doc's "Only `https://` URLs are accepted"), and add a `_assert_public_destination(url)` helper called both at registration and again in `send_once` immediately before the POST — the second call is required because DNS can be re-pointed after registration (decide on the object the request uses, not on the name checked earlier). The helper resolves the host and rejects any answer in loopback, link-local, RFC1918, CGNAT, unique-local, or multicast space; set `follow_redirects=False` so a 3xx is recorded as a non-2xx delivery failure rather than chased. Do not fix this by only tightening the scheme string — the scheme check is not the boundary, the resolved address is. Pin the allow side explicitly: a normal `https://hooks.example.com/acme` endpoint must still register and still deliver, and both must remain green, otherwise a helper that rejects everything passes every deny test. Red-prove each clause separately by execution: (i) register `http://…` — 422 reds if the scheme constraint is reverted; (ii) point a stubbed resolver at `127.0.0.1` — the registration test reds if the address check is reverted; (iii) return a 302 to `http://169.254.169.254/` from `MockTransport` and assert `send_once` records a failure instead of a second request — reds if `follow_redirects` is reverted. Fail loudly: DNS resolution failure, an unresolvable host, or a resolver timeout must reject the registration and mark the delivery failed with a named reason — "could not check" must not be spelled the same as "checked and public". Boundary and tie: state which side `100.64.0.0/10` and IPv6-mapped IPv4 (`::ffff:127.0.0.1`) fall on, and that a host resolving to both a public and a private address is rejected.

### Critical: the migration's status CHECK rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py::deliver` → `_finish(delivery.id, "failed_permanent", …)` and `app/webhooks/models.py::STATUSES`
What is wrong: the schema permits `'failed'`, the application writes `'failed_permanent'`, and `models.STATUSES` declares the application's four values but is imported nowhere, so nothing reconciles the two spellings (R2/R3: the same enum is hardcoded in three places with two different vocabularies).
What breaks in production: every delivery that exhausts its attempts raises a CHECK-constraint violation on the terminal UPDATE, so the failure is never recorded, the row stays `in_flight` forever, and the exception propagates out of `asyncio.gather` and kills the worker loop — the first permanently-failing endpoint stops all webhook delivery for every customer.
Fix: change the migration's CHECK to `IN ('pending','in_flight','delivered','failed_permanent')` and make `STATUSES` the single source — derive the SQL literal list in a test that reads `models.STATUSES` and asserts the migration file's CHECK clause contains exactly those values, so the two can never drift again. Preserve the constraint itself: do not fix this by dropping the CHECK, which is what makes an unknown status visible at all. Pin the allow side: writing each of the four `STATUSES` values against the real migrated schema must succeed. Red-prove each clause by execution: (i) add a fifth value to `STATUSES` without touching the SQL — the drift test reds; (ii) write a literal `'failed'` from `_finish` against the migrated schema — the round-trip test reds naming the constraint. Fail loudly: the drift test must fail, not skip, when the migration file cannot be found or parsed. Boundary: an existing row already holding `'failed'` (if any environment shipped this) is migrated explicitly in the same file rather than left to violate the new CHECK.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint with the same `event_id`, so the index rejects the insert as soon as an org has two subscribed endpoints — and `app/events/dispatcher.py` wraps the call in `except Exception: log.warning(...)`, so the failure is swallowed.
What breaks in production: any customer with two endpoints silently receives no webhooks at all for any event — the first insert of the batch rolls back with the rest, and the only trace is a warning line, so the outage is invisible until a customer reports missing events.
Fix: make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — this is the constraint actually wanted, since it is what makes the enqueue idempotent per destination — and change `session.add_all(rows)` to an `ON CONFLICT (endpoint_id, event_id) DO NOTHING` upsert so a redelivered event is a no-op rather than an error. Do not fix by dropping uniqueness altogether: the index is what stops a re-dispatched event double-sending, and that behaviour must be named as preserved. Pin the allow side: an org with two active endpoints subscribed to `invoice.paid` gets exactly two delivery rows for one event (this is the case that currently fails), and re-running `enqueue_for_event` with the same `event_id` adds none. Red-prove each clause by execution: (i) restore the single-column index — the two-endpoint test reds with the integrity error named; (ii) remove the `DO NOTHING` — the re-enqueue test reds. Fail loudly: the dispatcher's `except Exception` must re-raise or emit at `error` with the event id after recording a durable failure marker (see the fire-and-forget finding), so a rejected enqueue cannot be a warning nobody reads. Boundary and tie: state that two events with the same `endpoint_id` and different `event_id` are both stored, and that a delivery whose endpoint is later deleted cascades away rather than blocking a re-registration of the same URL.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` over a 100-row batch, but its retry pause is the blocking `time.sleep`, not `await asyncio.sleep` — the module already imports `asyncio` and uses `await asyncio.sleep(poll_interval)` correctly in `run_worker`, so the correct primitive is present in the same file and was not used at the second site (R1/R3).
What breaks in production: one endpoint that fails its first attempt freezes every other coroutine on the loop for the full 2+4+8+16 s backoff — deliveries serialize instead of running concurrently, a batch of failing endpoints takes hours, and if the worker shares a loop with any other component that component stalls too.
Fix: `await asyncio.sleep(delay)` in `deliver`, and stop looping in-process altogether: on a retryable failure, write `status="pending"`, `attempts=attempt`, `next_attempt_at=_now() + backoff_for(attempt)` and return, letting the poller pick the row up — the retry schedule then survives a worker restart, which the in-memory `while True` loop does not. Cap the batch's concurrency with an `asyncio.Semaphore` so 100 rows do not open 100 sockets. Preserve the retry behaviour itself, including `MAX_ATTEMPTS` and the exponential schedule — the fix moves where the wait happens, it does not remove the wait. Pin the allow side: a delivery that succeeds on its second attempt still ends `delivered` with `attempts == 2`. Red-prove each clause by execution: (i) restore `time.sleep` — a test asserting two concurrent `deliver` calls with a 1 s pause complete in under 1.5 s wall time reds; (ii) drop the `next_attempt_at` write — a test asserting the row is re-claimable after the backoff reds; (iii) remove the semaphore — an assertion on peak concurrent transport calls reds. Fail loudly: a delivery whose row cannot be re-persisted must raise into a handler that marks it failed with a named reason, never return silently. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (the filter is `<=`), and two rows with identical `next_attempt_at` are ordered by `id`.

### Major: the dispatch lock is not atomic, and can be left with no expiry
File: `app/webhooks/delivery.py` — `_acquire_lock()`
What is wrong: `get` then `set` is a check-then-act race that two workers pass simultaneously, the TTL is applied by a separate `expire` call so a crash in between leaves `webhooks:dispatch:lock` set forever, and the 60 s TTL is shorter than a batch's own worst case (up to 5 attempts × 30 s `REQUEST_TIMEOUT` per row) so the lock expires while work is still in flight.
What breaks in production: two workers claim overlapping batches and customers receive duplicate POSTs, or — after an unlucky crash — the key persists with no TTL and every worker spins on `poll_interval` forever, delivering nothing, with no log line saying why.
Fix: replace the three calls with one atomic `await redis_client.set(LOCK_KEY, worker_id, nx=True, ex=LOCK_TTL_SECONDS)` and release only if the value still matches `worker_id` (a Lua compare-and-delete), so a worker cannot delete a lock that already expired into another worker's hands; set `LOCK_TTL_SECONDS` above the measured worst-case batch wall time and refresh it between rows. Preserve the single-worker guarantee the lock exists for — do not fix by removing the lock and relying on the status column alone. Pin both sides: the second concurrent `_acquire_lock` returns `False` (deny), and the same worker re-acquires successfully after releasing (allow) — a lock that never grants satisfies every deny test. Red-prove each clause by execution: (i) drop `nx=True` — a test issuing two acquisitions against a real/in-memory Redis reds; (ii) drop `ex=` — a test asserting the key has a positive TTL reds; (iii) release from a different `worker_id` — the compare-and-delete test reds. Fail loudly: a Redis error in `_acquire_lock` must return `False` and log at `error`, so "cannot reach Redis" denies rather than proceeding unlocked. Boundary and tie: state what happens when the TTL expires at the exact moment the owner releases — the compare-and-delete makes that a no-op rather than stealing the successor's lock.

### Major: ORM instances are read after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returns rows outside `with session_scope()`; `deliver()` reads `endpoint.signing_secret` / `endpoint.url` after the `with` block
What is wrong: both functions exit the session scope and then keep using the mapped objects, while `_finish` in the very same file re-fetches by id inside a fresh scope — the file's own code shows the author knows objects do not survive the scope, and the pattern was not propagated to the two other sites (R1/R3).
What breaks in production: with the usual `expire_on_commit=True`, the first attribute access after the scope raises `DetachedInstanceError`, so the worker dies on its first claimed row and no webhook is ever delivered; where it does not raise, the values are silently stale.
Fix: have `_claim_batch` return plain data (a list of ids, or a frozen dataclass carrying `id`, `endpoint_id`, `payload`, `attempts`) and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside a scope before the request — the same shape `_finish` already uses, so the file has one convention rather than two. Preserve the batch claim's write: `_claim_batch` must still flip the rows to `in_flight` within the transaction it selects them in. Pin the allow side: a full claim→deliver→`_finish` pass against a real session ends with `status == "delivered"` (the current tests never touch this path at all). Red-prove each clause by execution: (i) return mapped instances again — that end-to-end test reds naming the detached error; (ii) read `endpoint.url` outside the scope — same. Fail loudly: `session.get(WebhookEndpoint, …)` returning `None` (a concurrently deleted endpoint) must mark the delivery failed with a named reason rather than raising `AttributeError` into `gather`. Boundary: a delivery whose endpoint was deactivated between claim and send is not sent, and that is asserted.

### Major: the claim query has no row lock and `in_flight` has no reaper
File: `app/webhooks/delivery.py` — `_claim_batch()` (`SELECT … LIMIT 100` then `row.status = "in_flight"`), and the absence of any transition out of `in_flight` except `_finish`
What is wrong: the select-then-update is not atomic against a second worker (no `FOR UPDATE SKIP LOCKED`), and `in_flight` is a non-terminal state reachable by crash, redeploy, or any exception inside `deliver` with nothing that ever returns such a row to `pending` — R38's non-terminal transient state, with a bounded timeout absent.
What breaks in production: rows stranded in `in_flight` are invisible to `_claim_batch` (which filters `status == "pending"`) so those events are never delivered and never reported failed — a permanent silent data-loss hole that grows with every deploy.
Fix: claim with `.with_for_update(skip_locked=True)` inside the same transaction that writes `in_flight`, add a `claimed_at` column, and add a reaper query that returns rows with `status='in_flight' AND claimed_at < now() - interval '10 minutes'` to `pending` with `attempts` incremented — the exit from the transient state is then explicit and bounded rather than dependent on the success path. Preserve the claim's exclusivity: the reaper must not resurrect a row a live worker still holds, which is what the `claimed_at` window buys. Pin the allow side: a row claimed and delivered normally is never touched by the reaper. Red-prove each clause by execution: (i) remove `skip_locked` — a two-session test asserting disjoint batches reds; (ii) remove the reaper — a test that kills a delivery mid-flight and asserts the row is re-claimable after the window reds; (iii) set the reaper window to zero — the "not touched while live" assertion reds. Fail loudly: a row that has been reaped more than N times is moved to a named `failed_stuck` status and logged at `error`, so an endlessly-recycling row is not mistaken for a healthy queue. Boundary and tie: a row whose `claimed_at` is exactly at the window edge is not yet reaped (`<`, not `<=`), stated explicitly.

### Major: 4xx responses are retried, contradicting the documented contract
File: `app/webhooks/delivery.py` — `deliver()`, the `status_code`/`detail` branch after the 2xx check
What is wrong: every non-2xx response falls through to the retry path, while `docs/webhooks.md` states "5xx, timeouts and connection errors are retried; a 4xx is permanent and we stop immediately" (R49: a claim stronger than the implementation).
What breaks in production: an endpoint that has been decommissioned and returns 404/410 is POSTed five times with backoff for every event, multiplying load on a customer who has already told us to stop and holding worker capacity that live endpoints need.
Fix: branch on the class — 2xx `delivered`; 408 and 429 retryable; any other 4xx `failed_permanent` immediately with the response status recorded; 5xx and `httpx.HTTPError` retryable — and put the classification in one named predicate `_is_retryable(status_code)` so the API, the worker, and the docs all read the same rule.
