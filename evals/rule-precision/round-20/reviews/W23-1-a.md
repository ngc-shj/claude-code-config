### Critical: the HMAC is computed over different bytes than the ones actually sent
File: `app/webhooks/signing.py` — `serialize`/`sign`, consumed by `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys sorted) while the request body is produced by `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and insertion order, so the signed string and the wire body are different byte sequences for any payload with more than one key or any nested structure.
What breaks in production: every customer following `docs/webhooks.md` — HMAC over the raw request body — computes a different digest and rejects 100% of our deliveries, and the failure is invisible to us because we record their 4xx as an endpoint problem.
Fix: serialize once and send those exact bytes. In `send_once`, build `body = signing.serialize(delivery.payload).encode()`, call `sign` on that same `bytes` object, and send `await client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` — never `json=`. Change `sign(secret, body: bytes)` to take the already-serialized bytes so the two paths structurally cannot diverge; `serialize()` becomes the single producer of the wire form (it already exists in this diff and `send_once` currently bypasses it — R1/R17: adopt it rather than leaving a second serialization at the call site). **Allow side that must still pass**: a delivery to a correct receiver still returns 2xx and is marked `delivered`; pin it with a round-trip test that captures `request.content` from `httpx.MockTransport` and feeds those exact bytes plus the captured `X-Acme-Timestamp` into an independently written receiver-side `hmac.new(SECRET, b"%s.%s" % (ts, body), sha256).hexdigest()`, asserting equality with the captured signature header — actual producer output through the actual consumer computation, not two mocked shapes (R40). **Red-prove each clause separately by execution**: (i) flip one byte of the captured body before recomputation → the equality assertion reddens; (ii) substitute a different secret → reddens; (iii) revert `content=body` to `json=payload` for a two-key payload → reddens, and this mutation is the regression proof for this finding specifically. **Fail loudly**: if `serialize` raises (a payload holding a non-JSON-serializable value), do not fall back to an unsigned or differently-serialized send — mark the delivery `failed_permanent` with `detail="payload not serializable"` so "could not sign" is spelled differently from "signed and delivered". **Preserve**: the `sha256=<hex>` header format and the payload contents must not change — do not "fix" this by dropping `sort_keys` on the receiver side of the test, which would delete the assertion that made the defect visible. **Boundary**: a payload of exactly `{}` must still produce a signature over `b"{}"` rather than an empty body, and two payloads with the same keys in different insertion order must now produce byte-identical bodies and identical signatures.

### Critical: the timestamp is unauthenticated, so the documented replay window is not a control
File: `app/webhooks/signing.py` — `sign` (lines returning `timestamp, "sha256=" + mac.hexdigest()`)
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign()` MACs the body alone and returns the timestamp as an unbound side value, so the `X-Acme-Timestamp` header is attacker-controlled while the signature still validates.
What breaks in production: a captured delivery can be replayed forever — the attacker rewrites the timestamp header to `now` and the signature still verifies, which defeats exactly the five-minute freshness check we instruct customers to rely on (R49: the doc describes an enforceable boundary; the implementation provides none).
Fix: bind the timestamp into the MAC — `mac = hmac.new(secret.encode(), b"%s.%s" % (timestamp.encode(), body), hashlib.sha256)` — and give `verify(secret, timestamp, body, signature)` the same signature so a caller cannot verify without supplying the timestamp it is about to trust. Add the freshness check to `verify` itself (`abs(now - int(timestamp)) <= TOLERANCE_SECONDS`, `TOLERANCE_SECONDS = 300`) rather than leaving it to prose, and reject a non-integer or absent timestamp. **Allow side**: a request signed 10 seconds ago still verifies, and the existing `test_verify_accepts_signature_produced_by_sign` must stay green after being updated to pass the timestamp through. **Red-prove separately**: (i) reuse a valid `(body, signature)` with the timestamp advanced by 1 second → verify returns False; (ii) present the correct timestamp with a body byte flipped → False; (iii) freeze the clock 301 seconds after signing → False, and at 300 seconds → True (this pair is the boundary proof, not one mutation). **Fail loudly**: a timestamp that is missing, non-numeric, or in the future beyond tolerance must return False with a distinct reason rather than being skipped — "no timestamp supplied" must not be spelled the same as "timestamp fresh". **Preserve**: the header names and the `sha256=` prefix, and the fact that the timestamp is still transmitted in clear so receivers can log it. **Boundary and tie**: state in the doc that a timestamp exactly `TOLERANCE_SECONDS` old is ACCEPTED and one second older is rejected, and that two requests sharing the same timestamp second are both valid (the timestamp is not a nonce — deduplication remains on `event_id`, as the doc already says).

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the shipped reference verification compares an attacker-supplied signature against the expected digest with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: an attacker with network access to any consumer of this helper can recover a valid signature byte-by-byte from response-timing differences and forge deliveries; the same defect is copied into every customer integration, because `docs/webhooks.md` points at this behaviour while telling customers to use constant-time comparison — we ship the opposite of what we document.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str`/`bytes` of the same type before the call, and keep the digest computation ahead of the comparison so the work is the same on both branches. **Allow side**: a genuinely valid signature must still return True — `test_verify_accepts_signature_produced_by_sign` is that case and must stay green. **Red-prove separately**: (i) a signature differing only in its last hex character returns False; (ii) a signature differing only in its first hex character returns False (the pair proves the comparison is not prefix-sensitive in outcome); (iii) revert to `==` and confirm the added `assert "compare_digest" in inspect.getsource(signing.verify)` style guard, or the timing test, goes red — a mutation per clause, each executed. **Fail loudly**: a `signature` of `None` or of the wrong type must raise or return False explicitly rather than falling through `compare_digest`'s `TypeError` unhandled at the call site. **Preserve**: `verify` must keep returning a plain bool and must not start raising on ordinary mismatch, which callers may branch on. **Boundary**: signatures of unequal length must return False without leaking the length difference by an early return placed before the comparison.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from process state, not a CSPRNG, so secrets drawn from it are predictable to anyone who observes ~624 outputs of the same generator (any other `random` consumer in the process shares that state).
What breaks in production: an attacker who recovers the generator state — or who simply brute-forces a weakly seeded worker — can derive other tenants' signing secrets and forge webhook deliveries that every receiver accepts as authentic.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` using the stdlib `secrets` module, and rename the constant to what it now means (`SECRET_BYTES = 32` genuinely becomes 32 bytes of entropy rather than 32 characters from a 62-symbol alphabet). **Codebase-awareness evidence**: `app/api/routes/settings.py` already imports `app.models.api_key.ApiKey`, which carries a `prefix` column — the same prefixed-token shape this function reinvents; before adding a second generator, check whether `app/models/api_key.py` or its creation path already exposes a token factory and adopt it (R1). If it does, enumerate the behavioural differences (prefix value, length, alphabet) and classify each before switching, and delete this duplicate outright rather than keeping it as a wrapper. **Allow side**: `create_webhook_endpoint` must still return a secret that `sign`/`verify` round-trip successfully, and the prefix assertion in `test_new_signing_secret_has_prefix_and_length` must stay green. **Red-prove separately**: (i) replace the body with a constant string → a new test asserting 1000 generated secrets are all distinct reddens (the current length-only test would NOT redden, which is why it must be added); (ii) drop the prefix → the prefix assertion reddens; (iii) shrink to `token_urlsafe(4)` → a minimum-entropy length assertion reddens. **Fail loudly**: nothing here may silently fall back to `random` if `secrets` is unavailable — there is no such fallback and none should be added. **Preserve**: the `whsec_` prefix, which customers use to recognise the credential. **Boundary**: state the exact post-change length (`len(SECRET_PREFIX) + 43` for `token_urlsafe(32)`) and update the length assertion to that value rather than to `SECRET_BYTES`, and note that existing rows keep their old-format secrets — verification must accept both, so do not add a format check on the secret.

### Critical: the signing secret is returned on every list request
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict()` embeds the secret and is used by `list_webhook_endpoints` as well as by the creation response, directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: every `GET /v1/settings/webhook-endpoints` puts live HMAC keys into responses, proxy logs, browser caches, and support screenshots, so a single read-scoped token leak becomes signature-forgery capability for that tenant (RS4).
Fix: remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the one call site that is documented to expose it — the secret then appears only where a reviewer can see the deliberate line. **Allow side**: `POST /v1/settings/webhook-endpoints` must still return the secret exactly once; pin it with a test asserting `signing_secret` is present in the 201 body AND absent from every element of the 200 list body — both directions in the same test file, so a fix that hides it everywhere is caught too. **Red-prove separately**: (i) re-add the key to `to_dict()` → the list-absence assertion reddens; (ii) delete the explicit merge in the create handler → the 201-presence assertion reddens. **Fail loudly**: `create_webhook_endpoint` must not return a `None`/empty secret silently — assert the generator produced a non-empty value before commit and raise a 500 naming the failure if not. **Preserve**: the rest of the endpoint representation (`id`, `url`, `event_types`, `active`) must keep its exact shape, since clients key off it. **Boundary**: an endpoint created before this change still has a secret in the row; the list response must omit it for those rows too, and no migration should attempt to null it out.

### Critical: delivery history is readable across organizations
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint` to check `org_id == user.org_id`, while the two sibling handlers added in the same file (`create_webhook_endpoint`, `list_webhook_endpoints`) do scope by `user.org_id` — the tenancy pattern was applied in two of three new routes and not the third (R3, security-relevant → Critical).
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other tenants' full webhook payloads — `WebhookDelivery.payload` holds the raw `invoice.paid` / `subscription.updated` bodies — which is a cross-tenant data breach reachable with one URL edit, and the docstring in `docs/webhooks.md` claims the endpoint returns attempts "for an endpoint belonging to your organization".
Fix: resolve the endpoint under the caller's org first and 404 when it does not resolve — `endpoint = session.query(WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`; `if endpoint is None: raise HTTPException(404, "endpoint not found")` — then query deliveries by `endpoint.id`. Use 404 rather than 403 so the response does not confirm the id exists. **Cross-cutting check performed**: the two other new routes are correctly scoped; `enqueue_for_event` also scopes by `org_id`; `_claim_batch` is a trusted worker path with no caller-supplied id, so no equivalent gap there. **Allow side**: a user listing deliveries for an endpoint their own org owns must still get 200 with the rows — pin both cases in one test file: same-org returns the rows, other-org returns 404 with an empty body, and assert on the returned row ids, not just the status code (RT8: asserting only the status leaves a handler that returns 404 plus the data still green). **Red-prove separately**: (i) delete the `org_id` predicate → the cross-tenant test reddens; (ii) delete the `is None` raise → the cross-tenant test reddens on a different assertion (200 instead of 404); (iii) hardcode the handler to always 404 → the same-org test reddens, which is the clause that stops the fix from being "deny everything". **Fail loudly**: an endpoint id that is not an integer, or a user whose `org_id` is unset, must produce a 4xx naming the failure rather than an unscoped query. **Boundary**: an endpoint that exists but is `active=False` still belongs to the org and must remain readable — inactive is not deleted — and a soft-deleted endpoint, if that concept is added later, must be explicitly decided rather than falling through this filter.

### Critical: the migration's status CHECK does not admit the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: the constraint allows `'failed'` while `app/webhooks/delivery.py:deliver` writes `"failed_permanent"` and `app/webhooks/models.py:STATUSES` declares `"failed_permanent"` — three declarations of one enum, two of which agree against the schema (R18/R3/R40).
What breaks in production: the terminal write for every exhausted delivery raises a check-constraint violation inside `_finish`, so the row never leaves `in_flight`, the exception propagates out of `deliver` into `asyncio.gather`, and the worker loses the whole batch — permanent failures accumulate as permanently stuck rows.
Fix: make the migration's list the derived one — write `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and add a comment naming `app.webhooks.models.STATUSES` as the source of truth, then add a test that imports `STATUSES` and asserts every member is accepted by an insert against the real schema (not a mocked session), so the two cannot drift again. **Allow side**: inserting each of the four legitimate statuses must SUCCEED; the same test must also assert that `'bogus'` is rejected, or a fix that drops the constraint entirely passes. **Red-prove separately**: (i) revert the constraint to `'failed'` → the `failed_permanent` insert case reddens; (ii) drop the CHECK clause → the `'bogus'` rejection case reddens; (iii) add a fifth member to `STATUSES` without touching the migration → the parametrised insert reddens, proving the test is derived from the constant and not a hand-copied list (RT3). **Fail loudly**: if the test cannot reach a real Postgres, it must error naming that, not skip silently — a skipped schema test is spelled the same as a passing one. **Preserve**: the constraint must remain (removing it is the tempting fix and would delete the thing that made the drift visible). **Boundary**: existing rows, if any, are all `pending`, so the constraint can be replaced in place; state that the migration must `DROP CONSTRAINT ... ; ADD CONSTRAINT ...` if it has already been applied anywhere.

### Critical: the unique index on `event_id` allows only one delivery row per event
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint and `event_id` is not scoped per endpoint or per org, so any event with two or more subscribed endpoints violates the index.
What breaks in production: the second endpoint's insert raises, `session.add_all` fails the whole batch, and the dispatcher's `except Exception: log.warning(...)` swallows it — customers with two webhook endpoints (or two orgs whose event ids ever collide) silently receive nothing, with only a warning line as evidence.
Fix: change it to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)` — that is the real idempotency key, one attempt-record per (endpoint, event) — and make `enqueue_for_event` insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` semantics so a retried dispatch is a no-op rather than an error. **Allow side**: an event fanning out to three endpoints of one org must produce exactly three rows; assert the count, not merely that no exception was raised. **Red-prove separately**: (i) revert to the single-column index → the three-endpoint test reddens on the insert; (ii) drop the index entirely → a test calling `enqueue_for_event` twice for the same event and asserting three rows (not six) reddens; (iii) remove the conflict clause → the double-call test reddens on an IntegrityError rather than a count. **Fail loudly**: `enqueue_for_event` must stop swallowing insert failures at the dispatcher — see the transaction finding below; a batch that partially fails must raise so the caller can retry. **Preserve**: the at-least-once guarantee the docs promise and the `event_id` deduplication contract customers are told to use — do not fix this by dropping uniqueness, which would remove the only protection against duplicate rows. **Boundary**: when the same event is enqueued concurrently by two workers, exactly one row per (endpoint, event) must survive and neither caller may see an error.

### Critical: any authenticated user can point the signed-request worker at internal hosts
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: the guard adjudicates the URL's *notation* — a prefix test on the scheme string and a non-empty `netloc` — rather than the address the HTTP client will actually connect to, and `app/webhooks/delivery.py:run_worker` compounds it with `follow_redirects=True`, so even a validated public host can redirect the request to a private address after the check (R47: the interpreter that gives the URL meaning is the resolver, and it is never consulted).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:6379/`, and our worker issues authenticated-looking POSTs from inside the VPC on a retry schedule, returning the response body to the tenant through the deliveries API — a full SSRF read primitive; separately, `startswith("http")` admits `http://`, so payloads the docs promise go only to `https://` endpoints travel in clear.
Fix: judge the resolved destination, not the string. (a) Require `parsed.scheme == "https"` exactly — an equality test, matching what `docs/webhooks.md` already claims — and reject anything else with 422. (b) Resolve the hostname at registration and again at send time, and deny when any resolved address is loopback, link-local, private, multicast, or reserved (`ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast` over every address from `socket.getaddrinfo`). (c) Set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure with a named reason, since a redirect re-targets the request after the check. (d) Declare the control's class at the artifact (R49): with the resolve-then-connect gap this is a fail-closed verification gate, not an enforceable boundary — the residual DNS-rebinding window must be named in a comment, with the real closure being connect-time address pinning. **Allow side**: `https://hooks.example.com/acme` must still register and still receive deliveries; assert the successful registration and a successful 2xx delivery in the same test, or a fix that denies every URL passes. **Red-prove separately**: (i) register `http://hooks.example.com/x` → 422; (ii) register `https://localhost/x` → 422; (iii) register a host resolving to `10.0.0.5` → 422; (iv) have the mock transport return a 302 to `http://127.0.0.1/` → the delivery is marked `failed_permanent` and no second request is issued; each mutation run and observed separately. **Fail loudly**: a hostname that does not resolve, or a resolver error, must DENY with a named reason ("could not resolve endpoint host") rather than being treated as "no private address found" — R47 sub-clause (a). **Preserve**: legitimate public HTTPS endpoints on non-standard ports must keep working; do not fix this by restricting to port 443 only unless that restriction is documented. **Boundary**: state which side IPv6-mapped IPv4 (`::ffff:10.0.0.5`) and `0.0.0.0` fall on — both deny — and that a host resolving to both a public and a private address is denied, not allowed on the public one.

### Critical: a blocking `time.sleep` inside the async retry loop stalls the whole worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is an `async def` scheduled through `asyncio.gather`, but its backoff uses the blocking `time.sleep`, which halts the event loop rather than yielding.
What breaks in production: one failing endpoint freezes the entire process for up to 2+4+8+16 = 30 seconds per delivery, and because `gather` runs the batch on one loop, 100 concurrent deliveries serialize into up to 50 minutes of wall-clock during which no other delivery, no HTTP response, and no lock refresh happens — the worker looks hung and the 60-second lock TTL expires underneath it.
Fix: replace with `await asyncio.sleep(delay)`. While there, do not hold the retry chain inside one invocation at all: on a retryable failure, persist `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and RETURN, letting the next poll pick it up — that removes the in-process sleep entirely and makes a worker restart harmless. **Allow side**: a delivery that succeeds on the first attempt must still be marked `delivered` with `attempts == 1` and must not sleep at all; assert both the status and the elapsed-time-under-threshold, so a fix that sleeps unconditionally is caught. **Red-prove separately**: (i) restore `time.sleep` → a test asserting the event loop stays responsive (a concurrent `asyncio.sleep(0)` task completes within the backoff window) reddens; (ii) remove the `next_attempt_at` update → a test asserting the retried row is scheduled into the future reddens; (iii) remove the status reset to `pending` → a test asserting the row is reclaimable by `_claim_batch` reddens. **Fail loudly**: if the persistence of the retry state itself fails, the delivery must not be left `in_flight` silently — log at error and let the reaper (below) reclaim it. **Preserve**: the documented retry count and the 2/4/8/16 backoff schedule must not change; `backoff_for` and `MAX_ATTEMPTS` stay as they are. **Boundary**: attempt number exactly `MAX_ATTEMPTS` is the last one attempted and terminates as `failed_permanent`; attempt `MAX_ATTEMPTS - 1` still reschedules — state which side, because the current `if attempt >= MAX_ATTEMPTS` after the increment is easy to shift by one during this edit.

### Critical: the webhook enqueue is outside the event transaction and its failure is swallowed
File: `app/events/dispatcher.py` — `dispatch`, `except Exception as exc: log.warning(...)`
What is wrong: the `Event` row commits in its own `session_scope`, then `enqueue_for_event` opens a second, independent transaction, and any failure of that second transaction is caught and downgraded to a warning (R9/R5) — there is no outbox and no reconciliation path from `events` to `webhook_deliveries`.
What breaks in production: a process crash, a connection blip, or the `event_id` unique-index violation described above leaves the event durably recorded with no delivery rows and nothing that will ever notice, which makes the "delivery is at-least-once" guarantee in `docs/webhooks.md` false — billing events silently never reach the customer.
Fix: write the delivery rows in the SAME transaction as the event — pass the open session into `enqueue_for_event(session, ...)` and move the call inside the existing `with session_scope() as session:` block, before `flush()`-derived `event_id` is used, so either both the event and its deliveries commit or neither does. Remove the blanket `except Exception`; let the failure propagate to `dispatch`'s caller so the producer can retry the whole unit. Keep the actual HTTP send out of the transaction — only the row insert moves in. **Allow side**: a successful dispatch must still return the `event_id` and must still run the in-process `SUBSCRIBERS`; assert both, or a fix that aborts on the first webhook problem breaks unrelated subscribers. **Red-prove separately**: (i) force the delivery insert to raise → assert NO `events` row is committed (this is the atomicity clause and reddens if the enqueue is moved back out); (ii) force a subscriber to raise → assert the event row IS committed and delivery rows exist, pinning that subscriber failures are not conflated with enqueue failures; (iii) restore the `except Exception: log.warning` → the first test reddens because the event commits alone. **Fail loudly**: an enqueue that matches zero endpoints is a legitimate zero, not a failure — it must return 0 and commit; an enqueue that ERRORS must raise. Those two must not be spelled the same, which is exactly what the current `except` does. **Preserve**: `dispatch` must keep returning `event_id` and must keep persisting the event for org/event-type combinations that have no webhook endpoints at all. **Boundary**: an event type that is in `WEBHOOK_EVENT_TYPES` but has zero active endpoints commits with zero delivery rows and is not an error; an event type outside the set does not even call the enqueue — say which of the two paths a newly added event type lands on.

### Critical: no test recomputes the signature over the bytes that were sent
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: the test captures both `request.headers` and `request.content` but only asserts the signature *starts with* `sha256=` and has the right length, never recomputing the HMAC over `captured["body"]` — the single assertion that would have caught the serialization mismatch and the unbound timestamp above (RT5: the test's call path reaches `send_once` but the production primitive being claimed — signature verification — is never exercised; RT7: the assertion cannot fail for the reason its name implies).
What breaks in production: the suite is green while every delivery we send is unverifiable by its recipient, and a reviewer reading "posts the signed payload" reasonably concludes signing is covered.
Fix: add the recomputation to this test — `expected = hmac.new(SECRET.encode(), b"%s.%s" % (captured["headers"][signing.TIMESTAMP_HEADER].encode(), captured["body"]), hashlib.sha256).hexdigest()` and `assert captured["headers"][signing.SIGNATURE_HEADER] == "sha256=" + expected`, written out literally in the test rather than by calling `signing.sign`, so the test is an independent oracle and not an identity over the subject's own output (RT1). **Allow side**: the correctly signed request must satisfy it — that is the green case, and it must be green only after the serialization fix lands. **Red-prove separately**: (i) change `send_once` to post `json=` instead of `content=` → reddens; (ii) drop the timestamp from the MAC input in `sign` → reddens; (iii) change the secret used by the fake endpoint → reddens. Three mutations, three different assertions, each executed. **Fail loudly**: if the signature or timestamp header is absent, the test must fail on a missing-key error naming the header, not silently pass a `.get(...)` that returned `None`. **Preserve**: the existing assertions on content-type and payload round-trip stay; the fix adds an assertion rather than replacing the weak ones. **Boundary**: assert on a payload with at least two keys inserted in non-sorted order — a single-key payload serializes identically under both schemes and would leave the test vacuous for exactly the defect it targets.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after the `with` block) and `deliver` (reads `endpoint.url` / `endpoint.signing_secret` outside its `session_scope`)
What is wrong: both functions fetch ORM objects inside a `session_scope` and then read attributes after that scope exits, which under SQLAlchemy's default `expire_on_commit=True` expires every loaded attribute and raises `DetachedInstanceError` on first access.
What breaks in production: the worker raises on the first delivery of the first batch and delivers nothing, with rows already flipped to `in_flight`. The answer that closes this: if `app/db.session_scope` constructs its sessionmaker with `expire_on_commit=False`, the attribute reads succeed and this is inert — that file is not in the diff, so confirm it before treating this as live.
Fix: stop passing ORM entities across session boundaries. ### Major: `in_flight` is a non-terminal state with no exit and no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; nothing resets it

### Major: the dispatch lock is not atomic and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does a GET, then a separate SET and a separate EXPIRE, so two workers can both observe the key absent and both proceed (a classic TOCTOU, R5), and the `finally` deletes the key by name without proving this worker still owns it.
What breaks in production: two workers claim overlapping batches and send duplicate webhooks, and after a batch overruns the 60-second TTL, worker A's `finally` deletes the lock worker B legitimately holds, cascading the overlap; if the process dies between SET and EXPIRE the lock never expires and delivery stops entirely.

RETURNING`. **Boundary**: a lock whose TTL expires at exactly the moment the owner tries to release — the compare-and-delete must be a no-op then, and the owner must not assume its batch is still exclusive.

### Major: the retry policy contradicts the documented one

### Major: one exception kills the worker permanently
File: `app/webhooks/delivery.py` — `run_worker`, the `try/finally` inside `while True` and the `if not batch` that follows it
What is wrong: `_claim_batch` and `asyncio.gather` are inside a `try` whose only handler is `finally`, so any exception escapes the `while True` and terminates `run_worker`; on that path `batch` is also unbound, so the trailing `if not batch` would raise `NameError` if the flow ever reached it.
