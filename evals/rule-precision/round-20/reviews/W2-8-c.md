### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (Python's default `", "` / `": "` separators, keys sorted) while the request is transmitted by `client.post(..., json=delivery.payload)`, which httpx serializes with compact `(",", ":")` separators and insertion order — so the MAC covers a byte string no receiver ever sees.
What breaks in production: every customer following `docs/webhooks.md` ("HMAC-SHA256 of `{timestamp}.{raw_request_body}`") computes a different digest and rejects 100% of our deliveries, and the ones who give up and stop verifying are then unauthenticated.
Fix: make the transmitted body the signing input, not a second rendering of it — build `body = serialize(payload).encode()` once in `send_once`, pass it as `client.post(endpoint.url, content=body, headers=headers)` (keep the explicit `Content-Type: application/json` header, which `content=` no longer sets for you), and have `sign` accept and MAC that exact `bytes` rather than re-serializing a dict. Preserve what the current code got right: the payload still reaches the endpoint as a JSON object and `serialize`'s `sort_keys=True` stays, because customers who already store the raw body depend on a stable rendering. Pin both directions: an allow case that captures `request.content` from `httpx.MockTransport` and asserts `hmac.compare_digest(hmac.new(SECRET.encode(), b"%s.%s" % (ts, body), sha256).hexdigest(), header.removeprefix("sha256="))` recomputed independently of `sign`, and a deny case where the body is mutated by one byte and the recomputation fails. Red-prove each clause separately by execution: (i) change `serialize`'s separators and watch the allow assertion redden; (ii) drop the one-byte mutation from the deny case and watch it redden. Where the check cannot run — `SIGNATURE_HEADER` absent from the captured headers, or `request.content` empty — the test must `fail("no signature captured")` rather than skip, so "examined nothing" is not spelled like "found nothing". Boundary and tie: an empty-dict payload serializes to `{}` and must still produce a signature over `b"{ts}.{}"`, not over `b""`; two payloads whose key order differs must produce byte-identical bodies and therefore identical signatures.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign` (line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`)
What is wrong: `sign` MACs the payload alone and returns the timestamp beside it unauthenticated, contradicting `docs/webhooks.md`, which tells customers the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "stops a captured request from being replayed".
What breaks in production: an attacker who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to now — the signature still validates because it never covered the timestamp — so the replay control every customer was told to build is decorative (R49: a claim stronger than the implementation).
Fix: change `sign` to compute `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` and change `verify` to take the timestamp explicitly (`verify(secret, timestamp, body, signature, max_age_seconds=300)`), rejecting when `abs(now - int(timestamp)) > max_age_seconds` and when `timestamp` is not an integer. Do not "fix" this by deleting the timestamp header or by relaxing the doc — the header is what makes the customer-side window possible and must keep its `X-Acme-Timestamp` name and unix-seconds format. Pair the sides: an allow test where a signature signed at `now - 299` still verifies, and deny tests for `now - 301`, for a signature whose timestamp was rewritten after signing, and for `timestamp="abc"`. Red-prove each clause by its own mutation and run it: drop `f"{timestamp}."` from the MAC input (the rewritten-timestamp deny test must redden), and change `>` to `>=` (the 299s allow test stays green, the exactly-300s case moves — see below). Fail loudly rather than silently allowing when the header is missing or unparseable: `verify` must return `False`, never raise-and-be-caught into a pass. Boundary and tie: state that exactly `max_age_seconds` old is ACCEPTED (`>` not `>=`) and that a timestamp exactly equal to `now` is accepted, so future clock-skew tuning has one documented edge.

### Critical: signing secrets are generated with a predictable PRNG
File: `app/webhooks/signing.py` — `new_signing_secret` (`random.choice(_ALPHABET)`)
What is wrong: `random` is the Mersenne Twister, a non-cryptographic generator whose internal state is recoverable from a modest run of outputs, so secrets minted for one org predict secrets minted for others.
What breaks in production: an attacker who registers a handful of their own endpoints and reads back their own secrets can reconstruct the generator state and forge signed webhook deliveries to other customers' endpoints, which is the entire security value of the feature.
Fix: replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` scaffolding; also rename or correct the constant, because `SECRET_BYTES = 32` currently produces 32 *characters* from a 62-symbol alphabet, not 32 bytes of entropy — `token_urlsafe(32)` makes the name true. Preserve what the current function got right and what a test already pins: the `whsec_` prefix must stay, since it is what customers key their secret-manager lookups on. Pair the sides: keep the allow test `secret.startswith(SECRET_PREFIX)` and add a deny-shaped one — assert `len(set(new_signing_secret() for _ in range(1000))) == 1000` (no collisions) and that no two secrets share a prefix beyond `whsec_`. Red-prove each clause separately by execution: revert to `random.seed(0)` plus `random.choice` and observe the collision assertion redden; strip the prefix and observe the prefix assertion redden — two mutations, two different reddened assertions. Note that the existing `test_new_signing_secret_has_prefix_and_length` is green against a function returning a hardcoded constant, which is why this shipped; it must not remain the only coverage. Fail loudly if `secrets` is unavailable rather than falling back to `random` — no fallback branch at all. Boundary and tie: fix the length assertion to the *new* length (`token_urlsafe(32)` yields 43 characters), and state that the assertion is on a minimum entropy claim, not on an exact display width, so a future encoding change loosens the check deliberately rather than by accident.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify` (`return expected == signature`)
What is wrong: the MAC comparison uses Python's short-circuiting `str.__eq__` instead of `hmac.compare_digest`, so the comparison time leaks the length of the matching prefix (RS1).
What breaks in production: any caller we ship this helper to — and our own inbound-verification path the moment one exists — lets an attacker recover a valid signature byte by byte from timing, and the docs simultaneously instruct customers to "compare using a constant-time comparison", so we are shipping the opposite of our own advice.
Fix: `return hmac.compare_digest(expected, signature)`, guarding first against a `signature` that is `None` or not `str` (return `False`) since `compare_digest` raises `TypeError` on mixed types. Do not weaken the function to compensate — it must keep returning `False` for a wrong secret, which is what `test_verify_rejects_a_signature_made_with_another_secret` pins. Pair the sides: the existing accept test stays as the allow case; add deny cases for a signature differing only in the final hex character, for `signature=None`, and for a signature missing the `sha256=` prefix. Red-prove each clause by execution, one mutation each: restore `==` and confirm the type-confusion deny case (`signature=None`) reddens with `TypeError` rather than passing; delete the `sha256=`-prefix check and confirm the prefix deny case reddens. Fail loudly when the input cannot be adjudicated — an unparseable signature returns `False` explicitly, never `None`, so a caller writing `if verify(...)` and a caller writing `if verify(...) is True` agree. Boundary and tie: a zero-length `signature` and a zero-length `expected` must not compare equal; state that `compare_digest` on unequal-length inputs returns `False` without leaking the length difference beyond what is already public.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id` taken straight from the path, with no join back to `WebhookEndpoint.org_id == user.org_id`, while both sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) do filter on `user.org_id` — R3, incomplete propagation of the tenancy pattern this very file establishes.
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other organizations' delivery records, and since `to_dict` exposes `event_type`, `response_status` and delivery timing, this is a cross-tenant read of billing-event metadata (`invoice.paid`, `invoice.payment_failed`).
Fix: resolve the endpoint first inside the same transaction — `endpoint = session.query(WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`; `if endpoint is None: raise HTTPException(404)` — and only then query deliveries by `endpoint.id`; return 404 rather than 403 so the endpoint-id space is not enumerable. Cross-cutting: `list_webhook_endpoints` and `create_webhook_endpoint` are correctly scoped, so this is the only missed site in the diff, but the deliveries route is also the only one taking a caller-supplied id — any future `DELETE /webhook-endpoints/{id}` must use the same resolve-then-act helper, so extract it as `_owned_endpoint(session, endpoint_id, user)` and call it from both. Preserve the working behavior: an owner listing their own deliveries must still get them, and the `limit`/ordering semantics are unchanged. Pair the sides with real fixtures: an ALLOW test where org A's user reads org A's endpoint and receives the rows, and a DENY test where org B's user requests org A's endpoint id — and per RT8, assert not only the 404 status but that the response body contains zero delivery rows, since a handler that 404s after having already leaked rows in a log or a partial response is still a breach. Red-prove each clause by execution: delete the `org_id` predicate and watch the deny test redden; delete the `one_or_none()`/404 branch and watch the not-found test redden (two mutations, two assertions). Fail loudly when the subject cannot be resolved: a missing endpoint and a foreign endpoint must take the same 404 path, and an unauthenticated caller must never reach the query at all. Boundary and tie: state that an endpoint belonging to the caller's org but `active=False` is still readable (deliveries are history, not configuration), and that two orgs owning endpoints with adjacent ids get no cross-visibility at the id boundary.

### Critical: the signing secret is returned on every endpoint listing, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`); consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict` unconditionally includes the plaintext signing secret and `list_webhook_endpoints` returns it for every endpoint in the org, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the shared secret that is the sole authentication of the webhook channel is re-served on an ordinary GET, so it lands in browser history, proxy and access logs, API-client caches, and support screenshots — and every reader of the settings page holds forgery capability for that org's endpoints.
Fix: remove `signing_secret` from `to_dict` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the single moment disclosure is intended; add a `rotate` route later if read-back is genuinely needed, never a read. Codebase awareness: `to_dict` is the only serializer for this model and is called from exactly two places in the diff (`create_webhook_endpoint`, `list_webhook_endpoints`), so the narrowing is complete — and `WebhookDelivery.to_dict` correctly omits `response_body`, which is the shape to copy. Do not fix this by redacting the string in the response layer, which leaves the secret in the object every future caller serializes; the default must be safe. Pair the sides: an ALLOW test asserting the POST response *does* contain `signing_secret` (the documented one-time disclosure must keep working, and a fix that removed it everywhere would satisfy every other clause while breaking onboarding), and a DENY test asserting the GET response for the same endpoint contains no key named `signing_secret` and no substring starting with `whsec_`. Red-prove each clause by execution: re-add the field to `to_dict` and watch the GET deny test redden; delete the explicit merge in the POST handler and watch the create allow test redden. Fail loudly rather than silently passing when the fixture never created an endpoint — assert the GET returned at least one row before asserting the absence, or the deny test is vacuously green on an empty list. Boundary and tie: state that an org with zero endpoints returns `[]` and that the absence assertion is skipped-with-failure, not skipped-with-pass, in that case.

### Critical: the migration's status CHECK constraint rejects the terminal status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` — `STATUSES`
What is wrong: the SQL constraint spells the terminal failure state `'failed'` while both the model's `STATUSES` tuple and the only writer in `delivery.py` use `'failed_permanent'` — the same enum spelled two ways across a strict consumer boundary (R40, R42).
What breaks in production: every delivery that exhausts `MAX_ATTEMPTS` raises `IntegrityError` inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and because `_claim_batch` only selects `status == "pending"` that delivery is never retried, never reported as failed, and never visible as anything but permanently in flight.
Fix: change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive it from one source rather than restating it — generate the constraint from `models.STATUSES` in the migration, or at minimum add a test that asserts the constraint's member set equals `STATUSES` by querying `pg_constraint`. `STATUSES` is already defined in `models.py` and is currently referenced by nothing, which is the helper this SQL reimplements (R1/R2). Do not fix this by dropping the CHECK constraint — it is what makes the drift visible, and removing it converts a loud `IntegrityError` into an unconstrained status column. Pair the sides: an ALLOW test that writes each of the four legitimate statuses through the real model and commits, and a DENY test that writes `'failed'` (the old spelling) and asserts `IntegrityError`. Red-prove each clause separately by execution against a real Postgres: revert the constraint to `'failed'` and watch the `failed_permanent` allow case redden; drop the CHECK entirely and watch the `'failed'` deny case redden. Fail loudly when the check cannot run — if no database is available the test must error, not skip silently, since a skipped constraint test is exactly how this reached the diff. Boundary and tie: state that an empty string and `NULL` are both rejected (the column is `NOT NULL`), and that adding a fifth status requires editing `STATUSES` only.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the index makes `event_id` unique across the whole table, but `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the fan-out the feature exists to provide violates its own schema.
What breaks in production: the first org that registers a second endpoint gets an `IntegrityError` on `session.add_all`, which `dispatcher.dispatch` swallows with `log.warning`, so that org silently receives **zero** webhooks for every event — including the org that had one working endpoint and adds a second.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint actually wanted: at-most-once enqueue per endpoint per event, matching the docs' "deduplicate on `event_id`" contract per destination. Preserve the property the current index was reaching for — idempotent re-enqueue must still be impossible to duplicate, so pair the insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` in `enqueue_for_event` rather than letting the retry path raise. Pair the sides: an ALLOW test enqueueing one event to two active endpoints of the same org and asserting two rows exist, and a DENY test enqueueing the same `(endpoint_id, event_id)` twice and asserting exactly one row remains. Red-prove each clause separately by execution: restore the single-column unique index and watch the two-endpoint allow test redden with `IntegrityError`; drop the unique index entirely and watch the duplicate deny test redden with a count of 2. Fail loudly when the check cannot run: assert the index exists in `pg_indexes` before asserting behavior, so a migration that never applied reads as an error rather than a pass. Boundary and tie: state that two *different* orgs' endpoints receiving the same `event_id` is legitimate and must not conflict — the current index forbids it and the composite one permits it — and that an event with zero matching endpoints inserts zero rows without error.

### Critical: any `http://` URL, including internal and metadata addresses, is accepted and its response body is stored and served
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`); `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`), `_finish(..., response.text)`
What is wrong: the URL check is a surface-form prefix test that admits plaintext `http://`, admits any scheme merely beginning with those four characters (`httpx://`, `http+unix://`), and applies no network policy at all, while the delivery client follows redirects and `_finish` persists the full response body — contradicting the doc's "Only `https://` URLs are accepted" (RS3, R47, R49).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or an https URL that 302s there), our worker issues the request from inside the VPC, and the credential response is written into `webhook_deliveries.response_body` — a full read-SSRF with a persistence layer, and separately every plain-`http` endpoint ships customer billing payloads in cleartext.
Fix: validate with equality, not prefix — `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)` — then resolve `parsed.hostname` with `socket.getaddrinfo` at registration and reject when any resolved address satisfies `ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast`; set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure; and re-check the resolved address at send time (registration-time DNS is not send-time DNS — a rebinding TTL of 1s defeats a check done only at registration). Do not fix this by dropping `_finish`'s response capture, which is what makes failures diagnosable — instead cap it, `detail[:2048]`, and never return `response_body` through the API. Cross-cutting: `create_webhook_endpoint` is the only URL entry point in the diff, but the same `startswith` shape governs nothing else here, so no second site is missed; the send-time check is a new obligation on `send_once`. Pair the sides: ALLOW fixtures for `https://hooks.example.com/acme` and for an https host resolving to a public address (both must still register and still deliver); DENY fixtures for `http://hooks.example.com`, `httpx://x`, `https://localhost`, `https://169.254.169.254`, `https://10.0.0.1`, and an https endpoint whose handler returns a 302 to `http://127.0.0.1`. Per RT8 the deny cases assert not only the 422/permanent-failure status but that no row was inserted and no request left the process. Red-prove each clause separately by execution — one mutation each: revert `!=` to `startswith` (the `httpx://` deny reddens); remove the private-range check (the `10.0.0.1` deny reddens); restore `follow_redirects=True` (the redirect deny reddens); remove the send-time re-resolution (a rebinding fixture whose second lookup returns 127.0.0.1 reddens). Fail loudly when adjudication is impossible: DNS resolution failure or `NXDOMAIN` must reject the registration with a named error, never fall through to "no bad address found". Boundary and tie: state which side `0.0.0.0`, IPv6 `::1`, IPv4-mapped `::ffff:10.0.0.1`, and a hostname resolving to *both* a public and a private address fall on — the last must be rejected, since resolving to any private address is disqualifying.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver` (`time.sleep(delay)`)
What is wrong: `deliver` is `async` and is fanned out with `asyncio.gather` over a batch of up to `BATCH_SIZE = 100`, but the retry backoff uses the synchronous `time.sleep`, which blocks the single event loop thread rather than yielding.
What breaks in production: one failing endpoint freezes the entire process for up to 2+4+8+16 = 30 seconds of sleeping plus its HTTP timeouts, so `asyncio.gather` degrades to strictly serial execution and a batch of 100 failing deliveries stalls the loop — and every other coroutine sharing that loop, including any HTTP server in the same process — for well over an hour.
Fix: use `await asyncio.sleep(delay)`; `asyncio` is already imported in this module and already used correctly in `run_worker`, so the async-sleep path is the established one this line reimplements (R1/R17). Better still, and consistent with the durability finding below, replace the in-process sleep with a persisted reschedule: write `next_attempt_at = _now() + backoff_for(attempt)`, `attempts = attempt`, `status = "pending"` and return, letting the next poll pick it up. Preserve the behavior the sleep provided: the delay between attempts must remain non-zero and monotonically increasing, which is what `test_backoff_grows_exponentially` pins, and `MAX_ATTEMPTS` must still cap total attempts at 5. Pair the sides: an ALLOW test asserting two `deliver` coroutines for two slow endpoints complete concurrently — total wall time under the sum of their individual delays, proving the loop yields — and a DENY test asserting a delivery still stops after exactly 5 attempts. Red-prove each clause separately by execution: restore `time.sleep` and watch the concurrency assertion redden on wall-clock; raise `MAX_ATTEMPTS` in the mutation and watch the attempt-count assertion redden. Do not write these with a real 30-second sleep — inject the clock so the tests do not need `sleep` at all, and fail loudly if the injected clock was never called rather than passing on a code path that skipped the backoff entirely. Boundary and tie: state that `attempt == MAX_ATTEMPTS` is the last attempt made (not the first one skipped) and that `backoff_for` is never consulted for that attempt, so the 5th failure finalizes immediately.

### Major: retries are held in process memory, so `in_flight` is a state with no exit
File: `app/webhooks/delivery.py` — `deliver`, `_claim_batch`, `_finish`
What is wrong: `_claim_batch` moves rows to `in_flight` and `deliver` then loops all 5 attempts inside one coroutine without ever persisting `attempts` or advancing `next_attempt_at`, and no code path ever returns a row from `in_flight` to `pending` (R38, non-terminal transient state).
What breaks in production: a deploy, an OOM kill, or any exception outside `httpx.HTTPError` leaves every in-flight delivery wedged in `in_flight` forever — invisible to `_claim_batch`'s `status == "pending"` filter, reported to the customer as neither delivered nor failed, and with `attempts = 0` in the row despite four attempts having been made.
Fix: make each attempt a persisted transition — `deliver` performs exactly one `send_once`, then either `_finish(..., "delivered", ...)`, or on a retryable failure writes `status="pending"`, `attempts=attempt`, `next_attempt_at=_now() + backoff_for(attempt)`, or on exhaustion `_finish(..., "failed_permanent", ...)` — and add a reaper that returns rows stuck in `in_flight` past a lease deadline to `pending`, by adding a `claimed_at TIMESTAMPTZ` column and selecting `status='in_flight' AND claimed_at < now() - interval '5 minutes'`. The columns to do this (`attempts`, `next_attempt_at`, `status`) already exist and are currently written only once, at the end — the schema already encodes the durable design the code bypasses. Preserve the retry semantics customers were promised: at most 5 attempts total across all reclaims (the reaper must not reset `attempts`), and the documented 2/4/8/16s spacing. Pair the sides: an ALLOW test where a delivery failing once is re-claimed on the next poll and succeeds, ending `delivered` with `attempts == 2`; a DENY test where a row wedged in `in_flight` with `claimed_at` inside the lease window is NOT reclaimed. Red-prove each clause separately by execution: delete the reaper predicate and watch the wedge-recovery test redden; make the reaper reset `attempts = 0` and watch an assertion that a poisoned delivery terminates after 5 total attempts redden (an unbounded mutation must be bounded so it fails rather than loops). Fail loudly when the lease cannot be evaluated — a `NULL` `claimed_at` on an `in_flight` row is a corrupt state and must be logged and reclaimed, not silently ignored. Boundary and tie: state that a row whose `claimed_at` is exactly at the lease deadline is reclaimed, and that two reapers racing on the same row are resolved by the conditional update's row count, with the loser doing nothing.

### Major: the Redis lock is not atomic and is released without ownership
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker` (`await redis_client.delete(LOCK_KEY)`)
What is wrong: `_acquire_lock` does GET-then-SET-then-EXPIRE as three separate round trips so two workers can both observe an empty key and both proceed, the 60-second TTL is shorter than a single batch's worst case (5 attempts × `REQUEST_TIMEOUT` 30s plus 30s of backoff), and the `finally` block deletes the key unconditionally, including when it now belongs to a different worker.
What breaks in production: two or more workers claim and deliver the same batch, so customers receive duplicate `invoice.paid` webhooks — and with no `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch` the duplicate claim is not caught at the database either.
Fix: acquire with a single atomic command carrying a per-worker token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL)` where `token = uuid4().hex` — release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`), renew the lease periodically while a batch is in flight, and independently add `.with_for_update(skip_locked=True)` to `_claim_batch` so correctness does not rest on the lock alone. Preserve the property the current code provides: a single worker must still make progress with no contention, and losing the lock must still lead to `asyncio.sleep(poll_interval)` rather than a busy loop. Pair the sides: an ALLOW test where one worker acquires, works, and releases, then a second worker acquires successfully; a DENY test where two `_acquire_lock` calls run concurrently and exactly one returns `True`. Per RT4 the concurrency test must be proven non-vacuous — assert both coroutines actually reached the acquire call (a counter incremented inside), or a test where one never ran passes for the wrong reason. Red-prove each clause separately by execution: revert to GET-then-SET and watch the exactly-one assertion redden; replace the compare-and-delete with an unconditional `delete` and watch a test where worker A's expired-and-reacquired lock survives worker B's release redden. Fail loudly when Redis is unreachable: `_acquire_lock` must propagate the error and the worker must stop claiming, never treat a connection failure as "lock free". Boundary and tie: state what happens when the TTL expires at exactly the moment the holder releases — the compare-and-delete finds a different token and does nothing, which is the correct no-op — and that the lease renewal interval must be strictly less than the TTL.

### Major: `run_worker` dies on the first exception, and can raise `NameError` doing it
File: `app/webhooks/delivery.py` — `run_worker`
What is wrong: `batch` is assigned inside `try` but read after the `finally` block, so any exception from `_claim_batch` leaves it unbound and the subsequent `if not batch` raises `NameError`; and because nothing catches exceptions from `asyncio.gather`, a single failing `deliver` propagates out of the `while True` loop entirely.
What breaks in production: the delivery worker exits on the first database blip or non-`httpx` exception and, with the lock deleted by `finally` and rows left `in_flight`, webhook delivery stops silently until someone notices the queue depth.
Fix: initialize `batch: list = []` before the `try`, wrap the claim-and-gather body in `except Exception: log.exception(...)` so the loop continues, and pass `return_exceptions=True` to `asyncio.gather` so one poisoned delivery cannot abort its 99 siblings. Preserve the loop's working behavior: an empty batch must still sleep `poll_interval` (not spin), and a non-empty batch must still poll again immediately. Pair the sides: an ALLOW test where a batch of two deliveries, one raising `ValueError`, still finalizes the other as `delivered`; a DENY test asserting the loop did not exit — run three iterations with a `_claim_batch` that raises on the first and assert iterations 2 and 3 executed. ### Major: the event is committed before the webhook rows, and the enqueue failure is swallowed
File: `app/events/dispatcher.py` — `dispatch` (`except Exception as exc: log.warning(...)`)

### Major: the dispatcher's hardcoded event allowlist contradicts the documented "empty subscribes to every event"

### Major: the implemented retry policy contradicts the documented one on two axes
File: `app/webhooks/delivery.py` — `deliver` (the `while True` loop), `backoff_for`; `docs/webhooks.md` — "Retries"
What is wrong: the docs promise "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx status equally through all 5 attempts and `backoff_for` returns a deterministic `2**attempt` with no jitter at all (R49, R29).
What breaks in production: a customer endpoint returning 400 or 404 is hammered 5 times for every event instead of failing fast, and because a whole batch shares one deterministic schedule, all failed deliveries retry in lockstep and re-converge on the same struggling endpoint at 2s, 4s, 8s and 16s.
Fix: branch on the status class — `if 400 <= response.status_code < 500 and response.status_code not in (408, 425, 429): _finish(..., "failed_permanent", ...); return` — and add jitter as full jitter over the computed delay: `timedelta(seconds=random.uniform(0, BASE_DELAY_SECONDS ** attempt))` using `random` (non-cryptographic is correct here, unlike in `signing.py`). Preserve the documented spacing as a bound rather than deleting the test that pins it: rewrite `test_backoff_grows_exponentially` to assert `0 <= backoff_for(n) <= 2**n` and that the *ceiling* still doubles, instead of removing the assertion. Pair the sides: ALLOW cases that 500, 429, and a `ConnectError` are each retried; DENY cases that 400, 404 and 422 finalize as `failed_permanent` after exactly one attempt with no sleep. Red-prove each clause separately by execution: remove the 4xx branch and watch the 404 deny case redden on `attempts == 1`; add 429 to the permanent set and watch the 429 allow case redden; fix jitter to a constant and watch a test asserting 50 samples produce more than one distinct delay redden. Fail loudly when the status cannot be classified — a transport error with no status must take the retry path explicitly, and an unexpected 1xx/3xx must be logged and treated as permanent, never fall off the end of the branch. Boundary and tie: state which side 429 and 408 fall on (retryable), and that exactly 400 is permanent while exactly 500 is not.

### Major: timestamps mix naive and aware values, and the migration's column types contradict the model's
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`) vs `_claim_batch` (`datetime.now(timezone.utc)`); `migrations/0042_webhook_delivery.sql` (`TIMESTAMP`) vs `app/webhooks/models.py` (`DateTime(timezone=True)`)

Red-prove each clause separately by execution: revert one site to `datetime.utcnow()` and watch the non-UTC allow test redden; revert the column to `TIMESTAMP` and watch it redden for the other reason, each naming its own failure. Fail loudly rather than coercing: add an assertion (or a model validator) that any datetime bound to these columns has `tzinfo is not None`, so a future naive value raises at the boundary instead of being silently interpreted. Boundary and tie: state that a row whose `next_attempt_at` equals `now` exactly IS claimed (`<=`), and that two rows sharing an identical `next_attempt_at` have no defined relative order — see the ordering finding below.

### Major: the delivery path logs full request headers and stores unbounded remote-controlled response bodies

### Major: the delivery tests never verify that a receiver can verify, and the `verify` tests are self-referential

### Minor: `ORDER BY created_at` is not a total order
File: `app/api/routes/settings.py` — `list_deliveries` (`.order_by(WebhookDelivery.created_at.desc()).limit(limit)`)
What is wrong: `created_at` defaults to `now()`, which in Postgres is transaction-start time, so all deliveries enqueued for one event in one transaction share a byte-identical timestamp and their relative order under `LIMIT` is undefined (R57).
