### Critical: the bytes that are signed are not the bytes that are sent, and the timestamp is not covered by the MAC
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` computes the HMAC over `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes itself with its own key order and separators, and the timestamp header is generated but never fed into the MAC — so the digest does not authenticate the request body that was actually sent, nor the timestamp.
What breaks in production: every receiver that implements `docs/webhooks.md` (HMAC of `"{timestamp}.{raw_request_body}"`) rejects 100% of our deliveries because the documented preimage is not the one we signed, and the replay window the doc advertises is unenforceable since an attacker can rewrite `X-Acme-Timestamp` without invalidating the signature.
Fix: change `sign(secret, body: bytes) -> tuple[str, str]` to compute `ts = str(int(time.time()))` and `hmac.new(secret.encode(), f"{ts}.".encode() + body, hashlib.sha256)`; in `send_once` build `body = serialize(delivery.payload).encode()` once and post it with `content=body` plus an explicit `Content-Type: application/json`, so the signed bytes and the wire bytes are the same object rather than two serializations. Preserve, do not delete, the properties that made this visible: `serialize` keeps `sort_keys=True` (stable digests for identical payloads) and `send_once` keeps returning the response unchanged. Pin the allow side: a round-trip test that captures `request.content` from `httpx.MockTransport` and asserts `verify(SECRET, captured_ts, captured_body, captured_sig)` is True — this is the assertion the current `test_send_once_posts_the_signed_payload` omits, since it checks only the `sha256=` prefix and the 64-hex length, which stay true under the mismatch. Red-prove the two clauses separately: (a) revert `content=body` to `json=delivery.payload` and observe the round-trip assertion go red on body bytes; (b) drop the `f"{ts}."` prefix from the MAC input and observe a separate assertion — signing the same payload at two different timestamps must yield two different signatures — go red. Fail loudly rather than silently: if `serialize` raises `TypeError` on a non-JSON-serializable payload, let it propagate and mark the delivery `failed_permanent` with the exception text; do not fall back to `str(payload)`. Boundary and tie: state in the doc and enforce in `verify` that the age check is `now - ts <= 300` inclusive (a request whose timestamp is exactly 300s old is accepted, 301 rejected), and that two deliveries sharing one timestamp are independent — the timestamp is not a nonce and must not be used for dedupe.

### Critical: signature comparison is not constant time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the reference verifier compares a computed HMAC against an attacker-supplied string with Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: an attacker with a signing oracle can recover a valid signature byte-by-byte from response-timing differences, forging events into any receiver that uses our published verifier, and `docs/webhooks.md` tells customers to "compare it against your own computation using a constant-time comparison" — advice our own implementation does not follow.
Fix: `return hmac.compare_digest(expected, signature)`, with `signature` first coerced with `if not isinstance(signature, str): return False` so a non-string header cannot reach `compare_digest` and raise. Preserve the existing accept behaviour: keep the `sha256=` prefix in both operands so the comparison remains over the full header value, and do not "simplify" by stripping the prefix from one side only. Pin the allow side: `test_verify_accepts_signature_produced_by_sign` must stay green. Red-prove separately: (a) replace `compare_digest` with `==` and confirm a new test asserting `verify` is called through `hmac.compare_digest` (patch and assert-called) goes red; (b) pass a `bytes` signature and confirm the isinstance guard returns False instead of raising. Fail loudly: a missing or empty `X-Acme-Signature` must return False from a named branch, not be spelled the same as a mismatch in the logs. Boundary and tie: two candidate signatures of unequal length must compare False without leaking the length through an early return — `compare_digest` handles this; do not add a `len(...) != len(...)` fast path in front of it.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice` over a base62 alphabet, and `random` is the Mersenne Twister — a deterministic generator whose entire internal state is recoverable from 624 observed outputs, seeded per process.
What breaks in production: an attacker who registers a handful of endpoints of their own observes enough generator output to reconstruct the state and predict the secrets minted for other organizations, letting them forge signed events into other customers' receivers.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and `import secrets`, deleting the `random`/`string` imports and `_ALPHABET`; rename `SECRET_BYTES` honestly (it is currently a character count, not a byte count) or keep the name and document that it is the entropy input in bytes. Do not fix by deleting the property the test relied on: keep an explicit length invariant so the secret stays fixed-width, but assert it as `len(secret) >= len(SECRET_PREFIX) + 32` rather than exact equality, since `token_urlsafe(32)` yields 43 characters — `test_new_signing_secret_has_prefix_and_length` will otherwise go red for the wrong reason and be "fixed" by reverting the RNG. Pin the allow side: the prefix assertion and a new "two consecutive calls differ" assertion must stay green. Red-prove separately: (a) `random.seed(0)` before two calls and assert they differ — red under the current code, green after; (b) monkeypatch `secrets.token_urlsafe` to raise and confirm registration returns a 5xx rather than a secret. Fail loudly: if entropy is unavailable the exception must propagate out of `create_webhook_endpoint`; there must be no fallback path that mints a weaker secret. Boundary and tie: two endpoints of the same org must never receive the same secret — assert distinctness across a batch of 1000 generated secrets.

### Critical: the signing secret is readable back on every list call
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict` unconditionally includes the secret, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` hands out the HMAC key for every endpoint in the org — directly contradicting `docs/webhooks.md`, which states the create response "is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation).
What breaks in production: any principal holding a read-scoped credential for the org — a leaked read-only API key, a support session, an over-broad OAuth grant, a browser devtools log — obtains the key needed to forge events into the customer's receiver, and the doc's promise means customers will not treat the list endpoint as secret-bearing.
Fix: remove `signing_secret` from `to_dict`, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held plaintext so the secret is emitted at exactly one call site. Cross-cutting check performed: `WebhookDelivery.to_dict` carries no secret, and no other serializer in the diff exposes one — this is the only site. Pin the allow side, which is what makes this fix incomplete without it: creation must still return the secret exactly once (assert the 201 body contains `signing_secret`), and because the secret becomes unreadable there must be a rotation path — add `POST /v1/settings/webhook-endpoints/{id}/rotate-secret`, org-scoped, returning the new plaintext once. Do not fix by deleting the feature: endpoint listing must still return `id`, `url`, `event_types`, `active`. Red-prove separately: (a) assert `"signing_secret" not in` any element of the list response — red today; (b) assert the create response does contain it — red if the fix over-tightens by removing it from both paths. Fail loudly: rotation must invalidate nothing retroactively but must return an error naming the endpoint if `id` does not belong to the caller's org, never a silent no-op. Boundary and tie: state which secret signs a delivery already claimed but not yet sent at the instant of rotation — sign with the secret read at `send_once` time, and document the resulting overlap window.

### Critical: delivery history is readable across organizations
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` with no join back to `WebhookEndpoint.org_id == user.org_id`, while its sibling `list_webhook_endpoints` three lines above does filter on `org_id` — the tenancy predicate was propagated to one new route and not the other (R3, security-relevant).
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other organizations' delivery records — event types, timestamps, success/failure status — a cross-tenant disclosure that also reveals which customers are on which billing events, and `docs/webhooks.md` states this route returns deliveries "for an endpoint belonging to your organization", so the claim is relied on.
Fix: join through the endpoint and scope by org — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the response does not distinguish "not yours" from "does not exist". Cross-cutting check performed: `create_webhook_endpoint` sets `org_id` from `user`, `list_webhook_endpoints` filters on it, and `enqueue_for_event` filters on it; `list_deliveries` is the only unscoped site in the diff. Pin the allow side: an owner listing their own endpoint's deliveries must still receive them — assert a non-empty body for the owning org in the same test that asserts 404 for the foreign org, or a fix that always denies passes. Red-prove separately: (a) delete the `org_id` filter and confirm the foreign-org test goes red; (b) delete the owner test's fixture endpoint and confirm the allow assertion goes red rather than silently passing on an empty list. Fail loudly: if `endpoint_id` resolves to no row the handler raises `HTTPException(404)`; it must not return `[]`, which is indistinguishable from an endpoint with no deliveries. Boundary and tie: an endpoint whose owning org was deleted (`ON DELETE CASCADE` in `migrations/0042_webhook_delivery.sql`) has no row to join, so it falls on the deny side — state that explicitly.

### Critical: the migration's status CHECK constraint omits the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: `app/webhooks/models.py` defines `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` and the code writes `"failed_permanent"`, but the migration allows `'failed'` — the member set was retyped by hand in a third place instead of derived from the one existing constant (R42/R2; note `STATUSES` is defined and then never referenced by anything in the diff).
What breaks in production: the first delivery to exhaust its attempts raises a `CheckViolation`, the `_finish` transaction aborts, the exception propagates out of `deliver` and out of `asyncio.gather`, and the row is left permanently in `in_flight` — so the terminal-failure path, the only path that records why a customer's webhook stopped, can never be written at all.
Fix: change the migration's CHECK to `status IN ('pending', 'in_flight', 'delivered', 'failed_permanent')` — the migration is unreleased, so amend it rather than adding a follow-up — and make the constraint and the ORM read from one source by generating the SQL list from `models.STATUSES` in a test that compares the parsed `CHECK` literal set against `set(STATUSES)`, so the next added status cannot drift again. Do not fix by widening the constraint away: keep the CHECK; dropping it to make the write succeed is exactly the "delete what made the defect visible" remedy. Pin the allow side: inserting each of the four `STATUSES` values must still succeed, and a fifth value (`'bogus'`) must still be rejected — without the second half a fix that drops the constraint passes. Red-prove separately: (a) revert the CHECK to `'failed'` and confirm the `failed_permanent` insert test goes red; (b) remove `'bogus'` from the reject test and confirm the constraint-still-enforced test goes red. Fail loudly: if the constraint-vs-`STATUSES` comparison test cannot locate the CHECK clause in the migration file, it must fail with "constraint not found", never pass by comparing two empty sets. Boundary and tie: `in_flight` is the only non-terminal member — say so in the constant and ensure the reaper (see the `in_flight` finding below) is keyed on exactly that member, not on "not delivered".

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the index is unique on `event_id` alone, but `app/webhooks/delivery.py` — `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, so a single event fanning out to two endpoints violates the index.
What breaks in production: any org with more than one subscribed endpoint gets an `IntegrityError` on commit, which `app/events/dispatcher.py` catches with `except Exception: log.warning(...)` — so the whole `add_all` batch rolls back, no endpoint receives the event, and the only trace is a warning line; the feature silently fails for exactly the customers who use it most.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which keeps the property the index was presumably for — one delivery row per endpoint per event, so a retried `enqueue_for_event` cannot duplicate — while permitting fan-out. Preserve that idempotency rather than dropping the uniqueness: pair it with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` on the insert path so a redelivered event is a no-op instead of an error. Pin the allow side: a test asserting two endpoints in one org both receive a row for one event must be green, alongside a test asserting a second `enqueue_for_event` call for the same `(endpoint, event)` inserts zero additional rows. Red-prove separately: (a) restore the single-column unique index and confirm the two-endpoint test goes red; (b) drop the `ON CONFLICT` clause and confirm the re-enqueue test goes red on row count. Fail loudly: `enqueue_for_event` must not swallow an `IntegrityError`; any conflict outside the declared `(endpoint_id, event_id)` pair must propagate to the caller. Boundary and tie: an org with zero matching endpoints inserts zero rows and must return 0 rather than raising — that is the tie between "no subscribers" and "insert failed", and the two must not be spelled the same.

### Critical: any customer-supplied URL is fetched, including internal addresses, with redirects followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only validation is a `startswith("http")` prefix test on the scheme and a non-empty netloc — which admits `http://` (contradicting `docs/webhooks.md`: "Only `https://` URLs are accepted"), admits any scheme spelled `http…` such as `httpx://`, and performs no resolution or address check, while the delivery client follows redirects (RS3: surface-form validation of a value whose meaning is defined by the HTTP client).
What breaks in production: an authenticated tenant registers `http://169.254.169.254/latest/meta-data/` — or any external URL that 302-redirects there — and our worker fetches it from inside the VPC with our own headers attached, returning the response body into `response_body` where the tenant reads it back via the deliveries endpoint; this is a full SSRF read primitive against cloud metadata and internal services.
Fix: validate at the schema boundary, not in the handler body — make `EndpointIn.url` a `pydantic.HttpUrl` and add a validator that requires `scheme == "https"` exactly (equality, not `startswith`), rejects userinfo in the netloc, rejects a non-default port outside `{443}` unless allowlisted, and resolves the host with `socket.getaddrinfo`, rejecting any resolved address for which `ipaddress.ip_address(addr).is_private or .is_loopback or .is_link_local or .is_reserved` is true. Because DNS can be re-pointed between registration and delivery, repeat the address check at connect time via a custom `httpx.AsyncHTTPTransport` that validates the peer address, and set `follow_redirects=False` so a 3xx is recorded as a delivery failure rather than chased into the network. Do not fix by deleting the feature: `https://` endpoints on public addresses, including those on non-standard ports if allowlisted, must still deliver. Pin the allow side explicitly: a test registering `https://hooks.example.com/acme` against a public test address must still return 201 and must still deliver, or a validator that rejects everything satisfies every other clause. Red-prove separately: (a) `http://` URL rejected with 422; (b) `https://127.0.0.1/x` rejected with 422; (c) an endpoint that 302s to `http://169.254.169.254/` records a failed delivery and issues no second request (assert the mock transport saw exactly one request). Fail loudly: when `getaddrinfo` raises (DNS down), registration must return an error naming DNS failure — an unresolvable host must never be admitted as "could not check, so allow". Boundary and tie: a hostname resolving to both a public and a private address must be rejected (any-private denies), and `0.0.0.0`/`::` fall on the deny side.

### Critical: the retry loop blocks the event loop and keeps retry state in memory
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)` inside `while True`
What is wrong: a blocking `time.sleep` is called inside an `async def` that `run_worker` schedules through `asyncio.gather`, and the retry loop lives in process memory — `next_attempt_at` is never advanced and `attempts` is never persisted between attempts, so the `WebhookDelivery` columns that exist to schedule retries are dead while the real schedule sits on the stack.
What breaks in production: one failing endpoint stalls the entire event loop for up to 2+4+8+16 = 30 seconds per delivery — with a batch of `BATCH_SIZE = 100` gathered coroutines the sleeps serialize into tens of minutes during which no other delivery, and no Redis lock refresh, can run; the 60-second lock TTL expires mid-batch and a second worker starts re-delivering the same rows, and any worker restart loses all in-memory retry state, leaving the rows stuck in `in_flight`.
Fix: delete the in-process loop and make `deliver` perform exactly one attempt: on 2xx call `_finish(..., "delivered", ...)`; on a retryable failure with `attempt < MAX_ATTEMPTS` write `attempts = attempt`, `status = "pending"`, `next_attempt_at = now + backoff_for(attempt)` in the same transaction; otherwise `_finish(..., "failed_permanent", ...)`. The scheduler is then `_claim_batch`'s existing `next_attempt_at <= now` predicate, which is what that column was for. Preserve the retry behaviour rather than removing it: attempts must still cap at `MAX_ATTEMPTS` and the delay sequence must still be 2/4/8/16 seconds (plus the jitter the docs promise — see the retry-policy finding). Pin the allow side: a delivery that succeeds on its first attempt must still be marked `delivered` with `attempts == 1` and must never be re-claimed. Red-prove each clause separately: (a) reinstate `time.sleep` and confirm a test asserting `deliver` returns within 100 ms of a failed attempt goes red; (b) drop the `next_attempt_at` write and confirm a test asserting the row is re-claimable only after the backoff interval goes red; (c) drop the `attempts = attempt` write and confirm a test asserting the fifth attempt terminates the row goes red. Fail loudly: if the reschedule write raises, the row must not be left `in_flight` — wrap the attempt so any exception routes to a `pending`/`next_attempt_at` reschedule with the exception text in `response_body`. Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal condition, so attempt 5 is the last one made and there is no sixth; and a row whose `next_attempt_at` equals `now` exactly is claimable (`<=`).

### Critical: one bad row kills the worker permanently
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`; `_finish`, `row = session.get(...)` with no None check
What is wrong: `gather` is called without `return_exceptions=True` and the `while True` loop has no exception handler, so any non-`httpx.HTTPError` raised by a single delivery — the `CheckViolation` from the status constraint above, an `AttributeError` when `_finish`'s `session.get` returns None because the endpoint was deleted under `ON DELETE CASCADE`, an `httpx.UnsupportedProtocol` from an `httpx://` URL — propagates out of the `try/finally`, out of the loop, and terminates `run_worker`.
What breaks in production: a single malformed or racing delivery stops all webhook delivery for every customer until someone notices and restarts the process, and because the crash happens after `_claim_batch` flipped the batch to `in_flight`, those hundred rows are never retried even after the restart.
Fix: pass `return_exceptions=True` to `gather` and iterate the results, routing each `Exception` to `_finish(delivery.id, "failed_permanent", attempt, None, repr(exc))` with a `log.exception` carrying the delivery id; wrap the body of the `while True` in its own `try/except Exception` that logs and continues after `await asyncio.sleep(poll_interval)`; and in `_finish` raise a named `DeliveryRowMissing(delivery_id)` when `session.get` returns None instead of dereferencing None. Do not fix by broadening `except httpx.HTTPError` to bare `except Exception` inside `deliver` — that would hide the programming errors this finding is about; the recovery must be explicit and must record the failure on the row. Pin the allow side: a batch of three deliveries where one raises must still mark the other two `delivered` — assert both the survivor count and that the loop performed another iteration afterwards. Red-prove separately: (a) remove `return_exceptions=True` and confirm the survivor-count test goes red; (b) remove the loop-level `except` and confirm a test asserting the worker still polls after a raising batch goes red; (c) restore the unchecked `session.get` and confirm the deleted-endpoint test goes red with `AttributeError` rather than the named exception. Fail loudly: `DeliveryRowMissing` must be logged at error with the id — "row vanished" must not be spelled the same as "delivery succeeded". Boundary and tie: a batch of exactly zero rows must not raise and must fall through to the `poll_interval` sleep.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`), `deliver` (`endpoint` read outside its `with`)
What is wrong: `_claim_batch` returns SQLAlchemy entities out of the `with session_scope()` block and `deliver` reads `endpoint.url` / `endpoint.signing_secret` and `delivery.payload` / `delivery.attempts` / `delivery.id` after their sessions have exited — under SQLAlchemy's default `expire_on_commit=True` every one of those attribute reads triggers a refresh on a detached instance.
What breaks in production: if `session_scope` commits with default settings the worker raises `DetachedInstanceError` on the first attribute access, so no delivery is ever sent; if it does not expire on commit the reads return values that may already be stale, which is the quieter failure. I cannot see `app/db.session_scope` in this change, so state which it is — that is what closes this finding.
Fix: stop passing entities across the boundary. Have `_claim_batch` return plain tuples or a small frozen dataclass — `(delivery_id, endpoint_id, event_type, payload, attempts)` — materialized inside the session, and have `deliver` open its own short session to read `endpoint.url` and `endpoint.signing_secret` immediately before `send_once`, which also picks up a rotated secret rather than a stale one. Preserve the batching: `_claim_batch` must still mark the claimed rows `in_flight` in the same transaction that selected them, and must still return `BATCH_SIZE` rows at most. Pin the allow side: a test that runs `_claim_batch` and then reads every field of the returned objects outside any session must succeed. Red-prove separately: (a) return the ORM entities again and confirm that test goes red; (b) delete the `row.status = "in_flight"` assignment and confirm a test asserting a second `_claim_batch` returns zero rows goes red. Fail loudly: if the endpoint row is gone when `deliver` re-reads it, mark the delivery `failed_permanent` with "endpoint deleted" rather than proceeding with a None. Boundary and tie: two rows sharing the same `next_attempt_at` must both be claimed by the same call or neither — see the ordering finding below.

### Major: the delivered payload carries no event identifier, so the documented dedupe key does not exist
File: `app/webhooks/delivery.py` — `send_once` (headers and `json=delivery.payload`); `docs/webhooks.md` — "delivery is at-least-once, so deduplicate on `event_id`"
What is wrong: the POST body is `envelope.payload` verbatim, and the headers are only `Content-Type`, `User-Agent`, `X-Acme-Timestamp` and `X-Acme-Signature` — `WebhookDelivery.event_id` is stored on our side but never crosses the wire, so the key customers are told to dedupe on is not present in anything they receive (R41: a declared capability with no backing path).
What breaks in production: at-least-once delivery combined with no dedupe key means a duplicated `invoice.paid` is indistinguishable from a second real payment on the receiver's side — customers double-fulfil orders and cannot implement the mitigation the doc prescribes.
Fix: wrap the body in an envelope — `{"id": f"evt_{delivery.event_id}", "type": delivery.event_type, "created_at": <iso8601>, "data": delivery.payload}` — sign that serialized envelope, and additionally emit `X-Acme-Event-Id` and `X-Acme-Delivery-Id` headers so a receiver can dedupe without parsing the body. Note the test fixture already assumes this shape (`FakeDelivery.payload = {"id": "evt_1", "type": "invoice.paid", ...}` and the assertion `json.loads(captured["body"])["type"] == "invoice.paid"`), while production sends the bare payload — the fake and the producer disagree, which is why the test passes over the gap (RT1). Preserve the payload contents: `data` must be byte-identical to what `enqueue_for_event` stored. Pin the allow side: a round-trip test asserting `json.loads(body)["data"] == stored_payload` and `json.loads(body)["id"] == "evt_<n>"` for a real `WebhookDelivery`, not for `FakeDelivery`. Red-prove separately: (a) revert to `json=delivery.payload` and confirm the `["id"]` assertion goes red; (b) change the stored payload and confirm the `["data"]` assertion goes red. Fail loudly: a delivery whose `event_id` is None must be marked `failed_permanent` rather than shipped with a null id. Boundary and tie: two deliveries of the same event to two endpoints share one `event_id` and differ in `X-Acme-Delivery-Id` — say which one the receiver dedupes on (the event id).

### Major: the dispatch lock is not atomic, is released unconditionally, and claims on a non-total order
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`, `_claim_batch`'s `order_by(next_attempt_at)`
What is wrong: `_acquire_lock` does a GET then a separate SET with a separate EXPIRE — three non-atomic round trips, so two workers starting together both observe an absent key and both proceed; the release deletes the key without checking ownership, so a worker whose 60-second TTL already expired deletes the successor's lock; and `_claim_batch` orders by `next_attempt_at`, which is not unique (an entire fan-out shares one instant), so concurrent claimants see overlapping candidate sets (R57).
What breaks in production: the same delivery is POSTed twice or more to a customer endpoint, which — given the previous finding, that no event id crosses the wire — the receiver cannot deduplicate.
Fix: acquire with a single atomic `SET key <token> NX EX 60` where `<token>` is a per-acquisition `secrets.token_hex(16)`, release with a Lua compare-and-delete (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so only the owner can release, and refresh the TTL between batches. Make the claim itself the authority rather than the lock: `SELECT ... WHERE status='pending' AND next_attempt_at <= now ORDER BY next_attempt_at, id LIMIT :n FOR UPDATE SKIP LOCKED`, which gives a total order and makes concurrent claims disjoint by construction. Preserve single-worker throughput: with one worker running, a batch of 100 due rows must still be claimed in one call. Pin the allow side: after a correct release, the next `_acquire_lock` must succeed — a fix that never releases satisfies mutual exclusion and breaks the worker. ### Major: the retry policy contradicts the published contract in two ways
