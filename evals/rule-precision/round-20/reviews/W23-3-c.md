### Critical: `list_deliveries` has no tenancy filter — any authenticated user can read any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The two sibling handlers added in the same hunk (`create_webhook_endpoint`, `list_webhook_endpoints`) scope every query by `user.org_id`, but this handler filters only on the caller-supplied `endpoint_id`, so the org predicate is missing from exactly the endpoint that returns event bodies (R3, incomplete pattern propagation, security-relevant).
What breaks in production: Any authenticated tenant can enumerate integer `endpoint_id`s and read another organization's `invoice.paid` / `subscription.updated` delivery rows, and `WebhookDelivery.to_dict()` exposes `event_id`, `event_type`, `status` and `response_status` for each — a cross-tenant data breach reachable with a single GET.
Fix: Join to `WebhookEndpoint` and filter on both keys — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the response does not disclose whether the id exists. Pin both directions with two tests that go through the real route (TestClient, not the model): the owning org still receives its rows (allow side — a fix that always denies satisfies every other clause), and a second org receives 404 with an empty list. Red-prove each clause separately by execution: mutation A deletes the `org_id` predicate and must redden only the cross-tenant test; mutation B makes the owner's lookup return `[]` and must redden only the allow test. Where `user.org_id` is absent or `None`, deny and log rather than falling through to an unfiltered query — "could not determine the tenant" must not be spelled the same as "no rows". Preserve the existing `order_by(created_at.desc()).limit(limit)` shape; the boundary case is a delivery whose endpoint was deleted (the join drops it, which is the intended behaviour) and two endpoints sharing a `created_at` — see the ordering finding below.

### Critical: the HMAC is computed over different bytes than the ones actually sent, and does not cover the timestamp
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes with its own separators and unsorted keys, so the signed string and the wire body are different byte sequences; the timestamp header is generated but never fed into the MAC (R40, producer shape vs strict consumer).
What breaks in production: Every customer following `docs/webhooks.md` recomputes HMAC over the raw request body and gets a mismatch, so 100% of deliveries are rejected by correctly-implemented receivers, and because the timestamp is outside the MAC an attacker can replay a captured request with a fresh `X-Acme-Timestamp` and defeat the five-minute replay window the docs claim to provide.
Fix: Make one function produce both the body and the signature: `body = serialize(payload).encode()`; `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`; then send that exact `body` via `client.post(url, content=body, headers={"Content-Type": "application/json", ...})` — never `json=`, which re-serializes. Update `docs/webhooks.md` in the same commit so the documented `"{timestamp}.{raw_request_body}"` construction and the implementation are one statement, not two. Add a round-trip test that feeds the *actual* captured `request.content` from the MockTransport handler through `signing.verify` (actual producer output through the actual consumer), plus an allow-side test proving a correctly-signed request verifies true. Red-prove each clause separately: (i) revert `content=` to `json=` — the round-trip test must redden; (ii) drop the `f"{timestamp}."` prefix — a second test asserting that a request replayed with a different timestamp fails verification must redden; (iii) flip one payload byte — verification must fail. If `serialize` raises (non-JSON-serializable payload), let it propagate and mark the delivery `failed_permanent` with the exception text: an unsignable payload must never be sent unsigned. Preserve `sort_keys=True` — it is what makes the signature reproducible; the boundary case is two payloads differing only in key order, which must now produce identical bytes and identical signatures.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice`, which draws from a Mersenne Twister seeded from predictable process state and is explicitly not cryptographically secure; this is the sole key material for the whole webhook authenticity control.
What breaks in production: An attacker who observes ~624 outputs of the same process's `random` stream (or who can influence seeding) can reconstruct the generator state and derive other tenants' signing secrets, letting them forge webhook deliveries that every customer's verifier accepts as genuine.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random` and `string` imports and `_ALPHABET`; rename `SECRET_BYTES = 32` to mean what it says (`token_urlsafe(32)` yields 32 bytes of entropy rendered as 43 characters). Update `test_new_signing_secret_has_prefix_and_length` to assert the character length of the base64url encoding rather than `SECRET_BYTES`, and add an assertion that 1,000 generated secrets are all distinct (allow side: generation must still succeed and still carry the `whsec_` prefix that receivers key on). Red-prove separately: (i) swap `secrets.token_urlsafe` back to `random.choice` under a fixed `random.seed(0)` and assert two seeded runs differ — that test must redden; (ii) drop `SECRET_PREFIX` — the prefix test must redden. If `secrets` cannot produce entropy the call raises; let it propagate and fail endpoint creation loudly rather than falling back to `random`. Boundary: existing rows already hold weak secrets, so ship a one-off rotation for every `webhook_endpoints` row created before this deploy and treat two endpoints that happen to receive identical secrets as an incident, not a collision to tolerate.

### Critical: `GET /v1/settings/webhook-endpoints` returns every endpoint's signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry
What is wrong: `to_dict()` embeds the secret and is used by both the create handler and the list handler, so the secret is readable on demand — directly contradicting `docs/webhooks.md`, which states the create response "is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: The secret is served on a routine GET, so it lands in browser caches, proxy logs, API-client history and any support tooling that mirrors settings responses, and anyone with read-only settings access can forge signed webhooks for that tenant.
Fix: Remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` using the value it just generated locally, so exactly one code path can emit it. Add a test asserting the create response contains `signing_secret` (allow side — the customer must still be able to obtain it once) and a second asserting the list response does not, for an org that owns an endpoint. Red-prove separately: (i) re-add the key to `to_dict()` — the list test must redden; (ii) drop the key from the create response — the create test must redden. If the secret is missing when the create response is assembled, raise rather than returning a 201 without it: a silently secret-less endpoint would sign with a value the customer never received. Preserve the rest of `to_dict()`'s shape (`id`, `url`, `event_types`, `active`), which the list endpoint's consumers need. Boundary: a re-issue/rotate route, if added later, is the only other place allowed to emit the value, and it must emit it once and not persist it in a response cache.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses Python's short-circuiting string equality instead of a constant-time comparison (RS1).
What breaks in production: This helper is the reference verifier shipped alongside the public documentation and is the one exercised by the test suite, so an attacker with network access to any service that adopts it can recover a valid signature byte-by-byte from response-time differences and forge deliveries.
Fix: `return hmac.compare_digest(expected, signature)`, with `hmac` already imported in this module. Keep both sides of the guard tested: `test_verify_accepts_signature_produced_by_sign` must still pass (allow side) and `test_verify_rejects_a_signature_made_with_another_secret` must still fail closed. Red-prove separately: (i) revert to `==` and run the repo's `check-timing-safe.sh` scan over the diff — it must report the line; (ii) mutate one hex character of `expected` — the reject test must redden. Handle the non-string case loudly: if `signature` is `None` or not a `str`, `compare_digest` raises `TypeError`; catch it at the call site and return `False` with a log line rather than letting an untyped header 500 the verifier. Boundary: a signature of the correct length that differs in the last character and one that differs in the first must take indistinguishable time, and a zero-length or wrong-length `signature` must return `False`, not raise.

### Critical: SSRF — URL validation accepts non-HTTPS and internal targets, and the client follows redirects
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` admits `http`, `httpx`, `http+unix` and anything else with that prefix (the docs claim only `https://` is accepted), and nothing rejects loopback, link-local or RFC1918 hosts, while `follow_redirects=True` means even a host that passed validation can bounce the request to an internal address.
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or a public host that 302s there) and the delivery worker fetches cloud instance credentials from inside the VPC and stores the response in `webhook_deliveries.response_body`, where the same tenant reads it back through the deliveries endpoint — full SSRF-to-credential-exfiltration.
Fix: Validate with `parsed.scheme != "https"` → 422, then resolve the hostname and reject any address in a loopback / link-local / private / reserved / multicast range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`; set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with a message naming the redirect target. Because DNS can be re-pointed after registration (TOCTOU), re-run the same address check inside `send_once` against the address actually connected to, using an httpx transport-level hook, rather than trusting the registration-time check. Pair deny with allow: one test registers `https://hooks.example.com/acme` and must still get 201 and must still be delivered to; others assert 422 for `http://`, for `httpx://`, and for `https://127.0.0.1/`, and assert a 302 to `http://169.254.169.254/` is recorded as `failed_permanent` with no second request. Red-prove each separately: drop the scheme check (the `http://` test reddens), drop the IP check (the loopback test reddens), re-enable `follow_redirects` (the redirect test reddens). When DNS resolution fails or the address is unresolvable, reject with an explicit "could not resolve endpoint host" error — never fall through to "no private address found, allow". Preserve the ability to register any legitimate public HTTPS endpoint; the boundary values to state are `169.254.169.253` (rejected, link-local) versus the first public address above the range, and a hostname resolving to both a public and a private address, which must be rejected.

### Critical: the status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/models.py` — `STATUSES`
What is wrong: The enum is duplicated in two places and the copies disagree — the model declares `failed_permanent` and `_finish` writes that exact string, while the constraint only permits `failed` (R2: one constant, two hardcoded spellings).
What breaks in production: The first delivery to exhaust `MAX_ATTEMPTS` raises an `IntegrityError` inside `_finish`, which propagates out of `deliver`, out of the `asyncio.gather` in `run_worker` and out of the `while True` loop, killing the delivery worker process — and every retry-exhausting delivery does it again after restart.
Fix: Change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make the model the single source: generate the SQL list from `models.STATUSES` in the migration test, or add a test that reads the constraint definition from `information_schema` and asserts set equality with `STATUSES`. Pair the sides: one test asserts a delivery that returns 200 lands as `delivered` (allow), another asserts a delivery exhausting `MAX_ATTEMPTS` lands as `failed_permanent` and does not raise. Red-prove separately: (i) revert the constraint spelling — the exhaustion test must redden with a constraint-violation message that names `status`; (ii) add `"failed"` to `STATUSES` without adding it to the constraint — the set-equality test must redden. Fail loudly if the constraint cannot be read (no such table, wrong schema) rather than treating an empty result as agreement. Preserve the constraint itself — deleting it to make the error go away removes the only thing that would catch the next spelling drift. Boundary: name the transition for a delivery that is `in_flight` when the process dies, which today matches no terminal state (see the stuck-`in_flight` finding).

### Critical: `UNIQUE INDEX ... (event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the unique index rejects the second and later rows of every fan-out.
What breaks in production: Any organization with two or more active endpoints gets an `IntegrityError` on the whole `add_all`, which the dispatcher catches with `except Exception: log.warning(...)`, so *zero* deliveries are created for that event and the only trace is a warning line — silent, total loss of outbound webhooks for exactly the customers who integrated most.
Fix: Replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which still gives the per-endpoint idempotency the docs promise ("deduplicate on `event_id`") while permitting fan-out. Pair the sides: a test enqueuing one event for an org with two active endpoints must produce exactly two rows (allow), and re-enqueuing the same `event_id` for the same endpoint must not create a third (deny). Red-prove separately: (i) restore the single-column index — the fan-out test must redden with a unique-violation; (ii) drop the index entirely — the re-enqueue test must redden by finding two rows for one endpoint. Make the dispatcher's failure loud rather than a `log.warning` (see the swallowed-exception finding), so "enqueue wrote nothing" can never be spelled the same as "enqueue had nothing to write". Preserve the dedup guarantee the index exists for. Boundary: state what happens when the same `(endpoint_id, event_id)` is retried concurrently — use `ON CONFLICT DO NOTHING` so the second inserter is a no-op rather than an error.

### Critical: `time.sleep` inside an `async` retry loop blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: A synchronous `time.sleep` is used inside a coroutine, so it blocks the event loop thread instead of yielding, and the backoff schedule (2+4+8+16 = 30s) plus up to five 30s request timeouts means one bad endpoint can hold the loop for minutes.
What breaks in production: `run_worker` gathers up to `BATCH_SIZE = 100` deliveries concurrently, but the first one to fail freezes all 99 others and every other coroutine on that loop — including the FastAPI request handlers if the worker shares a process — turning one slow customer endpoint into an application-wide stall.
Fix: Replace with `await asyncio.sleep(delay)` (`asyncio` is already imported). While there, stop retrying inside the coroutine at all and let the retry be a state transition: on a retryable failure write `status="pending"`, `attempts=attempt`, `next_attempt_at=_now() + backoff_for(attempt)` and return, so the poller picks it up — this is what `next_attempt_at` and the `backoff_for` helper already exist for, and it removes the coupling between retry duration and the 60s lock TTL. Pair the sides: a test asserting a 200 on the first try still finishes as `delivered` without any sleep (allow), and a test asserting a 500 schedules `next_attempt_at` exactly `backoff_for(1)` in the future and leaves the row `pending`. Red-prove separately: (i) restore `time.sleep` and assert with a monotonic-clock probe that the loop stayed responsive during the retry — that assertion must redden; (ii) drop the `next_attempt_at` update — the reschedule test must redden. If `backoff_for` overflows or returns a non-positive delay, refuse the reschedule and mark the delivery `failed_permanent` with a message naming the attempt number. Preserve `MAX_ATTEMPTS` as the terminal bound. Boundary: a delivery whose `next_attempt_at` is exactly `now` must be claimed (the existing `<=` is correct); two deliveries with the same `next_attempt_at` need a tie-break (see the ordering finding).

### Critical: the signature test never verifies a signature
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test captures the request body and the signature header but only asserts the header *starts with* `sha256=`; it never recomputes the MAC over `captured["body"]`, which is precisely the assertion that would expose the producer/wire byte mismatch reported above (RT5 — the test's call path reaches `send_once` but its assertions bypass the primitive the name claims to cover).
What breaks in production: The suite is green while every real receiver rejects every delivery, so the signature control ships broken with a test named as if it were verified — a reviewer reading "posts the signed payload" trusts a guarantee the test never checked.

Red-prove separately: (i) change `send_once` to sign a different dict than it posts — the verify assertion must redden; (ii) change it to omit the timestamp from the MAC — the raw-bytes assertion must redden. If the signature header is absent, the test must fail with a `KeyError` naming the header rather than silently skipping the assertion — do not wrap it in a truthiness guard. Preserve the existing content-type and payload assertions, which are the only things pinning the request shape. Boundary: state the behaviour for an empty payload `{}`, whose MAC is still well-defined and must be asserted rather than skipped.

### Major: rows claimed by `_claim_batch` are used after their session closes
File: `app/webhooks/delivery.py` — `_claim_batch` return value, and `deliver`'s use of `delivery.attempts` / `delivery.payload` / `delivery.id`; `endpoint` in `deliver`
What is wrong: Both `_claim_batch` and `deliver` return/keep ORM instances loaded inside a `with session_scope()` block and then read their attributes after the block exits, which under SQLAlchemy's default `expire_on_commit=True` triggers a refresh against a closed session; every pre-existing handler in `settings.py` builds its dicts *inside* the scope, so this is the first site in the diff to do otherwise.
What breaks in production: The first attribute access in `deliver` raises `DetachedInstanceError`, `asyncio.gather` propagates it out of `run_worker`, and no webhook is ever delivered — the feature is dead on arrival rather than degraded.
Fix: Have `_claim_batch` return plain data (`list[tuple[int, int, int, dict]]` of `id`, `endpoint_id`, `attempts`, `payload`) materialised inside the scope, and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside its own scope, so no ORM instance crosses a session boundary. Pair the sides: an integration test against a real session must show a claimed batch's payload readable after the scope exits (allow), and a test asserting `_claim_batch` returns no ORM instances (`not isinstance(row, m.WebhookDelivery)`) so the pattern cannot come back. Red-prove separately: (i) return the ORM rows again — the post-scope read test must redden with `DetachedInstanceError`; (ii) drop `payload` from the returned tuple — the payload assertion must redden. If the endpoint row is missing (deleted between enqueue and delivery), mark the delivery `failed_permanent` with "endpoint deleted" rather than dereferencing `None`. Preserve the `in_flight` claim write, which is what stops a second worker re-claiming. Open question that would close this at Minor instead: if `session_scope` is configured with `expire_on_commit=False`, only the missing-endpoint half stands.

### Major: `_acquire_lock` is a non-atomic check-then-set and its release has no ownership token
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by `set` is two round trips, so two workers can both observe an empty key and both proceed, and `set` followed by a separate `expire` leaves a permanent lock if the process dies between them; the release deletes the key unconditionally, including when it now belongs to a different worker.
What breaks in production: Concurrent workers claim overlapping batches and double-deliver, or — after a crash in the one-instruction window between `set` and `expire` — the key never expires and outbound webhooks stop entirely with no alarm and no reset path (R38: persisted fail-closed wedge with no explicit exit).
Fix: Use a single atomic call — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script that deletes only when the stored value equals `token`. Pair the sides: a test with two concurrent `_acquire_lock` calls asserts exactly one returns `True` (deny), and a test asserts the winner can release and a subsequent acquire then succeeds (allow — a lock that never releases satisfies the first test alone). Red-prove separately: (i) drop `nx=True` — the mutual-exclusion test must redden with two winners; (ii) drop `ex=60` — a test asserting the key carries a positive TTL immediately after acquisition must redden; (iii) release with a plain `delete` — a test where worker B holds the lock and worker A releases must redden. When Redis is unreachable, `_acquire_lock` must raise or return `False` with an error log naming the failure, never return `True`: "cannot tell whether another worker holds the lock" must not be spelled the same as "no worker holds it". Preserve the single-worker invariant the lock exists for. Boundary: state what happens when the TTL expires while the holder is still working — with per-delivery `in_flight` claims that is safe, without them it is a double delivery.

### Major: `run_worker` raises `UnboundLocalError` whenever `_claim_batch` fails
File: `app/webhooks/delivery.py` — `run_worker`, `if not batch:` after the `try/finally`
What is wrong: `batch` is assigned inside the `try` but read after the `finally`, so any exception from `_claim_batch` or `gather` leaves the name unbound — and since the `finally` has no `except`, the original exception escapes the `while True` loop anyway.
What breaks in production: A single transient database error terminates the delivery worker permanently; deliveries accumulate as `pending` until someone notices the process is gone.

Red-prove separately: (i) remove the `except` — the survival test must redden by propagating; (ii) remove the `log.exception` — the logging assertion must redden. Do not fix this by broadening the `except` to swallow `asyncio.CancelledError`; re-raise it so shutdown still works. Boundary: name the case of an empty batch versus a failed batch — both sleep, but only the second logs, and the two must be distinguishable in the logs.

### Major: `in_flight` is a non-terminal state with no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish`
What is wrong: A row is moved to `in_flight` before the HTTP attempt and only leaves that state through `_finish`; a worker crash, a `DetachedInstanceError`, or the `IntegrityError` from the status constraint above leaves it there permanently, and `_claim_batch` only selects `status == "pending"` (R38, non-terminal transient state).
What breaks in production: Deliveries silently disappear — never retried, never marked failed, invisible to the deliveries endpoint's users as anything but a row stuck mid-flight — and each worker restart strands another batch of up to 100.
Fix: Add a reclaim pass at the top of each poll that resets rows where `status == 'in_flight' AND updated_at < now() - interval '5 minutes'` back to `pending` with `next_attempt_at = now()`, and set `updated_at` at claim time so the age is meaningful. Pair the sides: a test with an `in_flight` row older than the threshold asserts it is reclaimed and re-attempted (allow), and a test with an `in_flight` row younger than the threshold asserts it is left alone — otherwise a reaper that reclaims everything passes the first test and double-delivers in production. Red-prove separately: (i) remove the reclaim query — the stale-row test must redden; (ii) remove the age predicate — the fresh-row test must redden. If `updated_at` is `NULL` on a claimed row, treat it as stale and log the anomaly rather than skipping the row forever. Preserve `attempts`, so a reclaimed row resumes its budget instead of restarting it. Boundary: a row whose `updated_at` is exactly the threshold must be reclaimed (use `<=`), and a row reclaimed while its original worker is still alive is the case the per-row `attempts` bound must survive.

### Major: the dispatcher swallows every webhook enqueue failure
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: A blanket `except Exception` downgrades total enqueue failure to a warning, so the two Critical defects above (the `event_id` unique index and the naive-datetime write) produce no error, no metric and no retry.
What breaks in production: Customers stop receiving webhooks while the API keeps returning 200 and the event rows keep being written — the outage is invisible until a customer reports missing events, and by then the events are unrecoverable because nothing recorded that they should have been enqueued.
Fix: Narrow the catch to the exceptions that are genuinely tolerable (transport/timeout to the queue), re-raise everything else, and emit a counter metric plus `log.exception` including `envelope.type` and `org_id` on every failure so it is alertable. Better still, write the delivery rows in the same transaction as the `Event` row so persistence is atomic and no enqueue is possible-but-lost. Pair the sides: a test asserts a successful enqueue increments the delivery count and dispatch returns the `event_id` (allow), and a test asserts an enqueue failure raises (or increments the failure metric) rather than returning normally. Red-prove separately: (i) restore the broad `except` — the failure test must redden by seeing a normal return; (ii) drop the metric — the metric assertion must redden. "Enqueued zero rows because the org has no endpoints" and "enqueued zero rows because the insert failed" must be distinguishable at the call site — return the count and check it. Preserve the ordering: the event is still persisted before enqueue, so a webhook failure must never roll back the event. Boundary: an org with exactly zero active endpoints is a legitimate zero, not an error.

### Major: `WEBHOOK_EVENT_TYPES` silently overrides the subscriptions customers configure
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/webhooks/delivery.py` — `enqueue_for_event`'s `if not endpoint.event_types or event_type in endpoint.event_types`
What is wrong: The dispatcher gates fan-out on a hardcoded three-element set while the endpoint model accepts any `event_types` list and the docs promise that an empty list "subscribes the endpoint to every event type we emit"; the two filters are independent and the outer one is invisible to the customer.

Red-prove separately: (i) remove the registration validation — the 422 test must redden; (ii) remove `"invoice.paid"` from the shared constant — the delivery test must redden. If the shared constant cannot be imported, fail at startup rather than defaulting to an empty set, which would silently disable all webhooks. Preserve the empty-list-means-all behaviour the docs advertise. ### Major: naive/aware datetime mixing, and the migration's columns are not timezone-aware
File: `app/webhooks/delivery.py` — `next_attempt_at=datetime.utcnow()`; `migrations/0042_webhook_delivery.sql` — the `TIMESTAMP` columns; `app/webhooks/models.py` — `_now`

If a naive datetime reaches the write path, raise rather than coercing it to UTC by assumption. Preserve the existing `_now()` helper as the single source. Boundary: a delivery whose `next_attempt_at` equals `now` to the microsecond must be claimed (`<=`), and two rows sharing that instant need the ordering fix below.

### Major: retry policy contradicts the documented policy in two ways
File: `app/webhooks/delivery.py` — `deliver`'s retry branch and `backoff_for`; `docs/webhooks.md` — the "Retries" section
What is wrong: The docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx status including 400/404/410, and `backoff_for` returns a deterministic `2**attempt` with no jitter (R29, rationale/derived-claim accuracy — and `test_backoff_grows_exponentially` pins the un-jittered values, so the suite ratifies the discrepancy).
What breaks in production: A customer endpoint returning 410 Gone is hammered five times per event, and because every failed delivery of a burst shares the same deterministic schedule, all of them retry in the same instant — a self-inflicted thundering herd against an endpoint that is already struggling.
Fix: Branch on the status class — `4xx` other than 408 and 429 finishes as `failed_permanent` immediately; 408, 429, 5xx, timeouts and connection errors retry — and add jitter as `backoff_for(attempt) * (1 + random.uniform(0, 0.5))` (jitter needs no CSPRNG, unlike the secret above). Pair the sides: a test asserts a 500 is retried and eventually reaches `failed_permanent` after `MAX_ATTEMPTS` (allow — retries must still happen), and a test asserts a 410 is `failed_permanent` after exactly one attempt. Red-prove separately: (i) remove the 4xx branch — the 410 test must redden by showing 5 attempts; (ii) remove the jitter — a test asserting two deliveries scheduled in the same instant get different `next_attempt_at` values must redden. Rewrite `test_backoff_grows_exponentially` to assert the value lies within `[2**n, 1.5 * 2**n]` rather than deleting it; the exponential base is the behaviour that must be preserved. Boundary: state the treatment of 429 explicitly (retry, and honour `Retry-After` if present) and of exactly 400 versus exactly 408, which fall on opposite sides.

### Major: the three new endpoints have no rate limiting

What is wrong: No limiter is applied to any of the new routes, and `create_webhook_endpoint` in particular performs an unbounded insert plus a secret generation per call (RS2).

### Major: `limit` on the deliveries endpoint has no upper bound

### Major: `EndpointIn` accepts unbounded strings and an unbounded list straight into JSONB

### Major: `response_body` stores the endpoint's entire response, unbounded
File: `app/webhooks/delivery.py` — `_finish(delivery.id, "delivered", attempt, response.status_code, response.text)` and the failure branch's `f"HTTP {...}: {response.text}"`
What is wrong: The full response body of a third-party endpoint is read into memory and written to a `TEXT` column with no size cap and no content filtering.
What breaks in production: A customer endpoint (or an SSRF target reached via the URL-validation gap above) returning a large or sensitive body has it stored in the database and served back through the deliveries endpoint, which is both an unbounded storage growth path and the exfiltration channel that makes the SSRF finding exploitable end to end.

Do not fix this by dropping `response_body` entirely — it is what makes a failed delivery diagnosable. ### Major: `test_verify_accepts_signature_produced_by_sign` cannot fail
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign`
What is wrong: `verify` computes its expected value by calling `sign` with the same secret and payload the test just called `sign` with, so the assertion compares a function's output to itself and holds for any MAC construction, correct or not (RT7 — a guard that cannot be made red).

### Major: `list_deliveries` orders by `created_at`, which is not a total order
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc()).limit(limit)`; `app/webhooks/delivery.py` — `_claim_batch`'s `.order_by(next_attempt_at)`

Red-prove separately: (i) remove the `id` tie-break — the identical-timestamp test must redden with a duplicate; (ii) remove the `created_at` key — the newest-first test must redden. Preserve `created_at` as the displayed value. Boundary: name the page cut through equal keys explicitly — a page boundary landing inside a tie group must resume from `(created_at, id)`, not from `created_at` alone.
