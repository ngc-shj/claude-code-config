### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (via `signing.serialize`) while the request body is produced independently by `client.post(..., json=delivery.payload)`, which httpx serializes with its own encoder — different key order and different separators — so the signature covers a byte string the receiver never sees.
What breaks in production: every customer who verifies the signature over the raw request body, exactly as `docs/webhooks.md` instructs, rejects 100% of our deliveries, and the failure is invisible to us because we record a 4xx and retry it four more times.
Fix: serialize once and send those exact bytes — in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, pass `body` to `sign()` (see the next finding for the timestamp binding), and POST with `client.post(endpoint.url, content=body, headers=headers)` where `headers["Content-Type"] = "application/json"` is set explicitly, since `content=` does not set it. Change `signing.sign`/`verify` to take `body: bytes` rather than `payload: dict` so no call site can re-serialize. Preserve, and say so in the change: the payload the receiver decodes must still be the same JSON document (`json.loads(body) == delivery.payload`), and `serialize`'s `sort_keys=True` must stay — the defect is the second serialization, not the canonicalization, and deleting `sort_keys` to "match httpx" would remove the determinism receivers need. Allow side that must still succeed: a receiver that computes `hmac.new(secret, raw_body, sha256)` over the bytes it received verifies true — pin it with a test that runs the httpx `MockTransport` handler, takes `request.content` verbatim, and calls the production `signing.verify` on it. Red-prove separately: (i) reintroduce `json=delivery.payload` in place of `content=body` and the raw-body verify assertion must go red; (ii) drop `sort_keys=True` from `serialize` and a test asserting `serialize({"b":1,"a":2}) == '{"a": 2, "b": 1}'` must go red. Fail loudly rather than silently: if `delivery.payload` is not JSON-serializable, `serialize` raises and `deliver` must record `failed_permanent` with the exception text — a payload that cannot be signed must never be POSTed unsigned. Boundary and tie: an empty payload `{}` still signs and sends (`b"{}"`, not an empty body), and two deliveries of the same event to two endpoints produce different signatures because the secrets differ, not because the bodies do.

### Critical: the timestamp header is not covered by the MAC, so the replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`
What is wrong: `sign` returns a timestamp and an HMAC computed over the payload alone, so `X-Acme-Timestamp` is unauthenticated attacker-controlled data, contradicting `docs/webhooks.md`, which states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`.
What breaks in production: anyone who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to the current second — the signature still verifies — so the five-minute freshness window the docs sell as the anti-replay control stops nothing, and for `invoice.paid` that means a replayed payment notification.
Fix: bind the timestamp into the MAC — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, body, timestamp, signature)` to take the timestamp from the caller and recompute over the same concatenation, rejecting when `abs(now - int(timestamp)) > 300`. Preserve what made the feature useful: the header set must not shrink — `X-Acme-Timestamp` still ships, because receivers need it to recompute, and the fix must not become "drop the timestamp header" (R36 shape). Allow side that must still succeed: a signature generated with a timestamp 299 seconds old still verifies; pin it. Red-prove separately: (i) revert the concatenation to `body` alone and a test that mutates only the timestamp header and asserts `verify` returns False must go red; (ii) remove the 300-second skew check and a test with a timestamp 301 seconds old must go red. Fail loudly: a `X-Acme-Timestamp` that is absent or not an integer must raise/return False, never be coerced to `0` or to `now` — "could not parse the timestamp" must not be spelled the same as "the timestamp is fresh". Boundary and tie: at exactly 300 seconds the request is accepted (`> 300` rejects), and two requests sharing one timestamp second are both accepted — freshness is not uniqueness, so idempotency stays the receiver's job on `event_id` as documented.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, instead of `hmac.compare_digest` (RS1).
What breaks in production: any caller we ship this helper to — and any internal path that verifies an inbound signature with it — leaks the expected digest byte-by-byte to a timing attacker, who then forges signed requests without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands normalized to `str` (or both to `bytes`) before the call, since `compare_digest` raises `TypeError` on mixed types. Preserve: the function must keep returning a plain bool and keep rejecting a signature made with a different secret — the fix is the comparison primitive, not the predicate. Allow side that must still succeed: `verify(SECRET, body, ts, sign(SECRET, body, ts)[1])` is still True; the existing `test_verify_accepts_signature_produced_by_sign` covers this and must stay green. Red-prove separately: (i) replace `compare_digest` with `==` and a test asserting `hmac.compare_digest` appears on the executed path — patch `hmac.compare_digest` with a spy and assert it was called — goes red; (ii) flip the return to `not compare_digest(...)` and `test_verify_rejects_a_signature_made_with_another_secret` goes red. Fail loudly: a `signature` argument that is `None` or non-`str` must raise rather than fall through to a `False` that reads identically to "the attacker guessed wrong" — an exception is the correct outcome for a malformed header, and the caller maps it to a 400. Boundary and tie: a signature of the wrong length must return False and not raise (`compare_digest` handles unequal lengths in constant time relative to the shorter operand), and the empty string compares False against every real digest.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is the Mersenne Twister, whose full 19937-bit state is recoverable from observed output, so secrets are predictable rather than unguessable.
What breaks in production: an attacker who registers a handful of endpoints of their own recovers the generator state, predicts every other tenant's signing secret, and forges signed `invoice.paid` webhooks that every customer's verification accepts as genuine.
Fix: use the `secrets` module — `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` — and delete `import random` and `_ALPHABET` so no second call site can reach the weak generator. Note the encoding change: `token_urlsafe(32)` returns 43 characters, not 32, so `test_new_signing_secret_has_prefix_and_length` must be updated to assert the entropy floor (`len(secret) - len(SECRET_PREFIX) >= 43`) rather than an exact character count; do not fix the test by widening it to `> 0`, which would delete what made the defect visible. Preserve: the `whsec_` prefix stays — it is what lets customers grep their config for a leaked secret. Allow side that must still succeed: a freshly minted secret round-trips through `sign`/`verify` unchanged; pin it. Red-prove separately: (i) revert to `random.choice` and a test asserting that `random.choice` is not on the executed path (spy on `random.choice`, assert not called) goes red; (ii) shorten to `secrets.token_urlsafe(8)` and the entropy-floor assertion goes red. Fail loudly: if `secrets` cannot produce bytes the exception must propagate out of `create_webhook_endpoint` as a 500 — an endpoint must never be created with an empty or fallback secret. Boundary and tie: two secrets generated in the same microsecond must differ; assert inequality over 100 successive calls, which is the cheapest test that reddens on any reintroduction of a seeded generator.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `endpoint_id` from the URL path and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate any other tenant's delivery history.
What breaks in production: a customer walks `endpoint_id` 1..N and reads every other organization's event types, delivery volumes, and per-attempt response statuses — a cross-tenant data breach reachable with a valid API key and a for-loop.
Fix: join and scope — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint id space is not an existence oracle. Preserve: the ordering and `limit` behaviour stay; the fix is the predicate, not the shape of the response. Allow side that must still succeed: the endpoint's own owner still receives their deliveries — pin a two-org fixture where org A gets its rows and org B gets 404 for the same `endpoint_id`, since a scoping fix that returns 404 to everyone satisfies the deny half alone. Red-prove separately: (i) delete the `org_id` clause and the org-B-404 assertion goes red; (ii) delete the join and the org-A-receives-its-rows assertion goes red (the join is what makes `WebhookEndpoint.org_id` resolvable). Fail loudly: when `user.org_id` is None the handler must raise, not fall through to an unfiltered query — an absent subject denies. Boundary and tie: an endpoint that exists but has zero deliveries returns `[]` for its owner and 404 for everyone else, and the two must be distinguishable in the test.

**Cross-cutting**: the correct pattern is already in this same file, twice — `list_api_keys` uses `.filter(ApiKey.org_id == user.org_id)` and the new `list_webhook_endpoints` uses `.filter(WebhookEndpoint.org_id == user.org_id)`. `list_deliveries` is the one new route that did not propagate it (R3, security-relevant → Critical). No other unscoped query exists in the diff.

### Critical: every endpoint listing returns the signing secret, contradicting the documented contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict()` includes the secret and is used by both `create_webhook_endpoint` and `list_webhook_endpoints`, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation).
What breaks in production: the secret is readable by every principal in the org on every `GET /v1/settings/webhook-endpoints` call, so it lands in browser caches, proxy logs, HAR files, and support screenshots — and because the doc promises otherwise, no customer will have rotated it after the leak.
Fix: remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at that single creation site, so the secret has exactly one egress path. Preserve the feature: creation must still return the secret once — a fix that removes it everywhere makes the endpoint unusable, since there is no rotation route in this change. Allow side that must still succeed: the 201 response body still contains a `whsec_`-prefixed secret; pin it. Red-prove separately: (i) re-add `signing_secret` to `to_dict()` and an assertion that `signing_secret not in list_webhook_endpoints(...)[0]` goes red; (ii) strip it from the creation response and the 201-contains-secret assertion goes red. Fail loudly: `to_dict()` should not be the place a future field silently becomes public — add an explicit `_PUBLIC_FIELDS` tuple and build the dict from it, so a new column is absent by default rather than exposed by default. Boundary and tie: an endpoint created before this change still lists without a secret (the field is dropped at serialization, not at storage), and two endpoints in one org never share a secret.

### Critical: URL validation admits non-HTTPS and internal targets, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http`, and also any scheme merely beginning with those four letters, there is no host policy at all, and the delivery client follows redirects — while `docs/webhooks.md` claims "Only `https://` URLs are accepted" (RS3, escalated: an unvalidated boundary value reaches an outbound-request sink).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` — or any https URL that 302s there — and our worker POSTs to it from inside the VPC on every matching event, storing the response in `webhook_deliveries.response_body` and exposing the status code through the deliveries API as a scan oracle; that is credential-grade SSRF, and plaintext `http` additionally ships every event payload unencrypted.
Fix: replace the `startswith` check with an explicit whitelist and a resolution-time host policy: (a) reject unless `parsed.scheme == "https"`; (b) reject when `parsed.hostname` is absent, is an IP literal in a private/loopback/link-local/reserved range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), or resolves — at request time in `send_once`, not only at registration — to such an address; (c) set `follow_redirects=False` and treat a 3xx as a permanent failure. Preserve: legitimate public HTTPS endpoints must still be registrable and deliverable — do not fix this by dropping the outbound POST or by hardcoding a per-tenant allowlist that makes the feature unusable. Allow side that must still succeed: `https://hooks.example.com/acme` (the docs' own example, resolving to a public address) registers with 201 and delivers; pin it, because a validator that rejects everything satisfies the deny half alone. Red-prove separately: (i) loosen (a) back to `startswith("http")` and a `http://hooks.example.com` → 422 assertion goes red; (ii) delete the IP-range check and a `https://127.0.0.1/x` → 422 assertion goes red; (iii) restore `follow_redirects=True` and a test whose MockTransport returns a 302 to `http://169.254.169.254/` and asserts no second request was issued goes red. Fail loudly: DNS resolution failure at send time must mark the attempt failed with a named reason, never fall through to "no private address found, proceed" — "could not resolve" and "resolved to a public address" must be distinct outcomes. Boundary and tie: `https://` on the standard port 443 is allowed and an explicit `https://host:22/` is rejected by a port whitelist of `{443}`; a hostname with two A records, one public and one private, is rejected — the check is over all resolved addresses, not the first.

**Cross-cutting**: `docs/webhooks.md` line "Only `https://` URLs are accepted" is the only other place this contract appears, and it already states the stricter rule the code does not implement; no third validation site exists in the diff.

### Critical: the migration's CHECK constraint forbids the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: the constraint permits `'failed'`, but `app/webhooks/delivery.py::deliver` writes `"failed_permanent"` and `app/webhooks/models.py::STATUSES` declares `"failed_permanent"` — three copies of one vocabulary, one of which disagrees (R2 / R3).
What breaks in production: the first delivery that exhausts its five attempts raises `CheckViolation` inside `_finish`, the exception escapes `deliver` into `asyncio.gather`, and the worker loop dies — so one unreachable customer endpoint halts webhook delivery for every tenant.
Fix: make the vocabulary single-sourced and correct — change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))`, and have `models.py` derive both the column default and the check from `STATUSES` (which is currently declared and never used) rather than restating the strings. Preserve: the constraint itself must stay — do not fix this by dropping the CHECK, which is what makes the divergence detectable at all. Allow side that must still succeed: a row transitioning `pending → in_flight → delivered` still commits, and one transitioning to `failed_permanent` now also commits; pin both. Red-prove separately: (i) revert the SQL to `'failed'` and an integration test that drives a delivery to exhaustion and asserts the persisted status goes red with a CheckViolation; (ii) add `'bogus'` to `STATUSES` without adding it to the SQL and a test asserting `set(STATUSES)` equals the constraint's value set — parsed from the migration file — goes red. Fail loudly: that parity test must fail explicitly when the migration file cannot be found or the CHECK cannot be parsed, rather than passing on an empty parse result. Boundary and tie: `in_flight` is in the allowed set but is not terminal (see the R38 finding below), and two rows may share a status — the constraint is about the domain, not uniqueness.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness is on `event_id` by itself, but `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint and calls `session.add_all(rows)`, so any org with two subscribed endpoints violates the index on the second row.
What breaks in production: the entire `add_all` transaction rolls back, `dispatch` catches the exception and logs a warning, and that organization receives **zero** webhooks for that event — silently, with a 200 on the originating request; and because the first org to add a second endpoint triggers it, this is the ordinary path, not an edge case.
Fix: make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the key the at-least-once contract in `docs/webhooks.md` actually needs — one delivery attempt-chain per (endpoint, event). Preserve: uniqueness must not simply be dropped; it is what makes a retried `dispatch` idempotent rather than duplicating deliveries, so state that in the change. Allow side that must still succeed: one event fanning out to three endpoints in one org produces three rows and commits; pin it, since a fix that only widens the key is otherwise indistinguishable from deleting the constraint. Red-prove separately: (i) revert to `(event_id)` and the three-endpoint fan-out test goes red on a unique violation; (ii) drop the index entirely and a test that calls `enqueue_for_event` twice for the same (endpoint, event) and asserts exactly one row exists goes red. Fail loudly: `enqueue_for_event` must distinguish "this delivery already exists" (an idempotent no-op, log at debug) from every other `IntegrityError` (re-raise) — collapsing them is how the next constraint bug becomes invisible. Boundary and tie: an endpoint whose `event_types` does not match contributes no row at all, and two endpoints in *different* orgs subscribed to the same `event_id` each get their own row under the composite key.

### Critical: the worker operates on detached ORM instances
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after the `with session_scope()` block) and `deliver` (`endpoint` fetched inside a `with` that closes immediately)
What is wrong: both functions let SQLAlchemy instances escape the session that loaded them, and every subsequent attribute read — `delivery.payload`, `delivery.attempts`, `delivery.id`, `endpoint.signing_secret`, `endpoint.url` — happens after the session closed, which raises `DetachedInstanceError` on any attribute expired by commit (the default `expire_on_commit=True`).
What breaks in production: the worker cannot deliver a single webhook; the first `deliver` call raises, `asyncio.gather` propagates, and `run_worker` exits — the feature is inert from the moment it ships, and the `_claim_batch` `row.status = "in_flight"` writes are the only thing that lands, so the batch is marked in-flight and never retried.
Fix: stop passing ORM objects across session boundaries — have `_claim_batch` return plain immutable value objects (a frozen dataclass carrying `id`, `endpoint_id`, `attempts`, `payload`, and the endpoint's `url` and `signing_secret`, loaded with a single join inside the session), and have `deliver`/`send_once` accept that dataclass. Preserve: the `in_flight` claim must still be committed inside `_claim_batch`'s transaction — that is what stops two workers claiming the same row — so do not fix this by widening one session to span the HTTP calls, which would hold a DB connection for up to 30 seconds per delivery. Allow side that must still succeed: a claimed batch of two rows is fully deliverable with the session already closed; pin it against a real (in-memory) database, not a mock, since a mocked session cannot raise `DetachedInstanceError` and would pass vacuously. Red-prove separately: (i) revert `_claim_batch` to returning ORM rows and the two-row delivery test goes red with `DetachedInstanceError`; (ii) remove the join and load the endpoint lazily and the same test goes red on `endpoint.signing_secret`. Fail loudly: when the join finds no endpoint for a claimed delivery (the endpoint was deleted mid-flight), the row must be marked `failed_permanent` with a named reason — not skipped, and not crashed on. Boundary and tie: an empty batch returns `[]` and the worker sleeps; two workers claiming concurrently must not both see the same row, which is exactly the property the `in_flight` write inside the transaction provides and the current code's out-of-session mutation does not.

**Cross-cutting**: the same escape appears in three places — `_claim_batch`'s returned `rows`, `deliver`'s `endpoint`, and the `delivery` object threaded into `send_once`. `_finish` is the only function that correctly confines its ORM access to the session, and it is the model the other three should follow. `create_webhook_endpoint` calls `to_dict()` inside its session and is therefore safe.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine but sleeps with the blocking `time.sleep` instead of `await asyncio.sleep`, so the backoff freezes the whole loop rather than yielding.
What breaks in production: a single retrying delivery stalls the process for 2+4+8+16 = 30 seconds of backoff plus up to 150 seconds of request timeouts, during which the `asyncio.gather` over the other 99 deliveries in the batch makes no progress and — if the worker shares a loop with the API — no HTTP request is served either.
Fix: `await asyncio.sleep(delay)`. Note the two sibling blocking calls in the same module: `enqueue_for_event`, `_claim_batch`, and `_finish` are declared `async` (or called from async code) but perform synchronous DB I/O, which blocks the loop identically — route all three through `asyncio.to_thread(...)` or a genuinely async session, and make `_finish` awaited rather than called bare. Preserve: the backoff delay itself must not be shortened or removed to "unblock" the loop — the retry spacing is the behaviour under repair. Allow side that must still succeed: a delivery that succeeds on its first attempt still returns without any sleep; pin it, so the fix is not measured only on the retry path. Red-prove separately: (i) restore `time.sleep` and a test that runs two `deliver` coroutines concurrently and asserts total wall time is under the sum of their delays goes red; (ii) remove the `to_thread` wrapper around `_claim_batch` and a test asserting the loop stays responsive (a concurrently scheduled `asyncio.sleep(0)` completes within a bound) goes red. Fail loudly: the responsiveness test must fail explicitly if the event loop is not the one under test rather than silently measuring nothing. Boundary and tie: `backoff_for(1)` is 2 seconds and must still be exactly that after the fix; two deliveries entering backoff in the same tick must both wake, not serialize.

### Critical: the dispatch lock is not a lock
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does a GET, then a separate SET, so two workers that both observe the key absent both "acquire" it (a textbook TOCTOU, R5), and `run_worker` unconditionally deletes the key in `finally` — including after the 60-second TTL has expired and a *different* worker owns it.
What breaks in production: with more than one worker replica, the same batch is claimed and POSTed by several workers at once, so customers receive duplicate signed `invoice.paid` webhooks; and because a single batch can legitimately run far longer than the 60-second TTL (5 attempts × 30s timeout + 30s backoff = up to 180s), the lock expires mid-batch and the duplication is guaranteed, not merely possible.
Fix: acquire atomically and release by ownership — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)`, and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`) so a worker can only delete its own token. Set `LOCK_TTL_SECONDS` above the worst-case batch wall time (`MAX_ATTEMPTS * REQUEST_TIMEOUT + sum(backoff_for(i) for i in range(1, MAX_ATTEMPTS))`, derived, not hardcoded) and renew it while the batch runs. Preserve: the lock must still be released promptly on the success path — do not fix the foreign-delete by removing the release and relying on the TTL, which would idle every worker for a full TTL after each batch. Allow side that must still succeed: a single worker acquires, completes, releases, and immediately re-acquires; pin it. Red-prove separately: (i) revert to GET-then-SET and a test running two `_acquire_lock` calls concurrently against a real (or fakeredis) server, asserting exactly one returns True, goes red; (ii) revert the release to an unconditional `delete` and a test where worker A's TTL expires, worker B acquires, then A releases, asserting B's token still holds the key, goes red. Fail loudly: a Redis error in `_acquire_lock` must return False (deny, do not process) and log at error — an unavailable lock service must never read as "lock acquired". Boundary and tie: a TTL of exactly 0 remaining is treated as expired; two workers presenting the same token is impossible by construction and does not need a tie rule, which is precisely why the token must be per-acquisition and not per-worker.

### Major: naive and aware datetimes are mixed, and the migration's columns have no timezone
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`; `migrations/0042_webhook_delivery.sql` — all four `TIMESTAMP` columns
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` into a column the model declares as `DateTime(timezone=True)` while `_claim_batch` filters against an aware `datetime.now(timezone.utc)`, and the migration declares plain `TIMESTAMP` (no time zone) for `next_attempt_at`, `created_at`, and `updated_at` — so model and schema disagree on all four columns.
What breaks in production: the comparison is between values with and without an offset, which either raises or silently compares wall-clock strings, and once the server is not on UTC every `next_attempt_at <= now` decision is off by the offset — deliveries fire hours early or never become claimable.
Fix: use the helper this change already defines — `app/webhooks/models.py::_now()` returns `datetime.now(timezone.utc)` and is the single source for `created_at`/`updated_at` defaults; call it from `enqueue_for_event` instead of `datetime.utcnow()`, and change all four migration columns to `TIMESTAMPTZ` so the schema matches `DateTime(timezone=True)`. Preserve: `WebhookDelivery.to_dict()` must keep emitting `next_attempt_at.isoformat()` — but the fix makes that string carry an offset, which is the behaviour customers need; note it in the API docs rather than stripping it. Allow side that must still succeed: a delivery enqueued at `now` is claimable by the very next `_claim_batch` call; pin it, since a fix that pushes everything into the future satisfies "no early fire" alone. Red-prove separately: (i) restore `datetime.utcnow()` and a test asserting `enqueue_for_event`'s row has `next_attempt_at.tzinfo is not None` goes red; (ii) revert one migration column to `TIMESTAMP` and a schema-introspection test asserting all four are `timestamptz` goes red, naming the column. Fail loudly: the schema test must fail explicitly when it cannot introspect the table, rather than passing on zero rows examined. What is wrong: the tuple is dead code — the `status` column's default is the string literal `"pending"`, `deliver` writes its own literals, and the migration restates a fourth (divergent) list — so nothing enforces that the four agree.
What breaks in production: nothing directly, but it is the reason the migration's `'failed'` divergence went unnoticed; the remedy is the single-sourcing described in the CHECK-constraint finding above.

### Minor: `deliver` opens one session per delivery to re-fetch an endpoint the claim already joined
File: `app/webhooks/delivery.py` — `deliver`, `with session_scope() as session: endpoint = session.get(...)`
What is wrong: each of the up-to-100 concurrent deliveries opens its own session and issues its own `SELECT` for an endpoint row that `_claim_batch` could have joined once.
What breaks in production: a full batch takes 100 connections from the pool simultaneously, which on a typical pool size starves the API's own request handling; the fix is already implied by the detached-instance remedy, which loads the endpoint fields in the claim's join.

### Minor (question): is endpoint registration meant to be available to every member of an organization?
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `user: CurrentUser = Depends(current_user)`
What is wrong: the route authenticates but performs no role check, so — on the evidence in the diff — any authenticated member of an org can register an outbound destination for that org's `invoice.paid` events; whether a role concept exists is not shown by this change, so this is recorded as a question rather than a defect, per the Finding Floor.
What breaks in production: if the product has non-admin roles, a low-privilege member can exfiltrate every billing event to a destination of their choosing, and the answer that closes this is either "`current_user` already resolves only org admins" or a pointer to the role dependency the other privileged `/v1/settings` routes use.

## Cross-cutting verification summary

- **Org scoping**: `list_api_keys` and `list_webhook_endpoints` filter on `user.org_id`; `list_deliveries` does not — one missed location, reported Critical.
- **Timestamp construction**: `models._now()`, `_claim_batch`, `_finish`, and `dispatch` all use `datetime.now(timezone.utc)`; `enqueue_for_event` alone uses `datetime.utcnow()` — one missed location, reported Major.
- **Timezone-aware columns**: the models declare `DateTime(timezone=True)` for all four datetime columns; the migration declares bare `TIMESTAMP` for all four — the divergence is systemic, not a single column.
- **Status vocabulary**: three declarations (`models.STATUSES`, the literals in `deliver`/the column default, the migration CHECK), one of which disagrees — reported Critical.
- **ORM-instance escape from `session_scope`**: three sites (`_claim_batch` return, `deliver`'s `endpoint`, the `delivery` threaded into `send_once`); `_finish` and `create_webhook_endpoint` are the two correct sites and are the model to follow.
- **Rate limiting**: absent on all three new routes, not one — reported Major once, covering all three.
- **Serialization**: `signing.serialize` is the single canonicalization helper and it is bypassed at exactly one site (`send_once`'s `json=` argument) — reported Critical.

## Codebase awareness

- `app/webhooks/models.py::_now()` already exists as the aware-UTC helper; `enqueue_for_event` reimplements it with `datetime.utcnow()` (R1 — helper present in the same change, not adopted).
- `app/webhooks/signing.py::serialize()` already exists as the canonical body encoder and is used by `sign`; `send_once` reimplements the encoding by delegating to httpx's `json=` (R1 — the duplicated behaviour is a security control, hence Critical).
