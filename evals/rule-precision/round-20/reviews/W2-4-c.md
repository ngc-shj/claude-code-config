### Critical: signature verification compares the HMAC with `==`
File: app/webhooks/signing.py — `verify()`, `return expected == signature`
What is wrong: The recomputed HMAC is compared to the caller-supplied signature with Python's short-circuiting `==`, which returns as soon as bytes differ, leaking the position of the first mismatch through timing (RS1).
What breaks in production: An attacker who can submit candidate signatures to any consumer of `verify()` recovers a valid digest byte-by-byte and forges webhook payloads that the service accepts as ours.
Fix: Replace the comparison with `hmac.compare_digest(expected, signature)` (both operands `str`, so encode to bytes first: `hmac.compare_digest(expected.encode(), signature.encode())`), and guard the non-str case — if `signature` is not a `str`, raise `TypeError` rather than returning `False`, so "could not compare" is spelled differently from "did not match". Preserve the existing behaviour that `verify` returns `True` for a signature produced by `sign` with the same secret and `False` for one produced with another secret — pin both: keep `test_verify_accepts_signature_produced_by_sign` (the allow side) and `test_verify_rejects_a_signature_made_with_another_secret` (the deny side) green, and add `test_verify_rejects_a_non_str_signature` asserting the `TypeError`. Red-prove each clause separately by execution: (1) revert `compare_digest` to `==` and assert the new `test_verify_uses_constant_time_comparison` — which monkeypatches `hmac.compare_digest` with a counting wrapper and asserts it was called exactly once — goes red; (2) make `verify` return `True` unconditionally and observe the deny-side test go red; (3) delete the `TypeError` raise and observe the non-str test go red. Boundary and tie: `compare_digest` on two strings of *different* length still returns `False` in constant time relative to the shorter operand, so a 64-hex and a 63-hex candidate both land on the deny side; two callers presenting byte-identical signatures both land on the allow side, and there is no ordering between them to define.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: app/webhooks/signing.py — `new_signing_secret()`, `random.choice(_ALPHABET)`
What is wrong: The 32-character secret is drawn from `random`, a Mersenne Twister seeded from predictable state and fully recoverable from 624 consecutive outputs, so the secret is not unpredictable (this is a security control reimplemented instead of using the stdlib's `secrets` helper — R1, Critical because the duplicated behaviour is the control itself).
What breaks in production: An attacker who observes enough secrets, or who can register endpoints and read their own secrets back (see the exposure finding below), reconstructs the generator state and derives other tenants' signing secrets, forging events that every customer's verifier accepts.
Fix: Change the body to `return SECRET_PREFIX + secrets.token_hex(SECRET_BYTES)` and `import secrets`, dropping `random`, `string` and `_ALPHABET`; rename the constant's contract so `SECRET_BYTES = 32` means 32 random bytes rendered as 64 hex characters. Preserve the two properties the current code actually delivers and the tests assert — the `whsec_` prefix and a fixed, known secret length — so update `test_new_signing_secret_has_prefix_and_length` to `len(secret) == len(SECRET_PREFIX) + 2 * SECRET_BYTES`, and add `test_new_signing_secret_is_unique_across_calls` asserting 1000 calls yield 1000 distinct values (the allow side: generation must still succeed and still produce a prefixed, correctly-sized secret). Fail loudly rather than silently weakening: add an import-time guard `if SECRET_BYTES < 32: raise ValueError(...)` so a later reduction of the constant refuses to load instead of shipping a short secret. Red-prove each clause by execution: (1) restore the `random.choice` body and assert a new `test_new_signing_secret_uses_the_csprng` — which monkeypatches `secrets.token_hex` to raise and expects the exception to propagate — goes red; (2) set `SECRET_BYTES = 16` and observe the import-time guard raise; (3) make `new_signing_secret` return a constant and observe the uniqueness test go red. Boundary and tie: `SECRET_BYTES == 32` is on the accept side of the guard (`< 32` denies), and two calls returning the same value is a failure of the uniqueness test, not a tie to be broken.

### Critical: every endpoint's signing secret is returned by the list API and written to the logs
File: app/webhooks/models.py — `WebhookEndpoint.to_dict()`, `"signing_secret": self.signing_secret`; app/webhooks/delivery.py — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`

Pair deny with allow: pin that the create response STILL contains the secret exactly once (`test_create_endpoint_returns_the_secret_once`) and that the list response contains the id, url, event_types and active fields (`test_list_endpoints_returns_the_display_fields`). Red-prove each clause by execution: (1) re-add `signing_secret` to `to_dict()` and observe the never-contains test go red; (2) drop the secret from the create response and observe the create test go red; (3) restore `headers=%s` in the log call and observe a new `test_send_once_does_not_log_headers` (caplog-based) go red. Boundary and tie: the create call is the single point on the "secret is emitted" side of the boundary; every later read of the same row is on the deny side, and two concurrent creates each emit only their own secret.

### Critical: the deliveries endpoint has no tenancy predicate
File: app/api/routes/settings.py — `list_deliveries`, `.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: The query filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while every sibling route added or present in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) scopes by `user.org_id` — the org-scoping pattern was propagated to two of three new routes and missed on the third (R3, security-relevant → Critical).
What breaks in production: Any authenticated user can enumerate integer endpoint ids and read another organization's delivery history — event types, event ids, response statuses and timing — a cross-tenant data leak, and `docs/webhooks.md` states the endpoint returns attempts "for an endpoint belonging to your organization", which the code does not enforce.
Fix: Join the tenancy predicate into the query: `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and before the query resolve the endpoint — if `session.get(WebhookEndpoint, endpoint_id)` is `None` **or** belongs to another org, raise `HTTPException(404)` (same status for both, so absence and non-ownership are indistinguishable to the caller) rather than returning an empty list, because "examined nothing" must not be spelled the same as "found nothing". Pair deny with allow: `test_list_deliveries_returns_rows_for_an_endpoint_in_my_org` must stay green and assert the row ids returned, alongside `test_list_deliveries_404s_for_an_endpoint_in_another_org`, and per RT8 the deny test must also assert that no `WebhookDelivery` row of the other org appears in the response body — not merely that the status is 404. Red-prove each clause by execution: (1) drop the `org_id` filter and observe the cross-org test go red on the body assertion; (2) drop the 404 raise and return `[]` instead, and observe a `test_unknown_endpoint_id_is_404` go red; (3) drop the join and observe the same-org test still green but the cross-org test red — confirming the two mutations redden different assertions. Boundary and tie: an endpoint whose `org_id` is exactly `user.org_id` is on the allow side; an endpoint id that exists but belongs to another org and one that does not exist at all both land on 404, and two orgs can never share an endpoint id because it is the primary key.

### Critical: the transmitted body is not the bytes that were signed, and the timestamp is not signed at all
File: app/webhooks/signing.py — `sign()` / `serialize()`; app/webhooks/delivery.py — `send_once`, `client.post(..., json=delivery.payload, ...)`
What is wrong: `sign` computes the HMAC over `json.dumps(payload, sort_keys=True)` and omits the timestamp entirely, while `send_once` transmits a body serialized independently by httpx (its own separators, insertion key order), and `docs/webhooks.md` instructs receivers to HMAC `"{timestamp}.{raw_request_body}"` — three mutually incompatible definitions of the signed message across a producer/strict-consumer boundary (R40).
What breaks in production: Every customer who implements the documented verification rejects 100% of our deliveries, and because the timestamp is outside the MAC the replay window the docs describe is unenforceable — an attacker can rewrite `X-Acme-Timestamp` on a captured request and it still verifies.
Fix: Make the signed message the exact bytes on the wire: have `serialize` return `bytes` via `json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, change `sign(secret, payload)` to compute `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` and return `(timestamp, signature, body)`, and change `send_once` to post those same bytes with `content=body` instead of `json=delivery.payload` — one serialization, used for both the MAC and the request. Update `verify(secret, body: bytes, timestamp: str, signature: str)` to take the raw body and timestamp rather than a dict, and reject a timestamp more than 300 seconds from now — the 5-minute window the docs already promise — returning a distinct outcome for "stale" versus "mismatched" so a receiver's logs can tell them apart. Do not fix by relaxing the doc to match the code: the property that must be preserved is that a third party holding only the secret, the raw body and the two headers can reproduce the signature. Pair deny with allow with a real round-trip test that feeds actual producer output through the actual consumer: `test_documented_verification_accepts_a_real_delivery` captures `request.content` and the headers from `httpx.MockTransport` in `send_once` and asserts an independently written verifier (`hmac.new(SECRET.encode(), ts.encode() + b"." + captured_body, sha256).hexdigest()`) equals the header — never two independently mocked shapes. Red-prove each clause by execution: (1) revert `content=body` to `json=delivery.payload` and observe the round-trip test go red; (2) drop `f"{timestamp}."` from the MAC input and observe a `test_signature_covers_the_timestamp` (which mutates only the timestamp header and expects verification to fail) go red; (3) set the skew window to `sys.maxsize` and observe `test_verify_rejects_a_timestamp_older_than_five_minutes` go red. Boundary and tie: a timestamp exactly 300 seconds old is accepted and 301 rejected; two deliveries signed within the same clock second produce different signatures because their bodies differ, and identical bodies in the same second legitimately produce identical signatures.

### Critical: the URL check accepts non-HTTPS and internal targets, and the client follows redirects
File: app/api/routes/settings.py — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` admits `http`, and any scheme whose name merely begins with those four characters, while `docs/webhooks.md` states "Only `https://` URLs are accepted", and nothing rejects loopback, link-local or RFC 1918 destinations — combined with `follow_redirects=True` this is a server-side request forgery primitive at an unvalidated boundary (RS3, Critical: the externally supplied value reaches an outbound HTTP interpreter; R49: the doc claims a control the code does not implement).
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/` or an external URL that 302-redirects there, and the delivery worker POSTs from inside the production network to cloud metadata or internal admin services, returning the response body into `webhook_deliveries.response_body` where the tenant can read it.
Fix: Validate at the schema boundary rather than in the handler body — add a pydantic validator on `EndpointIn.url` that requires `parsed.scheme == "https"` (exact equality, not `startswith`), a non-empty `parsed.hostname`, no userinfo and no non-default port outside an allowed set, then resolve the hostname with `socket.getaddrinfo` and reject when any resolved address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved`; set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure with a message naming the redirect. Because DNS can be re-pointed after registration, repeat the address check at delivery time in `send_once` via a pinned `httpx` transport rather than trusting the registration-time result — a name checked once and used later is not a bound object. Fail loudly when the check cannot run: a `getaddrinfo` failure must reject the registration with 422 and a message saying the host could not be resolved, never fall through to acceptance. Do not fix by dropping the URL field's usefulness: customer endpoints on public hosts with non-standard HTTPS ports must still register, so pin that allow case (`test_public_https_url_with_port_8443_is_accepted`). Red-prove each clause by execution: (1) restore `startswith("http")` and observe `test_http_scheme_is_rejected` go red; (2) remove the private-address check and observe `test_loopback_host_is_rejected` go red; (3) set `follow_redirects=True` and observe `test_redirect_to_internal_host_is_not_followed` go red; (4) make `getaddrinfo` raise and observe `test_unresolvable_host_is_422` go red. Boundary and tie: `https` on port 443 and on an explicitly allowed alternate port are on the accept side, `http` on any port is on the deny side, and a hostname resolving to both a public and a private address is denied — any private answer wins the tie, since fail-safe takes precedence.

### Critical: the unique index on `event_id` allows only one endpoint to receive each event
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all carrying the same `event_id`, but the index makes `event_id` globally unique, so the second row of any multi-endpoint fan-out violates it.
What breaks in production: The moment an organization registers a second endpoint, `session.add_all(rows)` fails on flush with a `UniqueViolation`, the enqueue raises, `dispatch` swallows it as a warning, and every webhook for that org silently stops — including the deliveries for the first endpoint, since the whole insert rolls back.
Fix: Replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — preserving the property the original was reaching for, namely the at-most-once-per-destination idempotency that `docs/webhooks.md` tells consumers to rely on when it says "deduplicate on `event_id`" (update that sentence to say deduplicate on the `(endpoint, event_id)` pair). Fail loudly when the guard cannot apply: make `enqueue_for_event` use an explicit `ON CONFLICT (endpoint_id, event_id) DO NOTHING` insert and log at warning level with the conflicting pair when the affected row count is lower than `len(rows)`, so a suppressed duplicate is recorded rather than invisible. Pair deny with allow: `test_two_endpoints_both_receive_one_event` asserts two rows exist after one `enqueue_for_event` (the allow side), and `test_reenqueuing_the_same_event_for_one_endpoint_inserts_no_second_row` asserts the count stays at one. Red-prove each clause by execution: (1) restore the single-column unique index and observe the two-endpoints test go red with a `UniqueViolation`; (2) drop the index entirely and observe the re-enqueue test go red on the row count; (3) remove the `DO NOTHING` clause and observe a `test_duplicate_enqueue_does_not_raise` go red. Boundary and tie: the uniqueness boundary is the `(endpoint_id, event_id)` pair — two endpoints sharing an `event_id` are both admitted, one endpoint seeing the same `event_id` twice keeps the first row, and the tie between the two inserts is resolved by first-writer-wins.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker event loop
File: app/webhooks/delivery.py — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` times concurrently, but the retry pause uses the blocking `time.sleep` rather than `await asyncio.sleep`, freezing the event loop for the full backoff.
What breaks in production: One slow endpoint stalls all 100 concurrent deliveries in the batch for up to 30 seconds of accumulated backoff each, the batch outruns the 60-second Redis lock TTL so a second worker claims the same rows, and the whole delivery pipeline's throughput collapses to serial.
Fix: Do not sleep in the request path at all — replace the in-coroutine retry loop with a reschedule: on a retryable failure, write `status = "pending"`, `attempts = attempt`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` through `_finish`, and return, letting the next `_claim_batch` pick the row up when it is due. This preserves the behaviour the loop provided — at most `MAX_ATTEMPTS` attempts with the documented exponential spacing — while removing the blocking call; where an in-process wait is genuinely wanted, it must be `await asyncio.sleep(delay)`, never `time.sleep`. Fail loudly when the reschedule cannot happen: if `_finish` cannot load the delivery row (see the `session.get` finding), log at error level and leave the row for the stale-`in_flight` reaper rather than returning as though the attempt were recorded. Pair deny with allow: pin that a delivery which succeeds on its first attempt still reaches `delivered` with `attempts == 1` and no reschedule (`test_first_attempt_success_is_terminal`), alongside `test_a_500_reschedules_with_the_documented_backoff` asserting the persisted `next_attempt_at`. Red-prove each clause by execution: (1) reinstate `time.sleep` and observe `test_deliver_does_not_block_the_event_loop` — which runs `deliver` concurrently with a ticking `asyncio.sleep(0)` counter and asserts the counter advanced — go red; (2) hardcode `next_attempt_at` to `now` and observe the backoff test go red; (3) remove the `attempt >= MAX_ATTEMPTS` terminal branch and observe `test_delivery_stops_after_five_attempts` go red (bound the loop in the mutation so it reddens rather than hangs). Boundary and tie: `attempt == MAX_ATTEMPTS` is the last attempt made and terminal, `attempt == MAX_ATTEMPTS - 1` reschedules; two rows whose `next_attempt_at` are equal are both due and both claimed in the same batch.

### Critical: `_claim_batch` hands out ORM rows after its session has closed
File: app/webhooks/delivery.py — `_claim_batch()`, `return rows` inside `with session_scope() as session:`; `deliver()`, `with session_scope() as session: endpoint = session.get(...)` then use after the block
What is wrong: Both functions return or use SQLAlchemy instances after the enclosing `session_scope` exits, and on commit those instances are expired and detached, so the next attribute access (`delivery.payload`, `delivery.attempts`, `endpoint.signing_secret`, `endpoint.url`) triggers a refresh with no session bound.
What breaks in production: The first real batch raises `DetachedInstanceError` on the first attribute read inside `send_once`, `asyncio.gather` propagates it, `run_worker`'s `finally` drops the lock, and the loop dies — while the claimed rows stay wedged in `in_flight`.

The behaviour that must be preserved is that the claim and the `status = "in_flight"` write remain in one transaction, so the rows are still marked before the function returns. Fail loudly when the load cannot run: if the endpoint row is gone, `_finish` the delivery as `failed_permanent` with detail `"endpoint deleted"` rather than raising an `AttributeError` that takes the batch down. Pair deny with allow: `test_claim_batch_returns_due_rows_and_marks_them_in_flight` asserts both the returned ids and the persisted status (the allow side), and `test_deliver_survives_a_deleted_endpoint` asserts the single delivery is marked failed while the other deliveries in the batch still complete. Red-prove each clause by execution: (1) revert `_claim_batch` to returning ORM instances and observe `test_claim_batch_result_is_usable_after_the_session_closes` go red with `DetachedInstanceError`; (2) delete the missing-endpoint branch and observe the deleted-endpoint test go red; (3) move the `status = "in_flight"` write outside the session and observe the persisted-status assertion go red. Boundary and tie: a row whose `next_attempt_at` equals `now` exactly is due and claimed; two rows with the same `next_attempt_at` are both claimed in the same batch, and their relative order is not relied on by anything.

### Major: the Redis lock is a non-atomic check-then-set and is released by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock()`, `if await redis_client.get(LOCK_KEY)` / `set` / `expire`; `run_worker`, `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: The read and the write are separate round-trips with no atomicity (R5 — a read followed by a dependent write outside any transaction), the TTL is a third round-trip so a crash between `set` and `expire` leaves the key forever, and the unconditional `delete` in `finally` frees a lock that may by then belong to another worker whose 60-second TTL claim succeeded.
What breaks in production: Two workers claim and POST the same batch, so customers receive duplicate deliveries beyond the at-least-once contract, and a crash in the window between `set` and `expire` wedges the pipeline until an operator deletes the key by hand.
Fix: Replace the three calls with a single atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = uuid4().hex` is unique per acquisition, and replace the `finally` delete with a compare-and-delete Lua script (`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`) so a worker can only release its own lock. Fail loudly when the check cannot run: on a Redis connection error, `_acquire_lock` must log at error level and return `False` — declining to process rather than assuming the lock was free. Do not fix by extending the TTL to cover the worst-case batch: the property to preserve is that the lock expires without an operator, so instead renew it periodically while the batch runs. Pair deny with allow: `test_lock_is_acquired_when_free` asserts the token was written and the batch ran (the allow side), `test_second_worker_does_not_acquire_a_held_lock` asserts the second call returns `False` **and** that no batch rows were claimed by it, and `test_release_does_not_delete_another_workers_lock` asserts the key still holds the other token. Red-prove each clause by execution: (1) revert to `get`-then-`set` and observe the second-worker test go red under two interleaved acquisitions against a real in-memory Redis fake; (2) revert the compare-and-delete to a plain `delete` and observe the release test go red; (3) make the fake raise `ConnectionError` and observe `test_redis_error_declines_the_lock` go red if the code returns `True`. Boundary and tie: exactly one of N simultaneous `SET NX` calls succeeds — that caller is on the allow side and every other is denied, with the tie resolved by Redis' single-threaded ordering rather than by client code.

### Major: naive `datetime.utcnow()` is written where every other site uses timezone-aware time, and the module reimplements an existing helper
File: app/webhooks/delivery.py — `enqueue_for_event()`, `next_attempt_at=datetime.utcnow()` vs `_claim_batch()`/`_finish()` using `datetime.now(timezone.utc)`; app/webhooks/models.py — `_now()`
What is wrong: `models.py` already defines `_now()` as the module's one source of current time and every model default uses it, yet `delivery.py` neither imports it nor uses a consistent replacement — it writes a naive UTC value in one place and aware values in two others, into columns declared `DateTime(timezone=True)` (R1/R17: the helper exists in the same diff and is not adopted).
