### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice` over `string.ascii_letters + string.digits`, and `random` is a Mersenne Twister whose internal state is fully recoverable from ~624 observed outputs, so a customer who registers a few endpoints and reads back their own secrets can predict every other tenant's secret generated by the same process.
What breaks in production: An attacker forges `X-Acme-Signature` for arbitrary payloads to any other customer's endpoint, and the HMAC scheme provides no authenticity at all for the affected tenants.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`, drop `random`/`string` and `_ALPHABET`, and delete the reimplementation outright rather than leaving it as an unused helper — R1 clause (d)); rename `SECRET_BYTES` to what it now is (a byte count fed to a CSPRNG, not a character count) and update `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` to assert `len(secret) > len(SECRET_PREFIX)` plus prefix, since `token_urlsafe(32)` yields 43 characters, not 32. Behavioural difference to state explicitly (R1 clause (a)/(b)): the alphabet gains `-` and `_`, so any customer-side secret validation that assumes alphanumeric must be checked before rollout, and existing rows keep their weak secrets — schedule a rotation, because swapping the generator does not repair already-issued secrets (R1 clause (e): the dedup does not address the installed base). Allow side that must still pass: `new_signing_secret()` still starts with `whsec_`, is still a `str`, and `sign(new_signing_secret(), {"a": 1})` still returns a 64-hex digest — pin all three. Red-proof, one mutation per clause, each executed: (i) revert to `random.choice` and assert failure of a new test that seeds `random.seed(0)` twice and asserts the two secrets differ — with the CSPRNG they differ, with `random` they are identical; (ii) drop the `SECRET_PREFIX` concatenation and watch the prefix assertion redden; (iii) shorten to `token_urlsafe(4)` and watch a minimum-length assertion redden. Fail-loudly case: if `secrets` is unavailable the import raises at module load — do not add a `try/except ImportError` fallback to `random`, because "could not use the CSPRNG" must not be spelled the same as "generated a secret". Boundary and tie: the length assertion is `>=`, and the value exactly at the minimum is accepted.

### Critical: `verify` compares HMACs with `==`, not a constant-time primitive
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` is Python's short-circuiting string comparison, which returns after the first differing byte, and this is the only signature-checking helper the change ships — while `docs/webhooks.md` simultaneously instructs customers to "compare it against your own computation using a constant-time comparison".
What breaks in production: An attacker with network access to any consumer of `verify` recovers a valid signature byte-by-byte through response-timing measurement, and the documentation's own advice is contradicted by the reference implementation shipped beside it.
Fix: Change to `return hmac.compare_digest(expected, signature)` (`hmac` is already imported at line 2 of the file — no new dependency), and guard the pre-comparison work so a malformed header cannot change the code path: reject and return `False` when `signature` does not match `^sha256=[0-9a-f]{64}$` before comparing. Allow side that must still pass: `verify(SECRET, payload, sign(SECRET, payload)[1])` is still `True` — the existing `test_verify_accepts_signature_produced_by_sign` covers this and must stay green. Red-proof, one mutation per clause, each executed: (i) revert to `==` and assert failure of a new test that monkeypatches `hmac.compare_digest` with a counting wrapper and asserts it was called exactly once; (ii) delete the shape guard and assert failure of a new test passing `signature=None`, which must return `False` rather than raise `TypeError` out of `compare_digest`. Fail-loudly case: a non-`str` `secret` or `payload` must raise at the boundary, not silently return `False`, so that a wiring error is not indistinguishable from a bad signature. Boundary and tie: comparison is over the full `"sha256="`-prefixed string including the prefix, and two candidate signatures of unequal length both return `False` in constant time relative to `expected`, never early.

### Critical: the signature does not cover the timestamp, so the documented replay window cannot be enforced
File: `app/webhooks/signing.py` — `sign` / `verify`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: `sign` computes `hmac.new(secret, serialize(payload), sha256)` over the payload alone, while the docs state the signature is "the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`" — the timestamp is transmitted in `X-Acme-Timestamp` but is not an input to the MAC, so it is attacker-mutable, and `verify` "works" only because it regenerates a fresh timestamp that it then discards.
What breaks in production: A captured request replays forever — the attacker rewrites `X-Acme-Timestamp` to now, the unchanged signature still validates, and the five-minute window the docs describe as "what stops a captured request from being replayed" stops nothing; separately, any customer who implements verification exactly as documented computes a different MAC and rejects 100% of our deliveries.
Fix: Make the timestamp an authenticated input — `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact transmitted bytes (see the serialization finding below) — and change `verify` to take the timestamp from the caller rather than minting one: `def verify(secret, timestamp, body, signature, *, max_age_seconds=300)`, which rejects when `abs(int(time.time()) - int(timestamp)) > max_age_seconds` before the `compare_digest`. Do not repair this by deleting the timestamp header or by relaxing the doc to match the code — the header and the replay bound are the feature (Remedy Floor clause 4); the doc's stated construction is the contract to implement. Allow side that must still pass: a request signed now and verified now returns `True`, and a request at exactly `max_age_seconds` old is accepted. Red-proof, one mutation per clause, each executed: (i) drop the timestamp from the MAC input and assert failure of a test that signs a payload, mutates only `X-Acme-Timestamp`, and asserts `verify` is now `False`; (ii) remove the age check and assert failure of a test that signs with `time.time() - 3600` and asserts `False`; (iii) flip the comparison to `<` and assert failure of the exactly-at-300s boundary test. Fail-loudly case: a `timestamp` that is absent or non-integer must raise or return `False` explicitly and be logged as a rejection, never be coerced to `0` (which would put every request outside the window and read as an ordinary signature mismatch). Boundary and tie: the window is inclusive at exactly `max_age_seconds` in both directions, and clock skew ahead of us is bounded by the same value.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `serialize`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` (default separators, keys sorted) while the request body is produced by `client.post(..., json=delivery.payload)`, which serializes with httpx's own encoder — no `sort_keys`, different separators — so for any payload with more than one key the signed string and the transmitted body are different byte sequences; note the change already contains the `serialize` helper and the transmit path does not adopt it (R1/R17 evidence: the helper exists at `app/webhooks/signing.py:serialize` and is called only from `sign`).
What breaks in production: Every receiver that verifies over the raw request body — which is the only correct way to verify, and what `docs/webhooks.md` tells customers to do — computes a mismatching MAC and rejects 100% of deliveries; because we retry non-2xx five times, the failure also multiplies every customer's rejection load fivefold.
Fix: Serialize once and send those exact bytes: in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, pass `ts, signature = sign(endpoint.signing_secret, body)` (change `sign` to take bytes rather than a dict, so the MAC is defined over the wire form and cannot drift again), and post with `content=body` plus an explicit `Content-Type: application/json` instead of `json=`. Do not fix this by removing `sort_keys` to match httpx — that leaves the two serializations independently reachable and the bug returns the next time either side changes (Remedy Floor clause 4); the single-serialization structure is the repair. Allow side that must still pass: a well-formed delivery still arrives with `content-type: application/json` and a body that `json.loads` back to the original dict — the existing `test_send_once_posts_the_signed_payload` assertions on content-type and `["type"]` must stay green. Red-proof, one mutation per clause, each executed: (i) revert `content=body` to `json=delivery.payload` and assert failure of a strengthened test that recomputes `hmac.new(SECRET.encode(), f"{ts}.{captured['body'].decode()}".encode(), sha256).hexdigest()` and asserts equality with the captured signature header, using a payload with deliberately unsorted keys such as `{"z": 1, "a": 2}`; (ii) drop the explicit `Content-Type` header and assert failure of the content-type assertion. Fail-loudly case: a payload that is not JSON-serializable must raise out of `serialize` and mark the delivery failed with a named reason, never fall back to `str(payload)`. Boundary and tie: an empty payload `{}` is signed as the two-byte body `{}` and is a legitimate delivery, not an absent one.

### Critical: `GET /v1/settings/webhook-endpoints` returns every endpoint's signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret` and is reused verbatim by the list route, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: The secret is exfiltrable through any read-scoped API token, any browser-cached settings response, any request log or APM trace that captures response bodies, and any read-only support tooling — turning a compromise of a low-privilege credential into full webhook forgery for that org (R49: a documented boundary that the implementation does not have, and customers were told to rely on it).
Fix: Remove `signing_secret` from `WebhookEndpoint.to_dict()` and return it only from `create_webhook_endpoint`, by building the 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}`; audit the third `to_dict` call site (`list_deliveries` → `WebhookDelivery.to_dict`) at the same time — it carries no secret today and must not gain one. Do not fix this by removing the field from the create response too — first-issue disclosure is what makes the feature usable (Remedy Floor clause 4). Allow side that must still pass: `POST /webhook-endpoints` still returns a body containing `signing_secret` and the caller can sign with it — pin that with a route test that posts, extracts the secret, and verifies a signature produced from it. Red-proof, one mutation per clause, each executed: (i) re-add `signing_secret` to `to_dict` and assert failure of a new test asserting `"signing_secret" not in list_webhook_endpoints_response[0]`; (ii) drop the create-route merge and assert failure of the 201-response test above. Fail-loudly case: if a future serializer cannot resolve a field it must raise, not emit a partial dict — an endpoint row that silently omits `url` must not read as a successful listing. Boundary and tie: an org with zero endpoints returns `[]` and is not an error.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on the path parameter `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint` to confirm `org_id == user.org_id`, so any authenticated user of any tenant can enumerate integer endpoint ids and read other orgs' deliveries — while the neighbouring `list_webhook_endpoints`, the pre-existing `list_api_keys`, and `enqueue_for_event` all do filter on `org_id` (R3: the tenancy pattern was propagated to every site in the diff except this one, and the miss is the security-relevant one).
What breaks in production: `WebhookDelivery.to_dict()` exposes `event_type`, `status`, and `response_status` for another tenant's `invoice.paid` and `subscription.updated` traffic — a cross-tenant data breach reachable by incrementing a number in a URL, and the docs assert the opposite ("attempts for an endpoint belonging to your organization").
Fix: Join and filter in the same query — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)` — and return `404` (not `403`) when the join yields nothing, so the route does not confirm the existence of other orgs' endpoint ids. Allow side that must still pass (RT10): a caller listing deliveries for an endpoint their own org owns still receives them, including when the org owns several endpoints — pin an allow fixture adjacent to the boundary, same integer id, owning org. Red-proof, one mutation per clause, each executed: (i) delete the `org_id` predicate and assert failure of a denial test where org A requests org B's `endpoint_id` and asserts BOTH a 404 status AND that the response body is `[]` with no delivery rows leaked (RT8: assert the absent data, not only the status code); (ii) change the 404 to a 403 and assert failure of an enumeration test asserting identical responses for "exists but not yours" and "does not exist". Fail-loudly case: if `user.org_id` is `None` the route must reject with a server error rather than matching rows whose `org_id IS NULL`. Boundary and tie: an endpoint that exists and belongs to the caller but has zero deliveries returns `[]` with 200, which is distinct from the 404 of a foreign endpoint.

### Critical: endpoint URL validation permits SSRF, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker`
What is wrong: The check is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts plaintext `http://`, accepts any scheme merely *prefixed* with `http` (`httpx://`, `httpfoo://`), performs no address filtering at all, and is paired with `httpx.AsyncClient(..., follow_redirects=True)` so even a public `https://` host can 302 the signed request into the internal network — while `docs/webhooks.md` states flatly "Only `https://` URLs are accepted" (R49: the doc describes an enforceable boundary the code does not implement; R47-shape: a surface-form prefix match standing in for a scheme decision).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://localhost:6379/` and our worker becomes an authenticated request generator inside our own VPC, exfiltrating cloud instance credentials or driving internal services; over plain `http` the payload and its MAC also cross the network in clear.
Fix: Validate with an exact scheme equality (`parsed.scheme != "https"` → 422) rather than a prefix test; resolve the hostname at registration AND again immediately before each send, and reject when any resolved address is not global unicast (`ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast`), rejecting the whole set if any record fails; set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with a named reason. Do not fix this by validating only at registration — DNS rebinding between registration and send is exactly why the pre-send check is required, and dropping either half leaves the hole (Remedy Floor clause 4). Allow side that must still pass (RT10): `https://hooks.example.com/acme` resolving to a public address is still accepted at registration and still delivered — pin it, and pin an https host on a non-443 port as also accepted, since the fix must not become a port allowlist nobody asked for. Red-proof, one mutation per clause, each executed: (i) revert to `startswith("http")` and assert failure of a test posting `{"url": "http://hooks.example.com/x"}` expecting 422; (ii) delete the address filter and assert failure of a test posting an `https://` URL whose host resolves to `127.0.0.1` (inject the resolver) expecting 422; (iii) set `follow_redirects=True` and assert failure of a `MockTransport` test whose handler returns a 302 to `http://169.254.169.254/` and asserts the delivery is marked failed with no second request issued. Fail-loudly case: when DNS resolution errors or times out, the registration must 422 and the send must mark the attempt failed with a reason naming "resolution failed" — an unresolvable host must never be treated as "no private address found, therefore safe". Boundary and tie: an address exactly at a private-range edge (`10.0.0.0`, `172.16.0.0`, `192.168.0.0`, `169.254.0.0`) is rejected, and a host resolving to both a public and a private record is rejected.

### Critical: the migration's status CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `webhook_deliveries.status` CHECK; `app/webhooks/delivery.py` — `_finish`
What is wrong: The constraint is `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` but `_finish` writes `"failed_permanent"`, and `app/webhooks/models.py::STATUSES` declares the fourth value as `"failed_permanent"` — three independent spellings of one enum with no shared source of truth, and the dead `STATUSES` tuple is referenced by nothing (R2/R3: the value was changed in the Python and not propagated to the SQL).
What breaks in production: The first delivery that exhausts its retries raises an `IntegrityError` inside `_finish`, which is uncaught — it propagates out of `deliver`, out of the `asyncio.gather` in `run_worker`, and out of the worker loop entirely, so one permanently-failing endpoint kills the background worker and stops all webhook delivery for every customer.
Fix: Correct the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make the constraint derive from one place: have `models.STATUSES` be the source, reference it from `_finish` and `_claim_batch` (`row.status = STATUS_IN_FLIGHT`) instead of bare literals, and add a test that asserts the SQL file's `IN (...)` list parses to exactly `set(models.STATUSES)`. Do not fix this by widening the constraint to accept any text — the CHECK is what makes an unknown status visible (Remedy Floor clause 4). Allow side that must still pass: a delivery reaching `"delivered"` and one reaching `"pending"` still insert and update without error — pin both against a real database, not a mock. Red-proof, one mutation per clause, each executed: (i) revert the SQL to `'failed'` and assert failure of the constraint/`STATUSES` equality test; (ii) change `_finish`'s literal to `"failed"` and assert failure of an integration test that drives a delivery through `MAX_ATTEMPTS` failures against a real database and asserts the row's final status is `"failed_permanent"`. Fail-loudly case: an `IntegrityError` from `_finish` must be caught, logged with the delivery id and the rejected value, and re-raised — the worker must not continue with the row silently stuck. Boundary and tie: attempt number exactly `MAX_ATTEMPTS` is the last attempt and terminates as `failed_permanent`; attempt `MAX_ATTEMPTS - 1` still retries.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)` permits at most one delivery row per event, but `enqueue_for_event` builds one row per matching endpoint and `session.add_all`s them together, so any org with two subscribed endpoints violates the constraint on the second row.
What breaks in production: The entire `add_all` flush fails, no delivery rows are written for that event, and the dispatcher's `except Exception: log.warning(...)` swallows it — so an org that adds a second endpoint silently stops receiving webhooks on *both*, with a `WARNING` line as the only trace and no reconciliation path to recover the lost events.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the design actually wants (per-endpoint idempotency, matching the docs' "deduplicate on `event_id`" advice being *per endpoint*). Do not fix this by dropping uniqueness altogether — the index is what makes a re-enqueue of the same event idempotent, and losing it converts a hard failure into duplicate customer-visible deliveries (Remedy Floor clause 4). Allow side that must still pass: one event fanning out to three endpoints of the same org inserts three rows; the same event re-enqueued for the same endpoint inserts zero additional rows. Red-proof, one mutation per clause, each executed: (i) revert the index to `(event_id)` and assert failure of an integration test that creates two active endpoints, calls `enqueue_for_event` once, and asserts `len(rows) == 2` in the database; (ii) drop the unique index entirely and assert failure of a test calling `enqueue_for_event` twice with the same `event_id` and asserting still two rows. Fail-loudly case: an `IntegrityError` on enqueue must be caught per-row (or handled with `ON CONFLICT DO NOTHING`) and any other error must propagate to a dead-letter record — see the separate finding on the dispatcher's blanket `except Exception`. Boundary and tie: an event matching zero endpoints legitimately writes zero rows and returns `0`, which must be distinguishable from an enqueue that failed.

### Critical: `time.sleep` inside an `async def` blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` (100) at a time, and its retry backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, so one retrying delivery freezes the whole process.
What breaks in production: A single failing endpoint stalls all 99 concurrent deliveries plus the Redis lock refresh for 2+4+8+16 = 30 seconds, throughput collapses to serial, and the freeze outlasts the 60-second lock TTL so a second worker starts on the same batch (see the lock finding).
Fix: Replace with `await asyncio.sleep(delay)` (`asyncio` is already imported at the top of the file) and add jitter as `docs/webhooks.md` already promises: `delay = backoff_for(attempt).total_seconds() * (0.5 + random.random() / 2)`. Do not fix this by lowering `BATCH_SIZE` or removing the backoff — the delay between attempts is what protects a struggling customer endpoint (Remedy Floor clause 4). Allow side that must still pass: a delivery that succeeds on its first attempt still completes without any sleep at all, and total wall time for a batch of N successful deliveries stays bounded by the slowest single request, not the sum — pin that with a `MockTransport` batch test. Red-proof, one mutation per clause, each executed: (i) revert to `time.sleep` and assert failure of a test that gathers two `deliver` calls (one failing-then-succeeding, one immediately succeeding) and asserts the fast one completes before the slow one's backoff elapses, measured on the event loop clock; (ii) remove the jitter multiplier and assert failure of a test asserting two computed delays for the same attempt number differ. Fail-loudly case: `asyncio.CancelledError` during the sleep must propagate and leave the row in a state a reaper can reclaim, never be swallowed by the surrounding `except`. Boundary and tie: at `attempt == MAX_ATTEMPTS` no sleep is performed at all, and the jitter's lower bound is `0.5 * base`, never zero.

### Critical: the dispatch lock is non-atomic to take and unconditionally released
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`
What is wrong: `_acquire_lock` does a separate `GET`, `SET`, and `EXPIRE` — two workers can both observe the empty key and both proceed — and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)` deletes the key without checking that this worker still owns it, which is the normal path because a 100-delivery batch with a 30-second request timeout and up to 30 seconds of backoff routinely exceeds the 60-second TTL.
What breaks in production: Two workers claim and deliver the same batch, so customers receive duplicate webhooks — and because the payloads are billing events (`invoice.paid`), duplicate processing on the customer side is a financial correctness problem; separately, a crash between the `SET` and the `EXPIRE` leaves a TTL-less lock that wedges every worker permanently with no expiry to save it.
Fix: Take the lock atomically with a unique owner token — `token = uuid.uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release it with a compare-and-delete Lua script (`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end`) so a worker can never delete a successor's lock; add a periodic extend while the batch is in flight, and bound the batch so its worst case (`BATCH_SIZE`-parallel, `REQUEST_TIMEOUT` + total backoff) is provably under the TTL, or drop the global lock in favour of `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch`, which removes the TTL question entirely. Do not fix this by lengthening the TTL alone — an unbounded TTL converts duplicate delivery into a total stall on crash (Remedy Floor clause 4). Allow side that must still pass (RT10): a single worker still acquires, processes, and releases across successive loop iterations without ever blocking itself, and after a crash the lock does expire and a new worker does acquire it. Red-proof, one mutation per clause, each executed: (i) revert to `GET`-then-`SET` and assert failure of a concurrency test that runs two `_acquire_lock` calls against a real (or fakeredis) instance interleaved at the `GET` and asserts exactly one returns `True`; (ii) revert the release to an unconditional `delete` and assert failure of a test where worker A's lock has expired, worker B has acquired, and A's `finally` runs — asserting B's token is still present; (iii) drop the `ex=` argument and assert failure of a test asserting `TTL` on the key is positive. Fail-loudly case: a Redis connection error in `_acquire_lock` must return `False` and log, never be treated as "no lock present, therefore mine" — the fail direction is toward not dispatching. Boundary and tie: exactly one worker wins when two race, and the loser sleeps `poll_interval` rather than proceeding.

### Critical: the one test named for signature verification never verifies a signature
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test asserts only that the signature header *starts with* `"sha256="` and that the timestamp header is digits — it never recomputes the HMAC over `captured["body"]`, so it passes for any implementation that emits a well-formed-looking header, including one that signs a completely different byte string (RT5: signature verification is a production security primitive and the test's call path never reaches a comparison against it; the test name asserts a guarantee the assertions do not deliver).
What breaks in production: The signed-bytes-vs-sent-bytes defect above ships green — a reviewer reads "posts the signed payload", sees a passing test, and concludes the signing path is covered when nothing in the suite would notice that every customer rejects our deliveries.
Fix: Add the missing assertion to this test — `expected = hmac.new(SECRET.encode(), f'{captured["headers"][signing.TIMESTAMP_HEADER]}.{captured["body"].decode()}'.encode(), hashlib.sha256).hexdigest(); assert captured["headers"][signing.SIGNATURE_HEADER] == "sha256=" + expected` — computing the expected value independently rather than by calling `signing.sign` (RT1: a double or helper that produces both sides makes the comparison an identity), and use a payload whose keys are deliberately unsorted (`{"z": 1, "a": 2, "type": "invoice.paid"}`) so key-order divergence is exercised rather than accidentally absent. Do not fix this by deleting the existing prefix/digit assertions — they pin header presence and shape (Remedy Floor clause 4). Allow side that must still pass: the correctly-signed request is accepted by the assertion, and `test_send_once_propagates_connection_errors` still passes unchanged. Red-proof, one mutation per clause, each executed: (i) change `send_once` to sign a fixed literal `b"{}"` and assert this test reddens naming the signature mismatch; (ii) reorder the payload keys in the signing path only and assert it reddens; (iii) drop the timestamp from the signed string and assert it reddens — three separate mutations reddening three assertions, not one mutation reddening the file. Fail-loudly case: if `captured` is empty because the transport was never invoked, the test must fail with a named "no request captured" assertion rather than a `KeyError` that reads as an unrelated error. Boundary and tie: an empty payload `{}` is still signed and asserted, not skipped.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `session_scope`), `deliver` (reads `endpoint.url` / `endpoint.signing_secret` after its `with` block)
What is wrong: Both functions exit the `session_scope` context before their return values are read, and with SQLAlchemy's default `expire_on_commit=True` every attribute on a committed instance is expired, so the first access — `delivery.attempts` in `deliver`, `endpoint.signing_secret` in `send_once` — attempts a refresh on a closed session and raises `DetachedInstanceError`.
What breaks in production: The worker raises on its very first claimed batch, the exception propagates out of `run_worker` (no `except` anywhere in the loop), and no webhook is ever delivered — while rows already flipped to `in_flight` are wedged. This rests on `session_scope`'s commit/close semantics, which the change does not contain; its use in `create_webhook_endpoint` (explicit `session.flush()` before reading `endpoint.id`) indicates commit-on-exit, which is the condition under which this fires — confirming `session_scope` sets `expire_on_commit=False` would close it.
Fix: Return plain data rather than live ORM objects — have `_claim_batch` return a list of detached dataclasses or dicts built inside the session (`{"id": r.id, "endpoint_id": r.endpoint_id, "attempts": r.attempts, "payload": r.payload}`), and have `deliver` read the endpoint's `url` and `signing_secret` inside its own session block into locals before the `with` exits. Do not fix this by setting `expire_on_commit=False` globally — that hides the same class of bug everywhere else in the codebase behind stale reads (Remedy Floor clause 4). Allow side that must still pass: a claimed batch of one still delivers end-to-end against a real database and a `MockTransport`, and `_claim_batch` on an empty table still returns `[]` without touching the session afterwards. Red-proof, one mutation per clause, each executed: (i) revert `_claim_batch` to returning ORM rows and assert failure of an integration test that seeds one pending row, claims it, and asserts `batch[0]["payload"]` is readable after the call returns; (ii) revert `deliver`'s endpoint read and assert failure of the same test carried through `send_once`. Fail-loudly case: a claimed row whose endpoint no longer exists must mark the delivery failed with a named reason rather than raising `AttributeError` on `None` (see the `_finish` Minor below). Boundary and tie: a batch of exactly `BATCH_SIZE` rows and a batch of zero rows both round-trip without a detached access.

### Major: `in_flight` is a non-terminal state with no reaper
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`, `run_worker`
What is wrong: `_claim_batch` flips rows to `in_flight` and only `_finish` moves them out, so a worker crash, an OOM kill, a deploy restart, or any exception between the claim and `_finish` leaves rows in `in_flight` forever — and `_claim_batch` selects only `status == "pending"`, so nothing ever reclaims them (R38 mode 1: a transient state with a success-only exit and no bounded timeout).
What breaks in production: Every worker restart permanently strands up to 100 deliveries; the loss is silent because the rows exist, look "in progress", and are reported to customers by `list_deliveries` as neither delivered nor failed.
Fix: Record `claimed_at` when flipping to `in_flight` and add a reclaim clause to `_claim_batch` — `(status == "pending" AND next_attempt_at <= now) OR (status == "in_flight" AND claimed_at < now - CLAIM_TIMEOUT)` — with `CLAIM_TIMEOUT` set above the worst-case single-delivery wall time (`REQUEST_TIMEOUT` plus total backoff), and add the `claimed_at` column to `migrations/0042_webhook_delivery.sql`. Do not fix this by having `_claim_batch` also select `in_flight` unconditionally — that reclaims rows a live worker is mid-flight on and duplicates deliveries (Remedy Floor clause 4); the age bound is the point. Allow side that must still pass: a delivery currently in flight and younger than `CLAIM_TIMEOUT` is NOT reclaimed by a second worker — pin that alongside the reclaim case. Red-proof, one mutation per clause, each executed: (i) remove the reclaim clause and assert failure of a test that seeds an `in_flight` row with `claimed_at` older than the timeout and asserts it is claimed; (ii) remove the age predicate and assert failure of a test seeding a fresh `in_flight` row and asserting it is NOT claimed. Fail-loudly case: a row reclaimed more than a configured number of times must be routed to `failed_permanent` with a named reason rather than looping forever. Boundary and tie: a row whose `claimed_at` is exactly `CLAIM_TIMEOUT` old is reclaimed (`<=`), and when two workers reclaim the same row simultaneously the `SKIP LOCKED` / lock fix above decides the winner.

### Major: the worker loop has no exception handling, so one error terminates delivery permanently
File: `app/webhooks/delivery.py` — `run_worker`
What is wrong: The `try` block has only a `finally`, and `asyncio.gather` is called without `return_exceptions=True`, so any exception from `_claim_batch` or from any single `deliver` (a DB blip, the `IntegrityError` from the status-CHECK finding, a `DetachedInstanceError`) propagates out of the `while True` loop and ends the coroutine; the `if not batch` at the bottom also sits outside the `try`, so `batch` is unbound on that path.
What breaks in production: The background worker dies quietly on the first transient error — there is no supervisor in the diff — and webhook delivery stops for all customers until someone notices the absence of traffic.
Fix: Pass `return_exceptions=True` to `gather` and log each returned exception against its delivery id; wrap the loop body in `except Exception: log.exception(...)` followed by `await asyncio.sleep(poll_interval)` so the loop survives; move the `if not batch` check inside the `try` and initialise `batch = []` before it. Do not fix this by catching and discarding — each swallowed exception must be logged with the delivery id and increment a counter a monitor can alert on (Remedy Floor clause 3/4). Allow side that must still pass: a batch in which one delivery raises still completes the other 99, and `asyncio.CancelledError` must still propagate so the worker can be shut down — catch `Exception`, never `BaseException`. Red-proof, one mutation per clause, each executed: (i) revert to bare `gather` and assert failure of a test where one of three deliveries raises and the other two are asserted delivered; (ii) revert the loop-body `except` and assert failure of a test where `_claim_batch` raises once and the loop is asserted to still be running on the next tick; (iii) catch `BaseException` and assert failure of a test asserting `run_worker` exits on cancellation. Fail-loudly case: N consecutive failed iterations must escalate to `log.error` rather than continuing to emit identical warnings indefinitely. Boundary and tie: an empty batch and a fully-failed batch both sleep `poll_interval` before re-polling.

### Major: `enqueue_for_event` uses naive `datetime.utcnow()` while every other site uses aware UTC
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`
What is wrong: The change already contains the `_now()` helper (`app/webhooks/models.py`, returns `datetime.now(timezone.utc)`) and every other datetime site in the diff is aware — `_claim_batch`, `_finish`, `models.WebhookEndpoint.created_at`, `dispatcher.dispatch` — but this one writes a naive value produced by the deprecated `datetime.utcnow()` (R17: a new shared helper exists and one call site of the underlying primitive does not adopt it; R3: the aware-UTC pattern is propagated to five sites and missed at the sixth).
What breaks in production: Once the column is corrected to `TIMESTAMPTZ` as `models.py` declares (see the next finding), Postgres interprets the naive value in the session's `TimeZone`, so on any non-UTC connection every `next_attempt_at` is shifted by the offset — deliveries fire hours early or sit undelivered for hours, and `_claim_batch`'s `next_attempt_at <= now` comparison against an aware value decides on shifted data with no error raised.

Allow side that must still pass: an event enqueued now is claimable by `_claim_batch` immediately (`next_attempt_at <= now` is true at equality) — pin that. Red-proof, one mutation per clause, each executed: (i) revert to `datetime.utcnow()` and assert failure of a test asserting `rows[0].next_attempt_at.tzinfo is not None`; (ii) set the session `TimeZone` to `America/New_York` in an integration test and assert the enqueued row is claimed at the correct instant. Fail-loudly case: a naive datetime reaching `_claim_batch`'s comparison must raise `TypeError` rather than be coerced — do not add a `.replace(tzinfo=utc)` rescue that guesses the zone. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimed (`<=`), and simultaneous rows are ordered by the tie-break added in the R57 finding below.

### Major: the retry policy contradicts the documented one on both jitter and 4xx handling
File: `app/webhooks/delivery.py` — `deliver`, `backoff_for`; `docs/webhooks.md` — "Retries"
What is wrong: The docs state "backoff is exponential with jitter" and "a 4xx is permanent and we stop immediately", but `backoff_for` returns a deterministic `2**attempt` with no jitter and `deliver` retries every non-2xx response identically, including 400, 401, 404 and 410 (R29/R49: two load-bearing claims about a control that the implementation does not make true).

Red-proof, one mutation per clause, each executed: (i) remove the 4xx branch and assert failure of a test whose handler always returns 404 and asserts exactly one request was issued and the status is `failed_permanent`; (ii) add 429 to the terminal set and assert failure of a test whose handler returns 429 then 200 and asserts two requests and `delivered`; (iii) remove the jitter and assert failure of the delay-variance test. Fail-loudly case: a response with an unparseable status must be treated as retryable and logged by name, never silently classified as terminal. Boundary and tie: 400 is terminal and 500 is retryable; 429 sits on the retryable side of the 4xx boundary and is the tie case to pin explicitly.

Boundary and tie: attempt exactly `MAX_ATTEMPTS` terminates and attempt `MAX_ATTEMPTS - 1` retries.

### Major: the test doubles diverge from the models they stand in for
File: `tests/webhooks/test_delivery.py` — `FakeEndpoint`, `FakeDelivery`
What is wrong: `FakeEndpoint` carries only `url` and `signing_secret` and `FakeDelivery` only `id`, `attempts`, and `payload`, while the real `m.WebhookEndpoint` and `m.WebhookDelivery` are SQLAlchemy models whose attributes are expired after commit and whose `payload` is a JSONB round-trip — so `send_once` is tested against plain-Python objects that can never raise the `DetachedInstanceError` production hits, and never against the real classes (RT1: the double's behaviour diverges from the boundary it replaces, and the divergence hides exactly the correctness defect reported above).
What breaks in production: `test_send_once_posts_the_signed_payload` passes for an implementation that cannot run at all against real ORM rows, so the suite reports coverage of the send path while the send path is broken.
Fix: Replace the doubles with real model instances constructed against a test database session (`m.WebhookEndpoint(org_id=1, url=..., signing_secret=SECRET, event_types=[], active=True)` persisted and re-read), keeping the `MockTransport` for the network boundary only — mock at the system boundary, not at the type you own. Do not fix this by adding the missing attributes to the fakes — completing a hand-rolled double makes the tautology larger, not smaller (RT1, Remedy Floor clause 4); the real class is the fix. Allow side that must still pass: the existing successful-send assertions and `test_send_once_propagates_connection_errors` both stay green with the real models substituted. Red-proof, one mutation per clause, each executed: (i) have `send_once` read a field the fakes lacked (`delivery.event_type`) and assert the test reddens with an `AttributeError` naming it under the fakes but passes under the real models; (ii) leave the session-detached read in `deliver` and assert the real-model test reddens where the fake-based test did not. Fail-loudly case: if the test database is unavailable the tests must error, not skip silently — a skipped tenancy test reads identically to a passing one in CI output. Boundary and tie: an endpoint with `event_types=[]` (subscribe-all) and one with an explicit single-element list must both be constructible as real rows.

### Major: `deliver` never re-checks whether the endpoint is still active
File: `app/webhooks/delivery.py` — `deliver`
What is wrong: `active.is_(True)` is evaluated once, at enqueue time in `enqueue_for_event`, and `deliver` loads the endpoint without consulting `active` — so a delivery queued before deactivation keeps retrying for up to five attempts afterwards.
What breaks in production: A customer who deactivates an endpoint because it is leaking or compromised continues to receive signed payloads at that URL for the full retry window, which is the case where continued delivery is most harmful.
Fix: Re-read `active` inside `deliver`'s endpoint load and, when false, terminate the delivery — `_finish(delivery.id, "failed_permanent", attempt, None, "endpoint deactivated")` — and re-check it before each retry, not only before the first attempt, since deactivation can land mid-loop. Do not fix this by only filtering at claim time — the window this closes is the one *inside* the retry loop (Remedy Floor clause 4). Allow side that must still pass (RT10): an active endpoint still receives all its attempts, and reactivating an endpoint before a queued delivery's next attempt lets that delivery proceed — pin both. Red-proof, one mutation per clause, each executed: (i) remove the pre-attempt check and assert failure of a test that deactivates the endpoint after enqueue and asserts zero HTTP requests were issued; (ii) remove the in-loop recheck and assert failure of a test that deactivates between attempt 1 and 2 and asserts exactly one request. Fail-loudly case: an endpoint row that has been deleted must terminate the delivery with a named reason, not raise `AttributeError` on `None`. Boundary and tie: deactivation exactly between the check and the send still results in one in-flight request — state that the guarantee is "no new attempt after deactivation is observed", not "no request in flight".

### Minor: `_finish` dereferences a possibly-absent row
File: `app/webhooks/delivery.py` — `_finish`, `row = session.get(m.WebhookDelivery, delivery_id)`
What is wrong: There is no `None` check before `row.status = status`, and the delivery row can be gone by then because `webhook_deliveries.endpoint_id` has `ON DELETE CASCADE` — deleting an endpoint mid-flight removes its deliveries.
What breaks in production: An `AttributeError` on `NoneType` propagates out of `deliver` and, given the missing exception handling in `run_worker`, terminates the worker.

### Minor: `list_deliveries` orders on a non-total key
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc())`
What is wrong: `created_at` defaults to `now()`, which in Postgres is transaction-start time, so every row written by one `enqueue_for_event` shares an identical value and the order among them is undefined, with no tie-break column (R57); the route uses a bare `limit` rather than a cursor, so the consequence today is a non-deterministic cut rather than skipped pages — but it becomes row-skipping the moment the `limit` is turned into the keyset cursor the RS3 finding recommends.
What breaks in production: Two identical requests can return different "most recent" sets for the same endpoint, which reads as data loss to a customer debugging a delivery.

### Minor: the backoff test hardcodes the constants it is meant to pin
File: `tests/webhooks/test_delivery.py` — `test_backoff_grows_exponentially`
What is wrong: The parametrisation hardcodes `(1, 2), (2, 4), (3, 8), (4, 16)` rather than deriving from `BASE_DELAY_SECONDS` (RT3), and it stops at attempt 4 while `MAX_ATTEMPTS` is 5, so the last backoff the code can compute is never exercised.
What breaks in production: Changing `BASE_DELAY_SECONDS` to tune retry pressure reddens four unrelated-looking assertions with no indication of which constant moved, and the attempt-5 path stays unmeasured.

### Minor: the claim query has no supporting index
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_status`
What is wrong: `_claim_batch` filters `status = 'pending' AND next_attempt_at <= now` and sorts by `next_attempt_at`, but the only index is on the low-cardinality `status` column alone, so the sort is unsupported.
What breaks in production: Once the deliveries table grows, every poll (once per `poll_interval`, i.e. once per second) performs a large sort, and the worker's own polling becomes the dominant database load.

### Minor (question): are the three new routes covered by a shared rate limiter?
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: None of the three routes carries a rate-limit dependency or decorator in the diff, and `create_webhook_endpoint` also imposes no per-org cap on the number of endpoints — but whether the application applies a limiter as global middleware is not visible in this change, so I am asking rather than asserting (RS2, downgraded per the Finding Floor).
What breaks in production: If there is no global limiter, an authenticated caller creates unbounded endpoints, each multiplying outbound request volume per event — an amplification lever on top of the SSRF finding.
What answer closes it: showing a global rate-limit middleware registered on the FastAPI app that covers `/v1/settings/*`. Independently of that answer, the absent per-org endpoint cap is grounded in this diff and should be added as an explicit limit in `create_webhook_endpoint`.
