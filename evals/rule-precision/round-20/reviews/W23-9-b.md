### Critical: the signed bytes are not the bytes that are sent, so no receiver can ever verify a delivery
File: app/webhooks/signing.py — `sign()` / app/webhooks/delivery.py — `send_once()`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted) while `send_once()` transmits `client.post(..., json=delivery.payload)`, which lets httpx re-encode the dict with compact separators in insertion order, and neither side includes the timestamp that `docs/webhooks.md` says is part of the signed string `"{timestamp}.{raw_request_body}"`.
What breaks in production: every customer who implements the documented verification against the raw request body computes a different digest, so 100% of deliveries are rejected as forged and the feature is inert from the first event.
Fix: Have `sign()` produce the wire bytes and the MAC over the same object — `body = serialize(payload).encode()`, `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — return `(timestamp, "sha256=" + mac.hexdigest(), body)`, and in `send_once()` post `content=body` with the explicit `Content-Type: application/json` header already in `headers` so httpx never re-serializes. `signing.serialize()` already exists and is the canonical encoder the sender bypassed; reuse it rather than adding a second one. Preserve the `sha256=` prefix, both header names, and the documented `{timestamp}.{body}` construction — do not repair this by rewriting the doc to match the code. Allow side to pin: a receiver recomputing over the captured `request.content` and captured `X-Acme-Timestamp` verifies. Red-prove three clauses by execution, one mutation each: (i) flip one byte of the captured body → verification reds; (ii) drop the timestamp from the MAC input on the sender only → verification reds; (iii) restore `json=delivery.payload` in place of `content=body` → verification reds. Fail loudly when the check cannot run: if `serialize()` raises on a non-JSON-serialisable payload, mark the delivery `failed_permanent` with the exception text and never send an unsigned or partially signed request. Boundary and tie: a receiver's five-minute window includes exactly `now - 300s` and excludes `now - 301s`; two deliveries signed within the same second carry identical timestamps and must both verify.

### Major: documented retry semantics do not match the implementation

What breaks in production: a deleted or misconfigured customer endpoint is hammered five times per event instead of once, and the absent jitter means every delivery queued during an outage retries in lockstep, producing synchronized thundering-herd bursts against the recovering receiver.
Fix: implement what the doc promises — in `deliver`, treat `400 <= status_code < 500` (excluding 408 and 429, which are retryable) as immediately `failed_permanent`, and add jitter in `backoff_for` as `timedelta(seconds=BASE_DELAY_SECONDS**attempt * (1 + random.uniform(0, 0.25)))` using a documented jitter fraction constant. Allow side to pin: a 500 and a `httpx.ConnectError` are both still retried, and a 2xx still marks `delivered` on the first attempt. Red-prove three clauses by execution: (i) a 404 response produces exactly one request and `failed_permanent` → remove the 4xx branch and it reds; (ii) a 429 is still retried → widen the branch to all 4xx and it reds; (iii) `backoff_for(2)` falls in `[4, 5)` across repeated calls and is not always exactly 4 → remove the jitter and it reds. Do not fix by editing the doc down to the current behaviour without deciding — if no-jitter and retry-all is the intended policy, say so and update the doc, but the existing `test_backoff_grows_exponentially` parameterization must then be replaced with range assertions rather than deleted. Boundary and tie: status 400 and 499 are permanent, 408 and 429 are not, and exactly 500 is retryable.

### Major: none of the three new routes has rate limiting
File: app/api/routes/settings.py — `create_webhook_endpoint()`, `list_webhook_endpoints()`, `list_deliveries()`
What is wrong: three new public endpoints are added with no rate limit and no cap on how many endpoints an org may register, and nothing in the diff shows a shared limiter being applied to them.
What breaks in production: an attacker loops `POST /v1/settings/webhook-endpoints` to create unbounded rows, each of which multiplies outbound delivery volume for every subsequent event, turning the worker into an amplifier and the deliveries table into unbounded storage growth.
Fix: apply the project's existing rate-limit dependency to all three routes (add it to the `router` for the whole `/v1/settings` prefix if a shared limiter dependency exists — grep for one before adding a new implementation, since a duplicate limiter is a second policy to keep in sync), and enforce a per-org endpoint cap by counting existing rows for `user.org_id` inside the create transaction and returning 409 above the limit. Allow side to pin: a caller under both the rate limit and the endpoint cap still creates an endpoint and receives 201. Red-prove three clauses by execution: (i) N+1 requests within the window → the last returns 429; (ii) creating one endpoint past the cap → 409, and the row count is unchanged (assert the count, not only the status); (iii) a caller at exactly the cap minus one still succeeds → set the comparison to `>=` on the wrong side and it reds. Do not fix by dropping the create route. Fail loudly: if the limiter backend is unreachable the request is rejected, not allowed through unlimited. Boundary and tie: the request at exactly the limit is allowed and the next is denied; two concurrent creates at the cap must not both succeed, which the in-transaction count plus a unique constraint or row lock decides.

### Major: unbounded `limit` and unvalidated `event_types` at the request boundary
File: app/api/routes/settings.py — `list_deliveries()` `limit: int = Query(50, ge=1)` and `EndpointIn.event_types`
What is wrong: `limit` has a floor but no ceiling, and `event_types` is an unconstrained `list[str]` never checked against the set of event types the system actually emits (`dispatcher.WEBHOOK_EVENT_TYPES`).
What breaks in production: `?limit=100000000` loads every delivery row for an endpoint into memory in one request, and a customer who registers `"invoice.payed"` gets a silently dead subscription that emits no error at registration and no event ever after.
Fix: change the parameter to `limit: int = Query(50, ge=1, le=200)` and validate `event_types` in `EndpointIn` with a Pydantic validator that rejects any member not in the shared emitted-types constant, returning 422 with the offending value named; export that constant from one place so `dispatcher.WEBHOOK_EVENT_TYPES` and the validator cannot drift. Allow side to pin: `limit=200` succeeds, and `event_types=["invoice.paid"]` and `event_types=[]` (subscribe-to-all) both succeed. Red-prove three clauses by execution: (i) `limit=201` → 422; (ii) `event_types=["invoice.payed"]` → 422 naming the value; (iii) `event_types=[]` → 201 (removing the empty-list allowance reds this and would break the documented subscribe-to-all behaviour). Do not fix by silently truncating the list or clamping the limit — a clamped limit reads as success while returning a different page size than asked for. Boundary and tie: `limit=200` is allowed and `201` denied; `limit=1` is allowed and `0` denied, matching the existing `ge=1`.

### Major: only three event types can ever reach webhooks, while the docs promise every emitted event
File: app/events/dispatcher.py — `WEBHOOK_EVENT_TYPES` vs docs/webhooks.md — "we POST every subscribed event to it" / "An empty `event_types` subscribes the endpoint to every event type we emit"
What is wrong: a hardcoded three-member set in the dispatcher gates whether `enqueue_for_event` is called at all, so `endpoint.event_types` — which `enqueue_for_event` treats as the real subscription filter — can never match anything outside those three, and nothing keeps the set in sync with `SUBSCRIBERS` or the event catalogue.
What breaks in production: a customer subscribing with an empty `event_types` receives only invoice and subscription events and silently misses everything else the system emits, and every new event type added later is invisible to webhooks until someone remembers this set.
Fix: derive the gate from the subscription data rather than a parallel literal — call `enqueue_for_event` for every dispatched event and let `enqueue_for_event`'s existing `if not endpoint.event_types or event_type in endpoint.event_types` filter decide, deleting `WEBHOOK_EVENT_TYPES`; if a deliberate allowlist is required instead, define it beside the event-type registry and add a test asserting it equals the emitted-type set so a new type reds the build. Allow side to pin: `invoice.paid` still enqueues for a subscriber, and an endpoint with `event_types=["invoice.paid"]` still receives nothing for `subscription.updated`. Red-prove three clauses by execution: (i) dispatch an event type outside the old set to an endpoint with empty `event_types` and assert one delivery row → restore the gate and it reds; (ii) an endpoint with an explicit non-matching `event_types` gets zero rows → remove the filter and it reds; (iii) with the allowlist variant, add a new emitted type without registering it → the equality test reds. Do not fix by removing the per-endpoint filter — that would deliver everything to everyone. Boundary and tie: an empty list means all, which must stay distinguishable from a null/absent value.

### Major: `organizations.webhooks_enabled` is added by the migration and never read
File: migrations/0042_webhook_delivery.sql — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: the change introduces a per-org feature flag defaulting to `FALSE` but no code path in the diff consults it — neither `create_webhook_endpoint`, nor `dispatch`, nor `enqueue_for_event` — so the declared capability has no backing implementation.
What breaks in production: operators will read the column as the kill switch it looks like and believe webhooks are off for every org, while any org that registers an endpoint receives deliveries regardless, and the intended default-off rollout is silently default-on.
Fix: wire the flag at the single choke point — in `enqueue_for_event`, join `Organization` and return `0` when `webhooks_enabled` is false, and reject `POST /webhook-endpoints` with 403 for an org whose flag is false — or drop the column from the migration if the gate is not wanted; shipping it unread is the only option that must not survive review. Allow side to pin: an org with `webhooks_enabled = TRUE` and an active endpoint still gets its delivery rows. Red-prove three clauses by execution: (i) an org with the flag false produces zero delivery rows for a subscribed event → remove the check and it reds; (ii) that same org's `POST /webhook-endpoints` returns 403 → remove the guard and it reds; (iii) flipping the flag to true makes both succeed without a restart → cache the flag and it reds. Do not fix by defaulting the column to `TRUE` — that removes the safe rollout the default was chosen for. Boundary and tie: an org with the flag false but pre-existing endpoints must stop enqueuing new deliveries while already-pending rows still drain.

### Major: every delivery logs its full signature header at INFO
File: app/webhooks/delivery.py — `send_once()`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: the `headers` dict logged in full contains `X-Acme-Signature` and `X-Acme-Timestamp`, and `_finish` additionally persists the untruncated `response.text` into `response_body`.
What breaks in production: anyone with log access — including downstream log shipping and indexing — can replay the exact signed request to the customer's receiver inside the documented five-minute window, and unbounded response bodies from customer endpoints (which may echo internal data, per the SSRF finding) land in both logs and the database.
Fix: log only the endpoint id and the URL host at INFO and drop the header dump entirely; if header-level debugging is needed, log the header names only. Bound `response_body` at write time to a constant `RESPONSE_BODY_MAX_CHARS` (e.g. 2048) with an explicit truncation marker. Allow side to pin: a delivery still emits one log line carrying the endpoint id and outcome, so operational tracing is preserved — the fix must not remove observability. Red-prove three clauses by execution: (i) capture log output for a delivery and assert the signature value does not appear → restore the header dump and it reds; (ii) assert the endpoint id does appear → delete the whole log line and it reds; (iii) a 10 KB response body is stored truncated to the cap with the marker → remove the bound and it reds. Boundary and tie: a body of exactly `RESPONSE_BODY_MAX_CHARS` is stored unmarked, one character more is truncated and marked.

### Major: the delivery tests stand on hand-written fakes, so none of the model-level defects can surface
File: tests/webhooks/test_delivery.py — `FakeEndpoint`, `FakeDelivery`, `test_send_once_posts_the_signed_payload`
What is wrong: the doubles are bare classes with three class attributes rather than `WebhookEndpoint`/`WebhookDelivery` instances, and the one test that touches the wire asserts only that the signature header `startswith("sha256=")` without ever recomputing the MAC over the captured `request.content`.
What breaks in production: the suite is green while the signature does not match the transmitted body, while `next_attempt_at` is naive, while `status` is unrepresentable in the database, and while every claimed row is detached — the four Criticals above are each one assertion or one real object away from being caught by this file.
Fix: bind the fixtures to the production types (construct real `WebhookEndpoint`/`WebhookDelivery` instances, or a factory returning them, so a schema change fails the test rather than passing silently) and strengthen `test_send_once_posts_the_signed_payload` to recompute the expected digest independently from `captured["body"]` and `captured["headers"][TIMESTAMP_HEADER]` and compare it to the transmitted signature exactly, rather than asserting a prefix. Choose fixture values away from defaults and zero values — a non-empty `event_types`, `attempts=2`, a payload with a key whose sorted position differs from its insertion position (e.g. `{"z": 1, "a": 2}`) so a serializer swap is observable. Allow side to pin: a correctly signed delivery still asserts equal. Red-prove three clauses by execution: (i) change one byte of the payload after signing → the equality assertion reds (the current prefix assertion would not); (ii) swap `content=body` for `json=payload` → the equality assertion reds; (iii) drop a required column from the fixture construction → the test errors at construction rather than passing. Do not fix by loosening the comparison to a regex or a snapshot. Boundary and tie: the assertion compares the full header value including the `sha256=` prefix, and a payload whose sorted and insertion orders coincide must not be the only fixture, since it cannot discriminate the two encoders.

### Major: the entire delivery pipeline ships with no tests
File: app/webhooks/delivery.py — `enqueue_for_event`, `deliver`, `run_worker`, `_claim_batch`, `_acquire_lock`, `_finish`; app/api/routes/settings.py — all three new routes
What is wrong: the diff adds these production entry points and the only test file exercises `signing.*`, `backoff_for`, `MAX_ATTEMPTS` and `send_once` — the retry loop, the claim/lock machinery, the enqueue fan-out and every HTTP handler have zero coverage.
What breaks in production: the state machine that decides whether a customer's event is delivered at all is unexercised, so the detached-session crash, the unbound `batch`, the CHECK violation and the missing tenancy filter all ship green and are discovered by customers rather than by CI.
Fix: add tests in the same change covering, at minimum: `enqueue_for_event` fan-out to two active endpoints and exclusion of inactive and non-matching ones; `deliver` marking `delivered`, rescheduling on a retryable failure, and terminating at `MAX_ATTEMPTS`; `_claim_batch` selecting only due rows and not re-claiming a leased one; `run_worker` surviving a raising `_claim_batch`; and one test per route covering the authorized path and the cross-org denial. Allow side to pin: every one of those tests must have a passing case, not only a failing one — the route tests in particular must assert the owner's successful read as well as the stranger's 404. Red-prove by execution, one mutation per test: invert each predicate under test in turn and confirm exactly the corresponding assertion reds, not the whole file. Do not fix by asserting only that functions are importable — `test_max_attempts_matches_documented_limit` is already that shape and pins a constant nothing exercises. Fail loudly: these tests must require a real database fixture and error, not skip, when one is unavailable, or they will report green having examined nothing. Boundary and tie: cover `attempts == MAX_ATTEMPTS - 1` (retried) against `attempts == MAX_ATTEMPTS` (permanent), and a `next_attempt_at` exactly equal to `now`.
