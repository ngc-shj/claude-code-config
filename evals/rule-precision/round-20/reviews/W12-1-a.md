### Critical: any tenant can read any other tenant's delivery history
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never constrains the endpoint to `user.org_id`, while its sibling `list_webhook_endpoints` three lines above does filter `WebhookEndpoint.org_id == user.org_id` — the org predicate was not propagated to the second read path.
What breaks in production: Any authenticated customer can enumerate `endpoint_id` 1..N and read every other organization's event ids, event types, delivery statuses and schedules, which is a cross-tenant data breach on a billing-event feed.
Fix: Resolve the endpoint through the org predicate first, then query deliveries from the resolved row: `endpoint = session.query(webhook_models.WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`; raise `HTTPException(404, detail="endpoint not found")` when it is `None`; query deliveries with `endpoint_id == endpoint.id`. Preserve the behaviour that must still succeed — the owning org still gets its rows newest-first under `limit` — and pin it with an allow-side test asserting the owner receives its N rows, paired with a deny-side test asserting a caller in another org receives 404. Red-prove the two clauses separately by execution: (i) delete the `org_id` predicate and observe the cross-org test go red on row count; (ii) replace the `None` branch with `pass` and observe the 404 test go red on status — two mutations, two different assertions. Fail loudly on the outcome that is neither: if `user.org_id` is `None`/unresolved the handler raises rather than running an unfiltered query, so "no org resolved" is not spelled the same as "no rows". Boundary and tie: an `endpoint_id` belonging to another org and an `endpoint_id` that does not exist must return byte-identical 404 bodies, so existence is not leaked by the difference.

### Critical: the HMAC is computed over bytes that are never transmitted, and does not cover the timestamp
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted) while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes compactly and in insertion order, and the MAC input omits the timestamp entirely although `docs/webhooks.md` states the signature is HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`.
What breaks in production: Every receiver that implements the documented verification recomputes the MAC over the raw body it received and gets a mismatch, so 100% of deliveries are rejected by correctly-written integrations; and because the timestamp is outside the MAC, an interceptor can rewrite `X-Acme-Timestamp` to defeat the five-minute replay window the docs say is the replay defence.
Fix: Serialize exactly once and send those bytes — in `signing.py` add `def canonical(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, make `sign` return `(timestamp, "sha256=" + hmac.new(secret.encode(), b"%s." % timestamp.encode() + body, hashlib.sha256).hexdigest())` over that same `body`, and change `send_once` to `client.post(endpoint.url, content=body, headers={... "Content-Type": "application/json" ...})` so the signed bytes and the wire bytes are one object rather than two independent serializations. Preserve what made the feature useful: the payload delivered must remain the full event JSON with `Content-Type: application/json` — do not fix this by dropping fields or by relaxing the receiver's check. Pair deny with allow: a round-trip test must feed the ACTUAL captured `request.content` and the ACTUAL captured timestamp header through an independently written verifier (recomputed with `hmac`/`hashlib` inline in the test, not by calling `sign`) and assert it passes, alongside a case where one byte of the captured body is flipped and the same verifier rejects. Red-prove each clause separately by execution: (i) revert `separators` to the default and observe the round-trip test red on signature mismatch; (ii) drop the `timestamp + "."` prefix from the MAC input and observe a distinct assertion — that a MAC computed with a different timestamp fails — go red; (iii) switch `content=` back to `json=` and observe the byte-equality assertion between signed and transmitted body go red. Fail loudly where the check cannot run: if `payload` is not JSON-serializable, raise at `canonical` rather than sending an unsigned or partially-signed request. Boundary and tie: state that verification uses the timestamp exactly as transmitted and that a request whose timestamp is exactly `now - 300s` is accepted while `now - 301s` is rejected, and document that two payloads differing only in key order now produce the same MAC because canonicalization sorts keys.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` compares a computed HMAC against an attacker-supplied value with Python's short-circuiting string equality instead of a constant-time comparison.
What breaks in production: An attacker who can submit many candidate signatures recovers the correct digest byte-by-byte from response-time differences and then forges arbitrary signed payloads for any endpoint whose secret this function guards.
Fix: Replace the body with `return hmac.compare_digest(expected, signature)`, keeping `expected` on the left and coercing both operands to `str` before comparison. Preserve the function's existing contract — it still returns `True` for a signature produced by `sign` with the same secret and payload; that allow case must stay pinned by `test_verify_accepts_signature_produced_by_sign`, which must not be deleted or weakened as part of this change. Red-prove the two clauses separately by execution: (i) revert to `==` and confirm a new test asserting `hmac.compare_digest` is on the call path (e.g. by patching `hmac.compare_digest` with a spy and asserting it was called once per `verify`) goes red; (ii) mutate the secret in the existing negative test and confirm it still goes red — a mutation applied singly each time. Fail loudly on the outcomes that are neither pass nor fail: `compare_digest` raises `TypeError` on non-ASCII `str` operands, so guard the input and reject with an explicit `return False` plus a warning log naming the reason rather than letting the exception surface as a 500 that a caller can distinguish from a rejection. Boundary and tie: signatures of unequal length must return `False` without raising, and the equal-length-but-differing case must take the same time as the equal case — note explicitly that `compare_digest` leaks length but not content, so callers must not treat a length mismatch as a distinct outcome.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built with `random.choice` over `string.ascii_letters + string.digits`, and `random` is a Mersenne Twister seeded from predictable state, not a CSPRNG.
What breaks in production: An attacker who observes a handful of issued secrets (or who can register endpoints to sample the generator) can reconstruct the MT19937 state and predict every other tenant's signing secret, letting them forge webhooks that receivers accept as authentic.
Fix: Replace with `secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, delete the `random`, `string` and `_ALPHABET` imports/constants so no second generator survives), and rename `SECRET_BYTES` to mean actual entropy bytes. Preserve what made the value useful — the `whsec_` prefix and the property that the returned value is URL-safe and copy-pasteable — and state that in the change; do not "fix" it by shortening the secret. Pair deny with allow: assert that a freshly generated secret still starts with `SECRET_PREFIX` and still round-trips through `sign`/`verify` (allow side), alongside a test that 1000 generated secrets are all distinct (deny side). Red-prove each clause separately by execution: (i) revert to `random.choice` seeded with `random.seed(0)` in a test process and observe a determinism test — generate under two fixed seeds, assert the outputs differ — go red; (ii) drop the prefix and observe the prefix assertion go red. Update `test_new_signing_secret_has_prefix_and_length` to assert a minimum length (`>= len(SECRET_PREFIX) + 32`) rather than deleting it, so the assertion that made the defect observable is preserved rather than removed. Boundary and tie: `token_urlsafe(32)` returns 43 characters, so the exact-equality length assertion must move to an inequality; state that 32 bytes is the floor and that two secrets colliding is treated as impossible rather than handled.

Red-prove each clause separately by execution: (i) re-add the key to `to_dict` and observe the list-response deny test go red on key presence; (ii) drop the merge in the create route and observe the 201 allow test go red — one mutation per assertion. Fail loudly on the middle outcome: if a rotation endpoint is added later, it must reuse the same explicit-merge path; add an assertion over the exact key set of `to_dict()` (not a subset match) so a future field addition fails the test rather than silently widening the response. Boundary and tie: state that an endpoint created and immediately listed in the same request sequence returns the secret exactly once, and that two endpoints in the same org are both returned without secrets.

Fail loudly where the check cannot run: if the constraint-vs-`STATUSES` comparison cannot read `pg_get_constraintdef` (no DB, wrong dialect), the test must error naming that, not skip silently green. ### Critical: the unique index on `event_id` alone drops every delivery after the first endpoint
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)` permits only one delivery row per event, but `enqueue_for_event` inserts one row per matching endpoint via `session.add_all(rows)`.
What breaks in production: For any organization with two or more active endpoints subscribed to an event, the whole `add_all` fails with a unique violation; the dispatcher's `except Exception: log.warning(...)` swallows it, so every endpoint — including the first — silently receives nothing for that event, and the customer's billing integration is never notified.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which keeps the idempotency guarantee the docs rely on ("deduplicate on `event_id`") per endpoint rather than per event. Preserve the deduplication property — do not fix this by deleting the unique index, which is what stops a re-run of `enqueue_for_event` from double-delivering. Pair deny with allow: an allow-side test enqueues one event for an org with two active endpoints and asserts two rows exist; a deny-side test calls `enqueue_for_event` twice with the same `event_id` and asserts the second raises/no-ops and the row count stays two. Red-prove each clause separately by execution: (i) revert the index to `(event_id)` and observe the two-endpoint allow test go red on IntegrityError; (ii) drop the index and observe the double-enqueue deny test go red on row count — two mutations, two assertions. Fail loudly: pair this with the dispatcher fix below so an enqueue failure is not absorbed by a `log.warning`. ### Critical: the worker uses ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`
What is wrong: `_claim_batch` returns `rows` after the `with session_scope() as session:` block exits, and `deliver` likewise reads `endpoint.signing_secret` / `endpoint.url` outside the block where `session.get` loaded it — with SQLAlchemy's default `expire_on_commit=True` these instances are expired and detached, so the first attribute read raises `DetachedInstanceError`.
What breaks in production: `deliver` raises before the first HTTP request on `delivery.attempts`, the exception is not an `httpx.HTTPError` so it is not caught, it propagates through `asyncio.gather` into `run_worker`, and the delivery worker dies on its very first batch — the feature never delivers anything, while the rows it already flipped to `in_flight` are unrecoverable.
Fix: Stop passing ORM instances across session boundaries — have `_claim_batch` return plain immutable snapshots (a frozen dataclass or dict of `id`, `endpoint_id`, `event_id`, `payload`, `attempts`) read inside the session, and have `deliver` load the endpoint's `url` and `signing_secret` into the same kind of snapshot inside its own `session_scope`. Preserve what made the design useful: the batch claim must remain a single transaction that flips `pending → in_flight` atomically, and `deliver` must still see the current secret. Pair deny with allow: an allow-side integration test runs `_claim_batch` against a real session and asserts every returned snapshot's `payload` is readable after the session closes; a deny-side test asserts that reading an attribute of a raw `WebhookDelivery` after close raises, so the test suite records why the snapshot exists. Red-prove each clause separately by execution: (i) return the raw ORM rows again and observe the post-close read assertion go red with `DetachedInstanceError`; (ii) remove the endpoint snapshot in `deliver` and observe a separate assertion — that `send_once` received a non-empty `signing_secret` — go red. Fail loudly: if `session.get(WebhookEndpoint, delivery.endpoint_id)` returns `None` (endpoint deleted mid-flight), `deliver` must call `_finish(..., "failed_permanent", ...)` with an explicit reason rather than raising `AttributeError` on `None`. Boundary and tie: state what happens when the endpoint is deactivated between claim and send — the current code would still deliver; decide and document that the claim-time snapshot wins, and that two workers cannot hold the same row because the claim is transactional.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, last line of the retry loop
What is wrong: The retry loop calls the blocking `time.sleep(delay)` (module imported as `time`) inside an `async def`, and the same coroutine is fanned out with `asyncio.gather` over a batch of up to `BATCH_SIZE = 100`.
What breaks in production: A single slow receiver stalls the whole loop for up to 2+4+8+16 = 30 seconds, and because the sleeps are blocking they serialize across the batch — 100 failing deliveries wedge the process for roughly 50 minutes, during which nothing else on that event loop (including the redis lock refresh and any co-hosted HTTP handlers) makes progress.
Fix: Do not retry in-line at all — replace the `while True` loop with a single attempt that, on failure, writes `attempts = attempt`, `status = "pending"` and `next_attempt_at = now + backoff_for(attempt)` and returns, letting the poller re-claim the row; if an in-process retry is still wanted, the sleep must be `await asyncio.sleep(delay)`. Preserve the retry semantics the docs promise — at most `MAX_ATTEMPTS` attempts with the same 2/4/8/16 spacing — and preserve `backoff_for` rather than deleting it. Pair deny with allow: an allow-side test asserts a receiver that fails once then succeeds ends `delivered` with `attempts == 2`; a deny-side test asserts a receiver that always fails ends `failed_permanent` with `attempts == MAX_ATTEMPTS` and no further requests. Red-prove each clause separately by execution: (i) change `next_attempt_at` to `now` and observe an assertion on the scheduled timestamp go red; (ii) raise `MAX_ATTEMPTS` to 6 and observe the attempt-count assertion go red; (iii) restore the blocking `time.sleep` and observe a wall-clock assertion — the whole batch completes in under one second against a mock transport — go red. Bound every one of those tests with a timeout so a re-introduced blocking sleep surfaces as a failure rather than a hang. Fail loudly: if `next_attempt_at` cannot be computed (overflow on a large `attempt`), cap it and log rather than writing a null. Boundary and tie: state that `attempt == MAX_ATTEMPTS` is terminal and `attempt == MAX_ATTEMPTS - 1` still reschedules, and that two rows with the identical `next_attempt_at` are ordered by `id` (see the ordering finding below).

### Critical: customer-supplied URLs are delivered to with no host restriction and redirects followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: The only URL check is `parsed.scheme.startswith("http") and parsed.netloc`, so `http://169.254.169.254/...`, `http://localhost:6379/...` and any RFC 1918 address are accepted, and the delivery client is constructed with `follow_redirects=True` so even an allowlisted host can bounce the request into the internal network.
What breaks in production: A tenant turns the delivery worker into an SSRF proxy that issues attacker-controlled POST bodies to cloud metadata endpoints and internal services from inside the trust boundary, with the response body captured into `webhook_deliveries.response_body`.
Fix: Validate at the boundary in `EndpointIn` (a pydantic validator, so the check is schema-level rather than in handler logic): require `scheme == "https"` exactly — which is what `docs/webhooks.md` already promises — reject URLs carrying userinfo, and resolve the host, rejecting any address in a private, loopback, link-local, or reserved range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`. In `run_worker` set `follow_redirects=False` and treat a 3xx as a permanent failure, and re-check the resolved address at connect time (a custom transport / `httpx` event hook) so a DNS rebind between registration and delivery does not bypass the check. Preserve what made the feature useful: an ordinary public HTTPS receiver must still register and still receive deliveries — pin that as the allow-side test alongside deny-side tests for `http://`, `https://127.0.0.1/`, `https://169.254.169.254/`, and a public host that 302s to a private one. Red-prove each clause separately by execution: (i) relax `scheme == "https"` back to `startswith("http")` and observe the `http://` deny test go red; (ii) remove the private-range check and observe the `127.0.0.1` deny test go red; (iii) set `follow_redirects=True` and observe the redirect deny test go red — three mutations, three assertions. Fail loudly where the check cannot run: if DNS resolution fails or times out, reject the registration with an explicit 422 naming "host could not be resolved" — unresolvable must not be spelled the same as allowed. Boundary and tie: name the decision for a host that resolves to both a public and a private address (reject if any resolved address is private) and for IPv6-mapped IPv4 literals.

### Major: deliveries wedge in `in_flight` with no exit and no timeout
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `_finish`
What is wrong: `_claim_batch` moves rows to `in_flight` but the only transitions out are `_finish`'s `delivered` and `failed_permanent`, and `_claim_batch` only ever selects `status == "pending"` — so a worker crash, a redeploy, or any exception escaping `deliver` leaves the row unreachable forever.
What breaks in production: Every delivery in flight at the moment of a deploy is silently lost with no retry and no alert, which for `invoice.paid` means customers are never told about payments they received.
Fix: Give the transient state a bounded exit — stamp `updated_at` (and a `claimed_at`) when claiming, and add a reaper query in `run_worker` that resets rows with `status == 'in_flight' AND updated_at < now() - interval '5 minutes'` back to `pending` with `next_attempt_at = now()` and `attempts` unchanged; additionally wrap the per-delivery work in `try/except BaseException` that routes any unexpected error to `_finish(..., "pending", ...)` with a rescheduled `next_attempt_at`. Preserve the claim's exclusivity — the reaper must not resurrect a row a live worker is still holding, which is what the timeout window buys — and preserve `MAX_ATTEMPTS` so a poison delivery still terminates. Pair deny with allow: an allow-side test asserts a row claimed 10 seconds ago is NOT reaped; a deny-side test asserts a row claimed 10 minutes ago is reset to `pending`. Red-prove each clause separately by execution: (i) remove the age predicate and observe the "not reaped" allow test go red; (ii) remove the reaper call from `run_worker` and observe the reset deny test go red. Fail loudly: if `updated_at` is null on an `in_flight` row (pre-migration data), the reaper must log and reset rather than skip silently. Boundary and tie: define the row at exactly the 5-minute mark as not yet reapable (strict `<`), and state that a reaped row that a zombie worker later `_finish`es must be guarded by a compare-and-set on `attempts`.

### Major: the redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by `set` is a check-then-act race two workers both win; `set` followed by a separate `expire` leaves a permanent lock if the process dies between them; and the `finally` deletes `LOCK_KEY` by name without proving this worker still owns it.
What breaks in production: Two workers claim and deliver the same batch (duplicate webhooks beyond the documented at-least-once, since dedup is only advisory on the receiver), and once a batch outruns the 60-second TTL the lock is owned by a second worker whose lock the first one then deletes, collapsing mutual exclusion entirely.
Fix: Acquire with a single atomic call carrying a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = secrets.token_hex(16)` per acquisition — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only drop its own lock; renew the TTL while a batch is in flight.
