### Critical: the HMAC is computed over different bytes than the request body, and excludes the timestamp
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, used by `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, key-sorted) while `send_once` puts the body on the wire with `client.post(..., json=delivery.payload)`, which httpx serializes with its own compact separators and insertion key order, and the timestamp that `sign()` returns is never fed into the MAC at all.
What breaks in production: every customer who implements the documented scheme — HMAC-SHA256 over `"{timestamp}.{raw_request_body}"` — computes a digest that cannot equal ours for any payload, so 100% of deliveries fail verification and the documented five-minute replay window is unenforceable because the timestamp is unauthenticated and freely rewritable by a man in the middle.
Fix: Make the signed bytes and the sent bytes the same object. In `send_once`, build `body = signing.serialize(delivery.payload).encode()` once, sign `f"{timestamp}.{body.decode()}"` (i.e. change `sign()` to take the already-serialized body and prefix the timestamp inside the MAC input, per `docs/webhooks.md`), and send it with `client.post(endpoint.url, content=body, headers=...)` — never `json=`, which re-serializes. `verify(secret, body_bytes, timestamp, signature)` must take the raw bytes too, not a dict, so no code path can re-serialize between signing and checking. Preserve what the current code got right and must keep working: `sort_keys=True` (stable digests across dict insertion order) and the `sha256=` prefix — do not "fix" this by dropping canonicalization. Deny/allow pairing: pin the allow case that must still succeed — a delivery whose body is signed and then verified through the *wire bytes* returns `True`, including for a payload with non-ASCII values and with keys supplied out of alphabetical order; and pin the deny case — the same body with one byte changed, or with the timestamp field altered while the signature is kept, returns `False`. Red-prove each clause separately by execution: (a) revert `content=body` to `json=payload` and observe the wire-bytes verification assertion go red; (b) drop the `f"{timestamp}."` prefix from the MAC input and observe only the timestamp-tamper assertion go red; (c) remove `sort_keys=True` and observe only the key-order assertion go red — three mutations, three distinct red assertions. Fail loudly when the check cannot run: `verify()` must raise on a signature that does not match the `sha256=<64 hex>` shape rather than returning `False`, so "malformed header" is not spelled the same as "wrong signature". Boundary and tie: state that a timestamp exactly `300` seconds old is REJECTED (`now - ts >= 300` denies) and that two deliveries with identical payload and identical timestamp legitimately produce identical signatures — that collision is expected and must not be treated as a replay by the receiver, which deduplicates on `event_id`.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: `verify()` compares the recomputed digest with `==`, whose byte-by-byte short-circuit leaks the position of the first mismatch through timing (RS1).
What breaks in production: an attacker with a verification oracle — any inbound path we later point at this helper, or any customer who copies it, since it is the reference implementation shipped beside the docs — recovers a valid signature byte by byte and forges events without ever knowing the signing secret.
Fix: Replace with `hmac.compare_digest(expected, signature)`, comparing already-normalized fixed-length strings so the length itself carries no information (reject on shape before comparing, per the previous finding). Deny/allow pairing: the valid signature must still authenticate — assert `verify()` returns `True` for a signature produced by `sign()` over the identical wire bytes — and the wrong-secret signature must still be rejected. Red-prove by execution: revert `compare_digest` to `==` and confirm a test that greps the module source for a constant-time primitive on the comparison line goes red (the timing itself is not assertable in a unit test, so the check is on the primitive, and that check must be red-proven, not assumed). Fail loudly when the check cannot run: if `signature` is `None` or not `str`, raise rather than returning `False`, so an absent header is distinguishable from a bad one. Do not fix by deleting: keep `verify()` public and keep it exercised by the existing wrong-secret test — removing the helper because production does not call it is not a fix, since the docs point customers at it. Boundary and tie: a signature of the correct length that differs only in the final byte must be rejected in the same time as one differing in the first.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from predictable state and is fully reconstructible from ~624 observed outputs, so the HMAC key is guessable rather than secret.
What breaks in production: an attacker who registers a handful of their own endpoints observes enough generator output to recover the internal state, predicts every other tenant's signing secret, and forges `invoice.paid` webhooks into their systems.
Fix: Use `secrets.token_urlsafe(SECRET_BYTES)` (or `secrets.choice` over `_ALPHABET` if the alphabet is contractual) and rename `SECRET_BYTES` to `SECRET_CHARS` if the character-count meaning is kept, since the current name claims bytes of entropy while the code produces 32 characters over a 62-symbol alphabet. Deny/allow pairing: the allow case that must still pass is that the returned value still starts with `whsec_` and still satisfies the existing length assertion, so `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` stays green unchanged; the deny case is a new assertion that 1,000 generated secrets are all distinct. Red-prove each clause separately: (a) revert to `random.choice` and confirm a source-level assertion that the module imports `secrets` and does not import `random` goes red; (b) shorten the generated length by one and confirm only the length assertion goes red. Fail loudly when the check cannot run: nothing here may fall back to `random` if `secrets` is unavailable — let the import error propagate. Do not fix by deleting: keep the prefix and the length test; they are what makes a truncated or unprefixed secret visible. Boundary and tie: state that a secret of exactly `len(SECRET_PREFIX) + SECRET_CHARS` is valid and that two independently generated secrets colliding is a test failure, not a tolerated tie.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query filters on the path parameter alone and never joins `WebhookEndpoint` to check `org_id == user.org_id`, so `endpoint_id` is an unguarded direct object reference (the sibling route `list_webhook_endpoints` in the same diff does apply the `org_id` filter — the tenancy predicate exists and this route omits it, R3).
What breaks in production: any authenticated user enumerates sequential `endpoint_id` values and reads other tenants' delivery rows, and since `to_dict()` exposes `event_type` and `response_status` for billing events, this is a cross-tenant data breach that also contradicts the docs' claim that the route returns attempts "for an endpoint belonging to your organization".
Fix: Join through the endpoint and filter on the caller's org in the same query: `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and return 404 (not 403) when the join is empty so the response does not confirm the id exists. Deny/allow pairing: pin both sides — a user of org A requesting their OWN endpoint's deliveries still gets the rows (this is the case a fix that always denies would silently break), and a user of org A requesting org B's endpoint gets 404 with an empty body. Red-prove each clause by execution: (a) delete the `org_id` predicate and confirm the cross-tenant test goes red while the own-org test stays green; (b) delete the join and confirm the own-org test goes red for a different reason (the query no longer resolves the endpoint). Per RT8, the cross-tenant test must assert the returned list is empty, not merely the status code. Fail loudly when the check cannot run: if `user.org_id` is `None`, deny with 403 rather than letting the predicate degrade to a no-op comparison. Do not fix by deleting: keep the `limit` and the ordering — the fix is scoping, not removing the feature. Boundary and tie: an endpoint that was transferred between orgs is decided by its CURRENT `org_id`, and a request for an endpoint id that does not exist at all returns the same 404 as one belonging to another org.

### Critical: the status CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py:deliver` writing `"failed_permanent"`
What is wrong: the migration enumerates `'failed'` while both `app/webhooks/models.py:STATUSES` and `_finish(delivery.id, "failed_permanent", ...)` use `failed_permanent` — the class of legal statuses was transcribed into a second place and drifted (R42, R2).
What breaks in production: the first delivery to exhaust its retries raises `IntegrityError` inside `_finish`, which propagates out of `deliver`, out of `asyncio.gather`, and kills `run_worker` — after the exception the Redis lock is deleted by the `finally` but the process is gone, so all webhook delivery stops on the first permanently-failing endpoint.
Fix: Derive the constraint from one source. Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and add a test that asserts the SQL literal set equals `app.webhooks.models.STATUSES` by parsing the migration file, so the next status added cannot drift again. Deny/allow pairing: the allow case is that inserting each of the four members of `STATUSES` succeeds against a real migrated schema; the deny case is that inserting `'bogus'` raises `IntegrityError`. Red-prove each clause separately by execution: (a) remove one member from the SQL list and confirm the parity test names that member in its failure output; (b) remove the `CHECK` clause entirely and confirm the `'bogus'` insert test goes red. Fail loudly when the check cannot run: if the parity test cannot locate or parse the migration file it must fail with "migration not found", never skip — "examined nothing" must not report green. Do not fix by deleting: do not resolve this by dropping the CHECK constraint; the constraint is what makes a typo'd status visible. Boundary and tie: state that a row already written as `'failed'` by any earlier hand-run of this migration is migrated to `'failed_permanent'` in the same transaction, and that `in_flight` is a legal persisted value at rest (a crashed worker leaves rows there — see the stuck-`in_flight` finding).

### Critical: `UNIQUE (event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint for the same `event_id`, so any org with two subscribed endpoints violates the index.
What breaks in production: the `add_all` raises on commit, rolling back every row for that event — including the first endpoint's — and `app/events/dispatcher.py` swallows the exception into a `log.warning`, so the customer's webhooks silently stop the moment they register a second endpoint, with no failed delivery row to inspect.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)` — that is the real idempotency key (one delivery per event per endpoint) and it still gives the at-least-once dedup guarantee the docs promise. Deny/allow pairing: the allow case that must still work is one event fanning out to three endpoints of the same org producing three rows; the deny case is re-running `enqueue_for_event` for the same `(endpoint_id, event_id)` producing no second row (use `ON CONFLICT DO NOTHING` / `INSERT ... ON CONFLICT` semantics rather than letting the exception escape). Red-prove each clause separately: (a) revert the index to `(event_id)` and confirm the three-endpoint fan-out test goes red on `IntegrityError`; (b) drop the uniqueness entirely and confirm the duplicate-enqueue test goes red by observing two rows. Fail loudly when the check cannot run: `enqueue_for_event` must not be the place that swallows a constraint error — see the dispatcher finding; a conflict on any key OTHER than this one must still raise. Do not fix by deleting: do not resolve this by dropping the unique index, which is what prevents duplicate delivery on a retried dispatch. Boundary and tie: an endpoint whose `event_types` does not match produces no row at all (not a row in a skipped state), and two endpoints of DIFFERENT orgs receiving the same `event_id` is legal and must not collide.

### Critical: endpoint URLs are unvalidated against internal networks, with redirects followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check is that the scheme string starts with `http` (which admits plain `http://`, contradicting the docs' "Only `https://` URLs are accepted", and admits any scheme literally prefixed `http`) and there is no restriction on the host, so `http://169.254.169.254/latest/meta-data/` or `http://127.0.0.1:6379/` is accepted and then POSTed to by the worker, with `follow_redirects=True` letting a public host bounce us to an internal one after validation (RS3: the value reaches an outbound-request sink unvalidated).
What breaks in production: a customer turns our worker into a server-side request forgery proxy against our own VPC, exfiltrating cloud instance-metadata credentials into their `response_body` column, which the deliveries API then hands back to them.
Fix: Validate at the schema boundary with a pydantic validator on `EndpointIn.url`: require `parsed.scheme == "https"` exactly (equality, not `startswith`), require a non-empty registrable hostname, resolve the host and reject when any resolved address is private, loopback, link-local, multicast, or unspecified (`ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved`), and cap the URL length. Then set `follow_redirects=False` on the delivery client so a 3xx is recorded as a failed attempt rather than chased, and re-resolve-and-re-check the host at send time, because the DNS answer at registration is not the answer at delivery (R51: the check and the use are separated by an interval, and the name is re-resolved). Deny/allow pairing: the allow case that must still succeed is `https://hooks.example.com/acme` — the exact URL in `docs/webhooks.md` and in the test fixture — registering with 201 and delivering; the deny cases are `http://hooks.example.com`, `https://127.0.0.1/x`, `https://metadata.internal` resolving to 169.254.169.254, and a public host that 302s to a private one. Red-prove each clause separately by execution: (a) revert `==` to `startswith` and confirm only the `http://` test reddens; (b) remove the address-class check and confirm only the loopback test reddens; (c) restore `follow_redirects=True` and confirm only the redirect test reddens. Fail loudly when the check cannot run: a DNS resolution failure at registration must return 422 "url host could not be resolved", never fall through to accepted — an unresolvable host must not be spelled the same as a safe one. Do not fix by deleting: keep the endpoint-creation feature and keep customer-supplied hosts working; the fix is an allowlist of address classes, not removing outbound delivery. Boundary and tie: state that a host resolving to BOTH a public and a private address is denied (any private answer denies), and that `https://` on a non-443 public port is allowed.

### Critical: `time.sleep()` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` for up to `BATCH_SIZE` (100) deliveries, but the retry backoff uses the blocking `time.sleep`, which stops the entire loop rather than yielding.
What breaks in production: one slow endpoint's 2+4+8+16 = 30 seconds of backoff freezes every other concurrent delivery, the Redis lock's 60-second TTL expires while the loop is blocked, and if the process also serves HTTP the API stops responding.
Fix: Replace with `await asyncio.sleep(delay)`; `asyncio` is already imported in this module (line: `import asyncio`) and `run_worker` already uses `await asyncio.sleep(poll_interval)` — the correct primitive is present in the same file and this call site reimplements it with the blocking twin (R1). Remove the now-unused `import time`. Deny/allow pairing: the allow case that must still hold is that the delay still elapses — assert with a patched clock that a retried delivery does not re-POST before `backoff_for(attempt)` has passed (a fix that simply drops the sleep satisfies "does not block" and is wrong); the deny case is that two `deliver()` coroutines gathered together complete in about the duration of the longer one, not the sum. Red-prove each clause separately: (a) restore `time.sleep` and confirm only the concurrency assertion reddens; (b) delete the sleep entirely and confirm only the elapsed-delay assertion reddens. Fail loudly when the check cannot run: if the concurrency test cannot install its clock patch it must error, not skip. Do not fix by deleting: the backoff itself must be preserved — retrying immediately would hammer a failing customer endpoint. Boundary and tie: at `attempt == MAX_ATTEMPTS` the code must finish `failed_permanent` WITHOUT sleeping first (the current ordering already does this — preserve it), and two deliveries scheduled for the identical `next_attempt_at` may run in either order.

### Critical: ORM objects are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returning `rows` outside the `with session_scope()` block; `deliver()` reading `endpoint` after its own `with` block exits
What is wrong: both functions open a `session_scope()`, load entities, and then return or use those entities after the block has exited — and this diff's own use of `session_scope` shows the block is a commit-and-close unit of work (`enqueue_for_event` returns a count with no explicit commit, and `_finish` opens a *fresh* scope by id precisely because the object from `_claim_batch` cannot be written through the original one), so every later attribute read (`delivery.payload`, `delivery.attempts`, `delivery.id`, `endpoint.url`, `endpoint.signing_secret`) touches expired attributes on a detached instance.
What breaks in production: `run_worker` raises `DetachedInstanceError` on the first claimed row, so the worker as written never delivers anything — and none of the shipped tests can catch it because they substitute `FakeEndpoint`/`FakeDelivery` plain classes for the real models.
Fix: Stop passing ORM entities across session boundaries — have `_claim_batch` return plain immutable snapshots (a frozen dataclass carrying `id`, `endpoint_id`, `attempts`, `payload`, plus the endpoint's `url` and `signing_secret` fetched in the same query via a join), built inside the block, and change `send_once`/`deliver` signatures to take those snapshots. This also removes `deliver`'s extra per-delivery endpoint SELECT (an N+1 against a set the batch query could have joined). Deny/allow pairing: the allow case is an integration test against a real session that claims a batch, delivers through a `MockTransport`, and asserts the row reaches `delivered` — this must pass, and it is what a fix that merely wraps everything in one long-lived session would appear to satisfy while holding a transaction open across network I/O; the deny case is that no attribute of a mapped entity is read outside a `with session_scope()` block, asserted by a test that claims a batch and then asserts the returned objects are not SQLAlchemy-mapped instances. Red-prove each clause separately: (a) revert `_claim_batch` to returning `rows` and confirm the integration test reddens with `DetachedInstanceError` named in the output; (b) revert `deliver`'s endpoint fetch and confirm only the not-mapped assertion reddens. Fail loudly when the check cannot run: if the test database is unavailable the integration test must error, never be skipped into a green run. Do not fix by deleting: the `in_flight` marking in `_claim_batch` must be preserved — it is the claim, and dropping it to simplify the return type reintroduces double delivery. Boundary and tie: a row whose `next_attempt_at` is exactly `now` IS claimed (`<=`), and two workers claiming the same instant are serialized by `SELECT ... FOR UPDATE SKIP LOCKED` on the claim query, which should be added here rather than relying on the Redis lock.

### Critical: the signing secret is returned by the endpoint-listing API
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()` including `"signing_secret": self.signing_secret`, consumed by `list_webhook_endpoints` in `app/api/routes/settings.py`
What is wrong: `to_dict()` is the single serializer used by both the creation response and the list response, so the long-lived HMAC key is returned on every `GET /v1/settings/webhook-endpoints` — directly contradicting `docs/webhooks.md`, which states the creation response "is the only place the signing secret appears — it cannot be read back afterwards" (R49: the documented control is stronger than the implementation; RS4: a secret in a routinely-returned artifact).
What breaks in production: the secret is served on an idempotent GET, so it lands in browser caches, proxy and CDN logs, API-gateway access logs, and any read-only integration granted "list endpoints" scope — turning a key-exposure incident into a routine one and making the documented rotation story false.
Fix: Remove `signing_secret` from `to_dict()` and return it exactly once, from `create_webhook_endpoint`, as an explicit extra key on that response only (`{**endpoint.to_dict(), "signing_secret": secret}`), constructed from the local variable rather than re-read from the model. Deny/allow pairing: the allow case that must still succeed is that `POST /v1/settings/webhook-endpoints` still returns a usable `signing_secret` in its 201 body — a fix that strips the field everywhere makes the feature unusable and would otherwise satisfy every clause; the deny case is that `GET /v1/settings/webhook-endpoints` and the delivery listing contain no key matching `secret` anywhere in the serialized response. Red-prove each clause separately by execution: (a) re-add `signing_secret` to `to_dict()` and confirm only the GET-response assertion reddens; (b) remove it from the POST handler and confirm only the creation assertion reddens. Fail loudly when the check cannot run: the GET assertion must scan the whole serialized body for the substring, so a future field added under another name still trips it rather than passing unexamined. Do not fix by deleting: keep `to_dict()` as the shared serializer — the fix is narrowing its contents, not forking a second serializer that will drift (R1/RT9). Boundary and tie: state that a re-created endpoint with the same URL gets a NEW secret, and that there is no read-back path at all, so a customer who loses the secret must delete and re-register.

### Major: the outbound request logs the signature header at INFO
File: `app/webhooks/delivery.py` — `send_once()`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: the whole header dict is logged, which includes `X-Acme-Signature` and `X-Acme-Timestamp` for every attempt.
What breaks in production: a valid `(timestamp, signature)` pair for a known payload sits in the shipped log index, so anyone with log-read access can replay that exact request to the customer's endpoint for as long as their acceptance window allows, and the log volume is one line per attempt per delivery.
Fix: Log only what is diagnosable without the credential — `log.debug("POST %s delivery=%s attempt=%s", endpoint.url, delivery.id, attempt)` — and never the headers dict or the payload. Deny/allow pairing: the allow case is that a failed delivery still produces a log line naming the endpoint and delivery id (a fix that removes logging entirely destroys the operability this line was there for); the deny case is a test asserting that no emitted record's formatted message contains the signature value. Red-prove: restore the headers interpolation and confirm the no-signature-in-logs assertion reddens; separately remove the delivery id and confirm the diagnosability assertion reddens. Fail loudly when the check cannot run: the log-capture fixture must fail if it captures zero records, so "no signature found" cannot be reported by a logger that emitted nothing. Do not fix by deleting: keep an attempt-level log line. Boundary and tie: at the final attempt the line must still be emitted before `_finish` writes the terminal status.

### Major: the Redis lock is not atomic to acquire, not atomic to expire, and released without ownership
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get`-then-`set` is a check-then-act with an interval two workers both pass; `set` followed by a separate `expire` leaves the key permanent if the process dies between them; and the release deletes the key unconditionally, without checking that this worker still holds it (R51 — the decision is bound to the key NAME, not to a token identifying the holder; R38(2) — a persisted fail-closed state with no reset path).
What breaks in production: a crash between `set` and `expire` wedges all webhook delivery permanently with no operator affordance short of manual Redis surgery, and when the 60-second TTL expires mid-batch (which the blocking backoff above makes routine) worker A's `finally` deletes worker B's freshly acquired lock, so two workers claim overlapping batches and customers get duplicate deliveries.
Fix: Acquire with a single atomic call carrying a per-acquisition token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock. Set `LOCK_TTL_SECONDS` from a named constant and renew it while a batch is in flight. Deny/allow pairing: the allow case that must still hold is that a worker whose predecessor exited cleanly acquires the lock on the next poll — a fix that only tightens (never releasing) stops all delivery; the deny case is that a second worker calling `_acquire_lock` while the first holds it gets `False`, and that the first worker's release after its token has been superseded deletes nothing. Red-prove each clause separately by execution: (a) revert to `get`-then-`set` and confirm the concurrent-acquire test reddens; (b) split `ex=` back into a separate `expire` call, kill the fake client between the two, and confirm the "lock expires even if the process dies mid-acquire" assertion reddens; (c) revert the release to an unconditional `delete` and confirm only the foreign-lock assertion reddens. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must propagate and stop the worker with a named error, not be caught into `return False`, which would spell "Redis is down" the same as "someone else holds the lock" and hide an outage as an idle worker. Do not fix by deleting: keep the single-dispatcher mutual exclusion; removing the lock in favour of "the DB claim is enough" is only safe once the claim uses `FOR UPDATE SKIP LOCKED`. Boundary and tie: state that a lock whose TTL expires at exactly the moment of release is treated as NOT held (the compare fails, delete is a no-op), and that two workers submitting `set nx` in the same millisecond result in exactly one winner.

### Major: `run_worker` dies on the first exception and busy-loops when work exists
File: `app/webhooks/delivery.py` — `run_worker()`
What is wrong: `batch` is assigned inside the `try` but read after the `finally` (`if not batch:`), so any exception from `_claim_batch` leaves it unbound; no exception from `_claim_batch`, `gather`, or `_finish` is caught, so the coroutine terminates and the loop never resumes; and when a batch is non-empty the loop immediately re-acquires the lock with no yield.
What breaks in production: a single transient database error permanently stops all webhook delivery with no supervisor and no alert beyond the process exiting, and under sustained load the worker spins acquiring and deleting the Redis lock on every iteration.
Fix: Initialize `batch: list = []` before the `try`, wrap the claim-and-deliver body in `except Exception: log.exception(...)` so one bad iteration does not kill the loop, use `return_exceptions=True` on the `gather` so one failing delivery does not cancel its siblings, and always `await asyncio.sleep(poll_interval)` at the end of the iteration (a short sleep when work remains, the full interval when idle). Deny/allow pairing: the allow case is that a worker fed one poisoned delivery and one good one still delivers the good one and is still running on the next iteration — a fix that only adds a bare `except: pass` satisfies "does not die" while silently discarding the failure, so also assert the exception was logged with its traceback; the deny case is that the loop does not iterate more than once per `poll_interval` when the batch is empty. Red-prove each clause separately by execution: (a) remove the `batch = []` initialization, make `_claim_batch` raise, and confirm the reddened test names `UnboundLocalError`; (b) remove `return_exceptions=True` and confirm only the sibling-delivery assertion reddens; (c) remove the unconditional sleep and confirm only the iteration-rate assertion reddens. Fail loudly when the check cannot run: the caught-and-logged branch must re-raise on `asyncio.CancelledError` so shutdown is not swallowed as "a transient error". Do not fix by deleting: the lock release in `finally` must be preserved. Boundary and tie: a batch of exactly zero rows sleeps the full `poll_interval`; a batch of exactly `BATCH_SIZE` rows implies more work and must sleep a short interval, not zero.

### Major: naive and aware datetimes are mixed across the three new files

### Major: retries loop in-process instead of rescheduling, and `in_flight` has no exit on crash
