### Critical: the transmitted body is not the bytes that were signed, and the timestamp is unauthenticated
File: app/webhooks/signing.py — `sign` / `serialize`, and app/webhooks/delivery.py — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, `ensure_ascii=True`) while `send_once` transmits a body httpx re-serializes itself from `json=delivery.payload` (insertion order, compact separators), and the timestamp header is never fed into the MAC at all — so the digest covers neither the bytes on the wire nor the timestamp, contradicting `docs/webhooks.md` ("the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`").
What breaks in production: every customer who verifies as documented — recompute over the raw body — gets a mismatch and rejects 100% of deliveries, and any receiver that instead ignores the body encoding can replay a captured request forever by rewriting the unauthenticated `X-Acme-Timestamp`.
Fix: serialize once in `send_once` (`body = serialize(delivery.payload).encode()`), change `sign` to take those exact bytes and MAC `f"{ts}.".encode() + body`, and post with `content=body` plus an explicit `Content-Type: application/json` header so httpx cannot re-encode. Preserve the deny side already present — `test_verify_rejects_a_signature_made_with_another_secret` must stay green — and add the allow side that is missing: a test that recomputes `hmac.new(SECRET, b"<ts>." + captured["body"], sha256)` from the captured request and asserts byte equality with the captured signature header. Red-prove the two clauses separately by executing them: (i) revert to `json=` and confirm the new byte-equality assertion reddens naming the digest mismatch, (ii) drop the `f"{ts}."` prefix and confirm a second assertion — that a request whose timestamp header is mutated fails `verify` — reddens independently. `sign` must raise on a payload `json.dumps` cannot encode rather than sending an unsigned body, so "could not sign" is not spelled like "signed". Boundary: a receiver's freshness window is inclusive at exactly `now - 300s`; two deliveries sharing one timestamp are distinguished by `event_id`, not by the timestamp.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: the secret is built from `random.choice` over a 62-character alphabet, and `random` is a Mersenne Twister seeded from a predictable source and fully recoverable from a few hundred observed outputs — the module ships a helper for exactly this (`secrets`) that the new code reimplements badly (R1).
What breaks in production: an attacker who obtains their own endpoint's secret, or who observes enough secrets issued by the same process, can reconstruct the generator state and forge signed webhooks for other organizations, which is the only thing the signature exists to prevent.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and rename `SECRET_BYTES` to what it now means (raw entropy bytes, not characters). Keep the deny/allow pair measurable: `test_new_signing_secret_has_prefix_and_length` must still pass after being updated to assert the new encoded length, and add an assertion that 1000 generated secrets are all distinct. Red-prove separately: (i) substitute a constant return and confirm the distinctness assertion reddens, (ii) substitute a 4-character secret and confirm the length assertion reddens. Do not fix by deleting the prefix or the length assertion — the `whsec_` prefix is what lets customers identify the credential in their own stores. If `secrets` is unavailable the call must raise at import, never fall back to `random`. Rotate every secret already issued by the deployed version; existing secrets are compromised.

### Critical: every endpoint's signing secret is readable back from the list route
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`, consumed by app/api/routes/settings.py — `list_webhook_endpoints`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns `to_dict()` for every endpoint, so the secret is served on every GET — directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards"), an overstated control claim in the sense of R49 and a committed-artifact credential exposure in the sense of RS4.
What breaks in production: any actor holding a read-scoped API token, and every log, proxy, or browser cache on the GET path, obtains the key that authenticates all webhook traffic for that organization.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held value, so exactly one route can emit it. Pair the sides: assert the create response contains `signing_secret` (allow) and that the list response for the same endpoint does not (deny) — a fix that strips the field everywhere would satisfy the deny side alone and silently break registration. Red-prove each separately: re-add the key to `to_dict()` and confirm only the list assertion reddens; drop the key from the create handler and confirm only the create assertion reddens. Add a rotation route rather than restoring readback, since the doc's promise is now the contract.

### Critical: the deliveries route is not scoped to the caller's organization
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: the query filters on the path-supplied `endpoint_id` only, while its sibling `list_webhook_endpoints` (and the pre-existing `list_api_keys`) both filter on `user.org_id` — the tenancy predicate was not propagated to the third route (R3, security-relevant).
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other tenants' delivery history — event ids, event types, and the response codes their partners returned.
Fix: join the delivery query to `WebhookEndpoint` and filter `WebhookEndpoint.org_id == user.org_id` alongside `endpoint_id`, and raise `HTTPException(404)` when the endpoint does not resolve under that predicate so a foreign id is indistinguishable from a missing one. Pair the sides: one test asserting the owner still receives their rows (allow) and one asserting a second org receives 404 (deny) — a fix that always 404s passes the deny test alone. Red-prove separately: delete the `org_id` clause and confirm only the cross-tenant test reddens; return 404 unconditionally and confirm only the owner test reddens. Assert the denial's substance, not just the status (RT8): the cross-tenant response body must be empty. Boundary: an endpoint whose org was just reassigned resolves under the new org and 404s for the old one.

### Critical: endpoint URLs are accepted without an SSRF guard, and redirects are followed
File: app/api/routes/settings.py — `create_webhook_endpoint`; app/webhooks/delivery.py — `run_worker` (`follow_redirects=True`)
What is wrong: `parsed.scheme.startswith("http")` admits `http`, and any other scheme whose name begins with those four letters, with no check that the host is publicly routable — while `docs/webhooks.md` states "Only `https://` URLs are accepted" (RS3, and an R49 claim stronger than the implementation).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/` — or a public URL that 302s there once `follow_redirects=True` takes over — and the worker POSTs signed internal requests from inside the VPC and stores the response body in `webhook_deliveries.response_body` for the tenant to read back, turning the delivery worker into an authenticated SSRF proxy.
Fix: validate with an exact `parsed.scheme != "https"` rejection, resolve the hostname at registration and reject when any resolved address is loopback, link-local, private, or reserved (`ipaddress.ip_address(a).is_global` is false), set `follow_redirects=False` on the client so a redirect is recorded as a non-2xx rather than chased, and re-check the address at send time because DNS can be re-pointed after registration. Pair the sides: `https://hooks.example.com/acme` must still register and deliver (allow) — do not fix by rejecting all outbound hosts. Red-prove each clause separately: `http://hooks.example.com` reddens the scheme assertion; `https://127.0.0.1/x` reddens the address assertion; a handler returning 302 to a private host reddens the redirect assertion. A DNS resolution failure must reject the registration with a named error, never fall through to "no bad address found". Boundary: an address exactly at the edge of a reserved range (`169.254.0.0`, `127.255.255.255`) is rejected; a host resolving to both a public and a private address is rejected.

### Critical: the unique index on `event_id` alone allows only one delivery row per event
File: migrations/0042_webhook_delivery.sql — `idx_webhook_deliveries_event`
What is wrong: `CREATE UNIQUE INDEX ... ON webhook_deliveries (event_id)` makes the event id globally unique, but `enqueue_for_event` inserts one row per matching endpoint, so the second endpoint's row violates the constraint.
What breaks in production: any organization with more than one active endpoint gets an `IntegrityError` on the enqueue transaction, which the dispatcher's `except Exception` swallows into a log line — no endpoint receives the event, and nothing surfaces the loss.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which preserves the property the index was there for — the at-least-once dedup key promised in `docs/webhooks.md` — while allowing fan-out. Pair the sides: an integration test enqueuing one event for two active endpoints must produce two rows (allow), and re-enqueuing the same event for the same endpoint must produce one (deny). Red-prove separately: revert the index to `(event_id)` and confirm the fan-out test reddens; drop the index entirely and confirm the dedup test reddens. Boundary: two endpoints of *different* orgs consuming the same `event_id` is legal under the composite key and must be asserted as such.

### Critical: the status CHECK constraint rejects the terminal status the code writes
File: migrations/0042_webhook_delivery.sql — `webhook_deliveries.status CHECK`, against app/webhooks/models.py — `STATUSES` and app/webhooks/delivery.py — `_finish`
What is wrong: the migration allows `('pending', 'in_flight', 'delivered', 'failed')` while `STATUSES` and `_finish` use `failed_permanent` — the same enum is spelled three times with no shared source (R2), and the two spellings disagree.
What breaks in production: the moment a delivery exhausts `MAX_ATTEMPTS`, `_finish` raises a check-constraint violation, the update rolls back, and the row is left in `in_flight` forever while the exception escapes `deliver` and kills the worker task.
Fix: correct the CHECK to `('pending', 'in_flight', 'delivered', 'failed_permanent')`, and have both `models.STATUSES` and `delivery.py` reference one exported tuple so a fourth spelling cannot appear; add a migration test that asserts the DB-accepted set equals `set(STATUSES)`. Pair the sides: inserting each member of `STATUSES` must succeed (allow) and inserting `"bogus"` must raise (deny) — widening the CHECK to accept anything would pass the allow side alone. Red-prove separately: remove `failed_permanent` from the CHECK and confirm the allow test reddens on that member by name; drop the CHECK and confirm the deny test reddens. Ship the constraint-set assertion rather than deleting the CHECK, which is what makes the drift visible.

### Critical: `time.sleep` blocks the event loop inside an async retry loop
File: app/webhooks/delivery.py — `deliver`
What is wrong: the retry backoff calls the blocking `time.sleep(delay)` from inside an `async def` that `run_worker` schedules under `asyncio.gather`, so the thread — not the coroutine — sleeps.
What breaks in production: a single failing endpoint freezes the whole event loop for up to 30 seconds per delivery (2+4+8+16), serializing the entire 100-row batch into roughly fifty minutes and stalling every other coroutine in the process, including the API server if it shares one.
Fix: replace with `await asyncio.sleep(delay)`. Pair the sides: assert that two deliveries whose first attempt fails complete in wall-clock time close to one backoff rather than two (allow — concurrency preserved), and keep an assertion that the delay actually elapses (deny — do not fix by deleting the sleep, which would hammer the customer's endpoint five times instantly). Red-prove separately: restore `time.sleep` and confirm the concurrency assertion reddens; set the delay to zero and confirm the elapsed-time assertion reddens. Use a monotonic clock, not wall time, so a clock step cannot make the timing assertion pass without the sleep having run. Boundary: `attempt == MAX_ATTEMPTS` must not sleep at all before finishing.

### Critical: signature verification uses a variable-time comparison
File: app/webhooks/signing.py — `verify`
What is wrong: the expected and supplied signatures are compared with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: wherever this helper is used to authenticate an inbound signed request, an attacker recovers a valid signature byte by byte from response timing without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, guarding against a non-`str` `signature` by rejecting before the comparison rather than letting `compare_digest` raise. Pair the sides: `test_verify_accepts_signature_produced_by_sign` must stay green (allow) alongside `test_verify_rejects_a_signature_made_with_another_secret` (deny). Red-prove separately: make `verify` return `True` unconditionally and confirm the reject test reddens; make it return `False` unconditionally and confirm the accept test reddens. A `signature` of `None` or bytes must raise a named error, not return `False` silently, so "could not compare" is distinguishable from "did not match". Boundary: a signature of correct length differing in the final byte must be rejected, and two distinct secrets producing the same digest is not a case the comparison is allowed to admit.

### Major: the distributed lock is non-atomic, expires mid-batch, and is released by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock` / `run_worker`
What is wrong: `get` then `set` is a check-then-act with no `NX`, the 60-second `expire` is far shorter than a batch's worst case (100 deliveries × up to 5 attempts × 30s timeout plus 30s of backoff), and `run_worker`'s `finally` deletes `LOCK_KEY` unconditionally — including a lock a *different* worker acquired after this one's expired.
What breaks in production: two or more workers claim the same batch and deliver every webhook twice or more, and because each release deletes the other's lock the mutual exclusion degrades to none under exactly the load it was added for.
Fix: acquire with a single atomic `SET LOCK_KEY <uuid> NX EX <ttl>`, release with a compare-and-delete (Lua `if GET == uuid then DEL end`) so a worker can only drop its own lock, and renew the TTL from the batch loop so the lease outlives a batch bounded by `BATCH_SIZE × MAX_ATTEMPTS × REQUEST_TIMEOUT`. Pair the sides: a single worker must still acquire and proceed (allow) and a second concurrent worker must not (deny) — a fix that never acquires satisfies the deny side alone. Red-prove separately: drop `NX` and confirm the mutual-exclusion test reddens; restore the unconditional delete and confirm the ownership test reddens; shorten the TTL below the batch bound and confirm the renewal test reddens. A Redis outage must make `_acquire_lock` raise rather than return `False` forever, so "cannot check" is not spelled like "someone else holds it". Boundary: a lock whose TTL expires at exactly the instant of release is not ours, and the compare-and-delete must treat that as a no-op.

### Major: `in_flight` is a non-terminal state with no reclaim path
File: app/webhooks/delivery.py — `_claim_batch` / `_finish`
What is wrong: `_claim_batch` marks rows `in_flight` and only `_finish` moves them out, while `_claim_batch` selects only `status == "pending"` — so a worker crash, a deploy, a lock expiry, or the CHECK-constraint failure above strands rows in `in_flight` permanently (R38 non-terminal transient state).
What breaks in production: silently undeliverable webhooks accumulate with no retry and no alert; customers discover the gap from their own missing data, not from us.
Fix: add a `claimed_at` column, have `_claim_batch` also select rows where `status = 'in_flight' AND claimed_at < now() - <lease>`, and set `claimed_at` on claim so a reclaim is bounded rather than automatic-on-restart. Pair the sides: a row stranded past the lease must be re-claimed (allow) and a row claimed one second ago by a live worker must not be (deny) — a reclaim with no lease would satisfy the allow side and cause duplicate concurrent delivery. Red-prove separately: remove the lease predicate and confirm the live-worker test reddens; remove the `in_flight` branch and confirm the stranded-row test reddens. Emit a counter for reclaimed rows rather than reclaiming silently, since silent reclaim is how the underlying crash stays invisible. Boundary: a row whose `claimed_at` equals exactly the lease deadline is reclaimed, and two workers racing the same expired row are serialized by `SELECT ... FOR UPDATE SKIP LOCKED`.

### Major: ORM instances are used after their session has closed
File: app/webhooks/delivery.py — `_claim_batch` (return), `deliver` (`endpoint`)
What is wrong: both functions return or hold SQLAlchemy instances whose `with session_scope()` block has already exited, then read `delivery.payload`, `delivery.attempts`, `delivery.id`, `endpoint.url`, and `endpoint.signing_secret` outside it — under SQLAlchemy's default `expire_on_commit=True` those attribute reads raise `DetachedInstanceError`.
What breaks in production: the worker raises on the first claimed row and delivers nothing at all; if `session_scope` happens to set `expire_on_commit=False` the reads instead return a snapshot taken before the retry loop, so `attempts` is stale against concurrent writers.
Fix: have `_claim_batch` and `deliver` project the fields they need into a plain frozen dataclass (`id`, `endpoint_id`, `payload`, `attempts`, `url`, `signing_secret`) inside the session block and return that, so nothing crosses the transaction boundary as a live instance. Pair the sides: a test that runs `_claim_batch` against a real session and then reads every field of the result must pass (allow), and a test asserting `_finish` still writes through a fresh session must pass (deny side of the same boundary) — do not fix by widening `session_scope` to keep sessions open, which would leak connections. Red-prove separately: return the ORM row instead of the dataclass and confirm the field-read test reddens naming the detached instance; drop `signing_secret` from the projection and confirm `send_once` reddens. If this rests on a `session_scope` configuration the diff does not show, the answer that closes it is `expire_on_commit=False` *with* the session left open — state which, because the current tests cannot tell (they use `FakeDelivery`, not the model).

### Major: the worker loop dies on the first exception and can reference an unbound `batch`
File: app/webhooks/delivery.py — `run_worker`
What is wrong: `asyncio.gather` is called without `return_exceptions=True` and nothing wraps the `while True` body, so any exception from `_claim_batch`, `deliver`, or `_finish` propagates out of `run_worker` and ends the loop; on that path `if not batch` also reads a name that was never bound.
What breaks in production: one malformed payload or one transient DB error stops webhook delivery process-wide until someone notices and restarts it, and the remaining gathered tasks are left running unawaited against a client that is about to close.
Fix: pass `return_exceptions=True` to `gather`, log each returned exception against its delivery id, and wrap the loop body in a `try/except Exception` that logs and continues after a bounded sleep; initialise `batch = []` before the `try`. Pair the sides: a batch containing one raising delivery must still complete the others and leave the loop running (allow), and a raising delivery must still be recorded as failed rather than silently dropped (deny). Red-prove separately: remove `return_exceptions` and confirm the sibling-completion test reddens; remove the per-exception log assertion and confirm the recording test reddens. The catch must log at error with the delivery id — a bare `continue` would make "the loop survived" and "the work happened" the same observation.

### Major: the enqueue is outside the event transaction and its failure is swallowed
File: app/events/dispatcher.py — `dispatch`
What is wrong: `enqueue_for_event` runs after the event's `session_scope` has committed, in its own transaction, wrapped in `except Exception` that downgrades any failure to `log.warning` — so the event is durable while its deliveries are not, with no retry and no marker (R9-adjacent: the fire-and-forget side effect is not atomic with the state change it reports).
What breaks in production: a DB hiccup, or the unique-index violation above, permanently loses every webhook for that event while the API reports success, and there is nothing in the schema to reconcile against later.
Fix: insert the `webhook_deliveries` rows in the same `session_scope` as the `Event` row (an outbox), so either both commit or neither does, and let the worker be the only thing that reads them; keep the log line but re-raise after logging if the write cannot be made transactional. Pair the sides: a successful dispatch must produce both the event row and its delivery rows in one transaction (allow), and a forced enqueue failure must leave *no* event row rather than an orphan (deny) — do not fix by deleting the try/except, which would leave the same split with a louder symptom. Red-prove separately: move the enqueue back outside the scope and confirm the atomicity test reddens; make `enqueue_for_event` raise and confirm the no-orphan test reddens. Boundary: an event whose org has zero active endpoints commits with zero delivery rows and must not be treated as a failure.

### Major: retry behaviour contradicts the documented contract on two axes
File: app/webhooks/delivery.py — `deliver` / `backoff_for`, against docs/webhooks.md "Retries"
What is wrong: the doc says "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", while `deliver` retries every non-2xx status identically and `backoff_for` returns a deterministic `2**attempt` with no jitter (R29/R49 — the prose describes a control the code does not implement).
What breaks in production: a customer's permanent 400 is re-POSTed five times, and because the backoff is deterministic, every delivery queued during an endpoint outage retries in lockstep and stampedes the endpoint the moment it recovers.
Fix: treat 4xx other than 408 and 429 as terminal (`_finish(..., "failed_permanent", ...)` on the first occurrence), and add full jitter — `timedelta(seconds=random.uniform(0, BASE_DELAY_SECONDS**attempt))` using a module-level `random.Random` instance so the sampler is injectable in tests. Pair the sides: a 500 must still retry to `MAX_ATTEMPTS` (allow) and a 400 must stop at one attempt (deny) — do not fix by making everything terminal, which would drop deliveries on transient 503s. Red-prove separately: remove the 4xx branch and confirm the single-attempt test reddens; freeze the jitter sampler to its maximum and confirm the distribution assertion reddens. Boundary: 429 retries and 499 does not; the existing `test_backoff_grows_exponentially` must be rewritten to assert the interval rather than the point, or it will red on the jitter it is asking for.

### Major: the response body is stored without a size bound
File: app/webhooks/delivery.py — `deliver` / `_finish` (`response.text`)
What is wrong: the customer-controlled response body is read in full and written verbatim to `webhook_deliveries.response_body` on both the success and failure paths, with no truncation and no cap on the bytes httpx reads.
What breaks in production: an endpoint returning a multi-megabyte error page on every attempt writes tens of megabytes per delivery into the deliveries table, and a batch of 100 exhausts memory before it exhausts disk.
Fix: cap the read (`await response.aread()` against a byte budget, or stream and stop at the budget) and store `detail[:2000]` with an explicit `"…truncated"` suffix so the truncation is visible rather than silent. Pair the sides: a short body must still be stored intact and byte-identical (allow) and an over-budget body must be stored truncated with the marker (deny). Red-prove separately: remove the slice and confirm the truncation test reddens; set the budget to zero and confirm the intact-body test reddens. Boundary: a body of exactly the budget is stored without the marker; the byte at budget+1 triggers it.

### Major: `enqueue_for_event` writes a naive timestamp into an aware column
File: app/webhooks/delivery.py — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`)
What is wrong: `datetime.utcnow()` returns a naive datetime, while the column is declared `DateTime(timezone=True)`, `_claim_batch` compares it against an aware `datetime.now(timezone.utc)`, and `app/webhooks/models.py` already ships the `_now()` helper that returns the correct aware value — the new code reimplements it in the wrong flavour (R1) and is the only site in the diff that does (the dispatcher and `_finish` both use `datetime.now(timezone.utc)`).
What breaks in production: on any deployment whose DB session timezone is not UTC, the naive value is interpreted as local time, so `next_attempt_at <= now` is wrong by the offset and deliveries fire hours early or hours late.
Fix: call `m._now()` — the existing helper — and add a check that no `utcnow()` remains in `app/webhooks/`. Pair the sides: a delivery enqueued now must be claimable immediately (allow) and one enqueued with a future `next_attempt_at` must not be claimed (deny) — do not fix by dropping the `<= now` predicate. Red-prove separately: restore `utcnow()` under a non-UTC session timezone and confirm the immediate-claim test reddens; set the future row's timestamp to the past and confirm the deferral test reddens. Boundary: a row whose `next_attempt_at` equals `now` exactly is claimed, since the predicate is `<=`; two rows sharing that instant are ordered arbitrarily (see the ordering finding below).

### Major: the migration declares `TIMESTAMP` where the models declare `timezone=True`
File: migrations/0042_webhook_delivery.sql — all five datetime columns, against app/webhooks/models.py
What is wrong: every datetime column in the migration is `TIMESTAMP` (without time zone) while `WebhookEndpoint.created_at`, `WebhookDelivery.next_attempt_at`, `created_at`, and `updated_at` are all `DateTime(timezone=True)` — the schema and the mapper disagree on the type, uniformly.
What breaks in production: aware values written by `_now()` are silently stripped of their offset on the way in and read back naive, so `WebhookDelivery.to_dict()`'s `next_attempt_at.isoformat()` returns a timestamp customers cannot interpret and every comparison in the worker is against a bare local-clock value.
Fix: change all five to `TIMESTAMPTZ` in this migration (it has not shipped, so no data conversion is needed) and add a schema test asserting each column's type matches its mapper declaration. Pair the sides: a round trip of an aware datetime must return the same instant *with* its offset (allow) and a naive write must be rejected rather than coerced (deny). Red-prove separately: revert one column to `TIMESTAMP` and confirm the round-trip test reddens naming that column; remove the mapper's `timezone=True` and confirm the type-match test reddens. Run the type-match assertion over every column rather than the four in this table, so the next migration cannot reintroduce the drift silently.

### Major: nothing in the test diff exercises delivery, enqueue, claiming, locking, or the three new routes
File: tests/webhooks/test_delivery.py — whole file, against app/webhooks/delivery.py and app/api/routes/settings.py
What is wrong: the diff adds `enqueue_for_event`, `deliver`, `run_worker`, `_acquire_lock`, `_claim_batch`, `_finish`, two model classes with `to_dict`, and three HTTP routes, and the only production code any test reaches is `sign`, `verify`, `new_signing_secret`, `backoff_for`, and `send_once` (RT6; RT5 — the retry, locking, and tenancy logic is never on a test call path).
What breaks in production: every defect above — the CHECK-constraint mismatch, the unique index, the blocking sleep, the missing org filter — is invisible to a green suite, which is precisely how they reach a deploy.
Fix: add (a) an integration test for `enqueue_for_event` against a real session and the real migration, asserting the fan-out row count and the CHECK-accepted statuses; (b) a `deliver` test driving a `MockTransport` that returns 500 four times then 200, asserting the attempt count, the terminal status, and the elapsed backoff; (c) a `_acquire_lock` test with two concurrent callers; (d) route tests for all three endpoints covering owner and cross-tenant callers. Pair the sides in each: the success path asserted alongside the failure path. Red-prove each test separately against a single mutation of the code it covers — one mutation per test, executed, with the failure output naming the assertion — rather than one broken build reddening all of them. Do not satisfy this by asserting only status codes; assert the mutation each route did or did not make (RT8).

### Major: the one test that touches the signature never checks that the signature is valid
File: tests/webhooks/test_delivery.py — `test_send_once_posts_the_signed_payload`, `FakeEndpoint`, `FakeDelivery`
What is wrong: the test captures the request and asserts only that the signature header *starts with* `sha256=` and that the timestamp is digits, never recomputing the HMAC over `captured["body"]`, and the two fakes are hand-written stand-ins for `WebhookEndpoint`/`WebhookDelivery` that share none of their fields or lifecycle (RT1: the double is a constant, and no assertion compares against an independently written expected value).
What breaks in production: this test passes green against a `send_once` that signs entirely different bytes from the ones it transmits — the Critical above — which is the exact defect it appears to cover.
Fix: recompute the expected digest in the test from `captured["body"]` and the captured timestamp using a literal `hmac.new(SECRET.encode(), b"<ts>." + body, sha256).hexdigest()` written independently of `signing.sign`, and assert byte equality; bind the fixtures to the real model classes (constructed, unsaved instances) so a field rename fails the test rather than being absorbed by a bare class. Pair the sides: the correct signature must verify (allow) and a body mutated by one byte must not (deny). Red-prove separately: change `send_once` to post `json=` instead of `content=` and confirm the equality assertion reddens; change the expected-digest key and confirm the deny assertion reddens. Choose payload values away from defaults and zero values — `{"a": 1}` and `{"b": 2, "a": 1}` in the neighbouring tests cannot distinguish sorted from insertion order for a single key, which is why the ordering divergence survived.

### Minor: `_finish` dereferences a row it never checks for existence
File: app/webhooks/delivery.py — `_finish` (`row = session.get(...)`)
What is wrong: the result of `session.get` is used without a `None` check, so a delivery deleted between claim and finish — via the `ON DELETE CASCADE` from `webhook_endpoints` when a customer removes an endpoint mid-flight — raises `AttributeError` instead of being handled.
What breaks in production: deleting an endpoint while a delivery is in flight crashes the worker task with an error that names none of the relevant ids.
Fix: return early with a warning naming `delivery_id` when the row is gone.

### Minor: `SECRET_BYTES` counts characters, not bytes
File: app/webhooks/signing.py — `SECRET_BYTES = 32`
What is wrong: the constant is consumed as a character count in `range(SECRET_BYTES)`, so it names 32 characters over a 62-symbol alphabet, not 32 bytes of entropy, and `test_new_signing_secret_has_prefix_and_length` encodes the confusion as a contract.
What breaks in production: the next reader sizing a related secret from this constant gets materially less entropy than the name promises.

### Minor: the claim query orders on a column with no total order
File: app/webhooks/delivery.py — `_claim_batch` (`order_by(next_attempt_at)`), and app/api/routes/settings.py — `list_deliveries` (`order_by(created_at.desc())`)
What is wrong: both orderings are on wall-clock timestamps that tie freely — every row `enqueue_for_event` inserts for one event shares an instant — so order among ties is undefined (R57).
What breaks in production: the `LIMIT 100` cut through a tie set is arbitrary, so under a burst some deliveries are repeatedly deferred while others at the same timestamp are claimed first; the delivery list has no cursor today, so nothing is skipped, but adding one over `created_at` later would silently drop rows.
Fix: add `id` as a tie-break to both orderings.

### Minor: the indexes do not match the queries
File: migrations/0042_webhook_delivery.sql — `idx_webhook_deliveries_status`
What is wrong: `_claim_batch` filters on `status` and `next_attempt_at` together and `list_webhook_endpoints` filters on `webhook_endpoints.org_id`, but only a single-column `status` index exists and there is no index on `org_id`.
What breaks in production: the claim query degrades to a scan of the low-cardinality `status` index as the deliveries table grows, lengthening the interval during which the Redis lease is held.
Fix: replace with a partial composite `CREATE INDEX ... ON webhook_deliveries (next_attempt_at, id) WHERE status = 'pending'`, and add `CREATE INDEX ON webhook_endpoints (org_id)`.

### Minor: registered event types are never checked against anything
File: app/api/routes/settings.py — `EndpointIn.event_types`
What is wrong: the field accepts any list of strings with no membership check, so a typo (`"invoice.pais"`) is stored and simply never matches in `enqueue_for_event`'s filter.
What breaks in production: the customer sees a successfully registered endpoint that receives nothing, with no error to correlate against.

## Cross-cutting verification

- **Tenancy predicate**: present in `list_api_keys` (pre-existing), `list_webhook_endpoints`, and `create_webhook_endpoint`; absent in `list_deliveries` — reported Critical above. `enqueue_for_event` correctly filters on `org_id`.
- **Aware datetimes**: `models._now()`, `dispatcher.dispatch`, `_claim_batch`, and `_finish` all use timezone-aware values; `enqueue_for_event` is the single divergent site — reported Major above.
- **Status literals**: spelled independently in `models.STATUSES`, the migration CHECK, and four string literals in `delivery.py`; no site references a shared constant — reported Critical above.
- **Secret in serialization**: `WebhookEndpoint.to_dict` exposes `signing_secret`; `WebhookDelivery.to_dict` correctly omits `payload` and `response_body`, so the leak is confined to the one method — reported Critical above.
- **Timestamp column type**: all five new datetime columns are `TIMESTAMP` against `timezone=True` mappers — uniform drift, reported Major above.
- **Doc-vs-code claims**: four independent divergences in `docs/webhooks.md` (https-only, secret non-readback, jitter, 4xx terminal), each folded into the finding for the code it describes.

## Codebase awareness

- `app/webhooks/models.py` already defines `_now()` returning an aware UTC datetime; `enqueue_for_event` reimplements it as `datetime.utcnow()` — evidence cited in the corresponding finding.
- `app/webhooks/signing.py` already defines `serialize()` as the canonical payload encoding; `send_once` bypasses it by handing the dict to httpx as `json=`, which is the mechanism of the signature mismatch.
- `list_webhook_endpoints` and the pre-existing `list_api_keys` both demonstrate the org-scoping pattern that `list_deliveries` omits — the fix reuses that shape rather than inventing one.
- The Python standard library's `secrets` and `hmac.compare_digest` are the shared helpers the two crypto findings adopt; no project-local wrapper for either appears in the diff.
