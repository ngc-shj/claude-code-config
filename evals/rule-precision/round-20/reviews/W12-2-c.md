### Critical: webhook signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, the Mersenne
Twister global instance, which is a deterministic generator whose internal state
is recoverable from a modest run of its own outputs and is seeded once per
process.
What breaks in production: An attacker who registers a handful of endpoints on
one API worker recovers the generator state and predicts the signing secret
issued to every other tenant served by that process, letting them forge
`X-Acme-Signature` on events delivered to those tenants — and because
`create_webhook_endpoint` is the only mint point, every existing secret is
already suspect.
Fix: Replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by
`SECRET_PREFIX` (import `secrets`, delete the `random`/`string`/`_ALPHABET`
imports so the weak path cannot be reintroduced by a merge), and rename
`SECRET_BYTES` to mean what `token_urlsafe` takes — bytes of entropy, 32 — since
the current constant is a character count. Preserve the two properties the
existing tests pin (the `whsec_` prefix and a fixed, non-empty length) so the
migration is not "delete the assertion": keep
`test_new_signing_secret_has_prefix_and_length` green as the allow-side case,
adjusting only the expected length. Add a separate test that 1000 generated
secrets are all distinct AND that `signing` has no module-level `random`
attribute; red-prove each clause with its own mutation, executed: (i) revert to
`random.choice` under `random.seed(0)` — the distinctness test stays green, so
this mutation must be caught by the second clause, the `random`-attribute
assertion, which reds and names the module; (ii) return a constant string —
the distinctness assertion reds naming the duplicate count. If `secrets` cannot
be imported the module must raise at import time rather than fall back to
`random`; "no CSPRNG available" must not be spelled the same as "secret
generated". Boundary: a secret of exactly `SECRET_BYTES` entropy is accepted;
two endpoints that tie on a generated value are a hard error, not a retry.

### Critical: the deliveries endpoint has no tenancy filter (IDOR across organizations)
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on
`WebhookDelivery.endpoint_id == endpoint_id` and never joins to
`WebhookEndpoint.org_id == user.org_id`, while the two sibling handlers in the
same diff (`list_webhook_endpoints`, `list_api_keys`) both filter on
`user.org_id` — the tenancy predicate this route omits is already the file's
established pattern (R3, security-relevant).
What breaks in production: Any authenticated user can enumerate
`endpoint_id=1,2,3…` and read another organization's delivery ledger — event
ids, event types, delivery status and response codes — which also falsifies the
`docs/webhooks.md` claim that the route returns attempts "for an endpoint
belonging to your organization" (R49: the doc asserts a boundary the code does
not implement).
Fix: Join through the endpoint and scope by org, and make an unowned id
indistinguishable from a missing one — resolve the endpoint first
(`session.query(WebhookEndpoint).filter(id == endpoint_id, org_id ==
user.org_id).one_or_none()`), raise `HTTPException(404)` when it is `None`, and
only then query deliveries for that endpoint. Do not fix this by dropping the
route: the allow-side case that must still pass is an owner reading their own
endpoint's deliveries and getting the full unfiltered list. Red-prove each
clause separately, by running the tests: (i) delete the `org_id` predicate — the
cross-tenant test reds with a 200 and a non-empty body where 404 was expected;
(ii) change the not-found branch to raise 403 — the "unowned id is
indistinguishable from absent" test reds on the status code. Route an
unresolvable `user.org_id` to a 401/500 refusal, never to an unfiltered query.
Boundary: `endpoint_id` belonging to the caller's own org is included;
an id that exists but belongs to another org returns 404, identical to an id
that does not exist.

### Critical: the signature does not cover the timestamp and is computed over a re-serialized payload
File: `app/webhooks/signing.py` — `sign`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: The doc states the signature is the HMAC of
`"{timestamp}.{raw_request_body}"`, but `sign` MACs only
`json.dumps(payload, sort_keys=True)` — the timestamp is absent from the MAC
input, and the bytes signed are a re-serialization that need not equal the bytes
`httpx` puts on the wire in `send_once` (`client.post(..., json=payload)` uses
its own separator and key-order rules).
What breaks in production: Every customer who implements the documented
verification computes a different digest and rejects 100% of deliveries — a
silent total-path failure of the integration (R40) — and because the timestamp
is unauthenticated, an attacker who captures one request replays it forever by
rewriting `X-Acme-Timestamp`, so the "five minutes" window the doc calls "what
stops a captured request from being replayed" is not a control at all (R49).
Fix: Change `sign` to take the exact bytes that will be sent and MAC
`f"{timestamp}.".encode() + body`, and change `send_once` to serialize once
(`body = serialize(delivery.payload).encode()`) and post that byte string via
`content=body` with an explicit `Content-Type: application/json`, so the signed
bytes and the transmitted bytes are the same object rather than two
serializations that agree by luck. `verify` takes the same raw bytes plus the
received timestamp, and rejects when `abs(now - timestamp) > 300`. Keep the
documented header names and the `sha256=` prefix — the fix must not be "change
the doc to match the code", because the doc describes the correct scheme and the
code is the defect. Allow-side: a request signed at `now` still verifies, and a
payload with non-ASCII keys round-trips byte-identically. Red-prove each clause
with its own executed mutation: (i) drop the `f"{timestamp}."` prefix — the
"signature changes when only the timestamp changes" test reds; (ii) re-serialize
inside `send_once` instead of reusing `body` — the "captured wire bytes verify
against the sent signature" test reds on a digest mismatch; (iii) remove the
skew check — the "timestamp 301 seconds old is rejected" test reds. A missing or
non-integer `X-Acme-Timestamp` must be an explicit reject that names itself, not
a `0` default. Boundary: skew of exactly 300s is accepted, 301s rejected; a
future timestamp is bounded by the same absolute window.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` is a short-circuiting byte
comparison on a MAC, where `hmac.compare_digest` is the required primitive
(RS1), and the same module's own documentation tells customers to "compare it
against your own computation using a constant-time comparison" — the shipped
reference implementation violates the advice it publishes.
What breaks in production: An attacker with request-timing access to any caller
of `verify` recovers the expected digest byte by byte and forges a signature
without the secret, and every internal or customer implementation copied from
this reference inherits the leak.
Fix: `return hmac.compare_digest(expected, signature)`, with `signature` coerced
to `str` and rejected when it is not a string, so a non-string body value cannot
reach `compare_digest` and raise instead of denying (RS3: an off-type value
reaching a credential comparison). Allow-side that must still pass:
`test_verify_accepts_signature_produced_by_sign` stays green — the fix changes
the comparison primitive, not the accept/reject decision. Red-prove each clause
separately, executed: (i) revert to `==` — a grep-based unit assertion that
`verify`'s source contains `compare_digest` reds (timing itself is not testable
in CI, so pin the primitive, not the duration); (ii) pass `signature=None` — the
type-guard test reds with an unhandled `TypeError` before the fix and returns
`False` after. Where `compare_digest` is unavailable the module must raise at
import, never fall back to `==`. Boundary: equal-length digests differing only
in the final byte must still return `False`; a signature that ties in length but
not content is a reject.

### Critical: the `failed_permanent` status violates the migration's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending','in_flight','delivered','failed'))`; `app/webhooks/models.py` — `STATUSES`; `app/webhooks/delivery.py` — `deliver`
What is wrong: The Python side defines
`STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` and
`deliver` writes `"failed_permanent"`, but the SQL CHECK admits `"failed"` — the
same enum spelled two ways across a strict consumer boundary (R40), and
`models.STATUSES` is never referenced by any code so nothing reconciles them.
What breaks in production: The first delivery to exhaust its retries raises a
`CheckViolation` inside `_finish`, the exception escapes `deliver` (it is not an
`httpx.HTTPError`) and propagates out of `asyncio.gather` in `run_worker`,
killing the worker loop — and the row it was writing stays `in_flight` forever.
Fix: Change the SQL CHECK to the four values in `models.STATUSES` and make
`STATUSES` the single source by adding `status = Column(String(20), nullable=
False, default="pending")` validation against it (a SQLAlchemy `validates` hook
or `Enum(*STATUSES, name="webhook_delivery_status")`), so a fifth spelling fails
at the ORM rather than at the constraint. Do not fix by dropping the CHECK — the
constraint is what made the drift visible, and it must survive the change.
Allow-side: writing each of the four legal statuses still commits. Red-prove
each clause with its own executed mutation: (i) revert the CHECK to the old
list — an integration test that runs the migration and inserts
`'failed_permanent'` reds naming the constraint; (ii) write an unlisted status
such as `'dead'` through the ORM — the validation test reds naming the value. A
migration that cannot be applied must abort the test run loudly rather than let
the suite run against a stale schema. Boundary: exactly the four members of
`STATUSES` are legal; any tie between an old row's `'failed'` and the new
`'failed_permanent'` needs a data migration statement in the same file.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`
What is wrong: The unique index is on `event_id` alone, but
`enqueue_for_event` inserts one row per matching endpoint for a single
`event_id`, so any organization with two subscribed endpoints violates it on the
same `add_all`.
What breaks in production: The insert raises, the dispatcher's blanket
`except Exception` swallows it as a warning, and **all** webhooks for that event
are dropped — including the delivery to the first endpoint, because `add_all`
commits as one unit — so a customer with two endpoints receives nothing and
nothing retries.
Fix: Replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON
webhook_deliveries (endpoint_id, event_id)`, which is the pair that actually
expresses "one delivery per endpoint per event" and simultaneously gives
`enqueue_for_event` an idempotency key it can use with `ON CONFLICT DO NOTHING`
for the at-least-once retry the docs promise. Do not fix by deleting the unique
index — the uniqueness is what prevents duplicate deliveries on a re-dispatch,
and that property must be preserved. Allow-side: one event fanning out to three
endpoints inserts three rows and commits. Red-prove each clause separately, by
execution: (i) restore the single-column index — the "one event, two endpoints"
test reds with an integrity error naming the index; (ii) drop the index
entirely — the "re-enqueueing the same event does not duplicate rows" test reds
with a row count of 4 instead of 2. Boundary: the same `event_id` under two
different `endpoint_id`s is legal; the same pair twice is the tie, resolved by
`DO NOTHING` in favour of the existing row.

### Critical: outbound URL validation permits non-HTTPS schemes and internal hosts, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker`
What is wrong: `parsed.scheme.startswith("http")` accepts `http://` and any
scheme merely prefixed with `http` (`urlparse("httpfoo://x").scheme` is
`"httpfoo"`), there is no check on the resolved host, and the delivery client is
constructed with `follow_redirects=True`, while `docs/webhooks.md` asserts "Only
`https://` URLs are accepted".
What breaks in production: A tenant registers
`http://169.254.169.254/latest/meta-data/` — or a compliant `https://` URL that
302-redirects there — and the worker fetches cloud metadata or an internal
service with the response body persisted verbatim into
`webhook_deliveries.response_body`, which the tenant then reads back; over plain
`http` the signed payload and signature also cross the network in the clear.
Fix: Validate at the schema level (RS3), not in the handler body: give
`EndpointIn.url` a `pydantic.HttpUrl`-typed field with a validator that requires
`scheme == "https"` exactly (equality, not `startswith`), rejects userinfo, and
resolves the host, rejecting any address in a private, loopback, link-local, or
unique-local range via `ipaddress.ip_address(...).is_private or .is_loopback or
.is_link_local or .is_reserved`. Set `follow_redirects=False` in the
`httpx.AsyncClient` and treat a 3xx as a delivery failure, and re-check the
resolved address at connect time (an allowed hostname can be re-pointed between
registration and delivery — the check-then-use interval is attacker-schedulable
here). Do not fix by only tightening the string check: the redirect and the
re-resolution are separate holes and the string check alone leaves both open.
Allow-side: `https://hooks.example.com/acme` on a public address still registers
and still delivers. Red-prove each clause with its own executed mutation:
(i) revert to `startswith("http")` — the `httpfoo://` and `http://` rejection
tests red with a 201; (ii) re-enable `follow_redirects=True` — the "302 to a
private address is not followed" test reds on the recorded request count;
(iii) remove the private-range check — the `https://127.0.0.1/` test reds with a
201. A DNS resolution that fails or times out must reject the registration with
a named error, never fall through to "not provably private, therefore allowed".
Boundary: a public address is allowed, an address exactly on a private-range
edge (`10.0.0.0`, `172.16.0.0`, `192.168.0.0`) is rejected; a hostname resolving
to both a public and a private address is rejected.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is an `async def` scheduled through
`asyncio.gather` in `run_worker`, and `time.sleep` blocks the event loop thread
rather than yielding, so the retry backoff freezes every other coroutine on the
loop.
What breaks in production: One failing endpoint stalls the entire delivery
worker for up to 2+4+8+16 = 30 seconds of sleep plus four 30-second request
timeouts, and because a `gather` over a 100-row batch shares the loop, a handful
of slow endpoints in a batch serialize the whole queue and the 60-second Redis
lock expires mid-batch while the worker is still inside `deliver`.
Fix: Replace with `await asyncio.sleep(delay)`. Preserve the retry pacing the
change is not allowed to lose: the delay values must remain those
`test_backoff_grows_exponentially` pins. Allow-side: a delivery that succeeds on
the first attempt must still complete without any sleep at all. Red-prove each
clause separately, by execution: (i) revert to `time.sleep` — a test that runs
`deliver` against a always-500 transport concurrently with a coroutine
incrementing a counter reds when the counter fails to advance during the
backoff; (ii) delete the sleep entirely — the "second attempt does not occur
before `BASE_DELAY_SECONDS`" test reds on elapsed monotonic time. Note that this
fix alone is insufficient: the in-process retry loop should be replaced by
persisting `next_attempt_at = now + backoff_for(attempt)` and returning (see the
Major finding on the dead retry schedule), which removes the sleep from the hot
path entirely. Boundary: `attempt == MAX_ATTEMPTS` sleeps zero times and
finalizes; `attempt == MAX_ATTEMPTS - 1` sleeps once more.

### Critical: ORM rows are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (`endpoint` escapes the `with`, then `delivery.payload` / `.attempts` / `.id` are read)
What is wrong: Both functions return or read SQLAlchemy instances after the
`session_scope()` block has exited and committed, and every other call site in
this diff obeys the opposite convention — `create_webhook_endpoint` calls
`session.flush()` and `endpoint.to_dict()` *inside* the block, and
`list_webhook_endpoints` materializes `to_dict()` inside it too — so the
codebase's own established shared path is "touch attributes before the scope
closes", which these two functions reimplement incorrectly (R1).
What breaks in production: With SQLAlchemy's default `expire_on_commit=True`
every attribute is expired at commit, so the first read of `delivery.payload` in
`send_once` raises `DetachedInstanceError`; that is not an `httpx.HTTPError`, so
`deliver`'s except clause does not catch it, it propagates through
`asyncio.gather`, and `run_worker` dies on its first batch — no webhook is ever
delivered.
Fix: Have `_claim_batch` return plain data, not ORM identities: inside the
scope, build a list of frozen dataclasses (or dicts) carrying
`id, endpoint_id, attempts, payload, event_type` plus the endpoint's `url` and
`signing_secret` loaded by an explicit join in the same query, and have
`deliver`/`send_once` take that value object. This also removes the N+1
`session.get(WebhookEndpoint, ...)` per delivery. Preserve the claim
semantics the current code has: the `status = "in_flight"` write must still
commit in the same transaction as the read. Allow-side: a claimed batch of two
rows still delivers both with the correct per-endpoint secret. Red-prove each
clause with its own executed mutation, run against a real (in-memory or
containerized) database rather than a mock — a mocked session cannot exhibit
expiry at all, which is exactly why the defect is invisible to the current
suite: (i) return the ORM rows again — the "claim then deliver" integration test
reds with `DetachedInstanceError`; (ii) drop the endpoint join and reintroduce
the per-row `session.get` — a query-count assertion reds at 1+N instead of 1.
Route a claimed row whose endpoint has been deleted to an explicit
`failed_permanent` with a named detail, not to an `AttributeError`. Boundary: a
batch of exactly `BATCH_SIZE` rows is claimed in one transaction; two workers
tying on the same row is settled by `FOR UPDATE SKIP LOCKED` (see the lock
finding), not by the Redis key.

### Critical: the signing secret is readable back from the endpoint list route
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`; `docs/webhooks.md`
What is wrong: `to_dict` includes `"signing_secret": self.signing_secret` and
`list_webhook_endpoints` returns it for every endpoint on an unauthenticated-by-
scope `GET`, while the documentation states "the response is the only place the
signing secret appears — it cannot be read back afterwards" (RS4: a live
credential in a routine response; R49: a doc claiming a containment property the
code does not have).
What breaks in production: The secret is returned on every settings page load
and therefore lands in access logs, browser caches, HAR files, proxy logs and
error trackers, so a single log export compromises the ability to forge signed
events to every endpoint in the organization — and customers who relied on the
documented "cannot be read back" property will not know rotation is required.
Fix: Remove `signing_secret` from `to_dict`, and have
`create_webhook_endpoint` return the secret explicitly and only there —
`{**endpoint.to_dict(), "signing_secret": secret}` using the value returned by
`new_signing_secret()` before it is persisted. Do not fix by removing the
creation response's secret too: the one-time reveal is what makes the feature
usable, and that is the behaviour the fix must preserve. Allow-side: the 201
response from `POST /v1/settings/webhook-endpoints` still contains a
`whsec_`-prefixed secret. Red-prove each clause separately, by execution:
(i) re-add the key to `to_dict` — the "GET response contains no key matching
`signing_secret` and no value starting with `whsec_`" test reds naming the
field; (ii) drop it from the create handler — the "201 body carries the secret"
test reds. Because the field has already been exposed on any deployed build,
treat existing secrets as compromised and ship a rotation endpoint in the same
change rather than only closing the read path. Boundary: exactly one response —
the 201 — carries the secret; every other representation of the same row,
including the deliveries route and any future update route, must not.

### Major: the persisted retry schedule is dead code and `in_flight` is a non-terminal state
File: `app/webhooks/delivery.py` — `deliver`, `_claim_batch`, `_finish`
What is wrong: `deliver` loops all five attempts in-process and only ever calls
`_finish` at a terminal outcome, so `attempts` and `next_attempt_at` are never
advanced between attempts, and `_claim_batch` selects only
`status == "pending"` — nothing anywhere resets a row out of `"in_flight"`
(R38 clause 1: an async state entered with no failure-exit and no bounded
timeout).
What breaks in production: A worker restart, a deploy, an OOM kill, or the
`CheckViolation` described above during a 30-second retry window strands every
in-flight row permanently — they are invisible to the claim query, never
retried, and never reported as failed — so deliveries silently vanish and the
`next_attempt_at`/`backoff_for` machinery that the schema and tests describe
never runs at all.
Fix: Make each attempt a single pass: on a retryable failure, persist
`attempts = attempt`, `status = "pending"`,
`next_attempt_at = now + backoff_for(attempt)` and return, letting the next poll
re-claim the row; keep `deliver`'s terminal `delivered`/`failed_permanent`
writes unchanged. Add a reaper in `run_worker` that returns rows stuck in
`in_flight` past a bounded lease (`updated_at < now - lease`) to `pending` with
`attempts` unchanged, and record the claim time in `updated_at` at claim. Do not
fix by widening the claim query to include `in_flight` — that reintroduces
concurrent double-delivery the status was there to prevent. Allow-side: a
delivery that succeeds on attempt 3 must still reach `delivered` with
`attempts == 3`, and a row currently being worked by a live worker must NOT be
reclaimed. Red-prove each clause with its own executed mutation: (i) remove the
`next_attempt_at` write — the "second attempt is not claimed before the backoff
elapses" test reds; (ii) remove the reaper — the "row left `in_flight` past the
lease returns to `pending`" test reds with the status unchanged; (iii) remove
the `updated_at` write at claim — the reaper test reds by reclaiming a row that
is still in its lease. A row whose `updated_at` is NULL must be treated as
expired and reaped with a warning that names the id, not skipped silently.
Boundary: a row whose `updated_at` is exactly `now - lease` is reaped; `attempts
== MAX_ATTEMPTS` is terminal and is never re-queued by the reaper.

### Major: the dispatch lock is not atomic in either direction
File: `app/webhooks/delivery.py` — `_acquire_lock`
What is wrong: The get-then-set sequence has a window in which two workers both
observe an empty key and both set it, and the separate `set` then `expire` calls
mean a crash between them leaves a key with no TTL.
What breaks in production: Two workers claim overlapping batches and the same
event is POSTed twice to the customer, and a single ill-timed crash leaves
`webhooks:dispatch:lock` set forever with no expiry, so `_acquire_lock` returns
`False` on every future poll and webhook delivery stops entirely across the
fleet until an operator manually deletes the key — a persisted fail-closed wedge
with no reset path (R38).
Fix: Replace the three calls with one atomic
`await redis_client.set(LOCK_KEY, worker_id, nx=True, ex=60)` and treat a falsy
return as "not acquired"; release only if the stored value is still this
worker's id (a Lua compare-and-delete), so a worker that overran the TTL cannot
delete a successor's lock. Independently, make correctness not depend on the
lock at all by adding `.with_for_update(skip_locked=True)` to `_claim_batch` —
the lock then becomes a throttle rather than the sole guard against double
delivery. Do not fix by lengthening the TTL: a longer lease widens the outage
window without closing the race. Allow-side: a single worker still acquires on
every poll and still releases at the end of the batch. Red-prove each clause
separately, by execution: (i) revert to get-then-set — a test driving two
concurrent `_acquire_lock` calls against a real Redis (or fakeredis) reds with
two `True` returns; (ii) drop the `ex=60` — the "lock has a positive TTL after
acquisition" test reds with `-1`; (iii) drop the compare-and-delete — the
"worker A cannot release worker B's lock" test reds. A Redis connection error
must propagate as a named refusal that stops the poll, never be caught into
"lock not held, proceed". Boundary: a lock whose TTL is exactly 0 is expired and
acquirable; two workers tying on acquisition are resolved by `SET NX`, and if
both somehow proceed, `SKIP LOCKED` resolves the row-level tie.

### Major: no rate limiting on any of the three new routes
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: All three new endpoints are added with no limiter (RS2), and
`create_webhook_endpoint` is a write that mints a credential and inserts a row
on every call.
What breaks in production: An authenticated tenant scripts endpoint creation and
fills `webhook_endpoints` unbounded, which also multiplies fan-out in
`enqueue_for_event` — N endpoints means N delivery rows and N outbound requests
per event, turning a cheap write into an amplified outbound load the worker must
carry.
Fix: Apply the project's existing limiter dependency to all three routes (the
diff does not show one; if `app/api/deps.py` exposes a limiter, reuse it rather
than writing a new one — check before adding, per R1), and independently cap
endpoints per organization with a count check inside the same transaction as the
insert plus a `UNIQUE (org_id, url)` constraint in the migration so the cap
cannot be raced. Do not fix with the cap alone: the cap bounds the steady state,
the limiter bounds the request rate, and each addresses a failure the other does
not. Allow-side: a tenant at `cap - 1` endpoints can still create one more, and
normal settings-page polling of the list routes is unaffected. Red-prove each
clause separately, by execution: (i) remove the limiter dependency — the "N+1
requests within the window returns 429" test reds with a 201; (ii) remove the
count check — the "creation at the cap returns 409" test reds. If the limiter
backend is unreachable the request must fail closed with a 503 that names the
limiter, not be admitted unlimited. Boundary: the request at exactly the limit
succeeds and the next one is rejected; two concurrent creations tying at
`cap - 1` are resolved by the unique constraint, one committing and one 409ing.

### Major: `limit` has a lower bound but no upper bound
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: The query parameter constrains only the floor, so
