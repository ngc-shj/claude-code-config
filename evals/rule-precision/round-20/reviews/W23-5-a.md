### Critical: the signature covers neither the timestamp nor the bytes actually transmitted
File: `app/webhooks/signing.py` — `sign()`; `app/webhooks/delivery.py` — `send_once()`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, which serializes independently (no `sort_keys`, different separators), and the returned `timestamp` is never fed into the MAC — so the signed bytes are not the wire bytes and the documented input `"{timestamp}.{raw_request_body}"` is a third, different string.
What breaks in production: every receiver that follows `docs/webhooks.md` computes a signature that can never match, so 100% of outbound webhooks are rejected by correctly-implemented customers, and because the timestamp is outside the MAC an attacker who captures one request can rewrite `X-Acme-Timestamp` freely, which removes the replay defence the docs tell customers to rely on.
Fix: sign the exact bytes that are sent, over the documented pre-image. In `signing.py` add `def canonical_body(payload) -> bytes: return serialize(payload).encode()` and change `sign(secret, payload)` to `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + canonical_body(payload), hashlib.sha256)`; in `send_once` replace `json=delivery.payload` with `content=canonical_body(delivery.payload)` so the transmitted body is byte-identical to the signed body (the `Content-Type: application/json` header stays). Reuse the existing `serialize()` helper rather than adding a second serializer — it is already in the diff and is what makes the two sides agree.
- Allow side to pin: a receiver that computes `HMAC(secret, timestamp + "." + raw_body)` over the bytes captured by `httpx.MockTransport` MUST verify true; assert `signing.verify_raw(SECRET, ts, captured["body"], captured["headers"][SIGNATURE_HEADER])` is `True` in `test_send_once_posts_the_signed_payload`, and assert `captured["body"] == signing.serialize(FakeDelivery.payload).encode()` byte-for-byte.
- Red-prove, one mutation per clause, each executed: (a) drop the `f"{timestamp}."` prefix from the MAC input → the raw-body verification assertion must red; (b) revert `content=` back to `json=` → the byte-equality assertion must red; (c) change `sort_keys=True` to `sort_keys=False` in `serialize` with a two-key payload whose insertion order is not sorted → the byte-equality assertion must red. Three mutations, three distinct failing assertions.
- Cannot-run outcome: if `serialize()` raises (non-JSON-serializable payload), `send_once` must not fall back to any other encoding — let it raise, and have `deliver` record `failed_permanent` with the exception text rather than sending an unsigned or differently-encoded body. "Could not sign" must not be spelled the same as "signed".
- Preserve: `sign()` must keep returning the `(timestamp, "sha256=<hex>")` pair and the two header names — customers already parse that shape, and `test_sign_returns_timestamp_and_prefixed_digest` must stay green.
- Boundary and tie: the timestamp is unix seconds; a receiver's five-minute window is `now - ts <= 300` inclusive, so a request signed at exactly 300s ago is still accepted, and two requests sharing one second produce different signatures only if their payloads differ — deduplication is `event_id`, never the signature.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice`, which draws from the Mersenne Twister — a predictable generator whose internal state is recoverable from observed output — instead of `secrets`/`os.urandom`, and `SECRET_BYTES = 32` in fact counts alphabet characters, not bytes.
What breaks in production: an attacker who learns or reconstructs the process RNG state (or simply observes enough generated values from any other `random` consumer in the same process) can predict other tenants' signing secrets and forge webhooks that every customer's verification accepts as genuine.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`; delete the `random`, `string` and `_ALPHABET` symbols so the weak path cannot be reintroduced), and rename `SECRET_BYTES` to keep meaning what it says — it is now genuinely a byte count fed to a CSPRNG.
- Allow side to pin: a freshly generated secret must still be accepted end-to-end — keep a test that generates a secret, signs with it, and verifies, and assert `secret.startswith(SECRET_PREFIX)` still holds.
- Red-prove, one mutation per clause, each executed: (a) revert to `random.choice` seeded with `random.seed(0)` in the test process → an assertion that two secrets generated after identical `random.seed(0)` calls differ must red under the mutation and pass under the fix; (b) set `SECRET_BYTES = 4` → an assertion that the secret carries at least 128 bits of entropy (`len(secret) - len(SECRET_PREFIX) >= 22` for token_urlsafe) must red.
- Cannot-run outcome: `secrets` failing to source entropy raises; do not catch it and do not fall back to `random` — a `create_webhook_endpoint` call that cannot obtain a secret must return 500 rather than persist a weak one.
- Preserve: the `whsec_` prefix and the "secret is a printable single-token string" property that customers copy into their config; do not fix this by shortening or restructuring the secret.
- Boundary and tie: the minimum accepted entropy is 128 bits inclusive; two endpoints in the same org must never share a secret, so the test asserts distinctness across 100 generations rather than across two.

### Critical: signature comparison in `verify()` is not constant-time (RS1)
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: the reference verification helper compares two MACs with `==`, whose early-exit byte comparison leaks the position of the first differing byte through timing, instead of `hmac.compare_digest`.
What breaks in production: any endpoint that adopts this helper to authenticate inbound requests lets an attacker recover a valid signature byte by byte from response-latency differences, forging authenticated webhook deliveries without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, and — because `sign()` will after finding #1 take the timestamp — change the signature to `verify(secret, timestamp, body, signature)` so the caller's own timestamp is the one checked rather than a freshly minted one; reject when `signature` is not `str` before comparing.
- Allow side to pin: a signature produced by the real `sign()` with the matching secret and the matching timestamp must still return `True` — keep `test_verify_accepts_signature_produced_by_sign` green, and add a case where the timestamp is 299 seconds old and still verifies.
- Red-prove, one mutation per clause, each executed: (a) change `compare_digest` back to `==` → a test asserting `signing.verify` is called through `hmac.compare_digest` (patch `hmac.compare_digest` with a counting wrapper and assert it was invoked) must red; (b) make `verify` recompute its own timestamp instead of using the argument → a test that verifies a signature produced with timestamp `T` while `time.time()` is stubbed to `T + 60` must red.
- Cannot-run outcome: a `None`, non-`str`, or wrong-length `signature` must return `False` explicitly, not raise a `TypeError` that a caller's broad `except` could turn into an accept.
- Preserve: `verify` must keep returning a plain `bool` and must not start raising on mismatch — callers branch on the return value.
- Boundary and tie: `compare_digest` on strings of unequal length returns `False` without leaking the length comparison; the timestamp window boundary belongs to the caller, and a signature whose timestamp equals exactly `now - 300` is accepted.

### Critical: `list_deliveries` has no tenancy filter (cross-organization read)
File: `app/api/routes/settings.py` — `list_deliveries()`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id` taken straight from the path, with no join back to `WebhookEndpoint.org_id == user.org_id`, while every sibling handler in the same file (`get_profile`, `list_api_keys`, `create_webhook_endpoint`, `list_webhook_endpoints`) does scope by `user.org_id` — R3 incomplete pattern propagation, security-relevant.
What breaks in production: any authenticated user can enumerate integer endpoint IDs and read other organizations' delivery history — event types, timestamps, delivery status and response codes — which is a cross-tenant data breach reachable with a single incrementing path parameter.
Fix: join and scope, and make a foreign endpoint indistinguishable from a missing one: query `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and raise `HTTPException(404)` when no endpoint with that id exists in the caller's org so the endpoint's existence is not disclosed. Authorize in this handler, not only wherever the endpoint was created.
- Allow side to pin: the owning organization must still receive its own deliveries — a test in which `user.org_id` matches the endpoint's org asserts the full expected list is returned, not merely a 200.
- Red-prove, one mutation per clause, each executed: (a) delete the `org_id` predicate → the cross-tenant test asserting a foreign caller receives `404` and an empty result must red; (b) change the `404` to a `403` → the existence-non-disclosure test asserting the same status for "endpoint does not exist at all" and "endpoint belongs to another org" must red.
- Cannot-run outcome: if `user.org_id` is `None` or absent, deny with `403` rather than letting the predicate degrade to a match-anything comparison; an unresolvable subject must be a refusal that names itself in the log, never an unscoped query.
- Preserve: the ordering by `created_at desc` and the `limit` behaviour that makes the endpoint useful for debugging — do not fix this by removing the route.
- Boundary and tie: `limit` is inclusive of its bound; deliveries sharing one `created_at` need a deterministic tie-break, so order by `(created_at DESC, id DESC)` or a page boundary cut through equal timestamps will silently drop or repeat rows.

### Critical: the signing secret is returned by every endpoint-list call
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`; `app/api/routes/settings.py` — `list_webhook_endpoints()`
What is wrong: `to_dict()` includes `"signing_secret"`, and `list_webhook_endpoints` calls it for every endpoint, so the secret is readable on demand — directly contradicting `docs/webhooks.md`, which states it "is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation, where the claimed control is what customers' rotation posture rests on).
What breaks in production: any principal with read access to organization settings — including lower-privileged members who could never create an endpoint — can lift every signing secret and forge webhooks to customers indefinitely, and the documented "write-once" property that customers were told to rely on does not exist.
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and return it only from `create_webhook_endpoint`, by building the 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at that one call site; add an explicit `POST /webhook-endpoints/{id}/rotate-secret` as the sanctioned recovery path, since a secret that can no longer be read must be replaceable.
- Allow side to pin: the creation response must still contain a usable secret — assert the 201 body's `signing_secret` starts with `whsec_` and that signing with it verifies; the list response must still contain `id`, `url`, `event_types` and `active`.
- Red-prove, one mutation per clause, each executed: (a) re-add `"signing_secret"` to `to_dict()` → a test asserting `"signing_secret" not in list_response[0]` must red; (b) delete the explicit merge at the create call site → the test asserting the 201 body carries a verifying secret must red.
- Cannot-run outcome: if the rotate path cannot generate a secret it must return 500 and leave the existing secret intact — a rotation that half-completes must not blank the column, or every delivery for that endpoint starts signing with an empty key.
- Preserve: the list endpoint must keep identifying endpoints well enough to manage them (id, url, event types, active flag) — this is not fixed by dropping the list route or reducing it to bare ids.
- Boundary and tie: during rotation both the old and the new secret must verify for a defined overlap window (state it explicitly, e.g. 24h inclusive) or in-flight deliveries signed with the old secret are rejected; if two rotations race, last write wins and the loser's secret must be invalidated, not silently orphaned.

### Critical: no egress restriction on the customer-supplied webhook URL (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`; `app/webhooks/delivery.py` — `run_worker()` (`follow_redirects=True`)
What is wrong: validation is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts plaintext `http://`, accepts any scheme merely beginning with those four characters (`httpx://evil`), and imposes no restriction on the host, so `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/` are accepted — and the worker then follows redirects, so even a public URL can bounce the request to an internal address (RS3: a boundary check that is present but decides nothing about the value's sink).
What breaks in production: the delivery worker becomes a confused deputy that will POST attacker-chosen JSON to cloud metadata services and internal-only HTTP endpoints from inside the trust boundary, and — because plaintext is accepted while the docs promise "Only `https://` URLs are accepted" — customer payloads are transmitted unencrypted.
Fix: validate as an allowlist, not a prefix. In `EndpointIn`, type `url` as pydantic `AnyHttpUrl` and add a validator that requires `scheme == "https"` exactly (equality, not `startswith`), resolves the host, and rejects when any resolved address is loopback, link-local, private, or otherwise non-global (`ipaddress.ip_address(...).is_global is False`); set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a non-retryable `failed_permanent`; re-check the resolved address at connection time via a pinned-address transport so a DNS record cannot change between registration and delivery.
- Allow side to pin: a legitimate public HTTPS endpoint must still register and still receive deliveries — assert `https://hooks.example.com/acme` returns 201 and that `send_once` against it succeeds; the existing `FakeEndpoint.url` case must stay green.
- Red-prove, one mutation per clause, each executed: (a) relax `scheme == "https"` back to `startswith("http")` → a test asserting `http://hooks.example.com` returns 422 must red; (b) delete the non-global-address check → a test asserting `https://169.254.169.254/` returns 422 must red; (c) restore `follow_redirects=True` → a test whose mock transport answers 302 to `http://localhost/` and asserts the delivery is marked `failed_permanent` with no second request must red.
- Cannot-run outcome: when DNS resolution fails or times out, reject the registration with 422 and mark the delivery `failed_permanent` with an explicit "host unresolvable" reason — an unresolvable host must never be treated as "no private address found, therefore allowed".
- Preserve: customers must keep being able to register endpoints behind CDNs and load balancers with multiple A records — the check evaluates every resolved address, and does not fix the problem by hardcoding a single-host allowlist.
- Boundary and tie: `is_global` puts `100.64.0.0/10` (CGNAT) and IPv6 ULAs on the deny side, and IPv4-mapped IPv6 (`::ffff:127.0.0.1`) must be normalised before the check; when a host resolves to both a global and a private address, deny — the tie resolves to the safe side.

### Critical: the migration's status CHECK constraint omits the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/models.py` — `STATUSES`
What is wrong: the constraint permits `'failed'` while `models.STATUSES` and `delivery._finish(..., "failed_permanent", ...)` write `'failed_permanent'` — the class of legal statuses is duplicated in two places and the copies disagree (R42: the member set was transcribed, not derived from the defining primitive).
What breaks in production: every delivery that exhausts `MAX_ATTEMPTS` raises a check-constraint violation inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and the exception propagates out of `asyncio.gather` and kills `run_worker` — so the first permanently-failing endpoint stops all webhook delivery for every tenant.

Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and add a test that asserts the SQL literal set equals `set(app.webhooks.models.STATUSES)` by parsing the migration file, so the two can no longer drift; since `0042` may already be applied, ship `0043` with `ALTER TABLE webhook_deliveries DROP CONSTRAINT ...; ADD CONSTRAINT ... CHECK (...)` rather than editing an applied migration in place.
- Allow side to pin: all four legitimate statuses must still be writable — a test inserts one row per member of `STATUSES` against the real schema and asserts each commits.
- Red-prove, one mutation per clause, each executed: (a) revert the constraint to `'failed'` → the insert-every-member test must red on `failed_permanent`; (b) add a fifth value to `STATUSES` without touching the migration → the set-equality test must red.
- Cannot-run outcome: if the migration file cannot be parsed or the constraint clause is not found, the drift test must FAIL, not skip — "found no statuses to compare" must be spelled differently from "the statuses matched".
- Preserve: the constraint itself must stay — this is not fixed by dropping the CHECK so that any string is accepted, which would remove the only thing keeping the state machine's vocabulary closed.
- Boundary and tie: the constraint is exact-match and case-sensitive, so `'FAILED_PERMANENT'` is rejected; a row already stored as `'failed'` by a pre-fix deploy must be migrated to `'failed_permanent'` in the same `0043` before the constraint is re-added, or the `ADD CONSTRAINT` itself fails.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` alone, but `enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint for a single `event_id`, so any organization with two subscribed endpoints violates the index.
What breaks in production: `session.add_all(rows)` fails with an integrity error for every org that has more than one endpoint, the dispatcher swallows it at `log.warning`, and those customers silently receive no webhooks at all — while `docs/webhooks.md` tells them delivery is at-least-once and to deduplicate on `event_id`, which the index has quietly redefined as globally at-most-once.
Fix: make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — that is the real idempotency key, one delivery per endpoint per event — and correct `docs/webhooks.md` to say deduplicate on `(endpoint_id, event_id)`; ship it as `0043` if `0042` is applied.
- Allow side to pin: an org with two subscribed endpoints must produce two delivery rows for one event — assert `enqueue_for_event` returns `2` and that both rows persist; a repeat call for the same event must still insert nothing new.
- Red-prove, one mutation per clause, each executed: (a) revert the index to `(event_id)` → the two-endpoint fan-out test must red with an integrity error; (b) drop the index entirely → the replay test asserting a second `enqueue_for_event` for the same event does not create duplicate rows must red.
- Cannot-run outcome: `enqueue_for_event` must surface an integrity error to its caller rather than returning a count; the dispatcher's current `except Exception: log.warning` is precisely how this defect stayed invisible, so route it to an alert and a retry queue (see finding #17).
- Preserve: idempotency on redelivery must survive — the fix must not be "drop the unique index", which would let a retried dispatch duplicate every delivery.
- Boundary and tie: the pair is the tie-break — two endpoints of the same org share `event_id` and differ on `endpoint_id`; an endpoint deleted and recreated gets a new `endpoint_id`, so it legitimately receives its own row for an event already delivered to the old one.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver()`, line `time.sleep(delay)`
What is wrong: `deliver` is `async def` but backs off with the blocking `time.sleep` instead of `await asyncio.sleep`, and it is invoked through `asyncio.gather` over a batch of up to `BATCH_SIZE = 100`.
What breaks in production: one failing endpoint blocks the entire event loop for 2+4+8+16 = 30 seconds — serialized across a batch, up to 50 minutes — during which no other delivery, no HTTP response, and no timer in that process runs, and the 60-second Redis lock expires mid-batch so a second worker starts claiming and re-sending the same rows.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)`, and stop retrying in-process at all: on a retryable failure, persist `attempts += 1`, `status = "pending"`, `next_attempt_at = now + backoff_for(attempt)` and return, letting `_claim_batch` pick the row up on a later poll — that is what the `next_attempt_at` column exists for and it removes the interaction with the lock TTL entirely.
- Allow side to pin: a delivery that succeeds on the first attempt must still complete without any sleep — assert `_finish(..., "delivered", 1, 200, ...)` and that the coroutine returns in well under the backoff interval; a delivery that succeeds on attempt 3 must still end `delivered` with `attempts == 3`.
- Red-prove, one mutation per clause, each executed: (a) restore `time.sleep` → a test that gathers two deliveries against a mock transport and asserts the second one's request is observed before the first one's backoff elapses must red; (b) remove the `next_attempt_at` write on the retry path → a test asserting a failed delivery is re-claimed by `_claim_batch` only after its backoff has passed must red.
- Cannot-run outcome: if persisting the retry state fails, the row must not be left `in_flight` — catch, log at error with the delivery id, and reset to `pending` with the original `next_attempt_at`, so "could not schedule the retry" is never spelled as "delivery in progress".
- Preserve: the retry behaviour itself and the `MAX_ATTEMPTS = 5` ceiling that `test_max_attempts_matches_documented_limit` pins — this is not fixed by deleting the backoff.
- Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal boundary, so attempt 5 is the last one sent and no sixth is scheduled; two rows whose `next_attempt_at` is identical are ordered by `(next_attempt_at, id)` so a batch cut through equal timestamps cannot starve one of them.

### Critical: the test suite stays green under a completely broken signer
File: `tests/webhooks/test_delivery.py` — `test_sign_returns_timestamp_and_prefixed_digest`, `test_verify_accepts_signature_produced_by_sign`, `test_send_once_posts_the_signed_payload`; `FakeEndpoint` / `FakeDelivery`
What is wrong: every signing assertion is either a shape check (`startswith("sha256=")`, `isdigit()`, `len == 71`) or a round-trip of the subject against itself (`verify(sign(x))`), so no assertion ever compares against an independently computed HMAC — replace `serialize(payload)` with `""` and all of them still pass — and the hand-written `FakeEndpoint`/`FakeDelivery` doubles stand in for SQLAlchemy models without their session lifetime, so `send_once` is exercised against objects the production path never has (RT1 clauses (c) and (d); RT5: the production primitive is present but fed a shape reality never produces).
What breaks in production: this is the mechanism by which findings #1 and #10 shipped — the suite reports the signing control as covered while being incapable of failing for any defect in what is actually signed, and it will keep reporting green after the fix regresses.
Fix: add an oracle test that compares against a value computed independently of `sign()` — `expected = hmac.new(SECRET.encode(), f"{ts}.".encode() + json.dumps(payload, sort_keys=True).encode(), hashlib.sha256).hexdigest()` written literally in the test, with `time.time` monkeypatched to a fixed `ts` — and assert `signature == "sha256=" + expected`; bind `FakeEndpoint`/`FakeDelivery` to the real `WebhookEndpoint`/`WebhookDelivery` classes (construct real model instances, unsaved) so a field or lifetime the models require cannot be omitted by a double, and assert the transmitted body equals the signed bytes exactly rather than by `json.loads(...)["type"]`.
- Allow side to pin: the correct implementation must still pass — the new oracle test is green against the fixed `sign()`, and `test_verify_rejects_a_signature_made_with_another_secret` stays green.
- Red-prove, one mutation per clause, each executed: (a) make `serialize` return `""` → the oracle assertion must red (today nothing reds); (b) drop the timestamp from the MAC pre-image → the oracle assertion must red with a different digest; (c) replace the real model instances with the old hand-written doubles → the type-bound fixture must fail to construct.
- Cannot-run outcome: if `time.time` cannot be patched or the model classes cannot be imported, the test must error, not skip — a skipped signing test must not be reported the same as a passing one.
- Preserve: the existing `httpx.MockTransport` structure and the connection-error propagation test, which are correct and are what let the wire bytes be captured — do not fix this by deleting the shape assertions, only by adding the oracle beside them.
- Boundary and tie: `len(signature) == len("sha256=") + 64` is exact for SHA-256; when two payloads differ only in key order the canonical serializer must produce one identical signature, which is the tie the oracle test must include as a case.

### Major: ORM rows are used after their session scope has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` (`return rows`), `deliver()` (`endpoint` read outside the `with`)
What is wrong: `_claim_batch` returns model instances after `with session_scope()` exits and `deliver` reads `endpoint.signing_secret` / `endpoint.url` and `delivery.payload` / `.attempts` / `.id` outside any session, which is only safe if `session_scope` neither commits-with-expiry nor closes — and it must commit, since `_claim_batch`'s `row.status = "in_flight"` and `_finish`'s writes have no explicit `commit()`.
What breaks in production: with SQLAlchemy's default `expire_on_commit=True` every one of those attribute reads triggers a refresh on a closed session and raises `DetachedInstanceError`, so the worker fails on the first delivery of the first batch and no webhook is ever sent.
Fix: stop passing ORM instances across the boundary — have `_claim_batch` return plain data (`list[tuple[int, int, dict, int]]` of `(delivery_id, endpoint_id, payload, attempts)`, or a frozen dataclass) read inside the session, and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside a `with session_scope()` block before using them. This also removes the need to guess `session_scope`'s expiry configuration.
- Allow side to pin: a claimed batch must still deliver — assert that a row inserted as `pending` with a past `next_attempt_at` is claimed, sent, and ends `delivered`, with the payload transmitted intact.
- Red-prove, one mutation per clause, each executed: (a) return the ORM instances again → an integration test that runs `_claim_batch` then `deliver` against a real session must red with `DetachedInstanceError`; (b) read `endpoint.url` outside the `with` in `deliver` → the same test must red at that attribute.
- Cannot-run outcome: if `session.get(WebhookEndpoint, endpoint_id)` returns `None` (endpoint deleted mid-flight), mark the delivery `failed_permanent` with "endpoint deleted" instead of dereferencing `None` — see also finding #14.
- Preserve: batch claiming and the single round-trip per batch — do not fix this by opening a session per attribute.
- Boundary and tie: the claim boundary is `next_attempt_at <= now` inclusive; rows sharing a `next_attempt_at` must be ordered by `(next_attempt_at, id)` so the `BATCH_SIZE = 100` cut never falls between two equal keys and strands one of them.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch()`, `run_worker()`
What is wrong: `_claim_batch` moves rows to `in_flight` and only `_finish` moves them out, so any worker crash, container restart, lock expiry, or exception inside `asyncio.gather` leaves rows stuck in `in_flight` forever with no reaper and no timeout (R38 clause 1: an async transition with a success-only exit).
What breaks in production: a single restart during a batch permanently strands up to 100 deliveries — they are never retried, never marked failed, and never surface in any alert, so customers silently miss events with no operator affordance to recover them.
Fix: add a `claimed_at TIMESTAMPTZ` column set when a row goes `in_flight`, and have `_claim_batch` also reclaim rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` by resetting them to `pending` and incrementing `attempts`; cap the reclaim count so a permanently-stuck row eventually reaches `MAX_ATTEMPTS` and terminates as `failed_permanent` rather than cycling forever.
- Allow side to pin: a healthy in-flight delivery must NOT be reclaimed — assert a row claimed 10 seconds ago is invisible to a second `_claim_batch`, while one claimed 6 minutes ago is reclaimed.
- Red-prove, one mutation per clause, each executed: (a) remove the reclaim predicate → the stale-reclaim test must red; (b) remove the `attempts` increment on reclaim → a test asserting a row that is reclaimed `MAX_ATTEMPTS` times ends `failed_permanent` rather than looping must red (bound the loop so it terminates instead of hanging).
- Cannot-run outcome: if `claimed_at` is `NULL` on a legacy `in_flight` row, treat it as stale and reclaim — an unreadable claim time must not mean "assume a worker still owns it", which is the wedge itself.
- Preserve: the guarantee that a delivery in flight is not sent twice concurrently under normal operation; the 5-minute threshold must exceed the worst-case single-attempt duration (`REQUEST_TIMEOUT = 30.0`) with headroom.
- Boundary and tie: the reclaim boundary is strict (`claimed_at < now - 5min`, so exactly 5 minutes is not yet stale); if two workers reclaim the same row simultaneously, the `UPDATE ... WHERE status = 'in_flight' AND claimed_at = <observed>` conditional write decides the tie and the loser claims nothing.

### Major: the Redis lock is neither atomic to acquire nor owned when released
File: `app/webhooks/delivery.py` — `_acquire_lock()`, `run_worker()` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: `get` then `set` is a check-then-act race, `set` and `expire` are two commands so a crash between them leaves a lock with no TTL, and the `finally` deletes `LOCK_KEY` unconditionally without checking who owns it.
What breaks in production: two workers acquire simultaneously and claim overlapping batches, and after a 60-second TTL expiry worker A's `finally` deletes the lock that worker B now holds — so a third worker joins and the same deliveries go out several times concurrently, each with a different signature, multiplying load on customer endpoints.
Fix: acquire with a single atomic command carrying a unique token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`) so only the owner can release; renew the TTL while a batch is in progress rather than choosing a fixed 60s that a long batch outlives.
- Allow side to pin: a single worker must still acquire, work, and release — assert `_acquire_lock` returns `True` on a free key and that the key is gone afterwards; a worker that re-acquires immediately after its own release must succeed.
- Red-prove, one mutation per clause, each executed: (a) revert to `get`-then-`set` → a test driving two concurrent `_acquire_lock` calls against a fake Redis that interleaves at the `get` must red by observing two `True` results; (b) revert the release to an unconditional `delete` → a test where worker A's token has been overwritten by B and asserts A's release leaves B's value intact must red; (c) drop `ex=60` from the `set` → a test asserting the key has a positive TTL must red.
- Cannot-run outcome: if Redis is unreachable, `_acquire_lock` must return `False` and the worker must sleep and retry — never `True`, which would turn a cache outage into every replica dispatching at once.
- Preserve: single-worker exclusivity and the non-blocking poll behaviour; do not fix this by removing the lock and relying on the DB claim alone unless that claim is made a conditional `UPDATE`.
- Boundary and tie: the TTL boundary is the renewal deadline — renew at 60s/3 so an expiry never coincides with a live batch; if two workers present the same token (impossible with `uuid4`) the compare-and-delete is idempotent and the second delete is a no-op.

### Major: naive/aware datetime mixing between the enqueue path, the claim path and the schema
File: `app/webhooks/delivery.py` — `enqueue_for_event()` (`next_attempt_at=datetime.utcnow()`); `_claim_batch()` (`datetime.now(timezone.utc)`); `app/webhooks/models.py` (`DateTime(timezone=True)`); `migrations/0042_webhook_delivery.sql` (`TIMESTAMP`)

- Red-prove, one mutation per clause, each executed: (a) restore `datetime.utcnow()` → the non-UTC-session claim test must red; (b) revert the column type to `TIMESTAMP` → a test asserting a round-tripped value retains its `tzinfo` must red.
- Cannot-run outcome: if a naive datetime reaches the write path, raise rather than coerce — add an assertion in `_now`'s consumers that `dt.tzinfo is not None`, so "timezone unknown" is never silently spelled as UTC.
- Preserve: the immediate-delivery semantics of a newly enqueued event (`next_attempt_at = now`, claimed on the very next poll).
- Boundary and tie: the claim comparison is `<=`, so a row whose `next_attempt_at` is exactly `now` is claimed on this pass, not the next; equal timestamps tie-break on `id`.

### Major: the retry policy contradicts the documented policy in two ways
File: `app/webhooks/delivery.py` — `deliver()`, `backoff_for()`; `docs/webhooks.md` — "Retries"
What is wrong: the docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx status including 4xx up to `MAX_ATTEMPTS`, and `backoff_for` is `timedelta(seconds=2**attempt)` with no jitter at all (R49: the prose describes a control the implementation does not have).
What breaks in production: a customer endpoint returning 400 or 404 is hammered five times per event instead of once, and because every failed delivery of a batch backs off by the identical deterministic interval, retries arrive as synchronized thundering herds that can keep a recovering endpoint down.
Fix: branch on the status class in `deliver` — `if 400 <= response.status_code < 500 and response.status_code not in (408, 429): _finish(delivery.id, "failed_permanent", attempt, status_code, detail); return` — and add jitter to `backoff_for` as full jitter over the computed interval (`timedelta(seconds=random.uniform(0, BASE_DELAY_SECONDS**attempt))` using a dedicated `random.Random` instance, which is fine here because jitter is not a secret — unlike finding #2).
- Allow side to pin: retryable failures must still retry — assert a 500 and a connection error each schedule a further attempt, and that 408 and 429 are retried rather than treated as permanent.
- Red-prove, one mutation per clause, each executed: (a) remove the 4xx branch → a test asserting a 404 response ends `failed_permanent` with `attempts == 1` and exactly one request observed must red; (b) remove the jitter → a test asserting 100 computed backoffs for the same attempt are not all identical must red; (c) include 429 in the permanent set → the retry-on-429 test must red.
- Cannot-run outcome: a response whose status cannot be read (transport error) is retryable and must be classified as such explicitly, not fall through to the permanent branch by default.
- Preserve: `MAX_ATTEMPTS == 5` and the documented rough intervals — `test_backoff_grows_exponentially` currently asserts exact equality against 2/4/8/16 and must be rewritten to assert the jittered value lies within `(0, 2**attempt]`, not deleted.
- Boundary and tie: 400 is permanent and 500 is retryable, with 408 and 429 explicitly on the retry side; full jitter's upper bound is inclusive of `2**attempt` and its lower bound must be floored above zero (e.g. 100ms) so a retry cannot fire instantly.

File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/webhooks/delivery.py` — `enqueue_for_event()`; `app/api/routes/settings.py` — `EndpointIn.event_types`

### Major: the enqueue failure is swallowed, so a committed event can lose its deliveries

What is wrong: the `Event` row is committed by its own `session_scope`, then `enqueue_for_event` runs in a separate transaction whose failure is caught and downgraded to a warning, so there is no atomicity between "the event happened" and "its deliveries exist" and no reconciliation path.

### Major: any exception permanently kills the delivery worker
File: `app/webhooks/delivery.py` — `run_worker()`, `_finish()`
What is wrong: `run_worker`'s loop has no exception handling around `_claim_batch` or `asyncio.gather` (the `finally` only releases the lock), `gather` is called without `return_exceptions=True` so one failing coroutine propagates while the others are left unawaited, and `_finish` dereferences `session.get(...)` without a `None` check.
What breaks in production: a single deleted delivery row, a single constraint violation (finding #7), or one transient database error terminates the worker coroutine entirely — all webhook delivery for all tenants stops until someone notices the process is idle.
Fix: wrap the loop body in `try/except Exception: log.exception(...); await asyncio.sleep(poll_interval); continue` so one bad batch cannot end the loop; pass `return_exceptions=True` to `asyncio.gather` and log each returned exception against its delivery id; and guard `_finish` with `if row is None: log.error("delivery %s vanished", delivery_id); return`.
- Allow side to pin: the worker must keep delivering after a failure — assert that with three deliveries in a batch where the middle one raises, the other two still reach `delivered` and the loop performs a subsequent poll.
- Red-prove, one mutation per clause, each executed: (a) remove the loop-level `except` → the "worker survives a raising `_claim_batch`" test must red (bound the loop to N iterations so it terminates rather than hangs); (b) remove `return_exceptions=True` → the sibling-deliveries-still-complete test must red; (c) remove the `None` guard → the deleted-row test must red with `AttributeError`.
- Cannot-run outcome: a caught exception must be logged with `log.exception` including the delivery id and must increment an error counter — a swallowed batch failure must be distinguishable from an empty batch, which today it is not.
- Preserve: the lock release in the `finally` and the poll-interval sleep on an empty batch; the fix must not turn a persistent failure into a hot spin loop, so back off after consecutive errors.
- Boundary and tie: after N consecutive failed iterations the worker should escalate (alert) rather than exit; a batch where every delivery raises is the boundary case and must not be mistaken for an empty batch.
