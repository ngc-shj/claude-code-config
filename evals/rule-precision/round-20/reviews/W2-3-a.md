### Critical: signing secrets are generated with the non-cryptographic `random` module
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: The secret is built from `random.choice` (Mersenne Twister, seeded from a predictable state and fully recoverable from ~624 observed outputs) instead of the `secrets` module, and `SECRET_BYTES = 32` is used as a *character* count, so the name overstates the entropy it produces.
What breaks in production: An attacker who registers a handful of their own endpoints can recover the PRNG state and derive every other tenant's signing secret, letting them forge `X-Acme-Signature` on webhooks delivered to those tenants' receivers — the signature stops being an authenticity control for every customer.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`; drop `random`, `string`, `_ALPHABET`), and rename the constant to `SECRET_ENTROPY_BYTES = 32` so the unit is stated. Preserve, do not delete, the two properties the current test pins — the `whsec_` prefix and a deterministic length check — but restate the length assertion as `len(secret) >= len(SECRET_PREFIX) + 40` (43 chars is `token_urlsafe(32)`'s output) rather than deleting it. Deny/allow pair: assert `new_signing_secret() != new_signing_secret()` over 1000 draws (uniqueness must still SUCCEED) *and* assert `"random" not in inspect.getsource(signing)` so a reintroduction reds. Red-prove each clause separately by execution: (i) revert to `random.choice` → the source assertion reds; (ii) return a constant string → the uniqueness assertion reds; (iii) return `SECRET_PREFIX` alone → the length assertion reds; run all three singly and confirm three different assertion names in the failure output. Fail loudly: `new_signing_secret` must not fall back to any weaker source if `secrets` is unavailable — let the `ImportError` propagate at module import rather than degrade. Boundary and tie: the length assertion is `>=`, so exactly 43 characters passes; two draws that collide are a hard failure, not a retry.

### Critical: HMAC does not cover the timestamp, so the documented replay window cannot be enforced
File: app/webhooks/signing.py — `sign` (and `docs/webhooks.md`, "Verifying the signature")
What is wrong: `sign` returns a timestamp header but MACs only `serialize(payload)`, while the docs instruct receivers to verify an HMAC of `"{timestamp}.{raw_request_body}"` and to reject timestamps older than five minutes.
What breaks in production: The timestamp is unauthenticated, so anyone who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to `now` — the five-minute window the docs call "what stops a captured request from being replayed" stops nothing (R49: claim strictly stronger than the implementation; R29: doc-derived algorithm is not what the code computes).
Fix: Change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact transmitted body (see the next finding), and change `verify` to take the timestamp and the raw body explicitly: `verify(secret, timestamp: str, body: bytes, signature: str, *, max_age_seconds: int = 300)`, rejecting when `abs(now - int(timestamp)) > max_age_seconds`. Preserve the header names and the `sha256=` prefix — receivers already deployed against the docs depend on both — and preserve the docs' stated algorithm rather than rewriting the docs to match the weaker code. Deny/allow pair: pin that a signature signed at `now` still verifies (the allow case), alongside the deny case of a 301-second-old timestamp. Red-prove each clause by execution, one mutation each: (i) drop `f"{timestamp}."` from the MAC input → the "signature changes when only the timestamp changes" assertion reds; (ii) delete the age check → the stale-timestamp deny test reds; (iii) set `max_age_seconds` to 0 → the fresh-timestamp allow test reds. Fail loudly: a `timestamp` that is not an integer, or absent, must raise/return False with a named reason — "unparseable" must not be spelled the same as "fresh". Boundary and tie: age is compared with `>`, so exactly 300 seconds is ACCEPTED and 301 rejected; two deliveries sharing one timestamp produce different signatures only if their bodies differ, which is intended.

### Critical: the signature is computed over a re-serialization, not over the bytes actually sent
File: app/webhooks/delivery.py — `send_once`; app/webhooks/signing.py — `serialize`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, `ensure_ascii=True`) while the body on the wire is produced independently by `client.post(..., json=delivery.payload)`, which httpx serializes with compact `(",", ":")` separators and insertion order — the two byte strings differ for every payload with more than one key.
What breaks in production: Every customer following `docs/webhooks.md` computes the HMAC over the raw request body they received and gets a mismatch, so 100% of deliveries fail verification and the feature is unusable for its stated purpose — the classic R40 same-team-owns-both-sides failure, invisible here because the only test asserts the header merely *starts with* `sha256=` and never recomputes over `captured["body"]`.
Fix: Serialize once and send those exact bytes: in `send_once`, `body = serialize(delivery.payload).encode()`, sign `body`, and post with `content=body` plus an explicit `Content-Type: application/json` header (never `json=`). Pin `serialize` to `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode()` so the wire form is fully specified, and document those exact serialization parameters in `docs/webhooks.md`. Add the R40 round-trip test the rule requires: drive `send_once` through `httpx.MockTransport`, then feed `captured["body"]` and `captured["headers"]` through the *actual* `signing.verify` — actual producer output through the actual consumer, not two mocked shapes. Preserve the existing assertion that the body parses as JSON and that `type == "invoice.paid"`; do not weaken it to a string compare. Deny/allow pair: the round-trip must PASS for a payload with unicode and with keys in non-sorted insertion order (allow), and must FAIL when one byte of the captured body is flipped (deny). Red-prove separately by execution: (i) revert `send_once` to `json=delivery.payload` → the round-trip verify assertion reds; (ii) remove `separators=` from `serialize` → the same round-trip reds with a different captured body; (iii) remove `sort_keys=True` → the non-sorted-insertion-order allow case reds. Fail loudly: if `serialize` raises on a non-JSON-serializable payload, `deliver` must mark the row `failed_permanent` with that reason rather than swallow it. Boundary and tie: an empty payload `{}` serializes to `b"{}"` and must still verify; two payloads whose dicts differ only in key order must produce the SAME signature, which is exactly what `sort_keys` guarantees.

### Critical: signature comparison in `verify` is not constant-time
File: app/webhooks/signing.py — `verify` (`return expected == signature`)
What is wrong: The exported reference verifier compares the computed and supplied signatures with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: This is the implementation customers copy and the one any inbound-verification path in this service will reach for, so it leaks the correct HMAC byte-by-byte under timing measurement, letting an attacker forge a valid signature without the secret.
Fix: `return hmac.compare_digest(expected, signature)`, comparing on `str`/`bytes` of equal encoding, and state in the docstring that the function is constant-time so callers do not re-wrap it in `==`. Preserve the existing behavioural contract — a signature made with another secret must still return False (that test must stay green, not be deleted). Deny/allow pair: pin both that a correct signature returns True (allow) and that a wrong-secret signature returns False (deny), plus a same-length-different-bytes case so the length short-circuit inside `compare_digest` is not the only thing exercised. Red-prove each clause by execution: (i) restore `==` and assert `"compare_digest" in inspect.getsource(signing.verify)` → that assertion reds; (ii) return `True` unconditionally → the wrong-secret deny test reds; (iii) return `False` unconditionally → the correct-signature allow test reds. Fail loudly: a `signature` of `None` or a non-`str` must raise a named `TypeError` from the boundary, not be coerced to a False that reads like "checked and rejected". Boundary and tie: a supplied signature of exactly the right length but wrong content must take the same code path as a short one — assert both, since `compare_digest` is only constant-time for equal-length inputs and the length difference is itself observable.

### Critical: the deliveries endpoint has no tenancy predicate (IDOR)
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike the sibling `list_webhook_endpoints` in the same file, which does filter on `org_id` (R3: the tenancy pattern present two functions above is not propagated).
What breaks in production: Any authenticated user can enumerate `endpoint_id` and read another organization's delivery rows, and since `WebhookDelivery.payload` holds the full `invoice.paid` / `subscription.updated` event body, this is a cross-tenant leak of billing data — while `docs/webhooks.md` states the endpoint returns attempts "for an endpoint belonging to your organization" (R49: claim stronger than the implementation).
Fix: Join and filter: `.join(webhook_models.WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and raise `HTTPException(404)` — not 403 — when the resulting endpoint lookup is empty, so the response does not confirm the id exists. Preserve the `limit` and `created_at DESC` ordering behaviour the docs advertise. Deny/allow pair: the owning org's request must still return its rows (allow) *and* a foreign org's request must return 404 with an empty body. Per RT8, the deny test must assert more than the status — assert that zero `WebhookDelivery` rows appear in the response payload, since a handler that returns 404 alongside a populated body would pass a status-only test. Red-prove each clause by execution: (i) delete the `org_id` filter → the foreign-org deny test reds; (ii) hardcode the filter to a non-matching org → the owning-org allow test reds; (iii) return 403 instead of 404 → the enumeration-resistance assertion reds. Fail loudly: if `user.org_id` is `None`, deny and log a named error rather than letting the filter degrade to a match-everything comparison. Boundary and tie: an endpoint that exists but belongs to another org and an endpoint id that does not exist at all must be indistinguishable in status, body, and timing class.

### Critical: `WebhookEndpoint.to_dict` returns the signing secret on every list call
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`; consumed by `list_webhook_endpoints`
What is wrong: `to_dict` includes `"signing_secret"`, and `list_webhook_endpoints` returns it for every endpoint, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: The secret is emitted on an ordinary read route, so it lands in browser history, HTTP proxy and access logs, APM traces, and any client-side cache — turning a write-once credential into one broadcast on every settings page load, and invalidating the docs' security model that customers built their storage decisions on.
Fix: Remove `signing_secret` from `to_dict` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the single creation site, so exposure is opt-in per call site rather than a property of the model. Preserve the create-time disclosure — that is the feature, and deleting it would make the secret unrecoverable. Deny/allow pair: assert the POST response DOES contain `signing_secret` (allow) and that the GET list response does NOT, for the same endpoint (deny). Red-prove each clause by execution: (i) re-add the key to `to_dict` → the list-response deny assertion reds; (ii) drop the explicit merge in the POST handler → the create-response allow assertion reds. Fail loudly: add a response-shape assertion in the test suite that scans every settings-route JSON body for the `whsec_` prefix and fails naming the route, so a future route that serializes an endpoint cannot leak it silently. Boundary and tie: an endpoint whose secret was rotated must expose the new secret exactly once, on the rotation response, and never on a subsequent list.

### Critical: the migration's status CHECK constraint omits the status the code writes
File: migrations/0042_webhook_delivery.sql — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint allows `'failed'`, but `app/webhooks/delivery.py::deliver` writes `"failed_permanent"` and `app/webhooks/models.py::STATUSES` declares `"failed_permanent"` — three spellings across three files, none of which agree with the DB (R2/R3), and `STATUSES` is never actually referenced by anything.
What breaks in production: Every delivery that exhausts `MAX_ATTEMPTS` raises a `CheckViolation` inside `_finish`, so the row is never moved off `in_flight`, the exception escapes into `asyncio.gather`, and permanently-failing endpoints wedge the worker instead of being retired.
Fix: Make `models.STATUSES` the single source and derive the rest from it: change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`, and replace the string literals in `delivery.py` with `m.STATUSES` members (or a `Status` enum) so the value cannot be typed twice. Add a test that asserts the set parsed out of `migrations/0042_webhook_delivery.sql` equals `set(models.STATUSES)` — that test is what makes the next divergence visible, so do not replace it with a hand-maintained list. Deny/allow pair: a delivery that exhausts attempts must PERSIST as `failed_permanent` and be re-readable (allow); an arbitrary status such as `"oops"` must be rejected by the constraint (deny). Red-prove each clause by execution: (i) change one spelling in the migration → the set-equality test reds; (ii) change one member of `STATUSES` → the same test reds naming the other side; (iii) write `"oops"` through `_finish` against a real Postgres → the constraint deny test reds. Fail loudly: if the SQL cannot be parsed for the CHECK clause, the test must fail with "constraint not found", never skip — "examined nothing" must not read as "found nothing". Boundary and tie: `in_flight` is in the allowed set but is not terminal — see the R38 finding below, which must be fixed with it or the constraint just legalises the wedge.

### Critical: the unique index on `event_id` alone makes fan-out to two endpoints impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness is on `event_id` only, but `enqueue_for_event` inserts one row per matching endpoint, so any org with two or more active endpoints violates the index on the second row.
What breaks in production: `session.add_all(rows)` raises `IntegrityError`, the dispatcher's blanket `except Exception: log.warning(...)` swallows it, and the org receives **no** webhook for that event at all — a silent total-path failure whose only trace is a warning line, made worse because the failure is all-or-nothing rather than per-endpoint.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — that is the pair the docs' "deduplicate on `event_id`" advice actually implies once fan-out exists — and add the covering index the claim query needs, `CREATE INDEX idx_webhook_deliveries_due ON webhook_deliveries (status, next_attempt_at, id)`. Preserve idempotency: the composite index is what stops a re-dispatched event from double-enqueueing to the same endpoint, so do not simply drop the unique index. Deny/allow pair: enqueueing one event to two endpoints of one org must insert TWO rows (allow); enqueueing the same `(endpoint_id, event_id)` twice must insert one and raise on the second (deny). Red-prove each clause by execution: (i) restore the single-column index → the two-endpoint allow test reds with `IntegrityError`; (ii) drop the unique index entirely → the duplicate-pair deny test reds by inserting two rows. Fail loudly: `enqueue_for_event` must translate the duplicate-pair `IntegrityError` into an explicit "already enqueued, skipping" per row (`ON CONFLICT DO NOTHING` on the insert), and must NOT translate any other `IntegrityError` the same way. Boundary and tie: an org with exactly zero matching endpoints must return 0 and commit nothing, and two endpoints of *different* orgs sharing an `event_id` must both be insertable.

### Critical: registration accepts arbitrary schemes and hosts, and the client follows redirects (SSRF)
File: app/api/routes/settings.py — `create_webhook_endpoint`; app/webhooks/delivery.py — `run_worker` (`follow_redirects=True`)
What is wrong: The only check is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts `http://`, and also accepts non-schemes like `httpfoo://` (`startswith`, not equality — R47-shaped surface-form check), with no restriction on the resolved host; `docs/webhooks.md` states "Only `https://` URLs are accepted" (R49).
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or an internal `http://admin.svc.cluster.local/`), the worker POSTs to it from inside the VPC, follows any redirect to a further internal target, and `_finish` persists `response.text` into `response_body` — a full read-and-store SSRF whose output the tenant can retrieve once the deliveries endpoint is fixed to be readable by them at all.
Fix: Validate at the schema boundary (RS3), not in the handler body: give `EndpointIn.url` a `pydantic.HttpUrl`-typed field constrained to `https` only (`parsed.scheme != "https"` → 422), cap length, and add a resolution-time guard used by BOTH the registration handler and `send_once` — resolve the host with `socket.getaddrinfo` and reject any address for which `ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast`. Set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a permanent failure. Because DNS can change between registration and delivery, the guard must run again at send time — validating only at registration leaves a TOCTOU window (R5/R51); pin the resolved address and pass it to httpx rather than re-resolving. Preserve the ability to register a legitimate public HTTPS endpoint — do not "fix" this with an allowlist that denies everything. Deny/allow pair: `https://hooks.example.com/acme` must still register and deliver (allow); `http://…`, `httpfoo://…`, `https://169.254.169.254/`, `https://localhost/`, and an endpoint whose DNS resolves to `10.0.0.1` must each be rejected (deny). Red-prove each clause separately by execution: (i) restore `startswith("http")` → the `httpfoo://` deny test reds; (ii) delete the private-IP check → the `169.254.169.254` deny test reds; (iii) set `follow_redirects=True` → the redirect-to-internal deny test reds; (iv) hardcode the guard to reject everything → the public-HTTPS allow test reds. Fail loudly: when `getaddrinfo` fails or times out, DENY with a named "unresolvable host" error and mark the delivery failed — an unresolvable host must not be spelled the same as a safe one. Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv6 `::1`/`fc00::/7` fall on the deny side; a hostname resolving to BOTH a public and a private address is denied, not partially allowed.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: app/webhooks/delivery.py — `deliver` (`time.sleep(delay)`)
What is wrong: `deliver` is `async def` but sleeps synchronously between retry attempts, and `run_worker` runs up to `BATCH_SIZE = 100` of them concurrently under `asyncio.gather`.
What breaks in production: One failing endpoint blocks the entire event loop for `2 + 4 + 8 + 16 = 30` seconds, stalling every other in-flight delivery and any other coroutine sharing that loop; with several failing endpoints in a batch the worker makes essentially no progress while the Redis lock (60s TTL) silently expires underneath it.
Fix: Replace with `await asyncio.sleep(delay)` (`time` import becomes unused in `delivery.py`; `signing.py` keeps its own). Do not remove the backoff itself — the delay is the feature. Because the retry loop also holds the row `in_flight` for the whole window, prefer rescheduling over sleeping: set `next_attempt_at = now + backoff_for(attempt)`, `status = "pending"`, `attempts = attempt`, and return, letting the next poll pick the row up — that removes the sleep entirely and makes attempts survive a worker restart. Deny/allow pair: a delivery that succeeds on the first attempt must still complete without any sleep (allow); a delivery that fails must be observably rescheduled with a strictly later `next_attempt_at` (deny side of "did not deliver"). Red-prove each clause by execution: (i) reintroduce `time.sleep` and assert `asyncio.get_running_loop()` stays responsive by racing a 50ms `asyncio.sleep` against a 2s retry → the responsiveness assertion reds; (ii) drop the `next_attempt_at` update → the "strictly later" assertion reds; (iii) drop the `attempts` write → the attempt-count assertion reds. Fail loudly: if the reschedule write fails, mark the row `failed_permanent` with the DB error rather than leaving it `in_flight`. Boundary and tie: `attempt == MAX_ATTEMPTS` is terminal (no reschedule) and `attempt == MAX_ATTEMPTS - 1` schedules one more; two rows with an identical `next_attempt_at` are ordered by `id` (see the R57 finding).

### Critical: ORM rows are used after their session closes (detached instances)
File: app/webhooks/delivery.py — `_claim_batch` (returns `rows` after the `with` block) and `deliver` (`endpoint` read after the `with` block)
What is wrong: `session_scope()` is a context manager, so both functions return/retain SQLAlchemy instances whose session has been closed and expired; `deliver` then reads `delivery.payload`, `delivery.attempts`, `delivery.id`, `endpoint.signing_secret` and `endpoint.url` off detached objects.
What breaks in production: With the default `expire_on_commit=True` the first attribute access raises `DetachedInstanceError`, so `run_worker` never delivers anything at all and the failure escapes `asyncio.gather` into the `while True` loop — and the test suite cannot see it, because `FakeEndpoint`/`FakeDelivery` are plain classes with class attributes (RT1: mock-reality divergence — the fakes are precisely why this is invisible).
Fix: Stop passing ORM objects across session boundaries — have `_claim_batch` return plain values (`list[tuple[int, int, dict, int]]` of `(delivery_id, endpoint_id, payload, attempts)`) selected with the endpoint's `url` and `signing_secret` joined in, so `deliver` and `send_once` take primitives and never touch a session. Per RT1/RT5, replace `FakeEndpoint`/`FakeDelivery` with the real `WebhookEndpoint`/`WebhookDelivery` models constructed against a session (or with the same dataclass the production path now uses) so the fake cannot diverge from the model again. Preserve `send_once`'s current signature shape at the call site — the existing MockTransport test must still exercise the same function, not a renamed stub. Deny/allow pair: an integration test that runs `_claim_batch` → `deliver` against a real session must DELIVER successfully (allow); a delivery whose endpoint row was deleted between claim and send must be marked failed with a named reason, not raise (deny). Red-prove each clause by execution: (i) revert `_claim_batch` to returning ORM rows → the integration test reds with `DetachedInstanceError`; (ii) revert `FakeEndpoint` in place of the real model → assert the test module imports `WebhookEndpoint`, which reds; (iii) delete the endpoint row mid-flight → the named-failure deny test reds if the code raises instead. Fail loudly: a claimed delivery whose endpoint no longer resolves must be finished as `failed_permanent` with "endpoint missing", never skipped silently. Boundary and tie: a batch of exactly zero claimed rows must return an empty list and sleep, not raise; two rows for the same endpoint must each carry their own copy of the endpoint fields.

### Critical: the dispatch lock is non-atomic and its `finally` deletes whichever lock is currently held
File: app/webhooks/delivery.py — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `GET` then a separate `SET` then a separate `EXPIRE` (three round trips, no `NX`), so two workers both observe an empty key and both proceed; the lock has a fixed 60s TTL that a batch of 100 deliveries with 30s of backoff each will outlive; and the unconditional `delete` releases the key regardless of who owns it.
What breaks in production: Two or more workers claim overlapping batches, each deleting the other's lock, so paid-invoice webhooks are delivered two or more times to customer endpoints — and because the receiver-side dedup the docs recommend keys on `event_id`, a fan-out to multiple endpoints of the same org cannot be distinguished from a duplicate.
Fix: Acquire with a single atomic call carrying a unique owner token — `token = secrets.token_hex(16)`; `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`), and renew the TTL while a batch is in flight (or, better, make the batch short by adopting the reschedule-instead-of-sleep fix above so a batch cannot exceed the TTL). Independently, make the DB claim atomic too: replace the SELECT-then-mutate in `_claim_batch` with `UPDATE ... SET status='in_flight' WHERE id IN (SELECT id FROM webhook_deliveries WHERE status='pending' AND next_attempt_at <= now() ORDER BY next_attempt_at, id LIMIT :n FOR UPDATE SKIP LOCKED) RETURNING ...` — with `SKIP LOCKED` the Redis lock stops being the only thing preventing double delivery, which is the point (a lock that can expire must never be the sole correctness guarantee). Preserve concurrency: the fix must not serialise the worker down to one delivery at a time. Deny/allow pair: with two workers and one due row, exactly ONE must deliver it (deny side) and it MUST be delivered (allow side — a fix that delivers zero satisfies "no duplicates" trivially). Red-prove each clause separately by execution: (i) revert to `GET` + `SET` → the exactly-once test reds with two deliveries; (ii) revert release to an unconditional `delete` and force a TTL expiry mid-batch → the "worker B does not release worker A's lock" assertion reds; (iii) drop `FOR UPDATE SKIP LOCKED` while keeping the Redis fix, and run two workers with the lock disabled → the exactly-once test reds, proving the DB claim carries the guarantee on its own; (iv) make `_claim_batch` return nothing → the delivered-at-least-once allow test reds. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise a named error and the worker must back off — a connection error must NOT be caught into `return True`, and it must not be spelled the same as "lock is free". Boundary and tie: `next_attempt_at == now()` is due (`<=`); two rows with identical `next_attempt_at` are broken by `id` so the LIMIT cut is deterministic.

### Major: `in_flight` is a non-terminal state with no reset path
File: app/webhooks/delivery.py — `_claim_batch` (`row.status = "in_flight"`) and `_finish`
What is wrong: A row leaves `in_flight` only when `_finish` runs on the success or exhausted-attempts path; a worker crash, a pod eviction, a `DetachedInstanceError`, or the CHECK violation described above leaves the row `in_flight` forever, and `_claim_batch` only ever selects `status == "pending"` (R38 case 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: Every delivery interrupted mid-flight is permanently stranded — never retried, never reported as failed, and invisible to the docs' "next attempt is scheduled" view, so customers silently miss events with no operator signal.
Fix: Bound the state: on claim, write `in_flight` together with `claimed_at = now()` and `next_attempt_at = now() + IN_FLIGHT_TIMEOUT` (a new NOT NULL column plus a migration), and widen the claim predicate to `status = 'pending' OR (status = 'in_flight' AND next_attempt_at <= now())` so a stranded row is reclaimed exactly like a due one. Add a counter/metric for reclaimed rows so the recovery is observable rather than silent. Preserve at-most-`MAX_ATTEMPTS` semantics — a reclaimed row must increment `attempts`, so reclaiming cannot become an infinite retry loop. Deny/allow pair: a row stranded for longer than the timeout must be reclaimed and delivered (allow); a row claimed 1 second ago must NOT be reclaimed by a second worker (deny).
