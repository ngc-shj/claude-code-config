### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built with `random.choice(_ALPHABET)`, i.e. Python's Mersenne Twister, which is fully reconstructible from ~624 observed outputs and is seeded from a small state, so the "secret" is predictable rather than unguessable.
What breaks in production: An attacker who registers a handful of their own endpoints (each response returns its secret, see the leak finding below) can recover the generator state and forge valid `X-Acme-Signature` headers for *other* customers' endpoints, so every downstream consumer that trusts the signature accepts attacker-authored invoice and subscription events.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and rename `SECRET_BYTES` to mean what it says (32 raw bytes, not 32 alphabet characters) — the current constant name asserts bytes while the loop produces characters, and that mismatch is what made the entropy question invisible. Preserve the two properties the current code and `test_new_signing_secret_has_prefix_and_length` rely on: the `whsec_` prefix must still be present, and the value must still be a URL-safe ASCII string storable in a `TEXT` column; update that test's length assertion to `len(secret) > len(SECRET_PREFIX) + 32` rather than deleting it. Allow side to pin: `new_signing_secret()` still returns a value that `sign`/`verify` round-trip successfully, and two successive calls differ. Red-prove each clause separately by execution — (a) monkeypatch `secrets.token_urlsafe` to a constant and assert a new uniqueness test goes red, (b) drop the prefix and assert the prefix test goes red, (c) shorten to 8 bytes and assert the length test goes red; three mutations, three distinct reddened assertions. Fail loudly if the CSPRNG is unavailable: do not add a `try/except ImportError` fallback to `random` — an unavailable `secrets` module must raise at import, because "could not obtain entropy" must not be spelled the same as "obtained entropy". Boundary/tie: state that `SECRET_BYTES` is a floor, not an exact length (`token_urlsafe(32)` yields 43 chars), so the length assertion is `>=`, and two secrets colliding is a 2^-256 event the uniqueness test treats as failure.

### Critical: `verify` compares signatures with `==`, not a constant-time primitive
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: The HMAC comparison uses Python's short-circuiting `str.__eq__`, which returns on the first differing byte, and `docs/webhooks.md` simultaneously tells customers to "compare it against your own computation using a constant-time comparison" — the shipped reference implementation does the opposite of the documented control (RS1; R49 clause 2, a claim stronger than the implementation).
What breaks in production: Any caller that can submit candidate signatures against this helper — and every customer who copies the shipped `verify` into their own receiver, which is what the doc invites — leaks the correct digest byte-by-byte through response timing, letting an attacker forge a signature without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with `hmac` already imported at line 2 of the same file — no new dependency. Preserve the current contract exactly: `verify` still takes the full `sha256=<hex>` header form (do not "simplify" by stripping the prefix, since that is the byte string customers actually receive) and still returns `bool`. Allow side to pin: `test_verify_accepts_signature_produced_by_sign` must stay green, and add the case where `signature` is `None`/empty so `compare_digest`'s `TypeError` on non-`str` is handled by an explicit `if not isinstance(signature, str): return False` guard rather than propagating. Red-prove separately: (a) revert to `==` and assert a new timing-independence test — one that asserts `compare_digest` is on the call path via `unittest.mock.patch("hmac.compare_digest", wraps=hmac.compare_digest)` and checks it was called — goes red; (b) flip the return to `not compare_digest(...)` and assert `test_verify_rejects_a_signature_made_with_another_secret` goes red. Two mutations, two different assertions. Fail loudly: the `isinstance` guard returns `False` (a deny), never `None`, so an unusable input cannot be read as a pass. Boundary/tie: `compare_digest` on two equal-length hex strings is the intended path; state that a signature of the wrong *length* is rejected and that the length difference itself is observable — that is accepted, since length is not secret.

### Critical: the timestamp is not covered by the HMAC, so the documented replay window is bypassable
File: `app/webhooks/signing.py` — `sign`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: `sign` computes `hmac.new(secret, serialize(payload), sha256)` over the payload only, while the doc states the signature is "the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`" and that rejecting stale timestamps "is what stops a captured request from being replayed" — the timestamp is transmitted in an unauthenticated header the attacker can rewrite freely.
What breaks in production: An attacker who captures one delivery replays it forever by editing `X-Acme-Timestamp` to the current second; the signature still verifies because it never covered the timestamp, so the five-minute freshness check every customer was told to implement is a no-op and duplicate `invoice.paid` events can be injected at will.
Fix: Change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact serialized body (see the next finding), and change `verify` to `verify(secret, timestamp, body, signature)` so the caller must pass the timestamp it received; inside `verify`, reject when `abs(now - int(timestamp)) > 300` *before* the compare, and treat a non-integer timestamp as a deny. Preserve what made the feature usable: the header names, the `sha256=` prefix, and the fact that `sign` still returns `(timestamp, signature)` so `send_once` is a one-line change. Allow side to pin: a request signed at `now` and verified at `now + 299` still verifies — the widened-tolerance failure mode is exactly what a deny-only fix would hide. Red-prove each clause separately: (a) revert to signing the payload alone and assert a new `test_verify_rejects_a_rewritten_timestamp` (same body, timestamp incremented by 1, original signature) goes red; (b) delete the freshness check and assert `test_verify_rejects_a_stale_timestamp` (timestamp `now - 301`) goes red; (c) delete the `int()` parse guard and assert `test_verify_denies_a_non_numeric_timestamp` goes red. Fail loudly: a missing or unparseable timestamp routes to an explicit `return False` with a distinct log line, so "could not evaluate freshness" is not spelled like "fresh". Boundary/tie: state that exactly 300 seconds is accepted and 301 is rejected, and that a timestamp in the *future* beyond 300s is rejected too — an unstated future bound is where clock-skew forgery re-enters.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `serialize`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys sorted) while the body actually transmitted is produced by `client.post(..., json=delivery.payload)`, which httpx serializes with its own separators and *insertion* key order — the signed string and the raw request body are different byte sequences (R40: producer wire shape vs strict consumer, same team owning both sides, so unit tests that never round-trip pass vacuously).
What breaks in production: Every customer following `docs/webhooks.md` computes the HMAC over the raw body they received and gets a mismatch, so 100% of deliveries are rejected by every correctly-implemented receiver — a silent total-path failure that the shipped test suite is structurally unable to detect.
Fix: Serialize once and send those exact bytes: in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, pass `ts, signature = sign(endpoint.signing_secret, ts, body)`, and call `client.post(endpoint.url, content=body, headers=headers)` with `Content-Type: application/json` set explicitly (it already is). Preserve the behaviour the feature needs: the receiver must still get valid JSON with the same field values — do not "fix" this by dropping `sort_keys`, since determinism is what makes a customer's re-serialization unnecessary; state in the doc that the body is canonical sorted-key JSON and must be HMACed as received, unparsed. Allow side to pin: a round-trip test that feeds the *actual* captured `request.content` from `MockTransport` through the *actual* `signing.verify` and asserts it returns `True` — actual producer output through the actual consumer, not two mocked shapes. Red-prove each clause separately: (a) switch the call back to `json=` and assert the round-trip test goes red; (b) remove `sort_keys=True` from `serialize` and assert a new `test_serialize_is_key_order_independent` (two dicts with the same pairs inserted in different order produce identical bytes) goes red; (c) mutate one payload value and assert the round-trip test goes red. Fail loudly: if `serialize` raises `TypeError` on a non-JSON-serializable payload, let it propagate and mark the delivery `failed_permanent` with that detail rather than sending an unsigned or empty body. Boundary/tie: name the empty-payload case (`{}` signs to a stable non-empty digest, and is a legitimate body, not "absent") and state that two payloads differing only in key order now produce the *same* signature by construction — that is the intended tie.

### Critical: `GET /webhook-endpoints/{id}/deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while the two sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) both filter on `org_id` — the tenancy predicate present on every peer route is missing on this one (R3, incomplete pattern propagation, security-relevant).
What breaks in production: Any authenticated user can enumerate `endpoint_id` values and read another organization's delivery rows, and `WebhookDelivery.to_dict()` exposes `event_id`, `event_type`, `status` and `response_status` for events belonging to that other tenant — a cross-tenant data disclosure reachable with a single incrementing integer, and `docs/webhooks.md` states these are "the most recent attempts for an endpoint belonging to your organization".
Fix: Add the join and the tenancy predicate — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return `404` (not `403`) when the join yields nothing, so the endpoint's existence is not itself an oracle. Preserve the useful behaviour: an endpoint the caller *does* own must still return its deliveries in `created_at desc` order up to `limit`. Allow side to pin (RT10): one test asserting the owning org gets its rows back with the expected ids, alongside the deny test — a fix that always returns `[]` satisfies the deny test alone. Red-prove each clause separately: (a) remove the `org_id` filter and assert `test_other_org_cannot_read_deliveries` goes red; (b) remove the `endpoint_id` filter and assert `test_only_the_requested_endpoints_deliveries_are_returned` goes red; (c) change the `404` to a `200` with an empty list and assert the status assertion goes red. The deny test must assert the *body*, not just the status (RT8): assert the response contains none of the other org's delivery ids. Fail loudly: an unresolvable `user.org_id` must raise, not fall through to an unfiltered query. Boundary/tie: state that an endpoint owned by the caller's org but soft-`active=False` still returns its deliveries (deactivation is not deletion), and that an `endpoint_id` belonging to no org returns the same `404` as one belonging to another org.

### Critical: every endpoint list response returns the signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`), consumed by `list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally includes the signing secret, and `GET /v1/settings/webhook-endpoints` returns `[e.to_dict() for e in endpoints]`, directly contradicting `docs/webhooks.md`: "The response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a documented control the implementation does not provide).
What breaks in production: The secret is re-readable on every list call, so it lands in browser caches, proxy logs, support screenshots and any client that logs API responses; combined with the predictable-PRNG finding, it also hands an attacker the generator samples needed to forge signatures for endpoints they do not own.
Fix: Remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable it already holds, so creation is the only path that emits it. Preserve what the feature needs: creation must still return the secret exactly once — do not fix this by removing it from creation too, which would leave customers unable to verify anything. Allow side to pin: `test_create_returns_the_secret_once` asserts the POST body contains `signing_secret`, paired with `test_list_never_returns_the_secret` asserting no element of the GET body has that key. Red-prove separately: (a) re-add the field to `to_dict` and assert the list test goes red; (b) drop the field from the create response and assert the create test goes red. Fail loudly: assert on the *key set* of the serialized dict, not on a substring of the JSON — a comparator that ignores extra keys is how the field silently returns (RT1 clause e). Boundary/tie: state that `to_dict()` is the single shared serializer for both routes, so any future field added there is exposed on the list route by default; the test asserts an exact allowed key set, and a new key is a deliberate decision rather than a default-open one.

### Critical: arbitrary user-supplied URLs are fetched with redirects followed — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`); `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check on the destination is that the scheme starts with `http` and a netloc exists, so `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/`, and `http://10.0.0.5/admin` are all accepted, and `follow_redirects=True` means even a validated public host can bounce the worker to an internal one at delivery time.
What breaks in production: The worker becomes a fully authenticated SSRF proxy into the cluster's private network — cloud metadata credentials, internal admin endpoints and the Redis instance backing `app.cache` are all reachable, with the response body persisted into `webhook_deliveries.response_body` and readable through the deliveries route.
Fix: Validate at the boundary and again at connect time, because DNS can change between them: (1) in `create_webhook_endpoint`, require `parsed.scheme == "https"` (exact equality, see the scheme finding), reject a non-default port unless it is 443, and reject when every resolved A/AAAA record for `parsed.hostname` is in a private, loopback, link-local, or unique-local range using `ipaddress.ip_address(...).is_global`; (2) in `delivery.run_worker`, set `follow_redirects=False` and treat a 3xx as a permanent failure with detail `"redirect not followed"`; (3) pin the connection with an `httpx` transport that re-checks `is_global` on the resolved peer address before the request is issued, so a rebind between registration and delivery is denied rather than followed. Preserve the useful behaviour: a legitimate public HTTPS endpoint on port 443 must still register and still receive deliveries — do not fix this with an operator allowlist that makes self-service registration impossible. Allow side to pin: `test_public_https_endpoint_is_accepted` and `test_delivery_to_a_public_host_succeeds`, run alongside the denies; a validator that rejects everything passes the deny suite alone. Red-prove each clause separately: (a) remove the `is_global` check and assert `test_rejects_link_local_metadata_host` goes red; (b) set `follow_redirects=True` and assert `test_redirect_to_internal_host_is_not_followed` goes red; (c) drop the port check and assert `test_rejects_non_443_port` goes red. Fail loudly: when DNS resolution fails or times out, deny registration with a 422 naming "could not resolve host" — an unresolvable name must not be spelled the same as a resolved-and-public one. Boundary/tie: state which side of the boundary the values fall on — port 443 accepted, 8443 rejected; `is_global` false rejected including `0.0.0.0` and IPv4-mapped IPv6 forms; a hostname resolving to both a public and a private address is rejected (any-private denies, not majority-public allows).

### Critical: the migration's status CHECK constraint omits the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: Three of the four enum spellings match, but the code's terminal-failure value is `failed_permanent` while the constraint permits `failed` — the producer's enum spelling does not match the strict consumer's contract (R40; R42, class-membership derived from the supplied list rather than from the defining primitive `STATUSES`).
What breaks in production: Every delivery that exhausts `MAX_ATTEMPTS` raises `IntegrityError` inside `_finish`, so the row stays `in_flight` forever, the exception propagates out of `deliver` and through `asyncio.gather`, and the worker loop terminates — one permanently failing customer endpoint takes down webhook delivery for every tenant.
Fix: Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the list from `models.STATUSES` rather than retyping it — add a test that reads `STATUSES` and asserts each member is insertable against a real (or containerized) Postgres, so the two lists cannot drift again. Preserve what the constraint is for: do not fix this by dropping the CHECK, which is the control that made the mismatch visible at all. Allow side to pin: `test_every_status_in_STATUSES_is_insertable` (the allow direction) beside `test_an_unknown_status_is_rejected` (the deny direction) — a constraint that permits everything passes the first alone. Red-prove each clause separately: (a) remove one member from the SQL list and assert the insertable test goes red naming that member; (b) remove the CHECK entirely and assert the unknown-status test goes red. Fail loudly: the test must fail, not skip, when no database is reachable — a skipped constraint test reports green while examining nothing. Boundary/tie: state that `STATUSES` is the single source of truth and that adding a member to it without a migration is what the new test reddens; the tie case is a status string differing only in case (`'Failed_Permanent'`), which the CHECK rejects because the comparison is exact.

### Critical: the unique index on `event_id` alone permits only one endpoint per event
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index makes `event_id` globally unique across the table, so the second row of any multi-endpoint fan-out violates it.
What breaks in production: Any organization with two or more active endpoints subscribed to the same event gets an `IntegrityError` on `session.add_all`, which `dispatch` catches and downgrades to `log.warning("webhook enqueue failed...")` — so *no* delivery rows are written at all and the events vanish silently, with only a warning line as evidence.
Fix: Replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — that is the constraint the intent ("deduplicate on `event_id`" per endpoint) actually requires, and it also gives the idempotency guarantee `docs/webhooks.md` promises. Preserve the deduplication property the original index was reaching for: re-dispatching the same `event_id` must still not create a second row for the same endpoint — do not fix this by deleting the unique index. Allow side to pin: `test_two_endpoints_both_receive_the_same_event` (two active endpoints, one event, two rows written) beside `test_reenqueueing_the_same_event_for_one_endpoint_is_a_noop`. Red-prove each clause separately: (a) revert to the single-column index and assert the two-endpoint test goes red with an integrity error; (b) drop the index entirely and assert the re-enqueue test goes red with two rows. Fail loudly: `enqueue_for_event` must stop swallowing this class — see the dispatcher finding; an integrity failure that reaches only `log.warning` is "examined nothing" spelled as "found nothing". Boundary/tie: state that the pair `(endpoint_id, event_id)` is the uniqueness key and that a *retry* of the same pair is an intended no-op (use `ON CONFLICT DO NOTHING`), while two different endpoints at the same instant both succeed — that is the tie the old index broke.

### Critical: `time.sleep` blocks the event loop inside an async coroutine
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is `async def` but its retry backoff calls the blocking `time.sleep`, freezing the entire event loop for 2, 4, 8 and 16 seconds rather than yielding — the module already imports `asyncio` at line 3 and uses `asyncio.sleep` correctly in `run_worker`, so the correct primitive is present and was not used at this one site (R3/R17: the pattern applied at one call site and not its sibling).
What breaks in production: A single unreachable endpoint stalls the whole worker process for up to 30 seconds per delivery — `asyncio.gather` over a `BATCH_SIZE` of 100 becomes fully serial, so a batch containing 100 failing endpoints blocks for ~50 minutes while the 60-second Redis lock expires underneath it and a second worker starts duplicating the same batch.
Fix: `await asyncio.sleep(delay)`. Note the same blocking-in-async class across this module: `enqueue_for_event`, `_claim_batch` and `_finish` are `async def`/called from coroutines but perform synchronous SQLAlchemy I/O inside `session_scope()`, which blocks the loop identically — either move those to an async session or dispatch them via `asyncio.to_thread`, and enumerate every `session_scope()` use in the diff (four sites: `delivery.py` lines in `enqueue_for_event`, `_claim_batch`, `_finish`, `deliver`) rather than fixing only the `sleep`. Preserve the retry timing the docs promise: the wall-clock gap between attempts must remain ~2/4/8/16 seconds — do not fix this by removing the backoff. Allow side to pin: a test that runs two `deliver` coroutines concurrently against a failing transport and asserts total wall-clock time is bounded by one backoff sequence, not two — the deny-only version (asserting a single delivery still retries) passes even with `time.sleep`. Red-prove each clause separately: (a) revert to `time.sleep` and assert the concurrency test goes red on the elapsed-time assertion; (b) delete the sleep entirely and assert a test on `MAX_ATTEMPTS` retry spacing goes red. Fail loudly: bound the concurrency test with `asyncio.wait_for` so a regression times out with a named failure instead of hanging the suite. Boundary/tie: state that the elapsed-time assertion is an upper bound with a stated tolerance (e.g. `< 1.5x` one sequence) rather than an equality, and that two coroutines sleeping the identical duration is the case being pinned.

### Critical: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`) and `deliver` (`with session_scope() as session: endpoint = session.get(...)` then `endpoint.signing_secret` outside the block)
What is wrong: Both functions load ORM objects inside a `session_scope()` context and then read their attributes after the context exits; on a committed-and-closed SQLAlchemy session those attributes are expired, so the first access raises `DetachedInstanceError` (or re-triggers a load on a dead session) — and this is the same pattern at two sites, so fixing one leaves the other.
What breaks in production: `run_worker` claims a batch, marks the rows `in_flight`, then dies on the first attribute read in `send_once`/`deliver` — the deliveries are permanently stranded in `in_flight` (no reaper resets them) and the worker loop exits, so webhook delivery never runs at all after the first non-empty batch.
Fix: Stop passing ORM instances across session boundaries: have `_claim_batch` return plain dataclasses or tuples of the fields the worker needs (`id`, `endpoint_id`, `event_id`, `attempts`, `payload`), and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside a single `session_scope()` before the request. Alternatively pass `expire_on_commit=False` in `session_scope`'s sessionmaker — but only if that is verified not to change semantics for the pre-existing `settings.py` handlers that also return `to_dict()` from inside a scope. Preserve the behaviour the current code needs: the `in_flight` marking must still commit before the HTTP request is issued, so a crash cannot re-deliver — do not fix this by moving the whole delivery inside the session, which would hold a DB transaction open for the full 30-second HTTP timeout. Allow side to pin: an integration test using a real session (not `FakeDelivery`) that claims a batch and successfully delivers it — the current suite's plain-attribute fakes make this defect structurally invisible (RT1: the double does not behave like the boundary it stands in for). Red-prove each clause separately: (a) revert `_claim_batch` to returning ORM rows and assert the integration test goes red with `DetachedInstanceError`; (b) revert `deliver`'s endpoint load and assert it goes red at `endpoint.signing_secret`. Fail loudly: the integration test must fail rather than skip when no database is available. Boundary/tie: state that the detach boundary is the `session_scope()` exit and that an empty batch (`rows == []`) is a legitimate value returned across it, distinct from an error.

### Critical: the delivery test asserts the signature's prefix, never that it verifies
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test captures `request.content` but asserts only `captured["headers"][signing.SIGNATURE_HEADER].startswith("sha256=")` and a single field of the parsed body — it never feeds the captured raw bytes and the captured timestamp back through `signing.verify`, so the assertion is true under any implementation that emits a correctly-prefixed string (RT1 clause d: no independently written expected value; the only end-to-end check of the signing control is a prefix match).
What breaks in production: This is precisely why the signed-bytes-vs-sent-bytes mismatch and the unsigned timestamp both ship green — the one test that touches the wire never exercises the verification path a customer will run, so the suite reports coverage of a security control it does not test.
Fix: Replace the prefix assertion with a real round-trip: `assert signing.verify(SECRET, captured["headers"][signing.TIMESTAMP_HEADER], captured["body"], captured["headers"][signing.SIGNATURE_HEADER])`, using the raw captured bytes and not a re-serialization of the payload dict. Add a second, independently written expected value — an HMAC computed inline in the test from a hardcoded secret, hardcoded timestamp (patch `time.time`) and hardcoded body string, compared byte-for-byte against the emitted header — so the assertion is not `f(g(x)) == x` over two outputs of the subject. Preserve the existing coverage: keep the content-type and payload-field assertions rather than replacing them. Allow side to pin: the round-trip must return `True` for the genuine request (the allow direction), beside a new negative case where one captured body byte is flipped and `verify` returns `False`. Red-prove each clause separately: (a) change `serialize` to drop `sort_keys` and assert the hardcoded-HMAC assertion goes red; (b) change `send_once` to post with `json=` instead of `content=` and assert the round-trip assertion goes red; (c) make `verify` return `True` unconditionally and assert the flipped-byte case goes red. Fail loudly: assert `captured` is non-empty first, so a transport that never invoked the handler fails with "request was never issued" rather than a `KeyError` that reads like an unrelated bug. Boundary/tie: state that the comparison is over the exact captured bytes including trailing whitespace, and that an empty payload `{}` is a legitimate signable body whose digest the test also pins.

### Major: 4xx responses are retried, contradicting the documented permanent-failure rule
File: `app/webhooks/delivery.py` — `deliver`, the `if 200 <= response.status_code < 300` branch
What is wrong: Every non-2xx response falls into the same retry path, but `docs/webhooks.md` states "a 4xx is permanent and we stop immediately" — the documented classification is not implemented (R49 clause 2).
What breaks in production: A customer endpoint returning `404` or `401` is hammered five times with escalating backoff for every event, burning the worker's serial capacity and the customer's rate limits, while their delivery dashboard shows five attempts where the docs promised one.
Fix: After the 2xx check, add `if 400 <= response.status_code < 500 and response.status_code not in (408, 429): _finish(delivery.id, "failed_permanent", attempt, response.status_code, detail); return`, and honour `Retry-After` on 429. ### Major: the claim query orders on a non-unique column with no tiebreak or row lock
File: `app/webhooks/delivery.py` — `_claim_batch`, `.order_by(m.WebhookDelivery.next_attempt_at).limit(BATCH_SIZE)`
What is wrong: `next_attempt_at` is a wall-clock value that ties routinely — `enqueue_for_event` writes `now()` for every row of a fan-out, so a burst produces many identical values — and the query has no secondary sort key and no `FOR UPDATE SKIP LOCKED`, so the order among tied rows is undefined across executions (R57: an ordering key without a total order).
What breaks in production: With more than `BATCH_SIZE` eligible rows sharing an instant, the engine may return the same subset on consecutive polls while other tied rows are never selected, starving them indefinitely; and without `SKIP LOCKED` the (already fail-open) Redis lock is the only thing preventing two workers from claiming the same rows.
Fix: Order on `(next_attempt_at, id)` — `id` is the `BIGSERIAL` primary key, unique and monotonic by construction — and add `.with_for_update(skip_locked=True)` so the claim is safe independent of the Redis lock. Add the composite index `CREATE INDEX idx_webhook_deliveries_claim ON webhook_deliveries (status, next_attempt_at, id);` replacing the status-only index, which does not support this query. Preserve the intended priority: the oldest-due delivery must still be attempted first — do not fix the ties by ordering on `id` alone. Allow side to pin: `test_the_oldest_due_delivery_is_claimed_first` beside `test_every_tied_row_is_eventually_claimed_across_successive_batches`; an ordering that is merely deterministic but wrong passes the second alone. Red-prove each clause separately: (a) remove the `id` tiebreak and assert the eventually-claimed test goes red under 2×`BATCH_SIZE` tied rows; (b) reverse the sort and assert the oldest-first test goes red; (c) remove `skip_locked` and assert `test_two_concurrent_claims_do_not_overlap` goes red. Fail loudly: if the claim query returns more than `BATCH_SIZE` rows, raise rather than proceed — a limit that silently did not apply must not read as a normal batch. Boundary/tie: state that a row whose `next_attempt_at` equals the cutoff is claimed (`<=`) and that among rows sharing that instant the lower `id` is claimed first — the tie is now decided rather than left to the planner.
