### Critical: signature does not cover the timestamp, so the documented replay window is unauthenticated
File: `app/webhooks/signing.py` — `sign()` (`mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`)
What is wrong: `sign()` returns a timestamp but MACs only the payload, while `docs/webhooks.md` tells integrators the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed".
What breaks in production: an attacker who captures one delivery can replay it forever by rewriting the unauthenticated `X-Acme-Timestamp` header to `now` — the signature still verifies, so the replay defence every customer was told to implement is void.
Fix: make the signed string the documented one — `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact bytes sent on the wire (see the next finding), and change `verify(secret, payload, signature)` to `verify(secret, body: bytes, timestamp: str, signature: str)` so the caller must supply the timestamp it received rather than letting `verify` mint a fresh one. Preserve the behaviour the current code has that the fix must not delete: `sign()` must still return `(timestamp, "sha256="+hex)` and `SIGNATURE_HEADER`/`TIMESTAMP_HEADER` must keep their current names and values, because `docs/webhooks.md` publishes them. Pair the sides: the ALLOW case is `verify(SECRET, body, ts, sig)` returning `True` for the `(ts, sig)` that `sign` just produced; the DENY case is the same `body`/`sig` presented with a different `ts` returning `False`. Red-prove each clause separately by execution: (i) drop `timestamp` from the MAC input and confirm the deny case flips to `True`; (ii) mutate one byte of `body` and confirm the allow case flips to `False`; (iii) mutate the separator from `.` to `:` and confirm the allow case flips to `False` — three mutations, three distinct failing assertions. Fail loudly rather than silently when the check cannot run: `verify` must raise (not return `False`) when `secret` is empty or `timestamp` is not a decimal string, so "could not check" is not spelled the same as "signature bad", and the delivery path must treat that raise as a configuration error. Boundary and tie: state in the docstring and the docs that the accepted skew is `abs(now - ts) <= 300` — 300 exactly is accepted, 301 is rejected — and that two deliveries sharing a timestamp are independent because the body differs.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once()` (`sign(...)` over `serialize(payload)` vs `client.post(..., json=delivery.payload)`)
What is wrong: `signing.serialize()` produces `json.dumps(payload, sort_keys=True)` while httpx re-serializes `json=delivery.payload` with insertion order and its own separators, so the HMAC is computed over a different byte string than the request body the receiver hashes.
What breaks in production: every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest and rejects every delivery, which the sender then retries five times — a total-path failure across all endpoints that no test in this diff can see (R40: producer and consumer shapes each verified in isolation).
Fix: serialize once and send the exact bytes — `body = serialize(payload).encode()`, `ts, signature = sign(secret, body)`, `await client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` — and change `sign`/`verify` to take `bytes` so it is structurally impossible to sign a value that was not the one transmitted. Do not fix this by deleting `sort_keys=True` and hoping the two serializers agree; the property the fix must preserve is that exactly one serialization exists in the codebase, and `serialize()` is that one. Pair the sides: the ALLOW case is a round-trip test that feeds the actual captured request body from `httpx.MockTransport` into the actual `signing.verify` and asserts `True`; the DENY case is the same test with one byte of the captured body altered asserting `False`. Red-prove each clause by execution: (i) revert `content=body` to `json=delivery.payload` and confirm the round-trip assertion reddens for a payload whose keys are not already sorted (e.g. `{"b": 2, "a": 1}` — the current test's `{"id","type","amount_cents"}` payload is insertion-ordered and would NOT redden, which is why the fixture must be chosen unsorted); (ii) drop `Content-Type` and confirm a separate header assertion reddens. Fail loudly: if `serialize()` raises on a non-JSON-serializable payload, `deliver()` must mark the row `failed_permanent` with that reason rather than letting the coroutine die inside `asyncio.gather`. Boundary and tie: the empty payload `{}` must sign and verify to `"{}"` — pin it, since it is the value where an "if payload" shortcut would silently send an empty body.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: `app/webhooks/signing.py` — `new_signing_secret()` (`random.choice(_ALPHABET)`)
What is wrong: `random` is a Mersenne Twister seeded from a small, observable state and is not a CSPRNG, yet its output is the HMAC key that authenticates every webhook we send.
What breaks in production: an attacker who observes enough generator output (or who can reason about process start time) recovers the internal state and derives other tenants' signing secrets, letting them forge deliveries that every customer's verifier accepts as genuinely ours.
Fix: replace with `secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, delete the `random`/`string`/`_ALPHABET` imports so the weak primitive cannot be re-reached) and rename the constant to reflect what it now measures — `SECRET_BYTES = 32` becomes a true byte count. Preserve the two properties the current code has that customers depend on: the `whsec_` prefix and a stable, documented length. Pair the sides: the ALLOW case asserts a freshly generated secret still starts with `SECRET_PREFIX` and is accepted by `sign`/`verify` end to end; the DENY case asserts two successive calls differ and that 1000 successive calls yield 1000 distinct values. Red-prove each clause by execution: (i) stub `new_signing_secret` to return a constant and confirm the distinctness assertion reddens; (ii) drop the prefix and confirm the prefix assertion reddens. Fail loudly: nothing here can silently "not run" except an import failure, so pin `import secrets` at module scope rather than inside the function, where an ImportError would surface only on first endpoint creation. Boundary and tie: `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which is false for `token_urlsafe(32)` (43 chars) — update that assertion in the same commit to `len(secret) >= len(SECRET_PREFIX) + 32`, and say in the fix which side of the bound is accepted.

### Critical: `verify()` compares HMACs with `==`
File: `app/webhooks/signing.py` — `verify()` (`return expected == signature`)
What is wrong: the MAC comparison uses Python's short-circuiting `==` instead of a constant-time comparison (RS1).
What breaks in production: an attacker who can submit candidate signatures to any code path that calls `verify` learns the correct digest byte by byte from response-time differences and then forges a valid signature.
Fix: `return hmac.compare_digest(expected, signature)`, with `signature` coerced through an explicit `isinstance(signature, str)` guard first. Cross-cutting: `verify()` is the only credential-shaped equality in the diff — I checked every `==`/`!=` on the added lines and no other compares a secret, digest, or token — so this one site is the complete member set. Pair the sides: the ALLOW case is `verify` returning `True` for a signature `sign` just produced (the existing `test_verify_accepts_signature_produced_by_sign` covers it — keep it); the DENY case is the existing wrong-secret test plus a new one for a correct-length-but-wrong-byte signature, since `compare_digest` and `==` differ only in timing and a length-mismatch fixture proves nothing about the constant-time property. Red-prove by execution, one mutation per clause: (i) revert to `==` and confirm a `grep`-based lint assertion (or a `dis`-based check that `compare_digest` appears in `verify.__code__.co_names`) reddens — a timing assertion is not reliably red-provable in CI and must not be the oracle; (ii) remove the `isinstance` guard and confirm the `verify(SECRET, payload, None)` case reddens on the raised `TypeError`. Fail loudly: a non-`str` `signature` must return `False` explicitly rather than propagating `compare_digest`'s `TypeError` into the caller, and an empty `secret` must raise — "no secret configured" must not be spelled the same as "signature did not match". Boundary and tie: signatures of unequal length return `False` (`compare_digest` is only constant-time for equal lengths — this is accepted and must be stated), and a signature equal to `expected` including the `sha256=` prefix is the single accepting value.

### Critical: the signing secret is returned by the endpoint-list API
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()` (`"signing_secret": self.signing_secret`)
What is wrong: `to_dict()` includes the raw HMAC key and is used by both `POST /v1/settings/webhook-endpoints` and `GET /v1/settings/webhook-endpoints`, directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: any actor with a read-only session or a leaked read-scoped API key for the org retrieves every endpoint's signing secret and can forge deliveries indefinitely, and the secret is now duplicated into every log, proxy cache, and browser history entry that touched the list response (RS4: a committed/served credential is compromised, not merely exposed).
Fix: remove `signing_secret` from `to_dict()` and return it exactly once, from the create handler only, by constructing the response there as `{**endpoint.to_dict(), "signing_secret": secret}` using the local variable — so the model can never leak it again regardless of which route calls `to_dict()`. Cross-cutting: `WebhookDelivery.to_dict()` was checked for the same pattern and does not expose `payload` or `response_body`, so the endpoint model is the only miss. The behaviour the fix must preserve is that the create response still carries the secret — deleting it there would make the documented "store it in your own secret manager" instruction impossible to follow. Pair the sides: the ALLOW case asserts `POST` response JSON contains `signing_secret`; the DENY case asserts `GET` response JSON for the same endpoint does not contain the key at all (assert on key absence, not on a falsy value). Red-prove each by execution: (i) re-add `signing_secret` to `to_dict()` and confirm the `GET` key-absence assertion reddens; (ii) drop the merge in the create handler and confirm the `POST` assertion reddens. Fail loudly: if the create handler cannot produce a secret, it must 500 rather than return an endpoint row with a missing key, because a silently secret-less endpoint would sign with `None`. Boundary and tie: the empty endpoint list `[]` must also be asserted to contain no `signing_secret` substring anywhere in the serialized body.

### Critical: `list_deliveries` has no organization scoping — cross-tenant read
File: `app/api/routes/settings.py` — `list_deliveries()` (`.filter(WebhookDelivery.endpoint_id == endpoint_id)`)
What is wrong: the query filters on the caller-supplied `endpoint_id` alone and never joins to `WebhookEndpoint.org_id == user.org_id`, so authorization is missing entirely on this route.
What breaks in production: any authenticated user enumerates `endpoint_id` and reads another organization's delivery history — event types, event ids, HTTP response codes and delivery schedule for their billing events — a direct cross-tenant data leak.
Fix: join and filter — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the route does not confirm the existence of other orgs' endpoint ids. Cross-cutting verification: I checked the other two new routes against this pattern — `create_webhook_endpoint` sets `org_id=user.org_id` from the session and `list_webhook_endpoints` filters `org_id == user.org_id`, so `list_deliveries` is the single missed location, and the codebase already contains the shared path this route should reuse: `list_api_keys` in the same file demonstrates the `filter(<Model>.org_id == user.org_id)` idiom that the new handler dropped (R3 — the pattern was propagated to two of three new sites). Pair the sides: the ALLOW case is org A's user reading org A's endpoint and receiving its deliveries; the DENY case is org B's user requesting org A's `endpoint_id` and receiving 404 with an empty body. Red-prove each by execution: (i) remove the `org_id` predicate and confirm the DENY test reddens on the returned rows, not merely on the status (RT8 — assert the row list is empty, not just the code); (ii) remove the `endpoint_id` predicate and confirm the ALLOW test reddens because it now sees a second endpoint's deliveries. Fail loudly: when `user.org_id` is `None` the handler must raise rather than filter on `None` and match nothing-or-everything. Boundary and tie: an endpoint that exists but belongs to no org, and an endpoint id that does not exist at all, must both return the same 404 shape so the two are indistinguishable to the caller.

### Critical: endpoint URLs are unvalidated against network destination — SSRF into internal services
File: `app/api/routes/settings.py` — `create_webhook_endpoint()` (`if not parsed.scheme.startswith("http") or not parsed.netloc`) with `app/webhooks/delivery.py` — `run_worker()` (`follow_redirects=True`)
What is wrong: the only check is on the URL's surface notation — a scheme string prefix and a non-empty netloc — with no resolution of where the host actually points, and the delivery client then follows redirects, so a tenant can register `http://169.254.169.254/…` or `http://10.0.0.5:6379/` (or a public URL that 302s to one) and the worker will POST attacker-controlled JSON to it from inside the network perimeter (R47: judging the notation rather than the resolved destination; every unenumerated spelling — decimal IP, IPv6-mapped, DNS name resolving to RFC1918, redirect — is a bypass).
What breaks in production: an authenticated tenant turns our delivery worker into a request forwarder against cloud metadata endpoints and internal HTTP services, and reads back a coarse oracle through the `response_status` field exposed by `GET .../deliveries`.
Fix: replace the notation check with a destination check — require `parsed.scheme == "https"` exactly (the docs already promise https-only, and `startswith("http")` today admits plain `http` and any scheme literally beginning with those letters), resolve the hostname with `socket.getaddrinfo` at registration time, reject when any resolved address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`, set `follow_redirects=False` on the `AsyncClient`, and re-run the same address check against the connected peer at request time (pin via a custom transport or an `httpx` event hook) so DNS rebinding between registration and delivery does not defeat it. Under R49 declare the class explicitly in a comment on the helper: registration-time resolution is a *best-effort tripwire* (DNS can change), the request-time peer check is the *enforceable boundary*, and the known residual is a host that is public at connect time and proxied internally. Preserve the feature the fix must not delete: legitimate public HTTPS endpoints, including those behind CDNs with multiple A records, must still register. Pair the sides: the ALLOW case registers `https://hooks.example.com/acme` resolving to a public address and asserts 201; the DENY cases assert 422 for `http://` (scheme), for a host resolving to `127.0.0.1`, and for a host resolving to `169.254.169.254`. Red-prove each clause separately by execution: (i) revert `== "https"` to `startswith("http")` and confirm only the scheme DENY case reddens; (ii) remove the `is_private` term and confirm only the RFC1918 case reddens; (iii) set `follow_redirects=True` and confirm a MockTransport test that 302s to `http://127.0.0.1/` reddens on the recorded final destination. Fail loudly: when `getaddrinfo` raises (NXDOMAIN, resolver down) the handler must return 422 naming the resolution failure — "could not resolve" must not fall through to "allowed". Boundary and tie: `100.64.0.0/10` (carrier-grade NAT) and IPv6 `::ffff:10.0.0.1` are the two boundary forms to pin explicitly, and a host with one public and one private A record must be rejected (any-private, not all-private).

### Critical: `time.sleep()` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver()` (`time.sleep(delay)`)
What is wrong: `deliver` is `async` and is scheduled under `asyncio.gather`, but its retry pause uses the blocking `time.sleep` instead of `await asyncio.sleep`.
What breaks in production: one failing endpoint freezes the entire event loop for up to 2+4+8+16 = 30 seconds per delivery, serializing a 100-item batch into a multi-hour crawl and stalling every other coroutine sharing that loop — including the lock refresh, so the 60-second lock expires and a second worker starts re-delivering the same rows.
Fix: `await asyncio.sleep(delay)`; `asyncio` is already imported at the top of the file, and `import time` becomes unused in `delivery.py` and should be removed so the blocking primitive is not reachable again. Cross-cutting: `time` is also imported in `app/webhooks/signing.py`, where `time.time()` is a non-blocking clock read and must be left alone — this is the R3 case where the same symbol is correct at one site and a defect at the other. Pair the sides: the ALLOW case asserts a successful first-attempt delivery still returns without sleeping at all; the DENY/latency case runs two `deliver()` coroutines that each fail once under `asyncio.gather` and asserts total wall time is under one backoff period rather than two. Red-prove each by execution: (i) restore `time.sleep` and confirm the concurrency assertion reddens because elapsed time roughly doubles; (ii) remove the retry pause entirely and confirm a separate assertion on the observed inter-attempt gap reddens. Do not fix by deleting the pause — the behaviour to preserve is that consecutive attempts to the same endpoint remain spaced by `backoff_for(attempt)`. Fail loudly: if `backoff_for` returns a negative or `NaN` delay the worker must raise rather than sleep zero, so a broken backoff cannot silently become a hot retry loop. Boundary and tie: `attempt == MAX_ATTEMPTS` must not sleep at all before finishing (the current code already returns first — keep and pin that), and two deliveries whose delays are equal must be allowed to run concurrently, not serially.

### Critical: ORM rows are used after their session closes, so no delivery can complete
File: `app/webhooks/delivery.py` — `_claim_batch()` (`return rows` outside the `with`) and `deliver()` (`endpoint` read after `session_scope()` exits)
What is wrong: both functions return or retain SQLAlchemy instances past the end of their `session_scope()` block and then read attributes (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret`, `endpoint.url`) on detached, expired-on-commit objects.
What breaks in production: every attribute access raises `DetachedInstanceError`, so no delivery is ever attempted — but `_claim_batch` has already committed `status = "in_flight"`, so the rows are permanently wedged in a non-terminal state that no code path ever resets (R38 clause 1), and each poll claims 100 more.
Fix: stop passing ORM entities across session boundaries — have `_claim_batch` return plain value objects built inside the session (`[DeliveryJob(id=r.id, endpoint_id=r.endpoint_id, payload=r.payload, attempts=r.attempts) for r in rows]`, a frozen dataclass) and have `deliver` load `endpoint.url`/`endpoint.signing_secret` into locals inside its own `with session_scope()` block before the first `await`. In the same change give the wedge an exit: add a reaper that returns rows to `pending` when `status = 'in_flight' AND updated_at < now() - interval '10 minutes'`, and set `updated_at` at claim time so the reaper has a clock to read. Preserve what the current shape gives you and the fix must not lose: the claim must stay a single committed transaction so two workers cannot claim the same row. Pair the sides: the ALLOW case is an integration test against a real session (not `FakeDelivery`) asserting a claimed job delivers and lands `delivered`; the DENY case asserts a row left `in_flight` with a stale `updated_at` is returned to `pending` by the reaper and that a fresh `in_flight` row is not. Red-prove each clause by execution: (i) revert `_claim_batch` to returning ORM rows and confirm the integration ALLOW test reddens with `DetachedInstanceError`; (ii) remove the reaper's age predicate and confirm the "fresh in_flight row is untouched" assertion reddens; (iii) remove the `updated_at` write at claim time and confirm the reaper test reddens on an unbounded reclaim. Fail loudly: `_claim_batch` must raise if the session is already closed rather than returning an empty list, so "claimed nothing" is distinguishable from "could not claim". Boundary and tie: a row whose `updated_at` is exactly the 10-minute threshold is reclaimed (`<=`), and two workers reclaiming the same stale row must be resolved by `SELECT ... FOR UPDATE SKIP LOCKED` so exactly one wins.

### Critical: the migration's CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES` / `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the SQL enumerates `'failed'` while the model constant and the only writer use `'failed_permanent'` — the same enum is hardcoded in three places and propagated to two of them (R2/R3).
What breaks in production: the first delivery to exhaust its retries raises a `CheckViolation`, the `_finish` transaction rolls back, and the row is left in `in_flight` forever with no record of the failure — so permanently-failed webhooks are invisible to both operators and the deliveries API.
Fix: change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `models.STATUSES` the single source by deriving the column from it (`Column(Enum(*STATUSES, name="webhook_delivery_status"))` or, if a text column is preferred, a startup assertion that the DB constraint's members equal `STATUSES`). Cross-cutting: the third and fourth copies of these literals are `_claim_batch`'s `status == "pending"` filter and `_finish`'s call sites — route both through `STATUSES`-derived names in the same change, otherwise the next value added drifts again. Pair the sides: the ALLOW case inserts one row per member of `STATUSES` against a real migrated database and asserts all four succeed; the DENY case inserts `'failed'` and asserts the constraint rejects it. Red-prove each by execution: (i) revert the SQL to `'failed'` and confirm the ALLOW loop reddens on `failed_permanent`; (ii) drop the CHECK entirely and confirm the DENY case reddens. Fail loudly: the startup assertion must abort the process when it cannot read the constraint definition, rather than logging and continuing — an unverifiable constraint must not report as verified. Boundary and tie: state that the empty string and `NULL` are both rejected by the `NOT NULL` plus CHECK pair, and that the assertion compares sets, so member order is not a difference.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint for a single `event_id`, but the index permits only one delivery row per event across all endpoints.
What breaks in production: the second endpoint any org registers causes `session.add_all(rows)` to raise a unique violation, and because `dispatch()` swallows that exception the event is delivered to *neither* endpoint — a silent, total loss of webhooks for every multi-endpoint customer.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is the real idempotency key, and it is what makes the documented "deduplicate on `event_id`" advice meaningful per endpoint. Add the covering index the worker's query actually needs at the same time: `CREATE INDEX idx_webhook_deliveries_claim ON webhook_deliveries (status, next_attempt_at);` (the existing `idx_webhook_deliveries_status` does not serve the `ORDER BY next_attempt_at` in `_claim_batch`). Preserve the property the current index was presumably reaching for: a repeated `enqueue_for_event` for the same event must still not create a duplicate row for the same endpoint — the composite index keeps that. Pair the sides: the ALLOW case enqueues one event for an org with two active endpoints and asserts exactly two rows exist; the DENY case enqueues the same `(endpoint_id, event_id)` twice and asserts the second is rejected. Red-prove each by execution: (i) restore the single-column unique index and confirm the two-endpoint ALLOW case reddens on the integrity error; (ii) drop the unique index and confirm the duplicate DENY case reddens with two rows. Fail loudly: `enqueue_for_event` must distinguish "duplicate, already enqueued" (swallow, return the existing count) from every other `IntegrityError` (re-raise) — catching broadly here would re-create the silent loss this finding is about. Boundary and tie: an org with zero active endpoints must insert zero rows and return `0` without error, and two endpoints of *different* orgs subscribed to the same `event_id` must both get a row.

### Critical: the dispatcher swallows every enqueue failure, outside the event's transaction
File: `app/events/dispatcher.py` — `dispatch()` (`except Exception as exc: log.warning("webhook enqueue failed …")`)
What is wrong: the webhook enqueue runs after the event transaction has already committed and its every failure is caught, logged at WARNING, and discarded — there is no retry, no outbox row, and no signal to the caller (R9: fire-and-forget across a closed transaction boundary).
What breaks in production: any transient database error, or the unique-violation above, permanently loses the webhook for that event while `dispatch()` returns the event id as if it had succeeded — making the documented "delivery is at-least-once" guarantee false, with no record anywhere that a delivery was owed.
Fix: move the enqueue inside the same `session_scope()` that persists the `Event`, using the same `session`, so the delivery rows and the event commit or roll back together — change `enqueue_for_event` to accept an optional `session` and only open its own when none is supplied. Where an in-transaction enqueue is not acceptable, the equivalent is a transactional outbox: insert an `outbox` row in the event's transaction and let a separate worker fan it out. Preserve the property the `try` was protecting: a webhook problem must not lose the *event*, so the enqueue must be limited to row inserts with no network I/O (it already is) and any remaining catch must re-raise after recording a durable row rather than only logging. Under R49, if fan-out is deliberately best-effort, say so in `docs/webhooks.md` and delete the "at-least-once" claim; leaving both is the finding. Pair the sides: the ALLOW case asserts a successful dispatch commits both the `Event` row and its `WebhookDelivery` rows; the DENY case injects a failure in the delivery insert and asserts neither the event nor the delivery rows are present afterwards (assert the rows, not just the raised exception — RT8). Red-prove each by execution: (i) restore the post-commit `try/except` and confirm the DENY case reddens because the `Event` row survives alone; (ii) remove the delivery insert and confirm the ALLOW case reddens on the missing rows. Fail loudly: the enqueue must raise a named exception on an unexpected error so the caller's transaction aborts — "logged a warning" must not be the same outcome as "nothing was wrong". Boundary and tie: an event type in `WEBHOOK_EVENT_TYPES` with zero subscribed endpoints commits the event and zero delivery rows, which is a success, not a failure.

### Critical: the signing test never verifies the signature against the body it was sent with
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload()` (`assert captured["headers"][signing.SIGNATURE_HEADER].startswith("sha256=")`)
What is wrong: the test that names itself "posts the signed payload" asserts only that the header exists and has the right prefix — it never recomputes the HMAC over `captured["body"]`, so the production signature primitive is present in the call path but its output is never checked against the transmitted bytes (RT5/RT1(c),(d): the assertion compares the subject's output to a shape, not to an independently computed expected value).
What breaks in production: this is exactly the test that should have caught the signed-bytes-vs-sent-bytes divergence above, and it is green — a reviewer reads it as proof that signing works and ships a feature no customer can verify.
Fix: add `assert signing.verify(SECRET, captured["body"], captured["headers"][signing.TIMESTAMP_HEADER], captured["headers"][signing.SIGNATURE_HEADER])` — feeding the *actual* captured request bytes through the *actual* production verifier — and independently, compute the expected digest in the test with a literal `hmac.new(SECRET.encode(), b'{"ts"}.{body}', hashlib.sha256).hexdigest()` so at least one assertion compares against a value written by hand rather than derived from the subject. ### Major: the dispatch lock is not atomic, is released by whoever finishes first, and expires mid-batch
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
