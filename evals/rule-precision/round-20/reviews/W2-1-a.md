### Critical: the transmitted body is not the bytes that were signed, and the timestamp is not covered by the MAC
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, and `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` computes the HMAC over `json.dumps(payload, sort_keys=True)` while `send_once()` transmits `client.post(..., json=delivery.payload)`, which re-serializes with insertion order (and, on httpx ≥ 0.27, compact separators), and the timestamp `sign()` returns is put in a header it never feeds into the MAC — whereas `docs/webhooks.md` tells every customer to HMAC `"{timestamp}.{raw_request_body}"`.
What breaks in production: every receiver that implements the documented scheme computes a different digest and rejects 100% of deliveries, and any receiver that instead ignores the timestamp has no replay protection at all because an attacker can rewrite `X-Acme-Timestamp` freely without invalidating the signature — the "five minute window" the docs call the anti-replay control is unauthenticated.
Fix: make the signed bytes and the sent bytes the same object. In `signing.py`, change `sign(secret, payload)` to `sign(secret, body: bytes) -> tuple[str, str]` that computes `timestamp = str(int(time.time()))` and `mac = hmac.new(secret.encode(), b"%s.%s" % (timestamp.encode(), body), hashlib.sha256)`; keep `serialize()` as the single canonical encoder (`json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`) and have `send_once()` call `body = serialize(delivery.payload)`, then `client.post(endpoint.url, content=body, headers={...})` — never `json=`, which is what silently re-encodes. `verify()` takes the same `body` plus the received timestamp and rejects when `abs(now - int(timestamp)) > 300`. **Preserve** the two behaviours the current code does get right: the `sha256=` prefix on the header value and the sorted-key canonicalization (do not "fix" this by removing the prefix or by dropping canonicalization and signing whatever bytes arrive). **Allow side**: pin that a receiver computing `HMAC(secret, f"{ts}.{raw_body}")` over the exact bytes captured by `MockTransport` still verifies, and that a payload whose keys are supplied out of order (`{"b":2,"a":1}`) still produces a byte-identical body and digest to `{"a":1,"b":2}`. **Red-prove each clause separately, by execution**: (i) revert `content=body` to `json=payload` and observe the receiver-side verification assertion go red; (ii) drop the timestamp from the MAC input and observe a replay test — same body, `X-Acme-Timestamp` shifted by 600s — go red on the skew assertion and only that one; (iii) change `separators` and observe the byte-identity assertion go red. Three mutations, three distinct red assertions. **Fail loudly**: `verify()` must raise (not return `False`) when the timestamp header is absent or non-numeric, so "could not check" is spelled differently from "signature mismatch"; `send_once()` must raise if `serialize()` fails rather than posting an unsigned body. **Boundary and tie**: a timestamp exactly 300s old is accepted (`> 300` rejects), state that in `docs/webhooks.md`, and two deliveries signed in the same clock second produce different digests only if their bodies differ — which is intended, since `event_id` and not the signature is the dedup key.

### Critical: `UNIQUE INDEX` on `event_id` alone makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event()` in `app/webhooks/delivery.py` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the unique index permits only one row per `event_id` across the whole table.
What breaks in production: the first org that registers two endpoints gets an `IntegrityError` on `session.add_all(rows)` — swallowed by the `except Exception` in `app/events/dispatcher.py`, so the whole batch is rolled back and *neither* endpoint receives the event, silently, for every event.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is the real idempotency key, since "at-least-once, deduplicate on `event_id`" in `docs/webhooks.md` is a statement about one receiver, not about the table. **Preserve** the idempotency guarantee the current index was reaching for: a redelivery of the same event to the same endpoint must still be rejected, so do not fix this by deleting the uniqueness. **Allow side**: pin that inserting the same `event_id` for two *different* `endpoint_id`s succeeds and yields two rows. **Red-prove each clause separately, by execution**: (i) insert the same `(endpoint_id, event_id)` twice and observe the integrity assertion go red without the index; (ii) revert to the single-column index and observe the two-endpoint fan-out test go red on the row-count assertion. **Fail loudly**: `enqueue_for_event()` must not swallow the constraint violation — see the dispatcher finding below; a duplicate must be an explicit `ON CONFLICT DO NOTHING` with the skip counted, not an exception routed to `log.warning`. **Boundary and tie**: an event matching zero endpoints inserts zero rows and returns `0` — that is success, not an error; two endpoints of the *same* org both subscribed to the type each get exactly one row.

### Critical: the migration's `CHECK` constraint rejects the only failure status the code writes
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: `app/webhooks/delivery.py:_finish()` writes `"failed_permanent"` (and `app/webhooks/models.py:STATUSES` declares `"failed_permanent"`), a spelling the constraint does not allow — a producer/consumer enum-spelling divergence of exactly the R40 shape, invisible to the tests because none of them touch the database.
What breaks in production: every exhausted delivery raises a constraint violation inside `_finish()`, so the row never leaves `in_flight`, the attempt count is never recorded, and the worker's `asyncio.gather` propagates the error out of `run_worker`'s try block.
Fix: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `app/webhooks/models.py:STATUSES` the single source by asserting the two agree in a test that reads the DB catalog (`pg_get_constraintdef`) and compares against `STATUSES` — the diff already declares `STATUSES` as the intended enumeration and nothing consumes it, which is the shared path this migration reimplements as a literal list. **Preserve** the constraint itself: do not fix this by dropping the `CHECK`, which is what makes a typo in `_finish()` visible at all. **Allow side**: pin that a row written with each of the four `STATUSES` members commits successfully. **Red-prove each clause separately, by execution**: (i) add a fifth member to `STATUSES` without touching the migration and observe the catalog-comparison test go red naming the extra member; (ii) revert the constraint to `'failed'` and observe an end-to-end "delivery exhausts its attempts" test go red on the persisted-status assertion, not on the count. **Fail loudly**: when the catalog query returns no such constraint (migration not applied, non-Postgres backend), the test must fail with "constraint not found", never skip — "examined nothing" must not read as green. **Boundary and tie**: `status` is `String(20)` in the model and `TEXT` in the migration; `failed_permanent` is 16 characters, so state that 20 is the cap and that any future member longer than 20 truncates on one side and not the other.

### Critical: `GET /webhook-endpoints/{id}/deliveries` has no tenancy predicate
File: `app/api/routes/settings.py` — `list_deliveries()`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id`, with no check that the endpoint belongs to `user.org_id`, while both sibling routes in the same file (`list_api_keys`, `list_webhook_endpoints`) do filter on `org_id` — the pattern is present in the diff and this one call site skipped it.
What breaks in production: any authenticated user can enumerate `endpoint_id` and read another organization's delivery history — event ids, event types, and delivery outcomes — and `docs/webhooks.md` states the endpoint returns attempts "for an endpoint belonging to your organization", so the control the documentation asserts does not exist (R49: claim stronger than the implementation).
Fix: resolve the endpoint first and scope it, then query its deliveries: `endpoint = session.query(webhook_models.WebhookEndpoint).filter_by(id=endpoint_id, org_id=user.org_id).one_or_none()`; `if endpoint is None: raise HTTPException(status_code=404, detail="endpoint not found")` — 404 rather than 403, so the response does not disclose whether the id exists in another org. **Preserve** the ordering and `limit` behaviour the route already has. **Allow side**: pin that the owning org still receives its rows in `created_at desc` order — a fix that always 404s satisfies the deny side and breaks the feature. **Red-prove each clause separately, by execution**: (i) an RT8-shaped cross-tenant test asserting both the 404 status *and* that the response body contains none of the foreign org's delivery ids, mutated by removing the `org_id` filter — red on the body assertion, which is the one the status-only version would miss; (ii) a same-org test mutated by hardcoding the 404 — red on the row-count assertion. **Fail loudly**: when `user.org_id` is `None` the route must deny, not query with `org_id IS NULL`. **Boundary and tie**: an endpoint that exists but has zero deliveries returns `[]` with 200, distinct from the 404 of an endpoint the caller does not own — and that distinction is exactly what must not leak, so assert both paths.

### Critical: the signing secret is returned on every endpoint read, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, consumed by `app/api/routes/settings.py:list_webhook_endpoints()`
What is wrong: `to_dict()` includes `"signing_secret"`, and `list_webhook_endpoints()` returns `[e.to_dict() for e in endpoints]`, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the shared-secret that authenticates every outbound webhook is served on an ordinary `GET` to anyone holding a session for the org — so it lands in browser history, proxy logs, and any client-side cache — and the documented security property customers rely on when deciding not to store it is false.
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` (the shared path both routes already use — this is the single place to change, not two), and have `create_webhook_endpoint()` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally-held value so the secret is disclosed exactly once, at creation. Add a `secret_last4`-style non-reversible hint to `to_dict()` if the UI needs to identify a secret. **Preserve** the create-time disclosure — the customer cannot use the feature without receiving the secret once, so do not fix this by removing it from both responses. **Allow side**: pin that the 201 response from `POST /webhook-endpoints` still contains a `signing_secret` starting with `whsec_`. **Red-prove each clause separately, by execution**: (i) re-add `"signing_secret"` to `to_dict()` and observe the list-route test go red on an assertion that `"signing_secret" not in body[0]`; (ii) drop the key from the create route's response and observe the create-route test go red. **Fail loudly**: the list route must not silently emit an endpoint whose secret column is unreadable — a missing secret at create time must raise, not return an endpoint with no usable secret. **Boundary and tie**: an org with zero endpoints returns `[]`, and two endpoints created in the same request second must each get a distinct secret — assert inequality, since the generator finding below makes that non-obvious.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, which draws from the Mersenne Twister — a deterministic generator whose internal state is recoverable from roughly 624 observed outputs and which is seeded predictably enough to be brute-forced.
What breaks in production: an attacker who registers a handful of their own endpoints (each disclosing its secret, per the previous finding) can recover the generator state and derive the signing secret of every endpoint created near it, then forge signed events into other organizations' systems — the signature stops being an authentication control.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and import `secrets`; delete the now-unused `random`, `string`, and `_ALPHABET`. Rename `SECRET_BYTES = 32` to mean what it says — `token_urlsafe(32)` consumes 32 bytes of entropy and emits 43 characters — and update `tests/webhooks/test_delivery.py:test_new_signing_secret_has_prefix_and_length`, which currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` and so encodes the char-count confusion. All existing secrets generated by the old code are compromised and must be rotated as part of this change, with the rotation window documented. **Preserve** the `whsec_` prefix and the property that the secret is URL/header-safe. **Allow side**: pin that a rotated endpoint keeps delivering — an old-secret delivery in flight during rotation must be signed with the secret the receiver is told about, so state the cutover explicitly. **Red-prove each clause separately, by execution**: (i) monkeypatch `secrets.token_urlsafe` to a constant and observe a "two consecutive secrets differ" assertion go red; (ii) reintroduce `random.seed(0)` before generation and observe a determinism assertion — same seed, same output — go red once `secrets` is in place, proving the test discriminates the generator rather than the length; (iii) shorten `SECRET_BYTES` to 4 and observe the minimum-entropy assertion go red. **Fail loudly**: if the platform's entropy source is unavailable, `secrets` raises — do not wrap it in a fallback to `random`. **Boundary and tie**: state the minimum accepted secret length at verification time (reject anything shorter than the `whsec_` prefix plus 43 chars) and what happens to an endpoint whose stored secret predates the change — it must be rotated, not silently accepted.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`
What is wrong: `verify()` compares the recomputed digest with `expected == signature`, an early-exit byte comparison on a credential (RS1).
What breaks in production: `verify()` is the reference implementation this repo ships and the one any inbound-webhook path would reuse, so a caller who can submit candidate signatures learns the correct digest byte by byte from response-time differences and forges a valid signature without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` of equal construction so the comparison does not leak on type. **Preserve** the `sha256=` prefix handling — compare the full prefixed strings, or strip the prefix on both sides before comparing, but do not fix this by comparing only the hex tail. **Allow side**: pin that a signature produced by `sign()` for the same secret and body still verifies `True` — a `return False` satisfies constant-time and every other clause. **Red-prove each clause separately, by execution**: (i) revert to `==` and observe a lint/AST assertion that `verify` contains no bare equality on the digest go red; (ii) flip `compare_digest` to `not compare_digest` and observe the accept-path test go red; (iii) truncate `expected` by one character and observe the reject-path test go red. **Fail loudly**: a `signature` that is `None` or not a string must raise a `TypeError` that names the input, not fall through to `False` — "malformed header" and "wrong signature" are different outcomes and the caller must be able to tell them apart. **Boundary and tie**: a signature of the correct length but differing in the final byte must be rejected, and `compare_digest` on operands of different lengths returns `False` without leaking the length — say so, because that is the case a hand-rolled loop gets wrong.

### Critical: `time.sleep()` inside an `async def` blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver()`, the `time.sleep(delay)` at the end of the retry loop
What is wrong: `deliver()` is a coroutine gathered across the whole batch, but it backs off with the blocking `time.sleep` rather than `await asyncio.sleep`, and `time` is imported at the top of the file for exactly this.
What breaks in production: one endpoint that times out stalls the entire worker process for up to 2+4+8+16 = 30 seconds per delivery — with a batch of 100 gathered coroutines the "concurrent" fan-out serializes into roughly 50 minutes, during which the 60-second Redis lock TTL expires and a second worker claims and re-delivers the same rows.
Fix: `await asyncio.sleep(delay)` (`asyncio` is already imported), and cap total in-process retry time by moving the backoff off the request path entirely: on a retryable failure, write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next `_claim_batch` pick it up — which also fixes the loss of retry state on process restart. **Preserve** the retry budget and the exponential shape the docs and `test_backoff_grows_exponentially` pin; do not fix this by reducing `MAX_ATTEMPTS` or flattening the backoff. **Allow side**: pin that a delivery which succeeds on its first attempt performs exactly one POST and never sleeps — a fix that always reschedules satisfies the non-blocking clause and destroys throughput. **Red-prove each clause separately, by execution**: (i) restore `time.sleep` and observe an assertion that `deliver()` on a failing endpoint yields control (measured by a concurrently scheduled task making progress within the backoff window) go red; (ii) remove the `next_attempt_at` write and observe the reschedule test go red on the timestamp assertion; (iii) remove the `attempts` write and observe the attempt-count assertion go red. **Fail loudly**: if `backoff_for` returns a non-positive or absurd delay, raise rather than sleeping forever or spinning. **Boundary and tie**: `backoff_for(MAX_ATTEMPTS)` is never used — the row goes terminal at `attempt >= MAX_ATTEMPTS` — so state that attempt 5 is the last POST and that a row whose `next_attempt_at` equals `now` exactly is claimable (`<=` in `_claim_batch`), and that ties on `next_attempt_at` are broken by `id`.

### Critical: outbound delivery is a full SSRF primitive — plaintext schemes accepted, no address filtering, redirects followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint()` URL check; `app/webhooks/delivery.py` — `run_worker()`'s `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the boundary check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://`, admits any scheme merely *prefixed* with `http` (`httpz://`), performs no resolution or address-range check, and the client then follows redirects — so a registered URL can point at `http://169.254.169.254/`, `http://127.0.0.1:6379/`, or a public host that 302s to either (RS3: validation at the boundary, and the redirect makes the check re-derivable after the fact).
What breaks in production: any authenticated customer turns the delivery worker into a proxy that issues authenticated-from-inside-the-VPC requests to cloud metadata and internal services, with the response body persisted into `response_body` and the whole thing signed with a secret they control; separately, accepting `http://` sends customer event payloads in plaintext even though `docs/webhooks.md` says "Only `https://` URLs are accepted".
Fix: validate at the schema level, not in the handler body — put a validator on `EndpointIn.url` that requires `parsed.scheme == "https"` exactly (equality, not `startswith`), requires a non-empty host, rejects userinfo and non-standard ports outside an allowlist, and resolves the host rejecting any result in a private, loopback, link-local, or reserved range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`). Set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with a named detail, because a redirect re-resolves the target after the check passed. Re-resolve and re-check the address at connect time via a custom transport, since DNS can change between registration and delivery. **Preserve** the ability to register a legitimate public HTTPS endpoint, including one behind a CDN with multiple A records. **Allow side**: pin that `https://hooks.example.com/acme` resolving to a public address is accepted at registration and delivered to — a validator that rejects everything satisfies every deny-side clause. **Red-prove each clause separately, by execution**: (i) `http://hooks.example.com` → red on the scheme assertion; (ii) `https://127.0.0.1/x` → red on the address-range assertion; (iii) a `MockTransport` returning a 302 to `http://169.254.169.254/` → red on an assertion that no second request was issued. Three inputs, three distinct assertions. **Fail loudly**: when DNS resolution fails or times out, registration must be rejected with a message naming the resolution failure — an unresolvable host must not be treated as "not private, therefore allowed"; likewise a delivery whose connect-time re-check cannot run must fail the delivery, not skip the check. **Boundary and tie**: state explicitly that `100.64.0.0/10` (CGNAT) and IPv6 unique-local `fc00::/7` are on the deny side, that a host resolving to *both* a public and a private address is denied (any private answer denies), and that port 443 is the default while any other port needs the allowlist.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock()` does `GET` then `SET` then `EXPIRE` as three separate round trips with no `NX`, so two workers passing the `GET` before either `SET`s both believe they hold the lock; and the `finally` deletes the key by name without checking ownership, so a worker whose batch outlived the 60-second TTL deletes the lock a *different* worker has since taken.
What breaks in production: two workers claim overlapping batches and POST the same event to the same endpoint twice with different signatures, and because `_claim_batch` performs no `SELECT ... FOR UPDATE SKIP LOCKED`, the database offers no second line of defence.
Fix: acquire with a single atomic call carrying a unique owner token — `token = secrets.token_hex(16)`; `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script that only deletes when the stored value equals `token`. Independently, make `_claim_batch` correct without the lock by adding `.with_for_update(skip_locked=True)` to the query so correctness does not rest on the lock at all. **Preserve** the single-worker-at-a-time intent and the TTL, so a crashed worker's lock still expires. **Allow side**: pin that a single worker with no contender does acquire the lock and does process its batch — a fix that never acquires satisfies mutual exclusion perfectly. **Red-prove each clause separately, by execution**: (i) revert to `get`-then-`set` and observe a two-task contention test assert that exactly one acquisition succeeded go red; (ii) revert the release to a bare `delete` and observe a test where worker A's lock has expired and worker B holds the key assert `redis.get(LOCK_KEY) == token_b` after A's `finally` go red; (iii) drop `skip_locked` and observe a two-session claim test assert disjoint row sets go red. **Fail loudly**: if Redis is unreachable, `run_worker` must stop and log an error rather than treat a failed `set` as "someone else holds it" and spin silently forever, and must never treat it as "no lock needed". **Boundary and tie**: a batch whose processing time exactly reaches the TTL must renew the lock rather than continue unprotected — state the renewal interval — and when two workers submit `SET NX` in the same millisecond exactly one wins and the loser sleeps `poll_interval`.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch()` sets `row.status = "in_flight"`; `_finish()` is the only exit
What is wrong: `_claim_batch` only ever selects rows with `status == "pending"`, and the only transition out of `in_flight` is `_finish()` on the success or exhaustion path — a worker crash, a container eviction, a `TypeError` from the naive/aware datetime comparison, or the constraint violation described above leaves the row in `in_flight` permanently (R38, non-terminal transient state).
What breaks in production: every delivery interrupted by a deploy is lost silently, forever, with no operator affordance to requeue it and no alert, and the customer's only signal is a webhook that never arrived.
Fix: add a `claimed_at TIMESTAMPTZ` column set when the row moves to `in_flight`, and have `_claim_batch` also select rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`, resetting them to `pending` with `attempts` unchanged; add an operator-facing counter for reclaimed rows so the reset is visible rather than silent. **Preserve** the exactly-one-worker-per-row property — the reclaim must go through the same `FOR UPDATE SKIP LOCKED` claim, not a blind `UPDATE`. **Allow side**: pin that a row claimed 10 seconds ago is *not* reclaimed while its worker is still alive — a reclaim window that is too aggressive turns one lost delivery into a duplicate storm. **Red-prove each clause separately, by execution**: (i) remove the stale-reclaim branch and observe a test that kills a worker mid-delivery and asserts the row returns to `pending` go red; (ii) remove the `attempts`-preservation and observe the attempt-count assertion go red on its own; (iii) remove the counter and observe the observability assertion go red. **Fail loudly**: a row whose `claimed_at` is `NULL` while `status = 'in_flight'` is corrupt state and must raise a named error, not be silently reclaimed or silently skipped. **Boundary and tie**: a row whose `claimed_at` is exactly 5 minutes old is reclaimed (`<` on `now() - interval`, so state which side), and if two workers race to reclaim the same stale row, `SKIP LOCKED` gives it to exactly one.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returns `rows` outside the `with session_scope()` block; `deliver()` reads `endpoint.signing_secret` / `endpoint.url` and `delivery.attempts` / `.payload` / `.id` after their sessions closed
What is wrong: both functions load ORM objects inside a `session_scope()` context and then hand them to code that runs after the context exits — with SQLAlchemy's default `expire_on_commit=True`, every attribute access on those detached instances raises `DetachedInstanceError`. This is grounded on the `session_scope()` used elsewhere in the diff committing on exit (`app/events/dispatcher.py:dispatch` reads `row.id` only *inside* the block, and `_finish()` relies on commit-on-exit for its mutations to persist); if `session_scope` sets `expire_on_commit=False`, this reduces to a staleness rather than a crash — say which, since the diff does not contain `app/db`.
What breaks in production: the worker raises on the first delivery of the first batch, `asyncio.gather` propagates out of the `try` in `run_worker`, and no webhook is ever delivered.
Fix: stop passing ORM entities across the session boundary. Have `_claim_batch()` return a list of plain dataclasses (`id`, `endpoint_id`, `payload`, `attempts`) built inside the session, and have `deliver()` load the endpoint's `url` and `signing_secret` into locals inside its own session block before the request. Note the diff already establishes the correct shape one function away — `dispatch()` in `app/events/dispatcher.py` extracts `event_id = row.id` inside the block and uses the scalar outside — so this is the existing in-repo pattern, not a new one. **Preserve** the batching and the `in_flight` claim; do not fix this by widening the session to span the HTTP requests, which would hold a DB connection open for the full 30-second timeout per delivery. **Allow side**: pin that a batch of two rows still yields two POSTs with the correct per-endpoint secrets. **Red-prove each clause separately, by execution**: (i) return the ORM rows instead of the dataclasses and observe an attribute-access assertion after session close go red; (ii) move the endpoint load outside its session block and observe the same for the endpoint; (iii) widen the session across the POST and observe a connection-hold-time assertion go red. **Fail loudly**: `session.get(m.WebhookEndpoint, delivery.endpoint_id)` returning `None` — an endpoint deleted between enqueue and delivery — must raise a named error and mark the delivery terminal, not `AttributeError` on `endpoint.signing_secret`; the same missing-row check is absent in `_finish()`, which does `row = session.get(...)` then `row.status = status` with no `None` guard. Both call sites need it.

### Major: retry state is never persisted, so `next_attempt_at` and `attempts` are meaningless
File: `app/webhooks/delivery.py` — `deliver()`'s `while True` loop and `_finish()`
What is wrong: the retry loop keeps `attempt` in a local variable and only calls `_finish()` on the terminal paths, so `attempts` is written once at the end and `next_attempt_at` is never updated at all after `enqueue_for_event` sets it to the enqueue time.
What breaks in production: a worker restart mid-retry loses the entire retry history — the row is stuck `in_flight` per the finding above, and even after a reclaim the recorded `attempts` is `0`, so the delivery gets a fresh budget of 5 and the endpoint receives up to 10 POSTs of the same event; meanwhile `docs/webhooks.md` promises "at most 5 times" and the deliveries API surfaces a `next_attempt_at` that is always in the past.
Fix: this is discharged by the reschedule-instead-of-sleep fix above — write `attempts` and `next_attempt_at` on *every* attempt, not only the terminal one, and let the claim loop drive the retry.
