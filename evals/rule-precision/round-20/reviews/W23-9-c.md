### Critical: `list_deliveries` has no organization filter — any authenticated user reads any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(...endpoint_id == endpoint_id)` clause
What is wrong: The query scopes only on the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so the path parameter alone selects rows.
What breaks in production: A tenant enumerates integer endpoint ids and reads other tenants' delivery rows — `event_type`, `status`, and (once `response_body` is ever surfaced) the responses of their billing webhooks.
Cross-cutting: this is R3 incomplete propagation of an in-diff pattern. Both siblings in the same file scope get it right — `list_api_keys` filters `ApiKey.org_id == user.org_id` and `list_webhook_endpoints` filters `WebhookEndpoint.org_id == user.org_id`. `list_deliveries` is the only one of the three that omits it, and it is the only one taking a caller-supplied resource id.
Fix: Join and scope in the same statement, and 404 (not 403) on a miss so the endpoint id space stays non-enumerable:
`session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and raise `HTTPException(404)` when the endpoint row does not resolve under the caller's org.
Deny side and allow side, both pinned (Remedy Floor 1): a test where org B requests org A's `endpoint_id` asserts 404 **and** that the returned list is empty — not the status alone (RT8) — and a paired test where the owning org requests its own `endpoint_id` still receives all its rows, so the fix is measured in the direction that gets it reverted.
Red-proof, one mutation per clause, executed (Remedy Floor 2): (i) delete the `org_id` predicate → the cross-org test reds; (ii) delete the join → the owning-org test reds on a wrong row set; run each singly.
Fail loudly (Remedy Floor 3): `user.org_id` being `None` must raise, not degrade to an unfiltered query — assert `user.org_id is not None` before building the statement.
Preserve (Remedy Floor 4): keep the `created_at DESC` ordering and the `limit` behaviour; do not "fix" this by removing the endpoint-scoped route.
Boundary and tie (Remedy Floor 5): an endpoint whose `org_id` equals the caller's is INSIDE (returned); an endpoint that has been reassigned between orgs resolves against its current `org_id`, and a delivery whose endpoint row was cascade-deleted returns no rows rather than an error.

### Critical: the signing secret is returned on every read of the endpoint list
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret"`
What is wrong: `to_dict()` embeds `signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` re-serves the secret on every call.
What breaks in production: The HMAC key is exposed to every principal who can reach the list route and is copied into every proxy log, browser cache, and support screenshot of that response, so any read-scoped token compromise becomes the ability to forge signed events.
This is also R49 (claim stronger than the implementation): `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards, so store it in your own secret manager." That claim is false as written, and it is relied on as a boundary — it is the stated reason a customer is told they need no other protection for the value.
Fix: Remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at that one call site, so exactly one route can emit it. Store the secret hashed or in the secret manager if it is never needed in plaintext server-side; if delivery needs the plaintext, keep the column but never let the serializer reach it.
Allow side (Remedy Floor 1): a test asserts the 201 create response DOES contain `signing_secret` — the feature the fix must not delete — while a test on the list route asserts `"signing_secret" not in body[0]`.
Red-proof (Remedy Floor 2): (i) re-add the key to `to_dict` → the list test reds; (ii) drop the explicit merge in `create_webhook_endpoint` → the create test reds. Two mutations, two different assertions.
Fail loudly (Remedy Floor 3): add a serializer-level assertion that no key in a `to_dict()` result matches `secret|token|key` and let it raise, so a future field added to the model cannot silently re-open this.
Preserve (Remedy Floor 4): do not fix by deleting the list route or by truncating the secret to a prefix — the customer still needs the full value once, at creation.
Boundary and tie (Remedy Floor 5): the create response is the single inclusive point; a re-create or rotate call is on the same side (it emits), every read route is on the other; two endpoints created in the same request each carry their own secret and neither leaks into the other's payload.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, which draws from the Mersenne Twister — a non-cryptographic, fully reconstructible generator — instead of `secrets`.
What breaks in production: An attacker who observes enough output from the same process (or simply brute-forces the seed space) recovers the generator state and derives every signing secret minted by that worker, which forges arbitrary signed webhooks against every customer served by it.
This is R1: the change reimplements secret generation on the wrong primitive while the language ships the correct one; the duplication is itself the security control, so the row's Critical branch applies.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, drop `random`, `string`, and `_ALPHABET`), and rename the constant to reflect what it now measures — `SECRET_BYTES = 32` becomes a true byte count rather than a character count.
Allow side (Remedy Floor 1): pin that a generated secret still round-trips through `sign`/`verify` and still starts with `whsec_`, so the fix is measured on the case that must keep succeeding, not only on entropy.
Red-proof (Remedy Floor 2): (i) replace the body with `SECRET_PREFIX + "a" * 32` → an entropy test asserting 1000 generated secrets are all distinct reds; (ii) drop `SECRET_PREFIX` → the prefix test reds. Note the existing `test_new_signing_secret_has_prefix_and_length` stays GREEN under mutation (i) — see the vacuous-test finding below — so it cannot serve as either proof.
Fail loudly (Remedy Floor 3): if `secrets` cannot supply entropy the call raises; do not wrap it in a `try` that falls back to `random`.
Preserve (Remedy Floor 4): the `whsec_` prefix and the fact that existing stored secrets keep verifying must survive — do not fix this by changing the HMAC algorithm at the same time.
Boundary and tie (Remedy Floor 5): `SECRET_BYTES = 32` is the minimum, not a target; a secret of exactly 32 bytes is accepted, and two endpoints minted in the same microsecond must not collide — assert distinctness across a batch, since that is precisely what the Mersenne Twister does not guarantee.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses Python's short-circuiting `str.__eq__` rather than `hmac.compare_digest`, so comparison time leaks the length of the matching prefix (RS1).
What breaks in production: A caller able to submit candidate signatures against this function recovers a valid signature byte by byte from timing, defeating the signature check entirely; the function is exported and is what any inbound verification path in this service will reach for.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` of equal type first and a `False` return when `signature` is not a `str` (an off-type value must not reach the comparison — RS3's interpreter-sink clause).
Allow side (Remedy Floor 1): the valid-signature case must still return `True` — keep `test_verify_accepts_signature_produced_by_sign` and add one whose expected value is written independently of `sign` (a hard-coded hex digest for a fixed secret and payload), so the allow side is not proven by the subject comparing itself.
Red-proof (Remedy Floor 2): (i) revert to `==` → a test asserting `hmac.compare_digest` is on the call path (monkeypatched spy) reds; (ii) invert the return → the valid-signature test reds; (iii) pass a `dict` as `signature` → the off-type test reds rather than raising `TypeError`. Three clauses, three mutations, run singly.
Fail loudly (Remedy Floor 3): a `None` or non-string `signature`, or a missing header, returns `False` explicitly and logs a counter — "could not compare" must not be spelled the same as "compared and matched".
Preserve (Remedy Floor 4): do not fix by deleting `verify` because nothing in this diff calls it; it is exported and documented.
Boundary and tie (Remedy Floor 5): a signature of the correct length but one differing byte is rejected; a signature of the wrong length is rejected without `compare_digest` raising; the empty string is rejected.

### Critical: the timestamp is not covered by the signature, and the signed bytes are not the bytes sent
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` MACs only `json.dumps(payload, sort_keys=True)` while `docs/webhooks.md` specifies the HMAC of `"{timestamp}.{raw_request_body}"`, and `send_once` transmits `json=delivery.payload` — httpx's own encoder, with different separators and no key sorting — so the receiver's raw body is not the string that was signed.
What breaks in production: Two total-path failures at once — every customer who implements the documented verification rejects 100% of deliveries (R40, producer shape vs strict consumer, with the same team owning both sides and no round-trip test to catch it), and because `X-Acme-Timestamp` is outside the MAC an attacker who captures one request can replay it forever with a rewritten timestamp, which is exactly the defence the docs tell customers the header provides.
Fix: Make the signed bytes and the sent bytes the same object. In `sign`, return `(timestamp, "sha256=" + hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256).hexdigest())` where `body` is a `str` parameter supplied by the caller, not a dict re-serialized inside. In `send_once`, compute `body = serialize(delivery.payload)` once, call `sign(endpoint.signing_secret, body)`, and post with `content=body.encode()` plus the explicit `Content-Type` header — never `json=`. Update `verify` to take the same raw body string.
Allow side (Remedy Floor 1): the case that must still SUCCEED is a customer-side verifier written only from `docs/webhooks.md` — add a test that reimplements the documented algorithm from the doc text against the actual bytes captured by `MockTransport` and asserts it matches the header. That test is the contract; it is what makes the fix measurable in the succeeding direction.
Red-proof (Remedy Floor 2), one mutation per clause: (i) drop `f"{timestamp}."` from the MAC input → the doc-derived verifier test reds; (ii) switch `content=` back to `json=` → the same test reds for a different reason (the byte comparison), so assert the raw body equals `serialize(payload)` separately to keep the two red for different assertions; (iii) hold the timestamp constant while varying the payload → a replay test asserting a captured (timestamp, signature) pair fails verification outside a five-minute window reds.
Fail loudly (Remedy Floor 3): a non-serializable payload, a missing secret, or a clock read that fails must raise before the request is sent — never post unsigned or with an empty signature header.
Preserve (Remedy Floor 4): keep `sort_keys=True` determinism and keep the `sha256=` prefix; do not "fix" the mismatch by weakening the doc to match the code, because the timestamp binding is the replay defence and deleting it deletes the feature.
Boundary and tie (Remedy Floor 5): the documented five-minute window — a request whose timestamp is exactly 300s old is REJECTED (state the side), and two deliveries signed within the same unix second produce different signatures because their payloads differ, so the timestamp is never the only varying input.

### Critical: endpoint URL validation permits `http`, internal hosts, and redirect-based SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http`, `http+unix`, and `httpfoo`; nothing constrains `netloc`, so `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/`, and any RFC1918 address are all accepted, and `follow_redirects=True` means even a validated public host can 302 the signed request to an internal one.
What breaks in production: The service becomes an authenticated SSRF proxy — a customer registers an endpoint pointing at cloud metadata or an internal admin port and the worker POSTs to it with the response body persisted into `response_body`, readable back through `GET .../deliveries`, which turns the SSRF into a full read primitive.
This is also R49: `docs/webhooks.md` says "Only `https://` URLs are accepted", declaring an enforceable boundary the code does not implement. The class of this control was never declared, and every reader defaults to (a).
Fix: Replace the prefix test with an explicit allow-list check plus destination resolution. (1) `if parsed.scheme != "https": raise HTTPException(422, "url must be an https URL")`. (2) Reject a `netloc` with credentials or a non-standard port outside `{443}`. (3) Resolve the hostname and reject when any resolved address `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`. (4) Set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure with a message naming the redirect. (5) Re-validate the destination at delivery time, not only at registration — DNS is re-resolved between the two, so a registration-time check alone is a name-versus-object gap.
Allow side (Remedy Floor 1): pin the legitimate case adjacent to the boundary — `https://hooks.example.com/acme` on port 443 resolving to a public address is still ACCEPTED and still delivered. Without this, a fix that rejects everything satisfies every other clause.
Red-proof (Remedy Floor 2), separately executed: (i) restore `startswith("http")` → the `http://` rejection test reds; (ii) remove the private-range check → the `http://169.254.169.254` test reds; (iii) restore `follow_redirects=True` → the redirect test reds; (iv) remove the delivery-time re-validation → a test whose stub resolver returns a public address at registration and a loopback address at delivery reds.
Fail loudly (Remedy Floor 3): DNS resolution failing, timing out, or returning zero addresses must REJECT with a named error ("could not resolve destination"), never fall through to accept — "examined nothing" must not be spelled the same as "found nothing".
Preserve (Remedy Floor 4): customers must still be able to register any public HTTPS host including one behind a CDN with several A records — the check is per-address over ALL resolved addresses, and every one must be public.
Boundary and tie (Remedy Floor 5): a host resolving to both a public and a private address is REJECTED (the strict side); `127.0.0.1` and `::1` are both on the reject side; a hostname resolving to `0.0.0.0` is rejected rather than treated as unroutable-and-harmless.

### Critical: the migration's status CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: The code's terminal failure status is `failed_permanent` (also the fourth member of `models.STATUSES`), but the constraint enumerates `failed`.
What breaks in production: Every exhausted delivery raises a `CheckViolation` at the moment `_finish` commits, so the row stays in `in_flight` forever, the worker's `deliver` coroutine dies inside `asyncio.gather`, and no delivery in the batch is ever marked terminal — a silent total-path failure on exactly the branch nobody tests (R40).
Cross-cutting: the status vocabulary is spelled in three independent places — `models.STATUSES`, the SQL CHECK, and bare string literals in `delivery.py` (`"pending"`, `"in_flight"`, `"delivered"`, `"failed_permanent"`). Only one of the three is wrong today; nothing prevents the next one drifting (R2).
Fix: Change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `models.STATUSES` the single source — replace every bare literal in `delivery.py` and `_claim_batch` with a member of it, and add a startup assertion (or a migration test) that the DB constraint's enumerated set equals `set(STATUSES)`.
Allow side (Remedy Floor 1): pin that a delivery that SUCCEEDS still writes `delivered` and commits — the tightened constraint must not reject the happy path.
Red-proof (Remedy Floor 2): (i) revert the constraint to `'failed'` → an integration test that drives a delivery to `MAX_ATTEMPTS` against a real Postgres reds with `CheckViolation`; (ii) add a fifth literal to `delivery.py` not in `STATUSES` → the constraint-parity test reds. Two mutations, two assertions.
Fail loudly (Remedy Floor 3): the parity check must fail the build when it cannot READ the constraint (no DB, introspection error), not skip — a skipped parity check reports the same green as a passing one.
Preserve (Remedy Floor 4): keep the CHECK constraint; do not fix this by dropping it, which would make the class of defect invisible rather than fixed.
Boundary and tie (Remedy Floor 5): a row already persisted as `failed` by an earlier deploy must be migrated (`UPDATE ... SET status = 'failed_permanent' WHERE status = 'failed'`) inside the same transaction, before the constraint is replaced, or the migration itself fails on existing data.

### Critical: `UNIQUE (event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: The uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint for the same `event_id`.
What breaks in production: The first org that registers a second endpoint breaks every event — `session.add_all(rows)` raises `UniqueViolation` on commit, `dispatch` swallows it as a `log.warning`, and that org silently receives NO webhooks at all rather than two.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is the real idempotency key (one delivery per event per destination). Keep the intent by making the insert `ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a re-dispatch of the same event is idempotent rather than an error.
Allow side (Remedy Floor 1): pin that an org with TWO active endpoints subscribed to `invoice.paid` gets exactly two rows for one event — the case the current index makes impossible and the whole feature exists for — alongside the deny case that re-enqueuing the same (endpoint, event) pair still yields one row.
Red-proof (Remedy Floor 2): (i) revert to `UNIQUE (event_id)` → the two-endpoint test reds; (ii) drop the unique index entirely → the re-enqueue idempotency test reds with two rows. Two mutations, two different assertions.
Fail loudly (Remedy Floor 3): `enqueue_for_event` must return the count actually inserted and `dispatch` must escalate a zero-inserted-but-endpoints-existed result, so a conflict-swallowing insert cannot report success.
Preserve (Remedy Floor 4): keep the idempotency guarantee the index was reaching for — do not fix by deleting the constraint and relying on the docs' "deduplicate on `event_id`".
Boundary and tie (Remedy Floor 5): the tie is the same event delivered to the same endpoint twice — resolved to one row by the pair constraint; two different endpoints of the same org at the same `event_id` are distinct rows; an endpoint deleted mid-fan-out cascades its rows away without affecting the sibling's.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop, and the persisted retry schedule is never used
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)` in the retry loop
What is wrong: `deliver` is `async` but retries by calling the synchronous `time.sleep`, and it loops all five attempts in-process rather than writing `next_attempt_at = now + backoff_for(attempt)` and returning.
What breaks in production: One failing endpoint freezes the whole worker process — `asyncio.gather` over a 100-row batch cannot progress, the httpx client's other requests time out, and a single slow customer stalls every other customer's deliveries for up to 5 × 30s of timeouts plus 30s of blocking sleeps; meanwhile `next_attempt_at`, `backoff_for`, and the `pending`/`next_attempt_at <= now` claim query — the entire scheduling machinery the migration and model exist for — are dead code after the first attempt.
Fix: Make `deliver` perform exactly ONE attempt and hand scheduling back to the store. On a 2xx call `_finish(..., "delivered", ...)`; on a retryable failure with `attempt < MAX_ATTEMPTS` write `status="pending"`, `attempts=attempt`, `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)`; on `attempt >= MAX_ATTEMPTS` write `failed_permanent`. Delete `time.sleep` and the `while True` loop; if any in-process wait remains anywhere, it must be `await asyncio.sleep(...)`.
Allow side (Remedy Floor 1): pin that a delivery which succeeds on its SECOND scheduled attempt still ends `delivered` with `attempts == 2` — the retry behaviour must survive the restructure, not be deleted with the loop.
Red-proof (Remedy Floor 2): (i) reintroduce `time.sleep(0.5)` → a test asserting `deliver` returns within a bound while a second coroutine makes progress concurrently reds; (ii) stop writing `next_attempt_at` → a test asserting the row is re-claimable only after the backoff interval reds; (iii) set `MAX_ATTEMPTS` comparison to `>` → the terminal-status test at attempt 5 reds. Bound every one of these mutations with a timeout so they red rather than hang.
Fail loudly (Remedy Floor 3): an exception that is not an `httpx.HTTPError` must still mark the row (`pending` with a bumped attempt, or `failed_permanent`) — a row left `in_flight` by an unexpected exception is a silent wedge, not a failure.
Preserve (Remedy Floor 4): keep at most `MAX_ATTEMPTS` total attempts and keep the 2s/4s/8s/16s spacing the docs promise; do not fix the blocking by lowering `REQUEST_TIMEOUT` or by dropping retries.
Boundary and tie (Remedy Floor 5): `attempt == MAX_ATTEMPTS` is terminal (state the side — the fifth attempt is made, the sixth is not); a row whose `next_attempt_at` is exactly `now` IS claimable, matching the `<=` in `_claim_batch`; two rows with identical `next_attempt_at` are both claimed rather than one starving.

### Critical: ORM instances are read after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from outside the `with session_scope()` block) and `deliver` (loads `endpoint` inside a `with` block, uses `endpoint.url` / `endpoint.signing_secret` after it)
What is wrong: Both functions let SQLAlchemy instances escape the scope that loaded them, then read attributes; under SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and the deferred load has no session to run on.
What breaks in production: The worker raises `DetachedInstanceError` on the first attribute access of every batch — `delivery.attempts` in `deliver`, `endpoint.signing_secret` in `send_once`, `delivery.payload` in the POST — so no webhook is ever delivered, and because `deliver` runs inside `asyncio.gather` the rows stay `in_flight` with no reaper.
Evidence this is the change's own inconsistency, not an assumption about code outside the diff: `create_webhook_endpoint` in `app/api/routes/settings.py` deliberately calls `session.flush()` and `endpoint.to_dict()` INSIDE its `with session_scope() as session:` block, and `list_webhook_endpoints` / `list_deliveries` likewise serialize inside the block. The two `delivery.py` sites are the only places in the diff that read an instance after the scope exits (R3 — the same pattern, propagated everywhere except here).
Fix: Stop passing ORM instances across the scope boundary. Have `_claim_batch` return plain dataclasses or tuples materialized inside the block — `(delivery_id, endpoint_id, attempts, payload, url, signing_secret)`, joined to `WebhookEndpoint` in the same query so the endpoint fields come back in one round trip and `deliver`'s separate `session.get` disappears. Change `deliver` and `send_once` to take those values.
Allow side (Remedy Floor 1): the case that must still SUCCEED is a full claim→deliver→finish cycle against a real session (not a fake), asserting the row ends `delivered` — that is the path a fix that merely eagerly-loads everything would leave unmeasured.
Red-proof (Remedy Floor 2): (i) return the ORM rows from `_claim_batch` again → the integration test reds with `DetachedInstanceError`; (ii) drop `signing_secret` from the projection → the signature-header assertion reds; (iii) drop the join and re-add the per-row `session.get` → a query-count assertion reds at N+1.
Fail loudly (Remedy Floor 3): if the join finds no endpoint for a delivery row (a race with a cascade delete), mark the row terminal with a named reason rather than skipping it silently.
Preserve (Remedy Floor 4): keep the claim's status transition to `in_flight` inside the same transaction as the SELECT — that atomicity is what stops double-claiming and must not be lost in the projection rewrite.
Boundary and tie (Remedy Floor 5): a batch of exactly `BATCH_SIZE` rows is fully materialized; a batch of zero returns an empty list rather than `None`; two rows sharing one `endpoint_id` each carry their own copy of the secret rather than aliasing one instance.

### Major: the dispatch lock is not atomic, its TTL is shorter than a batch, and `batch` can be unbound
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`
What is wrong: Four defects in one path — `get` then `set` is a check-then-act race so two workers can both acquire; `set` and `expire` are separate calls so a crash between them leaves a permanent lock with no TTL; the 60s TTL is far shorter than a batch's worst case (100 rows × up to 5 × 30s timeouts plus blocking sleeps), so the lock expires mid-run and a second worker claims the same rows; and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)` deletes whatever lock is present, including the second worker's, while `if not batch:` after the `finally` raises `NameError` when `_claim_batch` throws.
What breaks in production: Either the worker wedges forever on an immortal lock and no webhook is ever delivered, or two workers deliver the same batch concurrently and every customer receives duplicates while the first worker's cleanup unlocks the system for a third.
Fix: Replace the whole acquire with a single atomic call — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` — and release only if the token still matches, via a compare-and-delete Lua script (`if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) end`). Set `LOCK_TTL_SECONDS` from the measured worst case of a batch rather than a round number, and renew it periodically while the batch runs. Initialize `batch: list = []` before the `try` so the post-`finally` check is always bound.
Allow side (Remedy Floor 1): pin that a SINGLE worker still acquires the lock and processes its batch — a fix that always fails to acquire satisfies atomicity and delivers nothing.
Red-proof (Remedy Floor 2), one per clause: (i) drop `nx=True` → a two-worker concurrency test asserting exactly one acquires reds; (ii) drop the token comparison on release → a test where worker A's release runs after worker B acquired asserts B's lock survives, and reds; (iii) remove the `batch = []` initializer and make `_claim_batch` raise → the `NameError` test reds; (iv) set the TTL below a simulated batch duration → the no-double-claim test reds.
Fail loudly (Remedy Floor 3): a Redis error on acquire must be treated as "did not acquire" and logged as a distinct outcome from "another worker holds it" — the two must not share a log line, or an outage reads as normal contention forever.
Preserve (Remedy Floor 4): keep the single-active-dispatcher property and keep the `poll_interval` backoff when idle; do not fix the contention by removing the lock.
Boundary and tie (Remedy Floor 5): a lock whose TTL expires at exactly the moment of release is not deleted (the token no longer matches); two workers starting in the same millisecond resolve to one via `nx`.

### Major: `in_flight` has no exit path other than success or exhaustion
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; nothing resets it
What is wrong: A row enters `in_flight` at claim time and leaves only when `_finish` runs, so a worker crash, a deploy, an OOM kill, or any exception outside the `httpx.HTTPError` catch strands the row permanently (R38, non-terminal transient state).

What is wrong: The docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx response identically up to `MAX_ATTEMPTS` and `backoff_for` returns a deterministic `2 ** attempt` with no jitter (R29 / R49 — a claim stronger than, and different from, the implementation).

Fail loudly (Remedy Floor 3): a response with no status (transport failure) must route to the retryable branch explicitly rather than falling through the 4xx test on `None`.
Boundary and tie (Remedy Floor 5): status `400` is terminal and `399` is not; `499` is terminal and `500` is not; `429` and `408` are the named exceptions on the retryable side; the jittered delay's lower bound is the un-jittered value, so ordering by `next_attempt_at` never moves an earlier attempt behind a later one.

Preserve (Remedy Floor 4): keep the prefix assertion and keep the round-trip test; the fix adds the discriminating assertions rather than replacing the existing ones.
Boundary and tie (Remedy Floor 5): the distinctness batch of 1000 is the threshold — state that a single collision fails; the independent digest is compared byte-for-byte, with the `sha256=` prefix included on the compared side.

### Minor: both ordering keys are wall-clock timestamps with no tie-break
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc()).limit(limit)`; `app/webhooks/delivery.py` — `_claim_batch`, `.order_by(m.WebhookDelivery.next_attempt_at).limit(BATCH_SIZE)`
What is wrong: Deliveries fanned out in one transaction share an identical `created_at` (and an identical `next_attempt_at`), so the order among them is undefined and the `LIMIT` cuts an arbitrary subset of the tied group (R57).
What breaks in production: The deliveries list can show a different arbitrary subset of the same-instant rows on repeated calls, and a batch cut through a tie leaves the remainder to the next tick rather than losing it — bounded, because claimed rows change status, which is why this is Minor rather than Major here. It would become Major the moment a keyset cursor is added on `created_at`.
Suggested direction: add `.desc()` / ascending `id` as a secondary sort key on both queries so the order is total.

### Minor: an unbounded `gather` over the whole batch
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: All `BATCH_SIZE` (100) deliveries are launched at once with no concurrency limit and no per-batch deadline.
