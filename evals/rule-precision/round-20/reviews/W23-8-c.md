### Critical: `list_deliveries` has no tenancy check — any user reads any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The query filters on the caller-supplied `endpoint_id` only and never joins to `WebhookEndpoint` to confirm the endpoint belongs to `user.org_id`, while the two sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) both filter on `org_id`.
What breaks in production: Any authenticated user can enumerate `endpoint_id` and read other tenants' full webhook rows, and `WebhookDelivery.to_dict()` exposes `event_id`, `event_type`, `status` and `response_status` for invoice and subscription events belonging to other organizations.
Fix: Join the endpoint into the query and scope it — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403, so the id space is not oracle-ised) when the endpoint row does not exist or belongs to another org, so an unresolvable subject denies rather than returning an empty 200 that reads as "no deliveries". Preserve the existing ordering and `limit` behaviour. Pin both directions with two tests: the owning user still receives their own deliveries (allow side — an unconditional deny passes every deny test), and a second org's user receives 404 with the response body asserted empty of any delivery id (RT8: assert the leak did not happen, not only the status). Red-prove each clause separately: (a) delete the `org_id` filter and the cross-org test must red; (b) delete the 404 branch and the not-found test must red. Boundary: an endpoint whose `org_id` equals the caller's is inside; a soft-deleted or `active=False` endpoint still belongs to its owner and must remain readable, so do not fold `active` into this predicate.

### Critical: signature is computed over bytes that are not the bytes sent on the wire
File: `app/webhooks/signing.py` — `serialize` / `sign`, used by `app/webhooks/delivery.py` `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, so httpx re-serialises the dict with its own key order and separators, and the signed byte string is not the request body the receiver sees.
What breaks in production: Every customer following `docs/webhooks.md` — which specifies the HMAC is over the raw request body — computes a different digest and rejects 100% of deliveries, and the failure is invisible on our side because every attempt returns a customer-side 4xx that this code treats as a retry.
Fix: Serialise once and send the exact signed bytes: build `body = serialize(payload).encode()`, sign `body`, and post it with `client.post(endpoint.url, content=body, headers={"Content-Type": "application/json", ...})` so no second serialiser exists on the path. Preserve the current `sort_keys=True` canonicalisation and the `application/json` content type — the fix must not be "drop `sort_keys`", which would merely move the divergence. Add a round-trip test that captures `request.content` from `httpx.MockTransport` and feeds those captured bytes through `signing.verify`-equivalent recomputation, i.e. actual producer output through the actual consumer computation rather than two independently constructed strings (R40 reviewer action). Red-prove separately: (a) revert to `json=` and the round-trip test reds on digest mismatch; (b) change `sort_keys=True` to `False` in `serialize` only and the canonicalisation test reds. Fail loudly: if `serialize` raises on a non-JSON-serialisable payload, let it propagate out of `enqueue_for_event` rather than being caught — a payload that cannot be signed must not be enqueued as if it were deliverable. Boundary: two payloads differing only in key order must produce byte-identical bodies and identical signatures.

### Critical: the timestamp is not covered by the HMAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign` (`mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`)
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign` feeds only the body into the MAC and returns the timestamp as an unauthenticated side value; `verify` has no timestamp parameter at all, so the implementation structurally cannot bind the two.
What breaks in production: An attacker who captures one delivery can replay it indefinitely by rewriting `X-Acme-Timestamp` to the current second — the signature still validates — so the five-minute window the docs present as the anti-replay control (R49: a claim stronger than the implementation) provides no protection at all, and every customer that skipped their own dedup because the docs promised replay protection processes duplicate `invoice.paid` events.
Fix: Change the signed input to `f"{timestamp}.".encode() + body` and change `verify(secret, payload, signature)` to `verify(secret, timestamp, body, signature)` so the caller must supply the timestamp it received; update `send_once` to pass the same `ts` it puts in the header. Preserve the `sha256=` prefix and hex encoding so already-integrated receivers can be migrated on a documented cutover rather than silently broken, and state the cutover in `docs/webhooks.md`. Pin both sides: a signature produced with timestamp `T` verifies with `T` (allow), and the same signature presented with `T+1` fails (deny) — the deny case is what currently passes vacuously. Red-prove each clause: (a) drop the `f"{timestamp}."` prefix and the tamper test reds; (b) drop the timestamp argument from `verify` and the signature compiles no longer, i.e. the mis-call is caught at import. Fail loudly: a receiver-side helper that is handed a non-numeric or absent timestamp must raise, not return `False` indistinguishably from a bad key. Boundary: a request whose timestamp is exactly 300 seconds old — state in the docs that exactly-300 is accepted and 301 rejected, and that two requests sharing one timestamp are both valid, since the timestamp is not a nonce.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret` (`random.choice(_ALPHABET)`)
What is wrong: `random.choice` draws from the Mersenne Twister PRNG, whose internal state is recoverable from a modest run of observed outputs, so secrets minted by the same process are predictable from one another.
What breaks in production: An attacker who registers a handful of their own endpoints observes their own returned secrets, reconstructs the generator state, and predicts the signing secret of any other organization's endpoint created nearby, letting them forge signed `invoice.paid` webhooks into that tenant's receiver.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (or `secrets.choice` over `_ALPHABET` if the character set must be preserved) and rename `SECRET_BYTES` to `SECRET_CHARS` if the alphabet form is kept, because the current name claims bytes while the value is a character count. Preserve the `whsec_` prefix and the length assertion the existing test pins — the fix must not weaken entropy to keep the length. Pin the allow side: `new_signing_secret()` still returns a value accepted by `sign`/`verify` end to end, and still starts with `SECRET_PREFIX`. Red-prove: seed `random.seed(0)` in a test and assert two successive calls to `new_signing_secret` differ from the values that `random`-based generation produces under that seed — the assertion reds if `random` is reintroduced. Fail loudly: if the platform lacks `os.urandom`, `secrets` raises `NotImplementedError` and endpoint creation must 500 rather than fall back to `random`. Boundary: state the minimum accepted secret length and reject any stored secret shorter than it at sign time, so a legacy short secret fails closed rather than signing weakly.

### Critical: `verify` compares signatures with `==` instead of a constant-time comparison
File: `app/webhooks/signing.py` — `verify` (`return expected == signature`)
What is wrong: The comparison is Python's short-circuiting string equality, which leaks the length of the matching prefix through timing, and it is the exact control `docs/webhooks.md` tells customers to implement with a constant-time comparison — the repository's own reference implementation does the opposite of its own advice.
What breaks in production: Any caller that adopts this helper for inbound verification (it is exported and the tests exercise it as the reference verifier) gives an attacker a per-byte oracle for forging a valid signature without knowing the secret.
Fix: Return `hmac.compare_digest(expected, signature)`, and guard the non-`str` case explicitly (`if not isinstance(signature, str): return False`) because `compare_digest` raises on mixed types. Preserve the current return type (`bool`) and the accept-what-`sign`-produced behaviour. Pin both directions: a signature produced by `sign` with the same secret still returns `True` (allow side — `return False` would satisfy the deny test alone), and a signature made with a different secret returns `False`. Red-prove each clause separately: (a) revert to `==` and add a test asserting `verify` is implemented over `hmac.compare_digest` (patch `hmac.compare_digest` and assert it was called on the real call path — RT5's module-global identity sub-clause: assert the patched object is the one `signing` references); (b) remove the `isinstance` guard and a test passing `b"..."` must red with a `TypeError`-shaped failure rather than silently returning `False`. Boundary: a signature of the correct length but differing in the final byte must take the same path as one differing in the first.

### Critical: outbound URLs are unvalidated and redirects are followed — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`) and `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: The only check is that the scheme starts with `http` and a netloc exists, so `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:6379/`, and any internal hostname are accepted; `follow_redirects=True` then lets even an externally-valid host redirect the signed POST to an internal address after registration.
What breaks in production: Any authenticated user turns our delivery worker into a proxy that POSTs attacker-chosen JSON to cloud metadata endpoints and internal services and stores the response body in `WebhookDelivery.response_body` where they can read it back through the deliveries endpoint.
Fix: Validate at the boundary (RS3) with an explicit whitelist rather than a prefix test — require `parsed.scheme == "https"` exactly (which is what `docs/webhooks.md` already promises), reject when `parsed.hostname` is absent, and reject when it resolves to any address in a private, loopback, link-local, or reserved range using `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved` over every address returned by `socket.getaddrinfo`; set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a permanent failure. Because DNS can be re-pointed between registration and delivery, re-run the same address check inside `send_once` against the connected peer, not only at registration. Preserve the ability to deliver to legitimate public HTTPS endpoints — pin `https://hooks.example.com/acme` (allow side) alongside the deny cases, since a fix that rejects everything satisfies the deny tests. Red-prove each clause separately: (a) restore `startswith("http")` and the `http://` test reds; (b) remove the private-range check and the `http://127.0.0.1/` test reds; (c) restore `follow_redirects=True` and a MockTransport test returning a 302 to `http://169.254.169.254/` reds. Fail loudly: when `getaddrinfo` raises or returns nothing, reject with 422 and a message naming resolution failure — "could not check" must not be spelled the same as "checked and clean". Boundary: state that `https://` on a non-443 public port is accepted and that a hostname resolving to both a public and a private address is rejected (any-private-wins).

### Critical: the migration's status CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(..., "failed_permanent", ...)`
What is wrong: The SQL enumerates `'failed'` while `models.py` declares `STATUSES = (... "failed_permanent")` and `deliver` writes exactly `"failed_permanent"` — the same enum spelled two ways across a strict consumer boundary (R40), with no propagation of the value into the schema (R3).
What breaks in production: The first delivery to exhaust its attempts raises a `CheckViolation` on commit, the exception escapes `deliver` into `asyncio.gather` and out of `run_worker`'s `while` loop, killing the worker process, and the row is left in `in_flight` forever so it is never retried by the restarted worker either.
Fix: Change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the model column's validation from the one `STATUSES` tuple already present in `models.py` (`Enum(*STATUSES, name="webhook_delivery_status")`) rather than leaving a bare `String(20)` that agrees with the constraint only by convention; ship a follow-up statement for any environment where the old constraint already exists (`ALTER TABLE ... DROP CONSTRAINT ... ; ADD CONSTRAINT ...`). Preserve the constraint itself — the fix is not "drop the CHECK", which would remove the thing that made the divergence visible. Pin both directions: writing each member of `STATUSES` succeeds (allow side), and writing `"failed"` or `"bogus"` raises (deny side) — a test that only asserts the happy path passes with no constraint at all. Red-prove each clause: (a) revert the SQL to `'failed'` and the `failed_permanent` insert test reds against a real database, not a mock (R40: the divergence is invisible to a mocked session); (b) remove `Enum(...)` and the invalid-value test reds. Additionally wrap the `run_worker` loop body in `try/except Exception: log.exception(...)` so a single delivery's database error is logged and the loop continues instead of the worker dying silently. Boundary: state that `attempts == MAX_ATTEMPTS` is the last attempt and the transition to `failed_permanent` happens at that value, not at `MAX_ATTEMPTS + 1`.

### Critical: the unique index on `event_id` alone makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` creates one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index permits only one row per `event_id` across the whole table, and the uniqueness is not even scoped by `endpoint_id` or by org.
What breaks in production: The moment any organization registers a second endpoint (or a second organization subscribes to the same event id space) the `session.add_all(rows)` commit raises a unique violation, the dispatcher's blanket `except Exception` swallows it as a warning, and every endpoint for that event — including the first one — silently receives nothing.
Fix: Replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`, which preserves the idempotency property the single-column index was reaching for (one delivery per endpoint per event, so a re-dispatch of the same event does not double-send) while permitting fan-out. Preserve uniqueness — the fix is not "drop the index", which would remove the duplicate-suppression the feature's at-least-once contract depends on. Pin both directions: enqueueing one event against two endpoints inserts two rows (allow side), and enqueueing the same event twice against the same endpoint inserts one (deny side). Red-prove each clause separately against a real database: (a) revert to the single-column index and the two-endpoint test reds with a unique violation; (b) drop the index entirely and the re-enqueue test reds with two rows. Boundary: state which write wins when the same `(endpoint_id, event_id)` arrives concurrently — use `ON CONFLICT DO NOTHING` so the second is a no-op rather than an error the dispatcher swallows.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver` (`time.sleep(delay)`)
What is wrong: `deliver` is `async` and is run under `asyncio.gather` over a batch of up to `BATCH_SIZE = 100`, but the retry pause uses the blocking `time.sleep`, which stops the entire event loop rather than yielding.
What breaks in production: One failing endpoint freezes the process for up to 2+4+8+16 = 30 seconds per delivery, serialised across every other delivery in the batch and across anything else sharing the loop, so a single dead customer endpoint stalls the whole delivery pipeline for tens of minutes per batch.
Fix: The retry must not live inside the coroutine at all — on a retryable failure, persist `attempts = attempt`, `status = "pending"`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` via `_finish` and return, letting `_claim_batch` pick the row up when it is due; this also survives a worker restart, which the in-memory `while True` loop does not. If an in-process wait is retained anywhere, it must be `await asyncio.sleep(...)`. Preserve the documented five-attempt ceiling and the 2/4/8/16 schedule the existing parametrised test pins. Pin both directions: a delivery that succeeds on the first attempt is marked `delivered` and never rescheduled (allow side), and a delivery that fails is rescheduled exactly once per attempt with `next_attempt_at` in the future (deny side). Red-prove each clause: (a) reintroduce `time.sleep` and a test asserting the loop stays responsive (a concurrent `asyncio.sleep(0)` task completes within a bound) reds; (b) remove the `next_attempt_at` write and the rescheduling test reds because the row is immediately re-claimable. Fail loudly: if `_finish` finds no row for the id, raise rather than returning, so a lost delivery is not silently forgotten. Boundary: `_claim_batch` filters `next_attempt_at <= now`, so a row due at exactly `now` is claimed this pass — state that, and note that ties on `next_attempt_at` are broken by the primary key (see the ordering finding below).

### Critical: ORM rows are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` outside the `with session_scope()` block) and `deliver` (`endpoint` read after the `with` block exits)
What is wrong: Both functions return or retain SQLAlchemy instances after the enclosing `session_scope()` has exited, then read attributes (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.url`, `endpoint.signing_secret`) from the detached objects.
What breaks in production: The diff's own convention shows this does not survive the scope — `app/events/dispatcher.py` deliberately copies `event_id = row.id` *inside* the `with` block before using it outside, and `create_webhook_endpoint` calls `endpoint.to_dict()` inside the block — so under the standard expire-on-commit behaviour every attribute read here raises `DetachedInstanceError` and the worker dies on its first non-empty batch. Additionally `_claim_batch` writes `row.status = "in_flight"` and `_finish` later writes `status`/`attempts` on the same row through a different session, so the claim can be overwritten.
Fix: Follow the convention the diff already establishes: inside each `session_scope()` block, materialise plain data before returning — have `_claim_batch` return a list of frozen dataclasses or tuples carrying `(id, endpoint_id, attempts, payload)`, and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside its own block. Preserve the claim semantics — the `in_flight` write must still be committed by the same transaction that selects the rows, so use `.with_for_update(skip_locked=True)` on the select so two workers cannot claim the same row (this is the atomicity the Redis lock is standing in for). Pin both directions: a claimed batch's payloads are readable after the function returns (allow side), and a row already `in_flight` is not returned by a second concurrent `_claim_batch` (deny side). Red-prove each clause separately: (a) return the ORM rows again and the attribute-read test reds with `DetachedInstanceError`; (b) drop `skip_locked` and a two-task concurrent claim test reds by returning the same id twice. Fail loudly: `_finish` currently assumes `session.get` returns a row — raise a named error when it is `None`. Boundary: a row whose `next_attempt_at` equals `now` is claimable; a row already `in_flight` is not, regardless of age, until the reaper below resets it.

### Critical: the signature test cannot fail for the reason it claims
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test asserts only that the signature header `startswith("sha256=")` and the timestamp `isdigit()`, never that the signature is the HMAC of what was actually transmitted, so an implementation returning `"sha256=" + "0" * 64` and one signing the wrong bytes both pass (RT7: a structurally blind check over a security invariant).
What breaks in production: This is precisely why the serialisation divergence above ships green — the suite reads as coverage of the signing path while verifying nothing about the signature's value, so a reviewer trusts a control that was never exercised.
Fix: Recompute the expected digest in the test from the captured request bytes and an independently written HMAC (`hmac.new(SECRET.encode(), captured["body"], hashlib.sha256).hexdigest()`, not by calling `signing.sign` again, which would make the assertion an identity — RT1), and assert equality with the captured header. Preserve the existing prefix and content-type assertions — this adds a value assertion, it does not replace the shape assertions. Pin both directions: the correctly signed request verifies (allow side), and a test that mutates one byte of the captured body fails verification (deny side). Red-prove each clause separately: (a) change `serialize` to `json.dumps(payload)` without `sort_keys` and the equality assertion reds; (b) change the HMAC digest from `sha256` to `sha1` in `sign` and the same assertion reds with a length mismatch the failure output names. Fail loudly: if `captured` is empty because the handler was never invoked, assert that explicitly rather than letting a `KeyError` read as an unrelated failure. Boundary: an empty payload `{}` must still produce a well-formed 64-hex-char digest — include it as a case.

### Major: `signing_secret` is returned by the list endpoint, contradicting the documented guarantee
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py` `list_webhook_endpoints`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns it for every endpoint on every call, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation).
What breaks in production: Every credential for every endpoint in an organization is readable by any member who can call `GET /v1/settings/webhook-endpoints`, and customers who followed the documented advice to store it in their own secret manager reasonably believe that surface does not exist.
Fix: Remove `signing_secret` from `to_dict()` and return it only from `create_webhook_endpoint`, by constructing that one response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}`; add a `POST /webhook-endpoints/{id}/rotate-secret` route if read-back was actually needed, so the capability is replaced rather than merely removed. Preserve the create-time disclosure — the fix must not make the secret unobtainable, which would make the feature unusable. Pin both directions: the create response still contains `signing_secret` (allow side), and the list response does not (deny side). Red-prove each clause separately: (a) re-add the key to `to_dict` and the list-response test reds on an unexpected key; (b) remove the explicit merge in the create handler and the create-response test reds on a missing key. Boundary: state that an endpoint created and listed in the same request cycle is still redacted in the list, i.e. redaction is a property of the route, not of the row's age.

### Major: the Redis lock is not atomic and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `get` then a separate `set`, so two workers that both read an empty key both proceed; the `expire` is a third round trip, so a crash between `set` and `expire` leaves the key permanently held; and the `finally` deletes the key without checking the holder, so a worker that lost the race deletes the winner's lock.
What breaks in production: Two workers claim overlapping batches and send duplicate webhooks, or a mistimed crash leaves `webhooks:dispatch:lock` set forever with no TTL and all delivery stops silently.
Fix: Make acquisition a single atomic operation with the TTL attached — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script that deletes only when the stored value equals `token`. Preserve the 60-second expiry so a crashed holder still frees the lock, and note that the real claim atomicity should come from the `SELECT ... FOR UPDATE SKIP LOCKED` in the detached-instances fix above; the Redis lock is an optimisation, not the correctness boundary. Pin both directions: the first caller acquires and can do work (allow side), and a second concurrent caller does not (deny side) — an `_acquire_lock` that always returns `False` passes the deny test alone. Red-prove each clause separately: (a) revert to `get`-then-`set` and a test issuing two interleaved acquisitions reds by granting both; (b) replace the compare-and-delete with a bare `delete` and a test where holder B's release is attempted against holder A's token reds. Fail loudly: when Redis is unreachable, `_acquire_lock` must propagate rather than returning `False` forever, so an outage is an alarm rather than an indefinitely idle worker. Boundary: a lock at exactly its 60-second TTL is expired and re-acquirable; state that a batch still running past 60 seconds loses its lock and must therefore rely on `SKIP LOCKED`, not on the lock, for exclusion.

### Major: `in_flight` has no exit path — a crashed worker wedges deliveries forever
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) with no reaper anywhere in the diff
What is wrong: A row enters `in_flight` at claim time and leaves it only when `_finish` runs on the success or exhaustion path; a worker crash, an unhandled exception in `deliver`, or a process restart during the 30-second in-memory retry chain leaves the row in a state no query in the diff selects (R38 clause 1: a non-terminal transient state with no failure exit and no bounded timeout).
What breaks in production: Every delivery in flight at the moment of a deploy or crash is lost permanently and invisibly — `_claim_batch` filters on `status == "pending"` so the stuck rows are never retried, and nothing alerts on them.
Fix: Add a `claimed_at TIMESTAMPTZ` column set at claim time and a reaper pass at the top of the worker loop that returns rows to `pending` when `claimed_at < now() - interval '5 minutes'` and `attempts < MAX_ATTEMPTS`, and to `failed_permanent` when `attempts >= MAX_ATTEMPTS`, logging each reset at WARNING with the delivery id. Preserve the exclusion the `in_flight` state provides — the fix is not "stop marking `in_flight`". Pin both directions: a row claimed one second ago is not reaped (allow side), and a row claimed six minutes ago is returned to `pending` and subsequently redelivered (deny side). Red-prove each clause separately: (a) remove the reaper and the stale-row test reds because the row stays `in_flight`; (b) remove the `attempts >= MAX_ATTEMPTS` branch and a test asserting an exhausted stale row does not loop forever reds. Fail loudly: emit a counter/log line whenever the reaper resets anything, so wedging is visible rather than inferred. Boundary: a row whose `claimed_at` is exactly the five-minute threshold is reaped (`<=`), and a row reaped concurrently by two workers must be a single transition — do the reset with a conditional `UPDATE ... WHERE status = 'in_flight' AND claimed_at <= ...`.

### Major: naive `datetime.utcnow()` is written into a timezone-aware column while the reader compares aware values
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`) vs `_claim_batch` (`now = datetime.now(timezone.utc)`)
What is wrong: The write uses a naive UTC datetime while the column is declared `DateTime(timezone=True)` and the read filters against an aware value; `app/webhooks/models.py` already defines the `_now()` helper that returns `datetime.now(timezone.utc)` and this new code in the same package reimplements it incorrectly (R1: a shared helper reimplemented, with a behavioural difference).
What breaks in production: The driver interprets the naive value in the session timezone, so in any non-UTC deployment freshly enqueued deliveries are scheduled hours in the future (never claimed until then) or hours in the past — and the same `.isoformat()` value is returned to customers through `WebhookDelivery.to_dict()` without an offset, so their "next attempt" display is wrong too.
Fix: Import and use the existing `models._now()` at the single call site — `next_attempt_at=m._now()` — rather than adding a second time source; grep confirms `_now` is the only time helper in `app/webhooks/` and `delivery.py` already imports `models as m`. Preserve the immediate-dispatch intent (`next_attempt_at` equal to now, so the first claim picks it up on the next poll). Pin both directions: a delivery enqueued now is claimed by the next `_claim_batch` (allow side), and one with `next_attempt_at` one minute out is not (deny side). ### Major: `order_by(next_attempt_at)` and `order_by(created_at)` are not total orders
