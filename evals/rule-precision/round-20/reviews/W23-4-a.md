### Critical: the HMAC is computed over different bytes than the request body carries
File: `app/webhooks/signing.py` — `serialize` / `sign`, consumed by `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (default separators, `", "` / `": "`) while `send_once` transmits the body httpx produces from `json=delivery.payload` (compact `","` / `":"`, insertion order), so the signed string and the transmitted string differ for every payload with at least one key.

Do not fix by loosening the receiver-side comparison or by dropping `sort_keys` from the doc — the behaviour that must be preserved is that one payload maps to exactly one signable byte string. ### Critical: the timestamp header is not covered by the signature, so the documented replay window is not a control
File: `app/webhooks/signing.py` — `sign` (line `mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`)
What is wrong: `sign()` returns a timestamp but MACs only the payload, so `X-Acme-Timestamp` is unauthenticated and freely rewritable, while `docs/webhooks.md` tells integrators the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that the five-minute timestamp window "is what stops a captured request from being replayed".
What breaks in production: anyone who captures one delivery — a proxy, a log aggregator, a compromised intermediate — can replay it indefinitely by rewriting the timestamp header, and the customer's freshness check passes because nothing binds the timestamp to the MAC (R49: the doc declares an enforceable boundary where the implementation is a signature with no replay resistance at all).
Fix: MAC the concatenation the doc already specifies — `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact transmitted string from the previous finding. `verify()` must then take the timestamp as an explicit argument (`verify(secret, timestamp, body, signature)`) instead of calling `sign()` and discarding the fresh timestamp — as written, fixing `sign()` alone leaves `verify()` green because it re-signs with a *new* timestamp, which is the mirrored-wrong round trip R29 names ("never as `f(g(x)) == x`"). Pair deny with allow: a delivery signed at T verifies at T+60s (allow, still succeeds), and the same bytes with the timestamp rewritten to T+600 fail (deny). Red-prove each clause separately: (i) drop the `f"{timestamp}."` prefix from `sign` and observe the header-rewrite test go green (red-proving the deny clause), (ii) revert `verify` to re-deriving the timestamp and observe the same test go green. Fail loudly: a request whose `X-Acme-Timestamp` is absent or non-numeric must be rejected by `verify` with a named error, never treated as timestamp `0`. Do not fix by deleting the timestamp header or by widening the window — the behaviour to preserve is that integrators can bound replay by clock. Boundary and tie: state in the doc which side exactly-300-seconds falls on, and specify that two deliveries signed in the same second are distinguished by `event_id`, not by timestamp.

Boundary and tie: a secret of exactly `len(SECRET_PREFIX)` characters (empty body) must be rejected at generation, not stored.

### Critical: `time.sleep` inside the async retry loop blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver` (`time.sleep(delay)`)
What is wrong: `deliver` is a coroutine gathered 100-wide, and it uses the *blocking* `time.sleep` for its backoff, so one retrying delivery freezes the event loop for 2, 4, 8 and 16 seconds while every other delivery, the HTTP client's timeouts and the Redis lock heartbeat all stop.
What breaks in production: a single slow customer endpoint stalls the entire worker for up to 30 seconds per retrying delivery — with 100 gathered deliveries the batch serializes into tens of minutes, the 60-second `LOCK_KEY` TTL expires mid-batch so a second worker starts a parallel batch, and the first worker's `finally: redis_client.delete(LOCK_KEY)` then deletes the *second* worker's lock, admitting a third.

Add `return_exceptions=True` to the `asyncio.gather` so one delivery's exception cannot abort the batch or leave sibling coroutines orphaned. Pair deny with allow: a delivery that succeeds on the first attempt still finishes in one pass with `attempts=1` and status `delivered` (allow); a delivery that fails is rescheduled without the worker blocking, provable by asserting the loop remains responsive — e.g. a concurrently gathered marker coroutine still completes within the retry interval (deny). Red-prove each clause separately: (i) restore `time.sleep` and observe the marker-coroutine assertion red, (ii) remove `return_exceptions=True` and observe the batch-completion assertion red under one raising delivery. Fail loudly: a delivery whose row has vanished under it must raise a named error, not be silently dropped from the batch. Do not fix by shortening the delays — the exponential schedule the doc publishes (2s, 4s, 8s, 16s) is the behaviour to preserve. Boundary and tie: `attempt == MAX_ATTEMPTS` is terminal (no further reschedule), and two deliveries whose `next_attempt_at` are equal must both be claimable in one batch.

### Major: the distributed lock is a check-then-set with no ownership token

### Major: retry policy contradicts the published contract on both 4xx handling and jitter
File: `app/webhooks/delivery.py` — `deliver` / `backoff_for` vs `docs/webhooks.md` "Retries"
What is wrong: the doc says "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", while `deliver` retries every non-2xx status five times and `backoff_for` returns an exact `2**attempt` with no jitter (R49: claims stronger than, and different from, the implementation).
What breaks in production: a customer endpoint returning 401 or 404 gets hammered five times per event, and because every delivery for one outage retries on precisely the same 2/4/8/16 second grid, the whole backlog re-hits the recovering endpoint simultaneously — the thundering herd the documented jitter was there to prevent.

Red-prove each clause separately: (i) remove the 4xx branch and observe the 404 test red on `attempts`, (ii) fix the injected jitter source to a constant and observe the jitter test red on distribution spread. Fail loudly: a status the classifier does not recognise (a 1xx, a 3xx with redirects disabled) must be recorded as `failed_permanent` with the status in `response_body`, never retried by default. Do not fix by editing the doc to remove the jitter claim without also fixing the herd — and note the existing `test_backoff_grows_exponentially` asserts exact equality, so it must be relaxed to a bounded range rather than deleted, preserving its ability to catch a wrong exponent. Boundary and tie: state which side 429 falls on (retryable) and what happens when `Retry-After` exceeds the remaining attempt budget.

### Major: the response body of an untrusted endpoint is stored and read without bound

What is wrong: `response.text` is fully materialised and written into `webhook_deliveries.response_body` with no size cap, for a response body entirely under the remote party's control.
