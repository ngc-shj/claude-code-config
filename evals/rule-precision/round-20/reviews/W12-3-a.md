### Critical: the transmitted body is not the body that was signed, so no receiver can ever verify a delivery
File: `app/webhooks/signing.py` — `sign()` / `serialize()`; `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (keys sorted, default `", "` / `": "` separators) while `send_once()` hands the raw dict to httpx as `client.post(endpoint.url, json=delivery.payload, ...)`, which encodes it with its own compact separators and insertion order, and the timestamp that `docs/webhooks.md` says is part of the signed material (`"{timestamp}.{raw_request_body}"`) is never fed into the HMAC at all.
What breaks in production: every customer who implements the documented verification recomputes the MAC over the bytes they actually received and gets a mismatch, so 100% of deliveries are rejected as forged while our side reports them `delivered`; the timestamp header is also unauthenticated, so an attacker who captures one request can replay it forever by rewriting `X-Acme-Timestamp` past the documented five-minute window.
Fix: make `serialize()` the single producer of the wire bytes and send those exact bytes — change `sign(secret, payload)` to return `(timestamp, signature, body_bytes)` where `body_bytes = serialize(payload).encode()` with `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`, and MAC `f"{timestamp}.".encode() + body_bytes` (the documented `{timestamp}.{raw_body}` construction); change `send_once()` to `client.post(endpoint.url, content=body_bytes, headers={... "Content-Type": "application/json"})` — never `json=`, because that re-encodes and is exactly what made the divergence invisible. Keep `verify()` and keep the existing header names and `sha256=` prefix: they are what a customer already integrates against. Allow side that must still pass: a round-trip test that feeds the ACTUAL bytes captured by `httpx.MockTransport` back through `verify()` (not through `sign()` a second time) and asserts True — R40's "actual producer output through the actual consumer" round-trip. Red-prove each clause separately by running it: (i) revert `separators` to the default and assert the round-trip goes red; (ii) drop the `f"{timestamp}."` prefix from the MAC input and assert a second test that pins the documented construction against a hand-computed hex digest goes red; (iii) switch `content=` back to `json=` and assert the round-trip goes red. Fail loudly when the check cannot run: `verify()` must raise on a signature that is not `sha256=<64 hex>` rather than returning False, so "malformed header" is not spelled the same as "wrong key". Boundary and tie: state that a payload serializing to identical bytes must produce an identical signature for a given timestamp, and that the receiver's freshness window is `now - ts <= 300` inclusive at exactly 300 seconds.

### Critical: `GET /webhook-endpoints/{endpoint_id}/deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries()`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, even though the sibling handler `list_webhook_endpoints()` added in the same file and the same diff does apply exactly that org filter.
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other tenants' delivery rows, and because `WebhookDelivery.payload` holds the full `invoice.paid` / `subscription.updated` event body, this is a cross-tenant dump of billing data through a route documented as returning "attempts for an endpoint belonging to your organization".
Fix: join and filter — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookDelivery.endpoint_id == m.WebhookEndpoint.id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)`, and when the join yields no endpoint row raise `HTTPException(404)` rather than returning `[]`, so a foreign id and a nonexistent id are indistinguishable. Do not "fix" this by removing `endpoint_id` from the path or by dropping the route — the per-endpoint delivery view is the feature. Allow side that must still pass: a test where the endpoint DOES belong to the caller's org asserts the caller's own delivery rows are returned, non-empty, with the expected ids — a fix that always 404s satisfies the deny side alone. Red-prove each clause separately by execution: (i) delete the `org_id` predicate and assert the cross-tenant test goes red on rows returned; (ii) change the empty-result branch back to `return []` and assert the "foreign id is indistinguishable from missing id" test goes red on status code. Fail loudly when the check cannot run: `user.org_id` being None must raise, not fall through to an unfiltered query. Boundary and tie: an endpoint that exists but is `active=False` and belongs to the caller still returns its history (deactivation is not deletion), and a delivery whose endpoint row was cascade-deleted is not reachable at all.

### Critical: the signing secret is returned by the endpoint-listing API, contradicting the documented "cannot be read back"
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`; `app/api/routes/settings.py` — `list_webhook_endpoints()`; `docs/webhooks.md`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and `list_webhook_endpoints()` returns `[e.to_dict() for e in endpoints]`, so the secret is served on every `GET /v1/settings/webhook-endpoints` while the doc added in the same diff states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret is repeatedly emitted to every client, proxy log, and browser cache that touches the list route, and the documented security property that customers are told to rely on (store it yourself, it is never re-served) is false — an R49 claim stronger than the implementation, on the control that authenticates every webhook we send.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` and have only `create_webhook_endpoint()` add it, by returning `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at the creation site — one method, one shape, the secret added at exactly the one place the doc promises. Keep `to_dict()` as the shared serializer rather than hand-rolling a second dict in the list route; the shared path is what stops the next field from diverging. Allow side that must still pass: a test asserting `POST /v1/settings/webhook-endpoints` DOES return a `signing_secret` starting with `whsec_` — the fix must not delete the one place the customer can obtain it. Red-prove each clause separately by execution: (i) re-add the key to `to_dict()` and assert a test asserting `"signing_secret" not in body[0]` for the list route goes red; (ii) delete the merge in the create handler and assert the create-returns-secret test goes red. Fail loudly when the check cannot run: add an assertion in the list-route test over the full key set (`set(body[0]) == {...}`) rather than a `not in` check alone, so a renamed-but-still-present secret field cannot pass. Boundary and tie: an org with zero endpoints returns `[]` and asserts nothing vacuously — the test must seed at least one endpoint.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister in the `random` module, which is a deterministic generator whose internal state is recoverable from observed output and is documented as unsuitable for security purposes.
What breaks in production: an attacker who registers a handful of endpoints of their own observes enough generator output to reconstruct the process state and predict the secrets issued to other organizations, at which point they can forge signed webhooks that any customer verifying per our documentation will accept as genuine `invoice.paid` events.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`, drop `random`, `string` and `_ALPHABET`), and rename/redocument `SECRET_BYTES = 32` to mean what it now is — 32 bytes of entropy — since the current constant is named "bytes" but consumed as a character count. Do not fix this by only lengthening the `random`-based string: length is not the defect, predictability is. Allow side that must still pass: `new_signing_secret()` still starts with `whsec_` and the secret it returns still round-trips through `sign()`/`verify()`. Red-prove each clause separately by execution: (i) reinstate `random.seed(0)` before two calls and assert a test asserting two independently generated secrets differ goes red under the seeded `random` implementation but stays green under `secrets`; (ii) revert the prefix and assert the prefix test goes red. Note this also requires updating `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length`, which currently pins `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` — that assertion encodes the byte/character confusion and must be re-derived from `token_urlsafe`'s output length, not deleted. Boundary and tie: state the minimum accepted secret length at the verification side and what happens for a legacy stored secret exactly at the old 32-character length (it must keep verifying until rotated).

### Critical: signature comparison in `verify()` is not constant time
File: `app/webhooks/signing.py` — `verify()`
What is wrong: the function compares with `expected == signature`, a short-circuiting byte comparison, while the doc added in the same diff instructs customers to "compare it against your own computation using a constant-time comparison" — the reference implementation we ship does the opposite of what we tell integrators to do.
What breaks in production: any service that adopts `verify()` (it is exported and exercised by two tests, and is the natural helper for our own inbound-callback surfaces) leaks the correct digest byte-by-byte through response timing, letting an attacker recover a valid signature for a payload of their choice without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)` (RS1), keeping the `sha256=` prefix inside the compared strings so the prefix mismatch is also constant-time, and keep the docs' constant-time instruction — it is correct guidance and must not be softened to match the code. Allow side that must still pass: `test_verify_accepts_signature_produced_by_sign` continues to return True for a genuine signature. Red-prove each clause separately by execution: (i) revert to `==` and assert a test that asserts `verify.__code__.co_names` contains `compare_digest` — or, better, a test that patches `hmac.compare_digest` with a spy and asserts it was called — goes red; (ii) mutate `expected` by one character and assert the existing wrong-secret test goes red. Fail loudly when the check cannot run: `verify()` must reject a `signature` that is not a `str` of the expected shape by raising, since `compare_digest` raises `TypeError` on mixed types and that must not be caught into a `False`. Boundary and tie: name that a signature of a different length returns False without leaking length through timing, and that two callers passing byte-identical signatures always agree.

### Critical: the delivery worker can never read the rows it fetched — every ORM object escapes its session
File: `app/webhooks/delivery.py` — `_claim_batch()` and `deliver()`
What is wrong: `_claim_batch()` returns `rows` out of the `with session_scope() as session:` block and `deliver()` does `with session_scope() as session: endpoint = session.get(...)` then uses `endpoint` after the block, so both hand back instances that are detached and expired the moment the scope commits; the first attribute access afterwards (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret`, `endpoint.url`) raises `DetachedInstanceError`.
What breaks in production: the worker loop never delivers anything — the first `deliver()` call raises out of `asyncio.gather`, propagates through `run_worker`'s bare `try/finally`, and kills the worker, so a feature the docs advertise as live has no working backing path at all (R41).
Fix: stop passing ORM instances across session boundaries — have `_claim_batch()` return plain data (`list[tuple[int, int, dict, int]]` of `(delivery_id, endpoint_id, payload, attempts)`) built inside the scope, and have `deliver()` load the endpoint's `url` and `signing_secret` into locals inside its own scope before the HTTP call; `send_once()` then takes `(url, secret, payload)` instead of ORM objects. Do not "fix" this by setting `expire_on_commit=False` — that leaves the objects bound to a closed session and makes the next lazy-load fail at a different, later place. Allow side that must still pass: an end-to-end test that runs `_claim_batch()` against a real seeded DB and then `deliver()` through `httpx.MockTransport`, asserting the row reaches `status == "delivered"` — the fixture must use the real session, because `FakeEndpoint`/`FakeDelivery` in the current test file are plain classes with no session at all and are precisely why this never surfaced (RT5: the test call path excludes the production primitive). Red-prove each clause separately by execution: (i) restore the ORM return in `_claim_batch()` and assert the end-to-end test goes red with `DetachedInstanceError`; (ii) restore the ORM `endpoint` in `deliver()` and assert it goes red at `signing_secret`. Fail loudly when the check cannot run: `session.get(WebhookEndpoint, endpoint_id)` returning None must raise a named error and mark the delivery `failed_permanent`, not `AttributeError` on `None.url`. Boundary and tie: a batch of exactly `BATCH_SIZE` rows and a batch of zero rows must both be handled, and two deliveries for the same endpoint must each resolve the endpoint once.

Fail loudly when the check cannot run: the schema-vs-`STATUSES` test must fail if it cannot read the CHECK definition from the DB, rather than skipping. ### Critical: the unique index on `event_id` alone allows only one delivery row per event
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`; `app/webhooks/delivery.py` — `enqueue_for_event()`
What is wrong: `enqueue_for_event()` builds one `WebhookDelivery` per matching endpoint and calls `session.add_all(rows)`, but the unique index is on `event_id` by itself, so the second row for the same event violates uniqueness.
What breaks in production: any organization with two or more active subscribed endpoints gets an `IntegrityError` that aborts the whole enqueue transaction, so ALL of that event's deliveries are lost — and `app/events/dispatcher.py` swallows the exception into `log.warning`, so the loss is silent and the documented "delivery is at-least-once" guarantee is false.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)` — the pair is the real idempotency key, since the doc tells customers to "deduplicate on `event_id`" per endpoint — and make `enqueue_for_event()` insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a redelivery attempt is an idempotent no-op rather than a failure. Keep the uniqueness constraint; removing it would make the re-enqueue path silently duplicate deliveries, which is the property the index exists to prevent. Allow side that must still pass: a test seeding two active endpoints for one org and asserting `enqueue_for_event()` returns 2 and creates 2 rows. Red-prove each clause separately by execution: (i) revert to the single-column index and assert the two-endpoint test goes red with `IntegrityError`; (ii) call `enqueue_for_event()` twice with the same `event_id` and assert the row count stays at 2, then remove `DO NOTHING` and assert that test goes red. Fail loudly when the check cannot run: the enqueue must not be wrapped in a swallow — see the dispatcher finding. Boundary and tie: two different orgs whose endpoints receive the same `event_id` must both get rows (the old index forbade this), and an endpoint deleted between the query and the insert resolves via the FK's `ON DELETE CASCADE`.

### Critical: `time.sleep()` inside an async coroutine blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver()`, retry branch
What is wrong: the retry backoff uses the blocking `time.sleep(delay)` inside `async def deliver`, and `run_worker()` fans out up to `BATCH_SIZE` (100) of these through `asyncio.gather`, so a single sleeping coroutine freezes every other delivery, the HTTP client, and the lock-refresh path.
What breaks in production: one slow endpoint serializes the whole batch — with the documented 2+4+8+16 second backoff plus a 30 s `REQUEST_TIMEOUT` per attempt, a batch of 100 failing deliveries blocks the loop for hours, and the 60 s Redis lock expires long before the batch finishes so a second worker starts redelivering the same rows.
Fix: `await asyncio.sleep(delay)` (the `asyncio` import already exists in the file). Do not reduce the backoff constants to make the block tolerable — the backoff schedule is documented and is what protects the customer's endpoint. Allow side that must still pass: a test asserting a delivery that succeeds on the first attempt returns without sleeping at all (patch `asyncio.sleep` with a spy and assert zero calls). Red-prove each clause separately by execution: (i) restore `time.sleep` and assert a test that runs two `deliver()` coroutines concurrently and asserts total wall time is under the sum of their sleeps goes red; (ii) patch `asyncio.sleep` and assert the failing-then-succeeding case records exactly one call with `2` seconds. Fail loudly when the check cannot run: the concurrency test must assert a positive lower bound on the number of attempts made (RT4) so it cannot pass with zero deliveries. Boundary and tie: attempt number `MAX_ATTEMPTS` is the last attempt and is followed by no sleep at all, and two deliveries scheduled for the same instant both run.

### Critical: the dispatch lock is a non-atomic check-then-set and is released without ownership
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock()` does a `get` followed by a separate `set`/`expire`, so two workers can both observe an empty key and both proceed, and the release is an unconditional `delete` of a key that — after the 60 s TTL expires mid-batch — may belong to a different worker.
What breaks in production: concurrent workers claim overlapping batches and POST the same event to the customer twice or more, and because the release deletes another owner's lock the mutual-exclusion property degrades to none under exactly the load it was added for.
Fix: acquire atomically with `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = secrets.token_hex(16)` is unique per acquisition, and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`) so a worker never deletes a lock it does not own; additionally take the batch with `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch()` so correctness does not rest on the Redis lock alone. Keep the lock — removing it in favour of `SKIP LOCKED` alone would drop the throttle on total concurrent outbound requests. Allow side that must still pass: a single worker still acquires the lock, processes a batch, and releases it, with a test asserting the key is absent afterwards. Red-prove each clause separately by execution: (i) revert to `get`-then-`set` and assert a test that starts two `_acquire_lock()` calls concurrently and asserts exactly one returns True goes red; (ii) revert the compare-and-delete to a plain `delete` and assert a test where worker A's lock has expired and worker B holds the key, and A releases, asserting B's key survives, goes red; (iii) remove `SKIP LOCKED` and assert a two-session claim test asserting disjoint id sets goes red. Fail loudly when the check cannot run: a Redis error in `_acquire_lock()` must return False (do not process) rather than propagate into an unlocked run. Boundary and tie: a lock whose TTL expires at exactly the moment of release is a no-op release, and two workers presenting the same token is impossible by construction of `token_hex`.

### Critical: endpoint URL validation accepts any scheme starting with `http` and any host, including internal ones
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: `startswith("http")` is a surface-form prefix test that admits `http`, `httpx`, `httpfoo` and any other scheme sharing the prefix, it admits plaintext `http://` even though `docs/webhooks.md` states "Only `https://` URLs are accepted", and it places no restriction on the host at all while `run_worker()` drives the request with `follow_redirects=True`.
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/` and our worker issues authenticated-network POSTs to it on every matching event — a server-side request forgery with our infrastructure's network position, amplified by redirect following so even an allowlisted host can bounce the request inward, and the plaintext scheme additionally puts the signed event body on the wire in the clear.
Fix: validate against the resolved object rather than the string (R47) — require `parsed.scheme == "https"` exactly, require `parsed.hostname`, resolve it with `socket.getaddrinfo` and reject when any resolved address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast or .is_unspecified`, reject a non-default port outside an explicit allowlist, and set `follow_redirects=False` on the `httpx.AsyncClient` in `run_worker()` so a 3xx is treated as a non-2xx response rather than followed. Because DNS can change between registration and delivery, apply the same address check at delivery time in `send_once()` (or use a pinned-resolution transport); registration-time validation alone is a narrowing, not a closure. Correct `docs/webhooks.md` only insofar as it is already right — it says HTTPS-only, and the code must be brought to the doc, not the doc to the code. Allow side that must still pass: a test asserting `https://hooks.example.com/acme` resolving to a public address is accepted with 201 — a validator that rejects everything satisfies the deny side alone. Red-prove each clause separately by execution: (i) revert to `startswith("http")` and assert a test posting `httpfoo://x/` goes red on the 422; (ii) remove the address check and assert a test posting a hostname resolving to `127.0.0.1` goes red; (iii) restore `follow_redirects=True` and assert a `MockTransport` test where the endpoint 302s to an internal URL and the delivery is expected to end non-2xx goes red. Fail loudly when the check cannot run: DNS resolution failure must return 422 with a named reason, never "could not check, therefore allow". Boundary and tie: state which side of the boundary CGNAT `100.64.0.0/10` falls on (reject) and that a hostname resolving to both a public and a private address is rejected, not accepted on the public one.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch()` setting `row.status = "in_flight"`, and `_finish()` as the only exit
What is wrong: rows leave `in_flight` only through `_finish()`, which runs on the success and exhausted-retry paths of `deliver()`; a worker crash, an OOM kill, a deploy restart, or any exception other than `httpx.HTTPError` (all of which are live given the detached-instance and `IntegrityError` findings above) leaves the row in `in_flight` permanently, and nothing in the diff ever moves a row back to `pending` (R38 clause 1).
What breaks in production: every worker restart permanently strands the batch that was in flight, so deliveries are silently and irrecoverably lost while the customer-facing deliveries API shows them as still being worked on.
Fix: add a `claimed_at TIMESTAMPTZ` column and a reaper that runs at the top of each `run_worker()` iteration, resetting `status` to `pending` and bumping `next_attempt_at` for any row with `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`; also wrap `deliver()`'s body in a `try/except Exception` that routes any non-`HTTPError` failure through `_finish(..., "failed_permanent", ...)` so the state machine has an explicit failure exit. Keep `in_flight` as a distinct state — collapsing it back into `pending` would remove the visibility that makes a stuck delivery detectable. Allow side that must still pass: a row claimed 10 seconds ago is NOT reaped, asserted directly, so the reaper cannot be a blanket reset. Red-prove each clause separately by execution: (i) remove the reaper and assert a test that claims a batch, simulates a crash, runs a second iteration and asserts the row is `pending` goes red; (ii) remove the `except Exception` and assert a test raising `ValueError` from `send_once` and asserting terminal status goes red. Fail loudly when the check cannot run: a reaper that cannot read `claimed_at` (column missing) must raise at startup rather than silently reap nothing. Boundary and tie: a row claimed exactly at the 5-minute mark is reaped (`<` vs `<=` stated explicitly), and a row reaped while its original worker is still alive must be protected by the `SKIP LOCKED`/ownership token, not by the timeout alone.

### Major: the retry policy in code contradicts the retry policy in the documentation
File: `app/webhooks/delivery.py` — `deliver()`'s non-2xx branch and `backoff_for()`; `docs/webhooks.md` — "Retries"

### Major: `run_worker()` dies permanently on the first exception, and `batch` can be referenced unbound
File: `app/webhooks/delivery.py` — `run_worker()`
What is wrong: `batch = await _claim_batch()` sits inside a `try` whose only handler is `finally`, so any exception escapes the `while True` loop and terminates the coroutine; and because `if not batch` is evaluated after the `try/finally`, a raise from `_claim_batch()` leaves `batch` unbound — the `asyncio.gather(...)` call also has no `return_exceptions=True`, so one failing delivery cancels the rest and propagates.

Allow side that must still pass: a normal iteration with a non-empty batch still delivers every row and still releases the lock. Red-prove each clause separately by execution: (i) make `_claim_batch` raise and assert a test asserting the worker performs a second iteration goes red (bound the loop with a max-iterations parameter so the test terminates rather than hangs); (ii) remove `return_exceptions=True` and assert a test where delivery 1 raises and delivery 2 must still be attempted goes red on delivery 2's request count; (iii) remove the `batch = []` initialisation and assert the raise-path test goes red with `UnboundLocalError`. Fail loudly when the check cannot run: an exception the worker survives must still be logged at ERROR with the delivery id, so "recovered" is not spelled the same as "nothing happened". Boundary and tie: an empty batch sleeps exactly `poll_interval`, and a batch of exactly `BATCH_SIZE` does not sleep before the next iteration.
