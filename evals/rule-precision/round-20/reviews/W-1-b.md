### Critical: the signature is computed over bytes that are never the bytes sent, and does not cover the timestamp
File: app/webhooks/signing.py — `sign()`; app/webhooks/delivery.py — `send_once()`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` with the timestamp excluded, while `send_once` passes `json=delivery.payload` so httpx serializes the body itself (compact separators, insertion order), and `docs/webhooks.md` tells every customer the MAC is over `"{timestamp}.{raw_request_body}"`.
What breaks in production: every receiver that implements the documented verification rejects every delivery as a forgery, and because the timestamp is outside the MAC an attacker can rewrite `X-Acme-Timestamp` freely, so the documented five-minute replay window stops nothing.
Fix: build the body once and sign exactly it — in `signing.sign` compute `body = serialize(payload).encode()`, `ts = str(int(time.time()))`, `mac = hmac.new(secret.encode(), ts.encode() + b"." + body, hashlib.sha256)`, and return `(ts, "sha256=" + mac.hexdigest(), body)`; in `send_once` send `content=body` with the explicit `Content-Type`, never `json=`, so httpx cannot re-serialize. Preserve the header names, the `sha256=` prefix, and the `sort_keys=True` serialization the docs describe — do not "fix" this by relaxing the doc (clause 4). Allow side (clause 1): pin that a receiver-shaped test recomputing `hmac(secret, request.headers[TIMESTAMP_HEADER] + "." + request.content)` **equals** the `X-Acme-Signature` header on a valid delivery, not merely that a tampered one fails. Red-prove each clause separately (clause 2): (a) drop `ts` from the MAC input — the receiver-shaped equality reddens; (b) revert `content=` to `json=` with a payload whose insertion order differs from sorted order — reddens on byte mismatch; (c) flip one byte of the transmitted body — reddens. Clause 3: if `serialize` raises on a non-JSON-serializable payload, let it propagate and mark the delivery `failed_permanent` with the exception text — an unsigned or empty-body POST must never be sent. Clause 5: the receiver's freshness boundary is `now - ts >= 300` → reject (at exactly 300s it is rejected), and two deliveries may share one `ts`, so dedupe on `event_id` and never on the timestamp.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: app/webhooks/signing.py — `new_signing_secret()`
What is wrong: the secret is `random.choice` over an alphanumeric alphabet, i.e. Mersenne Twister, which is seeded predictably and whose internal state is recoverable from observed output, and `SECRET_BYTES = 32` names characters rather than bytes so the constant misstates the strength it claims.
What breaks in production: an attacker who can predict or reconstruct the RNG state forges `X-Acme-Signature` on arbitrary payloads, so a customer acts on fabricated `invoice.paid` events that never happened.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`, drop `random`/`string`/`_ALPHABET`), and rename the constant to what it now measures. Preserve the `whsec_` prefix and the property that the returned value is URL-safe and printable, since customers paste it into config (clause 4). Allow side (clause 1): keep an assertion that a freshly generated secret still starts with `SECRET_PREFIX` and is accepted end-to-end by `sign`/`verify` — a generator that returned a constant would satisfy a uniqueness test alone. Red-prove separately (clause 2): (a) revert to `random.choice` under a fixed `random.seed(0)` and assert two successive secrets differ across processes — reddens; (b) stub `secrets.token_urlsafe` to a constant — the distinctness assertion over 1000 draws reddens. Clause 3: do not wrap the generation in `try/except` — if the OS entropy source raises, the request must fail with a 5xx rather than fall back to `random`, and the endpoint must not persist a `WebhookEndpoint` row with a placeholder secret. Clause 5: `token_urlsafe(32)` yields a 43-character body, so any length assertion must compare against `len(SECRET_PREFIX) + 43` and not the old `+ 32`; two endpoints created in the same microsecond must still receive different secrets.

### Critical: signature comparison in `verify` is not constant time
File: app/webhooks/signing.py — `verify()` line `return expected == signature`
What is wrong: the shipped verification helper compares an HMAC with `==`, which short-circuits on the first differing byte, while `docs/webhooks.md` instructs customers to "compare it against your own computation using a constant-time comparison" (RS1).
What breaks in production: any caller of this helper — an inbound-verification path, a customer copying our reference implementation — leaks the expected digest byte-by-byte to a timing oracle, letting an attacker construct a valid signature without the secret.
Fix: `return hmac.compare_digest(expected, signature)`, and guard the non-`str` case by coercing with `str(signature or "")` before comparison so a `None` header cannot raise inside the comparator. Preserve the function's return type and its acceptance of the `sha256=`-prefixed form — do not "fix" it by stripping the prefix and comparing hex only (clause 4). Allow side (clause 1): pin that a signature produced by `sign` with the correct secret still returns `True`, since `return False` satisfies every rejection test. Red-prove separately (clause 2): (a) revert to `==` with a lint/AST check over `signing.py` forbidding `==` on a name matching `signature|digest|mac|secret` — reddens; (b) replace `compare_digest` with `len(a) == len(b)` — the wrong-secret rejection test reddens. Clause 3: if the header is absent or not a string the function must return `False` and the caller must log a rejection, never raise a `TypeError` that a broad `except` upstream converts into an accept. Clause 4/5: the boundary is byte-length — `compare_digest` is only constant-time for equal-length inputs, so document that a truncated signature is rejected by length before the comparison, and reject rather than pad.

### Critical: `list_deliveries` has no tenancy predicate
File: app/api/routes/settings.py — `list_deliveries()`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id` taken from the path, with no join to `WebhookEndpoint.org_id == user.org_id`, while both sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) do filter on `user.org_id` — the seed pattern was not propagated (R3, security-relevant).
What breaks in production: any authenticated customer can iterate `endpoint_id` and read another organization's delivery history — event types, event ids, timestamps and delivery outcomes — a cross-tenant data leak.
Fix: join the parent and scope it: `.join(webhook_models.WebhookEndpoint, webhook_models.WebhookEndpoint.id == webhook_models.WebhookDelivery.endpoint_id).filter(webhook_models.WebhookEndpoint.org_id == user.org_id, webhook_models.WebhookDelivery.endpoint_id == endpoint_id)`, and raise `HTTPException(404)` — not 403 — when the endpoint does not resolve under that scope, so ids stay non-enumerable. Preserve the existing `order_by(created_at.desc())` and `limit` behaviour for the legitimate owner (clause 4). Allow side (clause 1): pin that the owning user still receives their own deliveries, in the same order and count, as an explicit test — a predicate that returns `[]` for everyone passes the cross-tenant test alone. Red-prove separately (clause 2): (a) delete the `org_id` predicate — the cross-org test reddens with a non-empty list; (b) delete the 404 branch — the enumeration test reddens on a `200 []`. Clause 3: if `user.org_id` is `None` the handler must deny and log, never fall through to an unscoped query. Clause 5: the boundary is the endpoint that was just reassigned to another org — scope on the `org_id` read in the same transaction as the deliveries, and since `endpoint_id` is a primary key the join is unique, so no delivery can appear under two orgs.

### Critical: the unique index on `event_id` alone makes fan-out to more than one endpoint impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `delivery.enqueue_for_event` inserts one `WebhookDelivery` per matching active endpoint for a single `event_id`, so the second row of any fan-out violates the index — the uniqueness the design needs is per endpoint, not per event.
What breaks in production: for every organization with two or more subscribed endpoints, the entire enqueue transaction raises `IntegrityError` and rolls back, so **no** endpoint receives the event — and the dispatcher's blanket `except Exception: log.warning` turns that into a silent, unretried loss of billing events.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` and make the insert idempotent with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` (or a `session.merge` equivalent) so a redelivered dispatch is a no-op rather than a raise. Preserve the deduplication guarantee that made the original index worth having — one delivery row per (endpoint, event) — do not fix this by dropping uniqueness entirely (clause 4). Allow side (clause 1): pin that an org with two active endpoints subscribed to `invoice.paid` produces exactly two rows, alongside the test that a repeated dispatch of the same `event_id` produces no third row. Red-prove separately (clause 2): (a) restore the single-column index — the two-endpoint test reddens with an integrity error; (b) remove `ON CONFLICT` and dispatch the same event twice — the idempotency test reddens. Clause 3: the migration must fail loudly if the table already contains duplicate `(endpoint_id, event_id)` pairs rather than silently skipping index creation — no `IF NOT EXISTS` on this statement. Clause 5: the boundary is one event with two endpoints where one is inactive at enqueue time and reactivated later — the reactivated endpoint gets no backfill row, so state that explicitly; and two endpoints of *different* orgs sharing an `event_id` must both be allowed.

### Critical: the migration's status CHECK constraint does not admit the status the code writes

What is wrong: `models.STATUSES` and `delivery._finish(...,"failed_permanent",...)` use `failed_permanent`, but the SQL constraint spells that member `failed` — one member of a four-member set drifted across the boundary (R2/R40; `in_flight`, `pending` and `delivered` match, so this is the only divergence).
What breaks in production: the first delivery to exhaust `MAX_ATTEMPTS` raises `CheckViolation`, `_finish` aborts, and the row is left in `in_flight` forever — the terminal-failure path, which is the only path that records why a customer's endpoint is broken, never completes.
Fix: correct the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive both sides from one source — have `models.py` build the constraint from `STATUSES` (a `CheckConstraint` in `__table_args__`) so the literal cannot drift again; `STATUSES` already exists in the diff and is currently referenced by nothing. Preserve the constraint itself — do not fix this by deleting the CHECK (clause 4). Allow side (clause 1): pin that a delivery reaching `MAX_ATTEMPTS` is readable back with `status == "failed_permanent"`, not only that the insert no longer raises. Red-prove separately (clause 2): (a) revert the migration literal to `failed` — the exhaustion test reddens with a check violation; (b) add a fifth member to `STATUSES` without migrating — the generated-constraint parity test reddens. Clause 3: a status the constraint rejects must surface as a loud failure of the worker's `_finish` with the delivery id logged, not be swallowed into a retry loop that re-attempts a completed delivery. Clause 5: name the tie — a delivery that both exhausts attempts and receives a late 2xx must resolve to exactly one terminal status, and the write that arrives second must be rejected rather than overwrite `delivered`.

### Critical: `time.sleep` inside the async retry loop blocks the whole worker
File: app/webhooks/delivery.py — `deliver()` line `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered `BATCH_SIZE`-wide, but it retries with the blocking `time.sleep` instead of `await asyncio.sleep`, and it retries in-process rather than rescheduling `next_attempt_at` — so the `backoff_for`/`next_attempt_at` machinery the schema provides is never used after enqueue.
What breaks in production: one slow endpoint stalls the event loop for up to 30 s of backoff plus five 30 s request timeouts, far past the 60 s lock TTL, so the lock expires mid-batch, a second worker claims nothing but deletes the first worker's key, and every other delivery in the batch is frozen behind a single dead customer.
Fix: make retries persistent rather than in-process — on a non-2xx or transport error, write `attempts += 1`, `status = "pending"`, `next_attempt_at = now + backoff_for(attempts)` and return; let the next `_claim_batch` pick it up, and mark `failed_permanent` only when `attempts >= MAX_ATTEMPTS`. Where any sleep remains in a coroutine use `await asyncio.sleep`. Preserve the documented schedule (at most 5 attempts, roughly 2/4/8/16 s) and the existing `backoff_for` helper — do not fix this by shortening the timeout or dropping retries (clause 4). Allow side (clause 1): pin that a delivery whose first attempt returns 200 is marked `delivered` with `attempts == 1` and is never rescheduled, alongside the test that a failing one is rescheduled. Red-prove separately (clause 2): (a) reintroduce `time.sleep` and assert the batch's wall-clock under a fake transport with two slow endpoints stays under a bound — reddens; (b) drop the `next_attempt_at` update — the "second claim happens no earlier than the backoff" test reddens; (c) drop the `attempts >= MAX_ATTEMPTS` branch — the bounded-attempts test reddens. Clause 3: if the reschedule write itself fails, the row must be left claimable (not `in_flight`) and the failure logged with the delivery id — an unwritable reschedule must not read as a completed delivery. Clause 5: the boundary is `attempts == MAX_ATTEMPTS` — the fifth attempt is made and the sixth is not; and two deliveries with an identical `next_attempt_at` must both be claimed, so the claim order needs a tie-break on `id` (see the ordering finding below).

### Critical: the endpoint URL is unrestricted, so the worker is an SSRF proxy
File: app/api/routes/settings.py — `create_webhook_endpoint()` URL check; app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: validation is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plain `http://`, admits any scheme merely beginning with `http`, and applies no host restriction at all, while `follow_redirects=True` means even a permitted host can bounce the request to an internal one (RS3 — an externally supplied value reaching a network sink with no semantic floor).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or an internal service URL and our worker issues authenticated-looking POSTs from inside the VPC, exfiltrating cloud credentials or driving internal state changes; `docs/webhooks.md`'s claim that "Only `https://` URLs are accepted" is false as written.
Fix: validate in the Pydantic model rather than the handler — make `EndpointIn.url` an `HttpUrl` with `scheme == "https"` enforced (`parsed.scheme != "https"` → 422), resolve the hostname at registration and at each send, and reject any address in a private, loopback, link-local, multicast or reserved range via `ipaddress.ip_address(...).is_global`; set `follow_redirects=False` and treat a 3xx as a permanent failure. Preserve the ability to deliver to legitimate public HTTPS endpoints on non-standard ports, and keep the 422 status the API already returns (clause 4). Allow side (clause 1): pin that `https://hooks.example.com/acme` still registers **and** still receives a delivery — a validator that rejects everything satisfies every SSRF test. Red-prove separately (clause 2): (a) register `http://…` — reddens the scheme test; (b) register a host resolving to `127.0.0.1` — reddens the range test; (c) set `follow_redirects=True` and serve a 302 to a private address — reddens the redirect test. Clause 3: when DNS resolution fails or returns no address the registration must be refused and the delivery deferred with a named error, never sent "because the check could not run". Clause 5: state the boundary — resolution is re-checked at send time because DNS can be rebound between registration and delivery, and an address that resolves to both a public and a private record is rejected.

### Critical: the delivered body contains no event id or type, so the documented deduplication is impossible
File: app/webhooks/delivery.py — `send_once()` posts `json=delivery.payload`; app/events/dispatcher.py — `enqueue_for_event(payload=envelope.payload)`
What is wrong: only the raw `envelope.payload` is transmitted — `event_id` and `event_type` are stored on the `WebhookDelivery` row but never serialized into the request — while `docs/webhooks.md` instructs receivers to "deduplicate on `event_id`" (R40: producer wire shape versus the contract the consumer was handed).
What breaks in production: at-least-once delivery plus a body with no identity means a retried `invoice.paid` is indistinguishable from a second payment, so customers double-apply financial events; they also cannot route by type without inspecting the payload shape.
Fix: build an envelope in `send_once` — `body = {"id": f"evt_{delivery.event_id}", "type": delivery.event_type, "created_at": delivery.created_at.isoformat(), "data": delivery.payload}` — serialize it once via `signing.serialize`, sign those bytes and post them as `content=` (this composes with the signing fix above; `serialize` already exists in the diff and is currently bypassed by `json=`). Preserve the customer-visible payload verbatim under `data` — do not fix this by flattening the id into the payload namespace, which would collide with customer keys (clause 4). Allow side (clause 1): pin that a valid delivery's transmitted body parses to the full four-key envelope with `data` byte-equal to the stored payload, not only that `id` is present. Red-prove separately (clause 2): (a) drop `id` from the envelope — the receiver-shaped dedupe test reddens; (b) drop `type` — the routing test reddens; (c) nest the payload one level differently — the `data` equality test reddens. Clause 3: if `delivery.event_type` or `event_id` is missing the send must be refused and the delivery marked `failed_permanent` with that reason — never post a partial envelope. Clause 5: the boundary is retry — the same `event_id` must appear on all five attempts and must differ between two events with identical payload bytes, so derive `id` from the row's `event_id` and never from a hash of the payload.

### Major: the Redis lock is not atomic and is released by unconditional delete
File: app/webhooks/delivery.py — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act with an interleaving window, the `set`/`expire` pair is two round-trips so a crash between them leaks a lock with no TTL, and the `finally` deletes the key unconditionally even when the 60 s TTL already expired and another worker owns it.
What breaks in production: two workers claim and deliver the same batch, so customers receive duplicate `invoice.paid` events that they cannot deduplicate (the body carries no event id, per the finding above).
Fix: acquire with a single atomic call carrying a fenced token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script that deletes only when the stored value equals the token. Preserve single-writer semantics and the poll-and-continue behaviour when the lock is held (clause 4). Allow side (clause 1): pin that a worker with no competitor still acquires, processes and releases, and that the *next* acquire after release succeeds — a release that never deletes satisfies the mutual-exclusion test alone. Red-prove separately (clause 2): (a) revert to `get`+`set` and drive two concurrent acquires — the mutual-exclusion test reddens; (b) drop `ex=` — the TTL test reddens; (c) replace the compare-and-delete with a plain `delete` and expire the key mid-batch — the "does not delete another owner's lock" test reddens. Clause 3: if Redis is unreachable, `_acquire_lock` must raise or return `False` and the worker must sleep and retry — never proceed unlocked because the check could not run. Clause 5: state the boundary — a batch still running at exactly the TTL must not write, so the token is re-verified before `_finish`, and two workers presenting the same token is impossible by construction.

### Major: ORM instances are used after their session has closed
File: app/webhooks/delivery.py — `_claim_batch()` returns `rows` after the `with session_scope()` block; `deliver()` reads `endpoint.url`/`endpoint.signing_secret` after its own block
What is wrong: both functions let mapped instances escape the session that loaded them, then read attributes (`delivery.attempts`, `delivery.id`, `delivery.payload`, `endpoint.signing_secret`) outside it; under SQLAlchemy's default `expire_on_commit=True` every one of those reads triggers a refresh on a closed session.
What breaks in production: the worker raises `DetachedInstanceError` on the first claimed row, so the entire delivery pipeline is dead from the first batch — and if the project's `session_scope` happens to set `expire_on_commit=False`, the code instead reads silently stale values.
Fix: return plain data, not mapped instances — have `_claim_batch` return a list of dataclasses or dicts built inside the session (`id`, `endpoint_id`, `attempts`, `payload`, `event_id`, `event_type`), and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside its own session block before any `await`. Preserve the in-session `status = "in_flight"` write that makes claiming exclusive (clause 4). Allow side (clause 1): pin that a normal batch is claimed and delivered end-to-end against a real session, not only that no exception is raised. Red-prove separately (clause 2): (a) return the mapped rows again and run the worker against a session configured with `expire_on_commit=True` — reddens; (b) move the `signing_secret` read after the `with` block — reddens on the same test. Clause 3: if the endpoint row is missing (`session.get` returns `None`), fail the delivery loudly as `failed_permanent` with that reason rather than dereferencing `None`. Clause 5: name the boundary — the claim write and the attribute reads happen in one transaction, and a row claimed at exactly the batch limit must be either fully claimed or not claimed at all.

### Major: naive and aware datetimes are mixed, and the migration column type disagrees with the model

Clause 5: the boundary is `next_attempt_at == now` — it is claimable (`<=`), and two rows sharing that instant are both claimed.

### Major: `in_flight` has no exit on the failure path and no reaper
File: app/webhooks/delivery.py — `_claim_batch()` sets `status = "in_flight"`; `run_worker()`
What is wrong: only `_finish` moves a row out of `in_flight`, `_claim_batch` selects `status == "pending"` exclusively, and nothing bounds how long a row may stay claimed — so a worker crash, a `CheckViolation` in `_finish`, or the blocking-sleep stall above wedges the row permanently (R38 Part 1: no failure-exit, no bounded timeout).
What breaks in production: deliveries silently stop for the affected customers with no alert and no operator affordance short of manual SQL, and the `attempts` counter never advances so the failure is invisible in the deliveries API.
Fix: record `claimed_at` when the status is set, and add a reclaim predicate to `_claim_batch` — `status == "pending" OR (status == "in_flight" AND claimed_at < now - CLAIM_TIMEOUT)` — with `CLAIM_TIMEOUT` derived from `REQUEST_TIMEOUT * MAX_ATTEMPTS` plus the backoff sum, and wrap `deliver` in a `try/except Exception` that returns the row to `pending` with an incremented `attempts`. Preserve exclusive claiming — the reclaim must not let two workers hold one row inside the timeout (clause 4). Allow side (clause 1): pin that a row claimed one second ago is **not** reclaimed, alongside the test that a row claimed past the timeout is. Red-prove separately (clause 2): (a) remove the reclaim predicate — the stale-row test reddens; (b) remove the `except` re-queue — the crash-mid-delivery test reddens; (c) set `CLAIM_TIMEOUT` to zero — the not-yet-stale test reddens. ### Major: a failed enqueue is swallowed, and it is not atomic with the event write
File: app/events/dispatcher.py — `except Exception as exc: log.warning(...)`
What is wrong: the event row commits in its own `session_scope`, the webhook enqueue then runs in a second transaction, and any failure — including the `IntegrityError` from the unique-index defect above — is downgraded to a warning while `dispatch` still returns the event id as if delivery were scheduled.

Preserve the property that a slow or failing webhook endpoint cannot roll back the event write — only the *row insert* joins the transaction, never the HTTP call (clause 4). Allow side (clause 1): pin that a successful dispatch still returns the event id and still creates the delivery rows — a version that re-raises on everything would fail an unrelated subscriber error. Red-prove separately (clause 2): (a) force the insert to raise — the "event write is rolled back too" test reddens; (b) restore the blanket `except Exception` — the propagation test reddens; (c) move the HTTP send inside the transaction — the "transaction not held across the network call" test reddens. Clause 3: if the enqueue cannot run at all (webhook module import failure, DB unavailable), `dispatch` must raise rather than return an event id that implies scheduling. Clause 5: the boundary is the event with zero matching endpoints — that must commit successfully with zero delivery rows, and must be distinguishable in logs from an enqueue that failed.

### Major: three documented behaviours are not implemented
File: docs/webhooks.md — the Retries section and the "Only `https://` URLs are accepted" line
What is wrong: the doc promises exponential backoff "with jitter" (`backoff_for` is `2**attempt` exactly, no jitter), that "a 4xx is permanent and we stop immediately" (`deliver` retries every non-2xx status up to `MAX_ATTEMPTS`), and https-only registration (the handler accepts `http://`) — three claims the change's own code contradicts (R29).
What breaks in production: a customer endpoint returning 400 is hammered five times per event by every worker in lockstep, since without jitter all deliveries of the same batch retry at the same instants — a self-inflicted thundering herd against an endpoint already telling us to stop.
Fix: implement what the doc promises rather than weakening the doc — add jitter (`backoff_for` returns `2**attempt` scaled by a random factor in `[0.5, 1.5)` drawn from `random`, which is acceptable here because it is not key material), and branch in `deliver` so `400 <= status < 500` (excluding 408 and 429) goes straight to `failed_permanent`. Preserve retrying on 5xx, timeouts and connection errors, and keep the documented ceiling of 5 attempts (clause 4). Allow side (clause 1): pin that a 500 is still retried and that a 429 is still retried — a change that makes every 4xx terminal must not also terminate the rate-limited case. Red-prove separately (clause 2): (a) remove the 4xx branch — the "stops after one attempt on 400" test reddens; (b) remove the 429 exclusion — the "429 is retried" test reddens; (c) remove jitter — the "two deliveries do not share a retry instant" test reddens. Note this changes `test_backoff_grows_exponentially`, which asserts exact equality with 2/4/8/16: it must become a range assertion, which is the correct pinning of a jittered schedule. Clause 3: a response with no status (transport error) must route to the retry path, not to the 4xx path, and an unclassifiable status must retry rather than silently terminate. Clause 5: the boundary is status 400 exactly — permanent; 408 and 429 — retried; 500 — retried.

### Major: signature headers are logged and unbounded third-party response bodies are persisted

### Major: the worker exits permanently on any exception outside `deliver`
File: app/webhooks/delivery.py — `run_worker()`
What is wrong: `_acquire_lock` and `_claim_batch` are called with no exception handling inside `while True`, and `asyncio.gather` without `return_exceptions=True` propagates the first `deliver` failure, so a transient Redis or DB error escapes the loop; `batch` is also bound only inside the `try`, so the `if not batch` line references a name that need not exist.

Red-prove separately (clause 2): (a) remove the outer `except` and raise from `_claim_batch` — the survival test reddens; (b) remove `return_exceptions=True` and raise from one `deliver` — the "other deliveries still complete" test reddens; (c) remove the `CancelledError` re-raise — the shutdown test reddens by hanging. Clause 3: a repeated failure must escalate — after N consecutive failed iterations log at ERROR and stop claiming, so a permanently broken worker is loud rather than spinning silently. Clause 5: the boundary is an empty batch versus a failed claim — both must sleep, and the two must be distinguishable in the logs.

## Cross-cutting verification

- **Tenancy predicate**: checked all four queries in the diff that read tenant-scoped data. `list_api_keys` (pre-existing), `list_webhook_endpoints` and `create_webhook_endpoint` all bind `user.org_id`; `list_deliveries` is the only one that does not — reported above. Worker-side queries (`_claim_batch`, `_finish`, `deliver`) are correctly unscoped.
- **Status literals**: `models.STATUSES` declares four members; the migration CHECK declares four; only `failed_permanent`/`failed` diverges. `"pending"` appears as a literal in the model default and in `_claim_batch`, `"in_flight"` in `_claim_batch`, `"delivered"`/`"failed_permanent"` in `deliver` — none of the five call sites imports `STATUSES`, so the same drift can recur at any of them.
- **Datetime construction**: five sites construct timestamps. `models._now`, `_claim_batch`, `_finish` and `dispatcher.dispatch` are timezone-aware; `enqueue_for_event`'s `datetime.utcnow()` is the sole naive one. All five migration columns are `TIMESTAMP` against `DateTime(timezone=True)` models — the divergence is systemic, not a single column.
- **Serialization**: `signing.serialize` is the only declared wire-format helper, and `send_once` bypasses it by handing `json=` to httpx; `sign` uses it. That split is the root of the signature-mismatch Critical.
- **Redirect/scheme handling**: URL restriction exists at exactly one place (`create_webhook_endpoint`), and the send path adds `follow_redirects=True`, which reopens whatever that check closed — no second validation exists on the send side.

## Codebase awareness

Helpers already present in the change that new code reimplements or bypasses, with evidence:

- `signing.serialize()` (signing.py) — bypassed by `send_once`'s `json=delivery.payload`; this is the R1 case where the duplicate (httpx's serializer) differs behaviourally from the shared helper on key order and separators, and that difference is the defect.
- `models._now()` (models.py) — reimplemented as `datetime.utcnow()` in `enqueue_for_event`, and reimplemented again as inline `datetime.now(timezone.utc)` in `_claim_batch`, `_finish` and `dispatch`.
- `models.STATUSES` (models.py) — declared and then referenced by nothing; both the migration CHECK and the five status literals in `delivery.py` restate its members independently.
- `delivery.backoff_for()` (delivery.py) — computed correctly but only ever consumed by the blocking in-process sleep; `WebhookDelivery.next_attempt_at`, the column that exists to carry the schedule, is written once at enqueue and never updated.
- `WebhookEndpoint.event_types` (models.py) — the per-endpoint subscription filter is applied in `enqueue_for_event`, and then gated a second time by `dispatcher.WEBHOOK_EVENT_TYPES`, which the endpoint model has no way to consult.
