### Critical: the HMAC is computed over a different byte string than the body that is transmitted
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` (spaces after `,` and `:`, keys sorted) while `send_once` transmits the body via `client.post(..., json=delivery.payload)`, which httpx re-serializes with its own separators and insertion order, so the bytes the receiver hashes are not the bytes we signed.
What breaks in production: every customer who implements the documented verification recomputes the HMAC over the raw body they received and gets a mismatch, so 100% of deliveries are rejected as forged and no webhook integration ever works.
Fix: make one serialization the single source of both the MAC input and the wire body — have `serialize` return `bytes` via `json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, have `sign` return `(timestamp, signature, body_bytes)` (or expose `serialize` to the caller), and change `send_once` to `client.post(endpoint.url, content=body, headers=headers)` with an explicit `Content-Type: application/json`, never `json=`. Preserve what makes the feature useful: the body must still be valid JSON parseable by the customer and `Content-Type` must remain `application/json` — do not fix this by dropping the signature or by loosening verification. Deny/allow pair to pin: a test that feeds the ACTUAL bytes captured by `httpx.MockTransport` into an independently written HMAC computation must PASS (allow side, R40's actual-output-through-actual-consumer round trip), and a test asserting that a body differing by one byte fails that recomputation must FAIL verification (deny side). Red-prove each clause separately by execution: (i) change `separators` in `serialize` only — the round-trip assertion must redden while the deny test stays green; (ii) swap `content=body` back to `json=payload` — the round-trip assertion must redden; (iii) drop the `Content-Type` header — a distinct assertion on the captured header must redden. Fail loudly when the check cannot run: if `captured["body"]` is absent (the transport handler never fired) the test must raise a named failure such as `pytest.fail("transport handler never invoked; nothing was signed")` rather than skipping — "examined nothing" must not be spelled like "found nothing". Boundary and tie: the comparison is over the exact byte sequence, so an empty payload `{}` serializes to `b"{}"` and must still be signed and verified rather than short-circuited, and two payloads that are equal as Python dicts but differ in key insertion order must produce the SAME signature — that is exactly what `sort_keys=True` on both sides buys and what the test must assert.

### Critical: the timestamp is not covered by the signature, so the documented replay window authenticates nothing
File: `app/webhooks/signing.py` — `sign`, line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: the returned `timestamp` is never fed into the MAC, yet `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that the five-minute timestamp window "is what stops a captured request from being replayed".
What breaks in production: an attacker who captures one delivery can rewrite `X-Acme-Timestamp` to the current second and replay the identical body and signature forever, so the replay defence the documentation sells to customers does not exist (R49: a claim strictly stronger than the implementation, relied on elsewhere as the boundary).
Fix: change `sign` to compute `hmac.new(secret.encode(), f"{timestamp}.".encode() + body_bytes, hashlib.sha256)` and change `verify` to take the timestamp as an explicit parameter so it MACs the same string; keep the wire format `sha256=<hex>` and the two header names unchanged so the documented contract in `docs/webhooks.md` still describes the code. Do not fix this by weakening the doc instead of the code — the doc's construction is the correct one and is what customers have been told to implement. Deny/allow pair: a signature produced at timestamp `T` must still verify when checked with timestamp `T` (allow side), and the same signature presented with timestamp `T+1` must fail (deny side); add the freshness check as a separate, named function so a stale-but-authentic request is rejected with a distinguishable reason. Red-prove each clause by execution: (i) remove the `f"{timestamp}."` prefix from `sign` only — the "same signature with a different timestamp is rejected" assertion must redden while the happy-path assertion stays green; (ii) remove the freshness comparison only — the stale-timestamp assertion must redden; (iii) make `verify` ignore its timestamp argument — the tampered-timestamp assertion must redden. Fail loudly when the check cannot run: a `X-Acme-Timestamp` that is absent, empty, or non-numeric must raise a named rejection rather than being coerced or defaulted to `now`. Boundary and tie: state the window as `abs(now - ts) <= 300` and pin which side exactly 300 falls on (accept at exactly 300, reject at 301), and reject NEGATIVE skew beyond the same bound so a far-future timestamp is not accepted — a tie at exactly the boundary must resolve to accept, and the test must assert both 300 and 301.

### Critical: signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: the recomputed HMAC is compared to the caller-supplied signature with `==`, which short-circuits on the first differing byte, even though `hmac.compare_digest` is available from the `hmac` module already imported two lines above (RS1; the change reimplements a security control that the stdlib it already imports provides).
What breaks in production: any consumer of this helper — the reference implementation this repo ships and any inbound verification path that adopts it — leaks the expected signature one byte at a time under timing measurement, letting an attacker forge a valid signature for an arbitrary payload without ever learning the secret.
Fix: replace the comparison with `hmac.compare_digest(expected, signature)`, guarding for a non-`str` or non-ASCII `signature` by rejecting before the call rather than letting `compare_digest` raise. Preserve what made the function useful: `verify` must still return `True` for a genuinely valid signature — do not fix by making it always return `False`. Deny/allow pair: a signature produced by `sign` with the same secret must still return `True` (allow side, RT10 — a fix that only tightens is unmeasured in the direction that gets controls switched off), and a signature produced with a different secret must return `False` (deny side). Red-prove each clause by execution: (i) revert `compare_digest` to `==` — a test asserting the call path uses `hmac.compare_digest` (monkeypatch it with a counting wrapper and assert the count is 1) must redden while the value assertions stay green; (ii) make `verify` return `True` unconditionally — the wrong-secret assertion must redden; (iii) pass a `bytes` signature — the type-rejection assertion must redden. Fail loudly when the check cannot run: a `signature` of `None`, of the wrong type, or not matching `^sha256=[0-9a-f]{64}$` must return `False` through an explicitly named branch, never through an exception that a caller's bare `except` can convert into a pass. Boundary and tie: two signatures of DIFFERENT length must still be rejected in constant time relative to the secret — `compare_digest` handles this, so the test must include a truncated signature (63 hex chars) and a signature with the `sha256=` prefix missing, and assert both are `False`.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, line `random.choice(_ALPHABET) for _ in range(SECRET_BYTES)`
What is wrong: `random` is the Mersenne Twister, whose internal state is fully recoverable from 624 consecutive outputs and which is seeded from process state, so the secrets are predictable rather than unguessable; `SECRET_BYTES` is also a misnomer — it is a character count, not a byte count.
What breaks in production: an attacker who provisions endpoints in their own account observes enough generator output to reconstruct the shared PRNG state and then derives another tenant's signing secret, letting them forge signed `invoice.paid` deliveries into that tenant's system.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_hex(SECRET_BYTES)` (import `secrets`, drop the `random` and `string` imports and `_ALPHABET`), and rename the constant to `SECRET_BYTES = 32` meaning 32 random bytes rendered as 64 hex characters so the name and the value agree. Preserve what made it useful: the `whsec_` prefix must survive so existing customer key-detection tooling keeps working, and the returned value must remain a `str`. Deny/allow pair: the allow case is that a freshly generated secret still verifies a signature made with it end to end (`verify(new_signing_secret_value, payload, sig)` is `True`); the deny case is a statistical distinctness assertion — 1000 generated secrets yield 1000 distinct values. Red-prove each clause by execution: (i) monkeypatch `secrets.token_hex` to return a constant — the distinctness assertion must redden while the end-to-end verify assertion stays green; (ii) drop `SECRET_PREFIX` from the return — the prefix assertion must redden; (iii) halve the length argument — the length assertion must redden. Note the existing `test_new_signing_secret_has_prefix_and_length` is green under the defective code and stays green under a constant generator, so it is NOT the red-proof for clause (i). Fail loudly when the check cannot run: if the process has no `secrets` entropy source the call raises, and that exception must propagate out of `create_webhook_endpoint` as a 5xx — endpoint creation must never fall back to a weaker generator. Boundary and tie: state that the comparison of interest is length equality `len(secret) == len(SECRET_PREFIX) + 2 * SECRET_BYTES`, and that a collision between two generated secrets (a tie) is a test failure, not a retry.

Red-prove each clause by execution: (i) re-add `signing_secret` to `to_dict()` — the list-route absence assertion must redden while the create-route presence assertion stays green; (ii) remove the `{**..., "signing_secret": secret}` merge from the create route — the presence assertion must redden. ### Critical: `list_deliveries` has no tenancy filter, so any authenticated user can read any organization's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`, the query filtered only by `WebhookDelivery.endpoint_id == endpoint_id`
What is wrong: `endpoint_id` is taken straight from the path and the query never joins to `WebhookEndpoint` to confirm `org_id == user.org_id`, even though every sibling route in the same file — the pre-existing `get_profile` and `list_api_keys`, and the newly added `list_webhook_endpoints` — scopes by `user.org_id` (R3: the tenancy pattern was propagated to two of the three new routes and missed on the third).
What breaks in production: any logged-in customer enumerates `endpoint_id` values and reads other tenants' delivery history — event types, event ids, attempt counts and HTTP status codes — which is a cross-tenant data breach and discloses which of a competitor's invoices paid and when.
Fix: join the ownership check into the same query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — so the scope cannot be bypassed by a later refactor that drops a separate pre-check, and return 404 (not 403) for an endpoint belonging to another org so the route does not confirm existence. Preserve what made it useful: the owner must still receive their own deliveries in `created_at DESC` order with the `limit` applied. Deny/allow pair: the allow case is a request by the endpoint's owning user returning the expected rows (RT10 — an authz fix that only denies would satisfy every other clause here); the deny case is a request by a user in another org returning 404 AND, per RT8, asserting that no delivery row was read — assert the response body is `[]`/404 and that a spy on the query returned zero rows, because a status-only assertion passes even if the rows were fetched and then discarded. Red-prove each clause by execution: (i) delete the `WebhookEndpoint.org_id == user.org_id` predicate — the cross-tenant deny assertion must redden while the owner assertion stays green; (ii) change the join condition to a cross join — the owner-row-count assertion must redden; (iii) change 404 to 403 — the status assertion must redden. Fail loudly when the check cannot run: when `endpoint_id` does not resolve to any row at all, return the same 404 through an explicitly named branch rather than an empty list, so "no such endpoint" and "endpoint exists but is yours and empty" are not spelled the same. Boundary and tie: an endpoint whose `org_id` is NULL (possible only through direct DB manipulation, but the column is nullable in neither schema — state it) must be treated as NOT owned; and where two deliveries share `created_at` exactly, the ordering tie must be broken by `id DESC` so the `limit` truncation is deterministic.

### Critical: the unique index on `event_id` alone makes fan-out to a second endpoint fail, and the failure is swallowed
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`

Red-prove each clause by execution against a real database, not a mock: (i) revert the index to `(event_id)` — the two-endpoint fan-out assertion must redden; (ii) drop the index entirely — the duplicate-pair assertion must redden while the fan-out assertion stays green. Fail loudly when the check cannot run: `enqueue_for_event` must stop swallowing this — see the separate finding on `dispatcher.dispatch`'s bare `except Exception`; an enqueue that cannot write must surface, not warn. Boundary and tie: state that the tie case is exactly two endpoints of the same org subscribed to the same event type — both rows must exist — and that an endpoint whose `event_types` list excludes the type produces NO row, so the count for a three-endpoint org with one non-matching endpoint is exactly 2.

### Critical: the migration's status CHECK constraint does not contain the terminal status the code writes
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py::deliver` writing `"failed_permanent"` and `app/webhooks/models.py::STATUSES` declaring `"failed_permanent"`
What is wrong: the SQL allowlist spells the terminal failure state `failed` while both Python sites spell it `failed_permanent`, so the producer's enum spelling does not match the strict consumer's contract (R40; R18 — an allowlist updated on one side only).
What breaks in production: the first delivery that exhausts its five attempts hits `_finish(..., "failed_permanent", ...)`, Postgres rejects the UPDATE with a check-constraint violation, the transaction aborts, and the row is left in `in_flight` forever — so exhausted deliveries are never recorded as failed and never retried, and the `GET .../deliveries` endpoint reports them as still in flight indefinitely.
Fix: define the status vocabulary once and derive both sides from it — change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and have `models.STATUSES` be the constant that `_finish` validates its `status` argument against before writing (`if status not in STATUSES: raise ValueError(...)`), replacing the current dead declaration of `STATUSES`. Preserve what made the constraint useful: the CHECK must stay — it is what caught this — so do not fix by dropping the constraint or by widening it to any TEXT. Deny/allow pair: the allow case is that writing each of the four members of `STATUSES` succeeds against a real database; the deny case is that writing `"failed"` or any string outside `STATUSES` is rejected — assert both the `ValueError` from `_finish` and, in a separate integration case, the `IntegrityError` from the database, because the Python guard alone would pass even with the SQL still wrong. Red-prove each clause by execution: (i) revert the SQL to `'failed'` — the integration assertion that `failed_permanent` persists must redden while the Python guard assertion stays green (this is the mutation that proves the two checks are independent); (ii) delete the `status not in STATUSES` guard — the `ValueError` assertion must redden; (iii) add a fifth member to `STATUSES` without touching the SQL — a test that asserts the Python tuple and the SQL CHECK list are the same set must redden. Fail loudly when the check cannot run: the set-equality test must fail with a named message if it cannot locate or parse the CHECK clause in the migration file, rather than passing on an empty parse. Boundary and tie: name the exact membership — `{"pending", "in_flight", "delivered", "failed_permanent"}` — and state that the two sets must be equal in BOTH directions, so a status present in SQL but absent from Python is equally a failure.

### Critical: endpoint URL validation admits plaintext HTTP and arbitrary internal hosts, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, line `if not parsed.scheme.startswith("http") or not parsed.netloc:`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http://` and also any scheme literally prefixed with `http` (`urlparse("httpfoo://h/x").scheme` is `"httpfoo"`), there is no check on the resolved host, and `docs/webhooks.md` states "Only `https://` URLs are accepted" — a surface-form prefix test standing in for the scheme allowlist the doc claims (R47/R49).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:6379/` and our worker POSTs signed, authenticated internal requests to it from inside the VPC, with `follow_redirects=True` letting even an external-looking host redirect into the internal range after the check has passed — a server-side request forgery with credential-bearing payloads.
Fix: replace the prefix test with an exact allowlist `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)`, resolve the hostname and reject any address in a private, loopback, link-local, or reserved range using `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`, set `follow_redirects=False` on the `AsyncClient` so a redirect cannot re-target after validation, and re-apply the address check at connection time (not only at registration) so a DNS record flipped after registration cannot bypass it. Preserve what made the feature useful: a legitimate public HTTPS endpoint on a non-443 port must still be accepted — do not fix by allowlisting only port 443. Deny/allow pair: the allow case is `https://hooks.example.com/acme` accepted with 201 and a row written; the deny cases are `http://hooks.example.com`, `httpfoo://hooks.example.com`, `https://169.254.169.254/`, `https://localhost/` and a URL with no host, each 422 AND — per RT8 — asserted to have written no `webhook_endpoints` row, since a status-only assertion passes even if the row was created. Red-prove each clause by execution: (i) revert `!= "https"` to `startswith("http")` — the `http://` and `httpfoo://` deny assertions must redden while the `https://` allow assertion stays green; (ii) delete the private-range check — the `169.254.169.254` deny assertion must redden; (iii) set `follow_redirects=True` again — a `MockTransport` test that returns a 302 to an internal host must redden on an assertion that the second request was never issued. Fail loudly when the check cannot run: a hostname that fails to resolve must be rejected with a named 422 ("endpoint host could not be resolved"), never accepted on the grounds that the check could not be performed. Boundary and tie: state that the scheme comparison is exact and case-insensitive (`parsed.scheme.lower() != "https"`, since `urlparse` lowercases but a caller-built check may not), that IPv6 literals and IPv4-mapped IPv6 (`::ffff:10.0.0.1`) fall on the DENY side, and that a host resolving to BOTH a public and a private address is denied — the tie resolves to deny.

### Critical: the delivery worker operates on detached ORM instances and cannot read their attributes
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside the `with`, consumed after), `deliver` (`endpoint` read after its `session_scope` closes), `send_once` (`endpoint.signing_secret`, `delivery.payload`)
What is wrong: both `_claim_batch` and `deliver` let the `session_scope` context exit before the returned ORM objects are used, and SQLAlchemy's default `expire_on_commit=True` expires every attribute on commit, so the first attribute access outside the scope raises `DetachedInstanceError`.
What breaks in production: `run_worker` crashes on the very first non-empty batch — after `_claim_batch` has already flipped those rows to `in_flight` — so no webhook is ever delivered and the claimed rows are permanently stranded in a state no query re-selects.
Fix: stop passing ORM entities across session boundaries — have `_claim_batch` return plain immutable value objects (a frozen dataclass carrying `id`, `endpoint_id`, `attempts`, `payload`, and the endpoint's `url` and `signing_secret`, loaded in the same query via a join) built inside the session, and change `deliver`/`send_once` to take that dataclass. Preserve what made the design useful: the batch claim must still mark rows `in_flight` atomically in one transaction, and `send_once` must still be callable in isolation from tests. Deny/allow pair: the allow case is that `deliver` completes against a real session-backed row and `_finish` records `delivered` (this is the case the current test suite cannot reach at all); the deny case is that a `_claim_batch` result whose backing row was deleted concurrently is handled by a named branch rather than an `AttributeError`. Red-prove each clause by execution: (i) change `_claim_batch` back to returning ORM entities — an integration test that calls `deliver` on a real claimed row must redden with `DetachedInstanceError`; (ii) drop `signing_secret` from the join/dataclass — the assertion that the outgoing request carries a signature must redden; (iii) drop `attempts` from the dataclass — the assertion that a delivery resuming at attempt 3 finishes at attempt 5 rather than 7 must redden. Fail loudly when the check cannot run: if the join returns no endpoint for a claimed delivery (endpoint deleted between enqueue and claim), `deliver` must call `_finish(..., "failed_permanent", ..., detail="endpoint no longer exists")` — a named terminal outcome, never a silent `continue`. Cross-cutting: the same detach pattern appears in exactly these two functions in the diff; `list_deliveries`, `list_webhook_endpoints` and `create_webhook_endpoint` all serialize inside their `with` block and are correct as written.

### Critical: `time.sleep` inside an `async def` blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to 100 at a time by `run_worker`, but its retry pause uses the blocking `time.sleep` instead of `await asyncio.sleep`, so the pause halts every other coroutine in the process rather than yielding.
What breaks in production: one failing endpoint stalls the whole worker for 2+4+8+16 = 30 seconds of wall clock, and a batch of 100 failing deliveries serializes into 50 minutes of a frozen event loop during which no other delivery progresses, no HTTP response is read, and the 60-second Redis lock silently expires under the worker's feet.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` and drop the now-unused `import time`. Preserve what made it useful: the backoff pause itself must remain — do not fix by removing the delay, which would turn the retry loop into a hot loop against a struggling customer endpoint. Deny/allow pair: the allow case is that two concurrent `deliver` coroutines, one of which retries, both complete in roughly the longer single backoff rather than the sum — assert on a monotonic clock that total elapsed is less than the serialized sum; the deny case is that the retry still waits at least the computed delay before the second attempt (assert the recorded inter-attempt gap is `>= backoff_for(1).total_seconds()`). Red-prove each clause by execution: (i) revert to `time.sleep` — the concurrency assertion must redden while the minimum-delay assertion stays green (this is the mutation that distinguishes the two clauses); (ii) remove the sleep entirely — the minimum-delay assertion must redden. Fail loudly when the check cannot run: the concurrency test must use a real event loop with a patched-but-real `asyncio.sleep` (a counting wrapper that still awaits), never a stub that returns immediately, and must fail with a named message if the wrapper recorded zero calls — otherwise a test that never reached the retry path reports green. Boundary and tie: use `BASE_DELAY_SECONDS ** attempt` values small enough to keep the test fast but assert the ordering strictly (`gap >= delay`, not `> delay`), so a gap exactly equal to the computed backoff falls on the PASS side.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish` (only called on the two terminal paths inside `deliver`)
What is wrong: rows are moved to `in_flight` at claim time, but nothing ever moves them back to `pending` — `_claim_batch` selects only `status == "pending"`, so a worker crash, an unhandled exception inside `asyncio.gather`, or the detached-instance failure above strands the row permanently (R38 mode 1: an async transition with a success exit and no failure exit or timeout).
What breaks in production: every worker restart permanently loses the deliveries that were in flight, so paid-invoice webhooks are silently dropped with no alert and no recovery affordance, and `GET .../deliveries` reports them as forever pending.
Fix: give `in_flight` a bounded exit — stamp `claimed_at` (or reuse `updated_at`) at claim time, and have `_claim_batch` also select rows where `status = 'in_flight' AND updated_at < now() - interval '<lease>'`, resetting them to `pending` as part of the same claim transaction; add a `try/except BaseException` around each `deliver` that routes any non-terminal exit to `_finish(..., "pending", ...)` with `next_attempt_at` advanced by `backoff_for(attempt)`. Preserve what made the claim useful: two workers must still not deliver the same row simultaneously, so the lease must be strictly longer than the maximum single-attempt duration (`REQUEST_TIMEOUT`) — do not fix by removing the `in_flight` marker. Deny/allow pair: the allow case is that a row whose lease has expired IS reclaimed and eventually delivered; the deny case is that a row claimed one second ago is NOT reclaimed by a second worker — assert both, since a fix that reclaims everything immediately satisfies the recovery clause while destroying the exclusion. Red-prove each clause by execution: (i) remove the lease predicate from `_claim_batch` — the expired-lease reclaim assertion must redden while the fresh-claim exclusion assertion stays green; (ii) set the lease to zero — the exclusion assertion must redden; (iii) remove the `except BaseException` reset — an assertion that a `deliver` raising mid-flight leaves the row `pending` rather than `in_flight` must redden. ### Major: the signature tests compare the subject against itself and cannot detect the serialization defect
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign`, `test_verify_rejects_a_signature_made_with_another_secret`, `test_send_once_posts_the_signed_payload`
What is wrong: `verify` computes its expected value by calling `sign`, so `verify(SECRET, payload, sign(SECRET, payload)[1])` is an identity that is true under every implementation of `serialize` — and `test_send_once_posts_the_signed_payload` asserts only that the header *starts with* `sha256=`, never that the signature validates against the captured body (RT1 clauses (c) and (d): a constant/self-derived oracle, with no independently written expected value).
What breaks in production: the exact defect that makes every customer integration fail — the MAC being computed over different bytes than are sent — leaves this suite entirely green, so the tests read as coverage of the signing contract while proving nothing about it.
Fix: add an assertion against a hard-coded expected digest computed independently of the module — e.g. `assert signing.sign("whsec_fixed", {"a": 1, "b": 2})[1] == "sha256=<hex literal computed once with the documented construction>"` — and extend the `send_once` test to recompute `hmac.new(SECRET.encode(), f"{captured['headers'][TIMESTAMP_HEADER]}.".encode() + captured["body"], hashlib.sha256).hexdigest()` from the CAPTURED bytes and assert it equals the captured signature. Preserve what made the existing tests useful: keep the wrong-secret rejection case — it is the deny side and must stay green. Deny/allow pair: the allow side is the literal-digest equality and the captured-body recomputation both passing; the deny side is the wrong-secret case and a one-byte-mutated-body case both failing verification. Red-prove each clause by execution: (i) change `separators` in `serialize` — the literal-digest assertion must redden (it does not today); (ii) switch `send_once` from `content=` to `json=` — the captured-body recomputation must redden; (iii) make `verify` return `True` unconditionally — the wrong-secret assertion must redden. Fail loudly when the check cannot run: if `captured` is empty the test must `pytest.fail` with a message naming the un-invoked transport, not pass on an empty dict.

### Major: `FakeEndpoint` and `FakeDelivery` diverge from the ORM entities the production path actually receives

What is wrong: both doubles are hand-written plain classes with class-level attributes and no relationship to `m.WebhookEndpoint` / `m.WebhookDelivery`, so they are permanently attached, never expire, and carry only the three attributes the current code happens to touch (RT1 clause (a): shape completeness is not enforced by the type system, so a schema change silently reopens the gap).
