### Critical: the signature is computed over a different byte string than the one transmitted
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, sorted keys) while the request body is produced independently by `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and insertion order — so the MAC is over bytes the receiver never sees.
What breaks in production: every customer who verifies the signature against the raw request body (the only thing they have, and exactly what `docs/webhooks.md` tells them to do) computes a different digest and rejects 100% of our webhooks, while our own delivery records report `delivered`.
Fix: serialize once and send the same bytes — `body = serialize(payload).encode()`; `ts, sig = sign_bytes(secret, ts, body)`; `client.post(url, content=body, headers={..., "Content-Type": "application/json"})` — and change `sign`/`verify` to take `bytes` so no second serializer can exist. Preserve what the diff makes useful: the payload must still arrive as valid JSON with `Content-Type: application/json`, and `serialize()`'s `sort_keys=True` must stay so the digest is stable across dict orderings. Allow side to pin: a round-trip test that takes the body actually captured by `httpx.MockTransport` and feeds it to an independently written verifier (`hmac.new(SECRET, raw_body_from_transport, sha256)`) must PASS — assert on `captured["body"]`, not on the payload dict. Red-prove each clause separately by execution: (i) revert `content=` to `json=` → the round-trip assertion reddens; (ii) drop `sort_keys=True` and pass a payload whose insertion order differs from sorted order → the stability assertion reddens; (iii) flip one byte of the secret → the verifier assertion reddens. Fail loudly when the check cannot run: if `payload` is not JSON-serializable, raise and mark the delivery `failed_permanent` with the reason — do not fall back to `str(payload)`, and never emit a request with an absent or empty signature header. Boundary and tie: an empty payload `{}` still signs (`b"{}"`, not `b""`) and two payloads that serialize to identical bytes must produce identical signatures at the same timestamp — state that in the test.

### Critical: the timestamp header is not covered by the MAC, so replays are unbounded and the documented algorithm is unimplementable
File: `app/webhooks/signing.py` — `sign`, line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `docs/webhooks.md` states the signature is `HMAC-SHA256("{timestamp}.{raw_request_body}")` and instructs customers to reject requests older than five minutes, but the implementation HMACs the body alone, leaving `X-Acme-Timestamp` attacker-mutable.
What breaks in production: a captured request can be replayed forever by rewriting the timestamp header to `now`, so the freshness window the docs sell as the anti-replay control does not exist — and a customer who implements the documented algorithm verbatim rejects every delivery.
Fix: make the signed string `f"{timestamp}.".encode() + body` in `sign`, and have `verify(secret, timestamp, body, signature)` recompute over the caller-supplied timestamp rather than a fresh `time.time()`; `send_once` passes the same `ts` it puts in the header. Preserve the behaviour the current code has right: the digest stays `sha256=<hex lowercase>` and the timestamp stays unix seconds, so no already-published header format changes shape. Allow side to pin: a delivery signed at `T` and verified with the header timestamp `T` must PASS. Red-prove separately by execution: (i) mutate the header timestamp by +1 after signing → verification reddens; (ii) mutate one body byte → verification reddens; (iii) have `verify` re-read `time.time()` instead of the passed timestamp → the "tampered timestamp is rejected" test reddens. Fail loudly when the check cannot run: a missing, non-numeric, or non-ASCII timestamp header is a rejection that names itself (`invalid timestamp header`), never a skipped comparison. Boundary and tie: state the skew rule explicitly — a timestamp exactly `now - 300s` is ACCEPTED and `now - 301s` rejected; two deliveries sharing the same second are independent and both must verify.

### Critical: signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: the MAC comparison uses Python `==`, which short-circuits on the first differing byte, instead of `hmac.compare_digest` (RS1).
What breaks in production: this function is what we publish as the reference verifier and what `tests/webhooks/test_delivery.py` exercises, so every consumer that copies it leaks digest bytes through response timing and can have a forged signature ground out byte by byte.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str`/`bytes` of the same type before the call. Preserve what made the function useful: it still returns a plain `bool` and still accepts the `sha256=` prefixed form, so no caller signature changes. Allow side to pin: a signature genuinely produced by `sign` for the same secret, timestamp and body must still return `True` — that assertion already exists (`test_verify_accepts_signature_produced_by_sign`) and must stay green. Red-prove separately by execution: (i) replace `compare_digest` with `==` and assert the guard test that greps/AST-checks for a constant-time primitive in `signing.py` reddens; (ii) flip the last hex character of a valid signature → `verify` returns `False`. Fail loudly when the check cannot run: a signature that is not `sha256=` + 64 hex characters must return `False` after a length-independent path, not raise and not `True`. Boundary and tie: a signature of the correct length differing only in its final byte must be rejected in the same time as one differing in its first — that is the property under test, so compare the full-length strings and never early-return on a length mismatch of the digest portion.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, line `random.choice(_ALPHABET) for _ in range(SECRET_BYTES)`
What is wrong: `random.choice` draws from the Mersenne Twister, whose full internal state is recoverable from a few hundred observed outputs, and this is a reimplementation of `secrets` — the stdlib helper that already exists for exactly this (R1: the duplicated behaviour is a security control, so Critical).
What breaks in production: an attacker who registers a handful of endpoints of their own recovers the generator state and derives every other tenant's signing secret, then forges `invoice.paid` webhooks into their systems.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` code outright (R1(d) — not renamed, not kept as a wrapper). Enumerate the behavioural differences this adoption makes at the call site (R1(a),(b)): the alphabet gains `-` and `_`, and the secret's character length becomes `ceil(SECRET_BYTES * 4 / 3)` rather than `SECRET_BYTES`, so the existing length assertion must be updated to the new expression rather than deleted — do not fix by removing the assertion that made the shape checkable (Remedy Floor 4). Name the hazard the dedup does not address (R1(e)): secrets remain unrotatable and are still returned by `to_dict` — see the two findings below. Allow side to pin: `new_signing_secret()` still starts with `whsec_` and two consecutive calls differ. Red-prove separately by execution: (i) hardcode the generator to return a constant → the uniqueness assertion reddens; (ii) drop the prefix → the prefix assertion reddens; (iii) revert to `random.choice` under a fixed `random.seed(0)` → a test asserting two secrets generated across a `random.seed(0)` reset are still different reddens. Fail loudly when the check cannot run: if `secrets` cannot produce the requested length, let the exception propagate — the endpoint must fail to be created rather than be stored with a weak or empty secret. Boundary and tie: `SECRET_BYTES = 32` is entropy bytes, not characters; rename it `SECRET_ENTROPY_BYTES` and state that 32 is the floor, with 31 rejected at import time by an assertion.

### Critical: `list_deliveries` has no tenancy filter — cross-organization read of every webhook payload
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: the query filters on the caller-supplied `endpoint_id` only, with no join back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) do scope by `org_id` — an incomplete propagation of the file's own tenancy pattern (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` and read other tenants' `invoice.paid` payloads and stored response bodies, and `docs/webhooks.md` claims the route "returns the most recent attempts for an endpoint belonging to your organization" — a claim stronger than the implementation (R49).
Fix: join the parent and scope it — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the endpoint exists but belongs to another org, so the route does not confirm existence. Preserve what makes the route useful: ordering, the `limit`, and the `to_dict()` shape are unchanged. Cross-cutting: apply the same audit to the other two new routes — `create_webhook_endpoint` sets `org_id=user.org_id` (correct) and `list_webhook_endpoints` filters on it (correct), so `list_deliveries` is the only gap; state that in the PR. Allow side to pin: the owning org's own request for its own `endpoint_id` must still return its rows — assert a non-empty list for the owner in the same test that asserts 404 for the foreigner (Remedy Floor 1). Red-prove separately by execution: (i) delete the `org_id` predicate → the cross-tenant test reddens with a 200 and rows; (ii) delete the `endpoint_id` predicate → a test asserting one endpoint's deliveries do not include a sibling endpoint's rows reddens; (iii) change 404 to 403 → the existence-disclosure assertion reddens. Fail loudly when the check cannot run: an `endpoint_id` that does not parse, or a request whose `user.org_id` is `None`, must 4xx and never fall through to an unfiltered query. Boundary and tie: an endpoint owned by the caller's org but soft-deleted (`active=False`) is still readable — say so — and two deliveries sharing a `created_at` are ordered by `id DESC` as tie-break (see the R57 finding below).

### Critical: `to_dict()` returns the signing secret on every read, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret": self.signing_secret`
What is wrong: the single `to_dict()` is used both by the 201 create response and by `GET /webhook-endpoints`, so the secret is returned on every list call, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: claim stronger than the implementation).
What breaks in production: any principal with read access to settings — including a lower-privileged member, a browser extension reading the JSON, or anything that logs API responses — obtains the key that authenticates our webhooks and can forge arbitrary billing events to the customer's endpoint.
Fix: remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at that one call site, so disclosure is a deliberate act at a single line. Preserve what made the feature useful: the create response still carries the secret, because it is the only way the customer can ever obtain it. Add the missing rotation path the docs' "cannot be read back" model requires (`POST /webhook-endpoints/{id}/rotate-secret`, returning the new secret once) — without it a leaked secret has no remedy. Allow side to pin: the 201 body still contains a `whsec_`-prefixed secret and the customer flow still works end to end. Red-prove separately by execution: (i) re-add the key to `to_dict()` → a test asserting `"signing_secret" not in list_response[0]` reddens; (ii) remove the explicit merge in the create handler → the "create returns the secret exactly once" assertion reddens; (iii) point rotate at the wrong endpoint id → the tenancy assertion on rotate reddens. Fail loudly when the check cannot run: if the secret column is null or empty at create time, return 500 and do not persist the endpoint — an endpoint with no secret must never accept deliveries. Boundary and tie: after rotation, a delivery already `in_flight` was signed with the old secret; state which secret it carries (the one captured at signing time) and that both secrets verify for a stated overlap window, or that rotation invalidates in-flight deliveries.

### Critical: endpoint URL validation permits `http://` and arbitrary internal hosts, and the client follows redirects — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http`, and any scheme whose name merely begins with those four characters, with no check that `netloc` resolves outside private, loopback, or link-local space; `follow_redirects=True` then lets even a legitimate public HTTPS endpoint redirect the signed POST to an internal address (RS3: an unvalidated boundary value reaching a network sink).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/` (or a public host that 302s there) and our worker POSTs signed billing payloads to the cloud metadata service and stores the response body in `webhook_deliveries.response_body`, where the tenant reads it back through the deliveries route — a full credential-exfiltration primitive.
Fix: validate at the schema level with `url: HttpUrl` on `EndpointIn`, then in the handler require `parsed.scheme == "https"` exactly, resolve the hostname and reject any address in a private/loopback/link-local/unique-local/reserved range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`, and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a failed attempt rather than chased. Preserve what makes the feature useful: ordinary public HTTPS endpoints, including non-443 ports and IPv6 literals, still register and still receive deliveries. Cross-cutting: the same hostname check must run again at delivery time, not only at registration, because DNS can be re-pointed after the row is stored — pin the resolved address and connect to it. Allow side to pin: `https://hooks.example.com/acme` (the value in `docs/webhooks.md` and in the tests' `FakeEndpoint`) must still be accepted at registration and still be POSTed to. Red-prove separately by execution: (i) submit `http://hooks.example.com/x` → 422; (ii) submit `https://127.0.0.1/x` → 422; (iii) point a MockTransport handler at a 302 to `http://169.254.169.254/` → the delivery is recorded failed and no second request is issued. Fail loudly when the check cannot run: DNS resolution failure, a hostname with no A/AAAA record, or an unparseable URL is a rejection naming itself (`endpoint host could not be resolved`), never an accepted registration and never a silent skip of the range check. Boundary and tie: `0.0.0.0` and `::` are rejected; a hostname resolving to BOTH a public and a private address is rejected; the boundary case `100.64.0.0/10` (CGNAT) counts as private — state it.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` `STATUSES`
What is wrong: the producer writes `failed_permanent` and the strict consumer (the DB check constraint) admits only `failed` — an enum-spelling divergence across a storage boundary that no test crosses (R40).
What breaks in production: the first delivery to exhaust `MAX_ATTEMPTS` raises `IntegrityError` inside `_finish`, the exception escapes `deliver`, `asyncio.gather` propagates it out of `run_worker`, and the worker dies with the row still `in_flight` — a permanently failing endpoint takes down webhook delivery for every tenant.
Fix: change the constraint to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`, and derive it from one place — generate the SQL literal list from `models.STATUSES` (or assert equality between the two in a test that reads the migration file) so the two cannot drift again. Preserve what makes the constraint useful: it must still reject an unknown status, so do not fix this by dropping the CHECK. Cross-cutting: the same producer/consumer spelling audit applies to `event_type` (`String(100)` in the model vs unbounded `TEXT` in the migration — a 101-character type is accepted by the DB and silently truncated or rejected depending on driver) and to every `DateTime(timezone=True)` column mapped onto a bare `TIMESTAMP` (see the timezone finding). Allow side to pin: writing each of the four legal statuses must SUCCEED against a real database — a round-trip test that inserts every member of `models.STATUSES` through the actual ORM into the actual migrated schema, not a mock. Red-prove separately by execution: (i) revert the constraint to `'failed'` → the `failed_permanent` insert reddens; (ii) add a fifth member to `STATUSES` without touching the migration → the drift assertion reddens; (iii) insert `'bogus'` → the DB rejects it, proving the constraint is still enforcing. Fail loudly when the check cannot run: if the test database is unavailable the round-trip test must ERROR, not skip — "examined nothing" must not report as green. Boundary and tie: a delivery that reaches exactly `attempts == MAX_ATTEMPTS` is `failed_permanent` (not retried a sixth time); `attempts == MAX_ATTEMPTS - 1` is retried once more.

### Critical: `UNIQUE INDEX` on `event_id` allows only one delivery row per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: the uniqueness key is `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint, so any organization with two active subscribed endpoints violates the index on flush.
What breaks in production: `session.add_all` raises `IntegrityError`, the dispatcher's blanket `except Exception` swallows it as a `log.warning`, and that organization silently receives NO webhooks at all — not for the second endpoint, for either — with the event already committed and no retry or reconciliation path.
Fix: make the index `UNIQUE (endpoint_id, event_id)`, which is the idempotency key the at-least-once contract in `docs/webhooks.md` actually needs, and have `enqueue_for_event` use an upsert (`ON CONFLICT (endpoint_id, event_id) DO NOTHING`) so a redelivery of the same event is a no-op rather than an error. Preserve what the current index was for: duplicate suppression per endpoint must still hold, so do not fix this by dropping uniqueness. Allow side to pin: two active endpoints in one org, both subscribed, must both receive a row for the same `event_id` — assert `len(rows) == 2` in an integration test against the real schema, which is exactly the case that reddens today. Red-prove separately by execution: (i) restore the single-column unique index → the two-endpoint test reddens with `IntegrityError`; (ii) drop `DO NOTHING` and call `enqueue_for_event` twice with the same `event_id` → the duplicate-suppression assertion reddens; (iii) remove the index entirely → the "second enqueue creates no second row" assertion reddens. Fail loudly when the check cannot run: an `IntegrityError` from enqueue must be re-raised and surfaced (see the swallow finding below), never logged at warning and dropped. Boundary and tie: exactly one endpoint subscribed produces exactly one row; two endpoints in DIFFERENT orgs for the same `event_id` must both get a row — that pair is precisely what the current index forbids.

### Major: `time.sleep()` inside an async coroutine blocks the event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: the retry backoff uses the blocking `time.sleep` inside `async def deliver`, and `run_worker` runs these under `asyncio.gather`, so one retrying delivery halts every other coroutine on the loop.
What breaks in production: a batch of 100 deliveries is serialized by up to 30s of blocking sleep each (2+4+8+16), the 60s Redis lock expires mid-batch, a second worker claims and re-sends, and if this loop runs in the API process every HTTP request stalls behind it.
Fix: `await asyncio.sleep(delay)`. Preserve the behaviour that matters: the delay sequence stays 2/4/8/16 seconds so `test_backoff_grows_exponentially` remains meaningful, and the retry still happens in-coroutine rather than being dropped. Allow side to pin: a delivery that succeeds on its second attempt must still be recorded `delivered` with `attempts == 2` — pin that with a monkeypatched `asyncio.sleep` that records the delay and returns immediately. Red-prove separately by execution: (i) revert to `time.sleep` → a test asserting two concurrent `deliver()` calls complete in less than the sum of their delays reddens; (ii) remove the `await` → the recorded-delay assertion reddens; (iii) return a delay of 0 from `backoff_for` → the "delay was actually requested" assertion reddens. Fail loudly when the check cannot run: cap the cumulative in-coroutine wait and abandon the delivery to a later poll rather than sleeping unbounded — see the next finding. Boundary and tie: `attempt == MAX_ATTEMPTS` sleeps zero times (it returns before the sleep); `attempt == MAX_ATTEMPTS - 1` sleeps exactly once.

### Major: `in_flight` is a non-terminal state with no failure exit and no reclaim path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `deliver`, `run_worker`
What is wrong: rows are moved to `in_flight` and are only ever moved out by a successful return from `deliver`; a worker crash, a redeploy, an unhandled exception, or the `IntegrityError` above leaves them `in_flight` forever, and nothing in the diff ever selects `status == "in_flight"` to reclaim them (R38(1): failure exit and bounded timeout both absent).
What breaks in production: every delivery interrupted by a restart is silently and permanently lost, with `next_attempt_at` still in the past and no operator affordance to see or requeue it.
Fix: retry the whole `deliver` body inside `try/except BaseException` and route every non-success exit — exception, timeout, cancellation — back to `_finish(..., "pending", ...)` with `next_attempt_at = now + backoff_for(attempt)`; add a `claimed_at` column and a reclaim query at the top of `run_worker` that returns rows with `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` to `pending`. Preserve what `in_flight` was for: it must still prevent two concurrently running workers from claiming the same row, so do not fix this by deleting the state. Allow side to pin: a delivery that completes normally must still reach `delivered` and must NOT be reclaimed by the sweeper — assert both in the same test. Red-prove separately by execution: (i) raise inside `send_once` → assert the row returns to `pending` with a future `next_attempt_at`; (ii) freeze a row at `in_flight` with `claimed_at` six minutes old → assert the sweeper requeues it; (iii) set `claimed_at` to one minute old → assert the sweeper leaves it alone. Fail loudly when the check cannot run: if `claimed_at` is NULL on an `in_flight` row, treat it as stale and reclaim, logging the anomaly by name. Boundary and tie: a row whose `claimed_at` is exactly five minutes old is NOT yet reclaimed (strict `<`); two workers racing the reclaim are serialized by a conditional `UPDATE ... WHERE status = 'in_flight'` returning a row count, so only one wins.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (reads `endpoint.signing_secret` and `endpoint.url` after the `with` block exits)
What is wrong: both functions hand ORM entities out of the `session_scope()` block and then read attributes on them, whereas every other new call site in this diff (`list_api_keys`, `list_webhook_endpoints`, `list_deliveries`, `create_webhook_endpoint`) materializes to `dict` while the session is open — the divergence is visible within the diff itself.
What breaks in production: under SQLAlchemy's default `expire_on_commit=True`, every attribute is expired at commit and the first read after the block raises `DetachedInstanceError`, so `run_worker` dies on its very first batch and no webhook is ever delivered.
Fix: return plain data, not entities — have `_claim_batch` return a list of frozen dataclasses (`id`, `endpoint_id`, `payload`, `attempts`) built inside the block, and have `deliver` read the endpoint's `url` and `signing_secret` into locals inside its own `with` block before use. Preserve what the entities were carrying: the same fields must still reach `send_once`, so do not fix this by widening the transaction to span the network call (that is the R9 hazard). Allow side to pin: a claimed batch of one row must still produce one successful POST carrying that row's payload. Red-prove separately by execution: (i) return the ORM rows instead of the dataclasses → the batch test reddens with `DetachedInstanceError` against a real session (not a mock — a mocked session cannot exhibit expiry, RT1); (ii) drop `payload` from the dataclass → the POST-body assertion reddens; (iii) drop `attempts` → the "second attempt is numbered 2" assertion reddens. Fail loudly when the check cannot run: if `session.get(WebhookEndpoint, endpoint_id)` returns `None` (endpoint deleted between enqueue and delivery), mark the delivery `failed_permanent` with `endpoint no longer exists` — do not proceed to `sign(None, ...)`. Boundary and tie: an empty batch returns `[]` and `gather` is a no-op; a row claimed twice by the same worker is impossible because the claim is the only writer of `in_flight`.

### Major: the dispatch lock is neither atomically acquired nor safely released
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get`-then-`set` is two round trips with no `NX`, so two workers can both observe an empty key and both proceed; `expire` is a separate call, so a crash between `set` and `expire` leaves the lock permanently held; and the unconditional `delete` removes whatever value is at the key, including a lock a *different* worker acquired after the 60s TTL expired.
What breaks in production: duplicate deliveries under normal contention, or — after one crash at the wrong instant — a lock that is never released and a webhook pipeline that stops entirely with no alert.
Fix: acquire with a single atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` is unique per acquisition, and release with the compare-and-delete Lua script (`if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) end`) so a worker can only delete its own lock; renew the TTL while the batch is still running rather than sizing it by guess. Preserve what the lock was for: a single dispatcher at a time, so do not fix this by removing the lock and relying on the `in_flight` claim alone. Allow side to pin: after the holder releases, the next worker must SUCCEED in acquiring — assert acquire→release→acquire returns `True` twice. Red-prove separately by execution: (i) drop `nx=True` → a test where a second acquire runs against a held key reddens by returning `True`; (ii) replace the compare-and-delete with a plain `delete` → the "worker B's lock survives worker A's release" assertion reddens; (iii) drop `ex=` → the "lock expires after TTL" assertion reddens (with a fake clock, not a real sleep). Fail loudly when the check cannot run: a Redis error in `_acquire_lock` must return `False` and log by name — never `True`, because an unreachable Redis must not be read as an uncontended lock. Boundary and tie: two workers calling `set(nx=True)` in the same millisecond — exactly one gets `True`, and the loser sleeps `poll_interval`; a batch still running at exactly `LOCK_TTL_SECONDS` has already renewed.

### Major: any single delivery exception kills the worker loop permanently
File: `app/webhooks/delivery.py` — `run_worker`, line `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` without `return_exceptions=True` propagates the first exception out of the `while True` loop, and `deliver` only catches `httpx.HTTPError` — an `IntegrityError` from `_finish`, an `AttributeError` on a `None` row, a JSON encoding error, or a `DetachedInstanceError` all escape.
What breaks in production: one malformed payload or one unmigrated status value terminates the process's delivery loop for every tenant, and because the `finally` releases the lock, nothing distinguishes "worker exited" from "worker idle".
Fix: pass `return_exceptions=True`, then iterate the results and for each exception call `_finish(delivery_id, "pending", attempt, None, repr(exc))` with a backoff-scheduled `next_attempt_at`, logging at ERROR with the delivery id; wrap the body of the `while` in its own `try/except Exception` that logs and continues rather than exiting.
