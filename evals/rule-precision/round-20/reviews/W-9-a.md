Red-prove per clause: (i) allow side — an uninterrupted delivery still reaches `delivered` on the first attempt with `attempts == 1`; (ii) kill the process (or raise) after the claim and assert a subsequent `_claim_batch` returns the row once the lease expires, red-proved by removing the reclaim query; (iii) assert a row reclaimed four times reaches `failed_permanent` rather than retrying forever, red-proved by not incrementing `attempts` on reclaim. Boundary and tie: a row `in_flight` for exactly the lease duration is NOT yet reclaimed (strictly greater), and a reclaim racing a live worker's `_finish` must resolve by a conditional update on `status` so the terminal write wins.

### Major: the dispatch lock is non-atomic and is deleted without ownership, so two workers can run the same batch
File: `app/webhooks/delivery.py` — `_acquire_lock` (`get` then `set` then `expire`) and `run_worker` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: The check-then-set is three separate round trips rather than a single `SET key value NX EX 60`, so two workers can both observe an empty key and both proceed; the `finally` then deletes `LOCK_KEY` unconditionally, including a lock that expired and was re-acquired by a different worker, and the 60-second TTL is shorter than a batch's worst case (up to 5 × 30s request timeout plus 30s of backoff per delivery).
What breaks in production: Duplicate concurrent delivery of every event in a batch, and — worse than duplicates — two workers writing conflicting `status`/`attempts` on the same rows, so a delivery marked `delivered` by one worker is re-sent and re-marked by the other.
Fix: Acquire with a single atomic call carrying a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a compare-and-delete Lua script that deletes only when the stored value equals the token; set `LOCK_TTL_SECONDS` above the batch's worst-case duration (`BATCH_SIZE`-bounded, derived from `REQUEST_TIMEOUT` and `MAX_ATTEMPTS`, not a bare 60) and renew it mid-batch. Preserve what the lock made possible: a single worker must still be able to acquire immediately on a cold start, and releasing must still let the next poll acquire without waiting for the TTL. Red-prove per clause: (i) allow side — one worker acquires, releases, and re-acquires on the next iteration; (ii) two concurrent `_acquire_lock` calls yield exactly one `True`, red-proved by reverting to get-then-set; (iii) worker A's lock expires and worker B acquires; A's `finally` must NOT delete B's lock — assert the key still holds B's token, red-proved by removing the token comparison; (iv) if Redis is unreachable, `_acquire_lock` must raise or return `False` and the worker must not proceed unlocked — "cannot check the lock" must not be spelled the same as "lock is free". Boundary and tie: a batch running exactly to the TTL must have renewed before expiry, and when two workers tie on acquisition the `NX` semantics decide — state that explicitly rather than relying on ordering.
