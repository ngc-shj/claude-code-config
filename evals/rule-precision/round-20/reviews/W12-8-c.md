### Critical: the HMAC is computed over different bytes than the request body actually sent
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, with `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` while `send_once()` transmits `client.post(..., json=delivery.payload)`, which httpx serializes with its own key order and separators, so the signed string and the raw body are different byte sequences.
What breaks in production: every customer who implements the documented verification — HMAC over the raw request body — computes a different digest and rejects 100% of our webhooks, and the failure is invisible to us because we only look at their HTTP status.
Fix: build the body bytes once and sign exactly those bytes — `body = serialize(payload).encode()`, `ts, sig = sign(secret, body)`, then `client.post(endpoint.url, content=body, headers={...,"Content-Type":"application/json"})`; change `sign`/`verify` to take `bytes` so no second serialization can be introduced. Preserve the behaviour that makes the feature useful: the receiver must still get valid JSON with the same field values (do not "fix" this by dropping `sort_keys` and hoping the encoders agree, and do not delete the header assertions in `tests/webhooks/test_delivery.py` that made the mismatch observable). Add a round-trip test per R40 that feeds ACTUAL producer output through the ACTUAL consumer path: capture `request.content` in the `MockTransport` handler and assert `hmac.compare_digest(captured_signature, "sha256=" + hmac.new(SECRET.encode(), ts_header.encode() + b"." + captured_body, sha256).hexdigest())`. Deny side and allow side both pinned: the allow case is the unmodified payload, which must still verify green; the deny case is a single byte flipped in `captured_body`, which must fail. Red-prove each clause separately by execution — (a) revert `content=` to `json=` and observe the round-trip assertion red, (b) mutate `serialize` to drop `sort_keys=True` and observe the same assertion red on a two-key payload, (c) flip one payload byte and observe the tamper assertion red — three mutations, three distinct failures. Fail loudly when the check cannot run: if `captured` is empty (the handler never fired), the test must fail with "transport was never invoked", not pass over an empty dict. Boundary and tie: an empty payload `{}` serializes to `b"{}"` and must still produce a signature; two deliveries with byte-identical bodies at the same unix second legitimately produce identical signatures and that is not an error.

### Critical: the timestamp header is not covered by the signature, so it provides no replay protection
File: `app/webhooks/signing.py` — `sign()`, line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and tells customers the timestamp window "stops a captured request from being replayed", but `timestamp` is never fed into the MAC.
What breaks in production: anyone who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to the current second — the signature still validates — so the freshness window we instructed customers to rely on enforces nothing.
Fix: make the MAC input `f"{timestamp}.".encode() + body` and return the same `timestamp` in the tuple, so the header and the MAC input cannot diverge; `verify(secret, timestamp, body, signature)` must take the timestamp from the caller (the received header) rather than regenerating it. Preserve the documented wire format — the header names, the `sha256=` prefix and the unix-seconds encoding stay exactly as documented, so existing integrations that already implement the doc keep working. Pair deny with allow: the allow case is a request whose header timestamp is the one that was signed, which must verify; the deny case is the same body with the timestamp header rewritten, which must fail. Red-prove separately: (a) drop the `f"{timestamp}."` prefix from the MAC input and observe the replay test go green-when-it-should-be-red; (b) pass a different timestamp to `verify` than to `sign` and observe rejection. Fail loudly: a non-numeric or absent timestamp must raise/return a named refusal, never be coerced to `0` and compared. Boundary and tie: state that the receiver's window is inclusive at exactly 300 seconds and that two deliveries signed in the same second are indistinguishable by timestamp — dedup is `event_id`'s job, per the doc.

### Critical: `verify()` compares signatures with `==` (RS1)
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: the shipped signature comparison uses Python's short-circuiting `str.__eq__` instead of a constant-time comparison, which RS1 classifies Critical.
What breaks in production: an attacker who can submit candidate signatures to any surface reaching this function recovers a valid digest byte by byte from response-time differences, forging deliveries; and because this is our published reference implementation, every customer who copies it inherits the same oracle on their inbound endpoint.
Fix: `return hmac.compare_digest(expected, signature)`, guarding against the non-`str`/non-ASCII input that makes `compare_digest` raise. Preserve what made the function useful: it must still return `True` for a signature this module produced — do not "fix" it by making it stricter about the `sha256=` prefix and thereby rejecting valid input. Pair deny with allow: an allow test asserting a genuine signature still verifies, and a deny test asserting a one-character-different signature does not. Red-prove each clause by execution: (a) revert to `==` and confirm no test reddens today (this is itself the proof that the current suite cannot see this defect), so the new test must be written to redden on a *timing-independent* mutation — assert on `hmac.compare_digest` being on the call path via a deny case with an equal-length wrong digest and an allow case; (b) return a constant `True` and confirm the deny case reddens. Fail loudly: a `signature` that is `None` or not a string must raise a named `TypeError`/return an explicit refusal rather than silently comparing to `False`. Boundary and tie: signatures of unequal length must reject without leaking the length difference through an early return, and two calls with the identical correct signature must both return `True`.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`, line `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from a small, partially predictable state and is not a cryptographic generator, yet its output is the sole key protecting webhook authenticity.
What breaks in production: an attacker who observes enough output from the same process — or who registers a handful of endpoints of their own and reads back the secrets (see the exposure finding below) — can recover the generator state and derive other tenants' signing secrets, then forge signed events into their systems.
Fix: `import secrets` and return `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, and rename or re-document `SECRET_BYTES` so the unit it names is the unit it controls (see the Minor finding on that constant). Preserve the useful properties the current code has: the `whsec_` prefix and a URL/header-safe alphabet must survive, since `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` and the documented format depend on them. Pair deny with allow: the allow case is that a freshly generated secret still round-trips through `sign`/`verify`; the deny case is a statistical assertion that 1000 generated secrets are all distinct and none is reproducible after `random.seed(0)`. Red-prove each clause separately by execution: (a) restore `random.choice` after `random.seed(0)` and confirm the reproducibility assertion reddens; (b) return a fixed constant and confirm the distinctness assertion reddens — two mutations, two different failures. Fail loudly: if `secrets` cannot produce entropy the call must propagate the exception, never fall back to `random`. Boundary and tie: state the minimum accepted secret length and what happens on a collision — with 32 bytes of CSPRNG output a collision is not a case the code needs a branch for, and that must be said rather than silently assumed. Existing secrets minted by the weak generator are compromised: rotate them and treat rotation as part of this fix, not a follow-up.

### Critical: the signing secret is returned by the endpoint-list route
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, key `"signing_secret"`; reached from `app/api/routes/settings.py` — `list_webhook_endpoints()`
What is wrong: `to_dict()` includes `signing_secret` and is used by both the create route and the list route, so the secret is served on every `GET /v1/settings/webhook-endpoints`, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: the secret becomes readable by any principal who can call the list endpoint and lands in browser caches, proxy logs, and API-client history, so an authenticity control we tell customers is write-once is in fact a persistently readable field.
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint()` return `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable it already holds, so exactly one route can ever emit it. Preserve what made the feature useful: the create response must still carry the secret, because it is the only time the customer can capture it — do not fix this by removing the secret from both routes. Codebase awareness: `to_dict()` is the shared serializer already used by two call sites in this diff, so the fix belongs in it rather than in a new per-route filter. Pair deny with allow: a deny test asserting `"signing_secret" not in GET /webhook-endpoints` response bodies, and an allow test asserting `POST /webhook-endpoints` still returns a value starting with `whsec_`. Red-prove separately: (a) re-add the key to `to_dict()` and confirm the list-route assertion reddens; (b) drop the key from the create route's response and confirm the create assertion reddens. Fail loudly: if the create route cannot produce a secret it must 500 with a named error rather than return an endpoint row without one. Boundary and tie: an endpoint list of length zero must still pass the deny assertion (assert on the serializer's key set, not on a substring of the response body, or an empty list passes vacuously).

### Critical: `list_deliveries` has no tenancy check — any authenticated user reads any org's event payloads
File: `app/api/routes/settings.py` — `list_deliveries()`, filter `WebhookDelivery.endpoint_id == endpoint_id`
What is wrong: the query filters only on the path parameter and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike its two siblings in the same file which both scope by `org_id`.
What breaks in production: any authenticated customer can enumerate small integer endpoint IDs and read other tenants' delivery rows, and `WebhookDelivery.to_dict()` exposes `event_type` and `status` for every one of them — a cross-tenant data disclosure that the docs explicitly promise does not happen ("an endpoint belonging to your organization").
Fix: join and scope — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) for an endpoint outside the caller's org so the route does not confirm existence. Cross-cutting per R3: `create_webhook_endpoint` and `list_webhook_endpoints` in the same file already scope on `user.org_id`; `list_deliveries` is the one site in the diff that dropped the pattern, and `app/webhooks/delivery.py::_claim_batch` correctly needs no scoping because it is the worker. Preserve the feature: the endpoint's own org must still receive its deliveries — do not fix this by removing the route. Pair deny with allow: a deny test where user B requests user A's `endpoint_id` and receives 404, and an allow test where user A receives their rows. Red-prove each clause separately by execution: (a) drop the `org_id` predicate and confirm the deny test reddens; (b) drop the `endpoint_id` predicate and confirm the allow test reddens because it now sees a sibling endpoint's rows. Per RT8 the deny test must assert the response BODY is empty of the other org's delivery ids, not merely that the status is 404. Fail loudly: an `endpoint_id` that does not resolve must 404 with a named detail, never fall through to an unfiltered query. Boundary and tie: an endpoint that exists and belongs to the caller but has zero deliveries returns `[]` with 200, which is a different outcome from the cross-tenant 404 and must be tested as its own case.

### Critical: the migration's status CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`

What breaks in production: the first delivery to exhaust its attempts raises an integrity error inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and because `run_worker`'s `asyncio.gather` has no exception handling the worker dies and all webhook delivery stops.

Red-prove each clause separately by execution: (a) remove `failed_permanent` from `STATUSES` and confirm the parity test reddens; (b) remove it from the SQL and confirm the same test reddens for the opposite reason, with the failure output naming which side is missing; (c) write `"bogus"` and confirm the deny test reddens if the CHECK is dropped. Fail loudly: if the migration file cannot be parsed the parity test must fail with "could not extract CHECK values", never skip. Boundary and tie: state that the empty string and `NULL` are both rejected by `NOT NULL` + CHECK, and that the model's `default="pending"` is inside the allowed set.

### Critical: the unique index on `event_id` alone makes fan-out to two endpoints impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event()` inserts one row per active endpoint for a single `event_id`, but the index permits only one row per `event_id` across the whole table.
What breaks in production: any org with two or more registered endpoints hits a unique violation on the second row, `session.add_all` fails the whole transaction so even the first endpoint gets nothing, and `app/events/dispatcher.py` swallows the exception into a `log.warning` — the customer silently receives no webhooks at all.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`, which is the constraint that actually expresses the intended invariant (one delivery per event per endpoint) and preserves the idempotency the docs lean on ("deduplicate on `event_id`" is the receiver's job; ours is per-endpoint). Do not fix by deleting the uniqueness — it is what stops a redelivered event from double-charging a receiver. Pair deny with allow: an allow test enqueuing one event to two endpoints of the same org and asserting two rows; a deny test enqueuing the same `(endpoint_id, event_id)` twice and asserting the second is rejected. Red-prove each clause separately by execution: (a) restore the single-column index and confirm the two-endpoint allow test reddens; (b) drop the index entirely and confirm the duplicate deny test reddens. Fail loudly: `enqueue_for_event` must not swallow the integrity error — see the dispatcher finding below; a duplicate must be handled explicitly (`ON CONFLICT DO NOTHING` semantics) rather than aborting the batch. Boundary and tie: an org with zero active endpoints inserts zero rows and must return `0` rather than raise, and two endpoints belonging to different orgs subscribed to the same global event are distinct rows under the new key.

### Critical: `time.sleep()` blocks the event loop inside an async coroutine
File: `app/webhooks/delivery.py` — `deliver()`, line `time.sleep(delay)`
What is wrong: a synchronous `time.sleep` is called inside an `async def` that is run under `asyncio.gather`, so it blocks the entire event loop rather than yielding.
What breaks in production: a single failing endpoint stalls the whole process for up to 2+4+8+16 = 30 seconds per delivery — and with `BATCH_SIZE = 100` gathered coroutines the blocking is additive, so the 60-second lock TTL expires mid-batch, a second worker claims the same rows, and every delivery in flight is sent twice.
Fix: `await asyncio.sleep(delay)` (the module already imports `asyncio` for `run_worker`, so nothing new is needed). Better, remove the in-coroutine retry loop entirely and reschedule through the row: on a retryable failure set `status="pending"`, `attempts=attempt`, `next_attempt_at = now + backoff_for(attempt)` and return, letting the poller pick it up — this is what the `next_attempt_at` column and `_claim_batch`'s `next_attempt_at <= now` filter already exist for, and the current code reimplements that shared scheduling path in memory. Preserve the retry behaviour itself: total attempts must still cap at `MAX_ATTEMPTS` and the delays must still be roughly 2/4/8/16s. Pair deny with allow: an allow test that a 200 on the first attempt completes with no sleep at all, and a deny test that a 500 schedules a second attempt. Red-prove each clause separately by execution: (a) reinstate `time.sleep` and assert with a monotonic clock inside a concurrent-progress test that a second coroutine made progress during the delay — it must redden; (b) remove the `attempt >= MAX_ATTEMPTS` guard and confirm a bounded-attempts test reddens (bound the loop in the test so the mutation reds rather than hangs); (c) drop the `next_attempt_at` advance and confirm a scheduling test reddens. Fail loudly: an unexpected non-`httpx.HTTPError` exception must mark the row with a named error status rather than escaping and killing the worker. Boundary and tie: `attempt == MAX_ATTEMPTS` is terminal (the 5th attempt is made, the 6th is not), and two rows whose `next_attempt_at` are exactly equal are both claimed in the same batch.

### Critical: the signing tests are tautological — they pass against a constant implementation
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign` and `test_send_once_posts_the_signed_payload`
What is wrong: `verify()` internally calls `sign()`, so `test_verify_accepts_signature_produced_by_sign` asserts `sign(x) == sign(x)` — an identity that holds for any implementation, including one that returns a constant — and `test_send_once_posts_the_signed_payload` only asserts the header *starts with* `"sha256="` and never recomputes the digest over `captured["body"]`, which is precisely why the body/signature mismatch above ships green.
What breaks in production: the suite reports the signing scheme as covered while being structurally incapable of failing for a broken signature, so all four Critical crypto defects in this diff pass CI.
Fix: assert against an independently written expected value, per RT1 — compute the expectation in the test with `hmac.new(SECRET.encode(), b"<ts>." + body, hashlib.sha256).hexdigest()` written out literally rather than by calling `signing.sign`, and in the transport test verify that expectation against `captured["body"]` and `captured["headers"][TIMESTAMP_HEADER]`. Per RT5 the test call path must reach the real `sign`/`verify`, not a re-derivation of them. Preserve the existing negative case (`test_verify_rejects_a_signature_made_with_another_secret`), which is the one non-vacuous assertion in the file. Pair deny with allow: allow — the genuine signature verifies; deny — a signature over a one-byte-different body does not. Red-prove each clause separately by execution: (a) make `sign` return `("0", "sha256=" + "0"*64)` unconditionally and confirm the allow assertion reddens (today it does not); (b) make `verify` return `True` unconditionally and confirm the wrong-secret assertion reddens; (c) drop the timestamp from the MAC input and confirm the expectation assertion reddens — three mutations, three distinct named failures. Fail loudly: if `captured` is never populated the test must fail with "handler not invoked" rather than raise `KeyError` from an empty dict, which reads as an error rather than a controlled failure. Boundary and tie: an empty payload and a payload whose keys are already sorted must both be covered, since the second is the case where a `sort_keys` bug is invisible.

### Major: ORM objects are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returns `rows` outside the `with session_scope()` block; `deliver()` reads `endpoint`/`delivery` attributes after their sessions closed
What is wrong: `_claim_batch` mutates `row.status` and returns the instances after the context manager exits, and `deliver` likewise binds `endpoint` inside a `with` block then passes it to `send_once`, which reads `endpoint.signing_secret` and `endpoint.url` afterwards.
What breaks in production: under SQLAlchemy's default `expire_on_commit=True` every one of those attribute reads raises `DetachedInstanceError`, so no delivery is ever sent; if the project's `session_scope` disables that default, the reads instead return stale values and `deliver`'s `attempt = delivery.attempts` silently restarts the attempt count from a snapshot.
Fix: stop passing ORM instances across session boundaries — have `_claim_batch` return plain data (`[(row.id, row.endpoint_id, row.attempts, row.payload) for row in rows]`, materialised inside the block) and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside its own `with` block before any `await`. Preserve the claiming semantics that make the batch safe: the `status = "in_flight"` write must still commit before the rows leave the function. Pair deny with allow: an allow integration test that `deliver` completes against a `MockTransport` using rows produced by the real `_claim_batch`; a deny test asserting `_claim_batch`'s return value contains no `Base` subclass instances. Red-prove each clause separately by execution: (a) return the ORM rows again and confirm the allow test reddens with `DetachedInstanceError` named in the output; (b) remove the `status` write and confirm a second `_claim_batch` call re-claims the same row, reddening the claim test. Fail loudly: if `session.get(WebhookEndpoint, ...)` returns `None` the delivery must be finished with a named `failed_permanent` detail rather than `AttributeError` on `None.signing_secret`. Boundary and tie: a batch of exactly `BATCH_SIZE` rows and a batch of zero rows must both be handled, and two workers claiming rows whose `next_attempt_at` are equal must not both get the same row — which requires `SELECT ... FOR UPDATE SKIP LOCKED` or an equivalent conditional update, not the current read-then-write.

### Major: `in_flight` is a non-terminal state with no recovery path, and `attempts` is never persisted between attempts
File: `app/webhooks/delivery.py` — `_claim_batch()` sets `row.status = "in_flight"`; `deliver()` writes `attempts` only via the terminal `_finish()`
What is wrong: a row enters `in_flight` on claim and leaves it only when `deliver` reaches a terminal `_finish`, so a worker crash, a process restart, a lock expiry, or the `asyncio.gather` exception path leaves the row in `in_flight` permanently, and the retry counter lives only in a local variable (R38 clause 1).
What breaks in production: after any worker restart the affected deliveries are never retried and never reported as failed — they vanish from both the pending queue and the customer's `deliveries` view, which still shows the original `next_attempt_at` as though a retry were scheduled.
Fix: give the transient state a bounded exit — persist `attempts` and `next_attempt_at` on every attempt (not just the terminal one), stamp a `claimed_at` on the `in_flight` write, and add a reaper query that returns rows whose `claimed_at` is older than a stated lease (e.g. 5 minutes) to `pending` with their attempt count preserved. Do not fix this by removing the `in_flight` state, which is what prevents two workers double-sending. Pair deny with allow: allow — a row reclaimed by the reaper is delivered successfully and ends `delivered`; deny — a row claimed 10 seconds ago is NOT reclaimed. Red-prove each clause separately by execution: (a) remove the reaper and confirm the "stale row is retried" test reddens; (b) freeze `claimed_at` at `now` and confirm the same test reddens for the opposite reason; (c) drop the per-attempt `attempts` write and confirm an attempt-count-survives-restart assertion reddens. Fail loudly: if the reaper cannot read the clock or the lease value is unset it must refuse to run and log a named error, never default to reclaiming everything. Boundary and tie: a row whose `claimed_at` is exactly at the lease boundary is not yet reclaimable (state the side), and two rows sharing the same `claimed_at` are reclaimed together.

### Major: the Redis lock is not atomic and can be acquired by two workers, or held forever
File: `app/webhooks/delivery.py` — `_acquire_lock()`
What is wrong: `get` followed by `set` is a check-then-act with no atomicity, and `set` followed by a separate `expire` leaves a window in which a crash produces a key with no TTL.
What breaks in production: two workers pass the `get` before either `set` and deliver the same batch twice — customers get duplicate signed events — and a crash between `set` and `expire` leaves a permanent lock that stops all webhook delivery until someone deletes the key by hand.
Fix: one atomic call — `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token` is a per-worker random value, and release with a compare-and-delete (Lua `if get==token then del end`) so a worker whose lease already expired cannot delete the successor's lock, which the current unconditional `await redis_client.delete(LOCK_KEY)` in `run_worker`'s `finally` does today. Preserve the single-worker guarantee the lock exists for. Pair deny with allow: allow — a worker whose token matches releases the lock and a second worker then acquires it; deny — a worker whose token no longer matches does not delete it. Red-prove each clause separately by execution: (a) revert to `get`+`set` and confirm a concurrent-acquire test reddens (RT4: the test must be shown able to fail, not merely to run — assert both workers' acquire results, not just that no exception was raised); (b) revert to unconditional `delete` and confirm the stolen-lock test reddens; (c) drop `ex=60` and confirm a TTL assertion reddens. Fail loudly: a Redis error must be treated as "lock not acquired" and logged with a named reason, never as `False` indistinguishable from "someone else holds it" — the two must be separately observable. Boundary and tie: state that the lease is 60 seconds and that a batch whose processing exceeds it must renew or abort rather than continue unprotected, and that two workers presenting at exactly the same instant produce exactly one winner.

### Major: one failing delivery kills the worker and strands the rest of the batch
File: `app/webhooks/delivery.py` — `run_worker()`, line `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` without `return_exceptions=True` propagates the first exception out of the `while True` loop — and `deliver` only catches `httpx.HTTPError`, so a DB error, a `TypeError` from a non-JSON-serializable payload, or the integrity error from the status CHECK mismatch above escapes — while the remaining coroutines continue running detached against a client the `finally` is about to close.
What breaks in production: the delivery worker exits silently on the first unexpected error, every claimed row stays `in_flight`, and nothing restarts it or alerts, so webhooks stop for the whole platform until someone notices.
Fix: `results = await asyncio.gather(*[...], return_exceptions=True)`, then finish each row that returned an exception with a terminal status and a named detail, and wrap the loop body in a `try/except Exception` that logs with `log.exception` and continues to the next poll rather than exiting. Do not fix this by broadening `deliver`'s `except httpx.HTTPError` to a bare `except Exception` that swallows — the failure must still be recorded on the row and counted. Pair deny with allow: allow — a batch of three where one raises still delivers the other two and the loop performs a next iteration; deny — the raising delivery ends in a terminal state, not `in_flight`. Red-prove each clause separately by execution: (a) remove `return_exceptions=True` and confirm the "other two delivered" assertion reddens; (b) remove the per-result terminal write and confirm the "no row left in_flight" assertion reddens; (c) remove the loop-level `except` and confirm a "worker survives an unexpected error" assertion reddens (bound the loop in the test with a counter so the mutation reds rather than spins). Fail loudly: an exception the handler cannot classify must be logged with its type and the delivery id and set to a distinct status, so "we don't know what happened" is not spelled the same as "the endpoint returned 500". Boundary and tie: an empty `batch` must skip `gather` and sleep, and two deliveries failing with the same exception type must each get their own row update.

### Major: the dispatcher swallows every webhook enqueue failure
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: a blanket `except Exception` downgrades total enqueue failure to a warning and returns success, so the event is persisted and reported delivered-to-webhooks with nothing queued (R9: fire-and-forget past the transaction boundary with no compensating record).
What breaks in production: the unique-index defect and the CHECK-constraint defect above both surface here as a single `log.warning` line, so an outage in which no customer receives any webhook looks identical to a healthy run in every metric we have.
Fix: narrow the catch to the exceptions enqueue can legitimately raise, re-raise or record everything else, and make the failure durable rather than log-only — write a row (or increment a counter with the event id and error class) that an operator can query and that a reconciliation job can replay from `Event`. Preserve the property the `try` was added for: a webhook failure must still not roll back the already-committed event or block in-process subscribers. Pair deny with allow: allow — a successful enqueue emits no warning and returns the event id; deny — a raising enqueue produces a durable failure record AND the event id is still returned. Red-prove each clause separately by execution: (a) make `enqueue_for_event` raise and confirm the durable-record assertion reddens when the recording line is removed; (b) remove the `try` entirely and confirm the "event id still returned" assertion reddens. Per RT8 the deny test must assert the side effect (the failure record written, and that no delivery rows exist), not merely that `dispatch` returned. Fail loudly: an error class the handler does not recognise must be re-raised, so an unknown failure is never spelled the same as a handled one. Boundary and tie: an event type in `WEBHOOK_EVENT_TYPES` for an org with zero endpoints enqueues zero rows and is a success, not a failure — that is the case a naive "rows > 0" check would misclassify.

### Major: the hardcoded `WEBHOOK_EVENT_TYPES` set contradicts the documented subscription contract
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES = {"invoice.paid", "invoice.payment_failed", "subscription.updated"}`
What is wrong: the dispatcher gates enqueue on a three-element literal set while `app/webhooks/delivery.py::enqueue_for_event` treats an empty `endpoint.event_types` as "all events" and `docs/webhooks.md` promises "An empty `event_types` subscribes the endpoint to every event type we emit" — two independent membership decisions on one predicate, with the narrower one invisible to the customer (R12/R18/R48).
What breaks in production: a customer who registers with `event_types: []` or subscribes to any fourth event type receives nothing for it, with no error at registration time and no signal anywhere, and every new event type added later is silently excluded until someone remembers this set.
Fix: make the set the single registry both sides consult — derive it from the same source that `SUBSCRIBERS`/the event catalogue uses, export it, and have `create_webhook_endpoint` validate each requested `event_types` member against it and 422 on an unknown one so the mismatch surfaces at registration rather than at delivery time. Preserve the gate's purpose: events genuinely not intended for external delivery must still be excluded — the fix is to name that set once, not to remove it. Pair deny with allow: allow — registering `event_types: ["invoice.paid"]` succeeds and the event is enqueued; deny — registering `["invoice.refunded"]` while it is not webhook-eligible returns 422 naming the unknown type. Red-prove each clause separately by execution: (a) add a type to the registry without adding it to the dispatcher gate and confirm a parity test reddens; (b) remove the registration validation and confirm the 422 test reddens. Fail loudly: if the registry cannot be loaded, registration must refuse rather than accept every string. Boundary and tie: state explicitly what `event_types: []` means after this change — if it still means "all eligible types", the set it expands to is the registry at delivery time, and a type added later therefore starts flowing to existing empty-list endpoints, which is a behaviour change customers must be told about.

### Major: no restriction on the destination host — SSRF, and plaintext `http://` accepted against the documented contract
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; with `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the check accepts any scheme merely *beginning* with `http` and imposes no restriction on the host, so `http://169.254.169.254/...`, `http://localhost:6379/`, and internal RFC1918 addresses are all valid endpoints, and `follow_redirects=True` means even an external-looking host can redirect the request inward; `docs/webhooks.md` meanwhile states "Only `https://` URLs are accepted", which the code does not enforce.
What breaks in production: a customer can make our workers issue authenticated-looking POSTs with attacker-chosen JSON bodies to internal services and cloud metadata endpoints, and every event delivered over `http://` exposes the full payload in transit despite our published promise of TLS.
Fix: validate the scheme by equality (`parsed.scheme == "https"`, matching the doc) rather than by prefix; resolve the hostname at registration and reject loopback, link-local, RFC1918, RFC4193, and unspecified addresses; set `follow_redirects=False` on the delivery client so a 3xx is treated as a non-2xx failure; and re-check the resolved address at connection time (via a connection hook) because DNS can change between registration and delivery (R51 — the decision must bind to the address the socket uses, not to the name checked earlier). Preserve the feature: legitimate public HTTPS endpoints, including those on non-standard ports, must still register — do not fix this with a static customer-maintained allowlist. Pair deny with allow: allow — `https://hooks.example.com/acme` (the fixture already in the test file) registers and delivers; deny — `http://…`, `https://127.0.0.1/…`, `https://169.254.169.254/…`, and an external host that 302s to `http://127.0.0.1/` are each rejected. Red-prove each clause separately by execution: (a) restore `startswith("http")` and confirm the plaintext deny reddens; (b) remove the private-range check and confirm the metadata deny reddens; (c) restore `follow_redirects=True` and confirm the redirect deny reddens — three mutations, three named failures. Fail loudly: a hostname that does not resolve must be a named 422 at registration, never "no address to check, therefore allowed". Boundary and tie: state which side the boundary addresses fall on — `127.0.0.1` and `::1` are denied, `169.254.169.254` is denied, and a public address that a later DNS answer moves into a private range is denied at connect time rather than grandfathered by the registration check.

### Major: naive and timezone-aware datetimes are mixed across the write and the claim
File: `app/webhooks/delivery.py` — `enqueue_for_event()`, `next_attempt_at=datetime.utcnow()`; `_claim_batch()`, `now = datetime.now(timezone.utc)`; `migrations/0042_webhook_delivery.sql` — `next_attempt_at TIMESTAMP NOT NULL`

What breaks in production: in any deployment whose session or server time zone is not UTC the stored value is offset from the comparison value, so deliveries are either claimed early (before their backoff has elapsed, defeating the retry pacing) or never claimed at all.
Fix: use the aware helper the change already provides — `app/webhooks/models.py` defines `_now()` returning `datetime.now(timezone.utc)`, which `enqueue_for_event` reimplements as `datetime.utcnow()`; import and call `m._now()` there (R1: the shared helper exists in the same change). Change the migration to `TIMESTAMPTZ NOT NULL` for `next_attempt_at`, `created_at`, and `updated_at` on both new tables so the storage type matches the model. Preserve the scheduling behaviour: a freshly enqueued delivery must still be immediately claimable. Pair deny with allow: allow — a row enqueued now is returned by `_claim_batch`; deny — a row with `next_attempt_at` one minute in the future is not. Red-prove each clause separately by execution: (a) restore `utcnow()` and run the claim test under `TZ=Asia/Tokyo`, confirming it reddens; (b) restore `TIMESTAMP` in the migration and confirm a column-type assertion reddens. Fail loudly: comparing a naive to an aware datetime must raise rather than be coerced — do not add a `.replace(tzinfo=...)` that papers over the mismatch. Boundary and tie: a row whose `next_attempt_at` equals `now` exactly IS claimed (`<=`), and two rows with identical `next_attempt_at` are ordered arbitrarily by `ORDER BY next_attempt_at` — add `id` as a tie-break so pagination and claiming are deterministic (R57).

### Major: the signature header is written to application logs at INFO
File: `app/webhooks/delivery.py` — `send_once()`, line `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: the entire header dict, including `X-Acme-Signature` and `X-Acme-Timestamp`, is logged on every attempt at INFO level.
What breaks in production: because the signature does not bind the timestamp (see above), a logged signature is a reusable forgery token for that payload — anyone with log access, including downstream log-shipping and indexing systems, can replay signed events into the customer's endpoint indefinitely.

Fail loudly: if the log formatter raises on an unexpected argument the delivery must still proceed — logging must not be on the failure path of sending. Boundary and tie: state that the truncation cap is 2000 characters and that a body of exactly 2000 characters is stored unmodified.

### Major: `docs/webhooks.md` describes retry and scheduling behaviour the code does not implement (R29)
File: `docs/webhooks.md` — the "Retries" and "Inspecting deliveries" sections
What is wrong: three published claims are false against this diff — "backoff is exponential with jitter" (`backoff_for()` is deterministic `2**attempt`, no jitter anywhere), "a 4xx is permanent and we stop immediately" (`deliver()` retries every non-2xx status identically up to `MAX_ATTEMPTS`), and "when the next attempt is scheduled" (`next_attempt_at` is written once at enqueue and never advanced, so the value the endpoint returns is always the original enqueue time).
What breaks in production: customers size their own rate limits and alerting on the documented jitter and 4xx behaviour, so a broadcast event makes every endpoint retry in lockstep at exactly 2/4/8/16 seconds — a synchronised thundering herd — and a customer returning 400 for a malformed event is hammered five times instead of once.
Fix: change the code to match the published contract, since the contract is the one customers have integrated against — add full jitter to `backoff_for` (`timedelta(seconds=random.uniform(0, BASE_DELAY_SECONDS**attempt))` using a non-crypto RNG, which is correct here unlike in `signing.py`), branch on `400 <= status < 500` to `_finish(..., "failed_permanent", ...)` immediately (excluding 408 and 429, which are retryable), and write `next_attempt_at` on each retry per the scheduling fix above. Preserve the documented cap of 5 attempts and the 2/4/8/16-second growth of the upper bound. Pair deny with allow: allow — a 500 is retried and a 429 is retried; deny — a 400 is not retried and ends `failed_permanent` after exactly one attempt. Red-prove each clause separately by execution: (a) remove the 4xx branch and confirm the one-attempt assertion reddens; (b) remove the jitter and confirm a "two deliveries scheduled in the same second get different delays" assertion reddens; (c) remove the `next_attempt_at` write and confirm the schedule assertion reddens. Note that `tests/webhooks/test_delivery.py::test_backoff_grows_exponentially` asserts exact equality (`== 2`, `== 4`, …) and must be rewritten to assert the jitter range, not deleted — deleting it would remove the only check on the growth curve. Fail loudly: a status the classifier does not recognise (1xx, 3xx with redirects disabled) must be recorded with a named "unclassified status" detail rather than defaulting to retry. Boundary and tie: 400 and 499 are permanent, 500 and 408 and 429 are retryable, and 299/300 sit on either side of the success boundary — state each explicitly since `200 <= status < 300` is the only boundary the code currently draws.
