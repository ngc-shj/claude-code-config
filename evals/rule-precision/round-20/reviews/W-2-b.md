### Critical: migration CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint enumerates `'failed'`, but `app/webhooks/delivery.py:_finish` is only ever called with `"failed_permanent"` on the exhausted-retry path and `app/webhooks/models.py:STATUSES` also declares `"failed_permanent"`, so the value the code writes is not in the allowed set.
What breaks in production: The first delivery that exhausts `MAX_ATTEMPTS` raises an `IntegrityError` inside `_finish`, the row stays `in_flight` forever, and — because `_finish` is the last statement of `deliver` — the exception escapes `asyncio.gather` in `run_worker` and kills the worker for every other delivery in the batch.
Fix: Change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the SQL list from `models.STATUSES` in the review checklist so the two cannot drift again; add a migration-level test that inserts one row per member of `models.STATUSES` against the real migrated schema (not a mocked session) and asserts all four succeed — that is the allow side, and it must stay green after the fix. Red-prove each clause separately: (a) drop `'failed_permanent'` from the constraint and the `failed_permanent` insert must red with the constraint name in the failure text; (b) add a bogus `'x'` member to `STATUSES` and the same test must red on the insert of `'x'`, proving the test reads `STATUSES` rather than a hardcoded copy. If the test cannot reach a real Postgres (no `DATABASE_URL`, migration runner missing), it must `error` with a message naming the missing precondition, never `skip` — "examined nothing" must not be spelled like "found nothing". Preserve the constraint itself: do not fix this by deleting the `CHECK`, since the constraint is what stops a typo'd status from silently becoming a permanently unclaimable row. Boundary and tie: `STATUSES` is the exhaustive set — a status present in exactly one of the two lists is the failure this test pins, so assert set equality between `STATUSES` and the constraint's parsed membership, not one-way containment.

### Critical: unique index on `event_id` alone makes multi-endpoint fan-out fail
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `app/webhooks/delivery.py:enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the unique index permits at most one of those rows.
What breaks in production: An organization with two subscribed endpoints gets an `IntegrityError` on `session.add_all(rows)`, which `app/events/dispatcher.py:dispatch` swallows into `log.warning`, so **no** endpoint receives the event and the failure is invisible outside the log.
Fix: Replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — that is the idempotency key the feature actually needs, matching the docs' "deduplicate on `event_id`" per receiving endpoint. Pair the deny side with the allow side: one test enqueues an event for two active endpoints of the same org and asserts **two** rows are created (allow), and a second calls `enqueue_for_event` twice with the same `event_id` and asserts the second insert violates the constraint rather than creating duplicates (deny). Red-prove each separately: reverting to the single-column index must red the two-endpoint test on the insert; dropping the index entirely must red the duplicate-enqueue test on the row count. Fail loudly when the check cannot run: if the migration has not been applied the test must error naming `idx_webhook_deliveries_endpoint_event` as absent, not pass by finding zero rows. Do not fix by deleting the uniqueness — the index is the only thing preventing an at-least-once retry from re-enqueuing a duplicate row; keep it and widen the key. Boundary and tie: the tie case is two endpoints of the *same* org receiving the *same* `event_id` — that pair must be permitted, and the same `(endpoint_id, event_id)` pair must not.

### Critical: ORM rows are used after their session closes
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (reads `endpoint` and `delivery` attributes after the `with` block)
What is wrong: `_claim_batch` returns `m.WebhookDelivery` instances after the session that loaded them has exited, and `deliver` does the same with `endpoint`, then reads `delivery.attempts`, `delivery.id`, `delivery.payload`, `endpoint.url` and `endpoint.signing_secret` — all attribute loads on expired/detached instances.
What breaks in production: The worker raises `DetachedInstanceError` on the first claimed delivery, so no webhook is ever sent while rows accumulate permanently in `in_flight`; the deployed feature never works at all.
Fix: Have `_claim_batch` return plain data, not ORM instances — inside the session, mark the rows `in_flight` and return a list of frozen dataclasses (`id`, `endpoint_id`, `attempts`, `payload`) plus the joined endpoint's `url` and `signing_secret`, so nothing crosses the session boundary lazily; `deliver` and `send_once` then take that dataclass and never touch the ORM. Pair deny with allow: an integration test that runs `_claim_batch` against a real session and asserts the returned object's `payload` and `endpoint_id` are readable **after** the session has closed (allow side — the happy path must still produce a sendable delivery), and one asserting a claimed row's persisted `status` is `in_flight` when re-read in a fresh session. Red-prove separately: (a) return the ORM row instead of the dataclass and the after-close read must red with `DetachedInstanceError` named in the output; (b) remove the `row.status = "in_flight"` assignment and the fresh-session re-read must red on the status value. Fail loudly when the check cannot run: these tests must use a real session against the migrated schema and error — not skip — when the database is unavailable, since a mocked session returns live attributes and would pass vacuously (RT1: the mock's stability is what hides this defect). Do not fix by holding one long-lived session open across the HTTP calls: that would keep a database connection pinned for the full 30s request timeout per delivery and reintroduce the pool exhaustion the per-operation `session_scope` exists to avoid. Boundary and tie: the boundary is the `with session_scope()` exit — every field `deliver`/`send_once`/`_finish` reads must be materialized strictly before it, and two deliveries for the same endpoint must each carry their own copy rather than sharing one endpoint instance.

### Critical: the transmitted body is not the bytes that were signed, and the timestamp is unsigned
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` and does not include the timestamp, while `send_once` passes `json=delivery.payload` and lets `httpx` re-serialize the body with its own key order and separators — so the receiver following `docs/webhooks.md` ("HMAC-SHA256 of `{timestamp}.{raw_request_body}`") computes over neither the same bytes nor the same construction (R40; the change already contains the `serialize` helper that `send_once` bypasses — R1).
What breaks in production: Every customer who implements the documented verification rejects every webhook we send, and because the timestamp is outside the MAC an attacker who captures one request can rewrite `X-Acme-Timestamp` to defeat the five-minute replay window the docs present as the anti-replay control (R49: the doc claims a boundary the implementation does not provide).
Fix: Make the signed string and the wire bytes the same object: have `sign(secret, body: bytes)` return `(timestamp, "sha256=" + hmac_sha256(secret, f"{timestamp}.".encode() + body))`, and have `send_once` compute `body = serialize(delivery.payload).encode()` once and pass `content=body` (not `json=`) so httpx transmits exactly what was signed. Pair deny with allow: a round-trip test that feeds the **actual** captured `request.content` and the actual sent headers into `signing.verify` and asserts acceptance (allow side — the legitimate delivery must still verify), plus one that mutates only `X-Acme-Timestamp` on the captured request and asserts rejection (deny). Red-prove each clause separately: (a) revert `content=` to `json=` and the round-trip test must red on the signature comparison; (b) drop the `f"{timestamp}."` prefix and only the timestamp-mutation test must red; (c) change `sort_keys=True` to `False` and the round-trip test must red — three mutations, three distinct assertions. Fail loudly: `verify` must raise (not return `False`) on a signature that is not `sha256=<64 hex>`, so a malformed header is never spelled the same as a wrong key. Do not fix by relaxing the docs to match the code — the raw-body construction is what lets a receiver verify without re-serializing, and the timestamp binding is the replay control; both must be preserved. Boundary and tie: state that the replay window is `now - ts <= 300` inclusive at exactly 300 seconds, and that two requests sharing a timestamp are distinguished by `event_id`, which the receiver deduplicates on.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: This function is the reference verifier we publish for customers, so every integration built on it leaks signature-prefix timing and lets an attacker forge a signature byte-by-byte for payloads they choose.
Fix: `return hmac.compare_digest(expected, signature)` — `hmac` is already imported. Pair deny with allow: keep `test_verify_accepts_signature_produced_by_sign` green (the valid signature must still authenticate) and add a wrong-secret case that must return `False`. Red-prove each separately: (a) replace `compare_digest` with `==` and a static-analysis assertion (grep the module for a bare `==` on `expected`) must red; (b) invert the return and the accept test must red. Fail loudly: guard the length/shape first — `compare_digest` on a `str` raises `TypeError` for non-ASCII input, so normalize both sides to `bytes` and let a malformed header raise rather than silently comparing empty strings. Do not fix by deleting `verify` from the shipped module: it is the documented reference implementation, and removing it pushes every customer onto their own `==`. Boundary and tie: comparison must be over equal-length byte strings, and a signature of the correct length that differs in exactly one byte must take the same time as one differing in all of them.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from predictable state and is not a CSPRNG; `SECRET_BYTES = 32` is also used as a *character* count, so the name overstates what is produced.
What breaks in production: An attacker who observes enough generated secrets (or who knows roughly when an endpoint was created) can recover the generator state and forge signatures for any customer's webhooks, defeating the entire signing scheme.
Fix: `import secrets` and return `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, renaming nothing so `SECRET_BYTES` finally means bytes of entropy. Pair deny with allow: keep a test asserting the returned value still starts with `SECRET_PREFIX` and is accepted by `sign`/`verify` (allow — existing integrations must keep working), and add one asserting 1,000 generated secrets are all distinct. Red-prove each separately: (a) a module-level assertion that `app.webhooks.signing` does not import `random` — reintroducing `import random` must red it; (b) stub `secrets.token_urlsafe` to a constant and the distinctness test must red. Fail loudly: do not wrap the generation in a `try`/fallback to `random` — if the OS entropy source is unavailable, `secrets` raising is the correct outcome. Do not fix by only lengthening the output: entropy quality, not length, is the defect, and the existing prefix must be preserved because customers key on it. Boundary and tie: replace `test_new_signing_secret_has_prefix_and_length`'s `len(secret) == len(PREFIX) + SECRET_BYTES` assertion, which encodes the current bug and would still pass under `random.choice` — assert a minimum length instead and state that `token_urlsafe(32)` yields 43 characters.

### Critical: `list_deliveries` is not scoped to the caller's organization

Fail loudly: an unresolvable `user.org_id` must raise rather than fall through to an unfiltered query. Do not fix by removing the route — the deliveries view is the documented debugging surface; scope it instead. Boundary and tie: an endpoint that exists but belongs to another org and an endpoint that does not exist must be indistinguishable in the response, and a delivery whose endpoint was deleted (cascade) must simply not appear.

### Critical: the signing secret is returned on every endpoint list
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` returns `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py:list_webhook_endpoints`

Fail loudly: add a response-shape assertion over every route in the module that rejects any response dict containing a key matching `secret|token|key`, and have it error (naming the route) rather than skip when a route's response model cannot be introspected. Do not fix by removing the secret from the create response too — it is the only place the customer can ever obtain it, and the docs' storage instruction depends on it. ### Critical: customer-controlled delivery URLs give an unrestricted SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(timeout=REQUEST_TIMEOUT, follow_redirects=True)`
What is wrong: The only validation is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts `http://` (the docs say HTTPS only), accepts any host including loopback, RFC1918 and link-local addresses, and `follow_redirects=True` lets a benign-looking public host redirect the worker to an internal address after registration (R47: the check adjudicates the URL's surface form instead of the resolved destination).
What breaks in production: A customer registers `https://evil.example/x` that 302s to `http://169.254.169.254/latest/meta-data/`, and our worker POSTs signed internal requests and stores the response body in `webhook_deliveries.response_body`, turning the feature into a credential-exfiltration channel from inside the VPC.
Fix: Require `parsed.scheme == "https"` (exact equality, matching the documented contract), then resolve the host at *request* time and deny the request when any resolved address is loopback, link-local, private, reserved or multicast — implement it as an `httpx` transport/event hook so it is re-checked on every hop rather than once at registration, and set `follow_redirects=False` so a redirect is a delivery failure rather than a second unchecked destination. Pair deny with allow: a test that a normal public HTTPS endpoint still receives the POST and is marked `delivered` (allow — the whole feature is outbound HTTP; a fix that always denies satisfies every other clause), alongside deny tests for `http://`, `httpx://`, a literal `https://127.0.0.1/`, and a 302 to a private address. Red-prove each clause separately: (a) restore `startswith("http")` — the `httpx://` case must red; (b) restore `follow_redirects=True` — only the redirect case must red; (c) remove the address classification — only the private-address case must red. Fail loudly: when DNS resolution fails or returns no addresses, mark the delivery failed with a named reason; an unresolvable host must never take the same path as an allowed one. Do not fix by validating only at registration — that is the check the redirect and DNS rebinding both defeat — and do not narrow to an allowlist of hosts, which would break the feature's purpose. Boundary and tie: state which side `0.0.0.0`, IPv6 `::1` and IPv4-mapped `::ffff:127.0.0.1` fall on (all denied), and that a host resolving to both a public and a private address is denied.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered with `asyncio.gather`, but the retry backoff uses the blocking `time.sleep` rather than `await asyncio.sleep` (`asyncio` is already imported and used correctly in `run_worker`).
What breaks in production: One failing endpoint stalls the event loop for up to 2+4+8+16 = 30 seconds, freezing all 99 other deliveries in the batch and any other coroutine in the process, and pushing the total batch time past the 60-second lock TTL so a second worker starts re-delivering the same rows.
Fix: Replace with `await asyncio.sleep(delay)`. Pair deny with allow: a test asserting a delivery that succeeds on the second attempt still ends `delivered` (allow — retries must keep working), plus one that runs two `deliver` coroutines concurrently under `asyncio.gather` with a patched clock and asserts the second one's first request is issued before the first one's backoff elapses. Red-prove each separately: (a) restore `time.sleep` and the concurrency test must red on the observed request ordering; (b) remove the sleep entirely and the retry-timing test must red on elapsed time. Fail loudly: bound the total in-coroutine retry time and mark the delivery failed with a named reason when it is exceeded, so a hung endpoint is reported rather than silently holding a slot. Do not fix by deleting the backoff — the delay is what protects a struggling customer endpoint from being hammered. Boundary and tie: the first retry sleeps `BASE_DELAY_SECONDS**1` = 2s, the last permitted attempt is `MAX_ATTEMPTS`, and two deliveries scheduled for the same `next_attempt_at` must both progress rather than serializing.

### Major: the distributed lock is not atomic, expires mid-batch, and is deleted by non-owners
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a GET then a separate SET (two workers passing the GET both acquire), the TTL is 60s while a single `deliver` can legitimately run far longer (5 attempts × 30s timeout plus 30s backoff), and the `finally` deletes `LOCK_KEY` unconditionally even after the TTL has elapsed and another worker owns it.
What breaks in production: Two workers claim and POST the same deliveries, so customers receive duplicate `invoice.paid` webhooks — and because the delivery rows are already `in_flight`, the duplicate is invisible in our own data.
Fix: Use a single atomic `SET LOCK_KEY <uuid> NX EX 60` and delete only via a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) with the token this worker wrote; renew the TTL from a heartbeat task while the batch runs. Pair deny with allow: a test that a single worker acquires, processes and releases (allow — the worker must still make progress) and one where a second `_acquire_lock` while the first holds it returns `False`. Red-prove each separately: (a) revert to GET-then-SET and a test issuing two concurrent acquires must red on both returning `True`; (b) replace the compare-and-delete with a bare `delete` and a test where worker A's token has expired and worker B holds the lock must red on B's lock disappearing; (c) remove the heartbeat and a test with a batch longer than the TTL must red on the lock's expiry. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise and the worker must not process the batch — an errored lock must never be spelled the same as an acquired one. Do not fix by lengthening the TTL alone: a crashed worker would then wedge dispatch for the whole window, which is what the expiry exists to prevent. Boundary and tie: define the behaviour at exactly the TTL boundary (a worker whose token has expired must treat itself as having lost the lock and abandon the batch) and state that two workers presenting different tokens can never both delete.

### Major: `in_flight` is a non-terminal state with no recovery path
File: `app/webhooks/delivery.py` — `_claim_batch` (sets `row.status = "in_flight"`), `_finish` (the only writer back out of it)
What is wrong: `_claim_batch` only selects `status == "pending"`, so any row left `in_flight` by a crashed worker, an unhandled exception in `deliver`, or a lock expiry is never re-selected and never retried (R38 clause 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: A single worker restart silently drops every delivery in the batch it was holding, and because the deliveries API reports the row as `in_flight` rather than failed, nobody is alerted that customer webhooks stopped.
Fix: Stamp a `claimed_at` timestamp alongside `in_flight` and extend `_claim_batch` to also select `status == 'in_flight' AND claimed_at < now() - interval '5 minutes'`, resetting those rows to `pending` with `attempts` unchanged; add an explicit `except Exception` around each `deliver` in `run_worker` that routes the row back to `pending` (or to `failed_permanent` at `MAX_ATTEMPTS`). Pair deny with allow: a test that a row currently being worked (fresh `claimed_at`) is **not** re-claimed by a second pass (allow side — the reclaim must not cause duplicate sends), and one that a stale `in_flight` row is re-claimed. Red-prove each separately: (a) remove the staleness predicate and the stale-reclaim test must red; (b) remove the `claimed_at` freshness bound and the no-double-claim test must red; (c) remove the exception handler and a test whose `deliver` raises must red on the row's final status. Fail loudly: emit a counter/log naming the number of rows reclaimed per pass, so a silent backlog is visible rather than inferred. Do not fix by widening `_claim_batch` to all `in_flight` rows — that reintroduces the duplicate delivery the `in_flight` marker exists to prevent. Boundary and tie: a row whose `claimed_at` is exactly the staleness threshold is treated as stale (`<=`), and two workers racing on the same stale row are resolved by the row-level update returning zero affected rows for the loser.

### Major: naive and aware datetimes are mixed across the enqueue/claim boundary and the schema is timezone-naive
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP` columns; `app/webhooks/models.py` — `DateTime(timezone=True)`
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` while `_claim_batch` compares against an aware `datetime.now(timezone.utc)` and `_finish`/`models._now()` write aware values — and the migration declares `TIMESTAMP` (no time zone) where the models declare `DateTime(timezone=True)`, so the column type and the ORM type disagree (the change already contains `models._now()`, which `enqueue_for_event` reimplements incorrectly — R1/R3).
What breaks in production: On a database or session whose zone is not UTC, deliveries scheduled with `utcnow()` are interpreted as local time and become due hours early or late, and the aware/naive comparison in `_claim_batch` can raise `TypeError` outright, stalling dispatch.
Fix: Use `models._now()` (already defined and imported as `m`) in `enqueue_for_event`, and change every `TIMESTAMP` in the migration to `TIMESTAMPTZ` with `DEFAULT now()` so the column matches `DateTime(timezone=True)`. Pair deny with allow: a test that a delivery enqueued now is claimable by `_claim_batch` immediately (allow — the normal path must still fire) and one that a delivery scheduled one hour ahead is **not** claimed, both executed with the session time zone forced to a non-UTC value. Red-prove each separately: (a) restore `datetime.utcnow()` and the non-UTC future-delivery test must red by claiming a row it should not; (b) revert the column to `TIMESTAMP` and a round-trip test asserting `tzinfo is not None` on the re-read value must red. Fail loudly: assert `tzinfo is not None` on every datetime crossing into the model layer and raise on a naive value rather than coercing it. Do not fix by stripping tzinfo everywhere to match the migration — the aware values in `models._now` and `_claim_batch` are the correct side, and losing them removes the only thing that makes the schedule unambiguous across regions. Boundary and tie: `next_attempt_at <= now` is inclusive, so a delivery due at exactly this instant is claimed, and ties on `next_attempt_at` are broken by `id` in the `ORDER BY` so a batch boundary cannot repeat or skip a row.

### Major: the retry policy contradicts the documented one on 4xx and on jitter
File: `app/webhooks/delivery.py` — `deliver` retry loop; `docs/webhooks.md` — "Retries" section
What is wrong: The docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx status identically up to `MAX_ATTEMPTS` and `backoff_for` is a pure power of two with no jitter (R29: the documented rationale does not describe the implementation).
What breaks in production: A customer endpoint returning 401 or 410 is hammered five times per event, and because every delivery of a burst gets the identical backoff schedule, the retries arrive as a synchronized thundering herd on an endpoint that is already failing.
Fix: In `deliver`, treat `400 <= status_code < 500` (except 408 and 429, which are retryable by convention) as terminal and call `_finish(..., "failed_permanent", ...)` immediately; add jitter in `backoff_for` as `BASE_DELAY_SECONDS**attempt * random.uniform(0.5, 1.5)` using a dedicated non-crypto RNG (jitter is not a security value — keep `secrets` for the signing secret). Pair deny with allow: a test that a 500 is still retried to `MAX_ATTEMPTS` and a 429 is still retried (allow — retryable failures must keep retrying) alongside one that a 403 produces exactly one request. Red-prove each separately: (a) remove the 4xx branch and the 403 test must red on the request count; (b) remove the 408/429 carve-out and the 429 test must red; (c) fix `random.uniform` to a constant and a jitter test asserting distinct delays across runs must red. Fail loudly: an unexpected status outside 100–599 must be recorded as a failure with the raw value in `response_status`, not silently retried. Do not fix by editing the docs down to the current behaviour — the 4xx rule is what stops us from generating load against endpoints that have told us to stop, and the existing `test_backoff_grows_exponentially` parametrization must be updated to assert a range rather than deleted. Boundary and tie: 399 and 400 fall on opposite sides, 500 is retryable, and two deliveries scheduled for the same instant must get different jittered delays.

### Major: outbound signature headers are logged at INFO
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: `headers` contains `X-Acme-Signature` and `X-Acme-Timestamp`, so every delivery writes a valid signature for a known payload into the application log at INFO level (RS4).
What breaks in production: Anyone with log access — an indexer, an on-call engineer, a shipped log aggregator — can replay that exact payload to the customer's endpoint with a valid signature, and the log volume also grows with every attempt.

Pair deny with allow: a caplog-based test asserting the delivery id and URL **are** present in the emitted record (allow — the log must stay useful for debugging) and one asserting neither `SIGNATURE_HEADER` nor the signature value appears in any record emitted during a delivery. Red-prove each separately: (a) restore `headers=%s` and the redaction test must red naming the signature header; (b) drop the delivery id from the message and the usefulness test must red. Fail loudly: if the log record cannot be captured the test must error rather than pass on an empty record list. Do not fix by lowering the level to DEBUG — DEBUG is enabled in staging and the same credential lands in the same aggregator; remove the value, not the visibility. Boundary and tie: the redaction assertion must cover the header name and the header value independently, and a payload that happens to contain the literal `sha256=` must not make the test pass or fail for the wrong reason.

### Major: the enqueue failure path silently drops webhooks, and the enqueue is outside the event transaction
File: `app/events/dispatcher.py` — `dispatch`, `except Exception as exc: log.warning(...)`
What is wrong: The event row is committed in its own `session_scope`, then `enqueue_for_event` opens a second transaction, and any failure — including the `IntegrityError` from the `event_id` unique index above — is swallowed into a warning with no retry, no dead-letter, and no signal to the caller (R9: the dispatch is fire-and-forget across a closed transaction boundary).
What breaks in production: A transient database error between the two transactions permanently loses every webhook for that event with no record that a delivery was ever owed, and the caller's returned `event_id` implies success.
Fix: Enqueue the delivery rows in the **same** transaction as the `Event` insert — pass the open session into `enqueue_for_event` — so the event and its delivery rows commit or roll back together; where that is not possible, write an outbox row in the event transaction and have the worker expand it. Narrow the `except` to the exceptions you can actually recover from and re-raise the rest. Pair deny with allow: a test that a successful dispatch persists both the event and one delivery row per subscribed endpoint (allow — dispatch must still work end to end) and one where the delivery insert fails and asserts the event row is **also** absent afterwards. Red-prove each separately: (a) restore the separate `session_scope` and the atomicity test must red by finding an orphan event; (b) restore the bare `except Exception` and a test asserting the error propagates must red. Fail loudly: on an enqueue failure the dispatch must raise with the event type and org id in the message, so "no webhook was owed" is never spelled like "the webhook was enqueued". Do not fix by removing the try/except and letting webhook failures break event persistence for in-process subscribers — the `SUBSCRIBERS` loop must keep running; make the enqueue part of the same commit instead of unguarded. Boundary and tie: an event type in `WEBHOOK_EVENT_TYPES` with zero matching endpoints must commit normally with zero delivery rows (not an error), and an event whose org has exactly one endpoint must produce exactly one row.

### Major: `organizations.webhooks_enabled` is added by the migration and never read

### Major: untrusted response bodies are stored unbounded, and `_finish` assumes the row exists
File: `app/webhooks/delivery.py` — `_finish`, `row.response_body = detail` and `row = session.get(...)` with no `None` check
What is wrong: `detail` is built from `response.text` — arbitrary bytes from a customer-controlled server with no length cap — and `session.get` returns `None` for a deleted row, which then raises `AttributeError` on the next line.
What breaks in production: A customer endpoint returning a multi-megabyte error page writes it verbatim into `webhook_deliveries.response_body` on every delivery, bloating the table and the backups, and an endpoint deleted mid-flight (the `ON DELETE CASCADE` removes its deliveries) crashes the worker instead of skipping the row.

Do not fix by dropping `response_body` altogether: it is what makes the deliveries view diagnostic; cap it instead. Boundary and tie: a body of exactly `MAX_RESPONSE_BODY` characters is stored unchanged, and one of `MAX_RESPONSE_BODY + 1` is stored at exactly the limit.

### Major: the new tests never exercise the security primitives they appear to cover
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign`, `test_new_signing_secret_has_prefix_and_length`, `test_max_attempts_matches_documented_limit`
What is wrong: `verify` internally calls `sign`, so comparing `verify(SECRET, payload, sign(SECRET, payload))` asserts an identity of the subject against itself (RT1) and can never detect the `==` comparison or a change of algorithm; `test_new_signing_secret_has_prefix_and_length` passes identically under `random.choice` and under a CSPRNG; `test_max_attempts_matches_documented_limit` asserts a constant against a literal copy of itself rather than against the documented value (RT3); and no test reaches `deliver`, `_finish`, `_claim_batch`, `_acquire_lock`, or `enqueue_for_event` at all (RT5/RT6 — six new production symbols with no test diff).
What breaks in production: The suite is green while every defect above ships, which is worse than no tests because a reviewer reads "verify accepts / verify rejects" and concludes signature verification is covered.
Fix: Replace the tautological cases with tests that reach the production call path: verify against an **independently computed** expected digest written inline in the test (`hmac.new(SECRET.encode(), b"<ts>.<body>", sha256).hexdigest()`), not against `sign`'s own output; add a `deliver` test driving `MockTransport` through 500-500-200 that asserts the persisted status, `attempts` and `response_status`; add an `enqueue_for_event` test against a real session asserting one row per matching endpoint. Pair deny with allow throughout: each new test needs both the accepted and the rejected case (valid signature accepts, one-byte-mutated signature rejects; enabled endpoint enqueues, inactive endpoint does not). Red-prove each clause separately, one mutation per assertion: change `sha256` to `sha1` — only the independent-digest test reds; change `==` to always-true — only the mutated-signature test reds; force `send_once` to return 500 forever — only the retry-count assertion reds. Fail loudly: tests requiring a database must error naming the missing `DATABASE_URL` rather than `skip`, since a skipped security test reports the same green as a passing one. Do not fix by deleting the existing `send_once` tests — they are the only ones exercising the real HTTP path and must stay green after the change. Boundary and tie: assert the attempt boundary explicitly — exactly `MAX_ATTEMPTS` requests are issued and the row ends `failed_permanent`, with `MAX_ATTEMPTS - 1` retries, and a delivery that succeeds on the final attempt ends `delivered`.

## Cross-cutting verification summary

- **Org scoping**: applied in `list_webhook_endpoints`, absent in `list_deliveries` — the only missed location for that pattern in the diff.
- **Timezone-aware `datetime`**: `models._now()`, `_claim_batch` and `_finish` are aware; `enqueue_for_event`'s `datetime.utcnow()` is the single unpropagated site, and the migration's `TIMESTAMP` columns are the schema-side counterpart.
- **Status vocabulary**: `models.STATUSES` and `delivery.py` agree on `failed_permanent`; the migration's `CHECK` is the one site still on `failed`.
- **Serialization helper**: `signing.serialize` exists in the change and is used by `sign`, but `send_once` bypasses it with `json=` — the only site where the helper is reimplemented by the HTTP client.
- **Secret exposure**: `WebhookEndpoint.to_dict` is the single shared path; both `create_webhook_endpoint` and `list_webhook_endpoints` inherit the leak from it, so the fix belongs in `to_dict`, not in either route.
