### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The handler filters on the path-supplied `endpoint_id` alone while its two
sibling handlers added in the same hunk (`list_webhook_endpoints`, and `create_webhook_endpoint`
via `org_id=user.org_id`) both scope by `user.org_id`, so the org predicate was propagated to two
of the three new routes and dropped on the third (R3, security-relevant).
What breaks in production: Any authenticated user can enumerate integer endpoint ids and read
another tenant's delivery rows, whose `to_dict()` exposes `event_id`, `event_type` and response
status for that tenant's invoices — a cross-tenant data breach reachable with a single curl.
Fix: Join to the endpoint and filter on both keys in one query —
`session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` —
and return `404` (not `403`) when the join yields nothing, so the route does not confirm the
existence of a foreign endpoint. Still must pass: a caller listing deliveries for an endpoint their
own org owns gets the same rows and the same `limit` behaviour as before — assert that explicitly,
otherwise a handler that always returns `[]` satisfies the tightening. Red-prove separately, by
running each: (i) revert the `org_id` predicate and watch the foreign-tenant test go green-to-red on
row count; (ii) revert the 404 branch and watch the "no existence oracle" test fail on the status
code; (iii) delete the owner-side fixture's rows and watch the allow test fail on emptiness. Fail
loud: when `user.org_id` is None or absent, raise `HTTPException(401)` rather than falling through
to an unfiltered query — "no org resolved" must not be spelled the same as "no rows matched".
Preserve: the `created_at desc` ordering and the `limit` cap the endpoint already provides.
Boundary and tie: an endpoint whose `org_id` equals the caller's is INSIDE; a delivery whose
endpoint row was deleted is outside for every caller; when two orgs both reference the same
`event_id`, each sees only rows joined through its own endpoint.

### Critical: signing secrets are generated with the `random` module, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from predictable state and is not
cryptographically secure, so the per-endpoint HMAC key is drawn from a generator whose internal
state is recoverable from 624 prior outputs.
What breaks in production: An attacker who registers a few endpoints of their own recovers the
generator state and predicts other tenants' signing secrets, letting them forge webhooks that every
customer's verification code accepts as genuine — the entire signing scheme becomes decorative.
Fix: Replace with `secrets.choice(_ALPHABET)` (import `secrets`, drop `import random`) so the
existing length contract is unchanged, and rename `SECRET_BYTES` to `SECRET_CHARS` because the
value is a character count over a 62-symbol alphabet, not a byte count — the current name overstates
the entropy to the next reader. Still must pass: `test_new_signing_secret_has_prefix_and_length`
must remain green byte-for-byte in its assertions (this is why `secrets.token_urlsafe(32)` is the
wrong swap — it returns 43 chars and would force the test to be edited to accommodate the fix).
Red-prove separately, by running each: (i) put `random.choice` back and confirm a new
`test_secret_uses_the_crypto_rng` fails — assert it by monkeypatching `secrets.choice` and asserting
it was consulted, not by statistics; (ii) shorten the alphabet to one character and confirm a
uniqueness test over 1000 draws reddens; (iii) drop the prefix and confirm the prefix assertion
reddens. Fail loud: do not wrap the generator in a try/except that falls back to `random` when
`secrets` is unavailable — let the ImportError propagate at module load, because a silently
downgraded RNG is exactly the failure this fix exists to prevent. Preserve: the `whsec_` prefix and
the 32-character body, which the docs and the existing test both pin. Boundary and tie: two
endpoints created in the same millisecond must still receive different secrets — assert that, since
a time-seeded generator is precisely what makes them collide.

### Critical: the signature covers neither the timestamp nor the bytes actually transmitted
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` computes the MAC over `json.dumps(payload, sort_keys=True)` only, while
`docs/webhooks.md` tells customers the MAC is over `"{timestamp}.{raw_request_body}"`, and
`send_once` transmits a *different* byte string (`client.post(..., json=...)` re-serializes the dict
with httpx's own separators and insertion order) than the one that was signed.
What breaks in production: Every customer who implements verification exactly as documented
computes a different digest and rejects 100% of our webhooks, and the `X-Acme-Timestamp` header is
unauthenticated filler — an attacker can replay a captured request with any timestamp they like, so
the "five minute replay window" the docs sell as the anti-replay control is unenforceable.
Fix: Serialize once and sign what you send. Change `sign` to
`def sign(secret, body: bytes) -> tuple[str, str]` computing
`hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, have `send_once` build
`body = serialize(delivery.payload).encode()` and post it with `content=body` (not `json=`), and
change `verify(secret, body: bytes, timestamp: str, signature: str)` to take the same raw bytes.
Still must pass: a genuinely signed request must still verify — add a round-trip test that feeds the
bytes captured by `MockTransport` back through `verify` with the captured timestamp header and
asserts True (this is the case that a fix which merely tightens the MAC would silently break).
Red-prove separately, by running each: (i) flip one byte of the captured body and confirm the
round-trip test reddens; (ii) change the captured timestamp header by one second and confirm it
reddens for a reason the output names (timestamp not covered); (iii) swap `content=body` back to
`json=delivery.payload` and confirm the round-trip test reddens on the serialization divergence.
Fail loud: when `delivery.payload` is not JSON-serializable, let `serialize` raise and mark the
delivery `failed_permanent` with the exception text — never post an unsigned or partially-signed
body. Preserve: `sort_keys=True` determinism and the `sha256=` header prefix that the docs and
`test_sign_returns_timestamp_and_prefixed_digest` pin. Boundary and tie: state in the docs which
side of the five-minute window is rejected (`now - ts > 300` rejects, `== 300` accepts) and that
clock skew is the receiver's to absorb, since an unstated edge is where the next divergence enters.

### Critical: `verify` compares signatures with `==` instead of a constant-time comparison
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: Python's `str.__eq__` short-circuits on the first differing byte, so the comparison
leaks the length of the matching prefix through timing (RS1), in the one function whose entire job
is a credential comparison.
What breaks in production: Any component that adopts `verify` for inbound signature checking —
and our own docs instruct customers to use constant-time comparison, so this helper is the reference
implementation they will copy — lets an attacker recover a valid signature byte by byte over
repeated requests, defeating the HMAC without ever learning the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` of
equal charset first (`compare_digest` raises on mixed str/bytes). Still must pass: a signature
produced by `sign` for the same payload and secret must still return True —
`test_verify_accepts_signature_produced_by_sign` is that case and must stay green, which is what
distinguishes this fix from `return False`. Red-prove separately, by running each: (i) restore `==`
and confirm a new test asserting `hmac.compare_digest` is on the call path (monkeypatch spy)
reddens; (ii) corrupt the final hex character of a valid signature and confirm the reject test
reddens if `verify` returns True; (iii) pass a signature of a different length and confirm the
function returns False rather than raising. Fail loud: when `signature` is None or not a string,
return False explicitly with a `log.warning` naming the malformed input, rather than letting a
`TypeError` from `compare_digest` escape into a 500 that reads as a server fault. Preserve: the
existing signature-shape rejection behaviour and the return type (`bool`, not the digest). Boundary
and tie: a zero-length signature and a signature equal to `expected` but with a different `sha256=`
prefix casing must both be rejected — decide and assert the casing rule, because
`compare_digest` will not fold it for you.

### Critical: user-supplied endpoint URLs are fetched server-side with no scheme or address restriction
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only validation is `scheme.startswith("http")`, which admits plaintext `http://`
(and any scheme merely prefixed with it) while `docs/webhooks.md` states "Only `https://` URLs are
accepted", and nothing rejects private, loopback or link-local hosts before the worker POSTs to them
with redirects followed (RS3 — the boundary check exists but does not constrain the value's actual
sink).
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/` or an
internal service URL and our worker becomes a confused deputy, POSTing customer event payloads into
our own network from a trusted source address; even a well-meaning `https://` endpoint can redirect
us there, because `follow_redirects=True` re-resolves the target after the check.
Fix: Add a `_validate_endpoint_url(url) -> str` helper in `app/webhooks/delivery.py` (so the
worker and the route share one implementation rather than the route validating and the worker
trusting) that requires `parsed.scheme == "https"` exactly, resolves the hostname with
`socket.getaddrinfo` and rejects every resolved address for which
`ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved`, and rejects
a missing port-less netloc; call it from `create_webhook_endpoint` and again in `send_once`
immediately before the POST, and set `follow_redirects=False` on the client so a 3xx is recorded as
a failed delivery instead of being chased. Still must pass: `https://hooks.example.com/acme` — the
exact URL in `docs/webhooks.md` and in `FakeEndpoint` — must still be accepted and still be
delivered to; assert that, since a validator that rejects everything satisfies every other clause
here. Red-prove separately, by running each: (i) `http://hooks.example.com/acme` → expect 422, then
relax the scheme check to `startswith` and watch it redden; (ii) a host resolving to `127.0.0.1` →
expect 422, then remove the address check and watch it redden; (iii) an endpoint returning a 302 to
`http://169.254.169.254/` → expect the delivery recorded non-2xx and no second request issued, then
set `follow_redirects=True` and watch the request-count assertion redden. Fail loud: when DNS
resolution fails or times out, reject the registration with 422 and fail the delivery attempt with a
named reason — "could not resolve" must not fall through to "no disallowed address found".
Preserve: legitimate public HTTPS endpoints on non-standard ports must still register; do not
"fix" this by dropping `follow_redirects` support silently — document that redirects are no longer
followed in `docs/webhooks.md`. Boundary and tie: a hostname resolving to both a public and a
private address must be rejected (all-must-pass, not any), and re-resolution at POST time is what
closes the DNS-rebinding interval between check and use.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`

`'failed'`, so the same enum is spelled two ways across a storage boundary owned by one team (R40).
What breaks in production: Every delivery that exhausts its retries raises `IntegrityError` inside
`_finish`, the exception escapes `deliver` (it is not an `httpx.HTTPError`), and the row is left
stranded in `in_flight` forever — the failure path, which is the only path an operator ever
inspects, is the one that cannot be written.
Fix: Change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`
and generate the list from a single source: define `STATUSES` in `app/webhooks/models.py` (it already
exists and is currently unused by both the column and the constraint), set
`status = Column(String(20), nullable=False, default="pending")` to
`Enum(*STATUSES, name="webhook_delivery_status")`, and add a test that asserts the constraint's
accepted set equals `STATUSES` by attempting an insert of each member. Still must pass: inserting
`'pending'`, `'in_flight'` and `'delivered'` must continue to succeed — assert all four members
insert, not just the new one, because widening the CHECK to allow anything would satisfy a
new-member-only test. Red-prove separately, by running each: (i) revert the constraint to `'failed'`
and watch the `failed_permanent` insert test redden with a CHECK violation named in the output;
(ii) add a bogus member to `STATUSES` without touching the SQL and watch the set-equality test
redden; (iii) insert `'FAILED_PERMANENT'` and confirm it is rejected (case is significant).
Fail loud: `_finish` must not swallow the write error — wrap the session in a try/except that
re-raises after logging the delivery id, so a status that cannot be persisted is a loud failure
rather than a row silently left in `in_flight`. Preserve: the four documented lifecycle states and
the `attempts`/`response_status` columns written alongside. Boundary and tie: state that a delivery
at exactly `attempts == MAX_ATTEMPTS` is terminal (`>=` in `deliver`) and that a row already
`delivered` is never re-transitioned, so a late-arriving `_finish` cannot downgrade it.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all
sharing the same `event_id`, so the unique index rejects the batch for any organization with two or
more subscribed endpoints — the schema forbids exactly the fan-out the feature exists to provide.
What breaks in production: The `session.add_all` raises on flush, the dispatcher's blanket
`except Exception: log.warning(...)` swallows it, and the organization receives *zero* webhooks for
that event on *all* of its endpoints, with nothing in the deliveries table to show anything was ever
attempted.
Fix: Replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`,
which keeps the idempotency guarantee the index was reaching for (one delivery per endpoint per
event, so a re-dispatch of the same event cannot double-enqueue) while permitting fan-out; make
`enqueue_for_event` use `ON CONFLICT DO NOTHING` semantics
(`insert(...).on_conflict_do_nothing(index_elements=["endpoint_id", "event_id"])`) so a re-dispatch
is a no-op rather than an exception. Still must pass: an org with two subscribed endpoints must
receive two rows for one event — assert the row count is 2, since a fix that simply drops the index
would also make the single-endpoint test pass. Red-prove separately, by running each: (i) restore
the single-column index and watch the two-endpoint test redden with a unique violation; (ii) call
`enqueue_for_event` twice with the same `event_id` and watch a duplicate-suppression test redden if
`on_conflict_do_nothing` is removed; (iii) enqueue two *different* events for one endpoint and
confirm both rows persist (the index must not over-constrain). Fail loud: remove the dispatcher's
`except Exception` swallow for this path (see the separate finding) so an enqueue that cannot write
surfaces rather than being logged at WARNING and forgotten. Preserve: `idx_webhook_deliveries_status`
and the at-least-once contract the docs promise. Boundary and tie: two endpoints of the *same* org
subscribed to the same event each get exactly one row; the same `(endpoint_id, event_id)` arriving
twice yields one row, and the second call must report 0 inserted rather than raising.

### Critical: `time.sleep` inside the async retry loop blocks the worker's event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` (100) at a time, and
`time.sleep` is a synchronous call that parks the whole event loop rather than yielding — the same
mistake is latent in `enqueue_for_event` and `_claim_batch`, which are declared `async` but perform
blocking synchronous ORM work.
What breaks in production: A single slow endpoint stalls all 100 concurrent deliveries and every
other coroutine on that loop for up to 2+4+8+16 = 30 seconds, which also exceeds the 60-second lock
TTL once two such deliveries queue up, so a second worker acquires the lock and re-delivers the
batch — the blocking bug converts directly into duplicate customer webhooks.
Fix: Use `await asyncio.sleep(delay)`; then remove the in-process retry loop entirely and persist
the schedule instead — on a non-terminal failure, write `status="pending"`,
`attempts=attempt`, `next_attempt_at=datetime.now(timezone.utc) + backoff_for(attempt)` and return,
letting the next poll re-claim the row (this is what makes `next_attempt_at`, which the API already
returns to customers as "when the next attempt is scheduled", a true statement). Run the blocking
ORM calls through `asyncio.to_thread(...)` or an async session so `_claim_batch` and
`enqueue_for_event` stop parking the loop too. Still must pass: a delivery that succeeds on its
second attempt must still end `delivered` with `attempts == 2` — assert it, because a fix that
simply returns after the first failure also removes the blocking call. Red-prove separately, by
running each: (i) restore `time.sleep` and watch a test that gathers two deliveries and asserts
wall-clock elapsed < the sum of their delays redden; (ii) drop the `next_attempt_at` update and
watch a test asserting the row is not re-claimed before its backoff elapses redden; (iii) drop the
`attempts=attempt` write and watch the attempt-count assertion redden. Fail loud: if
`_finish`/reschedule cannot write, log at ERROR with the delivery id and re-raise — a delivery whose
schedule was not persisted must not be reported as handled. Preserve: the documented 2/4/8/16 second
progression and the 5-attempt ceiling; do not "fix" the stall by shrinking `BATCH_SIZE`.
Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (`<=`, as written),
and two rows with an identical `next_attempt_at` must both be claimed in one batch rather than one
being starved.

### Major: ORM instances are read after their `session_scope` block has exited
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after the `with` block) and `deliver` (`endpoint = session.get(...)` outside the block, then `endpoint.signing_secret`/`endpoint.url` in `send_once`)

assert the transmitted body equals the stored payload, since a fix that returns empty tuples also

`payload` from the projection and watch the body-equality assertion redden; (iii) delete the
endpoint row between claim and deliver and confirm the delivery is failed with a named reason rather
than raising `AttributeError` on `None`. Fail loud: `session.get` returning `None` for the endpoint
must call `_finish(..., "failed_permanent", ..., "endpoint deleted")`, not proceed into `send_once`.
Preserve: batch claiming and the `in_flight` marking that prevents double-claiming. Boundary and
tie: a row claimed at the instant its endpoint is deactivated must be resolved one way explicitly —
decide whether in-flight deliveries for a deactivated endpoint are sent or abandoned, and assert it.

### Major: `in_flight` is a non-terminal state with no timeout and no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `deliver`
What is wrong: A row enters `in_flight` at claim time and leaves it only via `_finish` on the
success or exhaustion path; a worker crash, a redeploy, an unhandled exception, or the CHECK-
constraint failure above leaves it there permanently, and nothing in the diff resets it (R38, mode 1:
an async transition with no failure-exit and no bounded timeout).
What breaks in production: Deliveries silently disappear — `_claim_batch` only selects
`status == "pending"`, so a stuck row is never retried, never reported as failed, and the customer's
event is lost with the deliveries API showing it perpetually mid-flight.
Fix: Add a `claimed_at TIMESTAMPTZ` column and reap on each poll:
`UPDATE webhook_deliveries SET status='pending', next_attempt_at=now() WHERE status='in_flight' AND claimed_at < now() - interval '10 minutes'`,
executed at the top of `run_worker`'s loop before `_claim_batch`, with the reaped count logged at
WARNING. Still must pass: a delivery currently being worked (claimed 5 seconds ago) must NOT be
reaped — assert that, because a reaper with no age predicate would re-claim everything and produce
duplicate sends. Red-prove separately, by running each: (i) set `claimed_at` to 11 minutes ago and
confirm the reaper returns it to `pending`, then remove the reaper and watch it redden; (ii) set
`claimed_at` to 9 minutes ago and confirm it is left alone, then remove the age predicate and watch
that assertion redden; (iii) crash a delivery mid-flight in an integration test and confirm the row
is eventually redelivered. Fail loud: if the reap statement itself errors, log at ERROR and skip the
poll rather than proceeding to `_claim_batch` on a possibly-wedged table. Preserve: the `in_flight`
state itself — it is what stops two workers claiming the same row; do not fix this by deleting the
state. Boundary and tie: a row at exactly the 10-minute mark must fall on the not-yet-reaped side
(strict `<`), and the reap window must exceed the worst-case single-attempt time
(`REQUEST_TIMEOUT` × `MAX_ATTEMPTS` plus backoff) or a live delivery gets duplicated.

### Major: the dispatch lock is acquired non-atomically and can wedge permanently
File: `app/webhooks/delivery.py` — `_acquire_lock`
What is wrong: `get` followed by `set` is a check-then-act race, and `set` followed by a separate
`expire` leaves a window in which the key exists with no TTL.
What breaks in production: Two workers starting together both observe an empty key and both
dispatch the same batch, doubling every webhook; and if a worker is killed between `set` and
`expire`, the lock never expires and *no* worker dispatches anything again until someone deletes the
key by hand — an outage with no error in any log.
Fix: One atomic call — `await redis_client.set(LOCK_KEY, worker_id, nx=True, ex=60)` and return
its truthiness; release with a compare-and-delete Lua script keyed on `worker_id` so a worker whose
lock already expired cannot delete the lock a *different* worker now holds; and renew the TTL
periodically while a batch is in flight rather than assuming 60 s is enough. Still must pass: a
single worker with no contention must still acquire the lock on every poll and make progress —
assert a full poll cycle completes, because always returning False satisfies the mutual-exclusion
half by itself. Red-prove separately, by running each: (i) run two `_acquire_lock` calls
concurrently and assert exactly one True, then restore the `get`/`set` pair and watch it redden;
(ii) simulate a crash after acquisition and assert the key carries a TTL, then drop `ex=60` and
watch it redden; (iii) have worker A's lock expire, let worker B acquire, then run A's release and
assert B still holds it — restore the unconditional `delete` and watch it redden. Fail loud: when
Redis is unreachable, `_acquire_lock` must raise or return False *and* log at ERROR — "cannot reach
the lock service" must not be spelled the same as "another worker holds it", and it must certainly
not be spelled the same as "acquired". Preserve: the existing poll-and-skip behaviour when the lock
is held. Boundary and tie: when two workers race at the same millisecond exactly one wins and the
loser sleeps `poll_interval`; state that the lock TTL must be strictly greater than the maximum
batch duration, or the guarantee is nominal only.

### Major: `organizations.webhooks_enabled` is added by the migration and never read
