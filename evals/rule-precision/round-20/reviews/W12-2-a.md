### Critical: the signature is computed over different bytes than the request actually sends
File: `app/webhooks/signing.py` — `sign`/`serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators) while `send_once` posts `client.post(endpoint.url, json=delivery.payload, ...)`, so httpx re-serializes the dict with its own encoder and the byte string that was signed is never the byte string on the wire; `docs/webhooks.md` additionally tells consumers the MAC covers `"{timestamp}.{raw_request_body}"`, but `sign` never feeds the timestamp into the HMAC at all.
What breaks in production: every customer who implements the documented verification over the raw body rejects 100% of our webhooks, and the `X-Acme-Timestamp` header being outside the MAC means the documented five-minute replay window is unenforceable because an attacker can rewrite the timestamp on a captured request without invalidating the signature.
Fix: serialize once and send those exact bytes — in `send_once` compute `body = serialize(delivery.payload).encode()`, `ts = str(int(time.time()))`, `sig = sign_raw(endpoint.signing_secret, ts, body)` where `sign_raw` HMACs `ts.encode() + b"." + body`, then `await client.post(endpoint.url, content=body, headers={"Content-Type": "application/json", ...})`; change `verify(secret, payload, signature)` to `verify(secret, timestamp: str, raw_body: bytes, signature: str)` so the verifier can never re-serialize its way to a false match. Behaviour that must be preserved: the request is still `Content-Type: application/json` carrying the same JSON object, so `test_send_once_posts_the_signed_payload`'s `content-type` and `json.loads(body)["type"] == "invoice.paid"` assertions must both stay green. Allow side to pin: a consumer that HMACs the literal received bytes with the correct secret verifies True. Red-prove each clause separately by execution: (i) drop `sort_keys=True` from `serialize` — the raw-body round-trip test reds on signature mismatch; (ii) remove `ts.encode() + b"."` from the MAC input — a test that mutates only the timestamp header and expects `verify` False reds; (iii) switch the POST back to `json=` — the raw-body round-trip test reds while the existing shape assertions stay green, which is the whole point. Fail loudly: if `serialize` raises (non-JSON-serialisable payload), `send_once` must raise before issuing the request so an unsigned or wrongly-signed POST is never sent — "could not sign" must not be spelled the same as "signed". Boundary and tie: state the skew rule as `abs(now - ts) <= 300` — a timestamp exactly 300s old is ACCEPTED, 301s is rejected — and document it in `docs/webhooks.md` in those terms.

### Critical: signature comparison is not constant-time (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, and this is the reference verifier we ship to customers in `docs/webhooks.md`.
What breaks in production: an attacker who can submit candidate signatures to any consumer built on this function recovers a valid signature byte-by-byte from response-time differences and forges webhook events.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` (or both to `bytes`) before the call. Behaviour that must be preserved: a signature produced by `sign` with the right secret still returns True — `test_verify_accepts_signature_produced_by_sign` is the allow-side case and must stay green, alongside `test_verify_rejects_a_signature_made_with_another_secret`. Red-prove separately: (i) revert to `==` — a test that monkeypatches `hmac.compare_digest` with a counting spy and asserts it was called exactly once reds; (ii) flip one hex nibble of a valid signature — `verify` returns False; (iii) pass a signature of the right value but wrong length prefix — returns False. Fail loudly: a `signature` argument that is not a string must raise `TypeError` rather than returning False, so a caller passing `None` sees an error instead of a silent, indistinguishable-from-forgery denial. Boundary and tie: `compare_digest` leaks length but not content — say so in the doc, and require consumers to length-check the `sha256=` prefix before comparing so an empty or truncated header is rejected on shape, not on timing.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is the Mersenne Twister, whose internal state is fully recoverable from a few hundred consecutive outputs, and it is seeded process-wide rather than from the OS entropy pool.
What breaks in production: an attacker who registers enough endpoints of their own to observe the generator's output stream (each registration returns 32 characters of it via `to_dict`) can predict the signing secrets issued to other organizations and forge signed `invoice.paid` events into their systems.
Fix: use `secrets` — `return SECRET_PREFIX + "".join(secrets.choice(_ALPHABET) for _ in range(SECRET_CHARS))`, and rename `SECRET_BYTES` to `SECRET_CHARS` because it counts characters from a 62-symbol alphabet (~190 bits), not bytes; drop the `import random` from this module entirely so no future edit reaches for it. Behaviour that must be preserved: the `whsec_` prefix and the exact length invariant, which `test_new_signing_secret_has_prefix_and_length` already pins and which must stay green. Allow side to pin: 1000 consecutive draws all start with `whsec_`, all have the documented length, and all 1000 are distinct. Red-prove separately: (i) revert to `random.choice` — a test asserting `"random" not in sys.modules` after a fresh import of `app.webhooks.signing`, or a spy on `secrets.choice` asserting it was called `SECRET_CHARS` times, reds; (ii) shorten the length to 8 — the existing length assertion reds; (iii) drop the prefix — the prefix assertion reds. Fail loudly: if the platform cannot supply entropy, `secrets` raises `NotImplementedError` — let it propagate out of endpoint creation as a 500 rather than falling back to any other generator, so "no entropy" cannot be spelled the same as "here is your secret". Boundary and tie: two endpoints created in the same microsecond must receive different secrets — this is the assertion that distinguishes a CSPRNG from a time-seeded one, and it is the tie case the current code fails on a fork.

### Critical: every read of an endpoint returns its signing secret, contradicting the documented contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict` embeds the secret, and `settings.py:list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` hands out every signing secret on demand — while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim strictly stronger than the implementation).
What breaks in production: the secret is now in every API response body, every client-side log, every HTTP cache and every proxy access log for a read-only listing endpoint, and any credential-scoped token that can list endpoints can forge webhooks; worse, downstream decisions were made on the doc's promise, so nobody is treating the listing response as secret-bearing.
Fix: delete the `"signing_secret"` key from `WebhookEndpoint.to_dict`, and in `create_webhook_endpoint` bind the generated value to a local (`secret = new_signing_secret()`) and return `{**endpoint.to_dict(), "signing_secret": secret}` so the one documented disclosure point still works. Behaviour that must be preserved: creation must still return the secret exactly once — removing it from creation too would satisfy every other clause while making the feature unusable. Allow side to pin: `POST /v1/settings/webhook-endpoints` response contains `signing_secret` and it round-trips through `verify`. Red-prove separately: (i) re-add the key to `to_dict` — a test asserting `"signing_secret" not in list_webhook_endpoints(...)[0]` reds; (ii) remove it from the creation response — the creation test reds; (iii) leave the doc claiming the current behaviour — a doc/response consistency test reds. Fail loudly: `to_dict` must not silently omit an attribute it cannot read; an endpoint row missing `url` should raise, not serialise to a partial dict a caller mistakes for complete. Boundary and tie: every secret issued before this change has already been exposed on a read path — the fix is incomplete without rotating all existing `webhook_endpoints.signing_secret` values and telling affected customers, since the code change does not un-disclose them.

### Critical: `list_deliveries` has no tenancy filter — cross-organization read
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query is scoped only by the caller-supplied `endpoint_id` and never joins back to `WebhookEndpoint.org_id == user.org_id`, even though the sibling handler added in the same diff, `list_webhook_endpoints`, does filter on `org_id` and the pre-existing `list_api_keys` does too (R3, incomplete propagation of a security-relevant pattern; `docs/webhooks.md` also claims the route returns deliveries "for an endpoint belonging to your organization").
What breaks in production: any authenticated user of any tenant iterating small integers reads every other tenant's delivery rows, and `WebhookDelivery.to_dict` exposes `event_type`, `status`, `attempts` and `response_status` per event — a full activity feed of every customer on the platform.
Fix: scope the query through the endpoint — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` when the endpoint does not resolve for this org, so a foreign id is indistinguishable from a nonexistent one. Behaviour that must be preserved: the owning org still receives its own rows in `created_at DESC` order under the same `limit`; a fix that returns an empty list for everyone satisfies the deny side and destroys the feature. Allow side to pin: org A's own endpoint returns exactly its own delivery rows. Red-prove separately: (i) delete the `org_id` predicate — a cross-tenant test (org B requests org A's endpoint id) that asserts BOTH a 404 status AND that the response body contains zero rows reds; (ii) change the not-found response from 404 to 403 — an enumeration test asserting the status for a foreign id equals the status for a nonexistent id reds; (iii) join on `WebhookDelivery.endpoint_id` without the `org_id` filter — the same cross-tenant test reds. Fail loudly: if `user.org_id` is `None` the handler must return 401 rather than issuing a query with `org_id IS NULL`, so a broken principal cannot be spelled the same as an empty result set. Boundary and tie: an endpoint that exists, belongs to the caller, but is `active=False` still returns 200 with its historical rows; an endpoint id that exists for another org and one that exists nowhere both return the identical 404 body.

### Critical: endpoint URL validation admits non-HTTPS and any private address, and the client follows redirects — SSRF with the response persisted
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `run_worker`, `httpx.AsyncClient(..., follow_redirects=True)` and `_finish(..., response.text)`
What is wrong: `scheme.startswith("http")` accepts `http`, and also `httpfoo`/`httpsx`, while `docs/webhooks.md` states "Only `https://` URLs are accepted"; nothing rejects loopback, link-local, or RFC1918 hosts; and `follow_redirects=True` means even a public HTTPS endpoint can bounce the worker to `http://169.254.169.254/latest/meta-data/` whose body is then stored in `response_body` and served back through `list_deliveries` (RS3/R47 — a surface-form check standing in for the property that matters).
What breaks in production: a customer registers an endpoint that redirects to internal infrastructure and reads cloud instance credentials, internal admin APIs, and anything else reachable from the worker's network position straight out of the deliveries listing, with our own signed request as the vehicle.
Fix: in `create_webhook_endpoint` require `parsed.scheme == "https"` and a non-empty `parsed.hostname`, resolve the hostname and reject when any resolved address satisfies `is_private or is_loopback or is_link_local or is_reserved or is_multicast` (`ipaddress.ip_address`), bound `EndpointIn.url` with `pydantic.HttpUrl` plus a max length so an arbitrarily long string cannot be stored; in `run_worker` set `follow_redirects=False` and treat any 3xx as `failed_permanent` with a named detail; and re-check the connected peer address at delivery time via a custom transport so DNS rebinding between registration and delivery does not walk around the registration-time check. Behaviour that must be preserved: an ordinary public endpoint such as `https://hooks.example.com/acme` still registers with 201 and still receives deliveries — that is the allow-side case to pin, and a validator that rejects everything satisfies every other clause. Red-prove separately: (i) revert to `startswith("http")` — a test asserting `http://hooks.example.com/x` returns 422 reds; (ii) remove the resolved-address check — a test registering a host that resolves to `127.0.0.1` and asserting 422 reds; (iii) restore `follow_redirects=True` — a `MockTransport` test where the endpoint returns 302 to `http://169.254.169.254/` and the test asserts exactly one outbound request and a `failed_permanent` status reds. Fail loudly: a hostname that cannot be resolved must return 422 naming "hostname could not be resolved", never fall through to acceptance — "could not check" must not be spelled the same as "checked and clean". Boundary and tie: CGNAT `100.64.0.0/10`, IPv6 `::1` and `fc00::/7` are rejected; a hostname resolving to both a public and a private address is rejected outright rather than being allowed on the public one.

### Critical: the migration's CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: the constraint allows `'failed'`, but `app/webhooks/models.py:STATUSES` declares `'failed_permanent'` and `app/webhooks/delivery.py:deliver` writes exactly that via `_finish(delivery.id, "failed_permanent", ...)` (R40 — a producer whose wire value the strict consumer rejects, with both sides owned by the same team and no test crossing the boundary).
What breaks in production: the first delivery to exhaust `MAX_ATTEMPTS` raises an `IntegrityError` inside the worker's `asyncio.gather`, so the row stays `in_flight` forever and, via the missing guard in `run_worker`, the worker loop dies — outbound webhooks stop platform-wide on the first permanently-failing endpoint.
Fix: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and wire `models.STATUSES` to it so the two cannot drift again — assert in a migration test that every member of `STATUSES` is insertable and that a value outside it is rejected. Behaviour that must be preserved: the constraint itself; loosening it to `status TEXT NOT NULL` would make the symptom vanish while removing the only thing that caught the typo, which is exactly the fix-by-deletion this must not be. Allow side to pin: inserting each of the four `STATUSES` members succeeds. Red-prove separately: (i) revert the SQL spelling to `'failed'` — the "every member of `STATUSES` is insertable" test reds; (ii) drop the CHECK clause entirely — a test asserting `INSERT ... status='bogus'` raises `IntegrityError` reds; (iii) add a fifth member to `STATUSES` without touching the SQL — the same insertability test reds, which is the drift guard. Fail loudly: the migration test must FAIL, not skip, when it cannot reach a real Postgres — a skipped constraint test reports the same green as a passing one. Boundary and tie: `'failed_permanent'` is 16 characters against `models.WebhookDelivery.status = Column(String(20))`, so it fits, but the SQL column is `TEXT` while the model says 20 — align them so a future status longer than 20 fails at the same place in both.

### Critical: `UNIQUE (event_id)` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness is on `event_id` alone, but `app/webhooks/delivery.py:enqueue_for_event` builds one row per matching endpoint for a single `event_id` and calls `session.add_all(rows)`.
What breaks in production: any organization with two subscribed endpoints hits a unique violation on every event, `dispatcher.dispatch` swallows it into `log.warning`, and all deliveries for that event — including the one that would have succeeded — are silently dropped with no row, no alert, and no retry.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`. Behaviour that must be preserved: per-endpoint idempotency — re-enqueuing the same event for the same endpoint must still be rejected, since that is what backs the doc's "delivery is at-least-once, so deduplicate on `event_id`"; dropping the index to make the insert succeed would remove the guarantee rather than fix the key. Allow side to pin: an org with two active endpoints subscribed to `invoice.paid` gets exactly two rows for one event. Red-prove separately: (i) revert to `(event_id)` — the two-endpoint fan-out test reds with `IntegrityError`; (ii) drop the unique index entirely — a test calling `enqueue_for_event` twice for the same event and asserting exactly one row per `(endpoint_id, event_id)` reds; (iii) reorder the columns to `(event_id, endpoint_id)` — the test still passes, which is correct and worth noting, but the index must lead with `endpoint_id` to also serve `list_deliveries`. Boundary and tie: two endpoints of the same org on one event both get rows; the same endpoint re-enqueued for the same event gets exactly one, and the second attempt must be handled with `ON CONFLICT DO NOTHING` rather than raising, so a retried dispatch is a no-op instead of an error.

### Critical: the worker uses ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` outside `with session_scope()`), `deliver` (`endpoint = session.get(...)` then used after the `with` block)
What is wrong: `_claim_batch` returns `WebhookDelivery` instances after `session_scope` exits, and `deliver`/`send_once` then read `delivery.payload`, `delivery.id`, `delivery.attempts`, `endpoint.signing_secret` and `endpoint.url` from instances whose session has committed and expired them, which raises `DetachedInstanceError` on the first attribute access under a standard SQLAlchemy `Session`.
What breaks in production: no webhook is ever delivered — every batch throws before the first POST — and the failure is invisible to the test suite because `tests/webhooks/test_delivery.py` substitutes `FakeEndpoint`/`FakeDelivery` plain classes with class attributes (RT1: the double diverges from the real boundary in precisely the property under test).
Fix: materialise plain data inside the session — have `_claim_batch` issue one join of `WebhookDelivery` to `WebhookEndpoint` and return a list of frozen dataclasses carrying `id`, `endpoint_id`, `attempts`, `payload`, `endpoint_url`, `signing_secret`, built and returned from inside the `with` block; change `deliver`/`send_once` to take that dataclass so no ORM instance ever crosses the session boundary. Behaviour that must be preserved: the `status = "in_flight"` claim must still happen in the same transaction as the read that selected the rows, or two workers re-claim the same row. Allow side to pin: an integration test against a real `Session` claims a pending row, delivers it, and observes `status='delivered'`. Red-prove separately: (i) return the ORM rows again — the real-`Session` integration test reds with `DetachedInstanceError`; (ii) remove the `row.status = "in_flight"` write — a test asserting a second `_claim_batch` returns an empty list reds; (iii) move the dataclass construction outside the `with` — the same detachment test reds. Fail loudly: if the join finds no endpoint for a claimed delivery (the endpoint was deleted mid-flight, which `ON DELETE CASCADE` makes possible), `_finish` it as `failed_permanent` with a named detail rather than skipping the row into permanent `in_flight`. Boundary and tie: a row whose `next_attempt_at` equals `now` exactly IS claimed (`<=`), and concurrent claimants must be separated by `SELECT ... FOR UPDATE SKIP LOCKED` inside that transaction rather than by the Redis lock.

### Critical: a blocking `time.sleep` inside an async coroutine
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` from `run_worker`, but it blocks with the synchronous `time.sleep` for up to 16 seconds per retry.
What breaks in production: the entire event loop stalls for the sum of every backoff in the batch — with `BATCH_SIZE = 100` and a widespread endpoint outage that is tens of minutes of a completely frozen process, and if the worker shares a loop with the FastAPI app every HTTP request including the health check times out.
Fix: stop retrying in-process — on a retryable failure, persist `attempts = attempt` and `next_attempt_at = _now() + backoff_for(attempt)`, set `status` back to `'pending'`, and return, letting the poller re-claim it; where an in-loop wait is genuinely required use `await asyncio.sleep(delay)`, never `time.sleep`. Behaviour that must be preserved: the documented 5-attempt cap and the 2/4/8/16-second schedule — `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` must both stay green. Allow side to pin: a delivery that fails once and succeeds on re-claim ends `delivered` with `attempts == 2`. Red-prove separately: (i) restore `time.sleep` — a test that schedules a concurrent `asyncio.sleep(0)` task and asserts it completes within a bound while a delivery is backing off reds; (ii) remove the `next_attempt_at` write — a test asserting a failed row is not re-claimable before its backoff elapses reds; (iii) leave `status` at `'in_flight'` instead of `'pending'` — a test asserting the row is re-claimable at all reds. Fail loudly: an exception that is not an `httpx.HTTPError` (a `DetachedInstanceError`, a JSON error, a DB error) must mark the row terminally with the exception text rather than escaping `gather` and leaving the row `in_flight` — "the worker crashed" must not be spelled the same as "nothing to do". Boundary and tie: at `attempt == MAX_ATTEMPTS` the row goes `failed_permanent` and is never rescheduled; at `attempt == MAX_ATTEMPTS - 1` it is rescheduled once more.

### Major: an `in_flight` delivery has no path back out on any failure (R38)
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish`
What is wrong: `in_flight` is left only by `_finish` on the success or exhaustion path, `_claim_batch` selects only `status == "pending"`, and nothing writes `attempts`/`next_attempt_at` between retries — so a crash, a redeploy, an `IntegrityError`, or the detachment error above strands the row forever.
What breaks in production: a single worker restart during a batch permanently loses up to 100 customer webhooks with no alert and no operator affordance to replay them.
Fix: give the transient state an explicit failure exit and a bounded timeout — write `attempts` and `next_attempt_at` on every attempt, and add to `_claim_batch` an OR branch reclaiming rows where `status = 'in_flight' AND updated_at < now() - interval '10 minutes'`, incrementing `attempts` so a poison row still terminates at `MAX_ATTEMPTS` rather than looping forever. Behaviour that must be preserved: a healthy in-progress delivery must not be reclaimed mid-flight, which is why the reclaim threshold must exceed `MAX_ATTEMPTS * REQUEST_TIMEOUT`; and the `attempts` increment on reclaim must stay, or the timeout becomes an infinite retry that satisfies the deny side while destroying the cap. Allow side to pin: a delivery in flight for 30 seconds is NOT reclaimed. Red-prove separately: (i) remove the reclaim branch — a test that marks a row `in_flight` with an old `updated_at` and asserts `_claim_batch` returns it reds; (ii) remove the `attempts` increment on reclaim — a test asserting a permanently-stranded row reaches `failed_permanent` within `MAX_ATTEMPTS` reclaims reds; (iii) set the threshold below the request timeout — the "healthy in-flight is not reclaimed" test reds. Fail loudly: emit a WARN naming each reclaimed delivery id so a stranded-row storm is visible rather than absorbed. Boundary and tie: a row whose `updated_at` is exactly at the threshold is NOT reclaimed (strict `<`), and two workers racing to reclaim the same stale row are separated by `FOR UPDATE SKIP LOCKED`.

### Major: `run_worker` raises `NameError` and dies whenever `_claim_batch` throws
File: `app/webhooks/delivery.py` — `run_worker`, `if not batch:` after the `try/finally`
What is wrong: `batch` is bound inside the `try`, but the `if not batch` test sits after the `finally`, so any exception from `_claim_batch` or `gather` propagates past the `finally` — and had it been caught, `batch` would be unbound.
What breaks in production: one transient DB error terminates the worker coroutine permanently and outbound webhooks stop until someone notices and restarts the process; there is no supervisor loop in the diff to restart it.
Fix: initialise `batch: list = []` before the `try`, wrap the body in `except Exception: log.exception("webhook dispatch pass failed")` so a single bad pass does not end the loop, and always `await asyncio.sleep(poll_interval)` on the error path to avoid a hot spin. Behaviour that must be preserved: a pass that legitimately finds no work still sleeps `poll_interval`, and a pass that finds work still loops immediately — collapsing both into an unconditional sleep would halve throughput. Allow side to pin: a pass returning 100 rows loops again without sleeping. Red-prove separately: (i) remove the pre-binding of `batch` and make `_claim_batch` raise — a test asserting the worker survives N passes reds with `NameError`; (ii) remove the `except` — the same test reds by the loop exiting; (iii) remove the sleep on the error path — a test asserting at most K iterations per second under a persistently failing `_claim_batch` reds. Fail loudly: `log.exception`, not `log.warning`, so the stack trace of the pass that failed is recorded rather than a one-line summary. Boundary and tie: an empty batch and a failed batch must be distinguishable in the logs — they are the two cases that currently both produce silence.

### Major: the Redis lock is non-atomic to acquire and released without ownership, and its TTL is shorter than the work it guards
File: `app/webhooks/delivery.py` — `_acquire_lock` (`get` then `set` then `expire`), `run_worker` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: the get-then-set is a TOCTOU window in which two workers both observe an empty key and both proceed; `set` and `expire` are separate round trips so a crash between them leaves a lock with no TTL; the `finally` deletes `LOCK_KEY` unconditionally without checking who owns it; and the 60-second TTL is less than a single delivery's worst case of `MAX_ATTEMPTS * REQUEST_TIMEOUT` plus 30 seconds of backoff.
What breaks in production: two workers claim the same batch — and because `_claim_batch` has no `FOR UPDATE SKIP LOCKED` either, the same event is POSTed twice to the customer, and a worker whose lock has expired deletes the lock a different worker is actively holding, so the double-delivery is self-sustaining rather than a one-off.
Fix: acquire with a single atomic call carrying a per-worker token — `token = secrets.token_hex(16); ok = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — release with a Lua compare-and-delete that only deletes when the stored value still equals the token, set `LOCK_TTL_SECONDS` above `MAX_ATTEMPTS * REQUEST_TIMEOUT + sum(backoff)`, and add `.with_for_update(skip_locked=True)` to `_claim_batch` so correctness does not rest on the lock alone. Behaviour that must be preserved: a worker that does not get the lock still sleeps and retries rather than exiting, and exactly one of N concurrent workers must get True — a fix that always returns False satisfies the deny side and stops all delivery. Allow side to pin: with one worker running, `_acquire_lock` returns True on every pass. Red-prove separately: (i) revert to get-then-set — a test launching two `_acquire_lock` coroutines concurrently and asserting exactly one True reds; (ii) replace the compare-and-delete with a plain `delete` — a test where worker A's token has been superseded by B's and A's release is asserted to be a no-op reds; (iii) drop `ex=` — a test asserting `TTL(LOCK_KEY) > 0` reds; (iv) drop `skip_locked` — a concurrent-claim test asserting disjoint batches reds. Fail loudly: a Redis error inside `_acquire_lock` must return False and log at ERROR, never be caught into a truthy result — "could not check the lock" must not be spelled the same as "the lock is free". Boundary and tie: a TTL expiring at the exact moment work completes makes the compare-and-delete a no-op rather than a cross-release, which is the tie this design exists to resolve.

### Major: 4xx responses are retried, contradicting the documented retry policy

### Major: the documented backoff jitter does not exist

### Major: the delivered request body carries no event identifier, so the documented deduplication is impossible
File: `app/webhooks/delivery.py` — `send_once`, `client.post(..., json=delivery.payload)`; `docs/webhooks.md` — "delivery is at-least-once, so deduplicate on `event_id`"

What breaks in production: at-least-once delivery is guaranteed by design (retries, reclaims, the double-delivery in the lock finding) and consumers are told to deduplicate on a value we never send, so every duplicate we emit is processed twice — for `invoice.paid` that is a double fulfilment.
Fix: send an envelope — `{"id": delivery.event_id, "type": delivery.event_type, "created_at": <iso8601>, "data": payload}` — and sign those bytes, so the identifier is inside the MAC and cannot be rewritten by a man in the middle. Boundary and tie: two endpoints receiving the same event share one `event_id` — which is correct, because dedup is per-consumer — while two retries to one endpoint also share it, which is the case the whole contract exists for.

### Major: `response_body` stores the remote endpoint's entire response, unbounded
File: `app/webhooks/delivery.py` — `deliver` (`detail = f"HTTP {response.status_code}: {response.text}"`, and `_finish(..., response.text)` on the success path); `migrations/0042_webhook_delivery.sql` (`response_body TEXT`)
What is wrong: the whole response body is read into memory and written to an unbounded `TEXT` column on every attempt, including successes, with no size limit anywhere in the path.
What breaks in production: a customer endpoint returning a large body writes it into the row and back out through `list_deliveries` — an amplification channel that a hostile registrant can point at us deliberately, and with the redirect-following SSRF above it is the exfiltration sink for whatever internal response the worker fetched.

Behaviour that must be preserved: enough of the body to diagnose a failing endpoint must survive, which is what the 2048-character head is for; recording nothing would satisfy the deny side and remove the feature's diagnostic value. Allow side to pin: a 200-character error body is stored verbatim and byte-identical. Red-prove separately: (i) remove the slice — a test with a 1MB response asserting the stored `response_body` length is `<= MAX_RESPONSE_BODY_CHARS` reds; (ii) truncate to 0 — the verbatim short-body test reds; (iii) buffer via `response.text` before slicing — a test asserting peak memory or bytes-read stays bounded for a 100MB response reds. Fail loudly: when truncation occurs, append an explicit `"… [truncated]"` marker so a truncated body cannot be read as a complete one. Boundary and tie: a body of exactly `MAX_RESPONSE_BODY_CHARS` is stored whole with no marker; `MAX_RESPONSE_BODY_CHARS + 1` is truncated and marked.
