### Critical: `verify()` compares HMACs with `==`, not a constant-time primitive
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: The signature comparison uses Python's short-circuiting `==` on the hex digest instead of `hmac.compare_digest`, so comparison time leaks how many leading bytes of a guessed signature are correct.
What breaks in production: Any caller of this shipped helper (and any customer who copies it, since `docs/webhooks.md` tells them to use constant-time comparison while our own reference implementation does not) can have a valid signature recovered byte-by-byte by an attacker who can time responses, letting forged webhook payloads be accepted.
Fix: Replace the body with `return hmac.compare_digest(expected, signature)`, importing nothing new (`hmac` is already imported at line 2). Preserve the behaviour the current line has that matters — `verify` must still return `False` rather than raise for a wrong-length or non-ASCII `signature`, so coerce with `signature.encode()`/`expected.encode()` and wrap the encode in a `try` that returns `False`; do not "fix" this by dropping the prefix check or by making `verify` raise, which would delete the caller-facing contract. Allow side to pin: `test_verify_accepts_signature_produced_by_sign` must still pass, plus a new case asserting a byte-identical signature from an independent literal (a checked-in known-answer vector) verifies `True`. Red-prove three clauses separately by execution: (i) mutate `compare_digest` back to `==` and assert a new timing/AST-level test reds; (ii) mutate one hex character of the vector and assert the reject test reds; (iii) pass `signature=None` and assert the test asserting `False` (not `TypeError`) reds when the `try` is removed. Fail loudly when the check cannot run: if `secret` is empty or `None`, raise `ValueError` rather than returning `False` — "no secret configured" must not be spelled the same as "signature did not match". Boundary and tie: a signature of the correct length that differs in exactly one character is the boundary case and must return `False`; two candidate signatures of different lengths must also return `False` without an early length short-circuit outside `compare_digest`.

### Critical: signing secrets are generated from `random`, a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The secret is drawn from `random`, a Mersenne Twister seeded from predictable state and explicitly not suitable for security use, rather than from `secrets`, which the standard library already provides for exactly this job (evidence for R1: no project helper is reimplemented here, but the language's own shared security helper is — `secrets.choice` has the identical signature to the `random.choice` on line 409).
What breaks in production: An attacker who observes ~624 outputs of the same generator (trivially harvested if the process also uses `random` elsewhere, or by registering endpoints repeatedly and reading back the secret via the leak reported below) can reconstruct the MT19937 state and predict every other tenant's signing secret, forging arbitrary signed webhooks into their systems.
Fix: `import secrets` and generate with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`; rename `SECRET_BYTES` to what it now means (raw entropy bytes, not output characters) and update `test_new_signing_secret_has_prefix_and_length`, which currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` and would otherwise red for the wrong reason. Preserve the two properties the current function does provide and that consumers depend on: the `whsec_` prefix and a URL/header-safe alphabet. Allow side to pin: a test asserting a freshly generated secret still starts with `SECRET_PREFIX` and still round-trips through `sign`/`verify`. Red-prove each clause separately: (i) mutate the generator to return a constant `"whsec_" + "a"*43` and assert a new uniqueness test (N=1000 distinct secrets) reds — the existing length test does not red under this mutation, which is why it never caught the defect; (ii) mutate `token_urlsafe(32)` to `token_urlsafe(4)` and assert a minimum-entropy test reds; (iii) mutate the prefix and assert the prefix test reds. Fail loudly when the check cannot run: rotate all secrets issued before this fix and treat them as compromised — add a `secret_version` column and reject `verify` against a v1 secret rather than silently accepting it, so "cannot evaluate this secret's provenance" denies. Boundary and tie: a secret of exactly the minimum accepted length must be accepted; two endpoints generated in the same microsecond must not collide, which is what the N=1000 uniqueness test pins.

### Critical: the bytes signed are not the bytes sent, so no receiver can ever verify a delivery
File: `app/webhooks/delivery.py` — `send_once`, `sign(...)` vs `client.post(..., json=delivery.payload)`
What is wrong: `sign` HMACs `signing.serialize(payload)` = `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted), while httpx re-serializes `json=` itself with compact separators and insertion order, so the MAC covers a different byte string than the request body — and `signing.serialize` exists in this same diff as the helper `send_once` was supposed to use (R1/R40 evidence).
What breaks in production: Every customer following `docs/webhooks.md` computes the HMAC over the raw body they received and gets a mismatch, so 100% of deliveries are rejected at every integration while our side records them as `delivered` — a silent total-path failure that no test in this diff can see, because `test_send_once_posts_the_signed_payload` only asserts the header *starts with* `sha256=` and never recomputes the MAC over `captured["body"]`.
Fix: Serialize once and send bytes: `body = serialize(payload).encode()`, sign that exact `bytes`, and post with `client.post(endpoint.url, content=body, headers=headers)` keeping the explicit `Content-Type: application/json`; delete the `json=` kwarg so there is exactly one serializer on the path. Do not fix this by relaxing the docs to "signature covers a canonical form" — the behaviour that must be preserved is that a receiver can verify using only the bytes on the wire. Allow side to pin: extend `test_send_once_posts_the_signed_payload` to recompute `hmac.new(SECRET, captured["body"], sha256).hexdigest()` from the captured raw body and assert it equals the captured signature header — a real producer-output-through-real-consumer round trip, not two mocked shapes (R40 reviewer action). Red-prove each clause separately: (i) revert `content=` to `json=` and assert the recomputation test reds; (ii) drop `sort_keys=True` from `serialize` and assert the same test reds for a two-key payload with non-sorted insertion order; (iii) mutate `serialize` to `ensure_ascii=False` and assert a non-ASCII payload fixture reds. Fail loudly when the check cannot run: if `payload` is not JSON-serializable, raise before the POST rather than shipping an unsigned or partially-signed request. Boundary and tie: an empty payload `{}` must still produce a well-defined MAC over `"{}"`, and two payloads that differ only in key order must produce the *same* MAC (that is what `sort_keys` buys) while two that differ in a value must not.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window stops nothing
File: `app/webhooks/signing.py` — `sign`, `mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`; `docs/webhooks.md` "Verifying the signature"
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed", but `sign` MACs the body alone and returns the timestamp as an independent, unauthenticated header (R49: a claim strictly stronger than the implementation; R29: a false rationale attached to a security control).
What breaks in production: An attacker who captures one delivery can rewrite `X-Acme-Timestamp` to the current time and replay the identical body and signature indefinitely, and every customer who implemented exactly what the docs said believes they are protected — a control that was documented as an enforceable boundary while implemented as nothing at all.
Fix: Change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` where `body` is the same byte string sent on the wire (see the previous finding), and change `verify` to take the timestamp as an explicit required argument rather than recomputing it from `time.time()` — the current `verify` re-derives a *fresh* timestamp and therefore cannot verify any signature it did not create in the same second, which is a second live defect in the same three lines. Add the five-minute skew check inside `verify` and make it deny. Preserve the header names and the `sha256=` prefix; do not fix by widening the window. Allow side to pin: a signature made with a timestamp 4 minutes 59 seconds old must still verify `True`. Red-prove each clause separately: (i) drop `f"{timestamp}."` from the MAC input and assert a new test that mutates only the timestamp header and expects `False` reds; (ii) remove the skew check and assert a `timestamp = now - 3600` test reds; (iii) remove the required-argument change and assert the "verify a signature produced one second ago" test reds. Fail loudly when the check cannot run: a missing, non-numeric, or future-dated timestamp must return `False` explicitly (and a *future* timestamp beyond the tolerance must deny, not pass the "not older than" test vacuously). Boundary and tie: state the boundary as inclusive at exactly 300 seconds — a timestamp exactly 300s old verifies, 301s does not — and a timestamp exactly equal to `now` verifies.

### Critical: `GET /webhook-endpoints/{endpoint_id}/deliveries` has no organization filter
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: The query is scoped by the caller-supplied `endpoint_id` alone and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user of any tenant can enumerate any other tenant's deliveries — while `docs/webhooks.md` claims the endpoint "returns the most recent attempts for an endpoint belonging to your organization" (R49 overstated control).
What breaks in production: Cross-tenant IDOR: iterating `endpoint_id` from 1 upward discloses every customer's event types, delivery volumes, failure states and schedules — a reportable data-protection incident, not a bug.
Fix: Join and filter in the same query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return `404` (not `403`) when the join yields nothing, so the endpoint does not confirm existence of another tenant's id. Cross-cutting verification: the sibling `list_webhook_endpoints` added in the same hunk *does* filter on `org_id`, and `create_webhook_endpoint` sets `org_id` from the session — this is the one of three new routes that dropped the pattern (R3, security-relevant, Critical). Do not fix by moving the check into a gateway or middleware; authorize in the handler that touches the data. Allow side to pin (Remedy Floor 1): a test where the caller's own org owns `endpoint_id` must still receive its rows — a fix that always 404s satisfies every other clause. Red-prove each clause separately: (i) remove the `org_id` predicate and assert the cross-tenant test reds; (ii) change `404` to returning an empty list and assert the "unknown id 404s" test reds; (iii) remove the `join` and assert the test using an `endpoint_id` that exists but belongs to another org reds. Fail loudly when the check cannot run: if `user.org_id` is `None`, deny rather than falling through to an unfiltered query. Boundary and tie: an `endpoint_id` that exists but is owned by another org and an `endpoint_id` that does not exist must be indistinguishable to the caller — same status, same body.

### Critical: the signing secret is returned on every read of `GET /webhook-endpoints`
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict` unconditionally includes the live signing secret and is used by both `create_webhook_endpoint` (where returning it once is intended) and `list_webhook_endpoints` (where `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards"), so the documented one-time-disclosure control does not exist (RS4 Critical escalation: a live credential, not merely identifying data).
What breaks in production: The secret is emitted on every list call and therefore lands in browser history, proxy logs, HAR captures, support screenshots and any client-side cache, and is readable by any principal with read-only settings access — an attacker with a read token can forge webhooks into the customer's systems.
Fix: Remove `signing_secret` from `to_dict` and have `create_webhook_endpoint` build its 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable returned by `new_signing_secret()`, so the secret exists on exactly one code path. Cross-cutting verification: `WebhookDelivery.to_dict` correctly omits its sensitive field (`response_body`) — `WebhookEndpoint.to_dict` is the one of the two new serializers that leaks (R3). Preserve the create-time disclosure; that is what makes the feature usable, and deleting it is not a fix. Allow side to pin: a test asserting the 201 body *does* contain `signing_secret`. Red-prove each clause separately: (i) re-add the key to `to_dict` and assert a new `test_list_endpoints_never_returns_the_secret` reds; (ii) remove the key from the create response and assert the 201 test reds; (iii) add a `whsec_` regex assertion over the full serialized list response and mutate `to_dict` to leak a truncated prefix, asserting it still reds. Fail loudly when the check cannot run: store a hash or an encrypted secret so a future read path *cannot* re-derive it, rather than relying on every serializer remembering to omit it. Boundary and tie: the create response and the list response for the same row must differ in exactly this one key; if a rotation endpoint is added later it takes the create-path shape, not the list-path shape.

### Critical: server-side request forgery — non-HTTPS URLs accepted, no host restriction, redirects followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The validator accepts any scheme whose name merely begins with `http` (including plain `http:`), performs no check on the resolved host, and the client follows redirects, so a customer can register `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/` — or a public HTTPS URL that 302s to either — and our worker will issue that request from inside the VPC; `docs/webhooks.md` simultaneously claims "Only `https://` URLs are accepted" (R49).
What breaks in production: Any authenticated customer turns our delivery worker into an SSRF proxy against cloud metadata endpoints and internal services, with the response body captured into `webhook_deliveries.response_body` and into the `log.warning` on the retry path.
Fix: Validate at the schema level: make `EndpointIn.url` a Pydantic `HttpUrl` with a `max_length`, then reject in the handler unless `parsed.scheme == "https"` (exact equality, not `startswith`) and the host resolves entirely outside RFC1918/loopback/link-local/ULA ranges — resolve with `socket.getaddrinfo` and check every returned address, then set `follow_redirects=False` on the client and treat a 3xx as a permanent failure. Preserve the ability to deliver to legitimate public HTTPS endpoints on non-standard ports; do not fix by pinning an allowlist of known customer hosts, which removes the feature. Allow side to pin (Remedy Floor 1): `https://hooks.example.com/acme` on port 8443 must still be accepted and delivered — a validator that denies everything satisfies every other clause here. Red-prove each clause separately: (i) restore `startswith` and assert a `http://example.com` fixture reds; (ii) remove the address check and assert a `https://<host-resolving-to-127.0.0.1>` fixture reds; (iii) restore `follow_redirects=True` and assert a fixture whose 302 target is `http://169.254.169.254/` reds. Fail loudly when the check cannot run: DNS resolution failure at registration must reject with a distinct 422 detail, and re-resolution at delivery time must abort the request rather than proceeding unchecked — "could not evaluate the host" must not be spelled like "host is public". Boundary and tie: name the boundary explicitly for the addresses that sit at range edges (`10.255.255.255` denied, `11.0.0.0` allowed; `169.254.169.254` denied), and for a hostname with both a public A record and a private AAAA record, deny — any address in the set failing denies the whole name.

### Critical: `failed_permanent` is not in the migration's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: The DDL enumerates `'failed'` while the code writes `'failed_permanent'` and `app/webhooks/models.py:STATUSES` declares a third copy that agrees with the code and is never enforced anywhere — three sources of truth for one enum, one of them divergent (R3 propagation; R2 constant duplicated across places).
What breaks in production: Every delivery that exhausts its retries raises a `CheckViolation` on the terminal UPDATE, so `_finish` throws, the row is left at `in_flight`, and `_claim_batch` (which selects only `status == "pending"`) never re-claims it — permanently exhausted deliveries silently accumulate as stuck rows and the exception propagates out of `deliver` into `asyncio.gather`, killing the batch.
Fix: Make the DDL derive from one enum: change the CHECK to `IN ('pending', 'in_flight', 'delivered', 'failed_permanent')` and replace the bare string literals in `delivery.py` (`"in_flight"`, `"pending"`, `"delivered"`, `"failed_permanent"`) with references to a single exported enum in `app/webhooks/models.py`, replacing the currently-dead `STATUSES` tuple. Add a test that asserts the set of statuses the code can write is a subset of what the constraint admits, reading both from their single definition. Do not fix by dropping the CHECK constraint — the constraint is what makes an unknown status visible. Allow side to pin: a delivery reaching `delivered` and one reaching `failed_permanent` must both commit successfully against the real schema (an integration test against a real Postgres, since a mocked session cannot see a CHECK violation). Red-prove each clause separately: (i) revert the CHECK to `'failed'` and assert the failure-path integration test reds; (ii) add a bogus status to the code enum without the DDL and assert the subset test reds; (iii) remove the terminal `_finish` call and assert the "row leaves `in_flight`" assertion reds. Fail loudly when the check cannot run: if the integration DB is unavailable, the suite must error, not skip — a skipped constraint test reports green on exactly this defect. Boundary and tie: state that `in_flight` is the only non-terminal status and that every path out of `deliver`, including the exception path, must leave a terminal one.

### Critical: `UNIQUE INDEX` on `event_id` alone makes multi-endpoint fan-out impossible, and the failure is swallowed
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`; `app/events/dispatcher.py` — `except Exception as exc: log.warning(...)`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, but the unique index permits exactly one `webhook_deliveries` row per event across the entire table, so the second endpoint's insert raises `IntegrityError` — and because `session.add_all` flushes as one unit and the dispatcher catches bare `Exception` and only logs a warning, *all* deliveries for that event are lost with no error surfaced to any caller.
What breaks in production: Any org with two endpoints, or any two orgs whose events share the global `event_id` sequence, loses webhook deliveries entirely and silently; `docs/webhooks.md` promises "delivery is at-least-once", which the swallowed exception makes at-most-once.
Fix: Change the index to `UNIQUE (event_id, endpoint_id)` — that is the idempotency key the fan-out actually needs — and replace the dispatcher's blanket `except Exception: log.warning` with a durable outbox: insert the delivery rows in the *same* transaction as the `Event` row (currently two independent `session_scope` blocks), so either both commit or neither does, and let a genuine failure raise. Do not fix by removing the unique index; it is what makes redelivery idempotent, and dropping it re-opens duplicate delivery. Allow side to pin (Remedy Floor 1): an org with three active endpoints subscribed to the same event must produce exactly three rows and all three must commit. Red-prove each clause separately: (i) revert to the single-column unique index and assert the three-endpoint test reds with `IntegrityError`; (ii) re-run `enqueue_for_event` for an event already enqueued and assert a duplicate-suppression test reds when the composite index is dropped; (iii) force the delivery insert to raise and assert a test that the `Event` row was also rolled back reds when the two `session_scope` blocks are re-split. Fail loudly when the check cannot run: an enqueue failure must mark the event as un-enqueued (or fail the dispatch) rather than logging a warning — "webhooks not sent" must not be spelled the same as "no endpoints subscribed". Boundary and tie: zero matching endpoints must be a successful no-op returning `0`, and two endpoints of the same org registered at the same URL must each get their own row.

### Critical: `time.sleep()` inside `async def deliver` blocks the event loop for the whole retry sequence
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: A synchronous `time.sleep` is called inside a coroutine that `run_worker` fans out with `asyncio.gather`, so the four backoff waits (2+4+8+16 = 30 s per failing delivery) block the entire loop rather than yielding — and because `gather` cannot interleave blocked coroutines, a batch of 100 failing deliveries serializes into ~50 minutes of a wholly frozen process.
What breaks in production: The 60-second Redis lock TTL expires while the loop is blocked, a second worker acquires the lock and re-claims nothing (the rows are already `in_flight`) but the first worker's `finally` then deletes the *second* worker's lock, so lock mutual exclusion collapses; meanwhile every other coroutine in the process — including the HTTP server, if colocated — stops serving.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (`asyncio` is already imported at line 183), and additionally move `_finish` and `_claim_batch`'s blocking DB work off the loop with `asyncio.to_thread` (or an async session) since they are synchronous calls in coroutines for the same reason. Preserve the backoff schedule itself — shortening the delays is not a fix for blocking. Allow side to pin: a test asserting that two concurrent `deliver` calls, each retrying once with a 2-second backoff, complete in ~2 s wall clock rather than ~4 s. Red-prove each clause separately: (i) revert to `time.sleep` and assert the concurrency test reds; (ii) remove the `to_thread` wrapper around `_finish` and assert an event-loop-blocking assertion (`loop.slow_callback_duration` / a heartbeat coroutine that must tick every 100 ms) reds; (iii) shorten `BASE_DELAY_SECONDS` and assert `test_backoff_grows_exponentially` reds, proving the schedule is still pinned. Fail loudly when the check cannot run: bound the total in-process time a single `deliver` may hold a claimed row and abandon to the scheduler past it, rather than sleeping past the lock TTL silently. Boundary and tie: state that a delivery whose accumulated backoff would exceed the lock TTL must be rescheduled rather than slept through, and that two deliveries scheduled at the identical `next_attempt_at` must both be claimable in the same batch.

### Critical: retries are held in memory, so a restart strands every in-flight delivery forever
File: `app/webhooks/delivery.py` — `deliver`'s `while True` loop; `_claim_batch`'s `status == "pending"` filter
What is wrong: The retry loop increments a local `attempt` and never writes `attempts` or `next_attempt_at` back between attempts, while `_claim_batch` marks rows `in_flight` up front and only ever re-selects `pending` — so `next_attempt_at`, the column the whole schema is built around, is written exactly once at enqueue time and never used for scheduling.
What breaks in production: Any deploy, crash, OOM or scale-in during the 30-second retry window leaves rows permanently at `in_flight` with `attempts = 0`, invisible to every future poll, and the customer never learns the delivery was dropped; there is no reaper and no dead-letter path.
Fix: Make one attempt per claim: `deliver` performs a single `send_once`, then on non-2xx writes `status='pending'`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` (terminal `failed_permanent` only once `attempt >= MAX_ATTEMPTS`), and `_claim_batch`'s predicate becomes `status='pending' AND next_attempt_at <= now` with `FOR UPDATE SKIP LOCKED` so the claim and the status flip are one atomic statement. Add a reaper that returns rows stuck `in_flight` past a lease deadline back to `pending`. Preserve the exponential schedule and `MAX_ATTEMPTS`; do not fix by making the worker retry more aggressively in memory. Allow side to pin: a delivery that succeeds on its first attempt must still reach `delivered` in one claim with `attempts = 1`. Red-prove each clause separately: (i) drop the `next_attempt_at` write and assert a test that a failed delivery is re-claimed only after the backoff reds; (ii) drop the reaper and assert a test that an `in_flight` row older than the lease returns to `pending` reds; (iii) drop `SKIP LOCKED` and assert a two-worker concurrent-claim test that expects disjoint batches reds. Fail loudly when the check cannot run: a row whose `attempts` already exceeds `MAX_ATTEMPTS` but whose status is `pending` must be forced terminal and logged, not re-attempted indefinitely. Boundary and tie: `next_attempt_at` exactly equal to `now` is claimable (`<=`), and two rows with identical `next_attempt_at` are ordered by `id` so the `LIMIT 100` page boundary cannot skip either.

### Major: `_claim_batch` hands ORM instances across a closed session boundary
File: `app/webhooks/delivery.py` — `_claim_batch` returns `rows` after the `with session_scope()` block; `deliver`/`send_once` read `delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.url`, `endpoint.signing_secret`
What is wrong: The rows and the `endpoint` in `deliver` are read outside the sessions that produced them; under SQLAlchemy's default `expire_on_commit=True` every one of those attribute reads triggers a refresh on a closed session and raises `DetachedInstanceError`, and even where the session is configured otherwise the in-memory `delivery.attempts` is never refreshed after `_finish` writes it through a *different* session, so the object is stale by construction.
What breaks in production: The worker either raises on the first attribute access of every delivery (delivering nothing at all) or silently retries from a stale `attempts` baseline; the test suite cannot see either, because `FakeEndpoint`/`FakeDelivery` are plain always-attached classes rather than the real models (RT1 mock-reality divergence).
Fix: Have `_claim_batch` return plain immutable data — a `dataclass(frozen=True)` carrying `id`, `endpoint_id`, `attempts`, `payload`, `url`, `signing_secret`, joined and read inside the session — and have `deliver`/`send_once` accept that dataclass so no ORM identity crosses a session boundary. What answer would close the residual question: if `app/db.session_scope` is configured with `expire_on_commit=False` *and* does not close the session, the reads happen to work today — confirm that and the finding narrows to the staleness half, which stands regardless. Preserve the current signatures' shape so the existing `send_once` test remains meaningful. Allow side to pin: a test that constructs the dataclass from a real committed row inside a real session and asserts `send_once` still posts the signed payload. Red-prove each clause separately: (i) replace `FakeDelivery` with a real detached `WebhookDelivery` and assert the current code reds with `DetachedInstanceError`; (ii) mutate the dataclass to carry the ORM object instead and assert the same test reds; (iii) mutate `_finish` to write a different `attempts` and assert a test comparing the persisted value to the dataclass's reds. Fail loudly when the check cannot run: `deliver` must raise a named error when `session.get(WebhookEndpoint, ...)` returns `None` (a deleted endpoint), which it currently does not — it proceeds to `send_once` and dies on `None.signing_secret`. Boundary and tie: an endpoint deleted between claim and delivery must terminate the delivery as `failed_permanent`, not retry it.

### Major: the Redis lock is acquired non-atomically, expires separately, and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` then `set` is a check-then-act race two workers win simultaneously; `set` and `expire` are separate round trips, so a crash between them leaves a lock with no TTL; and the `finally` deletes `LOCK_KEY` by name without proving this worker still holds it, so after a TTL expiry one worker deletes another's lock.
What breaks in production: Two workers dispatch the same batch (duplicate deliveries the customer sees as duplicated events), or — after a crash in the one-instruction window — no worker ever dispatches again and the queue silently stops draining with no alert.
