### Critical: `list_deliveries` has no tenancy predicate — any authenticated user reads any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The query is scoped only by the caller-supplied `endpoint_id` and never joined back to `user.org_id`, so authorization is decided by a path integer the caller chooses.
What breaks in production: Any authenticated customer can enumerate `endpoint_id` and read another organization's delivery rows — `payload` is not in `to_dict()`, but `event_id`, `event_type`, `status`, `attempts` and `response_status` are, which discloses another tenant's billing event stream and its failure history.
Codebase awareness: the correct pattern is already in this same file twice — `list_api_keys` filters `ApiKey.org_id == user.org_id`, and the sibling added in this very diff, `list_webhook_endpoints`, filters `WebhookEndpoint.org_id == user.org_id`. This is R3 incomplete propagation: three peers, two scoped, one not.
Fix: Join the delivery query to its endpoint and filter on the owner — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) for an endpoint that exists but belongs to another org, so the response does not confirm the id exists. Pair the deny side with the allow side: the owning org's request for its own `endpoint_id` MUST still return its rows in `created_at desc` order with the same `to_dict()` shape, and that success case gets its own test; a fix that always returns `[]` satisfies the deny test alone. Red-prove each clause separately by execution: (i) delete the `org_id` predicate and observe the cross-tenant test go red on the returned row count, (ii) change the 404 to 403 and observe the existence-disclosure test go red on the status code, (iii) delete the join and observe the owner-success test go red — three mutations, three different assertions. Fail loudly when the check cannot run: if `user.org_id` is absent or the endpoint row is missing, raise 404 rather than falling through to an unfiltered query; "no endpoint resolved" must not be spelled the same as "no deliveries". Preserve what made the endpoint useful — the ordering, the `limit`, and the full `to_dict()` field set stay exactly as they are; do not "fix" this by removing fields from the response. Name the boundary and the tie: an endpoint whose `org_id` is exactly the caller's is INSIDE (returned); an endpoint id that does not exist and one owned by another org must be indistinguishable to the caller, both 404.

### Critical: `signing_secret` is returned on every endpoint read and the docs claim it cannot be read back
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret"`
What is wrong: `to_dict()` unconditionally serializes the signing secret, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` hands the HMAC key back on every call — directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: The secret is copied into every API-response log, browser cache, proxy access log and client-side store that touches the list endpoint, so a read-only credential scoped to "list my settings" becomes sufficient to forge signed events, and the documented "store it in your own secret manager" ceremony protects nothing.
Cross-cutting: the same class of leak appears a second time in `app/webhooks/delivery.py` — `send_once` does `log.info("POST %s headers=%s", endpoint.url, headers)`, writing the per-request `X-Acme-Signature` into application logs at INFO for every delivery attempt.
Fix: Remove `"signing_secret"` from `to_dict()` and return the secret only from `create_webhook_endpoint`, by constructing the 201 body explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable — the model must have no path that emits it. In `send_once`, log `endpoint.url` and the delivery id only, never the header dict. Pair deny with allow: the create response MUST still contain the secret exactly once (assert it is present and `startswith("whsec_")`), otherwise a customer can never obtain it and the whole feature is dead; that allow case is a separate test from the "list response has no `signing_secret` key" test. Red-prove each clause separately: (i) re-add the key to `to_dict()` and observe the list-response test red on key presence, (ii) drop the `signing_secret` merge in the create handler and observe the create test red on key absence, (iii) restore the header log line and observe a caplog-based assertion red on the signature substring. Fail loudly when the check cannot run: if `new_signing_secret()` returns falsy, raise before `session.add` rather than persisting an endpoint with an empty key — an unsigned endpoint must not be creatable. Preserve what made it useful: rotation must remain possible, so add or keep an explicit rotate route that returns a new secret once; do not fix the leak by making the secret unobtainable. Name the boundary and the tie: exactly one response (the 201 on create, and any explicit rotate) carries the secret; every other representation of the same row, including two endpoints created in the same request batch, carries none.

### Critical: signing secret is generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, which is the Mersenne Twister — a non-cryptographic, fully reconstructible PRNG — so consecutive secrets are not independent.
What breaks in production: An attacker who registers a few endpoints of their own recovers the generator state from the returned secrets and predicts the secrets issued to other organizations, letting them forge `X-Acme-Signature` headers that every customer's verifier accepts — the entire authenticity guarantee of the feature collapses.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, drop `random`/`string`/`_ALPHABET`), and rename `SECRET_BYTES` to mean what it says — 32 raw bytes, ~43 URL-safe characters — updating `test_new_signing_secret_has_prefix_and_length`, which currently pins `len(secret) == len(prefix) + SECRET_BYTES` and would otherwise lock in the character-count misnomer. Pair deny with allow: the allow case that must still succeed is that a secret produced by the new generator round-trips through `sign`/`verify` and still `startswith(SECRET_PREFIX)`; a fix that returns a constant satisfies "no `random` import" and nothing else, so add an assertion that 100 successive calls yield 100 distinct values. Red-prove each clause separately by execution: (i) revert to `random.choice` under a fixed `random.seed(0)` and observe the distinctness/unpredictability test red, (ii) return `SECRET_PREFIX` alone and observe the entropy-length test red, (iii) drop the prefix and observe the prefix test red. Fail loudly when the check cannot run: `secrets.token_urlsafe` raising must propagate out of the create handler as a 5xx — never fall back to `random`, and never return an endpoint whose secret generation failed. Preserve what made it useful: the `whsec_` prefix and the "secret is a printable ASCII string safe in a header/env var" property must survive the change, since customers store it verbatim. Name the boundary and the tie: `SECRET_BYTES = 32` is the minimum accepted entropy, so a secret of exactly 32 bytes passes and anything shorter must be rejected at generation time; two endpoints created in the same millisecond must still receive different secrets.

### Critical: `verify` compares the signature with `==` (non-constant-time)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The shipped reference verifier compares an attacker-supplied signature against the expected HMAC with Python's short-circuiting `==` instead of `hmac.compare_digest`, so comparison time leaks the length of the matching prefix (RS1).
What breaks in production: This function is the pattern every customer copies from and is presumably reachable wherever the product verifies inbound signed traffic; an attacker with repeated attempts recovers the expected digest byte by byte and then replays or forges requests without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, and change the signature to accept the timestamp so replay is checkable — `verify(secret, payload, signature, timestamp, max_age_seconds=300)` rejecting when `abs(time.time() - int(timestamp)) > max_age_seconds`, matching the five-minute window `docs/webhooks.md` already promises. Pair deny with allow: the allow case is that a freshly signed payload with its own timestamp still verifies True (the existing `test_verify_accepts_signature_produced_by_sign`, extended to pass the timestamp), so a fix that returns False unconditionally is caught. Red-prove each clause separately: (i) swap `compare_digest` back to `==` and observe a test that asserts `verify.__code__.co_names` contains `compare_digest` (or a dedicated lint) go red — a timing assertion is not reliably red-provable in CI, so the mutation must target the structural check, (ii) set the age check to `> 0` and observe the fresh-signature allow test red, (iii) delete the age check entirely and observe a replay test with a timestamp of `now - 600` red. Fail loudly when the check cannot run: a non-numeric or absent `timestamp`, or a `signature` that is not `sha256=<64 hex>`, must return False explicitly rather than raising an uncaught `ValueError` that a caller's broad `except` converts into a skipped check. Preserve what made it visible: keep `verify` exported and keep the "another secret is rejected" test — do not delete the negative case while adding the timing fix. Name the boundary and the tie: a timestamp exactly `max_age_seconds` old is ACCEPTED and one second older is rejected; two signatures of equal length that differ in the last byte must take the same time and both be rejected.

### Critical: the signature does not cover the timestamp and is computed over a re-serialized body the receiver never sees
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: `sign` computes `HMAC(secret, json.dumps(payload, sort_keys=True))` while the docs instruct customers to compute `HMAC(secret, "{timestamp}.{raw_request_body}")`, and the raw body on the wire is whatever `client.post(..., json=...)` emits (compact separators, insertion order) — so the signed bytes, the transmitted bytes, and the documented bytes are three different strings (R40: producer wire shape vs strict consumer).
What breaks in production: Every customer who implements the documented verification rejects 100% of our webhooks, and any customer who instead re-serializes with `sort_keys=True` to make it work is verifying a signature that does not bind the timestamp, so a captured request can be replayed forever with a refreshed `X-Acme-Timestamp` and the documented five-minute window enforces nothing.
Fix: Make the signed bytes and the transmitted bytes the same object: have `serialize` produce the canonical body once (`json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`), sign `f"{timestamp}.".encode() + body`, and post that byte string with `client.post(endpoint.url, content=body, headers=headers)` — never `json=`, which re-serializes. Update `docs/webhooks.md` in the same commit to state that the signed string is `"{timestamp}.{raw_request_body}"` where raw body means the bytes as received. Pair deny with allow: the allow case is an actual-producer-output-through-actual-consumer round-trip — capture `request.content` from the `MockTransport` handler in `test_send_once_posts_the_signed_payload`, feed those exact bytes plus the captured `X-Acme-Timestamp` into `verify`, and assert True; that test is the one R40 requires and the current suite has no equivalent, because `test_verify_accepts_signature_produced_by_sign` feeds `sign`'s own input back into `sign` and is an identity. Red-prove each clause separately by execution: (i) flip `content=body` back to `json=delivery.payload` and observe the round-trip test red on the digest, (ii) drop the `f"{timestamp}."` prefix from the signed bytes and observe a replay test — same body, timestamp advanced — red because it now verifies, (iii) remove `sort_keys` and observe a test signing `{"b":2,"a":1}` and `{"a":1,"b":2}` red on digest equality. Fail loudly when the check cannot run: a payload that is not JSON-serializable must raise before the POST, not be posted unsigned or with a signature over a repr. Preserve what made it useful: `Content-Type: application/json` must still be sent explicitly (switching off `json=` drops the automatic header), and the existing header/content-type assertion in the test must stay green. Name the boundary and the tie: the delimiter between timestamp and body is a single `.` and the timestamp is unpadded unix seconds, so a payload whose own first byte is `.` must still verify unambiguously; two events signed in the same second produce different digests because the body differs.

Fail loudly when the check cannot run: `_finish` currently does `row = session.get(...)` and then attributes without a None check — a missing row must raise a named error, not `AttributeError: 'NoneType'`, and a status not in `STATUSES` must be rejected in Python before it reaches the database. Preserve what made it visible: keep the CHECK constraint; do not resolve the mismatch by deleting it. Name the boundary and the tie: the set is exactly these four spellings, and `attempts == MAX_ATTEMPTS` is the boundary at which the row becomes `failed_permanent` (the code's `if attempt >= MAX_ATTEMPTS` after incrementing means the 5th attempt is the last one made, matching the documented "at most 5 times").

### Critical: `UNIQUE (event_id)` on `webhook_deliveries` allows only one endpoint per event
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness key is `event_id` alone, but `enqueue_for_event` builds one row per matching endpoint from a single `event_id`, so the fan-out the feature exists to provide violates the index by construction (R57: a key chosen for its business meaning without the uniqueness property the schema asserts).
What breaks in production: The moment an organization registers a second endpoint, `session.add_all(rows)` raises a unique violation, the whole enqueue transaction rolls back, and because `dispatch` swallows the exception with `log.warning` the event is delivered to *no* endpoint at all — silent total loss of webhooks for exactly the customers who use the feature most.
Fix: Replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is also the key that makes the documented "deduplicate on `event_id`" contract enforceable per endpoint. Pair deny with allow: the allow case that must still succeed is an event fanning out to two active endpoints of one org producing two rows; the deny case is a re-enqueue of the same `(endpoint_id, event_id)` being rejected rather than duplicating a delivery. Red-prove each clause separately: (i) revert to the single-column index and observe the two-endpoint fan-out test red on `IntegrityError`, (ii) drop the index entirely and observe the duplicate-enqueue test red because the second insert now succeeds, (iii) swap the column order — harmless for uniqueness but observable — and confirm the `status`-scan index test still governs the claim path so the two indexes are not conflated. Fail loudly when the check cannot run: `enqueue_for_event` must not silently absorb an `IntegrityError`; a conflict means "already enqueued" and should be an explicit `ON CONFLICT DO NOTHING` with the affected count returned, while any other integrity error propagates. Preserve what made it useful: keep an index that supports the dedup claim in the docs — do not fix the fan-out by deleting uniqueness altogether. Name the boundary and the tie: the tuple `(endpoint_id, event_id)` is the identity of a delivery, so the same event to two endpoints is two rows and the same event redelivered to one endpoint is one row; a retry of an existing row updates it rather than inserting.

### Critical: endpoint URL validation accepts plaintext and internal targets, and the client follows redirects
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `startswith("http")` admits `http://` (and any scheme with that prefix such as `httpx://`) despite `docs/webhooks.md` stating "Only `https://` URLs are accepted", and nothing rejects loopback, link-local, or RFC 1918 destinations, so the worker will POST to whatever host a customer names (RS3: the boundary check is a surface-form test standing in for a real destination policy; R49: the doc claims a control stronger than the implementation).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://127.0.0.1:6379/` and our worker turns into an SSRF proxy against our own infrastructure from inside the network perimeter, and because `follow_redirects=True` even a well-formed public HTTPS endpoint can 302 the request to an internal address after the registration-time check has passed.
Fix: Require `parsed.scheme == "https"` exactly, resolve the host at registration and reject when any resolved address is loopback/link-local/private/reserved (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), cap the URL at a fixed length, and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a failed attempt rather than followed. Because DNS can be re-pointed after registration, the destination check must also run at delivery time against the address actually connected to — not the hostname (R51: the check and the use must not be separated by a re-resolution the customer controls). Pair deny with allow: the allow case is that `https://hooks.example.com/acme` — the exact URL in the docs and in `FakeEndpoint` — still registers with 201 and still receives a POST; a fix that rejects every URL passes every deny test. Red-prove each clause separately by execution: (i) restore `startswith("http")` and observe the `http://…` rejection test red on the status code, (ii) remove the private-address check and observe a `https://localhost/…` test red, (iii) set `follow_redirects=True` and observe a MockTransport test that returns a 302 to an internal host red because the request was followed. Fail loudly when the check cannot run: DNS resolution failing or timing out must reject the registration with a 422 naming the reason — "could not resolve" must not be spelled the same as "resolved and is public". Preserve what made it useful: customers on non-standard ports and with path/query components must still register, so the check constrains the destination address, not the port or path. Name the boundary and the tie: `https` is the only accepted scheme, an address that is exactly the first host of a private range is rejected, and a hostname resolving to both a public and a private address is rejected (any private answer denies).

### Critical: `deliver` blocks the event loop with `time.sleep` while the dispatch lock ages out
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: A synchronous `time.sleep` inside an `async def` blocks the entire event loop, and this file already imports and correctly uses the non-blocking form five lines away in `run_worker` (`await asyncio.sleep(poll_interval)`) — the correct primitive is present and unused here (R1).
What breaks in production: One failing endpoint stalls the whole worker process for up to 2+4+8+16 = 30 s per delivery — `asyncio.gather` over a 100-row batch cannot make progress, and since the batch's Redis lock is set to expire after 60 s, a batch that sleeps past the TTL leaves the lock unheld while its rows are still `in_flight`, so a second worker claims and re-sends the same events.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)` and drop the now-unused `import time`; separately, make the retry non-blocking at the queue level by having `deliver` perform one attempt, then `_finish`-or-reschedule (`status="pending"`, `next_attempt_at = now + backoff_for(attempt)`, `attempts = attempt`) and return, so the retry is a later claim rather than a held loop. Pair deny with allow: the allow case is that a delivery which succeeds on its first attempt still returns immediately and is marked `delivered` with `attempts == 1` — a fix that reschedules everything unconditionally would satisfy "loop never blocks" while never delivering anything. Red-prove each clause separately by execution: (i) restore `time.sleep` and observe a test that runs two `deliver` coroutines under `asyncio.gather` with a monotonic-clock assertion go red because wall time is the sum rather than the max, (ii) remove the `next_attempt_at` advance and observe a test red because a rescheduled row is immediately re-claimable, (iii) remove the `attempts` write and observe the attempt-budget test red because the retry count never advances past 1. Fail loudly when the check cannot run: an exception other than `httpx.HTTPError` (the `CheckViolation` and `DetachedInstanceError` cases below are real) must be caught in the per-delivery task and recorded on the row, so one poisoned delivery cannot terminate `run_worker` via `gather`; log it at ERROR with the delivery id. Preserve what made it useful: the total attempt budget must stay at `MAX_ATTEMPTS` and the delays must stay 2/4/8/16 s, so `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` must remain green unchanged. Name the boundary and the tie: `attempt >= MAX_ATTEMPTS` is the terminal boundary — the 5th attempt is made and then the row becomes `failed_permanent`, never a 6th — and two deliveries whose `next_attempt_at` are equal are both claimable in the same batch.

### Critical: ORM rows are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`) and `deliver` (`endpoint` fetched in a session that closes before `send_once` reads it)
What is wrong: Both functions return or retain SQLAlchemy instances past the end of their `with session_scope()` block and then read attributes (`delivery.attempts`, `delivery.payload`, `endpoint.signing_secret`, `endpoint.url`) — with SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and the instance is detached, so the first read raises `DetachedInstanceError`.
What breaks in production: `deliver` raises on its very first line of real work, the exception escapes the `httpx.HTTPError`-only handler and `asyncio.gather`, and `run_worker` dies — no webhook is ever delivered, while the rows it claimed remain `in_flight` forever with no reset path.
Fix: Do not let ORM identities cross the session boundary — have `_claim_batch` return plain data (a list of frozen dataclasses or `(id, endpoint_id, event_id, payload, attempts)` tuples read inside the session), and have `deliver` receive the endpoint's `url` and `signing_secret` as values loaded in the same claim query via a join, so `send_once` touches no ORM instance. Pair deny with allow: the allow case is an end-to-end test that claims a real row from a real (in-memory or test-database) session and delivers it through `send_once` against `MockTransport`, asserting a 200 and a `delivered` row — this is the test the current suite lacks, because `FakeEndpoint`/`FakeDelivery` are plain classes with class attributes that can never expire, so the fixtures structurally cannot reproduce the bug (RT1: the double diverges from the real boundary in exactly the property under test). Red-prove each clause separately by execution: (i) change `_claim_batch` back to returning ORM rows and observe the end-to-end test red with `DetachedInstanceError`, (ii) drop the endpoint join and re-fetch by id in a closed session, observing the same test red on `endpoint.url`, (iii) delete the `in_flight` write inside the claim and observe a double-claim test red because two claims return the same row. Fail loudly when the check cannot run: a claimed delivery whose endpoint row is missing (endpoint deleted between enqueue and claim) must be marked terminal with a named reason, not skipped silently and not left `in_flight`. Preserve what made it useful: the batch claim must stay a single round trip bounded by `BATCH_SIZE`, and the `ORDER BY next_attempt_at` fairness must survive the refactor. Name the boundary and the tie: rows with `next_attempt_at` exactly equal to `now` are claimed (the filter is `<=`), and two rows with identical `next_attempt_at` must not straddle a batch boundary in a way that starves one — add `id` as a tie-break to the ordering so the order is total.

### Major: the Redis dispatch lock is not atomic and is released by name, not by ownership
File: `app/webhooks/delivery.py` — `_acquire_lock` and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get`-then-`set` is a check-then-act with an interleaving window, `set` and `expire` are two round trips so a crash between them leaves a lock with no TTL, and the release deletes the key by name without proving the deleter still holds it (R51: the decision is bound to a name, not to the object).
What breaks in production: Two workers starting within the same millisecond both see an empty key and both claim overlapping batches, so customers receive duplicate events; and once the 60 s TTL expires under a slow batch, worker A's `finally` deletes worker B's freshly acquired lock, making the mutual exclusion permanently ineffective rather than merely racy.
Fix: Acquire with a single atomic conditional write carrying a per-worker token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` — and release with a compare-and-delete (a Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`), renewing the TTL while a batch is still running. Pair deny with allow: the allow case is that a single worker acquires, runs a batch, releases, and can immediately re-acquire on the next loop iteration — a fix that never releases satisfies "no double acquisition" and deadlocks the queue. Red-prove each clause separately by execution: (i) revert to `get`+`set` and observe a test that drives two concurrent `_acquire_lock` calls red because both return True, (ii) replace the compare-and-delete with a plain `delete` and observe a test where worker A releases after B acquired red on B's token still being present, (iii) remove the TTL and observe a crash-simulation test red because the key never expires. Fail loudly when the check cannot run: if `redis_client` is unreachable, `_acquire_lock` must raise or return False and the worker must back off — a Redis error must never be swallowed into "lock acquired", because that is the fail-open direction. Preserve what made it useful: the poll-interval sleep on a failed acquisition must stay, so a losing worker still backs off rather than spinning. Name the boundary and the tie: the TTL must exceed the maximum time a batch can hold the lock (with per-attempt rescheduling above, that is one attempt, not 30 s), and two workers presenting the same token — which the CSPRNG makes negligible — must be treated as one holder.

### Major: `in_flight` is a non-terminal state with no recovery path
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; nothing ever moves it back
What is wrong: The only transitions out of `in_flight` are inside `deliver`'s success and exhaustion branches, so a worker crash, a redeploy, or any of the exceptions above wedges the row permanently (R38 clause 1: an async transition without a failure-exit or a bounded timeout).
What breaks in production: Every restart during a batch silently strands up to `BATCH_SIZE` deliveries — `_claim_batch` only ever selects `status == "pending"`, so those events are never retried and never surface as failures; the customer sees nothing at all rather than a failed delivery.
Fix: Add a claim lease — store `claimed_at` when transitioning to `in_flight`, and have `_claim_batch`'s predicate also admit rows where `status = 'in_flight' AND claimed_at < now() - lease_interval AND attempts < MAX_ATTEMPTS`, resetting them to `pending` as part of the same claim. Red-prove each clause separately by execution: (i) remove the stale-reclaim predicate and observe the crash-recovery test red because the row stays `in_flight`, (ii) set the lease to zero and observe the "fresh row is not stolen" test red, (iii) drop the `attempts < MAX_ATTEMPTS` guard and observe a test red because an exhausted row is resurrected forever. Fail loudly when the check cannot run: a row that has been reclaimed more times than `MAX_ATTEMPTS` must be moved to `failed_permanent` with a reason naming the lease expiry, so "stuck" is never silently equivalent to "pending". Preserve what made it useful: the `in_flight` state itself must stay — it is what stops two live workers from double-sending; do not fix this by deleting the state. Name the boundary and the tie: a row whose `claimed_at` is exactly `now - lease_interval` is reclaimable, and a row reclaimed at the same instant by two workers must be resolved by the same atomic claim write (`UPDATE ... WHERE status='in_flight' AND claimed_at < ...` returning the affected rows), so exactly one wins.
