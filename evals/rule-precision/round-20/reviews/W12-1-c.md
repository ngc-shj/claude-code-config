### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` taken from the path, with no join back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling handlers in the same diff (`list_api_keys`, `list_webhook_endpoints`) both filter on `org_id == user.org_id`.
What breaks in production: any authenticated user can enumerate integer endpoint ids and read every other tenant's delivery history — event ids, event types, statuses and attempt schedules — a cross-tenant data breach reachable with a single `GET`.
Fix: join the delivery query to its endpoint and filter on the caller's org, and fail closed when the endpoint does not resolve —
`session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookDelivery.endpoint_id == m.WebhookEndpoint.id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)`; when that join yields no endpoint row at all, raise `HTTPException(404)` rather than returning `[]`, so "endpoint of another org" and "endpoint does not exist" are indistinguishable to the caller. Pair the deny side with the allow side: keep a test asserting the OWNING org still receives its own deliveries in full (`len(rows) == 2`, both ids present) — a fix that always returns `[]` satisfies the deny test alone. Red-prove each clause separately by execution: (i) delete the `org_id` predicate and observe the foreign-org test go red on a non-empty list; (ii) delete the 404 branch and observe the "unknown endpoint" test go red on `200` instead of `404`; (iii) delete the owning-org assertion and observe the allow test go red. Fail loudly when the check cannot run: `user.org_id` being `None` must raise, never widen the filter to "match anything" — assert `user.org_id is not None` at the top of the handler and return 401 otherwise. Preserve what made the endpoint useful: the ordering by `created_at DESC` and the `limit` behaviour stay exactly as written; do not "fix" this by removing the route. Boundary and tie: an endpoint whose `org_id` is exactly the caller's org is INCLUDED; ties on `created_at` are addressed by the separate ordering finding below and the two fixes must land together, since adding the join does not by itself make the page deterministic.

### Critical: the signature is computed over bytes that are never sent, and omits the timestamp
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serialises with its own separators and insertion order, and the MAC input excludes the timestamp that `docs/webhooks.md` says is part of it (`"{timestamp}.{raw_request_body}"`).
What breaks in production: no customer following the published verification recipe can ever produce a matching digest, so every integration rejects every webhook and the signature also carries no replay protection — a captured request stays valid forever because the timestamp header is unauthenticated and can be rewritten by anyone.
Fix: make the signed bytes and the wire bytes literally the same object. In `send_once` build `body = serialize(delivery.payload).encode()` once, sign `f"{timestamp}.".encode() + body`, and send `client.post(endpoint.url, content=body, headers=headers)` — `content=`, not `json=`, so httpx cannot re-serialise. Change `sign(secret, payload)` to `sign(secret, body: bytes) -> tuple[str, str]` and `verify(secret, body, timestamp, signature)` so neither can be called with a shape that reserialises, and update `docs/webhooks.md` only if the recipe changes (it should not — the code moves to the doc). Pair deny with allow: one test must feed the ACTUAL captured request bytes from `httpx.MockTransport` back through `signing.verify` and assert `True` (an actual-producer-output-through-actual-consumer round trip, R40), and a second must assert a one-byte mutation of the captured body verifies `False`. Red-prove each clause separately: (i) revert `content=body` to `json=delivery.payload` and observe the round-trip test go red; (ii) drop the `f"{timestamp}."` prefix from the MAC input and observe a dedicated "signature binds the timestamp" test go red when the header timestamp is rewritten while the body is unchanged; (iii) flip one byte of the transmitted body and observe the tamper test go red if it were to pass. Fail loudly when the check cannot run: `verify` must raise, not return `False`, when `signature` lacks the `sha256=` prefix or the timestamp is not an integer — "malformed input" must not be spelled the same as "wrong signature", and callers must not read an exception path as a silent reject. Preserve what made it useful: `sort_keys=True` stays, because it is what makes the customer's own re-serialisation reproducible; do not fix this by dropping the timestamp requirement from the doc. Boundary and tie: state the accepted clock skew explicitly — a request whose timestamp is exactly 300 seconds old is ACCEPTED, 301 rejected; two requests sharing a timestamp are both valid and dedup is the receiver's job on `event_id`, which the doc already says.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister seeded from process state, not from `secrets`/`os.urandom`, and `SECRET_BYTES = 32` is used as a character count over a 62-symbol alphabet, so the name overstates the entropy the value carries.
What breaks in production: an attacker who observes a few secrets (their own endpoints, registered back to back) can reconstruct the generator state and predict every other tenant's signing secret, forging webhooks that every receiver accepts as authentic.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` imports so the weak primitive cannot be reached again from this module; rename `SECRET_BYTES` usage in `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length`, which currently asserts `len(secret) == len(PREFIX) + SECRET_BYTES` and will red on the base64 expansion — assert `>= len(PREFIX) + 32` instead of an exact length so the test pins a FLOOR on entropy rather than a formatting coincidence. Pair deny with allow: keep an assertion that a freshly minted secret is still accepted end-to-end by `sign`/`verify` (the allow case), so a fix that returns a constant or an empty string cannot pass. Red-prove each clause separately: (i) substitute `random.choice` back in and observe a `grep`-style unit assertion (`"random" not in inspect.getsource(signing)`) go red; (ii) shorten the token to 8 bytes and observe the entropy-floor assertion go red; (iii) return a fixed literal and observe a "two calls differ" assertion go red. Fail loudly when the check cannot run: if `secrets.token_urlsafe` raises (no OS entropy source), let it propagate — endpoint creation must 500, never fall back to `random`. Preserve what made it useful: the `whsec_` prefix stays, because `docs/webhooks.md` and the tests both key off it. Boundary and tie: a secret of exactly 32 URL-safe bytes is the minimum ACCEPTED; two endpoints minted in the same microsecond must not share a value, which is exactly what the old seeded PRNG could not guarantee.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`
What is wrong: the recomputed digest is compared to the caller-supplied one with `expected == signature`, a byte-wise short-circuiting comparison, in the same module that `docs/webhooks.md` instructs customers to use a constant-time comparison for (RS1).
What breaks in production: an attacker who can submit candidate signatures to any code path that calls `verify` recovers a valid digest byte by byte from response-time differences, forging authenticated requests.
Fix: `return hmac.compare_digest(expected, signature)` — `hmac` is already imported at the top of the file, so no new dependency is introduced. Guard the inputs first: `if not isinstance(signature, str)` raise `TypeError`, because `compare_digest` raises on mixed types and a bare `except` around it would reintroduce the leak. Pair deny with allow: `test_verify_accepts_signature_produced_by_sign` is the allow case and must stay green unchanged; add the deny case for a signature of the correct length differing only in the final character. Red-prove each clause separately: (i) revert to `==` and observe an assertion `"compare_digest" in inspect.getsource(signing.verify)` go red; (ii) change the deny fixture to differ in the FIRST character and confirm both orderings still return `False`, then invert the return value and observe the deny test go red; (iii) pass a non-`str` signature and observe the `TypeError` test go red if the guard is removed. Fail loudly when the check cannot run: a `None` or bytes signature raises rather than returning `False`, so a caller cannot read "malformed" as "attacker rejected". Preserve what made it useful: `verify` keeps returning a plain `bool` for the same argument order — the docstring contract does not change. Boundary and tie: two signatures of DIFFERENT length must return `False` without early exit — `compare_digest` handles this, a hand-rolled length check before it would reintroduce the oracle.

### Critical: the endpoint's signing secret is returned by the list route on every read
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: the secret is served on every settings page load, so it lands in browser caches, proxy logs, HAR files and support screenshots, and any read-only credential scoped to settings becomes sufficient to forge webhooks for that tenant.

Add a rotation route rather than a read-back route, since the secret is now unrecoverable by design. Pair deny with allow: assert the CREATE response still contains a `signing_secret` starting with `whsec_` (the allow case a blanket redaction would break), alongside asserting the LIST response has no `signing_secret` key at all. Red-prove each clause separately: (i) re-add the field to `to_dict()` and observe the list-route test go red on key presence; (ii) delete the explicit merge in the create handler and observe the create-route test go red; (iii) assert on key ABSENCE (`"signing_secret" not in body[0]`) not on an empty/None value, and confirm returning `{"signing_secret": None}` still reds it. Fail loudly when the check cannot run: `create_webhook_endpoint` must raise if `new_signing_secret()` returned a falsy value rather than persisting an endpoint that can never be verified against. Preserve what made it useful: the list route keeps returning `id`, `url`, `event_types`, `active`; the fix must not reduce it to ids. Boundary and tie: an endpoint created BEFORE this change already has its secret exposed in caches — treat those as compromised and rotate them in the same deploy.

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`
What is wrong: `CREATE UNIQUE INDEX ... ON webhook_deliveries (event_id)` permits only one delivery row per event, while `enqueue_for_event` builds one row per matching endpoint and calls `session.add_all(rows)`.
What breaks in production: the moment an org registers a second endpoint, every event insert raises `UniqueViolation`, the exception is swallowed by the `except Exception` in `dispatch`, and every webhook for that org silently stops — including the first endpoint's, because the whole batch rolls back.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the idempotency key the design actually needs (one attempt-record per endpoint per event) and which `docs/webhooks.md` already implies by telling receivers to deduplicate on `event_id` per endpoint. Pair deny with allow: assert two endpoints of the same org BOTH receive a row for one event (the allow case the current index breaks), and assert a second `enqueue_for_event` for the same `(endpoint_id, event_id)` is rejected (the deny case a plain non-unique index would lose). Red-prove each clause separately: (i) restore the single-column unique index and observe the two-endpoint test go red; (ii) drop uniqueness entirely and observe the re-enqueue test go red; (iii) make `enqueue_for_event` emit rows for INACTIVE endpoints and observe a third assertion on row count go red. Fail loudly when the check cannot run: `enqueue_for_event` must not swallow `IntegrityError` — see the swallowed-exception finding; a duplicate must be handled by an explicit `ON CONFLICT DO NOTHING` whose skipped-row count is logged, so "already enqueued" and "enqueue failed" are distinguishable in the logs. Preserve what made it useful: the intent (at-most-once enqueue per event) is preserved, only its key is corrected. Boundary and tie: an org with exactly ONE endpoint must behave identically before and after; the tie case is two endpoints of the same org registering the SAME url, which must still produce two rows, since they hold different secrets.

### Critical: `deliver` blocks the event loop with `time.sleep` inside an `async` function
File: `app/webhooks/delivery.py` — `deliver`
What is wrong: the retry loop calls `time.sleep(delay)` (synchronous) rather than `await asyncio.sleep(delay)`, inside a coroutine that `run_worker` schedules with `asyncio.gather` across a batch of up to `BATCH_SIZE = 100`.
What breaks in production: a single failing endpoint freezes the entire event loop for 2+4+8+16 = 30 seconds per delivery — serialised across the batch, so the whole process (including any co-hosted HTTP server) stalls for up to 50 minutes and the 60-second Redis lock expires while the worker still believes it holds it.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` and delete the `import time` if nothing else in the module uses it. Better still, stop retrying in-process: write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next `_claim_batch` pick it up — that is what the `next_attempt_at` column and the `pending` status exist for and neither is currently ever written after enqueue. Pair deny with allow: assert a SUCCESSFUL delivery still completes without any sleep at all (the allow case a blanket `await asyncio.sleep` before every attempt would regress), and assert that two failing deliveries in one batch complete in wall-clock time close to one delay, not two. Red-prove each clause separately: (i) restore `time.sleep` and observe the concurrency test (two deliveries, measured elapsed time under a patched clock) go red; (ii) remove the `next_attempt_at` write and observe a "row is rescheduled, not left in_flight" assertion go red; (iii) remove the `attempts` write and observe an "attempt count survives a process restart" assertion go red. Fail loudly when the check cannot run: if `_finish` cannot locate the row, raise — see the `_finish` finding. Preserve what made it useful: the backoff SCHEDULE is unchanged (2, 4, 8, 16 s) and `MAX_ATTEMPTS` still caps at 5; do not fix the stall by removing the delay. Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal boundary — attempt number 5 is the LAST one made and is not followed by a sleep; two rows with the same `next_attempt_at` are both claimable in the same batch, which the ordering finding below covers.

### Critical: the endpoint URL check accepts plaintext and non-`http` schemes, and the client follows redirects into the internal network
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: `parsed.scheme.startswith("http")` accepts `http`, and any scheme merely PREFIXED with it, while `docs/webhooks.md` states "Only `https://` URLs are accepted"; nothing restricts the host, and the shared `httpx.AsyncClient` is constructed with `follow_redirects=True`, so even a validated public host can 302 the signed request to `169.254.169.254` or an internal service.
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/` (or a public host that redirects there) and the worker POSTs authenticated, signed traffic from inside the VPC to internal endpoints, returning the response body into `webhook_deliveries.response_body` — a full read-SSRF with an exfiltration channel.
Fix: enforce the documented contract at the schema layer and re-enforce it at the request layer, because the two are separated by a redirect the validator cannot see (R49 — this is a fail-closed verification gate, not an enforceable boundary, and both halves are needed). At creation: type `EndpointIn.url` as `pydantic.HttpUrl` and reject `parsed.scheme != "https"` explicitly rather than with `startswith`; resolve the hostname and reject any address in a private, loopback, link-local, or reserved range via `ipaddress.ip_address(...).is_global is False`. At delivery: construct the client with `follow_redirects=False` and treat 3xx as a non-retryable failure recorded with its `Location`, so a redirect is visible in the delivery record instead of being silently chased. Pair deny with allow: assert a plain `https://hooks.example.com/acme` endpoint is still created and still delivered (the allow case an over-broad denylist breaks), alongside deny cases for `http://`, `httpx://`, `https://127.0.0.1/`, and a 302 to a private address. Red-prove each clause separately: (i) restore `startswith("http")` and observe the `httpx://` deny test go red; (ii) remove the address-range check and observe the `https://127.0.0.1/` deny test go red; (iii) restore `follow_redirects=True` and observe the redirect test go red on a delivery marked `delivered` instead of failed. Fail loudly when the check cannot run: DNS resolution failing at create time must return 422 naming the unresolvable host, never fall through to "assume public" — "could not check" must not be spelled like "checked and allowed". Preserve what made it useful: legitimate customer endpoints behind CDNs must still work, so the check is on the resolved address family, not on a hostname denylist. Boundary and tie: an address that is exactly `0.0.0.0` or an IPv4-mapped IPv6 form of a private address is REJECTED; a host resolving to both a global and a private address is rejected, not accepted on the first global answer (TOCTOU on re-resolution at request time is why `follow_redirects=False` is the second half).

### Critical: the worker operates on detached ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`, `send_once`
What is wrong: `_claim_batch` returns `rows` after the `with session_scope() as session:` block has exited, and `deliver` likewise reads `endpoint = session.get(...)` inside a `with` block and then uses `endpoint.url` and `endpoint.signing_secret` outside it; on the default `expire_on_commit=True` every attribute access on those instances re-triggers a load against a closed session.

Red-prove each clause separately: (i) return the ORM rows again and observe the post-session `payload` read go red with `DetachedInstanceError`; (ii) drop `signing_secret` from the snapshot and observe the signature assertion go red on `AttributeError`; (iii) mutate the snapshot in the test and observe a `FrozenInstanceError`, proving the immutability clause is real. Fail loudly when the check cannot run: if the join finds no endpoint for a claimed delivery, mark that delivery `failed_permanent` with a named detail rather than skipping it silently. Preserve what made it useful: `BATCH_SIZE`, the `pending`/`next_attempt_at` filter and the ordering are unchanged. Boundary and tie: a delivery whose endpoint was deactivated BETWEEN enqueue and claim must be resolved explicitly — decide and document whether it is dropped or delivered; today it is delivered, because `_claim_batch` never re-checks `active`.

### Major: the dispatch lock is not atomic and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`
What is wrong: `_acquire_lock` does a `get` then a separate `set`/`expire`, a check-then-act with no atomicity, and `run_worker`'s `finally` calls `redis_client.delete(LOCK_KEY)` without proving the caller still owns the lock whose TTL is 60 s while a single `deliver` can take far longer.
What breaks in production: two workers starting within the same millisecond both see an empty key and both claim the batch, so every webhook is delivered twice; and after the TTL expires, worker A's `finally` deletes the lock worker B is holding, permanently removing the mutual exclusion.
Fix: acquire with a single atomic command carrying a unique owner token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`) so only the owner can release; renew the TTL from within the batch loop while work is in flight. Pair deny with allow: assert a single worker DOES acquire and DOES release (the allow case a permanently-failing acquire would satisfy), alongside asserting the second concurrent acquirer is refused and that a non-owner release is a no-op leaving the key present. Red-prove each clause separately: (i) revert to `get`-then-`set` and observe the concurrent-acquire test go red under two interleaved coroutines; (ii) drop `nx=True` and observe the same; (iii) replace the compare-and-delete with a plain `delete` and observe the non-owner-release test go red on the key's absence. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must propagate and stop the loop, never return `True` — "cannot check the lock" must not be spelled like "lock is free". Preserve what made it useful: a worker that finishes cleanly still releases immediately, so a restart is not blocked for 60 s. Boundary and tie: a batch running exactly at the TTL boundary must renew BEFORE expiry, not at it; two workers presenting the same token cannot occur because the token is per-acquire, not per-process.

### Major: `in_flight` is a non-terminal state with no reset path, and `next_attempt_at` is never rewritten
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`, `_finish`
What is wrong: `_claim_batch` sets `row.status = "in_flight"` and only `_finish` leaves that state, on the two paths where `deliver` returns normally; a process kill, an `asyncio.CancelledError`, the `DetachedInstanceError` above, or the `CheckViolation` above all leave the row `in_flight` forever, and no code path ever writes `next_attempt_at` after enqueue (R38 clause 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: any worker restart permanently strands every delivery that was in flight — they are invisible to `_claim_batch`, which filters on `status == "pending"`, so the events are lost with no alert and no operator affordance to recover them.
Fix: add a claim deadline and a reaper. Give `webhook_deliveries` a `claimed_at TIMESTAMPTZ` column written by `_claim_batch`, and have the worker, before each batch, reset rows where `status = 'in_flight' AND claimed_at < now() - interval '10 minutes'` back to `pending` with `next_attempt_at = now()` and an incremented `attempts`; wrap each `deliver` in `asyncio.wait_for` with a bound above `REQUEST_TIMEOUT` so a hung attempt cannot outlive the reaper window. Pair deny with allow: assert a delivery claimed 1 second ago is NOT reclaimed (the allow case an unconditional reset would break, causing duplicate delivery of everything in flight), alongside asserting one claimed 11 minutes ago IS reclaimed. Red-prove each clause separately: (i) remove the `claimed_at` predicate and observe the "recently claimed row is untouched" test go red; (ii) remove the reaper and observe the "stranded row is recovered" test go red; (iii) remove the `attempts` increment and observe an "a permanently hanging endpoint eventually reaches failed_permanent" test go red by never terminating — bound that test with `MAX_ATTEMPTS` iterations so it reds rather than hangs. Fail loudly when the check cannot run: if the reaper query itself errors, the worker must log at ERROR and stop claiming, not proceed with a batch it may be duplicating. Preserve what made it useful: the `in_flight` state stays — it is what prevents two workers double-claiming within the window; do not fix this by deleting the state. Boundary and tie: a row whose `claimed_at` is EXACTLY the deadline is reclaimed (`<=`), and two rows sharing a `claimed_at` are both reclaimed in the same pass.

### Major: the webhook enqueue is outside the event transaction and its failure is swallowed
File: `app/events/dispatcher.py` — `dispatch`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: the `Event` row commits in its own `session_scope`, then `enqueue_for_event` opens a second, unrelated `session_scope`, and any failure of the second is caught by `except Exception` and downgraded to `log.warning` (R5/R9: two independently committing transactions with an atomicity invariant asserted across them).
What breaks in production: a database blip, the `UniqueViolation` above, or a transient error between the two commits leaves the event persisted with no delivery rows and nothing to reconcile against — the customer's webhook simply never arrives, and the only trace is a warning line nobody alerts on.
Fix: pass the caller's session into `enqueue_for_event(session, ...)` and create the `Event` row and its `WebhookDelivery` rows in the SAME `session_scope`, so either both commit or neither does; remove the blanket `except Exception` so a failure rolls the event back and the caller sees it.
