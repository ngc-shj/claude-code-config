### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, filter `WebhookDelivery.endpoint_id == endpoint_id`
What is wrong: The query filters on the path-supplied `endpoint_id` alone and never joins `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate integer ids and read another tenant's delivery rows.
What breaks in production: A customer walks `endpoint_id=1..N` and reads every other customer's `event_type`, delivery status, and response codes — a cross-tenant data breach through an endpoint the docs advertise as "belonging to your organization".
Fix: Join the parent and filter on it — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403, which confirms existence) when the endpoint id resolves to no row under that org. Preserve the existing behaviour that a caller's OWN endpoint still returns its rows in `created_at desc` order: pin both sides — an allow test where the endpoint's `org_id` equals `user.org_id` and the same rows come back, and a deny test asserting 404 AND that the response body contains no delivery ids. Red-prove each clause by executing it separately: (i) delete the `org_id` filter and watch the deny test go red; (ii) delete the `endpoint_id` filter and watch the allow test return foreign rows; (iii) change 404 to 403 and watch the enumeration-response assertion go red. If `user.org_id` is absent or `None`, deny rather than filtering on `None` (which matches nothing silently in some dialects but is indistinguishable from "no rows") — raise a named error so "could not determine tenant" is not spelled the same as "no deliveries". Boundary: an endpoint whose `org_id` is exactly `user.org_id` is allowed; an endpoint id that exists but belongs to another org and an endpoint id that does not exist must be indistinguishable in status, body, and timing.

### Critical: the signing secret is returned on every endpoint read
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`
What is wrong: `to_dict()` includes `signing_secret`, and it is the serializer used by `GET /v1/settings/webhook-endpoints`, so the secret is handed back on every list call — directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: Any actor with a read-scoped API key or a captured session can retrieve the HMAC key and forge signed events, which is the entire security property webhook signing exists to provide.
Fix: Remove `signing_secret` from `to_dict()` and add a separate `to_dict_with_secret()` used only by the 201 response of `create_webhook_endpoint`, so exactly one code path can emit it. Pin both sides: an allow test asserting the create response body DOES contain `signing_secret` (the feature must keep working — do not fix this by deleting the secret from the create response too), and a deny test asserting `"signing_secret" not in body` for every element of the list response. Red-prove separately: (i) re-add the key to `to_dict()` and watch the list test go red; (ii) switch the create handler back to `to_dict()` and watch the create test go red. Because this is a read-back removal, add a rotation route (`POST /webhook-endpoints/{id}/rotate-secret`) in the same change or the secret becomes unrecoverable for customers who lose it; if the rotate path cannot be built now, the docs must say the secret is unrecoverable. Boundary: the secret is emitted exactly once, at creation; a second read of the same endpoint by the same caller returns no secret, and two endpoints created in the same request path must not share one.

### Critical: signing secret generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: `random.choice` draws from the Mersenne Twister, a non-cryptographic PRNG whose internal state is recoverable from a few hundred observed outputs, and the constant is misnamed `SECRET_BYTES = 32` when it actually produces 32 alphanumeric characters (~190 bits from a 62-symbol alphabet, not 256 bits).
What breaks in production: An attacker who registers a handful of endpoints of their own observes enough generator output to reconstruct the MT state and predict the signing secret issued to other tenants, forging events that every receiver accepts as authentic.
Fix: Replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX`, import `secrets`, delete the `random`/`string`/`_ALPHABET` imports outright rather than leaving them unreferenced, and rename the constant to make the unit explicit. Preserve what made the feature usable: the `whsec_` prefix must stay (receivers and support tooling key off it) and the value must stay URL-safe ASCII. Pin both sides: an allow test asserting the returned value still starts with `SECRET_PREFIX` and is accepted by `sign`/`verify` round-trip, and a distinctness test asserting 1000 generated secrets yield 1000 unique values with minimum length ≥ 43 chars. Red-prove separately: (i) revert to `random.choice` under a seeded `random.seed(0)` and assert two processes produce identical secrets — that test must be red against the fixed code and green against the old; (ii) drop the prefix and watch the prefix assertion go red; (iii) shorten `SECRET_BYTES` to 8 and watch the length-floor assertion go red. Update `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length`, which currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` — that equality is false for `token_urlsafe` and must become a `>=` floor, stated as a floor and not as an exact length. Boundary: a secret of exactly the floor length is accepted; two secrets that collide is the failure condition the distinctness test names.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The MAC comparison uses Python's short-circuiting `str.__eq__` instead of `hmac.compare_digest`, leaking the length of the matching prefix through timing (RS1).
What breaks in production: This function is the reference verifier we publish to customers and use in tests, so every consumer that copies it can have a valid signature recovered byte-by-byte by an attacker who can time the endpoint.
Fix: `return hmac.compare_digest(expected, signature)`, guarding the non-`str`/`None` case first so a caller passing a missing header gets a `False` rather than a `TypeError` from `compare_digest`. Preserve the current true-case behaviour: an allow test asserting a signature produced by `sign` still verifies. Red-prove separately: (i) revert to `==` and assert via `ast`/source inspection or a lint rule that the constant-time helper is present — a timing assertion is not reliable in CI, so the gate must be a structural one that names itself; (ii) pass `None` as `signature` and assert `False` is returned rather than an exception escaping; (iii) flip one hex character and assert `False`. If `hmac.compare_digest` is unavailable in the runtime, raise at import rather than silently degrading to `==` — "cannot compare safely" must not be spelled the same as "did not match". Boundary: strings of equal length differing in the last character, and strings of unequal length, must both return `False` through the same path.

### Critical: the signature does not cover the timestamp and is computed over bytes the receiver never sees
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, whose httpx encoding uses insertion order and compact separators — so the signed bytes and the wire bytes differ — and the returned `timestamp` is never fed into the HMAC at all, contradicting `docs/webhooks.md` which specifies `HMAC-SHA256("{timestamp}.{raw_request_body}")` (R40, R49).
What breaks in production: Every customer who implements verification from our published documentation computes a different digest and rejects 100% of our deliveries, and any customer who instead matches our implementation gets no replay protection because the unauthenticated timestamp header can be rewritten to any value.
Fix: Make the signed bytes and the sent bytes the same object: serialize once with `body = serialize(payload).encode()`, MAC `f"{timestamp}.".encode() + body`, and send `client.post(url, content=body, headers={..., "Content-Type": "application/json"})` instead of `json=`. Add a round-trip test that feeds the ACTUAL bytes captured by `httpx.MockTransport` through the ACTUAL `verify` — not two independently constructed strings — and change `verify` to take the raw body and the timestamp so it can recompute what was really sent. Preserve the documented contract rather than editing the doc down to the code: `docs/webhooks.md` states timestamp-in-MAC and a five-minute replay window, and that window is only enforceable once the timestamp is authenticated, so `verify` must also reject a timestamp whose skew exceeds `MAX_SKEW_SECONDS = 300`. Pin both sides: allow — a request signed 299 seconds ago with unmodified body verifies; deny — the same request with the timestamp header rewritten to `now` fails, and the same request replayed at 301 seconds fails. Red-prove separately: (i) drop the `f"{timestamp}."` prefix from the MAC input and watch the timestamp-rewrite test go red; (ii) switch `send_once` back to `json=` and watch the round-trip test go red on the reordered-keys payload `{"b": 2, "a": 1}`; (iii) remove the skew check and watch the 301-second test go red. A malformed or non-numeric timestamp header must be a named rejection, not a fall-through to "no skew known". Boundary: skew of exactly 300 seconds is accepted, exactly 301 is rejected; two requests sharing the same second and the same body produce the same signature, which is why the receiver still needs the event-id dedupe key below.

### Critical: unvalidated destination URL plus `follow_redirects=True` is a signed-request SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker`, `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check is `parsed.scheme.startswith("http") and parsed.netloc`, which accepts `http://` (the docs say HTTPS only), accepts any scheme beginning with the four letters `http`, and imposes no restriction on the resolved host, while the worker follows redirects so even an initially-legitimate host can bounce the request anywhere (RS3).
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/` — or a public host that 302s there — and our worker fetches cloud instance credentials and stores the response body in `webhook_deliveries.response_body`, which that tenant then reads back through the deliveries endpoint.
Fix: Validate at the schema level with `url: HttpUrl` on `EndpointIn`, then add an explicit `assert_public_https(url)` helper that (a) requires `scheme == "https"` by exact equality, not `startswith`, (b) resolves the host with `socket.getaddrinfo` and rejects every address in a private, loopback, link-local, multicast, or reserved range via `ipaddress.ip_address(...).is_global`, and (c) rejects userinfo and non-standard ports outside an allowlist. Set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with a message naming the redirect target, so a customer whose endpoint moved gets a diagnosable error instead of a silent internal fetch. Because DNS can be re-pointed between registration and delivery, run the same `assert_public_https` check in `send_once` against the address actually connected to, not only at registration (R51-shaped check-to-use gap). Preserve the feature: an allow test registering `https://hooks.example.com/acme` (resolving to a global address via a stubbed resolver) must still create the endpoint and still deliver. Red-prove separately: (i) register `http://hooks.example.com` and assert 422; (ii) register `https://localhost/x` and assert 422; (iii) stub a handler returning 302 to `http://169.254.169.254/` and assert the delivery is marked failed with no second request issued; (iv) revert `scheme == "https"` to `startswith("http")` and watch (i) go red. If DNS resolution fails or the resolver is unavailable, reject with a named "could not verify destination" error rather than allowing the registration through. Boundary: an address that is exactly the first host of a private block (`10.0.0.0`) is rejected, a global address adjacent to it is allowed; a hostname resolving to both a global and a private address is rejected.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: The application writes `"failed_permanent"` (also the value in `models.py` `STATUSES`) but the table only permits `"failed"`, so the terminal-failure write violates the constraint (R3, R40).
What breaks in production: Every delivery that exhausts its retries raises `IntegrityError` inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and the worker's `asyncio.gather` propagates the exception and kills the batch.
Fix: Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and import the tuple from a single place — `models.STATUSES` is already the declared source of truth, so the migration must be generated from or asserted against it rather than restating the literals a third time (R2). Add a test that asserts `set(STATUSES)` equals the set parsed out of the migration's CHECK clause, so the two cannot drift again. Pin both sides: allow — a row inserted with each of the four values in `STATUSES` succeeds; deny — a row inserted with `'bogus'` is rejected by the constraint (do not fix this by dropping the CHECK, which is what makes the mismatch visible). Red-prove separately: (i) remove `failed_permanent` from the migration and watch the parity test go red; (ii) add a fifth value to `STATUSES` without touching the migration and watch the same test go red; (iii) insert `'bogus'` and watch the deny test go red if the CHECK is dropped. If the migration file cannot be parsed for the CHECK clause, the test must fail loudly rather than skip. Boundary: exactly the four values pass; a value differing only in case (`'Pending'`) must be rejected, since the constraint is case-sensitive and the code never emits it.

### Critical: the unique index on `event_id` alone prevents fan-out to more than one endpoint
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness is on `event_id` alone, but `enqueue_for_event` creates one row per matching endpoint for the same event, so the second row of any fan-out violates the index.
What breaks in production: An organization with two subscribed endpoints gets an `IntegrityError` on `session.add_all`, the whole enqueue fails, and because the dispatcher swallows that exception the event is dropped for BOTH endpoints with only a warning line.
Fix: Replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the key that actually expresses the intended idempotency ("one delivery of one event per endpoint"), and change `enqueue_for_event` to `INSERT ... ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a redelivered event is a no-op rather than an exception. Preserve the idempotency the original index was reaching for — do not fix this by deleting the unique index, which would let a retried dispatch double-deliver. Pin both sides: allow — one event with two active endpoints creates exactly two rows; deny — calling `enqueue_for_event` twice with the same `event_id` still leaves exactly two rows. Red-prove separately: (i) revert to the single-column index and watch the two-endpoint test go red; (ii) drop the unique index entirely and watch the double-enqueue test count four rows; (iii) remove the `ON CONFLICT` and watch the double-enqueue test raise instead of no-op. Boundary: two endpoints of the SAME org and one endpoint receiving two DIFFERENT events both stay legal; the tie is the same `(endpoint_id, event_id)` pair arriving twice, which must resolve to the first row and leave its `status`/`attempts` untouched.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async def` but sleeps with the blocking `time.sleep`, so the backoff halts the entire event loop rather than yielding.
What breaks in production: With `asyncio.gather` over a 100-row batch, one endpoint's 16-second backoff freezes all 100 concurrent deliveries, the redis lock heartbeat, and any other coroutine on that loop — a single slow customer stalls the whole webhook pipeline.
Fix: Use `await asyncio.sleep(delay)`; `asyncio` is already imported in this module so nothing new is needed. Preserve the retry pacing the sleep exists for — do not fix this by removing the delay. Pin both sides: allow — a delivery that fails once then succeeds still waits `BASE_DELAY_SECONDS**1` before the second attempt (assert against a monkeypatched `asyncio.sleep` recording its argument); deny — a test running two `deliver` coroutines concurrently under `asyncio.gather`, one of which backs off, asserts the other completes before the backoff elapses. Red-prove separately: (i) restore `time.sleep` and watch the concurrency test go red; (ii) delete the sleep call entirely and watch the recorded-argument test go red. Boundary: the delay for `attempt` exactly equal to `MAX_ATTEMPTS - 1` is the last one taken; at `attempt == MAX_ATTEMPTS` no sleep occurs at all because `_finish` returns first.

### Critical: ORM rows are used after their session closes, in two places
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (`endpoint` fetched inside a `with` block and read outside it)
What is wrong: Both functions return or retain SQLAlchemy instances past the end of their `session_scope`, and with the default `expire_on_commit=True` every subsequent attribute read (`delivery.id`, `delivery.attempts`, `delivery.payload`, `endpoint.url`, `endpoint.signing_secret`) triggers a refresh against a closed session.
What breaks in production: `run_worker` raises `DetachedInstanceError` on the first batch it claims, so the worker never delivers anything and crashes on its first iteration — the feature is dead on arrival, and the `in_flight` status the claim already wrote is left stranded.
Fix: Convert both sites to plain data before the session exits — have `_claim_batch` return a list of frozen dataclasses (`id`, `endpoint_id`, `payload`, `attempts`) built inside the `with` block, and have `deliver` read `endpoint.url` and `endpoint.signing_secret` into locals inside its `with` block. This is a cross-cutting instance of one pattern: the same escape occurs at `create_webhook_endpoint` (`endpoint.to_dict()` is called inside the block, so that site is correct) and at `list_webhook_endpoints` / `list_deliveries` (`to_dict()` inside the block, also correct) — so only the two delivery sites need the change, and the working sites show the shape to copy. Preserve the claim's write: `_claim_batch` must still set `status = "in_flight"` and commit it, which is what makes the batch exclusive. Pin both sides: allow — `_claim_batch` against a seeded DB returns objects whose `payload` is readable after the function returns; deny — a test asserting the returned objects are not SQLAlchemy instances (`not isinstance(row, m.WebhookDelivery)`) so the regression cannot come back. Red-prove separately: (i) return the ORM rows and watch the readable-after-return test raise `DetachedInstanceError`; (ii) return the dataclasses but drop the `status = "in_flight"` write and watch a second `_claim_batch` call re-return the same ids. If the session is already closed when a field is read, that must surface as the named error rather than a silent `None`. Boundary: a batch of exactly `BATCH_SIZE` rows and a batch of zero rows both return cleanly.

### Major: the dispatch lock is a non-atomic check-then-set and is deleted unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `GET` followed by a separate `SET` is a TOCTOU window in which two workers both observe an empty key and both proceed, the `SET` and `EXPIRE` are not atomic so a crash between them leaves a permanent lock, and the `finally` deletes the key without checking the holder token (R5).
What breaks in production: Two workers claim overlapping batches and one worker's `finally` deletes the other's lock mid-batch, producing duplicate POSTs to customer endpoints — visible to customers as double-charged or double-processed events.
Fix: Replace the three calls with a single atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` is unique per acquisition, and release with a Lua compare-and-delete (`if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) end`) so a worker can only delete its own lock. Set `LOCK_TTL_SECONDS` above the worst-case batch duration — with `MAX_ATTEMPTS=5`, `REQUEST_TIMEOUT=30` and backoffs of 2+4+8+16, a single delivery can run 180 seconds, so the current 60 is already too short and must be raised (or the lock renewed on a heartbeat). Preserve single-worker liveness: the TTL must still exist so a crashed worker's lock expires. Pin both sides: allow — a worker that acquires and releases can immediately re-acquire; deny — a second `_acquire_lock` while the first holds returns `False`, and the second worker's release does NOT remove the first's key. Red-prove separately: (i) revert to `get`-then-`set` and run two acquisitions concurrently, asserting exactly one wins; (ii) remove `nx=True` and watch the same test see two winners; (iii) drop the token comparison from the release and watch the foreign-release test go red; (iv) drop `ex=` and assert the key has a TTL. If redis is unreachable, `_acquire_lock` must raise a named error, not return `True` — an unavailable lock service must stop the worker, not open it. Boundary: a lock whose TTL expires exactly as the holder finishes must not have the holder's release delete a successor's lock, which is exactly what the token comparison decides.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` sets `status = "in_flight"`; only `_finish` leaves it
What is wrong: A row transitions to `in_flight` at claim time and returns to a terminal state only if `deliver` reaches `_finish`, but the worker can crash, be redeployed, be cancelled by a sibling's exception in `asyncio.gather` (no `return_exceptions=True`), or hit any non-`httpx.HTTPError` exception — and `_claim_batch` only ever selects `status == "pending"`, so nothing reclaims a stranded row (R38 mode 1).
What breaks in production: Every deploy during a delivery batch permanently strands up to 100 customer events in `in_flight` with no operator affordance to recover them, and the failure is silent because no terminal state and no alert is ever produced.
Fix: Make the claim recoverable rather than one-way: add a `claimed_at TIMESTAMPTZ` column, have `_claim_batch` select `status = 'pending' OR (status = 'in_flight' AND claimed_at < now() - interval '10 minutes')`, and wrap `deliver` in a `try/except Exception` that routes any unexpected error back to `status = 'pending'` with `next_attempt_at` advanced by `backoff_for(attempt)` and `attempts` persisted. Pass `return_exceptions=True` to the `asyncio.gather` so one delivery's failure does not cancel its siblings mid-flight. Preserve the exclusivity the `in_flight` marker provides — do not fix this by removing the status, which would let two workers deliver the same row. Pin both sides: allow — a normally-completing delivery still reaches `delivered` and is never re-claimed; deny — a row left `in_flight` with `claimed_at` older than the reclaim window IS returned by the next `_claim_batch`, and a row `in_flight` for one second is NOT. Red-prove separately: (i) remove the reclaim clause and watch the stale-row test go red; (ii) remove the `except Exception` reset and watch a `deliver` raising `ValueError` leave the row `in_flight`; (iii) drop `return_exceptions=True` and watch a sibling delivery report cancelled. Boundary: `claimed_at` exactly at the reclaim horizon is not reclaimed, one second past it is; the reclaim window must exceed `REQUEST_TIMEOUT * MAX_ATTEMPTS` plus total backoff or a live delivery gets duplicated.

### Major: the retry loop retries 4xx, which the docs declare permanent
File: `app/webhooks/delivery.py` — `deliver`; `docs/webhooks.md` — "Retries"
What is wrong: The loop treats every non-2xx identically and retries up to `MAX_ATTEMPTS`, while the published contract states "5xx, timeouts and connection errors are retried; a 4xx is permanent and we stop immediately" (R29, R49).
What breaks in production: A customer endpoint returning 401 or 404 receives five POSTs of every event instead of one, amplifying our traffic five-fold against an endpoint that has already told us to stop, and the documented behaviour customers built their alerting around never happens.
Fix: Branch on the class before deciding: `if 200 <= code < 300: delivered`; `elif 400 <= code < 500 and code not in RETRYABLE_4XX: _finish(..., "failed_permanent", ...); return`; else retry. `RETRYABLE_4XX = {408, 429}` should be named explicitly since request-timeout and rate-limit are the two 4xx codes that genuinely mean "try again", and `429` should honour `Retry-After` when present. Update `docs/webhooks.md` in the same change to name those two exceptions rather than saying "a 4xx is permanent" flatly — the doc claim must be calibrated to what the code does, in both directions. Pin both sides: allow — a 500 is still retried to `MAX_ATTEMPTS`, and a 429 is still retried; deny — a 404 produces exactly one POST and a `failed_permanent` row. Red-prove separately: (i) remove the 4xx branch and watch the 404 test count five POSTs; (ii) add 404 to `RETRYABLE_4XX` and watch the same test go red; (iii) remove 429 from the set and watch the rate-limit test stop at one attempt. Boundary: status exactly 400 is permanent, exactly 399 and exactly 500 are retried; 299 is success and 300 is not (and, with redirects disabled per the SSRF finding, 3xx must be an explicitly named permanent failure rather than falling into the retry branch by default).

### Major: documented jitter does not exist, and the test pins the un-jittered values
File: `app/webhooks/delivery.py` — `backoff_for`; `tests/webhooks/test_delivery.py` — `test_backoff_grows_exponentially`
What is wrong: `backoff_for` returns exactly `2**attempt` seconds with no randomization, while `docs/webhooks.md` says "backoff is exponential with jitter", and the parametrized test asserts the exact deterministic values — so the test actively locks in the divergence (R29).
What breaks in production: A customer endpoint that goes down takes every in-flight delivery with it and all of them retry at the same instants, so the endpoint is hit by a synchronized thundering herd at t+2, t+4, t+8, t+16 exactly when it is trying to recover.
Fix: Return `timedelta(seconds=BASE_DELAY_SECONDS**attempt * (1 + random.random() * JITTER_FRACTION))` with `JITTER_FRACTION = 0.25` and an injected `rng` parameter defaulting to the module rng so the test can seed it — jitter is a scheduling concern, so `random` is correct here even though it is wrong for the secret above, and that distinction should be stated in a comment at each site. Rewrite the test to assert a range rather than an equality: `base <= delay <= base * 1.25` for each attempt. Preserve the growth property the current test pins — do not fix this by deleting the exponential assertion. Pin both sides: allow — with a seeded rng the delay is deterministic and reproducible; deny — 100 calls at the same `attempt` produce more than one distinct value. Red-prove separately: (i) remove the jitter multiplier and watch the distinctness test go red; (ii) change the exponent base and watch the range test go red; (iii) set `JITTER_FRACTION = 5.0` and watch the upper-bound assertion go red. Boundary: `attempt = 1` yields a delay in `[2, 2.5]`, `attempt = MAX_ATTEMPTS - 1 = 4` yields `[16, 20]`; `attempt = 0` (never reached in `deliver`, which pre-increments) must still return a positive delay rather than 1 second silently.

### Major: `enqueue_for_event` reimplements the module's own timezone helper, with a naive value
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`
What is wrong: `app/webhooks/models.py` already defines `_now()` returning `datetime.now(timezone.utc)` and uses it for every other timestamp default, but the enqueue path calls the deprecated naive `datetime.utcnow()` into a column declared `DateTime(timezone=True)` (R1).
What breaks in production: The naive value is written without an offset and interpreted in the session timezone, so on any non-UTC database session every delivery's `next_attempt_at` is shifted by the offset — deliveries either fire hours late or are claimed by `_claim_batch` (which compares against an aware `datetime.now(timezone.utc)`) hours early.
Fix: Call the existing `m._now()`; it is already imported transitively via `from app.webhooks import models as m`, so no new dependency is introduced. Enumerate the behavioural difference before adopting it: `_now()` returns an aware datetime where `utcnow()` returned naive, which IS a behaviour change at this call site and is exactly the change wanted — the row will now carry an explicit `+00:00` where it previously carried none, and any already-written rows from a prior deploy remain naive and must be backfilled by the migration or they compare wrong forever. Delete the `datetime` import from `delivery.py` if `_finish` and `_claim_batch` are converted too — they use `datetime.now(timezone.utc)` inline, which is the same reimplementation in two more places (cross-cutting: three sites, one helper). Pin both sides: allow — a row enqueued now is claimed by `_claim_batch` on the next poll; deny — a test running under `TZ=America/New_York` (or a session with `SET TIME ZONE`) asserts the stored value round-trips to the same instant. Red-prove separately: (i) restore `utcnow()` and watch the non-UTC test go red; (ii) drop the `tzinfo` from `_now()` and watch the same test go red under UTC as well. Boundary: a row whose `next_attempt_at` is exactly `now` must be claimed (the filter is `<=`), and two rows sharing the same instant must both be claimed — which they will, since the tie is not used as a cursor here.

### Major: the migration's timestamp columns are `TIMESTAMP` while the models declare `timezone=True`
File: `migrations/0042_webhook_delivery.sql` — `created_at`, `next_attempt_at`, `updated_at` on both tables
What is wrong: Every timestamp column is `TIMESTAMP` (without time zone) but `app/webhooks/models.py` declares `DateTime(timezone=True)`, so SQLAlchemy sends and expects offsets the column cannot store (R40).
What breaks in production: Postgres silently drops the offset on write and returns naive values on read, so `WebhookDelivery.to_dict()`'s `next_attempt_at.isoformat()` emits a timestamp with no zone to API consumers, and the `next_attempt_at <= now` comparison in `_claim_batch` is evaluated against a value whose zone is whatever the server session says.
Fix: Change all six columns to `TIMESTAMPTZ NOT NULL DEFAULT now()`. Preserve the `NOT NULL` and the defaults — the fix is the type only. Add a test that reflects the created tables and asserts each timestamp column's type matches the corresponding SQLAlchemy column's `timezone` flag, so the pair cannot drift again. Pin both sides: allow — a value written through the ORM reads back equal to what was written, including offset; deny — the reflection test fails when either side is changed alone. Red-prove separately: (i) revert one column to `TIMESTAMP` and watch the reflection test name that column; (ii) flip one model column to `timezone=False` and watch the same test name it from the other direction. If reflection cannot connect to a database, the test must error rather than skip silently. Boundary: a value at exactly `1970-01-01T00:00:00+00:00` and one at a DST transition instant must both round-trip identically.

### Major: `webhooks_enabled` is added by the migration and read by nothing
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: The column defaults to `FALSE` for every existing organization and no code path in the diff reads it — `create_webhook_endpoint` and `enqueue_for_event` both proceed regardless (R41).
What breaks in production: Either the flag is meant to gate the feature, in which case the gate does not exist and webhooks ship enabled for every tenant including those not entitled to them, or it is not, in which case an operator toggling it to `TRUE` sees no effect and believes the feature is on when its actual state is governed by something else entirely.
Fix: Wire it or drop it, and say which. If it is the entitlement gate: check it in `create_webhook_endpoint` (raise 403 with a message naming the entitlement when false) and join it in `enqueue_for_event`'s endpoint query (`.join(Organization).filter(Organization.webhooks_enabled.is_(True))`), so a disabled org neither registers nor receives. Pin both sides: allow — an org with `webhooks_enabled = TRUE` registers an endpoint and receives a delivery row; deny — an org with `FALSE` gets 403 on registration AND, separately, an existing endpoint under a since-disabled org produces zero delivery rows (assert the row count, not only the status — asserting the 403 alone leaves the enqueue path unverified). Red-prove separately: (i) remove the route check and watch the 403 test go red; (ii) remove the query join and watch the zero-rows test go red while the 403 test stays green — this is the pair that proves the two checks are independent. If the join cannot resolve the organization row, deny rather than defaulting to enabled. Boundary: the column's `DEFAULT FALSE` means the deploy turns webhooks OFF for every existing org at the moment this ships, so the migration needs an explicit backfill statement for orgs already using the feature, or the rollout silently disables them.

### Major: the dispatcher's hardcoded event allowlist contradicts the per-endpoint subscription and the docs
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`, `if envelope.type in WEBHOOK_EVENT_TYPES`
What is wrong: The dispatcher gates enqueue on a three-element module constant while `enqueue_for_event` independently filters on `endpoint.event_types` and `docs/webhooks.md` promises that "an empty `event_types` subscribes the endpoint to every event type we emit" (R2, R12, R29).
What breaks in production: A customer who registers an endpoint with an empty `event_types` list, following the documented contract, receives only three of our event types and silently misses every other one — and adding a fourth webhook-eligible event type requires editing a constant in an unrelated module that nothing tests.
Fix: Delete `WEBHOOK_EVENT_TYPES` and its branch, and call `enqueue_for_event` for every dispatched event — the per-endpoint `event_types` filter already in `enqueue_for_event` is the authoritative subscription check and reimplementing a coarser one upstream is what created the divergence. If a global allowlist is genuinely required (to keep high-volume internal events out of the webhook table), it must live beside the subscription logic in `app/webhooks/` and be validated at registration time so `POST /webhook-endpoints` rejects an unsupported `event_type` at the boundary rather than accepting it and never delivering. Preserve the log line's usefulness — the `webhooks=%s` field should become the count of rows enqueued, which is the fact an operator actually needs. Pin both sides: allow — an endpoint with `event_types = ["invoice.paid"]` receives `invoice.paid` and not `subscription.updated`; deny — an endpoint with `event_types = []` receives an event type absent from the old constant. Red-prove separately: (i) restore the constant gate and watch the empty-subscription test go red; (ii) remove the `endpoint.event_types` filter and watch the selective-subscription test receive both events. Boundary: an `event_types` list containing exactly the dispatched type matches; an empty list matches everything, and `None` (which the JSONB column permits at the Python level despite `nullable=False`, since the default is applied only on insert) must be treated as empty rather than raising in the `in` test.

### Major: a failed enqueue is swallowed and the event is lost with no retry or dead letter
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning(...)`
What is wrong: The enqueue happens after the event's `session_scope` has already committed and any failure — the `IntegrityError` from the unique-index defect above, a DB blip, a connection exhaustion — is caught and reduced to a warning with no retry, no dead-letter row, and no metric.
What breaks in production: The event is durably persisted but its webhook deliveries never exist and never will, so the customer permanently misses a paid invoice notification and nothing in the system records that a delivery was owed.
Fix: Enqueue inside the same transaction as the `Event` insert so the delivery rows and the event commit atomically (they are both rows in the same database, so no cross-system coordination is needed), and let the exception propagate to the dispatcher's caller rather than being swallowed. If enqueue must stay outside the transaction, then the failure must be recorded durably — an outbox row the worker retries — never a log line. Preserve the property the `try` was protecting: a webhook failure must not break in-process subscribers, so the enqueue must run AFTER the `for subscriber` loop (it already does) and the transactional version must not roll back the event on a webhook-only failure unless that is the stated intent. Pin both sides: allow — a normal dispatch returns `event_id` and creates delivery rows; deny — a dispatch whose enqueue raises leaves NO orphaned `Event` row with zero deliveries (assert both the raised exception and the absence of the committed event, not the exception alone). Red-prove separately: (i) restore the bare `except Exception` and watch the orphan-row assertion go red; (ii) move the enqueue outside the transaction and watch the same assertion go red; (iii) make a subscriber raise and assert the event still commits, proving the two failure domains stayed separate. Boundary: an event whose org has exactly zero active endpoints must commit successfully with zero delivery rows — that is not a failure and must not be routed to the error path.

### Major: no rate limiting on any of the three new routes
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: All three routes are added without a rate limiter, and `create_webhook_endpoint` in particular performs a DNS-resolving, secret-generating, row-inserting operation with no cap on endpoints per organization (RS2).
What breaks in production: A single tenant scripts endpoint creation and both exhausts the `webhook_endpoints` table and multiplies every subsequent event's fan-out by the number of endpoints they registered, turning one event into thousands of outbound POSTs from our infrastructure.

Add a hard `MAX_ENDPOINTS_PER_ORG` check in `create_webhook_endpoint` returning 409 when exceeded. Preserve normal usage: pin the allow side with a test making `MAX_ENDPOINTS_PER_ORG` creations that all succeed, alongside the deny test asserting the next one is 409 AND that no row was inserted (asserting the status alone leaves the mutation unverified). Red-prove separately: (i) remove the count check and watch the row-count assertion go red while the status assertion also goes red; (ii) raise the cap by one and watch the allow test still pass and the deny test go red, proving the boundary is the cap and not an unrelated failure; (iii) remove the router dependency and watch the rate-limit test go red. ### Major: signature and full response bodies are written to logs and to the database
File: `app/webhooks/delivery.py` — `send_once` `log.info("POST %s headers=%s", endpoint.url, headers)`; `_finish` storing `response.text` into `response_body`
What is wrong: The log line prints the complete header dict including `X-Acme-Signature`, and `_finish` persists the customer's entire, unbounded response body into a column read back through the deliveries API.
What breaks in production: The signature is the credential that authenticates a request, so anyone with log access can replay a captured event body against the customer's endpoint verbatim, and an endpoint returning a large or sensitive body (an error page containing internal identifiers, or megabytes of HTML) bloats the table and is served back through `to_dict()`'s sibling fields on any future serializer change.
Fix: Log the URL, the delivery id, and the timestamp header only — never the signature or the header dict — and truncate the stored body with an explicit `response.text[:RESPONSE_BODY_LIMIT]` where `RESPONSE_BODY_LIMIT = 2048`, appending a visible `"…[truncated]"` marker so a reader can tell truncation from a short body. Preserve the diagnostic value that made the log and the column useful: the status code, the URL, and the first 2 KB of the body must still be recorded, so this is not fixed by removing the logging. Pin both sides: allow — a delivery against a handler returning a 40-byte body stores those 40 bytes with no marker; deny — a delivery against a handler returning 10 KB stores exactly `RESPONSE_BODY_LIMIT` characters plus the marker, and a log-capture assertion finds no substring `"sha256="` in any emitted record. Red-prove separately: (i) restore the header dict in the log call and watch the log-capture assertion go red; (ii) remove the slice and watch the length assertion go red; (iii) remove the truncation marker and watch the short-vs-truncated distinguishability assertion go red. Boundary: a body of exactly `RESPONSE_BODY_LIMIT` characters is stored untruncated and unmarked; one character longer is truncated and marked.

### Major: `test_send_once_posts_the_signed_payload` cannot see the signature defect it appears to cover
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, and `FakeEndpoint` / `FakeDelivery`
What is wrong: The test asserts only that the signature header `startswith("sha256=")` and never recomputes the MAC over `captured["body"]`, so the serialize-vs-wire mismatch and the missing timestamp are both invisible; and the fake objects are plain classes rather than the ORM types, so the detached-instance defect in `deliver` is equally invisible (RT1 clauses c and d, RT5).
What breaks in production: The suite reports the signing path as covered while every customer-facing verification fails, which is exactly the "green test, broken control" case that let the header contract ship wrong.

Bind `FakeEndpoint`/`FakeDelivery` to the real `m.WebhookEndpoint` / `m.WebhookDelivery` constructors so a field added to the model cannot silently be missing from the fixture. Preserve the transport-level assertions already present (status, content-type) — they are correct. Pin both sides: allow — the recomputed digest matches for the correct secret; deny — the same recomputation with a different secret does not match, and the deliberately-unsorted payload proves the body is byte-identical to what was signed. ### Major: receivers cannot deduplicate on `event_id` as the docs instruct
File: `app/webhooks/delivery.py` — `send_once`; `docs/webhooks.md` — "delivery is at-least-once, so deduplicate on `event_id`"
What is wrong: The POST body is `delivery.payload` — the raw event payload — and no header or envelope field carries `delivery.event_id`, so the documented dedupe key is not present in anything the receiver sees (R41, R49).
What breaks in production: A customer following our documentation has no key to deduplicate on, so every retry after a timeout that actually succeeded is processed as a second event — the exact double-processing the at-least-once caveat was written to prevent.
Fix: Add an `X-Acme-Event-Id` header set from `delivery.event_id` and include it in the signed bytes (it must be inside the MAC or an attacker can rewrite it to force reprocessing), and document the header in `docs/webhooks.md` beside the dedupe instruction. Preserve the payload shape customers already parse — do not fix this by wrapping the payload in a new envelope, which is a breaking change for anyone integrating during the rollout. Pin both sides: allow — two deliveries of different events carry different values and both verify; deny — a delivery whose `X-Acme-Event-Id` header is rewritten in transit fails signature verification. Red-prove separately: (i) remove the header and watch the presence assertion go red; (ii) remove the header from the MAC input and watch the rewrite test go red while the presence assertion stays green — that pair is what proves the header is authenticated and not merely present. Boundary: two retries of the SAME delivery must carry the identical event id (that is the point), while two endpoints receiving the same event also carry it — so the receiver's dedupe key is `event_id` alone only within one endpoint, which the docs must state.
