### Critical: the list endpoint returns every endpoint's signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, used by `GET /v1/settings/webhook-endpoints` in `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and that same serializer backs the list route, so the HMAC key is returned on every read — directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: any principal who can reach the settings API with a read-scoped token (or anything that logs/caches API responses — browser history, an APM payload capture, a support screenshot) obtains the key that authenticates all outbound webhooks, so a third party can forge events that customers' handlers will accept as ours.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held plaintext, so exactly one response carries it; store only a hash or an envelope-encrypted value if the secret must survive (`sign()` needs the plaintext, so encryption-at-rest — not hashing — is the option that preserves signing). **Allow side that must still succeed**: the 201 response body from `create_webhook_endpoint` still contains a `signing_secret` starting with `whsec_`, and `send_once` still signs with the same value — pin both, or the fix degrades into "webhooks can no longer be signed". **Red-proof, one mutation per clause**: (i) re-add the key to `to_dict()` and observe the list-route test asserting `"signing_secret" not in body[0]` go red; (ii) change the create route to return `endpoint.to_dict()` instead of the merged dict and observe the create-route test asserting the plaintext is present go red — two mutations, two different assertions, both executed rather than reasoned about. **Fail loudly**: if the stored value cannot be decrypted at delivery time, `send_once` must raise and `_finish` must record `failed_permanent` with a named reason; "could not read the key" must not be spelled the same as "signature computed". **Preserve**: the list route keeps returning `id`, `url`, `event_types`, `active` — do not fix this by deleting the route. **Boundary and tie**: the boundary is "the create response, and nothing else"; a re-created endpoint with the same URL is a distinct row with a distinct secret, and the old row's secret is never re-emitted.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once` (`sign(endpoint.signing_secret, delivery.payload)` then `client.post(..., json=delivery.payload, ...)`)
What is wrong: `signing.sign` computes the MAC over `json.dumps(payload, sort_keys=True)` with default separators, while httpx re-serializes the same dict itself for the `json=` argument (no `sort_keys`, different separators), so the signature is over a byte string the receiver never sees — and `signing.serialize()`, the helper the change itself introduces for exactly this, is not used to produce the wire body (R1: the encoder is reimplemented at the call site by delegating to httpx).
What breaks in production: every receiver following `docs/webhooks.md` computes the HMAC over the raw body it received and gets a mismatch, so 100% of deliveries are rejected by any correctly implemented consumer while our side records them as `delivered` (2xx) — a silent total-path failure of the feature's only security control.
Fix: serialize once and send the bytes you signed — `body = signing.serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, body)`, `client.post(endpoint.url, content=body, headers=headers)` — and change `sign`/`verify` to take the already-serialized bytes so no caller can re-encode between signing and sending. **Allow side that must still succeed**: a receiver that recomputes `hmac_sha256(secret, raw_body)` over the exact `request.content` captured by the existing `MockTransport` handler must still validate, and `Content-Type: application/json` must still be set explicitly (httpx no longer sets it for you once `json=` is dropped) — assert `json.loads(captured["body"])["type"] == "invoice.paid"` still passes. **Red-proof, one mutation per clause**: (i) reintroduce `json=delivery.payload` alongside the signature and observe the new round-trip assertion (`hmac` over `captured["body"]` equals the sent header) go red; (ii) drop the explicit `Content-Type` header and observe the existing content-type assertion go red. **Fail loudly**: a payload that is not JSON-serializable must raise before the POST and be recorded as `failed_permanent` with the encoder error, never be sent unsigned. **Preserve**: sorted-key serialization is fine to keep — the defect is the second encoder, not the ordering. **Boundary and tie**: the boundary is the byte string; two payloads that differ only in key insertion order must produce identical bytes and therefore identical signatures.

### Critical: the timestamp header is not covered by the MAC, so replay is unbounded
File: `app/webhooks/signing.py` — `sign` / `verify`
What is wrong: `sign` returns a timestamp but computes `hmac.new(secret, serialize(payload))` over the payload alone, so `X-Acme-Timestamp` is unauthenticated and can be rewritten freely, while `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` — the documented anti-replay window described as "what stops a captured request from being replayed" does not exist in the implementation (R49: a claim stronger than the control).
What breaks in production: an attacker who captures one delivery can replay it forever with a fresh timestamp — the signature stays valid — so a customer following our documented five-minute window is protected against nothing, and a replayed `invoice.paid` can be re-processed indefinitely.
Fix: make the signed string `f"{timestamp}.{body}"` in `sign`, have `verify` take the timestamp as an argument and reject when `abs(now - timestamp) > 300`, and keep the two headers as the only inputs a receiver needs. **Allow side that must still succeed**: a signature produced now must verify now (`verify(SECRET, ts, body, sig) is True` for a freshly signed payload) and a timestamp 299 seconds old must still verify — without this the fix is indistinguishable from one that rejects everything. **Red-proof, one mutation per clause**: (i) revert the signed string to `body` alone and observe the test asserting that altering only the timestamp header invalidates the signature go red; (ii) remove the 300-second bound and observe the test feeding a 10-minute-old timestamp go red. **Fail loudly**: a non-numeric or absent timestamp must return False from `verify` and be reported as a rejection reason, not be coerced to 0 or skipped. **Preserve**: `verify` must remain usable by our own tests as the receiver-side reference — do not fix this by deleting `verify`. **Boundary and tie**: 300 seconds is inclusive-reject at 301 and accept at exactly 300; a timestamp exactly equal to `now` and one exactly at the bound both accept, and clock skew in the future direction must use the same symmetric bound rather than being unbounded.

### Critical: signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the MAC comparison uses Python's `==` on `str`, which short-circuits on the first differing byte, instead of `hmac.compare_digest` (RS1).
What breaks in production: `verify` is the reference implementation we publish the semantics of and the one our own tests use; anywhere it is used to authenticate an inbound value it leaks the correct digest byte-by-byte through response timing, letting an attacker forge a valid signature without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, comparing the full `sha256=`-prefixed strings so the prefix mismatch does not exit early either. **Allow side that must still succeed**: `test_verify_accepts_signature_produced_by_sign` must remain green — `compare_digest` on equal strings returns True. **Red-proof**: revert to `==` and observe a timing test (N=10000 comparisons against a digest differing at byte 1 versus byte 63, asserting the two medians are within tolerance) go red; run it, do not reason it — one mutation, one assertion. **Fail loudly**: `compare_digest` raises `TypeError` on non-ASCII `str`; catch it and return False with a logged rejection reason rather than letting it escape as a 500. **Preserve**: the function's boolean contract and its use in the two existing tests are unchanged. **Boundary and tie**: strings of unequal length must still compare in constant time relative to the expected digest — `compare_digest` handles this, a manual loop over `zip()` does not.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from process state and is explicitly not suitable for security purposes; 32 outputs of `random.choice` are enough for an observer with any other sample from the same generator to reconstruct its state.
What breaks in production: an attacker who can obtain any secret issued by the same process (their own endpoint's, from the create response) can predict the secrets issued to other organizations around the same time and forge signed events to those customers' handlers.
Fix: `import secrets` and return `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, making `SECRET_BYTES` mean bytes of entropy rather than characters; delete the `random`, `string` imports and `_ALPHABET` outright rather than leaving them as an unused fallback (R1 clause d). **Allow side that must still succeed**: the secret must still start with `whsec_` and must still be accepted end-to-end by `sign`/`verify` — keep an assertion that a freshly generated secret signs and verifies. **Red-proof, one mutation per clause**: (i) revert to `random.choice` after `random.seed(0)` and observe a test asserting two secrets generated from a re-seeded `random` differ go red; (ii) drop the prefix and observe the existing `startswith(SECRET_PREFIX)` assertion go red. **Fail loudly**: if `secrets` cannot produce entropy the exception must propagate and fail endpoint creation — never fall back to `random`. **Preserve**: the existing length assertion must be updated, not deleted; `len(token_urlsafe(32))` is 43, so assert `>= 32` entropy characters rather than removing the check (deleting the assertion is not fixing it). **Boundary and tie**: the boundary is entropy, not length — two endpoints created in the same millisecond in the same process must receive independent secrets, and a test should assert that over a batch of 1000.

### Critical: the deliveries route is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query filters on the path-supplied `endpoint_id` only, with no join back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling routes added in the same file (`create_webhook_endpoint`, `list_webhook_endpoints`) both scope by `user.org_id` — the tenancy pattern was applied to two of three new routes (R3, security-relevant).

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible

What is wrong: `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so the second row of any fan-out violates the unique index; the index should be on `(endpoint_id, event_id)` if it is meant to enforce the documented "deduplicate on `event_id`" idempotency.

### Critical: outbound URLs are attacker-chosen with no scheme, host, or redirect restriction
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`, and `app/webhooks/delivery.py:run_worker`, `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http`, `httpx`, `httpfoo` and any other prefix match, no host restriction blocks loopback/link-local/RFC1918 targets, and the delivery client follows redirects, so a validated public URL can bounce to an internal one (RS3 Critical — externally supplied input reaching a request-issuing sink; and `docs/webhooks.md` claims "Only `https://` URLs are accepted", which the code does not implement, R49).
What breaks in production: a customer registers `https://evil.test/x` that 302s to `http://169.254.169.254/latest/meta-data/iam/security-credentials/`, our worker follows it, and `_finish` stores the response body in `response_body` — which that customer then reads back through `GET /webhook-endpoints/{id}/deliveries`, turning the webhook feature into a credential exfiltration channel.
Fix: validate with an allow-list — require `parsed.scheme == "https"` exactly, require a non-empty `hostname`, cap `len(body.url)` at 2048 via a pydantic `HttpUrl`/`constr` field so it is rejected at the schema rather than in the handler, resolve the hostname and reject when any resolved address is private/loopback/link-local/multicast/reserved (`ipaddress.ip_address(a).is_global` is False), set `follow_redirects=False` on the delivery client, and re-run the same address check against the connected peer at request time (a DNS-rebind between registration and delivery re-resolves the *name*, so the registration-time check does not bind the socket the request uses — R51). **Allow side that must still succeed**: `https://hooks.example.com/acme` (the fixture already in `tests/webhooks/test_delivery.py`) must still register and still be delivered to, and a 301 response must now be recorded as a non-2xx failure rather than followed — pin both. **Red-proof, one mutation per clause**: (i) revert to `startswith("http")` and observe the test registering `httpfoo://x` go red; (ii) remove the private-address check and observe the test registering a hostname resolving to `127.0.0.1` go red; (iii) set `follow_redirects=True` and observe the test asserting a 302 is recorded as a failure go red — three clauses, three separate executed mutations. **Fail loudly**: DNS resolution failure at registration must reject with 422 naming the reason, not be treated as "no private addresses found". **Preserve**: legitimate public HTTPS endpoints on non-standard ports must still be allowed; do not fix this with a static domain allow-list that kills the feature. **Boundary and tie**: the boundary is `is_global` per resolved address — a hostname resolving to both a public and a private address is rejected (all addresses must pass), and IPv6-mapped IPv4 forms are normalized before the check.

### Critical: `time.sleep` inside an async coroutine blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` for a batch of up to `BATCH_SIZE` (100), but the retry backoff uses the blocking `time.sleep` instead of `await asyncio.sleep`, so one failing delivery freezes every other coroutine in the batch and the client's in-flight HTTP reads.
What breaks in production: a single unreachable endpoint stalls the loop for 2+4+8+16 = 30 seconds while the other 99 deliveries' sockets sit unread and time out spuriously against `REQUEST_TIMEOUT`; with several failures per batch the stall exceeds the 60-second lock TTL, a second worker claims the same work, and endpoints receive duplicate deliveries.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` and remove the now-unused `time` import; separately, do not retry in-process at all — persist `attempts` and `next_attempt_at = now + backoff_for(attempt)`, set the row back to `pending`, and return, so the backoff is carried by the scheduler rather than by a held coroutine (see the retry-persistence finding below). **Allow side that must still succeed**: a delivery that succeeds on the first attempt must still complete without any sleep at all, and the total wall time of a 100-row batch of successes must stay under one second — assert it, or a fix that serializes everything satisfies every other clause. **Red-proof, one mutation per clause**: (i) revert to `time.sleep` and observe a test that gathers two `deliver` calls (one failing, one succeeding) and asserts the successful one completes within its own timeout go red; (ii) remove the `next_attempt_at` write and observe the scheduling test go red. **Fail loudly**: if `asyncio.sleep` is interrupted by cancellation, the row must be returned to `pending` in a `finally`, not left `in_flight`. **Preserve**: the documented 2/4/8/16-second schedule and the `MAX_ATTEMPTS == 5` cap stay exactly as `tests/webhooks/test_delivery.py` pins them. **Boundary and tie**: the boundary is `attempt >= MAX_ATTEMPTS` — attempt 5 is the last one made and is recorded `failed_permanent`; two deliveries whose `next_attempt_at` is the same instant are both eligible and must both be claimed.

### Major: `in_flight` is a non-terminal state with no path back to `pending`
File: `app/webhooks/delivery.py` — `_claim_batch` (sets `row.status = "in_flight"`) and `run_worker`
What is wrong: `_claim_batch` selects only `status == "pending"` and marks claimed rows `in_flight`, but nothing ever returns a row to `pending` — a worker crash, a cancelled `gather`, the `IntegrityError` from the status-vocabulary defect above, or an unhandled exception in `deliver` all leave the row permanently claimed (R38 clause 1: a transient state exited only on the success path, with no failure exit and no timeout).
What breaks in production: after any worker restart mid-batch, up to 100 real customer events are silently never delivered and never retried, with no alert — the deliveries API shows them stuck at `in_flight` forever.
Fix: add `claimed_at TIMESTAMPTZ` and reclaim on a lease — `_claim_batch` selects `status = 'pending' OR (status = 'in_flight' AND claimed_at < now() - interval '5 minutes')`, sets `claimed_at = now()`, and `deliver` wraps its body in `try/finally` that returns the row to `pending` (with `attempts` incremented and `next_attempt_at` advanced) on any exception. **Allow side that must still succeed**: a delivery currently in flight and inside its lease must NOT be reclaimed by a concurrently running `_claim_batch` — assert that a row claimed 10 seconds ago is invisible to a second claim, alongside the assertion that one claimed 10 minutes ago is reclaimed. **Red-proof, one mutation per clause**: (i) remove the lease-expiry disjunct and observe the reclaim test go red; (ii) remove the `finally` reset and observe the test that raises inside `send_once` and then asserts the row is `pending` go red; (iii) shorten the lease to zero and observe the in-lease no-reclaim test go red. **Fail loudly**: a row that has been reclaimed more than `MAX_ATTEMPTS` times must go to `failed_permanent` with a "lease expired repeatedly" detail rather than cycling forever. **Preserve**: the batch claim must remain a single statement so two workers cannot claim the same row — do not fix this by dropping the claim step. **Boundary and tie**: the boundary is `claimed_at` exactly at the lease edge, which is treated as expired (reclaimable); two workers whose claims tie on the same row are resolved by the `UPDATE ... WHERE status = 'pending' RETURNING` compare-and-swap, not by read-then-write.

### Major: the distributed lock is not atomic and is released by whoever runs last
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does `get` then `set` then `expire` as three separate round trips, so two workers both observe an empty key and both proceed; and the `finally` deletes `LOCK_KEY` by name without proving the current value is the one this process wrote, so a worker whose 60-second TTL already expired deletes the lock a *different* worker now holds (R51: the release is bound to the key's name, not to the lock object the acquire examined).
What breaks in production: two or more workers claim and deliver the same rows concurrently, so customers receive duplicated events and the `attempts` accounting diverges; because `deliver` can block far past the 60-second TTL, this is the normal case under load rather than a rare race.
Fix: acquire with a single atomic `SET key <random-token> NX EX 60` and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1]) == ARGV[1] then return redis.call('del',KEYS[1]) end`) passing the token this process generated; renew the TTL from a background task while the batch runs, or make the TTL longer than the worst-case batch. **Allow side that must still succeed**: a single worker must still acquire the lock on every poll iteration and must still release it so the next iteration proceeds — assert two sequential iterations both acquire, or a "never release" fix passes every other clause. **Red-proof, one mutation per clause**: (i) revert to `get`-then-`set` and observe a test issuing two concurrent `_acquire_lock` calls against a fake Redis that asserts exactly one returns True go red; (ii) replace the compare-and-delete with a bare `delete` and observe the test where worker A's token has been overwritten by worker B and A's release must be a no-op go red. **Fail loudly**: a Redis error in acquire must return False (skip this iteration) rather than raise or be read as "lock is free" — the unavailable-dependency case must not spell the same as "acquired". **Preserve**: the TTL must stay, so a crashed worker still releases eventually; do not fix the stolen-lock problem by removing expiry. **Boundary and tie**: the boundary is TTL expiry — a lock expiring exactly as another worker's `SET NX` lands means the newcomer holds it and the old holder's release must be refused; the token is what breaks the tie.

### Major: retry state is never persisted, so `next_attempt_at`, `attempts`, and `backoff_for` are dead in the schema
File: `app/webhooks/delivery.py` — `deliver`'s `while True` loop; `app/webhooks/models.py` — `WebhookDelivery.attempts`, `next_attempt_at`
What is wrong: the schema and the claim query are built for a scheduled-retry design (`next_attempt_at <= now`, `attempts` counter), but `deliver` runs all five attempts inside one coroutine, writing `attempts` only once at the very end via `_finish`, and never writing `next_attempt_at` at all — the declared retry capability has no backing runtime path (R41).
What breaks in production: `attempts` reads 0 for every in-flight delivery so operators cannot see retry progress, `next_attempt_at` stays at its enqueue value forever so the ordering key is meaningless, and any process restart during the 30-second retry chain loses every attempt made so far with the row wedged `in_flight`.
Fix: make `deliver` perform exactly one attempt — on a retryable failure, write `attempts = attempt`, `next_attempt_at = now + backoff_for(attempt)`, `status = 'pending'`, and return; on a 2xx write `delivered`; on `attempt >= MAX_ATTEMPTS` write `failed_permanent`. **Allow side that must still succeed**: a first-attempt success must still be a single POST and a single `delivered` write with `attempts == 1` — assert it, so a fix that always reschedules is caught. **Red-proof, one mutation per clause**: (i) stop writing `next_attempt_at` and observe the test asserting a failed delivery is re-claimed only after `backoff_for(1)` has elapsed go red; (ii) stop writing `attempts` and observe the test asserting `attempts == 3` after three claim cycles go red; (iii) remove the `MAX_ATTEMPTS` terminal branch and observe the bounded test (a permanently failing endpoint reaches `failed_permanent` and stops being claimed) go red — bound that test with a timeout so a non-terminating loop reds rather than hangs. **Fail loudly**: a delivery whose endpoint row has been deleted must be recorded `failed_permanent` with that reason, not skipped. **Preserve**: the documented 2/4/8/16 schedule and the 5-attempt cap — the existing parametrized `backoff_for` test must stay green unchanged. **Boundary and tie**: the boundary is `next_attempt_at <= now` inclusive; rows tied at the same instant are ordered by the primary key (see the ordering finding).

### Major: a failed webhook enqueue is swallowed after the event is already committed
File: `app/events/dispatcher.py` — `dispatch`, `except Exception as exc: log.warning(...)`
