### Critical: the HMAC is computed over different bytes than the bytes actually POSTed
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, with `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys re-ordered) while `send_once()` hands the dict to `client.post(..., json=delivery.payload)`, so httpx serializes the body itself with its own separators and the original key order — the signed string and the transmitted body are not the same bytes, and `docs/webhooks.md` tells the receiver to MAC the **raw request body**.
What breaks in production: every customer following the published verification recipe computes a different digest and rejects 100% of deliveries, so the whole feature is dead on arrival while our own tests stay green.
Fix: make the serialized bytes the single source for both signing and transport — have `send_once()` call `body = signing.serialize(delivery.payload).encode()`, sign exactly `body`, and send `client.post(endpoint.url, content=body, headers={...,"Content-Type":"application/json"})`; never pass `json=` again (evidence for reuse: `signing.serialize()` already exists as the canonical encoder and `send_once()` bypasses it — R1). Preserve: the body must remain valid `application/json` with the same field values, and the deterministic `sort_keys=True` ordering must stay (it is what makes the receiver's recomputation reproducible) — do not "fix" this by deleting `sort_keys` or by loosening the doc to say "any JSON encoding". Allow side that must still succeed: a round-trip test that captures the bytes off `httpx.MockTransport` and feeds them, unmodified, through `signing.verify`-equivalent recomputation must PASS. Red-prove each clause separately by execution: (i) mutate `serialize` to drop `sort_keys` and observe the round-trip assertion redden on a payload whose keys are unsorted (e.g. `{"b":1,"a":2}`); (ii) mutate `send_once` back to `json=` and observe the same assertion redden; (iii) mutate one payload byte in the transport handler and observe the digest assertion redden. Fail loudly: if `serialize()` raises (non-JSON-serializable payload) the delivery must be marked `failed_permanent` with the exception text, never signed-and-sent with a partial body and never silently skipped. Boundary and tie: an empty payload `{}` signs `"{ts}.{}"` and must still verify; two deliveries with byte-identical payloads and the same timestamp legitimately produce the same signature — that is not a duplicate-detection signal and nothing may branch on signature equality.

### Critical: the timestamp is sent but not covered by the signature, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign()` (line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`)
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign()` MACs the body alone and returns the timestamp as an unauthenticated header.
What breaks in production: an attacker who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to "now" — the five-minute freshness check the docs sell as "what stops a captured request from being replayed" validates a value nothing signed.
Fix: change the MAC input to `f"{timestamp}.".encode() + body` where `body` is the exact transmitted bytes from the finding above, and update `verify()` to take the timestamp explicitly (`verify(secret, timestamp, body, signature)`) instead of re-deriving a fresh one — note that today's `verify()` only passes because the timestamp is absent from the MAC, so this is a coupled change and both must land together. Preserve: `X-Acme-Timestamp` must still be sent as unix seconds and the header names must not change (customers key on them). Allow side: a verification test with a timestamp 4 minutes 59 seconds old must PASS. Red-prove separately: (i) alter only the timestamp in a captured request and assert verification reddens (this is the clause that fails today); (ii) alter only one body byte and assert verification reddens; (iii) set the timestamp 5 minutes 1 second old and assert the freshness check reddens while the MAC itself still matches, proving the two checks are independent. Fail loudly: a non-numeric or absent `X-Acme-Timestamp` must reject with a named error, not fall through to a MAC-only comparison. Boundary and tie: define the window as inclusive at exactly 300 seconds (accept `age <= 300`), state it in `docs/webhooks.md`, and specify that two requests sharing a timestamp are independent — the window is not a nonce and does not dedupe.

### Critical: signing secrets are generated with the `random` module, which is a predictable PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. Mersenne Twister seeded from process state and not a CSPRNG, so secrets are predictable to anyone who can observe enough outputs of the same process.
What breaks in production: a recovered secret lets an attacker forge signed events into a customer's webhook receiver — fabricated `invoice.paid` events driving fulfilment — and the customer's verification code correctly reports the forgery as authentic.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and rename `SECRET_BYTES` to mean actual entropy bytes (32), removing `import random` and `_ALPHABET` so the weak path cannot be reached again; keep `SECRET_PREFIX` and the `whsec_` shape, which customers key on. Preserve: existing stored secrets must keep working — do not rotate or invalidate them as part of this change; add a separate rotation endpoint if rotation is wanted. Allow side: a test asserting a freshly generated secret still starts with `whsec_` and is accepted end-to-end by `sign`/`verify` must PASS. Red-prove separately: (i) assert 1,000 generated secrets are all distinct and redden it by stubbing the generator to a constant; (ii) assert the secret's decoded entropy is >= 32 bytes and redden it by passing `token_urlsafe(8)`; (iii) grep-gate in the test suite that `app/webhooks/signing.py` contains no `import random`, reddened by re-adding the import. Fail loudly: if the platform's `secrets` source raises, endpoint creation must return 5xx and persist nothing — never fall back to `random`. Boundary and tie: the existing length assertion in `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` pins `len == len(prefix) + 32`, which is a *character* count and will fail for `token_urlsafe(32)` (43 chars) — update it to assert a minimum length and byte-entropy, not an exact character count, or the test blocks the fix.

### Critical: signature comparison is a plain `==`, not constant-time
File: `app/webhooks/signing.py` — `verify()` (`return expected == signature`)
What is wrong: the published verification helper compares the expected digest to the supplied one with Python's short-circuiting `==` instead of `hmac.compare_digest`.
What breaks in production: any caller using this helper on an inbound path leaks the digest byte-by-byte through response timing, letting an attacker recover a valid signature without the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str`/`bytes` of the same type first; keep the `sha256=` prefix comparison inside the constant-time compare rather than short-circuiting on the prefix. Preserve: `verify()` must keep returning a plain `bool` and must keep accepting the exact header value (`sha256=<hex>`) — do not "fix" it by making callers strip the prefix. Allow side: `verify` with the correct secret and an untampered signature must still return `True`. Red-prove separately: (i) flip one hex character of a valid signature and assert `False`; (ii) sign with a different secret and assert `False`; (iii) reintroduce `==` and assert a lint/grep gate over `app/webhooks/signing.py` reddens. Fail loudly: a `signature` that is `None` or not `str` must raise a named `TypeError`/`ValueError` at the boundary rather than returning `False`, so "could not compare" is not spelled the same as "did not match". Boundary and tie: signatures of unequal length must still take the constant-time path (`compare_digest` handles this) and must return `False`, not raise.

### Critical: `list_deliveries` has no tenancy filter — any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries()`
What is wrong: the query filters only `WebhookDelivery.endpoint_id == endpoint_id` and never joins `WebhookEndpoint` to check `org_id == user.org_id`, so `endpoint_id` is a raw, enumerable object reference.
What breaks in production: any customer can walk `endpoint_id` 1..N and read other tenants' delivery records — event types, response statuses, and delivery schedules for invoices and subscriptions — a cross-tenant data breach reachable with a valid API key.
Fix: join and scope the query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. Cross-cutting evidence: `list_api_keys()` and the new `list_webhook_endpoints()` both filter on `org_id == user.org_id`; `list_deliveries()` is the single site in the diff that omits the established pattern (R3), and no other route in the diff takes a caller-supplied primary key. Preserve: the owning org must still receive its rows in `created_at DESC` order with the `limit` honoured — do not fix this by removing the endpoint or by dropping the `endpoint_id` path parameter. Allow side, pinned as a test: the owning org's caller receives exactly its own rows (200, non-empty). Red-prove separately: (i) a foreign-org caller receives 404 and an empty body — redden by deleting the `org_id` filter; (ii) per RT8, assert the foreign-org call also returns **zero rows**, not merely a status, so the test cannot pass on the status alone; (iii) an unauthenticated caller is rejected by `current_user` — redden by removing the dependency. Fail loudly: if `user.org_id` is `None`, deny with 403 rather than querying with `org_id IS NULL`. Boundary and tie: an `endpoint_id` that exists but belongs to another org and an `endpoint_id` that does not exist must be indistinguishable (both 404, same body).

### Critical: no destination validation — the delivery worker is a fully controllable SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint()` (URL check), with `app/webhooks/delivery.py` — `run_worker()` (`follow_redirects=True`)
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://`, `httpfoo://`, and any host including `127.0.0.1`, `169.254.169.254`, and internal RFC1918 addresses — while `docs/webhooks.md` claims "Only `https://` URLs are accepted" — and the client then follows redirects, so even a validated public host can bounce the request to a private one.
What breaks in production: any authenticated customer makes our worker POST attacker-chosen JSON to cloud metadata and internal admin services from inside the VPC, and reads the outcome back through the response status stored on the delivery row; plaintext `http://` destinations additionally ship signed event payloads over the wire in the clear.
Fix: add a `validate_destination(url)` helper in `app/webhooks/` used by BOTH the create route and `send_once()` — require `scheme == "https"` by exact equality (not `startswith`), reject userinfo and non-default ports outside an allowlist, resolve the hostname and reject every resulting address that is loopback/link-local/private/reserved/multicast, and set `follow_redirects=False` on the `AsyncClient` so a 3xx is recorded as a permanent failure. Re-validate at send time, not only at registration, because DNS can be re-pointed after the endpoint row is stored (R51-shaped check/use gap). Preserve: legitimate public HTTPS endpoints on port 443 must keep working unchanged, and the create route must keep returning 422 with the existing `detail` wording for a malformed URL — do not fix this by dropping the deliveries listing or by removing the response-status field. Allow side, pinned: `https://hooks.example.com/acme` resolving to a public address is accepted at create time AND delivered at send time. Red-prove separately: (i) `http://hooks.example.com/x` → 422, reddened by restoring `startswith("http")`; (ii) `https://localhost/x` and `https://169.254.169.254/x` → 422, reddened by removing the address-class check; (iii) a public host that redirects to `http://127.0.0.1/` is recorded `failed_permanent` and never re-requested, reddened by setting `follow_redirects=True`. Fail loudly: when DNS resolution fails or times out, reject registration with a named error and mark the send attempt failed — an unresolvable host must not be treated as "no private address found, therefore safe". Boundary and tie: state that a host resolving to *both* a public and a private address is rejected (any-private-wins), and that IPv6-mapped IPv4 literals such as `::ffff:127.0.0.1` fall on the reject side.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending','in_flight','delivered','failed'))`, with `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the SQL constraint allows `'failed'` while `app/webhooks/models.py::STATUSES` and `delivery.py` both use `'failed_permanent'`, and `STATUSES` is defined but never referenced by the model column or the constraint, so three copies of one enum disagree (R2).
What breaks in production: the first delivery to exhaust its attempts raises a `CheckViolation` inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and the worker task dies — the failure path of the retry feature has never once executed successfully.
Fix: change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and derive it from a single source — make `models.STATUSES` the definition, add `status = Column(String(20), ..., default="pending")` with a `CheckConstraint` built from `STATUSES`, and add a test that asserts the SQL text in `migrations/0042_webhook_delivery.sql` lists exactly `STATUSES`. Preserve: the constraint must remain a real DB-level CHECK — do not fix this by widening the column to unconstrained `TEXT`, which would delete the thing that made the mismatch visible. Allow side: writing each of the four legitimate statuses through `_finish` must succeed against a real (not mocked) database. Red-prove separately: (i) write `'failed'` and assert the DB rejects it; (ii) add a fifth member to `STATUSES` without touching the migration and assert the sync test reddens; (iii) remove the CHECK from the migration and assert an arbitrary junk status is then accepted, proving the constraint is load-bearing. Fail loudly: if `_finish`'s `session.get` returns `None` (see the Minor below) or the write violates the constraint, log at ERROR with the delivery id and re-raise — the current `except`-free path silently kills the gather task. Boundary and tie: name `'failed_permanent'` and `'delivered'` as the only terminal states, and specify that a row already terminal must not be transitioned again (a retry landing after a terminal write is a no-op, not an overwrite).

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event()` creates one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index permits only one row per `event_id` across the whole table.
What breaks in production: the moment an organization registers a second endpoint, `session.add_all(rows)` violates the unique index, `enqueue_for_event` raises, the `except Exception` in `dispatch()` swallows it as a warning, and the event is delivered to **nobody** — silently, with the event row already committed.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is also the idempotency guard the "deduplicate on `event_id`" line in `docs/webhooks.md` implies, and update that doc line to say deduplicate on `(endpoint, event_id)`. Preserve: the per-endpoint idempotency guarantee must remain — do not fix this by simply dropping the unique index, which would let a re-dispatched event enqueue duplicate rows for the same endpoint. Allow side, pinned: an org with two active endpoints enqueues exactly two rows for one event and both are delivered. Red-prove separately: (i) enqueue the same `(endpoint_id, event_id)` twice and assert the second insert is rejected; (ii) enqueue one `event_id` across two endpoints and assert both rows persist — redden by restoring the single-column index; (iii) drop the index entirely and assert clause (i) reddens, proving the constraint rather than application logic is enforcing it. Fail loudly: `enqueue_for_event` must surface a conflict as a named, logged outcome (`already_enqueued`) rather than letting `dispatch()`'s blanket `except Exception` turn a constraint violation into a WARNING. Boundary and tie: state that a *replayed* dispatch of the same event is expected to hit the constraint and must be treated as success (already enqueued), not as an error.

### Critical: the worker uses ORM objects after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` (`return rows` inside `with session_scope()`), `deliver()` (`endpoint` fetched in a closed session)
What is wrong: both functions return or retain SQLAlchemy instances past the end of their `session_scope()` block, and every later attribute read (`delivery.id`, `delivery.payload`, `delivery.attempts`, `endpoint.signing_secret`, `endpoint.url`) touches expired attributes on a detached instance.
What breaks in production: on the default `expire_on_commit=True`, the first attribute access in `send_once()` raises `DetachedInstanceError`, `asyncio.gather` propagates it, and `run_worker` dies on its first non-empty batch — after `_claim_batch` has already flipped those rows to `in_flight`, where nothing will ever pick them up again.
Fix: stop passing ORM entities across session boundaries — have `_claim_batch()` return plain dataclasses/tuples of the fields the sender needs (`id`, `endpoint_id`, `attempts`, `payload`) and have `deliver()` load the endpoint's `url` and `signing_secret` into locals inside its own `session_scope()` before the first `await`. Preserve: the claim must stay a single statement that both selects and marks `in_flight` (an atomic `UPDATE ... RETURNING` or `SELECT ... FOR UPDATE SKIP LOCKED`), so two workers cannot claim the same row — do not fix detachment by widening the session to span the HTTP calls, which would hold a DB transaction open for up to 30 seconds per delivery. Allow side, pinned: a happy-path integration test against a real session delivers one claimed row end-to-end and marks it `delivered`. Red-prove separately: (i) restore `return rows` and assert the integration test raises `DetachedInstanceError`; (ii) run two concurrent `_claim_batch()` calls against one pending row and assert exactly one claims it, reddened by removing `SKIP LOCKED`; (iii) assert a claimed row's `attempts` value read in the sender equals the value in the DB, reddened by stubbing the projection to a stale constant. Fail loudly: if `session.get(WebhookEndpoint, ...)` returns `None` (endpoint deleted between enqueue and send), mark the delivery `failed_permanent` with a named reason instead of raising `AttributeError` into `gather`. Boundary and tie: rows with `next_attempt_at` exactly equal to `now` are claimable (`<=`), and ties on `next_attempt_at` must be broken by `id ASC` so the claim order is total (see the R57 Minor below).

### Major: the signing secret is returned by the list endpoint, contradicting the documented one-time-disclosure control
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns it on every `GET`, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation).
What breaks in production: the secret is repeatedly re-emitted into browser caches, proxy logs, and API-client history, so a single leaked response transcript hands over the ability to forge signed events; customers who believed the documented control skipped storing it in their own secret manager and now have no rotation story.
Fix: remove `signing_secret` from `to_dict()` and return it only from the `POST` handler by building the create response explicitly (`{**endpoint.to_dict(), "signing_secret": secret}` from the in-memory value), keeping the doc claim true; expose a redacted hint (`whsec_…` plus last 4) on the list route if operators need to correlate. Preserve: the create response must still contain the full secret exactly once — do not fix this by removing it from `POST` as well, which would make registered endpoints unverifiable. Allow side, pinned: `POST /webhook-endpoints` response contains a full `whsec_`-prefixed secret. Red-prove separately: (i) assert `GET /webhook-endpoints` response JSON contains no key `signing_secret` and no substring of the stored secret — redden by putting the field back in `to_dict()`; (ii) assert the `POST` response *does* contain it — redden by removing it from the create handler; (iii) assert the delivery-listing response also contains no secret. Fail loudly: if the create handler cannot read back the generated secret it must 500 rather than return an endpoint with a silently absent secret field. Boundary and tie: state that two endpoints registered in the same request cycle get independent secrets, and that the redacted hint must not be long enough to distinguish two secrets sharing a prefix.

### Major: `time.sleep` blocks the event loop inside an async coroutine
File: `app/webhooks/delivery.py` — `deliver()` (`time.sleep(delay)`)
What is wrong: `deliver()` is a coroutine gathered with up to 100 siblings, and it calls the blocking `time.sleep` rather than `await asyncio.sleep`, freezing the whole event loop for 2+4+8+16 = 30 seconds per failing delivery.
What breaks in production: one unreachable customer endpoint stalls every other delivery in the batch and every other coroutine in the process, and because `LOCK_KEY` expires after 60 seconds the lock lapses mid-batch, letting a second worker claim and re-send the same events.
Fix: replace with `await asyncio.sleep(delay)`, and stop holding retries inside a single coroutine at all — on a failed attempt, write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the poll loop re-claim it, so the process can restart mid-retry without losing the delivery; separately, renew or size `LOCK_KEY`'s TTL to exceed the worst-case batch wall time (`BATCH_SIZE` concurrency × `REQUEST_TIMEOUT`) rather than the current fixed 60. Preserve: the documented attempt count (5) and the 2/4/8/16 s schedule must not change — do not fix the blocking by shortening the backoff. Allow side, pinned: a delivery that succeeds on attempt 2 is still marked `delivered` with `attempts == 2`. Red-prove separately: (i) assert two concurrent `deliver()` calls, one of which retries, complete in roughly the max rather than the sum of their delays — redden by restoring `time.sleep`; (ii) kill the worker between attempt 2 and 3 and assert the row is re-claimed with `attempts == 2` preserved — redden by keeping the in-coroutine `while True`; (iii) assert `next_attempt_at` after attempt 3 equals `now + 8s` — redden by changing `BASE_DELAY_SECONDS`. Fail loudly: if the row cannot be re-scheduled (DB write fails), log ERROR and leave the row claimable rather than dropping the delivery on the floor. Boundary and tie: at `attempt == MAX_ATTEMPTS` the row goes terminal and is NOT rescheduled; `attempt == MAX_ATTEMPTS - 1` is rescheduled once more — state the comparison as `attempt >= MAX_ATTEMPTS`.

### Major: the Redis lock is not atomic and can wedge permanently
File: `app/webhooks/delivery.py` — `_acquire_lock()`
What is wrong: `get` followed by `set` is a check-then-act race two workers both win, and `set` followed by a separate `expire` leaves an un-expiring key if the process dies between the two calls.
What breaks in production: either two workers dispatch the same batch (duplicate webhook deliveries beyond the documented at-least-once budget), or a single ill-timed crash leaves `webhooks:dispatch:lock` set with no TTL and the entire delivery pipeline silently stops forever, since `run_worker`'s `finally` only deletes the key on a path that successfully acquired it.
Fix: use a single atomic call — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token` is a per-worker random value — and release with a compare-and-delete Lua script so a worker whose lock already expired cannot delete a successor's lock; add a renewal heartbeat while a batch is in flight. Preserve: only one worker may dispatch at a time — do not fix the wedge by dropping the lock, and do not fix the race by lengthening the TTL alone. Allow side, pinned: after the holder releases, the next `_acquire_lock()` call returns `True`. Red-prove separately: (i) two concurrent `_acquire_lock()` calls against a real/fake Redis yield exactly one `True` — redden by restoring get-then-set; (ii) a key set without TTL is impossible — assert `ttl(LOCK_KEY) > 0` immediately after acquisition, reddened by splitting `set` and `expire` again; (iii) worker A's expired lock cannot delete worker B's lock — redden by replacing compare-and-delete with a plain `delete`. Fail loudly: if Redis is unreachable, `_acquire_lock()` must raise/log ERROR and the worker must NOT dispatch — an unreachable coordinator must read as "cannot establish exclusivity", never as "no lock found, therefore free". Boundary and tie: a lock whose TTL is exactly expiring at the moment of the CAS release falls on the "do not delete" side; two workers arriving in the same millisecond are resolved by `NX`, not by ordering.

### Major: `in_flight` is a non-terminal state with no timeout and no reaper
File: `app/webhooks/delivery.py` — `_claim_batch()` / `deliver()` / `run_worker()`
What is wrong: `_claim_batch()` writes `status = "in_flight"` and nothing ever moves a row out of it except a successful `_finish`, while `_claim_batch` only ever selects `status == "pending"` (R38, non-terminal transient state).
What breaks in production: any worker crash, deploy, OOM kill, or the `DetachedInstanceError` above leaves rows stranded in `in_flight` permanently — customers stop receiving events for those deliveries and nothing alerts, because the queue looks empty.
Fix: add a `claimed_at` column and a reaper query that returns rows with `status = 'in_flight' AND claimed_at < now() - INTERVAL '<visibility timeout>'` to `pending` with `attempts` unchanged, run it at the top of each `run_worker` iteration; set the visibility timeout strictly greater than `REQUEST_TIMEOUT` so a slow-but-live request is not double-sent. Preserve: `in_flight` must remain a real state that prevents concurrent claim — do not fix this by deleting the status transition and claiming `pending` rows optimistically. Allow side, pinned: a row claimed 1 second ago is NOT reaped and its in-progress delivery still completes. Red-prove separately: (i) a row whose `claimed_at` is older than the timeout is returned to `pending` — redden by removing the reaper; (ii) the reaped row retains its `attempts` count — redden by resetting `attempts = 0`; (iii) a row claimed within the timeout is untouched — redden by inverting the comparison. Fail loudly: emit a WARNING metric each time the reaper reclaims a row, so a crash loop is visible rather than absorbed as normal throughput. Boundary and tie: a row whose `claimed_at` is *exactly* at the timeout is not yet reaped (`<` strictly), and if two reapers run concurrently the reclaim must be a conditional `UPDATE ... WHERE status = 'in_flight'` so only one wins.

### Major: naive and timezone-aware datetimes are mixed, and the migration's columns are not `timestamptz`
File: `app/webhooks/delivery.py` — `enqueue_for_event()` (`next_attempt_at=datetime.utcnow()`), `migrations/0042_webhook_delivery.sql` (`TIMESTAMP NOT NULL`), `app/webhooks/models.py` (`DateTime(timezone=True)`)
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` while `_claim_batch` compares against an aware `datetime.now(timezone.utc)`, the model declares `timezone=True` but the migration creates plain `TIMESTAMP`, and `models.py` already defines a `_now()` helper returning an aware UTC value that `delivery.py` reimplements incorrectly (R1: a helper exists in the same change and the new code reimplements it).
What breaks in production: on a database or connection whose session `TimeZone` is not UTC, the aware bound in `_claim_batch` is converted before truncation, so rows become claimable hours early or hours late — deliveries fire against a schedule nobody configured, and the drift is invisible in any test that runs under UTC.
Fix: change both tables' timestamp columns to `TIMESTAMPTZ` in the migration, and replace `datetime.utcnow()` with the existing `models._now()` (promote it to a shared `app/webhooks/_now` import) at every construction site. Preserve: `next_attempt_at` semantics — "the earliest instant this delivery may be attempted" — must not change, and existing rows must be migrated with an explicit `AT TIME ZONE 'UTC'` clause rather than a bare type change that reinterprets them in the server's local zone. Allow side, pinned: a delivery scheduled for `now + 2s` is not claimed at `now` and IS claimed at `now + 2s`, under a non-UTC session timezone. Red-prove separately: (i) run the claim test with `SET TIME ZONE 'America/New_York'` and assert it still passes — redden by reverting the column to `TIMESTAMP`; (ii) assert `enqueue_for_event` stores a tz-aware value — redden by restoring `utcnow()`; (iii) assert `_now()` is the only clock source in `app/webhooks/` via a grep gate, reddened by reintroducing `datetime.utcnow()`. Fail loudly: reject (raise) any naive datetime handed to a delivery constructor rather than coercing it silently. ### Major: a failed enqueue is swallowed, committing an event with no delivery rows and no retry
File: `app/events/dispatcher.py` — `dispatch()` (`except Exception as exc: log.warning(...)`)
What is wrong: the event row is committed in its own `session_scope` and the webhook enqueue happens afterwards in a separate transaction whose failure is caught, logged at WARNING, and discarded — there is no outbox, no retry, and no dead-letter (R9-shaped: the side effect is not atomic with the write it belongs to).
What breaks in production: a transient DB blip, or the unique-index violation described above, permanently drops the webhook for that event with only a WARNING line; the customer never learns an `invoice.paid` was never delivered and no operator query can enumerate the losses.
Fix: write the delivery rows in the SAME transaction as the `Event` insert (a transactional outbox: `dispatch` opens one `session_scope`, inserts the event, calls `enqueue_for_event(session=session, ...)` with the caller's session, and commits once), so either both exist or neither does; keep the worker as the only component that performs network I/O. Preserve: the in-process `SUBSCRIBERS` fan-out must stay outside the transaction and must keep running even when enqueue fails — do not fix this by moving subscriber calls inside the transaction. Allow side, pinned: a normal `invoice.paid` dispatch returns the event id and creates the expected delivery rows. Red-prove separately: (i) force the delivery insert to raise and assert the `Event` row is absent afterwards — redden by restoring the split transactions; (ii) assert `dispatch` re-raises rather than returning an id when the combined commit fails — redden by restoring the blanket `except`; (iii) assert a subscriber raising does not roll back the event. Fail loudly: if enqueue cannot run at all (module import failure, DB down), `dispatch` must raise a named error to its caller — "enqueued nothing" must not be spelled the same as "enqueued zero matching endpoints". Boundary and tie: an org with zero active endpoints legitimately produces zero delivery rows and must be a success, not an error — that is the case the loud path must not swallow into.

### Major: 4xx responses are retried although the docs promise they are permanent
File: `app/webhooks/delivery.py` — `deliver()` (the `if 200 <= response.status_code < 300 ... else` branch), against `docs/webhooks.md` ("a 4xx is permanent and we stop immediately")
What is wrong: every non-2xx status falls through to the same retry path, so a 400, 404, 410, or 401 is retried the full five times.
What breaks in production: endpoints that have been decommissioned or that reject our payload are hammered five times per event with exponential backoff, wasting worker capacity and, for customers on metered ingress, generating charges for requests we documented as never being repeated.
Fix: branch on the class — `2xx → delivered`; `408` and `429` → retry (honouring `Retry-After` where present); other `4xx` → `failed_permanent` immediately; `5xx`, timeouts, and connection errors → retry. Preserve: the retry behaviour for 5xx and transport errors must be unchanged, and `MAX_ATTEMPTS` stays 5 — do not fix the doc mismatch by editing the doc to say "everything is retried", which would delete the guarantee customers rely on. Allow side, pinned: a 503 followed by a 200 still results in `delivered` with `attempts == 2`. Red-prove separately: (i) a 400 response yields `failed_permanent` with `attempts == 1` — redden by removing the 4xx branch; (ii) a 429 is retried — redden by folding it into the permanent branch; (iii) a 500 is retried to `MAX_ATTEMPTS` — redden by folding 5xx into the permanent branch. Fail loudly: an unexpected status class (1xx, 3xx with redirects disabled) must be recorded `failed_permanent` with the status in `response_status`, never silently retried under the default branch. Boundary and tie: state that `399` and `400` fall on opposite sides and that `200` and `299` are both success — the comparisons are `200 <= s < 300` and `400 <= s < 500`.

### Major: `webhooks_enabled` is added to `organizations` and never read
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: the migration declares a per-org feature flag defaulting to FALSE, but no code in the diff — not `create_webhook_endpoint`, not `dispatch`, not `enqueue_for_event` — ever consults it (R41: a declared capability with no backing path).

### Major: `event_types` is stored unvalidated and cannot match most of what the API advertises

### Major: `limit` on the deliveries route has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries()` (`limit: int = Query(50, ge=1)`)
What is wrong: the query parameter is bounded below by `ge=1` but has no `le`, so a caller may request an arbitrarily large page (RS3: a new request parameter validated only on one side at the schema boundary).
What breaks in production: `?limit=100000000` makes the database materialize and the app serialize every delivery row with its JSONB payload for that endpoint, exhausting memory and taking the API process down — a one-request denial of service available to any authenticated customer.

### Major: three new authenticated routes ship with no rate limiting

What breaks in production: a single API key can register unbounded endpoints — each of which then multiplies every future event into another outbound HTTP request — turning our own dispatcher into an amplifier, while the deliveries route can be polled to exhaust DB connections.

### Major: outbound signatures are logged at INFO and full third-party response bodies are persisted unbounded
File: `app/webhooks/delivery.py` — `send_once()` (`log.info("POST %s headers=%s", endpoint.url, headers)`) and `_finish()` (`row.response_body = detail`)
What is wrong: the entire header dict — including `X-Acme-Signature` and `X-Acme-Timestamp` — is written to the application log on every attempt, and the customer's complete response body is stored in an unbounded `TEXT` column with no truncation or redaction.
What breaks in production: log readers and anyone with log-index access obtain valid signatures which, because the timestamp is not covered by the MAC (see above), can be replayed against the customer indefinitely; and a customer endpoint returning a multi-megabyte error page writes that blob into our database on every one of five attempts, per delivery.

Preserve: enough diagnostic detail must survive to debug a failing endpoint — the status code, the error class, and the first 2 KiB of the body must still be stored, and the truncation marker must make truncation visible rather than silently shortening. Allow side, pinned: a normal short error body is stored byte-identically with no marker. Red-prove separately: (i) assert the log line for a delivery contains no substring of the signature — redden by restoring `headers=%s`; (ii) assert a 10 KiB response body is stored at 2 KiB plus the marker — redden by removing the truncation; (iii) assert a 2 KiB body is stored unchanged with no marker — redden by making truncation unconditional. Boundary and tie: a body of exactly 2048 bytes is stored whole with no marker; 2049 is truncated.

### Major: the signature tests are tautological and never check the signature against the bytes sent

Allow side, pinned: the recomputation matches for the untouched happy-path request. Red-prove separately: (i) drop `sort_keys` from `serialize` and assert the recomputation assertion reddens; (ii) drop the timestamp from the MAC input and assert it reddens; (iii) change one payload value in the handler and assert it reddens. Fail loudly: if `captured` is empty because the transport handler never ran, the test must fail with a named assertion rather than raising `KeyError` from an absent key.
