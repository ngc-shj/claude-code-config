### Critical: signing secrets are generated with a non-cryptographic PRNG
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: The secret is built from `random.choice` over `_ALPHABET`, i.e. the Mersenne Twister, which is a deterministic generator whose internal state is recoverable from a modest run of its outputs and is seeded from process state, not entropy.
What breaks in production: An attacker who observes or brute-forces a few secrets (or who registers two endpoints of their own and recovers the generator state) can predict every other tenant's signing secret and forge webhook deliveries that receivers accept as ours.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (`import secrets`; drop `random`, `string`, `_ALPHABET`), and rename `SECRET_BYTES` to match its new meaning of raw entropy bytes. Preserve the behaviour the format depends on: the returned string must still start with `SECRET_PREFIX` and remain a single URL-safe token, so `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` must be updated to assert the prefix plus `len(secret) >= len(SECRET_PREFIX) + 40` rather than an exact character count — pin the ALLOW side by asserting a freshly generated secret still round-trips through `sign`/`verify` unchanged. Add a test asserting `len({new_signing_secret() for _ in range(1000)}) == 1000` and a test asserting the module does not import `random`. Red-prove each clause separately: (i) revert to `random.choice` and confirm the no-`random`-import test reds; (ii) seed-pin the generator (`random.seed(0)`) under the reverted implementation and confirm the uniqueness test reds; (iii) strip `SECRET_PREFIX` and confirm the prefix assertion reds. Fail loudly rather than degrading: do not wrap `secrets` in a try/except fallback to `random` — if the entropy source is unavailable the call must raise, because a silent fallback is spelled the same as success. Boundary: `SECRET_BYTES = 32` is the floor, not a target; state that 32 bytes is the minimum accepted and that two secrets colliding is treated as a fatal generator fault, not a retry.

### Critical: HMAC signatures are compared with `==`
File: app/webhooks/signing.py — `verify`, `return expected == signature`
What is wrong: The recomputed MAC is compared to the supplied signature with Python's short-circuiting string equality, which returns as soon as the first differing byte is found (RS1).
What breaks in production: Any caller that can submit candidate signatures against this helper — and any receiver that copies it, since `docs/webhooks.md` is the integration guide this code backs — can recover a valid signature byte by byte from response-time differences, defeating the signature entirely.
Fix: Change the comparison to `return hmac.compare_digest(expected, signature)` (`hmac` is already imported). Preserve the function's contract that a signature produced by `sign` for the same secret and payload still verifies — pin that ALLOW side with the existing `test_verify_accepts_signature_produced_by_sign`, and add an adjacent allow case for a signature that differs only in the `sha256=` prefix casing to state explicitly that it is rejected. Red-prove the two clauses separately: (i) revert to `==` and confirm a new test that asserts `signing.verify.__code__.co_names` contains `compare_digest` reds; (ii) mutate `expected` by one hex character and confirm `test_verify_rejects_a_signature_made_with_another_secret` reds for the reason its output names. Fail loudly on the non-decidable cases: `verify` must raise (not return `False`) when `secret` is empty or `signature` is `None`, so "could not check" is not spelled the same as "did not match". Boundary and tie: state that comparison is over the full `sha256=<hex>` string including the prefix, and that two signatures of unequal length are rejected without leaking the length through the comparison path.

### Critical: the signature does not cover the timestamp, so the documented replay window is not a control
File: app/webhooks/signing.py — `sign`, `mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`
What is wrong: The MAC is computed over the payload alone while `X-Acme-Timestamp` is sent unauthenticated, contradicting `docs/webhooks.md` which states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "stops a captured request from being replayed" (R40 producer/consumer divergence; R49 claim stronger than the implementation).
What breaks in production: Anyone who captures one delivery can replay it indefinitely by rewriting the timestamp header to the current time — the signature still validates, so receivers that implemented exactly what our documentation told them to implement have no replay defence at all, and duplicate `invoice.paid` events will be processed as new.
Fix: Make the signed material the documented one: `signed = f"{timestamp}.{body}"` where `body` is the exact byte string transmitted (see the next finding), and have `verify` take the timestamp as an explicit argument rather than regenerating it — `verify(secret, timestamp, body, signature)` — so the caller's timestamp is what enters the MAC. Preserve the useful behaviour: `sign` must keep returning `(timestamp, "sha256=<hex>")` so `send_once`'s header construction is unchanged, and the existing `test_sign_returns_timestamp_and_prefixed_digest` must still pass byte-for-byte on shape. Pin the ALLOW side with a test that a signature produced at timestamp T verifies at timestamp T. Red-prove each clause separately: (i) alter only the timestamp passed to `verify` and confirm a new `test_verify_rejects_a_replayed_timestamp` reds; (ii) alter one byte of the body and confirm the existing wrong-secret test's sibling body-tamper test reds; (iii) drop the `"."` separator and confirm a vector test against a hand-computed expected hex reds. Fail loudly: `verify` must raise on a non-numeric or absent timestamp rather than returning `False`, so a malformed header is distinguishable from a bad MAC. Boundary and tie: the freshness check belongs to the receiver, so document the boundary as `now - timestamp <= 300` inclusive, and state that a timestamp exactly 300 seconds old is accepted while 301 is rejected — do not add clock-skew tolerance silently in `sign`.

### Critical: the bytes that are signed are not the bytes that are sent
File: app/webhooks/delivery.py — `send_once`, `sign(endpoint.signing_secret, delivery.payload)` then `client.post(..., json=delivery.payload, ...)`
What is wrong: `signing.serialize` produces `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys sorted) while httpx's `json=` parameter serializes the dict independently with compact separators and insertion order, so the HMAC is computed over a different byte string than the one placed on the wire (R40 — same team owns both sides, so nothing forces a round-trip).
What breaks in production: Every receiver following `docs/webhooks.md`, which tells them to HMAC the raw request body, computes a different digest than we sent, so signature verification fails for 100% of deliveries and the whole feature is dead on arrival at any customer who actually verifies.
Fix: Serialize once and send those exact bytes: in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, pass it to `sign`, and post with `content=body` plus the explicit `Content-Type: application/json` header already present — never `json=`. Preserve the behaviour the tests rely on: the request body must still parse as JSON with `type == "invoice.paid"`, so `test_send_once_posts_the_signed_payload` keeps its `json.loads(captured["body"])` assertion, and pin the ALLOW side by adding to that same test an assertion that recomputing the HMAC over `captured["body"]` with `SECRET` and the captured timestamp equals the captured signature — a real round-trip through the actual producer output rather than two mocked shapes. Red-prove each clause separately: (i) switch the post back to `json=delivery.payload` and confirm the new round-trip assertion reds; (ii) drop `sort_keys=True` from `serialize` and confirm a fixture whose keys are inserted out of order reds; (iii) change `Content-Type` and confirm the existing content-type assertion reds. Fail loudly: if `serialize` raises on a non-JSON-serializable payload the delivery must be marked `failed_permanent` with that reason recorded, not retried five times. Boundary: state that the signed unit is `f"{timestamp}.".encode() + body` with no trailing newline, and that an empty payload signs `{}` rather than an empty body.

### Critical: the endpoint list route returns every endpoint's signing secret
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict` embeds the signing secret and is used by both `create_webhook_endpoint` (where returning it once is intended) and `list_webhook_endpoints` (where `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards") (R49; RS4).
What breaks in production: The secret is readable indefinitely by anything holding a session for the org — a stolen browser token, a read-only integration, a proxy log, a client-side cache — so a documented one-time secret becomes a permanently exposed one that customers were told they need not protect on our side.
Fix: Remove `"signing_secret"` from `WebhookEndpoint.to_dict` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` using the value it just generated locally. Preserve what makes the feature usable — the create response must still carry the secret, so pin the ALLOW side with a route test asserting `POST /v1/settings/webhook-endpoints` returns a `signing_secret` starting with `whsec_`. Red-prove the two clauses separately: (i) re-add the key to `to_dict` and confirm a new `test_list_endpoints_never_returns_the_secret` (asserting `"signing_secret" not in body[0]` and that no value in the response starts with `SECRET_PREFIX`) reds; (ii) drop the merge in the create handler and confirm the create-side allow test reds. Fail loudly rather than by deletion: do not "fix" this by removing the secret from the create response too — name the preserved behaviour explicitly, that the secret is disclosed exactly once at creation. Boundary: the same rule applies to any future read path (an endpoint-detail or update route); state that `to_dict` is the read shape and the secret is never in it.

### Critical: the deliveries route has no tenancy filter, so any user can read any org's event payloads
File: app/api/routes/settings.py — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: The query filters only on the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while the two sibling handlers in the same file — `list_api_keys` and the newly added `list_webhook_endpoints` — both scope by `user.org_id`, so the tenancy pattern present in this very file was not propagated to the new route (R3, security-relevant; the omission also contradicts `docs/webhooks.md`, which says the route returns attempts "for an endpoint belonging to your organization").
What breaks in production: Any authenticated user can enumerate `endpoint_id` values and read other organizations' delivery rows — a cross-tenant data breach whose blast radius is every event we deliver.
Fix: Join and scope the query: `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and return 404 (not 403) when the join yields nothing, so the route does not confirm the existence of another org's endpoint. Preserve the working case — pin the ALLOW side with a test that a user of org A listing their own endpoint's deliveries still receives the rows, adjacent to the boundary (same endpoint id, correct org). Red-prove each clause separately: (i) drop the `org_id` predicate and confirm a new `test_deliveries_of_another_org_are_not_visible` reds on the returned row count, not merely on the status code; (ii) change the not-found response to 403 and confirm an enumeration test asserting 404 reds. Fail loudly: an unresolvable `endpoint_id` must return 404, never an empty 200, so "no such endpoint" is not spelled the same as "no deliveries yet". Boundary and tie: state that an endpoint belonging to the caller's org but soft-inactive still lists, and that `limit` is applied after the tenancy predicate, never before.

### Critical: endpoint URLs are not restricted, and the delivery client follows redirects — server-side request forgery
File: app/api/routes/settings.py — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check is a prefix test on the scheme, which admits plain `http://` (contradicting `docs/webhooks.md`: "Only `https://` URLs are accepted") and any scheme literally beginning with `http`, with no restriction on the host at all, while the worker follows redirects so even an allowed host can bounce the request to an internal address (RS3 — the boundary check is a surface-form test where the HTTP client defines the meaning).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://127.0.0.1:6379/`, and our worker POSTs signed internal-event payloads to cloud metadata or internal services from inside the VPC, returning the response body into `WebhookDelivery.response_body` where the same customer can read it via the deliveries route.
Fix: Require `parsed.scheme == "https"` exactly (equality, not `startswith`), require a non-empty `parsed.hostname`, reject userinfo (`parsed.username`/`parsed.password`), reject a non-default port outside an allowlist, and resolve the hostname at registration and again immediately before each POST, rejecting any address in a private/loopback/link-local/unique-local/reserved range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`; set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure with the redirect target recorded. Preserve the feature: a public `https://hooks.example.com/acme` endpoint must still register and still deliver — pin that ALLOW side with a registration test and a `send_once` test using the existing `FakeEndpoint.url`, adjacent to the boundary (a public address one step outside every rejected range). Red-prove each clause separately: (i) revert to `startswith("http")` and confirm a `http://…` rejection test reds; (ii) re-enable `follow_redirects` and confirm a `MockTransport` test that returns a 302 to `http://127.0.0.1/` and asserts no second request was made reds; (iii) remove the private-range predicate and confirm a test registering `https://localhost/x` reds. Fail loudly: DNS resolution failing at registration must return a 422 naming the resolution failure, and failing at delivery must mark the attempt failed with that reason — an unresolvable host must never be treated as "no restriction applies". Boundary and tie: state which side `0.0.0.0`, IPv6-mapped IPv4 (`::ffff:127.0.0.1`), and a host resolving to both a public and a private address fall on — the last must be rejected, since a re-resolution between check and use is the attacker's window.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: migrations/0042_webhook_delivery.sql — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint permits `'failed'`, but `app/webhooks/models.py` declares `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` and `app/webhooks/delivery.py::deliver` writes `_finish(delivery.id, "failed_permanent", ...)` — the enum value was changed in the Python constants and not propagated to the SQL (R3 / R2, and the third spelling of the same set means there is no single source of truth).
What breaks in production: The first delivery to exhaust its five attempts raises a check-constraint IntegrityError inside `_finish`, so the row never leaves `in_flight`, the exception escapes `deliver` into `asyncio.gather`, and the worker dies — every endpoint that is merely down takes the whole delivery pipeline with it.
Fix: Change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and remove the duplication that caused the drift: generate the SQL list from `models.STATUSES` in the migration test rather than restating it, and add a test that asserts the constraint's admissible set equals `set(models.STATUSES)` by querying `pg_constraint`. Preserve the working transitions — pin the ALLOW side with a test that inserting each of the four `STATUSES` values succeeds. Red-prove each clause separately: (i) revert the constraint to `'failed'` and confirm the set-equality test reds naming the missing member; (ii) add a fifth value to `STATUSES` without touching the migration and confirm the same test reds; (iii) insert `'bogus'` and confirm the deny test reds. Fail loudly: `_finish` must let an IntegrityError propagate as a named worker error rather than being swallowed, so a constraint mismatch is never spelled the same as a successful finish. Boundary: state that `in_flight` is the only non-terminal member and that any value outside the set is rejected by the database, not merely by the application.

### Critical: the unique index on `event_id` alone makes fan-out to a second endpoint impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id` via `session.add_all(rows)`, but the index permits only one row per `event_id` across the whole table — and it is also globally unique, so two different orgs' events could collide if event ids are ever not globally unique.
What breaks in production: Any org with two active endpoints subscribed to the same event type gets an IntegrityError on the second insert, the whole `add_all` transaction rolls back so *no* endpoint receives the event, and `dispatch`'s blanket `except Exception` downgrades that total loss to a warning line.
Fix: Replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the fan-out actually needs and which is what makes the documented "deduplicate on `event_id`" advice safe at the endpoint level. Preserve the intended property — the index still prevents enqueueing the same event twice for the same endpoint, so pin the ALLOW side with a test that one event fans out to two endpoints of the same org and produces exactly two rows, and pin the deny side with a test that re-running `enqueue_for_event` for the same `(endpoint_id, event_id)` raises rather than duplicating. Red-prove each clause separately: (i) revert to the single-column index and confirm the two-endpoint fan-out test reds with an IntegrityError; (ii) drop the index entirely and confirm the duplicate-enqueue test reds; (iii) make `enqueue_for_event` skip an endpoint and confirm the row-count assertion reds. Fail loudly: `enqueue_for_event` must not catch the IntegrityError — see the `dispatch` finding below — so a rejected insert surfaces as a named failure rather than an event silently reaching nobody. Boundary and tie: state that an endpoint deleted and recreated gets a new `endpoint_id` and therefore may legitimately receive an already-delivered `event_id` again, and that this is intended.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: app/webhooks/delivery.py — `deliver`, `time.sleep(delay)`
What is wrong: The retry backoff uses the blocking `time.sleep` inside `async def deliver`, which does not yield to the event loop.
What breaks in production: A single failing endpoint freezes the whole worker process for 2+4+8+16 = 30 seconds of sleep plus up to 4×30 s of request timeouts, so the up-to-100 deliveries gathered in the same batch — and every other coroutine in the process — stall behind it, and the 60-second Redis lock TTL expires mid-batch while nothing can run to renew it.
Fix: Replace with `await asyncio.sleep(delay)` (`asyncio` is already imported). Better, stop sleeping in-process at all: on a retryable failure, call `_finish`-style persistence that sets `status="pending"`, `attempts=attempt`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)`, and return — the schedule columns and the `next_attempt_at <= now` claim query already exist for exactly this and are currently dead. Preserve the documented retry behaviour: at most `MAX_ATTEMPTS` total attempts with the 2/4/8/16-second schedule, so `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` must remain green unchanged. Red-prove each clause separately: (i) restore `time.sleep` and confirm a test that runs `deliver` concurrently with a fast sentinel coroutine and asserts the sentinel completed first reds; (ii) remove the `next_attempt_at` advance and confirm a test asserting the row's `next_attempt_at` moved forward by `backoff_for(attempt)` reds; (iii) set `attempt` never to increment and confirm the attempt-count assertion reds. Fail loudly: a delivery whose reschedule write fails must be left in a state a reaper can find, and the failure logged at ERROR — never returned as if delivered. Boundary and tie: state that `attempt >= MAX_ATTEMPTS` is the permanent-failure boundary (attempt 5 is the last one made, attempt 6 is never made), and that two deliveries with an identical `next_attempt_at` are ordered by the tie-break key introduced in the ordering finding below.

### Critical: ORM rows are used after the session that loaded them has closed
File: app/webhooks/delivery.py — `_claim_batch` (`return rows` outside the `with`), `deliver` (`endpoint = session.get(...)` then used after the `with`)
What is wrong: Both functions load ORM instances inside `with session_scope() as session:` and then read their attributes after the block has exited — `delivery.attempts`, `delivery.payload`, `delivery.id` in `deliver`, and `endpoint.signing_secret`, `endpoint.url` in `send_once` — which is exactly the hazard the change itself acknowledges elsewhere, since `_finish` re-fetches the row by id rather than holding a reference.
What breaks in production: Under SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and the first access outside the scope raises `DetachedInstanceError`, so the worker throws on its first batch and no webhook is ever delivered; the rows it already flipped to `in_flight` stay there permanently.
Fix: Stop passing ORM instances across scope boundaries — have `_claim_batch` return plain data (a list of `dict`s or a frozen dataclass carrying `id`, `endpoint_id`, `attempts`, `payload`), and have `deliver` load the endpoint's `url` and `signing_secret` into that same structure inside one scope, so `send_once` receives values rather than mapped objects. Preserve the tested call shape: `send_once(client, endpoint, delivery)` must keep working with objects exposing `.url`/`.signing_secret` and `.payload`, so the existing `FakeEndpoint`/`FakeDelivery` tests stay green unchanged. Red-prove each clause separately: (i) return the mapped instances again and confirm an integration test that calls `_claim_batch` against a real session and reads `rows[0].payload` after the scope reds with `DetachedInstanceError`; (ii) drop `signing_secret` from the extracted structure and confirm a `deliver` test reds on the missing attribute; (iii) leave `attempts` unread and confirm the attempt-count assertion reds. Fail loudly: if the endpoint row is missing when `deliver` loads it, mark the delivery `failed_permanent` with that reason rather than proceeding with a `None` endpoint. Boundary: state that the claim scope commits the `in_flight` transition before any HTTP call is made, and that nothing outside a session scope ever touches a mapped attribute.

### Critical: the Redis lock is not atomic, can be set without a TTL, and is deleted by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a GET, then a separate SET, then a separate EXPIRE, so two workers racing between the GET and the SET both win, and a crash between the SET and the EXPIRE leaves a key with no TTL; the `finally` block then deletes `LOCK_KEY` unconditionally, including a lock a *different* worker acquired after the 60-second TTL expired mid-batch (R5 — a read followed by a separate write with no atomicity).
What breaks in production: Two failure modes, both severe: duplicate deliveries because two workers claim overlapping batches, and a permanent total outage because a crash between SET and EXPIRE wedges an eternal lock that no code path clears while every worker spins in the `await asyncio.sleep(poll_interval)` branch forever.
Fix: Make acquisition a single atomic operation with the TTL inline — `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` — and make release conditional on ownership via a Lua compare-and-delete (`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end`), so a worker never deletes a lock it does not hold; renew the TTL while a batch is in flight, or set `LOCK_TTL_SECONDS` above the worst-case batch duration and state the number. Better still, drop the distributed lock and claim rows with `SELECT ... FOR UPDATE SKIP LOCKED` inside `_claim_batch`, which makes concurrent workers correct by construction rather than by mutual exclusion. Preserve the useful behaviour — a single worker must still acquire and process a batch, so pin the ALLOW side with a test asserting one worker acquires, processes, and releases. Red-prove each clause separately: (i) revert to GET-then-SET and confirm a test that interleaves two `_acquire_lock` calls (both awaited before either SET) and asserts exactly one returns `True` reds; (ii) remove `ex=` and confirm a test asserting `TTL(LOCK_KEY) > 0` immediately after acquisition reds; (iii) revert to unconditional `delete` and confirm a test where worker B holds the lock and worker A's `finally` runs, asserting B still holds it, reds. Fail loudly: a Redis error during acquisition must abort the poll iteration with a logged ERROR and must not fall through to processing — "could not check the lock" must not be spelled the same as "acquired the lock". Boundary and tie: state that a TTL expiring exactly as the holder releases is resolved by the ownership token (the stale release is a no-op), and name the worst-case batch duration the TTL must exceed.

### Major: `in_flight` is a non-terminal state with no reset path, and `next_attempt_at` is never advanced
File: app/webhooks/delivery.py — `_claim_batch` (`row.status = "in_flight"`), `deliver`
What is wrong: `_claim_batch` flips rows to `in_flight` and only `_finish` moves them out, on the two paths inside `deliver`; any worker crash, restart, deploy, `DetachedInstanceError`, IntegrityError, or `asyncio.CancelledError` leaves rows in `in_flight` forever, and `_claim_batch` selects only `status == "pending"`, so nothing reclaims them — meanwhile `next_attempt_at` is written once at enqueue and never updated, so the persisted schedule carries no information about the retry state (R38 clause 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: A single deploy during a batch silently and permanently drops up to 100 customer deliveries with no alert, and because the retry loop lives entirely in process memory, everything already attempted is lost with it.
Fix: Give the transient state a bounded exit: record `claimed_at` when flipping to `in_flight`, and extend `_claim_batch`'s predicate to also reclaim `status == 'in_flight' AND claimed_at < now() - INTERVAL '<lease>'`, incrementing `attempts` on reclaim so a wedged row still terminates at `MAX_ATTEMPTS`; add the `claimed_at` column to `migrations/0042_webhook_delivery.sql` alongside an index on `(status, next_attempt_at)`. Pair this with persisting the retry schedule (see the `time.sleep` finding) so a restart resumes from the database rather than losing in-memory state. Preserve the working path — a delivery that succeeds on its first attempt must still go straight to `delivered` with `attempts = 1` and never be reclaimed, so pin that ALLOW side with a test asserting a freshly delivered row is not returned by a subsequent `_claim_batch`. Red-prove each clause separately: (i) remove the reclaim predicate and confirm a test that marks a row `in_flight` with an old `claimed_at` and asserts it is re-claimed reds; (ii) remove the `attempts` increment on reclaim and confirm a test asserting a repeatedly abandoned row reaches `failed_permanent` reds (this also proves the reclaim terminates rather than looping forever); (iii) shorten the lease below the request timeout and confirm a test asserting an actively-in-flight row is *not* reclaimed reds. Fail loudly: a row whose `attempts` already exceeds `MAX_ATTEMPTS` when reclaimed must be finished as `failed_permanent` with a named reason, not re-queued. Boundary and tie: state that the lease boundary is `claimed_at <= now - lease` inclusive, that the lease must exceed `REQUEST_TIMEOUT` plus the longest backoff so a live attempt is never double-claimed, and how two workers reclaiming the same row at the same instant are resolved (the `SKIP LOCKED` claim, or the compare-and-set on `status`).

### Major: `asyncio.gather` without `return_exceptions` kills the worker on the first failed delivery
File: app/webhooks/delivery.py — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` re-raises the first exception, and `deliver` only catches `httpx.HTTPError`, so any other exception — the `DetachedInstanceError` and the `failed_permanent` IntegrityError above, a JSON serialization error, a `None` endpoint — propagates out of `run_worker` and terminates the loop, while the sibling coroutines are left running unawaited.
What breaks in production: One malformed payload or one deleted endpoint stops the entire webhook worker for every customer until someone notices the process is gone, with the rest of the batch stranded in `in_flight`.
