### Critical: `list_deliveries` has no tenancy filter — any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: The query filters only on the path parameter `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while every sibling route in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) scopes by `user.org_id`.
What breaks in production: Any logged-in customer can enumerate `endpoint_id` and read other tenants' delivery rows — event type, delivery status, and the response status of another organization's private billing events — a cross-tenant data breach reachable with a single incrementing integer.
Fix: Join and filter in the query, not after it: `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and raise `HTTPException(404)` when the endpoint id does not resolve inside the caller's org (404 not 403, so the route does not confirm existence to a prober). Deny side and allow side both pinned by test: `test_list_deliveries_rejects_another_orgs_endpoint` (org B's endpoint id → 404, and **assert the response body is empty**, not merely that the status is 404) and `test_list_deliveries_returns_own_org_deliveries` (org A's own endpoint still returns its rows, same count as before the change) — the second is what stops the fix from degenerating into "deny everything". Red-prove each clause separately by execution: (i) delete the `WebhookEndpoint.org_id == user.org_id` clause and confirm only the cross-tenant test reddens; (ii) change the raise to `403` and confirm only the status assertion reddens. Fail loudly when the check cannot run: if `user.org_id` is `None` the handler must raise, never fall through to an unfiltered query. Boundary and tie: an endpoint whose `org_id` equals the caller's is *in* (allowed); an endpoint id that exists in no org and one that exists in another org must produce the identical 404 body so the two cases are indistinguishable. Preserve: the route must keep returning the same rows, in the same order, for the legitimate owner.

### Critical: the unique index on `event_id` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the unique constraint on `event_id` alone rejects every row after the first whenever an org has more than one active endpoint.
What breaks in production: The `session.add_all` flush raises `IntegrityError`, the dispatcher swallows it as a `log.warning`, and **no** endpoint receives the event — the first customer to register a second webhook silently stops receiving all webhooks, including `invoice.payment_failed`.
Fix: Change the index to the composite that matches the row's actual identity — `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — which preserves the property the current index was reaching for (idempotency: one delivery per endpoint per event, which is what the doc's "deduplicate on `event_id`" needs) while allowing fan-out. Pair the deny side with the allow side in tests: `test_enqueue_is_idempotent_for_the_same_endpoint_and_event` (second enqueue of the same `(endpoint_id, event_id)` inserts 0 rows) **and** `test_enqueue_fans_out_to_every_active_endpoint` (two endpoints → two rows, both persisted and readable after commit) — the allow test is the one this defect would have failed. Red-prove separately: (i) revert the index to `(event_id)` and confirm only the fan-out test reddens; (ii) drop the index entirely and confirm only the idempotency test reddens. Fail loudly: `enqueue_for_event` must not report success on an `IntegrityError` — see the swallowed-exception finding below; a constraint violation must surface, not be spelled the same as "nothing to enqueue". Boundary and tie: two endpoints of the *same* org subscribing to the *same* event type are the exact tie this index decides, and after the fix both must get a row.

### Critical: the persisted status vocabulary disagrees with the DB CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` `STATUSES`
What is wrong: The application writes `"failed_permanent"` and the model's `STATUSES` tuple declares `"failed_permanent"`, but the migration's CHECK permits `"failed"` — the same enum is spelled three times, in three places, and one of them disagrees.
What breaks in production: Every delivery that exhausts `MAX_ATTEMPTS` raises `CheckViolation` inside `_finish`, the transaction rolls back, the row is left in `in_flight` forever, and the exception escapes `deliver` → `asyncio.gather` → `run_worker`, killing the delivery worker for all tenants.
Fix: Make one place authoritative and derive the others: keep `STATUSES` in `app/webhooks/models.py` as the single source, generate the CHECK from it in the migration (`CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`), and add a test that reads the CHECK's allowed set out of the live schema and asserts set-equality with `models.STATUSES` so a future divergence cannot merge. Preserve the constraint itself — do not "fix" this by dropping the CHECK, which is what made the mismatch visible. Deny and allow: `test_status_check_rejects_an_unknown_status` (writing `"weird"` raises) **and** `test_each_declared_status_is_writable` (a loop over `models.STATUSES` writes and commits each one) — the second is the direction this defect broke. Red-prove separately by execution: (i) add a bogus member to `STATUSES` and confirm only the set-equality test reddens; (ii) remove `'failed_permanent'` from the CHECK and confirm only the writable-status test reddens. Fail loudly: if the schema-introspection query returns no CHECK for the column, the test must **fail**, not skip — "no constraint found" must not be spelled the same as "constraint matches". Boundary and tie: `String(20)` must remain wide enough for the longest member (`failed_permanent`, 16 chars); assert `max(len(s) for s in STATUSES) <= 20` in the same test so a longer future status is caught at the boundary rather than truncated at write time.

### Critical: the HMAC is computed over a different byte string than the one actually sent
File: `app/webhooks/signing.py` — `sign` / `serialize`, consumed by `app/webhooks/delivery.py` `send_once`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` (sorted keys, default `", "` / `": "` separators) while `send_once` transmits `client.post(..., json=delivery.payload)`, whose body httpx serializes in insertion order with its own separators — so the signature never matches an HMAC over the raw request body, which is what `docs/webhooks.md` tells every receiver to compute.
What breaks in production: Every customer who implements the documented verification rejects 100% of our deliveries as forged; the failure is total and silent on our side because we only ever record the receiver's HTTP status, and our own tests mock both halves so nothing round-trips (R40's "same team owns both sides" trap).
Fix: Sign the exact bytes that go on the wire — build the body once (`body = signing.serialize(delivery.payload).encode()`), MAC that buffer, and send it with `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` instead of `json=`; delete the second serialization so there is only one producer of the bytes. Add the round-trip test R40 requires: capture `request.content` from the `MockTransport` handler and assert `signing.verify_raw(SECRET, captured_body, captured_headers[SIGNATURE_HEADER])` — actual producer output through the actual verifier, never two independently constructed strings. Deny and allow: `test_signature_verifies_against_the_bytes_actually_sent` (allow) **and** `test_signature_fails_when_one_body_byte_is_flipped` (deny). Red-prove separately: (i) restore `json=delivery.payload` and confirm only the round-trip test reddens; (ii) flip a byte in the captured body inside the deny test and confirm only that assertion reddens. Fail loudly: if the transport captured no body, the test must fail rather than pass on a vacuous `None`. Boundary and tie: fix the serialization to a canonical form (`sort_keys=True, separators=(",", ":"), ensure_ascii=False`) and state it in the doc, so two payloads that are equal as dicts produce byte-identical bodies and therefore identical signatures. Preserve: the payload the receiver sees must stay semantically identical — this is a serialization change, not a payload change.

### Critical: the timestamp is emitted but not covered by the signature, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`, `verify`
What is wrong: `sign` returns `timestamp` alongside the MAC but computes the MAC over the payload only, while `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`; `verify` proves the gap — it recomputes with a *fresh* timestamp and still matches, which is only possible because the timestamp is not an input.
What breaks in production: An attacker who captures one delivery can replay it indefinitely with any `X-Acme-Timestamp` they choose, because the header they must forge is not authenticated — the five-minute freshness rule we tell customers to rely on stops nothing.
Fix: Bind the timestamp into the MAC exactly as documented — `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` — and change `verify` to take the timestamp and the raw body as explicit arguments (`verify(secret, timestamp, body, signature)`) so a caller structurally cannot verify without supplying the timestamp that was signed. Deny and allow: `test_verify_accepts_the_timestamp_and_body_that_were_signed` (allow) and `test_verify_rejects_a_swapped_timestamp` (same body, timestamp incremented by one → rejected) — plus `test_verify_rejects_a_timestamp_outside_the_tolerance`. Red-prove each separately by execution: (i) drop the `f"{timestamp}."` prefix and confirm only the swapped-timestamp test reddens; (ii) widen the tolerance to infinity and confirm only the tolerance test reddens. Fail loudly: a missing or non-numeric `X-Acme-Timestamp` must raise a named rejection, never be coerced to `0` or skipped — "no timestamp supplied" must not be spelled the same as "timestamp fresh". Boundary and tie: state the tolerance boundary explicitly — a delivery whose timestamp is *exactly* 300 seconds old is accepted, 301 is rejected, and clock skew in the future is bounded symmetrically (a timestamp more than 300s ahead is rejected); document that boundary in `docs/webhooks.md` beside the rule.

### Critical: `verify` compares signatures with `==`, not a constant-time primitive
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The signature comparison uses Python's short-circuiting `str.__eq__`, whose running time depends on the length of the matching prefix, where `hmac.compare_digest` exists in the module already imported (`hmac`).
What breaks in production: A caller that uses this helper to authenticate *inbound* signed traffic leaks the expected MAC one byte at a time under timing measurement, letting an attacker forge a valid signature without the secret; the helper is exported and documented as the verification primitive, so its first inbound consumer inherits the flaw.
Fix: Replace the comparison with `hmac.compare_digest(expected, signature)` — the module is already imported, so no new dependency — and keep both operands as `str` of equal charset (or encode both to `bytes`) since `compare_digest` raises on mixed types. Deny and allow: `test_verify_accepts_a_valid_signature` must still pass unchanged (this is the direction a constant-time swap most often breaks, via a type error), and `test_verify_rejects_a_signature_made_with_another_secret` must still fail closed. Red-prove separately: (i) revert to `==` and confirm a grep-based lint gate (`check-timing-safe`) reddens on the line; (ii) pass a `bytes` signature into `verify` and confirm the added type-normalisation test reddens rather than the function silently returning `False`. Fail loudly: `verify` must raise a named error on a `None` or non-string signature rather than returning `False`, because "malformed input" and "wrong signature" are different outcomes and only one of them should be logged as an attack. Boundary and tie: signatures of *different lengths* must still take the deny path without early return — `compare_digest` handles this, but assert it with a short-signature case so the length side channel is pinned too.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random.choice` draws from the Mersenne Twister, a fully predictable PRNG whose internal state is recoverable from a modest run of outputs, and it is being used to mint the HMAC key that is the entire authenticity guarantee of the webhook channel.
What breaks in production: An attacker who registers a handful of endpoints of their own recovers the generator state from their own secrets and then predicts every other tenant's signing secret, letting them forge `invoice.paid` events into any customer's receiver — a total compromise of the feature's security model.
Fix: Use `secrets.token_urlsafe(SECRET_BYTES)` (or `secrets.choice` over `_ALPHABET`) and delete the `random` import so the weak primitive cannot be reached from this module; rename `SECRET_BYTES` to match its meaning (it is currently a *character* count, see the test finding below) or switch to a genuine byte count. Deny and allow: keep the existing prefix/format test passing (`secret.startswith(SECRET_PREFIX)` and the documented length) — that is the property the fix must preserve — and add `test_two_secrets_are_never_equal` plus `test_secret_has_at_least_128_bits_of_entropy` (assert alphabet size and length satisfy the floor). Red-prove separately by execution: (i) replace the generator with a constant and confirm only the uniqueness test reddens; (ii) shorten the length below the floor and confirm only the entropy test reddens; (iii) re-introduce `import random` and confirm a module-level import gate reddens. Fail loudly: if `secrets` is unavailable the module must fail to import, never fall back to `random` — a silent downgrade is exactly how this defect ships twice. Boundary and tie: state the entropy floor as an explicit constant (128 bits) and assert the *computed* entropy `length * log2(len(alphabet))` is `>=` it, so a value sitting exactly on the boundary is admitted and one below is refused.

### Critical: no destination validation on registered URLs, and the deliverer follows redirects — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check is `parsed.scheme.startswith("http") and parsed.netloc`, with no block on loopback, link-local, or RFC1918 destinations, and the worker follows redirects, so even an allowlisted host can bounce the request to an internal address.
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or any internal service), our worker POSTs to it from inside the VPC, and `_finish` writes the response status — and the full response body — into `webhook_deliveries`, from where the customer reads it back via the deliveries route; cloud credentials and internal service data exfiltrate through a feature working exactly as coded.
Fix: Validate the destination at the boundary and again at connect time, because DNS can rebind between them: at registration, require `scheme == "https"` (exact match, not `startswith`), resolve the host and reject any address in a loopback / link-local / private / reserved range via `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved`; at delivery, set `follow_redirects=False` and re-apply the same address check through a custom transport or a pinned-IP connection. Deny and allow: `test_registration_rejects_a_private_destination` (`http://127.0.0.1`, `https://10.0.0.1`, `https://169.254.169.254` → 422) **and** `test_registration_accepts_a_public_https_endpoint` (`https://hooks.example.com/acme` → 201) — the allow case is mandatory, since an address check that denies everything satisfies every deny test. Red-prove each separately: (i) remove the private-range predicate and confirm only the private-destination test reddens; (ii) restore `follow_redirects=True` and confirm only the redirect test (a 302 to `http://127.0.0.1` must not be followed) reddens. Fail loudly: when DNS resolution fails or returns no addresses, **reject** the registration with a named error — "could not resolve" must not be spelled the same as "no private address found". Boundary and tie: state the boundary on the response side too — truncate `response_body` (see below) and, for a host resolving to *both* a public and a private address, reject; the tie must resolve to deny.

### Critical: `time.sleep` inside an `async def` blocks the whole worker event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered across a batch of up to `BATCH_SIZE = 100` deliveries, but its retry backoff uses the blocking `time.sleep`, freezing the event loop rather than yielding it.
What breaks in production: A single unreachable customer endpoint stalls the entire delivery worker for up to 30 seconds per delivery (2+4+8+16), the 60-second Redis lock expires while the loop is frozen so a second worker starts double-sending, and every other tenant's webhooks queue behind one broken receiver.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (`asyncio` is already imported in this module), and — because in-process retry loops are the wrong shape here at all — persist the retry instead: on a retryable failure write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` via `_finish` and **return**, letting the next poll pick it up, so a worker restart does not lose the attempt count or re-run from zero. Deny and allow: `test_a_retryable_failure_reschedules_rather_than_blocking` (asserts the row comes back `pending` with `attempts == 1` and `next_attempt_at` advanced) **and** `test_a_2xx_still_marks_delivered_on_the_first_attempt` — the second pins the success path the reschedule must not disturb. Red-prove separately by execution: (i) restore `time.sleep` and confirm a test asserting the coroutine yields (measured via a concurrently scheduled task incrementing a counter) reddens; (ii) drop the `next_attempt_at` advance and confirm only the reschedule test's timing assertion reddens. Fail loudly: if `_finish` cannot write the reschedule, the exception must propagate to a handler that logs and leaves the row reclaimable, never be swallowed into a lost delivery. Boundary and tie: define the boundary at `attempt == MAX_ATTEMPTS` — the 5th attempt is the last and produces `failed_permanent` with no further sleep; two deliveries with the same `next_attempt_at` must both be claimable in the same batch (see the ordering finding).

### Major: `in_flight` is a non-terminal state with no reclaim path, and one exception kills the worker permanently
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `run_worker` (`await asyncio.gather(*[deliver(client, d) for d in batch])`)
What is wrong: Rows are moved into `in_flight` and are only ever moved out by `_finish` on a completed `deliver`, while `gather` is called without `return_exceptions=True` and the loop body has no `except`, so any single failure — a deleted endpoint making `session.get` return `None`, the CHECK violation above, a `DetachedInstanceError` — propagates out of `run_worker` and stops the process (R38 non-terminal transient state).
What breaks in production: The worker exits, every row it had claimed is stranded in `in_flight` where `_claim_batch`'s `status == "pending"` filter will never see it again, and those deliveries are lost forever with no alert, no retry, and no operator affordance to release them.
Fix: Give the transient state both a failure exit and a bounded timeout: pass `return_exceptions=True` to `gather` and, for each returned exception, call `_finish(delivery.id, "pending", attempt, None, str(exc))` with `next_attempt_at` advanced so the row is reclaimable; add a `claimed_at` column and have `_claim_batch` also select rows `status == "in_flight" AND claimed_at < now - LEASE_TIMEOUT` so a killed process's rows self-heal; wrap the whole `while True` body in a `try/except Exception` that logs and continues rather than exiting. Deny and allow: `test_a_crashed_delivery_leaves_the_row_reclaimable` (raise from `deliver`, then assert the next `_claim_batch` returns that row) **and** `test_a_healthy_batch_still_completes_and_is_not_reclaimed` (a delivered row must *not* be re-picked by the lease sweep) — the second is what stops the reclaim from re-sending delivered webhooks. Red-prove separately: (i) remove `return_exceptions=True` and confirm only the crashed-delivery test reddens; (ii) remove the lease-timeout clause from `_claim_batch` and confirm only the stranded-row test reddens; (iii) mark a row `delivered` and confirm the healthy-batch test reddens if the sweep's status predicate is dropped. Fail loudly: the `except` must log at ERROR with the delivery id and increment a failure counter — a continuing loop that logs nothing is indistinguishable from a healthy one. Boundary and tie: state the lease boundary — a row claimed *exactly* `LEASE_TIMEOUT` ago is reclaimable, and `LEASE_TIMEOUT` must exceed the maximum in-flight time (`REQUEST_TIMEOUT`, 30s) so a slow-but-live delivery is never double-claimed.

### Major: the Redis lock is neither atomic to acquire nor safe to release
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `get` then a separate `set` then a separate `expire`, so two workers can both observe an empty key and both proceed (TOCTOU across a read-then-write, R5), and a crash between `set` and `expire` leaves a lock with no TTL; the `finally` deletes `LOCK_KEY` unconditionally, including a lock some *other* worker acquired after ours expired mid-batch.
What breaks in production: Two workers claim overlapping batches and customers receive duplicate webhooks, or — after an unlucky crash — the TTL-less lock is never released and webhook delivery stops entirely across the fleet with no expiry to heal it.
Fix: Make acquisition a single atomic command with the TTL inline and a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete a lock it still owns. Deny and allow: `test_a_second_worker_cannot_acquire_a_held_lock` (deny) **and** `test_the_lock_is_acquirable_again_after_release` plus `test_the_lock_is_acquirable_after_its_ttl_expires` (allow) — the allow pair is what prevents the fix from wedging delivery permanently, which is the failure mode the current `finally` was reaching for. Red-prove each separately by execution: (i) replace `nx=True` with an unconditional `set` and confirm only the second-worker test reddens; (ii) drop `ex=LOCK_TTL` and confirm only the TTL-expiry test reddens; (iii) revert the release to an unconditional `delete` and confirm only the ownership test (worker A's stale release must not clear worker B's lock) reddens. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise rather than return `True` — an unavailable coordinator must stop the worker, not silently license unsynchronised delivery. Boundary and tie: `LOCK_TTL` must exceed the worst-case batch time after the blocking-sleep fix above, and when two workers race the `SET NX` the tie is resolved by Redis — exactly one wins and the loser must sleep, never proceed.

### Major: `list_webhook_endpoints` returns every endpoint's signing secret, contradicting the documented guarantee
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py` `list_webhook_endpoints`
What is wrong: `to_dict` embeds the signing secret and is used by both the create route (where the secret is intended) and the list route, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation).
What breaks in production: Every HMAC key in the org is retrievable on a plain `GET`, so it lands in browser caches, proxy logs, support screenshots and any lower-privileged org member's session — and customers who followed our doc's advice believe the key's only copy is in their secret manager, so a leak here is one they will not think to rotate.
Fix: Split the serializers — `to_dict()` omits `signing_secret`, and a separate `to_dict_with_secret()` is called *only* from `create_webhook_endpoint`; add a rotation route (`POST /webhook-endpoints/{id}/rotate-secret`) so the doc's "cannot be read back" is survivable, and correct the doc if any read-back is retained. Deny and allow: `test_list_endpoints_never_returns_the_signing_secret` (assert the key is absent from every element, not merely that the status is 200) **and** `test_create_endpoint_returns_the_signing_secret_exactly_once` — the second preserves the behaviour that makes the feature usable at all and is what a blanket redaction would break. Red-prove separately: (i) re-add `signing_secret` to `to_dict` and confirm only the list test reddens; (ii) point the create route at `to_dict()` and confirm only the create test reddens. Fail loudly: the omission must be by explicit field list, not by a `pop` on a shared dict — if a future column is added, the serializer must default to *not* exposing it. Boundary and tie: state the boundary on rotation — after a rotate, both the old and new secret verify for a stated overlap window (or neither does, if we choose hard cutover), and say which in the doc so receivers know what happens to in-flight deliveries signed with the old key.

### Major: every delivery logs its signature header at INFO
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: The whole header dict, including `X-Acme-Signature` and `X-Acme-Timestamp`, is written to the application log on every single delivery attempt.
What breaks in production: Logs are shipped, indexed and read by people with no access to the webhook data, and each line carries a *valid* signature for a known payload — anyone with log read access can replay a genuine `invoice.paid` into the customer's receiver, at a volume of one line per delivery attempt.
Fix: Log only the fields that aid debugging — `log.info("POST %s delivery=%s attempt=%s", endpoint.url, delivery.id, attempt)` — and drop the header dict entirely; if header-level debugging is needed, log the header *names* only, never their values. Deny and allow: `test_delivery_log_does_not_contain_the_signature` (capture with `caplog`, assert the signature value is absent) **and** `test_delivery_log_still_identifies_the_endpoint_and_delivery` — the second names the behaviour the fix must preserve, so the remedy is not "delete the log line". Red-prove separately: (i) restore `headers=%s` and confirm only the absence test reddens; (ii) remove the delivery id from the format string and confirm only the identification test reddens. Fail loudly: the redaction must be at the call site, not a log-processor filter downstream — a filter that fails open leaves the secret material in the record, and "filter not configured" must not be spelled the same as "nothing sensitive logged". Boundary and tie: the same rule applies to `_finish`'s `detail` argument, which currently carries `response.text` into the DB — see the next finding; state that no value derived from a secret ever crosses into a log or a stored column.

### Major: the documented retry policy is not the implemented one
File: `docs/webhooks.md` — "Retries" section, vs `app/webhooks/delivery.py` `deliver` / `backoff_for`
What is wrong: The doc promises "exponential with jitter" (`backoff_for` has no jitter — it is deterministic `2**attempt`) and "a 4xx is permanent and we stop immediately" (`deliver` retries *every* non-2xx, including 400 and 410, through all 5 attempts), so two load-bearing statements about our own control are false (R29 / R49).
What breaks in production: Deterministic backoff synchronises every pending delivery to the same receiver into a thundering herd after an outage, and hammering a receiver that already answered 400 five times burns its rate limits and ours while never succeeding.
Fix: Implement what the doc says rather than weakening the doc: add full jitter (`random.uniform(0, 2**attempt)` — using `secrets`-independent randomness is fine here, this is not key material) and classify the response before retrying — `4xx` other than `408` and `429` goes straight to `failed_permanent`; `5xx`, `408`, `429`, timeouts and connection errors retry.
