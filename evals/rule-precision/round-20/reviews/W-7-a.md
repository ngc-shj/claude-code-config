### Critical: signing secrets are generated from `random`, not a CSPRNG
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, which is the Mersenne Twister seeded from predictable state and is not cryptographically secure, so an attacker who observes a few secrets (or the process start time) can reconstruct the generator and derive every other tenant's secret.
What breaks in production: An attacker can forge `X-Acme-Signature` for any customer endpoint and inject fabricated `invoice.paid` events, which downstream billing systems will treat as authentic.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and `import secrets` in place of `import random`/`import string`, deleting `_ALPHABET` outright rather than leaving it unreferenced (R1 clause d). Rename `SECRET_BYTES` in the same edit or keep it at 32 and note it is now genuinely 32 bytes of entropy, since `token_urlsafe(32)` returns 43 characters — update `test_new_signing_secret_has_prefix_and_length` to assert `len(secret) >= len(SECRET_PREFIX) + 43` and, separately, that 1000 generated secrets are all distinct. Still must succeed: an existing stored secret of the old shape must keep verifying, so do not add a format check in `verify` — only generation changes. Red-proof each clause separately by execution: (i) revert to `random.choice` and confirm the new "two processes seeded with `random.seed(0)` produce different secrets" test reddens; (ii) drop the `SECRET_PREFIX` concatenation and confirm the prefix assertion reddens; (iii) return a fixed string and confirm the distinctness assertion reddens. Fails loudly: if `secrets` is unavailable the import raises at module load rather than falling back to `random` — never wrap it in a `try/except ImportError`. Preserve: the `whsec_` prefix and the fact that the value is URL-safe ASCII, since customers store it verbatim. Boundary: at exactly `SECRET_BYTES` bytes the secret is accepted; two endpoints that somehow collide on a secret are not deduplicated and must not be — the uniqueness assertion is about the generator, not a DB constraint.

### Critical: `verify` compares signatures with `==` (RS1)
File: app/webhooks/signing.py — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses Python's short-circuiting `str.__eq__` instead of `hmac.compare_digest`, so the time to reject leaks the length of the matching prefix.
What breaks in production: This is the function the change ships as the reference verifier (and `docs/webhooks.md` instructs customers to "compare it against your own computation using a constant-time comparison" — the shipped code does the opposite), so any service that adopts it is byte-by-byte brute-forceable over a few thousand requests.
Fix: `return hmac.compare_digest(expected, signature)`. Because `compare_digest` raises `TypeError` on a non-ASCII `str`, coerce both sides with `.encode()` first and let a non-`str` `signature` argument raise rather than returning `False`. Still must succeed: `test_verify_accepts_signature_produced_by_sign` must stay green — a valid signature still verifies. Red-proof separately: (i) mutate to `==` and confirm a new timing-shape test (compare rejection times for a signature sharing a 60-char prefix vs. a signature differing at index 0, over 2000 iterations, asserting the medians are within tolerance) reddens; (ii) mutate to `return True` and confirm the wrong-secret test reddens; (iii) pass `signature=None` and confirm the call raises rather than silently returning `False`. Fails loudly: an empty or absent `signature` must raise or return `False` through an explicit branch that logs the reason — "no signature supplied" must not be spelled the same as "signature mismatched". Preserve: the function's `(secret, payload, signature) -> bool` shape, since the tests and the docs both depend on it. Boundary: two signatures of unequal length must take the same path as equal-length mismatches — `compare_digest` already handles this; do not add a fast-path length check in front of it.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: app/api/routes/settings.py — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate any other organization's deliveries by incrementing the integer id. Cross-cutting evidence: the two sibling handlers in the same file, `list_api_keys` and the newly added `list_webhook_endpoints`, both filter on `user.org_id` — this is the one new read path where the equivalent change was not made (R3/R18 shape).
What breaks in production: A tenant learns which events another tenant emits, at what volume, with what event ids and delivery outcomes — a cross-tenant data leak that also contradicts the promise in `docs/webhooks.md` that the endpoint returns attempts "for an endpoint belonging to your organization".
Fix: Change the query to `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and raise `HTTPException(404)` — not 403 — when a lookup of the endpoint under the caller's org returns `None`, so the response does not confirm the id exists. Still must succeed: a member of the owning org listing their own endpoint's deliveries still receives the same rows in the same order — pin that with a test that seeds two orgs and asserts the owner sees exactly its N rows. Red-proof separately: (i) delete the `org_id` predicate and confirm the cross-tenant test (org B requests org A's endpoint id, expects 404 and an empty body) reddens; (ii) change the 404 to a 403 and confirm an existence-disclosure assertion reddens; (iii) delete the `endpoint_id` predicate and confirm the owner-sees-only-this-endpoint assertion reddens. Fails loudly: when `user.org_id` is `None` the handler must raise, not fall through to an unfiltered query. Preserve: the `limit`/`created_at desc` ordering and the `to_dict` response shape, which the docs describe. Boundary: an endpoint id that exists but belongs to another org and one that does not exist at all must both return 404 with an identical body; a delivery row whose endpoint was hard-deleted is not reachable by either tenant.

### Critical: `WebhookEndpoint.to_dict` returns the signing secret on every read
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`

Red-proof separately: (i) re-add the key to `to_dict` and confirm a `"signing_secret" not in body` assertion on the list endpoint reddens; (ii) drop the merge in the create handler and confirm the 201 assertion reddens; (iii) add a third serializer path that calls `to_dict` and confirm a repo-wide assertion that no GET response body contains `whsec_` reddens. Fails loudly: if the create handler cannot obtain the generated secret it must raise rather than return a 201 without it — an endpoint the customer cannot verify against is worse than a failed creation. Preserve: the `id`/`url`/`event_types`/`active` fields, which the settings UI reads. Boundary: an endpoint created before this change still has a stored secret and must remain usable; this fix changes disclosure, not storage — a rotation endpoint is a separate follow-up, not part of this fix.

### Critical: outbound deliveries are an unauthenticated SSRF primitive
File: app/webhooks/delivery.py — `run_worker`'s `httpx.AsyncClient(..., follow_redirects=True)` together with app/api/routes/settings.py `create_webhook_endpoint`
What is wrong: Any authenticated customer can register `http://169.254.169.254/latest/meta-data/` or an internal hostname (the only check is `parsed.scheme.startswith("http") and parsed.netloc`), and the worker will POST to it from inside the production network with redirects followed, so even a URL that passes a public-address check at registration can bounce to a private one at delivery time.
What breaks in production: A customer reads cloud instance metadata, internal admin endpoints, or unauthenticated internal services through our worker, and observes the result via `list_deliveries`' stored `response_status`.
Fix: Add an allowlist-shaped validator in `app/webhooks/signing.py`'s sibling module (or a new `app/webhooks/urls.py`) that (a) requires `scheme == "https"` by exact equality, (b) resolves the hostname and rejects any address in a private, loopback, link-local, unique-local, or reserved range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`, and (c) rejects userinfo and non-default ports outside {443}; call it from `create_webhook_endpoint`. Set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with the reason recorded. Pin the DNS result used for the connection to the address that was validated (`httpx` transport with a resolved-IP host header, or re-validate in an event hook) so the check is on the object the request uses, not on a name re-resolved later. Still must succeed: `https://hooks.example.com/acme` — the URL in `docs/webhooks.md` and in the tests' `FakeEndpoint` — must still register and still deliver; pin that as an explicit allow test. Red-proof separately: (i) `http://hooks.example.com` must 422 (mutate the scheme check to `startswith` and confirm it reddens); (ii) `https://127.0.0.1/x` must 422 (remove the range check and confirm it reddens); (iii) an endpoint that 302s to `http://169.254.169.254/` must be recorded `failed_permanent` with no second request issued (flip `follow_redirects=True` and confirm the "exactly one request was made" assertion reddens). Fails loudly: when DNS resolution fails or returns no addresses, registration must 422 with "hostname could not be resolved" — an unresolvable host must not be spelled the same as an allowed one. Preserve: the ability to deliver to any legitimate public HTTPS endpoint, including one behind a CDN with multiple A records — validate every returned address, not just the first. Boundary: an address exactly at the edge of a reserved block (`100.64.0.0` for CGNAT, `::ffff:127.0.0.1` as an IPv4-mapped IPv6) is rejected; a host resolving to both a public and a private address is rejected, not partially allowed.

### Critical: the signature does not cover what the docs say it covers, or the bytes actually sent
File: app/webhooks/signing.py — `sign`; app/webhooks/delivery.py — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` and nothing else, while `docs/webhooks.md` states the signature is "the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`" — the timestamp is not in the MAC at all, and `send_once` transmits `client.post(..., json=delivery.payload)`, whose httpx encoding (insertion order, `", "`/`": "` separators) differs byte-for-byte from `serialize`'s sorted, compact-free output (R40: producer wire shape vs. the consumer contract the docs publish).
What breaks in production: Every customer who implements the documented verification computes a different digest and rejects 100% of our webhooks, and because the timestamp is unauthenticated, the five-minute replay window the docs promise stops nothing — an attacker replays a captured body with a fresh `X-Acme-Timestamp` and the signature still validates.
Fix: Make the signed bytes the transmitted bytes. Have `serialize` remain the single encoder, have `send_once` compute `body = serialize(delivery.payload).encode()` once and pass `content=body` (not `json=`), and change `sign` to accept those bytes and MAC `f"{timestamp}.".encode() + body`. Add a `verify(secret, timestamp, body, signature, tolerance_seconds=300)` overload that recomputes over the caller-supplied timestamp and rejects when `abs(now - int(timestamp)) > tolerance_seconds`. Update `docs/webhooks.md` only if the code cannot be made to match it — the docs describe the correct scheme, so the code moves. Still must succeed: a body signed and immediately verified with the correct secret verifies (`verify` at `now` returns True), and `test_send_once_posts_the_signed_payload`'s `content-type: application/json` assertion still holds — set the header explicitly since `content=` no longer sets it. Red-proof separately: (i) drop the timestamp from the MAC input and confirm a "signature changes when only the timestamp changes" test reddens; (ii) revert `send_once` to `json=` and confirm a "HMAC over the exact `request.content` captured by the MockTransport equals the sent signature" test reddens; (iii) set the timestamp to `now - 301` and confirm the tolerance test reddens, then `now - 299` and confirm it stays green. Fails loudly: a `timestamp` header that is absent or not an integer must raise/return False through a distinct branch, never be coerced to 0. Preserve: `sort_keys=True`, since dropping it makes the digest depend on dict insertion order across Python versions. Boundary: a timestamp exactly `tolerance_seconds` old is accepted and `tolerance_seconds + 1` is rejected; a clock exactly at the signing second is accepted, and future timestamps are bounded by the same tolerance in the other direction.

### Critical: the unique index on `event_id` makes multi-endpoint orgs receive nothing
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so the second row of any org with two subscribed endpoints violates the constraint and the whole `session.add_all` transaction rolls back.
What breaks in production: An org with two endpoints receives zero webhooks rather than two, and the failure is invisible because `dispatch` swallows the exception into a `log.warning` — the customer sees silence, not an error.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);`. Since the migration is not yet released, edit it in place rather than adding 0043; if it has shipped anywhere, add a follow-up migration that drops and recreates inside the same transaction. Still must succeed: re-enqueuing the same `(endpoint_id, event_id)` — the retry-after-crash case the index exists to guard — must still be rejected exactly once; pin that with an integration test asserting `IntegrityError` on the duplicate pair. Red-proof separately: (i) drop the index entirely and confirm the duplicate-pair test reddens; (ii) revert to `(event_id)` and confirm a new "one event, two active endpoints, two rows persisted" test reddens; (iii) insert the same event for two different orgs' endpoints and confirm both persist. Fails loudly: `enqueue_for_event` must catch `IntegrityError` on the unique pair and log it at INFO as an idempotent skip, while any other `IntegrityError` re-raises — "already enqueued" must not be spelled the same as "the insert was malformed". Preserve: the index's idempotency purpose, which `docs/webhooks.md` leans on ("delivery is at-least-once, so deduplicate on `event_id`") — note that the doc line should say deduplicate on `(endpoint, event_id)`, since the receiver only ever sees one endpoint. Boundary: two endpoints of the same org on the same event produce two rows; the same endpoint re-enqueued for the same event produces one, and the second attempt is a no-op rather than an error.

Red-proof separately: (i) revert one member of the CHECK and confirm the parity test reddens; (ii) add a fifth member to `STATUSES` without touching the SQL and confirm it reddens from the other direction; (iii) insert `'bogus'` and confirm the reject assertion reddens if the CHECK is dropped. Preserve: `failed_permanent` as the spelling — it is what `docs/webhooks.md`'s retry section describes and what any operator dashboard will be built on; do not "fix" the code down to `failed`. ### Critical: the worker uses detached ORM instances after their session has closed
File: app/webhooks/delivery.py — `_claim_batch` (returns `rows` after the `with session_scope()` block) and `deliver` (reads `endpoint.signing_secret`, `endpoint.url`, `delivery.payload`, `delivery.attempts` outside any session)
What is wrong: Both functions return or hold SQLAlchemy instances past the end of their `session_scope()`; on a session with the default `expire_on_commit=True`, every attribute read after commit triggers a refresh on a closed session and raises `DetachedInstanceError`.
What breaks in production: The worker raises on the first attribute access of the first delivery, `asyncio.gather` propagates it out of `run_worker`, the process exits, and no webhook is ever delivered — while the rows it already flipped to `in_flight` are permanently unclaimable.
Fix: Stop passing ORM objects across the session boundary. Have `_claim_batch` return a list of plain dataclasses (`ClaimedDelivery(id, endpoint_id, event_id, payload, attempts)`) built inside the session, and have `deliver` load `endpoint.url` and `endpoint.signing_secret` into a `SignedTarget` dataclass inside its own short session before the first request. Alternatively set `expire_on_commit=False` on the worker's sessions — but that is the weaker fix, because it leaves the code reading through instances whose identity map is gone. Still must succeed: `send_once` must keep accepting any object exposing `.url`/`.signing_secret` so `tests/webhooks/test_delivery.py::FakeEndpoint` continues to work; type the parameter as a `Protocol` rather than the concrete model. Red-proof separately: (i) revert `_claim_batch` to returning ORM rows and confirm an integration test that claims a batch against a real session and reads `.payload` reddens with `DetachedInstanceError`; (ii) remove the eager load of `signing_secret` and confirm the same test reddens at the signing step; (iii) claim a batch, delete the endpoint, and confirm the delivery is finished as `failed_permanent` rather than raising. Fails loudly: `session.get(WebhookEndpoint, ...)` returning `None` in `deliver` must finish the delivery `failed_permanent` with a named reason, not raise `AttributeError` (see the `_finish` Minor below for the same defect on the delivery row). Preserve: the batching behaviour — the fix must not turn one query per batch into one query per delivery; load the endpoints for the whole batch with a single `IN` query. Boundary: a delivery whose endpoint was deactivated between claim and send is still sent (it was claimed under the active predicate) unless the product decides otherwise — state which, and pin it; a delivery whose endpoint row is gone is terminal, not retried.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: app/webhooks/delivery.py — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather`, but its backoff uses the blocking `time.sleep`, which stops the loop rather than yielding — and the module already imports `asyncio` and uses `await asyncio.sleep(poll_interval)` correctly in `run_worker`, so the correct primitive is present in the same file (R1/R3: the pattern exists and was not propagated to this call site).
What breaks in production: A single failing endpoint freezes the whole worker process for up to 2+4+8+16 = 30 seconds of backoff plus up to 5×30 s of request timeouts, so a batch of 100 deliveries serializes instead of running concurrently and every other coroutine in that process — including the Redis lock refresh — stalls.
Fix: `await asyncio.sleep(delay)`. Still must succeed: the delay must remain observable — a test that patches `asyncio.sleep` and asserts it was awaited with `2, 4, 8, 16` in order for a permanently-failing endpoint pins both that the backoff still happens and that it is now awaitable. Red-proof separately: (i) revert to `time.sleep` and confirm a "two `deliver` coroutines for two slow endpoints complete in roughly max(t1,t2), not t1+t2" test reddens; (ii) delete the sleep entirely and confirm the awaited-delays assertion reddens; (iii) set `MAX_ATTEMPTS = 1` and confirm no sleep is awaited at all. Fails loudly: if the delay is computed as non-finite or negative (`backoff_for` on a negative attempt) the function must raise rather than sleep forever — bound `delay` to a `MAX_DELAY_SECONDS` ceiling and log when clamped. Preserve: the total elapsed retry envelope the docs advertise ("roughly 2s, 4s, 8s, 16s") — this fix changes who blocks, not how long the endpoint waits. Boundary: `attempt == MAX_ATTEMPTS` finishes without sleeping at all (the current code already returns before the sleep — keep that ordering); `attempt == MAX_ATTEMPTS - 1` sleeps once more.

What is wrong: `startswith("http")` admits `http`, and also `httpz://`, `httpfoo://` and any other scheme with that prefix, while `docs/webhooks.md` states "Only `https://` URLs are accepted" (RS3 — the boundary check is weaker than the contract it publishes; R29 — the doc claims a control the code does not implement).

Fails loudly: a URL `urlparse` cannot parse must 422 with the reason, not fall through as an empty scheme. ### Major: the Redis lock is non-atomic and is released by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does GET-then-SET-then-EXPIRE as three round trips, so two workers can both observe the key absent and both proceed (TOCTOU), and the unconditional `delete` in `finally` removes the key regardless of who owns it — with a 60 s TTL that is shorter than one batch's worst case (5 attempts × 30 s `REQUEST_TIMEOUT` + 30 s backoff), expiry mid-batch is the normal case, not the edge case.
What breaks in production: Two workers claim and deliver the same batch, so customers receive duplicate events, and the second worker's lock is deleted by the first worker's `finally`, cascading into a third.
Fix: Replace `_acquire_lock` with a single atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex`, returning the token or `None`. Release with the standard compare-and-delete Lua script (`if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`) passing the token. Set `LOCK_TTL_SECONDS` from the batch's worst case rather than a magic 60, and renew it between deliveries. Still must succeed: a single worker must still acquire, run, and release — assert the key is gone after a clean run and that the same worker can immediately re-acquire. Red-proof separately: (i) revert to GET-then-SET and confirm a test that fires two `_acquire_lock` calls concurrently against a real Redis and asserts exactly one returns a token reddens; (ii) revert the release to an unconditional `delete` and confirm a "worker A's stale release does not remove worker B's lock" test reddens; (iii) set the TTL below the batch duration and confirm a "lock is still held at the end of a long batch" assertion reddens. Fails loudly: if Redis is unreachable, `_acquire_lock` must raise and the worker must back off, never return `True` — a lock manager that cannot be consulted must not be read as "lock is free". Preserve: the single-worker-at-a-time invariant and the poll-interval sleep when the lock is held. Boundary: at exactly the TTL the lock is considered expired and another worker may take it, so the renewal must fire strictly before that; two workers presenting the same token is impossible by construction and must not be handled by "delete anyway".

### Major: `in_flight` has no exit path, and the retry loop bypasses the scheduler columns it was given
File: app/webhooks/delivery.py — `_claim_batch` (`row.status = "in_flight"`), `deliver`'s `while True` loop, and the unused `next_attempt_at`/`attempts` columns
What is wrong: A row is flipped to `in_flight` and only ever leaves that state through `_finish` at the end of a single in-process loop; a crash, restart, deploy, or the `_finish` CheckViolation above leaves it `in_flight` forever, and `_claim_batch`'s `status == "pending"` predicate means nothing reclaims it (R38 mode 1 — a transient state with no failure exit and no timeout). The schema already provides `attempts` and `next_attempt_at` for exactly this, and `backoff_for` already computes the schedule — the loop reimplements scheduling in memory instead of persisting it.
What breaks in production: Every worker restart silently strands whatever was in flight, and because `attempts` is written only once at the very end, a process killed on attempt 4 loses all record of the prior three.
Fix: Make `deliver` perform exactly one attempt: on 2xx set `delivered`; on a retryable failure with `attempts + 1 < MAX_ATTEMPTS` write `status="pending"`, `attempts=attempt`, `next_attempt_at = now + backoff_for(attempt)`; otherwise `failed_permanent`. Change `_claim_batch`'s predicate to `status == PENDING OR (status == IN_FLIGHT AND updated_at < now - CLAIM_TIMEOUT)` and set `updated_at` at claim time, so a stranded row is reclaimed after a bounded interval.
