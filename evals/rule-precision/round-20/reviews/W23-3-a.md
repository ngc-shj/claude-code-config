### Critical: `list_deliveries` has no tenancy predicate — any authenticated user can read any organization's delivery history
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query is scoped only by the caller-supplied `endpoint_id` and never joins back to `WebhookEndpoint.org_id == user.org_id`, while its sibling `list_webhook_endpoints` added in the same file *does* carry that predicate — the tenancy pattern was propagated to one of the two new read routes (R3, security-relevant).
What breaks in production: Any authenticated tenant can enumerate `endpoint_id` values and read another organization's `event_type`, `status`, `attempts`, `response_status` and delivery timestamps, disclosing when competitors' invoices are paid and which of their endpoints are failing.
Fix: Join the delivery query to `WebhookEndpoint` and filter `WebhookEndpoint.org_id == user.org_id` in the same statement (`session.query(WebhookDelivery).join(WebhookEndpoint, WebhookDelivery.endpoint_id == WebhookEndpoint.id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`), rather than a two-step fetch-then-check, so there is no interval between the ownership read and the data read. **Deny side**: a caller requesting an `endpoint_id` owned by another org gets 404 (not 403 — 403 confirms the id exists and is itself a cross-tenant oracle). **Allow side that must still succeed**: the owning org's caller still receives the full, unfiltered, `created_at DESC`-ordered page for its own endpoint — pin this with a fixture asserting the returned id list is byte-identical to the pre-change response, so a fix that always denies does not pass. **Boundary and tie**: an `endpoint_id` that does not exist at all and one that exists in another org must return the *same* 404 body; an endpoint whose owning org row was deleted (org `ON DELETE CASCADE` removes the endpoint) yields an empty join and therefore 404, not a 500. **Fail loudly**: if `user.org_id` is `None` or unresolvable, raise 401 rather than falling through to an unfiltered query — "could not determine the tenant" must not be spelled the same as "no rows". **Preserve**: keep the `limit` parameter and the descending order; do not "fix" this by deleting the route. **Red-prove separately, by execution**: (1) delete the `org_id` filter → the cross-tenant fixture returns rows and reds; (2) delete the `endpoint_id` filter → the wrong-endpoint fixture reds; (3) replace the 404 with 403 → the oracle-parity assertion reds. Three mutations, three distinct assertions.

### Critical: `UNIQUE INDEX ... (event_id)` makes every organization with two or more endpoints receive zero webhooks
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row *per matching endpoint* for a single `event_id`, so the second row of every fan-out violates the unique index and aborts the whole `session.add_all` flush.
What breaks in production: An org with two subscribed endpoints gets no deliveries at all — not one, zero — because the flush rolls back the entire batch, and the `except Exception: log.warning` in `dispatch` swallows the `IntegrityError` so nothing alerts.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint actually wanted: at most one delivery row per (endpoint, event) so a re-dispatch of the same event does not double-send. **Allow side that must still succeed**: an org with N≥2 active endpoints produces exactly N rows for one event — assert `enqueue_for_event` returns N and that N rows are readable afterwards; a fix that drops the uniqueness entirely would pass a "2 rows inserted" check, so also assert that calling `enqueue_for_event` twice with the same `event_id` still yields N rows, not 2N. **Boundary and tie**: N=1 (single endpoint) must behave exactly as today, and the duplicate-enqueue case must surface as a handled `IntegrityError`/`ON CONFLICT DO NOTHING` on the composite key, not as a swallowed batch abort. **Fail loudly**: the flush must not be wrapped in a bare `except` — a constraint violation the code did not anticipate has to propagate, because "inserted nothing" and "inserted everything" currently read identically to the caller. **Preserve**: the index still has to prevent the duplicate-send this constraint was added for; do not fix by deleting the unique index. **Red-prove separately**: (1) revert to `(event_id)` → the two-endpoint fan-out test reds; (2) drop the index → the double-enqueue idempotency test reds.

### Critical: migration `CHECK` constraint rejects the status the code actually writes on the failure path
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` `STATUSES`
What is wrong: The status vocabulary is written out three times — `models.STATUSES` (`failed_permanent`), the `_finish` call site (`failed_permanent`), and the SQL `CHECK` (`failed`) — and the SQL copy diverges (R2, R3).
What breaks in production: The very first delivery that exhausts `MAX_ATTEMPTS` raises `CheckViolation` at commit inside the worker, so an endpoint outage escalates into a crashed delivery worker and the row is left stuck in `in_flight`.
Fix: Change the `CHECK` list to `('pending', 'in_flight', 'delivered', 'failed_permanent')` and make `models.STATUSES` the single source by giving the column `String(20)` an explicit `Enum`/`CheckConstraint` generated from `STATUSES` — `STATUSES` is declared in the diff and currently consulted by nothing, which is why the drift was invisible. **Allow side that must still succeed**: a delivery that succeeds still commits with `status='delivered'`, and one exhausting attempts commits with `status='failed_permanent'` — assert both round-trip through a real database, not a mock, since the constraint lives only in the database. **Boundary and tie**: `attempts == MAX_ATTEMPTS` is the terminal case (the code writes `failed_permanent` when `attempt >= MAX_ATTEMPTS`, so attempt 5 is the last send, not the first skip) — pin the exact attempt count on the terminal row. **Fail loudly**: add a startup or migration-test assertion comparing the database's `CHECK` clause to `models.STATUSES` and failing with a named error when they differ, so a future divergence is reported rather than discovered by a crash. **Preserve**: keep the constraint — do not fix by dropping the `CHECK`, which is what made this drift detectable at all. **Red-prove separately**: (1) revert the `CHECK` to `'failed'` → the exhausted-attempts round-trip test reds; (2) add a bogus member to `STATUSES` → the schema/vocabulary parity test reds.

### Critical: the bytes signed are not the bytes sent, so no receiver can ever verify a signature
File: `app/webhooks/delivery.py` — `send_once`, the `sign(...)` / `client.post(..., json=delivery.payload)` pair
What is wrong: `sign` computes the HMAC over `serialize(payload)` = `json.dumps(payload, sort_keys=True)` (spaced separators, sorted keys) while the request body is produced independently by httpx's `json=` encoder (compact separators, insertion order), so the signed preimage and the transmitted body are different byte strings for any payload with more than one key (R40 — producer wire shape vs strict consumer, with the added twist that `serialize` is a helper the diff already provides and `send_once` bypasses).
What breaks in production: Every customer following `docs/webhooks.md` computes the HMAC over the raw body they received, gets a mismatch, and rejects 100% of our webhooks — a total-path failure that no test in this diff can see because `test_send_once_posts_the_signed_payload` only asserts the header *starts with* `sha256=`.
Fix: Build the body once and sign exactly that: have `send_once` call `body = serialize(delivery.payload).encode()`, pass it as `client.post(endpoint.url, content=body, headers=...)` with an explicit `Content-Type: application/json`, and have `sign` accept those bytes rather than a `dict`. Change `verify(secret, payload: dict, ...)` to `verify(secret, body: bytes, timestamp: str, signature: str)` for the same reason — a verifier that re-serializes a parsed dict cannot reproduce a third party's raw bytes either. **Allow side that must still succeed**: a payload the service legitimately emits (nested dicts, non-ASCII strings, integers) still POSTs successfully with a signature that an *independent* verifier — one that reads `request.content` and recomputes the MAC without calling `sign` — accepts. **Boundary and tie**: pin the exact serialization contract in the docs and the test (sorted keys, UTF-8, and whether `ensure_ascii` is on), because two payloads that differ only in key order must produce the same bytes and therefore the same signature. **Fail loudly**: if the payload is not JSON-serializable, the delivery must fail with a named permanent error rather than an unhandled `TypeError` inside `asyncio.gather`. **Preserve**: the request must still be valid JSON with the `application/json` content type — do not fix by dropping the `json=` convenience and forgetting the header. **Red-prove separately**: (1) revert to `json=delivery.payload` → the independent-verifier test on a two-key payload reds; (2) change `serialize` to drop `sort_keys` → the key-order-invariance test reds; (3) mutate one byte of the body after signing → the verifier test reds.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window cannot be enforced
File: `app/webhooks/signing.py` — `sign`, `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but the implementation MACs the body alone and ships the timestamp as an unauthenticated sibling header (R29 — the doc claim is stronger than the implementation; R49 — a control claimed as a replay defence that is not one).
What breaks in production: An attacker who captures one delivery can replay it indefinitely by rewriting `X-Acme-Timestamp` to the current second — the signature still validates — so the five-minute window the docs tell customers to rely on stops nothing, and a captured `invoice.paid` can be re-delivered for as long as the endpoint's secret lives.
Fix: Make the preimage `f"{timestamp}.".encode() + body` exactly as documented, and have `verify` take the timestamp as a parameter, recompute over the same concatenation, and reject when `abs(now - int(timestamp)) > 300` *before* comparing digests. **Allow side that must still succeed**: a freshly signed request verifies — assert `verify` accepts a request signed 0 seconds ago and one signed 299 seconds ago, so a fix that always rejects does not pass. **Boundary and tie**: state which side 300 falls on (reject at exactly 300, accept at 299), and reject a non-numeric or absent timestamp rather than coercing it — an unparseable timestamp must deny, not default to `0` or to `now`. **Fail loudly**: a missing `X-Acme-Timestamp` is a named `MissingTimestamp` rejection, distinct from a signature mismatch, so "no timestamp to check" is not spelled the same as "timestamp checked and fine". **Preserve**: the header names and the `sha256=` prefix are the customer-visible contract and must not change silently; if they do, the docs and the version note change with them. **Red-prove separately**: (1) drop the timestamp from the preimage → a test that alters only the timestamp header and expects rejection reds; (2) remove the freshness check → the 301-seconds-old fixture reds; (3) invert the boundary to `>=` / `>` → the exactly-300 fixture reds.

### Critical: signing secrets are generated with `random`, not a cryptographic RNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The HMAC key is drawn from the Mersenne Twister, whose internal state is fully recoverable from 624 consecutive 32-bit outputs and which is seeded per-process from system time in many deployments.
What breaks in production: An attacker who registers a handful of webhook endpoints observes a long run of the same generator's output, recovers its state, and predicts every other tenant's signing secret — at which point they can forge signed `invoice.paid` webhooks into any customer's endpoint.
Fix: Replace with `secrets.token_urlsafe(32)` (or `secrets.choice` over `_ALPHABET` if the alphabet is a compatibility requirement), and rename `SECRET_BYTES` to `SECRET_CHARS` or make it mean bytes — today it is a character count fed to a per-character loop, so the name understates nothing but misleads a future reader raising it. Every secret already issued was generated by this generator and must be rotated, not merely fixed forward. **Allow side that must still succeed**: `new_signing_secret()` still returns a `whsec_`-prefixed string of the documented length that `sign`/`verify` round-trip, so the fix does not break existing parsing. **Boundary and tie**: state the minimum entropy the fix guarantees (≥128 bits) and assert it structurally — `len(alphabet) ** n_chars >= 2**128` — rather than trusting the character count. **Fail loudly**: `secrets` raises if the OS entropy source is unavailable; do not wrap it in a fallback to `random`, since a silent downgrade is exactly this defect again. **Preserve**: the prefix and the length assertion the existing test relies on. **Red-prove separately**: (1) revert to `random.choice` with a fixed `random.seed(0)` → a test asserting two secrets generated after identical seeding differ reds (the current test cannot fail here — it passes for `SECRET_PREFIX + "a"*32`); (2) shorten the secret → the entropy-floor assertion reds.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: A MAC is compared with Python's short-circuiting string equality instead of `hmac.compare_digest` (RS1).
What breaks in production: The comparison leaks the length of the matching prefix through timing, letting an attacker who can drive repeated verifications recover a valid signature byte by byte without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands normalized to `str` (or both to `bytes`) beforehand, since `compare_digest` raises on mixed types. **Allow side that must still succeed**: a correct signature still returns `True` — the existing `test_verify_accepts_signature_produced_by_sign` covers this only tautologically (it compares `sign`'s output against `sign`'s output), so add an assertion against a digest computed independently from the documented preimage. **Boundary and tie**: a signature of the wrong *length* must return `False` and not raise; `compare_digest` is length-leaking by design, so the fix must not be described as closing the length channel. **Fail loudly**: a `signature` that is `None` or non-string returns `False` via an explicit type guard, not via an exception that a caller might catch as "verification unavailable". **Preserve**: `verify` must keep rejecting a signature made with a different secret — the one property the current tests do pin. **Red-prove separately**: (1) revert to `==` → a mutation test asserting `compare_digest` is on the call path reds (an execution-time assertion, since timing itself is not testable per RT2); (2) remove the type guard → the `None`-signature fixture reds.

### Critical: `list_webhook_endpoints` returns every endpoint's signing secret, contradicting the documented "cannot be read back"
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py` `list_webhook_endpoints`
What is wrong: The secret was put into the *shared* serializer to satisfy the create route's one-time-display need, so the list route inherits it, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (RS4 — a committed artifact path exposing live credential material; R49 — a claim stronger than the implementation).
What breaks in production: Any token, session, or log capture with read access to `GET /v1/settings/webhook-endpoints` yields every one of that org's live HMAC keys, and customers who built on the documented guarantee treated the read scope as non-sensitive.
Fix: Remove `signing_secret` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` construct its 201 body explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable, so the secret has exactly one egress point. Because the current build already served secrets on a read route, treat previously issued secrets as exposed and add a rotate endpoint. **Allow side that must still succeed**: the create response still contains the secret exactly once — assert its presence there and its absence from the list response in the same test, so a fix that strips it everywhere does not pass. **Boundary and tie**: an endpoint created and then immediately listed must show the same `id` and `url` with no `signing_secret` key at all (absent, not `null` — a `null` still tells a client the field exists and invites a later reintroduction). **Fail loudly**: add a response-schema test that fails when any route's serialized output contains a `whsec_`-prefixed value, so a future serializer that reintroduces it is reported by name rather than shipped. **Preserve**: the one-time display is the feature — do not fix by removing the secret from the create response too. **Red-prove separately**: (1) re-add the key to `to_dict` → the list-response assertion reds; (2) remove it from the create body → the one-time-display assertion reds; (3) plant a `whsec_` string in an unrelated route's response → the schema sweep reds.

### Critical: the worker uses ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` returning `rows` from inside `with session_scope()`, and `deliver`'s `endpoint = session.get(...)` used after the `with` block
What is wrong: Both functions return or retain SQLAlchemy instances past the end of their session scope; with the default `expire_on_commit=True` every attribute read afterwards (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret`, `endpoint.url`) triggers a refresh on a closed session and raises `DetachedInstanceError`.
What breaks in production: The first delivery of the first batch raises, the exception escapes `asyncio.gather` inside `run_worker`'s `try`, the `finally` drops the lock, and the exception propagates out of the `while True` loop — the worker process exits and no webhook is ever delivered.
Fix: Have `_claim_batch` return plain immutable value objects — a frozen dataclass carrying `(id, endpoint_id, payload, attempts)` — materialized inside the session, and have `deliver` load the endpoint's `url` and `signing_secret` into the same kind of value object inside its own `with` block before using them; alternatively configure `session_scope`'s sessionmaker with `expire_on_commit=False`, but the value object is preferable because it also stops the worker from holding rows across the network call. **Allow side that must still succeed**: a claimed batch still delivers end-to-end against a real session (not the `FakeDelivery` stand-in), and the values read post-session equal the values written pre-session — assert field-by-field. **Boundary and tie**: an empty batch must return `[]` and take the `if not batch: await asyncio.sleep(...)` path rather than raising; a delivery whose endpoint row was deleted between claim and send must resolve to a named skip, not `None.signing_secret`. **Fail loudly**: wrap the `gather` in a handler that logs the failing `delivery_id` and continues the loop, so a single bad row is a reported skip rather than a silent worker death — "the worker stopped" must not be spelled the same as "there was nothing to do". **Preserve**: the batch claim must still flip rows to `in_flight` inside the transaction, which is what stops a second worker re-claiming them. **Red-prove separately**: (1) return the ORM rows again → the post-session attribute-read test reds against a real session; (2) delete the endpoint row mid-flight → the named-skip test reds; (3) raise from one delivery in a batch of three → the "other two still delivered" assertion reds.

### Critical: `time.sleep` inside an `async def` blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: The retry backoff uses the blocking `time.sleep` inside a coroutine that `run_worker` schedules through `asyncio.gather`, so the sleep halts the loop rather than yielding it.
What breaks in production: One endpoint timing out freezes every other delivery in the batch for the full 2+4+8+16 = 30 s backoff chain, and a batch of 100 failing deliveries wedges the loop for roughly 50 minutes — during which the 60 s Redis lock expires and a second worker starts re-delivering the same rows.
Fix: `await asyncio.sleep(delay)`. Since `deliver` is already a coroutine this is a one-token change, but it must be paired with a concurrency bound: replace the unbounded `asyncio.gather(*[deliver(...) for d in batch])` over `BATCH_SIZE = 100` with a `asyncio.Semaphore`-gated gather so a full batch cannot open 100 simultaneous outbound connections. **Allow side that must still succeed**: a delivery that succeeds on the first attempt still completes without any sleep at all — assert the fast path does not await the backoff, so a fix that sleeps unconditionally does not pass. **Boundary and tie**: two deliveries scheduled to retry at the same instant must both proceed (the semaphore admits them in some order, neither is dropped); state the semaphore's bound explicitly rather than leaving it at `BATCH_SIZE`. **Fail loudly**: if the loop is not running when `deliver` is called, that is a programming error and must raise, not silently fall back to blocking sleep. **Preserve**: the delays themselves — the fix is to yield during them, not to shorten or remove them. **Red-prove separately**: (1) revert to `time.sleep` → a test asserting a second coroutine makes progress during a retry backoff reds; (2) remove the semaphore → the max-in-flight assertion reds.

### Critical: registered URLs are never checked against internal address space, and the delivery client follows redirects
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only validation is a scheme prefix test and a non-empty netloc, so any tenant can register `http://169.254.169.254/…`, `http://127.0.0.1:6379/`, or an internal hostname, and even a public-looking host can 302 the signed request into the same places because redirects are followed unconditionally (RS3 — boundary validation whose value reaches an outbound request sink).
What breaks in production: The worker issues attacker-controlled POSTs from inside the production network to cloud metadata endpoints and internal services, and stores the response text in `webhook_deliveries.response_body`, turning the delivery pipeline into a full SSRF read primitive.
Fix: Validate at the route boundary with a positive check — `parsed.scheme == "https"` (equality, not `startswith`, which today admits `httpfoo://`) — then resolve the hostname and reject when any resolved address is loopback, link-local, private, unique-local, multicast, or reserved (`ipaddress.ip_address(addr).is_global` is the single predicate); reject IP-literal hosts and non-default ports outside an allowlist. Set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with a message naming the redirect target, since a redirect defeats any check made at registration time. Because DNS can be re-pointed after registration, re-run the address check at send time against the address actually connected to (a pinning transport or a resolve-then-connect step), not only at registration. **Allow side that must still succeed**: a legitimate public HTTPS endpoint on port 443 still registers and still receives deliveries — pin one, or the fix reduces to "reject everything". **Boundary and tie**: name the disposition of a hostname resolving to *both* a public and a private address (reject — any private answer is disqualifying) and of IPv6-mapped IPv4 literals such as `::ffff:127.0.0.1`. **Fail loudly**: DNS resolution failure at registration is a 422 naming the unresolvable host, and resolution failure at send time is a retryable delivery error — neither may fall through to "no private address found, proceed". **Preserve**: the endpoint must still be able to reach ordinary customer hosts, including those behind CDNs with many A records. **Red-prove separately**: (1) point a fixture at `127.0.0.1` → the registration test reds; (2) set `follow_redirects=True` → the 302-to-loopback test reds; (3) revert `==` to `startswith` → the `httpfoo://` fixture reds; (4) skip the send-time re-check → the DNS-rebinding fixture reds.

### Critical: the Redis lock is non-atomic, loses its TTL on a crash, and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get`-then-`set` is a check-then-act race, `set` and `expire` are two round trips so a crash between them leaves a key with no TTL, and the `finally` deletes `LOCK_KEY` without proving the deleting worker still owns it (R38 — a persisted state with no reset path).
What breaks in production: A crash in the one-instruction window between `set` and `expire` stops all webhook delivery permanently and silently — every subsequent `_acquire_lock` returns `False` forever with no alarm and no operator-visible exit — and in the ordinary case two workers acquire concurrently, or worker A's `finally` deletes worker B's lock after A's 60 s TTL lapsed during the ~30 s of retry backoff the same function performs.
Fix: Acquire with a single atomic `SET LOCK_KEY <uuid> NX EX 60` and treat a falsy reply as "not acquired"; release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) keyed on that same uuid; and extend the TTL periodically while a batch is in flight, since `deliver`'s in-process retry chain can exceed 60 s by design. **Allow side that must still succeed**: a single worker still acquires on the first try and still releases so the next poll re-acquires — assert two sequential iterations both acquire, or a fix that never releases passes every deny-side check. **Boundary and tie**: two workers calling `_acquire_lock` at the same instant — exactly one must get `True` and the other `False`, and the loser must not release; state what happens when the TTL expires while a batch is genuinely still running (the renewal must have refreshed it; if it did not, the stale owner's compare-and-delete must be a no-op). **Fail loudly**: a Redis connection error must raise a named error that stops the iteration, not be caught into "lock not acquired" — a Redis outage would otherwise present as a quiet, indefinite delivery stop indistinguishable from an idle queue. **Preserve**: single-flight execution is the property being bought; do not fix by removing the lock. **Red-prove separately**: (1) revert to `get`-then-`set` → a concurrent-acquire test asserting exactly one winner reds; (2) revert to unconditional `delete` → the "B's lock survives A's release" test reds; (3) remove the TTL from the `SET` → a test asserting the key has a positive TTL immediately after acquisition reds; (4) remove the renewal → the long-batch test reds.

### Major: the dispatcher swallows every enqueue failure, so webhook loss is permanent and silent
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: The event row is committed and the enqueue runs afterwards in its own transaction, but any failure — the `IntegrityError` from the unique-index defect above, a database blip, an import error — is caught and downgraded to a warning with no retry, no dead-letter, and no counter.
What breaks in production: Events are durably recorded while their deliveries are silently never created, so a customer's missed webhook is unreconstructable from anything but a log grep, and the two Critical defects above manifest as "nothing happened" rather than as an error.
Fix: Narrow the `except` to the transient class you intend to tolerate and record the intolerable rest: on failure, write a durable marker (an `webhook_enqueue_failed` row or a `pending_enqueue` flag on the event) that a reconciliation job retries from the persisted `Event`, and increment a named metric so the failure is visible without log inspection. **Allow side that must still succeed**: a successful enqueue still returns `event_id` unchanged and creates no marker — assert the happy path is byte-identical, so a fix that always records a failure does not pass. **Boundary and tie**: an event type in `WEBHOOK_EVENT_TYPES` with zero matching endpoints must be a *success* with zero rows, distinguishable from an enqueue that failed — those two currently look the same to every observer. **Fail loudly**: `dispatch` must still return the `event_id` to its caller even when the marker is written (the event genuinely persisted), but the metric and the marker must both name the event id. **Preserve**: enqueue failure must not roll back the event — the current ordering is right, only the reporting is wrong. **Red-prove separately**: (1) make `enqueue_for_event` raise → the marker-written assertion reds; (2) restore the bare `except` → the metric assertion reds.

### Major: `in_flight` is a non-terminal state with no path back to `pending`
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish` (writes only `delivered` / `failed_permanent`)
What is wrong: A row is flipped to `in_flight` inside the claim transaction, but nothing anywhere returns it to `pending`; `_claim_batch` selects only `status == "pending"`, so any row whose `deliver` call does not reach `_finish` — worker restart, deploy, crash, an exception outside `httpx.HTTPError` — is stranded permanently (R38 clause 1: an async transition with no failure exit and no bounded timeout).
What breaks in production: A routine deploy during a batch permanently drops up to 100 deliveries, with no retry, no alert, and no way for an operator to find them other than an ad hoc SQL query.

What is wrong: `next_attempt_at` is set to the same instant for every delivery of one event's fan-out, so rows tie and the order among them is undefined; with `LIMIT 100` the cut can land inside a tie group and the rows on the far side are not claimed in a defined order across iterations (R57).
What breaks in production: Under burst enqueues the claim order is nondeterministic, which is tolerable for delivery but makes the backlog non-reproducible when debugging a stuck queue; adding `, m.WebhookDelivery.id` as a tiebreaker makes it total.
