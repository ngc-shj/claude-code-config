### Critical: the signature does not cover the timestamp, so the documented replay window is fail-open
File: `app/webhooks/signing.py` — `sign()` / `docs/webhooks.md` "Verifying the signature"
What is wrong: the doc states the MAC is over `"{timestamp}.{raw_request_body}"`, but `sign` computes `hmac.new(secret, serialize(payload))` with the timestamp excluded from the MAC input and returned only as a separate unauthenticated header.
What breaks in production: anyone who captures one delivery (from a proxy, a log, or the `log.info("POST %s headers=%s", ...)` line in `delivery.py`) replays it indefinitely by rewriting `X-Acme-Timestamp` to now — the five-minute freshness check the doc sells as the anti-replay control validates an attacker-chosen value.
Fix: change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact bytes that will be transmitted (see the next finding), return `(timestamp, body, signature)` so the caller cannot re-serialize, and make `verify(secret, timestamp, body, signature)` recompute over the same concatenation. Preserve the two-header wire format and the `sha256=` prefix — the fix must not change what receivers read, only what the digest binds. Pin the allow side: a signature produced by `sign` at timestamp T still verifies at T (byte-identical digest), so the tightening cannot be satisfied by a `verify` that always returns False. Red-prove each clause separately by execution: (i) mutate the MAC input back to `serialize(payload)` and observe the new `test_signature_binds_the_timestamp` fail on the digest assertion; (ii) mutate the transmitted timestamp by +1 second while keeping the digest and observe the verify test fail; (iii) mutate the body by one byte and observe the third assertion fail — three mutations, three distinct reddened assertions. Fail loudly rather than silently passing when the check cannot run: `verify` must raise (not return False, and not return True) when `timestamp` is absent, non-numeric, or the signature lacks the `sha256=` prefix, so "could not evaluate" is never spelled the same as "valid". Boundary and tie: state that a timestamp exactly `now - 300s` is ACCEPTED and `now - 301s` is REJECTED, and that two deliveries sharing one timestamp are independent — freshness is per-request and no dedup is implied by an equal timestamp.

### Critical: the signed bytes are not the bytes on the wire, so no receiver following the docs can ever verify a delivery
File: `app/webhooks/delivery.py` — `send_once()`, and `app/webhooks/signing.py` — `serialize()`
What is wrong: `sign` digests `json.dumps(payload, sort_keys=True)` (compact key order, default `", "` / `": "` separators) while the request body is produced independently by `client.post(..., json=delivery.payload)`, which serializes with httpx's own encoder in insertion order — the producer signs one byte string and transmits a different one (R40, cross-boundary serialization shape vs strict consumer).
What breaks in production: every customer who implements the documented "HMAC of the raw request body" check rejects 100% of deliveries as forged, and because the same team owns both sides no integration forces a round-trip, so the failure only appears as customer reports after launch.
Fix: serialize once and send those exact bytes — `body = serialize(delivery.payload).encode()`, `sign` over `body`, then `client.post(endpoint.url, content=body, headers={... "Content-Type": "application/json"})`, deleting the `json=` kwarg so a second encoder cannot exist. `serialize()` already exists in `signing.py` and is the helper the wire path is bypassing; adopt it rather than adding a new one. Preserve the JSON content type and the payload's semantic content — the fix must not drop `sort_keys`, which is what makes the digest reproducible for the receiver. Pin the allow side with a round-trip test that feeds the ACTUAL captured request bytes back through `verify` and asserts True, so a fix that merely rejects everything fails this case. Red-prove by execution, one mutation per clause: (i) restore `json=delivery.payload` and observe the round-trip assertion redden on the digest, not on the status code; (ii) drop `sort_keys=True` from `serialize` and observe the same test redden for a payload with keys inserted out of order; (iii) change `content=body` to `content=body + b" "` and observe the byte-equality assertion redden. Fail loudly when the check cannot run: if `serialize` raises on a non-JSON-serializable payload, `send_once` must mark the delivery terminally with a named reason rather than posting an unsigned or partially-signed request. Boundary and tie: an empty payload `{}` still produces a body of `b"{}"` and a real digest — the empty case must not shortcut past signing — and two deliveries with equal payloads legitimately produce equal digests at different timestamps, which is not a dedup signal.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice` over an alphabet, and `random` is the Mersenne Twister — its internal state is recoverable from a modest run of outputs, so the generator is not suitable for key material.
What breaks in production: an attacker who obtains a few secrets (their own endpoints across several orgs, or any leaked one) can predict the secrets issued to other organizations and forge signed webhook deliveries into those customers' systems, which is the exact trust the signature exists to establish.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, drop the `random` and `string` imports and `_ALPHABET` so the weak generator cannot be reached again), and rename `SECRET_BYTES` usage consistently — note the current constant names bytes but is consumed as a character count, so state which one the new code means. Preserve what made the feature usable: the `whsec_` prefix and URL-safe characters, since customers store the value in config files. Pin the allow side: a generated secret still round-trips through `sign`/`verify` and still starts with `SECRET_PREFIX`, so the fix is not satisfied by returning a constant. Red-prove each clause by execution: (i) revert to `random.choice` under a fixed `random.seed(0)` and observe a new `test_secret_is_not_reproducible_from_a_seeded_prng` (two secrets generated after identical `random.seed(0)` calls must differ) turn red; (ii) drop the prefix and observe the prefix assertion redden; (iii) shorten the length and observe the entropy-floor assertion redden — three mutations, three assertions. Note that the existing `test_new_signing_secret_has_prefix_and_length` cannot fail for this defect and must be kept, not replaced: it pins the prefix contract. Fail loudly: if `secrets` cannot produce randomness the exception must propagate out of endpoint creation and 5xx, never fall back to `random`. Boundary and tie: fix the minimum accepted secret length and say that a secret of exactly that length is valid while one byte shorter is rejected; two independently generated secrets colliding is the property the test asserts against.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: the recomputed digest is compared to the caller-supplied signature with `==`, which short-circuits on the first differing byte (RS1 — the module already imports `hmac`, so `hmac.compare_digest` is available with no new dependency and is the shared primitive being reimplemented).
What breaks in production: any consumer that adopts this helper — and it is the reference implementation the diff ships — leaks the expected digest byte-by-byte through response timing, letting an attacker forge a valid signature without the secret.
Fix: `return hmac.compare_digest(expected, signature)`, keeping both operands as `str` of equal character domain (or encode both to `bytes`) so `compare_digest` does not fall back to a non-constant-time path on mixed types. Preserve the boolean contract and the `sha256=`-prefixed comparand — do not "fix" it by comparing only the hex tail, which would drop the algorithm binding. Pin the allow side: a signature genuinely produced by `sign` must still return True (the existing `test_verify_accepts_signature_produced_by_sign` covers presence but is a tautology — see the RT1 finding — so add one asserting True against an independently computed `hmac.new(...).hexdigest()`). Red-prove by execution: (i) revert to `==` and observe the constant-time assertion (a test that asserts `verify.__code__.co_names` contains `compare_digest`, or an equivalent structural check) redden; (ii) flip the last hex character of a valid signature and observe the reject test redden if `verify` is made to return True unconditionally. Fail loudly: `compare_digest` raises `TypeError` on non-str/bytes input — let that propagate rather than wrapping it in a `return False`, so a malformed call is distinguishable from a rejected signature. Boundary and tie: a signature of the correct length differing in exactly one byte must be rejected, and one of a different length must be rejected without an early length-based return that reintroduces a timing channel.

### Critical: the delivery listing endpoint has no organization scope
File: `app/api/routes/settings.py` — `list_deliveries()`
What is wrong: the query filters on `WebhookDelivery.endpoint_id == endpoint_id` alone and never joins to `WebhookEndpoint` to confirm the endpoint belongs to `user.org_id`, so any authenticated user can enumerate any other organization's deliveries by incrementing the path id.
What breaks in production: cross-tenant disclosure of every other customer's event ids, event types, delivery outcomes and schedules — and `docs/webhooks.md` states the endpoint "returns the most recent attempts for an endpoint belonging to your organization", a claim stronger than the implementation (R49).
Fix: join and scope the query — `.join(webhook_models.WebhookEndpoint).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. Preserve the ordering, the `limit` behaviour, and the response shape; the fix must not be a blanket deny that also breaks the owner's read. Cross-cutting: `list_api_keys` and `list_webhook_endpoints` in the same file both filter on `user.org_id`; `list_deliveries` is the one missed location of that pattern (R3). Pin the allow side explicitly: a user reading deliveries for an endpoint their own org owns still receives all matching rows in the same order — this case must be asserted, or a fix that always 404s satisfies every other clause. Red-prove each clause by execution: (i) delete the `org_id` predicate and observe the cross-tenant test (org B requesting org A's endpoint id) go from 404 to 200; (ii) delete the `endpoint_id` predicate and observe the same-org test return another endpoint's rows; (iii) change the 404 to a 403 and observe the existence-disclosure assertion redden. Fail loudly: when `user.org_id` is None or unresolvable the handler must raise rather than fall through to an unscoped query. Boundary and tie: a delivery whose endpoint was reassigned between orgs is scoped by the endpoint's CURRENT `org_id`, and where two deliveries share `created_at` the ordering is undefined — pair the `desc()` with `WebhookDelivery.id.desc()` (see R57 below).

### Critical: the signing secret is returned on every endpoint list request
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, consumed by `list_webhook_endpoints()` in `app/api/routes/settings.py`
What is wrong: `to_dict()` includes `"signing_secret"` and is used both by the creation response (where the doc intends it) and by the list endpoint, so `GET /v1/settings/webhook-endpoints` hands the secret back on demand, directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: any credential with read access to settings — a read-only API key, a support tool, a cached HTTP response, a browser devtools log — yields every endpoint's signing secret, collapsing the signature to a shared value the reader can forge with.
Fix: remove `"signing_secret"` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the single site that is allowed to disclose it. Codebase awareness: one serializer is currently serving two different trust levels, which is why the leak is invisible at the call site; splitting the disclosure to the creation handler makes every future reader of `to_dict()` safe by default. Preserve the create-time disclosure — the doc's contract depends on the secret being returned exactly once, so a fix that removes it everywhere breaks the feature. Pin the allow side: the 201 response from `create_webhook_endpoint` still contains a `signing_secret` matching the persisted row. Red-prove each clause by execution: (i) re-add `"signing_secret"` to `to_dict()` and observe a `test_list_endpoints_never_returns_the_secret` assertion (`"signing_secret" not in body[0]`) redden; (ii) remove the explicit merge in the create handler and observe the create-time disclosure assertion redden — two mutations, two assertions. Fail loudly: if the create handler cannot read back the generated secret after flush it must 500 rather than return a 201 without it, since a customer who receives a 201 with no secret can never sign-verify and has no way to recover it. Boundary and tie: an endpoint created and listed in the same request cycle must still be absent the secret in the list projection.

### Critical: the migration's status CHECK constraint omits the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: `models.py` declares `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` and `deliver()` writes `"failed_permanent"`, but the DB constraint permits `'failed'` — the enum was propagated to two of the three places that encode it (R3, and R2: one value spelled in three files).
What breaks in production: the first delivery to exhaust its attempts raises a check-constraint violation at commit, the row stays `in_flight` forever, `_claim_batch` never re-selects it (it selects only `status == "pending"`), and the exception escapes `deliver` → `asyncio.gather` → `run_worker`, killing the worker for every other delivery too.
Fix: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive it from one source — generate the SQL list from `models.STATUSES`, or add a test that asserts the constraint text parsed out of the migration equals `set(models.STATUSES)`, so the third copy cannot drift again. Preserve the constraint itself: the fix is to correct the member list, not to drop the CHECK, which is what makes an unknown status visible at all. Pin the allow side: a delivery transitioning `pending → in_flight → delivered` still commits, and one transitioning to `failed_permanent` now also commits — both must be asserted, or widening the constraint to allow any text would pass. Red-prove each clause by execution: (i) revert the constraint to `'failed'` and observe the `failed_permanent` insert test raise `IntegrityError`; (ii) add a bogus member `'oops'` to `models.STATUSES` and observe the migration/model parity test redden; (iii) write `'delivered'` and confirm it still commits (the allow case) — reddening only under the first two mutations. Fail loudly: the parity test must ERROR with a named message when it cannot locate or parse the CHECK clause in the migration file, so "constraint not found" is not reported as "constraint matches". Boundary and tie: name `failed_permanent` and `delivered` as the only terminal states, and say explicitly what a row already sitting in `in_flight` from a previous deploy transitions to (see the R38 finding — it needs a reset path).

### Critical: the unique index on `event_id` alone allows only one delivery per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint with the same `event_id`, so the uniqueness constraint is on the wrong tuple — it should be `(endpoint_id, event_id)`.
What breaks in production: any organization with two or more active subscribed endpoints hits an `IntegrityError` on `session.add_all(rows)`, and because `dispatcher.dispatch` catches that with `log.warning("webhook enqueue failed ...")`, the org receives ZERO webhooks with no error surfaced to the customer or to the caller.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`. This is also the constraint that makes the doc's "delivery is at-least-once, so deduplicate on `event_id`" honest per-endpoint — preserve the uniqueness rather than dropping the index, since it is the only thing preventing a duplicate enqueue on a retried dispatch. Pin the allow side: enqueueing one event to three endpoints of one org must insert three rows and commit; re-enqueueing the same `(endpoint_id, event_id)` must still be rejected. Red-prove each clause by execution: (i) revert to the single-column index and observe the three-endpoint fan-out test raise `IntegrityError`; (ii) drop the index entirely and observe the duplicate-enqueue test insert two rows where it asserts one — two mutations, two distinct assertions. Fail loudly and separately: `dispatcher.dispatch` must stop swallowing enqueue failures into `log.warning` (see the R9 finding) — an `IntegrityError` here must be surfaced with the event id and the constraint name, because "enqueued nothing" is currently spelled the same as "enqueued successfully". Boundary and tie: a single endpoint receiving the same event twice is the tie the index resolves (second insert loses); an org with zero matching endpoints inserts zero rows and that is a success, not a failure.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker event loop
File: `app/webhooks/delivery.py` — `deliver()`, line `time.sleep(delay)`
What is wrong: the retry backoff uses the blocking `time.sleep` inside `async def deliver`, which is scheduled by `asyncio.gather` across up to `BATCH_SIZE` (100) concurrent deliveries.
What breaks in production: one failing endpoint freezes the entire event loop for up to 2+4+8+16 = 30 seconds per retry cycle, stalling all 99 other in-flight deliveries and anything else sharing that loop, and the stall compounds with the 30-second `REQUEST_TIMEOUT` so a batch can hold the loop far past the 60-second lock TTL.
Fix: `await asyncio.sleep(delay)` (`asyncio` is already imported at the top of the file — the blocking primitive is a reimplementation of the async one already in scope), and bound total in-loop retry time so a single delivery cannot occupy the batch: after a failed attempt, persist `attempts` and `next_attempt_at = _now() + backoff_for(attempt)`, set status back to `pending`, and RETURN, letting the next poll re-claim it. Preserve the retry semantics — the same five attempts with the same growing delays — the fix moves where the wait happens, it does not remove the wait. Pin the allow side: a delivery that succeeds on the first attempt still completes with zero sleeps and status `delivered`. Red-prove each clause by execution: (i) restore `time.sleep` and observe a test asserting that two concurrent `deliver` calls interleave (each records a monotonic timestamp before and after its wait; overlapping intervals) turn red; (ii) remove the `next_attempt_at` write and observe the requeue test find the row still at its old schedule; (iii) remove the `status = "pending"` write and observe the re-claim test find zero claimable rows — three mutations, three assertions. Cap the mutation's runtime so it reddens instead of hanging: run it with `BASE_DELAY_SECONDS` patched to a fraction of a second. Fail loudly: if the requeue write fails, the delivery must not silently remain `in_flight` — raise and let the worker log the delivery id. Boundary and tie: state that `attempt == MAX_ATTEMPTS` is the last attempt made (terminal, no requeue) and `attempt == MAX_ATTEMPTS - 1` still requeues, and that two deliveries computing the same `next_attempt_at` are both claimable in the same batch.

### Critical: unvalidated endpoint URL plus `follow_redirects=True` is a server-side request forgery primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, and `app/webhooks/delivery.py` — `run_worker()` `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://`, admits any scheme literally beginning with those four characters, and performs no check of the resolved address — while the delivery client follows redirects, so even a check on the registered URL would be bypassed by a `302` at delivery time (RS3/RS5: an externally supplied parameter reaching a network primitive with no whitelist).
What breaks in production: a customer registers an endpoint that redirects to `http://169.254.169.254/…` or an internal service, and the worker issues authenticated-from-inside requests to it and persists the response into `webhook_deliveries.response_body`, turning the delivery pipeline into an internal-network read primitive; the plaintext-`http` path additionally ships every signed payload unencrypted, contradicting `docs/webhooks.md` ("Only `https://` URLs are accepted") — R49.
Fix: validate with equality, not prefix — `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)` — reject URLs whose resolved addresses are private, loopback, link-local, or unspecified (`ipaddress.ip_address(...).is_private/is_loopback/is_link_local/is_reserved` over every address returned by resolution), cap the URL length, and set `follow_redirects=False` on the delivery client so a 3xx becomes a normal non-2xx failure rather than a second uncontrolled request. Because DNS can change between registration and delivery, the address check must run again at delivery time, not only at registration. Preserve what makes the feature useful: ordinary public HTTPS endpoints on non-default ports must still register and still receive deliveries — assert one, or a fix that rejects everything satisfies every other clause. Red-prove each clause separately by execution: (i) revert to `startswith("http")` and observe the `http://hooks.example.com` rejection test go from 422 to 201; (ii) remove the private-address check and observe the `https://127.0.0.1/x` test go from 422 to 201; (iii) restore `follow_redirects=True` and observe the redirect test (a MockTransport returning `302 Location: http://10.0.0.1/`) record a second request where it asserts one; (iv) remove the delivery-time re-check and observe the rebinding test (registration resolves public, delivery resolves private) deliver where it asserts a refusal. Fail loudly: when name resolution fails or returns no addresses, both registration and delivery must REFUSE with a named reason — "could not resolve" must not be spelled the same as "resolved to something safe". Boundary and tie: an address exactly at the edge of a private range (`10.255.255.255`) is rejected while the adjacent public address (`11.0.0.0`) is accepted, and a host resolving to both a public and a private address is rejected.

### Critical: the send-path test cannot detect a wrong signature or wrong signed bytes
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`
What is wrong: the send test asserts only that the signature header `.startswith("sha256=")` and re-parses the body with `json.loads` rather than comparing the raw bytes, and the verify test compares `verify`'s recomputation against `sign`'s output — two outputs of the same subject, an identity true under every implementation of the MAC (RT1 clauses (c), (d), (g)).
What breaks in production: this is the mechanism by which the timestamp-omission and the serialization mismatch above ship fully green — the suite has no contact with the property it names, so both signature defects reach customers with a passing CI.
Fix: in the send test, compute the expected digest independently in the test body — `hmac.new(SECRET.encode(), (ts + "." + captured["body"].decode()).encode(), hashlib.sha256).hexdigest()` using the timestamp read off the captured header — and assert `captured["headers"][SIGNATURE_HEADER] == "sha256=" + expected` plus `captured["body"] == signing.serialize(FakeDelivery.payload).encode()` (exact bytes, at the serialization boundary the receiver sees). Bind `FakeEndpoint`/`FakeDelivery` to the real `WebhookEndpoint`/`WebhookDelivery` types so a field added to the model fails the fixture rather than silently defaulting, and choose fixture values away from each type's zero value (`attempts = 3`, not `0`, so "the subject substituted a default" is distinguishable from "the subject used what was stored"). Preserve the existing status-code and content-type assertions — they pin real contract — and do not weaken the new byte comparison to a loose matcher. Pin the allow side: the correct implementation must still pass all four assertions unchanged. Red-prove each clause by execution: (i) drop the timestamp from the MAC input and observe the digest assertion redden; (ii) swap `content=` back to `json=` and observe the byte-equality assertion redden; (iii) change `SECRET` in `send_once`'s path and observe the digest assertion redden; (iv) add a field to `WebhookDelivery` and observe the fixture fail to construct — four mutations, four distinct failures. Fail loudly: if `captured` is empty because the transport handler never ran, the test must fail with that named cause rather than raising an opaque `KeyError` that reads as an unrelated error. Boundary and tie: assert the empty-payload case (`{}`) produces a real digest over `b"{}"`, and note that two payloads differing only in key insertion order must produce the SAME digest — that tie is what `sort_keys=True` exists to resolve.

### Major: the distributed lock is a check-then-act race and can wedge permanently with no TTL
File: `app/webhooks/delivery.py` — `_acquire_lock()`
What is wrong: `get` followed by a separate `set` is not atomic, so two workers can both observe an empty key and both acquire; and `set` followed by a separate `expire` means a crash between the two statements leaves `webhooks:dispatch:lock` with no expiry — a persisted fail-closed state with no reset path (R38).
What breaks in production: either every delivery is sent twice by two workers at once (the doc promises at-least-once, but the duplicate here is simultaneous, not a retry), or a single unlucky crash stops all webhook delivery permanently for every customer with no automatic recovery and no operator-visible signal.
Fix: make acquisition one atomic command — `await redis_client.set(LOCK_KEY, worker_id, nx=True, ex=LOCK_TTL_SECONDS)` and treat a falsy return as "not acquired"; release only if the stored value is still this worker's id (compare-and-delete), so a worker whose lease expired mid-batch cannot delete a successor's lock in its `finally`. Set `LOCK_TTL_SECONDS` above the worst-case batch duration, or renew it inside the batch loop — the current 60s is already shorter than one delivery's 5×30s timeout budget. Preserve the single-worker guarantee the lock exists to provide; the fix must not become "no lock" to dodge the wedge. Pin the allow side: a single worker with no contender still acquires on every poll and still delivers — assert it, or an `_acquire_lock` that always returns False passes the mutual-exclusion test. Red-prove each clause by execution: (i) revert to `get`-then-`set` and observe a two-task concurrent test assert both acquired where it expects one; (ii) drop `ex=` and observe the TTL assertion (`ttl(LOCK_KEY) > 0`) redden; (iii) drop the value check from the release and observe the "expired lease must not delete a successor's lock" test redden — three mutations, three assertions. Fail loudly: when the redis call raises or returns an unexpected type, `_acquire_lock` must propagate rather than return False forever, so "redis unreachable" is not silently identical to "another worker holds it". Boundary and tie: state that a lock whose TTL is exactly 0 is treated as free, and that when two workers race the loser polls again after `poll_interval` rather than proceeding unlocked.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch()` / `deliver()` / `run_worker()`
What is wrong: `_claim_batch` writes `status = "in_flight"` and commits, but the only transitions out are inside `deliver`'s in-process loop, and `_claim_batch` selects only `status == "pending"` — nothing anywhere returns an `in_flight` row to `pending` (R38 non-terminal transient state).
What breaks in production: any worker restart, deploy, OOM, unhandled exception, or the CHECK-constraint failure described above strands every row in that batch in `in_flight` permanently, so up to 100 customer events are silently never delivered and never appear as failures either.
Fix: record a claim lease — add a `claimed_at` column and reclaim rows where `status == 'in_flight' AND claimed_at < now() - LEASE_TIMEOUT` back to `pending` at the top of `_claim_batch`, incrementing `attempts` so a poison row still terminates at `MAX_ATTEMPTS` rather than looping forever. Preserve the claim itself — the fix must not be "stop writing `in_flight`", which is what prevents double-claiming. Pin the allow side: a row claimed and delivered within the lease is NOT reclaimed and stays `delivered` — assert it, or a reclaimer that resets everything on every poll satisfies the recovery test while destroying the claim. Red-prove each clause by execution: (i) remove the reclaim query and observe a test that claims a batch, simulates a worker death, and re-polls find zero claimable rows; (ii) remove the `attempts` increment and observe the poison-row test loop past `MAX_ATTEMPTS`; (iii) advance the clock to exactly the lease boundary and observe the boundary assertion — three mutations, three assertions. Fail loudly: emit a warning naming the reclaimed delivery ids and count on every reclaiming poll, so a healed run is distinguishable from an ordinary one. Boundary and tie: a row whose `claimed_at` is exactly `now - LEASE_TIMEOUT` is reclaimed (inclusive), one microsecond newer is not, and two workers racing to reclaim the same row are resolved by the same atomic claim as above.

### Major: one bad delivery kills the entire worker loop
File: `app/webhooks/delivery.py` — `run_worker()`, `await asyncio.gather(*[deliver(client, d) for d in batch])`; `deliver()` `except httpx.HTTPError`
What is wrong: `gather` is called without `return_exceptions=True`, and `deliver` catches only `httpx.HTTPError` — so any other exception (an `AttributeError` from `endpoint` being `None` after the endpoint's `ON DELETE CASCADE` fired, the CHECK-constraint `IntegrityError`, a JSON encoding failure) propagates out of `gather`, past the `finally` that releases the lock, and out of `run_worker`.
What breaks in production: the worker process exits and stays down until something restarts it, and every other delivery in the batch is abandoned mid-flight in `in_flight`, so a single malformed row halts all webhook traffic for all customers.
Fix: pass `return_exceptions=True` and iterate the results, logging each exception with its delivery id and marking that row `failed_permanent` (or requeuing it) so the batch's other 99 deliveries complete; add an explicit `if endpoint is None: _finish(delivery.id, "failed_permanent", ...)` guard in `deliver` before `send_once`, and the same `None` guard in `_finish`, whose `session.get` result is used without a check. Also wrap the `while True` body of `run_worker` in a broad handler that logs and continues rather than exiting. Preserve fail-visibility: each swallowed exception must be logged at error with the delivery id — the fix must not convert a loud crash into a silent skip. Pin the allow side: a batch of three healthy deliveries with one poisoned row still marks the three `delivered`. Red-prove each clause by execution: (i) drop `return_exceptions=True` and observe the mixed-batch test find the healthy rows still `pending`; (ii) drop the `endpoint is None` guard and observe the deleted-endpoint test raise `AttributeError`; (iii) drop the error log and observe the log-capture assertion redden — three mutations, three assertions. Fail loudly: a result that is an exception must be logged with `exc_info`, never counted as a success in any metric. Boundary and tie: a batch of exactly zero rows must not raise from `gather` and must fall through to the `poll_interval` sleep; a batch where every row raises must still release the lock exactly once.

### Major: the event row commits in a separate transaction from the webhook enqueue, and the enqueue failure is swallowed
File: `app/events/dispatcher.py` — `dispatch()`, the `try/except Exception ... log.warning` block
What is wrong: the `Event` row is committed by its own `session_scope` before `enqueue_for_event` opens a second one, and any failure of the enqueue is downgraded to a warning and the function returns the event id as if it had succeeded (R9/R5 — the write pair is not atomic, and R49 — `docs/webhooks.md` claims "delivery is at-least-once").

Replace the `except Exception` with a narrow catch that re-raises after recording the failure durably, and log at `error` with the event id and org id. Preserve the existing behaviour that in-process subscribers still run and that `dispatch` still returns the event id on success — the fix must not make a subscriber failure abort the event write. Pin the allow side: a normal `invoice.paid` dispatch still commits one event row AND N delivery rows in one transaction, and returns the event id. Red-prove each clause by execution: (i) make `enqueue_for_event` raise and observe the atomicity test find zero event rows (currently it finds one); (ii) restore the broad `except` and observe the propagation test see a returned id where it expects a raise; (iii) remove the error log and observe the log-capture assertion redden — three mutations, three assertions. Fail loudly: "enqueued zero rows because no endpoint matched" and "enqueued zero rows because the insert failed" must be distinct log lines, since `enqueue_for_event` returns `len(rows)` for both today. Boundary and tie: an org with zero active endpoints legitimately enqueues zero rows and that must remain a success; an event type outside `WEBHOOK_EVENT_TYPES` skips the enqueue entirely and that path must be asserted too.

### Major: 4xx responses are retried despite the documented contract, and there is no jitter
File: `app/webhooks/delivery.py` — `deliver()` retry loop, `backoff_for()`; `docs/webhooks.md` "Retries"
What is wrong: the doc states "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx up to `MAX_ATTEMPTS` and `backoff_for` returns a deterministic `2**attempt` — two claims stronger than the implementation (R49), with `test_backoff_grows_exponentially` pinning the jitter-free values so the divergence is codified in the suite.

Replace `test_backoff_grows_exponentially`'s exact-equality parametrization with a bounded-range assertion rather than deleting it, so the exponential growth it pins is preserved while jitter is admitted. Fail loudly: a status outside 200-599 (or a response with no status) must be treated as retryable-with-a-named-reason, not silently classified. Boundary and tie: 400 and 499 are permanent, 500 and 399 are retryable, and 429 is the named exception on the permanent side of the boundary.
