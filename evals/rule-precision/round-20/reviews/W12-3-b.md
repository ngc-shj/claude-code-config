### Critical: the signature is computed over different bytes than the ones sent
File: `app/webhooks/signing.py` — `sign()`; `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes with its own separators and key order, so the digest in `X-Acme-Signature` is not the digest of the request body the receiver actually gets.
What breaks in production: every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest, so 100% of deliveries are rejected as forged and the whole feature silently fails at the receiver.
Fix: sign and send the *same* byte string — build `body = serialize(payload).encode()` once in `send_once`, pass it as `client.post(endpoint.url, content=body, headers=headers)` (not `json=`), and have `sign()` take those bytes rather than the dict. Deny side: a test that mutates one byte of the transmitted body and asserts the receiver-side recomputation rejects it. Allow side (Remedy Floor 1): a round-trip test that feeds the *actual* `captured["body"]` from the `MockTransport` handler into an independent verifier and asserts it accepts — this is the case that must still succeed, and it is what `test_send_once_posts_the_signed_payload` currently omits. Red-prove each clause separately by execution: (a) revert `content=` to `json=` and confirm the round-trip test reddens; (b) change `sort_keys=True` to `sort_keys=False` and confirm it reddens on a payload whose insertion order differs from sorted order. Preserve (Remedy Floor 4): keep `serialize()` as the single canonical encoder — do not "fix" this by loosening the receiver-side check to compare parsed JSON. Boundary/tie (Remedy Floor 5): state that the signed string is exactly the transmitted body with no trailing newline, and that an empty payload signs `{}`.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign()` / `verify()`
What is wrong: `sign()` returns a timestamp but MACs only the payload, and `verify()` discards the timestamp entirely (`_, expected = sign(...)`), so `X-Acme-Timestamp` is attacker-mutable and `verify()` accepts a captured request of any age — contradicting `docs/webhooks.md`, which states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that the timestamp window "is what stops a captured request from being replayed".
What breaks in production: anyone who captures one delivery (from a proxy, a log, or the `log.info("POST %s headers=%s")` line in `delivery.py`) can replay it indefinitely with a freshened timestamp, re-triggering the receiver's `invoice.paid` handling forever.
Fix: MAC the concatenation the docs already specify — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, body, timestamp, signature)` to take the timestamp from the caller, recompute with it, and reject when `abs(now - int(timestamp)) > 300` before comparing. Deny side: three tests — tampered timestamp, timestamp 301s old, tampered body — each asserting `verify` returns False. Allow side (Remedy Floor 1): a timestamp at exactly 300s old with a correct MAC must still verify True, so the tightening cannot be satisfied by rejecting everything. Red-prove separately: drop the `f"{timestamp}."` prefix → tampered-timestamp test reddens; drop the age check → the 301s test reddens; keep both → the 300s allow test stays green. Fail loudly (Remedy Floor 3): a non-numeric or absent timestamp must raise/return False explicitly, not fall through to a comparison. Boundary/tie (Remedy Floor 5): 300s is inclusive-accept, 301s rejects; a future-dated timestamp beyond +300s also rejects.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, instead of `hmac.compare_digest` (RS1).
What breaks in production: an attacker with network timing access can recover a valid signature byte-by-byte and forge deliveries without knowing the signing secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` (or both to `bytes`) first so `compare_digest` cannot raise on a mixed-type input. Allow side (Remedy Floor 1): keep `test_verify_accepts_signature_produced_by_sign` green — the correct signature must still verify. Red-prove: revert to `==` and confirm a test asserting `signing.verify.__code__.co_names` contains `compare_digest` reddens (timing itself is not testably deterministic, so the pinned property is the primitive's presence, per RT5's "call path includes the production primitive"). Fail loudly (Remedy Floor 3): a `signature` of the wrong length or type must return False rather than propagate a `TypeError` into the caller's error path. Preserve: do not drop the wrong-secret rejection test while rewriting.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from system time and fully reconstructible from ~624 observed outputs, so it must never generate key material; `SECRET_BYTES = 32` also names characters, not bytes, so the constant lies about the strength it claims.
What breaks in production: an attacker who registers a handful of endpoints of their own can recover the generator state and derive every other tenant's signing secret, then forge signed events into any customer's system.
Fix: `import secrets` and return `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, renaming the constant to what it measures (`SECRET_BYTES = 32` now genuinely means 32 random bytes). Allow side (Remedy Floor 1): the existing prefix assertion must still pass; replace the exact-length assertion with `len(secret) > len(SECRET_PREFIX) + 32` so the test does not have to be deleted to accommodate base64 expansion. Red-prove: swap `secrets.token_urlsafe` back to `random.choice` and confirm a test asserting the module does not import `random` reddens; separately assert 1000 generated secrets are all distinct and confirm it reddens against a constant-returning stub. Preserve (Remedy Floor 4): keep the `whsec_` prefix — it is what lets customers identify the value in their own secret store, and `test_new_signing_secret_has_prefix_and_length` must not be weakened past the prefix check. Boundary: state that secrets are never truncated or re-encoded downstream, since `to_dict()` and the DB column are both `Text`.

### Critical: every GET of the endpoint list returns the signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, and its call site `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and `list_webhook_endpoints` reuses the same `to_dict()` as the create route, so the secret is readable back on every listing — directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards"). Cross-cutting check: `to_dict()` is the only serializer, used by both routes, so there is no second location to fix — but there is also no non-secret variant, which is what makes the leak unavoidable at the list route.
What breaks in production: the secret is exposed to every principal who can call the read endpoint, is written into API access logs, browser history, and any client-side cache, and the documented security property customers rely on is false.
Fix: make `to_dict()` secret-free and add an explicit `to_dict_with_secret()` used *only* by `create_webhook_endpoint`'s 201 response. Deny side: a test asserting `"signing_secret" not in (await client.get("/v1/settings/webhook-endpoints")).json()[0]`. Allow side (Remedy Floor 1): a paired test asserting the POST 201 body *does* still contain `signing_secret` — without it, a fix that strips the field everywhere passes the deny test and silently removes the only way a customer ever obtains the secret (Remedy Floor 4: that is the behaviour the fix must preserve). Red-prove each separately: re-add the key to `to_dict()` → list test reddens; point create at `to_dict()` → create test reddens. Boundary: state that the secret also must not appear in the deliveries listing; `WebhookDelivery.to_dict()` already excludes it and must stay that way.

### Critical: the deliveries listing has no tenant scoping
File: `app/api/routes/settings.py` — `list_deliveries()`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike its two sibling routes in the same file (`list_api_keys` and `list_webhook_endpoints`), both of which do filter on `user.org_id` — the incomplete propagation of an authorization pattern the file already establishes (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` values and read other organizations' delivery history — event types, event ids, timing and upstream response bodies — a cross-tenant data breach.
Fix: join the parent and filter on it: `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)`, and return 404 (not 403) when the join yields nothing so the route does not leak endpoint existence. Deny side (RT8): assert both the 404 status *and* that the response body is empty — a status-only assertion passes against a handler that 404s while still having read the rows. Allow side (Remedy Floor 1): the owning org must still receive its own deliveries — pin a test where `user.org_id` matches and rows come back, or a fix that returns `[]` unconditionally satisfies the deny test. Red-prove separately: remove the `org_id` filter → cross-tenant test reddens; remove the `endpoint_id` filter → a test asserting a second endpoint of the *same* org is not mixed in reddens. Boundary/tie (Remedy Floor 5): state the behaviour for an endpoint id that does not exist at all (404, same shape as the cross-tenant case, so the two are indistinguishable to the caller).

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` (`app/webhooks/delivery.py`) inserts one row per matching endpoint all carrying the same `event_id`, so the second row of any fan-out violates the unique index.
What breaks in production: for any org with two or more subscribed endpoints, `session.add_all(rows)` raises on commit, the dispatcher's blanket `except Exception` swallows it, and *no* endpoint receives the event — a silent total loss of webhook delivery for exactly the customers who configured redundancy.
Fix: change it to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — which preserves the property the index was presumably for (one delivery row per event per endpoint, i.e. the idempotency the docs' "deduplicate on `event_id`" line depends on) rather than dropping uniqueness altogether (Remedy Floor 4). Allow side (Remedy Floor 1): a test that enqueues one event for two active endpoints of one org and asserts two rows exist. Deny side: enqueue the same `(endpoint_id, event_id)` twice and assert the second insert is rejected. Red-prove separately: revert to the single-column index → the two-endpoint test reddens with an IntegrityError naming the index; drop the index entirely → the duplicate test reddens. Boundary/tie: state what happens when the same event is legitimately re-enqueued after a permanent failure — either the retry reuses the existing row (preferred) or the enqueue must be an explicit `ON CONFLICT DO NOTHING`, and say which.

### Critical: the `failed_permanent` status violates the migration's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the same status enum is written in three places that disagree — the SQL CHECK says `'failed'`, `app/webhooks/models.py::STATUSES` says `'failed_permanent'`, and `delivery.py` hardcodes bare string literals at every use site (R2: one concept, three unsynchronized copies; R3: the rename reached two of the three).
What breaks in production: the moment a delivery exhausts `MAX_ATTEMPTS`, `_finish` raises an IntegrityError inside `deliver()`, the exception escapes the `httpx.HTTPError` handler and the un-guarded `asyncio.gather`, killing the worker — and the row is left stuck in `in_flight` forever.
Fix: make the SQL the derived copy of one Python source of truth: keep `STATUSES` in `models.py`, replace every literal in `delivery.py` and `models.py`'s `default=` with a named member of it, and correct the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`. Add a test that asserts the constraint text parsed out of `migrations/0042_webhook_delivery.sql` is exactly `set(STATUSES)` — this is what stops the three copies drifting again. Deny side: a test that writes an unknown status and asserts the DB rejects it. Allow side (Remedy Floor 1): a test writing each of the four legal statuses and asserting all four commit, so a fix that tightens the CHECK to a subset cannot pass. Red-prove separately: remove one member from the SQL list → the parity test reddens naming the missing member; remove one from `STATUSES` → it reddens naming the other direction. Fail loudly (Remedy Floor 3): if the parity test cannot locate or parse the CHECK clause it must fail, not skip — "examined nothing" must not be spelled the same as "found nothing".

### Critical: endpoint URLs are accepted on a prefix match with no host policy, and redirects are followed (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the guard adjudicates the *notation* of a URL rather than the destination the HTTP client will actually reach (R47) — `startswith("http")` admits any scheme spelled `http…` (`httpz://`), admits plaintext `http://` despite `docs/webhooks.md` stating "Only `https://` URLs are accepted" (R49: the doc claims a control stronger than the code implements), and imposes no restriction on the host, so `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:6379/`, or any RFC1918 address is a valid endpoint; `follow_redirects=True` then lets a benign-looking public URL redirect into the same internal space at delivery time.
What breaks in production: a customer registers an internal address and the delivery worker — running inside the VPC with whatever credentials the environment grants — POSTs attacker-chosen JSON to cloud metadata, Redis, or an internal admin API, and the response body is stored in `response_body` and readable back through the deliveries listing, turning SSRF into a full read primitive.
Fix: judge the resolved destination, not the string (R47 authority ladder). At registration: require `parsed.scheme == "https"` (exact equality, matching the doc), require a non-empty hostname with no userinfo, and reject when `socket.getaddrinfo(host)` yields any address for which `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved` — and re-run that same check at delivery time (registration-time DNS is re-resolvable by the owner, R51). At delivery: set `follow_redirects=False` and treat 3xx as a permanent failure. Because DNS is re-resolvable, declare this control's class explicitly (R49): with an httpx transport that pins the vetted IP it is an enforceable boundary; without pinning it is a best-effort tripwire, and the known bypass — DNS rebinding between the check and the connect — must be written next to it. Deny side: parametrized tests for `http://…`, `httpz://…`, `https://127.0.0.1/`, `https://169.254.169.254/`, and a host whose A record is `10.0.0.1`, each asserting 422 *and* (RT8) that no `WebhookEndpoint` row was created. Allow side (Remedy Floor 1): `https://hooks.example.com/acme` resolving to a public address must still return 201 — over-blocking here is what gets the check disabled (RT10). Red-prove separately: relax `==` back to `startswith` → the `httpz` case reddens; drop the address check → the metadata-IP case reddens; set `follow_redirects=True` → a MockTransport test issuing a 302 to a private address reddens. Fail loudly (Remedy Floor 3): a DNS failure must reject with a named error, never fall through to accept. Boundary/tie: state that a hostname resolving to *both* a public and a private address is rejected.

### Critical: `time.sleep()` inside an async coroutine blocks the entire delivery worker
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is fanned out with `asyncio.gather`, but the retry pause uses the blocking `time.sleep`, which stops the event loop rather than yielding it.
What breaks in production: one endpoint that is slow or erroring freezes every other delivery in the 100-item batch and the worker's own loop for up to 2+4+8+16 = 30s per failing delivery, so a single broken customer endpoint stalls all customers' webhooks and the lock's 60s TTL expires mid-batch.
Fix: `await asyncio.sleep(delay)`. Allow side (Remedy Floor 1): keep the retry actually retrying — a test that fails once then succeeds must still end `delivered` with `attempts == 2`, so the fix cannot be "remove the sleep". Red-prove by execution: with `asyncio.sleep` patched to record calls, run two deliveries concurrently against a handler that 500s once and assert both complete within one backoff interval; revert to `time.sleep` and confirm the elapsed-time assertion reddens. Preserve (Remedy Floor 4): do not shrink `BASE_DELAY_SECONDS` to make the test fast — inject the sleep function or patch `asyncio.sleep`, so the production backoff schedule stays observable. Boundary: state that the final attempt does not sleep at all (the `attempt >= MAX_ATTEMPTS` branch returns before the sleep), which is already the code's behaviour and must remain.

### Critical: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returning `rows`, `deliver()` reading `endpoint` outside its `with session_scope()`
What is wrong: `_claim_batch` returns `WebhookDelivery` objects after the `with session_scope()` block exits, and `deliver` fetches `endpoint` inside a block and reads `endpoint.signing_secret` / `endpoint.url` after it — with SQLAlchemy's default `expire_on_commit=True` every attribute on those detached instances is expired and re-access raises `DetachedInstanceError`.
What breaks in production: the worker raises on the first attribute read of the first delivery, the exception escapes the un-guarded `asyncio.gather`, and no webhook is ever delivered — the feature is inert from the first deploy.
Fix: stop passing ORM instances across session boundaries — have `_claim_batch` return plain data (`dataclass DeliveryJob(id, endpoint_id, payload, attempts)` built inside the session) and have `send_once` take `url` and `signing_secret` as arguments, so no lazy load can occur outside a session. Allow side (Remedy Floor 1): an integration test against a real (or in-memory) session that claims a batch and reads every field the worker uses, asserting the values match what was inserted — this is exactly the path the current unit tests avoid by substituting `FakeEndpoint`/`FakeDelivery` (RT5: the tests never traverse the production primitive). Red-prove: return the ORM rows again from `_claim_batch` and confirm that test reddens with `DetachedInstanceError` named in the output. Preserve: keep the in-session `row.status = "in_flight"` write — the claim must still be atomic with the read. Boundary: state what an empty claim returns (`[]`, not `None`) so `if not batch` keeps working.

### Critical: no test binds the signature to the bytes actually transmitted
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`
What is wrong: the delivery test captures `request.content` but asserts only that the signature header *starts with* `sha256=` and that the body's `type` field survives, never that the signature verifies against `captured["body"]`; and `test_verify_accepts_signature_produced_by_sign` is a round trip through the same `sign()` call, so both tests stay green under every one of the signing defects above (RT5: the production primitive — verification of the transmitted bytes — is never on the test call path; RT1: `FakeEndpoint`/`FakeDelivery` are hand-written doubles whose fields cannot diverge from the real models' behaviour because the real models are never loaded).
What breaks in production: the test suite reports the signing scheme as covered while the digest does not match the body, the timestamp is unsigned and the comparison is not constant-time — the reviewer's confidence is precisely inverted.
Fix: add one test that acts as an independent customer implementation: capture `request.content` and `request.headers`, recompute `hmac.new(SECRET.encode(), f"{ts}.".encode() + body, sha256).hexdigest()` *written out longhand in the test rather than by calling `signing.sign`*, and assert equality with the header (Remedy Floor 4: the value of this test is that it does not reuse the production encoder, so do not refactor it to call `sign()`). Deny side: flip one byte of the captured body before recomputing and assert mismatch. Allow side (Remedy Floor 1): the unmodified capture must verify. Red-prove each separately by execution: change `sort_keys=True` → the equality assertion reddens; drop the timestamp from the MAC → the recomputation reddens; leave both correct → both assertions green. Fail loudly (Remedy Floor 3): if the signature or timestamp header is absent the test must fail with a named assertion, not `KeyError`-skip. Boundary: state that the test asserts against the *exact* bytes including any trailing whitespace, since that is where producer/consumer encoders diverge.

### Major: `in_flight` is a non-terminal state with no exit, and retry progress is never persisted
File: `app/webhooks/delivery.py` — `_claim_batch()`, `deliver()`, `_finish()`
What is wrong: `_claim_batch` sets `status = "in_flight"` and only `_finish` ever leaves that state, while `deliver` loops all 5 attempts in memory without updating `attempts` or `next_attempt_at` between them — so a worker crash, deploy, or the un-guarded `gather` exception strands the row in `in_flight`, and `_claim_batch`'s `status == "pending"` filter can never reclaim it (R38 mode 1: an async transition with no failure-exit and no bounded timeout). `_finish` additionally calls `row.status = status` on the result of `session.get()` without a None check.
What breaks in production: every delivery in flight at the moment of any restart is lost permanently and invisibly, breaking the at-least-once guarantee `docs/webhooks.md` promises, and the rows accumulate as permanent `in_flight` garbage no operator has a way to release.
Fix: give the state machine an explicit failure exit and a bounded timeout. Persist per-attempt: after each failed attempt write `attempts += 1`, `next_attempt_at = now + backoff_for(attempt)`, `status = "pending"` and *return*, letting the poller pick the row up again rather than looping in memory. Add a `claimed_at` column and have `_claim_batch` also reclaim `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`. Make `_finish` raise a named error when `session.get` returns None (Remedy Floor 3 — a missing row must not be spelled the same as a completed one). Deny side: kill a worker mid-delivery and assert the row is reclaimed on the next poll. Allow side (Remedy Floor 1): a delivery still in progress at 4 minutes must *not* be reclaimed — without this the timeout duplicates every slow delivery. Red-prove separately: remove the reclaim clause → the crash test reddens; remove the `claimed_at` predicate → the 4-minute test reddens; drop the None check → a test passing a deleted id reddens with the named error. Boundary/tie (Remedy Floor 5): state which side of exactly 5 minutes reclaims, and that `attempts` is compared with `>= MAX_ATTEMPTS` so a reclaimed row on its 5th attempt goes to `failed_permanent` rather than looping.

### Major: the retry policy contradicts the documented one in two ways
File: `app/webhooks/delivery.py` — `deliver()`, `backoff_for()`; `docs/webhooks.md` — "Retries"
What is wrong: the docs state "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver()` retries every non-2xx status identically — including 400, 404 and 410 — and `backoff_for` returns a deterministic `2**attempt` with no jitter at all (R29/R49: the prose describes a control the implementation does not have).
What breaks in production: a customer who deletes their endpoint gets 5 POSTs of every event instead of one, and because all deliveries in a batch fail at the same instant and back off by the identical amount, retries arrive as synchronized thundering herds that keep a recovering endpoint down.
Fix: branch on the status class — `if 400 <= response.status_code < 500 and response.status_code not in (408, 429): _finish(..., "failed_permanent", ...); return` — and add jitter, `timedelta(seconds=BASE_DELAY_SECONDS**attempt * random.uniform(0.5, 1.5))` using `random` (jitter is not key material, unlike `new_signing_secret`). Allow side (Remedy Floor 1): 429 and 408 and every 5xx must still retry — a fix that treats all 4xx as permanent breaks the documented rate-limit path. Red-prove separately: remove the 4xx branch → a test asserting one attempt on a 404 reddens; remove the 408/429 carve-out → a test asserting 5 attempts on a 429 reddens; remove the jitter → a test asserting 100 samples of `backoff_for(1)` are not all identical reddens. Preserve (Remedy Floor 4): `test_backoff_grows_exponentially` currently pins exact equality (`== 2`, `== 4`…) and will block jitter — rewrite it as a bounded range (`1.0 <= backoff_for(1).total_seconds() <= 3.0`) rather than deleting it, and update `docs/webhooks.md`'s "roughly 2s, 4s, 8s, 16s" to name the jitter range. Boundary/tie: state that exactly 400 and exactly 499 are permanent while exactly 500 retries.

### Major: the delivered payload carries no event id, so the documented deduplication is impossible
File: `app/webhooks/delivery.py` — `send_once()`; `docs/webhooks.md` — "delivery is at-least-once, so deduplicate on `event_id`"
What is wrong: `send_once` posts `delivery.payload` verbatim, while `event_id` and `event_type` live only in the `WebhookDelivery` row and are never placed in the body or in a header — the docs instruct customers to deduplicate on a value the request does not contain (R41: a declared capability with no backing path; R40: the wire shape does not carry what the documented consumer contract requires).
What breaks in production: every customer following the integration guide double-processes retried `invoice.paid` events because they have nothing to deduplicate on, causing duplicate charges or duplicate fulfilment.
Fix: wrap the payload in the envelope the docs describe — `{"id": delivery.event_id, "type": delivery.event_type, "created": ts, "data": delivery.payload}` — and sign that envelope, so the id is inside the MAC and cannot be rewritten in transit. Allow side (Remedy Floor 1): the receiver must still be able to reach the original fields — assert `json.loads(body)["data"]["amount_cents"] == 4200` alongside `["id"] == delivery.event_id`, so the envelope is additive rather than a replacement. Red-prove separately: post the bare payload again → the `["id"]` assertion reddens; move the id to a header outside the MAC → a tamper test reddens. Preserve (Remedy Floor 4): `docs/webhooks.md`'s example body must be updated in the same change, or the doc becomes the next R29 finding. Boundary: state that `event_id` is unique per `(endpoint_id, event_id)` and that a retried delivery reuses the same id — that is what makes dedup work.

### Major: the dispatch lock is not atomic, is deleted unconditionally, and expires before a batch can finish
File: `app/webhooks/delivery.py` — `_acquire_lock()`, `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a GET then a separate SET, so two workers can both observe an empty key and both proceed (a TOCTOU on a distributed lock, R5's shape outside a transactional store); the 60s `expire` is shorter than a worst-case batch (5 attempts × 30s `REQUEST_TIMEOUT` plus 30s of backoff, per delivery); and the `finally` deletes `LOCK_KEY` by name without checking ownership, so a slow worker whose lease already expired deletes the lock a *different* worker now holds.
What breaks in production: two workers process the same claimed batch concurrently, producing duplicate POSTs of financial events and duplicate `_finish` writes, and the mutual lock-stealing makes the condition persistent rather than transient.
Fix: use a single atomic acquire with a unique token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`), and renew the lease from a background task while the batch runs. Deny side: a test where a second `_acquire_lock` with the key already set returns False, and one where releasing with a stale token leaves the key intact. Allow side (Remedy Floor 1): after a genuine release the next `_acquire_lock` must return True — a fix that never releases satisfies the deny tests and wedges the worker permanently. Red-prove separately: drop `nx=True` → the second-acquire test reddens; drop the token comparison in release → the stale-token test reddens; drop the renewal → a test with a batch exceeding `LOCK_TTL_SECONDS` reddens on a second acquisition mid-batch. Fail loudly (Remedy Floor 3): a Redis error during acquire must be logged and treated as *not acquired* (fail-closed, skip the batch), never as acquired. Boundary/tie: state what happens at exactly the TTL expiry — the renewal interval must be strictly less than half the TTL.

### Major: one failing delivery kills the worker loop
File: `app/webhooks/delivery.py` — `run_worker()`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` without `return_exceptions=True` propagates the first exception, and `deliver` only catches `httpx.HTTPError` — so any DB error, `DetachedInstanceError`, `IntegrityError` from the status CHECK mismatch, or `AttributeError` in `_finish` escapes `run_worker` entirely.
What breaks in production: the delivery worker process exits on the first unexpected error, all webhook delivery stops until someone notices, and the rest of the batch is left stranded in `in_flight` with no reclaim path.
Fix: `results = await asyncio.gather(*(deliver(client, d) for d in batch), return_exceptions=True)`, then iterate `results` and for each `BaseException` log it with the delivery id and mark that row back to `pending` with a bumped `attempts`; wrap the whole `while True` body in a `try/except Exception` that logs and continues after a backoff so the loop survives a transient DB outage. Allow side (Remedy Floor 1): a batch in which every delivery succeeds must still complete with no error logged — a fix that marks everything failed satisfies the resilience test. Red-prove separately: remove `return_exceptions=True` → a test where one of three deliveries raises and asserts the other two still finish reddens; remove the outer `try` → a test where `_claim_batch` raises once and the loop is asserted to keep polling reddens. Fail loudly (Remedy Floor 3): swallowing must be logged at ERROR with the delivery id — the point is that the loop survives, not that the failure disappears (Remedy Floor 4). Boundary: state that a delivery raising *after* `_finish` succeeded is not re-marked pending.

### Major: webhook enqueue failures are swallowed by a bare `except Exception`
File: `app/events/dispatcher.py` — `dispatch()`, `except Exception as exc: log.warning(...)`
What is wrong: every failure of `enqueue_for_event` — including the guaranteed unique-index violation on any multi-endpoint org — is caught, logged at WARNING, and `dispatch` returns success, so the caller cannot distinguish "webhooks enqueued" from "webhooks lost".
What breaks in production: webhook delivery fails silently for entire organizations while every upstream caller and every dashboard reports the event dispatched successfully, and the only evidence is a WARNING line nobody alerts on.
Fix: narrow the catch to the failures that are genuinely recoverable (`SQLAlchemyError`), log at ERROR with `org_id`, `event_id` and `event_type`, increment a `webhook_enqueue_failed` counter that an alert can fire on, and persist a retryable marker so a reconciliation job can re-enqueue from the `events` table — the events are already durably written above, so the data to recover from exists. Allow side (Remedy Floor 1): the happy path must still return `event_id` without touching the failure path, and a non-webhook event type must still skip enqueue entirely. Red-prove separately: raise `SQLAlchemyError` from a stubbed `enqueue_for_event` and assert the counter increments and the ERROR names the event id; raise a `KeyboardInterrupt` and assert it propagates (proving the catch narrowed). Preserve (Remedy Floor 4): do not "fix" this by letting the exception propagate out of `dispatch` — persisting the event and notifying in-process subscribers must not be undone by a webhook problem; that separation is the reason the try/except is there. Boundary: state that a partial `add_all` (some rows inserted) counts as a failure and is reconciled, not treated as success.

### Major: `webhooks_enabled` and `active` are declared but nothing drives them
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled`; `app/webhooks/models.py` — `WebhookEndpoint.active`; `app/api/routes/settings.py` — the three new routes
What is wrong: the migration adds `webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE` to `organizations` and no code in the diff ever reads it, while `active` is read by `enqueue_for_event`'s filter but is set to `True` at creation and never changed, because the diff adds no PATCH or DELETE route (R41: a capability declared to the schema with no working backing path).
What breaks in production: the feature ships enabled for every organization despite a per-org kill switch existing in the schema and defaulting to off, and a customer whose signing secret leaks has no way to disable, delete, or rotate an endpoint — there is no route that writes `active` and no route that regenerates `signing_secret`.
Fix: wire both — have `create_webhook_endpoint` and `enqueue_for_event` join `Organization.webhooks_enabled` and refuse/skip when false, and add `PATCH /webhook-endpoints/{id}` (sets `active`, org-scoped like the listing fix above) and `POST /webhook-endpoints/{id}/rotate-secret` (returns the new secret once, via `to_dict_with_secret`). Allow side (Remedy Floor 1): an org with `webhooks_enabled = TRUE` must still enqueue — pin it, or a fix that always skips passes the deny test and disables the whole feature. Deny side: assert `enqueue_for_event` returns 0 and inserts no rows for a disabled org, and 0 for an org whose only endpoint has `active = FALSE`. Red-prove separately: remove the org join → the disabled-org test reddens; remove the `active.is_(True)` filter → the inactive-endpoint test reddens; remove the PATCH route → a test asserting deactivation stops delivery reddens. Boundary/tie: state whether deliveries already enqueued for a now-deactivated endpoint are still sent (they are, given `_claim_batch` does not re-check `active`) — decide it explicitly rather than leaving it emergent.

### Major: the three new routes have no rate limiting
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: none of the new endpoints carries a limiter, and `create_webhook_endpoint` in particular has no per-org cap on how many endpoints may exist (RS2). Evidence for the "missing" claim per Finding Floor: the file's pre-existing routes visible in the diff carry no limiter dependency either, so there is no established shared limiter this route merely forgot to adopt — which is why the cap belongs in this change rather than being assumed present at a gateway.
What breaks in production: a single account can register thousands of endpoints, and because `enqueue_for_event` fans out to every active endpoint of an org, each registration multiplies the outbound request volume of every event — a self-service amplification vector against both our worker and any third-party host the attacker names.
Fix: enforce a hard per-org cap in the handler (`if session.query(WebhookEndpoint).filter_by(org_id=user.org_id).count() >= MAX_ENDPOINTS_PER_ORG: raise HTTPException(429, ...)`, `MAX_ENDPOINTS_PER_ORG = 10` as a named module constant) and attach the project's request limiter to all three routes; if the project has no limiter, say so and add the cap regardless, since the cap is what bounds the amplification. Deny side: create `MAX_ENDPOINTS_PER_ORG` endpoints, assert the next returns 429 *and* (RT8) that no row was inserted. Allow side (Remedy Floor 1): the `MAX_ENDPOINTS_PER_ORG`-th creation must succeed — pin the boundary explicitly. Red-prove separately: change `>=` to `>` → the boundary test reddens; remove the cap → the 429 test reddens. Boundary/tie (Remedy Floor 5): the cap counts inactive endpoints too, or deactivation becomes a cap bypass — state which and test it.

### Major: request parameters are typed but not bounded
File: `app/api/routes/settings.py` — `EndpointIn.url` / `EndpointIn.event_types`, `list_deliveries`'s `limit: int = Query(50, ge=1)`
What is wrong: `url` is a bare `str` with no length limit, `event_types` is an unbounded `list[str]` never checked against the known set (`app/events/dispatcher.py::WEBHOOK_EVENT_TYPES`, which the change itself introduces as the authoritative list), and `limit` has a `ge` but no `le`, so it is unbounded above (RS3).
What breaks in production: `GET …/deliveries?limit=100000000` loads the entire delivery table into memory and serializes it, taking the API process down; a megabyte-long URL is stored and then dialled by the worker; and a typo'd event type is accepted silently, so the customer's endpoint receives nothing and the misconfiguration is undiagnosable from the API.
Fix: bound all three at the schema — `url: str = Field(max_length=2048)`, `event_types: list[str] = Field(default_factory=list, max_length=50)` with a validator rejecting any member not in `WEBHOOK_EVENT_TYPES` (import the existing set rather than restating it — the codebase already owns this list, so no second copy is created), and `limit: int = Query(50, ge=1, le=200)`. Deny side: 422 for `limit=201`, for a 3000-char url, and for `event_types=["invoice.paidd"]`, each asserting no row was written. Allow side (Remedy Floor 1): `limit=200`, a 2048-char url, and `event_types=[]` (the documented subscribe-to-everything case) must all still succeed — `[]` in particular must not be caught by the membership validator, or the documented default breaks (Remedy Floor 4). Red-prove separately: drop `le=200` → the 201 case reddens; drop the membership validator → the typo case reddens; apply the validator to the empty list → the `[]` allow case reddens. Boundary/tie (Remedy Floor 5): 200 accepts and 201 rejects; 2048 accepts and 2049 rejects.

### Major: signature headers and full upstream response bodies are logged and stored
File: `app/webhooks/delivery.py` — `send_once()`'s `log.info("POST %s headers=%s", endpoint.url, headers)`, `_finish()`'s `row.response_body = detail`
What is wrong: every delivery logs the complete header dict including `X-Acme-Signature` and `X-Acme-Timestamp` at INFO, and `_finish` persists `response.text` in full with no size cap into a column readable through the deliveries route.
What breaks in production: because the timestamp is not signed (see the Critical above), anyone with log-shipper access holds a replayable signature for every event, and unbounded upstream bodies — which may contain the customer's own error pages, tokens, or PII — are stored indefinitely and served back through the API.
Fix: log only the destination and the delivery id at INFO (`log.info("POST %s delivery=%s", endpoint.url, delivery.id)`), never the header dict; truncate stored bodies to a named constant (`RESPONSE_BODY_LIMIT = 2048`) with a `"…truncated"` marker so truncation is visible rather than silent. Allow side (Remedy Floor 1): a body shorter than the limit must be stored byte-identically — an unconditional truncation destroys the diagnostic value the column exists for (Remedy Floor 4: keep enough of the body to debug a failing endpoint). Deny side: a 10KB response stores exactly `RESPONSE_BODY_LIMIT` characters plus the marker, and a test asserts no log record emitted by the module contains the string `sha256=`. Red-prove separately: restore the header log → the log-scan test reddens naming the record; remove the truncation → the 10KB test reddens on length. Boundary/tie: a body of exactly `RESPONSE_BODY_LIMIT` characters is stored untruncated and carries no marker.

### Major: the schema declares timezone-aware columns that the migration creates without a time zone, and the two writers disagree
File: `app/webhooks/models.py` — all four `DateTime(timezone=True)` columns; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP NOT NULL`; `app/webhooks/delivery.py` — `next_attempt_at=datetime.utcnow()` in `enqueue_for_event` vs `datetime.now(timezone.utc)` in `_claim_batch` and `_finish`
What is wrong: the ORM declares `timestamptz` while the migration creates `timestamp without time zone`, and within one module the scheduling column is *written* with a naive `utcnow()` but *compared* against an aware `now(timezone.utc)` (R3: the aware-datetime pattern reached three of the four call sites; R40: the model's declared type and the actual column type diverge).
What breaks in production: on any database session whose `TimeZone` is not UTC, the aware value is converted on the way into a naive column while the naive one is not, so `next_attempt_at <= now` is off by the offset — deliveries fire hours early or are never claimed at all, and the direction depends on deployment configuration rather than on code.
Fix: make the migration `TIMESTAMPTZ NOT NULL` on all four columns (`created_at`, `next_attempt_at`, `updated_at`, and `webhook_endpoints.created_at`) to match the models, and replace `datetime.utcnow()` with the module's existing `datetime.now(timezone.utc)` — note `app/webhooks/models.py` already defines `_now()` for exactly this, so `enqueue_for_event` should call it rather than introducing a fourth spelling (codebase-awareness: the helper is in the change already). Allow side (Remedy Floor 1): a delivery scheduled for the past must still be claimed immediately — pin it, so a fix that makes everything look future-dated passes a "not claimed early" test. Deny side: a delivery scheduled 1 second in the future is not claimed. Red-prove separately: revert to `utcnow()` and run the claim test under `SET TIME ZONE 'America/New_York'` → it reddens; revert the column to `TIMESTAMP` → an assertion on the reflected column type reddens. Boundary/tie (Remedy Floor 5): `next_attempt_at` exactly equal to `now` is claimed (`<=`), and two rows with the identical `next_attempt_at` are ordered by `id` — add `id` to the `order_by`, since `next_attempt_at` alone is not a total order (R57).

### Major: newly added delivery logic ships with no test coverage
File: `tests/webhooks/test_delivery.py` — imports only `MAX_ATTEMPTS`, `backoff_for`, `send_once`
What is wrong: the diff adds `enqueue_for_event`, `deliver`, `run_worker`, `_acquire_lock`, `_claim_batch`, `_finish`, both model classes and three HTTP routes, and the only production symbols the test file imports are `MAX_ATTEMPTS`, `backoff_for` and `send_once` — the retry loop, the claim/lock protocol, the state transitions and every route are untested (RT6).

### Minor: the delivery listing orders on a non-total key

### Minor: the delivery indexes do not match the queries the change issues

What is wrong: the only non-unique index is on `status` alone, a very low-cardinality column, while `_claim_batch` filters `status = 'pending' AND next_attempt_at <= now` ordered by `next_attempt_at`, and `list_deliveries` filters `endpoint_id` ordered by `created_at`.
