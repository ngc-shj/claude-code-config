### Critical: the signature is computed over bytes that are never sent, so no customer can ever verify a delivery
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, used by `app/webhooks/delivery.py::send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys reordered) while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx serializes with its own separators and the dict's insertion order — so the signed string and the wire body are different byte strings for any payload whose keys are not already sorted.
What breaks in production: every integrator following `docs/webhooks.md` computes HMAC over the raw request body, gets a mismatch, and rejects 100% of deliveries — a silent total-path failure that the shipped tests cannot see because they only assert the `sha256=` prefix (R40, Critical: silent total-path failure).
Fix: make one byte string authoritative. In `send_once`, build the body once — `body = serialize(delivery.payload).encode()` — sign exactly that (`sign(secret, body)` taking `bytes`, not `dict`), and send it with `client.post(endpoint.url, content=body, headers=headers)` so `json=` never re-serializes; change `verify(secret, body: bytes, signature)` to take the same raw bytes. Preserve, and state in the docstring, the two behaviours the fix must not delete: the `sha256=` prefix on the header value and the `Content-Type: application/json` header (dropping `json=` removes httpx's automatic content-type, so it must stay in the explicit `headers` dict). Deny/allow pairing: pin the ALLOW case — a test that reads `request.content` out of the `MockTransport` handler and asserts `signing.verify(SECRET, captured["body"], captured["headers"][SIGNATURE_HEADER])` is `True`, i.e. the receiver's own procedure succeeds on real transmitted bytes — alongside the DENY case that flipping one byte of `captured["body"]` makes `verify` return `False`. Red-prove each clause separately by execution: (i) revert `content=` to `json=` and observe the allow-side round-trip assertion go red; (ii) drop the explicit `Content-Type` and observe the existing `captured["headers"]["content-type"] == "application/json"` assertion go red; (iii) mutate one payload byte and observe the deny assertion go red — three mutations, three different assertions. Fail loudly when the check cannot run: `serialize` must reject a payload that is not JSON-serializable with a named error (`raise WebhookPayloadError(...)`) rather than letting `TypeError` surface as a generic delivery failure, so "could not sign" is never spelled like "signed and delivered". Boundary and tie: an empty payload `{}` signs the two-byte body `{}` and must still produce a full 64-hex digest, and two payloads that differ only in key ORDER must now produce the SAME signature (`serialize` sorts) — pin that equality explicitly so the tie is not left to the next implementer.

### Critical: signing secrets are generated with a non-cryptographic PRNG, so they are predictable
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, which draws from the Mersenne Twister — a deterministic generator whose full internal state is recoverable from a modest run of outputs, and which is seeded per process — so secrets minted in one process are correlated and reconstructible.
What breaks in production: an attacker who observes or provokes enough secret generation can predict another organization's signing secret and forge webhook deliveries that verify, defeating the entire signing scheme this change exists to provide.
Fix: replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX` (`import secrets`; delete the now-unused `random`/`string` imports and `_ALPHABET`), and rename `SECRET_BYTES` to mean what it now is — actual entropy bytes, not output characters. Name the behaviour preserved: the `whsec_` prefix and the "secret is a single opaque ASCII token" contract that `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` asserts — do not fix this by weakening that test; update its length assertion to `>= SECRET_BYTES` (token_urlsafe emits ~1.33 chars/byte) rather than deleting it. Deny/allow pairing: the ALLOW case that must still succeed is `verify(new_signing_secret(), body, sign(same_secret, body)[1])` returning `True` — a freshly minted secret still signs and verifies end to end; the DENY case is that 10,000 generated secrets contain no duplicate and none is reproducible after re-seeding `random.seed(0)`. Red-prove separately: (i) `random.seed(0)` before two calls and assert the two secrets differ — red under the current code, green after; (ii) truncate to 8 bytes and assert the entropy-floor test reds; (iii) drop the prefix and assert the prefix test reds. Fail loudly: if `secrets` cannot draw (no OS entropy source), let the `OSError` propagate as a named `SigningSecretUnavailable` at endpoint creation so the POST returns 5xx — a secret must never be created from a fallback path, and "generated nothing" must not be spelled like "generated a secret". Boundary and tie: `SECRET_BYTES = 32` is the floor, not a target — state that a secret shorter than 32 bytes is rejected at the boundary (`< 32` fails, `== 32` passes), and that two endpoints of the same org must never share a secret.

### Critical: `verify()` compares signatures with `==`, leaking the expected digest through timing
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: the HMAC comparison uses Python's short-circuiting string `==` instead of a constant-time comparison, even though `hmac` is already imported in this very file and ships `hmac.compare_digest` (RS1, Critical).
What breaks in production: an attacker who can submit candidate signatures to any consumer of this helper recovers the correct digest byte by byte from response-time differences, forging a valid delivery without ever learning the secret.
Fix: `return hmac.compare_digest(expected, signature)` — the helper is already reachable via the existing `import hmac`, so no new dependency or local re-implementation is warranted (codebase-awareness check: the diff contains no other comparison helper, and `delivery.py` has no second verification path, so this is the only site). Do not fix by deleting `verify` as "unused by production code" — it is the reference implementation `docs/webhooks.md` tells integrators to mirror, and that documentation role is the behaviour to preserve. Deny/allow pairing: the ALLOW case is the existing `test_verify_accepts_signature_produced_by_sign` still passing byte-identically; the DENY case is `test_verify_rejects_a_signature_made_with_another_secret` still returning `False`. Red-prove separately: (i) return a constant `True` and watch the deny test red; (ii) return a constant `False` and watch the allow test red; (iii) pass a `None` signature and watch the new type-guard test red. Fail loudly: `compare_digest` raises `TypeError` on non-ASCII `str` or on `None`, so guard the parameter at the top (`if not isinstance(signature, str): return False` is NOT acceptable here because it hides a caller bug) — instead raise a named `InvalidSignatureHeader`, so a malformed header is distinguishable from a wrong signature. Boundary and tie: state that a signature of the wrong LENGTH returns `False` rather than raising, and that the empty string `""` is a rejection, not a match.

### Critical: the timestamp header is generated but never bound into the signature, so the documented replay window does not exist
File: `app/webhooks/signing.py` — `sign()`; `docs/webhooks.md` "Verifying the signature"
What is wrong: `docs/webhooks.md` states the signature is "the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`", but `sign()` MACs only `serialize(payload)` and returns the timestamp as an independent, unauthenticated value.
What breaks in production: because the timestamp is not covered by the MAC, an attacker who captures one delivery can replay it forever with a freshly rewritten `X-Acme-Timestamp`, and every integrator who implements the documented five-minute rejection will additionally compute a different HMAC than we send — the replay defence the docs sell is absent (R29, Critical: an inaccurate documented derivation drives a security decision; compounds the serialization defect above).
Fix: change the signed input to `f"{timestamp}.".encode() + body` where `body` is the exact transmitted bytes from the first finding, so one change repairs both; keep `sign()` returning `(timestamp, "sha256=" + hexdigest)` so the header contract in `send_once` is unchanged. Do not fix by editing the docs down to match the weaker code — the five-minute replay window is the feature, and the doc sentence naming it is what makes the defect visible. Deny/allow pairing: ALLOW — a delivery signed now verifies when the receiver recomputes with the received timestamp; DENY — the same body with the timestamp advanced by one second fails verification. Red-prove separately: (i) drop the `{timestamp}.` prefix from the signed input and watch the timestamp-binding test red; (ii) mutate one body byte and watch the body-binding test red; (iii) feed a timestamp 6 minutes old to the reference verifier and watch the staleness test red. Fail loudly: if `time.time()` yields a value before the epoch-sanity floor, raise a named `ClockUnavailable` rather than signing with a nonsense timestamp — "could not timestamp" must not be spelled like "timestamped". Boundary and tie: the window is inclusive-exclusive at exactly 300 seconds — a delivery at exactly 300s old is REJECTED, at 299s accepted — and two deliveries sharing one timestamp are both valid, so the timestamp is a freshness bound and not a nonce; say so in the docs.

### Critical: `GET /webhook-endpoints` returns every endpoint's signing secret, contradicting the documented one-time-reveal
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, key `"signing_secret"`; consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally includes `signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret is re-served on every list call and lands in browser history, proxy logs, HAR captures, and support screenshots, so any read-only viewer of the settings page can forge signed webhooks for the whole organization — and the documented security property that other decisions rest on is false (R49/R29 escalated: the overstated control is relied on as a boundary).
Fix: drop `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` alone return it, by composing the reveal at the route — `return {**endpoint.to_dict(), "signing_secret": secret}` where `secret` is the local returned by `new_signing_secret()` before it is assigned to the row. Codebase-awareness evidence: `WebhookDelivery.to_dict()` in the same file already omits all sensitive columns (no `payload`, no `response_body`), so the safe serializer shape already exists in this diff and `WebhookEndpoint.to_dict()` is the outlier — this is the established pattern, not a new one. Do not fix by leaving the secret in `to_dict()` and filtering it at the route, which re-admits it the moment a third caller appears. Deny/allow pairing: ALLOW — a test asserting the 201 response body from `POST /webhook-endpoints` still contains a `signing_secret` starting with `whsec_` (the one-time reveal must keep working); DENY — a test asserting `"signing_secret" not in` any element of the `GET /webhook-endpoints` response, and not in `to_dict()`'s key set. Red-prove separately: (i) re-add the key to `to_dict()` and watch the GET-absence test red; (ii) remove the route-level merge and watch the POST-presence test red; (iii) add a third key to `to_dict()` and watch an exact key-set equality assertion red (per RT1 clause (e), compare the whole key set, not a subset). Fail loudly: if the route cannot obtain the plaintext secret at creation time, return 5xx with a named error rather than a 201 carrying no `signing_secret` — a created-but-unrevealed endpoint is unusable and must not read as success. Boundary and tie: state that the reveal happens exactly once, on the 201 path only; a retried POST creates a NEW endpoint with a NEW secret rather than re-revealing the old one, and two endpoints of one org never share a secret.

### Critical: `GET /webhook-endpoints/{id}/deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: the query filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user of any organization can enumerate any other organization's delivery history by incrementing the id.
What breaks in production: cross-tenant data disclosure — delivery ids, event ids, event types, and response statuses of every customer are readable by every customer, a reportable breach (R3, Critical: the security-relevant org-scoping pattern was propagated to two of three new routes and dropped on the third).
Cross-cutting verification: the same pattern is applied correctly in three sibling sites in this diff — `list_api_keys` (`ApiKey.org_id == user.org_id`), `list_webhook_endpoints` (`WebhookEndpoint.org_id == user.org_id`), and `enqueue_for_event` (`m.WebhookEndpoint.org_id == org_id`). `list_deliveries` is the only new query over tenant-owned rows without it, and `get_profile` is scoped by construction. No further missed location.
Fix: join and scope — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. Codebase-awareness evidence: no shared tenancy helper exists in the diff, so the join is written inline exactly as the three siblings above write their filter; if a `scoped_query(session, model, user)` helper is introduced it must be adopted at all four sites in the same change, not just here. Do not fix by validating `endpoint_id` in the client or by relying on ids being unguessable — the row-level predicate is what makes the defect visible and must be in the handler that touches the data. Deny/allow pairing: ALLOW — a user of org A requesting their OWN endpoint's deliveries still receives the full, correctly ordered, correctly limited list (a fix that always 404s satisfies every other clause); DENY — a user of org B requesting org A's endpoint id receives 404 with an empty body. Red-prove separately: (i) delete the `org_id` predicate and watch the cross-tenant deny test red; (ii) delete the `endpoint_id` predicate and watch a test asserting only one endpoint's rows come back red; (iii) change 404 to 403 and watch an existence-disclosure assertion red. Fail loudly: when `user.org_id` is `None` or absent, raise rather than falling through to an unfiltered query — an unresolvable subject must refuse, never widen. Boundary and tie: an endpoint id that exists but belongs to another org and an endpoint id that does not exist must be indistinguishable (both 404); an endpoint owned by the caller with zero deliveries returns `200 []`, not 404.

### Critical: no destination restriction on the registered URL, and redirects are followed — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `startswith("http")` admits `http://` (docs say "Only `https://` URLs are accepted") and any scheme merely beginning with those four characters, and nothing rejects loopback, link-local, or RFC 1918 destinations — while the worker follows redirects, so even an initially-public host can bounce a delivery to `169.254.169.254` (RS3, Critical: an unvalidated externally-supplied value reaches a request sink).
What breaks in production: any authenticated customer turns our worker into an SSRF proxy that POSTs signed, authenticated requests to internal services and cloud metadata endpoints and stores the response body in `webhook_deliveries.response_body` for retrieval, exfiltrating internal data and credentials.
Fix: validate at the schema boundary, not in the handler body — give `EndpointIn.url` a strict validator that (a) requires `parsed.scheme == "https"` by exact equality, (b) requires a non-empty `netloc` with no embedded credentials (`parsed.username is None`), and (c) resolves the hostname and rejects every resulting address for which `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast` — and set `follow_redirects=False` on the client so the resolve-time decision cannot be re-pointed after the check (R51-shaped: the check must bind to the address actually connected to, not to the name checked earlier; where the HTTP stack supports it, pin the resolved address or re-validate in a connection hook). Do not fix by dropping the redirect feature silently — record in `docs/webhooks.md` that a 3xx is now treated as a delivery failure, since that is a behaviour customers can observe. Deny/allow pairing: ALLOW — `https://hooks.example.com/acme` (the exact URL in `docs/webhooks.md` and in `FakeEndpoint`) still registers with 201 and still delivers; DENY — `http://hooks.example.com`, `httpx://x`, `https://127.0.0.1/x`, `https://169.254.169.254/latest/meta-data/`, and `https://user:pw@host/` each return 422. Red-prove separately: (i) relax `==` back to `startswith` and watch the `http://` deny test red; (ii) remove the private-address check and watch the `127.0.0.1` deny test red; (iii) re-enable `follow_redirects=True` and watch a redirect-to-loopback deny test red — three mutations, three assertions. Fail loudly: when DNS resolution fails or times out, return 422 with a named "destination could not be verified" error rather than registering the endpoint unchecked — "could not resolve" must not be spelled like "resolved to something safe". Boundary and tie: a hostname resolving to BOTH a public and a private address is rejected (any-private, not all-private); IPv6 loopback `::1` and IPv4-mapped `::ffff:127.0.0.1` are rejected on the same predicate as `127.0.0.1`.

### Critical: `time.sleep()` inside an async coroutine blocks the entire event loop for the whole backoff
File: `app/webhooks/delivery.py` — `deliver()`, line `time.sleep(delay)`
What is wrong: `deliver` is `async`, is fanned out through `asyncio.gather`, and calls the blocking `time.sleep` for backoffs of 2/4/8/16 seconds — freezing the loop rather than yielding, while the same file's `run_worker` correctly uses `await asyncio.sleep(poll_interval)`.
What breaks in production: one failing endpoint stalls every concurrent delivery and every other coroutine on that loop; a batch of 100 deliveries each retrying to a dead host serialises into roughly 100 × 30 seconds of frozen process, so healthy customers' webhooks stop and any HTTP server sharing the loop stops answering.
Fix: `await asyncio.sleep(delay)` — `asyncio` is already imported in this file and `run_worker` already establishes it as the idiom, so no new helper is warranted (codebase-awareness evidence: the blocking call is the outlier within its own module, and `import time` becomes unused once it is removed). Preserve the behaviour the sleep exists for: the delay must remain the value `backoff_for(attempt)` returns, so the change is a yield-point change and not a timing change. Deny/allow pairing: ALLOW — a test that gathers two `deliver` calls where the first backs off and asserts the second's request is observed by the mock transport BEFORE the first's retry, proving concurrency survives; DENY — a test asserting total wall time for two concurrent one-retry deliveries is below the sum of their delays. Red-prove separately: (i) restore `time.sleep` and watch the interleaving assertion red; (ii) hardcode `delay = 0` and watch an assertion that the retry happened no earlier than `backoff_for(attempt)` red; (iii) remove the `await` keyword and watch a coroutine-never-awaited warning promoted to error red. Fail loudly: cap the cumulative sleep per delivery and raise a named `DeliveryBudgetExceeded` when a delivery exceeds it, so a wedged retry loop reports itself rather than sleeping indefinitely. Boundary and tie: `attempt == MAX_ATTEMPTS` must return WITHOUT sleeping at all (the current code already returns before the sleep — pin that, since the natural refactor breaks it), and two deliveries with identical delays must both wake independently rather than one gating the other.

### Critical: the `failed_permanent` status violates the migration's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; written by `app/webhooks/delivery.py::_finish` and declared in `app/webhooks/models.py::STATUSES`
What is wrong: the Python side uses `"failed_permanent"` in both `models.STATUSES` and `_finish(delivery.id, "failed_permanent", ...)`, while the SQL CHECK enumerates `'failed'` — two of three sites agree and the migration is the outlier (R3, Critical: the enumeration is what the delivery state machine is adjudicated on).
What breaks in production: the very first delivery to exhaust its retries raises `IntegrityError` inside `_finish`, the transaction rolls back, and the row stays `in_flight` forever — so exhausted deliveries are never marked failed, are never visible in the deliveries API, and the `in_flight` rows accumulate unbounded.
Cross-cutting verification: the other three status literals match across all three sites (`pending` in `_claim_batch` and the SQL default, `in_flight` in `_claim_batch` and the CHECK, `delivered` in `_finish` and the CHECK). `failed_permanent` is the only divergence.
Fix: change the migration's CHECK to `status IN ('pending', 'in_flight', 'delivered', 'failed_permanent')` — align the SQL to the code rather than the reverse, because `models.STATUSES` and `_finish` already agree with each other and with the `failed_permanent` semantics the retry loop implements — and add a startup assertion that `models.STATUSES` equals the constraint's enumerated set so the two cannot drift again. Do not fix by removing the CHECK constraint; it is what makes this class of drift visible, and its absence would have let a typo'd status persist silently. Deny/allow pairing: ALLOW — an integration test that runs the migration against a real database and inserts one row of EACH of the four statuses, all succeeding; DENY — an insert of `'failed'` (the now-removed spelling) and of `'bogus'` both raising `IntegrityError`. Red-prove separately: (i) revert the CHECK to `'failed'` and watch the `failed_permanent` insert test red; (ii) drop one status from `models.STATUSES` and watch the startup parity assertion red; (iii) drop the CHECK entirely and watch the `'bogus'` deny test red. Fail loudly: the parity assertion must raise a named `StatusEnumDrift` at import time when it cannot READ the constraint (no database, introspection unavailable) rather than passing — "could not compare" must not be spelled "compared and matched". Boundary and tie: name `failed_permanent` and `delivered` as the two terminal states and `pending`/`in_flight` as the two non-terminal ones, and state that a row may move `in_flight → pending` (requeue) but never leave a terminal state.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: the index is unique on `event_id` by itself, but `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the second row of any fan-out collides.
What breaks in production: the moment an organization registers a second endpoint (or two organizations both subscribe, since `event_id` is global and not org-scoped), `session.add_all(rows)` raises `IntegrityError`; that exception is then swallowed by the `except Exception` in `dispatch`, so ALL webhook deliveries for that event are silently dropped with only a `log.warning`.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is what the documented at-least-once/deduplicate-on-`event_id` contract actually needs, since a receiver deduplicates within its own endpoint. Preserve the behaviour the unique index exists for: exactly-once enqueue per (endpoint, event), which is what stops a re-dispatched event from double-enqueueing — do not fix by dropping uniqueness altogether. Codebase-awareness evidence: `enqueue_for_event` is the only writer of these rows and it already iterates endpoints, so the composite key matches its natural insert unit; no dedup helper exists in the diff that this reimplements. Deny/allow pairing: ALLOW — an integration test where one event fans out to three endpoints of one org and all three rows persist; DENY — enqueueing the SAME (endpoint_id, event_id) twice raises `IntegrityError`. Red-prove separately: (i) revert to the single-column index and watch the three-endpoint fan-out test red; (ii) drop the index entirely and watch the duplicate-enqueue deny test red; (iii) reorder the columns to `(event_id, endpoint_id)` and confirm the claim-query plan test still passes or is corrected. Fail loudly: `enqueue_for_event` must convert the `IntegrityError` into a named `DuplicateEnqueue` that the caller can distinguish from a transport failure, and `dispatch` must stop swallowing it (see the fire-and-forget finding below) — "already enqueued" and "enqueue failed" must not be spelled the same. Boundary and tie: state that an event matching ZERO endpoints inserts zero rows and is a success, not a failure, and that two endpoints of DIFFERENT orgs subscribing to the same `event_id` each get their own row.

### Critical: ORM instances are used after their session closes, so every delivery raises on first attribute access
File: `app/webhooks/delivery.py` — `_claim_batch()` returning `rows`, and `deliver()`'s `with session_scope() as session: endpoint = session.get(...)`
What is wrong: both functions return or retain SQLAlchemy instances that escape the `with session_scope()` block; on commit the default `expire_on_commit` marks every attribute stale, so the first access outside the block (`delivery.attempts`, `delivery.payload`, `endpoint.signing_secret`, `endpoint.url`) triggers a refresh on a detached instance.
What breaks in production: `run_worker` raises `DetachedInstanceError` on the first claimed row, the `asyncio.gather` propagates it out of the `try`, the `finally` releases the lock, and the loop re-enters and fails identically forever — the worker never delivers a single webhook while the rows it claimed stay stuck in `in_flight`.
Cross-cutting verification: the same escape pattern appears at exactly two sites (`_claim_batch`'s return, `deliver`'s `endpoint`); `_finish` and `enqueue_for_event` correctly confine all attribute access inside their blocks, and the route handlers call `to_dict()` inside `session_scope` — so those four sites are clean.
Fix: stop passing ORM entities across the session boundary. Have `_claim_batch` return plain immutable snapshots taken inside the block — a frozen dataclass `ClaimedDelivery(id, endpoint_id, attempts, payload, url, signing_secret)` built from a joined query against both tables — and have `deliver` take that snapshot instead of re-fetching the endpoint, deleting the second `session_scope` in `deliver` entirely. Codebase-awareness evidence: `WebhookDelivery.to_dict()` and `WebhookEndpoint.to_dict()` already exist as in-session snapshot helpers in `models.py`; the snapshot dataclass is the same idea and should be built from them rather than as a third serialization path — but note `to_dict()` omits `payload`, `url`, and (after the secret fix) `signing_secret`, so the dataclass must add those explicitly rather than reusing `to_dict()` verbatim. Preserve the behaviour the current code intends: the claim and the status flip to `in_flight` must remain in ONE transaction with the read. Deny/allow pairing: ALLOW — an integration test against a real session (not a mock) asserting `deliver` completes and `_finish` writes `delivered` for a claimed row; DENY — a test asserting the returned objects are not SQLAlchemy-mapped and that touching them after the session closes raises nothing. Red-prove separately: (i) return the mapped rows again and watch the detachment test red; (ii) move the status flip outside the block and watch a "claimed rows are `in_flight` after commit" assertion red; (iii) omit `signing_secret` from the snapshot and watch the send test red. Fail loudly: if the join returns a delivery whose endpoint row is missing, skip it and mark it `failed_permanent` with a named reason rather than letting `None.signing_secret` raise — an unresolvable subject must refuse by name. Boundary and tie: a batch of exactly `BATCH_SIZE` rows and a batch of zero must both be handled (the zero case already feeds the `if not batch` sleep), and two rows with the identical `next_attempt_at` must both be claimed rather than one being dropped by the ordering.

### Critical: the Redis mutex is not atomic and is released unconditionally, so batches are claimed and delivered twice
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `get`, then a separate `set`, then a separate `expire` — a check-then-act with two windows in which a second worker passes the same check — and the lock carries no owner token, so `run_worker`'s `finally` deletes whatever lock is present, including one a different worker acquired after the 60-second TTL expired mid-batch.
What breaks in production: two or more workers claim overlapping batches (there is no `FOR UPDATE SKIP LOCKED` on `_claim_batch` either, so nothing else serialises them), customers receive duplicate signed deliveries, and a batch that outlives the 60-second TTL — trivially reached at 100 deliveries × 5 attempts × a 30-second `REQUEST_TIMEOUT` — has its lock stolen and then deleted by the original holder.
Fix: make acquisition one atomic operation with an owner token and a TTL — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release only via a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can never delete a lock it does not own; independently, add `.with_for_update(skip_locked=True)` to `_claim_batch`'s query so correctness does not rest on the lock alone, and renew the lock while a batch is in flight. Do not fix by lengthening the TTL only — that widens the window in which a crashed worker blocks all others, and it deletes nothing of the defect. Deny/allow pairing: ALLOW — a single worker still acquires, processes a batch, and releases, and the NEXT poll acquires again (a fix that always denies the lock satisfies every other clause and delivers nothing); DENY — two concurrent `_acquire_lock` calls against one Redis yield exactly one `True`, and a worker whose token no longer matches deletes nothing. Red-prove separately: (i) drop `nx=True` and watch the mutual-exclusion test red; (ii) replace the compare-and-delete with a bare `delete` and watch the steal test red; (iii) remove `ex=` and watch a "lock expires after TTL when the holder dies" test red. Fail loudly: when Redis is unreachable, `_acquire_lock` must raise a named `LockUnavailable` that stops the worker, never return `True` (fail-open) and never return `False` forever in silence — the poll loop must log the refusal by name. Boundary and tie: a lock whose TTL expires at exactly the release moment must not cause the holder to delete a successor's lock (that is precisely what the token comparison decides), and two workers whose `SET NX` land in the same millisecond must produce exactly one winner.

### Minor: the delivery-claim query has no supporting index
File: `migrations/0042_webhook_delivery.sql` — `CREATE INDEX idx_webhook_deliveries_status ON webhook_deliveries (status);`
What is wrong: `_claim_batch` filters on `status` AND `next_attempt_at <= now` and orders by `next_attempt_at`, but the only index is on the low-cardinality `status` column alone.
What breaks in production: once the table grows, every poll (once per second per worker) sorts a large `pending` set, and the ordering step dominates the worker's cycle. A composite `(status, next_attempt_at)` index serves both the predicate and the ordering.

### Minor: `run_worker` never returns claimed rows to `pending` on shutdown
File: `app/webhooks/delivery.py` — `run_worker()`'s `while True` with no cancellation handling
What is wrong: the loop has no `asyncio.CancelledError` branch, so a graceful shutdown between the claim and the finalisation leaves the batch `in_flight` — the reaper proposed above is the safety net, but the clean path should release its own claims.
What breaks in production: every deploy delays up to `BATCH_SIZE` deliveries by the full reaper timeout rather than milliseconds.

### Minor: `models.STATUSES` is declared and never referenced
File: `app/webhooks/models.py` — `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")`
What is wrong: the tuple is defined but no code validates against it — `status` is a plain `String(20)` with no `Enum` or `CheckConstraint` at the ORM level, and `_finish` passes raw string literals.
What breaks in production: it reads as the authoritative enumeration while enforcing nothing, which is how the migration's `'failed'` divergence survived; binding it to a `CheckConstraint` on the model would have made that a build-time failure.

### Minor (question): is `_claim_batch`'s status flip visible to a concurrent claimer before `deliver` runs?
File: `app/webhooks/delivery.py` — `_claim_batch()`
What is unclear: the flip to `in_flight` commits when `session_scope` exits, but the diff does not show `session_scope`'s isolation level or whether it commits, so whether a second worker can observe `pending` rows in the window depends on code this change does not contain.
What would close it: the definition of `app/db.session_scope` — specifically whether it commits on clean exit and at what isolation level. If it commits at `READ COMMITTED`, the `FOR UPDATE SKIP LOCKED` proposed in the lock finding is required rather than merely advisable.
