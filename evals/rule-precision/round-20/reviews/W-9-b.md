### Critical: the HMAC is computed over bytes that are never sent on the wire
File: app/webhooks/delivery.py — `send_once`; app/webhooks/signing.py — `serialize`/`sign`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys reordered) while the request body is produced by `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and original key order, so the signed byte string and the transmitted byte string are never equal.
What breaks in production: every customer who verifies the signature against the raw body they received — the only procedure documented in `docs/webhooks.md` — computes a different digest and rejects 100% of our deliveries, so the whole feature is dead on arrival for every integrator who actually checks the signature.
Fix: make the signed bytes and the sent bytes the same object. In `send_once`, build `body = serialize(delivery.payload).encode()` once, pass `content=body` (not `json=`) with an explicit `Content-Type: application/json`, and change `sign` to take that exact `bytes` rather than a dict: `def sign(secret: str, body: bytes) -> tuple[str, str]`. Keep `serialize` as the single canonicalizer so there remains exactly one definition of "the payload bytes" (do not fix this by loosening the test's `json.loads` assertion — that assertion is what must get stricter, per Remedy Floor 4; the behaviour to preserve is that the receiver still gets valid JSON with the same fields). Allow side to pin (Remedy Floor 1): a round-trip test that captures `request.content` in the `MockTransport` handler and asserts `signing.verify(SECRET, captured["body"], captured["headers"][SIGNATURE_HEADER])` is True — actual producer output through the actual verifier, per R40's reviewer action, not two independently constructed shapes. Red-prove each clause separately (Remedy Floor 2): (i) revert `content=` to `json=` and observe that round-trip assertion go red; (ii) drop `sort_keys=True` from `serialize` while leaving everything else, feed a two-key payload with keys out of order, and observe the digest change. Fail loudly (Remedy Floor 3): `serialize` must raise on a payload it cannot canonicalize — pass `allow_nan=False` and let `TypeError`/`ValueError` propagate to `deliver`, which records `failed_permanent` with the serializer's message, so "could not sign" is spelled differently from "delivered". Boundary/tie (Remedy Floor 5): the signed unit is the byte string, so two payloads that differ only in key order MUST produce the same bytes and therefore the same signature; assert that equality explicitly.

### Critical: the timestamp header is unauthenticated, so the documented replay window enforces nothing
File: app/webhooks/signing.py — `sign`; docs/webhooks.md — "Verifying the signature"
What is wrong: `sign` HMACs only the payload, but the docs tell customers the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed" — since the timestamp is outside the MAC, an attacker replaying a captured request simply rewrites `X-Acme-Timestamp` to the current second and the signature still verifies.
What breaks in production: a captured `invoice.paid` delivery can be replayed against the customer's endpoint indefinitely, and the customer's staleness check — which our own documentation told them was sufficient — never fires, which is exactly R49's Critical case of an overstated control that caused a real one to be skipped.
Fix: bind the timestamp into the MAC. `sign(secret, body)` computes `timestamp = str(int(time.time()))` then `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, and `verify(secret, timestamp, body, signature)` recomputes with the *caller-supplied* timestamp rather than a fresh one — the current `verify` regenerates its own timestamp, which is why the omission was invisible. Add the staleness check to `verify` itself with an explicit `max_age_seconds: int = 300` parameter so our reference verifier enforces what the docs promise. Allow side to pin (Remedy Floor 1): a signature produced 299 seconds ago still verifies True. Red-prove each clause separately (Remedy Floor 2): (i) verify a signature with the timestamp mutated by one second and assert False — this is the assertion that is currently unwritable and that no existing test could ever fail; (ii) freeze the clock at `t+301` and assert the same signature now verifies False for staleness while `t+299` still passes. Fail loudly (Remedy Floor 3): a missing, non-numeric, or negative timestamp argument raises rather than being coerced to 0, because a coerced 0 is always stale and would silently deny every delivery. Do not fix this by deleting the five-minute claim from the docs (Remedy Floor 4) — the window is the feature; preserve the documented `sha256=<hex>` header shape so existing integrators' parsing does not break. Boundary/tie (Remedy Floor 5): age exactly 300 seconds is accepted, 301 is rejected; two requests sharing the same second are indistinguishable to this check, which is why the timestamp is a freshness bound and not an idempotency key — `event_id` remains the dedup key as documented.

Red-prove each clause separately (Remedy Floor 2): (i) re-add `"signing_secret"` to `to_dict` and observe the GET-list test asserting `"signing_secret" not in body[0]` go red; (ii) delete the explicit merge in `create_webhook_endpoint` and observe the POST test go red. Fail loudly (Remedy Floor 3): if the endpoint row somehow has no secret at mint time, raise rather than returning a body with the key absent — "no secret was generated" must not be spelled the same as "secret withheld on read". Do not fix by deleting the documented guarantee (Remedy Floor 4); the one-shot property is the reason customers are told to store it themselves. Boundary/tie (Remedy Floor 5): the boundary is the mint response only — a re-`POST` to the same URL creates a *new* endpoint with a *new* secret rather than revealing the old one, and that must be asserted.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: the secret is built from `random.choice`, which draws from the Mersenne Twister — a deterministic generator whose internal state is recoverable from a modest run of its outputs and which is process-seeded, not entropy-backed.
What breaks in production: an attacker who obtains their own endpoint's secret (trivially, by registering one) can recover the generator state and predict the secrets minted for other organizations around the same time, then forge signed `invoice.paid` events into those customers' systems.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and `import secrets`, deleting the `random`/`string`/`_ALPHABET` imports so the unsafe primitive cannot be reached from this module at all. Rename or re-document `SECRET_BYTES = 32` — it currently names a *character count* consumed as `range(SECRET_BYTES)`, and `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which will legitimately change to the base64url expansion (43 chars for 32 bytes); update that assertion to `>= len(SECRET_PREFIX) + 40` rather than deleting it (Remedy Floor 4 — the length check is what made the misnomer visible). Allow side to pin (Remedy Floor 1): the prefix assertion and a `signing.verify` round-trip using a freshly minted secret must both still pass, so the fix is not "emit an unusable token". Red-prove each clause separately (Remedy Floor 2): (i) monkeypatch `secrets.token_urlsafe` to a constant and assert a new test — "two consecutive mints differ" — goes red; (ii) shorten `SECRET_BYTES` to 4 and assert the length-floor test goes red. Fail loudly (Remedy Floor 3): `secrets` raises `NotImplementedError` on a platform with no OS entropy source; let it propagate out of `create_webhook_endpoint` as a 500 rather than falling back to `random`, because a silently weaker secret is the failure this fix exists to prevent. Boundary/tie (Remedy Floor 5): the boundary is the entropy floor — 32 bytes, asserted; two mints colliding is the tie case and the "two consecutive mints differ" test is what names it.

### Critical: signature verification compares digests with `==`
File: app/webhooks/signing.py — `verify`, line `return expected == signature`
What is wrong: `verify` compares the recomputed digest to the supplied one with Python's short-circuiting `==`, which returns as soon as bytes differ — the exact non-constant-time comparison RS1 classifies Critical, and the same function's own docstring in `docs/webhooks.md` instructs customers to "compare it against your own computation using a constant-time comparison".
What breaks in production: any caller of `verify` (this is an exported helper, and it is what our own inbound tooling and any first-party consumer will reach for) leaks digest-prefix information through response timing, letting an attacker recover a valid signature byte by byte without ever knowing the secret.
Fix: `import hmac` is already present — return `hmac.compare_digest(expected, signature)`. Both operands must be normalized to the same type first (`str` here, since both carry the `sha256=` prefix); `compare_digest` raises `TypeError` on mixed `str`/`bytes`, so coerce at the boundary rather than inside. Allow side to pin (Remedy Floor 1): `test_verify_accepts_signature_produced_by_sign` must still pass — `compare_digest` returning True for the legitimate signature is the case that a fix which "always returns False" would break, and it is already in the suite. Red-prove each clause separately (Remedy Floor 2): (i) revert to `==` and observe a new lint/gate check for `compare_digest` in this module go red — the behavioural assertion cannot distinguish the two, which is why the gate is the check here, and RT7 requires that gate itself be mutated to prove it can fail; (ii) mutate `expected` by one character and observe `test_verify_rejects_a_signature_made_with_another_secret` stay red for the reason its output names. Fail loudly (Remedy Floor 3): a `signature` argument that is `None` or non-`str` must raise, not return False — a silent False on a malformed input is indistinguishable from a genuine rejection and hides a caller bug. Do not fix by removing the docs' constant-time instruction (Remedy Floor 4). Boundary/tie (Remedy Floor 5): the comparison is over the full prefixed string including `sha256=`, so a signature differing only in the prefix is rejected, and two identical signatures compare equal in time independent of content.

What is wrong: the query scopes only on the path parameter `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate integer endpoint ids and read other organizations' deliveries.

### Critical: endpoint URL validation admits internal targets and redirects follow them
File: app/api/routes/settings.py — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the check accepts any scheme whose name merely *begins* with `http` (`http`, `httpx`, `http-foo`) and applies no host restriction at all, and the delivery client then follows redirects, so a registered URL of `http://169.254.169.254/latest/meta-data/` — or an external host that 302s there — is fetched by the worker from inside the network perimeter.
What breaks in production: any customer turns our delivery worker into an SSRF proxy against cloud metadata, internal admin services, and `localhost`, with the response body persisted verbatim into `webhook_deliveries.response_body` by `_finish` and then readable through `GET .../deliveries` — a full request-and-read SSRF primitive. This also contradicts `docs/webhooks.md` ("Only `https://` URLs are accepted"), an R49 overstatement.

Allow side to pin (Remedy Floor 1): `https://hooks.example.com/acme` — the exact URL used by `FakeEndpoint` — must still be accepted with 201, and a public-IP host must still be delivered to; a fix measured only on its deny side is what gets an SSRF filter switched off (RT10). Fail loudly (Remedy Floor 3): DNS resolution failure at registration must 422 with "host could not be resolved" — an unresolvable host must not be silently admitted on the theory that it will fail later, and the resolver being unavailable must refuse rather than skip the check. Do not fix by dropping `response_body` capture (Remedy Floor 4) — the stored response is genuinely useful for debugging; bound it instead (see the Major finding below). Boundary/tie (Remedy Floor 5): a hostname resolving to both a public and a private address is rejected (any-private-rejects), and IPv6-mapped IPv4 loopback `::ffff:127.0.0.1` falls on the reject side.

### Critical: the unique index on `event_id` alone allows only one endpoint per event
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all sharing the same `event_id`, so the second row of any multi-endpoint fan-out violates the unique index.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: app/webhooks/delivery.py — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is `async def` and is run under `asyncio.gather`, but its retry backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, so the sleeping coroutine holds the event loop thread for the whole delay.
What breaks in production: a batch of up to `BATCH_SIZE = 100` deliveries with `MAX_ATTEMPTS = 5` serializes into up to 100 × (2+4+8+16) = 3000 seconds of fully blocked event loop, during which no other coroutine — including the HTTP responses of any process sharing the loop — makes progress, and the 60-second `LOCK_KEY` TTL expires mid-batch so a second worker starts re-delivering the same rows.
Fix: two changes, both required. Replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (`asyncio` is already imported). Then move the backoff out of the in-process loop entirely: on a retryable failure, write `status = "pending"`, `attempts = attempt`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` via a new `_reschedule(delivery_id, attempt, code, detail)` and `return`, letting the next poll pick the row up. Codebase-awareness evidence: `backoff_for` and the `next_attempt_at` column already exist and `_claim_batch` already filters on `next_attempt_at <= now` — the scheduling machinery is fully built and the in-loop `sleep` bypasses it, so this is not new infrastructure but the adoption of the path the change already contains. Allow side to pin (Remedy Floor 1): a delivery that succeeds on its first attempt must still complete in one pass with no sleep and reach `delivered` — a fix that always reschedules would satisfy every other clause. Red-prove each clause separately (Remedy Floor 2): (i) restore `time.sleep` and observe an event-loop-responsiveness test (a concurrent `asyncio.sleep(0)` task that must complete within the delay window) go red; (ii) remove the `next_attempt_at` write from `_reschedule` and observe an assertion that the retried row is not claimable before the backoff elapses go red; (iii) remove the `attempts` write and observe the attempt-count assertion go red. Fail loudly (Remedy Floor 3): if `_reschedule` cannot find the delivery row, raise rather than returning — a lost row must not be spelled the same as a successful reschedule. Do not fix by shrinking `BASE_DELAY_SECONDS` (Remedy Floor 4); the backoff is protecting the customer's endpoint and must be preserved. Boundary/tie (Remedy Floor 5): a row whose `next_attempt_at` is exactly `now` is claimable (the existing `<=` is correct and must stay `<=`); ties among equal `next_attempt_at` values are addressed by the ordering finding below.

### Critical: ORM instances are used after their session has closed
File: app/webhooks/delivery.py — `_claim_batch` (returns `rows` from inside `with session_scope()`) and `deliver` (uses `endpoint` after the `with` block exits)
What is wrong: `_claim_batch` returns `WebhookDelivery` instances after `session_scope` has committed and closed the session, and `deliver` likewise reads `endpoint.url` / `endpoint.signing_secret` in `send_once` after its own `session_scope` exited — SQLAlchemy expires instance attributes on commit, so the first attribute access on a detached instance raises `DetachedInstanceError`.
What breaks in production: the worker raises on the very first delivery it attempts, at `delivery.attempts` in `deliver` or at `endpoint.signing_secret` in `send_once`, and because `run_worker` has no handler around its loop body the process exits — no webhook is ever delivered.
Fix: stop passing ORM instances across session boundaries. Define a frozen dataclass carrying exactly what delivery needs — `DeliveryJob(id: int, endpoint_id: int, url: str, signing_secret: str, payload: dict, attempts: int)` — and have `_claim_batch` build it inside the session by joining `WebhookEndpoint` (one query instead of the current per-delivery `session.get` in `deliver`, which is also an N+1). `deliver`, `send_once` and `_finish` then take plain values and never touch a live mapper. Note this is why the existing tests cannot catch the defect: `FakeEndpoint`/`FakeDelivery` in `tests/webhooks/test_delivery.py` are plain classes with class-level attributes that are never detached, an RT1 mock-reality divergence that hides a total-path correctness failure. Allow side to pin (Remedy Floor 1): a test using the real `WebhookEndpoint`/`WebhookDelivery` models against a real session must run `_claim_batch` → `deliver` end to end and reach `delivered`; that path is what proves the fix does not merely stop raising by delivering nothing. Red-prove each clause separately (Remedy Floor 2): (i) revert `_claim_batch` to returning ORM rows and observe that end-to-end test go red with `DetachedInstanceError` named in the output; (ii) drop `signing_secret` from the dataclass and observe the signature assertion go red. Fail loudly (Remedy Floor 3): if the join finds no endpoint for a claimed delivery — possible between the claim and a concurrent endpoint delete — mark the row `failed_permanent` with "endpoint deleted" rather than skipping it silently, so an unclaimable row is never spelled as a clean batch. Do not fix by adding `expire_on_commit=False` (Remedy Floor 4): that suppresses the symptom while leaving the instances bound to a closed session and lazy relationships still failing, which is the markerless weakening R36 rejects. Boundary/tie (Remedy Floor 5): the boundary is the `with session_scope()` block — every attribute read must occur inside it or on a detached-safe value object, and a delivery claimed by one worker while another holds the same id is covered by the locking finding below.

### Major: the distributed lock is not atomic and is released by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock` and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does a `get` then a separate `set` then a separate `expire`, so two workers can both observe the key absent and both proceed; and the `finally` deletes `LOCK_KEY` unconditionally, without checking that this worker still owns it, so a worker whose 60-second TTL already expired deletes the lock a *different* worker now holds.
What breaks in production: two workers claim and deliver the same rows concurrently, doubling every customer's webhook traffic and racing the `in_flight` transition; and a crash between `set` and `expire` leaves a lock with no TTL, wedging all delivery until someone manually deletes the key.
Fix: make acquisition atomic and ownership-checked. `token = secrets.token_hex(16)`; acquire with a single `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` and return the token or `None`; release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`) passing the token, so a worker can only release its own lock. Define `LOCK_TTL_SECONDS` as a named constant and set it above the worst-case batch duration (`REQUEST_TIMEOUT` × the per-poll attempt count) rather than the current bare `60`, which is already exceeded by a single 30-second-timeout delivery pair. Allow side to pin (Remedy Floor 1): a single worker must still acquire, work, and release, then re-acquire on the next poll — a lock that never grants satisfies every other clause. Red-prove each clause separately (Remedy Floor 2): (i) replace `nx=True` with an unconditional set and observe a two-concurrent-acquirer test asserting exactly one success go red; (ii) replace the compare-and-delete with a bare `delete` and observe a test where worker A's token has been superseded by worker B's — asserting A's release is a no-op — go red; (iii) drop `ex=` and observe a TTL assertion go red. Per R49 the choice must be recorded — if this is a staged-rollout flag intended to be wired in a follow-up, that is legitimate, but the unwired state must be named in the migration as a comment so no one relies on it. Allow side to pin (Remedy Floor 1, if wiring): an org with `webhooks_enabled = TRUE` must still create endpoints and still receive deliveries — assert both, or the flag becomes a switch that only ever denies. Red-prove each clause separately (Remedy Floor 2): (i) an org with the flag FALSE gets 403 from `create_webhook_endpoint` — red if the check is removed; (ii) an org with the flag FALSE and a pre-existing active endpoint enqueues zero rows — red if the join predicate is removed. Note these are two distinct sites and one mutation cannot redden both, which is why the enqueue-side check is easy to omit. Fail loudly (Remedy Floor 3): an organization row where the column is somehow NULL must be treated as disabled, not as enabled by truthiness coercion. Boundary/tie (Remedy Floor 5): the default is FALSE, so the boundary is the migration's own backfill — state explicitly whether existing organizations are flipped to TRUE on deploy, because leaving them FALSE silently disables webhooks for every current customer once the flag is wired.

### Minor: the permanent-failure write does not check that the row still exists
File: app/webhooks/delivery.py — `_finish`, `row = session.get(m.WebhookDelivery, delivery_id)` followed immediately by `row.status = status`
What is wrong: `session.get` returns `None` when the row has been deleted — reachable via the `ON DELETE CASCADE` on `webhook_endpoints` if a customer deletes an endpoint mid-flight — and the next line dereferences it unguarded.
What breaks in production: an `AttributeError` propagates out of `deliver` through the unshielded `asyncio.gather` and terminates the worker, converting a benign concurrent delete into a total delivery outage.

### Minor: no per-attempt timeout budget relative to the lock lifetime
File: app/webhooks/delivery.py — `REQUEST_TIMEOUT = 30.0`, `LOCK_KEY` expiry of 60 seconds, `BATCH_SIZE = 100`
What is wrong: two consecutive 30-second timeouts exhaust the lock's 60-second TTL before a single delivery finishes, and a full batch cannot complete within it under any timing.
What breaks in production: the lock expires during normal operation rather than only on crash, so the mutual exclusion it provides is routinely absent — this is subsumed by the lock fix above but the constants themselves need reconciling, not just the acquisition logic.

### Minor: the secret-length test cements a misleading constant name
File: tests/webhooks/test_delivery.py — `test_new_signing_secret_has_prefix_and_length`; app/webhooks/signing.py — `SECRET_BYTES = 32`
What is wrong: `SECRET_BYTES` is consumed as `range(SECRET_BYTES)` over a character alphabet, so it names a character count, and the test asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, locking the misnomer in as the contract; there is also no assertion anywhere that two mints differ.
