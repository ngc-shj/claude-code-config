### Critical: `list_deliveries` has no tenancy filter — any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query is keyed only on the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while the two sibling routes added in the same hunk (`create_webhook_endpoint`, `list_webhook_endpoints`) both scope on `user.org_id` — the tenancy pattern was propagated to two of three new sites (R3, security-relevant).
What breaks in production: Any logged-in customer can enumerate integer endpoint IDs and read another tenant's delivery rows, whose `to_dict` exposes `event_type` and whose underlying `payload` column holds invoice and subscription data.
Fix: Join through the endpoint and filter on the caller's org in the same query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403, to avoid confirming existence) when the endpoint row is absent or belongs to another org. Deny side and allow side both pinned: a test where org B requests org A's `endpoint_id` must get 404 **and** assert the returned list is empty rather than only asserting the status (RT8 — status-only is vacuous here because the handler returns a list, and an empty list is also what a legitimate empty endpoint returns, so the allow fixture must return a non-empty list to make the deny assertion non-degenerate); a second test where the owning org requests its own endpoint must still return its rows, so a fix that filters everything out is caught. Red-prove each clause separately by execution: (a) delete the `org_id` predicate → the cross-tenant test reds; (b) change the join to `WebhookEndpoint.id == WebhookEndpoint.id` → the same test reds for a different reason; (c) invert the predicate to `!= user.org_id` → the owner test reds. Fail loudly when the check cannot run: if `user.org_id` is `None` the handler must raise, not query with `org_id IS NULL`. Preserve: the `order_by(created_at.desc())` ordering and the `limit`, which are the feature's point. Boundary and tie: an endpoint whose `org_id` equals the caller's is IN; two endpoints sharing a `created_at` tie must still be ordered deterministically — see the cursor finding below.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`, `sign(...)` paired with `client.post(..., json=delivery.payload)`
What is wrong: `sign` computes the MAC over `signing.serialize(payload)` (`json.dumps(payload, sort_keys=True)`, default `", "`/`": "` separators) while httpx re-serializes the same dict itself for `json=` (no `sort_keys`, compact separators), so the signature covers a different byte string than the request body — and the change already contains the helper (`signing.serialize`) that the call site bypasses (R1 clause (d)/(e): the helper exists and is not adopted at the one site whose correctness depends on it; R40 producer/strict-consumer shape).
What breaks in production: Every customer following `docs/webhooks.md` — which specifies the MAC is over the raw request body — computes a different digest and rejects 100% of deliveries, and because a rejection is a non-2xx the worker retries all five attempts, multiplying the failure by five against every endpoint.
Fix: Serialize exactly once and send the bytes you signed. In `send_once`: `body = serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, body)` (change `sign`/`verify` to take `bytes` so the encoding decision has one owner), then `await client.post(endpoint.url, content=body, headers={**headers, "Content-Type": "application/json"})`. Delete the `json=` path outright rather than leaving both (R1 (d)). Pair deny with allow: the round-trip test must feed the **actual** captured `request.content` through the **actual** `signing.verify` and assert True (allow side), alongside a case where one byte of the captured body is flipped and `verify` returns False (deny side) — two independently-mocked shapes do not discharge this (R40 reviewer action). Red-prove each clause by execution, one mutation each: (a) restore `json=delivery.payload` while keeping the signature over `serialize(...)` → the allow assertion reds; (b) drop `sort_keys=True` from `serialize` → the allow assertion reds on a payload with keys out of order (`{"b":2,"a":1}`, which the existing `test_verify_accepts_signature_produced_by_sign` already uses); (c) remove the explicit `Content-Type` header → the header assertion reds. Fail loudly: if `serialize` raises on a non-JSON-serializable payload, `send_once` must surface a named `WebhookPayloadError` and mark the delivery `failed_permanent`, not fall through to an unsigned or retried request. Preserve: `Content-Type: application/json` and the `User-Agent`, which receivers route on. Boundary and tie: a payload of `{}` must still produce a signature over `b"{}"` and verify, and two payloads differing only in key order must produce the **same** signature under `sort_keys=True` — state that equality explicitly, because it is the property receivers who re-serialize will rely on.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`, `return timestamp, "sha256=" + mac.hexdigest()`
What is wrong: `docs/webhooks.md` states the signature is `HMAC-SHA256` of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed", but the implementation feeds only the body into the MAC, leaving `X-Acme-Timestamp` an unauthenticated attacker-controlled header (R49 clause (2): the doc claims a boundary the code does not implement; R29 rationale accuracy).
What breaks in production: An attacker who captures one signed request can replay it forever by rewriting the timestamp header to `now`, and the signature still verifies — the documented anti-replay control is decorative, and customers have been told to rely on it instead of building their own.
Fix: Make the MAC input the documented string: `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, with `verify(secret, body, timestamp, signature)` taking the timestamp as an explicit argument rather than regenerating it (the current `verify` calls `sign` and discards the fresh timestamp, which is why the omission is invisible to the existing tests). Pair deny with allow: a request signed at `T` and verified at `T` passes; the same bytes with the header rewritten to `T+3600` fails. Red-prove each clause separately by execution: (a) drop the `f"{timestamp}."` prefix from the MAC input → the rewritten-timestamp test goes green, i.e. reds the deny assertion; (b) verify with a timestamp one second off the signed one → the allow assertion reds, proving the timestamp is genuinely bound; (c) pass a non-numeric timestamp → the loud-failure assertion below reds if it silently returns False. Fail loudly: `verify` must raise a named `SignatureFormatError` when the timestamp is absent or not an integer string, so "could not evaluate freshness" is not spelled the same as "signature did not match". Preserve: the `sha256=` prefix and the two header names, which are already in the published docs. Boundary and tie: define the window as accept when `now - ts <= 300`, reject when `> 300` — exactly 300 seconds old is accepted — and state that a future-dated timestamp beyond a small clock-skew allowance (say 60s) is rejected, since an unbounded future timestamp reopens the replay window from the other side.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The secret that keys every outbound HMAC is drawn from `random`, a Mersenne Twister seeded from process state and fully reconstructible from ~624 observed outputs, rather than from `secrets`.
What breaks in production: An attacker who registers a handful of their own endpoints observes secrets from the same generator stream, recovers the PRNG state, and predicts other tenants' signing secrets — at which point they can forge events into any customer's webhook receiver, including `invoice.paid`.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`, `string`, and `_ALPHABET` imports so the weak path cannot be reintroduced by a merge. Rename `SECRET_BYTES` honestly: it currently governs a **character** count over a 62-symbol alphabet, so the existing test `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` will red under `token_urlsafe` — that is correct, and the test must be rewritten to assert entropy-relevant properties (prefix present; decoded length `>= 32` bytes) rather than being loosened to make the old assertion pass (Remedy Floor 4: do not fix by deleting what made the defect visible). Pair deny with allow: a static check (`grep -n 'random\.' app/webhooks/signing.py` in CI, or a Ruff `S311` rule scoped to this module) must FAIL the build when `random.` reappears, and must PASS on the corrected file — pin both directions. Red-prove each clause by execution: (a) reinstate `random.choice` → the static check reds; (b) drop `SECRET_PREFIX` → the prefix assertion reds; (c) shorten to `token_urlsafe(8)` → the length assertion reds. Fail loudly: if the static check's tool is missing or non-executable, CI must exit non-zero with a message naming the missing tool — "examined nothing" must not report PASS (R50 clause ii). Preserve: the `whsec_` prefix, which customers key their secret managers on. Boundary and tie: state that existing rows minted by the weak generator are compromised and need a rotation migration — a fix that only changes the generator leaves every already-issued secret predictable.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The MAC comparison uses Python's short-circuiting string equality instead of `hmac.compare_digest`, in the very helper that `docs/webhooks.md` tells customers to implement with "a constant-time comparison" (RS1; R49 — the doc claims a property the shipped reference does not have).
What breaks in production: This function is the reference implementation customers copy, and any server-side use of it leaks the expected digest byte-by-byte to an attacker who can time repeated verification attempts, allowing signature forgery without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, after normalizing both to `str`. Pair deny with allow: keep the two existing behavioural tests — `test_verify_accepts_signature_produced_by_sign` (allow) and `test_verify_rejects_a_signature_made_with_another_secret` (deny) — and add a source-level assertion that `signing.py` contains no `==` or `!=` on a signature-shaped name, so the behavioural pair cannot go green over a timing-unsafe body. Red-prove each clause separately by execution: (a) revert to `expected == signature` → the source-level check reds while both behavioural tests stay green, which is the whole point of adding it; (b) mutate `expected` to `expected[:-1]` → the allow test reds; (c) mutate to `compare_digest(expected, expected)` → the deny test reds. Fail loudly: raise a named `SignatureFormatError` when `signature` is `None`/non-`str`/empty rather than returning `False`, so a receiver that forgot to read the header cannot mistake a missing signature for a wrong one. Preserve: `verify` must keep returning a plain `bool` for the matched/unmatched case — callers branch on it. Boundary and tie: `compare_digest` on operands of different length returns `False` without an early exit; say so, because that is the case a reader will assume still leaks.

### Critical: `GET /webhook-endpoints` returns every endpoint's signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry
What is wrong: `to_dict` embeds the raw signing secret and is used by both `create_webhook_endpoint` and `list_webhook_endpoints`, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards"); the sibling `WebhookDelivery.to_dict` in the same file exposes no secret, so the leak is one of two `to_dict` implementations (R3 cross-cutting).
What breaks in production: The secret is returned on every list call and therefore lands in browser history, CDN/proxy access logs, API-client debug traces, and any support tooling that pretty-prints responses — and because the docs promise it is unreadable, no rotation flow exists to recover from the exposure.
Fix: Remove `signing_secret` from `to_dict` and return it exactly once, as an extra key merged in by `create_webhook_endpoint` only (`{**endpoint.to_dict(), "signing_secret": secret}` built from the local variable, not read back off the model). Pair deny with allow: assert `GET /webhook-endpoints` responses contain no key or value matching `whsec_` (deny), **and** assert the `POST` response still contains the secret exactly once (allow) — a fix that strips it from both breaks the only way a customer can ever obtain it. Red-prove each clause separately by execution: (a) re-add `"signing_secret"` to `to_dict` → the list-response test reds; (b) remove the merge in the create handler → the create-response test reds; (c) return the secret from a re-read of `endpoint.signing_secret` after the write instead of the local → add a rotation test that changes the stored value and observe which assertion reds. Fail loudly: if `new_signing_secret()` returns a value not matching `^whsec_`, the handler must raise before `session.add`, so a misconfigured generator cannot persist an endpoint with an unusable secret. Preserve: the `id`/`url`/`event_types`/`active` fields, which the settings UI reads. Boundary and tie: state that the secret is present in the 201 body and absent from every subsequent representation — including the deliveries route, which must not gain it.

### Critical: no destination validation plus `follow_redirects=True` makes the worker a full SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`, together with `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check on a customer-supplied destination is a prefix test on the URL scheme string, which admits plain `http://` (the docs say "Only `https://` URLs are accepted") and any scheme merely beginning with those four characters, and nothing rejects loopback, link-local, or RFC1918 hosts — judging the notation instead of resolving the address through the mechanism the runtime uses (R47; the redirect follower means even a validated public host can bounce the request inward).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or a public host that 302s there) and the worker POSTs from inside the VPC and stores the response in `webhook_deliveries.response_body`, turning the delivery log into an exfiltration channel for cloud instance credentials; over plain `http` the signed payloads and headers also cross the network in cleartext.
Fix: Replace the prefix test with `parsed.scheme == "https"` (exact match, matching the published doc), then resolve the hostname with `socket.getaddrinfo` at registration time and reject when any returned address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved`; set `follow_redirects=False` on the client and treat a 3xx as a permanent failure with a message naming the redirect target. Because DNS can be re-pointed between registration and delivery, re-apply the same address check in the transport at connect time (an `httpx` transport wrapper that inspects the resolved peer) rather than trusting the registration-time result. Pair deny with allow: `https://hooks.example.com/acme` (the docs' own example, already the fixture in `tests/webhooks/test_delivery.py`) must still register and deliver; `http://hooks.example.com`, `https://127.0.0.1/x`, `https://metadata.internal` resolving to 169.254.0.0/16, and a public host returning a 302 to `http://127.0.0.1/` must each be rejected. Red-prove each clause separately by execution: (a) relax back to `startswith("http")` → the `http://` deny test reds; (b) delete the private-address predicate → the loopback deny test reds; (c) restore `follow_redirects=True` → the redirect deny test reds; (d) invert the predicate to reject public addresses → the `hooks.example.com` allow test reds. Fail loudly: when `getaddrinfo` raises or returns no addresses, reject the registration with a 422 naming DNS resolution as the reason — an unresolvable host must not be admitted as "no private address found" (R50 clause ii, and the reason R47 says an unconsultable interpreter means the control is not a boundary). Preserve: legitimate public HTTPS endpoints behind CDNs, which is why the check is on resolved addresses and not on a hostname denylist. Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv6 `::1`/`fc00::/7` fall on the reject side; a host resolving to both a public and a private address is rejected — any-private, not all-private.

### Critical: the migration's status CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES = (..., "failed_permanent")`
What is wrong: The DDL enumerates `'failed'` while both `models.STATUSES` and `delivery._finish(delivery.id, "failed_permanent", ...)` use `failed_permanent`, so the value the code writes on exhaustion is the one value the constraint forbids (R55/R12 — the enum has four members in two places and they do not agree).
What breaks in production: The first delivery to exhaust its retries raises a `CheckViolation` inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and the exception propagates through `asyncio.gather` and kills the worker loop — a single unreachable customer endpoint stops all webhook delivery.
Fix: Change the DDL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive both sides from one place — have the migration's list be generated from, or asserted equal to, `models.STATUSES` by a test that imports the tuple and greps the `.sql` file, so the next added status cannot drift again. Pair deny with allow: a test that inserts each member of `STATUSES` against the real migrated schema must succeed (allow), and one that inserts `'bogus'` must raise `IntegrityError` (deny) — a fix that simply drops the CHECK satisfies the first and fails the second, which is why both are required. Red-prove each clause separately by execution: (a) revert the DDL to `'failed'` → the `failed_permanent` insert test reds; (b) drop the CHECK entirely → the `'bogus'` rejection test reds; (c) add a fifth member to `STATUSES` without touching the SQL → the equality test reds. Fail loudly: the equality test must fail with a message naming the symmetric difference when it cannot locate the CHECK clause in the file at all, rather than passing because its regex matched nothing. Preserve: the constraint itself — the point is a checked enum, not an unchecked column. Boundary and tie: state that this migration has not shipped, so amending the DDL in place is correct; if it has, the follow-up is `ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ... NOT VALID` plus a backfill of any `'failed'` rows.

### Critical: `UNIQUE INDEX ... (event_id)` permits only one delivery row per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` builds one `WebhookDelivery` per matching endpoint and `session.add_all(rows)`, but the unique index is on `event_id` alone, so the second row of that batch collides with the first.
What breaks in production: Any organization with two or more active endpoints subscribed to the same event gets an `IntegrityError` on flush; because `dispatch` wraps the enqueue in `except Exception: log.warning(...)`, the event is committed and every endpoint including the first silently receives nothing, with only a warning line as evidence.
Fix: Replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint that actually expresses the intended idempotency ("deduplicate on `event_id`" per endpoint, as `docs/webhooks.md` describes to receivers). Pair deny with allow: a test enqueuing one event for an org with two active endpoints must produce two rows (allow), and a second enqueue of the same `event_id` for the same endpoint must not add a third (deny). Red-prove each clause separately by execution: (a) restore the single-column index → the two-endpoint test reds; (b) drop the index entirely → the duplicate-enqueue test reds; (c) make the index non-unique → the same duplicate test reds. Fail loudly: `enqueue_for_event` must catch `IntegrityError` specifically and re-raise a named `WebhookEnqueueConflict` rather than letting the generic `except Exception` in `dispatch` swallow it (see the swallowed-enqueue finding). Preserve: at-most-once enqueue per endpoint per event, which is what the docs promise receivers. Boundary and tie: two endpoints of the same org registered with identical URLs are distinct rows under this key and both receive the event — state it, because the alternative reading (dedup by URL) is what someone will "fix" it to next.

### Critical: `time.sleep` inside an async coroutine blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: The retry backoff uses the blocking `time.sleep` inside an `async def` that `run_worker` schedules through `asyncio.gather`, so the sleeping coroutine freezes the whole loop rather than yielding.
What breaks in production: One slow endpoint stalls all 100 concurrent deliveries in the batch and the worker's own poll loop for up to 2+4+8+16 = 30 seconds per failing delivery, so a single misbehaving customer serializes and delays every other tenant's webhooks, and the 60-second Redis lock expires mid-batch while the process is unresponsive.
Fix: `await asyncio.sleep(delay)` — `asyncio` is already imported in this module, so no new dependency. The real repair is larger and should land with it: the in-process `while True` retry loop should be replaced by persisting `next_attempt_at = now + backoff_for(attempt)` and `status = "pending"`, returning immediately and letting the poll loop re-claim — the `next_attempt_at` column and its `order_by` already exist in the model and are currently write-once, so the scheduling machinery is present and unused (R1 (e): the hand-rolled inline loop reimplements the durable scheduler this change already built). Pair deny with allow: a test asserting the loop stays responsive (a second coroutine scheduled alongside a delivery that backs off must complete during the backoff window) plus a test asserting that a delivery that fails once and then succeeds is still marked `delivered` — a fix that removes retries entirely would pass the first and fail the second. Red-prove each clause separately by execution: (a) restore `time.sleep` → the responsiveness test reds; (b) set the persisted `next_attempt_at` to `now` instead of `now + backoff` → assert the row is not re-claimed before the delay elapses and observe it red; (c) stop persisting `attempts` → the "gives up after MAX_ATTEMPTS" test reds. Bound the responsiveness test with a real timeout so a regression reds rather than hangs. Fail loudly: if `backoff_for` returns a non-positive or non-finite delay, raise rather than sleeping zero and hot-looping. Preserve: the 5-attempt ceiling and the 2/4/8/16 schedule, which are documented and asserted. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (the existing `<= now` filter), and two rows with the same `next_attempt_at` need a deterministic tiebreak — see the ordering finding.

### Major: `in_flight` is a non-terminal state with no reclaim path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish`
What is wrong: `_claim_batch` moves rows to `in_flight` and only `_finish` moves them out, so any worker crash, deploy, `asyncio.gather` abort, or exception between claim and finish leaves the row wedged in a state no query ever selects again — `_claim_batch` filters on `status == "pending"` only (R38 mode 1: an async transition with no failure-exit and no timeout).
What breaks in production: A single restart during a batch permanently loses up to 100 deliveries with no alert and no operator affordance to recover them, and the customer sees a gap in their event stream that the deliveries UI reports as `in_flight` forever.
Fix: Add a `claimed_at TIMESTAMPTZ` column set at claim time and a reaper that returns rows with `status = 'in_flight' AND claimed_at < now() - interval '10 minutes'` to `pending` with `attempts` unchanged and `next_attempt_at = now()`; wrap the per-delivery work in `try/except BaseException` that calls `_finish(..., "pending", ...)` on unexpected failure so the common case never needs the reaper. Pair deny with allow: a test that kills a delivery mid-flight and asserts the row is reclaimed and eventually delivered (allow — the recovery must actually work), and a test that a row claimed 10 seconds ago is **not** reclaimed (deny — the reaper must not steal live work and cause duplicate sends). Red-prove each clause separately by execution: (a) remove the reaper query → the recovery test reds; (b) set the reap threshold to 0 → the not-yet-stale test reds; (c) remove the `except BaseException` handler → the crash-recovery test reds at the fast path. Fail loudly: the reaper must log a counted, named event per reclaimed row (`webhook.delivery.reclaimed`) so silent recovery is still visible; if it cannot connect, it must exit non-zero rather than report zero reclaims. Preserve: exactly-one-worker-per-row while a claim is live — the point of `in_flight` is to prevent duplicate sends, and the reaper must not undo that. Boundary and tie: a row whose `claimed_at` is exactly the threshold is NOT reclaimed (strict `<`), and a row reclaimed concurrently by two reapers must be guarded by `UPDATE ... WHERE status = 'in_flight'` returning a row count, not a read-then-write.

### Major: the Redis lock is acquired with a non-atomic get-then-set and released without ownership
File: `app/webhooks/delivery.py` — `_acquire_lock`, and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` followed by `set` is two round trips with an interleaving window, `expire` is a third call so a crash between `set` and `expire` leaves a lock with no TTL, and `delete` is unconditional so a worker whose 60-second TTL already expired deletes the successor's lock.
What breaks in production: Two workers claim overlapping batches and send duplicate webhooks, or a crashed worker wedges the key with no TTL and all delivery stops until someone deletes it by hand.
Fix: One atomic call — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` is unique per acquisition — and release via a Lua compare-and-delete (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so only the owner releases. Set `LOCK_TTL_SECONDS` from the worst-case batch duration (`BATCH_SIZE` × `REQUEST_TIMEOUT` is 3000s today, which is the real finding: 60 is far below it) or renew the lock periodically while the batch runs. Pair deny with allow: a second acquirer while the lock is held must get `False` (deny), and an acquirer after the TTL elapses must get `True` (allow) — a fix that never releases satisfies the first and breaks the second. Red-prove each clause separately by execution: (a) drop `nx=True` → the contention test reds; (b) drop `ex=` → the after-expiry test reds (assert the key has a TTL, `ttl > 0`, not merely that it exists); (c) replace the compare-and-delete with a plain `delete` and have worker A release after B acquires → the ownership test reds. Fail loudly: if `set` returns `None`/raises, `_acquire_lock` must propagate a named error and the loop must back off — a Redis outage must not be indistinguishable from "another worker holds the lock" forever, because that is a silent total stop. Preserve: single-writer semantics across workers, which is the lock's purpose. Boundary and tie: state that the lock is best-effort (R49 class (c) — Redis TTL expiry under a GC pause still admits two holders), which is exactly why the reaper and the per-row `UPDATE ... WHERE status` guard above are the actual correctness boundary.

### Major: one failing delivery aborts the batch and kills the worker loop
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` without `return_exceptions=True` propagates the first exception, and there is no `try/except` around the loop body, so any unhandled error (the `CheckViolation` above, a `None` row in `_finish`, a DNS failure outside `httpx.HTTPError`) escapes `while True` and terminates the coroutine.
What breaks in production: The delivery worker exits on the first unexpected error and every webhook stops silently until someone notices the process is idle; the sibling deliveries in the batch are left `in_flight` and, per the finding above, unreclaimable.
Fix: `results = await asyncio.gather(*(deliver(client, d) for d in batch), return_exceptions=True)`, then iterate `results` and for each `BaseException` log it with the delivery id and route the row back to `pending` via the same recovery path; wrap the whole loop body in `try/except Exception` with a bounded backoff so the loop survives a transient DB or Redis outage.
