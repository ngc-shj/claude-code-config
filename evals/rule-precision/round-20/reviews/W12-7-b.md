### Critical: `list_deliveries` has no tenancy filter — any org can read any other org's delivery history
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: The query filters only `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while its sibling `list_webhook_endpoints` in the same diff hunk does filter on `org_id`, so `endpoint_id` is a caller-supplied integer that addresses every tenant's rows.
What breaks in production: Any authenticated user can enumerate `endpoint_id` 1..N and read other organizations' event types, event ids, delivery status and upstream response codes — a cross-tenant data leak reachable with a single incrementing loop.
Fix: Resolve the endpoint under the tenancy predicate first and 404 when it does not resolve — `endpoint = session.query(WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`; `if endpoint is None: raise HTTPException(404, "endpoint not found")` — then query deliveries on `endpoint.id`. Return 404 (not 403) so the response does not disclose existence. Preserve the existing ordering and `limit` behaviour for the owning caller. Pin both directions: a test where the owning user gets its rows back (allow side — a fix that always 404s satisfies every other clause), and a test where a user of org B receives 404 with an empty body for org A's `endpoint_id`. Red-prove each clause separately by execution: (i) delete the `org_id` predicate — the org-B test must go from 404 to 200-with-rows; (ii) change the `one_or_none()` miss branch to `pass` — the org-B test must fail on an unhandled `AttributeError` rather than silently returning `[]`. Fail loudly when the check cannot run: `endpoint_id` that is not resolvable, and a `user.org_id` that is `None`, must both raise, never fall through to an unfiltered query. Boundary and tie: an endpoint whose row exists but whose `org_id` is NULL falls on the deny side; an endpoint soft-deleted or `active=False` still belongs to its org and stays on the allow side, because the endpoint is the tenancy key and `active` is not an authorization flag.

### Critical: the signature is computed over bytes that are never transmitted, and over a different string than the docs specify
File: app/webhooks/signing.py — `sign`; app/webhooks/delivery.py — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys sorted) while `send_once` transmits the body via `client.post(..., json=delivery.payload)`, which httpx encodes with compact separators and no key sorting — so the bytes the receiver hashes can never equal the bytes we hashed — and `docs/webhooks.md` tells integrators to HMAC `"{timestamp}.{raw_request_body}"`, a third string that neither side produces.
What breaks in production: Every customer who implements the published verification algorithm rejects 100% of our deliveries, and every customer who instead hashes the raw body they received also rejects 100% of them, so the feature fails totally and silently — our side records 2xx-or-4xx from their endpoint and reports the deliveries as normal.
Fix: Serialize once and sign what you send. In `sign`, take the already-encoded body: `def sign(secret: str, body: bytes) -> tuple[str, str]` computing `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`. In `send_once`, build `body = serialize(delivery.payload).encode()` using the existing `signing.serialize` helper the change already contains, then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` — never `json=`, which re-encodes. Update `verify` and `docs/webhooks.md` to the same one sentence. Preserve the useful property the docs promise, canonical key ordering, by keeping `sort_keys=True` inside `serialize` — do not fix this by deleting the canonicalization. Pin the allow side: a round-trip test that feeds the ACTUAL captured `request.content` from `httpx.MockTransport` into `verify` with the same secret and asserts True (R40 requires actual producer output through the actual consumer, not two mocked shapes). Red-prove each clause separately by execution: (i) revert `content=body` to `json=delivery.payload` — the round-trip test must red; (ii) drop `sort_keys=True` from `serialize` — a test signing `{"b":2,"a":1}` and verifying against the same dict built as `{"a":1,"b":2}` must red; (iii) remove the `f"{timestamp}."` prefix — the replay test in the next finding must red. Fail loudly when the check cannot run: a payload that is not JSON-serializable must raise at `serialize` before any HTTP call, not be caught into a retry. Boundary and tie: state that the signed string is exactly `timestamp + "." + body` with no trailing newline, and that two deliveries whose bodies are byte-identical but whose timestamps differ produce different signatures.

### Critical: the timestamp header is not covered by the MAC, so the documented replay window is unenforceable
File: app/webhooks/signing.py — `sign` / `verify`; docs/webhooks.md — "Verifying the signature"
What is wrong: `sign` returns `timestamp` and a MAC computed only over the payload, so `X-Acme-Timestamp` is an unauthenticated attacker-editable field, and `verify` — the reference implementation we ship — never looks at a timestamp at all, while the docs assert "that window is what stops a captured request from being replayed".
What breaks in production: Anyone who captures one delivery (from our own INFO logs, a proxy, or the customer's own ingress) can replay it forever by rewriting the timestamp header to `now`, because the signature stays valid — and the doc has already told the integrator that the timestamp check is what makes replay impossible, so no second control was built (R49: a claim relied on elsewhere as the boundary).
Fix: Bind the timestamp into the MAC as in the previous finding, and give `verify` the full contract: `def verify(secret, timestamp: str, body: bytes, signature: str, *, tolerance_seconds: int = 300) -> bool` that (a) rejects a non-integer timestamp, (b) rejects when `abs(int(time.time()) - int(timestamp)) > tolerance_seconds`, and (c) compares with `hmac.compare_digest`. Declare the control class at the artifact in a docstring: this is a fail-closed verification gate over a five-minute window, and state its known residual — a replay inside the window is not prevented by the signature and needs consumer-side dedup on `event_id`, which is what the "Retries" section of the doc should point at. Preserve the existing convenience of `sign` returning the timestamp so callers do not have to source their own clock. Pin the allow side: a fresh delivery with a correct signature verifies True — a `verify` that always returns False satisfies every other clause. Red-prove each clause separately by execution: (i) rewrite the timestamp on a captured tuple to `now` and assert `verify` is False (this reds today); (ii) set the tolerance branch to `pass` and assert an 800-second-old delivery flips to True; (iii) feed a non-numeric timestamp and assert `verify` returns False rather than raising `ValueError` out to the caller. Fail loudly when the check cannot run: a missing or empty timestamp/signature header must return False, never be treated as "no timestamp supplied, skip the window check". Boundary and tie: a delivery exactly `tolerance_seconds` old is ACCEPTED (`>` not `>=`), and a future-dated timestamp is subject to the same symmetric bound via `abs`, so a customer whose clock is four minutes fast still verifies.

### Critical: HMAC comparison in `verify` is not constant-time
File: app/webhooks/signing.py — `verify`, `return expected == signature`
What is wrong: The shipped reference verifier compares two MACs with Python's `==`, which short-circuits on the first differing byte, while the docs in the same change instruct integrators to "compare it against your own computation using a constant-time comparison" — the code contradicts its own published guidance (RS1).
What breaks in production: An attacker who can submit candidate signatures to any consumer that copied our `verify` (and to any of our own future inbound uses of it) recovers a valid MAC byte-by-byte from response-time differences, forging deliveries without ever knowing the signing secret.
Fix: `return hmac.compare_digest(expected, signature)`, with `signature` coerced to `str` and rejected as False when it is not a `str` (an off-type value from a header dict makes `compare_digest` raise `TypeError`). Preserve the `"sha256="` prefix in both operands so the comparison stays over equal-length strings rather than stripping it and losing the algorithm binding. Pin the allow side: the correct signature still returns True — `return False` satisfies every other clause here. Red-prove each clause separately by execution: (i) revert to `==` and assert that a timing-harness test over 10k trials with a first-byte-wrong candidate versus a last-byte-wrong candidate shows a measurable delta, or, if a timing assertion is too flaky for CI, assert statically that `compare_digest` appears in the function via the repo's own `check-timing-safe.sh` gate; (ii) pass a `bytes` signature and assert False rather than an escaping `TypeError`. Fail loudly when the check cannot run: a `secret` of `None` or `""` must raise at the boundary, not silently produce a MAC over an empty key that both sides can compute. Boundary and tie: two candidate signatures of different lengths must return False without leaking the length via an early exit — `compare_digest` handles this, `==` does not.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: app/webhooks/signing.py — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The HMAC key for every customer endpoint is drawn from `random.choice`, i.e. the Mersenne Twister, which is not cryptographically secure and whose internal state is recoverable from a modest run of observed outputs (R1: a security primitive reimplemented instead of using the standard `secrets` helper).
What breaks in production: An attacker who registers a handful of their own endpoints observes consecutive PRNG outputs (the secret is returned in the create response), reconstructs the generator state, and predicts the signing secret issued to any other organization — after which they can forge webhooks that every customer's verifier accepts as genuine, including `invoice.paid` events.
Fix: `import secrets` and `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`; rename `SECRET_BYTES` to say what it now means (32 bytes of entropy, ~43 characters) and delete the now-unused `_ALPHABET` and `random`/`string` imports, since a partial migration that leaves `random` imported invites the next author to reuse it. Preserve the `whsec_` prefix, which the docs and the test both depend on for identifying the key type. Pin the allow side: a generated secret still starts with `SECRET_PREFIX` and still round-trips through `sign`/`verify`. Red-prove each clause separately by execution: (i) revert to `random.choice` and assert a test that seeds `random.seed(0)`, generates two secrets, re-seeds, and generates two more, finds them equal — that test reds against `secrets` and greens against `random`, and it is the only shape that distinguishes the two; (ii) assert `len(new_signing_secret()) >= len(SECRET_PREFIX) + 40` so a truncation regression reds. Fail loudly when the check cannot run: nothing in this function may fall back to `random` if `secrets` is unavailable — that import failing must crash startup. Boundary and tie: fix the existing test `test_new_signing_secret_has_prefix_and_length`, which asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` and therefore encodes the character-count-as-bytes confusion; it must assert the new length or it reds for the wrong reason. Note this secret is also the value leaked by the `to_dict` and logging findings below, so rotating after this fix requires a rotation path that does not yet exist.

### Critical: the migration's status CHECK constraint does not contain the value the code writes
File: migrations/0042_webhook_delivery.sql — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; app/webhooks/delivery.py — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: The migration spells the terminal failure state `'failed'` while `app/webhooks/models.py:STATUSES` and `delivery.deliver` both write `"failed_permanent"`, so the producer's enum spelling diverges from the strict consumer that is the database constraint (R40).
What breaks in production: The first delivery to exhaust `MAX_ATTEMPTS` raises an `IntegrityError` inside `_finish`, which is not caught, so the exception escapes `deliver`, propagates through `asyncio.gather` and kills `run_worker` — and because the row was already set `in_flight` by `_claim_batch` and is never reset, that delivery plus every sibling in the batch is permanently stuck.
Fix: Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `models.STATUSES` the single source by generating the constraint from it, or at minimum add a test that asserts the constraint's value set equals `STATUSES` by reading the migration file — the tuple is currently defined and referenced nowhere, which is what let the two drift. Preserve the CHECK constraint itself; do not "fix" this by dropping the constraint, which would remove exactly the thing that would have made the divergence visible. Pin the allow side: a delivery that succeeds still writes `'delivered'` and commits — a fix that widens the CHECK to allow anything satisfies every other clause. Red-prove each clause separately by execution against a real Postgres, not a mock: (i) write `'failed_permanent'` before the migration fix and observe the `IntegrityError`, then after the fix observe the commit; (ii) write `'bogus'` after the fix and assert it still raises, proving the constraint is still enforcing. Fail loudly when the check cannot run: `_finish` must wrap the write and re-raise with the delivery id in the message rather than letting a bare `IntegrityError` reach `gather`. Boundary and tie: state the migration's ordering constraint — if any `webhook_deliveries` rows already exist with `'failed'` from a partial rollout, the constraint change needs an `UPDATE ... SET status='failed_permanent' WHERE status='failed'` inside the same `BEGIN`/`COMMIT` block before the CHECK is replaced, or the ALTER itself fails.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness is on `event_id` alone, but `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint and `session.add_all(rows)`, so any organization with two active subscribed endpoints inserts two rows carrying the same `event_id` and violates the index.
What breaks in production: The insert raises, the exception is caught by the bare `except Exception` in `app/events/dispatcher.py` and downgraded to a `log.warning`, so an org with two endpoints silently receives NO webhooks at all — not one, not the first — for every `invoice.paid` and `subscription.updated` event, and the only trace is a warning line; this also directly contradicts `docs/webhooks.md`, which tells customers "delivery is at-least-once, so deduplicate on `event_id`".
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)` — this is the pair that actually expresses the intended idempotency ("one delivery of one event to one endpoint") and it keeps the useful property the current index was reaching for, so do not fix this by dropping uniqueness altogether. Add `ON CONFLICT (endpoint_id, event_id) DO NOTHING` semantics at the insert so a redelivered event is a no-op rather than a 500. Pin the allow side: an org with two active endpoints subscribed to `invoice.paid` gets exactly two rows, one per endpoint — a fix that drops the index satisfies every other clause and loses the idempotency guarantee. Red-prove each clause separately by execution against a real Postgres: (i) insert two rows with the same `(event_id)` and different `endpoint_id` and assert both land after the fix and only one lands before it; (ii) insert the same `(endpoint_id, event_id)` twice and assert the second is rejected/ignored, proving the constraint is still live. Fail loudly when the check cannot run: `enqueue_for_event` must let an `IntegrityError` that is not the expected conflict propagate rather than being absorbed by the dispatcher's blanket handler (see the dispatcher finding). Boundary and tie: an endpoint deleted and re-created gets a new `endpoint_id`, so the same `event_id` legitimately produces a new row — state that this is intended and that dedup is per-endpoint-instance, not per-URL.

### Critical: SSRF — arbitrary user-supplied URLs are fetched with redirect following, and the response body is stored and readable
File: app/api/routes/settings.py — `create_webhook_endpoint`; app/webhooks/delivery.py — `run_worker` (`follow_redirects=True`) and `_finish` (`row.response_body = detail`)
What is wrong: The only validation is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://`, `http://169.254.169.254/`, `http://127.0.0.1:6379/`, `http://[::1]/` and even `http+unix://`, and the worker then POSTs to it from inside the production network with `follow_redirects=True`, storing `response.text` where the caller can retrieve the status via the deliveries endpoint (RS3: an unvalidated externally-supplied value reaching an interpreter — here the HTTP client).
What breaks in production: Any customer turns our delivery worker into a request forwarder against internal services and cloud metadata endpoints, exfiltrating the response status through the deliveries API and the response body through anyone with DB or log access; `follow_redirects=True` means even an allowlisted public host can 302 the request to `169.254.169.254`.
Fix: Validate at the schema boundary — make `EndpointIn.url` a Pydantic `AnyHttpUrl` with an explicit validator that requires `scheme == "https"` (matching `docs/webhooks.md`, which already claims https-only), rejects userinfo, and rejects a host that resolves to a private, loopback, link-local, or unique-local address using `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved` over ALL addresses returned by `socket.getaddrinfo`. Set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure. Because DNS can change between registration and delivery (TOCTOU), re-check at send time by resolving the host and pinning the connection to the checked address rather than trusting the registration-time check alone. Truncate `response.text` to a bounded prefix (e.g. 4 KiB) before persisting, and do not persist bodies from non-2xx internal-looking responses at all. Preserve the feature: customers with legitimate public HTTPS endpoints must still register and receive deliveries — that is the allow case to pin, and a validator that rejects everything satisfies every other clause. Red-prove each clause separately by execution: (i) `POST` a `http://` URL and assert 422 where it currently returns 201; (ii) `POST` `https://localhost/x` and assert 422; (iii) with `follow_redirects` restored to `True`, assert a mock endpoint returning `302 -> http://169.254.169.254/` results in a followed request, then assert it does not after the fix; (iv) `POST` a valid `https://hooks.example.com/acme` and assert 201, proving the validator is not blanket-denying. Fail loudly when the check cannot run: a hostname that fails to resolve at registration must return 422 with a named reason, never be admitted on the grounds that "we could not check it". Boundary and tie: state that a host resolving to BOTH a public and a private address is rejected (any-private-denies, not all-private-denies), and that an IPv4-mapped IPv6 form of a private address falls on the deny side.

### Critical: `time.sleep` inside `async def deliver` blocks the event loop for the whole retry window
File: app/webhooks/delivery.py — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered 100-wide by `run_worker`, but it calls the blocking `time.sleep` for its 2/4/8/16-second backoff, and the same function performs synchronous SQLAlchemy work (`session_scope()` in `_finish` and in its own endpoint lookup) inside `async def`.
What breaks in production: One failing endpoint freezes the entire worker process — all 99 sibling deliveries, the httpx connection pool, and the redis keepalive — for up to 30 seconds of backoff plus 5 × 30 seconds of request timeout, which exceeds the 60-second lock TTL and lets a second worker claim and re-send the same batch, so a payment webhook is delivered twice.
Fix: Replace the in-process retry loop with a persisted schedule, which is what the change's own unused machinery was shaped for: on a retryable failure write `attempts += 1`, `status = "pending"`, `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` and return, letting the next `_claim_batch` pick it up. Where an in-process wait remains, it must be `await asyncio.sleep(...)`. Move all `session_scope()` calls off the loop with `run_in_executor` or an async session. Preserve the retry behaviour and the `MAX_ATTEMPTS` cap — do not fix this by deleting the backoff. Pin the allow side: a delivery that succeeds on the first attempt still completes without any sleep and still writes `delivered` — a fix that removes retries entirely satisfies every other clause. Red-prove each clause separately by execution: (i) a test that gathers two `deliver` calls where the first fails once and the second succeeds, asserting via a monotonic clock that total wall time is under the backoff sum — it reds against `time.sleep` and greens against the persisted schedule; (ii) assert `next_attempt_at` advanced by exactly `backoff_for(attempt)` after a retryable failure, which nothing asserts today; (iii) assert `attempts` is persisted after a failure, not only at the terminal state. Fail loudly when the check cannot run: a delivery whose endpoint row is missing must go to a named terminal state, not loop. Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal boundary — state that `MAX_ATTEMPTS = 5` means five sends and four sleeps, and that a row re-claimed at exactly `next_attempt_at == now` is eligible (`<=`, matching `_claim_batch`).

### Critical: the redis dispatch lock is not atomic, its TTL is set separately, and it is deleted unconditionally
File: app/webhooks/delivery.py — `_acquire_lock`, `run_worker` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: `_acquire_lock` does a GET then a separate SET (two workers both observe an empty key and both proceed), the `expire` is a third round trip (a crash between SET and EXPIRE leaves a lock with no TTL), and `run_worker` deletes the key in `finally` without checking it still owns it.
What breaks in production: Two workers process the same claimed batch and every customer receives duplicate `invoice.paid` webhooks; separately, a process killed between SET and EXPIRE wedges the entire delivery pipeline permanently with no reset path, so no webhook is ever sent again until someone manually deletes a redis key nobody has documented (R38: a persisted fail-closed wedge with no exit).
Fix: Acquire with a single atomic command carrying a fencing token — `token = secrets.token_hex(16)`; `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a Lua compare-and-delete (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can never delete a lock it does not hold. Renew the TTL while the batch runs, or set `LOCK_TTL_SECONDS` strictly greater than the worst-case batch duration (`MAX_ATTEMPTS * REQUEST_TIMEOUT` plus the backoff sum) and state that number in a comment; with the persisted-retry fix above the worst case collapses to `BATCH_SIZE`-bounded concurrency × `REQUEST_TIMEOUT`. Preserve the single-worker guarantee — do not fix this by dropping the lock and relying on `SELECT ... FOR UPDATE SKIP LOCKED` alone without also adding that clause to `_claim_batch`. Pin the allow side: a single worker still acquires, runs, and releases, and the next loop iteration reacquires — a fix that always returns False from `_acquire_lock` satisfies every other clause and silently stops all delivery. Red-prove each clause separately by execution against a real redis: (i) two concurrent `_acquire_lock` calls, assert exactly one True (this reds against the GET/SET version); (ii) acquire, then have a second identity call the release path, assert the key survives; (iii) acquire, kill before release, assert the key expires within `LOCK_TTL_SECONDS` rather than persisting. Fail loudly when the check cannot run: a redis connection error in `_acquire_lock` must raise and stop the worker with a named error, never be treated as "no lock present, proceed", which is the fail-open direction. Boundary and tie: state what happens when the TTL expires at the exact moment the batch finishes — the fenced release is a no-op and the second worker's `_claim_batch` must not see the rows, which is why `_claim_batch` needs `FOR UPDATE SKIP LOCKED` as the real mutual exclusion and the redis lock is only an optimization.

### Critical: no test can distinguish the signing implementation from one that ignores the payload
File: tests/webhooks/test_delivery.py — `test_verify_accepts_signature_produced_by_sign`, `test_verify_rejects_a_signature_made_with_another_secret`, `test_send_once_posts_the_signed_payload`
What is wrong: `verify` is implemented by calling `sign` again, so the round-trip test asserts `sign(x) == sign(x)` — an identity — and the other tests assert only the `"sha256="` prefix and the 64-character length; mutating `sign` to `hmac.new(secret.encode(), b"", hashlib.sha256)`, which authenticates nothing but the secret, leaves the entire suite green (RT7: a check that cannot be made to fail for the reason it claims; RT1: a double whose return is fixed before the call).
What breaks in production: The signing algorithm has no test that pins the payload into the MAC, which is exactly why the transmitted-bytes divergence and the unsigned timestamp both shipped — the suite reports coverage of the security control while being blind to its only security property.
Fix: Replace the self-consistency test with an independently computed expected value: hard-code a fixed secret, a fixed payload, a fixed timestamp injected via a clock parameter, and the hex digest computed once by hand (or by an independent one-liner recorded in a comment), then assert `sign` reproduces it byte-for-byte. Add a test asserting that two DIFFERENT payloads under the same secret and timestamp produce different signatures, and one asserting that the same payload under two different timestamps produces different signatures. Preserve the existing negative test — the wrong-secret case is still worth having and must not be deleted. Pin the allow side explicitly: the correct secret, payload, and timestamp verify True, so a `sign` that returns a constant reds on the negative test and a `verify` that returns False reds on this one. Red-prove each clause separately by execution, one mutation per assertion: (i) `hmac.new(secret.encode(), b"", ...)` must red the payload-sensitivity test only; (ii) removing the `f"{timestamp}."` prefix must red the timestamp-sensitivity test only; (iii) dropping `sort_keys=True` must red the golden-vector test only. Fail loudly when the check cannot run: the clock must be injected, not monkeypatched globally, so a test that forgets to pin time fails deterministically instead of passing by luck. Boundary and tie: the golden vector must state which timestamp it was computed at and assert the exact 64-hex-character digest, not a length or a prefix.

### Major: `in_flight` is a non-terminal state with no exit path
File: app/webhooks/delivery.py — `_claim_batch` (`row.status = "in_flight"`), `_finish`
What is wrong: `_claim_batch` commits `in_flight` for the whole batch, and the only writes back out of that state are the two `_finish` calls on the success and permanent-failure paths inside `deliver` — a worker restart, an unhandled exception, an OOM kill, or the CHECK-constraint failure above leaves rows in `in_flight` forever, and `_claim_batch` only ever selects `status == "pending"` (R38 clause 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: Every worker deploy or crash permanently strands up to `BATCH_SIZE` paid-invoice webhooks in a state no query will ever reclaim, and no metric or alert exists to surface them.
Fix: Add a `claimed_at TIMESTAMPTZ` column set alongside `in_flight`, and make `_claim_batch` also reclaim `status == 'in_flight' AND claimed_at < now() - interval '10 minutes'` — a bounded timeout is the explicit failure-exit R38 requires. Add a startup reaper that resets stale `in_flight` rows to `pending`, and a gauge on the count of `in_flight` rows older than the timeout so the wedge is visible rather than silent. Preserve the claim semantics: a row genuinely in flight must not be reclaimed before the timeout, or the reaper becomes a duplicate-delivery source — that is the property the fix must not delete. Pin both directions: a row claimed 1 minute ago is NOT reclaimed (allow side of the guard), a row claimed 11 minutes ago IS. Red-prove each clause separately by execution: (i) remove the `claimed_at` predicate and assert an in-flight row is stolen immediately; (ii) remove the reclaim branch entirely and assert a stale row is never returned. Fail loudly when the check cannot run: a row with `status='in_flight'` and `claimed_at IS NULL` must be treated as stale and reclaimed, not skipped. Boundary and tie: a row at exactly the timeout is reclaimed (`<`, so exactly-10-minutes is not yet stale); when two workers race to reclaim the same stale row, the `FOR UPDATE SKIP LOCKED` from the lock finding is what makes exactly one win.

### Major: `_claim_batch` returns ORM instances after its session has closed

### Minor: indexes do not match the queries the change introduces
File: migrations/0042_webhook_delivery.sql — `CREATE INDEX idx_webhook_deliveries_status ON webhook_deliveries (status)`
What is wrong: `_claim_batch` filters `status = 'pending' AND next_attempt_at <= now` ordered by `next_attempt_at`, `list_deliveries` filters `endpoint_id` ordered by `created_at DESC`, and `list_webhook_endpoints` / `enqueue_for_event` filter `webhook_endpoints.org_id` — none of which the single low-cardinality `status` index serves.

### Minor: `SECRET_BYTES` counts characters, and the test encodes the same confusion
File: app/webhooks/signing.py — `SECRET_BYTES = 32`; tests/webhooks/test_delivery.py — `test_new_signing_secret_has_prefix_and_length`
What is wrong: The constant names bytes but is used as a character count over a 62-symbol alphabet (~5.95 bits each, ~190 bits total, not 256), and the test asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which locks the misnaming in.
What breaks in production: The next author reading `SECRET_BYTES = 32` believes the key carries 256 bits of entropy and sizes another security decision on that belief.
What would close this: renaming to `SECRET_ENTROPY_BYTES` and generating with `secrets.token_urlsafe(SECRET_ENTROPY_BYTES)` per the CSPRNG finding, with the test asserting the entropy source rather than a character count.
