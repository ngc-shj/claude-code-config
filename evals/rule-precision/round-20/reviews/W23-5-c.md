### Critical: the bytes we sign are not the bytes we send, and the timestamp is outside the MAC
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, with `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (sorted keys, default `", "`/`": "` separators) while `send_once()` transmits the body via `client.post(..., json=delivery.payload)`, which serializes with httpx's own encoder (insertion order, compact separators) and never calls the `serialize()` helper this same diff added — and neither string includes the timestamp, contrary to `docs/webhooks.md` which tells every customer the MAC covers `"{timestamp}.{raw_request_body}"`.
What breaks in production: every customer who implements the documented verification computes a different digest and rejects 100% of our deliveries, and because the timestamp header is unauthenticated an attacker who captures one request can rewrite `X-Acme-Timestamp` to `now` and replay it past the documented five-minute window forever.

Red-prove each clause separately by execution: (i) drop `sort_keys=True` from `serialize` and observe the round-trip assertion go red on a payload whose keys are not already sorted (e.g. `{"b":2,"a":1}`); (ii) send `json=payload` instead of `content=body` and observe the same assertion red; (iii) remove the `f"{timestamp}."` prefix from the MAC input and observe a *separate* assertion — one comparing the header against an independently written expected HMAC literal — go red. Fail loudly when the check cannot run: `verify()` must raise on a signature that is not `sha256=<64 hex>` rather than returning `False`, so "malformed header" is not spelled the same as "wrong key". Boundary and tie: state that a request whose timestamp is exactly `now - 300s` is ACCEPTED and `now - 301s` rejected, and that two deliveries signed in the same second produce identical timestamps and therefore must be distinguished by `event_id`, never by the timestamp.
