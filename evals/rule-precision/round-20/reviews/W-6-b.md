### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built with `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, which is seeded from a small state, is not a CSPRNG, and whose entire future output is reconstructible from ~624 observed outputs — and `SECRET_BYTES = 32` is used as a *character* count over a 62-symbol alphabet, so the secret carries ~190 bits from a generator that provides none of them cryptographically.
What breaks in production: Anyone who can register two endpoints of their own can recover the process's PRNG state and derive the signing secret of every other tenant's endpoint created in the same worker, then forge `invoice.paid` webhooks that every customer's verifier accepts as genuine.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and import `secrets`; delete the `random`, `string` and `_ALPHABET` imports outright rather than leaving them unreferenced (R1 clause d). Rename the constant to `SECRET_ENTROPY_BYTES = 32` so the unit it names is the unit it is used in, and change `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` from the char-count identity to two independent assertions: `secret.startswith(SECRET_PREFIX)` and `len(set(signing.new_signing_secret() for _ in range(1000))) == 1000`. Allow side that must still pass: a freshly minted secret is still accepted end-to-end — `signing.verify(signing.new_signing_secret(), payload, sign(...)[1])` stays `True`, and existing `whsec_`-prefixed secrets already in the table keep verifying unchanged (the prefix and the HMAC path are the behaviour the fix must preserve). Red-prove each clause separately by execution: (i) revert to `random.choice` under `random.seed(0)` and observe the uniqueness assertion redden; (ii) drop the prefix and observe only the `startswith` assertion redden; (iii) confirm neither mutation reddens the verify round-trip, proving the two clauses are independent. Fail loudly when the check cannot run: `secrets.token_urlsafe` has no failure mode, but the test must `import secrets` at module scope so an unavailable stdlib module errors at collection rather than silently skipping. Boundary and tie: `SECRET_ENTROPY_BYTES = 32` is a floor, not a target — a value of `0` must raise at import rather than mint an empty secret, and two secrets colliding is exactly the case the uniqueness assertion pins.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: `verify` compares the recomputed HMAC to the caller-supplied one with Python's `==`, which short-circuits on the first differing byte (RS1: any credential/signature comparison not using `hmac.compare_digest`).
What breaks in production: An attacker calling any inbound path that reaches `verify` can recover a valid signature byte by byte from response-time differences, defeating the only authenticity control the webhook channel has.
Fix: `return hmac.compare_digest(expected, signature)` — `hmac` is already imported, so no new dependency. Guard the non-`str` and `None` cases explicitly before the compare (`compare_digest` raises `TypeError` on mixed str/bytes) and return `False` for them, so a malformed header is a denial rather than a 500. Allow side that must still pass: `test_verify_accepts_signature_produced_by_sign` must stay green — a legitimately signed payload still verifies, and the `sha256=` prefix stays part of the compared string (do not "fix" this by comparing only the hex tail; the prefix is what pins the algorithm). Red-prove each clause separately by execution: (i) replace `compare_digest` with `==` and assert, via a timing harness over 10k trials with a first-byte-wrong versus last-byte-wrong signature, that the mean-difference assertion reddens; (ii) pass `signature=None` and observe the new type-guard test redden when the guard is removed, with a `TypeError` traceback rather than a `False`; run each mutation singly. Fail loudly when the check cannot run: if the timing harness cannot collect its sample (interpreter without `time.perf_counter_ns`, sample size below the configured floor), the test must `pytest.fail("timing sample unavailable")` — "examined nothing" must not be spelled the same as "found nothing". Boundary and tie: the equal-length-but-different case is the one the timing test must use; equal-length-and-equal is the allow case, and a length mismatch must deny without leaking the length through an early return placed before the compare.

### Critical: the signature does not cover the timestamp and is computed over a body that is never sent
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: The doc states the signature is `HMAC-SHA256("{timestamp}.{raw_request_body}")`, but `sign` MACs only `json.dumps(payload, sort_keys=True)` — the timestamp is generated, sent in `X-Acme-Timestamp`, and then excluded from the MAC, while `send_once` transmits `json=delivery.payload` whose httpx encoding (insertion order, `", "`/`": "` separators) is a different byte string from `serialize`'s sorted, default-separator output (R40: producer wire shape versus the consumer's stated contract; R29: a published rationale that the code does not implement).
What breaks in production: Every customer who implements the documented verification recomputes the MAC over the raw body they received and gets a mismatch, so either the entire integration fails closed on day one or customers reverse-engineer the real scheme — and because the unsigned timestamp can be rewritten freely, the "reject requests older than five minutes" replay defence the doc sells is unenforceable even for those who get verification working.
Fix: Make the signed bytes the bytes on the wire. In `send_once`, build `body = serialize(delivery.payload).encode()` once, pass it as `content=body` (not `json=`), and set `Content-Type: application/json` explicitly; change `sign` to take the already-serialized body — `sign(secret, timestamp, body) -> str` MACing `f"{timestamp}.".encode() + body` — and have `verify(secret, timestamp, body, signature)` recompute from the same two inputs plus a caller-supplied `max_age_seconds=300` staleness check that denies. Preserve the `sha256=` prefix and both header names; do not "fix" this by relaxing the doc, because the timestamp binding is the feature (Remedy Floor clause 4). Allow side that must still pass: add a round-trip test that feeds the *actual* bytes captured by `httpx.MockTransport` in `test_send_once_posts_the_signed_payload` back through `signing.verify` and asserts `True` — actual producer output through the actual consumer, never two independently constructed shapes (R40). Red-prove each clause separately by execution: (i) drop the timestamp from the MAC input and observe the round-trip test redden; (ii) re-serialize inside `sign` instead of MACing the passed body and observe the same test redden with a digest mismatch named in the output; (iii) set the request timestamp to `now - 301` and observe only the staleness assertion redden. Fail loudly when the check cannot run: a missing or non-numeric `X-Acme-Timestamp` must make `verify` return `False`, not skip the age check. Boundary and tie: a timestamp exactly `max_age_seconds` old is accepted and `max_age_seconds + 1` is rejected — state that in the doc — and two deliveries signed within the same second are independent, so the timestamp is never used as an identity.

### Critical: `GET /webhook-endpoints/{id}/deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters on `WebhookDelivery.endpoint_id == endpoint_id` only, with no join back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling handlers added in the same diff (`list_api_keys`, `list_webhook_endpoints`) both filter on `org_id` — the tenancy predicate was applied to two of three peers (R3 incomplete pattern propagation, security-relevant; RS3).
What breaks in production: Any authenticated user can enumerate `endpoint_id` values and read other tenants' delivery rows, and `WebhookDelivery.payload` holds full `invoice.paid` bodies, so the endpoint is a cross-tenant billing-data exfiltration primitive requiring nothing but a valid session and an integer.
Fix: Join and filter in one statement — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403) when the join yields nothing, so the response does not disclose whether the id exists. Do not implement this as a separate pre-check `session.get(WebhookEndpoint, endpoint_id)` followed by the original query: that reintroduces the same shape one line later and is not the boundary. Allow side that must still pass: an owner listing their own endpoint's deliveries still receives every row it received before, in the same order, with the same `limit` semantics — pin it with a test that seeds two orgs and asserts the owner sees exactly its N rows. Red-prove each clause separately by execution: (i) remove the `org_id` filter and observe the cross-tenant test redden on a non-empty body (assert `== []` *and* assert the response status, so a 500 cannot be mistaken for a denial); (ii) remove the `404` branch and observe the not-found test redden on the status. Fail loudly when the check cannot run: `user.org_id` being `None` must deny, not match rows whose `org_id` is `NULL`. Boundary and tie: an endpoint that exists but belongs to another org and one that does not exist at all must be indistinguishable — same status, same body.

### Critical: `to_dict()` returns the signing secret on the list endpoint, and `send_once` logs the signature at INFO
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/webhooks/delivery.py` — `send_once` line `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: `to_dict` unconditionally includes `"signing_secret"`, and it is the serializer used by both `create_webhook_endpoint` and `list_webhook_endpoints`, so the secret is returned on every list call — directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards") — while `send_once` writes the complete header dict, signature included, into the application log (RS4: a live credential in an artifact that gets shipped and indexed).
What breaks in production: The secret is readable by anyone who reaches the list route and by anyone with log access, so it is no longer a shared secret and the entire signature scheme degrades to an unauthenticated POST; per RS4 a secret that has been logged is compromised and must be rotated, not merely hidden.
Fix: Drop `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held value, so exposure is a property of the one call site that is allowed it rather than of the shared serializer. In `send_once`, log only `endpoint.url` and the delivery id — never the header dict — and if header logging is wanted for debugging, log `sorted(headers)` (key names only). Do not remove the log line entirely; the request trace is what makes delivery debuggable (Remedy Floor clause 4). Allow side that must still pass: the create response still contains a usable `signing_secret` (assert the returned value verifies a payload signed with it), and the list response still contains `id`, `url`, `event_types` and `active`. Red-prove each clause separately by execution: (i) re-add `signing_secret` to `to_dict` and observe a list-route test asserting `"signing_secret" not in body[0]` redden; (ii) restore the header log and observe a `caplog` test asserting no record text contains the signature redden, naming the leaked record; run the two singly. Fail loudly when the check cannot run: the `caplog` test must assert at least one record was captured before asserting the absence, so a logger misconfiguration cannot make it pass vacuously. Boundary and tie: the create response is the single point of disclosure — an endpoint created and immediately listed must show the secret exactly once, on the create call, and never again.

### Critical: the migration's status CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` versus `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(..., "failed_permanent", ...)`
What is wrong: The code's terminal failure status is `failed_permanent` in both the model's `STATUSES` tuple and the `_finish` call in `deliver`, but the constraint enumerates `failed` — the member set was derived from a supplied list rather than from the defining primitive (R42), and the Python and SQL enumerations of the same class have diverged.
What breaks in production: The first delivery that exhausts its five attempts raises a `CheckViolation` inside `_finish`, the transaction aborts, the row stays `in_flight` forever, and the exception propagates out of `deliver` through the un-guarded `asyncio.gather` and kills the worker — so the first failing endpoint takes down webhook delivery for every tenant.
Fix: Make one enumeration authoritative and generate the other from it: export `STATUSES` from `app/webhooks/models.py`, write the migration's CHECK as `status IN ('pending','in_flight','delivered','failed_permanent')`, and add a test that reads the constraint definition from `information_schema`/`pg_constraint` on a migrated test database and asserts its member set equals `set(models.STATUSES)` — so the next added status reddens rather than aborting a transaction at runtime. Allow side that must still pass: inserting each of the four legitimate statuses succeeds, and a fifth arbitrary string is still rejected by the constraint (the CHECK is the behaviour to preserve — do not fix this by dropping it). Red-prove each clause separately by execution: (i) revert the migration to `'failed'` and observe the parity test redden naming `failed_permanent` as the missing member; (ii) append a bogus member to `STATUSES` without touching the SQL and observe the same test redden from the other direction; (iii) attempt to insert `'bogus'` and confirm the constraint still raises, proving the CHECK was not weakened to `TEXT`. Fail loudly when the check cannot run: if the test cannot query the constraint (no database, constraint not found by name), it must fail with that message, not skip. Boundary and tie: the migration must also be shipped with an `UPDATE webhook_deliveries SET status='failed_permanent' WHERE status='failed'` guard in case any row already carries the old spelling, and the constraint name must be explicit (`CONSTRAINT webhook_deliveries_status_check`) so the parity test can address it rather than pattern-matching.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness key is `event_id` by itself while `enqueue_for_event` inserts one row per matching endpoint via `session.add_all(rows)`, so the key does not include the dimension the producer fans out over.
What breaks in production: An organization with two subscribed endpoints raises a unique-violation on the second insert, `session_scope` rolls back the whole batch, the dispatcher's blanket `except Exception` logs a warning and returns — so the event is delivered to *no* endpoint, silently, and the failure is invisible outside a WARNING line.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is also the key the documented at-least-once dedup contract needs, and add an integration test that enqueues one event for an org with two active endpoints and asserts two rows exist. Allow side that must still pass: the idempotency the single-column index was providing must survive — enqueuing the *same* `(endpoint_id, event_id)` twice must still produce exactly one row, so pair the index change with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` on the insert path rather than dropping uniqueness. Red-prove each clause separately by execution: (i) revert to the single-column index and observe the two-endpoint test redden with an `IntegrityError`; (ii) drop the `ON CONFLICT` clause and re-enqueue the same event, observing the idempotency test redden; run singly. Fail loudly when the check cannot run: `enqueue_for_event` must return the number of rows it actually inserted (post-conflict), and the dispatcher must treat a return of `0` for a subscribed org as a warning with the event id, so "nothing to enqueue" is distinguishable from "enqueue silently collapsed". Boundary and tie: an org with zero active endpoints legitimately produces zero rows and must not warn; the tie between two endpoints subscribed to the same event type is now representable, which is the whole point.

### Critical: endpoint URL validation is a string check, and the client follows redirects — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The guard adjudicates the notation rather than consulting the resolver that gives the URL meaning (R47) — `startswith("http")` admits `http://` (the doc says only `https://` is accepted) and any scheme with that prefix, `netloc` is non-empty for `169.254.169.254`, `127.0.0.1`, `[::1]`, `localhost`, `10.0.0.5` and for any hostname whose DNS record resolves to those, and `follow_redirects=True` means even a validated public host can bounce the request to an internal one.
What breaks in production: A tenant registers `https://evil.example/redirect` and receives, on their own inbound endpoint, whatever the cloud metadata service or an internal admin API returns to a request originating from inside the production network — with signed, authenticated-looking POSTs issued by the platform's own worker.
Fix: Replace the surface-form check with a resolution-based one, climbing to the interpreter's own rung: require `parsed.scheme == "https"` exactly (an equality, not a prefix), reject a URL carrying userinfo or a non-standard port outside an allowlist, then resolve the hostname with `socket.getaddrinfo` and reject if *any* returned address is private, loopback, link-local, unique-local, multicast or reserved per `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`. Set `follow_redirects=False` on the delivery client and treat a 3xx as a non-retryable permanent failure. Because DNS can change between registration and delivery, re-run the same address check inside the delivery path via a custom `httpx` transport that validates the connected peer address — registration-time validation alone is a time-of-check/time-of-use gap. Declare the control class explicitly at the function (R49): this is a *fail-closed verification gate*, not a complete boundary, and DNS rebinding within a single connection remains a known residual — list it in `docs/webhooks.md` rather than claiming the class is closed. Allow side that must still pass: `https://hooks.example.com/acme` — the exact URL in the doc and in `tests/webhooks/test_delivery.py::FakeEndpoint` — must still register and still deliver; pin that as an explicit allow test alongside each deny case. Red-prove each clause separately by execution: (i) revert to `startswith("http")` and observe the `http://hooks.example.com` deny test redden; (ii) remove the address filter and observe the `https://localhost/x` and `http://169.254.169.254/` deny tests redden; (iii) set `follow_redirects=True` and observe the redirect-to-internal test redden; (iv) confirm the allow test stays green under all three, proving no mutation reddens everything. Fail loudly when the check cannot run: a `getaddrinfo` failure (NXDOMAIN, timeout) must deny with 422 and a message naming resolution failure — an unresolvable host must never fall through to "no private address found, therefore allowed". Boundary and tie: `0.0.0.0` and IPv4-mapped IPv6 (`::ffff:127.0.0.1`) are on the deny side and must be tested explicitly, and a hostname resolving to both a public and a private address denies (any-private, not all-private).

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is `async def` and is scheduled concurrently via `asyncio.gather`, but the retry pause uses the blocking `time.sleep` rather than `await asyncio.sleep`, so it halts the entire loop rather than yielding.
What breaks in production: One failing endpoint stalls every other coroutine in the batch for 2+4+8+16 = 30 seconds of wall clock; with a 100-row batch of failing endpoints the worker blocks for tens of minutes, blows past the 60-second lock TTL so a second worker starts double-delivering, and any co-hosted async work on the same loop stops dead.
Fix: `await asyncio.sleep(delay)` (`asyncio` is already imported at the top of the file, so this reimplements nothing). Additionally, remove the in-process retry loop entirely and reschedule instead: on a retryable failure, write `status='pending'`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting `_claim_batch` pick the row up on a later poll. Allow side that must still pass: the retry *schedule* is the behaviour to preserve — a delivery that fails twice and succeeds on the third attempt must still end `delivered` with `attempts == 3`, and the observed gaps must still be ~2s and ~4s; do not fix the blocking by deleting the backoff. Red-prove each clause separately by execution: (i) restore `time.sleep` and observe a test that runs two `deliver` coroutines concurrently and asserts total wall time < the sum of their sleeps redden; (ii) remove the `next_attempt_at` update and observe a test asserting the row is re-claimable only after the backoff redden; run singly, with the loop bounded by `MAX_ATTEMPTS` so a non-terminating mutation reddens rather than hanging. Fail loudly when the check cannot run: if `backoff_for` ever returns a non-positive or non-finite delay, raise rather than sleeping zero and hot-looping. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (the existing `<=` comparison) — keep that inclusive and say so; two rows with the same `next_attempt_at` are ordered by the tiebreak added under the R57 finding below.

### Major: `_claim_batch` and `deliver` use ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`), `deliver` (`endpoint` read after the `with` block; `delivery.attempts`, `delivery.payload`, `delivery.id`)
What is wrong: Both functions return or retain SQLAlchemy instances past the end of their `session_scope()` block, and every attribute read afterwards is on a detached, expired-on-commit instance.
What breaks in production: The first attribute access in `run_worker`'s `deliver(client, d)` raises `DetachedInstanceError`, which propagates through the unguarded `gather` and terminates the worker — meaning webhook delivery does not work at all after the first poll that finds a row.
Fix: Have `_claim_batch` return plain data, not ORM rows — a list of frozen dataclasses or dicts carrying `id`, `endpoint_id`, `attempts`, `payload` — and have `deliver` load the endpoint inside a session and extract `url` and `signing_secret` as locals before leaving the block. Allow side that must still pass: the batch still marks rows `in_flight` and still returns at most `BATCH_SIZE` rows in `next_attempt_at` order; pin it with a test asserting both the returned count and the persisted status. Red-prove each clause separately by execution: (i) return the ORM rows again and observe an integration test that calls `run_worker` for one poll redden with `DetachedInstanceError` named in the output; (ii) drop the `in_flight` write and observe the persisted-status assertion redden. Fail loudly when the check cannot run: `session.get(WebhookEndpoint, delivery.endpoint_id)` returning `None` (the endpoint was deleted mid-flight — reachable, since the migration declares `ON DELETE CASCADE` from `organizations`) must mark the delivery `failed_permanent` with an explicit detail, not raise `AttributeError` on `endpoint.signing_secret`. Boundary and tie: an empty batch returns `[]` and must not be conflated with a claim failure.

### Major: the dispatch lock is not atomic and is released by whoever finishes first
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does `get` then `set` then `expire` as three separate round trips, so two workers can both observe an absent key and both proceed; and the release deletes the key unconditionally, without checking that this worker still owns it, so a worker whose 60-second TTL already expired deletes the *successor's* lock.
What breaks in production: Two workers claim overlapping batches and every customer endpoint receives duplicate POSTs for the same event — which the docs push onto the customer as "deduplicate on `event_id`", except the unique index means the duplicate rows cannot even exist, so the real symptom is double HTTP delivery plus contention.
Fix: Acquire with a single atomic command carrying a unique owner token and the TTL together — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = uuid.uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker cannot delete a lock it no longer owns. Keep the TTL: it is what prevents a crashed worker wedging the queue (Remedy Floor clause 4). Allow side that must still pass: a single worker still acquires the lock on every poll and still releases it, so successive polls make progress — pin it with a test running two consecutive polls and asserting both claimed. Red-prove each clause separately by execution: (i) revert to get-then-set and observe a concurrency test launching two `_acquire_lock` coroutines and asserting exactly one `True` redden (assert the count is exactly 1, not merely ">= 1", so the test cannot pass vacuously); (ii) revert the release to an unconditional `delete` and observe a test that expires the token before release and asserts the successor's key survives redden. Fail loudly when the check cannot run: a Redis error during acquire must be raised or logged as an error and the poll skipped — it must not be caught into `return False` in a way that is indistinguishable from "another worker holds it", and it must never fall through to `True`. Boundary and tie: when both workers race and one loses, the loser sleeps `poll_interval` and retries; the TTL must exceed the worst-case batch duration, which after the rescheduling fix above is one HTTP timeout (30s) per row rather than 30s of sleeps — state the chosen relationship in a comment.

### Major: `in_flight` is a non-terminal state with no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; `_finish` is the only writer that leaves it
What is wrong: A row transitions out of `in_flight` only on the success or exhaustion path inside `deliver`; a worker crash, a pod eviction, a lock expiry, or any exception before `_finish` leaves the row `in_flight` permanently, and nothing anywhere selects on that status to recover it (R38 mode 1: an async transition with no failure-exit and no bounded timeout).
What breaks in production: Deliveries silently stop being attempted with no error and no alert — the customer's endpoint simply never receives the event, and the row reads as "in progress" forever in the deliveries API.
Fix: Add a `claimed_at TIMESTAMPTZ` column set when the row is claimed, and a reaper query in `run_worker`'s poll — `UPDATE webhook_deliveries SET status='pending', next_attempt_at=now() WHERE status='in_flight' AND claimed_at < now() - interval '5 minutes'` — logging the reclaimed count at WARNING with the row ids. Allow side that must still pass: a row currently being worked on by a live worker (claimed 10 seconds ago) must NOT be reclaimed; pin both directions with a test seeding one stale and one fresh `in_flight` row and asserting exactly one transitions. Red-prove each clause separately by execution: (i) remove the age predicate and observe the fresh-row assertion redden; (ii) remove the reaper entirely and observe the stale-row assertion redden; run singly. Fail loudly when the check cannot run: the reaper must log the count it reclaimed on every poll where it is non-zero, so a queue quietly filling with stale rows is visible rather than inferred. Boundary and tie: a row whose `claimed_at` is exactly the threshold must fall on one stated side — choose reclaimed (`<=`) and document it — and a row reclaimed while its original worker is still alive will be delivered twice, which is why the `(endpoint_id, event_id)` idempotency key from the Critical finding above is a precondition for shipping this.

### Major: an exception in any single delivery kills the worker permanently, and `batch` can be unbound
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])` and `if not batch:`
What is wrong: `asyncio.gather` without `return_exceptions=True` re-raises the first exception, which escapes the `try` (the `finally` releases the lock but does not suppress), unwinds the `while True` loop and ends the coroutine; and if `_claim_batch` itself raises, the `finally` runs and then `if not batch:` evaluates an unbound local, turning a database blip into a `NameError`.
What breaks in production: One malformed row, one detached instance, one CHECK violation stops webhook delivery process-wide until a human notices and restarts — and the supervisor sees a clean exit rather than a crash loop, so nothing restarts it automatically.
Fix: Initialize `batch: list = []` before the `try`, pass `return_exceptions=True` to `gather`, and iterate the results logging each `Exception` at ERROR with its delivery id while marking that row `pending` for retry; wrap the whole poll body so a `_claim_batch` failure logs and continues to the next iteration rather than exiting.
