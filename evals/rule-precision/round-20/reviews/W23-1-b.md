### Critical: `list_deliveries` has no tenancy filter — any authenticated user reads any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries` (`GET /v1/settings/webhook-endpoints/{endpoint_id}/deliveries`)
What is wrong: The query filters only on `WebhookDelivery.endpoint_id`, which is a caller-supplied integer, while every sibling handler in the same file (`list_api_keys`, `list_webhook_endpoints`, `get_profile`) filters on `user.org_id`.
What breaks in production: Any authenticated customer can enumerate `endpoint_id` values and read other organizations' full `invoice.paid` / `subscription.updated` payloads, which is a cross-tenant data breach through a documented, discoverable endpoint.
Fix: Join `WebhookDelivery` to `WebhookEndpoint` and add `WebhookEndpoint.org_id == user.org_id` to the filter, returning 404 (not 403) when the join yields nothing so endpoint existence is not leaked; keep the `order_by(created_at.desc()).limit(limit)` behaviour exactly as written, since that ordering is what the docs promise ("the most recent attempts"). Allow side to pin alongside the deny side: a test where the endpoint *does* belong to `user.org_id` must still return the rows, byte-identical to today's response — a fix that always 404s satisfies the deny test alone. Red-prove the two clauses separately: (1) delete the `org_id` predicate and assert the foreign-org test goes red on the row count, (2) delete the `endpoint_id` predicate and assert the same-org test goes red because it now sees a second endpoint's deliveries. Fail loudly if `user.org_id` is absent or `None` — raise, do not fall through to an unfiltered query, so "could not determine the tenant" is never spelled the same as "no rows". Boundary and tie: an endpoint whose `org_id` equals the caller's is *inside* the boundary; two deliveries sharing the same `created_at` must be ordered deterministically, so add `WebhookDelivery.id.desc()` as the tiebreaker or the `limit` cut can drop and duplicate rows across pages.

### Critical: `verify()` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` is a short-circuiting byte comparison on an HMAC, not a constant-time comparison (RS1), and this is the reference verifier the codebase ships and tests against.
What breaks in production: The comparison leaks a timing oracle that lets an attacker recover a valid signature byte-by-byte for a chosen payload, forging events into any consumer that adopts this helper.
Fix: Replace the body with `hmac.compare_digest(expected, signature)` (`hmac` is already imported at line 2 of the file, so no new dependency), and normalize both operands to `str` before the call so a `bytes`/`str` mix raises rather than silently returning `False`. Preserve the property that makes the function useful: it must still return `True` for a signature that `sign()` just produced with the same secret — pin that allow case, because `return False` passes every negative test. Red-prove each clause separately: (1) revert to `==` under a timing harness that feeds a signature differing in byte 0 versus byte 63 and assert the measured difference collapses; (2) mutate `expected` by one hex character and assert the accept-test goes red. Fail loudly when the check cannot run: a `signature` that is `None`, empty, or lacks the `sha256=` prefix must raise or return a distinct rejection, not be fed to `compare_digest` where a length mismatch is indistinguishable from a content mismatch. Boundary and tie: two signatures of *equal length but differing content* is the case `compare_digest` is for and must be asserted; unequal length is the case it does not protect, so reject on prefix/length before comparing.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice`, which is the Mersenne Twister — a deterministic, fully state-recoverable PRNG — rather than `secrets`, and `SECRET_BYTES = 32` actually names 32 *characters*, not bytes.
What breaks in production: An attacker who observes enough generator output (or who registers a few endpoints and reads back the secrets from `to_dict()`) can reconstruct the PRNG state and derive other tenants' signing secrets, at which point every webhook signature we issue is forgeable.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(32)` (or `secrets.choice` over `_ALPHABET` if the alphabet must stay), import `secrets`, and delete the `random` and `string` imports so the weak primitive cannot be reintroduced by a nearby edit — R1(d): delete the duplicate outright rather than leaving it as an unused fallback. Rename `SECRET_BYTES` to `SECRET_CHARS`, or switch to a true byte count, so the constant stops asserting something false. Preserve what made the feature usable: the returned string must still start with `SECRET_PREFIX` and must still be accepted unchanged by `sign()`/`verify()`; keep the existing prefix test green rather than deleting it, and update its length arithmetic in the same commit. Red-prove the clauses separately: (1) reseed `random.seed(0)` in a test and assert two processes no longer produce the same secret (this is red today and green after); (2) mutate the constant to a smaller value and assert a new entropy-floor assertion goes red. Fail loudly if the platform cannot supply entropy — let `secrets` raise; do not fall back to `random`. Boundary and tie: state the minimum accepted entropy explicitly (32 URL-safe characters ≈ 190 bits) and assert *at* that boundary, and reject rotation that would produce a secret shorter than it. Cross-cutting: this is the only secret generator in the diff, but `ApiKey` (imported at `app/api/routes/settings.py`) has a `prefix` column implying a pre-existing key-minting helper — locate it and reuse it rather than adding a second minting path (R1(f): say why the existing helper was not found).

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (space-after-separator, keys sorted) while the request is sent as `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and insertion order — so the signed string and the wire body differ for every payload with more than one key or any nested object.
What breaks in production: Every customer following `docs/webhooks.md` and computing the HMAC over the raw request body gets a mismatch, so 100% of deliveries fail verification while our side reports them `delivered` — a silent total-path failure that no test in this diff can see, because `test_send_once_posts_the_signed_payload` only checks that the header *starts with* `sha256=` (R40: mutual mocking, no round-trip).
Fix: Serialize once and send those exact bytes — compute `body = serialize(payload).encode()`, sign `body`, and post with `content=body` plus an explicit `Content-Type: application/json` header instead of `json=`. Preserve the behaviour that made the endpoint useful: the receiver must still get valid JSON with the same keys and values, so keep `serialize()` as the single producer and do not "fix" this by loosening the docs to say "verify over a re-serialized body" — that deletes the property, not the defect. Add the round-trip test R40 requires: capture `request.content` in the `MockTransport` handler and assert `signing.verify(SECRET, ...)` recomputes over *those captured bytes* — do not recompute from the dict. Red-prove separately: (1) change `serialize` to `sort_keys=False` and assert the round-trip test reddens; (2) revert `content=body` to `json=payload` and assert the same test reddens on a two-key payload; (3) drop the explicit `Content-Type` and assert the existing content-type assertion reddens. Fail loudly when serialization cannot run: a payload containing a non-JSON-serializable value must raise at enqueue time, at the boundary, rather than at delivery time inside the retry loop where the failure is logged as a transient error and retried five times. Boundary and tie: fix the canonical form in the docs (UTF-8, `sort_keys=True`, `separators` as emitted) and state that a payload differing only in key order produces the same signature — that equality is the tie case consumers will hit.

### Critical: the documented signature construction does not match `sign()`, so the documented replay defence does not exist
File: `app/webhooks/signing.py` — `sign`; `docs/webhooks.md` — "Verifying the signature"
What is wrong: The docs state the signature is `HMAC-SHA256("{timestamp}.{raw_request_body}")`, but `sign()` MACs the body alone and returns the timestamp as an unauthenticated side value (R29/R49: a claim stronger than the implementation).
What breaks in production: Because the timestamp is outside the MAC, an attacker who captures one request can replay it forever with a freshly rewritten `X-Acme-Timestamp`, and the "reject requests more than five minutes old" instruction the docs sell as the anti-replay control silently protects nothing.
Fix: Change `sign()` to compute `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` so the returned timestamp is covered, and change `verify()` to take the timestamp as an explicit parameter (`verify(secret, timestamp, body, signature)`) instead of generating a new one internally — the current `verify` calls `sign()`, which mints `int(time.time())` afresh, and only "works" today *because* the timestamp is not in the MAC; that coincidence disappears with this fix and would otherwise break every verification. Preserve the useful behaviour: the header names and the `sha256=<hex>` shape stay unchanged, so existing consumers' parsing does not move. Red-prove each clause: (1) replay a captured request with the timestamp advanced by one second and assert `verify` now returns `False` (red before the fix); (2) keep the timestamp and flip one payload byte and assert `verify` returns `False`; (3) remove the timestamp from the MAC input and assert (1) reddens. Fail loudly: a missing or non-numeric `X-Acme-Timestamp` must be a rejection that names itself, not a skipped check. Boundary and tie: state which side of the five-minute window is inclusive — a request whose timestamp is exactly 300 s old is accepted, 301 s is rejected — and specify the clock the receiver compares against; leave that unstated and the next defect of this class enters at the boundary. Also state the class (R49): with the timestamp signed and the window enforced this is a fail-closed verification gate; without it, it is detection only, and the docs must not describe it as a boundary.

### Critical: `time.sleep()` inside an `async def` blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered over a batch of up to `BATCH_SIZE = 100` deliveries, and it calls the blocking `time.sleep` for the backoff instead of `await asyncio.sleep`.
What breaks in production: One endpoint that returns 500 freezes the entire worker process for 2+4+8+16 = 30 s per delivery, serializing the batch and stalling every other tenant's webhooks — with 100 failing deliveries the worker is wedged for ~50 minutes and the redis lock (TTL 60 s) has long expired.
Fix: Replace with `await asyncio.sleep(delay)` (`asyncio` is already imported at the top of this file) and delete the now-unused `import time`. Preserve the property the sleep exists for: the retry must still be spaced by `backoff_for(attempt)`, so assert the *elapsed* delay, not merely that the call happened. Red-prove each clause separately: (1) with the fix in place, run two failing deliveries concurrently under `asyncio.gather` and assert total wall time is ≈ one backoff, not two — this is red today; (2) replace `await asyncio.sleep(delay)` with `await asyncio.sleep(0)` and assert a test that pins the per-attempt spacing reddens. Fail loudly if the loop is not running (a synchronous caller) rather than silently blocking. Boundary and tie: the last attempt must not sleep at all — `attempt == MAX_ATTEMPTS` returns before the sleep, which the current code does get right; pin that with an assertion so the reordering does not regress it. Cross-cutting: `run_worker` already uses `await asyncio.sleep(poll_interval)` correctly, so the blocking call in `deliver` is the sole unpropagated site of the pattern (R3).

### Critical: the migration's status CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/models.py` — `STATUSES`
What is wrong: The SQL allows `'failed'` while `STATUSES` and `deliver()`'s `_finish(delivery.id, "failed_permanent", ...)` write `'failed_permanent'` — the same enum spelled two ways across a strict consumer boundary (R40, R2: one vocabulary hardcoded in two places).
What breaks in production: Every delivery that exhausts its retries raises a `CheckViolation` inside `_finish`, so the row stays `in_flight` forever, the failure is never recorded, and the exception escapes into `asyncio.gather`, cancelling the sibling deliveries in the batch.
Fix: Change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the constraint text from `models.STATUSES` in a schema test so the two cannot drift again. Preserve the constraint's purpose: it must still reject an unknown status — do not "fix" this by dropping the CHECK, which is fixing by deleting what made the defect visible. Red-prove separately: (1) insert a row with `status='failed_permanent'` and assert it succeeds (red today); (2) insert `status='bogus'` and assert it still raises; (3) mutate one member of `STATUSES` and assert the drift test reddens. Fail loudly if the schema test cannot resolve the constraint definition from `information_schema` — report "could not read the constraint" as a failure, not a pass. Boundary and tie: the four names are the complete domain; state that `'failed'` is deliberately *not* accepted so a partially-migrated database is rejected rather than silently accumulating rows in a status nothing reads. Note the same table declares `TIMESTAMP` (naive) for `created_at`/`updated_at`/`next_attempt_at` while `models.py` declares `DateTime(timezone=True)` — align these in the same migration.

### Critical: `UNIQUE INDEX` on `(event_id)` alone allows only one delivery per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the unique index over `event_id` alone makes the second and later rows of any multi-endpoint org violate uniqueness.
What breaks in production: The whole `session.add_all` fails on flush for any organization with two or more active endpoints, the dispatcher swallows the exception as a warning, and *no* endpoint receives the event — the failure is silent and total for exactly the customers who use the feature most.
Fix: Change it to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);`, which is the idempotency key the feature actually needs (one attempt record per endpoint per event) and which the documented "deduplicate on `event_id`" guidance assumes on the *receiver* side, not ours. Preserve the property the index exists for: a re-run of `enqueue_for_event` for the same event must still not create duplicate rows — assert that the second call raises or no-ops, rather than dropping the uniqueness. Red-prove separately: (1) enqueue one event for an org with two active endpoints and assert two rows exist (red today); (2) enqueue the same event twice for one endpoint and assert the second is rejected (reddens if the index is dropped entirely). Fail loudly on the conflict: use `ON CONFLICT DO NOTHING` explicitly if re-enqueue is legitimate, so "already enqueued" and "insert silently vanished" are not spelled the same. Boundary and tie: state what happens when an endpoint is deleted and recreated with the same id domain — the pair is unique per endpoint row, so a cascade-deleted endpoint's rows are removed with it (`ON DELETE CASCADE` is already declared) and re-enqueue is then legal.

### Critical: endpoint URL validation is a string check, not a resolution — SSRF into internal services
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: The guard judges notation rather than the destination the HTTP client will actually reach (R47): `startswith("http")` admits `httpx://`, `httpfoo://` and plain `http://`, nothing restricts the host, and the worker's client is built with `follow_redirects=True`, so even a validated public host can redirect the signed POST to `http://169.254.169.254/` or an internal `10.x` service.
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/` (or a public host that 302s there) and our worker fetches cloud instance credentials and stores the response body verbatim in `webhook_deliveries.response_body`, readable back through the deliveries endpoint — a full SSRF-to-credential-exfiltration chain.
Fix: Judge the resolved destination, not the string: require `parsed.scheme == "https"` exactly (which is what `docs/webhooks.md` already claims we enforce), require a non-empty hostname, resolve that hostname with `socket.getaddrinfo` at registration time and reject any address in a private, loopback, link-local, or reserved range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`; then set `follow_redirects=False` on the delivery client and re-apply the same address check to the connected peer at request time, since DNS can be re-pointed between registration and delivery. Preserve the allow side: a normal `https://hooks.example.com/acme` must still register and still receive deliveries — pin it, because a guard that rejects everything passes every SSRF test. Red-prove each clause separately: (1) register `http://…` and assert 422 (red today); (2) register `https://localhost/x` and assert 422; (3) register a public host that 302s to `http://127.0.0.1/` and assert the delivery does not follow it; (4) register the legitimate HTTPS host and assert 201 and a successful delivery. Fail loudly when the check cannot run: a DNS resolution failure must reject the registration with a named error, never fall through to "no private address found". Boundary and tie: name which addresses sit on the deny side (RFC1918, `127.0.0.0/8`, `::1`, `169.254.0.0/16`, `100.64.0.0/10`) and state that a hostname resolving to *both* a public and a private address is rejected, not accepted on the public one. Declare the class (R49): with resolution-time re-checking this is a fail-closed gate; without it, it is a best-effort tripwire and must be documented as such.

### Critical: ORM rows are used after their session closes
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (reads `endpoint.url` / `endpoint.signing_secret` after the `with` block)
What is wrong: `session_scope()` is a commit-and-close context manager (its use elsewhere in the diff is strictly inside the `with`), so under SQLAlchemy's default `expire_on_commit=True` every attribute of the returned `WebhookDelivery` and `WebhookEndpoint` objects is expired and reloading it outside the scope raises `DetachedInstanceError`.
What breaks in production: The first attribute access — `delivery.attempts` in `deliver`, `endpoint.signing_secret` in `send_once` — raises, so the worker delivers nothing at all while the rows it already flipped to `in_flight` are stranded; this is a total-path failure that no test in the diff exercises because every test uses `FakeEndpoint`/`FakeDelivery` plain objects (RT1/RT5: the test call path never touches the production ORM primitive).
Fix: Stop passing ORM instances across session boundaries — have `_claim_batch` return plain immutable snapshots (a `@dataclass(frozen=True)` carrying `id`, `endpoint_id`, `attempts`, `payload`, plus the endpoint's `url` and `signing_secret` fetched in the *same* query via a join), and have `deliver`/`send_once` take that dataclass. Preserve what the current shape gives you: `deliver` must still see the row's real `attempts` value so the retry counter is not reset — assert that a row with `attempts=3` gets at most two further attempts. Red-prove each clause separately: (1) add an integration test that runs `_claim_batch` against a real session and reads `.payload` after the scope closes — red today, green after; (2) drop the endpoint join and assert `send_once` reddens on a missing secret; (3) hardcode `attempts=0` in the snapshot and assert the retry-counter test reddens. Fail loudly: `session.get(WebhookEndpoint, ...)` returning `None` (endpoint deleted mid-flight) must mark the delivery terminal with a named reason, not raise `AttributeError` inside the gather. Boundary and tie: a delivery claimed in the same transaction as its endpoint's deactivation should be dropped, not sent — state that the snapshot is taken under the claim's transaction so `active=False` at claim time wins.

### Major: the dispatch lock is not atomic and its TTL is shorter than a batch
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act race with no `NX`, and the 60 s expiry is shorter than a batch's worst case (5 attempts × `REQUEST_TIMEOUT` 30 s + 30 s of backoff ≈ 180 s), so a second worker acquires the expired lock while the first is still running and the first's unconditional `delete` in `finally` then removes the *second* worker's lock.
What breaks in production: Two or more workers process the same claimed batch concurrently and the lock degenerates into no lock at all, producing duplicate signed POSTs of financial events (`invoice.paid`) to customer endpoints.
Fix: Replace the three redis calls with a single atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL)` where `token` is a per-worker `uuid4`, and release with a compare-and-delete Lua script that deletes only when the stored value still equals `token`; set `LOCK_TTL` from the measured worst-case batch duration (`MAX_ATTEMPTS * REQUEST_TIMEOUT` plus the sum of `backoff_for(1..MAX_ATTEMPTS-1)`), not a round 60. Preserve the property the lock exists for: a single worker must still acquire on the first try and proceed without delay — pin that allow case. Red-prove separately: (1) two concurrent `_acquire_lock` calls, assert exactly one wins (red today); (2) let worker A's lock expire, have B acquire, then run A's release and assert B still holds the lock (red today); (3) shrink `LOCK_TTL` below the batch duration and assert a duration-headroom test reddens. Fail loudly if redis is unreachable: `run_worker` must stop and report, not treat a connection error as "lock free" — that is the fail-open direction. Boundary and tie: state what happens when the TTL expires at exactly the moment the worker finishes — the compare-and-delete finds no key and must be a no-op, not an error.

### Major: deliveries can wedge in `in_flight` forever with no recovery path
File: `app/webhooks/delivery.py` — `_claim_batch` (sets `row.status = "in_flight"`), `run_worker`
What is wrong: `in_flight` is entered on claim but left only on the success or permanent-failure paths inside `deliver`; a worker crash, a redeploy, or the `CheckViolation` above leaves rows in a state that `_claim_batch`'s `status == "pending"` filter can never re-select (R38, non-terminal transient state).
What breaks in production: Every worker restart permanently strands its in-flight batch — up to 100 customer events silently never delivered and never surfaced as failed, with no operator affordance to requeue them.
Fix: Add a reaper that, on each poll, resets rows with `status = 'in_flight'` and `updated_at < now() - claim_timeout` back to `pending` with `next_attempt_at = now()` and `attempts` unchanged, and stamp `updated_at` at claim time so the timeout has a basis (today `_claim_batch` never writes `updated_at`). Preserve the property the `in_flight` state exists for: a row genuinely being delivered must *not* be reclaimed — assert that a row claimed 1 s ago is left alone. Red-prove each clause separately: (1) claim a row, kill the worker, run the reaper, assert the row returns to `pending` (red today); (2) claim a row and run the reaper immediately, assert it is untouched; (3) remove the `updated_at` stamp at claim and assert the reaper's timeout test reddens. Fail loudly if the reaper itself errors — log at error and stop the poll, do not continue into `_claim_batch` with a stale backlog silently accumulating. Boundary and tie: a row whose `updated_at` is *exactly* `now() - claim_timeout` should be reclaimed (inclusive), and `claim_timeout` must exceed the worst-case `deliver` duration used for the lock TTL above, or the reaper races the worker that still owns the row.

### Major: `to_dict()` returns the signing secret on every read, contradicting the documented contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`; `docs/webhooks.md`
What is wrong: `to_dict()` includes `"signing_secret"`, and `GET /v1/settings/webhook-endpoints` returns it for every endpoint, while the docs state "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim stronger than the implementation).
What breaks in production: The secret is re-exposed on every list call and therefore lands in browser caches, proxy logs, API-client history, and any support tooling that renders the list, multiplying the number of places a compromise of one log store yields signature-forging material.
Fix: Remove `signing_secret` from `to_dict()` and return it exactly once, from the `create_webhook_endpoint` response, by building that response as `{**endpoint.to_dict(), "signing_secret": secret}` at the creation site. Preserve what makes the feature usable: creation must still return the secret in full — pin that, because a fix that strips the field everywhere breaks onboarding. Red-prove separately: (1) call the list endpoint and assert `"signing_secret" not in body[0]` (red today); (2) call create and assert the secret *is* present and matches what was persisted (reddens if the strip is over-applied). Fail loudly: if a future caller needs the secret, add an explicit re-issue endpoint that rotates rather than reveals — do not reintroduce the field. Boundary and tie: state that rotation issues a new secret and that both old and new are accepted for a stated overlap window, or that rotation is immediate; leaving it unstated is where the next defect enters.

### Major: full signature headers are logged and full third-party response bodies are persisted
File: `app/webhooks/delivery.py` — `send_once` (`log.info("POST %s headers=%s", endpoint.url, headers)`), `deliver` (`_finish(..., response.text)`)
What is wrong: The `headers` dict logged at INFO contains the `X-Acme-Signature` and `X-Acme-Timestamp` values, and `response.text` is written unbounded into `webhook_deliveries.response_body`, which is readable through the deliveries endpoint.
What breaks in production: Signature material is replicated into the log pipeline where a much wider audience can read it (and, given the unsigned-timestamp defect above, a captured signature is replayable indefinitely), while an endpoint returning a multi-megabyte body bloats the table and is echoed back through the API.
Fix: Log only `endpoint.url` and the header *names* (`sorted(headers)`), and truncate the persisted body with an explicit cap (`detail[:RESPONSE_BODY_LIMIT]` with a named constant and a `"… truncated"` marker so the truncation is visible, not silent). Preserve the diagnostic value the log exists for: the URL, the delivery id, the status code and the attempt number must still appear — do not fix this by deleting the log line. Red-prove separately: (1) assert the emitted log record contains no value matching `sha256=` (red today); (2) return a body larger than the cap and assert the stored value is exactly the cap length plus the marker; (3) remove the marker and assert the truncation test reddens. Fail loudly when the response cannot be decoded (binary body): store a named placeholder rather than raising inside the retry loop. Boundary and tie: a body of exactly `RESPONSE_BODY_LIMIT` bytes is stored whole with no marker; one byte more is truncated.

### Major: three new routes ship with no rate limiting (RS2)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: None of the new endpoints declares a rate limit, and `create_webhook_endpoint` in particular is an unbounded write that also performs an outbound DNS/network-adjacent decision once the SSRF fix above lands.
What breaks in production: A single authenticated token can create endpoints without bound (each one multiplying the fan-out of every future event) and can hammer the deliveries listing, turning one compromised API key into a self-amplifying load generator.
Fix: Apply the project's existing rate-limit dependency to all three routes (R1: locate it before writing a new one — `app/api/deps` already exports `current_user`, so check that module first and, if no limiter exists there, say so explicitly rather than hand-rolling one), and additionally cap endpoints per organization with a `COUNT` check inside `create_webhook_endpoint` returning 409 past the cap. Preserve the allow side: a normal client creating one endpoint and listing deliveries at a human rate must be unaffected — pin a request just under the limit that still returns 201/200. Red-prove separately: (1) exceed the request rate and assert 429; (2) send one request under the limit and assert success; (3) create endpoints up to the per-org cap and assert the next one is 409. Fail loudly if the limiter's backing store is unavailable — deny, do not fall open, since a limiter that silently disables itself is worse than none. ### Major: unvalidated request inputs at the new boundaries (RS3)

### Major: webhook enqueue is fire-and-forget outside the event transaction, and every failure is swallowed
File: `app/events/dispatcher.py` — the `try/except Exception` around `webhook_delivery.enqueue_for_event`
What is wrong: The `Event` row is committed by its own `session_scope`, the enqueue then runs in a *separate* transaction, and any failure is caught by a bare `except Exception` that logs at WARNING and returns success (R9: fire-and-forget across a transaction boundary; the common baseline's "catch to recover" is not satisfied — nothing recovers).

Red-prove each clause separately: (1) force `enqueue_for_event` to raise and assert no `Event` row is committed (red today, where the event survives); (2) assert the happy path still returns `event_id` and both rows exist; (3) narrow the except to the specific recoverable exception and assert an unexpected error now propagates.
