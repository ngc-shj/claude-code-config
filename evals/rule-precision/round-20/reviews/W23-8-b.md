### Critical: signed bytes and transmitted bytes are produced by two different serializers
File: `app/webhooks/delivery.py` — `send_once` (`sign(...)` then `client.post(..., json=delivery.payload)`)
What is wrong: `sign()` computes the HMAC over `serialize(payload)` = `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`), while `client.post(json=...)` re-serializes the same dict with httpx's own encoder (insertion order, compact separators), so the digest in `X-Acme-Signature` is not a MAC of the bytes on the wire.
What breaks in production: every customer following `docs/webhooks.md` ("HMAC-SHA256 of `{timestamp}.{raw_request_body}`") computes a different digest and rejects 100% of deliveries — a silent total-path failure the delivery worker records as a 4xx and retries five times per event (R40, and R1: the shared `serialize()` helper exists in this diff and `send_once` bypasses it).
Fix: in `send_once`, build the body once and send those exact bytes — `body = serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, delivery.payload)`, then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})`; make `sign()` take and return the serialized bytes so the MAC input and the wire body are provably the same object rather than two calls that happen to agree. Preserve what the current code makes useful — the request must still carry `Content-Type: application/json` and the payload must still be a JSON object, so do not "fix" this by dropping the header or by sending a form body. Boundary and tie: state that the signed region is the complete body with no trailing newline, and that an empty payload signs the two bytes `{}`. Red-prove each clause separately, by execution: (i) mutate `serialize` to `json.dumps(payload)` (drop `sort_keys`) and observe a round-trip test that recomputes the HMAC over `request.content` go red; (ii) mutate `send_once` back to `json=delivery.payload` and observe the same test go red for the separator difference; (iii) mutate the header name and observe a third, differently-named assertion go red. Pair the deny side with the allow side: the round-trip test must also assert that a correctly signed request VERIFIES — feed `request.content` and the captured header through `signing.verify` and assert `True`, so a fix that always produces a mismatching signature cannot pass. Fail loudly when the check cannot run: if `serialize` raises on a non-JSON-serializable payload, `send_once` must raise a named error and `_finish` must record `failed_permanent`, never post an unsigned or partially signed body.

### Critical: the signature does not cover the timestamp, so `X-Acme-Timestamp` is unauthenticated
File: `app/webhooks/signing.py` — `sign` / `verify`
What is wrong: `sign()` returns a timestamp but MACs only the payload, so the timestamp header is attacker-mutable and the documented replay defence ("reject requests whose timestamp is more than five minutes old") is defeated by rewriting a single header on a captured request.
What breaks in production: any party who observes one delivery (a proxy, a log aggregator, the `log.info` line below, a misrouted request) can replay it forever with a fresh timestamp, and a replayed `invoice.paid` is a billing-state mutation on the customer's side (R49: the doc claims a control the implementation does not provide).
Fix: change the signed region to the documented one — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` where `body` is the exact bytes sent (see the previous finding), and give `verify(secret, body, timestamp, signature)` the same signature so producer and verifier cannot drift. Add a `MAX_SKEW_SECONDS = 300` bound checked in `verify` before the MAC comparison is even reached, and export it so the doc's "five minutes" and the code's constant are one value (R2). Do not fix by deleting what made the feature useful: the timestamp header must still be emitted and must still be a unix-seconds integer string, and `verify` must remain callable by customers with only the secret, the raw body, and the two headers. Boundary and tie: a request whose timestamp is exactly `now - 300` is ACCEPTED (`skew <= MAX_SKEW_SECONDS`), `now - 301` is rejected, and a timestamp in the future by more than the same bound is rejected — state this in `docs/webhooks.md` too. Red-prove each clause separately: (i) rewrite only the timestamp header on an otherwise valid request and assert `verify` returns `False`; (ii) set the timestamp to `now - 301` with a correctly recomputed MAC and assert rejection for the skew reason, not the MAC reason; (iii) set it to `now + 3600` and assert rejection. Pair with the allow side: a request signed one second ago with the correct secret must still verify `True`, and that assertion must be in the same test file, so a `verify` that returns `False` unconditionally fails the suite.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: `random.choice` draws from the Mersenne Twister, a non-cryptographic PRNG whose internal state is recoverable from a modest run of outputs, and the secret is 32 characters from a 62-symbol alphabet rather than the 32 random *bytes* the constant name claims.
What breaks in production: an attacker who registers a handful of endpoints of their own recovers the generator state and predicts every other tenant's signing secret, at which point they can forge deliveries that every customer's verifier accepts as genuine.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` imports, so the weak primitive cannot be reached from this module at all. Rename nothing else, but state in the module that `SECRET_BYTES` is now an entropy count in bytes, and correct `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length`, which currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` and therefore enshrines the character-count reading — that assertion is what made the defect invisible, so it must be corrected rather than deleted (assert `>= len(SECRET_PREFIX) + 40`, the base64url length of 32 bytes). Existing rows keep their old secrets, so ship a one-time rotation: mark endpoints created before the fix, surface a rotation endpoint (see the missing-rotation finding below), and do not invalidate old secrets silently. Pair the deny side with the allow side: assert that two consecutive calls differ AND that a secret produced by the new generator still round-trips through `sign`/`verify` successfully — a generator returning a constant would otherwise satisfy every tightening assertion. Boundary and tie: two calls returning the identical string is a hard failure, not a flake; assert it over 1000 draws. Red-prove separately: (i) stub `secrets.token_urlsafe` to return a fixed string and observe the uniqueness assertion go red; (ii) drop `SECRET_PREFIX` and observe the prefix assertion go red; (iii) shorten the token to 8 bytes and observe the length assertion go red. Fail loudly: if `secrets` is unavailable the call must raise, never fall back to `random`.

### Critical: HMAC comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the digest comparison uses Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: this function is the reference verifier shipped to customers in the same module the docs point at, and any customer or internal service that uses it to authenticate inbound webhooks leaks the correct digest byte-by-byte to a timing attacker, who then forges deliveries.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` (or both to `bytes`) before the call so a `bytes`/`str` mix raises rather than silently returning `False`. Do not fix by deleting the function: it is the documented verification reference and must keep the same public shape. Boundary and tie: a signature of the wrong LENGTH must still be rejected via `compare_digest` (it is length-safe) rather than by an early `len()` return that reintroduces the leak; a `None` or empty signature must be rejected, not raise. Pair the deny side with the allow side: keep `test_verify_accepts_signature_produced_by_sign` green — a `verify` hardcoded to `False` must fail the suite. Red-prove separately: (i) flip one hex character of a valid signature and observe rejection; (ii) truncate the signature and observe rejection without an exception; (iii) mutate `compare_digest` back to `==` and observe a grep-based or `ast`-based guard test naming the operator go red — a timing measurement is not a reliable CI assertion, so the invariant that must be pinned is "this module contains no `==` on a digest".

### Critical: `list_deliveries` has no tenancy filter — cross-organization data exposure
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `endpoint_id` taken from the URL path and never joins to `WebhookEndpoint.org_id == user.org_id`, while every sibling handler in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) scopes by `user.org_id` (R3, security-relevant → Critical).
What breaks in production: any authenticated user can enumerate `endpoint_id` and read other organizations' delivery rows, and `WebhookDelivery.to_dict()` exposes `event_id`, `event_type` and `response_status` for those tenants.
Fix: join and scope the query — `.join(webhook_models.WebhookEndpoint, webhook_models.WebhookEndpoint.id == webhook_models.WebhookDelivery.endpoint_id).filter(webhook_models.WebhookEndpoint.org_id == user.org_id, webhook_models.WebhookDelivery.endpoint_id == endpoint_id)` — and return `404` (not `403`) when the join yields nothing, so the endpoint does not become an existence oracle. Cross-cutting check performed: the same missing-scope shape does not recur on the other two new routes (both already filter on `user.org_id`), and `enqueue_for_event` already scopes by `org_id`; `deliver`/`_claim_batch` are worker paths with no request principal, so tenancy there is carried by `endpoint_id` and is out of this finding's scope. Do not fix by removing the endpoint — the doc advertises it and it must still return this organization's own deliveries. Boundary and tie: an endpoint belonging to the caller's org returns its rows; an endpoint id that does not exist and one that exists in another org must be indistinguishable in status code, body, and timing. Red-prove each clause separately: (i) a test where org B requests org A's `endpoint_id` asserts `404` AND asserts the response body contains no delivery rows — assert the absence of the rows, not only the status, or the test passes against a handler that returns data with a 404; (ii) mutate the handler to drop the `org_id` filter and observe that test go red; (iii) a paired allow-side test where org A requests its own endpoint asserts `200` and a non-empty list, so a handler that 404s everything fails.

### Critical: the `signing_secret` is returned on every list call, contradicting the documented one-time-disclosure control
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `list_webhook_endpoints`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so the secret is readable on every `GET`, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R49: a claim strictly stronger than the implementation; RS4 escalation, the artifact carries live credential material).
What breaks in production: any actor with a read-only session, a leaked read token, or access to a response cache or browser history recovers every endpoint's signing secret and can forge webhook deliveries indistinguishable from genuine ones.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` entirely and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held value at creation time — the disclosure then exists at exactly one call site rather than being a property of the model. Do not fix by leaving the field in and filtering it in the route: that reinstates the same defect at the next consumer of `to_dict()`. Boundary and tie: on the create path the secret appears exactly once, in the 201 body; on every other path the key is absent (absent, not `null` and not a masked prefix, so no partial digest leaks). Pair the deny side with the allow side: assert the 201 response DOES contain a `whsec_`-prefixed secret — a `to_dict()` that drops every field passes a deny-only test. Red-prove each clause separately: (i) re-add `"signing_secret": self.signing_secret` to `to_dict()` and observe a test asserting `"signing_secret" not in body` for the list route go red; (ii) drop the explicit merge in the create route and observe the create-path assertion go red; (iii) grep-assert that `signing_secret` appears in no serializer, and mutate a second serializer to include it to prove the guard is not blind to a second declaration (RT9's drift direction).

### Critical: the DB CHECK constraint and the application's terminal status string disagree
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the application writes `"failed_permanent"` (matching `models.STATUSES`), which the migration's CHECK constraint rejects; the diff contains three independent spellings of the same vocabulary — `models.STATUSES`, the SQL CHECK list, and bare literals in `delivery.py` (R2, and R40 with the database as the strict consumer).
What breaks in production: every permanently failed delivery raises a `CheckViolation` inside `_finish`, so the row never leaves `in_flight` and — because `_claim_batch` only selects `status == "pending"` — is never retried or reported; the failure is invisible in the deliveries API, which is the only place a customer would see it.
Fix: make the SQL constraint derive from one source. Change the migration's list to `('pending', 'in_flight', 'delivered', 'failed_permanent')` to match `models.STATUSES`, replace every bare status literal in `delivery.py` with a reference to that tuple (add named members, e.g. `STATUS_PENDING`, so `_claim_batch` and `_finish` cannot drift again), and add a test that asserts the CHECK constraint's accepted set equals `set(models.STATUSES)` by reading the constraint definition from the migration file — a hand-copied second list is what produced this defect and must not be reintroduced. Do not fix by dropping the CHECK constraint: the constraint is what makes an unknown status visible, and removing it converts a loud failure into a corrupt column. Boundary and tie: `models.STATUSES` and the constraint set must be equal, not merely one a subset of the other, so both an added and a removed member fail. Red-prove each clause separately: (i) add a fifth member to `models.STATUSES` and observe the equality test go red; (ii) remove `failed_permanent` from the SQL list and observe it go red for the other direction; (iii) an integration test that drives one delivery to permanent failure asserts the persisted `status` reads back as `failed_permanent`, and reverting `_finish` to the old literal must redden it. Pair the deny side with the allow side: a successful delivery must still persist `delivered` and be readable through `list_deliveries`.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint, so any organization with two or more active endpoints violates the index on the second insert; the doc's "delivery is at-least-once, so deduplicate on `event_id`" also contradicts a schema that permits at most one delivery per event globally.
What breaks in production: `session.add_all(rows)` raises `IntegrityError`, `dispatch` swallows it with `log.warning`, and **every** webhook for that event is dropped — including the first endpoint's, since the whole unit of work rolls back; the customer sees nothing at all and the only trace is a warning line.
Fix: make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the pair that actually expresses the idempotency the doc promises (one delivery per event per endpoint) and keeps the at-least-once dedup key the doc tells customers to use. Add the composite `CREATE INDEX idx_webhook_deliveries_due ON webhook_deliveries (status, next_attempt_at)` in the same migration, since the claim query orders by `next_attempt_at` and the shipped `(status)`-only index does not serve it. Do not fix by dropping uniqueness altogether: it is what prevents a re-dispatched event from double-charging a customer's downstream system. Boundary and tie: two endpoints receiving the same `event_id` both succeed; the same `(endpoint_id, event_id)` inserted twice raises, and `enqueue_for_event` must handle that with `ON CONFLICT DO NOTHING` semantics rather than aborting the batch. Red-prove each clause separately: (i) a test enqueuing one event for an org with two active endpoints asserts two rows exist, and reverting the index to `(event_id)` reddens it; (ii) a test enqueuing the same event twice for one endpoint asserts exactly one row and no exception; (iii) drop the uniqueness entirely and observe (ii) go red. Pair the deny side with the allow side: the duplicate-suppression test must not be satisfiable by an `enqueue_for_event` that inserts nothing — assert the row count is 1, not `<= 1`.

### Critical: endpoint URLs are unvalidated against internal targets and the client follows redirects — SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`parsed.scheme.startswith("http")`) with `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check is that the scheme string begins with `http` (which also admits `httpx:`, `http+unix:`) and that `netloc` is non-empty — there is no denial of loopback, RFC 1918, link-local, or `.internal` targets, no DNS-resolution check, and the delivery client follows redirects, so even an initially-public URL can redirect into the cluster (RS3, escalated: caller-supplied input reaches a request-issuing interpreter).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or a public host that 302s there) and the worker fetches cloud instance credentials, storing the response verbatim in `webhook_deliveries.response_body`, which that same tenant reads back through `GET /webhook-endpoints/{id}/deliveries`.
Fix: validate at the schema boundary with a pydantic `HttpUrl`-typed field plus an explicit check that `parsed.scheme == "https"` (the doc already promises https-only — see the scheme finding below), then resolve the hostname at delivery time and reject any address in a denylist of `ipaddress` categories (`is_private`, `is_loopback`, `is_link_local`, `is_reserved`, `is_multicast`, and the IPv4-mapped IPv6 forms of each) before the socket is opened, using a pinned-address transport so the check and the connection use the same IP (a re-resolve between check and connect is R51's rebinding window). Set `follow_redirects=False` and record a 3xx as a permanent failure with a message naming redirects as unsupported. Truncate `response_body` to a bounded prefix so an exfiltrated body cannot be read back wholesale. Do not fix by deleting the deliveries API — customers need the response status; keep the status and the truncated body. Boundary and tie: `127.0.0.1`, `::1`, `10.0.0.1`, `169.254.169.254`, `0.0.0.0` and `[::ffff:127.0.0.1]` are all rejected; a genuine public HTTPS host is accepted; a host that resolves to BOTH a public and a private address is rejected (any-address-private, not first-address-private). Red-prove each clause separately: (i) register a link-local URL and assert `422`, then remove the IP denylist and observe it go red; (ii) point a public test host at a 302 to a private address and assert the delivery is recorded permanently failed, then re-enable `follow_redirects` and observe it go red; (iii) submit `http://` and assert `422`, then relax the scheme check and observe it go red. Pair the deny side with the allow side: a valid `https://hooks.example.com/acme` must still register with `201` and still deliver — a validator that rejects everything must fail the suite. Fail loudly when the check cannot run: DNS resolution failure at delivery time must be a named, retryable error, never a fall-through to "no private address found, proceed".

### Critical: `time.sleep` inside an async coroutine blocks the entire delivery worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine driven by `asyncio.gather` over a whole batch, and `time.sleep` blocks the event loop rather than yielding, so one retrying delivery freezes every other coroutine, the HTTP client, and the worker loop itself.
What breaks in production: a batch of 100 with even a few failures serializes into minutes of frozen event loop (up to 2+4+8+16 = 30s of blocking per failing delivery, plus up to 30s per request timeout), during which the 60-second Redis lock expires and a second worker claims and re-sends the same rows — every customer receives duplicates while throughput collapses to zero.
Fix: `await asyncio.sleep(delay)`. That alone is not sufficient: the in-process retry loop must also be replaced by a rescheduling write, because a worker restart mid-loop loses the retry entirely (see the non-terminal-state finding). Concretely, on a retryable failure `_finish` should persist `status="pending"`, the incremented `attempts`, and `next_attempt_at = now + backoff_for(attempt)`, and `deliver` should return rather than loop — the delay then lives in the database where a restart preserves it, and no coroutine sleeps at all. Do not fix by removing the backoff: the delay between attempts is what protects the customer's endpoint from a retry storm, and it must survive the change. Boundary and tie: an attempt at exactly `attempts == MAX_ATTEMPTS` writes `failed_permanent` and schedules nothing; `attempts == MAX_ATTEMPTS - 1` writes `pending` with a future `next_attempt_at`; a row whose `next_attempt_at` is exactly `now` is claimable (`<= now`). Red-prove each clause separately, by execution: (i) a test that measures wall-clock time across `deliver` for a failing delivery asserts it returns in well under the backoff, and restoring `time.sleep` reddens it; (ii) a test asserts a retryable failure leaves `status == "pending"` with `attempts == 1` and `next_attempt_at` advanced by exactly `backoff_for(1)`, and reverting to the in-process loop reddens it; (iii) a test asserts the fifth failure writes `failed_permanent`. Pair the deny side with the allow side: a first-attempt 200 must still write `delivered` with `attempts == 1` and must not schedule a retry.

### Major: no rotation, deactivation, or deletion path for a signing secret or an endpoint
File: `app/api/routes/settings.py` — the three new `/webhook-endpoints` routes; `app/webhooks/models.py` — `WebhookEndpoint.active`
What is wrong: the change creates a long-lived credential and an egress target but ships only create and list — there is no route to rotate `signing_secret`, to flip `active` to `False`, or to delete an endpoint, even though the model and the migration both carry an `active` column that nothing ever writes after creation.
What breaks in production: a customer whose signing secret leaks (or whose endpoint host is decommissioned or taken over) has no way to revoke it, and support must edit the database by hand while the worker keeps POSTing signed events to a host the customer no longer controls.
Fix: add `PATCH /v1/settings/webhook-endpoints/{endpoint_id}` accepting `{"active": bool}` and `POST /v1/settings/webhook-endpoints/{endpoint_id}/rotate-secret` returning the new secret exactly once, both scoped by `user.org_id` through the same join used in the tenancy fix above, and both writing an audit row. Rotation must not invalidate in-flight deliveries silently: sign each pending delivery with the secret current at send time and document that a rotation may produce one delivery under each secret. Do not fix by deleting the `active` column — it is what lets a customer stop delivery without losing delivery history. Boundary and tie: an endpoint with `active = False` is skipped by `enqueue_for_event` (which already filters `active.is_(True)`) but its existing pending rows still drain, and two rotations in the same second must both succeed and the second must win. Red-prove each clause separately: (i) deactivate an endpoint, dispatch a subscribed event, assert zero new delivery rows for it, then remove the `active` filter and observe it go red; (ii) rotate and assert the returned secret differs from the stored-before value and that a signature made with the old secret no longer verifies; (iii) attempt both routes as another org and assert `404`. Pair the deny side with the allow side: an active endpoint must still receive events after an unrelated endpoint is deactivated.

### Major: no rate limiting on any of the three new routes
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: three new authenticated endpoints are added with no rate limiter, and `create_webhook_endpoint` in particular performs an unbounded row insert plus a CSPRNG draw per call (RS2).
What breaks in production: a single tenant can register endpoints without bound, multiplying the worker's fan-out per event by the number of registered endpoints and turning one dispatched event into an arbitrary volume of outbound requests from the platform's IP range.
Fix: apply the project's existing rate-limiter dependency to all three routes (grep for a shared limiter before writing a new one — R1: do not add a second implementation), and additionally cap endpoints per organization with a hard `MAX_ENDPOINTS_PER_ORG` check inside `create_webhook_endpoint` that returns `409` when exceeded, since a rate limit bounds the rate but not the total. Do not fix by removing the create route. Boundary and tie: the request that brings the org to exactly `MAX_ENDPOINTS_PER_ORG` succeeds; the next one returns `409`; two concurrent creates at the boundary must not both succeed, so the count and the insert must share one transaction with a unique constraint or a row lock. Red-prove each clause separately: (i) drive the limiter past its threshold and assert `429`, then remove the dependency and observe it go red; (ii) create up to the cap and assert the next returns `409`; (iii) run two creates concurrently at the boundary and assert exactly one succeeds. Pair the deny side with the allow side: a single create under both limits must still return `201` — a limiter that rejects everything must fail the suite.

### Major: `limit` on the deliveries route has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: `ge=1` bounds the parameter below but nothing bounds it above, so a caller may request `limit=100000000` (RS3).
What breaks in production: a single request materializes an unbounded result set into memory and serializes it through `to_dict()`, exhausting the worker process and taking down unrelated requests on the same instance.
Fix: `limit: int = Query(50, ge=1, le=200)` so the rejection happens in the schema layer with a `422` rather than deep in the query, and switch the route to keyset pagination on the primary key (see the ordering finding below) so a caller who genuinely needs more pages has a correct way to get them. Do not fix by removing the `limit` parameter: callers need to ask for fewer than the default. Boundary and tie: `limit=200` succeeds, `limit=201` returns `422`, `limit=0` returns `422`, and a non-integer returns `422`. Red-prove each clause separately: (i) request `limit=201` and assert `422`, then remove `le=200` and observe it go red; (ii) request `limit=0` and assert `422`; (iii) request `limit=200` and assert `200` with at most 200 rows.

### Major: `enqueue_for_event` writes a naive datetime into an aware column, and the migration declares no time zone at all
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP NOT NULL` columns
What is wrong: three of the four datetime producers in this diff are timezone-aware (`models._now()`, `_claim_batch`'s `datetime.now(timezone.utc)`, `_finish`'s `updated_at`) and only `enqueue_for_event` uses naive `datetime.utcnow()`, while the SQLAlchemy models declare `DateTime(timezone=True)` and the migration declares bare `TIMESTAMP` (without time zone) — R3, the one site the pattern did not reach.
What breaks in production: on a non-UTC database session the naive value is interpreted in the server's local zone, so `_claim_batch`'s `next_attempt_at <= now` comparison is wrong by the UTC offset and deliveries are either claimed hours early or never become due; on some driver configurations the aware/naive mix raises `TypeError` outright and no delivery is ever enqueued.
Fix: change `enqueue_for_event` to `next_attempt_at=_now()` importing the existing helper from `app.webhooks.models` rather than adding a fourth clock call (R1: the helper is already in this diff), and change every `TIMESTAMP` in the migration to `TIMESTAMPTZ` with `DEFAULT now()` so the storage type matches the `timezone=True` the models declare. ### Major: `in_flight` is a non-terminal state with no timeout and no reclaim path

### Major: the Redis lock is not atomic, not owned, and shorter-lived than the work it guards
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does GET-then-SET with a race window between them and a second window between `set` and `expire` (a crash in between leaves a lock with no TTL that wedges every worker forever); the 60-second TTL is far shorter than a batch of up to 100 deliveries at up to 30s request timeout each; and the `finally` deletes the key unconditionally, including a key another worker has since acquired.
What breaks in production: two or more workers run concurrently, claim overlapping rows (see the `SKIP LOCKED` finding), and customers receive duplicate deliveries — and because the lock is released by whichever worker finishes first, the duplication is not self-limiting.
Fix: acquire with a single atomic command carrying both the TTL and a per-worker token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a Lua compare-and-delete that removes the key only when its value still equals this worker's token. Add a heartbeat that extends the TTL while the batch runs, and set `LOCK_TTL_SECONDS` from the worst-case batch duration (`BATCH_SIZE * REQUEST_TIMEOUT`) rather than a bare `60`. Do not fix by removing the lock: single-flight is what keeps duplicate deliveries out, and the fix must keep it. Boundary and tie: two workers calling acquire simultaneously — exactly one gets `True`; a worker whose lease expired mid-batch must NOT delete the successor's lock, and its own subsequent writes must be refused rather than silently applied. Red-prove each clause separately: (i) run two acquires concurrently against a real Redis (not a mock — a mocked `set` returns whatever the fixture says and the race is invisible, RT5) and assert exactly one `True`, then revert to GET-then-SET and observe the assertion go red under repeated runs; (ii) let worker A's lease expire, have worker B acquire, then have A release, and assert B's lock still exists; (iii) kill a worker between `set` and `expire` in the old code path and assert the new path leaves a key with a positive TTL. Pair the deny side with the allow side: after a clean release the next acquire must return `True` — a lock that never releases satisfies every mutual-exclusion assertion.

### Major: `_claim_batch` reads then writes without row locking — two workers claim the same rows
