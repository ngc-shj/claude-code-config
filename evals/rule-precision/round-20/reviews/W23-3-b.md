### Critical: deliveries endpoint is not scoped to the caller's organization
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` while every sibling route in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) filters on `user.org_id`, so the org predicate was not propagated to the new read path (R3, security-relevant).
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other tenants' delivery rows — event types, response statuses and schedule of every customer's webhooks.
Fix: join through the endpoint and filter on ownership — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and raise `HTTPException(404)` when no endpoint with that id belongs to `user.org_id`, so a foreign id is indistinguishable from a missing one. Preserve the existing behaviour that an owner with zero deliveries still gets `200 []` (do not repair this by making the route always 404): pin an allow-case test asserting the owning org receives its own rows, and a deny-case test asserting a second org's user gets 404 and that the response body contains no delivery ids. Red-prove the two clauses separately — (i) delete the `org_id` predicate and the deny test must red on status, (ii) change the not-found branch to return `[]` and a second assertion must red on the 404 — and make the endpoint-lookup failure path deny explicitly rather than fall through to an empty list, so "no such endpoint" is never spelled the same as "no deliveries". Boundary/tie: an endpoint whose `org_id` differs from the caller's and an endpoint id that does not exist must both yield 404 with identical bodies.

### Critical: registered webhook URLs are unvalidated against internal targets and redirects are followed
File: app/api/routes/settings.py — `create_webhook_endpoint`; app/webhooks/delivery.py — `run_worker` (`follow_redirects=True`)
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, so `http://127.0.0.1:6379/`, `http://169.254.169.254/latest/meta-data/` or any RFC1918 host is accepted, and the client follows redirects so even a public URL can bounce the request to those targets.
What breaks in production: the worker becomes a server-side request forgery primitive against the cluster's metadata service and internal admin ports, with the target's reply persisted verbatim into `webhook_deliveries.response_body`.
Fix: validate at the boundary (RS3) in a single `validate_webhook_url(url)` helper used by the route: require `parsed.scheme == "https"`, reject userinfo and non-default ports outside an allowlist, resolve the host with `socket.getaddrinfo` and reject every address for which `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast` (including the 100.64.0.0/10 and IPv6-mapped forms), then set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure, and re-run the same address check at delivery time (or pin the connection to the vetted address) because DNS can be re-pointed after registration. Preserve delivery to legitimate public HTTPS endpoints and preserve retry of genuine transient errors — do not "fix" this by disabling retries. Red-prove each clause with its own mutation: an `http://` URL must red the scheme assertion, `https://127.0.0.1/x` must red the address assertion, and a stub responding `302` to `http://169.254.169.254/` must red the redirect assertion; pin the allow case that `https://hooks.example.com/acme` (resolving to a public address) still registers and still delivers. When `getaddrinfo` raises or returns nothing, reject the registration with a named error and mark the delivery `failed_permanent` with that reason — an unresolvable host must never be treated as "not proven private, therefore allowed". Boundary/tie: a hostname resolving to both a public and a private address is rejected.

### Critical: the signature is computed over bytes that are not the bytes transmitted
File: app/webhooks/signing.py — `serialize` / `sign`; app/webhooks/delivery.py — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys sorted) while the body actually sent is produced by `client.post(..., json=delivery.payload)`, which emits compact, insertion-ordered JSON — the two byte strings differ for essentially every payload.
What breaks in production: every receiver that follows `docs/webhooks.md` and HMACs the raw request body computes a different digest, so 100% of deliveries are rejected as forged and the integration never works for anyone (R40, producer shape vs strict consumer).
Fix: serialize once and send those exact bytes — have `send_once` compute `body = serialize(delivery.payload).encode()`, sign that buffer, and call `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` instead of `json=`; keep `serialize` as the single canonicalization point so signer and sender cannot drift, and state in `docs/webhooks.md` that the signature covers the raw body verbatim. Do not fix this by relaxing the receiver's check or by dropping the canonical form. Add a round-trip test that feeds the *actual* captured `request.content` from `httpx.MockTransport` into the *actual* `signing.verify` (not a re-serialized copy) and asserts it verifies — that pins the allow case; red-prove it by changing `serialize` to use `separators=(",", ":")` on the signing side only, which must red that single assertion. Boundary/tie: payloads containing non-ASCII must be pinned too (`ensure_ascii` and the encoding are part of the signed byte contract), and an empty `{}` payload must still produce a verifiable signature rather than an empty body.

### Critical: the timestamp is not covered by the MAC, so the documented replay window is unenforceable
File: app/webhooks/signing.py — `sign` / `verify`
What is wrong: `sign` returns a timestamp header but HMACs only the payload, whereas `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`; `verify` likewise ignores the timestamp entirely.
What breaks in production: an attacker who captures one delivery can replay it forever with a freshly rewritten `X-Acme-Timestamp`, because the signature stays valid and the receiver's five-minute check is applied to an unauthenticated field — for `invoice.paid` that is a replayed payment notification.
Fix: change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` over the exact transmitted body, and change `verify` to take `timestamp` and `body` explicitly, recompute over the same concatenation, and reject when `abs(now - int(timestamp)) > TOLERANCE_SECONDS` (define `TOLERANCE_SECONDS = 300` once and reference it from the doc rather than restating `five minutes`). Keep `verify` usable by receivers with legitimately skewed clocks — pin the allow case that a signature made 299 seconds ago still verifies, alongside the deny case that one made 301 seconds ago does not. Red-prove the two clauses separately: removing the timestamp from the MAC input must red an assertion that a signature is invalid after the timestamp header is altered, and removing the tolerance check must red the 301-second assertion. A non-numeric or absent timestamp must raise/deny with a named error, never be coerced to `0` (which would silently pass or silently fail every request). Boundary/tie: `abs(delta) == 300` is accepted; delta of exactly `-300` (future-dated) is accepted, beyond that rejected.

### Critical: signature comparison is not constant time
File: app/webhooks/signing.py — `verify` (`return expected == signature`)
What is wrong: the recomputed digest is compared with Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: any receiver that adopts this shipped helper leaks the expected digest byte-by-byte to a remote attacker who can time responses, letting them forge signatures for arbitrary payloads.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands normalised to `str`/`bytes` of the same type first, and keep the `sha256=` prefix inside the compared string so the prefix is not a separate short-circuiting check. Preserve the current true case — pin an allow test that a signature produced by `sign` still verifies — and add the deny test that a digest differing only in its last hex character is rejected. Red-prove by reverting to `==` and asserting, in a separate test, that `verify` is implemented via `hmac.compare_digest` (patch/spy on it) so the mutation reds an assertion that names the primitive rather than one that merely still returns `False`. If `signature` is `None` or malformed, return `False` explicitly rather than raising a `TypeError` that a caller might catch and treat as "verified".

### Critical: signing secrets are generated with the non-cryptographic `random` module
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: the secret is built from `random.choice` over a 62-character alphabet, i.e. the Mersenne Twister seeded from process state, instead of the standard library's own CSPRNG helper (`secrets.token_urlsafe` / `secrets.choice`) — a security control reimplemented with a weaker primitive (R1, Critical arm).
What breaks in production: an attacker who observes a handful of outputs (their own endpoint secrets, created in sequence) can recover the generator state and predict every other tenant's signing secret, forging webhooks into their systems.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` code outright rather than leaving it as an unused helper; rename `SECRET_BYTES` to reflect that it now really is a byte count (32 bytes → 43 URL-safe characters) and update `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length`, which currently pins `len == len(prefix) + SECRET_BYTES` and would otherwise fail for the right reason and be "fixed" by widening. Preserve the `whsec_` prefix and the property that the secret is opaque and URL-safe — pin an allow test that the new secret still verifies a signature end-to-end through `sign`/`verify`, plus an entropy floor test asserting 1000 generated secrets are distinct and each has at least the documented length. Red-prove separately: (i) swapping `secrets` back to `random` must red an assertion that patches `secrets.token_urlsafe` and asserts it was the source, (ii) shortening the length must red the length assertion. Rotation: existing rows created by the weak generator must be treated as compromised — ship a one-off re-issue of every `webhook_endpoints.signing_secret` created before this change, not just the code fix.

### Critical: the `status` CHECK constraint does not admit the value the code writes
File: migrations/0042_webhook_delivery.sql — `webhook_deliveries.status CHECK`; app/webhooks/delivery.py — `_finish`
What is wrong: the constraint allows `('pending','in_flight','delivered','failed')` while `models.STATUSES` and `_finish` use `failed_permanent` — an enum-spelling divergence across a producer/strict-consumer boundary (R40).
What breaks in production: the first delivery that exhausts its attempts raises a `CheckViolation` inside `_finish`, the exception escapes `deliver` (only `httpx.HTTPError` is caught) and propagates through `asyncio.gather`, killing the worker loop; the row stays `in_flight` forever and no webhook is ever delivered again until a restart.
Fix: change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and derive it from one source — generate the constraint list from `app.webhooks.models.STATUSES` in the migration test, or add a test that asserts the constraint's allowed set equals `set(STATUSES)` by querying `pg_constraint` — so the two cannot drift again. Keep the constraint (do not fix this by dropping the CHECK, which is what made the divergence visible). Pin the allow case that inserting each member of `STATUSES` succeeds, and the deny case that inserting `'bogus'` raises. Red-prove the two clauses separately: removing `failed_permanent` from the constraint must red the allow test for that one value, and removing the CHECK entirely must red the deny test. Boundary/tie: state that the migration must run against a database that may already contain rows — since the table is new here, the constraint can be created directly, but the same test must fail loudly (not skip) when the database is unavailable.

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible
File: migrations/0042_webhook_delivery.sql — `idx_webhook_deliveries_event`; app/webhooks/delivery.py — `enqueue_for_event`
What is wrong: `CREATE UNIQUE INDEX ... ON webhook_deliveries (event_id)` permits exactly one delivery row per event, but `enqueue_for_event` inserts one row per matching endpoint, and the dispatcher swallows the resulting `IntegrityError`.
What breaks in production: any organization with two or more active endpoints silently receives no webhooks at all — the whole `add_all` is rolled back and `dispatch` logs a warning nobody reads.
Fix: make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the real idempotency key (one delivery per event per destination), and add the composite worker index `CREATE INDEX ... ON webhook_deliveries (status, next_attempt_at)` that the claim query actually needs. Preserve the de-duplication intent — do not fix this by deleting the unique index, since it is what stops a re-dispatched event double-notifying an endpoint. Pin the allow case: an event fanned out to two endpoints of the same org creates two rows; and the deny case: enqueuing the same `(endpoint_id, event_id)` twice raises rather than duplicating. Red-prove separately by (i) reverting to the single-column index, which must red the two-endpoint test, and (ii) dropping the index, which must red the duplicate test. Boundary/tie: an org with exactly one endpoint must be unaffected, and `enqueue_for_event` must use `ON CONFLICT DO NOTHING` semantics (or catch `IntegrityError` per row) so one duplicate does not roll back the other endpoints' rows.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: app/webhooks/delivery.py — `deliver` (`time.sleep(delay)`)
What is wrong: the retry backoff uses the blocking `time.sleep` inside an `async def` that is run under `asyncio.gather`, so it stalls the loop rather than yielding.
What breaks in production: one failing endpoint freezes the entire process for up to 2+4+8+16 = 30 seconds per delivery — the other 99 gathered deliveries, the lock's 60-second expiry, and (if the worker shares a loop with the API) every inbound HTTP request stop dead.
Fix: replace with `await asyncio.sleep(delay)`; better, stop sleeping in-process at all — persist `attempts` and `next_attempt_at = now + backoff_for(attempt)`, set `status = "pending"`, and return, letting the next poll pick the row up, which also makes retry state survive a restart. Preserve the retry schedule (the documented ~2/4/8/16s) while changing where the waiting happens; do not fix this by shortening the delays. Red-prove separately: (i) a test that `deliver` returns promptly and the row is left `pending` with `next_attempt_at` advanced must red if the code sleeps in-process, (ii) a test asserting `attempts` is persisted after a failed attempt must red if the increment is dropped. Pin the allow case that a 2xx on the first attempt still marks the row `delivered` with `attempts == 1` and schedules nothing. Boundary/tie: at `attempt == MAX_ATTEMPTS` the row goes to `failed_permanent` and `next_attempt_at` is not advanced; a row exactly at `next_attempt_at == now` is claimed (the query already uses `<=`, which must stay).

### Critical: the delivered body carries no envelope, so the documented `event_id` de-duplication is impossible
File: app/webhooks/delivery.py — `send_once` (`json=delivery.payload`); docs/webhooks.md — "delivery is at-least-once, so deduplicate on `event_id`"
What is wrong: the request body is the bare `envelope.payload` dict passed through from `dispatch`, which contains no `event_id`, no event type and no delivery id, so the field the documentation tells receivers to de-duplicate on is not in the request at all.
What breaks in production: because delivery is at-least-once (lost 2xx responses, and the non-atomic worker lock below), receivers get duplicate `invoice.paid` bodies they cannot tell apart and double-apply them — a payments-side data corruption with no receiver-side remedy.
Fix: build an explicit envelope in `send_once` — `body = {"id": delivery.event_id, "type": delivery.event_type, "created_at": <iso8601 of the event>, "data": delivery.payload}` — sign and send exactly those bytes (see the serialization finding above), and update `docs/webhooks.md` to name the field as `id` rather than `event_id` so the doc and the wire agree. Preserve the customer-visible payload contents unchanged under `data`; do not fix this by telling receivers to de-duplicate on a header, which is unsigned. Pin the allow case with a round-trip test asserting the captured request body parses to an envelope whose `id` equals the delivery's `event_id` and whose `data` is byte-identical to the source payload, and red-prove it by removing the envelope wrapper (the `data` assertion reds) and by hardcoding `id` to `0` (the id assertion reds) as two separate mutations. `tests/webhooks/test_delivery.py::FakeDelivery` already asserts `json.loads(captured["body"])["type"] == "invoice.paid"` against a fixture payload that contains those keys — that fixture is what hid this defect and must be replaced by the real envelope shape, not kept alongside.

### Major: the signing secret is returned by the list endpoint, contradicting the documented control
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`; docs/webhooks.md — "it cannot be read back afterwards"
What is wrong: `to_dict` includes `signing_secret`, and it is used by both `create_webhook_endpoint` and `list_webhook_endpoints`, so the secret is returned on every list call while the documentation claims the creation response is the only place it appears (R49 — a claim stronger than the implementation).
What breaks in production: the secret is repeatedly exposed to every principal with read access to the settings API, is logged by any proxy or client that records response bodies, and integrators who trusted the doc treat those responses as non-sensitive.
Fix: split the serializers — `to_dict()` omits `signing_secret`, and a separate `to_dict_with_secret()` is called only from the creation handler; make the doc's claim true rather than deleting the claim. Preserve the create-time disclosure (that is the feature): pin the allow case that `POST /v1/settings/webhook-endpoints` returns a body containing `signing_secret`, and the deny case that `GET /v1/settings/webhook-endpoints` returns bodies whose key set does not include it. Red-prove separately: adding `signing_secret` back to `to_dict` must red the GET assertion; removing it from the create path must red the POST assertion. Also add a rotation route or state in the doc that no rotation exists — an integrator who loses the secret otherwise has no recovery path but deleting the endpoint. ### Major: `in_flight` is a non-terminal state with no timeout and no reset path
File: app/webhooks/delivery.py — `_claim_batch` / `deliver`
What is wrong: `_claim_batch` writes `status = "in_flight"` and only `_finish` leaves that state, so any crash, deploy, unhandled exception or OOM between the two wedges the row permanently (R38 case 1: an async transition with no failure exit and no bounded timeout).
What breaks in production: rows silently stop being retried after a routine deploy — no error is raised, the delivery simply never happens, and the customer's `GET .../deliveries` shows `in_flight` forever.
Fix: stamp `claimed_at` (or reuse `updated_at`) when marking `in_flight`, and have `_claim_batch` also reclaim rows with `status = 'in_flight' AND updated_at < now() - interval '5 minutes'` by returning them to `pending`; define the lease duration as one constant shared with the lock TTL. Preserve the guard against two workers taking the same row — do not fix this by dropping the `in_flight` state, which is what prevents concurrent claim. Red-prove separately: (i) a test that a row left `in_flight` with a stale `updated_at` is reclaimed on the next poll must red if the reclaim predicate is removed, (ii) a test that a row `in_flight` for one second is NOT reclaimed must red if the interval is set to zero. Pin the allow case that a freshly claimed row is invisible to a second concurrent `_claim_batch`. Boundary/tie: a row whose `updated_at` is exactly at the lease horizon is reclaimed (`<=`), and reclaim must increment nothing so the attempt count stays honest.

### Major: the worker lock is a non-atomic check-then-set with a separate expiry
File: app/webhooks/delivery.py — `_acquire_lock`
What is wrong: `get` followed by `set` followed by `expire` is three round trips with no atomicity, so two workers can both observe an empty key and both proceed (R5 TOCTOU), and a crash between `set` and `expire` leaves a key with no TTL.
What breaks in production: either every delivery is sent twice by two workers racing the same batch, or — after one badly timed crash — the lock is held forever and webhook delivery stops silently across the whole fleet.
Fix: use a single atomic call — `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` with a per-worker random `token`, and release with a compare-and-delete Lua script so a worker that overran the TTL cannot delete a successor's lock. Preserve single-worker exclusivity — do not fix this by removing the lock. Red-prove separately: (i) replacing `nx=True` with an unconditional set must red a test where a second `_acquire_lock` against a fake Redis returns `True`, (ii) removing `ex=` must red a test asserting the key has a positive TTL, (iii) replacing the compare-and-delete with a plain `delete` must red a test where worker B's lock survives worker A's release. If Redis is unreachable, `_acquire_lock` must raise or return `False` with a named error and the worker must not proceed — an exception from `get` currently escapes `run_worker` and kills the loop, and a "cannot check" must never read as "not locked". Boundary/tie: a token that equals another worker's token must be impossible (use `secrets.token_hex`), and the lease horizon must exceed the maximum time a batch can hold the lock.

### Major: the worker loop dies on the first unhandled exception and can raise `NameError`
File: app/webhooks/delivery.py — `run_worker`
What is wrong: `batch = await _claim_batch()` and the `gather` sit inside a `try/finally` with no `except`, so any DB error, any non-`httpx` exception from `deliver`, or a `None` endpoint propagates out of the `while` loop; and because `batch` is assigned inside that `try`, the trailing `if not batch` raises `NameError` when `_claim_batch` itself fails.
What breaks in production: one malformed row permanently stops all webhook delivery until someone notices the process exited — and `asyncio.gather` without `return_exceptions=True` lets the lock be released in `finally` while sibling deliveries are still running, so a second worker starts double-sending.
Fix: initialise `batch: list = []` before the `try`, wrap the loop body in `except Exception: log.exception(...)` followed by `await asyncio.sleep(poll_interval)` so the worker survives a bad iteration, and call `asyncio.gather(..., return_exceptions=True)` then inspect the results and mark each failed delivery rather than letting the first exception unwind while its siblings run. Preserve fail-fast on programming errors by logging with `log.exception` and incrementing a counter, not by swallowing silently — "examined nothing" must not look like "found nothing". Red-prove separately: (i) a test where `_claim_batch` raises must red an assertion that the loop performed a second iteration, (ii) a test where one of two deliveries raises must red an assertion that the other still reached `_finish`, (iii) a test asserting the lock is released only after all gathered tasks completed must red if `return_exceptions` is dropped. Pin the allow case that a normal batch of two successful deliveries still finishes and releases the lock exactly once.

### Major: `deliver` dereferences an endpoint that may not exist and `_finish` a row that may not exist
File: app/webhooks/delivery.py — `deliver` / `_finish`
What is wrong: `session.get(m.WebhookEndpoint, delivery.endpoint_id)` and `session.get(m.WebhookDelivery, delivery_id)` are used without a `None` check, and the endpoint can legitimately be gone — the migration declares `ON DELETE CASCADE` from `webhook_endpoints`, so an endpoint deleted between enqueue and claim takes its deliveries with it.

Preserve the normal path — pin the allow case that an existing active endpoint still delivers and still records `delivered` — and add the deny cases for a deleted endpoint and a deleted delivery row. Red-prove separately by removing each `None` guard and observing that the corresponding test reds with the `NoneType` message named in its failure output. Note that `deliver` also re-reads the endpoint that `enqueue_for_event` already resolved; the missing-row case must be a named refusal, not an implicit skip. Boundary/tie: an endpoint that exists but has `active = False` is treated the same as a deleted one (`failed_permanent`), not silently retried.

If the limiter's backing store is unavailable the request must be rejected, not allowed through unlimited. Boundary/tie: exactly at the cap the request succeeds; exactly one over it fails.

### Major: every delivery logs the signature and timestamp headers at INFO

### Major: the documented retry semantics do not match the implementation
