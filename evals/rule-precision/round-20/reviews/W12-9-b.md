### Major: the retry semantics the code implements contradict the semantics the documentation publishes
File: `docs/webhooks.md` — the "Retries" section; `app/webhooks/delivery.py` — `deliver`, `backoff_for`
What is wrong: The docs state that "a 4xx is permanent and we stop immediately" and that backoff is "exponential with jitter", while `deliver` retries every non-2xx response identically through all five attempts and `backoff_for` returns a pure power of two with no jitter (R29: a published claim that the implementation does not support).

Red-prove each clause separately: (i) make 404 retryable again and assert the permanent-4xx test reds on the attempt count; (ii) remove the jitter and assert a test that 100 backoffs for the same attempt are not all identical reds; (iii) ignore `Retry-After` and assert the 429 scheduling test reds. Fail loudly when the check cannot run: an unparseable `Retry-After` falls back to the computed backoff and logs, rather than being read as zero. Preserve: `MAX_ATTEMPTS == 5` and the roughly-2/4/8/16 shape the docs publish — note that `test_backoff_grows_exponentially` asserts exact equality and must be relaxed to a range, and that the jitter bounds must be stated in the docs. Boundary and tie: 400 through 499 excluding 408 and 429 are permanent; a response of exactly 300 is neither 2xx nor retryable and must be classified explicitly rather than falling into the retry branch by default.
