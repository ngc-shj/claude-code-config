### Major: the Redis dispatch lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` (`get` then `set` then `expire`) and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: the check and the set are two round trips with no `NX`, so two workers that both see the key absent both acquire; the 60-second `expire` is a third round trip that a crash between calls skips entirely; and the `finally` deletes `LOCK_KEY` by name regardless of whether this worker still owns it, while one batch can legitimately run far longer than 60s.
What breaks in production: two workers claim overlapping batches and customers receive duplicate deliveries, and a worker whose lock has already expired deletes the successor's lock on exit, cascading the overlap.
Fix: replace the body with a single atomic `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` is unique per acquisition, return the token, and release with a compare-and-delete Lua script (`if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) end`) so a worker can only delete its own lock; additionally add `.with_for_update(skip_locked=True)` to the `_claim_batch` query so correctness does not depend on the lock at all. Preserve single-writer batching — do not fix this by removing the lock. The case that must still SUCCEED and be pinned: a single worker acquires, runs a batch and releases, and the next iteration re-acquires. Red-prove each clause by execution: (i) revert to `get`-then-`set` — a test running two `_acquire_lock` calls concurrently against a real Redis and asserting exactly one returns a token must red; (ii) release with an unconditional `delete` — a test where worker A's lock has expired and worker B holds it, asserting A's release leaves B's token in place, must red; (iii) drop `skip_locked` — a test with two sessions claiming concurrently and asserting disjoint row sets must red. Fail loudly where the check cannot run: a Redis error inside `_acquire_lock` must propagate as a named failure that stops the worker, never be caught into `return True`. Boundary and tie: the TTL must exceed the maximum batch wall time (with the in-process retry loop removed, one attempt per row per pass), and a worker whose lock expires mid-batch must find its rows already claimed rather than re-sending.

### Major: `in_flight` is a non-terminal state with no reset path

What is wrong: a row is moved to `in_flight` before the HTTP work, and the only transitions out are the two `_finish` calls on the success and exhausted paths, so any worker crash, deploy, OOM, or unhandled exception type leaves the row in `in_flight` where `_claim_batch`'s `status == "pending"` filter can never see it again.

### Major: the retry policy contradicts the documented one on two axes
File: `app/webhooks/delivery.py` — `deliver` (non-2xx falls through to the retry path) and `backoff_for` (`timedelta(seconds=BASE_DELAY_SECONDS**attempt)`); `docs/webhooks.md` — "backoff is exponential with jitter" and "a 4xx is permanent and we stop immediately"

Preserve the five-attempt ceiling and the exponential growth of the upper bound; do not fix this by editing the doc to describe the current behaviour, since retrying a 4xx is the defect. The case that must still SUCCEED and be pinned: a 503 is still retried and a 429 is still retried. Red-prove each clause by execution: (i) remove the 4xx branch — a test asserting a 404 response yields `failed_permanent` with `attempts == 1` must red; (ii) put 429 in the permanent set — a test asserting a 429 reschedules must red; (iii) replace the jittered value with the bare exponential — a test asserting 100 samples of `backoff_for(3)` are not all equal must red, and update the existing `test_backoff_grows_exponentially` to assert bounds (`0 < v <= 8`) instead of exact equality. Fail loudly where the check cannot run: a response with a status outside 100–599 (a broken proxy) must be treated as retryable and logged with the raw value named. Boundary and tie: 400 is permanent, 399 and 500 are retryable, and 408/429 are explicitly carved back to retryable.

### Major: naive and aware datetimes are mixed, and the migration's columns have no timezone at all

### Major: `run_worker` references `batch` outside the block that binds it
File: `app/webhooks/delivery.py` — `run_worker`, `try: batch = await _claim_batch() ... finally: ...` then `if not batch:` after the `try`
What is wrong: `batch` is assigned inside the `try` and read after it, so any exception from `_claim_batch` or `asyncio.gather` propagates past the `finally` — and if the loop is ever wrapped in an outer handler that continues, `batch` is unbound and the read raises `UnboundLocalError` masking the original error.

Fail loudly where the check cannot run: use `log.exception` so the traceback is preserved, never a bare `log.warning(str(exc))`. Boundary and tie: an empty batch sleeps `poll_interval`, a batch of exactly `BATCH_SIZE` does not, and the failure path sleeps the same interval so a persistent fault does not spin.
