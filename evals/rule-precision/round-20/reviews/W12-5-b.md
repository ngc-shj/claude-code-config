### Critical: `list_deliveries` has no tenancy filter — any authenticated user reads any org's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: the query filters only on the caller-supplied `endpoint_id` and never on `user.org_id`, while both siblings added in the same file (`list_api_keys`, `list_webhook_endpoints`) do filter on `org_id` — the tenancy predicate was propagated to two of three new read paths (R3, security-relevant).
What breaks in production: any customer can enumerate integer endpoint ids and read another organization's delivery history — event types, response statuses and delivery schedule for their invoices and subscriptions.
Fix: join through the endpoint and scope by org in the query itself, not in a post-filter: `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and return 404 (not 403) when the join yields nothing so ids of other orgs are not distinguishable from absent ids. Preserve the existing behaviour the endpoint is for: the owning org still gets its rows, newest first, honouring `limit` — pin that allow case with a test that creates two endpoints in the caller's org and asserts both are listable. Red-prove the two clauses with two separate mutations: (a) drop the `org_id` predicate and assert the cross-org test goes red on rows returned; (b) drop the `endpoint_id` predicate and assert the same-org test goes red on rows from the caller's *other* endpoint leaking into the response. Boundary/tie: an endpoint whose `org_id` equals the caller's org is IN; a delivery whose endpoint row was cascade-deleted has no matching join row and is OUT — state that in the test. Not-pass-not-fail case: if `user.org_id` is None the handler must raise 401/403, never fall through to an unscoped query.

### Critical: registration accepts non-HTTPS and internal-network URLs, and the client follows redirects — SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: `scheme.startswith("http")` admits `http://` and any scheme merely prefixed `http` (`httpx://`, `httpfoo://`), there is no check that `netloc` resolves outside private/link-local space, and `app/webhooks/delivery.py:run_worker` builds the client with `follow_redirects=True`, so a registered URL is a server-side request primitive the customer controls.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://internal-admin.svc/` (or a public URL that 302s there) and the worker fetches internal endpoints from inside the VPC, echoing the response body back to them through `WebhookDelivery.response_body`.
Fix: validate at the schema, not in the handler — make `EndpointIn.url` a `pydantic.HttpUrl` constrained to `https` only (matching `docs/webhooks.md` "Only `https://` URLs are accepted"), and add an egress guard in `delivery.send_once` that resolves the host and rejects any address in loopback/link-local/private/unique-local/reserved ranges, applied again on each hop rather than once at registration (registration-time DNS is re-resolvable — R51 shape). Set `follow_redirects=False`; a 3xx becomes a permanent failure with a named detail. Preserve the feature: a public `https://hooks.example.com/acme` must still register and still deliver — pin that as the allow case. Red-prove separately: (a) register `http://hooks.example.com` → 422; (b) register `https://127.0.0.1/x` → 422; (c) a public host that 302s to `http://169.254.169.254` → delivery recorded failed, no request issued to the internal address, asserted on the transport mock's call list. Fail loudly when the check cannot run: DNS resolution failure or an unresolvable host must reject (fail closed), not skip the guard. Boundary/tie: a host resolving to *both* a public and a private address must be rejected; IPv4-mapped IPv6 (`::ffff:127.0.0.1`) is on the reject side.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from predictable state and is not cryptographically secure, so the per-endpoint HMAC key is predictable to anyone who can observe enough outputs from the same process.
What breaks in production: an attacker who recovers the generator state (e.g. by registering several endpoints of their own and reading the secrets back from `to_dict`) can forge signatures for other tenants' endpoints, defeating the only authenticity control the webhook protocol has.
Fix: use `secrets.token_urlsafe(SECRET_BYTES)` (or `secrets.choice`) and make the constant honest — `SECRET_BYTES = 32` currently produces 32 *characters* from a 62-symbol alphabet, so rename it to `SECRET_CHARS` or switch to a byte-count-based generator and update the test that asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` to the new length rather than deleting it. Preserve what the current code gets right: the `whsec_` prefix and URL-safe output stay, so existing stored secrets remain parseable — the allow case is "an existing `whsec_`-prefixed secret still verifies". Red-prove with one mutation per clause: (a) monkeypatch `secrets` to a fixed value and assert the collision test reddens; (b) revert to `random.choice` and assert a test asserting `secrets` is the source module (via `inspect.getsource` or a patched `secrets.choice` spy being called) goes red. Not-pass-not-fail: if the entropy source raises, the registration request must fail with 500 and no endpoint row — never fall back to `random`. Boundary: a secret of exactly the configured length is valid; anything shorter is rejected at load.

### Critical: signature comparison in `verify` is not constant-time (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, instead of `hmac.compare_digest`.
What breaks in production: a caller who can invoke this verification path repeatedly recovers the expected digest byte by byte from response-time differences, forging a valid signature without ever knowing the secret — and because `docs/webhooks.md` instructs customers to "compare it against your own computation using a constant-time comparison", the shipped reference implementation contradicts the documented requirement.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str`/`bytes` of the same type first so `compare_digest` cannot raise on a `None` or non-ASCII header. Preserve the accepting side: `test_verify_accepts_signature_produced_by_sign` must stay green — that is the allow case. Red-prove the two clauses separately: (a) revert to `==` and assert a test that patches `hmac.compare_digest` with a spy goes red on "not called"; (b) pass a signature of a different length and assert the function returns `False` rather than raising. Fail loudly: a `signature` that is `None` or not a `str` returns `False` and logs at warning — "could not compare" must not be spelled the same as "matched". Boundary/tie: a signature equal to `expected` except for the `sha256=` prefix casing is on the reject side; state that the prefix is compared inside the constant-time call, not stripped before it.

### Critical: the signature is computed over bytes the receiver never sees, and excludes the timestamp (R40, R29)
File: `app/webhooks/signing.py` — `sign` / `serialize`; consumed by `app/webhooks/delivery.py:send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, whose body httpx serializes without `sort_keys` and with different separators — so the signed bytes and the wire bytes differ whenever the payload's keys are not already in sorted order; additionally the timestamp is returned as a header but is not part of the MAC input, contradicting `docs/webhooks.md` ("the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`").
What breaks in production: every customer who implements verification as documented — HMAC over `timestamp + "." + raw body` — computes a digest that never matches, so the entire integration fails closed for all tenants at once; and any customer who verifies over the body alone finds the timestamp unauthenticated, so the documented five-minute replay window can be re-dated by an attacker replaying a captured request.
Fix: make the transmitted bytes the signed bytes and bind the timestamp in. Serialize once — `body = serialize(payload).encode()`, `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and have `send_once` send `content=body` with an explicit `Content-Type: application/json` header instead of `json=`, so httpx never re-serializes. Change `verify(secret, payload, signature)` to `verify(secret, timestamp, raw_body: bytes, signature)` so the verification helper takes the same raw bytes a receiver has, and update `docs/webhooks.md` only if the code's canonicalisation choice changes. Preserve what makes the defect visible and the feature useful: keep `sort_keys=True` (it is what makes the signature reproducible from a re-parsed body) and keep the timestamp header. Red-prove three clauses with three mutations: (a) drop the `f"{timestamp}."` prefix → a round-trip test that verifies using the documented formula reddens; (b) re-introduce `json=payload` in `send_once` → a test that captures `request.content` and runs `verify` on those exact bytes reddens; (c) alter one payload byte in the captured body → verify returns False. Not-pass-not-fail: if `Content-Type` is absent or the body is empty, verification must return False, not skip. Boundary/tie: a timestamp exactly `max_age` seconds old — state which side it falls on (accept at exactly the bound, reject beyond) and enforce that bound in the reference verifier, since the diff currently ships no age check at all.

### Critical: `UNIQUE INDEX` on `event_id` alone makes multi-endpoint fan-out impossible

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` for up to `BATCH_SIZE = 100` deliveries, but the retry backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`.
What breaks in production: one failing endpoint freezes the whole worker process — with `BASE_DELAY_SECONDS ** attempt` the four sleeps total 30 s per failing delivery, and because the loop is blocked they serialise across the batch, so a batch of 100 failing endpoints stalls all delivery (and anything else on that loop) for roughly 50 minutes while the 60 s Redis lock expires underneath it.
Fix: the sleep is a symptom of the larger shape — `deliver` retries in-process while the schema already carries `attempts` and `next_attempt_at` for scheduled retry. Replace the `while True` loop with a single attempt that, on failure, writes `attempts += 1`, `status = "pending"`, and `next_attempt_at = now + backoff_for(attempt)`, letting `_claim_batch` pick the row up later; keep the terminal `failed_permanent` write when `attempts >= MAX_ATTEMPTS`. If in-process retry must be kept for the first attempt, it must be `await asyncio.sleep(delay)`. Preserve the retry budget itself — `MAX_ATTEMPTS = 5` and the 2/4/8/16 s schedule stay, and `test_max_attempts_matches_documented_limit` stays green (allow case). Red-prove three clauses: (a) a failing delivery leaves `status='pending'` with `next_attempt_at` in the future — reverting to the in-process loop reddens it; (b) `attempts` is persisted after each failure, not only at the terminal state — asserting `attempts == 1` after one failed pass reddens under the current code; (c) two concurrent `deliver` coroutines against a slow transport complete in ~max, not ~sum, of their delays — restoring `time.sleep` reddens the wall-clock assertion. Fail loudly: a delivery whose row vanished between claim and finish must log and count, not silently return. Boundary/tie: `attempts == MAX_ATTEMPTS` is terminal (the 5th attempt is made and then the row is permanent) — state it, because the current `attempt >= MAX_ATTEMPTS` check runs *after* the attempt and therefore makes exactly 5 attempts; keep that.

### Critical: the dispatch lock is not atomic, not owned, and can wedge permanently (R38)
File: `app/webhooks/delivery.py` — `_acquire_lock` and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: acquisition is a check-then-set (`get` then `set`) with a third non-atomic `expire`, and release is an unconditional `delete` of a key the caller may not own.
What breaks in production: three distinct failures — two workers pass the `get` before either `set`s and both claim the same batch, sending every webhook twice; a crash between `set` and `expire` leaves a TTL-less lock so all delivery stops permanently with no reset path; and since the lock TTL is 60 s while a batch can run far longer (5 attempts × 30 s `REQUEST_TIMEOUT` plus 30 s of backoff), a second worker acquires the expired lock mid-run and the first worker's `finally` then deletes the *second* worker's lock.
Fix: acquire with a single atomic call carrying both the TTL and a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` — and release with a compare-and-delete Lua script that deletes only if the stored value equals the token. Add a heartbeat that re-extends the TTL while the batch runs, and size `LOCK_TTL_SECONDS` above the worst-case batch duration derived from `MAX_ATTEMPTS`, `REQUEST_TIMEOUT` and `backoff_for` rather than at a hardcoded 60. Preserve the single-worker property the lock exists for — this is not fixed by removing the lock and relying on `SELECT ... FOR UPDATE SKIP LOCKED` alone, though adding `SKIP LOCKED` to `_claim_batch` is the correct second layer. Red-prove three clauses separately: (a) two concurrent `_acquire_lock` calls → exactly one True (reverting to get-then-set reddens it under a fake Redis that yields between the two calls); (b) kill the process after acquisition and assert the key has a TTL > 0 (splitting `set` and `expire` reddens it); (c) worker A releases while B holds → B's key survives (unconditional `delete` reddens it). Fail loudly: if Redis is unreachable, `_acquire_lock` must raise or return False and the worker must log "lock unavailable" and back off — an exception swallowed into `False` would silently mean "someone else holds it". Boundary/tie: two workers presenting the same token is impossible by construction; a worker whose TTL expires exactly as it finishes must treat its compare-and-delete miss as "I lost the lock" and log it, not as success.

### Critical: webhook enqueue is outside the event transaction and its failure is swallowed (R9)
File: `app/events/dispatcher.py` — `dispatch`, the `try/except Exception: log.warning("webhook enqueue failed ...")` block after the `session_scope` exits
What is wrong: the event row commits in one transaction and the delivery rows are written in a separate one inside `enqueue_for_event`, with any failure between them caught and downgraded to a warning; there is nothing in the change that reconciles events against missing deliveries.
What breaks in production: a transient DB error, the IntegrityError from the single-column unique index above, or a worker restart between the two commits permanently loses the webhook for a paid invoice with no retry and no alert — while `docs/webhooks.md` promises "delivery is at-least-once".
Fix: make it a transactional outbox — write the `Event` row and its `WebhookDelivery` rows in the *same* `session_scope`, by passing the open session into `enqueue_for_event` instead of letting it open its own, so either both commit or neither does. Keep the current call ordering relative to in-process `SUBSCRIBERS` (they must still run after the event is durable). Do not keep the bare `except Exception` as a safety net: if it is retained for a genuinely non-fatal case, it must re-raise anything that is not that case and increment a counter/emit at `error`, so "enqueue failed" is not spelled the same as "nothing to enqueue". Preserve the property that a webhook failure must not lose the event — that is the reason the try/except was written; the outbox preserves it structurally because the delivery rows are only attempted asynchronously. Red-prove three clauses: (a) force `enqueue_for_event` to raise and assert the `Event` row is absent after `dispatch` returns (currently it is present); (b) assert `dispatch` propagates rather than returning an id on that failure; (c) assert the happy path still returns `event_id` and creates N delivery rows for N endpoints (the allow case). Fail loudly: the "no active endpoints" case must be distinguishable in logs from the "enqueue errored" case. Boundary/tie: an event whose type is in `WEBHOOK_EVENT_TYPES` but whose org has zero endpoints commits with zero delivery rows and is a success — say so.

### Major: ORM instances are used after their `session_scope` has closed

### Major: `in_flight` has no exit path and the worker dies on the first unexpected exception (R38)
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `run_worker` (`await asyncio.gather(*[deliver(client, d) for d in batch])`)
What is wrong: rows are moved to `in_flight` before delivery but nothing ever moves them back — `deliver` only ever writes `delivered` or `failed_permanent`, and `gather` is called without `return_exceptions=True` so any exception outside the `httpx.HTTPError` catch (a DB error, the CheckViolation above, `AttributeError` on a missing endpoint) escapes the `try/finally`, exits `while True`, and terminates the worker.
What breaks in production: a single malformed row both wedges its own delivery in a non-terminal state forever and takes down the delivery loop for every tenant, with the only signal being the process exiting.
Fix: (1) pass `return_exceptions=True` to `gather` and log each returned exception against its delivery id, then finish that row as `pending` with a bumped `attempts` and a future `next_attempt_at`; (2) wrap the body of the `while True` in a `try/except Exception` that logs at `error` and continues after `poll_interval`, so the loop is supervised; (3) add a reaper query that returns rows `in_flight` older than a bounded lease (derived from `REQUEST_TIMEOUT * MAX_ATTEMPTS`) to `pending`, giving the transient state an explicit timeout-driven exit. Preserve the fail-fast signal: the reaper must emit a counter/`error` log per reaped row, so a systematic wedge is visible rather than silently smoothed over. Red-prove three clauses: (a) make one `deliver` raise `ValueError` → the other deliveries in the batch still complete and the worker survives one more poll (reverting `return_exceptions` reddens it); (b) leave a row `in_flight` with an old `updated_at` → the reaper returns it to `pending` (removing the reaper reddens it); (c) a healthy batch still completes with no reaping and no error log — the allow case. Fail loudly: if the reaper itself errors, the worker logs and does not claim a new batch that cycle. Boundary/tie: a row whose lease expires at exactly the bound is reaped; state whether a concurrently-completing `deliver` writing `delivered` after the reap wins — it must, via a status-conditional update (`WHERE status = 'in_flight'`).

### Major: the delivered body carries no event id or type, so the documented deduplication is impossible
File: `app/webhooks/delivery.py` — `send_once`, `client.post(endpoint.url, json=delivery.payload, ...)`
What is wrong: only the raw `payload` is transmitted — `WebhookDelivery.event_id` and `event_type` are stored but never sent in the body or in a header — while `docs/webhooks.md` states "delivery is at-least-once, so deduplicate on `event_id`".

### Major: retry policy contradicts the documented policy in two ways, and the test pins the wrong one
File: `app/webhooks/delivery.py` — `deliver` (the non-2xx branch falls through to retry) and `backoff_for`; `tests/webhooks/test_delivery.py:test_backoff_grows_exponentially`
What is wrong: `docs/webhooks.md` says "a 4xx is permanent and we stop immediately" and "backoff is exponential **with jitter**", but `deliver` retries every non-2xx status including 400/401/404, and `backoff_for` returns a deterministic `2 ** attempt` that the parametrized test locks in at exactly 2/4/8/16 s.

Preserve the retry budget: 5 attempts and the 2/4/8/16 s centre points stay. Red-prove three clauses: (a) a handler returning 404 produces exactly one request and a `failed_permanent` row — removing the 4xx branch reddens it; (b) a handler returning 429 retries — over-tightening to "all 4xx permanent" reddens this allow case; (c) 100 calls to `backoff_for(1)` yield more than one distinct value — removing jitter reddens it. Fail loudly: a response with a status outside 100–599 (a broken proxy) must be treated as retryable and logged as anomalous, not silently classed 2xx. Boundary/tie: 400 is permanent, 408 and 429 are retryable, 500 is retryable — name each boundary explicitly in the test parameters.

### Major: only three event types can ever reach webhooks, contradicting the "every event type" contract (R12)
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES` and the `if envelope.type in WEBHOOK_EVENT_TYPES:` guard
What is wrong: the dispatcher gates webhook enqueue on a hardcoded three-element set, while `app/webhooks/delivery.py:enqueue_for_event` already implements per-endpoint filtering (`if not endpoint.event_types or event_type in endpoint.event_types`) and `docs/webhooks.md` promises that "an empty `event_types` subscribes the endpoint to every event type we emit" — the filter is implemented twice with different domains and the outer one silently wins.

Red-prove two clauses: (a) dispatch an event type absent from the current set to an endpoint with `event_types: []` and assert a delivery row is created — restoring the gate reddens it; (b) dispatch to an endpoint with `event_types: ["invoice.paid"]` and a non-matching event and assert *no* row is created — removing the per-endpoint filter reddens this allow case. Fail loudly: an event type not present in the registry at all must log at `warning` naming the type. ### Major: `webhooks_enabled` is added to the schema and never read (R41)
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: a per-org feature flag is created and defaulted to FALSE, but no code in the diff consults it — `create_webhook_endpoint`, `dispatch`, and `enqueue_for_event` all proceed regardless.

Preserve the delivery path for enabled orgs; do not resolve this by changing the default to TRUE, which discards the staged-rollout capability the column was added for. Red-prove two clauses: (a) an org with `webhooks_enabled = FALSE` produces zero delivery rows for a subscribed event — removing the join reddens it; (b) an org with it TRUE produces the rows — over-tightening to "always deny" reddens this allow case. ### Major: `EndpointIn` validates nothing beyond types, and nothing caps endpoints per org (RS3)
File: `app/api/routes/settings.py` — `class EndpointIn`, `url: str` and `event_types: list[str] = []`
What is wrong: `url` is a bare `str` with no length bound and only the handler-level scheme check, `event_types` is an unbounded list of arbitrary strings never checked against any known event type, and `create_webhook_endpoint` inserts without counting the caller's existing endpoints — the schema layer performs no validation at all, which is exactly what RS3 requires it to do.
What breaks in production: a caller posts a 10 MB URL string or a million-element `event_types` array straight into a JSONB column, or scripts thousands of endpoint rows for one org, each of which multiplies every subsequent event's fan-out (`enqueue_for_event` creates one row and one outbound request per endpoint) into a self-inflicted amplification.

Red-prove four clauses separately: (a) an unknown event type → 422; (b) `event_types: []` → 201 (allow case); (c) the (cap+1)th endpoint → 409 while the cap-th succeeds; (d) a duplicate URL for the same org → 409 while the same URL under a different org succeeds. Fail loudly: if the event-type registry cannot be loaded, registration must 503 rather than accept anything. Boundary/tie: exactly `cap` endpoints is allowed and `cap+1` is rejected — name that, and note two concurrent creations at `cap-1` must not both succeed, which is what the `FOR UPDATE` is for.
Question (Minor, per Finding Floor clause 2): the three new routes carry no rate limiter, but no limiter appears on the pre-existing `get_profile` / `list_api_keys` either, so a global middleware may already cover them (RS2). What would close this: confirmation that the app's middleware stack rate-limits `POST /v1/settings/*`; if it does not, `create_webhook_endpoint` needs a per-org limit independent of the cap above.

### Major: the secret-strength test is blind to the defect it appears to cover (RT7)

### Major: naive `utcnow()` and a `TIMESTAMP` column diverge from the module's own tz-aware helper (R1, R3)

### Major: unbounded third-party response bodies are stored and the full header set is logged
File: `app/webhooks/delivery.py` — `send_once` (`log.info("POST %s headers=%s", endpoint.url, headers)`) and `deliver` (`_finish(delivery.id, "delivered", attempt, response.status_code, response.text)`)

## Cross-cutting verification

- **Tenancy predicate (`org_id`)**: present in `list_api_keys` and `list_webhook_endpoints`, **absent** in `list_deliveries` — reported above. Also absent from `enqueue_for_event`'s endpoint query in the sense that it is the only place `org_id` is trusted from the envelope rather than the session, which is correct there.
- **`session_scope` object lifetime**: `_claim_batch` and `deliver` both let entities escape; `_finish` and all three route handlers keep their usage inside the block. Two sites, both reported.
- **Status value spelling**: three copies (`STATUSES`, the SQL CHECK, string literals in `delivery.py`) — the SQL copy is the one that drifted; no fourth copy exists in the diff.
- **Timestamp construction**: `models._now()` (aware), `_claim_batch`/`_finish` `datetime.now(timezone.utc)` (aware), `enqueue_for_event` `datetime.utcnow()` (naive) — one divergent site, reported.
- **Event-type filtering**: implemented twice, in `dispatcher.WEBHOOK_EVENT_TYPES` and in `enqueue_for_event`'s comprehension — reported.
- **`to_dict` secret exposure**: one definition, two call sites with different intents — reported.
- **URL validation**: performed only in `create_webhook_endpoint`; there is no second registration path in the diff, and no re-validation at send time — the missing re-validation is folded into the SSRF fix.

## Codebase awareness

- `models._now()` already exists and is used as the column default; `enqueue_for_event` reimplements it (R1) — evidence cited in the finding above.
- `_finish` already demonstrates the correct re-fetch-inside-a-scope pattern the detached-instance fix generalises.
- `enqueue_for_event` already implements per-endpoint event filtering, which is why the dispatcher's `WEBHOOK_EVENT_TYPES` gate is a duplicate rather than a complement.
- `signing.serialize` already exists as the single canonicalisation point; the wire-bytes fix reuses it rather than introducing a second serializer.
- The `webhook_deliveries.attempts` / `next_attempt_at` columns already model scheduled retry, which is why the `deliver` fix removes the in-process loop rather than adding a second retry mechanism.
