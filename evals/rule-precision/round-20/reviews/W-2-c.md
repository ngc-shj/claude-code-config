### Critical: the transmitted body is not the signed byte string, and the timestamp is not in the MAC
File: `app/webhooks/signing.py` — `sign()` / `serialize()`; `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` and returns the timestamp outside the MAC, while `send_once()` transmits the body via httpx `json=delivery.payload` (httpx serializes with its own separators and no key sorting), so the bytes a receiver hashes are not the bytes that were signed, and `docs/webhooks.md` tells receivers to HMAC `"{timestamp}.{raw_request_body}"` — a string this code never computes.
What breaks in production: every customer who implements the documented verification rejects 100% of our deliveries, and any customer who instead ignores the timestamp is replayable forever because an attacker can rewrite `X-Acme-Timestamp` without invalidating the signature that does not cover it.
Codebase awareness: the change already contains the serializer (`signing.serialize`) that `send_once` should be feeding to httpx as `content=`; `send_once` bypasses it by using `json=`, so this is a reimplementation of the producer side inside httpx rather than a missing helper (R1 evidence).
Fix: make the signed bytes and the wire bytes one object — `serialize()` returns `bytes` with pinned `separators=(",", ":")` and `sort_keys=True`; `sign(secret, body: bytes) -> tuple[str, str]` computes `timestamp = str(int(time.time()))` and MACs `f"{timestamp}.".encode() + body`; `send_once` computes `body = serialize(delivery.payload)` once and passes `content=body`. Rewrite `verify(secret, body: bytes, timestamp: str, signature: str, max_age: int = 300)` to take the raw received body and header timestamp. Allow side to pin: an independently written verifier that follows `docs/webhooks.md` verbatim accepts a live request — the round-trip test must feed the `request.content` and headers captured by `httpx.MockTransport` into that verifier and compare against a hard-coded expected hex digest for a fixed secret/payload/timestamp, never `verify(*sign(...))` (R29 forbids the `f(g(x)) == x` shape; the current `test_verify_accepts_signature_produced_by_sign` is exactly that and passes for two mirrored-wrong implementations). Red-prove each clause separately, by execution: (i) flip one byte of the transmitted body → verifier rejects; (ii) change only the timestamp header, keep the signature → verifier rejects (this assertion cannot fail against today's code, which is the proof the clause is new); (iii) reorder the producer's dict keys → `request.content` is byte-identical, so the digest is unchanged; (iv) present a timestamp 301s old → rejected. Fail loudly: absent, non-integer, or `sha256=`-prefix-less inputs return a named rejection distinct from "signature mismatch" — a missing header must never take the same path as a valid one. Preserve: keep both header names and the `sha256=<hex>` shape, and do not "fix" this by editing the doc to describe payload-only signing — the timestamp binding is what the documented replay window rests on. Boundary and tie: `now - timestamp <= max_age` accepts exactly 300s and rejects 301s; a timestamp more than `max_age` in the future is also rejected, so a receiver with a fast clock fails closed rather than accepting indefinitely.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: the HMAC comparison uses Python `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: any consumer that adopts this helper as its verification path — and we ship it as the reference implementation next to the doc that tells customers to use a constant-time compare — leaks the expected digest byte-by-byte to an attacker who can time responses, letting them forge a signed event.
Fix: `return hmac.compare_digest(expected, signature)` operating on the reworked signature from the finding above. Allow side to pin: a signature produced by `sign()` for the same secret and body still verifies true. Red-prove, one mutation per clause: (i) a signature differing only in its last hex character → `verify` returns False (reds if the comparison is deleted entirely); (ii) the equality-operator swap itself is not behaviourally observable, so pin it with the repo's timing-safe grep gate over `app/webhooks/signing.py` and red-prove that gate by reintroducing `expected == signature` and observing a non-zero exit. Fail loudly: `compare_digest` raises `TypeError` on a non-`str`/`bytes` signature — catch it at the boundary and return a named "malformed signature" rejection rather than letting the exception surface as a 500, and never coerce with `str()`. Preserve: keep `verify` returning a plain bool so existing callers are unchanged. Boundary and tie: state the control class (R49) — this is a *fail-closed verification gate*, not a boundary; `compare_digest` does not hide the length of the compared strings, so the `sha256=`+64 length must stay fixed rather than being taken from the header.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister whose internal state is recoverable from a few hundred consecutive outputs, so secrets minted in sequence are predictable from other secrets (`SECRET_BYTES = 32` also names characters, not bytes).
What breaks in production: an attacker who registers a handful of their own webhook endpoints recovers the generator state and derives other tenants' signing secrets, then forges signed events that those tenants' systems accept as authentic — including `invoice.paid`.
Fix: `import secrets` and build the string with `secrets.choice(_ALPHABET)`; rename the constant to `SECRET_CHARS = 32` and record in a comment that 32 characters over a 62-symbol alphabet is ~190 bits. Allow side to pin: the format contract is unchanged — a secret still starts with `whsec_`, is still `len(SECRET_PREFIX) + SECRET_CHARS` long, is drawn only from `_ALPHABET`, and an already-issued secret of that shape still signs and verifies (keep `test_new_signing_secret_has_prefix_and_length` green). Red-prove each clause by execution: (i) call `random.seed(0)`, generate a secret, re-seed and generate again — the two must differ; this reds against today's code and passes after the change, and it is the executable oracle for the actual defect, unlike the length assertion which a constant would satisfy; (ii) generate 10,000 secrets and assert all distinct and alphabet-conformant (reds if the generator degenerates); (iii) a grep gate asserting `import random` is absent from `app/webhooks/signing.py`, red-proved by reinstating the import. Fail loudly: no fallback path — if `secrets` is unavailable the module must fail to import rather than silently degrading to `random`. Preserve: do not switch to `token_urlsafe`, which changes the alphabet and length and would break the documented `whsec_`+32 shape customers may already be pattern-matching. Boundary: secrets already minted by this code are compromised by construction — the fix must be accompanied by rotating every existing `webhook_endpoints.signing_secret`, since changing the generator does not change what has already been issued.

### Critical: the signing secret is returned by the list endpoint, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: one serializer serves two audiences with different secrecy requirements, so `GET /v1/settings/webhook-endpoints` returns every endpoint's signing secret while `docs/webhooks.md` states the creation response "is the only place the signing secret appears — it cannot be read back afterwards" (R49: the claim is stronger than the implementation).
What breaks in production: the secret is readable by anyone holding any credential scoped to the org and lands in access logs, browser caches, and support screenshots, so the signature stops being evidence of origin for every endpoint in the account.
Cross-cutting check: `to_dict()` has exactly two call sites in the diff — `create_webhook_endpoint` (where disclosure is intended) and `list_webhook_endpoints` (where it is the defect); `WebhookDelivery.to_dict()` was checked and exposes no secret material.
Fix: make `WebhookEndpoint.to_dict()` omit `signing_secret`, and add a separate `to_dict_with_secret()` used only by the 201 response of `create_webhook_endpoint`. Allow side to pin: the create response still contains a usable `signing_secret` — assert the returned value verifies a signature — because deleting the only disclosure would make the feature unusable. Red-prove separately: (i) re-add `signing_secret` to `to_dict()` → the list-route test asserting `"signing_secret" not in body[0]` reds; (ii) point `create_webhook_endpoint` at `to_dict()` → the create-route test reds. Assert key ABSENCE, not a falsy value, so a `None` placeholder cannot satisfy it. Fail loudly: declare a Pydantic response model on the list route that forbids unknown fields, so a future column added to `to_dict()` fails the route rather than leaking silently. Boundary and tie: endpoints created before this change keep their secrets and no read-back path is added — the operator recovery path is rotation (issue a new secret), which must be named in the doc alongside the removal.

### Critical: delivery listing is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the query filters on the path-supplied `endpoint_id` alone and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate any other organization's deliveries (R3, security-relevant: the sibling handlers `list_webhook_endpoints` and `list_api_keys` in the same file both scope by `user.org_id`, and this one does not).
What breaks in production: a tenant walks integer endpoint ids and reads other customers' delivery rows — `event_id`, `event_type`, status and schedule today, and the row carries the full event `payload` — a cross-tenant data breach through an ordinary authenticated request.
Fix: join through the endpoint and scope by org: `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and raise `HTTPException(404)` when the endpoint does not resolve within the caller's org. Allow side to pin: the owning org still receives its own deliveries in `created_at DESC` order under the same `limit` — assert the full expected list, not just a non-empty response, so a fix that always denies cannot pass. Red-prove each clause: (i) delete the `org_id` predicate → the cross-org test (org B requests org A's endpoint) reds; (ii) delete the `endpoint_id` predicate → the owner test reds because it sees a sibling endpoint's rows; (iii) assert the denial returns zero rows AND that no delivery row was read into the response, not merely that the status is 404 (RT8: status-only assertion is vacuous). Fail loudly: an unresolvable or foreign endpoint id must produce 404, never an empty 200 — today an empty list spells both "no deliveries yet" and "not yours". Boundary and tie: a foreign-but-existing endpoint id returns the identical 404 body as a nonexistent id, so the response is not an existence oracle for other tenants' endpoints.

### Critical: the status the code writes is rejected by the table's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` — `STATUSES`
What is wrong: the producer writes `failed_permanent` (as does the `STATUSES` tuple in `models.py`), but the strict consumer — the database CHECK — only admits `failed`, so the enum spelling diverges across the boundary (R40).
What breaks in production: every delivery that exhausts its retries raises an `IntegrityError` inside `_finish`, the row stays `in_flight` forever, and the worker's `asyncio.gather` propagates the error and kills the loop — the permanent-failure path, the one that only runs when something is already wrong, is the one that has never executed.
Cross-cutting check: `STATUSES` in `models.py` is a third copy of this vocabulary and is referenced nowhere — the `status` column's `default="pending"` is a separate literal again (R2).
Fix: make one definition authoritative — keep `STATUSES` in `app/webhooks/models.py`, use `Enum(*STATUSES, name="webhook_delivery_status")` or a CHECK generated from it, and add migration `0043` that drops and recreates the constraint with `'failed_permanent'`. Allow side to pin: a `delivered` write and a `pending` insert still succeed against the migrated schema. Red-prove separately, against a real migrated database and not a mock (a mocked session cannot validate a CHECK): (i) revert the constraint to `'failed'` → the `failed_permanent` insert test reds; (ii) add a member to `STATUSES` without migrating → the "every member of STATUSES is insertable" test reds; (iii) attempt an unlisted status → the insert is rejected, proving the constraint still constrains. Fail loudly: `_finish` must let the `IntegrityError` propagate to a named handler that marks the worker unhealthy — do not wrap it in a `try/except` that logs and continues, which would convert this into silent data loss. Preserve: keep the constraint (the fix is aligning the vocabulary, not deleting the CHECK). Boundary and tie: the table ships in this same change, so no rows exist in either spelling and the migration needs no backfill — state that explicitly in the migration comment, because the same edit against a populated table would need one.

### Critical: the unique index allows only one delivery row per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: uniqueness is on `event_id` alone while `enqueue_for_event` inserts one row per matching endpoint, so any org with two subscribed endpoints violates the index on the first fan-out.
What breaks in production: `session.add_all(rows)` fails, the whole enqueue transaction rolls back so even the first endpoint gets nothing, and the dispatcher's bare `except Exception` (see below) downgrades a total delivery outage to a `log.warning` — events are silently never delivered for every multi-endpoint customer.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`. Allow side to pin: an org with two active endpoints subscribed to `invoice.paid` gets exactly two rows for one event — assert both rows and their distinct `endpoint_id`s, since a fix that merely relaxes uniqueness to nothing would also pass a "no error" test. Red-prove each clause: (i) revert to `(event_id)` → the two-endpoint test reds; (ii) drop the index entirely → the duplicate-enqueue test (same event, same endpoint, enqueued twice) reds, proving the index still provides the `event_id` dedup the doc promises to consumers; (iii) enqueue for an endpoint whose `event_types` excludes the type → no row, proving the filter is still applied. Fail loudly: change `add_all` to an insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` and return the count of rows actually inserted, so a re-dispatch is an idempotent no-op that reports how many were skipped rather than aborting the batch — "inserted nothing" must not be spelled the same as "inserted everything". Preserve: keep at-least-once semantics and the per-endpoint payload copy. Boundary and tie: two concurrent enqueues of the same `(endpoint_id, event_id)` resolve to exactly one row, and the loser is a success, not an error.

### Critical: any tenant can point an endpoint at internal infrastructure, and read the response back
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `startswith("http")` admits `http://` and anything else beginning with those four characters (`httpx://`), there is no check on the resolved address, and the client follows redirects — while `docs/webhooks.md` claims "Only `https://` URLs are accepted" (R49: the claim is stronger than the check, and the check is the only thing standing between a tenant and our network).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/...` or `http://127.0.0.1:6379/`, our worker POSTs to it from inside the perimeter, `_finish` stores the response text in `response_body`, and a public endpoint that 302s to a private address bypasses even a registration-time host check.
Fix: reject at the boundary with `parsed.scheme != "https"`, reject userinfo in the netloc, and resolve the hostname with `socket.getaddrinfo` rejecting the registration if any returned address fails `ipaddress.ip_address(a).is_global`; set `follow_redirects=False` and treat a 3xx as a failed attempt with a named reason; re-check the resolved address at connect time (via a transport/resolver hook that pins the validated IP for the request) because a name validated at registration is re-resolved by the worker minutes later and DNS rebinding makes that interval attacker-schedulable (R51 — a name is a lookup key, not an identity; validating at registration alone is a narrowing, not a closure, and the residual window must be declared). Allow side to pin: `https://hooks.example.com/acme` still registers with 201 and still delivers — assert a successful POST through `MockTransport`, or a fix that denies everything satisfies every other clause. Red-prove each clause separately, by execution: (i) `http://hooks.example.com/x` → 422; (ii) `https://169.254.169.254/x` → 422; (iii) an endpoint whose name resolves to `127.0.0.1` only at send time → the delivery attempt is refused before any socket is opened (this clause is not covered by (ii) and needs its own mutation); (iv) a public endpoint returning 302 to `http://localhost` → exactly one outbound request is recorded and the delivery is marked failed. Fail loudly: DNS resolution failure, NXDOMAIN, or an address family we cannot classify must reject with a named reason — never fall through to "assume public". Preserve: keep recording `response_status` and the failure detail so operators can still debug a legitimate endpoint. Boundary and tie: the decision is on every resolved address, not on the first — a name resolving to one global and one private address is rejected; declare the control class as a fail-closed verification gate over the addresses we resolved, not as an enforceable boundary, since a rebinding window remains between the pinned resolution and the SYN.

### Critical: the retry loop blocks the event loop with `time.sleep` inside an async function
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: a synchronous `time.sleep` inside `async def deliver` blocks the entire event loop for the full backoff, and `run_worker` runs up to `BATCH_SIZE = 100` deliveries through `asyncio.gather` on that one loop.
What breaks in production: one endpoint that returns 500 stalls every other delivery in the batch for up to 30 seconds of accumulated backoff (2+4+8+16), so a batch of slow endpoints runs far past the 60-second `LOCK_KEY` TTL and the worker keeps writing under a lock it no longer holds; if the worker shares a process with the API, every HTTP request stalls with it.
Fix: `await asyncio.sleep(delay)`, and bound the claim: stop retrying in-process once elapsed time exceeds a fraction of the lock TTL, writing `next_attempt_at = now + backoff_for(attempt)` and returning the row to `pending` so the next poll picks it up. Allow side to pin: the retry still happens and the delays are unchanged — keep `test_backoff_grows_exponentially` green and assert a 500-then-200 endpoint still ends `delivered` with `attempts == 2`. Red-prove each clause: (i) start an independent task that increments a counter every 10ms, run a delivery that backs off, and assert the counter advanced — this reds under `time.sleep` and is the executable proof, not the reasoning; (ii) two deliveries where one backs off and the other returns 200 → the second completes before the first's sleep ends; (iii) force elapsed time past the TTL fraction → the row is left `pending` with a future `next_attempt_at`, and no further POST is issued under the stale lock. Fail loudly: when the claim is abandoned for time, log at warning with the delivery id and the reason, and never write a terminal status from a claim whose lock has expired. Preserve: do not fix this by removing the retry or by shrinking `MAX_ATTEMPTS` — the at-most-5-attempts contract is documented. Boundary and tie: a delivery whose elapsed time is exactly at the abort threshold is abandoned rather than retried, and a delivery abandoned mid-flight keeps its accumulated `attempts` so the total across claims is still capped at `MAX_ATTEMPTS`.

### Major: the dispatch lock is neither atomic nor owned, and a crash wedges it permanently
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act with an interval two workers both pass; `set` then `expire` is two round trips, so a crash between them leaves a key with no TTL; and `delete(LOCK_KEY)` removes whatever lock is present by name rather than the one this worker acquired (R51: the decision is bound to the key name, not to the lock instance; R38 clause 2: the TTL-less key is a persisted fail-closed wedge with no reset path in the change).
What breaks in production: two workers deliver the same batch twice on the race, and after a single crash at the wrong instant webhook delivery stops for every customer until someone manually deletes the key — there is nothing in the diff that clears it.
Fix: acquire with a single atomic call carrying an owner token and a TTL — `token = secrets.token_hex(16); await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a compare-and-delete Lua script that deletes only when the stored value equals `token`. Allow side to pin: a single worker still acquires, works, and releases, and the *next* poll re-acquires successfully — a fix that never releases would satisfy the mutual-exclusion clause alone. Red-prove each clause separately: (i) two concurrent `_acquire_lock()` calls → exactly one returns True (reds against the `get`/`set` form); (ii) simulate a crash after acquire (skip the release) and assert the key still expires within `LOCK_TTL_SECONDS`, so the wedge clears itself (reds against the separate `expire` call); (iii) worker A acquires, the key expires, worker B acquires, then A calls release → the key still holds B's token (reds against `delete` by name). Fail loudly: a Redis error during acquire must return False and be logged as "lock unavailable", never be swallowed into a True — "could not decide" must not be spelled like "acquired". Preserve: keep the single-flight property; do not fix the wedge by dropping the lock. Boundary and tie: `LOCK_TTL_SECONDS` must exceed the worst-case claim duration bounded in the `asyncio.sleep` finding above, and when two workers contend the loser sleeps `poll_interval` rather than erroring.

### Major: nothing recovers a delivery left in `in_flight`
File: `app/webhooks/delivery.py` — `_claim_batch()` sets `row.status = "in_flight"`; `_claim_batch`'s own filter is `status == "pending"`
What is wrong: `in_flight` is entered on claim and left only by `_finish` on the success or permanent-failure path, so a worker crash, a lock expiry, an unhandled exception in `gather`, or the CHECK-constraint failure above strands the row in a state no query ever selects again (R38 clause 1: transient state with no failure exit and no timeout).
What breaks in production: every delivery interrupted by a deploy or a restart is lost silently — it is neither delivered nor visible as failed, and `GET /deliveries` reports it as perpetually in flight.
Fix: stamp `claimed_at` when transitioning to `in_flight` and widen the claim query to also pick up `status == 'in_flight' AND claimed_at < now() - interval '<lease>'`, incrementing `attempts` on reclaim; add the matching column and index in migration `0043`. Allow side to pin: a delivery currently being worked on by a live worker is NOT reclaimed — assert that a row claimed 5 seconds ago is invisible to a second `_claim_batch`, or a fix that reclaims everything trades this bug for duplicate deliveries. Red-prove each clause: (i) claim a row, age `claimed_at` past the lease, call `_claim_batch` → the row is returned (reds today, where it is unreachable); (ii) claim a row and do not age it → not returned; (iii) reclaim a row already at `MAX_ATTEMPTS` → it is finalized `failed_permanent` rather than looping forever. Fail loudly: log a warning naming each reclaimed delivery id, so a reclaim storm is visible rather than looking like ordinary throughput. Preserve: keep `attempts` monotonic across reclaims so `MAX_ATTEMPTS` still bounds total tries. Boundary and tie: a row whose `claimed_at` is exactly at the lease boundary is not reclaimed (strict `<`), and two workers racing to reclaim the same expired row must be resolved by a conditional UPDATE on the previous `claimed_at`, not by read-then-write.

### Major: the worker loop dies permanently on the first unhandled exception
File: `app/webhooks/delivery.py` — `run_worker()`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` without `return_exceptions=True` re-raises the first failure, and there is no `try/except` around the body of `while True`, so any exception — the `IntegrityError` from the status mismatch, an `AttributeError` from a `None` endpoint, a Redis timeout — escapes the loop and terminates the worker; the `if not batch` check is also placed after the `try/finally`, where `batch` is unbound if `_claim_batch` raised.
What breaks in production: one poisoned delivery stops all webhook delivery process-wide with no retry and no restart path, and the failure looks like an idle worker rather than a crashed one.
Fix: pass `return_exceptions=True` to `gather` and inspect the results, routing each exception to `_finish(..., "failed_permanent", ...)` or to a reclaimable state for that delivery only; wrap the loop body in `try/except Exception` that logs with the delivery ids in the batch and continues after `poll_interval`; initialize `batch: list = []` before the `try` so the post-`finally` check cannot raise `NameError`. Allow side to pin: a batch where one delivery raises and one succeeds → the successful one is still marked `delivered` and the loop performs a subsequent poll; a fix that swallows everything would otherwise pass. Red-prove each clause: (i) make one `deliver` raise → the sibling still completes and the loop iterates again (reds today); (ii) make `_claim_batch` raise → the loop logs and iterates rather than exiting (reds today with `NameError`/propagation); (iii) make every delivery raise → each is recorded against its own row, not one aggregate. Fail loudly: the per-iteration handler must log at error with the exception type and the affected ids, and increment a failure counter — a silent `pass` here reproduces exactly the invisibility this finding is about. Preserve: keep the lock released in `finally` on every path. Boundary and tie: an empty batch is not an error and must not count toward any consecutive-failure backoff.

### Major: ORM instances are used after the session that loaded them has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returns `rows` after its `with session_scope()` block; `deliver()` reads `delivery.attempts`, `delivery.payload`, `delivery.id` and uses the `endpoint` fetched in a closed scope
What is wrong: both functions let mapped instances escape the scope that owns them and then read attributes from them, which under SQLAlchemy's default `expire_on_commit=True` raises `DetachedInstanceError` on first access, and under any configuration means `deliver` signs a snapshot rather than the current row.
What breaks in production: if `session_scope` uses the default, no delivery ever sends — the first attribute read in `deliver` throws, `gather` propagates, and the worker dies per the finding above; if it does not, retry accounting silently works from stale `attempts`.
Grounding note: `session_scope` itself is not in the diff, so the `expire_on_commit` half of this is a question rather than an assertion — the answer that closes it is the sessionmaker's configuration. The escape of the instances is visible in the diff regardless, and the fix is required either way.
Fix: have `_claim_batch` return plain data (e.g. a frozen dataclass of `id`, `endpoint_id`, `payload`, `attempts`) rather than mapped rows, and have `deliver` load the endpoint's `url` and `signing_secret` into the same structure inside one scope, so nothing crosses the boundary but immutable values. Allow side to pin: a claimed delivery still sends with the correct payload and the correct endpoint secret — assert the transmitted body and signature against a fixture, so the refactor is not merely "no exception". Red-prove each clause: (i) run `deliver` against a session factory configured with `expire_on_commit=True` → reds today, passes after; (ii) mutate `attempts` in the database between claim and send → the delivery uses the claimed value, pinning that the snapshot is intentional and bounded; (iii) delete the endpoint between claim and send → a named "endpoint missing" failure rather than an `AttributeError` on `None` (`deliver` does not check `session.get` for `None` today). Fail loudly: a missing endpoint finalizes the delivery with a named reason; it must not be indistinguishable from a transport failure. Preserve: keep one query per claim — do not fix this by reloading the endpoint per attempt inside the retry loop. Boundary and tie: a delivery whose endpoint was deactivated after the claim is still sent (the claim decided), and that choice must be stated in the code, because the opposite choice is equally defensible and the next reader will assume whichever they prefer.

### Major: the documented retry policy is not the implemented one
File: `docs/webhooks.md` — "backoff is exponential with jitter" and "a 4xx is permanent and we stop immediately"; `app/webhooks/delivery.py` — `backoff_for()` and `deliver()`
What is wrong: `backoff_for` returns `2**attempt` with no jitter at all (and `test_backoff_grows_exponentially` pins the exact values, so the doc is definitively contradicted by the change's own test), and `deliver` retries every non-2xx response up to `MAX_ATTEMPTS` including 4xx (R29 rationale accuracy; R49 claim stronger than implementation).
What breaks in production: customers size their endpoints against a policy we do not implement, and a mass event (an outage restoring 10,000 pending deliveries) retries in lockstep at exactly 2s, 4s, 8s and 16s, producing a thundering herd against endpoints that returned a permanent 400 four times over.
Fix: implement what the doc states — add full jitter (`random.uniform(0, 2**attempt)` is acceptable here because this is scheduling, not secret material; do not reuse the secret-generation path) and stop on 4xx other than 408 and 429, which stay retryable. Allow side to pin: a 500 is still retried and a 2xx is still `delivered` with `attempts == 1`; assert those explicitly, or a fix that treats everything as permanent passes. Red-prove each clause separately: (i) return 400 → exactly one POST is issued and status is `failed_permanent` (reds today, which issues five); (ii) return 429 → retried (reds if the 4xx rule is applied bluntly); (iii) assert `backoff_for(attempt)` is bounded by `[0, 2**attempt]` and that 100 samples are not all equal (reds against today's constant); (iv) return 500 five times → `failed_permanent` at `attempts == MAX_ATTEMPTS`. Fail loudly: an unclassifiable outcome (no response, no exception) must take the retry path with a named reason rather than defaulting to `delivered`. Preserve: keep the "at most 5 attempts" ceiling and keep the exponential growth — jitter must not be added by widening the ceiling. Boundary and tie: state which side 408 and 429 fall on and that exactly `MAX_ATTEMPTS` attempts are made, not `MAX_ATTEMPTS + 1`; if instead the doc is what should change, that edit still needs the jitter claim removed rather than left as aspiration.

### Major: `organizations.webhooks_enabled` is added but never read

What is wrong: the change declares an org-level capability flag and nothing in the diff consults it — `create_webhook_endpoint` registers regardless, `enqueue_for_event` filters only on `WebhookEndpoint.active`, and `dispatch` gates only on `WEBHOOK_EVENT_TYPES` (R41: a declared capability with no backing path).

Cross-cutting check: `webhooks_enabled` appears exactly once in the diff, in the migration; there is no reader anywhere in the added Python.
Fix: enforce the flag at both boundaries — `create_webhook_endpoint` returns 403 with a named reason when the caller's org has it false, and `enqueue_for_event` joins `Organization` and filters `webhooks_enabled.is_(True)`. Red-prove each clause separately: (i) flag false → registration is refused (reds today); (ii) flag false → `enqueue_for_event` creates zero rows for an org that has an active endpoint (reds today, and is a different call site from (i)); (iii) flag true → both succeed. Boundary and tie: flipping the flag off mid-flight does not cancel already-enqueued deliveries — state that, because the alternative (checking at send time) is a different and equally defensible contract.

### Major: two independent allowlists decide one predicate, and neither is validated at registration

### Major: enqueue failure is swallowed, so an event is durably recorded and permanently undeliverable
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: the event row is committed by its own `session_scope` before `enqueue_for_event` runs in a separate transaction, and any failure of that second transaction is caught, logged at warning, and discarded with no retry, no outbox, and no state on the event marking it un-enqueued (R9: fire-and-forget outside the transaction that made the decision).
What breaks in production: a transient database error, or either of the two schema defects above, loses the webhook for a paid invoice permanently and reports success to the caller — the only trace is a warning line, and nothing can reconstruct which events were missed.
Fix: write the delivery rows in the same transaction as the event (an outbox: `dispatch` opens one `session_scope` that inserts the `Event` and the `WebhookDelivery` rows together, with the worker picking them up), so either both exist or neither does. Allow side to pin: a successful dispatch still returns `event_id` and still notifies in-process `SUBSCRIBERS` — assert both, since moving the write inside the transaction must not change the dispatch contract. Red-prove each clause separately: (i) force the delivery insert to fail → the `Event` row is absent too and `dispatch` raises (reds today, where the event persists and the caller sees success); (ii) force a subscriber to raise → deliveries are unaffected, pinning that only the delivery write joined the transaction; (iii) a normal dispatch → exactly one event row and one delivery row per subscribed endpoint. Fail loudly: replace the bare `except Exception` with a handler that re-raises after logging; "enqueue failed" must reach the caller rather than being downgraded to a warning. Preserve: keep the `WEBHOOK_EVENT_TYPES`/endpoint filtering — the fix is the transaction boundary, not the selection. Boundary and tie: an event type with zero subscribed endpoints commits the event alone and is a success, not a failure.

### Major: the signature header is written to the application log at INFO
File: `app/webhooks/delivery.py` — `send_once()`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: the whole header dict — including `X-Acme-Signature` and its timestamp — is logged for every attempt at INFO level.
What breaks in production: logs are shipped, indexed, and read far more widely than the webhook path itself, so anyone with log access can replay a captured signed request verbatim against the customer's endpoint (and once the timestamp is inside the MAC per the first finding, the pair in the log is a complete, indefinitely valid forgery for that payload).
Fix: log the endpoint id and the event type only — `log.info("POST endpoint=%s event=%s", endpoint.id, delivery.event_type)` — and never the header mapping or the URL's query string. Allow side to pin: the log line still identifies which delivery attempt was made, so operators keep the debugging affordance; assert the line contains the delivery and endpoint ids. Red-prove each clause: (i) capture log records during `send_once` and assert no record's formatted message contains the signature value (reds today); (ii) assert no record contains the raw URL query string; (iii) assert the identifying record is still emitted (reds if the fix is "delete the log line"). Fail loudly: if a redaction helper is introduced it must raise on an unknown header rather than passing it through, so a header added later is not logged by default. Preserve: keep the failure-path `log.warning` in `deliver`, which already logs only `delivery.id` and a detail string — but bound that detail, since it is response text from an untrusted endpoint. Boundary and tie: state that the signature is secret-derived material for logging purposes even though it is transmitted in the clear — the tie-breaker is that the log outlives the request.

### Major: the delivery pipeline ships with no tests, and the signing test that exists is a tautology
