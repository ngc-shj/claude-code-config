### Critical: `list_deliveries` has no tenancy filter — any authenticated user reads any organization's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters on the caller-supplied `endpoint_id` only and never joins to `WebhookEndpoint.org_id == user.org_id`, while its sibling `list_webhook_endpoints` three lines above in the same diff does apply exactly that org filter — the pattern was propagated to one route and not the other (R3, security-relevant).
What breaks in production: Any logged-in customer can enumerate `endpoint_id` 1..N and read every other tenant's delivery history — event ids, event types, upstream response statuses — which is a cross-tenant data breach, and `docs/webhooks.md` states the endpoint returns deliveries "belonging to your organization", so the leak is invisible to anyone reading the contract.
Fix: Join the tenancy predicate into the query rather than checking it in the handler body — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id, ...)` — and return `404` (not `403`) when the join yields nothing, so the response does not disclose whether the id exists. Boundary and tie: an endpoint whose `org_id` is exactly `user.org_id` is ALLOWED (this is the case that must still succeed); an endpoint id that does not exist and an endpoint id owned by another org must produce byte-identical 404 responses, so existence is not inferable from the pair. Pin both sides with two route-level tests: (a) owner requests own endpoint, asserts 200 and the exact delivery ids (allow side — a fix that always denies must fail this); (b) a user in org B requests org A's endpoint id, asserts 404 AND asserts the response body contains no delivery rows (RT8: assert the mutation/disclosure did not happen, not only the status). Red-prove each clause separately by executing it: delete the `org_id` predicate → (b) reddens; change the `404` to `403` → the identical-response assertion reddens; delete the `id == endpoint_id` predicate → (a) reddens on the returned id set. Preserve what made the feature useful: the owner path must still return the same rows in the same `created_at DESC` order it returns today. If the join cannot resolve the endpoint at all (row missing, session error), raise rather than returning `[]` — an empty list must not be the spelling of "could not check".

### Critical: every endpoint's signing secret is returned on every `GET /webhook-endpoints`
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry
What is wrong: `to_dict()` includes the raw signing secret and is the serializer used by `list_webhook_endpoints`, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: The webhook secret — the sole authenticator for outbound events — is readable from a plain GET, so any actor with a read-scoped API key or a leaked browser session can pull it and forge signed events into the customer's system, and the documented "cannot be read back" property that customers rely on when scoping API keys is false.
Fix: Remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return the secret explicitly once — `return {**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` — so the disclosure lives at exactly one call site that a reader can see. Add a rotation route (`POST /webhook-endpoints/{id}/rotate-secret`, org-scoped as above) returning the new secret once, since the secret is otherwise unrecoverable after this change; that is the behaviour the fix must preserve, not delete. Boundary and tie: the create response is the one place the secret appears, and two endpoints created in the same request-second must each return their own distinct secret. Pin the allow side (creation still returns a usable secret: assert the returned secret verifies a signature produced for that endpoint) and the deny side (list and deliveries responses contain no key matching `signing_secret` and no value with the `whsec_` prefix — assert on the serialized JSON, not on the dict, so a rename does not slip past). Red-prove separately: re-add the key to `to_dict()` → the list assertion reddens; make `create` return the plain `to_dict()` → the create assertion reddens.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, which draws from the Mersenne Twister — a fully deterministic generator whose internal state is recoverable from 624 observed outputs — instead of the `secrets` module the standard library provides for exactly this (R1: a shared security primitive reimplemented, escalated to Critical because the duplicated behaviour IS the security control).
What breaks in production: An attacker who obtains one secret (see the disclosure finding above, or any customer-side leak) can reconstruct the generator state and derive the signing secrets of endpoints created around the same time, then forge `invoice.paid` events into other customers' systems — a signature scheme whose keys are predictable provides no authentication at all.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete `_ALPHABET` and the `random`/`string` imports outright rather than leaving them unreferenced (R1 clause d). Rename `SECRET_BYTES` to reflect what it now is — 32 bytes of entropy, not 32 characters — and note the behavioural change at the call site (R1 clause b): the secret string length changes from `len(prefix)+32` to `len(prefix)+43`, so `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` must be updated to assert `len(secret) >= len(SECRET_PREFIX) + 40` and, on the allow side, that the secret still starts with `SECRET_PREFIX` and still verifies through `sign`/`verify`. Boundary and tie: two calls in the same process tick must return different secrets — assert `new_signing_secret() != new_signing_secret()`, which is the property `random.seed(0)` breaks and length assertions do not. Red-prove each clause separately by execution: seed `random` and revert to `random.choice` → the distinctness test must still pass (it does, so it is NOT the red-proof) while a stubbed `token_urlsafe` returning a constant → the distinctness test reddens; shorten `SECRET_BYTES` to 4 → the length floor reddens. Do not "fix" this by widening the length assertion instead of changing the generator. If `secrets` is unavailable the import fails loudly at module load — do not wrap it in a `try/except` that falls back to `random`.

### Critical: the transmitted body is not the body that was signed
File: `app/webhooks/delivery.py` — `send_once`, `sign(endpoint.signing_secret, delivery.payload)` paired with `client.post(..., json=delivery.payload)`
What is wrong: `sign` HMACs `serialize(payload)` = `json.dumps(payload, sort_keys=True)` (sorted keys, `", "`/`": "` separators) while httpx re-serializes the same dict independently for the `json=` kwarg (insertion order, compact separators), so the signature covers a byte string that is never sent — the change already contains the canonical serializer, `signing.serialize`, and `send_once` bypasses it (R40, R1).
What breaks in production: Every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest than we sent, so 100% of deliveries fail verification and the feature is dead on arrival for every integrator — and because our retry loop treats their rejection as a retryable failure, each event is redelivered 5 times before being written off.
Fix: Serialize once and send those exact bytes: `body = serialize(delivery.payload).encode()`; `ts, signature = sign_bytes(endpoint.signing_secret, body)`; `await client.post(endpoint.url, content=body, headers={...,"Content-Type": "application/json"})`. Refactor `sign` to take the already-serialized bytes (`sign_bytes(secret, body: bytes)`) and keep a thin `sign(secret, payload)` that calls `serialize` then `sign_bytes`, so the signed bytes and the wire bytes are the same object by construction rather than by two implementations agreeing. Boundary and tie: two payloads that differ only in key insertion order must produce the identical body and the identical signature (that is what `sort_keys` buys and what the fix must preserve); a payload containing a non-ASCII string must be signed and sent in the same encoding — fix `ensure_ascii` explicitly rather than inheriting two different defaults. Pin it with a round-trip test that feeds ACTUAL producer output through the ACTUAL consumer (R40's requirement): in `test_send_once_posts_the_signed_payload`, replace the `startswith("sha256=")` assertion with `assert signing.verify_bytes(SECRET, captured["body"], captured["headers"][SIGNATURE_HEADER], captured["headers"][TIMESTAMP_HEADER])` — recomputing over the captured raw bytes is the assertion that currently would have caught this and does not exist. Red-prove separately: revert `content=` to `json=` → the round-trip assertion reddens; drop `sort_keys` from `serialize` → a two-key out-of-order payload case reddens; change the Content-Type → the header assertion reddens. Do not fix by deleting the `sort_keys` canonicalization; the allow side that must still pass is that a dict built in a different key order still yields a byte-identical request.

### Critical: the timestamp is not covered by the MAC and `verify` ignores it, so replay protection does not exist
File: `app/webhooks/signing.py` — `sign` and `verify`
What is wrong: `sign` computes `hmac(secret, serialize(payload))` and returns the timestamp alongside it rather than inside it, and `verify` discards the timestamp entirely (`_, expected = sign(...)`), while `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed" (R29 intra-repo rationale, R49 claim stronger than the implementation).
What breaks in production: An attacker who captures one delivery can replay it forever with any `X-Acme-Timestamp` value they like — the header is unauthenticated, so rewriting it does not invalidate the signature — and a customer who implements the documented five-minute window still accepts the replay because the window is checked against a value the attacker controls, meaning a captured `invoice.paid` can be replayed to trigger repeated fulfilment.
Fix: Make the signed message `f"{timestamp}.".encode() + body` and give `verify` the timestamp as a required argument: `verify(secret, body: bytes, signature: str, timestamp: str, tolerance_seconds: int = 300)`, which recomputes over the supplied timestamp, compares in constant time, and then rejects when `abs(now - int(timestamp)) > tolerance_seconds`. Boundary and tie: a timestamp exactly `300` seconds old is ACCEPTED and `301` is rejected — state that in the docstring and in the docs, and reject a timestamp in the future by more than the same tolerance so clock skew is bounded on both sides. Fail loudly rather than silently: a non-integer, absent, or empty `X-Acme-Timestamp` must raise/return False through a named path, not be coerced to `0` (which would place it outside the window and read as an ordinary signature mismatch). Pin the allow side (a freshly signed payload verifies) and the deny side (the same body and signature with the timestamp rewritten to `now-3600` is rejected — this is the case no current test covers). Red-prove each clause separately by execution: remove the timestamp from the MAC input → the rewritten-timestamp test reddens; remove the tolerance check → the stale-timestamp test reddens; widen tolerance to 301 → the boundary test reddens. Update `docs/webhooks.md` in the same change only after the code matches it; do not close this by editing the doc down to what the code does.

### Critical: `verify` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses Python's short-circuiting `==` instead of `hmac.compare_digest`, in the function shipped as the reference verifier and exercised by two tests (RS1).
What breaks in production: A remote attacker can recover a valid signature byte-by-byte from response-time differences on any host that calls this helper on an inbound path, and — worse — `docs/webhooks.md` instructs customers to "compare it against your own computation using a constant-time comparison" while our own reference implementation does not, so the example we ship teaches the bug.
Fix: `return hmac.compare_digest(expected, signature)`, and compare over `bytes` (`expected.encode()`, `signature.encode()`) so the comparison length is not itself variable with the caller's input encoding. Boundary and tie: a signature of the wrong LENGTH must reject through the same path and not short-circuit earlier — `compare_digest` on unequal-length inputs still returns False without leaking position, which is the property to preserve; a signature missing the `sha256=` prefix must reject rather than raise. Pin the allow side (`test_verify_accepts_signature_produced_by_sign` must still pass) and add a deny case for a signature differing only in the final hex character. Red-prove by execution: replace `compare_digest` with `==` → add a test asserting `verify` is implemented via `compare_digest` at the source level only if you cannot measure timing, and red-prove that grep-style check by removing the call (a timing assertion is flaky and is not an acceptable substitute — state which of the two you shipped). If `hmac.compare_digest` is unavailable the import fails at module load rather than falling back.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so the index forbids the exact fan-out the feature exists to perform.
What breaks in production: Any organization with two active endpoints subscribed to the same event hits a unique-violation on `session.add_all`, the whole enqueue rolls back, and `dispatcher.dispatch` swallows the exception as a `log.warning` — so NO endpoint receives the event, silently, and `docs/webhooks.md`'s "delivery is at-least-once, so deduplicate on `event_id`" becomes at-most-once-globally.

Pin with two tests: (allow) enqueue an event for an org with two active subscribed endpoints, assert exactly 2 rows with distinct `endpoint_id`; (deny) enqueue the same event twice, assert still 2 rows and no exception raised. Red-prove separately by execution: revert the index to `(event_id)` → the two-endpoint test reddens with IntegrityError; drop the `ON CONFLICT` clause → the double-enqueue test reddens; drop the index entirely → the double-enqueue row-count assertion reddens (4 rows). Also add the index the hot path actually needs — `(status, next_attempt_at)` — since `idx_webhook_deliveries_status` alone does not serve `_claim_batch`'s ordered range scan.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` over a batch of up to `BATCH_SIZE = 100`, but its retry pause is the blocking `time.sleep`, which halts the loop thread rather than yielding.
What breaks in production: One failing endpoint stalls every other delivery in the batch and any other coroutine sharing that loop — with 2+4+8+16 = 30s of backoff plus four 30s request timeouts per delivery, a batch of failing endpoints wedges the process for tens of minutes, and if the worker shares a loop with the API server every inbound request hangs with it.
Fix: The retry must not be an in-process loop at all — it must be persisted, because a lock TTL of 60s cannot cover a 30s-plus retry chain (see the `in_flight` finding below). Replace the `while True` loop in `deliver` with a single attempt: on 2xx call `_finish(..., "delivered", ...)`; on a retryable failure with `attempt < MAX_ATTEMPTS` write `status="pending"`, `attempts=attempt`, `next_attempt_at = now + backoff_for(attempt)` and return; on `attempt >= MAX_ATTEMPTS` write `failed_permanent`. If an in-process retry is kept instead, it must at minimum be `await asyncio.sleep(delay)` — but state which of the two you shipped, because only the persisted form survives a worker restart. Boundary and tie: a delivery whose `next_attempt_at` is exactly `now` IS claimable (`<=` in `_claim_batch`), and two deliveries scheduled to the same microsecond must both be claimed rather than one being skipped — order by `(next_attempt_at, id)` so the tie has a total order (R57). Pin the allow side (a first-attempt 200 still marks `delivered` in one pass and issues exactly one POST) and the deny side (a 500 leaves the row `pending` with `attempts=1` and `next_attempt_at` advanced by exactly 2s). Red-prove each separately by execution: restore `time.sleep` and assert the batch of 10 failing deliveries completes within a wall-clock budget → reddens; remove the `next_attempt_at` advance → the scheduling assertion reddens; remove the `MAX_ATTEMPTS` branch → the terminal-state assertion reddens. Preserve the retry budget — five attempts and the 2/4/8/16 schedule — the fix changes where the wait happens, not that there is one.

### Critical: endpoint URLs are unvalidated against internal targets, plaintext `http` is accepted, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` admits `http`, and any scheme merely prefixed with it, with no host restriction at all, while `docs/webhooks.md` claims "Only `https://` URLs are accepted" — and even a host that passed a check at registration time can redirect the delivery worker elsewhere because the client follows redirects (RS3/RS5 semantic-floor gap; R49 doc claim stronger than the implementation).
What breaks in production: An authenticated customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://127.0.0.1:6379/` and our delivery worker POSTs signed payloads to it from inside the VPC — a server-side request forgery that reaches the cloud metadata service and internal admin ports — and every plaintext `http://` endpoint additionally puts the full event payload on the wire in clear.
Fix: Replace `startswith` with an exact-membership check against a whitelist — `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)` — then resolve the hostname and reject when any resolved address is private, loopback, link-local, multicast, or unspecified (`ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved` over every result of `socket.getaddrinfo`). Set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure, since a redirect target bypasses the registration-time check entirely; also re-check the resolved address at delivery time (DNS rebinding means the registration-time answer is not the delivery-time answer — the check must be at the socket, so pin it with a custom transport/resolver rather than only at the route). Boundary and tie: `https://` on a non-default port is ALLOWED (do not restrict to 443 — that is the allow side that must still succeed); `http://` on any port, an IPv6 literal in private space (`https://[::1]/`), and a public hostname whose A record is `10.0.0.1` are all DENIED. Fail loudly: when DNS resolution fails or times out, reject the registration with a named error — an unresolvable host must not fall through to "no private address found, therefore allowed". Red-prove each clause separately by execution: revert to `startswith("http")` → the `http://` deny case reddens; remove the private-IP check → the `http://169.254.169.254` case reddens; set `follow_redirects=True` → the redirect-to-internal case reddens; remove the resolution-failure branch → the DNS-failure case reddens. Update `docs/webhooks.md` only after the code enforces https-only.

### Major: a delivery left mid-retry is wedged in `in_flight` with no path back
File: `app/webhooks/delivery.py` — `_claim_batch` (sets `row.status = "in_flight"`) and `_claim_batch`'s filter `status == "pending"`
What is wrong: `_claim_batch` is the only writer of `in_flight` and the only reader selects `pending`, so a delivery whose worker crashes, is redeployed, or whose 60s lock expires mid-retry has no transition out of `in_flight` — the state machine has a non-terminal state with no timeout and no reaper (R38 clause 1).
What breaks in production: Every rolling deploy silently drops the deliveries in flight at that moment, permanently — the rows are neither delivered nor retried nor visible as failures in `GET .../deliveries`, so the customer sees an event that simply never arrived and we have no signal that it did not.
Fix: Add a lease rather than a status flag: store `claimed_at` (or reuse `updated_at`) when transitioning to `in_flight`, and widen `_claim_batch`'s predicate to `status == 'pending' OR (status == 'in_flight' AND claimed_at < now - LEASE_TIMEOUT)` with `LEASE_TIMEOUT` set above the worst-case single attempt (`REQUEST_TIMEOUT` plus margin). Boundary and tie: a row whose `claimed_at` is exactly `now - LEASE_TIMEOUT` is reclaimed (`<=`), and reclaiming must increment `attempts` so a permanently-crashing delivery still terminates at `MAX_ATTEMPTS` rather than looping forever — that bound is what stops the reaper from becoming an infinite redelivery source. Pin the allow side: a delivery claimed 1 second ago is NOT stolen by a second worker (the case a naive reaper breaks, causing duplicate POSTs). Red-prove each clause separately by execution: remove the reclaim predicate → the crashed-worker test (insert an `in_flight` row with an old `claimed_at`, run one worker pass, assert it is picked up) reddens; remove the `attempts` increment on reclaim → the termination test reddens; shorten `LEASE_TIMEOUT` below `REQUEST_TIMEOUT` → the not-stolen test reddens.

### Major: the Redis lock is neither atomic nor safely released
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act with a window in which two workers both observe the key absent, the `expire` is a separate round trip so a crash between `set` and `expire` leaves a key with no TTL, and the unconditional `delete` in `finally` removes whatever lock is currently held — including one a different worker acquired after this worker's TTL lapsed (R5 read-then-write without atomicity; R38 clause 2 persisted fail-closed wedge).
What breaks in production: Two workers claim overlapping batches and the customer receives duplicate POSTs; or a single crash at the wrong instant leaves `webhooks:dispatch:lock` set forever with no expiry, and all webhook delivery stops silently until someone deletes the key by hand.
Fix: Acquire with a single atomic command carrying its own TTL — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = uuid4().hex` is unique per acquisition — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock. Boundary and tie: `LOCK_TTL_SECONDS` must exceed the worst-case batch duration (`BATCH_SIZE` deliveries at `REQUEST_TIMEOUT` each, under the persisted-retry model above) or renew the lease mid-batch — state which; and when two workers race, exactly one gets `True` and the other must sleep rather than proceed. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise (or return False and log at ERROR) — it must NOT return True and run unlocked, and "could not check the lock" must not be spelled the same as "no lock held". Pin the allow side: a single worker still acquires, runs, and releases so the next pass acquires again (a fix that always returns False satisfies every other clause and delivers nothing). Red-prove each separately by execution: drop `nx=True` → a two-concurrent-acquire test reddens; drop `ex=` → a test asserting `TTL(LOCK_KEY) > 0` reddens; revert the release to unconditional `delete` → a test where worker A's token has been superseded asserts the key still exists and reddens.

### Major: a failed webhook enqueue is swallowed and nothing reconciles it
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: The enqueue runs after the event transaction has committed and any failure is caught, logged at WARNING, and dropped, with no retry, no dead-letter row, and no later scan that could find events with no corresponding deliveries (R4).

Concretely: move the `WebhookEndpoint` query and `WebhookDelivery` insert inside `dispatch`'s existing `with session_scope() as session:` block (passing the session into `enqueue_for_event`), remove the `try/except`, and let a failure roll back the event too. Boundary and tie: an event type present in `WEBHOOK_EVENT_TYPES` with zero matching endpoints must commit the event and zero delivery rows without error (the allow side); an event whose delivery insert fails must leave NO event row, so "the event happened" and "we owe a webhook for it" cannot disagree. Red-prove each separately by execution: re-add the `except Exception` → a test forcing an insert failure and asserting the event row is absent reddens; move the insert back outside the scope → the same test reddens on the event row being present; break the zero-endpoint path → the allow-side test reddens. ### Major: `limit` and `event_types` accept unbounded values

### Major: full response bodies are persisted and headers are logged on every delivery
File: `app/webhooks/delivery.py` — `log.info("POST %s headers=%s", endpoint.url, headers)` and `_finish(..., detail)` where `detail` is `response.text` or `f"HTTP {code}: {response.text}"`
What is wrong: The entire remote response body is stored unbounded in `response_body TEXT` on both the success and failure paths, and every delivery logs its full header dict at INFO including the signature.
What breaks in production: An endpoint returning a large HTML error page writes megabytes per attempt into `webhook_deliveries` — five times per failing delivery, across every endpoint — bloating the table and the log volume, and the signature header lands in log aggregation where it is retained far longer than the five-minute replay window it authenticates.

Red-prove each separately by execution: remove the slice → the oversized-body test reddens on stored length; remove the marker → the truncation-marker assertion reddens; restore the header logging → a log-content assertion reddens.

### Major: naive and aware timestamps are mixed across the enqueue, claim, and schema layers
File: `app/webhooks/delivery.py` — `next_attempt_at=datetime.utcnow()` in `enqueue_for_event` vs `now = datetime.now(timezone.utc)` in `_claim_batch`; `migrations/0042_webhook_delivery.sql` — `next_attempt_at TIMESTAMP NOT NULL` vs `app/webhooks/models.py` — `DateTime(timezone=True)`

### Major: the signature tests are round-trips through the same function and cannot detect the wire-format or timestamp defects
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign`, `test_send_once_posts_the_signed_payload`
What is wrong: `verify` calls `sign` internally, so `test_verify_accepts_signature_produced_by_sign` asserts `f(g(x))` against `g(x)` — a tautology that two mirrored-wrong implementations satisfy, exactly the shape R29 names — and `test_send_once_posts_the_signed_payload` asserts only that the header *starts with* `sha256=`, never recomputing the HMAC over `captured["body"]` (RT1, RT5).
What breaks in production: The suite is green while the signature covers different bytes than the request body and omits the timestamp, so a reviewer reading these test names concludes signing is verified when nothing about the actual signed message has been checked.

Red-prove each separately by execution: revert `send_once` to `json=` → the recomputed-MAC assertion reddens; drop the timestamp from the MAC input → the literal-digest test reddens; drop `sort_keys` → the key-order test reddens. Keep the existing tests — they are cheap and non-vacuous for the prefix/length properties; add these rather than replacing them.

### Major: `run_worker` has no exception handling and can raise `NameError` on its own control flow
File: `app/webhooks/delivery.py` — `run_worker`, the `try/finally` around `batch = await _claim_batch()` and the following `if not batch:`
What is wrong: `batch` is assigned inside the `try` and read after the `finally`, so any exception from `_claim_batch` or `asyncio.gather` propagates out of the `while True` loop and terminates the worker — and if it were caught, `batch` would be unbound at the `if not batch` line.
What breaks in production: One bad delivery row kills the worker process, and since the `finally` releases the lock on the way out, nothing is left holding it and nothing is left running — webhook delivery stops entirely with a single traceback and no retry.
Fix: Initialize `batch: list = []` before the `try`, wrap the body in `except Exception: log.exception(...)` inside the loop so one bad pass does not end the worker, and add a `finally`-scoped sleep so a repeatedly failing pass cannot become a hot loop against the database. Boundary and tie: an EMPTY batch sleeps `poll_interval` and a FULL batch (`len(batch) == BATCH_SIZE`) continues immediately without sleeping — that is the intended throughput behaviour and it must be preserved; state which side `len(batch) == BATCH_SIZE` falls on. Red-prove each separately by execution: remove the initializer and force `_claim_batch` to raise → the `NameError` reddens; remove the `except` → a test asserting the loop survives one raising pass reddens; remove the sleep-on-empty → a timing/call-count assertion on the idle path reddens.

### Major: retries ignore the documented 4xx-is-permanent rule
File: `app/webhooks/delivery.py` — `deliver`, the branch after `if 200 <= response.status_code < 300`
What is wrong: Every non-2xx status falls through to the retry path, but `docs/webhooks.md` states "a 4xx is permanent and we stop immediately" (R29 — the doc is the contract customers integrate against).
What breaks in production: An endpoint that has been deleted (410) or is rejecting our signature (401) receives five POSTs per event instead of one, multiplying wasted requests against a customer that has already told us to stop and burning our own worker capacity on deliveries that cannot succeed.
Fix: Branch explicitly — `if 400 <= status < 500 and status not in RETRYABLE_4XX: _finish(..., "failed_permanent", ...); return` — with `RETRYABLE_4XX = {408, 429}`, and honour `Retry-After` on a 429 by setting `next_attempt_at` from the header rather than the backoff curve. Boundary and tie: status `399` and `400` fall on opposite sides, as do `499` and `500` — pin all four; `429` is retryable and `403` is not. Pin the allow side: a 500 must still retry to `MAX_ATTEMPTS` (a fix that makes everything permanent satisfies "stop on 4xx" and destroys the retry feature). Red-prove each separately by execution: remove the 4xx branch → the "one POST on 404" test reddens; add 403 to `RETRYABLE_4XX` → the 403 test reddens; remove 429 from it → the 429-retries test reddens.

### Major: the documented jitter does not exist
File: `app/webhooks/delivery.py` — `backoff_for`; `docs/webhooks.md` — "backoff is exponential with jitter"
What is wrong: `backoff_for` returns `2**attempt` exactly, with no randomization, while the docs claim jitter — and `test_backoff_grows_exponentially` pins the exact deterministic values, cementing the divergence (R29).
What breaks in production: When a popular endpoint has an outage, every pending delivery to it retries at the identical second, so all of them hit the endpoint simultaneously on recovery — the thundering herd the jitter was documented to prevent, aimed at a customer already in an incident.
Fix: Return `timedelta(seconds=base * (1 + random.random() * JITTER_FRACTION))` with `JITTER_FRACTION = 0.25` and `base = BASE_DELAY_SECONDS ** attempt`, using `random` (this is scheduling, not key material — say so in a comment so a reader does not confuse it with the secret-generation fix above). Boundary and tie: the delay must remain within `[base, base * 1.25]` inclusive at both ends, and must never be less than `base` — a jitter that can shorten the delay lets a retry storm arrive earlier than the backoff intends. Change `test_backoff_grows_exponentially` to assert the RANGE per attempt rather than equality, and add a test that two calls for the same attempt differ — that distinctness test is the one the current suite would pass without any jitter, so it is the red-proof. Red-prove each separately by execution: remove the jitter term → the distinctness test reddens; make jitter symmetric (`±25%`) → the lower-bound assertion reddens; change `BASE_DELAY_SECONDS` → the range test reddens for every parametrized attempt.

## Cross-cutting verification

- **Tenancy filter**: `list_webhook_endpoints` filters `org_id == user.org_id`; `list_deliveries` does not (reported Critical). `create_webhook_endpoint` takes `org_id` from the session, not the body — correct. `enqueue_for_event` scopes by `org_id` — correct. No other route in the diff reaches tenant data.
- **Secret exposure via `to_dict`**: `WebhookEndpoint.to_dict` leaks `signing_secret` (reported Critical); `WebhookDelivery.to_dict` was checked and exposes no secret — the miss is one-sided, not systemic.
- **Status string literals**: `"pending"` appears in `models.STATUSES`, the `status` column default, `_claim_batch`'s filter and the migration CHECK; `"in_flight"`, `"delivered"`, `"failed_permanent"` similarly — four sites, none using the `STATUSES` constant the change declares, and the migration is the one that drifted (reported Critical).
- **Datetime construction**: `models._now()` (aware) is the shared helper; `enqueue_for_event` uses `datetime.utcnow()` (naive), `_claim_batch` and `_finish` use `datetime.now(timezone.utc)` inline — three spellings of one concept, one of them wrong (reported Major).
- **Serialization**: `signing.serialize` is the canonical serializer the change introduces; `send_once` is the only caller that bypasses it, via httpx's `json=` (reported Critical). `sign` and `verify` both route through it correctly.
- **Rate limiting**: none of the three new routes carries a limiter; the pre-existing `get_profile` and `list_api_keys` in the same file do not either, so this is not a propagation gap within the file but an absent control on new mutation surface (reported Major on the mutation route).

## Codebase awareness

Helpers the change already contains that the new code reimplements or bypasses:
`signing.serialize` (bypassed by `send_once`'s `json=`), `models._now` (reimplemented as `datetime.utcnow()` in `enqueue_for_event` and as an inline `datetime.now(timezone.utc)` in `_claim_batch`/`_finish`), `models.STATUSES` (declared, then not used by any of the four status write sites), and `app.api.deps.current_user` (correctly reused by all three new routes — the tenancy defect is the missing use of `user.org_id` in the query, not a missing dependency).
