### Critical: `WebhookEndpoint.to_dict()` returns the signing secret, so `GET /webhook-endpoints` hands it back on every read
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`), consumed by `app/api/routes/settings.py` — `list_webhook_endpoints` and `create_webhook_endpoint`
What is wrong: the one serializer is used for both the create response and the list response, so the shared secret that authenticates every outbound webhook is returned on an unauthenticated-by-secret read path, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: any actor holding a read-scoped session for the org — including anything that logs or caches `GET /v1/settings/webhook-endpoints` responses — obtains the HMAC key and can forge events that the customer's receiver accepts as ours.
Fix: split the serializer — `to_dict()` drops `signing_secret` entirely and a separate `to_dict_with_secret()` is called only from `create_webhook_endpoint`'s 201 path; store the secret as a hash-free but separately-columned value the list query does not load (`deferred`/`load_only` excluding it) so a future `to_dict` addition cannot re-leak it. Allow side that must still pass: the create response body still contains `signing_secret` and a test asserts the 201 body has the `whsec_` value, because that is the only delivery channel for it (Remedy Floor 1, 4 — do not fix by deleting the secret from the create response, which is what makes the feature usable). Red-prove separately: (a) re-add `signing_secret` to `to_dict()` → the list-endpoint test asserting `"signing_secret" not in body[0]` reds; (b) remove the key from the create serializer → the create test reds; (c) point `list_webhook_endpoints` at `to_dict_with_secret` → the list test reds. Fail loudly: if the create path cannot produce a secret (generator raises), return 500 and do not persist the endpoint row — never persist an endpoint with an empty/`None` secret, which would otherwise sign every payload with the empty key. Boundary/tie: an endpoint created before this change already has its secret exposed — treat every existing `signing_secret` as compromised and rotate on deploy; two endpoints of the same org sharing a URL still get distinct secrets.

### Critical: `list_deliveries` is not scoped to the caller's organization (IDOR)
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: `endpoint_id` comes straight from the path and is never joined back to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user reads any organization's delivery history; `docs/webhooks.md` claims the endpoint "returns the most recent attempts for an endpoint belonging to your organization" (R49 — claim stronger than the implementation).
What breaks in production: a customer enumerates `endpoint_id` 1..N and reads other tenants' event ids, event types, delivery status and response codes — a cross-tenant data leak with no audit trail distinguishing it from normal use.
Fix: join the delivery query to `WebhookEndpoint` and filter `WebhookEndpoint.org_id == user.org_id`, returning 404 (not 403) when the join is empty so ownership is not disclosed. This is R3 propagation, not new design: the two sibling handlers in the same file (`list_api_keys`, `list_webhook_endpoints`) already carry the `org_id == user.org_id` filter — the new handler is the only one in the file that dropped it. Allow side: a test where the endpoint DOES belong to the caller's org still returns the rows, asserting the row count and ids, so a fix that always 404s is caught (Remedy Floor 1). Red-prove separately: (a) delete the `org_id` filter → the cross-tenant test reds with a 200 and non-empty body; (b) change the empty-join response from 404 to 200-empty → the "unknown endpoint is indistinguishable from foreign endpoint" test reds. Fail loudly: when `user.org_id` is `None` or unresolvable, deny (404) rather than filtering on `NULL`, which matches no rows but for the wrong reason. Boundary/tie: an endpoint that was soft-deleted or deactivated (`active=False`) still belongs to the org and must still list its deliveries; an endpoint id that exists in another org and an id that exists nowhere must return byte-identical responses.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is the Mersenne Twister, seeded from process state and fully recoverable from 624 outputs, so the HMAC key is predictable rather than unguessable.
What breaks in production: an attacker who registers a handful of their own endpoints observes enough generator output to predict other organizations' secrets and forge signed webhooks that receivers accept as authentic.
Fix: use `secrets.token_urlsafe(SECRET_BYTES)` (or `secrets.choice` over `_ALPHABET`) and rename `SECRET_BYTES` to `SECRET_CHARS` or make it a true byte count, since today it counts alphabet characters (~5.95 bits each, not 8) and the name misstates the entropy. Allow side: `test_new_signing_secret_has_prefix_and_length` must still pass — keep the `whsec_` prefix and a deterministic total length, because clients key their secret managers off that shape (Remedy Floor 1, 4). Red-prove separately: (a) revert to `random.choice` with a fixed `random.seed(0)` in the test → a new test asserting two secrets generated after identical seeding differ reds; (b) shorten the length by one → the length test reds; (c) drop the prefix → the prefix test reds. Fail loudly: `secrets` raising `NotImplementedError` on a platform without an OS entropy source must propagate as a 500 from `create_webhook_endpoint`, never fall back to `random`. Boundary/tie: state the minimum accepted secret length (≥ 32 characters) and reject at that exact boundary rather than below it; two endpoints created in the same microsecond must not share a secret, which seeded-PRNG generation does not guarantee.

### Critical: `verify` compares signatures with `==` (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: Python's `str.__eq__` short-circuits on the first differing byte, so the comparison leaks the length of the matching prefix through timing.
What breaks in production: any caller of `verify` — this is the primitive we ship as the reference implementation and the one an inbound-webhook path would reuse — lets an attacker recover a valid signature byte by byte instead of brute-forcing 2^256, and `docs/webhooks.md` tells customers to "compare it against your own computation using a constant-time comparison" while our own helper does not.
Fix: `return hmac.compare_digest(expected, signature)`, and have `verify` take the timestamp as a parameter and reject it outside the documented five-minute window (see the next finding — the window is unenforceable while the timestamp is not in the MAC). Allow side: `test_verify_accepts_signature_produced_by_sign` must still pass with a fresh timestamp, so the fix must not become "reject everything" (Remedy Floor 1). Red-prove separately: (a) swap `compare_digest` back to `==` → a test that asserts `verify` is called through `hmac.compare_digest` (patch it and assert invoked) reds; (b) widen the freshness window past its bound → a test signing at `now - 301s` reds; (c) pass a signature of the wrong length → assert `verify` returns `False` rather than raising, since `compare_digest` on unequal-length strings returns False without leaking. Fail loudly: a `signature` that is `None` or missing the `sha256=` prefix must return `False` explicitly rather than raising a `TypeError` a caller might catch as "transport error" and retry. Boundary/tie: a timestamp exactly 300 seconds old is accepted, 301 rejected — state which side the boundary falls on in the doc and the test; two requests with the same timestamp and the same body are indistinguishable, which is why replay protection needs an `event_id` dedup as well.

### Critical: the signed bytes are not the bytes we send, and the timestamp is not covered by the signature
File: `app/webhooks/signing.py` — `sign`/`serialize`; `app/webhooks/delivery.py` — `send_once` (`client.post(..., json=delivery.payload, headers=headers)`); `docs/webhooks.md` — "Verifying the signature"
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (sorted keys, `", "`/`": "` separators) while httpx re-serializes the same dict for the wire with its own compact separators and insertion order, and the documented signed string is `"{timestamp}.{raw_request_body}"` whereas `sign` never mixes the timestamp in — so no receiver following our documentation can ever reproduce our signature, and the timestamp header is unauthenticated (R40; R29/R49 on the doc claim).
What breaks in production: every customer who implements verification exactly as documented rejects 100% of our webhooks, and any attacker who captures one delivery can freely rewrite `X-Acme-Timestamp` to defeat the replay window the doc says protects them.
Fix: serialize once and send the exact bytes — have `send_once` compute `body = serialize(delivery.payload).encode()`, sign `f"{timestamp}.{body.decode()}"`, and post with `content=body` plus an explicit `Content-Type: application/json` header instead of `json=`; change `sign` to take and return the timestamp it actually mixed in, and update `verify` to accept the timestamp. Allow side: a round-trip test that feeds the ACTUAL captured request body and the ACTUAL captured headers into `signing.verify` and asserts `True` — R40's required actual-producer-output-through-actual-consumer test, which today's `test_send_once_posts_the_signed_payload` does not do (it only asserts the header starts with `sha256=`). Red-prove separately: (a) re-introduce `json=delivery.payload` alongside the signature over `serialize(...)` → the round-trip test reds; (b) drop the `f"{timestamp}."` prefix from the signed string → a test signing two requests with the same body and different timestamps and asserting different signatures reds; (c) reorder the payload's keys before posting → the round-trip test still passes, proving the sort-keys canonicalization is the one that ships. Fail loudly: if `serialize` raises on a non-JSON-serializable payload, mark the delivery `failed_permanent` with that detail rather than posting an unsigned or partially-signed request. Boundary/tie: state that the signed string is the byte-for-byte request body and that a body of `{}` and a body of `{ }` are different subjects; document the separator convention so a re-encoding proxy is a known-breaking case.

### Critical: the migration's status CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`; `app/webhooks/models.py` — `STATUSES`
What is wrong: the code and the model constant use `failed_permanent`, the constraint allows `failed`, and no code path ever writes `failed` — a strict consumer (the DB) rejects the producer's only terminal-failure value (R40; R2 on the same enum spelled twice).
What breaks in production: the first delivery to exhaust `MAX_ATTEMPTS` raises `CheckViolation` inside `_finish`, which `deliver` does not catch (its `except` is `httpx.HTTPError` only) and which `asyncio.gather` re-raises out of `run_worker` — the worker dies, the row stays `in_flight` forever, and every subsequent restart dies the same way on the next permanent failure.
Fix: make the enum single-sourced — change the constraint to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` in a corrective migration (0042 has not shipped; if it has, add 0043 with `DROP CONSTRAINT ... ADD CONSTRAINT ... NOT VALID` then `VALIDATE`), and generate the SQL list from `app/webhooks/models.py::STATUSES` (today unused — it is imported by nothing in the diff) or assert equality between the two in a test that reads the migration file. Allow side: inserting each of the four legal statuses must still succeed, asserted one row per status, so a fix that tightens the constraint into rejecting `in_flight` is caught (Remedy Floor 1). Red-prove separately: (a) write `"failed"` from `_finish` → the sync test comparing `STATUSES` to the parsed constraint reds; (b) drop `in_flight` from the constraint → the four-status insert test reds; (c) add a fifth status to `STATUSES` without the migration → the sync test reds. Fail loudly: if the sync test cannot locate or parse the migration file, it must fail with "migration not found", not skip — "examined nothing" must not be spelled like "found nothing". Boundary/tie: name which status a delivery holds at exactly `attempts == MAX_ATTEMPTS` (it is terminal `failed_permanent`, not `pending`), and state that a row already `delivered` is never re-transitioned.

### Critical: `UNIQUE INDEX` on `webhook_deliveries(event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`; `app/webhooks/delivery.py` — `enqueue_for_event`'s `session.add_all(rows)`
What is wrong: `enqueue_for_event` builds one row per matching endpoint all sharing the same `event_id`, but the index permits exactly one delivery row per event across the entire table.
What breaks in production: the moment an organization registers a second endpoint (or two organizations subscribe to the same event id space), `add_all` raises `IntegrityError`, the dispatcher swallows it as a warning, and the event is delivered to nobody — silently, since the only signal is a `log.warning`.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the at-least-once/dedup story in `docs/webhooks.md` actually needs, and add the missing claim-query index `(status, next_attempt_at)`. Allow side: a test enqueuing one event for two endpoints of the same org asserts two rows are created and both are `pending` — the deny side (the same endpoint enqueued twice for one event yields one row) must be tested in the same test, so a fix that simply drops uniqueness is caught (Remedy Floor 1, 4 — the uniqueness is what makes the dedup guarantee real). Red-prove separately: (a) revert to `UNIQUE (event_id)` → the two-endpoint test reds with `IntegrityError`; (b) drop the index entirely → the duplicate-enqueue test reds with two rows; (c) remove the `(status, next_attempt_at)` index → a plan assertion (or the explicit index-existence test) reds. Fail loudly: `enqueue_for_event` must not swallow `IntegrityError` — a conflict on the composite key is the expected idempotent case and should use `ON CONFLICT DO NOTHING` with the inserted count returned; any other integrity error must propagate. Boundary/tie: an event with zero matching endpoints returns 0 and is not an error; two endpoints of DIFFERENT orgs receiving the same `event_id` is legal under the composite key and must be covered.

### Critical: `time.sleep` inside `async def deliver` blocks the event loop and outlives the dispatch lock
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: a synchronous sleep in a coroutine blocks the whole event loop, so the `asyncio.gather` over the batch in `run_worker` runs strictly serially instead of concurrently, and a single delivery's retry chain (2+4+8+16 = 30s) already sits at half the 60-second `LOCK_KEY` TTL.
What breaks in production: a batch of `BATCH_SIZE` = 100 deliveries takes up to ~50 minutes of wall clock while the lock silently expires after 60 seconds, letting a second worker enter and process the same table concurrently — the very condition the lock exists to prevent.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` and, better, stop retrying in-process: on a retryable failure write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next poll pick it up — that is what the `next_attempt_at` column and the `_claim_batch` filter already exist for and it removes the lock-lifetime coupling entirely. Allow side: a test asserting that two deliveries in one batch overlap (both send_once calls entered before either returned, via an event both wait on) must pass, so a fix that serializes deliveries "safely" is caught (Remedy Floor 1). Red-prove separately: (a) restore `time.sleep` → the overlap test reds (times out); (b) drop the `next_attempt_at` write on retry → a test asserting the row's next attempt is strictly in the future reds; (c) set the retry status to `in_flight` instead of `pending` → a test asserting the row is re-claimable by `_claim_batch` reds. Fail loudly: if the lock's TTL has expired while a batch is still in flight, the worker must detect it (compare a per-worker token in the lock value) and abort the batch rather than continuing to write rows another worker now owns. Boundary/tie: a delivery whose `next_attempt_at` is exactly `now` must be claimed (the filter is `<=`), and two rows with identical `next_attempt_at` must not both be claimed by two workers — which the claim query's lack of `FOR UPDATE SKIP LOCKED` does not currently prevent.

### Critical: customer-supplied URL is fetched with redirects followed and no scheme or egress restriction (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the check adjudicates the surface form of the scheme string rather than the resolved destination (R47) — `startswith("http")` admits `http://`, which `docs/webhooks.md` says is rejected ("Only `https://` URLs are accepted"), and also `httpx://`, `http+unix://` and anything else prefixed `http` — while nothing restricts the host, so `http://169.254.169.254/...` or `http://10.0.0.5:6379/` is accepted and `follow_redirects=True` lets a legitimate-looking public host redirect the signed POST into the same private space.
What breaks in production: our worker becomes a confused deputy issuing authenticated POSTs to cloud metadata and internal services from inside the VPC, and payloads intended for TLS travel in cleartext over `http://`.
Fix: validate with an exact `parsed.scheme == "https"` check plus a resolved-address guard — resolve the hostname at request time and reject any address in a private, loopback, link-local, or unique-local range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), and set `follow_redirects=False` so the redirect target cannot bypass the check that was made against the original host. Allow side: a public `https://hooks.example.com/acme` endpoint must still register and still receive a delivery — pin that with a test, so a fix that denies everything is caught (Remedy Floor 1). Red-prove separately: (a) loosen to `startswith("http")` → the `http://` rejection test reds; (b) re-enable `follow_redirects=True` → a test whose handler 302s to `http://127.0.0.1/` and asserts no second request is made reds; (c) remove the private-range check → the `https://` + private-IP registration test reds. Fail loudly: when DNS resolution fails or returns no addresses at delivery time, mark the attempt retryable with an explicit "unresolvable host" detail — never treat "could not check" as "passed the check". Boundary/tie: state which side `0.0.0.0`, IPv4-mapped IPv6 (`::ffff:10.0.0.1`) and a host resolving to BOTH a public and a private address fall on — the multi-address case must deny if ANY address is private, and re-resolution between check and connect (R51) means the guard belongs at connect time, not only at registration.

### Major: `_claim_batch` returns ORM rows after its session closes, so `deliver` reads detached objects
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`), used by `run_worker` → `deliver`
What is wrong: the returned `WebhookDelivery` instances are expired and detached once `session_scope` commits and closes, so every attribute `deliver`/`send_once` touches (`delivery.attempts`, `delivery.payload`, `delivery.id`) triggers a refresh on a dead session.
What breaks in production: the worker raises `DetachedInstanceError` on the first delivery of the first batch, `asyncio.gather` re-raises it out of `run_worker`, and no webhook is ever sent — while the rows have already been flipped to `in_flight` and can never be reclaimed.
Fix: return plain data, not ORM instances — have `_claim_batch` build a frozen dataclass (`id`, `endpoint_id`, `attempts`, `payload`, plus the endpoint's `url` and `signing_secret` fetched in the same query via a join) inside the session and return that; `deliver` then needs no second `session.get(m.WebhookEndpoint, ...)` either, removing an N+1 per delivery. Allow side: a test that claims a batch and asserts the returned objects' `payload` and `url` are readable AFTER the session has closed must pass — that is exactly the property being fixed (Remedy Floor 1). Red-prove separately: (a) return the ORM rows again → the post-session attribute-read test reds; (b) omit `signing_secret` from the projection → the `send_once` signing test reds with an attribute error; (c) drop the join and keep the per-delivery `session.get` → a query-count assertion reds. Fail loudly: if the endpoint row referenced by a claimed delivery no longer exists, mark the delivery `failed_permanent` with "endpoint deleted" instead of letting `session.get` return `None` and `send_once` fail on `None.signing_secret`. Boundary/tie: an endpoint deactivated (`active=False`) between enqueue and claim — decide and state whether its already-queued deliveries still go out; ties on `next_attempt_at` are covered by the claim-query finding below.

### Major: the dispatch lock is not atomic, has a TTL-less window, and is deleted by whoever finishes rather than by its owner
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get`-then-`set` is a check-then-act race two workers both win, `set` and `expire` are separate calls so a crash between them leaves a lock with no expiry, and the unconditional `delete` in `finally` frees a lock this worker may no longer hold after the 60-second TTL elapsed (R38 — persisted fail-closed wedge with no reset path, plus fail-open supersession).
What breaks in production: either two workers process the same `pending` rows concurrently and send duplicate webhooks, or a single badly-timed crash wedges the entire delivery pipeline until an operator manually deletes a Redis key nobody has documented.
Fix: acquire with a single atomic `SET LOCK_KEY <random-token> NX EX 60` and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) keyed on that worker's token; renew the TTL inside the batch loop while work is outstanding. Allow side: a second worker must still be able to acquire the lock after the first releases it — pin that, so a fix that never releases is caught (Remedy Floor 1). Red-prove separately: (a) revert to `get`+`set` → a test where two `_acquire_lock` calls interleave asserts exactly one returns `True` and reds; (b) drop the `EX` from the `SET` → a test asserting `ttl(LOCK_KEY) > 0` immediately after acquisition reds; (c) replace the compare-and-delete with a plain `delete` → a test where worker A's token has expired and worker B holds the lock asserts A's release does not remove B's lock and reds. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise rather than return `True` — a lock that cannot be checked must not be assumed free. Boundary/tie: a worker whose batch takes exactly the TTL must be treated as having lost the lock (deny at the boundary), and two workers presenting the same token is a misconfiguration the release script should log, not silently honour.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish`, filtered by `status == "pending"`
What is wrong: a delivery leaves `in_flight` only on the success or permanent-failure path inside `_finish`; a worker crash, an OOM kill, a deploy, or any of the exceptions above strands the row forever, because nothing selects `in_flight` rows and nothing ages them out (R38 clause 1 — every async transition needs an explicit failure-exit and a bounded timeout).
What breaks in production: after the first worker restart, a silently growing set of customer events is never delivered and never reported as failed — the delivery list endpoint shows them as permanently "in flight" with no next attempt the operator can act on.
Fix: stamp `updated_at` (or a `claimed_at`) when claiming, and add a reaper that returns rows whose `status = 'in_flight' AND updated_at < now() - interval '5 minutes'` to `pending` with `attempts` preserved and `next_attempt_at = now()`; alternatively drop `in_flight` and claim with `UPDATE ... WHERE status='pending' AND next_attempt_at <= now() ... RETURNING` under `FOR UPDATE SKIP LOCKED`, which makes the claim atomic and the state self-healing. Allow side: a delivery legitimately in flight for 10 seconds must NOT be reclaimed — assert that, so a reaper that resets everything is caught (Remedy Floor 1). Red-prove separately: (a) remove the reaper → a test that claims a row, simulates a crash, advances the clock and asserts the row is re-claimable reds; (b) reset `attempts` to 0 in the reaper → a test asserting attempts are preserved across a reap reds; (c) set the stale threshold below the request timeout (30s) → the "still in flight at 10s is not reclaimed" test reds. Fail loudly: the reaper must log a count per run and emit a distinct "reaped" signal, so a run that reaped nothing is distinguishable from a run that did not execute. Boundary/tie: a row whose `updated_at` is exactly the threshold is NOT reaped (deny at the boundary), and the reap threshold must exceed `REQUEST_TIMEOUT` plus the longest in-process wait, or the reaper duplicates a delivery still on the wire.

### Major: retry state is never persisted, so `next_attempt_at`, `attempts` and `backoff_for` are dead columns
File: `app/webhooks/delivery.py` — `deliver`'s `while True` loop; `app/webhooks/models.py` — `next_attempt_at`, `attempts`
What is wrong: `deliver` loops in memory and only calls `_finish` at a terminal outcome, so `attempts` stays at its enqueue value and `next_attempt_at` is written exactly once by `enqueue_for_event` and never advanced.
What breaks in production: any restart mid-retry loses all attempt progress, and `GET .../deliveries` reports `"attempts": 0` and a stale `next_attempt_at` for every delivery currently retrying — the exact fields `docs/webhooks.md` promises operators can inspect ("including the response status we saw and when the next attempt is scheduled").
Fix: fold this into the per-attempt persistence described in the `time.sleep` finding — after each failed attempt write `attempts=attempt`, `response_status`, `response_body`, `next_attempt_at = now() + backoff_for(attempt)` and `status='pending'`, then return; the loop becomes one attempt per claim. Allow side: a delivery that succeeds on the first attempt must still be written exactly once with `attempts=1` and `status='delivered'` — assert that, so a fix that always re-queues is caught (Remedy Floor 1, 4 — the terminal-success path must be preserved). Red-prove separately: (a) skip the per-attempt write → a test asserting `attempts == 2` after two failures reds; (b) omit the `next_attempt_at` advance → a test asserting the second claim occurs no earlier than `backoff_for(1)` reds; (c) write `status='in_flight'` instead of `'pending'` → the re-claim test reds. Fail loudly: if the post-attempt write itself fails, log at ERROR with the delivery id and let the reaper handle the row — do not silently continue the loop. Boundary/tie: at `attempts == MAX_ATTEMPTS - 1` the row is still re-queued, at `MAX_ATTEMPTS` it is terminal — state which comparison holds; two deliveries scheduled for the identical `next_attempt_at` must both eventually be claimed, not one.

### Major: 4xx responses are retried although the documentation says they are permanent
File: `app/webhooks/delivery.py` — `deliver`'s `if 200 <= response.status_code < 300` branch; `docs/webhooks.md` — "a 4xx is permanent and we stop immediately"
What is wrong: every non-2xx status takes the same retry path, so a 400, 403 or 410 is retried the full `MAX_ATTEMPTS` (R29/R49 — the doc states a control the implementation does not have).
What breaks in production: a customer who deletes an endpoint route or returns 401 receives five copies of every event instead of one, multiplying our egress and their alerting, and the delivery is finalized 30 seconds late for no reason.
Fix: branch explicitly — 2xx → `delivered`; 408, 429 and 5xx → retryable; all other 4xx → `failed_permanent` immediately with the status recorded. Allow side: a 500 must still be retried and a 429 must still be retried (with `Retry-After` honoured if present) — assert both, so a fix that makes every non-2xx permanent is caught (Remedy Floor 1). Red-prove separately: (a) merge 4xx back into the retry path → the "404 finishes after one attempt" test reds; (b) classify 429 as permanent → the "429 is retried" test reds; (c) classify 500 as permanent → the "500 is retried" test reds. Fail loudly: an unclassifiable status (a 1xx or 3xx arriving with redirects disabled) must be recorded as retryable with the raw status in `response_body`, never silently treated as success. ### Major: `backoff_for` has no jitter although the documentation promises it

### Major: webhook enqueue is fire-and-forget outside the event transaction and its failure is swallowed
