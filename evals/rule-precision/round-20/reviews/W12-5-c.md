### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, and `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` computes the HMAC over `json.dumps(payload, sort_keys=True)` while `send_once()` transmits the body via `client.post(..., json=delivery.payload)`, which lets httpx do its own encoding (different key order, different separators), so the digest in `X-Acme-Signature` is a MAC of a byte string the receiver never sees.
What breaks in production: every customer who follows `docs/webhooks.md` and computes HMAC-SHA256 over the raw request body gets a mismatch, so 100% of deliveries are rejected as forgeries by every correctly-implemented receiver while our side records them as `delivered`.
Fix: canonicalize once and send exactly what was signed — in `send_once`, build `body = serialize(delivery.payload).encode()`, change `sign()` to take those bytes (`sign(secret: str, body: bytes)`), and post with `content=body` plus an explicit `Content-Type: application/json` header instead of `json=`. Pair the deny side with the allow side: add a round-trip test that runs the real `send_once` through `httpx.MockTransport`, takes `request.content` verbatim, and recomputes `hmac.new(secret, request.content, sha256)` the way the doc tells customers to — that assertion must PASS, and it is the case the fix exists to keep working. Red-prove each clause separately by execution: (a) revert `content=body` to `json=payload` and confirm the round-trip test reds on digest mismatch; (b) drop `sort_keys=True` from `serialize` and confirm a two-key-payload test reds; (c) mutate one payload byte after signing and confirm it reds — three mutations, three distinct reddened assertions. Fail loudly when the check cannot run: wrap `serialize()` and route a `TypeError` from a non-JSON-serializable payload to a terminal `failed_permanent` with the exception text in `response_body`, never to a silent skip that leaves the row `in_flight`. Preserve the behaviour the current code gets right — the wire document stays the same JSON object with the same `Content-Type`; the change is only which byte string is authoritative. Name the boundary: an empty payload signs as the two bytes `{}` (not the empty string), and a payload whose serialization is byte-identical to another's is a legitimate tie that must produce the same digest.

### Critical: the timestamp header is not covered by the signature, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign()`, line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "stops a captured request from being replayed", but `sign()` MACs the payload alone, so `X-Acme-Timestamp` is unauthenticated attacker-controlled data.
What breaks in production: anyone who captures one delivery can replay it forever by rewriting the timestamp header to `now`, and every receiver that implemented the documented five-minute window believes it is protected while it is not (R49: the claim is stronger than the implementation, and the control other parties skipped because they trusted it is replay defence).
Fix: sign the timestamp with the body — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and update `verify()` to take the timestamp explicitly (`verify(secret, timestamp, body, signature)`) so a caller physically cannot verify without supplying the value being bound. Pair deny with allow: assert both that a request signed at T verifies at T (must succeed) and that the same request with the timestamp rewritten to T+1 fails. Red-prove by execution, one mutation per clause: remove the `f"{timestamp}."` prefix and confirm the tamper test reds; keep the prefix but compare with `!=` inverted and confirm the accept test reds. Fail loudly: a non-numeric or absent timestamp must raise/return False with a named reason, never be coerced to 0 and silently pass a skew check. Do not fix this by deleting the five-minute claim from the doc — the window is the feature; make the code able to support it. Name the boundary: a timestamp exactly 300 seconds old is REJECTED (`age > 300` accepts, `age >= 300` rejects — pick and state it), and two deliveries sharing one second are independent, each verified on its own digest.

### Critical: signature comparison in `verify()` is not constant time
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: an HMAC digest is compared with Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: this is the reference verifier we ship and document, so any internal service or customer sample built on it leaks the correct digest byte-by-byte to a remote attacker who can time responses, letting them forge a valid `X-Acme-Signature` without the secret.
Fix: `return hmac.compare_digest(expected, signature)` — and take both operands as `str` of equal expected length so the comparison is over the full `sha256=<64 hex>` form. Pair deny with allow: keep `test_verify_accepts_signature_produced_by_sign` green (the valid signature must still authenticate) alongside the wrong-secret rejection. Red-prove by execution: replace `compare_digest` with `==` and confirm a test that asserts `verify.__code__.co_names` contains `compare_digest`, or a lint gate on `==` over signature-shaped names, goes red — a behavioural test cannot see this, so the check must be structural and must itself be shown failing. Fail loudly: a `signature` argument that is `None` or not a `str` must raise a named `TypeError` rather than returning `False`, so "could not compare" is never spelled the same as "did not match". Preserve the existing signature of `verify()` for callers apart from the added timestamp parameter. Boundary: `compare_digest` on unequal-length inputs still returns `False` without leaking length beyond what the caller already knows; state that a truncated header is a rejection, not an error.

### Critical: signing secrets are generated with the non-cryptographic `random` module
File: `app/webhooks/signing.py` — `new_signing_secret()`, line `random.choice(_ALPHABET) for _ in range(SECRET_BYTES)`
What is wrong: `random` is a Mersenne Twister seeded from process state, not a CSPRNG, and its internal state is recoverable from a modest run of outputs.
What breaks in production: an attacker who registers a few endpoints of their own recovers the generator state and predicts the signing secret issued to every other organization created by the same worker process, which lets them forge `invoice.paid` events into other tenants' systems — the exact thing the whole signing scheme exists to prevent.
Fix: use `secrets.choice(_ALPHABET)` (or better, `SECRET_PREFIX + secrets.token_urlsafe(32)`) and drop the `random` import so the weak primitive cannot be reached from this module at all; also rename `SECRET_BYTES` to `SECRET_CHARS` since it counts alphabet characters, not bytes. Pair deny with allow: the allow-side case that must keep passing is that a freshly generated secret is accepted end-to-end by `sign`/`verify` and still carries the `whsec_` prefix the docs promise. Red-prove by execution, per clause: (a) swap `secrets.choice` back to `random.choice` and confirm a source-level gate (`rg -n '\brandom\.' app/webhooks/` in a test or CI check) reds; (b) shorten the length by one and confirm the length test reds; (c) generate 10,000 secrets and assert zero collisions — then mutate the generator to draw from a 2-character alphabet and confirm that test reds (the current length-only test would stay green through every one of these). Fail loudly: if `secrets` raises (no entropy source), let it propagate — endpoint creation must fail with a 5xx rather than fall back to `random`. Do not remove the prefix/length assertions that make the secret recognizable to customers. Boundary: the returned string is exactly `len(SECRET_PREFIX) + 32` characters; two endpoints created in the same millisecond must produce different secrets, and that is what the collision test pins.

### Critical: `list_deliveries` has no organization scoping
File: `app/api/routes/settings.py` — `list_deliveries()`, filter `WebhookDelivery.endpoint_id == endpoint_id`
What is wrong: the route filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike the three sibling handlers in the same file.
What breaks in production: any authenticated user can enumerate integer endpoint ids and read another tenant's delivery history — event types, event ids, timestamps and upstream response codes — a cross-tenant data breach through a route the doc explicitly describes as scoped ("deliveries for an endpoint belonging to your organization").
Fix: join and scope in the query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. Pair deny with allow: two tests, not one — the owning user still receives their rows (the allow case), and a user from another org receives 404 with an empty body. Red-prove each clause by execution: delete the `org_id` predicate and confirm the cross-tenant test reds; delete the `endpoint_id` predicate and confirm the owning-user test reds on row count. Assert the mutation, not just the status (RT8): the cross-tenant test must assert the response list is empty as well as the 404. Fail loudly: if `endpoint_id` does not parse or the join errors, return 4xx/5xx — never fall back to an unscoped query. Boundary: an endpoint that exists but is soft-inactive still belongs to its org and remains readable by that org; a delivery whose endpoint row was cascade-deleted is unreachable by anyone. Cross-cutting: `get_profile`, `list_api_keys` and `list_webhook_endpoints` in this same file all scope on `user.org_id` — this handler is the single missed site of that pattern (R3).

### Critical: the signing secret is returned on the list route, contradicting the documented write-once contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, key `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints()`
What is wrong: `to_dict()` is shared by the create and list handlers, so the secret intended to appear exactly once at creation is emitted on every `GET /v1/settings/webhook-endpoints`, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: live key material is served on a cacheable read route and lands in response logs, proxies and browser-accessible client state, so any org member or log reader with the weakest read scope can forge signed events, and customers who relied on the documented non-readback property when choosing not to rotate are wrong (R49).
Fix: remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the one call site that is allowed to disclose it; add a separate `POST /webhook-endpoints/{id}/rotate-secret` if readback is genuinely needed. Codebase awareness — the correct pattern is already in this diff's own file: `list_api_keys` returns `{"id", "prefix", "created_at"}` and never the key, so this is that convention's missed site (R1/R3). Pair deny with allow: the create-route test must still assert the secret IS present in the 201 body (otherwise a fix that strips it everywhere breaks the only way a customer can ever obtain it), and the list-route test asserts `"signing_secret" not in body[0]`. Red-prove by execution, separately: put the key back into `to_dict()` and confirm the list test reds; remove the explicit merge in the create handler and confirm the create test reds. Fail loudly: no fallback that re-adds the field when it is missing. Boundary: an endpoint created and listed in the same request cycle still hides the secret on the list path; the tie case — two endpoints in one org — must show the field absent from every element, not just the first.

### Critical: the migration's status CHECK constraint omits the status the code actually writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the application writes `failed_permanent` (also declared in `app/webhooks/models.py::STATUSES`) but the database permits only `failed`, so the terminal write violates the constraint (R40: the DB is the strict consumer and the producer's enum spelling diverges).
What breaks in production: every delivery that exhausts its attempts raises `IntegrityError` inside `_finish`, the exception escapes `deliver` (which catches only `httpx.HTTPError`), and the row is left in `in_flight` forever — so permanently failed deliveries are simultaneously invisible to the operator and never retried.
Fix: change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the constraint from `models.STATUSES` in a test rather than restating it (`assert set(STATUSES) == parsed_check_values`), so the two spellings cannot drift again. Pair deny with allow: a test that inserts one row per member of `STATUSES` and asserts all four succeed (the allow side — a fix that tightens the CHECK to a single value would otherwise satisfy every other clause), plus one asserting `'bogus'` is rejected. Red-prove by execution, one mutation per clause: drop `failed_permanent` from `STATUSES` and confirm the parity test reds; drop it from the SQL and confirm the insert test reds on `IntegrityError`. Fail loudly: if the migration file cannot be parsed by the parity test, the test must fail with "could not read CHECK constraint", not skip. Do not fix this by making `_finish` write `failed` — that erases the distinction between transient and permanent failure that `MAX_ATTEMPTS` exists to record. Boundary: state which status a row exhausting attempt number exactly `MAX_ATTEMPTS` receives (it is `failed_permanent`, on attempt 5, not 6).

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint, all carrying the same `event_id`, but the index permits only one row per `event_id` across the entire table.
What breaks in production: any organization with two or more active endpoints gets a unique-violation on the batch insert, the dispatcher's blanket `except Exception` swallows it as a warning, and the event is delivered to nobody — the failure mode is total, silent, and worse for the customers with the most integrations.
Fix: make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is what the at-least-once/dedupe contract in `docs/webhooks.md` actually needs, since dedupe is per receiver. Pair deny with allow: an integration test that enqueues one event for an org with two active endpoints and asserts TWO rows are created (the allow case, currently impossible), alongside one asserting a second enqueue of the SAME event to the SAME endpoint is rejected/ignored. Red-prove each by execution: revert the index to `(event_id)` and confirm the two-endpoint test reds with `UniqueViolation`; drop the index entirely and confirm the duplicate-enqueue test reds on row count. Fail loudly: change `session.add_all(rows)` so an `IntegrityError` is caught narrowly and re-raised after logging the endpoint ids, rather than reaching the dispatcher's catch-all. Do not fix by removing uniqueness — the constraint is what makes redelivery idempotent. Boundary: an endpoint that matches an event twice via overlapping `event_types` entries must still produce exactly one row; the tie is resolved by `ON CONFLICT (endpoint_id, event_id) DO NOTHING`.

### Critical: `time.sleep` inside an async coroutine blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver()`, line `time.sleep(delay)`
What is wrong: a synchronous sleep of up to 16 seconds runs inside `async def deliver`, which is scheduled by `asyncio.gather` over a batch of up to `BATCH_SIZE` deliveries.
What breaks in production: one slow endpoint freezes every concurrent delivery, the batch degrades from parallel to strictly serial with worst-case 100 × 30s of blocked loop time, the Redis lock's 60-second TTL expires mid-batch so a second worker starts re-sending the same rows, and no heartbeat or health check on that loop can respond.
Fix: stop sleeping in-process at all — on a retryable failure, persist the schedule instead: `_finish`-style write of `status="pending"`, `attempts=attempt`, `next_attempt_at=datetime.now(timezone.utc) + backoff_for(attempt)` and return, letting `_claim_batch` pick the row up when it is due (this is what the `next_attempt_at` column and `backoff_for` were added for and are currently dead weight). Pair deny with allow: assert both that a failing delivery is rescheduled with a strictly later `next_attempt_at` and still `pending` (the allow side — retries must keep happening), and that a delivery at `attempts == MAX_ATTEMPTS` is written `failed_permanent` and never re-claimed. Red-prove each clause by execution: (a) remove the `next_attempt_at` bump and confirm a test asserting the row is not immediately re-claimable reds; (b) remove the `MAX_ATTEMPTS` branch and confirm the terminal test reds (bound the loop in the test so the mutation reds rather than hanging); (c) reintroduce `time.sleep` and confirm a test asserting `deliver` returns within N ms under a failing transport reds. Fail loudly: if the reschedule write itself fails, log at error and leave the row claimable by the stuck-row reaper rather than returning as if the retry were queued. Preserve the retry semantics customers are promised (5 attempts, ~2/4/8/16s) — this changes where the wait happens, not that it happens. Boundary: a row whose `next_attempt_at` is exactly `now` IS claimed (`<=` in `_claim_batch`, already correct); two rows with identical `next_attempt_at` tie and must both be claimable in one batch.

### Critical: customer-supplied delivery URLs are unvalidated destinations and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, line `if not parsed.scheme.startswith("http") or not parsed.netloc:`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http://` (and any scheme merely beginning with those four characters, e.g. `httpfoo://`) despite `docs/webhooks.md` stating "Only `https://` URLs are accepted", and nothing anywhere rejects loopback, link-local, or private-range hosts before the worker POSTs to them with redirects enabled.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:8080/admin`, and our worker — inside the VPC, with no egress restriction visible in this change — POSTs event payloads there and follows any redirect to a second internal target, giving server-side request forgery plus plaintext exfiltration of invoice data (R49: the doc declares an enforceable boundary that the code does not implement).
Fix: replace the hand-rolled check with an explicit allow-list validation — require `parsed.scheme == "https"` (exact equality, not `startswith`), reject when `parsed.hostname` resolves to any address in a private/loopback/link-local/unique-local range, reject non-default ports outside `{443}` unless configured, and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a delivery failure instead of a second unvalidated request. Codebase awareness: `pydantic` is already imported in this file — declare `url: HttpUrl` on `EndpointIn` so the parse is schema-level rather than in the handler body (RS3), keeping the explicit scheme/IP checks on top of it. Pair deny with allow: `https://hooks.example.com/acme` must still be accepted and still be delivered to (that case is exactly what `follow_redirects=False` risks breaking if the customer's host redirects — assert the 3xx is recorded as a retryable failure with its `Location` in `response_body`, not silently dropped). Red-prove each clause by execution: (a) restore `startswith` and confirm the `http://` rejection test reds; (b) remove the private-range check and confirm the `http://169.254.169.254` test reds; (c) set `follow_redirects=True` and confirm the redirect test reds. Fail loudly: when DNS resolution fails during validation, reject the registration with 422 naming "could not resolve host" — an unresolvable name must not be treated as "not private, therefore fine", and re-check at delivery time since DNS can be rebound between registration and use (R51-shaped: the decision must bind to the resolved address the request actually connects to, not to the name checked earlier). Boundary: an address exactly at a range edge (`10.255.255.255`, `172.31.255.255`) is private and rejected; two endpoints resolving to the same address are each checked independently.

### Major: ORM instances are used after their session scope has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returns `rows` from inside `with session_scope()`, and `deliver()` reads `endpoint.signing_secret` / `delivery.payload` / `delivery.attempts` outside the scope
What is wrong: both helpers hand back SQLAlchemy entities whose session has already committed and closed, and the callers then read attributes that a default `expire_on_commit=True` session marks expired.
What breaks in production: the first attribute access raises `DetachedInstanceError` and no delivery is ever sent, with the claimed rows already flipped to `in_flight` and therefore unrecoverable — unless `session_scope` sets `expire_on_commit=False`, which this change does not show, so please confirm.
Fix: stop passing entities across the boundary — have `_claim_batch` return plain value objects (`[(row.id, row.endpoint_id, row.attempts, row.payload) for row in rows]`) materialized inside the scope, and have `deliver` read the endpoint's `url`/`signing_secret` into locals inside its own `with session_scope()` block before the HTTP call. Pair deny with allow: a test that runs `deliver` against a row created through the real session and asserts the POST happened (the allow side — a fix that simply stops touching the attributes would pass a detachment test while delivering nothing). Red-prove by execution: return the entities again and confirm the test reds with `DetachedInstanceError`; and separately, mutate the extracted `payload` local and confirm the posted body changes, proving the value actually flows. Fail loudly: if `session.get(WebhookEndpoint, ...)` returns `None` (endpoint deleted between claim and delivery), write the delivery `failed_permanent` with `detail="endpoint deleted"` instead of raising `AttributeError` on `None.signing_secret`. Boundary: a delivery claimed in the same transaction as its endpoint's deactivation is still sent once; state that `active=False` is honoured at claim time, not mid-flight.

### Major: the Redis lock is a non-atomic check-then-set and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by `set` followed by a separate `expire` is three round trips with no atomicity and no owner token, and the `finally` block deletes `LOCK_KEY` regardless of who currently holds it.
What breaks in production: two workers starting within the same millisecond both see an empty key and both proceed; worse, once a batch outlives the 60-second TTL (trivially, given the in-process retry sleeps), worker A's `finally` deletes worker B's freshly acquired lock, so the exclusion the design depends on silently stops existing under exactly the load it was built for.
Fix: acquire with a single atomic call carrying an owner token and a TTL — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock; renew the TTL periodically while a batch is in flight. Pair deny with allow: assert that a second worker is refused while the first holds the lock (deny), AND that the second worker DOES acquire it after the first releases (allow — a fix that never releases satisfies every exclusion assertion). Red-prove each clause by execution: (a) replace `nx=True` with an unconditional `set` and confirm the concurrent-acquire test reds; (b) replace the compare-and-delete with a plain `delete` and confirm the "worker A must not free worker B's lock" test reds; (c) drop `ex=60` and confirm a crash-recovery test (lock still held after the owner dies) reds. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise rather than return `False` forever (a silent permanent `False` is an invisible full outage of webhook delivery) — log at error and let the supervisor restart. Do not remove the lock in favour of DB-only claiming without also adding `SELECT ... FOR UPDATE SKIP LOCKED` in `_claim_batch`, which today has its own read-then-write race (R5). Boundary: a TTL expiring at the exact moment the owner finishes must not delete a successor's lock — the token comparison is what decides the tie.

### Major: `in_flight` is a non-terminal state with no reaper and no timeout
File: `app/webhooks/delivery.py` — `_claim_batch()` sets `row.status = "in_flight"`; nothing anywhere transitions it back
What is wrong: rows leave `in_flight` only through `_finish` on the success or exhausted paths inside `deliver`, so any worker crash, deploy, `IntegrityError`, or non-`httpx.HTTPError` exception (the `except` clause catches only `httpx.HTTPError`) strands the row permanently (R38 mode 1).
What breaks in production: stranded deliveries are never retried and never reported as failed, so a customer silently misses `invoice.paid` events with the delivery list showing them as apparently still in progress forever.
Fix: add a claim deadline and a reaper — record `claimed_at` when a row is set `in_flight`, and at the top of each worker cycle reset rows with `status='in_flight' AND claimed_at < now() - interval '5 minutes'` back to `pending` with `next_attempt_at = now()` and `attempts` unchanged; broaden `deliver`'s handler to `except Exception as exc` so a serialization or DB error is written terminal with its text rather than escaping. Pair deny with allow: assert a genuinely in-flight row younger than the deadline is NOT reclaimed (the allow side — a reaper that resets everything produces duplicate deliveries), and that one older than the deadline IS. Red-prove each clause by execution: (a) remove the age predicate and confirm the "young row untouched" test reds; (b) remove the reaper entirely and confirm the crash-recovery test reds; (c) narrow the exception handler back to `httpx.HTTPError`, raise a `TypeError` from the transport, and confirm the "row reaches a terminal state" test reds. Fail loudly: a row reset by the reaper must be logged at warning with its id and attempt count, so "reclaimed after crash" is distinguishable from "never claimed". Do not fix by dropping the `in_flight` state — it is what prevents double-claiming. Boundary: a row whose `claimed_at` is exactly at the deadline is reclaimed (`<=`), and `attempts` is not incremented by reclaiming, so a crash does not consume one of the customer's five attempts.

### Major: one failing delivery kills the worker loop
File: `app/webhooks/delivery.py` — `run_worker()`, line `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `asyncio.gather` without `return_exceptions=True` propagates the first exception, and `run_worker` has no `except` around the loop body, so any error escaping `deliver` terminates the worker.
What breaks in production: a single malformed payload or DB error stops all webhook delivery process-wide, and every row in the claimed batch is left `in_flight` (see the previous finding) rather than retried.
Fix: `results = await asyncio.gather(*[deliver(client, d) for d in batch], return_exceptions=True)` followed by an explicit loop that logs each `Exception` result at error with its delivery id and marks that row for reclaim; wrap the whole cycle body in `try/except Exception` so the loop continues to the next iteration. Pair deny with allow: assert a batch of three where one raises still delivers the other two (allow), and that the raising one is recorded as failed rather than silently forgotten (deny). Red-prove each separately by execution: (a) remove `return_exceptions=True` and confirm the "other two still delivered" test reds; (b) remove the result-inspection loop and confirm the "failure is recorded" test reds. Fail loudly: never `except Exception: pass` — every swallowed result must produce a log line naming the delivery id, so "nothing failed" and "we stopped looking" are distinguishable. Preserve the crash-on-unrecoverable behaviour for startup errors (a bad Redis URL should still exit) — the broad catch belongs around the per-cycle body only. Boundary: an empty batch is not an error and must not be logged as one; the tie of all-N-failing must still complete the cycle and release the lock.

### Major: naive and aware datetimes are mixed, and the migration's column types contradict the model's
File: `app/webhooks/delivery.py` — `enqueue_for_event()`, `next_attempt_at=datetime.utcnow()`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP` columns vs `app/webhooks/models.py` — `DateTime(timezone=True)`
What is wrong: `datetime.utcnow()` returns a naive value that is compared in `_claim_batch` against `datetime.now(timezone.utc)`, and the migration declares `TIMESTAMP` (without time zone) for `created_at`, `next_attempt_at` and `updated_at` on both tables while the models declare `timezone=True`.
What breaks in production: on a database or session whose time zone is not UTC the naive value is interpreted as local time, so deliveries become due hours early or late (or, where the naive/aware comparison reaches Python, raise `TypeError: can't compare offset-naive and offset-aware datetimes`), and the retry schedule silently drifts by the UTC offset.

### Major: retry policy contradicts the documented policy in two ways
