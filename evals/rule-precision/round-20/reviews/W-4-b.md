### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice`, Python's Mersenne Twister, which is seeded from a predictable source and whose internal state is recoverable from a modest run of its output.
What breaks in production: An attacker who obtains one org's secret (or enough generator output) can predict the secrets issued to other orgs and forge signed webhook deliveries that every customer's verifier accepts as genuine.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and drop the `random`/`string`/`_ALPHABET` imports; rename `SECRET_BYTES` to match its new unit (it is currently a character count, not a byte count — 32 chars, and `token_urlsafe(32)` yields 43). Deny side: add a test asserting `new_signing_secret()` returns a distinct value across 1000 calls and that `random.seed(0)` before the call does **not** make two processes agree. Allow side that must still succeed: `test_new_signing_secret_has_prefix_and_length` must stay green — update its length assertion to the token's actual length rather than deleting it, and keep the `whsec_` prefix so existing stored secrets remain parseable. Red-prove each clause separately by execution: (i) revert to `random.choice` and observe the seeded-determinism test go red; (ii) drop the prefix and observe the prefix assertion go red; (iii) shorten the token to 8 and observe the length assertion go red. Fail loudly: if `secrets` raises (no OS entropy source), let it propagate — the endpoint must 500 rather than fall back to `random`, so "could not generate a secret" is never spelled the same as "generated one". Boundary and tie: minimum accepted secret length is defined once as `SECRET_BYTES`; two orgs generating in the same microsecond must still receive different secrets, which the distinctness test pins.

### Critical: signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: `==` on `str` short-circuits at the first differing byte, so comparison time leaks a prefix-match oracle (RS1).
What breaks in production: This is the reference verifier we ship and that `docs/webhooks.md` tells customers to mirror; an attacker with repeated request timing can recover a valid signature byte by byte and replay forged events into any consumer that adopts it.
Fix: `return hmac.compare_digest(expected, signature)` (`hmac` is already imported). Deny side: a test that a one-character-mutated signature is rejected. Allow side that must still succeed: `test_verify_accepts_signature_produced_by_sign` stays green — a genuine signature must still return `True`, and `compare_digest` on unequal-length inputs must return `False` rather than raise, so coerce both to `str` before the call. Red-prove separately: (i) restore `==` and confirm a grep-based lint or an AST check over `signing.py` reds; (ii) invert the return and confirm the accept test reds; (iii) feed a `None` signature and confirm the boundary handler reds rather than throwing `TypeError` out of the verifier. Fail loudly: a signature header that is absent or not `sha256=<64 hex>` must return `False` from an explicit shape check, not reach `compare_digest` at all, and that rejection must be distinguishable in logs from "compared and differed". Do not fix by loosening: the fix must not widen `verify` to accept an unprefixed digest. Boundary and tie: exactly 64 hex characters after `sha256=` is accepted, 63 and 65 are rejected; two payloads that serialize identically legitimately produce the same signature and both must verify.

### Critical: the signature does not cover the timestamp, so signed requests replay forever
File: `app/webhooks/signing.py` — `sign` (`mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`) and `verify`
What is wrong: The MAC input is the payload alone; the returned timestamp is transmitted in `X-Acme-Timestamp` but is not authenticated, and `verify` recomputes with a fresh `time.time()` and never consults the caller's timestamp — directly contradicting `docs/webhooks.md`, which states the signature is HMAC over `"{timestamp}.{raw_request_body}"` and that the five-minute window "is what stops a captured request from being replayed" (R29, R49).
What breaks in production: A captured delivery can be replayed indefinitely with any timestamp the attacker likes and still verify, so the anti-replay control the docs sell to customers does not exist; downstream consumers that treat a valid signature as proof of freshness will re-apply the same `invoice.paid` event repeatedly.
Fix: Change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact bytes that will be transmitted (see the serialization finding below), and change `verify(secret, body, timestamp, signature)` to take the received timestamp, recompute over `f"{timestamp}.{body}"`, and reject when `abs(int(time.time()) - int(timestamp)) > 300`. Deny side: tests that a signature valid at T fails at T+301, and that swapping the timestamp header while keeping the signature fails. Allow side that must still succeed: a signature presented at T+299 and one presented at exactly T+300 both verify, and a delivery re-sent by our own retry loop (a fresh `sign` call) verifies at its own new timestamp — the retry path must not be broken by the tolerance. Red-prove separately: (i) drop the timestamp from the MAC input and watch the header-swap test red; (ii) remove the window check and watch the T+301 test red; (iii) make the window comparison one-sided and watch a T-301 (clock-skewed-future) case red. Fail loudly: a `X-Acme-Timestamp` that is missing or not an integer must raise a named `SignatureError("missing/malformed timestamp")` — never be coerced to `0`, which would silently place every request outside the window and read as an ordinary rejection. Do not fix by deleting: the currently-returned timestamp header must stay on the wire, since consumers already key on it. Boundary and tie: `300` seconds is inclusive on both sides; two deliveries signed in the same second are independent and both verify.

### Critical: the signed bytes are not the transmitted bytes
File: `app/webhooks/delivery.py` — `send_once` (`sign(endpoint.signing_secret, delivery.payload)` then `client.post(..., json=delivery.payload)`)
What is wrong: The MAC is computed over `signing.serialize()` (`json.dumps(payload, sort_keys=True)`, default `", "`/`": "` separators) while httpx independently serializes the body with compact separators and insertion order, so the receiver HMAC-ing the raw body per `docs/webhooks.md` computes a different digest (R40 — same team owns both sides, and the test mocks the transport so the divergence never round-trips).
What breaks in production: Every outbound delivery fails verification at every correctly-implemented customer endpoint, and because a non-2xx is retried, each undeliverable event burns all 5 attempts against the customer's rate limits before landing in `failed_permanent`.
Fix: Serialize once and send the bytes you signed — `body = serialize(delivery.payload).encode()`, then `sign` over `body` and `client.post(endpoint.url, content=body, headers=headers)` with the explicit `Content-Type: application/json` already present; export `serialize` as the single definition of the wire form and have `verify` take the raw body rather than a dict, since the change already contains that helper and `send_once` currently bypasses it. Deny side: a round-trip test that feeds the *actual* captured request bytes from `MockTransport` through the *actual* `signing.verify` and asserts `True`, plus a mutation of one byte of the captured body asserting `False`. Allow side that must still succeed: `test_send_once_posts_the_signed_payload` stays green including its `json.loads(captured["body"])["type"] == "invoice.paid"` assertion — the body must remain valid JSON with the same fields, only its byte-level form is pinned. Red-prove separately: (i) restore `json=` and watch the round-trip test red; (ii) change `sort_keys` to `False` and watch it red on a two-key payload whose insertion order differs from sorted order; (iii) change the separators and watch it red. Fail loudly: a payload that is not JSON-serializable must raise before any HTTP call, with the delivery marked `failed_permanent` and the exception text recorded — never posted with an empty body. Boundary and tie: two payloads differing only in key order serialize to the same bytes and therefore to the same signature, which is the intended tie.

### Critical: `list_deliveries` has no organization scope — cross-tenant read
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters on `endpoint_id` only, while every sibling handler in the same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) filters on `user.org_id`; the pattern was propagated to two of the three new routes and missed on the third (R3, security-relevant).
What breaks in production: Any authenticated user can enumerate `endpoint_id` and read another organization's delivery rows, whose `to_dict()` exposes `event_id`, `event_type`, `status` and attempt history for that org's billing events.
Fix: Join to `WebhookEndpoint` and filter `WebhookEndpoint.org_id == user.org_id`, returning 404 (not 403) when the endpoint exists but belongs to another org so the endpoint id space is not enumerable. Deny side: a test asserting org B's user gets 404 for org A's endpoint id **and** that the response body contains no delivery rows (RT8 — assert the absence of the data, not only the status). Allow side that must still succeed: org A's own user still receives their rows, ordered newest first, for an endpoint with zero deliveries returning `[]` rather than 404. Red-prove separately: (i) delete the org filter and watch the cross-tenant test red; (ii) change 404 to 403 and watch the enumerability assertion red; (iii) delete the join and watch a test that a non-existent endpoint id returns 404 red. Fail loudly: when `user.org_id` is `None` the handler must raise 401 rather than filter on `NULL`, which silently matches nothing and reads as "no deliveries". Do not fix by deleting the endpoint: the delivery-inspection capability documented in `docs/webhooks.md` must survive. Boundary and tie: an endpoint whose org was reassigned is judged by its current `org_id`; two endpoints with the same id cannot exist, so there is no tie.

### Critical: `WebhookEndpoint.to_dict()` returns the signing secret on every read
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: The secret is included unconditionally, so `GET /v1/settings/webhook-endpoints` returns every endpoint's signing secret on every call — while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (RS4, and R49: the doc claims a containment property the code does not implement).
What breaks in production: The shared secret that authenticates all webhook traffic is served to every request with a valid session, replicated into browser caches, proxy logs and API-client history, so any read-only token compromise yields forgery capability for all of an org's endpoints.
Fix: Remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at the creation site only; add a `POST /webhook-endpoints/{id}/rotate-secret` route as the one other place it is emitted. Deny side: a test asserting `"signing_secret" not in` any element of the list response and not in the deliveries response. Allow side that must still succeed: the 201 creation response must still carry the secret exactly once — the whole feature is unusable without it — and a test must assert that field is present and prefixed `whsec_`. Red-prove separately: (i) re-add the key to `to_dict` and watch the list-response test red; (ii) delete the creation-site merge and watch the creation test red; (iii) return an empty string at the creation site and watch the prefix assertion red. Fail loudly: any future serializer for this model must fail the build rather than default to including new columns — pin the exact key set of `to_dict()` with an equality assertion, so an added secret-bearing column reds instead of leaking. Boundary and tie: exactly one response body in the whole API may contain the secret; a rotation returns the new secret and never the old.

### Critical: the migration's status CHECK constraint does not admit the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: The schema allows `'failed'` while both the model constant and the only writer use `'failed_permanent'`.
What breaks in production: Every delivery that exhausts its retries raises a CHECK violation inside `_finish`, so the row never leaves `in_flight`, the transaction aborts, and the worker's `deliver` coroutine raises out of `asyncio.gather` — permanently failing deliveries wedge the queue instead of terminating.
Fix: Change the constraint to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and derive it from `models.STATUSES` in a test rather than restating the tuple in a third place (R2 — the literal set now exists in the migration, in `STATUSES`, and inline in `_finish`/`_claim_batch`). Deny side: a test that inserting `status = 'failed'` is rejected by the database. Allow side that must still succeed: an insert of each member of `models.STATUSES` succeeds, and an existing `pending` row can be updated to `failed_permanent` — pin this against a real database, not a mock, since a mocked session validates no constraint. Red-prove separately: (i) drop one member from `STATUSES` and watch the parity test red; (ii) drop one member from the SQL and watch it red; (iii) write an unlisted status through `_finish` and watch the insert test red. Fail loudly: if the parity test cannot reach a database it must error with "no database — constraint parity unverified", never skip silently and report green. Boundary and tie: `STATUSES` is the single source; the migration and every `status = "..."` literal must be generated from or asserted against it.

### Critical: the unique index on `event_id` allows only one endpoint per event
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: Uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint for the same `event_id`.
What breaks in production: An org with two or more active endpoints gets an `IntegrityError` on `session.add_all`, which the dispatcher's blanket `except Exception` downgrades to a `log.warning`, so **all** webhook deliveries for that event — including the first endpoint's — are silently dropped with no retry and no user-visible signal.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, and make `enqueue_for_event` insert with `ON CONFLICT (endpoint_id, event_id) DO NOTHING` so a redelivered event is idempotent rather than fatal. Deny side: a test that enqueueing the same `(endpoint_id, event_id)` twice leaves exactly one row and raises nothing. Allow side that must still succeed: an org with three active endpoints subscribed to `invoice.paid` produces exactly three rows for one event — assert the count, since a fix that merely widens the index without the conflict clause still passes a single-endpoint test. Red-prove separately: (i) restore the single-column index and watch the three-endpoint test red; (ii) remove `DO NOTHING` and watch the double-enqueue test red; (iii) return early from `enqueue_for_event` and watch the row-count assertion red. Fail loudly: `enqueue_for_event` must let a genuine `IntegrityError` propagate to the caller so the dispatcher can surface it, rather than being absorbed as a conflict. Do not fix by dropping the index: at-least-once delivery with consumer-side dedup on `event_id` (the documented contract) depends on our not enqueuing the same pair twice. Boundary and tie: the tie is exactly the `(endpoint_id, event_id)` pair — same event to different endpoints is not a conflict, same event to the same endpoint is.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: A synchronous sleep is executed inside an `async def` that is run under `asyncio.gather`, blocking the event loop rather than yielding.
What breaks in production: One failing endpoint stalls the entire loop for up to 30 seconds (2+4+8+16) per delivery, and because the batch is gathered, 100 deliveries retrying serialize into ~50 minutes of frozen event loop during which no other delivery, no lock refresh, and no HTTP response completes.
Fix: Replace the in-process retry loop with a reschedule — on a retryable failure, write `status='pending'`, `attempts=attempt`, `next_attempt_at = now + backoff_for(attempt)` and return, letting the worker's next poll pick the row up (the `next_attempt_at` column and its ordering in `_claim_batch` already exist for exactly this and are currently written only once, at enqueue). If an in-process retry is kept instead, it must be `await asyncio.sleep(delay)`. Deny side: a test that a delivery failing at attempt 1 leaves `status='pending'` with `next_attempt_at` at least 2 seconds in the future and is not retried within the same `deliver` call. Allow side that must still succeed: a delivery that succeeds on its first attempt still reaches `delivered` in one call with no sleep at all — assert wall-clock under 100 ms so a fix that sleeps unconditionally is caught. Red-prove separately: (i) restore `time.sleep` and watch a test that runs two `deliver` coroutines concurrently and asserts their completion order interleaves go red; (ii) drop the `next_attempt_at` write and watch the reschedule test red; (iii) set the backoff to zero and watch the future-timestamp assertion red. Fail loudly: a delivery whose row vanished between claim and finish must log a named `delivery %s disappeared` and count toward a metric, never be swallowed. Do not fix by deleting the retries: the documented "at most 5 attempts" behaviour and `MAX_ATTEMPTS` must survive the restructure. Boundary and tie: `attempt >= MAX_ATTEMPTS` terminates at exactly 5 attempts (5 does not sleep again); rows whose `next_attempt_at` equals `now` are eligible, as `<=` already implements.

### Critical: no SSRF guard on the customer-supplied delivery URL, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http")`) and `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check is that the scheme *starts with* `http` (so `httpfoo://` passes) with no restriction on the host, and the delivery client follows redirects, so even a host allowlist applied at registration would be bypassed at delivery time (RS3 — a boundary check that the interpreter downstream does not honour; R49 — `docs/webhooks.md` claims "Only `https://` URLs are accepted", which the code does not implement).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/` and our worker POSTs signed internal requests to cloud metadata and internal services, returning the response body into `response_body` where the customer reads it back.
Fix: Require `parsed.scheme == "https"` by equality (not `startswith`), reject URLs with credentials, a non-default port outside `{443}`, or a hostname that resolves to any address in a private/loopback/link-local/unique-local range; resolve once at registration and pin the resolved IP for the delivery connection so the check and the use refer to the same object; set `follow_redirects=False` and treat a 3xx as a permanent failure. Deny side: tests that `http://…`, `httpfoo://…`, `https://localhost/`, `https://169.254.169.254/`, `https://user:pw@host/` and a 302 to an internal host are each rejected — the redirect case asserting no request was issued to the redirect target, not merely that the delivery failed. Allow side that must still succeed: `https://hooks.example.com/acme` (the fixture URL in `docs/webhooks.md` and `tests/webhooks/test_delivery.py`) registers and delivers, and a public host on port 443 with a path and query string is accepted — a guard that rejects everything satisfies every other clause. Red-prove separately: (i) restore `startswith` and watch the `httpfoo://` test red; (ii) remove the private-range check and watch the metadata-address test red; (iii) restore `follow_redirects=True` and watch the redirect test red. Fail loudly: a hostname that fails to resolve at registration must return 422 naming "hostname does not resolve", and one that fails at delivery must mark the attempt failed with that reason — neither may fall through to an unchecked connection. Boundary and tie: the accepted set is exactly `https` on port 443 to a publicly-routable address; a host resolving to both a public and a private address is rejected, and the pinned address is the one connected to.

### Critical: the delivery test cannot detect the signature defect it appears to cover
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test asserts only that the signature header *starts with* `sha256=` and that the timestamp is digits; it never feeds `captured["body"]` back through `signing.verify`, so it passes identically whether the MAC covers the transmitted bytes or not (RT1 clause d — no assertion against an independently derived expected value; RT5 — the production verification primitive is absent from the call path).

Deny side: a companion test that mutates one byte of `captured["body"]` before verifying and asserts `False`. Red-prove separately: (i) revert `send_once` to `json=delivery.payload` while signing `serialize(...)` and watch the round-trip assertion red; (ii) drop the timestamp from the MAC and watch the header-swap variant red; (iii) return a constant signature from `sign` and watch the byte-mutation test red. Fail loudly: if `MockTransport` captures no request, the test must fail on a missing key rather than skip — assert `captured` is non-empty before dereferencing it. ### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish`
What is wrong: `_claim_batch` writes `in_flight` and commits, but the only transition out is `_finish`, which runs on the success and exhaustion paths inside `deliver`; a worker crash, a redeploy, a cancelled `gather`, or the CHECK-constraint failure above leaves the row in `in_flight` forever, and nothing in the diff ever moves a row back to `pending` (R38 mode 1 — no failure-exit and no bounded timeout).
What breaks in production: Every restart during a batch permanently orphans up to 100 deliveries, which no query will ever claim again and no operator surface reveals.
Fix: Add a `claimed_at TIMESTAMPTZ` column set at claim time, and have `_claim_batch` also reclaim rows whose `status='in_flight'` and `claimed_at < now() - interval '5 minutes'`, resetting them to `pending` with `attempts` unchanged. Deny side: a test that a row stuck in `in_flight` with `claimed_at` 6 minutes old is reclaimed on the next poll, asserting the row's status transitions and that `attempts` is not reset (a reclaim that zeroes attempts turns the 5-attempt cap into an infinite loop). Allow side that must still succeed: a row claimed 10 seconds ago by a live worker is **not** reclaimed — assert it is absent from the second worker's batch, since a reaper that reclaims everything satisfies the deny test and causes duplicate delivery. Red-prove separately: (i) remove the reclaim clause and watch the stale-row test red; (ii) remove the `claimed_at` age predicate and watch the live-row test red; (iii) reset `attempts` in the reclaim and watch the attempts-preserved assertion red. Fail loudly: a row that has been reclaimed more than `MAX_ATTEMPTS` times must be moved to `failed_permanent` with a named reason rather than cycling silently. Boundary and tie: a row at exactly 5 minutes is reclaimed; two workers reclaiming the same row simultaneously must be resolved by the conditional update below, and only one may win.

### Major: the dispatch lock is a non-atomic check-then-set and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by `set` is two round-trips with no atomicity, so two workers can both observe an empty key and both proceed; the `set` and `expire` are likewise separate, so a crash between them leaves a lock with no TTL; and the `finally` deletes the key by name without checking ownership, so a worker whose 60-second TTL expired mid-batch deletes the *successor's* lock.
What breaks in production: Two workers claim overlapping batches and deliver the same events twice, and — worse than duplication, which the docs permit — a crash between `set` and `expire` wedges dispatch permanently with no delivery at all.
Fix: `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token` is a per-worker `secrets.token_hex()`, and release with a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so only the owner can clear it; refresh the TTL while the batch is in flight. Deny side: a test that a second `_acquire_lock` with the key already held returns `False`, and that a release with the wrong token leaves the key intact. Allow side that must still succeed: after the holder releases, the next `_acquire_lock` returns `True` — a lock that is never released satisfies the deny test and stops dispatch entirely. Red-prove separately: (i) drop `nx=True` and watch the contention test red; (ii) drop `ex=60` and watch a TTL assertion red; (iii) replace the compare-and-delete with a plain `delete` and watch the wrong-token test red. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise a named error and the worker must back off without dispatching — an exception must not be caught into `return True`, which would fail open into concurrent dispatch. Boundary and tie: the lock TTL must exceed the maximum batch duration; two workers racing on `nx` — exactly one receives `True`.

### Major: `run_worker` releases the lock while deliveries are still running and crashes on a claim error
File: `app/webhooks/delivery.py` — `run_worker`
What is wrong: `asyncio.gather` without `return_exceptions=True` propagates the first exception out of the `try`, the `finally` then deletes the lock while the remaining delivery coroutines are still in flight, and `batch` is referenced after the `finally` where it is unbound if `_claim_batch` raised — an `UnboundLocalError` that kills the worker loop.
What breaks in production: A single malformed row raises out of one `deliver`, the lock is dropped mid-batch so another worker re-claims rows still being delivered, and the second failure mode terminates the only dispatch process with no supervision visible in the change.
Fix: Use `results = await asyncio.gather(*[...], return_exceptions=True)`, log each exception against its delivery id, initialise `batch: list = []` before the `try`, and wrap the loop body so an unexpected exception logs and continues rather than exiting. Deny side: a test that one `deliver` raising leaves the other deliveries in the batch completed and the worker still looping. Allow side that must still succeed: a fully successful batch still releases the lock and sleeps only when the batch was empty — assert a non-empty successful batch does *not* sleep, so a fix that swallows everything into a permanent sleep is caught. Red-prove separately: (i) remove `return_exceptions` and watch the one-raises test red; (ii) remove the `batch = []` initialisation, force `_claim_batch` to raise, and watch the loop-survives test red; (iii) remove the per-exception log and watch an assertion on the log record red. Fail loudly: an exception the loop continues past must be logged at `error` with the delivery id and increment a failure counter — "continued" must not be spelled the same as "succeeded". Boundary and tie: an empty batch sleeps `poll_interval`; a batch of exactly `BATCH_SIZE` polls again immediately, since a full batch implies more work is waiting.

### Major: ORM rows are used after the session that loaded them has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`) and `deliver` (reads `endpoint.url`, `endpoint.signing_secret` after the `with` block)
What is wrong: Both functions hand persistent instances out of the scope that owns them and then read attributes — `delivery.payload`, `delivery.id`, `delivery.attempts`, `endpoint.url` — outside it; under SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and the first read raises `DetachedInstanceError`.
What breaks in production: The worker cannot deliver anything at all — the first `send_once` raises on `endpoint.signing_secret` — and the failure surfaces only under a real session, which no test in this change uses. (If `session_scope` is configured with `expire_on_commit=False`, this is instead a staleness bug rather than a crash; that is the answer that would close it.)

### Major: a failed webhook enqueue is swallowed, breaking the documented at-least-once guarantee

## Cross-cutting verification

- **Organization scoping**: applied in `get_profile`, `list_api_keys`, `list_webhook_endpoints`, and in `enqueue_for_event`'s endpoint query; missing only in `list_deliveries` — reported above.
- **Timezone-aware `now`**: `models._now`, `_claim_batch` and `_finish` are aware; `enqueue_for_event`'s `datetime.utcnow()` is the only naive site — reported above. The migration is the mirror-image miss on the schema side.
- **Status literal set**: appears three times — `models.STATUSES`, the migration CHECK, and inline strings in `_claim_batch`/`_finish`; only the migration disagrees, but the triplication is what let it drift.
- **Secret exposure**: `WebhookEndpoint.to_dict` is the only serializer returning `signing_secret`; `WebhookDelivery.to_dict` correctly omits `payload` and `response_body`, so the two serializers in the same file follow opposite policies.
- **Timing-unsafe comparison**: `verify` is the only credential comparison in the change; no second site.
- **`follow_redirects=True`**: set once, on the only outbound client — but it is what defeats the registration-time URL check, so the two sites must be fixed together.

## Codebase awareness

- `app/webhooks/models.py::_now()` already exists in this change and is what `enqueue_for_event`'s `datetime.utcnow()` reimplements — evidence: both are in the diff, the former used by three call sites, the latter by one.
- `app/webhooks/signing.py::serialize()` already exists and defines the wire form; `send_once` bypasses it by passing `json=` to httpx — evidence: `sign()` calls `serialize(payload)` while `client.post(..., json=delivery.payload)` on the very next line does its own encoding.
- `app/webhooks/signing.py::verify()` already exists as the reference verifier customers are told to mirror; the `verify`/`sign` asymmetry on the timestamp is therefore a defect in shipped guidance, not only in internal code.
- `enqueue_for_event`'s per-endpoint filter (`if not endpoint.event_types or event_type in endpoint.event_types`) already implements the documented subscription semantics, which is why the dispatcher's hardcoded `WEBHOOK_EVENT_TYPES` gate is redundant as well as wrong.
