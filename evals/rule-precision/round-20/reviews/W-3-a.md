### Critical: delivery history is readable across organizations
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id` and never joins back to `WebhookEndpoint.org_id`, so any authenticated user can page another organization's deliveries by guessing the integer `endpoint_id`.
What breaks in production: every stored `payload`/`response_body` — invoice amounts, customer identifiers, whatever the receiving endpoint echoed back — leaks cross-tenant through a normal 200 response, with no anomaly in the logs.
Cross-cutting evidence: the two sibling routes in the same file, `list_api_keys` and `list_webhook_endpoints`, both carry `.filter(... .org_id == user.org_id)`; this is the one new route that dropped it (R3, security-relevant).
Fix: join the endpoint and scope by tenant — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)` — and return `HTTPException(404)` (not 403) when the join yields nothing, so the endpoint id space is not an existence oracle. Allow side that must still pass: an owner listing their own endpoint's deliveries still gets all rows, unchanged in count and order. Red-prove separately by execution: (a) delete the `org_id` predicate and assert the cross-org test goes red; (b) delete the `endpoint_id` predicate and assert the "only this endpoint's rows" test goes red; (c) make the join return rows for a soft-deleted/foreign endpoint and assert the 404 test goes red. Failure to run must be loud: if `user.org_id` is `None`, raise rather than issuing the query with `org_id IS NULL`, so "could not scope" is never spelled the same as "scoped to nothing". Preserve: the route must keep returning the same `to_dict()` shape and the `created_at desc` + `limit` behaviour — do not fix this by removing the route. Boundary/tie: an endpoint that exists but belongs to another org falls on the *deny* side and is answered 404, identically to a nonexistent id.

### Critical: the worker reads ORM objects after their session closed, so no delivery ever happens
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`
What is wrong: `_claim_batch` returns `rows` from inside `with session_scope() as session`, and `deliver` fetches `endpoint = session.get(...)` inside its own `with session_scope()` block and then uses `endpoint.url` / `endpoint.signing_secret` / `delivery.payload` / `delivery.attempts` after both blocks have exited and committed — with SQLAlchemy's default `expire_on_commit=True` every attribute is expired and each access raises `DetachedInstanceError`.
What breaks in production: the whole retry pipeline is a declared capability with no working backing path (R41) — the first `deliver()` raises before any HTTP request, `asyncio.gather` re-raises, and `run_worker` exits, so zero webhooks are ever delivered while the API cheerfully accepts endpoint registrations.
Fix: stop passing ORM entities across session boundaries. Have `_claim_batch` return plain immutable snapshots (e.g. a frozen dataclass carrying `id`, `endpoint_id`, `attempts`, `payload`, plus `url` and `signing_secret` fetched via the same `join` in one query), and have `deliver` take that snapshot; alternatively open one `session_scope` for the whole `deliver` call. Allow side that must still pass: a happy-path test that calls `run_worker` for one tick against a `MockTransport` returning 200 must observe exactly one POST and a row in `delivered`. Red-prove separately by execution: (a) revert `_claim_batch` to returning entities and assert the new worker-level test reddens with `DetachedInstanceError`; (b) drop `signing_secret` from the snapshot and assert the signing assertion reddens; (c) drop `attempts` from the snapshot and assert the retry-count assertion reddens. Failure to run must be loud: if the join returns a delivery whose endpoint row is missing, mark it `failed_permanent` with an explicit reason rather than skipping the row silently. Preserve: batch claiming and the `BATCH_SIZE` cap must survive the refactor. Boundary/tie: a delivery whose `next_attempt_at` is exactly `now` is claimed by this tick, not the next.

### Critical: the signature is not the signature the documentation tells receivers to compute
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `docs/webhooks.md` states the HMAC input is `"{timestamp}.{raw_request_body}"`, but `sign` computes `hmac(secret, json.dumps(payload, sort_keys=True))` — the timestamp is not in the MAC at all, and the bytes actually transmitted come from httpx's `json=` serializer (default separators, insertion order), which is not the string `serialize()` produced.
What breaks in production: every receiver that follows the published verification recipe computes a different digest and rejects 100% of deliveries (R40: producer wire shape vs strict consumer), and because the timestamp is unauthenticated an attacker can replay a captured request forever by rewriting `X-Acme-Timestamp`, defeating the five-minute window the docs present as the anti-replay control (R49: claim stronger than the implementation).
Fix: serialize once and sign exactly what is sent — build `body = serialize(payload).encode()`, compute `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, and POST with `content=body, headers={"Content-Type": "application/json", ...}` instead of `json=delivery.payload` so no second serializer can intervene. Allow side that must still pass: a receiver-side test that recomputes the MAC from the *captured raw request bytes* and the captured timestamp header must return True. Red-prove separately by execution: (a) mutate the transmitted body by one byte and assert verification reddens; (b) mutate the timestamp header only and assert verification reddens (this is the clause that is silently absent today); (c) send with `json=` again and assert the raw-bytes verification test reddens. Failure to run must be loud: `verify` must reject — not return True — when the signature header is absent, malformed, or lacks the `sha256=` prefix, and when the timestamp is not parseable as an integer. Preserve: keep `sort_keys=True` so the documented canonical form still holds, and keep the two header names. Boundary/tie: a timestamp exactly `now - 300s` is accepted (inclusive) and `now - 301s` rejected; state that in `docs/webhooks.md` alongside the corrected recipe.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify` (`return expected == signature`)
What is wrong: the published verification helper compares an attacker-supplied signature to the expected HMAC with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: this is the reference implementation customers are pointed at, so anyone able to submit candidate signatures against a receiver that uses it can recover a valid digest byte-by-byte from response-timing differences and forge webhook events into the customer's system.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` of identical charset first, and reject non-`str` input explicitly. Allow side that must still pass: `verify(SECRET, payload, sign(SECRET, payload)[1])` still returns True. Red-prove separately by execution: (a) restore `==` and assert a test that asserts `compare_digest` is on the call path (e.g. via monkeypatch spy) reddens; (b) pass a signature with a correct prefix and wrong tail and assert the reject test reddens; (c) pass `None`/`bytes` and assert the type-rejection test reddens rather than raising `TypeError` out of `compare_digest`. Failure to run must be loud: an unparseable signature returns False with a logged reason, never True and never an uncaught exception. Preserve: the function keeps returning a plain bool and keeps accepting the `sha256=`-prefixed form. Boundary/tie: two signatures of different length must return False, not raise — `compare_digest` handles this, but the length check must not be added *before* it as an early return, which would reintroduce a length oracle.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice`, i.e. the Mersenne Twister global instance, which is documented as unsuitable for security purposes and whose state is recoverable from observed output.
What breaks in production: an attacker who obtains one organization's secret (they are handed one for their own endpoint, see the next finding) can work toward predicting others generated by the same process, letting them forge signed events into another tenant's webhook receiver.
Codebase awareness: the standard library already provides the shared helper this reimplements — `secrets.token_urlsafe` / `secrets.choice` — and nothing in the diff wraps it, so there is no project-local generator to adopt (R1).
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and rename `SECRET_BYTES` to reflect that it is now genuinely a byte count (it is currently used as a character count against a 62-symbol alphabet). Allow side that must still pass: the existing prefix assertion and a *lower-bound* entropy assertion (`len(secret) - len(SECRET_PREFIX) >= 32`) must still pass, since `token_urlsafe` output length is not a fixed function of the byte count. Red-prove separately by execution: (a) swap back to `random.choice` under a fixed `random.seed(0)` and assert a determinism test (two seeded calls returning equal secrets) reddens the "unpredictable" assertion; (b) truncate to 8 bytes and assert the length-floor test reddens; (c) drop the prefix and assert the prefix test reddens. Failure to run must be loud: if `secrets` cannot supply entropy the call raises — do not add a `random` fallback. Preserve: the `whsec_` prefix and the "shown once" contract. Boundary/tie: exactly 32 bytes is accepted, 31 is rejected by the floor assertion.

### Critical: endpoint URLs are unvalidated, redirects are followed, and response bodies are readable — a full SSRF read primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: the only check is `parsed.scheme.startswith("http")` (which also admits `httpx:`, `httpfoo:` and plain `http:`) with no host/IP restriction, the client follows redirects, and `_finish` stores `response.text` into `webhook_deliveries.response_body`, which `list_deliveries` exposes back to the caller.
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or any internal service), the worker issues the request from inside the VPC, and the response body is read straight back through the deliveries API — cloud credential theft with no exploit beyond two ordinary API calls; a public HTTPS host redirecting to `127.0.0.1` achieves the same past any host check applied only at registration.
Cross-cutting evidence: `docs/webhooks.md` states "Only `https://` URLs are accepted", which the implementation does not do (R49) — the doc is the only place the control is described.
Fix: enforce `parsed.scheme == "https"` (exact equality, not `startswith`) and a non-empty netloc at registration; resolve the hostname and reject any address in a private, loopback, link-local, multicast, or reserved range via `ipaddress.ip_address(...).is_global`; set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure; re-resolve and re-check the address at connect time (a DNS rebind between registration and delivery otherwise walks past the registration check — R51 shape); and stop persisting the raw body — store a truncated, non-echoed excerpt (e.g. first 512 bytes, and only for non-2xx) and remove `response_body` from anything the API returns. Allow side that must still pass: registering and delivering to a genuine public HTTPS endpoint continues to work end to end, and the deliveries API still reports `response_status`. Red-prove separately by execution: (a) point a fixture at `http://` and assert the 422 test reddens when the scheme check is loosened back to `startswith`; (b) point a fixture at `https://127.0.0.1/` and assert the private-range test reddens when the `is_global` check is removed; (c) serve a 302 to an internal host and assert the no-redirect test reddens when `follow_redirects=True` is restored. Failure to run must be loud: a DNS resolution failure at registration must reject the URL with a stated reason, never fall through to "could not check, allow". Preserve: legitimate customers must still be able to register any public HTTPS host — do not fix this with a static allowlist of hostnames. Boundary/tie: IPv6 and IPv4-mapped IPv6 forms of the same private address must both be denied; check the resolved address object, not the textual host.

### Critical: the signing secret is returned by the list endpoint, contradicting the documented "shown once" contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret"`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so the secret is served on every GET despite `docs/webhooks.md` saying "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret that is the sole authenticator of every outbound event is handed out on a read-only route, so any read-scoped token, cached response, browser history entry, or proxy log yields the ability to forge events into that customer's receiver.
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the single creation site. Allow side that must still pass: the 201 response from `POST /v1/settings/webhook-endpoints` must still contain the secret, since it is the only place a customer can obtain it. Red-prove separately by execution: (a) re-add the key to `to_dict()` and assert a test asserting `"signing_secret" not in` the list response reddens; (b) remove the explicit key from the create handler and assert the create-response test reddens; (c) add a third serializer path (e.g. an error handler echoing the model) and assert a repo-wide "no route body contains signing_secret except create" test reddens. Failure to run must be loud: if a future field is added to `to_dict()` the test must enumerate the allowed key set rather than only checking the one forbidden name. Preserve: customers must still be able to list endpoints and see `id`, `url`, `event_types`, `active`. Boundary/tie: the rotate flow (when it exists) is the only other place a secret may be emitted, and it must go through the same explicit-site rule, not through `to_dict()`.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `idx_webhook_deliveries_event`; `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: the unique index is on `event_id` alone, but `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint and `session.add_all(rows)`, so the second endpoint's row violates the constraint and the whole enqueue transaction aborts.
What breaks in production: any organization with two subscribed endpoints gets *zero* deliveries for every event — the `IntegrityError` propagates to the dispatcher, which swallows it as a `log.warning`, so the failure is invisible until a customer reports missing webhooks.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — this is also the index the intended idempotency guard needs, since "at-least-once, deduplicate on `event_id`" is a per-endpoint property. Allow side that must still pass: enqueuing one event for three subscribed endpoints inserts exactly three rows and all three deliver. Red-prove separately by execution: (a) restore the single-column index and assert the three-endpoint fan-out test reddens with `IntegrityError`; (b) drop the index entirely and assert a re-enqueue-of-the-same-event test (which must insert one row, not two) reddens; (c) insert the same `(endpoint_id, event_id)` from two concurrent transactions and assert exactly one commits. Failure to run must be loud: `enqueue_for_event` must catch the unique violation on re-enqueue and treat it as "already queued" (a named, logged outcome), while any other `IntegrityError` propagates. Preserve: the fan-out semantics documented in `docs/webhooks.md` ("we POST every subscribed event"). Boundary/tie: two endpoints in the same org subscribing to the same event type each get their own row; the same endpoint re-enqueued for the same event gets exactly one.

### Critical: the code writes a status the database CHECK constraint forbids
File: `app/webhooks/models.py` — `STATUSES`; `migrations/0042_webhook_delivery.sql` — `webhook_deliveries.status CHECK`
What is wrong: the model and `deliver()` use `"failed_permanent"`, while the migration's CHECK allows only `('pending', 'in_flight', 'delivered', 'failed')` — the same enum spelled two ways in two artifacts (R2 value/meaning duplication, R40 producer vs strict consumer).
What breaks in production: every delivery that exhausts its retries raises a CHECK violation inside `_finish`, the transaction rolls back, and the row is left permanently in `in_flight` — so failures are neither recorded nor retried, and the exception kills the worker's `gather`.
Fix: pick one spelling and derive the other from it — set the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and add a test that asserts `models.STATUSES` equals the set parsed out of the migration file, so the two cannot drift again. Allow side that must still pass: writing each of the four legal statuses through `_finish` succeeds against a real database. Red-prove separately by execution: (a) change one member of `STATUSES` and assert the migration-parity test reddens; (b) change the CHECK list in the migration and assert the same test reddens from the other side; (c) have `_finish` write an unlisted status and assert an integration test reddens with the constraint violation rather than passing. Failure to run must be loud: if the parity test cannot locate or parse the migration file it must fail, not skip. Preserve: the four-state machine itself, and the existing `pending`/`in_flight` spellings that `_claim_batch` filters on. Boundary/tie: the state written at exactly `attempt == MAX_ATTEMPTS` is `failed_permanent`; the state at `attempt == MAX_ATTEMPTS - 1` is still `pending` with a scheduled retry.

### Critical: `time.sleep` inside an async coroutine blocks the entire worker
File: `app/webhooks/delivery.py` — `deliver` (`time.sleep(delay)`)
What is wrong: the retry backoff uses the blocking `time.sleep` in an `async def`, freezing the event loop instead of yielding.
What breaks in production: `asyncio.gather` over a 100-delivery batch degenerates into strictly serial execution, each failing delivery stalls the loop for up to 2+4+8+16 = 30 s (plus 30 s of request timeout per attempt), the 60 s Redis lock expires while the batch is still running, and a second worker starts claiming the same rows.
Fix: `await asyncio.sleep(delay)`; additionally, do not hold a delivery's retries inside a single coroutine at all — persist `next_attempt_at = now + backoff_for(attempt)` with `status = "pending"` and return, letting the next poll pick it up, so a worker restart does not lose in-progress retries. Allow side that must still pass: a delivery that succeeds on its second attempt is still marked `delivered` with `attempts == 2`. Red-prove separately by execution: (a) restore `time.sleep` and assert a test that runs two failing deliveries concurrently and asserts wall-clock < serial-sum reddens; (b) remove the `next_attempt_at` write and assert the reschedule test reddens; (c) remove the `status = "pending"` write and assert the "row is reclaimable" test reddens. Failure to run must be loud: if the reschedule write fails, the row must be marked `failed_permanent` with the reason rather than left `in_flight`. Preserve: the exponential schedule `backoff_for` produces and the `MAX_ATTEMPTS` cap. Boundary/tie: at exactly `attempt == MAX_ATTEMPTS` no reschedule is written; below it, a row whose `next_attempt_at` equals the poll instant is claimed by that poll.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch`, `run_worker`
What is wrong: `_claim_batch` writes `row.status = "in_flight"` and commits, but the only paths out are `_finish("delivered")` and `_finish("failed_permanent")` inside the same process — a crash, deploy, OOM kill, or any exception in `deliver` leaves the row wedged, and `_claim_batch` only ever selects `status == "pending"` (R38 mode 1).
What breaks in production: after the first worker restart, the stuck deliveries are never retried and never reported as failed; they simply vanish from the pipeline while the API still shows them as in progress.
Fix: give the transient state a bounded timeout and an explicit failure exit — record `claimed_at` when transitioning to `in_flight`, and have each poll first re-`pending` any row with `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` (incrementing `attempts` so the retry cap still binds), plus wrap `deliver` in a `try/except` that routes any unexpected exception to `_finish(..., "failed_permanent", ...)`. Allow side that must still pass: a delivery currently being attempted by a live worker (claimed 3 s ago) must NOT be reclaimed by a concurrent poll. Red-prove separately by execution: (a) kill a worker mid-batch and assert the reaper test reddens when the reclaim query is removed; (b) remove the `attempts` increment and assert the "reclaim does not create an infinite retry loop" test reddens; (c) raise a non-HTTP exception inside `deliver` and assert the terminal-state test reddens when the `except` is removed. Failure to run must be loud: if `claimed_at` is NULL on an `in_flight` row (a pre-migration row), reclaim it and log that it was reclaimed for want of a timestamp. Preserve: the batch claim must stay a single statement so it does not become slower than the work it schedules. Boundary/tie: a row claimed exactly 5 minutes ago is reclaimed; the tie is broken toward reclaiming, since a duplicate delivery is within the documented at-least-once contract while a lost one is not.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`
What is wrong: `_acquire_lock` does `get` then `set` as two round trips (a classic TOCTOU — two workers both see the key absent and both proceed), the TTL is set in a separate `expire` call that can be lost between them, and `run_worker`'s `finally` calls `redis_client.delete(LOCK_KEY)` without checking ownership.
What breaks in production: after the 60 s TTL expires under a slow batch, worker A deletes the lock worker B legitimately holds, and both then claim and POST the same deliveries — and because `_claim_batch` reads and updates without `FOR UPDATE SKIP LOCKED`, the same rows are dispatched twice.
Fix: acquire with a single atomic call carrying a unique owner token and the TTL together — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — release only via a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`), and make the claim itself safe independently of the lock by using `SELECT ... FOR UPDATE SKIP LOCKED` inside one transaction that both selects and marks `in_flight`. Allow side that must still pass: a single worker with no contention still acquires the lock on every poll and processes its batch. Red-prove separately by execution: (a) revert to `get`+`set` and assert a two-concurrent-acquirers test reddens; (b) revert to unconditional `delete` and assert an "expired holder does not delete the new owner's lock" test reddens; (c) remove `SKIP LOCKED` and assert the "two workers claim disjoint row sets" test reddens. Failure to run must be loud: if Redis is unreachable, the worker must log and back off rather than treating the exception as "lock is free". Preserve: the poll loop must still make progress when the previous holder crashed — that is what the TTL is for; do not replace it with an untimed lock. Boundary/tie: at the exact TTL expiry the non-owner's compare-and-delete is a no-op, and the next `set nx` decides ownership.

### Major: one bad delivery takes down the worker loop
File: `app/webhooks/delivery.py` — `run_worker` (`asyncio.gather` without `return_exceptions`), `_finish`
What is wrong: `gather` re-raises the first exception, and `_finish` does `row = session.get(...)` then `row.status = ...` without a `None` check, so a deleted or missing delivery row raises `AttributeError` out of `deliver`, out of `gather`, and out of `run_worker`.
What breaks in production: a single malformed row stops the entire webhook worker process, leaving the rest of the batch stranded in `in_flight` (see the R38 finding above) and all subsequent events unqueued until someone notices the crash loop.
Fix: use `results = await asyncio.gather(*[...], return_exceptions=True)` and log each returned exception against its delivery id, and make `_finish` raise a named `DeliveryRowMissing` (caught and logged per delivery) when `session.get` returns `None`. Allow side that must still pass: a batch where every delivery succeeds must still complete with no logged exceptions and all rows `delivered`. Red-prove separately by execution: (a) make one delivery in a batch of three raise and assert the "other two still delivered" test reddens without `return_exceptions=True`; (b) delete the row before `_finish` and assert the `DeliveryRowMissing` test reddens when the `None` check is removed; (c) drop the per-exception logging and assert the "failure is reported" test reddens. Failure to run must be loud: swallowing the exception list without logging would reintroduce exactly the silent mode this fixes — the log line must name the delivery id and the exception type. Preserve: `return_exceptions=True` must not become a blanket ignore; each exception still routes to a terminal row state. Boundary/tie: a batch of exactly zero deliveries must still sleep `poll_interval` rather than spinning.

### Major: 4xx responses are retried although the documentation promises they are permanent
File: `app/webhooks/delivery.py` — `deliver`; `docs/webhooks.md` — "Retries"
What is wrong: the retry loop treats every non-2xx identically (`detail = f"HTTP {response.status_code}"` then retry), while the docs state "a 4xx is permanent and we stop immediately" (R29/R49 — the claim is stronger than the implementation, in the loosening direction).
What breaks in production: a customer who deletes an endpoint route or revokes its auth gets four extra POSTs per event across 30 s of held worker capacity, and the delivery is eventually recorded with a status the operator was told could not occur.
Fix: branch on the class — `if 400 <= response.status_code < 500 and response.status_code not in (408, 425, 429): _finish(delivery.id, "failed_permanent", attempt, response.status_code, detail); return` — and honour `Retry-After` on 429. Allow side that must still pass: a 500 and a `httpx.ConnectError` must both still retry to `MAX_ATTEMPTS`. Red-prove separately by execution: (a) return 404 and assert the "exactly one attempt" test reddens when the 4xx branch is removed; (b) return 429 and assert the "still retried" test reddens when 429 is dropped from the exception set; (c) return 503 and assert the retry-count test reddens if the branch is widened to all non-2xx. Failure to run must be loud: an unparseable `Retry-After` falls back to `backoff_for(attempt)` with a logged note, never to zero delay. Preserve: the documented "any 2xx marks the delivery delivered" behaviour, and the 5-attempt cap for retriable classes. Boundary/tie: 400 through 499 inclusive are permanent except the three named codes; 399 and 500 are not.

### Major: naive and timezone-aware datetimes are mixed, and the migration disagrees with the model
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); `migrations/0042_webhook_delivery.sql`
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` into a column the model declares `DateTime(timezone=True)` and that `_claim_batch` filters against a tz-aware `datetime.now(timezone.utc)`, and every timestamp column in the migration is declared `TIMESTAMP` (without time zone) rather than `TIMESTAMPTZ`.
What breaks in production: the comparison is between values with different offset semantics, so in any deployment whose database session TZ is not UTC the scheduling window shifts by the offset — deliveries fire hours early or, worse, never become eligible.
Codebase awareness: `app/webhooks/models.py` already defines the shared helper `_now()` returning `datetime.now(timezone.utc)`, and `delivery.py` reimplements the concept twice with two different semantics (R1).
Fix: change every `TIMESTAMP` in `0042_webhook_delivery.sql` to `TIMESTAMPTZ`, and replace `datetime.utcnow()` with the existing `m._now()` (exported as `now_utc` if a public name is wanted) so one helper produces all timestamps. Allow side that must still pass: a delivery enqueued now must be claimable by the very next poll under a database session set to a non-UTC TZ.
