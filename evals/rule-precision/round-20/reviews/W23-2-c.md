### Critical: `list_deliveries` has no tenancy predicate — any authenticated user reads any org's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters on the caller-supplied `endpoint_id` alone and never joins to
`WebhookEndpoint.org_id == user.org_id`, while its two siblings in the same file
(`list_webhook_endpoints`, and `enqueue_for_event` in `app/webhooks/delivery.py`) both scope by
`org_id` — the pattern was propagated to two of three sites (R3, security-relevant).
What breaks in production: Any logged-in customer can enumerate `endpoint_id` and read every other
organization's webhook delivery rows, including `event_type`, `event_id` and delivery status for
`invoice.paid` events.
Fix: Join through the endpoint and scope by the caller's org, deriving `endpoint_id`'s validity from
the same predicate rather than trusting it:
```python
deliveries = (
    session.query(m.WebhookDelivery)
    .join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id)
    .filter(
        m.WebhookEndpoint.id == endpoint_id,
        m.WebhookEndpoint.org_id == user.org_id,
    )
    ...
)
```
and raise `HTTPException(404)` when the endpoint does not resolve under that predicate (404, not 403,
so the response does not confirm the id exists in another org).
*Still must pass (deny+allow):* the owning org's caller still receives its own rows — assert a
non-empty list for the owner in the same test that asserts 404 for the non-owner; a fix that always
404s satisfies every other clause here.
*Red-prove, one mutation per clause:* (a) delete the `org_id` predicate → the cross-tenant test goes
red on a non-empty body; (b) delete the `WebhookEndpoint.id == endpoint_id` predicate → the owner
test goes red because it now sees a second endpoint's rows. Run both, singly.
*When the check cannot run:* if `user.org_id` is absent or null, deny with an explicit 403 that names
the missing subject — do not let a `None` org_id degrade into `org_id IS NULL` matching nothing (a
silent empty list is spelled the same as "this org has no deliveries").
*Preserve:* the endpoint must still return deliveries for an endpoint the caller owns, ordered and
limited — do not fix by removing the route.
*Boundary/tie:* an endpoint whose `org_id` equals the caller's org is IN; a soft-deleted or
`active=False` endpoint the caller owns is still IN (inactive is not unowned) — state that choice in
the test.

### Critical: `signing_secret` is returned on every read of an endpoint, contradicting the documented one-time-disclosure control
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret"`
What is wrong: `to_dict()` includes the raw signing secret and is called by BOTH
`create_webhook_endpoint` and `list_webhook_endpoints`, while `docs/webhooks.md` states "The response
is the only place the signing secret appears — it cannot be read back afterwards" (RS4 Critical:
committed artifact/response carrying live credential material; R49: claim strictly stronger than the
implementation).
What breaks in production: The HMAC key that authenticates every outbound event is readable forever
by anyone who can call `GET /v1/settings/webhook-endpoints` — including a lower-privileged member, a
leaked read-only API key, or any log/proxy that captures the list response — so a third party can
forge signed `invoice.paid` events into the customer's endpoint.
Fix: Remove `"signing_secret"` from `to_dict()` and return the secret only from the creation path, as
an explicit field the create handler adds to its own response body:
```python
# models.py
def to_dict(self) -> dict:
    return {"id": ..., "url": ..., "event_types": ..., "active": ...}

# settings.py, create_webhook_endpoint only
return {**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}
```
Store the secret hashed or in the secret manager if it must be re-derivable; if it stays plaintext in
`webhook_endpoints.signing_secret`, say so in the doc instead of claiming it cannot be read back.
*Still must pass (deny+allow):* the create response must still carry the secret exactly once —
assert `201` body contains `signing_secret`, and assert the list response for the same endpoint does
not. Without the first assertion a fix that strips the key everywhere passes.
*Red-prove:* (a) re-add `"signing_secret"` to `to_dict()` → the list-response test goes red; (b)
delete the `{**..., "signing_secret": ...}` spread in the create handler → the create-response test
goes red. Two mutations, two different assertions.
*When the check cannot run:* if the secret cannot be produced at create time (generator raises), fail
the request with 500 and create no endpoint row — never return a 201 with the field omitted, which
reads to the caller as "secret disclosure suppressed" rather than "no secret exists".
*Preserve:* customers must still be able to obtain a secret for a new endpoint; do not fix by never
returning it.
*Boundary/tie:* an endpoint created before this change already had its secret exposed — treat those
as compromised and state the rotation path; two endpoints of the same org must not share a secret.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The HMAC key is drawn from `random`, a Mersenne Twister PRNG whose internal state is
recoverable from 624 observed outputs and which is seeded from system time in many deployments — a
security primitive reimplemented instead of using the stdlib's `secrets` (R1, Critical branch: the
duplicated behaviour IS the security control).
What breaks in production: An attacker who obtains a handful of signing secrets (their own endpoints
are enough — creation is self-service) can reconstruct the generator state and derive other tenants'
secrets, then forge signed billing events into their endpoints.
Fix: Use `secrets`, and make the constant mean what it says:
```python
import secrets
SECRET_PREFIX = "whsec_"
SECRET_ENTROPY_BYTES = 32

def new_signing_secret() -> str:
    return SECRET_PREFIX + secrets.token_urlsafe(SECRET_ENTROPY_BYTES)
```
Delete the `random`, `string` imports and `_ALPHABET` outright — do not leave the old path as a
fallback (R1 clause d). Rotate every secret issued by the current implementation.
*Still must pass (deny+allow):* a freshly generated secret must still be accepted by `sign`/`verify`
round-trip and still carry the `whsec_` prefix — assert both, so a fix that returns a constant or an
empty string is caught.
*Red-prove:* (a) swap `secrets.token_urlsafe` back to `random.choice` → a test asserting
`signing.secrets` is the module used (or a `random.seed(0)` determinism probe: seed, generate twice
across separate seeds, assert the values differ from the seeded-`random` reference) goes red; (b)
set `SECRET_ENTROPY_BYTES = 1` → a minimum-entropy assertion goes red. Run each singly.
*When the check cannot run:* if `secrets` cannot produce bytes, let the exception propagate to a 500 —
never fall back to `random` on failure.
*Preserve:* the `whsec_` prefix, which is how customers identify the value in their secret manager.
*Boundary/tie:* `test_new_signing_secret_has_prefix_and_length` currently pins
`len == len(prefix) + SECRET_BYTES`, which is a CHARACTER count, not bytes — that assertion must be
updated to the new length (43 chars for 32 urlsafe bytes) or it fails the fix for the wrong reason.

### Critical: `verify` compares signatures with `==` — not constant time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The shipped verification helper compares an attacker-supplied signature to the
computed one with Python's short-circuiting `==` instead of `hmac.compare_digest` (RS1), while
`docs/webhooks.md` instructs customers to "Compare it against your own computation using a
constant-time comparison" — the doc demands of the customer exactly what the reference
implementation does not do (R49).
What breaks in production: Anywhere this helper is used to admit a request (it is exported and is the
only verification path in the change), byte-wise timing differences let an attacker recover a valid
signature for a chosen payload one hex digit at a time, without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, and take the comparison operands as `str`
of fixed length so `compare_digest` does not leak on length. Fold this into the signature-scheme fix
below so `verify` receives the raw body and timestamp rather than a re-serialized dict.
*Still must pass (deny+allow):* a correct signature must still verify true — keep
`test_verify_accepts_signature_produced_by_sign` green alongside the new reject case; a fix that
returns `False` unconditionally satisfies the timing requirement and every other clause.
*Red-prove:* (a) revert to `==` → a test asserting `hmac.compare_digest` is on the call path (patch
`hmac.compare_digest` with a counting wrapper and assert it was called once) goes red; (b) return
`False` unconditionally → the accept test goes red. Two mutations, two assertions.
*When the check cannot run:* a malformed signature (missing `sha256=` prefix, non-hex, wrong length)
must return `False` explicitly at a named guard, not raise out of `compare_digest` — an exception
escaping `verify` in a customer's handler is a different failure than "signature rejected".
*Preserve:* `verify` must keep accepting the exact output of `sign` for the same secret and payload.
*Boundary/tie:* an empty signature string and a correct-length-but-wrong signature both return
`False`; state that a signature of the wrong LENGTH is rejected before the comparison, since
`compare_digest` on unequal lengths is itself short-circuiting.

### Critical: the timestamp is not covered by the HMAC, and the signed bytes are not the bytes sent
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: Two divergences from `docs/webhooks.md`, which specifies "the HMAC-SHA256 of
`"{timestamp}.{raw_request_body}"`": (1) `sign` MACs only `serialize(payload)` and returns the
timestamp unauthenticated; (2) `send_once` signs `serialize(payload)` (`json.dumps(..., sort_keys=True)`,
default `", "`/`": "` separators) but transmits `json=delivery.payload`, which httpx serializes with
its own separators and key order — the producer's wire bytes do not match what any strict consumer
following the docs will hash (R40, Critical: silent total-path failure).
What breaks in production: Every customer who implements the documented verification rejects 100% of
our deliveries, and every customer who instead reproduces our actual (undocumented) scheme has no
replay protection at all — an attacker who captures one request can re-send it with any timestamp,
because the timestamp is outside the MAC and the documented five-minute window therefore constrains
nothing.
Fix: Sign the exact bytes that go on the wire, with the timestamp inside the MAC:
```python
def sign(secret: str, body: bytes, timestamp: str | None = None) -> tuple[str, str]:
    ts = timestamp or str(int(time.time()))
    mac = hmac.new(secret.encode(), ts.encode() + b"." + body, hashlib.sha256)
    return ts, "sha256=" + mac.hexdigest()

def verify(secret: str, body: bytes, timestamp: str, signature: str,
           max_age_seconds: int = 300) -> bool:
    if abs(int(time.time()) - int(timestamp)) > max_age_seconds:
        return False
    _, expected = sign(secret, body, timestamp)
    return hmac.compare_digest(expected, signature)
```
and in `send_once`:
```python
body = serialize(delivery.payload).encode()
ts, signature = sign(endpoint.signing_secret, body)
return await client.post(endpoint.url, content=body, headers=headers)  # not json=
```
Add the round-trip test R40 requires: feed the ACTUAL bytes captured by `MockTransport` through the
ACTUAL `verify`, not two independently constructed shapes.
*Still must pass (deny+allow):* a request whose captured body and headers are fed back into `verify`
must return `True` — the existing `test_send_once_posts_the_signed_payload` should be extended with
`assert signing.verify(SECRET, captured["body"], captured["headers"][TIMESTAMP_HEADER], captured["headers"][SIGNATURE_HEADER])`.
Without that allow-side assertion, a `verify` that always returns `False` passes the replay test.
*Red-prove, one per clause:* (a) revert `content=body` to `json=delivery.payload` → the captured-body
round-trip goes red (body bytes differ from signed bytes); (b) drop `ts.encode() + b"."` from the MAC
input → a test that re-signs the same body under a DIFFERENT timestamp and asserts the signature
CHANGES goes red; (c) set `max_age_seconds` to a huge value → the stale-timestamp test goes red.
Three mutations, three assertions.
*When the check cannot run:* a non-integer or absent timestamp header must return `False` from a
named guard, not raise `ValueError` out of `int()` — "could not parse the timestamp" must not be
spelled the same as "signature matched".
*Preserve:* the `sha256=` prefix and the two header names, which are already documented; and keep
`serialize`'s `sort_keys=True`, which is what makes the body reproducible for a receiver that re-hashes.
*Boundary/tie:* a timestamp exactly `max_age_seconds` old is ACCEPTED (`>` not `>=`); a
future-dated timestamp beyond the same window is REJECTED — the `abs()` above makes skew symmetric,
state that in the doc.

### Critical: `UNIQUE (event_id)` means an org with two subscribed endpoints receives no webhooks at all
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` creates one `WebhookDelivery` row per matching endpoint for a
single `event_id`, so any org with two or more active endpoints subscribed to the same event violates
the unique index; the index is on the wrong key for the idempotency it was clearly meant to express.
What breaks in production: `session.add_all(rows)` raises `UniqueViolation` on commit, the exception
propagates to `dispatch`, which catches bare `Exception` and logs a warning — so such orgs silently
receive ZERO deliveries for every event, permanently, with no error visible to them or to us beyond a
`log.warning`.
Fix: Key the index on the pair that is actually unique per delivery, and keep it unique so it doubles
as the enqueue idempotency guard:
```sql
CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event
    ON webhook_deliveries (endpoint_id, event_id);
```
and make the enqueue insert conflict-tolerant (`ON CONFLICT DO NOTHING`, or SQLAlchemy's
`postgresql.insert(...).on_conflict_do_nothing`) so a retried `dispatch` re-enqueues idempotently
rather than raising.
*Still must pass (deny+allow):* an org with two subscribed endpoints must receive TWO delivery rows
for one event — assert `enqueue_for_event(...) == 2` and that both rows exist; a fix that drops the
index entirely would pass a "no exception raised" test alone. Also assert that calling
`enqueue_for_event` twice for the same event still yields exactly two rows (the idempotency side).
*Red-prove:* (a) restore `UNIQUE (event_id)` → the two-endpoint test goes red on `UniqueViolation`;
(b) remove the `ON CONFLICT DO NOTHING` → the double-enqueue test goes red; (c) drop the index → the
double-enqueue test goes red with four rows instead of two. Three mutations, three assertions.
*When the check cannot run:* if the insert fails for any reason other than the conflict, it must
propagate — see the `except Exception` finding below; a swallowed enqueue error is exactly how this
defect stays invisible.
*Preserve:* the ability to look deliveries up by `event_id` (keep a non-unique index or rely on the
composite's leading column reordering — note `(endpoint_id, event_id)` does NOT serve an
`event_id`-only lookup, so add `CREATE INDEX ... ON webhook_deliveries (event_id)` if that query
exists).
*Boundary/tie:* an endpoint whose `event_types` is empty matches every event — an org with one
empty-list endpoint and one explicit `["invoice.paid"]` endpoint gets two rows for `invoice.paid`
and one for the others; pin that case, it is the one the current index breaks first.

### Critical: `time.sleep` inside `async def deliver` blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: A synchronous `time.sleep` sits inside a coroutine that `run_worker` launches under
`asyncio.gather` — it blocks the single event loop thread rather than yielding, so `asyncio.sleep`
is what was meant.
What breaks in production: One failing endpoint stalls the entire worker for up to 30 seconds
(2+4+8+16) and, because a batch is 100 deliveries gathered onto the same loop, a batch of failing
endpoints serializes into ~50 minutes of total blockage; nothing else on that loop — including the
`httpx` transport for the healthy deliveries already in flight — makes progress, so healthy
deliveries hit the 30s `REQUEST_TIMEOUT` and fail too.
Fix: `await asyncio.sleep(delay)`. Better, remove the in-process retry loop entirely: on a retryable
failure, write `status='pending'`, `attempts=attempt`, `next_attempt_at=_now() + backoff_for(attempt)`
and return, letting the next `_claim_batch` pick it up — that is what the `next_attempt_at` column
exists for, and it makes retries survive a worker restart (see the `in_flight` finding).
*Still must pass (deny+allow):* a delivery that succeeds on its second attempt must still end
`delivered` with `attempts == 2` — assert that, not only that the loop no longer blocks; a fix that
gives up after one attempt satisfies "does not block".
*Red-prove:* (a) restore `time.sleep` → a test that gathers two deliveries and asserts wall-clock
elapsed is less than the sum of their backoffs goes red; (b) drop the `attempts=attempt` write → the
retry-count assertion goes red. Two mutations. Use a monkeypatched `backoff_for` returning
milliseconds so the timing test terminates (an unbounded sleep mutation hangs instead of reddening).
*When the check cannot run:* if `next_attempt_at` cannot be written (DB error), the delivery must not
be left `in_flight` — route that to an explicit re-queue-or-alarm path that names itself.
*Preserve:* the documented retry schedule (≈2s, 4s, 8s, 16s, at most 5 attempts) and the fact that a
2xx terminates immediately.
*Boundary/tie:* `attempt >= MAX_ATTEMPTS` is the terminal test — attempt 5 is the last one ATTEMPTED
and is not followed by a sleep; state that the 5th failure writes `failed_permanent` rather than
scheduling a 6th.

### Critical: `_claim_batch` returns ORM objects after its session closed, so `deliver` reads detached state
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`), consumed by `deliver`
What is wrong: The rows are queried and mutated inside `with session_scope() as session:` and
returned to callers that use them after the block exits; `deliver` then reads `delivery.attempts`,
`delivery.payload` and `delivery.id` from instances whose session has committed and closed. Under
SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and the first
access raises `DetachedInstanceError`.
What breaks in production: The worker's entire claim→deliver path raises on the first attribute
access, `asyncio.gather` propagates it out of `run_worker`, and no webhook is ever delivered — while
the claimed rows are left in `in_flight` and are never re-selected.
Fix: Do not hand ORM identities across the session boundary. Have `_claim_batch` return plain data
the worker needs, and have `deliver` re-load or accept that data:
```python
def _claim_batch() -> list[dict]:
    with session_scope() as session:
        rows = (... same query ...)
        claimed = []
        for row in rows:
            row.status = "in_flight"
            claimed.append({
                "id": row.id, "endpoint_id": row.endpoint_id,
                "attempts": row.attempts, "payload": row.payload,
            })
        return claimed
```
(The same defect exists in `deliver`'s own `with session_scope() as session: endpoint = session.get(...)`
followed by `send_once(client, endpoint, ...)` reading `endpoint.url` and `endpoint.signing_secret`
after the block — fix both sites, they are the same pattern.) Note the change already has an
in-file precedent for the correct shape: `enqueue_for_event` returns `len(rows)`, a plain value, not
the rows.
*Grounding:* `session_scope` is not in this diff. What the diff itself establishes is that
`session_scope` commits (nothing calls `session.commit()`, yet `_finish` is expected to persist). If
`session_scope` were configured `expire_on_commit=False` AND did not close the session, the symptom
degrades from `DetachedInstanceError` to silently stale reads of `attempts`/`payload` — still a
defect, one severity lower. Reading `session_scope`'s definition closes this.
*Still must pass (deny+allow):* a claimed batch must still be deliverable end to end — assert a
pending row goes `pending → in_flight → delivered` through the real `_claim_batch` + `deliver` path;
a `_claim_batch` that returns `[]` satisfies "no detached access".
*Red-prove:* (a) revert `_claim_batch` to returning `rows` → the end-to-end test goes red naming
`DetachedInstanceError`; (b) revert the `deliver` endpoint load → the same test goes red at
`endpoint.url`. Two mutations, two distinct failure sites.
*When the check cannot run:* if the endpoint referenced by `endpoint_id` no longer exists, `deliver`
must mark the delivery terminally failed with a named reason, not raise `AttributeError` on `None`.
*Preserve:* the `in_flight` claim itself, which is what stops two workers double-sending.
*Boundary/tie:* a row whose `next_attempt_at` is exactly `now` IS claimed (`<=`); state what happens
when many rows tie on `next_attempt_at` — see the ordering finding below.

### Critical: plain `http://` endpoints are accepted and redirects are followed, giving customers an SSRF primitive into our network
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `parsed.scheme.startswith("http")`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The validation accepts any scheme beginning with `http` (so `http`, but also `httpx`,
`http-foo`), performs no host check at all, and `docs/webhooks.md` states "Only `https://` URLs are
accepted" — a claim the code does not implement (RS3 + R49). `follow_redirects=True` then re-POSTs
the signed payload to whatever `Location` the customer's endpoint returns.
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/` or
`http://10.0.0.5:6379/`, or returns a 302 to one, and our worker issues authenticated POSTs from
inside the VPC — cloud instance metadata, internal admin endpoints and unauthenticated Redis are all
reachable, and the response body is stored in `response_body` where the customer can be shown it.
Fix: Validate the scheme by equality and the resolved host by allowlist-complement, at the boundary,
and stop following redirects:
```python
parsed = urlparse(body.url)
if parsed.scheme != "https" or not parsed.hostname:
    raise HTTPException(422, "url must be an https:// URL")
for info in socket.getaddrinfo(parsed.hostname, parsed.port or 443, proto=socket.IPPROTO_TCP):
    ip = ipaddress.ip_address(info[4][0])
    if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved or ip.is_multicast:
        raise HTTPException(422, "url must resolve to a public address")
```
plus `follow_redirects=False` on the delivery client, and re-run the same address check at delivery
time against the socket actually connected (registration-time DNS is re-resolvable — a customer can
repoint the hostname after passing validation).
*Still must pass (deny+allow):* a legitimate public HTTPS endpoint must still register and still
receive deliveries — assert `201` for `https://hooks.example.com/acme` and a successful `send_once`
against it, alongside the 422 cases. A validator that rejects everything satisfies every deny-side
clause.
*Red-prove, one per clause:* (a) revert to `scheme.startswith("http")` → the `http://` rejection test
goes red; (b) delete the private-range loop → the `http://169.254.169.254` (and
`https://localhost`) rejection tests go red; (c) restore `follow_redirects=True` → a MockTransport
test that returns `302 Location: http://127.0.0.1/` and asserts no second request is issued goes red.
Three mutations.
*When the check cannot run:* DNS resolution failure must DENY registration with a named 422
("could not resolve host"), not fall through to accept — an unresolvable host must not be spelled the
same as a public one.
*Preserve:* customers must still be able to register any genuinely public HTTPS endpoint, including
non-443 ports and IPv6 literals; do not fix by hardcoding an allowlist of known hosts.
*Boundary/tie:* IPv4-mapped IPv6 (`::ffff:10.0.0.1`) and `0.0.0.0` must both be rejected — check
`ip.ipv4_mapped` explicitly, since `is_private` on the mapped form is the case that is usually
missed; a hostname resolving to BOTH a public and a private address must be rejected (any-private
denies, not all-private).

### Major: `_acquire_lock` is a non-atomic check-then-set, and the release deletes whoever holds the lock
File: `app/webhooks/delivery.py` — `_acquire_lock`; `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` followed by `set` is a TOCTOU window two workers both pass (R5 applied to a
non-transactional store), `set` followed by a separate `expire` leaves the key with no TTL if the
process dies between them, and the release deletes `LOCK_KEY` unconditionally without checking that
this worker still owns it.
What breaks in production: Two workers claim overlapping batches and double-POST events to customer
endpoints; separately, a crash between `set` and `expire` leaves a TTL-less lock that halts all
delivery until someone deletes the key by hand; and because a batch with retries exceeds the 60s TTL,
a worker routinely deletes the lock a second worker has since acquired.
Fix: Single atomic acquire with a unique token, and a compare-and-delete release:
```python
token = uuid.uuid4().hex
acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)
...
# release, atomic via Lua
RELEASE = "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end"
await redis_client.eval(RELEASE, 1, LOCK_KEY, token)
```
and renew the TTL while a batch is in flight, or size the TTL above the worst-case batch duration
once the blocking retry loop is removed.
*Still must pass (deny+allow):* a single worker must still acquire the lock and make progress —
assert `_acquire_lock()` is true on a free key, not only that a second concurrent call is false. A
`return False` stub satisfies the mutual-exclusion side alone.
*Red-prove:* (a) revert to `get`-then-`set` → a test issuing two concurrent acquires against a real
(or fakeredis) server and asserting exactly one succeeds goes red; (b) revert the release to a plain
`delete` → a test where worker A's lock has expired and worker B holds a new token, asserting A's
release leaves B's token in place, goes red; (c) drop `ex=60` → a TTL assertion (`ttl(LOCK_KEY) > 0`)
goes red. Three mutations.
*When the check cannot run:* if Redis is unreachable, `_acquire_lock` must raise or return False and
the worker must back off — never treat a Redis error as "lock acquired", which is what a bare
`except` around the `get` would produce.
*Preserve:* the worker must still be able to run at all after an unclean shutdown; the TTL is what
provides that, do not remove it in favour of an explicit-release-only design.
*Boundary/tie:* a lock whose TTL has expired at exactly the moment of release — the compare-and-delete
above resolves the tie by doing nothing, which is correct; say so.

### Major: `in_flight` is a non-terminal state with no failure exit and no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `_finish`
What is wrong: `_claim_batch` is the only writer into `in_flight` and `_finish` is the only writer
out of it, and `_finish` is reached only on the success or exhausted-retries path — a worker crash,
an OOM kill, a deploy restart, or any of the exceptions catalogued above leaves rows in `in_flight`
forever, and `_claim_batch` selects only `status == "pending"` (R38 part 1: transient state with no
failure exit and no bounded timeout).
What breaks in production: Every worker restart permanently strands the in-flight batch (up to 100
deliveries); the customer never receives those events, the delivery row shows `in_flight` with
`attempts` still at its pre-claim value, and nothing retries or alerts.
Fix: Add a claim deadline and a reaper. Give `webhook_deliveries` a `claimed_at TIMESTAMPTZ` column
set at claim time, and reclaim on the next pass:
```python
.filter(
    or_(
        m.WebhookDelivery.status == "pending",
        and_(m.WebhookDelivery.status == "in_flight",
             m.WebhookDelivery.claimed_at < now - CLAIM_TIMEOUT),
    ),
    m.WebhookDelivery.next_attempt_at <= now,
)
```
with `CLAIM_TIMEOUT` strictly greater than `REQUEST_TIMEOUT` plus the total backoff budget, and
increment `attempts` on reclaim so a poison delivery still terminates at `MAX_ATTEMPTS` rather than
being reclaimed forever.
*Still must pass (deny+allow):* a delivery genuinely in flight must NOT be reclaimed — assert that a
row claimed 1 second ago is invisible to a second `_claim_batch`, alongside the assertion that a row
claimed `CLAIM_TIMEOUT + 1` seconds ago is reclaimed. A reaper with a zero timeout satisfies the
recovery side and reintroduces double-sends.
*Red-prove:* (a) remove the `claimed_at < now - CLAIM_TIMEOUT` branch → the stranded-row recovery test
goes red; (b) remove the `attempts` increment on reclaim → a test asserting a permanently-crashing
delivery reaches `failed_permanent` within `MAX_ATTEMPTS` reclaims goes red (bound the loop so it
terminates instead of hanging). Two mutations.
*When the check cannot run:* if `claimed_at` is NULL on a legacy `in_flight` row, treat it as
reclaimable and log that the row predates the column — do not skip it silently, which is the current
behaviour under a different name.
*Preserve:* the single-claim guarantee within the timeout window; do not fix by removing `in_flight`
and letting any worker claim any pending row.
*Boundary/tie:* a row whose `claimed_at` is exactly `now - CLAIM_TIMEOUT` — pick `<` (not reclaimed)
and pin it, so the reaper and the deliverer never contend at the boundary.

### Major: `asyncio.gather` without `return_exceptions` terminates the worker on the first non-HTTP error
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`

```python
    body = b'{"a": 1}'
    ts = "1700000000"
    expected = "sha256=" + hmac.new(SECRET.encode(), b"1700000000." + body,
                                    hashlib.sha256).hexdigest()
    assert signing.sign(SECRET, body, ts) == (ts, expected)
```
and add the producer→consumer round trip R40 requires: capture the bytes and headers `send_once`
actually transmits via `MockTransport` and feed them through the real `verify`. Replace `FakeEndpoint`
/`FakeDelivery` with real `WebhookEndpoint`/`WebhookDelivery` instances so the test loads what
production loads.
*Still must pass (deny+allow):* the independently computed expected value must MATCH for the correct
secret and body — that is the allow side; the wrong-secret and stale-timestamp cases are the deny
side. A test that only asserts inequality passes against a `sign` returning a constant.
*Red-prove:* (a) drop the timestamp from `sign`'s MAC input → the literal-expectation test goes red
(the current self-referential test stays green — run both to demonstrate the difference); (b) swap
`content=body` for `json=payload` in `send_once` → the captured-bytes round trip goes red. Two
mutations.
*When the check cannot run:* if `MockTransport` captures no request (handler never invoked), the test
must fail on an explicit `assert captured` rather than KeyError-ing on `captured["body"]` — the
current tests would raise `KeyError`, which reads as an error rather than as "nothing was sent".
*Preserve:* the existing wrong-secret rejection case; it is weak, not wrong.
*Boundary/tie:* a payload with keys in a different insertion order must produce an IDENTICAL signature
(that is what `sort_keys=True` buys) — `test_verify_accepts_signature_produced_by_sign` passes
`{"b": 2, "a": 1}` and should assert equality against the `{"a": 1, "b": 2}` signature explicitly.

### Major: `organizations.webhooks_enabled` is added by the migration and read by nothing
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE;`
What is wrong: The column declares a per-org feature gate, but no code in the change consults it —
`create_webhook_endpoint` does not check it before issuing a secret and `enqueue_for_event` does not
check it before creating deliveries (R41: a declared capability with no backing path).
What breaks in production: Operations will reasonably believe webhooks are off by default (the column
defaults to FALSE) and are gated per org, when in fact every organization can register an endpoint and
receive live billing events the moment this deploys — a feature flag that grants nothing is worse
than no flag, because a rollback of the flag changes nothing.
Fix: Either wire it or drop it. To wire it, check it at both boundaries — 403 in
`create_webhook_endpoint` when `org.webhooks_enabled` is false, and an `Organization.webhooks_enabled`
join predicate in `enqueue_for_event`'s endpoint query — and flip the default only when the rollout
decision is made. To drop it, remove the `ALTER TABLE` from this migration.
*Still must pass (deny+allow):* an org with `webhooks_enabled = TRUE` must still register endpoints
and still receive deliveries — assert that alongside the 403 for a disabled org. A gate that denies
everyone satisfies the deny side and takes the feature down.
*Red-prove:* (a) remove the route's flag check → the disabled-org 403 test goes red; (b) remove the
join predicate in `enqueue_for_event` → a test asserting a disabled org with a pre-existing active
endpoint gets zero delivery rows goes red. Two mutations — note (a) alone leaves (b) open, which is
precisely why both sites need their own.
*When the check cannot run:* if the `Organization` row cannot be loaded, deny with a named 503 rather
than defaulting to enabled.
*Preserve:* existing enabled orgs must not be disabled by the change.
*Boundary/tie:* an org flipped from TRUE to FALSE while deliveries are already `pending` — state
whether in-flight deliveries drain or are cancelled; the join predicate above cancels them, which may
not be what operations expects.

### Minor: `docs/webhooks.md` makes four claims the implementation does not support
File: `docs/webhooks.md` — the "Registering an endpoint", "Verifying the signature" and "Retries" sections
What is wrong: Beyond the https-only and at-least-once claims already covered above, the doc states
"backoff is exponential with jitter" (`backoff_for` returns `2**attempt` exactly, with no jitter — and
`test_backoff_grows_exponentially` pins the exact values, so the doc and the test contradict each
other), and "a 4xx is permanent and we stop immediately" (`deliver` retries every non-2xx status,
including 400 and 401, the full five times). It also says an empty `event_types` subscribes "to every
event type we emit", when `dispatch` only reaches the webhook path for the three types in
`WEBHOOK_EVENT_TYPES` (R29: rationale and derived-claim accuracy).
What breaks in production: Customers size their retry-absorbing infrastructure against a jittered
schedule that does not exist, so all our retries for a given event land in the same instant across
customers; and a customer returning 401 during a credential rotation absorbs five identical POSTs
instead of one.
Fix: Implement the two behavioural claims rather than editing them away — add jitter
(`timedelta(seconds=BASE_DELAY_SECONDS**attempt * random.uniform(0.8, 1.2))`, using `random` here is
correct since this is not key material) and add `if 400 <= response.status_code < 500 and
response.status_code != 429: _finish(..., "failed_permanent", ...); return`. Then correct the third
claim to name the three emitted types explicitly.

### Minor: `create_webhook_endpoint` returns 201 before its transaction commits
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `session.flush()` then `return endpoint.to_dict()`
What is wrong: The response is built from a flushed-but-uncommitted row, so a commit failure at

diagnosable cause.

explicitly before serializing.

## Cross-cutting verification

- **Tenancy predicate** — present in `list_webhook_endpoints` and `enqueue_for_event`, ABSENT in
  `list_deliveries`. That is the missed location (reported Critical, first finding).
- **Status literals** — spelled in five places: `models.STATUSES`, the `status` column default
  `"pending"`, `_claim_batch`'s `"in_flight"`, `deliver`'s `"delivered"`/`"failed_permanent"`, and the
  SQL `CHECK`. One has drifted (`failed` vs `failed_permanent`).
- **Timestamp construction** — three spellings of "now in UTC": `models._now()`,
  `datetime.now(timezone.utc)` inline in `_claim_batch` and `_finish`, and naive `datetime.utcnow()`
  in `enqueue_for_event`. Only the last is wrong, but the helper the change itself defines is used at
  none of the three delivery-module sites.
- **Column timezone** — all six datetime columns are `DateTime(timezone=True)` in `models.py` and
  `TIMESTAMP` (naive) in the migration. Six paired mismatches, not one.
- **Session-scope escape** — ORM instances outlive their `session_scope` at two sites: `_claim_batch`'s
  `return rows` and `deliver`'s `endpoint` load. `enqueue_for_event` does it correctly (`return len(rows)`),
  which is the in-diff precedent for the fix.
- **`to_dict` secret exposure** — reaches two routes (`create_webhook_endpoint`,
  `list_webhook_endpoints`); fixing only the list route leaves the model itself unsafe for any third
  caller.
- **Doc-vs-code claims** — five independent divergences (https-only, jitter, 4xx-permanent,
  at-least-once, "every event type we emit"), all in one 38-line file; each needs its own fix, they do
  not share a root cause.

## Codebase awareness

Helpers the new code reimplements, with evidence from the diff itself:
- `app/webhooks/models.py::_now()` returns exactly `datetime.now(timezone.utc)`; `delivery.py` never
  imports it and open-codes the same expression twice, and gets it wrong a third time.
- `app/webhooks/signing.py::serialize()` is the canonical body serializer, and `send_once` bypasses it
  for the wire body (`json=delivery.payload`) while using it for the MAC — the helper exists and the
  producer path does not adopt it.
- `enqueue_for_event`'s `return len(rows)` is the correct session-boundary discipline already present
  in the same module that `_claim_batch` and `deliver` violate.
- `WEBHOOK_EVENT_TYPES` in `dispatcher.py` is the authoritative eligible-type set; the route that
  accepts `event_types` does not import it, though `settings.py` already imports from
  `app.webhooks.models` and `app.webhooks.signing`.
- No rate limiter, SSRF guard, or retry/backoff helper appears anywhere in the diff, so the fixes
  above do not assume one exists; where such a helper may exist outside the change, I have said so
  and marked it a question rather than a requirement.
