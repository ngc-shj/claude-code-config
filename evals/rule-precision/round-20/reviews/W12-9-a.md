### Critical: `list_deliveries` has no tenancy predicate — any authenticated user reads any org's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The query filters only on the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while its sibling `list_webhook_endpoints`, added in the same hunk, does filter on `org_id`.
What breaks in production: Any authenticated customer can enumerate `endpoint_id` integers and read every other organization's delivery history — event ids, event types, response codes and schedule — a cross-tenant data breach reachable from a single GET.
Fix: Join the delivery query to `WebhookEndpoint` and filter on both — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and raise `HTTPException(404)` when the endpoint row does not exist *or* is not owned, so a probe cannot distinguish the two. Preserve the behaviour the route exists for: the owning org must still get its own deliveries, newest first, so pin an allow case — org A's user requesting org A's endpoint receives exactly the rows enqueued for it (assert the returned ids, not just a 200). Red-prove each clause separately by execution: (i) delete the `org_id` predicate and watch the cross-tenant test go red on returned ids; (ii) delete the `id == endpoint_id` predicate and watch the same-org test go red by returning a second endpoint's rows; (iii) point the fixture at an endpoint id that does not exist and watch the 404 assertion go red if the handler returns 200 with `[]`. Fail loudly when the check cannot run: if `user.org_id` is None, deny with 403 rather than letting the filter degrade to a match-nothing (or match-anything) comparison — "no org resolved" must not be spelled the same as "org matched". Boundary and tie: an endpoint that exists but is `active=False` still belongs to its org and must remain readable (deactivating an endpoint must not hide its failure history), and an `endpoint_id` of `0` or a negative integer takes the same 404 path as an unknown id.

### Critical: the signing secret is returned on every list call, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret"`; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` embeds `signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so the secret is readable on every `GET /v1/settings/webhook-endpoints` even though `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: The webhook secret becomes a routinely-served, routinely-logged, routinely-cached response field, so any read-scoped token, browser cache, proxy log or support screenshot yields the key that forges signed events into a customer's system (RS4 Critical: an identifier that alone grants access).
Fix: Drop `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally-held plaintext, so exactly one code path can emit it; store only a hash or an envelope-encrypted value in the column if the secret never needs re-display. Do not fix this by deleting the list route or by removing the secret from the create response — the documented one-time disclosure is the feature and must be preserved. Pair deny with allow: assert the create response *does* contain a `whsec_`-prefixed secret (the allow case) and that the list and deliveries responses contain no key matching `signing_secret` and no value matching `whsec_` (the deny case). Red-prove separately: (i) re-add the key to `to_dict()` — the list assertion reddens; (ii) drop the merge in `create_webhook_endpoint` — the create assertion reddens; run both mutations singly. Fail loudly when the check cannot run: make the response-scrubbing assertion walk the serialized JSON rather than the dict, and fail the test if the response body is empty or unparseable, so "nothing to scan" cannot pass as "nothing leaked". Boundary and tie: the same scrub applies to any future endpoint that serializes a `WebhookEndpoint`, and to the error path — a 422 or 500 raised after `new_signing_secret()` must not echo the generated value in `detail`.

### Critical: the HMAC is computed over bytes that are never sent, and omits the timestamp the docs make load-bearing
File: `app/webhooks/signing.py` — `sign`/`serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` while `send_once` transmits `client.post(..., json=delivery.payload)`, whose httpx-produced bytes use different key order and separators, and the MAC input excludes the timestamp although `docs/webhooks.md` specifies the signature as `HMAC-SHA256("{timestamp}.{raw_request_body}")`.
What breaks in production: Every receiver implemented from the published documentation computes a different digest and rejects 100% of deliveries, and a receiver that instead reproduces `serialize()` still gets a signature that is valid for the payload forever, because no timestamp is bound into it and a captured request replays past any window the receiver enforces (R40: producer wire shape versus strict consumer; the same team owns both sides, so nothing forces the round trip).
Fix: Serialize exactly once and sign the bytes that go on the wire — in `sign`, take `body: bytes`, compute `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, and in `send_once` build `body = serialize(delivery.payload).encode()`, then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` so the signed bytes and the transmitted bytes are one object. Give `verify(secret, body, timestamp, signature)` the same signature and have it recompute from the caller-supplied timestamp rather than from `time.time()`. Preserve what makes the feature useful: the payload must still arrive as valid JSON with `Content-Type: application/json`, so keep the header explicit now that httpx no longer sets it. Pair deny with allow: the allow case is a round-trip test that captures the *actual* request bytes from `MockTransport` and feeds them plus the captured `X-Acme-Timestamp` through `verify`, asserting True — the actual-producer-output-through-actual-consumer round trip R40 requires, not two independently constructed strings. Red-prove each clause by execution: (i) flip one byte of the captured body before verifying — the round-trip assertion reddens; (ii) pass a timestamp one second off — reddens, proving the timestamp is inside the MAC; (iii) re-serialize inside `sign` instead of using the passed bytes — reddens on a payload with keys out of sorted order. Fail loudly: if `serialize` raises on a non-JSON-serializable payload, let it propagate and mark the delivery `failed_permanent` with a named reason; a payload that cannot be serialized must not be silently posted unsigned. Boundary and tie: state the receiver's window explicitly — a timestamp exactly `now - 300` is accepted and `now - 301` rejected — and document that two deliveries signed in the same second produce different digests only because their bodies differ, so the timestamp is not a nonce.

### Critical: `verify` compares HMACs with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The recomputed digest is compared to the caller-supplied one with Python's short-circuiting `str.__eq__` instead of `hmac.compare_digest` (RS1).
What breaks in production: `verify` is the reference implementation shipped for anyone who runs this code on the receiving side, so a caller-controlled signature can be recovered byte-by-byte through response-timing differences and used to forge signed webhook events.
Fix: `return hmac.compare_digest(expected, signature)`, and normalise both operands to `str` before the call so a `bytes`/`str` mix raises `TypeError` rather than silently returning False. Preserve the accept path: keep an allow case asserting a correctly signed payload still verifies True — a fix that always denies satisfies the timing requirement and destroys the feature. Red-prove each clause: (i) revert to `==` and assert with a linter or an AST check over `signing.py` that no `==` remains on a variable named `signature`/`expected` — reddens; (ii) corrupt the last hex character of a valid signature and assert `verify` returns False — reddens if `compare_digest` were replaced by a constant `True`; (iii) pass a `bytes` signature and assert `TypeError` — reddens if the operands are coerced. Fail loudly: a `None` or empty-string signature must return False through the same constant-time path rather than raising, and an unparseable `sha256=` prefix must be rejected explicitly, not fall through. Boundary and tie: a signature of the correct 71-character length but wrong content and one of the wrong length must both take the same time and the same path — `compare_digest` leaks length, so compare only after both sides are known to be the fixed-width hex form.

### Critical: signing secrets come from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The secret is drawn from `random`, the Mersenne Twister PRNG, whose internal state is fully recoverable from 624 observed outputs and whose seeding is not cryptographically strong.
What breaks in production: An attacker who registers a handful of endpoints of their own recovers the generator state and predicts every other organization's signing secret, letting them forge signed `invoice.paid` events into any customer's system.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, drop `random`, `string` and `_ALPHABET`), and rename `SECRET_BYTES` to match what it now means — the current constant is named "bytes" while `random.choice` consumes it as a *character* count, which is exactly the kind of unit drift that survives a rename. Preserve the caller contract: the `whsec_` prefix and the `startswith` assertion in `test_new_signing_secret_has_prefix_and_length` must keep passing; update its length assertion to `len(secrets.token_urlsafe(32))` rather than deleting it — dropping the assertion is not fixing it. Pair deny with allow: assert two successive calls differ (the allow case for randomness) *and* assert the module no longer imports `random` (an AST or import check, since a value test cannot distinguish the two generators). Red-prove separately: (i) restore `import random` — the import assertion reddens; (ii) make `new_signing_secret` return a constant — the distinctness assertion reddens; (iii) strip the prefix — the prefix assertion reddens. Fail loudly: `secrets.token_urlsafe` raises rather than degrading if the OS entropy source is unavailable, and that exception must propagate out of `create_webhook_endpoint` as a 500 — an endpoint must never be created with a weak or empty secret. Boundary and tie: `SECRET_BYTES = 32` yields 256 bits before encoding; state that as the floor and reject any later reduction below it, and note that two endpoints sharing a secret value is not merely improbable but must be treated as a defect if ever observed.

### Critical: the migration's status CHECK constraint does not admit the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, against `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`

What breaks in production: The first delivery to exhaust its retries raises an `IntegrityError` inside `_finish`, the row is never moved out of `in_flight`, and because `run_worker` calls `asyncio.gather` without `return_exceptions=True` the exception escapes the worker loop and kills the dispatcher process.

Preserve the constraint itself: do not fix this by dropping the CHECK — the constraint is what keeps a typo'd status out of the table. Pair deny with allow: assert a delivery transitioned to `failed_permanent` commits (allow) *and* that a write of `'failed'` or `'FAILED'` is rejected by the database (deny). Red-prove each separately: (i) revert the migration literal to `'failed'` — the allow case reddens with an IntegrityError; (ii) add a stray member to `STATUSES` — the set-equality test reddens; (iii) change `_finish`'s literal to `'dead'` — the allow case reddens. Fail loudly: if the equality test cannot locate the constraint (migration renamed, table absent), it must fail with a message naming what it could not find, not skip — "constraint not found" must not report the same as "constraint matches". ### Critical: `UNIQUE (event_id)` allows only one endpoint per event
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: The uniqueness is on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint via `session.add_all(rows)`, so an org with two subscribed endpoints violates the index on the very first fan-out.
What breaks in production: The whole `add_all` fails, the dispatcher's blanket `except Exception` downgrades it to `log.warning`, and the event is delivered to *zero* endpoints instead of two — a silent total-path failure for exactly the customers who configured redundancy.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the key that actually expresses the intended idempotency ("one delivery per endpoint per event", the guarantee `docs/webhooks.md` tells consumers to deduplicate on). Preserve the deduplication the original index was reaching for: the pair must stay UNIQUE so a re-run of `enqueue_for_event` for the same event cannot double-deliver — do not fix this by deleting the index. Pair deny with allow: assert two endpoints in one org both receive a row for one event (allow, and assert `len(rows) == 2`, a positive cardinality, not merely "no exception"), and assert that calling `enqueue_for_event` twice for the same `(endpoint, event)` raises or no-ops rather than inserting a second row (deny). Red-prove separately: (i) revert to `UNIQUE (event_id)` — the two-endpoint allow case reddens; (ii) drop the index entirely — the double-enqueue deny case reddens; (iii) make `enqueue_for_event` skip endpoints whose `event_types` is empty — the allow case reddens on cardinality. Fail loudly: give `enqueue_for_event` an explicit `ON CONFLICT DO NOTHING` and have it return the count actually inserted, so a caller can tell "zero endpoints subscribed" from "insert suppressed" — those must not share a return value. Boundary and tie: an endpoint deactivated between two enqueues of the same event still holds its unique pair and must not be resurrected; state that the pair, not `event_id`, is what a consumer's dedup key corresponds to.

### Critical: `deliver` blocks the event loop with `time.sleep`
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)` inside the retry `while True`
What is wrong: A synchronous `time.sleep` is called from an `async def` that `run_worker` schedules through `asyncio.gather`, while the same file's `run_worker` correctly uses `await asyncio.sleep(poll_interval)` — the async idiom already exists three lines away and `deliver` reimplements it wrongly (R1).
What breaks in production: One slow customer endpoint freezes the entire process for up to 30 seconds per delivery (2+4+8+16), serialising a 100-row batch into hours of wall clock, stalling every other coroutine in the process including the Redis lock renewal, and letting the 60-second lock TTL lapse mid-batch so a second worker re-delivers the same events.
Fix: Do not retry in-process at all — replace the `while True` loop with a single attempt that, on failure, writes `attempts = attempt`, `status = "pending"`, `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` and returns, so the retry lives in the durable queue that `_claim_batch` already polls and survives a restart; keep `_finish(..., "failed_permanent", ...)` for `attempt >= MAX_ATTEMPTS`. If an in-process retry is kept for other reasons, it must at minimum be `await asyncio.sleep(delay)`. Preserve the retry policy itself: at most `MAX_ATTEMPTS` attempts with the same exponential schedule — moving retries to the queue must not silently become one-shot delivery. Pair deny with allow: assert a delivery that succeeds on the second attempt ends `delivered` with `attempts == 2` (allow), and assert a delivery failing five times ends `failed_permanent` and is never claimed again (deny). Red-prove each separately by execution: (i) restore `time.sleep` and assert with a wall-clock bound that a two-delivery batch of failing endpoints completes in under one backoff period — reddens; (ii) drop the `next_attempt_at` update — the "retried after backoff, not immediately" assertion reddens; (iii) drop the `MAX_ATTEMPTS` guard and bound the loop so the test terminates red rather than hanging — the attempts-cap assertion reddens. Fail loudly: an exception type not covered by `except httpx.HTTPError` (a `ValueError` from serialization, the `IntegrityError` above) must be caught, recorded on the row with its type name, and re-raised into a logged worker-level handler — it must not escape `gather` and stop the loop. Boundary and tie: state that `attempt == MAX_ATTEMPTS` is the last attempt made (not the first one skipped), and that two deliveries whose `next_attempt_at` is the same instant are both claimed by the same batch.

### Critical: registered webhook URLs are unvalidated against internal addresses, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check on a caller-supplied URL is a `startswith("http")` prefix test and a non-empty netloc, so `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:6379/` and `http://db-internal:5432/` are all accepted, and `follow_redirects=True` means even an allowlisted host can bounce the request to any of them (RS3 Critical: an unvalidated boundary value reaching an interpreter — here, an HTTP client with network position inside the perimeter).
What breaks in production: A customer registers an endpoint pointing at the cloud metadata service or an internal admin port and receives its response body persisted verbatim in `response_body`, readable through the deliveries API — a full server-side request forgery with a built-in exfiltration channel; separately, `http://` acceptance contradicts `docs/webhooks.md` ("Only `https://` URLs are accepted") and ships signed customer event payloads in plaintext.
Fix: Validate at the schema boundary with a `pydantic` validator on `EndpointIn.url` that requires `parsed.scheme == "https"` (exact equality, not `startswith`), a non-empty hostname, no userinfo, no non-standard port outside `{443}` unless explicitly allowed, and a length cap; then resolve the hostname and reject any address in a loopback, link-local, private, multicast, or reserved range via `ipaddress.ip_address(...).is_global` over every A/AAAA record. Re-run the same address check at delivery time immediately before the request and set `follow_redirects=False`, because DNS can be re-pointed between registration and delivery and a 302 otherwise bypasses the registration-time check entirely. Preserve what makes the feature useful: a legitimate public HTTPS endpoint on a CDN with several rotating public addresses must still be accepted and delivered to — pin that as the allow case with a fixture resolving to a public address. Red-prove each clause separately by execution: (i) `http://hooks.example.com/x` returns 422 — reddens if `startswith` is restored; (ii) `https://127.0.0.1/x` returns 422 — reddens if the address check is removed; (iii) a public endpoint that 302-redirects to `http://169.254.169.254/` results in a failed delivery with no request issued to the redirect target — reddens if `follow_redirects=True` is restored; (iv) the public-address allow case still returns 201 and delivers — reddens if the validator over-blocks. Fail loudly when the check cannot run: DNS resolution failure, an empty answer, or an unparseable address must reject the registration and fail the delivery with a named reason ("could not resolve"), never fall through to "no disallowed address found". Boundary and tie: state the sides explicitly — `100.64.0.0/10` (CGNAT) and IPv4-mapped IPv6 forms are rejected, a hostname resolving to *both* a public and a private address is rejected rather than accepted on the public one, and an endpoint that resolved publicly at registration but privately at delivery is failed, not delivered.

### Major: `in_flight` is a non-terminal state with no reclaim path, and attempt progress is never persisted
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `deliver`
What is wrong: `_claim_batch` commits `in_flight` and only `_finish` ever moves a row out of it, so a worker crash, a container restart, or any exception not caught by `except httpx.HTTPError` strands the row permanently, and because `attempts` is written only by `_finish` the in-process retry counter is lost with the process (R38, non-terminal transient state, persisted across restart).
What breaks in production: Deliveries silently stop for the affected events with no alert and no operator affordance — nothing in the diff ever selects `status == "in_flight"` — and a restart mid-retry resets the attempt count so a permanently broken endpoint is retried forever in bursts.
Fix: Add a lease instead of a bare status flag: give `webhook_deliveries` a `claimed_until TIMESTAMPTZ` column set to `now() + lease` when a row is claimed, have `_claim_batch` select `status = 'pending' OR (status = 'in_flight' AND claimed_until < now())`, and persist `attempts` on every attempt rather than only at terminal state. Add a bounded overall timeout so a hung `httpx` call cannot hold a lease indefinitely. Preserve the guarantee the `in_flight` flag was providing: two concurrent workers must still not deliver the same row at the same moment, so the claim must be a conditional `UPDATE ... WHERE status = 'pending' ... RETURNING` (or `SELECT ... FOR UPDATE SKIP LOCKED`), not a read followed by a write. Pair deny with allow: assert a healthy delivery still moves `pending → in_flight → delivered` and is *not* reclaimed while its lease is live (allow), and assert a row abandoned in `in_flight` past its lease is reclaimed exactly once (deny side of the reclaimer). Red-prove separately: (i) remove the lease-expiry clause from the claim query — the reclaim test reddens; (ii) remove the `claimed_until` write — the "not reclaimed while live" test reddens by double-claiming; (iii) revert `attempts` persistence to `_finish` only — the "attempt count survives a simulated restart" test reddens. Fail loudly: if the reclaimer finds a row whose `claimed_until` is null while `status = 'in_flight'` (a row written by the pre-lease code), it must log and reclaim rather than skip it silently. Boundary and tie: a row whose `claimed_until` is exactly `now()` is treated as expired and reclaimable, and two workers reaching the same expired row resolve it by the conditional update — exactly one wins.

### Major: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after the `with session_scope()` block) and `deliver` (`endpoint` read outside its `with` block, then `endpoint.url` / `endpoint.signing_secret` in `send_once`)
What is wrong: Both functions return or hold SQLAlchemy entities past the end of their `session_scope()`, then read attributes off them (`delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.url`, `endpoint.signing_secret`), which requires a live session to refresh once the session commits and expires them.
What breaks in production: The first attribute access after commit raises `DetachedInstanceError` and every delivery fails before a request is ever made, leaving the batch stranded in `in_flight` per the previous finding.
Fix: Stop passing entities across session boundaries — have `_claim_batch` return plain data (a list of `dataclass` or dict rows with `id`, `endpoint_id`, `attempts`, `payload`), and have `deliver` read the endpoint's `url` and `signing_secret` into locals inside its own `with session_scope()` block before the request. This also removes the null hazard: `session.get(m.WebhookEndpoint, delivery.endpoint_id)` returning `None` for a deleted endpoint currently reaches `send_once` and raises `AttributeError`. Preserve the batching: `_claim_batch` must still claim and return up to `BATCH_SIZE` rows in one transaction. Pair deny with allow: assert a full `pending → delivered` path runs end to end against a real session with `expire_on_commit` at its production setting (allow), and assert a delivery whose endpoint row was deleted is marked `failed_permanent` with a named reason rather than raising (deny). Red-prove separately: (i) return entities from `_claim_batch` again — the end-to-end test reddens with `DetachedInstanceError`; (ii) remove the `None` check on the endpoint lookup — the deleted-endpoint test reddens with `AttributeError`; (iii) set `BATCH_SIZE` to 1 with two claimable rows — the cardinality assertion reddens. Fail loudly: a missing endpoint must produce a recorded terminal status naming "endpoint deleted", not an unhandled exception and not a silent skip. Boundary and tie: exactly `BATCH_SIZE` claimable rows yields one full batch and an empty second claim; a row deleted between claim and finish must leave `_finish` logging a miss rather than raising on `row.status`.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does a `GET` then a separate `SET` (a check-then-act race two workers both win), the `SET` and `EXPIRE` are two round trips (a crash between them leaves a lock with no TTL), and the release deletes the key by name without checking ownership.
What breaks in production: Two workers process the same batch concurrently and double-deliver, or a crash mid-acquire deadlocks all workers forever with no expiry, or a worker that overran the 60-second TTL deletes the lock a *different* worker now holds and hands a third worker the same batch.
Fix: Acquire with a single atomic command carrying a unique token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = secrets.token_hex(16)` — release with a Lua compare-and-delete (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`), and renew the lease periodically while the batch runs so a long batch never silently loses it. Preserve the concurrency the lock exists to allow: a second worker must still acquire the lock promptly once the holder releases it — pin that as the allow case, not just the mutual-exclusion deny case. Red-prove each clause separately by execution: (i) revert to `GET`+`SET` and run two `_acquire_lock` calls interleaved at the `GET` — the mutual-exclusion assertion reddens with both returning True, and assert a positive cardinality (exactly one True out of N) rather than "no double delivery observed" so the test cannot pass with zero contention; (ii) drop the `ex=60` — the "lock expires after a crashed holder" assertion reddens; (iii) release with a bare `delete` — the "worker B's lock survives worker A's release" assertion reddens. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise or return False and the worker must back off — an exception swallowed into "lock acquired" would run every worker unguarded. Boundary and tie: a holder whose TTL expires at the exact moment it finishes must not delete the successor's lock (the token comparison decides this), and two workers presenting tokens at the same instant resolve by `NX` — exactly one wins.

### Major: `run_worker` can die on an unbound name, and `gather` swallows nothing
File: `app/webhooks/delivery.py` — `run_worker`, `if not batch:` after the `try/finally`
What is wrong: `batch` is assigned inside the `try`, so if `_claim_batch` raises, the `finally` runs and control reaches `if not batch` with the name unbound, raising `NameError` out of the `while True` loop; separately `asyncio.gather` without `return_exceptions=True` propagates the first delivery exception and abandons the rest mid-flight.
What breaks in production: A single transient database error permanently stops the webhook worker with no retry and no restart logic anywhere in the diff, and every delivery still in flight when a sibling raises is left in `in_flight`.
Fix: Initialise `batch: list = []` before the `try`, wrap the loop body in `try/except Exception` that logs with the exception type and continues after a backoff, and call `asyncio.gather(*tasks, return_exceptions=True)` then inspect the results and record a terminal status for each exception rather than discarding it. Preserve the loop's liveness: the worker must still exit promptly on cancellation, so let `asyncio.CancelledError` propagate rather than catching it under the bare `Exception`. Pair deny with allow: assert the worker keeps processing after `_claim_batch` raises once (allow — a subsequent batch is still delivered), and assert a raising delivery does not stop its siblings from completing (deny side of the isolation). Red-prove separately: (i) remove the `batch = []` initialisation and make `_claim_batch` raise — the "worker survives" test reddens with `NameError`; (ii) drop `return_exceptions=True` — the sibling-completion test reddens; (iii) catch `CancelledError` in the broad handler — the "worker stops on cancel" test reddens by hanging, so bound it with a timeout that fails rather than blocks. Fail loudly: each swallowed loop exception must be logged at ERROR with its type and the batch size, and a run of consecutive failures must escalate rather than loop silently — "processed nothing" must not look like "nothing to process". Boundary and tie: an empty batch and a failed claim both lead to a sleep, and they must be distinguishable in the logs; state which of the two the metric counts.

### Major: the dispatcher swallows enqueue failures, so an event can be recorded with no delivery rows and no reconciliation

What is wrong: Every failure of `enqueue_for_event` — the unique-index violation above, a database error, a serialization error — is downgraded to a warning and `dispatch` returns the event id as though delivery were arranged, and nothing in the diff ever reconciles `events` against `webhook_deliveries` (R36: a markerless weakening standing in for handling).
What breaks in production: Customers silently miss events with no failure signal on either side, and because the event row is already committed there is no queue to drain and no way to discover which events were lost.

Narrow the `except` to the exception types that are genuinely recoverable and let the rest propagate. Preserve the property the broad catch was protecting: a webhook failure must still not roll back or block the in-process subscribers, so the in-process path stays ahead of the enqueue and the enqueue failure must not raise into `dispatch`'s callers. Pair deny with allow: assert a normal deliverable event ends with `webhooks_enqueued_at` set and rows present (allow), and assert an event whose enqueue raised ends with the marker null and is picked up by the reconciler on its next pass (deny). Red-prove separately: (i) delete the marker write — the reconciler test reddens by re-enqueuing an already-enqueued event; (ii) delete the reconciler's null predicate — the same test reddens by re-enqueuing everything; (iii) restore the bare `log.warning` — the "failure is discoverable" assertion reddens. Boundary and tie: an event enqueued at exactly the reconciler's threshold is not re-enqueued twice — the `(endpoint_id, event_id)` unique pair from the earlier finding is what makes a double pass safe, so state that dependency.

### Major: two disjoint definitions of "deliverable event type", and `event_types` is never validated

### Major: the documented retry semantics do not match the implementation
File: `docs/webhooks.md` — the "Retries" section, against `app/webhooks/delivery.py` `backoff_for` and `deliver`
What is wrong: The docs promise "exponential with jitter" while `backoff_for` returns exactly `2**attempt` seconds with no jitter, and promise "a 4xx is permanent and we stop immediately" while `deliver` retries every non-2xx response including 400, 401, 404 and 410 up to `MAX_ATTEMPTS` (R49: a claim stronger than the implementation; the doc is the contract customers build against).
What breaks in production: Every delivery for a shared outage retries on exactly the same schedule, so a customer endpoint coming back up is hit by a synchronised thundering herd; and a permanently-rejecting endpoint receives five attempts of every event instead of one, multiplying load on an integration that has already said no.
Fix: Implement both documented behaviours rather than weakening the doc: add full jitter (`random.uniform(0, 2**attempt)` via `secrets`-independent `random` is acceptable here since it is not security material, but state that in a comment) and branch on the response class in `deliver` — `4xx` other than `408` and `429` goes straight to `failed_permanent`, `429` honours `Retry-After`, `5xx`/timeout/connection errors retry. Preserve the retry budget: `MAX_ATTEMPTS` must still cap the retried classes, and the existing `test_max_attempts_matches_documented_limit` must keep passing. Pair deny with allow: assert a 500 is retried and eventually succeeds (allow) and assert a 404 is *not* retried, ending `failed_permanent` with `attempts == 1` (deny). Red-prove each separately: (i) remove the 4xx branch — the 404 test reddens on `attempts`; (ii) remove the `429` exception to that branch — the rate-limit test reddens; (iii) remove jitter and assert two concurrent deliveries' delays differ — reddens; note that `test_backoff_grows_exponentially` asserts exact equality and must be rewritten as a range assertion (`0 < delay <= 2**attempt`) rather than deleted. Fail loudly: an unparseable `Retry-After` must fall back to the computed backoff and log that it did, not be treated as zero. Boundary and tie: state which side each status boundary falls on — `399` and `400` are non-2xx, `200` and `299` are success, `408`/`429` are retried, and a response with no status (a connection error) takes the retry path.

### Major: `webhooks_enabled` is added to the schema and never read
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: The migration declares an org-level capability flag that no code in the diff consults — `create_webhook_endpoint`, `dispatch` and `enqueue_for_event` all proceed regardless (R41: a declared capability with no backing path).

### Major: unbounded endpoint registration multiplies outbound requests per event
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `enqueue_for_event`, which iterates every active endpoint of the org
What is wrong: Nothing in the change caps how many endpoints an organization may register, and `enqueue_for_event` creates one delivery per active endpoint, so the fan-out per event is entirely caller-controlled.
What breaks in production: A single account registering thousands of endpoints turns each event into thousands of outbound POSTs from the shared worker, exhausting the batch, the connection pool and the deliveries table for every other tenant.
Fix: Enforce a per-org endpoint cap in `create_webhook_endpoint` — count active endpoints for `user.org_id` inside the same `session_scope()` and raise `HTTPException(409, detail="endpoint limit reached")` at the limit — and make the constant (`MAX_ENDPOINTS_PER_ORG`) shared with any docs that state it. Preserve legitimate multi-endpoint use: registering the second and third endpoint must still succeed, pinned as the allow case, since a cap that rejects everything satisfies the requirement and breaks the feature. Red-prove separately: (i) remove the cap — the "N+1th registration is rejected" test reddens; (ii) count all endpoints instead of active ones (or vice versa) — a test registering up to the cap, deactivating one, and registering again reddens on whichever semantics is chosen; (iii) set the cap to 0 — the allow case reddens. Fail loudly: if the count query fails, deny the registration rather than proceeding uncapped. Boundary and tie: state which side the cap falls on — the Nth registration succeeds and the N+1th is rejected — and that two concurrent registrations at N-1 must not both succeed, which requires the count and the insert in one transaction with a unique or exclusion constraint backing it.

### Major: `limit` on the deliveries route has a floor but no ceiling

### Major: the new worker, queue and enqueue paths have no tests, and the tests that exist cannot see the signing defect
File: `tests/webhooks/test_delivery.py` — whole file, against `app/webhooks/delivery.py` `enqueue_for_event`, `_claim_batch`, `_acquire_lock`, `deliver`, `run_worker`

What breaks in production: The suite reports the delivery path as covered while the security primitive it names is never exercised, so the signing defect, the status-enum mismatch, the unique-index collapse and the blocking sleep all ship green.

Preserve the existing coverage: keep `test_verify_rejects_a_signature_made_with_another_secret` and the `MAX_ATTEMPTS` test — do not fix this by deleting or loosening assertions. Fail loudly: if `MockTransport`'s handler is never invoked, the test must fail on a captured-request count of zero rather than passing with an empty `captured` dict — "no request made" must not read the same as "request verified". Boundary and tie: state that a body of exactly zero bytes and a payload with duplicate-after-sorting keys are both covered, and that two deliveries signed within the same second must still produce different digests when their bodies differ.

### Major: full request headers — including the signature — are logged at INFO for every delivery
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: The entire header dict is interpolated into an INFO-level log line, so `X-Acme-Signature` and `X-Acme-Timestamp` are written verbatim to the application log for every attempt.
What breaks in production: Logs get shipped, indexed and read far more widely than the delivery path itself, and a signature plus the (deterministically re-derivable) payload is everything an attacker needs to replay a valid signed request against the customer's endpoint — the more so because the signature currently carries no timestamp binding.
Fix: Log only what is diagnostically needed — `log.info("POST %s delivery=%s attempt=%s", endpoint.url, delivery.id, attempt)` — and if header presence must be observable, log the header *names* only. Preserve the diagnostic value the line was providing: the target URL and a delivery correlator must still appear, so an operator can still trace a delivery end to end. Red-prove separately: (i) restore the full-header interpolation and run an assertion over captured log records that no record contains the substring `sha256=` — reddens; (ii) remove the delivery id from the line — the correlation assertion reddens; (iii) log the secret itself — the `whsec_` scan reddens. Fail loudly: the log-scanning assertion must fail if zero log records were captured, so a misconfigured caplog cannot report clean. Boundary and tie: the scan covers WARNING and ERROR records too — the retry warning already interpolates `detail`, which is `response.text` from an untrusted endpoint, so bound that as well (see the next finding).

### Major: untrusted response bodies are read and persisted without a size bound
File: `app/webhooks/delivery.py` — `_finish(delivery.id, "delivered", attempt, response.status_code, response.text)` and `detail = f"HTTP {response.status_code}: {response.text}"`
What is wrong: The full response body of a customer-controlled endpoint is materialised by `response.text` and stored verbatim into the `response_body TEXT` column and into a WARNING log line, with no length cap anywhere.
What breaks in production: A hostile or merely verbose endpoint returning a multi-hundred-megabyte body exhausts the worker's memory and bloats the deliveries table and the log pipeline, and every retry repeats it.
Fix: Cap on both sides — stream with a byte limit (`async with client.stream(...)` reading at most `MAX_RESPONSE_BYTES`, e.g. 4 KiB, then closing) and truncate before persisting: `detail[:MAX_RESPONSE_CHARS]` with an explicit `"…(truncated)"` marker so a reader can tell truncation from a short body. Preserve the diagnostic value: a short error body from a well-behaved endpoint must still be stored in full and be readable — that is what the field is for, so pin the untruncated short-body case as the allow case. Red-prove each separately: (i) remove the truncation and assert the stored `response_body` length is `<= MAX_RESPONSE_CHARS` for a 1 MiB response — reddens; (ii) remove the marker and assert a truncated value is distinguishable from a body that legitimately ends at the cap — reddens; (iii) return a 20-byte body and assert it is stored byte-identical — reddens if the truncation is off-by-one or unconditional. Fail loudly: if the stream is cut at the limit, record that fact in the status detail rather than treating the partial body as the whole response. Boundary and tie: a body of exactly `MAX_RESPONSE_CHARS` is stored whole and unmarked; `MAX_RESPONSE_CHARS + 1` is truncated and marked.

## Cross-cutting verification performed

- **Tenancy predicate**: `list_webhook_endpoints` filters `org_id == user.org_id`; `list_deliveries`, added in the same hunk, does not. `enqueue_for_event` correctly scopes by `org_id`. One missed location, reported first.
- **`to_dict()` secret exposure**: `WebhookEndpoint.to_dict` is called from two places in the diff (`create_webhook_endpoint`, `list_webhook_endpoints`); the leak is in the shared helper, so both are affected. `WebhookDelivery.to_dict` carries no secret.
- **Status spelling**: `failed_permanent` appears in `models.STATUSES` and `delivery._finish`; `failed` appears only in the migration's CHECK. One drift site.
- **Naive vs aware datetimes**: `datetime.utcnow()` appears exactly once (`enqueue_for_event`); `models._now()`, `_claim_batch` and `_finish` all use `datetime.now(timezone.utc)`, so the one naive call is the outlier — and the migration declares `TIMESTAMP` (no zone) for all five timestamp columns while `models.py` declares `DateTime(timezone=True)`, so the type mismatch is systemic across the table rather than local to one column. Reported under the `in_flight`/lease finding's schema change; it needs its own migration correction to `TIMESTAMPTZ`.
- **Blocking sleep**: `time.sleep` appears once (`deliver`); `run_worker` in the same file uses `await asyncio.sleep` twice — the correct idiom exists adjacent to the defect, which is the codebase-awareness evidence for the R1 framing of that finding.
- **Session-scope escape**: both `_claim_batch` (returns entities) and `deliver` (holds `endpoint`) leak ORM instances past their `with` block; `enqueue_for_event` and `_finish` do not. Two sites, both reported.
- **Docs versus code**: three separate divergences in `docs/webhooks.md` — HTTPS-only, secret-not-readable-back, and the retry semantics (jitter, 4xx) — each reported against the code path that contradicts it rather than as a documentation nit.
