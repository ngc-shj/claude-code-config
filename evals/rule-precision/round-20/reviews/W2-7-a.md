### Critical: the bytes that are signed are not the bytes that are sent, so no receiver can ever verify a webhook
File: `app/webhooks/signing.py` — `serialize` / `sign`, consumed at `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys sorted) while `send_once` transmits the body produced by `client.post(json=...)`, which httpx serializes with compact separators `(",", ":")` and no key sorting — two different byte strings for the same dict.
What breaks in production: every customer following `docs/webhooks.md` recomputes the HMAC over the raw request body they received and gets a mismatch, so 100% of deliveries are rejected as forged and the feature is dead on arrival for every integrator — the classic same-team-owns-both-sides R40 case, invisible here because no test ever feeds the actual wire body back through `verify`.
Fix: make one canonical byte string and send exactly it. Add `def canonical_body(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")` in `signing.py`; have `sign()` take and MAC that exact `bytes`; change `send_once` to `client.post(endpoint.url, content=body, headers=headers)` passing the same `body` object it handed to `sign` — never `json=`, which re-serializes. Preserve what made this visible and useful: keep `serialize`'s determinism (sorted keys) so the docs' verification recipe stays reproducible, and keep `Content-Type: application/json` set explicitly since `content=` will no longer set it. Deny/allow pairing: pin an ALLOW case that must still succeed — a round-trip test that captures `request.content` from `MockTransport` and asserts `signing.verify(SECRET, captured_body, captured_headers[SIGNATURE_HEADER])` is `True` for a payload containing a non-ASCII string, a nested dict, and an int; and a DENY case where one byte of `captured_body` is flipped and `verify` returns `False`. Red-prove each clause separately by execution: (i) revert `separators` to the default and run — the round-trip assertion must red; (ii) revert `sort_keys=True` and run with a payload whose insertion order differs from sorted order — the same assertion must red; (iii) change `content=body` back to `json=delivery.payload` and run — it must red again, each with a distinct failing assertion, not one mutation reddening all three. Fail loudly when the check cannot run: if `payload` is not JSON-serializable, let `TypeError` propagate out of `enqueue_for_event` rather than storing an unsignable row — "could not serialize" must not be spelled the same as "signed nothing". Boundary and tie: the comparison is byte equality on the full body; an empty payload `{}` serializes to `b"{}"` and must still produce a verifiable signature, and two payloads that differ only in key insertion order must produce the identical signature.

### Critical: the timestamp header is not covered by the signature, so replay protection does not exist
File: `app/webhooks/signing.py` — `sign` / `verify`
What is wrong: `sign()` returns a timestamp but MACs only the payload, whereas `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, so `X-Acme-Timestamp` is unauthenticated attacker-mutable data and the signature is valid forever.
What breaks in production: anyone who captures one `invoice.paid` delivery can replay it indefinitely against the customer's endpoint with a freshly rewritten timestamp that still passes the documented five-minute freshness window, because rewriting the header does not invalidate the signature — and the doc claim is what stops the integrator from adding their own defence (R49: a claim stronger than the implementation).
Fix: bind the timestamp into the MAC — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, timestamp, body, signature)` to take the received timestamp, recompute over `f"{timestamp}."+body`, and reject when `abs(int(time.time()) - int(timestamp)) > MAX_SKEW_SECONDS` with `MAX_SKEW_SECONDS = 300` as a module constant referenced by name from `docs/webhooks.md`. Do not fix this by relaxing the doc to match the code: the five-minute window is the behaviour the fix must preserve, and dropping it removes the only replay bound. Deny/allow pairing: ALLOW — a signature produced 299 seconds ago still verifies; DENY — the same signature with the timestamp header rewritten to `now` fails, and a signature 301 seconds old fails. Red-prove each clause by execution, one mutation each: (i) drop `f"{timestamp}."` from the MAC input — the header-rewrite DENY case must red; (ii) delete the skew check — the 301-second DENY case must red; (iii) widen `MAX_SKEW_SECONDS` to `10**9` — the 301-second case must red again, while the 299-second ALLOW case stays green in all three. Fail loudly: a non-numeric or absent timestamp must raise/return `False` explicitly rather than falling through to a comparison that happens to be false for an unrelated reason. Boundary and tie: exactly 300 seconds of skew is ACCEPTED (`> 300` rejects), skew is absolute so a clock 300s ahead is also accepted, and two deliveries signed in the same second are independent — freshness never dedupes, that is `event_id`'s job.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, instead of `hmac.compare_digest` (RS1).
What breaks in production: `verify` is the reference implementation this repo publishes and the only signature check it owns, so any internal or customer-facing route that adopts it leaks the expected digest one byte at a time under timing measurement, letting an attacker forge a signature without ever knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, comparing the full `"sha256=<hex>"` strings so a length difference is not itself a fast-path signal. Preserve the behaviour that made the function useful: `verify` must still return `False` (not raise) for a well-formed-but-wrong signature, so callers keep their existing branch. Deny/allow pairing: ALLOW — `verify` still returns `True` for a signature produced by `sign` with the same secret and timestamp; DENY — returns `False` for a signature made with `"whsec_someoneelse"`, and `False` for a signature that shares the first 60 hex characters with the expected one. Red-prove each clause by execution: (i) revert to `==` and assert via `dis`/AST inspection or a lint rule that `compare_digest` is absent — the guard test reds; (ii) return a constant `True` — the DENY tests red; (iii) truncate `expected` to 10 chars — the ALLOW test reds. Fail loudly: if `signature` is `None` or not a `str`, raise `TypeError` rather than returning `False`, so a caller passing the wrong header name is a loud bug and not a silent permanent rejection. Boundary and tie: the empty string and a correct-length-but-wrong signature must both take the same code path and the same time; a signature equal to `expected` except in case must be rejected, since hex digests are compared verbatim.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice` over `string.ascii_letters + string.digits`, i.e. Python's Mersenne Twister, which is seeded from process state and whose full internal state is recoverable from a modest amount of observed output.
What breaks in production: an attacker who registers a handful of their own endpoints and reads back their own secrets (trivially, given the secret-disclosure finding below) can reconstruct the generator state and predict every other tenant's signing secret, then forge signed `invoice.paid` webhooks to those tenants' endpoints.
Fix: use `secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, delete the `random`/`string`/`_ALPHABET` imports so the weak generator cannot be reintroduced by a later edit) and rename the constant to `SECRET_BYTES = 32` meaning actual entropy bytes, updating `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` to assert `>= 32` bytes of entropy rather than an exact character count — the existing exact-length assertion is what would otherwise force the fix to be reverted. Do not fix by deleting the length assertion: replace it with a floor, so a future one-character secret still reds. Deny/allow pairing: ALLOW — `new_signing_secret()` still starts with `SECRET_PREFIX` and is still accepted by `sign`/`verify` round-trip; DENY — 1000 generated secrets are all distinct, and a test asserts `"random" not in inspect.getsource(signing)`. Red-prove each clause by execution: (i) swap `secrets.token_urlsafe` back to `random.choice` — the source-inspection test reds; (ii) set `SECRET_BYTES = 1` — the entropy-floor test reds; (iii) return a constant secret — the distinctness test reds. Fail loudly: `secrets` failing to source entropy raises `NotImplementedError` and must be allowed to propagate out of the create-endpoint handler as a 500, never caught into a fallback generator. Boundary and tie: exactly 32 bytes is accepted (`< 32` rejected); two endpoints created in the same request-handling millisecond must receive different secrets.

### Critical: the signing secret is returned by the list endpoint, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret"` and is used both by the create route and by `GET /v1/settings/webhook-endpoints`, while `docs/webhooks.md` states the create response "is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: every actor holding a read-scoped API key or session for the org can enumerate all webhook signing secrets and forge deliveries to that org's endpoints, and the documented security property that customers rely on (treat the secret as write-once, store it in a secret manager) is false — a stronger claim than the implementation (R49).
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` build its response explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable returned by `new_signing_secret()`, so disclosure is a property of one call site rather than of the shared serializer. Preserve what made the feature useful: the create response must still carry the secret exactly once, otherwise no integrator can ever verify. Deny/allow pairing: ALLOW — a route test asserts `POST /v1/settings/webhook-endpoints` response body contains `signing_secret` and it verifies a signature from `sign`; DENY — a route test asserts `"signing_secret" not in` any element of the `GET` list response, and asserts the persisted row still holds a non-empty secret (RT8: assert the mutation, not only the status). Red-prove each clause by execution: (i) re-add the key to `to_dict()` — the GET-absence assertion reds; (ii) drop the key from the create response — the create-presence assertion reds; (iii) blank the column on read — the persisted-row assertion reds. Fail loudly: if the create path cannot obtain a secret, return 500 rather than persisting an endpoint with an empty `signing_secret`, since an empty-secret endpoint would sign every payload with a guessable key. Boundary and tie: the boundary is the response serializer, not the route — any future route reusing `to_dict()` inherits the safe shape by default; two endpoints for the same org must never share a secret.

### Critical: the deliveries endpoint has no tenancy check, so any org can read any other org's deliveries
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint` to confirm the endpoint's `org_id` matches `user.org_id`, unlike the sibling `list_webhook_endpoints` in the same file which does filter on `org_id`.
What breaks in production: incrementing `endpoint_id` in the URL returns another tenant's delivery history — event types, event ids, response statuses and schedule — a cross-tenant data leak reachable by any authenticated user with no special privilege.
Fix: join and scope in the same statement — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing so the endpoint's existence is not disclosed. Authorize in this handler, not only at the gateway; do not fix by adding the check to a shared dependency that a second route could later be registered without. Preserve the useful behaviour: an owner listing their own endpoint's deliveries must still get the same rows in the same order. Deny/allow pairing: ALLOW — a test where `user.org_id` owns `endpoint_id` asserts the expected delivery ids come back; DENY — a test where the endpoint belongs to another org asserts a 404 AND asserts the response body contains zero rows (status alone is a vacuous denial assertion, RT8). Red-prove each clause by execution: (i) delete the `org_id` filter — the DENY test reds on the row-count assertion; (ii) delete the `endpoint_id` filter — the ALLOW test reds by returning a foreign org's rows; (iii) change 404 to 200-with-empty — the DENY status assertion reds. Fail loudly: if `user.org_id` is `None`, raise rather than letting `org_id == None` produce a silently empty result set that reads as "no deliveries". Boundary and tie: an endpoint that exists but is soft-inactive still belongs to its org and must be readable by that org; a delivery whose endpoint was cascade-deleted is not reachable by anyone. Cross-cutting: `list_webhook_endpoints` and `create_webhook_endpoint` are correctly org-scoped, so `list_deliveries` is the single missed site — the pattern exists in the same file and was not propagated (R3).

### Critical: endpoint URLs are unvalidated and redirects are followed, giving an authenticated SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`parsed.scheme.startswith("http")`), with `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: `scheme.startswith("http")` accepts `http://` (the docs say HTTPS only) and any scheme literally prefixed with `http` such as `httpfoo://`, there is no check that the host is not loopback, link-local, or RFC1918, and the worker's client is configured with `follow_redirects=True` so even a validated public host can redirect the request inward.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` (or a public host that 302s there) and the worker POSTs signed JSON to the cloud metadata service from inside the VPC, with the response body persisted into `webhook_deliveries.response_body` and readable through the deliveries endpoint — a full read-capable SSRF with exfiltration channel.
Fix: replace the string check with `parsed.scheme != "https"` → 422, resolve the hostname at registration and again immediately before each POST, and reject when any resolved address is in a denied set (`ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast`); set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a permanent failure with a message naming the redirect target. Because the DNS answer can change between the registration check and the request (R51), the pre-request re-resolution is the load-bearing half and must not be dropped as redundant. Preserve what made the feature useful: legitimate public HTTPS endpoints on non-standard ports must still be accepted, and the existing 422 shape for malformed URLs must not change. Deny/allow pairing: ALLOW — `https://hooks.example.com/acme` resolving to a public address is accepted at registration and delivered to; DENY — `http://hooks.example.com`, `httpfoo://x`, `https://127.0.0.1/`, `https://10.0.0.5/`, `https://[::1]/`, and a public host whose delivery-time resolution returns `169.254.169.254` are each rejected, the last one asserting that no HTTP request was issued (assert the suppressed side effect, not just the status). Red-prove each clause by execution: (i) restore `startswith("http")` — the `http://` and `httpfoo://` DENY cases red; (ii) delete the IP-class check — the loopback/RFC1918 cases red; (iii) restore `follow_redirects=True` and serve a 302 to `127.0.0.1` — the redirect DENY case reds; (iv) delete the delivery-time re-resolution — the rebinding case reds. Fail loudly: DNS resolution failing must reject the registration with 422 and must mark a delivery attempt failed with a named reason, never fall through to "no denied address found, therefore allowed". Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv4-mapped IPv6 forms count as denied; a hostname resolving to both a public and a private address is denied (any-denied wins, not all-denied), and the tie between two A records is broken toward refusal.

### Critical: the migration's status CHECK constraint does not include the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py:deliver` writing `"failed_permanent"` and `app/webhooks/models.py:STATUSES`
What is wrong: the SQL enumerates `'failed'` while both `STATUSES` and the only writer of a terminal failure state use `'failed_permanent'` — the same enum spelled two ways in two files (R2: value drift across duplicated constants).
What breaks in production: the first delivery that exhausts its five attempts raises a `CheckViolation` inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and the exception escapes `deliver` (which catches only `httpx.HTTPError`) through a bare `asyncio.gather` and kills the worker loop — so one unreachable customer endpoint takes down webhook delivery for every tenant.
Fix: change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `STATUSES` the single source: define the tuple in `models.py`, import it in `delivery.py`, and add a migration-parity test that reads the `CHECK` clause from `information_schema`/`pg_constraint` in the test database and asserts set equality with `models.STATUSES`. Do not fix by widening the constraint to accept any text — the constraint is what makes a typo visible. Deny/allow pairing: ALLOW — inserting each of the four `STATUSES` values succeeds; DENY — inserting `'failed'` or `'FAILED_PERMANENT'` raises `IntegrityError`, and the parity test reds when either side gains a member the other lacks. Red-prove each clause by execution: (i) add a fifth member to `STATUSES` only — the parity test reds; (ii) drop `'failed_permanent'` from the SQL only — the parity test reds with a different message; (iii) hardcode `"failed"` back into `_finish` — the exhausted-retry integration test reds on `IntegrityError`. Fail loudly: if the parity test cannot read the constraint (no database, constraint absent), it must error out naming that, not skip — "examined nothing" must not report PASS. Boundary and tie: the value set is compared as a set, so ordering does not matter but case does; a status added to the DB but not to `STATUSES` is equally a failure, not a permitted superset.

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` alone while `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the second row of any fan-out violates the index.
What breaks in production: the moment an org registers a second endpoint, `session.add_all(rows)` fails on flush, the whole batch rolls back, `dispatch` swallows the exception into a `log.warning`, and that org silently receives no webhooks at all for that event on any endpoint — while the docs promise at-least-once delivery to every subscribed endpoint.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_event_endpoint ON webhook_deliveries (endpoint_id, event_id)`, which is the idempotency key the design actually needs (one attempt row per event per endpoint) and which also makes a re-dispatched event a no-op via `ON CONFLICT DO NOTHING`. Preserve the useful property the current index accidentally provides: duplicate enqueue of the same event to the same endpoint must still be prevented — do not fix by dropping uniqueness altogether. Deny/allow pairing: ALLOW — enqueueing one event for an org with three matching endpoints inserts exactly three rows and each is delivered; DENY — enqueueing the same `event_id` twice for the same endpoint leaves exactly one row and does not raise. Red-prove each clause by execution: (i) restore the single-column unique index — the three-endpoint ALLOW test reds on `IntegrityError`; (ii) drop uniqueness entirely — the duplicate-enqueue DENY test reds with two rows; (iii) remove the `if not endpoint.event_types or event_type in endpoint.event_types` filter — the ALLOW test's row count reds. Fail loudly: `enqueue_for_event` must not swallow an `IntegrityError`; the caller in `dispatcher.py` currently converts it to a warning, which is exactly how this defect would stay invisible. Boundary and tie: an org with zero matching endpoints inserts zero rows and that is success, not an error; two endpoints of the same org pointing at the identical URL are still two distinct rows.

### Critical: ORM instances are used after their session closes, so the worker cannot read a payload or a secret
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` after `with session_scope()` exits) and `deliver` (reads `endpoint.signing_secret` / `endpoint.url` outside the `with` block)
What is wrong: both functions let SQLAlchemy entities escape the `session_scope()` context manager and then read attributes on them; under SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit and a subsequent read on a detached instance raises `DetachedInstanceError`.
What breaks in production: `run_worker`'s very first batch raises out of `deliver` (which catches only `httpx.HTTPError`), propagates through `asyncio.gather`, and terminates the worker loop — no webhook is ever delivered, and the tests do not catch it because `FakeDelivery`/`FakeEndpoint` are plain classes that were never attached to a session.
Fix: stop passing entities across the boundary — have `_claim_batch` return plain frozen dataclasses (`ClaimedDelivery(id, endpoint_id, event_id, payload, attempts)`) built inside the session, and have `deliver` accept the endpoint's `url` and `signing_secret` as values loaded in the same query via a join rather than a second lookup. Do not fix by setting `expire_on_commit=False` globally: that hides the lifetime bug rather than removing it, and leaves stale reads elsewhere. Preserve what made the code useful: `_claim_batch` must still mark the claimed rows `in_flight` inside the same transaction that selects them. Deny/allow pairing: ALLOW — an integration test against a real session asserts `_claim_batch()` returns N objects whose `payload` and `signing_secret` are readable after the context manager has exited, and that `deliver` completes; DENY — a test asserts that claiming leaves exactly those N rows at `in_flight` in the database and leaves later-scheduled rows at `pending`. Red-prove each clause by execution: (i) revert `_claim_batch` to returning entities — the attribute-read ALLOW assertion reds with `DetachedInstanceError`; (ii) revert `deliver`'s endpoint lookup to the detached `session.get` — the delivery ALLOW assertion reds; (iii) remove the `row.status = "in_flight"` assignment — the DENY row-state assertion reds. Fail loudly: `session.get(WebhookEndpoint, ...)` returning `None` (the endpoint was cascade-deleted mid-flight) must raise a named error and mark the delivery failed, not `AttributeError` on `None.signing_secret`. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (`<=`); two rows with identical `next_attempt_at` are broken by `id` so the batch is deterministic. Cross-cutting: the same escape pattern appears a third time in `enqueue_for_event`, which returns `len(rows)` (safe) but would break identically if a caller ever needed the row ids.

### Critical: `time.sleep` inside an async coroutine blocks the entire worker event loop
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: the retry backoff uses the blocking `time.sleep` inside an `async def` rather than `await asyncio.sleep`, so it stalls the thread that runs every other coroutine.
What breaks in production: a batch of 100 deliveries gathered by `asyncio.gather` is serialized rather than concurrent, and a single failing endpoint holds the loop for up to 2+4+8+16 = 30 seconds of pure sleep plus 5×30s of request timeouts — well past the 60-second Redis lock TTL, so a second worker claims the same rows and every delivery is sent twice.
Fix: `await asyncio.sleep(delay)`, and stop retrying inside the coroutine at all — write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting `_claim_batch` re-claim it, which is what the `next_attempt_at` column and the backoff table were built for and which currently is dead. Preserve what the loop provided: the total attempt budget must still be `MAX_ATTEMPTS` and the delays must still be the documented 2/4/8/16 sequence. Deny/allow pairing: ALLOW — a test asserts a delivery whose first attempt 500s is rescheduled with `next_attempt_at` in `[now+2s, now+3s]` and status `pending`, and that a second gathered delivery completed while the first was waiting (concurrency, measured as wall-clock < the sum of the delays); DENY — a delivery on its 5th attempt is written `failed_permanent` and is not rescheduled. Red-prove each clause by execution: (i) restore `time.sleep` — the concurrency ALLOW assertion reds on wall-clock; (ii) delete the `next_attempt_at` write — the reschedule ALLOW assertion reds; (iii) change `attempt >= MAX_ATTEMPTS` to `>` — the DENY assertion reds with a 6th attempt. Fail loudly: a delivery whose reschedule write itself fails must not be left `in_flight` — route it to an explicit error status that the reaper picks up. Boundary and tie: attempt number 5 is the last one attempted (`>=`, so five POSTs total, matching the doc's "at most 5 times"); two deliveries rescheduled to the same `next_attempt_at` are ordered by `id`.

### Major: only three hardcoded event types ever reach the webhook pipeline
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES` / `dispatch`
What is wrong: `dispatch` enqueues webhooks only when `envelope.type` is in a hardcoded three-element set, while `WebhookEndpoint.event_types` accepts any string and `docs/webhooks.md` promises "an empty `event_types` subscribes the endpoint to every event type we emit" (R12 coverage gap, R49 overstated claim).
What breaks in production: a customer registers with `event_types: []` expecting everything, or subscribes to a fourth event type the product emits, and silently receives nothing forever with no error anywhere — the endpoint looks healthy and the deliveries list is empty.
Fix: delete `WEBHOOK_EVENT_TYPES` and enqueue for every dispatched event, letting `enqueue_for_event`'s existing per-endpoint `event_types` filter be the single place subscription is decided (it already implements exactly the documented semantics — this is the shared path the dispatcher-side set reimplements, R1). If a global allowlist is genuinely wanted, move it next to that filter and derive it from a registry that every emitter must register into, so adding an event type without deciding its webhook visibility fails a test. Preserve the useful property: internal-only event types must still be excludable — record that exclusion as an explicit `webhook_visible: bool` on the event registry, not as a set the dispatcher happens to hold. Deny/allow pairing: ALLOW — dispatching a type absent from today's set to an endpoint with `event_types: []` produces one delivery row; DENY — dispatching a type marked non-visible produces zero rows and the assertion checks the row count, not just a return value. Red-prove each clause by execution: (i) reinstate the hardcoded set — the ALLOW test reds with zero rows; (ii) invert the per-endpoint filter to `event_type not in endpoint.event_types` — a targeted-subscription ALLOW test reds; (iii) mark the visible type non-visible — the DENY test reds. Fail loudly: an event type absent from the registry must raise at dispatch rather than defaulting to either visible or hidden. Boundary and tie: an endpoint with `event_types: []` matches every visible type including ones added later; an endpoint listing a type that no longer exists matches nothing and is not an error.

### Major: webhook enqueue failures are swallowed after the event has already been committed
File: `app/events/dispatcher.py` — `dispatch`, the `except Exception as exc: log.warning(...)` block
What is wrong: the event row commits in its own `session_scope`, then `enqueue_for_event` opens a second, independent transaction whose failure is caught by a bare `except Exception` and downgraded to a warning, so there is no atomicity between "the event happened" and "the event will be delivered" and no retry.
What breaks in production: any transient database error, the `IntegrityError` from the unique-index defect above, or a serialization failure permanently loses every webhook for that event with only a WARN line as evidence — and the caller still gets a successful `event_id`, so nothing upstream retries.
Fix: write the delivery rows in the SAME transaction as the `Event` insert (transactional outbox): move the `enqueue_for_event` body into a function taking the open `session`, call it inside the existing `with session_scope() as session:` block before the flush completes, and let the worker be the only thing that touches the network. Then narrow the `except` to the specific recoverable exception, if any survives, and re-raise everything else. ### Major: an unhandled exception anywhere in a batch terminates the worker loop permanently
File: `app/webhooks/delivery.py` — `run_worker` (`await asyncio.gather(*[deliver(client, d) for d in batch])`, and `batch` referenced after the `try/finally`)
What is wrong: `gather` is called without `return_exceptions=True` and `deliver` catches only `httpx.HTTPError`, so any `DetachedInstanceError`, `IntegrityError`, `TypeError`, or `asyncio.CancelledError` propagates out of `run_worker` and ends the loop; separately, if `_claim_batch` raises, `batch` is unbound when `if not batch` executes, producing a confusing `NameError` that masks the real cause.
What breaks in production: one poison delivery row stops all webhook delivery for every tenant until someone notices and restarts the process — and the `NameError` variant makes the logs point at the wrong line.
Fix: pass `return_exceptions=True` to `gather`, iterate the results and route each exception to `_finish(..., "failed_permanent", ...)` with the exception type named in the detail, wrap the whole poll body in a `try/except Exception` that logs at ERROR and continues after a backoff, and initialize `batch: list = []` before the `try` so the post-`finally` check is always defined. Do not fix by broadening `deliver`'s own `except` to bare `Exception`: that would swallow programming errors into per-delivery failures and hide exactly the defects above — the routing must record the exception type so poison rows are visible. Preserve the useful behaviour: a clean batch must still exit the poll immediately without the extra `poll_interval` sleep. Deny/allow pairing: ALLOW — a batch of three where one delivery raises `ValueError` still delivers the other two and the loop performs a fourth poll; DENY — the raising delivery is written `failed_permanent` with the exception type in `response_body`, asserted on the row, not on the log. Red-prove each clause by execution: (i) remove `return_exceptions=True` — the fourth-poll ALLOW assertion reds; (ii) remove the per-result exception routing — the `failed_permanent` DENY row assertion reds; (iii) make `_claim_batch` raise — with the `batch = []` initializer removed, the loop-continues assertion reds with `NameError`. Fail loudly: an exception the loop cannot classify must be logged at ERROR with the delivery id and must still mark the row terminal — never leave it `in_flight` and continue silently. Boundary and tie: an empty batch sleeps `poll_interval` and a non-empty one does not; a batch where every delivery raises must still release the lock and poll again.

### Minor: `STATUSES` is declared but never enforced
File: `app/webhooks/models.py` — `STATUSES`
What is wrong: the tuple is defined at module level and imported nowhere; `status` is a plain `String(20)` with a string default, and `delivery.py` writes its status values as inline literals.

### Minor: `SECRET_BYTES` names bytes but is used as a character count
File: `app/webhooks/signing.py` — `SECRET_BYTES = 32`, used as `range(SECRET_BYTES)` over a 62-character alphabet
What is wrong: the identifier claims a byte count while the code produces 32 characters (~190 bits), and `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` asserts the exact character count, pinning the misnomer.
What breaks in production: a future reader increasing "bytes" to satisfy an entropy requirement will get characters instead, and the exact-length test will block the switch to a byte-based generator.

### Minor: the deliveries listing has no total order, so pages are unstable
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc()).limit(limit)`
What is wrong: `created_at` is a wall-clock timestamp with no uniqueness, and a burst enqueue writes many rows at the same instant, so the order among ties is undefined (R57).
What breaks in production: two identical requests return different subsets of the same-instant rows, and when this listing gains a cursor the tie is where rows will be skipped or repeated — add `.order_by(created_at.desc(), id.desc())` now.

### Minor: `_finish` dereferences a row that may not exist
File: `app/webhooks/delivery.py` — `_finish`, `row = session.get(m.WebhookDelivery, delivery_id)`
What is wrong: the return value is used without a `None` check, and the migration's `ON DELETE CASCADE` from `webhook_endpoints` means a customer deleting an endpoint mid-flight removes the row this function is about to write.
What breaks in production: an `AttributeError: 'NoneType' object has no attribute 'status'` escapes `deliver`, and per the worker finding above that terminates the whole delivery loop.
