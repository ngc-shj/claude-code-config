### Critical: the signature is computed over bytes that are never the bytes sent, and omits the timestamp the docs say it covers
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, used by `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys reordered) while `send_once` hands the dict to `client.post(..., json=delivery.payload)` so httpx does its own encoding, and the MAC input excludes the timestamp that `docs/webhooks.md` tells customers to prepend as `"{timestamp}.{raw_request_body}"`.
What breaks in production: every customer who implements verification exactly as documented — HMAC over the raw body they received, timestamp-prefixed — computes a different digest than we sent, so 100% of deliveries are rejected at the receiver while our side records them `delivered`; and because the timestamp is outside the MAC, any captured request can be replayed forever by rewriting only the `X-Acme-Timestamp` header, which is precisely the defence the doc claims.
Fix: make the signed bytes and the wire bytes one object. In `signing.py` add `def canonical_body(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, change `sign(secret, body: bytes) -> tuple[str, str]` to compute `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, and change `send_once` to build `body = canonical_body(delivery.payload)` once and send `client.post(endpoint.url, content=body, headers=headers)` — never `json=`, which re-encodes. Preserve what makes the defect visible and the feature useful: keep `serialize()`/`verify()` exported and keep the `sha256=` prefix and both header names, since customers already parse them; do not "fix" this by relaxing the doc, because the doc is the contract the receiver implements. Allow side that must still pass: a body produced by `canonical_body` and signed by `sign` must verify under an independently written HMAC computation in the test (write the expected digest with `hmac.new(SECRET.encode(), b"1700000000." + b'{"a":1}', sha256).hexdigest()` literal-style, not by calling `sign` twice). Red-prove each clause separately by execution: (1) mutate `separators` back to the default and observe the raw-body round-trip assertion redden while the sign/verify pair stays green — that divergence is the whole bug; (2) mutate the timestamp out of the MAC input and observe a distinct assertion redden (two different timestamps over the same body must give two different signatures); (3) mutate `content=` back to `json=` and observe the assertion comparing `request.content` to `canonical_body(payload)` redden. Fail loudly when the check cannot run: if `payload` is not JSON-serializable, let `json.dumps` raise out of `send_once` and mark the delivery `failed_permanent` with the exception text, rather than sending an unsigned or partially-signed request. Boundary and tie: the timestamp is unix seconds, so two signings inside the same second over the same body legitimately produce identical signatures — that is expected and must not be asserted against; the receiver's five-minute window is `now - ts <= 300` inclusive at exactly 300, and that inclusivity belongs in `docs/webhooks.md` beside the window.

### Critical: `list_deliveries` has no organization scope — any authenticated user can read any organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`

Allow side that must still pass: a delivery belonging to the caller's own endpoint is still returned with the same fields — pin that as an explicit test, because a fix that always returns `[]` satisfies the deny test. Red-prove each clause by execution: (1) delete the `org_id` predicate and observe the cross-tenant test redden; (2) delete the join and observe a `NameError`/SQL error rather than a silent pass; (3) change the not-found branch from 404 to 200-with-empty-list and observe the oracle test redden. Fail loudly when the check cannot run: `user.org_id` being `None` must raise a 401/403, never widen the filter to "match everything" — assert that case. Boundary and tie: an endpoint that exists but belongs to another org and an endpoint id that does not exist must produce the identical 404 body; state that equality in the test so a later refactor cannot re-separate them.

### Critical: signing secrets are returned on every read and written to the application log
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`; `app/webhooks/delivery.py` — `send_once` log line
What is wrong: `to_dict()` includes `"signing_secret"`, and it is the serializer used by both `create_webhook_endpoint` and `list_webhook_endpoints`, so `GET /v1/settings/webhook-endpoints` hands back every secret in plaintext — directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards") — while `log.info("POST %s headers=%s", endpoint.url, headers)` writes the derived signature header into logs on every attempt.
What breaks in production: any actor with a read-scoped API key or a captured session can retrieve the secrets for the whole org and forge webhook deliveries indistinguishable from ours, and the log line ships those signatures to whatever aggregator ingests application logs, where they are indexed and readable by people never meant to see them.
Fix: split the serializer — `to_dict()` drops `signing_secret` entirely, and `create_webhook_endpoint` returns `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at the single creation site, so the secret has exactly one egress path; reduce the delivery log to `log.info("POST %s delivery=%s", endpoint.url, delivery.id)`, keeping the request-observability the line was added for while dropping the header dict. Do not fix by redacting the log string only — the list route is the larger leak. Allow side that must still pass: the 201 response body from `create_webhook_endpoint` still carries `signing_secret`, since customers have no other way to obtain it; pin that, or a fix that strips it everywhere passes the deny test and silently breaks onboarding. Red-prove each clause separately: (1) re-add `"signing_secret"` to `to_dict` and observe the list-route test asserting `"signing_secret" not in body[0]` redden; (2) remove the explicit merge in the create route and observe the create-route test redden; (3) restore `headers=%s` in the log format and observe a caplog assertion that no emitted record contains `SIGNATURE_HEADER`'s value redden. Fail loudly when the check cannot run: if `signing_secret` is `None` at creation, raise rather than returning a 201 with a null secret, because a null secret means every later `sign()` call raises inside the worker instead of at the boundary. Boundary and tie: the rule is "one response, at creation" — a retried `POST` that creates a second endpoint returns a second, different secret, and two endpoints of one org must never share one; assert the two secrets differ.

### Critical: signing secrets are generated with the `random` module, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice`, which draws from the Mersenne Twister — a fully reconstructible generator, not a cryptographic one — and this is the key material for every outbound HMAC.
What breaks in production: an attacker who observes enough generator output (any process sharing the untweaked global `random` state, or a sequence of secrets issued to endpoints they control) can predict other tenants' signing secrets and forge signed webhooks that our documented verification procedure accepts as genuine.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` with `import secrets`, and rename the constant to what it now means — `SECRET_BYTES = 32` really is 32 bytes of entropy under `token_urlsafe`, whereas today it is a character count over a 62-symbol alphabet, so the current name is already wrong and the test encodes the wrong meaning. Delete the `random`/`string`/`_ALPHABET` imports so the weak path cannot be reached again. Do not preserve the exact length assertion as-is; preserve what it was protecting — that the secret is prefixed and long — by asserting `len(secret) >= len(SECRET_PREFIX) + 40` and `secret.startswith(SECRET_PREFIX)`. Allow side that must still pass: a freshly generated secret must round-trip through `sign`/`verify` unchanged — pin it, because a fix returning a constant satisfies every length assertion. Red-prove each clause by execution: (1) revert to `random.choice` seeded with `random.seed(0)` and observe an added test asserting two secrets generated after identical `random.seed(0)` calls differ — that test is red on the old code and green on the new; (2) drop the prefix and observe the prefix assertion redden; (3) shorten to 8 bytes and observe the length-floor assertion redden. Fail loudly when the check cannot run: `secrets` is stdlib and cannot be absent, but if `SECRET_BYTES` is ever configured below 32 the function must raise at import, not silently issue a short secret. Boundary and tie: `token_urlsafe(32)` yields 43 characters, so the floor of 40 sits below the real value with headroom; state that two calls must never collide and assert it over a batch, since a colliding generator is exactly the failure this fix exists to prevent.

### Critical: signature comparison in `verify` is not constant-time (RS1)
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the recomputed digest is compared to the supplied one with `==`, which short-circuits on the first differing byte.
What breaks in production: `verify` is an exported production helper for checking a signature against a secret, so any inbound path that adopts it — our own re-ingest, a test harness, a customer copying the reference implementation from this module — leaks digest bytes through response timing and lets an attacker construct a valid signature byte by byte.
Fix: `return hmac.compare_digest(expected, signature)`, and guard the inputs first — if `signature` is not a `str`, return `False` rather than letting `compare_digest` raise a `TypeError` that a caller might catch as "verified". Keep `verify`'s signature and return type unchanged so callers are unaffected; do not resolve this by deleting `verify`, which is the only reference implementation customers have. Allow side that must still pass: a signature produced by `sign` over the same secret and payload still returns `True` — `test_verify_accepts_signature_produced_by_sign` already pins this and must stay green. Red-prove each clause separately: (1) replace `compare_digest` with `==` and observe a test asserting `verify` is called through `hmac.compare_digest` (patch it with a counting wrapper and assert the counter incremented) redden; (2) remove the type guard and pass `signature=None`, observing the added `assert verify(SECRET, {"a": 1}, None) is False` redden with a `TypeError`; (3) flip one hex character of a valid signature and observe the reject assertion redden if the comparison is removed entirely. Fail loudly when the check cannot run: a `None` or non-`str` secret must raise at the call, not compare as equal-to-empty. Boundary and tie: a signature of the correct length but differing in the final character and one differing in the first must both return `False` in the same measured time; state that the empty string is a reject, not a pass, since `compare_digest("", "")` is `True` and an unset secret must never reach it.

### Critical: the unique index on `event_id` alone makes every multi-endpoint organization lose all its deliveries
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index permits only one row per `event_id` across the whole table.
What breaks in production: for any org with two or more active endpoints the batch insert raises a unique violation, the enqueue transaction rolls back so even the *first* endpoint's row is lost, and `dispatcher.dispatch` swallows the exception at `log.warning` — so the events are silently never delivered to anyone, with no failed row to inspect; worse, the index is global, so two different orgs whose events happen to share an `event_id` also collide.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the at-least-once/dedupe contract in `docs/webhooks.md` actually needs (one delivery per endpoint per event), and add the composite claim index the worker's own query needs: `CREATE INDEX idx_webhook_deliveries_claim ON webhook_deliveries (status, next_attempt_at)` — the existing single-column `(status)` index does not serve `WHERE status = 'pending' AND next_attempt_at <= now() ORDER BY next_attempt_at`. Keep a uniqueness constraint; do not fix this by dropping uniqueness, because that is what makes a double-enqueue visible. Allow side that must still pass: two endpoints of one org receiving the same `event_id` both insert successfully — pin that as an integration test, since dropping the index alone also passes a "no error" test. Red-prove each clause by execution: (1) revert to the single-column unique index and observe the two-endpoint insert test redden with an `IntegrityError`; (2) attempt the same `(endpoint_id, event_id)` pair twice and observe the duplicate-rejection test redden if the composite index is dropped; (3) remove the composite claim index and observe a plan assertion (`EXPLAIN` containing an index scan on `idx_webhook_deliveries_claim`) redden. Fail loudly when the check cannot run: `enqueue_for_event` must not swallow an `IntegrityError` into a partial success — see the dispatcher finding below; a failed enqueue must surface. Boundary and tie: the tie is exactly the duplicate `(endpoint_id, event_id)` produced by a re-dispatch of the same event; that must be a no-op insert (`ON CONFLICT DO NOTHING`), and say so, so a retry of `dispatch` does not fail the whole call.

### Critical: the worker uses ORM rows after their session has closed

Fail loudly when the check cannot run: if `session.get(WebhookEndpoint, ...)` returns `None` — the endpoint was deleted mid-flight — `deliver` must call `_finish(..., "failed_permanent", ..., "endpoint deleted")` explicitly, not `AttributeError` its way out. Boundary and tie: the boundary is the `with` block's closing line — every attribute read must happen strictly before it; the tie is a row claimed by this batch and deleted by a cascade in the same instant, which must land on the explicit `failed_permanent` path.

### Critical: SSRF — customer-supplied URLs are neither restricted to https nor to external hosts, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the guard is `parsed.scheme.startswith("http") and parsed.netloc`, which admits `http://`, admits any scheme whose name merely begins with those four letters (`httpz://`), and applies no restriction on the destination host, while the delivery client follows redirects so even a validated host can bounce the request onward.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` (or an external host that 302s there) and our worker POSTs signed, authenticated-from-inside requests to cloud metadata and internal services, returning the response body into `WebhookDelivery.response_body` where the customer can read it — a full server-side request forgery with an exfiltration channel; separately, `docs/webhooks.md` states "Only `https://` URLs are accepted", a claim the implementation does not support (R49).
Fix: replace the check with an allow-shaped validator in one place — require `parsed.scheme == "https"` exactly, require a hostname, resolve it and reject any address in a private, loopback, link-local, or unique-local range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), and reject a non-default port unless it is 443; set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure with a message naming the redirect target. Because DNS can change between registration and delivery, apply the same host check inside the delivery path via a `httpx` transport hook — validating only at registration is a check-then-use gap. Do not fix by removing `response_body` (it is the feature customers inspect); bound it instead (see the Major below). Allow side that must still pass: `https://hooks.example.com/acme` — the exact URL in `docs/webhooks.md` and in `FakeEndpoint` — still registers and still delivers; pin it, because a validator that rejects everything satisfies every deny case. Red-prove each clause separately: (1) relax `scheme == "https"` to `startswith("http")` and observe the `http://…` rejection test redden; (2) delete the private-range check and observe the `https://169.254.169.254/` rejection test redden; (3) set `follow_redirects=True` and observe a `MockTransport` test that returns a 302 to an internal host redden; (4) drop the delivery-time host check and observe a test whose resolver is patched to return a private address post-registration redden. Fail loudly when the check cannot run: DNS resolution failure must reject the registration with 422 and must fail the delivery as retryable — "could not resolve" must not be spelled the same as "resolved to something public". Boundary and tie: port 443 is allowed and every other port denied; `https://example.com:443/x` and `https://example.com/x` are the same case and both must pass, and a hostname resolving to both a public and a private address must be denied (any-private denies, not all-private).

### Critical: `time.sleep` inside the async retry loop blocks the event loop for the whole backoff
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` times on one loop, and it calls the blocking `time.sleep` rather than `await asyncio.sleep`, so its backoff freezes every other delivery, the httpx client, and the worker's own loop.
What breaks in production: one endpoint that returns 500 stalls the entire batch for 2+4+8+16 = 30 seconds of pure blocking plus up to four 30-second request timeouts, which is far past the 60-second `LOCK_KEY` TTL — the lock expires mid-batch, a second worker claims and re-sends the same events, and the customer receives duplicates while throughput collapses to one endpoint at a time.
Fix: `await asyncio.sleep(delay)` (the module already imports `asyncio`), and add the jitter `docs/webhooks.md` promises — `delay = backoff_for(attempt).total_seconds() * random.uniform(0.5, 1.5)` using `secrets`-independent `random`, which is acceptable here because jitter is not key material. Then decouple the retry from the in-process loop: instead of sleeping inside `deliver`, write `status='pending'`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next `_claim_batch` pick it up — this is what `next_attempt_at` exists for and it removes the lock-expiry window entirely. Keep `MAX_ATTEMPTS` and the `backoff_for` curve, which the existing parametrized test pins. Allow side that must still pass: a delivery that succeeds on the first attempt still completes with no sleep at all, and one that succeeds on the second attempt still ends `delivered` with `attempts == 2`; pin both, since a fix that never retries also removes the blocking. Red-prove each clause by execution: (1) restore `time.sleep` and observe a test asserting `deliver` yields control (run it concurrently with a coroutine that sets a flag, assert the flag is set before `deliver` returns) redden; (2) remove the jitter multiplier and observe a test asserting two consecutive scheduled `next_attempt_at` values for the same attempt number differ redden; (3) remove the reschedule and observe the assertion that a 500 leaves `status == 'pending'` with `next_attempt_at` in the future redden. Fail loudly when the check cannot run: an exception that is neither `httpx.HTTPError` nor a 2xx — a JSON encoding error, a `DetachedInstanceError` — must land on an explicit `_finish(..., 'failed_permanent', ...)` with the exception text, never escape into `gather`. Boundary and tie: `attempt >= MAX_ATTEMPTS` is the terminal boundary, so attempt 5 is the last one *sent* and attempt 6 never happens; ties in `next_attempt_at` between two rows are resolved by `id` (see the ordering finding below).

### Major: `_acquire_lock` is a non-atomic check-then-set and releases a lock it may no longer own
File: `app/webhooks/delivery.py` — `_acquire_lock`, and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` then `set` then `expire` is three round trips with no atomicity, so two workers can both observe an absent key and both proceed; and the unconditional `delete` in `finally` removes whatever value is at `LOCK_KEY`, including a lock a *different* worker acquired after this one's TTL expired.
What breaks in production: two workers claim overlapping batches and the customer receives duplicate webhooks, which the docs promise only as at-least-once but which here happens on every deploy that runs more than one replica.
Fix: acquire with a single atomic command carrying a unique token and the TTL together — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`) so a worker can only delete its own lock; renew the TTL while a batch is in flight rather than relying on 60 seconds covering it. Keep the lock (it is what prevents the duplicate batch); do not fix by widening the TTL, which only lengthens the stall. Allow side that must still pass: a single worker still acquires the lock on a clean Redis and still releases it, so the next iteration re-acquires — pin the acquire/release/re-acquire cycle, because a fix that never acquires satisfies "no duplicate batches". Red-prove each clause separately: (1) revert to `get`-then-`set` and observe a test that runs two `_acquire_lock` calls concurrently against a fake Redis asserting exactly one returns `True` redden; (2) revert the release to an unconditional `delete` and observe a test where worker A's TTL expires, worker B acquires, then A releases — asserting B's token still present — redden; (3) drop the `ex=60` and observe a TTL assertion redden. Fail loudly when the check cannot run: a Redis connection error inside `_acquire_lock` must propagate or return `False` with an error log naming Redis, never be treated as "lock is free". Boundary and tie: the boundary is the TTL instant — a batch still running at exactly 60 seconds must have renewed by then; the tie is two workers submitting `SET NX` in the same millisecond, which Redis resolves to exactly one winner and the test must assert that count is one, not "at least one".

### Major: rows left in `in_flight` are never reclaimed — a non-terminal state with no exit (R38)
File: `app/webhooks/delivery.py` — `_claim_batch` sets `status = "in_flight"`; `deliver` only ever writes `delivered` or `failed_permanent`
What is wrong: `_claim_batch` filters on `status == "pending"`, so any row that reaches `in_flight` and does not complete — worker crash, deploy, the `CheckViolation` above, an uncaught `DetachedInstanceError` — has no path back to `pending` anywhere in the change.
What breaks in production: every restart during a batch permanently strands up to 100 deliveries in `in_flight`; they never retry, never appear as failures, and the only visible symptom is a customer reporting a missing event weeks later.
Fix: add a reaper predicate to the claim query rather than a new background job — claim `status = 'pending' OR (status = 'in_flight' AND updated_at < now() - interval '5 minutes')`, and have `_claim_batch` stamp `updated_at = now()` when it sets `in_flight` (it currently does not, so the column is only written by `_finish`). Keep `in_flight` — it is what prevents two workers doubling up within a batch — and do not fix by writing `pending` back optimistically, which reintroduces the double-send.
