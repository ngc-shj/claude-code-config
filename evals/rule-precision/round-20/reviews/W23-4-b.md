### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters only on the path parameter `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate integer endpoint ids and read another tenant's delivery rows — which carry the full event `payload` and the upstream `response_body`.
What breaks in production: Cross-tenant disclosure of invoice and subscription payloads to any customer who increments an id, and `docs/webhooks.md` ("returns the most recent attempts for an endpoint belonging to your organization") makes the claim that hides it.
Fix: Join the delivery query through `WebhookEndpoint` and filter `WebhookEndpoint.org_id == user.org_id` alongside the `endpoint_id` predicate — the same scoping the three sibling handlers in this file already apply (`get_profile` on `user.org_id`, `list_api_keys` on `ApiKey.org_id == user.org_id`, `list_webhook_endpoints` on `WebhookEndpoint.org_id == user.org_id`); this handler is the only new query in the diff that omits it, so no new helper is needed, only adoption of the established predicate. Distinguish "not yours / no such endpoint" from "yours, no deliveries yet": resolve the endpoint first and raise `HTTPException(404)` when the lookup returns None or a foreign `org_id`, so an unauthorized read cannot be spelled the same as an empty result (today both return `[]`). Pair the deny case with the allow case in tests: (a) foreign `endpoint_id` → 404 and zero rows, (b) the caller's own endpoint with zero deliveries → 200 `[]`, (c) the caller's own endpoint with rows → 200 with exactly those rows, including an `active=False` endpoint, which must still list. Red-prove each separately by execution: delete the `org_id` predicate → (a) reds; change the 404 branch back to returning `[]` → the "unauthorized is not empty" assertion reds; drop the inactive-endpoint fixture's rows from the expected set → (c) reds. Preserve the `created_at DESC` ordering and the `limit` behaviour — do not remove them while adding the join. Boundary: an endpoint whose `org_id` equals the caller's is IN; an endpoint id that exists under no organization and one that exists under another are both 404, and the two must be indistinguishable to the caller.

### Critical: endpoint URL accepts any host and the client follows redirects — SSRF with a read-back channel
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only validation is `parsed.scheme.startswith("http") and parsed.netloc`, so `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/`, or any RFC1918 address is accepted, the worker POSTs to it from inside the network with `follow_redirects=True`, and `_finish` stores `response.text` where the caller can read it back through `GET /webhook-endpoints/{id}/deliveries`.
What breaks in production: A customer registers an internal URL and reads cloud instance-metadata credentials or internal service responses out of the deliveries API — a full SSRF read primitive, not a blind one.
Fix: Add an egress guard in `app/webhooks/delivery.py` used by every outbound POST: resolve the endpoint host with `socket.getaddrinfo`, reject when any resolved address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast or .is_unspecified`, and connect to the pinned resolved address so a DNS-rebind between check and connect cannot re-point it (R51's check-then-use interval). Set `follow_redirects=False` and treat 3xx as a permanent failure rather than following it. Apply the same host check at registration time in `create_webhook_endpoint` so the obvious case is rejected at 422, but keep the delivery-time check as the enforcing one — registration-time validation alone is a TOCTOU window across DNS TTL. Pair deny with allow: a public `https://` host must still receive the POST and mark `delivered`. Red-prove each clause separately by execution: point a fixture endpoint at `169.254.169.254` → the literal-address test reds when the `is_link_local` term is deleted; point a public host at a 302 to `http://127.0.0.1/` → the redirect test reds when `follow_redirects=False` is reverted; make the fixture resolver return a public address on the first call and `127.0.0.1` on the second → the pinning test reds when the connect-to-resolved-address change is reverted. Fail loudly on the outcomes that are neither pass nor fail: DNS failure, no address returned, or a host that resolves to both public and private addresses must record a named permanent failure (`status="failed_permanent"`, detail naming the guard), never a delivery attempt and never a silent skip. Preserve delivery to legitimate public endpoints and the existing retry classification. Boundary: an address one below a reserved range (e.g. `169.253.255.255`) is allowed and `169.254.0.0` is denied; when a host resolves to a mixed set, the tie resolves to deny.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: `random.choice` draws from the Mersenne Twister, whose state is recoverable from observed output and whose seeding is not cryptographically strong, so the HMAC key protecting every outbound webhook is predictable rather than secret.
What breaks in production: An attacker who obtains one org's secret (or enough generator output) can predict other orgs' secrets and forge signed `invoice.paid` events that customers' systems accept as authentic.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and drop `random`/`string`/`_ALPHABET`; rename the constant's meaning honestly — `SECRET_BYTES = 32` currently counts characters of a 62-symbol alphabet, not bytes, so state which it is and keep it at ≥32 bytes of entropy. Do not change `sign`/`verify`, so secrets already issued keep verifying — the fix must not force a rotation of live endpoints. Pair deny with allow: (a) two successive calls under `random.seed(0)` must produce different secrets (deny side: predictability), (b) an existing `whsec_`-prefixed secret must still produce the same signature through `sign` as before the change (allow side: no rotation). Red-prove separately: revert to `random.choice` with `random.seed(0)` → (a) reds; change `SECRET_PREFIX` → (b) reds. Fail loudly if the entropy source is unavailable: let the `secrets` call propagate and return 500 from `create_webhook_endpoint` rather than falling back to any weaker generator — a weak secret must never be spelled the same as a strong one. Note the existing test `test_new_signing_secret_has_prefix_and_length` asserts only prefix and length and passes identically before and after; it is not the red-proof.

### Critical: the signature is computed over different bytes than the ones sent on the wire
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `serialize`/`sign`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (sorted keys, `", "`/`": "` separators) while `client.post(..., json=delivery.payload)` serializes the body itself with insertion order and compact separators, so the bytes signed are not the bytes delivered.
What breaks in production: Every customer following `docs/webhooks.md` ("HMAC-SHA256 of `{timestamp}.{raw_request_body}`") computes a different digest and rejects 100% of deliveries — a silent total-path failure that no test in the diff can see, because `test_send_once_posts_the_signed_payload` only asserts the header *starts with* `sha256=`.
Fix: Serialize once and send those exact bytes: `body = serialize(delivery.payload).encode()`, then `client.post(endpoint.url, content=body, headers=headers)` with `Content-Type: application/json` kept explicit (passing `content=` no longer sets it — that header must be preserved, not dropped as a side effect). Sign the same `body` object, not a re-serialization. Add the round-trip test R40 requires: capture `request.content` from the `MockTransport` handler and feed the actual captured bytes plus the actual `X-Acme-Timestamp` through an independently written verifier that implements the documented formula literally, rather than calling `signing.verify`. Pair deny with allow: (a) the captured body verifies under the documented formula, (b) a body mutated by one byte fails it. Red-prove separately: revert to `json=payload` → (a) reds; skip the mutation → (b) reds. Boundary: a payload containing non-ASCII must round-trip identically — pin `ensure_ascii` and `separators` explicitly in `serialize` so the wire form is defined rather than inherited from the stdlib default, and state that ties between two dict orderings are resolved by `sort_keys=True`.

### Critical: the timestamp is not bound into the MAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign` and `verify`
What is wrong: `sign` returns a timestamp header but HMACs only the payload, and `verify` recomputes with a *fresh* timestamp it then discards, so the signature is independent of the timestamp and a receiver rejecting old timestamps gains nothing — the attacker replays the captured body with a current timestamp of their choosing and the signature still validates.
What breaks in production: `docs/webhooks.md` tells customers the five-minute timestamp window "is what stops a captured request from being replayed"; it stops nothing, so a captured `invoice.paid` can be replayed indefinitely against every customer that followed the documented verification (R49: a claim stronger than the implementation, relied on as the replay boundary).
Fix: Make the signed string the documented one — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, timestamp, body, signature)` to take the *received* timestamp and body rather than manufacturing its own, reject when `abs(now - int(timestamp)) > 300`, and reject a non-integer timestamp. Pair deny with allow: (a) a signature produced by `sign` verifies when replayed within the window, (b) the same signature with the timestamp field rewritten fails, (c) a signature whose timestamp is 301s old fails. Red-prove separately by execution: drop the `f"{timestamp}."` prefix → (b) reds; drop the skew check → (c) reds; widen the skew to 0 → (a) reds. Fail loudly on the non-decidable cases: a missing, empty, or non-numeric timestamp header must raise/return False with a named reason, never be coerced to 0 (which would land inside no window and read as an ordinary signature mismatch). Do not fix this by deleting the timestamp header — the header is what makes the window possible and must be preserved. Boundary: skew of exactly 300s is accepted, 301s rejected; when two deliveries share the same second the timestamp is not a uniqueness key and must not be used as one.

### Critical: signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: This is the reference implementation shipped in the product and mirrored by `docs/webhooks.md`; every customer copying it exposes a byte-at-a-time timing oracle that lets an attacker forge a valid signature for a payload of their choosing without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str`/`bytes` of the same type first. Pair deny with allow: (a) the signature produced by `sign` still verifies True, (b) a signature of identical length differing in the last hex character verifies False, (c) a truncated signature verifies False rather than raising. Red-prove each separately: revert to `==` — that alone does not red, so pin the property structurally instead by asserting the module contains no `==` comparison on `expected` (a source-level check that reds on the revert) and keep (a)/(b)/(c) as the behavioural pins; drop the length coercion → (c) reds with a `TypeError` instead of False. Cross-cutting: this is the only credential-shaped comparison in the diff — the delivery path never verifies a signature — so no other site needs the same change today; state that in the PR so the next inbound-webhook feature does not re-add `==`. Boundary: operands of unequal length must return False, and two signatures equal in every byte are the only True case.

### Critical: `UNIQUE INDEX ... (event_id)` allows only one delivery row per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so any organization with two or more subscribed endpoints violates the unique index on the second row.
What breaks in production: `session.add_all(rows)` raises on flush, the exception is swallowed by the `except Exception` in `app/events/dispatcher.py`, and multi-endpoint organizations silently receive *zero* webhooks — including the first endpoint, since the whole insert rolls back.
Fix: Replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is the key that actually expresses the intended idempotency (one delivery per endpoint per event) and keeps the documented at-least-once/deduplicate-on-`event_id` contract meaningful per receiver. Pair deny with allow: (a) enqueueing one event for an org with two active subscribed endpoints inserts two rows and both are later delivered, (b) enqueueing the same `event_id` twice for the same endpoint still inserts only one row. Red-prove separately: restore the single-column index → (a) reds; drop the unique index → (b) reds. Do not fix by removing uniqueness altogether — the duplicate-suppression it provides is what makes retries safe. Boundary: the pair `(endpoint_id, event_id)` is the tie-break; two endpoints of the same org sharing an `event_id` are distinct rows, and the same endpoint re-enqueued for the same `event_id` is the same row.

### Critical: the worker uses ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` return value, and `deliver`'s `endpoint` lookup
What is wrong: `_claim_batch` returns `WebhookDelivery` rows after the `with session_scope()` block exits, and `deliver` fetches `endpoint` in a session it immediately closes, then reads `delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret` and `endpoint.url` from those detached instances.
What breaks in production: With SQLAlchemy's default `expire_on_commit=True` every one of those attribute reads raises `DetachedInstanceError`, so the first batch kills `asyncio.gather`, the lock is deleted in `finally`, `batch` is unbound, and the worker crashes on its first tick — no webhook is ever delivered.
Fix: Stop passing ORM entities across session boundaries: have `_claim_batch` return plain dataclasses/tuples carrying `(delivery_id, endpoint_id, attempts, payload, url, signing_secret)` read inside the session — joining `WebhookEndpoint` in the same query so `deliver` needs no second lookup — and have `deliver`/`send_once` take those values. Pair deny with allow: (a) an integration test that runs `run_worker` for one tick against a real session factory and a `MockTransport` must mark the row `delivered`, (b) a unit test asserting the object returned by `_claim_batch` exposes no lazy ORM attribute (`assert not isinstance(row, m.WebhookDelivery)`). Red-prove separately: return the ORM rows again → (a) reds with `DetachedInstanceError`; return a `WebhookDelivery` in a wrapper → (b) reds. Note the existing tests cannot catch this: `FakeEndpoint`/`FakeDelivery` are plain classes with class attributes, an RT1 mock-reality divergence — the double cannot exhibit the detached behaviour the real boundary has, so `test_send_once_posts_the_signed_payload` passes while production raises. The fix must keep `send_once` unit-testable with simple values, not delete that test.

### Critical: `time.sleep` inside an async coroutine blocks the event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` but backs off with the blocking `time.sleep`, holding the loop thread for up to 2+4+8+16 = 30 seconds per failing delivery.
What breaks in production: `asyncio.gather` over a 100-row batch serializes instead of running concurrently, one unreachable customer endpoint stalls the loop (and every other coroutine sharing it) for tens of minutes, and the 60-second Redis lock expires while the worker still believes it holds it, so a second worker starts re-delivering the same rows.
Fix: `await asyncio.sleep(delay)` — `asyncio` is already imported. Better, stop retrying in-process at all: on a retryable failure write `status='pending'`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the poll loop re-claim the row (this also repairs the never-advanced `next_attempt_at` reported below). Pair deny with allow: (a) a test that runs two failing deliveries concurrently and asserts wall-clock elapsed is close to one backoff rather than two — proving concurrency was restored, (b) a test that a single failing delivery still waits the full documented interval before its next attempt, so the fix does not simply remove the backoff. Red-prove separately by execution: revert to `time.sleep` → (a) reds; set the delay to 0 → (b) reds. Do not fix by deleting the backoff or shrinking `MAX_ATTEMPTS` — the retry budget is the behaviour being preserved. Boundary: attempt 5 is the last attempt and schedules no further wait; attempt 4 schedules 16s.

### Major: the dispatch lock is not atomic and can wedge permanently
File: `app/webhooks/delivery.py` — `_acquire_lock`, and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` then `set` is a check-then-act with no atomicity, `set` and `expire` are two separate commands so a crash in between leaves a key that never expires, and `run_worker` deletes `LOCK_KEY` unconditionally — including a lock a different worker acquired after this one's TTL lapsed.
What breaks in production: Two workers claim and deliver the same batch (duplicate POSTs beyond the documented at-least-once tolerance), and a single ill-timed crash leaves a permanent lock that stops all webhook delivery with no reset path (R38 persisted fail-closed wedge).
Fix: Acquire with a single atomic command carrying both the flag and the TTL and a per-worker token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release only if the token still matches, via a compare-and-delete Lua script or a `WATCH`/`GETDEL` equivalent; renew the TTL from a heartbeat while a batch is in flight, or set the TTL above the worst-case batch duration implied by `MAX_ATTEMPTS`. Pair deny with allow: (a) two concurrent `_acquire_lock` calls yield exactly one `True`, (b) after the holder releases, the next `_acquire_lock` returns `True` — the lock must not become unacquirable, (c) a worker whose lock already expired must not delete the successor's key. Red-prove separately: revert to `get`+`set` and drive two coroutines through the same await point → (a) reds; remove the release path → (b) reds; drop the token comparison → (c) reds. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must log an error and back off, not return `True` and not return `False` silently forever — "could not ask" must not be spelled like "someone else holds it". Boundary: TTL expiry at exactly the batch duration is the tie — pick a TTL strictly greater than the worst-case batch and assert that relation in a test.

### Major: `in_flight` is a non-terminal state with no reaper, and `next_attempt_at` is never advanced
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; `_finish`; `backoff_for`
What is wrong: A row leaves `in_flight` only through `_finish` on the success or exhaustion path, `_claim_batch` re-claims only rows with `status == "pending"`, and no code ever writes `next_attempt_at` after enqueue — so a worker restart, a `DetachedInstanceError`, or the CHECK-constraint failure above strands the row in `in_flight` forever (R38 non-terminal transient state).
What breaks in production: Deliveries silently disappear with no alert and no retry, and `GET .../deliveries` reports a `next_attempt_at` in the past that nothing will ever act on, so operators reading the API believe a retry is pending when none is scheduled.
Fix: Give the transient state a bounded exit: stamp `claimed_at` when moving to `in_flight`, and make `_claim_batch` also re-claim rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`; write `next_attempt_at = now() + backoff_for(attempt)` and `status='pending'` on every retryable failure (see the `time.sleep` fix). Pair deny with allow: (a) a row abandoned in `in_flight` past the stale window is re-claimed on the next tick, (b) a row currently being worked on (fresh `claimed_at`) is NOT re-claimed — the reaper must not duplicate live work. Red-prove separately by execution: remove the stale-`in_flight` clause → (a) reds; remove the `claimed_at` age predicate → (b) reds. Fail loudly: a row that has been re-claimed more than a bounded number of times must terminate as `failed_permanent` with a named reason rather than cycling forever. Boundary: `claimed_at` exactly at the stale threshold is not yet stale (strict `<`); ties on `claimed_at` are broken by `id` so two workers cannot both take the same row.

### Major: retry classification contradicts the documented contract — 4xx responses are retried
File: `app/webhooks/delivery.py` — `deliver`, the `if 200 <= response.status_code < 300` branch and its `else` fallthrough
What is wrong: Every non-2xx is treated identically and retried up to `MAX_ATTEMPTS`, while `docs/webhooks.md` states "a 4xx is permanent and we stop immediately".
What breaks in production: A customer endpoint that has been decommissioned and returns 410, or one rejecting a payload with 400, receives five POSTs per event instead of one, multiplying load on a receiver that has already said no, and the documentation misleads anyone reasoning about the retry budget (R49: claim stronger than implementation).
Fix: Branch explicitly — 2xx → `delivered`; 408 and 429 → retryable; other 4xx → `failed_permanent` on the first attempt; 5xx, timeouts, and connection errors → retryable — and update `docs/webhooks.md` to name 408/429 as the retried 4xx codes rather than saying all 4xx stop. Pair deny with allow: (a) a 400 response produces exactly one request and status `failed_permanent`, (b) a 500 response still produces `MAX_ATTEMPTS` requests and ends `failed_permanent` — the retry budget must survive the change, (c) a 429 is retried, not treated as permanent. Red-prove separately by counting requests in a `MockTransport` handler: make 400 retryable → (a) reds; make 5xx permanent → (b) reds; fold 429 into the generic 4xx branch → (c) reds. Boundary: 399 and 400 fall on opposite sides, and 429 is the explicitly carved-out tie inside the 4xx range.

### Major: retry backoff has no jitter, contrary to the documented behaviour
File: `app/webhooks/delivery.py` — `backoff_for`; `tests/webhooks/test_delivery.py` — `test_backoff_grows_exponentially`
What is wrong: `backoff_for` returns exactly `2**attempt` seconds with no randomization, while `docs/webhooks.md` says "backoff is exponential with jitter"; the test pins the exact values, so it will red the moment jitter is added — the test currently encodes the wrong contract.
What breaks in production: When a shared customer endpoint or a network segment fails, every queued delivery retries in lockstep at 2s/4s/8s/16s, so the retry storm arrives as synchronized spikes exactly when the receiver is least able to absorb it.
Fix: Return `timedelta(seconds=BASE_DELAY_SECONDS**attempt * (1 + random.random() * JITTER_FRACTION))` with `JITTER_FRACTION = 0.25` (use `random` here deliberately — jitter is not key material, unlike `new_signing_secret`; state that distinction in a comment so the next reader does not "fix" it back). Rewrite `test_backoff_grows_exponentially` to assert bounds rather than equality: for each attempt, `base <= delay < base * 1.25`. Pair deny with allow: (a) 100 samples at the same attempt must not all be equal — jitter is actually applied, (b) every sample must still lie within the documented band, so the fix does not turn backoff into an unbounded random wait. Red-prove separately: remove the jitter term → (a) reds; raise `JITTER_FRACTION` to 4.0 → (b) reds. Do not fix by relaxing the assertion to "delay is a positive number" — the exponential growth the original test pinned is the behaviour to preserve. Boundary: the lower bound is inclusive (a zero-jitter draw is legal) and the upper bound exclusive.

### Major: request signature headers are logged, and the upstream response body is stored unbounded
File: `app/webhooks/delivery.py` — `log.info("POST %s headers=%s", endpoint.url, headers)` in `send_once`; `_finish(..., response.text)` in `deliver`
What is wrong: The full header dict — including `X-Acme-Signature` and `X-Acme-Timestamp` — is written at INFO on every attempt, and the entire upstream response body is persisted into `webhook_deliveries.response_body` with no size cap.
What breaks in production: Signatures reach log aggregation where anyone with log access can replay a captured body against the customer's receiver, and a customer endpoint returning a large body (or an SSRF target returning an internal page) writes unbounded text into the database and back out through the deliveries API.
Fix: Log the endpoint id and the delivery id only — never the header dict — and if a diagnostic is needed log the first 8 characters of the signature with an explicit comment saying why that prefix is not sufficient to replay. Truncate the stored body: `detail = response.text[:2048]` with an explicit `"… (truncated)"` marker so a truncated body is distinguishable from a short one. Pair deny with allow: (a) a log-capture test asserts no emitted record contains the value of `SIGNATURE_HEADER`, (b) a failing delivery still records a non-empty `response_body` explaining the failure — the diagnostic value must be preserved, not deleted. Red-prove separately: restore the `headers=%s` format → (a) reds; set the truncation length to 0 → (b) reds. ### Major: only three event types can ever reach webhooks, regardless of what an endpoint subscribed to
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES` and the `if envelope.type in WEBHOOK_EVENT_TYPES` guard
What is wrong: A hardcoded three-member set gates enqueueing, while `WebhookEndpoint.event_types` accepts arbitrary strings and `docs/webhooks.md` states that an empty `event_types` "subscribes the endpoint to every event type we emit" — two independent membership decisions with different domains (R12/R42).

Red-prove separately: restore the dispatcher-level set → (a) reds; remove the per-endpoint filter in `enqueue_for_event` → (b) reds. Do not fix by widening `WEBHOOK_EVENT_TYPES` to the current list of types — that reproduces the drift the next time an event is added. Boundary: an empty `event_types` list means all types (the documented tie) and must be tested explicitly, since it is also the default value.

### Major: `organizations.webhooks_enabled` is added by the migration and read by nothing
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: The column is created and defaults to FALSE, but no model maps it and no code path consults it — `create_webhook_endpoint` and `enqueue_for_event` both proceed regardless (R41: a declared capability with no backing path).
What breaks in production: Operators see a per-org kill switch that does nothing — turning it off leaves webhooks flowing, and the FALSE default advertises "webhooks are off for everyone" while every org can register endpoints and receive deliveries.

To wire it: map the column on `Organization`, reject `create_webhook_endpoint` with 403 when `org.webhooks_enabled` is false, and skip `enqueue_for_event` for those orgs — enforced at the enqueue path, not only at registration, so disabling it stops in-flight subscriptions too. ### Major: webhook enqueue failures are swallowed, and the enqueue runs outside the event's transaction
File: `app/events/dispatcher.py` — the `try: await webhook_delivery.enqueue_for_event(...) except Exception as exc: log.warning(...)` block
What is wrong: The enqueue happens in a separate `session_scope` after the event transaction has already committed, and any failure is downgraded to a warning with no retry, no dead-letter, and no signal to the caller (R9/R5).
What breaks in production: The event is durably recorded while its webhook rows are not, and because the failure is a WARNING among high-volume INFO logs, an outage of the delivery table or the unique-index violation reported above drops customer notifications indefinitely without an alert.
Fix: Persist the delivery rows in the same transaction as the `Event` insert — move the endpoint lookup and `add_all` inside the existing `with session_scope()` block in `dispatch`, so the event and its outbox rows commit atomically and the worker's poll loop becomes the only delivery mechanism (a transactional-outbox shape the schema already supports, since `webhook_deliveries` is polled rather than pushed). If the enqueue must stay separate, replace the bare `except Exception` with a narrow catch that re-raises after recording a durable failure row, and log at ERROR with the event id. Pair deny with allow: (a) an exception raised while inserting delivery rows must roll back the `Event` insert too — assert the event row is absent afterwards, (b) the normal path still returns `event_id` and still notifies the in-process `SUBSCRIBERS`, which must not be moved inside the transaction. Red-prove separately: keep the enqueue in its own session → (a) reds; move the `for subscriber in SUBSCRIBERS` loop inside the transaction → (b)'s ordering assertion reds. Do not fix by removing the `try` and letting the exception escape `dispatch` — event persistence must not become dependent on webhook availability in the *other* direction; the atomic-commit form is what gives both.

### Major: three new public routes ship with no rate limiting and no per-org endpoint cap
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: No rate limiter is applied to any of the new routes (RS2), and nothing bounds how many endpoints an organization may register.
What breaks in production: A single customer can register thousands of endpoints, each of which multiplies every emitted event into another outbound POST from your infrastructure — an amplification vector that compounds with the SSRF finding above — and the unauthenticated-by-id `deliveries` route can be scraped at full speed.

Pair deny with allow: (a) creating the 11th endpoint returns 409 and inserts nothing, (b) creating the 10th succeeds — the cap must not be off by one against legitimate users, and (c) deleting an endpoint frees a slot, so the cap does not become a permanent lockout. Red-prove separately: change `>` to `>=` in the cap comparison → (b) reds; remove the cap → (a) reds; count all endpoints instead of active ones → (c) reds. ### Major: timestamps mix naive and aware values across the model, the migration, and the writer
File: `app/webhooks/delivery.py` — `next_attempt_at=datetime.utcnow()` in `enqueue_for_event`; `app/webhooks/models.py` — `DateTime(timezone=True)`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP NOT NULL`

Red-prove separately by executing the suite under both `TZ` values: revert to `utcnow()` → (a) reds; revert the DDL to `TIMESTAMP` → (a) reds for a different reason the failure names (the comparison operand type). ### Minor: `_finish` dereferences a row that may not exist

### Minor: `run_worker` can raise `NameError` on `batch`
