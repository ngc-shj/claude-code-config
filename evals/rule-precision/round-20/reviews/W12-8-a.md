### Critical: `list_deliveries` has no tenancy filter — any authenticated user reads any org's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The query is scoped only by the caller-supplied `endpoint_id` and never joined back to `user.org_id`, while its sibling `list_webhook_endpoints` two functions above does filter `WebhookEndpoint.org_id == user.org_id`.
What breaks in production: Any authenticated tenant can enumerate `endpoint_id` and read another organization's `event_type`, `status` and delivery metadata — and, once `response_body` is exposed or joined, the third-party response bodies too.
Fix: Resolve the endpoint first inside the same `session_scope` with `session.query(WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`, raise `HTTPException(404)` when it is `None` (404, not 403, so the endpoint id space is not an oracle), and only then query deliveries by `endpoint_id`. Preserve the feature the endpoint exists for: the owning org must still receive its own rows, so pair the tests — one test asserting an owner GET returns the seeded delivery ids, one asserting a foreign-org GET returns 404 **and** that the response body contains none of the seeded ids (assert the absence of data, not only the status, per RT8). Red-prove each clause separately by execution: (a) delete the `org_id ==` predicate and confirm the foreign-org test reddens on the leaked id assertion; (b) change the `404` to `200`+empty-list and confirm the status assertion reddens; (c) confirm the owner test stays green under both mutations, so the fix is not measured only in the deny direction. Route the non-decidable cases loudly rather than permissively: an endpoint id that does not resolve, and a `user.org_id` that is `None`, must both raise rather than fall through to an unfiltered query — "no org to compare" must not be spelled the same as "org matches". Boundary and tie: the comparison is exact equality on `org_id`, an endpoint whose `org_id` equals the caller's is inside, and two orgs can never share an `endpoint_id` because it is the `webhook_endpoints` primary key.

### Critical: the signing secret is returned on every endpoint read, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret"`
What is wrong: `to_dict()` embeds `signing_secret`, and `list_webhook_endpoints` calls the same `to_dict()` for every row, so the secret is served on every `GET /v1/settings/webhook-endpoints` — while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: The HMAC key that is the sole authenticity control for outbound webhooks is disclosed to any principal that can call the list route (and to every proxy, access log, and browser cache along the way), so signature verification proves nothing about origin.
Fix: Remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` build its 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable returned by `new_signing_secret()`, so exactly one call site discloses it. Do not fix by deleting the disclosure entirely: the create response must still carry the secret or the feature is unusable, so state that as the preserved behaviour and pin it with an allow-side test asserting the 201 body contains a `whsec_`-prefixed value. Red-prove the two clauses separately: (a) re-add `"signing_secret"` to `to_dict()` and confirm a list-route test asserting `"signing_secret" not in body[0]` reddens; (b) drop the key from the create response and confirm the 201 test reddens. Because the same `to_dict()` is the response shape for both routes, add the assertion at the route level, not the model level, so a later caller of `to_dict()` cannot re-leak silently; where a caller needs the secret it must ask for it by name and that call must fail loudly (`KeyError`) rather than return `None`. Boundary and tie: the create response is the single inside case, every other read is outside, and a re-create for the same URL mints a new secret rather than re-reading the old one. Cross-cutting: `WebhookDelivery.to_dict()` was checked and exposes no secret material, but it does expose `payload`-derived fields to the route above — fix that route's tenancy first.

### Critical: endpoint URL validation permits `http://` and internal addresses, and the client follows redirects — full read SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: `scheme.startswith("http")` admits `http`, and any scheme merely prefixed with it, with no host restriction, while `run_worker` builds its client with `follow_redirects=True` and `deliver` stores `response.text` into `response_body`.
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or any RFC1918 host), the worker POSTs to it and persists the response body, and the tenant reads it back through the deliveries route — an authenticated cloud-credential exfiltration primitive, amplified because a `302` to an internal host is followed automatically.
Fix: Replace the prefix test with an exact allowlist `if parsed.scheme != "https"` (matching `docs/webhooks.md`, which already says only `https://` is accepted), require `parsed.hostname`, resolve the hostname at request time and reject when any resolved address is private, loopback, link-local, or unique-local (`ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved`), and set `follow_redirects=False` on the `httpx.AsyncClient` in `run_worker`. Re-validate at send time in `send_once`, not only at registration — DNS is re-resolved per request and a registration-time check is a TOCTOU window (R51), so the same helper must be called from both sites. Preserve the feature: legitimate public HTTPS endpoints must still be registerable and still deliver, so pair every deny fixture with an allow fixture — `https://hooks.example.com/acme` resolving to a public address registers with 201 and delivers, adjacent to the boundary. Red-prove each clause separately: (a) restore `startswith("http")` and confirm the `http://` fixture test reddens; (b) remove the private-address check and confirm the `https://` host resolving to `127.0.0.1` test reddens; (c) restore `follow_redirects=True` and confirm a MockTransport test asserting no second request after a `302` reddens; (d) confirm the public-host allow test stays green under all three. Fail loudly on the undecidable cases: DNS resolution failure, an empty address list, or an unparseable host must raise a 422 at registration and mark the delivery failed at send time — never fall through to "not proven private, therefore allowed". Boundary and tie: `0.0.0.0` and IPv6-mapped IPv4 (`::ffff:127.0.0.1`) are inside the deny set, and a hostname resolving to both a public and a private address is denied.

### Critical: signature comparison is a plain `==`, not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The HMAC digest is compared with Python's short-circuiting `str.__eq__` instead of `hmac.compare_digest` (RS1).
What breaks in production: Any consumer of this shipped helper — and the inbound path it will be reused for — leaks digest bytes through comparison timing, letting an attacker recover a valid signature byte by byte without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with a guard rejecting a non-`str` or `None` `signature` before the call (`compare_digest` raises `TypeError` on mixed types, which must surface as an explicit rejection rather than a 500). Preserve the allow side: `test_verify_accepts_signature_produced_by_sign` must stay green, and add a second allow case using a hard-coded known-answer digest so the change is measured in both directions. Red-prove the two clauses separately by execution: (a) revert to `==` and confirm a test asserting `hmac.compare_digest` is on the call path — e.g. monkeypatching `hmac.compare_digest` to raise and asserting `verify` propagates — reddens; (b) pass `signature=None` and confirm the added guard test reddens when the guard is removed. Fail loudly rather than silently: a malformed signature (missing `sha256=` prefix, wrong length) must return `False` through an explicit branch that is itself tested, so "could not compare" is not spelled the same as "did not match". Boundary and tie: equal-length digests are the only inside case, a length mismatch returns `False` without leaking the length through an early return, and two distinct payloads producing the same digest is the collision case `compare_digest` is not asked to decide.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The secret is drawn from `random.choice`, which is the Mersenne Twister — a deterministic, fully reconstructible generator — and the `SECRET_BYTES = 32` name describes bytes while the loop produces 32 alphanumeric characters.
What breaks in production: An attacker who observes any 624 consecutive outputs of the process's shared `random` state (or who can create endpoints in a loop) recovers the generator state and predicts every other tenant's signing secret, forging webhooks that verify perfectly.
Fix: Use `secrets.token_urlsafe(SECRET_BYTES)` (or `secrets.choice` over `_ALPHABET`), drop the `random` import, and rename the constant to what it now measures — keep `SECRET_BYTES = 32` only if the value passed is a byte count. Preserve what made the defect visible: `test_new_signing_secret_has_prefix_and_length` currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which is a length identity that would silently keep passing across a weakened generator, so replace it rather than delete it — assert the prefix, assert a minimum entropy-bearing length, and add a distinctness test drawing 1000 secrets and asserting no duplicates. Red-prove each clause separately: (a) reseed `random.seed(0)` before two calls and confirm a test asserting the two secrets differ reddens against the old `random.choice` implementation and stays green against `secrets`; (b) shorten the generated portion by one and confirm the length assertion reddens. Fail loudly when the source is unavailable: `secrets` raises `NotImplementedError` on a platform without a system CSPRNG, and that must propagate as a 500 at registration rather than be caught and replaced with a fallback — "no entropy source" must not be spelled the same as "here is a secret". Boundary and tie: the minimum acceptable length is 32 URL-safe characters inclusive, and two endpoints in the same org must never share a secret, which is what the distinctness test pins.

### Critical: the timestamp is not covered by the HMAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`, `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `sign` computes the timestamp and then MACs the payload alone, while `docs/webhooks.md` tells every customer the signature is "the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`" and that rejecting old timestamps "is what stops a captured request from being replayed" (R49: the claim is stronger than the implementation).
What breaks in production: An attacker who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to now — the header is unauthenticated, so every customer who implements the documented five-minute check still accepts the replay.
Fix: Change the MAC input to `f"{timestamp}.{body}"` where `body` is the exact byte string transmitted, and thread `timestamp` through `verify(secret, payload, signature, timestamp)` so verification recomputes over the same bound pair; reject when the supplied timestamp is absent or non-numeric. Do not fix by relaxing the doc instead: the replay window is the feature, so state that the five-minute rejection described in `docs/webhooks.md` must remain implementable and pin it with a test that signs at `t`, verifies at `t+299` (allow) and at `t+301` (deny). Red-prove each clause separately: (a) revert the MAC input to payload-only and confirm a test asserting that a signature made at `t` fails verification when presented with timestamp `t+3600` reddens; (b) remove the numeric guard and confirm the malformed-timestamp test reddens; (c) confirm the `t+299` allow case stays green under both, so the fix is not measured only in the deny direction. Fail loudly on the middle cases: a missing timestamp header, a non-integer, and a timestamp in the future beyond the tolerance must each return `False` through a branch that names itself in the log, never through the same path as a digest mismatch. Boundary and tie: the window is inclusive at exactly 300 seconds, a timestamp exactly equal to now is accepted, and two deliveries signed in the same second are distinguished by `event_id` in the payload, not by the timestamp.

### Critical: the bytes signed are not the bytes transmitted
File: `app/webhooks/delivery.py` — `send_once`, `sign(endpoint.signing_secret, delivery.payload)` followed by `client.post(..., json=delivery.payload, ...)`
What is wrong: The MAC is taken over `signing.serialize(payload)` (`json.dumps(..., sort_keys=True)`, default `", "`/`": "` separators) while httpx serializes the body itself with its own compact encoder and original key order, so the signed string and the wire body differ in both separators and key order (R40: producer wire shape vs a strict consumer).
What breaks in production: Every customer following `docs/webhooks.md` and computing the HMAC over the raw request body they received gets a mismatch on every single delivery, so the whole feature fails closed at 100% of integrations while the retry loop hammers each endpoint five times.
Fix: Serialize once and send those exact bytes — `body = signing.serialize(delivery.payload).encode()`, sign `body`, then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` — never `json=` alongside a separately-computed signature. Add the round-trip test R40 requires: feed the *actual* transmitted `request.content` captured by `httpx.MockTransport` into an independently written verifier (recompute `hmac.new(secret, f"{ts}.{body}".encode(), sha256).hexdigest()` in the test, not by calling `sign`) and assert equality — the current `test_verify_accepts_signature_produced_by_sign` cannot detect this class because both sides call the same serializer. Red-prove each clause separately: (a) restore `json=delivery.payload` and confirm the round-trip test reddens on the digest comparison; (b) drop `sort_keys=True` from `serialize` and confirm a fixed known-answer-vector test reddens; (c) confirm a delivery with a single-key payload still succeeds, so the fix is not measured only on the failing shape. Fail loudly when serialization cannot run: a payload containing a non-JSON-serializable value must raise and mark the delivery `failed_permanent` with a named reason, not be silently coerced. Boundary and tie: the empty payload `{}` must sign and verify, and two payloads differing only in key order must produce the same digest — which is exactly what `sort_keys=True` guarantees and what the wire body must therefore also honour.

### Critical: the unique index on `event_id` alone makes multi-endpoint orgs receive nothing
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all sharing the same `event_id`, so the second row of any batch violates the unique index and aborts the whole `session.add_all` transaction.
What breaks in production: Any organization with two or more active endpoints receives zero webhooks — and the failure is invisible because `dispatch` wraps the call in `except Exception` and downgrades it to `log.warning`, returning the event id as if delivery were scheduled.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint the at-least-once/dedupe contract in `docs/webhooks.md` actually needs (one delivery per endpoint per event). Preserve the property the index was added for: duplicate enqueue of the same event to the same endpoint must still be rejected, so pair the tests — one asserting two endpoints in one org both get a row for a single event, one asserting a second `enqueue_for_event` call for the same `(endpoint_id, event_id)` raises `IntegrityError`. Red-prove each clause separately: (a) revert to the single-column index and confirm the two-endpoint test reddens; (b) drop the index entirely and confirm the duplicate-enqueue test reddens. Separately, stop the swallow from hiding it: narrow `except Exception` in `app/events/dispatcher.py` to re-raise `IntegrityError` (or at minimum `log.exception` and increment a failure counter) so "enqueue examined nothing" is not spelled the same as "enqueue found nothing to do". Boundary and tie: an org with exactly one endpoint is the case both index shapes accept identically, and an endpoint whose `event_types` excludes the event produces no row at all — that absence must not be counted as a dedupe hit.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: The retry backoff uses the blocking `time.sleep` inside an `async def` that `run_worker` runs under `asyncio.gather`, so the sleep halts the event loop rather than yielding.
What breaks in production: One failing endpoint freezes the entire worker process for up to 2+4+8+16 = 30 seconds per delivery, and because `gather` interleaves nothing during a blocking call the 100-row batch serializes — a batch of failing endpoints stalls the loop for tens of minutes, past the 60-second Redis lock TTL, so a second worker starts while the first still holds rows.
Fix: Replace with `await asyncio.sleep(delay)` (`asyncio` is already imported in this module) and add jitter as `docs/webhooks.md` already promises: `delay = backoff_for(attempt).total_seconds() * random.uniform(0.5, 1.5)` using `random` for jitter only, never for secrets. Preserve the behaviour the sleep exists for: the delay between attempts must still be observably non-zero and monotonically growing, so keep `test_backoff_grows_exponentially` and add an allow-side test asserting a delivery that succeeds on attempt 2 completes with `attempts == 2`. Red-prove each clause separately: (a) restore `time.sleep` and confirm a test that starts a competing coroutine and asserts it makes progress during the backoff reddens; (b) remove the jitter and confirm a test asserting 100 sampled delays are not all identical reddens; (c) confirm the success-on-attempt-2 test stays green under both. Fail loudly on the case neither pass nor fail: if the computed delay exceeds the lock TTL the worker must release the lock and re-claim rather than sleep past it — "slept through the lease" must not look like "still holding the lock". Boundary and tie: `attempt == MAX_ATTEMPTS` sleeps zero times and finishes terminally, and two deliveries scheduled for the identical `next_attempt_at` are both claimed in the same batch, which is why the jitter matters.

### Major: `in_flight` has no exit path or timeout — crashed batches are lost forever
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `run_worker`
What is wrong: `_claim_batch` moves rows to `in_flight` but only `_finish` ever leaves that state, and `_claim_batch` selects `status == "pending"` exclusively, so any exception that is not `httpx.HTTPError` — the `IntegrityError` above, a `TypeError`, a process kill — strands the rows permanently (R38, non-terminal transient state with no failure-exit and no bounded timeout).
What breaks in production: Deliveries silently vanish with no operator-visible signal, and the deliveries API reports them as perpetually `in_flight`, so a customer chasing a missing invoice webhook is told it is still being attempted.
Fix: Stamp `claimed_at` when moving a row to `in_flight`, and extend `_claim_batch`'s predicate to also reclaim rows where `status == "in_flight" AND claimed_at < now() - INTERVAL '5 minutes'`, resetting them to `pending` with `attempts` unchanged; wrap `deliver`'s body in `try/except Exception` that calls `_finish(..., "pending", ...)` with a future `next_attempt_at` so an unexpected exception exits the transient state instead of stranding it. Preserve what the state is for: a delivery genuinely in flight must not be double-sent, so the reclaim threshold must exceed `REQUEST_TIMEOUT` (30s) with margin, and pair the tests — one asserting a row stuck at `claimed_at = now - 6min` is reclaimed, one asserting a row at `now - 10s` is *not*. Red-prove each clause separately: (a) remove the reclaim predicate and confirm the stuck-row test reddens; (b) remove the `except Exception` exit and confirm a test injecting a `TypeError` into `send_once` and asserting the row ends `pending` reddens; (c) confirm the fresh-row test stays green under both, so the reclaim is measured in the false-reclaim direction too. Fail loudly: a row whose `claimed_at` is `NULL` (rows written before this migration) must be treated as reclaimable and logged, never skipped silently. Boundary and tie: a row at exactly the 5-minute mark is reclaimed, and two workers reclaiming the same row are serialized by the `SELECT ... FOR UPDATE SKIP LOCKED` the claim query should also carry.

### Major: the Redis lock is not atomic to acquire, not atomic to expire, and released by whoever finishes first
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get`-then-`set` is a check-then-act race, `expire` is a separate round trip so a crash between `set` and `expire` leaves a TTL-less lock nothing ever clears, and the unconditional `delete` in `finally` removes the key even when the TTL already expired and another worker owns it (R5, and R38's persisted fail-closed wedge with no reset path).
What breaks in production: Two workers pass the lock simultaneously and double-deliver, or a single mistimed crash wedges the whole webhook pipeline permanently with no automatic recovery and no alert.
Fix: Acquire with a single atomic command carrying a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = secrets.token_hex(16)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only free its own lease; renew the lease inside the batch loop rather than assuming 60s suffices. Preserve the mutual exclusion the lock provides: a second worker must still be excluded while the first holds a live lease, so pair the tests — one asserting concurrent `_acquire_lock` calls yield exactly one `True`, one asserting a worker whose lease expired cannot delete the successor's key. Red-prove each clause separately: (a) revert to `get`-then-`set` and confirm the concurrency test reddens; (b) drop `ex=60` and confirm a test asserting `TTL(LOCK_KEY) > 0` immediately after acquisition reddens; (c) revert to unconditional `delete` and confirm the foreign-lease test reddens. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must raise and stop the worker, not `return False` forever and not `return True` — "cannot determine lock state" must be neither of the two normal answers. Boundary and tie: a lease whose TTL is exactly 0 is treated as expired, and two workers presenting the same token is impossible by construction of `token_hex`.

### Major: `_claim_batch` and `deliver` use ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` returning `rows` outside the `with session_scope()` block, and `deliver`'s `endpoint` fetched inside its own closed block

Red-prove each clause separately: (a) return the ORM rows again and confirm the payload-access test reddens with `DetachedInstanceError`; (b) remove the status assignment and confirm the fresh-session status test reddens. Grounding note per Finding Floor: `app/db.session_scope` is not in this diff, so if it is already built with `expire_on_commit=False` this finding closes — the answer that closes it is that configuration plus a test pinning it, and the fix above should then be reduced to adding that test. ### Major: an endpoint with empty `event_types` receives three event types, not "every event type we emit"
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES` and the `if envelope.type in WEBHOOK_EVENT_TYPES` guard

Fail loudly: an event type absent from the registry must raise at startup, not be silently non-deliverable. ### Major: retry policy diverges from the documented contract on 4xx and on jitter
File: `app/webhooks/delivery.py` — `deliver`'s `while True` loop and `backoff_for`
What is wrong: `docs/webhooks.md` states "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` retries every non-2xx response — including 400, 401 and 410 — for the full five attempts, and `backoff_for` returns a pure power of two with no jitter (R29, a documented rationale that the implementation contradicts).
What breaks in production: A customer endpoint returning 401 after a credential rotation is hammered five times per event across every event in the batch, and because every delivery of a batch shares the identical unjittered schedule, all retries land in the same instant — a synchronized thundering herd against an endpoint that is already failing.
Fix: Branch on the status class in `deliver` — `if 400 <= response.status_code < 500 and response.status_code not in RETRIABLE_4XX: _finish(delivery.id, "failed_permanent", attempt, status_code, detail); return` — with `RETRIABLE_4XX = frozenset({408, 425, 429})` named as a module constant beside `MAX_ATTEMPTS`, and add multiplicative jitter in the sleep site as described above. Preserve what the retry loop exists for: 5xx, timeouts and connection errors must still retry to the documented limit, so pair the tests — one asserting a 400 finishes `failed_permanent` after exactly one attempt, one asserting a 503 retries to `MAX_ATTEMPTS`. Red-prove each clause separately: (a) remove the 4xx branch and confirm the one-attempt test reddens on the `attempts` value (assert the attempt count, not only the status); (b) add `429` to the permanent side and confirm the retriable-429 test reddens; (c) confirm the 503 test stays green under both. Fail loudly on the case that is neither: a response with no status (a raised `httpx.HTTPError`) already routes to the retry path, and a status outside 100–599 must be logged and treated as permanent rather than falling through the range checks. Boundary and tie: 400 is inclusive-permanent and 500 is inclusive-retriable, 429 sits on the retriable side of the 4xx boundary, and two attempts scheduled for the identical instant are separated by the jitter.

### Major: the delivery request signature is written to the application log
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: The logged `headers` dict contains `X-Acme-Signature` and `X-Acme-Timestamp` for every delivery, at `INFO`, so a valid signature for a known payload is written to a surface that is shipped, indexed, and readable by people with no access to the webhook system.
What breaks in production: Anyone with log access can replay a captured delivery to the customer endpoint with a valid signature — and because the timestamp is not covered by the MAC (see above), the replay is not even time-bounded.

Fail loudly: if the redaction helper is unavailable the call must raise at import rather than silently fall back to logging the raw mapping. Boundary and tie: the timestamp header alone is not secret and may stay, the signature never may, and two deliveries of the same event to different endpoints are distinguished in the log by `delivery.id`.
