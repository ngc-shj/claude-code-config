### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, and `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (separators `", "` / `": "`, keys reordered), while `send_once` puts the payload on the wire via `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and insertion order — so the signature covers a byte string the receiver never sees, and `docs/webhooks.md` tells the receiver to HMAC `"{timestamp}.{raw_request_body}"`, a third string that neither side produces.
What breaks in production: every customer who implements the documented verification rejects 100% of deliveries, and every customer who instead HMACs the raw body they received also rejects 100% of them, so the feature ships totally non-functional while the sender's own tests stay green (R40, Critical — silent total-path failure).
Fix: make `serialize()` the single producer of the wire bytes. In `send_once`: `body = signing.serialize(delivery.payload).encode()`; `ts, sig = sign(endpoint.signing_secret, body)`; `await client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` — `content=`, never `json=`. Change `sign`/`verify` to take the already-serialized `bytes` so no caller can re-serialize, and MAC the documented string `f"{timestamp}.".encode() + body`. Add a round-trip test that captures `request.content` from `httpx.MockTransport` and feeds those exact bytes into a verifier written independently from the doc text (do not call `sign()` to build the expected value — RT1 clause (d)). Allow side that must still pass: unmodified captured body + its own `X-Acme-Timestamp` + the correct secret verifies True. Red-prove each clause separately, by execution: (i) flip one byte of the captured body → verifier False; (ii) reorder two top-level payload keys before signing → the round-trip still True (proves `serialize` is the only serializer, not that the test is insensitive); (iii) revert `content=` to `json=` → the round-trip test reds. Fail loudly: `verify` returns False (never raises `binascii.Error`) on a signature lacking the `sha256=` prefix or carrying non-hex, and `send_once` raises rather than sending if `endpoint.signing_secret` is empty — "could not sign" must not be spelled like "signed". Preserve: deterministic key ordering (`sort_keys=True`) stays — it is what makes the MAC reproducible; the fix moves it onto the wire, it does not delete it. Boundary/tie: a payload serializing to zero-length body is signed as `f"{ts}."` and is valid, not skipped; equal payloads to two endpoints produce different MACs because the secrets differ, which is the intended non-tie.

### Critical: the timestamp is outside the MAC, so the documented replay window is not enforceable
File: `app/webhooks/signing.py` — `sign()` line `mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`
What is wrong: the returned `timestamp` is sent in `X-Acme-Timestamp` but is not an input to the HMAC, so the header is attacker-mutable while the signature stays valid, and `verify()` neither accepts nor checks a timestamp at all.
What breaks in production: `docs/webhooks.md` instructs receivers to "reject requests whose timestamp is more than five minutes old — that window is what stops a captured request from being replayed", but an attacker who captures one delivery can rewrite the timestamp to `now` forever and the signature still verifies, so the only advertised replay defence is void and a captured `invoice.paid` can be replayed indefinitely against the customer's ledger (R49 — a claim stronger than the implementation, relied on elsewhere as the boundary).
Fix: bind the timestamp into the MAC as the doc already specifies — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, body, timestamp, signature, *, max_age=300)` to recompute over the caller-supplied timestamp and reject when `abs(now - int(timestamp)) > max_age`. Ship the reference verifier in `docs/webhooks.md` as code, since prose is what diverged. Allow side that must still pass: a signature produced `max_age` seconds ago with the correct secret still verifies True. Red-prove each clause separately, by execution: (i) mutate only the timestamp header of a valid request → verify False; (ii) set the request timestamp to `now - max_age - 1` with a correct MAC over it → verify False for staleness, and the failure must be distinguishable from a MAC mismatch in the return/log; (iii) remove the `f"{timestamp}."` prefix from the MAC input → test (i) reds. Fail loudly: a non-integer, absent, or overflowing timestamp returns False and logs "unparseable timestamp", never falls through to a MAC-only comparison. Preserve: verification must still succeed for a well-formed in-window request — do not fix staleness by widening `max_age` past 300s. Boundary/tie: at exactly `now - ts == max_age` the request is ACCEPTED (`>` rejects, not `>=`), and a future-dated timestamp is rejected under the same absolute bound so clock skew cannot be used to mint a long-lived signature.

### Critical: HMAC comparison is not constant-time
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: `==` on the hex digest short-circuits at the first differing byte, so comparison time leaks a prefix-match oracle (RS1).
What breaks in production: anyone able to submit candidate signatures to a service that reuses this `verify()` — it is exported, and `docs/webhooks.md` presents this scheme as the customer-side recipe — can recover a valid signature byte by byte from timing, forging deliveries without ever learning the secret.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` first and a `TypeError`/non-`str` input returning False before the comparison. Allow side that must still pass: the signature produced by `sign()` for the same secret and body verifies True. Red-prove each clause separately, by execution: (i) pass a signature differing only in its last hex character → False; (ii) pass `signature=None` and a `bytes` signature → False, not `TypeError` escaping the function; (iii) revert to `==` and assert `hmac.compare_digest` appears in the call path (a grep-based or `unittest.mock` spy assertion), because no functional test can distinguish `==` from `compare_digest` on outcome alone — this is the mutation the outcome tests cannot catch. Fail loudly: a malformed signature returns False and increments a counted "malformed signature" log line rather than being silently indistinguishable from a wrong-key rejection. Preserve: `verify` keeps returning a plain bool for the correct-key case; do not "fix" by raising on mismatch and changing every caller's control flow. Boundary/tie: `compare_digest` on two equal-length equal strings returns True; unequal lengths return False in time proportional to the first argument only, which is why `expected` (fixed length, 71 chars) is passed first.

### Critical: the signing secret is returned by the list endpoint, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: the single `to_dict()` used by both the create handler (where disclosure is intended) and `GET /v1/settings/webhook-endpoints` (where it is not) emits the secret on every read, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: any credential with read access to the settings API — a dashboard session, a read-scoped API key, a browser extension, an HTTP access log, a support screen-share — yields the HMAC key for every endpoint in the org, letting the holder forge deliveries the customer's verifier will accept (RS4, Critical: secrets in a served artifact; R49, the doc claim is the reason no other protection was added).
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()`; add a separate `to_dict_with_secret()` that calls `to_dict()` and adds the key, and call it from `create_webhook_endpoint` only. Allow side that must still pass: `POST /v1/settings/webhook-endpoints` still returns a `signing_secret` in its 201 body — assert on it, because a fix that strips the secret everywhere breaks the only way a customer can ever obtain it. Red-prove each clause separately, by execution: (i) a test that `GET /v1/settings/webhook-endpoints` response JSON contains no key matching `secret` at any depth — reds if `to_dict()` regains the field; (ii) a test that the 201 create body does contain it — reds if the fix over-strips; (iii) grep-style assertion that `to_dict_with_secret` has exactly one call site. Fail loudly: serialization of an endpoint whose `signing_secret` is unexpectedly `None` raises rather than emitting `null`, so a rotation bug cannot masquerade as a redacted field. Preserve: the list endpoint keeps returning `id`, `url`, `event_types`, `active` — do not fix by removing the list route. Boundary/tie: the create response is the boundary; a retried create (same URL, same org) mints a NEW endpoint row with a new secret rather than re-disclosing the existing one, so the "only place" claim stays literally true.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`, `random.choice(_ALPHABET)`
What is wrong: `random` is the Mersenne Twister, a deterministic generator whose full internal state is recoverable from a few hundred consecutive outputs, used here to mint an HMAC key while the stdlib's `secrets` module — the shared, purpose-built helper for exactly this — is not used (R1, Critical: the duplicated behaviour is a security control).
What breaks in production: an attacker who registers enough endpoints of their own observes enough MT output to reconstruct the generator state and predict the secrets minted for other tenants around the same time, forging signed deliveries into those customers' systems.
Fix: `import secrets` and `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`; delete the `random`, `string`, and `_ALPHABET` definitions outright rather than leaving them as an unreferenced fallback (R1 clause (d)), and rename `SECRET_BYTES` to match its new meaning (it currently names bytes but is consumed as a character count — see Minor below). Behavioural differences this adoption introduces, per R1 clause (b): `token_urlsafe(32)` yields 43 characters from a 64-symbol alphabet including `-` and `_`, not 32 from 62 alphanumerics, so the length and character-class assertions must move with it. Allow side that must still pass: a freshly minted secret still starts with `whsec_` and still round-trips through `sign`/`verify` unchanged. Red-prove each clause separately, by execution: (i) a test asserting `len(set(new_signing_secret() for _ in range(1000))) == 1000` reds against any seeded/repeating generator; (ii) a test asserting the entropy budget — `len(secret) - len(SECRET_PREFIX) >= 43` — reds if someone shortens the token; (iii) revert to `random.choice` under `random.seed(0)` and assert two processes produce different secrets — this reds only for the CSPRNG version, which is the point. Fail loudly: if `secrets` cannot produce bytes the call raises and endpoint creation returns 5xx; it must never fall back to `random`. Preserve: the `whsec_` prefix, which customers use to recognise the value. Boundary/tie: two endpoints created in the same microsecond must receive different secrets — that is the tie the current implementation is weakest on and the one clause (i) pins.

### Critical: `list_deliveries` is not scoped to the caller's organization (IDOR)
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the filter uses only the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while every sibling handler in the very same file — `get_profile`, `list_api_keys`, `list_webhook_endpoints`, and `enqueue_for_event` in `delivery.py` — does scope by org (R3, Critical because the unpropagated pattern is a tenancy control).
What breaks in production: any authenticated user can walk `endpoint_id = 1, 2, 3, …` and read other tenants' delivery history — event types, event ids, volumes, failure counts, and the timing of their billing events — a cross-tenant disclosure that a customer discovers before you do.
Fix: join and filter — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) for an id outside the org so the endpoint-id space is not enumerable. Cross-cutting: this is the only new handler missing the scope; the other two new handlers already carry it, and no other unscoped query exists in the diff. Allow side that must still pass: the owning org's caller still receives that endpoint's deliveries in full — assert a non-empty list for the owner in the same test that asserts 404 for the stranger, or a fix that always 404s passes every deny fixture (RT10). Red-prove each clause separately, by execution: (i) two orgs, org A requests org B's `endpoint_id` → 404, reds if the join is removed; (ii) org A requests its own `endpoint_id` → 200 with the expected rows, reds if the filter over-narrows (e.g. joining on the wrong column); (iii) org A requests an `endpoint_id` that exists in no org → 404, distinguishing "absent" from "forbidden" identically. Fail loudly: an `endpoint_id` that fails to resolve to an endpoint row denies; it must not fall through to an unfiltered query. Preserve: the `limit` and the `created_at DESC` ordering behaviour for the legitimate caller. Boundary/tie: an endpoint whose org was deleted resolves to no row and therefore denies, rather than becoming ownerless and readable by everyone.

### Critical: the migration's status CHECK constraint does not admit the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py:deliver` writing `"failed_permanent"` and `app/webhooks/models.py:STATUSES`
What is wrong: three of the four vocabularies agree on `failed_permanent` (the model's `STATUSES` tuple, `_finish`'s call site, the retry exhaustion branch) and the fourth — the constraint that actually enforces it — says `failed` (R40: producer shape versus strict consumer; R3: the status vocabulary was propagated to three of four sites).
What breaks in production: the moment any delivery exhausts `MAX_ATTEMPTS`, `_finish` raises `IntegrityError`, its transaction rolls back, the row keeps whatever status it had — `in_flight` — and is never reclaimed by `_claim_batch` (which selects only `pending`), so every permanently-failing endpoint silently accumulates undead rows and the operator sees no `failed` records at all.
Fix: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `models.STATUSES` — currently defined and never referenced — the single source by rendering the constraint from it in a test: `assert set(STATUSES) == statuses_in_migration_file()`. Allow side that must still pass: inserting each of the four legal statuses succeeds — assert all four, or a constraint tightened to a single value passes the "illegal value rejected" test. Red-prove each clause separately, by execution: (i) insert `status='failed_permanent'` against the migrated schema → succeeds after the fix, reds before it; (ii) insert `status='nonsense'` → `IntegrityError`, reds if the constraint is dropped rather than corrected; (iii) add a fifth member to `STATUSES` without touching the SQL → the drift test reds. Fail loudly: the drift test must fail when the migration file cannot be parsed or the CHECK clause is not found, rather than comparing against an empty set and passing. Preserve: the constraint itself — do not resolve the mismatch by deleting the CHECK, which is what makes the vocabulary enforceable at all. Boundary/tie: `delivered` and `failed_permanent` are both terminal; a row already in one must not be transitioned to the other, which the constraint does not express and `_finish` must guard.

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint fail the whole enqueue
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness is on `event_id` alone, but `enqueue_for_event` deliberately creates one delivery row per matching endpoint for the same event, so any org with two subscribed endpoints violates the index.
What breaks in production: `session.add_all(rows)` fails on flush with a unique violation, the exception is caught and merely logged by `dispatcher.dispatch`'s `except Exception`, and the org receives ZERO webhooks for that event — not one, not a partial fan-out — while the event itself is durably recorded, so the loss is silent and unrecoverable; the failure appears exactly when a customer adds their second endpoint (R40).
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is also the key that makes the documented "deduplicate on `event_id`" contract meaningful per receiver. Allow side that must still pass: two endpoints in one org both receive a row for one event — assert `len(rows) == 2`, or an index that rejects everything satisfies the duplicate test. Red-prove each clause separately, by execution: (i) enqueue one event against two active endpoints → two rows, reds against the current index; (ii) enqueue the same `(endpoint_id, event_id)` twice → unique violation, reds if the index is dropped instead of re-keyed; (iii) enqueue two different events to one endpoint → two rows. Fail loudly: `enqueue_for_event` must not swallow the violation — see the dispatcher finding below; a fan-out that inserted fewer rows than it had matching endpoints has to raise. Preserve: idempotency of re-enqueue for the same event and endpoint, which is what the original index was reaching for. Boundary/tie: a manual re-delivery of an already-delivered event needs its own row and therefore its own key — if that is a requirement, the unique key must become `(endpoint_id, event_id, attempt_group)`; name the decision rather than leaving the retry route to collide later.

### Critical: outbound URL validation permits plaintext and internal targets, and the client follows redirects
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py:run_worker`, `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `startswith("http")` admits `http://` (plaintext) and any scheme merely prefixed `http` such as `http+unix://`, `parsed.netloc` is checked for presence but never for reachability class, so `http://127.0.0.1:6379/`, `http://169.254.169.254/latest/meta-data/`, and `http://10.0.0.5/admin` are all accepted — and even a validated public HTTPS host can 302 the delivery to those targets because `follow_redirects=True` (RS3 escalated: the unvalidated value reaches an HTTP client as its target; R49: `docs/webhooks.md` asserts "Only `https://` URLs are accepted", which is false).
What breaks in production: a customer turns your worker into an SSRF proxy against your own VPC and cloud metadata service, with the response body captured into `response_body` and the `log.warning` line, and signed payloads carrying billing data are additionally sent in cleartext to any `http://` endpoint they register.
Fix: validate with an explicit allow rule, not a prefix test — `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)` — then resolve the hostname and reject when any resolved address is loopback, link-local, private, reserved, or multicast (`ipaddress.ip_address(a).is_global` is False); set `follow_redirects=False` on the client and treat a 3xx as a permanent failure; and re-check the resolved address at connection time via a pinned-IP transport or an egress proxy, because a DNS answer that passed at registration can point elsewhere at delivery (the check-to-use interval is attacker-schedulable). Allow side that must still pass: `https://hooks.example.com/acme` resolving to a public address is accepted at registration and delivered to — assert it, or a validator that rejects everything passes every SSRF fixture (RT10). Red-prove each clause separately, by execution: (i) `http://hooks.example.com/x` → 422, reds if the scheme check reverts to `startswith`; (ii) `https://localhost/x` and `https://169.254.169.254/x` → 422, reds if the address-class check is removed; (iii) an endpoint returning 302 to `http://169.254.169.254/` → delivery marked failed and no second request issued, reds if `follow_redirects` returns to True. Fail loudly: a hostname that fails to resolve, or resolves to a mix of global and non-global addresses, is REJECTED with a named reason — "could not classify" must not be spelled like "global". Preserve: customers can still register any genuinely public HTTPS endpoint, including non-standard ports and IPv6 literals; do not fix by hardcoding an allowlist of hostnames. Boundary/tie: an address that is global at registration and private at delivery is decided at DELIVERY time (fail closed), and a hostname resolving to both an allowed and a disallowed address is disallowed.

### Critical: `time.sleep()` inside an `async def` blocks the whole event loop through the retry backoff
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` wide by `run_worker`, and it performs a synchronous sleep of 2, 4, 8 then 16 seconds inside the loop, which halts the event loop rather than yielding.
What breaks in production: one unreachable endpoint stalls the entire worker process for ~30 seconds per delivery and, because the sleeps are synchronous, the 100 gathered coroutines serialize into as much as ~50 minutes of frozen loop — during which the Redis lock's 60-second TTL expires, a second worker claims the same rows, and nothing else on that loop (including the API, if co-hosted) responds.
Fix: do not retry in-process at all — replace the `while True` loop with a single attempt that, on failure below `MAX_ATTEMPTS`, persists `attempts = attempt`, `status = "pending"`, `next_attempt_at = _now() + backoff_for(attempt)` and returns, letting `_claim_batch` pick the row up when it is due. This removes the sleep entirely and simultaneously fixes the crash-loses-retries and lock-expiry problems; if an in-process sleep is kept for any path, it must be `await asyncio.sleep(delay)`. `enqueue_for_event` and the three route handlers are `async def` performing synchronous `session_scope()` ORM work and block the loop the same way — run them through `asyncio.to_thread`/a threadpool executor or an async session (the pre-existing `list_api_keys` in the same file has the same defect and is in scope). Allow side that must still pass: a delivery that succeeds on its first attempt is still marked `delivered` in one pass with no rescheduling — assert `attempts == 1` and no second HTTP request. Red-prove each clause separately, by execution: (i) an endpoint returning 500 once → the row is left `pending` with `next_attempt_at` advanced by exactly `backoff_for(1)`, reds if the reschedule is dropped; (ii) the same row on its 5th attempt → `failed_permanent`, reds if the terminal branch is removed; (iii) a test asserting the worker loop's wall-clock time for a batch of 10 failing deliveries stays under a bound (e.g. 2s) — reds against any synchronous sleep, and terminates rather than hanging because the bound is enforced by `pytest.mark.timeout`. Fail loudly: a delivery whose reschedule write fails must leave the row in a state `_claim_batch` will retry, not in `in_flight`. Preserve: the total attempt budget of 5 and the 2/4/8/16 spacing the docs advertise — the fix moves where the wait happens, it does not shorten it. Boundary/tie: at exactly `attempt == MAX_ATTEMPTS` the delivery is terminal and NOT rescheduled (`>=`, as written), and two rows whose `next_attempt_at` are equal are both eligible in the same batch.

### Critical: `_acquire_lock` is not a lock — get-then-set is not atomic, and release is unconditional
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: the `get`/`set` pair has a window in which two workers both observe an empty key and both proceed; the `set` and `expire` are separate commands so a crash between them leaves the key with no TTL; and the release deletes the key by name without proving ownership, so a worker whose lock already expired deletes the lock a different worker now holds.
What breaks in production: two or more workers claim overlapping batches and the same customer receives duplicate deliveries at scale, while the no-TTL variant is a permanent wedge — a single crash between `set` and `expire` stops all webhook delivery forever with no automatic reset path and no alert (R38: a persisted fail-closed state with no reset path; the mutual-exclusion primitive is a security-relevant control over an at-least-once side effect).
Fix: acquire with a single atomic command carrying a fencing token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a Lua compare-and-delete (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`) so a worker can only delete its own lock; renew the TTL while the batch runs, or make the TTL exceed the maximum batch duration. Allow side that must still pass: a single worker acquires, runs, releases, and the NEXT poll acquires again — assert two consecutive successful acquisitions, or a lock that never grants passes every mutual-exclusion test. Red-prove each clause separately, by execution: (i) two coroutines calling `_acquire_lock` concurrently against a real (or fakeredis) server → exactly one True, and the assertion must be on the count, not on "at least one False" (RT4: a race test that cannot observe the interleaving is vacuous — drive it with a barrier, not a sleep); (ii) kill the holder without releasing → a second worker acquires after the TTL and not before, reds if `ex=` is dropped; (iii) worker A's TTL expires, worker B acquires, worker A runs its release → B still holds the lock, reds against the unconditional `delete`. Fail loudly: a Redis error during acquisition must return False (do not run) and log a named "lock backend unavailable" refusal, so "could not check" is not spelled like "lock is free". Preserve: the worker must still make progress on the normal path — a fix that always returns False satisfies every mutual-exclusion assertion and delivers nothing, which is why clause (i)'s allow side is mandatory. Boundary/tie: when both workers issue `SET NX` in the same millisecond exactly one wins, and the loser sleeps `poll_interval` rather than spinning.

### Critical: ORM instances are used after the session that loaded them has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` returning `rows` from inside `with session_scope()`, and `deliver()` loading `endpoint` inside a scope then reading it in `send_once`
What is wrong: both functions exit their `session_scope()` context before their results are read — `deliver` reads `delivery.attempts`, `delivery.id` and `delivery.payload`, and `send_once` reads `endpoint.signing_secret` and `endpoint.url`, all on detached instances whose attributes were expired by the commit that the scope performs (the same scope's commit is what `enqueue_for_event` and `_claim_batch`'s `row.status = "in_flight"` rely on to persist, so the scope demonstrably commits).
What breaks in production: every attribute access raises `DetachedInstanceError` and the worker delivers nothing at all — the failure is at the top of the batch loop, it escapes `asyncio.gather` (which has no `return_exceptions`), and the rows are already marked `in_flight`, so the first run of the worker permanently strands its first 100 deliveries.
Fix: stop returning ORM instances across scope boundaries. Have `_claim_batch` return plain dataclasses or tuples built inside the scope (`id, endpoint_id, attempts, payload`) joined to the endpoint's `url` and `signing_secret` in the same query, so `deliver`/`send_once` receive data, not mapped objects; change their type hints from `m.WebhookDelivery`/`m.WebhookEndpoint` accordingly. Allow side that must still pass: a claimed batch is still fully deliverable end to end — assert a delivery claimed by `_claim_batch` reaches `delivered` through the real `deliver` path, or a fix that returns empty batches passes every detachment test. Red-prove each clause separately, by execution: (i) a test that calls `_claim_batch()` and reads every field `deliver` touches, run against a real session — reds today, green after; (ii) a test that `deliver` marks a row `delivered` without ever opening a session for the endpoint mid-flight; (iii) revert one field to a lazy ORM attribute → (i) reds again. Fail loudly: if the join finds no endpoint for a claimed delivery (the endpoint was deleted), the delivery is finished as `failed_permanent` with a named reason, not skipped and left `in_flight`. Preserve: the batch claim's `in_flight` marking and its ordering must survive the refactor. Boundary/tie: a delivery whose endpoint was deactivated between enqueue and claim is decided at CLAIM time — state which side you take; as written the `active` filter exists only in `enqueue_for_event`, so a deactivated endpoint still receives everything already queued.

### Major: `in_flight` is a non-terminal state with no exit path
File: `app/webhooks/delivery.py` — `_claim_batch()` setting `row.status = "in_flight"`; `_claim_batch`'s filter `status == "pending"`
What is wrong: only `_finish` moves a row out of `in_flight`, and `_claim_batch` selects `pending` exclusively, so any interruption — process kill, the `DetachedInstanceError` above, the CHECK-constraint rollback above, a redeploy mid-batch — strands the row permanently (R38 mode 1: an async transition with no failure-exit and no bounded timeout).
