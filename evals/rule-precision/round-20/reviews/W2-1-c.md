### Critical: the signature covers neither the timestamp nor the bytes that are actually sent
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, against `app/webhooks/delivery.py:send_once` and `docs/webhooks.md` "Verifying the signature"
What is wrong: the doc tells every customer to HMAC `"{timestamp}.{raw_request_body}"`, but `sign()` HMACs only `json.dumps(payload, sort_keys=True)` — the timestamp is never fed to the MAC, and the signed byte string differs from the body `send_once` transmits, because `client.post(..., json=delivery.payload)` serializes in insertion order (and with its own separators) while `serialize()` re-orders keys.
What breaks in production: every customer who implements the documented verification rejects every webhook we send (total delivery-path failure, R40), and because the timestamp is outside the MAC an attacker who captures one request can rewrite `X-Acme-Timestamp` freely, so the five-minute replay window the doc sells as the anti-replay control enforces nothing.
Fix: make the signed bytes the transmitted bytes and cover the timestamp. In `signing.py` add `def canonical_body(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode()`, change `sign()` to `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` returning `(timestamp, body, "sha256=" + mac.hexdigest())`, and change `send_once` to `client.post(endpoint.url, content=body, headers=headers)` so httpx never re-serializes — the `Content-Type: application/json` header stays, since dropping it would break customers parsing on it (Remedy Floor 4: the fix must preserve JSON content negotiation and the existing header names, which are already published). Add a documented `TIMESTAMP_TOLERANCE_SECONDS = 300` and give `verify()` a `now` parameter; state the boundary explicitly: `abs(now - ts) == 300` is ACCEPTED, `301` is rejected, and two requests sharing the same timestamp second are both accepted (the timestamp is not a de-duplication key — `event_id` is). Allow side to pin (Remedy Floor 1): a test that captures the real `httpx` request via `MockTransport` and asserts `signing.verify(SECRET, captured_body_bytes, captured_ts, captured_sig)` is True must still pass. Red-prove each clause separately by execution (Remedy Floor 2): (i) revert `content=body` to `json=delivery.payload` with a two-key payload whose insertion order is not sorted — the verify assertion must red; (ii) drop the `f"{timestamp}."` prefix from the MAC input — a test that re-signs the same body under a different timestamp and asserts the signatures DIFFER must red; (iii) set tolerance to `inf` — the `now = ts + 301` rejection test must red. Fail loudly when the check cannot run (Remedy Floor 3): `verify()` must raise (never return `False` silently) when the timestamp header is absent or non-numeric, and `send_once` must raise rather than post when `canonical_body` fails to encode, so "could not verify" is never spelled the same as "signature mismatch".

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, which draws from the Mersenne Twister — a fully reconstructible generator, not a CSPRNG.
What breaks in production: an attacker who observes enough output from the same process (or who can register endpoints repeatedly to harvest secrets, which the create route returns in full) can recover the generator state and forge signatures for other organizations' endpoints, defeating the only authenticity control the webhook product has.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and import `secrets`, deleting the `random`/`string`/`_ALPHABET` imports so the weak path cannot be reused; rename `SECRET_BYTES` to mean what it now is (32 bytes of entropy) and keep `SECRET_PREFIX` unchanged, because the prefix is published in `docs/webhooks.md` and customers may key on it (Remedy Floor 4). Allow side (Remedy Floor 1): the existing `test_new_signing_secret_has_prefix_and_length` must still pass after its length assertion is updated to `len(SECRET_PREFIX) + len(secrets.token_urlsafe(SECRET_BYTES))`, and a freshly generated secret must still round-trip through `sign`/`verify`. Red-prove separately by execution (Remedy Floor 2): (i) monkeypatch `secrets.token_urlsafe` to return a constant and run a new `test_two_secrets_differ` over 100 generations — it must red; (ii) re-introduce `random.seed(0)` before generation in a test that asserts the module does not import `random` (`assert "random" not in sys.modules or not hasattr(signing, "random")`) — it must red. Fail loudly (Remedy Floor 3): do not wrap generation in a try/except that falls back to `random`; if the OS entropy source raises, the create route must return 503 rather than issue a weak secret. Boundary and tie (Remedy Floor 5): two endpoints must never receive equal secrets — add a uniqueness assertion over a batch, and note that the DB has no unique constraint on `signing_secret`, so a collision would be silent.

### Critical: `verify()` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify()`, line `return expected == signature`
What is wrong: the HMAC comparison is a short-circuiting string equality, not a constant-time comparison (RS1).
What breaks in production: an attacker with timing access to any caller of `verify()` recovers the expected digest byte by byte and forges a valid signature without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, guarding the input first — `if not isinstance(signature, str): raise TypeError(...)`, since `compare_digest` raises on non-ASCII `str` and an unvalidated header value can be either. Preserve the current True result for a genuinely matching signature (Remedy Floor 4); do not "fix" this by trimming or lowercasing the header, which would widen what is accepted. Allow side (Remedy Floor 1): `test_verify_accepts_signature_produced_by_sign` must still pass unchanged. Red-prove separately by execution (Remedy Floor 2): (i) revert to `==` and run a test asserting `signing.verify.__code__.co_names` contains `compare_digest` — it must red; (ii) delete the `isinstance` guard and pass `signature=None` — the test asserting a `TypeError` (not a `False`) must red. Fail loudly (Remedy Floor 3): a malformed signature (missing `sha256=` prefix, wrong hex length) must raise a named `InvalidSignatureFormat`, distinct from the `False` that means "computed and did not match" — today both spell "not verified". Boundary and tie (Remedy Floor 5): a signature of exactly the expected length that differs in the last byte must return False, and `compare_digest` on unequal-length inputs must be reached, not short-circuited by a length pre-check.

### Critical: `list_deliveries` has no organization filter — cross-tenant read
File: `app/api/routes/settings.py` — `list_deliveries()`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: `endpoint_id` comes straight from the URL and is never checked against `user.org_id`, so any authenticated user enumerates any other organization's deliveries; `docs/webhooks.md` states the endpoint "returns the most recent attempts for an endpoint belonging to your organization", a claim the implementation does not make true (R49 clause 2).
What breaks in production: a single incrementing loop over `endpoint_id` exposes every tenant's event types, event ids, delivery statuses and response codes — a tenancy breach that is invisible in the logs because each request is a well-formed authenticated call.
Fix: join to the endpoint and scope by org — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join is empty so the route does not confirm the existence of another org's id. Cross-cutting evidence (codebase awareness): the org-scoping idiom already exists three times in this same file — `get_profile` reads `user.org_id`, `list_api_keys` filters `ApiKey.org_id == user.org_id`, and `list_webhook_endpoints` filters `WebhookEndpoint.org_id == user.org_id`; `list_deliveries` is the sole route in the diff that omits it, so this is R3 incomplete pattern propagation on a security control, not a novel design question. Allow side (Remedy Floor 1): a test where the endpoint DOES belong to the caller's org must still return 200 with the full ordered delivery list — a fix that 404s everything satisfies the deny test alone. Red-prove separately by execution (Remedy Floor 2): (i) drop the `org_id` predicate and run the cross-org test — the 404 assertion must red; (ii) drop the `endpoint_id` predicate and run the same-org two-endpoint test — the assertion that only endpoint A's rows come back must red. Per RT8, the cross-org test must assert the response BODY is empty/absent, not merely the status code. Fail loudly (Remedy Floor 3): when `user.org_id` is `None` the route must deny, not fall through to an unfiltered query. Boundary and tie (Remedy Floor 5): an endpoint that was transferred between orgs is adjudicated by its CURRENT `org_id`, and two deliveries sharing `created_at` (see the ordering finding below) must not silently drop one.

### Critical: the signing secret is returned by the list endpoint
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, key `"signing_secret"`, consumed by `app/api/routes/settings.py:list_webhook_endpoints`

Fail loudly (Remedy Floor 3): make the redaction structural rather than a per-route reminder — asserting in a test that `set(WebhookEndpoint.to_dict(...).keys())` equals an explicit allowlist means a future column added to the model fails the test rather than leaking silently. Boundary and tie (Remedy Floor 5): because the secret becomes unreadable, a rotation route is now required for the case where a customer loses it — see the Minor below.

### Critical: URL validation accepts non-HTTPS and internal targets, and the client follows redirects — SSRF
File: `app/api/routes/settings.py` — `create_webhook_endpoint()`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the guard adjudicates the notation of the URL rather than consulting the resolver that gives it meaning (R47) — `startswith("http")` admits `http`, and any other scheme whose spelling begins with those four characters — while `docs/webhooks.md` states "Only `https://` URLs are accepted"; nothing restricts the host, and `follow_redirects=True` means even a legitimate public HTTPS endpoint can 302 the worker into the internal network.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or any public URL that redirects there) and the delivery worker fetches internal metadata, cluster services or Redis on the worker's behalf, with the response body persisted into `webhook_deliveries.response_body` and readable through the deliveries route.
Fix: replace the notation check with a resolution check. Validate with `pydantic.AnyHttpUrl` and require `parsed.scheme == "https"` exactly (an equality, not a prefix); then resolve the hostname with `socket.getaddrinfo` and reject when ANY returned address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`, rejecting also when the host is a bare IP literal in those ranges. Set `follow_redirects=False` on the delivery client and treat a 3xx as a permanent failure with a named reason, because a redirect target is not the URL the customer authorised. Because DNS can change between registration and delivery (R51's interval), re-run the same address check at delivery time via a custom `httpx` transport that inspects the connected peer address, so the decision binds to the socket, not to the name. Preserve the ability to register ordinary public HTTPS endpoints (Remedy Floor 4). Allow side (Remedy Floor 1): registering `https://hooks.example.com/acme` must still return 201, and delivery to it must still succeed. Red-prove separately by execution (Remedy Floor 2): (i) restore `startswith("http")` and run the `http://hooks.example.com` rejection test — it must red; (ii) remove the private-range check and run the `https://127.0.0.1/x` and `https://169.254.169.254/x` rejection tests — they must red; (iii) restore `follow_redirects=True` and run a MockTransport test where the endpoint 302s to a loopback URL, asserting no request reaches the second host — it must red. Fail loudly (Remedy Floor 3): when `getaddrinfo` raises or returns no addresses, the route must return 422 with "endpoint host could not be resolved" — an unresolvable host must not be admitted on the grounds that no private address was seen. Boundary and tie (Remedy Floor 5): a hostname resolving to both a public and a private address is REJECTED (any-private, not all-private), and IPv6-mapped IPv4 (`::ffff:127.0.0.1`) must be normalised before the range test.

### Critical: `time.sleep()` inside an async coroutine blocks the whole worker event loop
File: `app/webhooks/delivery.py` — `deliver()`, `time.sleep(delay)`
What is wrong: `deliver` is `async def` but sleeps synchronously, so the retry backoff blocks the event loop rather than yielding it.
What breaks in production: `run_worker` gathers up to `BATCH_SIZE = 100` deliveries concurrently, so one failing endpoint freezes all 99 others plus the lock-renewal and poll loop for up to 2+4+8+16 = 30 seconds per delivery — the batch serialises, the 60-second Redis lock expires mid-flight, and a second worker starts re-sending the same deliveries.
Fix: `await asyncio.sleep(delay)`. `asyncio` is already imported at the top of this file, so the async primitive is available and no new dependency is needed (codebase awareness). Preserve the backoff itself (Remedy Floor 4) — shortening or deleting the delay is not the fix. Allow side (Remedy Floor 1): a test asserting a successful first attempt performs NO sleep at all must still pass. Red-prove separately by execution (Remedy Floor 2): (i) revert to `time.sleep` and run a test that gathers two `deliver()` calls against a MockTransport where the first fails once and the second succeeds immediately, asserting the second completes before the first's backoff elapses (patch `asyncio.sleep` to record calls and `time.sleep` to raise) — it must red; (ii) delete the `MAX_ATTEMPTS` break and run `test_stops_after_max_attempts` with a bounded fake clock — it must red, and it must terminate rather than hang. Fail loudly (Remedy Floor 3): if `backoff_for` ever returns a negative or non-finite delay, raise rather than sleeping zero. Boundary and tie (Remedy Floor 5): `attempt == MAX_ATTEMPTS` is the LAST attempt made (no sleep follows it); `attempt == MAX_ATTEMPTS - 1` still sleeps.

### Critical: ORM instances are used after their session closes — every delivery raises
File: `app/webhooks/delivery.py` — `_claim_batch()` `return rows`, and `deliver()` `with session_scope() as session: endpoint = session.get(...)` followed by use outside the block
What is wrong: both functions return/retain SQLAlchemy instances past the end of their `session_scope()` context, and every subsequent attribute read (`delivery.payload`, `delivery.id`, `delivery.attempts`, `endpoint.url`, `endpoint.signing_secret`) is on a detached, commit-expired object (R9's shape: work outliving the transaction that produced it).
What breaks in production: `DetachedInstanceError` on the first attribute access in `send_once`, so no webhook is ever delivered; the rows are already flipped to `in_flight` by `_claim_batch`, so they are also unrecoverable — see the `in_flight` finding below.
Fix: stop passing ORM identities across the boundary. Have `_claim_batch` return plain values — `[DeliveryTask(id=r.id, endpoint_id=r.endpoint_id, attempts=r.attempts, payload=r.payload, url=ep.url, signing_secret=ep.signing_secret) for ...]` built inside the session with the endpoint joined in one query — and change `deliver`/`send_once` to take that frozen dataclass, removing the second `session_scope` in `deliver` entirely. Preserve `_finish`'s write-back through a fresh session (Remedy Floor 4): the fix must not turn the status write into an in-memory no-op. Allow side (Remedy Floor 1): a test that claims a real persisted `WebhookDelivery` and delivers it against `MockTransport` must reach a `delivered` row in the DB — this is the case the current tests never exercise, because they substitute `FakeEndpoint`/`FakeDelivery` for the real models (RT5). Red-prove separately by execution (Remedy Floor 2): (i) revert `_claim_batch` to returning ORM rows and run the integration test — it must red with `DetachedInstanceError`, named in the failure output; (ii) drop the endpoint join and pass a `DeliveryTask` with `signing_secret=None` — the signing assertion must red. Fail loudly (Remedy Floor 3): when the joined endpoint is missing (cascade-deleted between enqueue and claim), `_claim_batch` must mark the row `failed_permanent` with a named reason rather than skipping it silently, so "no endpoint" is not spelled the same as "nothing to send". Boundary and tie (Remedy Floor 5): a row claimed at exactly `next_attempt_at == now` is claimed (the filter is `<=`), and two rows sharing `next_attempt_at` are ordered by `id` — today the `order_by(next_attempt_at)` alone has no total order (R57).

### Critical: the migration's CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, against `app/webhooks/models.py:STATUSES` and `app/webhooks/delivery.py:_finish(..., "failed_permanent", ...)`
What is wrong: the SQL allows `'failed'` while both the Python constant tuple and the only writer use `'failed_permanent'` — the same enum spelled two ways across the storage boundary (R40, R3).
What breaks in production: the first delivery that exhausts `MAX_ATTEMPTS` raises a Postgres check-constraint violation inside `_finish`, so the exception escapes `deliver` into `asyncio.gather`, kills `run_worker` (no exception handling around the loop), and leaves the row stuck at `in_flight` forever.
Fix: change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make the Python side stop hardcoding the strings — `_claim_batch`, `_finish` and the model default must all read from `models.STATUSES` (or a `StatusEnum`), which already exists in `models.py` and is currently referenced nowhere (codebase awareness: the shared constant is present and unused, so this is R2/R1 duplication rather than a missing helper). Preserve the constraint itself (Remedy Floor 4) — widening it to `TEXT NOT NULL` with no CHECK would hide the next divergence. Allow side (Remedy Floor 1): inserting each of the four legal statuses must still succeed. Red-prove separately by execution (Remedy Floor 2): (i) revert the SQL to `'failed'` and run a migration-applied integration test that exhausts attempts — it must red with the constraint name in the failure output; (ii) add a fifth status to `STATUSES` without touching the SQL and run a test that asserts the Python tuple equals the constraint's value set parsed from `information_schema` — it must red. Fail loudly (Remedy Floor 3): that parity test must ERROR (not skip) when the migration has not been applied, so "no database" is not reported as "statuses agree". Boundary and tie (Remedy Floor 5): `attempts == MAX_ATTEMPTS` is the transition into `failed_permanent`; `MAX_ATTEMPTS - 1` schedules another attempt.

### Critical: `UNIQUE (event_id)` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);` against `app/webhooks/delivery.py:enqueue_for_event`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, but the index permits exactly one delivery row per event across the whole table.
What breaks in production: the moment an org has two active endpoints (the fan-out the feature exists for), the `add_all` commit raises a unique violation, the dispatcher's blanket `except Exception` swallows it as a `log.warning`, and NO endpoint receives the event — a silent, total, per-event data loss with no retry and no alert; the same index also blocks two different orgs from receiving the same platform-level event.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — which additionally gives `enqueue_for_event` the idempotency the docs promise ("delivery is at-least-once, so deduplicate on `event_id`") when the dispatcher retries — and add `ON CONFLICT (endpoint_id, event_id) DO NOTHING` at the insert. Keep a uniqueness constraint (Remedy Floor 4): dropping the index entirely would remove the duplicate-suppression the retry path depends on. Allow side (Remedy Floor 1): enqueueing one event for an org with three matching endpoints must produce exactly three rows. Red-prove separately by execution (Remedy Floor 2): (i) revert the index to `(event_id)` and run the three-endpoint test — the row-count assertion must red; (ii) remove `ON CONFLICT DO NOTHING` and call `enqueue_for_event` twice with the same event — the "still three rows, no exception" assertion must red. Fail loudly (Remedy Floor 3): the dispatcher must not keep swallowing this — see the dispatcher finding. Boundary and tie (Remedy Floor 5): an endpoint deactivated between the two enqueues is excluded by the `active.is_(True)` filter on the second call, and the pre-existing row is left untouched rather than cancelled.

File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`; `app/webhooks/models.py` — `_now()`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP NOT NULL`

### Major: the Redis lock is not atomic, is deleted unconditionally, and expires before a batch can finish
File: `app/webhooks/delivery.py` — `_acquire_lock()`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act race with no `NX`, `set` and `expire` are two round-trips (a crash between them leaves a lock with no TTL), the `finally` deletes the key without proving ownership, and the 60-second TTL is shorter than a single delivery's worst case (5 attempts x 30s `REQUEST_TIMEOUT` plus 30s of backoff).
What breaks in production: two workers claim overlapping batches and customers receive duplicate webhooks — the exact failure the doc tells them to dedupe on `event_id`, which the current `UNIQUE (event_id)` index makes worse rather than better — and a crashed worker can wedge the lock permanently.
Fix: acquire with a single atomic `SET key <random-token> NX EX 120` and release with the standard compare-and-delete Lua script so only the owner deletes; renew the TTL from a background task while the batch runs, and raise `LOCK_TTL` above the worst-case batch duration derived from `MAX_ATTEMPTS`, `REQUEST_TIMEOUT` and `backoff_for` rather than a hand-picked 60. Preserve single-worker exclusion (Remedy Floor 4): removing the lock to "avoid the wedge" would guarantee duplicates. Allow side (Remedy Floor 1): a single worker running two consecutive iterations must acquire the lock both times — a release that never fires would satisfy the mutual-exclusion test alone. Red-prove separately by execution (Remedy Floor 2): (i) revert to `get`/`set` and run two concurrent `_acquire_lock()` calls against a fake Redis that interleaves — the "exactly one True" assertion must red; (ii) replace the compare-and-delete with an unconditional `delete` and run a test where worker A's TTL expires, B acquires, then A's `finally` runs — the assertion that B still holds the lock must red; (iii) set the TTL below the worst case in a test with a fake clock — the "no expiry during batch" assertion must red, bounded so it terminates. Fail loudly (Remedy Floor 3): when Redis is unreachable, `_acquire_lock` must raise and the worker must back off — returning `False` on error is fine, but returning `True` is not, and today an exception propagates out of the loop entirely. Boundary and tie (Remedy Floor 5): a batch finishing at exactly the TTL is treated as expired (renew before, not at, the boundary), and two workers presenting the same token must be impossible — use `secrets.token_hex`, not a counter.

### Major: `in_flight` has no exit path, and `next_attempt_at` is never rewritten
File: `app/webhooks/delivery.py` — `_claim_batch()` (`row.status = "in_flight"`), `deliver()` (in-process retry loop)
What is wrong: `_claim_batch` only ever selects `status == "pending"`, so a row flipped to `in_flight` by a worker that then crashes, is deployed over, or raises (which it will — see the detached-instance and CHECK-constraint findings) is never reclaimed, and `deliver` retries entirely in memory without ever writing `next_attempt_at` or `attempts` back between attempts (R38 non-terminal transient state).
What breaks in production: a rolling restart during a batch silently strands up to 100 paid-event webhooks in `in_flight` forever, with `attempts` still reading 0 and no alert, and the scheduling columns the schema and the deliveries API expose are decorative.
Fix: persist each attempt — on a retryable failure, `_finish`-style write `status="pending"`, `attempts=attempt`, `next_attempt_at=_now() + backoff_for(attempt)` and return, letting the next poll pick it up, instead of looping in memory. Add a reaper: `_claim_batch` also selects rows where `status == "in_flight" AND updated_at < now() - CLAIM_TIMEOUT`, and stamp `updated_at` when claiming. Preserve the retry ceiling (Remedy Floor 4): the reaper must respect `MAX_ATTEMPTS` rather than resurrecting rows forever. Allow side (Remedy Floor 1): a normal successful delivery must still reach `delivered` on the first pass with `attempts == 1` and must NOT be reclaimed by the reaper. Red-prove separately by execution (Remedy Floor 2): (i) remove the reaper predicate and run a test that flips a row to `in_flight` with a stale `updated_at` — the reclaim assertion must red; (ii) remove the `next_attempt_at` write-back and assert the persisted value advanced by `backoff_for(1)` — it must red; (iii) let the reaper ignore `MAX_ATTEMPTS` and assert an exhausted row is not reclaimed — it must red. Fail loudly (Remedy Floor 3): a row found `in_flight` past the timeout AND past `MAX_ATTEMPTS` must be written `failed_permanent` with a reason, not left in place. Boundary and tie (Remedy Floor 5): `updated_at == now - CLAIM_TIMEOUT` exactly is reclaimed, and two workers reaping the same stale row must be serialised by `SELECT ... FOR UPDATE SKIP LOCKED` — without it the reaper reintroduces the duplicate delivery the lock exists to prevent.

### Major: `run_worker` dies on the first exception, and `batch` can be referenced unbound
File: `app/webhooks/delivery.py` — `run_worker()`
What is wrong: `batch = await _claim_batch()` is inside `try`/`finally` with no `except`, so any DB error propagates out of the `while True` loop and terminates the worker; `asyncio.gather` without `return_exceptions=True` propagates the first `deliver` failure the same way; and `if not batch:` reads a name that is unbound whenever `_claim_batch` raised.
What breaks in production: a single transient database blip or one unhandled delivery exception stops webhook processing entirely, and because the process exits from inside a `while True` it looks like a clean shutdown to a supervisor that only restarts on non-zero exit.
Fix: wrap the loop body in `except Exception: log.exception(...)` followed by `await asyncio.sleep(poll_interval)` and `continue`; initialise `batch: list = []` before the `try`; pass `return_exceptions=True` to `gather` and log every returned exception against its delivery id. Preserve the crash-visibility (Remedy Floor 4): log at ERROR with the traceback and increment a failure counter — swallowing quietly would replace one silent stop with a silent spin. Allow side (Remedy Floor 1): a healthy iteration must still process its batch and must NOT sleep the poll interval when the batch was non-empty. Red-prove separately by execution (Remedy Floor 2): (i) make `_claim_batch` raise once and assert the worker completes a subsequent successful iteration (bounded by a stop event so the test terminates) — it must red without the `except`; (ii) make one of two deliveries raise and assert the other still reaches `delivered` — it must red without `return_exceptions=True`. Fail loudly (Remedy Floor 3): after N consecutive failed iterations the worker must exit non-zero so the supervisor restarts it — an infinite quiet retry loop is the same invisibility in a different shape. Boundary and tie (Remedy Floor 5): an empty batch sleeps, a batch of exactly 1 does not; two exceptions in one `gather` must both be logged, not just the first.

### Major: the dispatcher silently swallows every webhook enqueue failure
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: a blanket catch downgrades total enqueue failure to a WARNING with no retry, no dead-letter and no metric, and it fires after the event transaction has already committed so there is no rollback either.
What breaks in production: the unique-index defect above (and any DB hiccup) makes every webhook for an event vanish while `dispatch()` returns success to its caller — the customer never learns the `invoice.paid` webhook was lost, and the only trace is one warning line among the info-level dispatch logs.

Red-prove separately by execution (Remedy Floor 2): (i) make `enqueue_for_event` raise and assert an outbox row exists and the counter incremented — it must red without the outbox write; (ii) assert `dispatch()` still returns the event id in that same failure case — it must red if the fix converts the catch into a re-raise. Fail loudly (Remedy Floor 3): the ERROR path must name the event id and the exception class; "enqueue returned 0 endpoints" and "enqueue threw" must be distinguishable in the logs, since today both are quiet. Boundary and tie (Remedy Floor 5): an event type in `WEBHOOK_EVENT_TYPES` with zero matching endpoints is a normal zero-row outcome, not a failure — do not alert on it.

### Major: `docs/webhooks.md` describes retry behaviour the code does not implement
File: `docs/webhooks.md` — the "Retries" section, against `app/webhooks/delivery.py:backoff_for` and `deliver`
