### Critical: the HMAC is computed over a different byte string than the one sent on the wire
File: `app/webhooks/signing.py` — `sign` / `serialize`, consumed by `app/webhooks/delivery.py:send_once`
What is wrong: `sign` MACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys sorted) while `send_once` transmits `client.post(..., json=delivery.payload)`, whose body httpx serializes with `(",", ":")` separators and insertion order, so the signed bytes and the sent bytes differ for every payload with more than one key or any non-trivial value.
What breaks in production: every customer that follows `docs/webhooks.md` and HMACs the raw request body computes a different digest, so 100% of deliveries fail signature verification at the receiver while our side records them `delivered` — a silent total-path failure (R40).
Fix: make the transmitted bytes the signed bytes — have `send_once` build `body = serialize(delivery.payload).encode()` once, pass it as `client.post(endpoint.url, content=body, headers=headers)` with an explicit `Content-Type: application/json`, and change `sign` to take that exact `bytes` object rather than a `dict` so no second serialization can exist; `verify` takes `bytes` for the same reason. Preserve what makes the feature useful: the payload content and the `sha256=` header format are unchanged, and `serialize`'s `sort_keys=True` stays so receivers can canonicalise. Pin the allow side and the deny side in one round-trip test — feed the ACTUAL bytes captured by the `MockTransport` handler in `tests/webhooks/test_delivery.py::test_send_once_posts_the_signed_payload` into the production `signing.verify` with the production secret and assert it returns True (allow), and assert it returns False for the same bytes with one byte flipped (deny). Red-prove each clause separately by execution, one mutation per clause: (a) revert `send_once` to `json=` and observe the allow assertion go red, (b) change `serialize` to `sort_keys=False` and observe the allow assertion go red, (c) remove the byte flip and observe the deny assertion go red. Fail loudly when the check cannot run: if the handler captured no body (`captured.get("body") is None`) the test must fail with "no request body captured", never pass by verifying an empty string. Boundary and tie: an empty-dict payload serializes to `b"{}"` and must still produce and verify a signature rather than being treated as "nothing to sign".

### Critical: the timestamp is not covered by the MAC, so the documented replay window enforces nothing
File: `app/webhooks/signing.py` — `sign`, lines computing `mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign` MACs the body alone and returns the timestamp as an unauthenticated side value, so `X-Acme-Timestamp` can be rewritten by anyone holding a captured request without invalidating `X-Acme-Signature`.
What breaks in production: an attacker who captures one delivery can replay it forever by setting the timestamp header to "now", defeating the five-minute freshness check the docs tell every customer to rely on as their replay defence (R49: the claim is stronger than the implementation, and the doc is what customers build their verifier against).
Fix: change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` and `verify` to accept the timestamp as an explicit argument and recompute over the same concatenation, so the header is bound to the digest; do not fix this by deleting the freshness sentence from the docs — the replay window is the feature being preserved. Add a maximum-age check to `verify` (default 300s) that rejects a timestamp older than the window, and keep the class of the control declared in the docstring: this is a fail-closed verification gate, not a boundary. Pin the allow side and the deny side: a signature produced now verifies (allow); the same `(timestamp, body, signature)` triple with only the timestamp string changed to `timestamp+1` fails (deny); a well-formed signature whose timestamp is `now-3600` fails (deny). Red-prove each separately by execution: (a) drop the `f"{timestamp}."` prefix and the tampered-timestamp deny assertion reds, (b) remove the age check and the stale-timestamp deny assertion reds, (c) shift the fixture timestamp forward and the allow assertion reds. Fail loudly when the check cannot run: a non-numeric or absent timestamp must raise/return False with a named reason, not be coerced to 0 — "could not parse" must not be spelled the same as "old". Boundary and tie: a timestamp exactly `now - 300` is accepted (`age <= MAX_AGE`), `now - 301` is rejected, and a future timestamp beyond a small clock-skew allowance (60s) is rejected; state both in the docs.

### Critical: signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the shipped reference verifier compares the recomputed digest to the caller-supplied signature with Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: this function is the implementation every internal consumer and every copy-pasting customer will use, so an attacker with repeated verification attempts can recover a valid signature byte by byte from the timing profile and forge deliveries.
Fix: replace with `hmac.compare_digest(expected, signature)`, keeping both operands as `str` of identical alphabet (or encode both to `bytes`) so `compare_digest` does not raise on mixed types. Preserve the behaviour that makes this useful: a signature produced by `sign` for the same secret and body must still return True. Pin allow and deny: `verify` returns True for a signature from `sign` (allow — this is `test_verify_accepts_signature_produced_by_sign`, keep it), and False for a signature from a different secret (deny — keep `test_verify_rejects_a_signature_made_with_another_secret`). Red-prove separately by execution: (a) mutate `compare_digest` to always return True and the deny test reds, (b) mutate it to always return False and the allow test reds. Fail loudly when the check cannot run: a signature that is not `sha256=`-prefixed or not 64 hex chars must return False by an explicit branch that logs the malformed shape, never raise a `ValueError` that a caller's `except Exception: pass` converts into an accept. Boundary and tie: a signature string of the correct length but differing only in its last character must be rejected, and the `sha256=` prefix is compared before the digest so a prefix mismatch does not leak digest-length information.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is the Mersenne Twister, seeded predictably and fully recoverable from 624 observed outputs, so the per-endpoint HMAC key is not unpredictable.
What breaks in production: an attacker who registers a handful of endpoints of their own recovers the generator state and derives other tenants' signing secrets, letting them forge signed webhooks that any customer verifier accepts as ours.
Fix: use `secrets.token_hex(SECRET_BYTES)` (or `secrets.choice` over the alphabet if the alphanumeric shape must be kept) and rename `SECRET_BYTES` to reflect what it counts — today it is a character count, not a byte count, and the test asserts `len(secret) == len(prefix) + SECRET_BYTES` against that misreading. Preserve what made the feature usable: the `whsec_` prefix and a length that the existing prefix/length test still checks. Pin allow and deny: a generated secret still starts with `SECRET_PREFIX` and has the documented length (allow); two consecutive calls are unequal and 1000 calls yield 1000 distinct values (deny — a stuck generator). Red-prove each separately by execution: (a) hardcode the return to a constant and the distinctness assertion reds, (b) drop the prefix and the prefix assertion reds, (c) halve the length and the length assertion reds. Fail loudly: if the entropy source raises, the endpoint-creation request must 500 rather than fall back to any default or shorter secret — "no entropy" must not be spelled the same as "here is a secret". Boundary and tie: two endpoints created in the same request-second must receive different secrets, and the uniqueness assertion must be on the secret value, not on the row id.

### Critical: `GET /v1/settings/webhook-endpoints` returns every endpoint's signing secret
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`; call site `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: `to_dict` is the single serializer used by both the create response and the list response, so the secret that `docs/webhooks.md` promises "cannot be read back afterwards" is returned on every list call (R49 — the doc states a control the code does not implement).
What breaks in production: any actor with a read-scoped API key or a stolen session — a class explicitly weaker than "can create endpoints" — can read the HMAC keys for the whole organisation and forge webhook deliveries to that customer indefinitely.
Fix: remove `signing_secret` from `to_dict`, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` so the secret is emitted at exactly one call site; the doc sentence then becomes true rather than being edited away. Preserve the feature: the create response must still carry the secret, since it is the customer's only chance to capture it. Pin allow and deny with two API tests: the create response body contains `signing_secret` (allow), and the list response contains no `signing_secret` key for an org with an existing endpoint (deny). Red-prove separately by execution: (a) re-add the key to `to_dict` and the list deny test reds, (b) delete the explicit merge in the create handler and the create allow test reds. Fail loudly when the check cannot run: the list deny test must first assert the response array is non-empty, or an org with zero endpoints passes it vacuously — "examined nothing" must not be spelled "found nothing". Cross-cutting: `WebhookDelivery.to_dict` was checked and carries no secret, but it does expose `event_id` and `event_type` — see the authorization finding below.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: the handler filters only on the path-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike its two siblings in the same file which both scope on `user.org_id`.
What breaks in production: any authenticated user can enumerate integer endpoint ids and read other tenants' delivery history — event ids, event types, delivery status and timing — a cross-tenant data leak reachable with a `for` loop.
Fix: join and scope the query — `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) for an endpoint belonging to another org so existence is not disclosed. Preserve the feature: the owner's own deliveries must still be returned in the same shape and order. Pin allow and deny: org A's user listing org A's endpoint receives its rows (allow — the assertion must be on row ids present, not merely on status 200); org B's user requesting org A's endpoint id receives 404 AND an empty body (deny). Red-prove separately by execution: (a) drop the `org_id` filter and the deny test reds on the non-empty body, (b) drop the join and the deny test reds on the status. Fail loudly: an unknown `endpoint_id` returns 404, and the handler must not silently return `[]` for a scoping failure — an empty list is indistinguishable from "no deliveries yet" and would let this regression pass unnoticed. Boundary and tie: an endpoint that exists but is soft-deleted/`active=False` still belongs to its org and must return its history to that org only. Cross-cutting verification: `create_webhook_endpoint` and `list_webhook_endpoints` do scope on `user.org_id`; `delivery.py:deliver`'s `session.get(WebhookEndpoint, delivery.endpoint_id)` is an internal path with no external id and is unaffected.

### Critical: endpoint URL validation admits non-HTTPS and internal targets, and the client follows redirects
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `scheme.startswith("http")` accepts `http://` and any scheme merely prefixed with `http` while `docs/webhooks.md` states "Only `https://` URLs are accepted", and nothing rejects loopback, link-local (`169.254.169.254`), or RFC1918 hosts, while `follow_redirects=True` lets a compliant public host redirect the worker to those targets after validation passed.
What breaks in production: a customer registers an endpoint pointing at our own metadata service or an internal admin API and our worker issues authenticated-looking POSTs to it from inside the perimeter (SSRF), with the response body persisted into `response_body` and readable through the deliveries API.
Fix: validate at the schema boundary (RS3) — make `EndpointIn.url` an `HttpUrl`-typed field with a validator that requires `parsed.scheme == "https"` (exact equality, not `startswith`) and rejects a host that resolves to a loopback, link-local, unique-local or private address, and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a failed attempt rather than chased. Preserve the feature: a normal public HTTPS endpoint must still be registrable and deliverable — that is the allow case to pin. Pin allow and deny: `https://hooks.example.com/acme` is accepted (allow) and a delivery to it succeeds with the redirect setting off; `http://hooks.example.com`, `httpx://evil`, `https://127.0.0.1/x`, and `https://169.254.169.254/latest/meta-data` are each rejected with 422 (deny). Red-prove each clause separately by execution: (a) restore `startswith` and the `httpx://` deny reds, (b) remove the scheme equality and the `http://` deny reds, (c) remove the address check and the link-local deny reds, (d) restore `follow_redirects=True` and a MockTransport test that returns a 302 to `http://127.0.0.1/` reds. Fail loudly when the check cannot run: DNS resolution failure during validation must reject with a named reason (422 "host could not be resolved"), never be caught and treated as "not private, therefore allowed" — that inversion is how the guard fails open. Boundary and tie: re-resolution between validation and delivery is a live DNS-rebinding window (R51-shaped); either pin the resolved address at delivery time or state explicitly in the docstring that this control is a best-effort tripwire (R49 class (c)) with rebinding as a listed known bypass, rather than letting readers default to "enforceable boundary".

### Critical: the migration's status CHECK constraint does not contain the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py:deliver` writing `"failed_permanent"`
What is wrong: the SQL enumerates `'failed'` while both `app/webhooks/models.py:STATUSES` and the only writer in `delivery.py` use `'failed_permanent'` — the same enum spelled two ways across the schema boundary (R3 propagation gap; the models copy is correct and the SQL is the drifted one).
What breaks in production: every delivery that exhausts its five attempts raises a CheckViolation inside `_finish`, so the row is never moved out of `in_flight`, the failure is never recorded, and the exception escapes `deliver` into `asyncio.gather` and takes the worker down with it.
Fix: change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the constraint from a single source — generate it from `models.STATUSES` in the migration, or add a test that asserts the constraint's enumerated set equals `set(STATUSES)` by reading `pg_constraint` on the migrated schema. Preserve the feature: the constraint must still reject a genuinely invalid status, so do not fix this by dropping the CHECK. Pin allow and deny against the real migrated database: inserting each of the four `STATUSES` values succeeds (allow), inserting `'bogus'` raises (deny). Red-prove separately by execution: (a) revert the constraint to `'failed'` and the allow insert of `failed_permanent` reds, (b) remove the CHECK entirely and the `'bogus'` deny reds. Fail loudly: if the test cannot reach a real Postgres it must error as "constraint not verified", not skip silently — a skipped schema test reads as a pass. Boundary and tie: adding a fifth status later must red this test rather than silently pass, which is what deriving the assertion from `STATUSES` buys.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` alone, but `delivery.py:enqueue_for_event` inserts one row per matching endpoint for a single event, so the second endpoint's row violates the index; the same file's docs say delivery is "at-least-once", which this index forbids.
What breaks in production: any organization with two subscribed endpoints gets an IntegrityError on flush, which `dispatcher.dispatch` swallows into a `log.warning`, so the entire event's webhooks — including the first endpoint's — are silently dropped for every paid invoice.
Fix: make the index `UNIQUE (endpoint_id, event_id)`, which is the constraint the code actually needs (one delivery per event per endpoint) and which also gives `enqueue_for_event` a real idempotency key for the retry-of-enqueue case. Preserve the feature: duplicate suppression per endpoint must still hold, so do not fix this by deleting the unique index. Pin allow and deny: enqueuing one event for an org with two active subscribed endpoints creates exactly two rows (allow — assert the count is 2, not merely that no exception was raised); enqueuing the same `(endpoint_id, event_id)` twice creates one row or raises a handled conflict (deny). Red-prove separately by execution: (a) revert to `UNIQUE (event_id)` and the two-endpoint allow test reds, (b) drop the unique index and the duplicate deny test reds. Fail loudly: the allow test must fail if the org has fewer than two endpoints in the fixture, otherwise it passes vacuously on a single-endpoint org. Boundary and tie: an endpoint with `event_types = []` and one with an explicit match both subscribe to the same event and must produce two distinct rows.

### Critical: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` returning `rows` from inside `with session_scope()`, and `deliver` reading `endpoint`/`delivery` attributes after the `with` block
What is wrong: `_claim_batch` returns `WebhookDelivery` objects after the scope commits and closes, and `deliver` fetches `endpoint` inside a scope then reads `endpoint.url`, `endpoint.signing_secret`, `delivery.payload`, `delivery.id` and `delivery.attempts` outside it, where the attributes are expired and the instances detached.
What breaks in production: the first batch the worker claims raises `DetachedInstanceError` on the first attribute access, the exception propagates through `asyncio.gather` and out of `run_worker`'s `while` loop, and the delivery pipeline dies with a hundred rows stranded in `in_flight`.
Fix: stop passing ORM objects across session boundaries — have `_claim_batch` return plain values (a list of small frozen dataclasses or dicts carrying `id`, `endpoint_id`, `attempts`, `payload`, plus the endpoint's `url` and `signing_secret` fetched by the same query via a join), and have `deliver` and `send_once` take those values. Preserve the feature: the claim must still mark rows `in_flight` in the same transaction that reads them. Pin allow and deny: a worker iteration over a seeded pending row reaches `send_once` and marks the row `delivered` (allow — assert the persisted status after the iteration, not just that no exception was raised); a row whose endpoint was deleted between claim and send is finished as `failed_permanent` with a named reason rather than raising (deny). Red-prove each separately by execution: (a) revert `_claim_batch` to returning ORM rows and the allow test reds with `DetachedInstanceError`, (b) remove the deleted-endpoint branch and the deny test reds. Fail loudly: a claimed row whose endpoint row is missing must be finished with an explicit `endpoint_missing` detail, never skipped — a skipped row silently stays `in_flight` forever. Boundary and tie: a row claimed at exactly the batch limit boundary (row 100 of 100) must be handled identically to row 1.

### Critical: `time.sleep` inside an async coroutine blocks the whole delivery event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)` at the end of the retry loop
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` times concurrently, but its backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, so one retrying delivery freezes the event loop for the full 2+4+8+16 = 30 seconds.
What breaks in production: a batch of 100 deliveries to a single down endpoint blocks the loop for roughly 3000 seconds while the 60-second Redis lock expires underneath the worker, letting a second worker claim and re-send the same rows — a stalled pipeline and duplicate customer deliveries at the same time.
Fix: use `await asyncio.sleep(delay)`, and separately bound total in-process retrying — a single delivery must not hold a worker slot for 30s; prefer rescheduling by writing `status='pending'` with `next_attempt_at = now + backoff_for(attempt)` and returning, which is what `next_attempt_at` exists for and what `_claim_batch` already selects on. Preserve the feature: the documented retry count and the growing delay between attempts must be unchanged. Pin allow and deny: a delivery that fails once then succeeds is finished `delivered` with `attempts == 2` (allow); with the reschedule form, a first failure leaves the row `pending` with `next_attempt_at` advanced by exactly `backoff_for(1)` (deny of the "give up immediately" direction). Red-prove separately by execution: (a) restore `time.sleep` in a test that runs two gathered deliveries and asserts wall-clock elapsed is below the sum of their sleeps — it reds, (b) remove the `next_attempt_at` advance and the scheduling assertion reds. Fail loudly: if `backoff_for` is handed an attempt beyond `MAX_ATTEMPTS` the code must raise rather than compute a 32-second-plus delay silently. Boundary and tie: at `attempt == MAX_ATTEMPTS` the row is finished, never rescheduled — `>=` is the correct operator and the row at exactly 5 attempts is terminal.

### Critical: no test verifies a signature against the bytes actually transmitted
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`
What is wrong: the only assertion on the signature header is `startswith("sha256=")`, and the verify test round-trips `sign` into `verify` with the same `dict`, so the production primitive under test — signature verification over the wire body — is never exercised against `captured["body"]` (RT5: the test's call path excludes the primitive; RT1: the pair is a self-consistency tautology that cannot disagree with itself).
What breaks in production: this is why the serialization divergence and the missing timestamp binding above are both green in CI — the suite would stay green through a total customer-facing signature failure, so a reviewer reads coverage that does not exist.
Fix: add a test that takes the exact `captured["body"]` bytes and `captured["headers"][SIGNATURE_HEADER]` / `[TIMESTAMP_HEADER]` from the `MockTransport` handler and passes them to production `signing.verify` with the production secret, asserting True. Preserve what makes the existing tests useful: keep the header-shape assertions, since they catch a different regression. Pin allow and deny in the same test: unmodified captured bytes verify (allow), and the same bytes with one byte of the body changed, and separately with the timestamp header incremented, do not verify (deny). Red-prove each separately by execution: (a) change `serialize` to `sort_keys=False` and the allow assertion reds, (b) make `verify` return True unconditionally and both deny assertions red, (c) remove the timestamp from the MAC and the timestamp-tamper deny reds. Fail loudly when the check cannot run: assert `captured` contains both `body` and `headers` before verifying, so a handler that never fired fails as "request not captured" rather than passing over an empty dict. Boundary and tie: a payload whose JSON encoding contains non-ASCII must be covered, since `ensure_ascii` differences are exactly the class of divergence this test exists to catch.

### Major: the Redis dispatch lock is neither atomically acquired nor safely expired
File: `app/webhooks/delivery.py` — `_acquire_lock`, `get` then `set` then `expire`; `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: the check-then-set across three round trips lets two workers both observe an empty key and both acquire, and a crash between `set` and `expire` leaves a key with no TTL that only the `finally` of the crashed process would have removed — a persisted state with no reset path (R38 mode 1).
What breaks in production: concurrent workers claim overlapping batches and customers receive duplicate deliveries; after a hard crash the untouched lock key wedges the entire delivery fleet permanently and silently.
Fix: acquire with a single atomic command carrying the TTL and a unique owner token — `SET key <token> NX EX 60` — and release only if the stored value still equals this worker's token (a Lua compare-and-delete), so a worker whose lock already expired cannot delete its successor's. Preserve the feature: exactly one worker still dispatches at a time. Pin allow and deny: a worker with a free key acquires and dispatches (allow — assert the batch was processed, not merely that acquire returned True); a second worker against a held key does not acquire and does not claim rows (deny — assert zero rows changed status, per RT8, not just that acquire returned False). Red-prove each separately by execution: (a) drop `NX` and the deny test reds, (b) drop `EX` and a test asserting `TTL(key) > 0` after acquire reds, (c) replace the compare-and-delete with a plain `DELETE` and a test where worker A's expired lock is held by B, and A's release leaves B's token intact, reds. Fail loudly: a Redis error during acquire must return False and log a named reason so the worker sleeps, never be swallowed into a truthy acquire — an unreachable Redis must not read as "lock is free". Boundary and tie: two workers issuing `SET NX` in the same millisecond — exactly one must win, and the loser must take the sleep path rather than proceeding.

### Major: the claim query reads and writes without row-level locking
File: `app/webhooks/delivery.py` — `_claim_batch`, `SELECT ... WHERE status='pending' AND next_attempt_at <= now` followed by `row.status = "in_flight"`
What is wrong: the read and the status write are in one transaction but with no `FOR UPDATE SKIP LOCKED`, so two concurrent claimers select the same rows and both mark them `in_flight` (R5 TOCTOU); the Redis lock above is the only thing preventing this, and it does not.
What breaks in production: the same invoice webhook is POSTed twice to a customer, and because `attempts` is written only at `_finish` the duplicate is invisible in the delivery history.
Fix: add `.with_for_update(skip_locked=True)` to the claim query so a concurrent claimer takes the next unlocked rows instead of the same ones, and keep the batch limit. Preserve the feature: a single claimer must still get a full `BATCH_SIZE` batch when that many rows are due. Pin allow and deny: one claimer against 100 due rows claims 100 (allow); two concurrent claimers against 100 due rows claim disjoint sets whose union is 100 and whose intersection is empty (deny of the double-claim). Red-prove each separately by execution: (a) remove `skip_locked` and the concurrency test reds or deadlocks within its timeout, (b) remove `with_for_update` entirely and the disjointness assertion reds. Fail loudly: the concurrency test must assert both claimers actually ran (both returned before the timeout) so a test where one silently errored cannot pass as "disjoint". Boundary and tie: a row whose `next_attempt_at` is exactly `now` is due (`<=` is correct), and two rows with identical `next_attempt_at` must both be claimable — the ORDER BY tie must not cause one to be skipped.

### Major: `run_worker` dies on the first exception and can raise `NameError` on its own control flow
File: `app/webhooks/delivery.py` — `run_worker`, `batch = await _claim_batch()` inside `try`, `if not batch` after `finally`, and `asyncio.gather(...)` without `return_exceptions`
What is wrong: `batch` is bound inside the `try` so any exception from `_claim_batch` leaves it unbound, the `finally` releases the lock and re-raises, the exception escapes `while True` and terminates the coroutine, and `gather` without `return_exceptions=True` propagates the first delivery failure while the remaining tasks are abandoned mid-flight.
What breaks in production: one transient database error permanently stops webhook delivery for the whole deployment with no restart path, and the rows it had claimed stay `in_flight` forever.
Fix: wrap the loop body in `try/except Exception` that logs with the event id and continues after a sleep, initialise `batch: list = []` before the `try`, and call `gather(..., return_exceptions=True)` then log each returned exception so one bad endpoint cannot cancel its ninety-nine neighbours. Preserve the feature: a genuine `asyncio.CancelledError` must still propagate so the worker can be shut down — catch `Exception`, not `BaseException`. Pin allow and deny: a batch where every delivery succeeds still finishes all rows `delivered` and the loop continues (allow); a batch where one delivery raises leaves the other rows `delivered` and the loop still running on the next iteration (deny of the fail-everything behaviour). Red-prove each separately by execution: (a) remove `return_exceptions=True` and the one-bad-delivery test reds, (b) remove the loop-body `except` and a test that makes `_claim_batch` raise once then succeed reds, (c) remove the `batch = []` initialisation and that same test reds with `NameError`. Fail loudly: the swallowed exceptions must be logged individually with the delivery id, so "one delivery failed" is never spelled the same as "batch empty". ### Major: `in_flight` is a non-terminal state with no reaper and no per-attempt persistence

### Major: the retry policy contradicts the published contract, and the test pins the wrong behaviour
File: `app/webhooks/delivery.py` — `deliver`'s retry branch and `backoff_for`; `docs/webhooks.md` "Retries" section; `tests/webhooks/test_delivery.py::test_backoff_grows_exponentially`

Fail loudly: a response with an unexpected status class (1xx, 3xx with redirects disabled) must be recorded as a named non-retryable outcome rather than falling through the `else` into a retry. Boundary and tie: 299 is success, 300 is not; 399 with `follow_redirects=False` is terminal; 429 is retryable despite being 4xx, and that exception is stated in the docs.
