### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `serialize`/`sign`
What is wrong: `sign()` computes the HMAC over `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`), while `send_once` hands the dict to httpx as `json=delivery.payload`, which re-serializes it with httpx's own encoder — different key order and different separators — so the digest in `X-Acme-Signature` is over a byte string the receiver never sees.
What breaks in production: every customer following `docs/webhooks.md` (HMAC over the raw request body) rejects 100% of our deliveries as forged, and because a 4xx is retried here (see below) each event burns all 5 attempts before landing in `failed_permanent`.
Fix: serialize exactly once and send that string. In `signing.py` add `def canonical_body(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`, have `sign()` take and MAC those same bytes, and change `send_once` to `body = signing.canonical_body(delivery.payload)` / `client.post(endpoint.url, content=body, headers=headers)` with `Content-Type: application/json` kept explicitly (httpx does not set it for `content=`). Preserve what the current code got right: the payload dict still reaches the wire as valid JSON with identical semantics, and `sort_keys=True` stays so the digest is stable across dict insertion order. Allow side to pin, not just the deny side: a test asserting `signing.verify_body(SECRET, captured["body"], captured["headers"][SIGNATURE_HEADER], captured["headers"][TIMESTAMP_HEADER]) is True` for a normally-signed request must stay green. Red-prove each clause separately by running it: (1) change `separators` in `canonical_body` only → the verify-true assertion reddens; (2) drop `sort_keys=True` and feed a payload whose keys are inserted in non-sorted order → reddens; (3) revert `content=body` to `json=...` → reddens. Failure to run must be loud: if `captured` is empty because the transport handler never fired, the test must fail with that message rather than skipping the assertions. Boundary and tie: an empty payload `{}` signs as `b"{}"` and must still verify; two payloads differing only in key insertion order must produce byte-identical bodies and identical signatures.

### Critical: the signature does not cover the timestamp, so the documented replay window is not enforceable
File: `app/webhooks/signing.py` — `sign`, `verify`
What is wrong: `docs/webhooks.md` tells customers the signature is `HMAC(secret, "{timestamp}.{raw_body}")` and that rejecting timestamps older than five minutes "stops a captured request from being replayed", but `sign()` MACs the body alone and returns the timestamp as an unauthenticated side value, so an attacker replaying a captured request can rewrite `X-Acme-Timestamp` to now and the signature still verifies (R49: the claim is stronger than the implementation; the receiver-side control customers were told to rely on is not bound to anything).
What breaks in production: a single captured delivery — of `invoice.paid`, say — can be replayed against the customer's endpoint indefinitely and forever passes their verification, so the anti-replay control the docs promise does not exist for any integrator.
Fix: bind the timestamp into the MAC: `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + canonical_body(payload), hashlib.sha256)`, and give `verify` the received timestamp as a parameter — `verify(secret, timestamp, body_bytes, signature, max_age=300)` — recomputing over the received values instead of minting a fresh `time.time()` (the current `verify` cannot detect a stale request at all, because it re-signs with the current second). Keep the documented wire format unchanged so `docs/webhooks.md` stays true rather than rewriting the doc down to the code. Pair deny with allow: a request signed 10 seconds ago must still verify true; one signed 301 seconds ago must verify false. Red-prove separately by execution: (1) mutate the MAC input back to body-only → the "tampered timestamp is rejected" test reddens; (2) remove the `max_age` check → the stale-timestamp test reddens; (3) flip one byte of the body → the tampered-body test reddens. Fail loudly: a non-numeric or absent `X-Acme-Timestamp` must return False with a named reason, never be coerced to 0 or skipped. Boundary and tie: `age == max_age` exactly is accepted (`age > max_age` rejects), and a timestamp in the future by more than the same tolerance is rejected — state both in the doc.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: any caller of `verify` — and this is the reference implementation we publish to customers in `docs/webhooks.md` — leaks digest-prefix information timing-wise, letting an attacker forge a signature byte by byte over enough requests.
Fix: `return hmac.compare_digest(expected, signature)`, with both sides coerced to `str`/`bytes` of the same type first. Do not fix by deleting `verify` because it has no production caller today — it is the primitive the delivery tests and the published customer recipe both stand on. Allow side: a correctly signed payload must still return True. Red-prove by execution: revert to `==` and confirm a test asserting `verify` is implemented via `hmac.compare_digest` (patching `hmac.compare_digest` with a spy and asserting it was called with both operands) goes red — a pure timing measurement is flaky and is not the oracle. Fail loudly: when `signature` is `None` or not a `str`, raise/return False with a named reason rather than letting `compare_digest` throw an opaque `TypeError`. Boundary and tie: an empty-string signature and a signature of the correct length but wrong content both return False through the same path.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built with `random.choice`, i.e. the Mersenne Twister, which is seeded from a small state and fully predictable once ~624 outputs are observed — and `SECRET_BYTES = 32` counts alphabet characters, not bytes, so the name overstates the entropy too.
What breaks in production: an attacker who observes or provokes enough secrets (creating endpoints is unauthenticated by rate limit — see below) can recover the generator state and forge signatures for every other tenant's webhooks, which is a full break of the only authenticity control in this feature.
Fix: `import secrets` and `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)`, renaming the constant to `SECRET_ENTROPY_BYTES = 32` so the unit is honest, and delete the now-unused `random`/`string`/`_ALPHABET` outright rather than leaving them as a fallback. Preserve what the current code made useful: the `whsec_` prefix and a stable, URL-safe, single-token shape, so existing docs and any stored secrets keep parsing. Allow side: `new_signing_secret()` must still start with `SECRET_PREFIX` and still be accepted by `sign`/`verify` end to end. Red-prove each clause by execution: (1) swap `secrets.token_urlsafe` back to `random.choice` → a test that seeds `random.seed(0)` twice and asserts two `new_signing_secret()` calls differ goes red; (2) drop the prefix → the prefix test reddens; (3) shrink `SECRET_ENTROPY_BYTES` to 4 → a minimum-length assertion reddens. Fail loudly: no `except` around the CSPRNG that falls back to `random`; if the OS entropy source is unavailable the request must 500, not issue a weak secret. Boundary and tie: fix the minimum accepted secret length at exactly `len(SECRET_PREFIX) + 43` (token_urlsafe(32)) and assert `>=`, so two secrets generated in the same second are still distinct by construction.

### Critical: the signing secret is returned on every read of an endpoint
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, used by `list_webhook_endpoints` in `app/api/routes/settings.py`
What is wrong: `to_dict()` includes `"signing_secret"`, and `GET /v1/settings/webhook-endpoints` returns it for every endpoint, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: the secret is handed out on every list call, so it lands in browser caches, proxy logs, support screenshots, and any read-only integration token's reach — a read-scoped credential becomes a signing-forgery credential, and the documented security posture customers built on is false.
Fix: remove `"signing_secret"` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the one creation site — the secret appears in exactly one code path, matching the doc. Add a rotation route (`POST /webhook-endpoints/{id}/rotate-secret`) so removing read-back does not strand customers who lost the secret; do not "fix" this by softening the doc instead. Allow side: the create response must still carry the secret, and the list response must still carry `id`/`url`/`event_types`/`active`. Red-prove each separately by execution: (1) re-add `signing_secret` to `to_dict()` → a test asserting `"signing_secret" not in list_response[0]` reddens; (2) delete the explicit merge in the create handler → the create-returns-secret test reddens. Fail loudly: assert on the exact key set of the list payload (`set(body[0]) == {...}`), so a future field added to `to_dict` fails the test rather than slipping through a subset check. Boundary and tie: an org with zero endpoints returns `[]` and must not error; two endpoints in the same org each get a distinct secret and neither is echoed by the list route.

### Critical: the deliveries route has no tenancy filter
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `endpoint_id` taken from the path and never joins back to `WebhookEndpoint.org_id == user.org_id`, while every sibling handler in this same file (`get_profile`, `list_api_keys`, `list_webhook_endpoints`) does scope by `user.org_id` — the cross-cutting check shows this is the one changed site that dropped the pattern (R3).
What breaks in production: any authenticated user can enumerate `endpoint_id` and read another organization's delivery history — event ids, event types, delivery status and the response codes their endpoint returned — a cross-tenant data leak reachable with a single incrementing integer.
Fix: join and scope in one query: `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookEndpoint.id == m.WebhookDelivery.endpoint_id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)`, and raise `HTTPException(404)` when no endpoint with that id exists in the caller's org, so a foreign id is indistinguishable from a missing one. Preserve the existing ordering and `limit` behaviour. Pair deny with allow: the owning org still receives its rows (assert the row ids, not just the 200), and a foreign org receives 404 — assert both, and per RT8 assert that the foreign request produced no rows in the response body, not merely a status. Red-prove each clause by execution: (1) remove the `org_id` predicate → the foreign-org test reddens; (2) change 404 to 403 → the "foreign id is indistinguishable from missing" test reddens; (3) remove the `endpoint_id` predicate → the owning-org test reddens because it sees another endpoint's rows. Fail loudly: if `user.org_id` is `None` the handler must 401/403 rather than fall through to an unfiltered query. Boundary and tie: an endpoint that exists in the caller's org but has zero deliveries returns `[]` with 200, not 404.

### Critical: no SSRF guard on the destination URL, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: validation is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plain `http://`, admits bogus schemes like `httpx://`, and admits any host — loopback, RFC1918, and `169.254.169.254` — while the delivery client follows redirects, so even an initially-public HTTPS host can bounce the request to an internal address; `docs/webhooks.md` meanwhile states "Only `https://` URLs are accepted" (R49: the doc describes a control the code does not implement).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/iam/...` (or a public host that 302s there), and our worker POSTs to it from inside the VPC and stores the response body in `webhook_deliveries.response_body`, which that tenant can then read back — cloud credential exfiltration through a customer-controlled URL.
Fix: validate at the schema level with a Pydantic `HttpUrl`-based field constrained to `https` plus an explicit host check, and enforce it again at send time (the check must live where the request is made, not only at the gateway): reject when `scheme != "https"`, when the hostname is missing, and when every resolved A/AAAA address is loopback, link-local, private, reserved, or multicast (`ipaddress.ip_address(...).is_global` is the allow predicate). Set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure with a named reason. Preserve the feature: ordinary public HTTPS endpoints still deliver, and the DNS check is done on the resolved addresses at send time so a rebinding answer cannot slip past a create-time-only check. Pair deny with allow: `https://hooks.example.com/acme` must still be accepted at create and still delivered; `http://…`, `https://127.0.0.1/…`, `https://10.0.0.5/…`, and a public host whose delivery-time redirect targets a private address must each be rejected. Red-prove each clause by execution: (1) relax `scheme != "https"` back to `startswith("http")` → the plain-http test reddens; (2) remove the private-address predicate → the 169.254 test reddens; (3) restore `follow_redirects=True` → the redirect-to-internal test reddens. Fail loudly: when DNS resolution fails or times out, deny the delivery and record `failed_permanent` with the resolution error — "could not check" must not be spelled the same as "checked and allowed". Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv6-mapped IPv4 (`::ffff:10.0.0.1`) fall on the deny side; a hostname resolving to both a global and a private address is denied.

### Critical: the status value the code writes violates the migration's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(..., "failed_permanent", ...)` and `app/webhooks/models.py` `STATUSES`
What is wrong: three sources of truth disagree — the migration allows `failed`, the model tuple and the delivery code use `failed_permanent` — and nothing reconciles them (R18/R3: the allowlist was not synchronized with the value the code emits).
What breaks in production: the first delivery that exhausts its retries raises a `CheckViolation`, the `_finish` transaction rolls back, and the row is left in `in_flight` forever — every permanently-failing delivery both errors the worker and leaks a row that no later batch will ever reclaim.
Fix: make the migration the single source: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and have `models.STATUSES` be the only place the strings are written, with `delivery.py` referencing `m.STATUSES` members rather than repeating literals (`_finish(delivery.id, m.STATUS_FAILED_PERMANENT, ...)`). Do not fix by dropping the CHECK constraint — it is what makes the mismatch visible. Allow side: a delivery that succeeds still writes `delivered` and a fresh row still writes `pending`, both accepted by the constraint. Red-prove each clause by execution against a real database, not a mock: (1) write `"failed"` from `_finish` → an integration test asserting a permanently-failed row reaches `failed_permanent` reddens; (2) revert the constraint list → the same test reddens with a `CheckViolation`; (3) add a `STATUSES` member without adding it to the migration → a test asserting the Python tuple equals the values parsed from the constraint reddens. Fail loudly: that parity test must fail if the migration file cannot be found or parsed, rather than passing on an empty match. Boundary and tie: state explicitly that `failed_permanent` is terminal — a row in it is never re-claimed — and that `in_flight` is not, so the reaper below owns it.

### Critical: the unique index on `event_id` allows only one delivery row per event globally
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so the second endpoint's row violates the unique index; `docs/webhooks.md` also tells customers "delivery is at-least-once, so deduplicate on `event_id`", which this index makes structurally impossible.
What breaks in production: any organization with two or more active endpoints gets an `IntegrityError` on the whole `add_all`, the dispatcher swallows it as a `log.warning`, and *none* of that org's endpoints — not even the first — ever receives the event.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which keeps the idempotency the index was reaching for (one row per endpoint per event) while permitting fan-out; keep the uniqueness rather than dropping the index, since it is what stops a retried `enqueue_for_event` from double-inserting. Allow side: an org with three active endpoints produces exactly three rows for one event; a re-run of `enqueue_for_event` for the same event produces zero additional rows (use `ON CONFLICT DO NOTHING` in the insert). Red-prove each clause by execution: (1) restore the single-column index → the three-endpoint fan-out test reddens; (2) drop the index entirely → the re-enqueue-is-idempotent test reddens; (3) remove `ON CONFLICT DO NOTHING` → the re-enqueue test reddens with an `IntegrityError`. Fail loudly: the fan-out test must assert the exact row count, so a partially-inserted batch fails rather than passing a "at least one row" check. Boundary and tie: two endpoints in *different* orgs subscribed to the same global `event_id` each get their own row — that is the case the old index broke, and the test must cover it.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather`, but the retry backoff uses the blocking `time.sleep`, which stops the entire loop — including the other 99 deliveries in the batch, the HTTP client's transport, and the lock refresh.
What breaks in production: one slow endpoint stalls the whole worker for up to 30 seconds per attempt chain (2+4+8+16), so a batch of 100 with a few failing endpoints serializes into tens of minutes, the 60-second Redis lock expires mid-batch, and a second worker starts re-sending the same deliveries.
Fix: `await asyncio.sleep(delay)`; `asyncio` is already imported. Better, stop sleeping in-process at all: on a retryable failure write `attempts` and `next_attempt_at = _now() + backoff_for(attempt)`, set `status = "pending"`, and return — letting `_claim_batch` pick the row up later, which is what the `next_attempt_at` column and the persisted `attempts` counter exist for and which survives a worker restart. Preserve the retry semantics the current loop provides: still at most `MAX_ATTEMPTS` total attempts with the same 2/4/8/16-second schedule. Allow side: a delivery that succeeds on the first attempt still returns `delivered` without any sleep. Red-prove each clause by execution: (1) restore `time.sleep` → a test asserting the loop stays responsive (a concurrent `asyncio.sleep(0)` task completes within the retry window) reddens; (2) remove the `next_attempt_at` write → a test asserting the row is re-claimable at the scheduled time reddens; (3) remove the `attempts` write → a test asserting the retry budget is not reset across worker restarts reddens. Fail loudly: if the reschedule write fails, mark the delivery `failed_permanent` with the write error rather than returning as if it were queued. Boundary and tie: a row whose `next_attempt_at` is *exactly* now is claimable (`<=`), and `attempt == MAX_ATTEMPTS` is terminal (`>=` in the current code is correct — keep it).

### Critical: ORM rows are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (fetches `endpoint` in one scope, uses it after), `run_worker`
What is wrong: `_claim_batch` returns `WebhookDelivery` instances after the `session_scope` context exits, and `deliver` likewise reads `endpoint.signing_secret` / `endpoint.url` after its own scope closed — SQLAlchemy expires instance attributes on commit, so the first attribute access outside the scope raises `DetachedInstanceError`.
What breaks in production: the worker crashes on its very first non-empty batch, before a single webhook is ever delivered, and because the tests only exercise `send_once` with hand-rolled fakes nothing in this diff would have caught it.
Fix: never let ORM entities cross a session boundary — have `_claim_batch` return plain data (`[DeliveryJob(id=..., endpoint_id=..., payload=..., attempts=...) for row in rows]`, a frozen dataclass), and have `deliver` read the endpoint's `url`/`signing_secret` into that same job inside the claiming query via a join, so `send_once` receives values rather than entities. Preserve the current call signature usefully: keep `send_once(client, endpoint_like, delivery_like)` taking anything with `.url`/`.signing_secret`/`.payload`, which is what makes the existing test doubles work. Allow side: a claimed batch must still deliver end to end against a real session — add an integration test that goes `enqueue_for_event` → `_claim_batch` → `deliver` → row is `delivered`. Red-prove each clause by execution: (1) return the ORM rows from `_claim_batch` again → the integration test reddens with `DetachedInstanceError`; (2) drop `signing_secret` from the join → the signature assertion reddens; (3) drop `attempts` from the job → the retry-budget assertion reddens. Fail loudly: if the join finds no endpoint for a delivery (endpoint deleted mid-flight), mark the delivery `failed_permanent` with that reason rather than skipping the row silently. Boundary and tie: a batch of exactly `BATCH_SIZE` rows is handled identically to a smaller one, and two jobs for the same endpoint share one endpoint read.

### Major: the Redis lock is not atomic, has no owner token, and is deleted by whoever finishes first
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` is a check-then-act race, `expire` is a separate round trip so a crash between `set` and `expire` leaves a TTL-less lock, and the `delete` in `finally` carries no ownership check, so a worker whose batch outran the 60-second TTL deletes a lock a *different* worker now holds.
What breaks in production: with a batch of 100 deliveries the 60-second TTL is routinely exceeded, so two or more workers run concurrently and re-send the same deliveries, while a crash in the one-command window between `set` and `expire` wedges dispatch permanently with no delivery at all and no alert.
Fix: acquire with a single atomic command carrying a unique owner value and a TTL — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — release with a compare-and-delete Lua script (`if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) end`), and refresh the TTL periodically while the batch runs (or size `LOCK_TTL_SECONDS` from `BATCH_SIZE * REQUEST_TIMEOUT` and assert that relation in a test). Preserve the single-worker guarantee the lock exists for; do not fix by widening the TTL alone, which only moves the boundary. Allow side: a single worker must still acquire the lock on every loop iteration and make progress — assert a delivery is actually sent, not just that `_acquire_lock` returned True. Red-prove each clause by execution: (1) revert to `get`+`set` → a test running two `_acquire_lock` calls concurrently against a fake Redis with an interleave point reddens; (2) drop `nx=True` → the same test reddens; (3) replace the compare-and-delete with a plain `delete` → a test where worker A's TTL expires and worker B acquires, then A releases, reddens because B's lock vanished. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise/return False and the worker must back off — never treat an errored lock check as "no one holds it". Boundary and tie: a lock whose TTL expires at exactly the moment of release is released by no one but the owner token, and two workers presenting different tokens for the same key resolve to exactly one holder.

### Major: `in_flight` is a non-terminal state with no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` sets `status = "in_flight"`; `_finish` is the only exit
What is wrong: a row moves to `in_flight` at claim time, but `_claim_batch` selects only `status == "pending"`, so any row whose worker crashed, was redeployed, or hit the `DetachedInstanceError` above is never re-selected and never reaches a terminal state (R38 non-terminal transient state — the async transition has a success exit and a failure exit but no timeout exit).
What breaks in production: every deploy or crash during a batch permanently strands up to `BATCH_SIZE` deliveries in `in_flight`, silently — the customer never gets the event and nothing in the system reports it as failed.
Fix: add a claim timestamp (`claimed_at TIMESTAMPTZ`) written by `_claim_batch`, and have each loop iteration first reclaim stale work: `UPDATE webhook_deliveries SET status='pending', next_attempt_at=now() WHERE status='in_flight' AND claimed_at < now() - interval '5 minutes'` — bounded, explicit, and automatic, since a stuck delivery restrains no one and the R38 confirmation gate does not apply. Preserve the retry budget: reclaiming does not reset `attempts`, so a crash-looping delivery still terminates at `MAX_ATTEMPTS` rather than retrying forever. Allow side: a delivery currently in flight and younger than the stale threshold must NOT be reclaimed — assert that, or the reaper causes the duplicates it was meant to prevent. Red-prove each clause by execution: (1) remove the reclaim statement → the crashed-worker test reddens; (2) widen the interval to zero → the young-in-flight test reddens; (3) reset `attempts` in the reclaim → the retry-budget test reddens. Fail loudly: log a counter of reclaimed rows per pass and alert above a threshold, so a persistent crash loop is visible rather than absorbed. Boundary and tie: a row claimed exactly at the threshold is not yet stale (`<` not `<=`), and two workers racing to reclaim the same row are resolved by the `status='in_flight'` predicate in the UPDATE.

### Major: naive/aware datetime mixing, and a `_now()` helper in this same diff that `delivery.py` ignores
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`) vs `_claim_batch` (`datetime.now(timezone.utc)`) and `app/webhooks/models.py` `_now()`
What is wrong: `enqueue_for_event` writes a naive UTC datetime into a `DateTime(timezone=True)` column while every other timestamp in the change goes through `models._now()` or `datetime.now(timezone.utc)` — codebase-awareness check: `_now()` is defined in `app/webhooks/models.py` in this very diff and is used for all four `created_at`/`updated_at` defaults, so `delivery.py` reimplements it and does so incorrectly (R1: the behavioural difference is tz-awareness, and it is not accidental — it changes the stored instant).
What breaks in production: psycopg interprets the naive value in the session time zone, so on a non-UTC database session every new delivery's `next_attempt_at` is offset by the UTC offset — deliveries are either withheld for hours (positive offsets) or, on negative offsets, all deliveries become instantly due and the `next_attempt_at <= now` claim predicate stops throttling anything.
Fix: import `_now` from `app.webhooks.models` and use it in `enqueue_for_event` and in `_finish`/`deliver`'s reschedule, deleting the three ad-hoc constructions (`datetime.utcnow()`, and the two `datetime.now(timezone.utc)` calls) so one helper is the only source of "now"; also change the migration's `TIMESTAMP` columns to `TIMESTAMPTZ` so the column type matches `DateTime(timezone=True)` on both models. Behaviour change to state: adopting `_now()` makes `enqueue_for_event`'s stored value tz-aware, which is the point — the equivalence with the old code holds only when the DB session is already UTC. ### Major: the claim query has no total order, no atomic claim, and no supporting index

Fail loudly: if the UPDATE returns fewer rows than expected because the connection dropped, surface the error rather than treating it as an empty batch. Boundary and tie: rows sharing an identical `next_attempt_at` are ordered by `id`, and the row at exactly `next_attempt_at == now` is included.
