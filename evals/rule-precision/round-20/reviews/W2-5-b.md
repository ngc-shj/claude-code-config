### Critical: the bytes that are signed are not the bytes that are sent
File: app/webhooks/delivery.py — `send_once`; app/webhooks/signing.py — `sign`/`serialize`
What is wrong: `sign()` computes the HMAC over `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators) while `send_once` transmits the body via `client.post(..., json=delivery.payload)`, which httpx serializes with its own separators and insertion-order keys, so the digest in `X-Acme-Signature` is over a different byte string than the request body the receiver hashes.
What breaks in production: Every customer following `docs/webhooks.md` computes a different HMAC from the one we send and rejects 100% of deliveries, and because `deliver()` retries any non-2xx we generate five requests per event forever.
Fix: Serialize once and send the exact bytes: in `send_once`, `body = serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, body)`, then `client.post(endpoint.url, content=body, headers={...})` with `Content-Type: application/json` set explicitly; change `sign`/`verify` to take `body: bytes` so no caller can re-serialize. Must still succeed: a payload whose keys are already in sorted order still delivers and still verifies — pin it. Red-prove each clause separately by execution: (i) revert to `json=` and observe the new "signature matches the captured raw body" assertion go red on a two-key payload; (ii) change `serialize` to `sort_keys=False` and observe a second assertion, comparing `serialize` output to the captured `request.content`, go red; (iii) flip one byte of the secret and observe the HMAC assertion go red. Fail loudly: if `serialize` raises on a non-JSON-serializable payload, `_finish(..., "failed_permanent", ...)` with the exception text rather than letting the delivery silently stay `pending`. Preserve: the payload must still reach the endpoint as a JSON object, not a quoted string. Boundary and tie: an empty payload `{}` signs and sends as the two bytes `{}` — assert that case, and assert two payloads with the same keys in different insertion order produce the identical signature.

### Critical: `UNIQUE (event_id)` makes an org with two endpoints receive nothing
File: migrations/0042_webhook_delivery.sql — `idx_webhook_deliveries_event`
What is wrong: The unique index is on `event_id` alone, but `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single event, so the second row of any multi-endpoint org violates the constraint.
What breaks in production: The whole `session.add_all` transaction raises `IntegrityError`, the dispatcher's blanket `except Exception` downgrades it to a `log.warning`, and every event for that org is silently lost with no delivery row to show for it.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` — this keeps the intended per-endpoint idempotency guarantee that the `event_id`-only index was reaching for, so do not simply drop uniqueness. Must still succeed: one event fanning out to three active endpoints of the same org inserts three rows — add an integration test asserting `len == 3`. Red-prove each clause separately: (i) restore the `(event_id)` index and observe the three-endpoint test go red with `IntegrityError`; (ii) re-enqueue the same `(endpoint_id, event_id)` pair and observe a separate test assert exactly one row survives. Fail loudly: catch `IntegrityError` in `enqueue_for_event` and re-raise as a named `WebhookEnqueueError` so the dispatcher logs "enqueue rejected" rather than "enqueue failed" for a duplicate. Boundary and tie: state which side the re-delivery boundary falls on — a second enqueue of the same pair is a no-op (`ON CONFLICT DO NOTHING`), not an error, and two different events for one endpoint must both insert.

### Critical: the status vocabulary in the migration and in the code disagree (R2)
File: migrations/0042_webhook_delivery.sql — `status ... CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; app/webhooks/models.py — `STATUSES`
What is wrong: The SQL CHECK allows `'failed'` while `models.STATUSES` and `delivery._finish(delivery.id, "failed_permanent", ...)` use `'failed_permanent'`, and value-equality was never checked against meaning-equality across the two declarations.
What breaks in production: Every permanently failed delivery raises a CHECK violation inside `_finish`, so the row keeps whatever status it had (`in_flight`) and the failure is never recorded — the exact case operators page on.
Fix: Make the database the single source and derive the Python tuple from it: set the CHECK to `IN ('pending','in_flight','delivered','failed_permanent')` in the migration and assert in a test that `set(models.STATUSES)` equals the set parsed out of the migration's CHECK clause, so the two cannot drift again. Must still succeed: a delivery transitioning `pending → in_flight → delivered` still commits — pin that path. Red-prove each clause separately: (i) rename one member of `STATUSES` and observe the parity test go red naming the missing member; (ii) write `'failed'` from `_finish` against the new CHECK and observe an integration test go red on the constraint. Fail loudly: if the migration file cannot be parsed for a CHECK clause the parity test must fail with "could not locate status CHECK", never skip — "examined nothing" must not be spelled the same as "found nothing". Preserve: keep the CHECK constraint; do not fix this by deleting it, since it is what made the drift visible. Boundary and tie: `'failed_permanent'` is terminal and `'in_flight'` is not — say explicitly that `_claim_batch` must never re-select a terminal status.

### Critical: every delivery touches detached ORM instances and raises before the first request
File: app/webhooks/delivery.py — `_claim_batch`, `deliver`
What is wrong: `_claim_batch` returns `rows` after `session_scope()` has exited and `deliver` fetches `endpoint` inside a `with` block that closes immediately, then reads `delivery.attempts`, `delivery.payload`, `delivery.id`, `endpoint.signing_secret` and `endpoint.url` on instances whose session is gone.
What breaks in production: With SQLAlchemy's default `expire_on_commit=True` the first attribute access raises `DetachedInstanceError`, `asyncio.gather` propagates it out of `run_worker`'s `try`, and the worker dies — no webhook is ever delivered.
Fix: Stop passing ORM instances across session boundaries: have `_claim_batch` return plain immutable value objects (`@dataclass(frozen=True) class ClaimedDelivery: id, endpoint_id, attempts, payload, url, signing_secret`) built inside the session from a joined query against `WebhookEndpoint`, and change `deliver`/`send_once` to accept that dataclass. Must still succeed: a batch of two claimed deliveries still POSTs both bodies — pin with a `MockTransport` test that runs the real `_claim_batch` output through `deliver`. Red-prove each clause separately: (i) return the ORM rows again and observe the new end-to-end test go red with `DetachedInstanceError`; (ii) drop `signing_secret` from the dataclass and observe the signature assertion go red. Fail loudly: if the join finds no endpoint row for a claimed delivery, `_finish(..., "failed_permanent", ..., "endpoint missing")` rather than skipping the row. Preserve: the tests' `FakeEndpoint`/`FakeDelivery` doubles must be replaced by the real dataclass so the double cannot again be shaped unlike the production object (RT1(a)). Boundary and tie: an empty claimed batch must be a no-op that still releases the lock.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: app/webhooks/delivery.py — `deliver`, line `time.sleep(delay)`
What is wrong: The retry backoff uses the blocking `time.sleep` inside an `async def` that `run_worker` fans out with `asyncio.gather`, so the sleep freezes the entire loop rather than yielding.
What breaks in production: One failing endpoint stalls all 100 deliveries in the batch for up to 30s each, the 60-second Redis lock TTL expires while the worker is still blocked, and a second worker claims and re-sends the same batch.
Fix: Replace in-process retrying with rescheduling: on a retryable failure, write `status='pending'`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` via `_finish` and return, letting the next poll pick the row up; delete the `while True` loop and the `time.sleep` import. Must still succeed: a delivery that succeeds on its first attempt still completes in one pass and is marked `delivered` — pin it. Red-prove each clause separately: (i) re-introduce `time.sleep(0.5)` and observe a test asserting `deliver` returns within 50ms go red; (ii) make `backoff_for` return zero and observe a test asserting `next_attempt_at > now` go red; (iii) force a 500 response and observe an assertion that `status == 'pending'` and `attempts == 1` go red if the row is marked terminal. Fail loudly: a delivery whose row disappears between claim and finish must log "delivery %s vanished" and count a metric, not pass silently. Preserve: the retry budget itself — attempts must still stop at `MAX_ATTEMPTS`. Boundary and tie: at exactly `attempt == MAX_ATTEMPTS` the row goes terminal (`failed_permanent`) and is not rescheduled; at `MAX_ATTEMPTS - 1` it is rescheduled.

### Critical: the signing secret is readable back through the list endpoint and printed to logs (RS4)
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`; app/webhooks/delivery.py — `log.info("POST %s headers=%s", ...)`
What is wrong: `to_dict()` includes `signing_secret`, and `list_webhook_endpoints` returns it for every endpoint, directly contradicting `docs/webhooks.md` ("the response is the only place the signing secret appears — it cannot be read back afterwards"); separately, `send_once` logs the full header dict, which contains `X-Acme-Signature`.
What breaks in production: Live HMAC key material is served on a routine GET and copied into every log sink, index, and support screenshot, so any log-read or token-scoped API access is a signature-forgery capability.
Fix: Remove `signing_secret` from `to_dict()`; return the secret only from `create_webhook_endpoint`, by constructing that one response explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held value; change the log line to `log.info("POST %s delivery=%s", endpoint.url, delivery.id)`. Must still succeed: the 201 response of `POST /v1/settings/webhook-endpoints` still carries the secret exactly once — pin it with a test asserting the key is present there and absent from the subsequent GET. Red-prove each clause separately: (i) re-add `signing_secret` to `to_dict()` and observe the GET-response test go red; (ii) restore the header log line and observe a caplog assertion that no record contains `SIGNATURE_HEADER` go red. Fail loudly: since secrets already reaching logs cannot be un-published, treat existing secrets as compromised and add a rotation endpoint rather than only stopping the leak. Preserve: the create response must keep returning the secret — the feature is unusable without it. Boundary and tie: exactly one response body in the API surface may contain the secret; name it in the test so a third response added later fails the assertion.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id` from the path and never joins `WebhookEndpoint.org_id == user.org_id`, unlike its sibling `list_webhook_endpoints` in the same file, which does filter on `org_id`.
What breaks in production: Any authenticated user can enumerate integer endpoint ids and read other tenants' delivery rows, including the `response_status` and scheduling of their invoice and subscription events.

Red-prove each clause separately: (i) remove the `org_id` filter and observe a cross-tenant test asserting `404` go red; (ii) remove the owner allow-case fixture's rows and observe the allow assertion go red for the right reason. Fail loudly: when `user.org_id` is `None` the handler must 403 rather than fall through to an unfiltered query. Boundary and tie: an endpoint id that exists but belongs to another org and an endpoint id that does not exist must both return 404, indistinguishably — assert both.

### Critical: signing secrets are generated from a non-cryptographic PRNG (R1)
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: The secret is built from `random.choice`, the Mersenne Twister, which is seeded predictably and fully recoverable from observed output, rather than from the stdlib's existing `secrets` helper that already provides exactly this behaviour.
What breaks in production: An attacker who can observe or provoke enough generator output can reconstruct the state and derive other tenants' signing secrets, forging webhook payloads that every customer's verification accepts.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`, `string` and `_ALPHABET` duplicates outright rather than leaving them unreferenced (R1(d)); note the behavioural difference this adopts (R1(b)): `token_urlsafe(32)` returns 32 random *bytes* base64url-encoded to 43 characters, so `SECRET_BYTES` now means bytes rather than characters and the existing length assertion must be updated to `len(secrets.token_urlsafe(SECRET_BYTES))`. The unaddressed hazard the dedup does not fix (R1(e)): the secret is still stored in plaintext in `webhook_endpoints.signing_secret` and served back by the list endpoint — that is a separate finding above. Must still succeed: `new_signing_secret()` still returns a value that `create_webhook_endpoint` stores and `sign` accepts — pin a round-trip test. Red-prove each clause separately: (i) monkeypatch `secrets.token_urlsafe` to a constant and observe a "two calls differ" assertion go red; (ii) drop the prefix and observe the prefix assertion go red. Fail loudly: `new_signing_secret` must not fall back to `random` if `secrets` import fails — let the import error propagate. Boundary and tie: state the minimum acceptable entropy (256 bits) so a later reviewer lowering `SECRET_BYTES` has a stated floor to cross.

### Critical: `verify` compares signatures with `==` (RS1)
File: app/webhooks/signing.py — `verify`, `return expected == signature`
What is wrong: The HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, in a function the docs tell integrators to model their own verification on.
What breaks in production: A remote attacker can recover a valid signature byte-by-byte from response-time differences on any endpoint that calls `verify`, defeating the signature scheme entirely.
Fix: `return hmac.compare_digest(expected, signature)` (`hmac` is already imported), and update `docs/webhooks.md` to keep its existing constant-time instruction consistent with the shipped helper. Must still succeed: a genuine signature still verifies — the existing `test_verify_accepts_signature_produced_by_sign` covers the allow side once it is de-tautologised (see the test finding below). Red-prove each clause separately: (i) revert to `==` and observe a test asserting `verify` is implemented via `compare_digest` (inspecting `inspect.getsource`) go red; (ii) pass a signature differing in the final byte and observe the deny assertion go red. Fail loudly: `compare_digest` raises `TypeError` on a non-str/bytes argument — catch it and return `False` explicitly rather than letting an off-type header 500 the caller. Boundary and tie: a signature of the wrong length must return `False`, not raise; assert the empty-string case.

### Critical: the timestamp header is unauthenticated, so the documented replay window does not exist (R49)
File: app/webhooks/signing.py — `sign`, `verify`; docs/webhooks.md — "Verifying the signature"
What is wrong: `sign` returns a timestamp but MACs only `serialize(payload)`, so the timestamp is outside the authenticated data, and `verify` discards the caller's timestamp entirely by calling `sign` again to get a fresh one — the docs nevertheless claim the timestamp window "is what stops a captured request from being replayed".
What breaks in production: A captured request replays forever with a rewritten `X-Acme-Timestamp`, and any integrator who trusted the documented guarantee accepts it, so the control the docs sell as the anti-replay boundary is absent (a claim stronger than the implementation).
Fix: Bind the timestamp into the MAC — `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` — and change `verify(secret, body, timestamp, signature, max_age=300)` to recompute with the *supplied* timestamp, reject when `abs(now - int(timestamp)) > max_age`, and compare with `compare_digest`. Must still succeed: a signature produced 10 seconds ago still verifies — pin it with a frozen clock. Red-prove each clause separately: (i) remove the timestamp from the MAC input and observe a test asserting two signatures of the same payload at different timestamps differ go red; (ii) set the clock 400 seconds back and observe the freshness assertion go red; (iii) keep a valid signature but alter the timestamp header and observe the tamper assertion go red. Fail loudly: a non-numeric or absent timestamp must return `False` with a named reason, not be treated as 0 (which would be silently stale) and not be skipped. Preserve: the doc's stated wire format — after this fix the docs' `"{timestamp}.{raw_request_body}"` description becomes true rather than being edited down to match the weaker code. Boundary and tie: a timestamp exactly `max_age` seconds old is accepted and `max_age + 1` is rejected — state that and assert both.

### Critical: endpoint URLs are barely validated and the client follows redirects (RS3)
File: app/api/routes/settings.py — `create_webhook_endpoint`; app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plaintext `http://`, admits any scheme whose name begins with `http`, and applies no host restriction, while the delivery client follows redirects.
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/` (or an https host that 302s there) and turns our worker into an authenticated SSRF probe of the internal network, with signed invoice payloads additionally travelling in cleartext for `http://` endpoints.
Fix: Validate at the schema level with a pydantic field validator on `EndpointIn.url`: require `parsed.scheme == "https"` exactly, require a non-empty hostname, resolve the hostname and reject when any resolved address is in a private, loopback, link-local, or reserved range (`ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved`), and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a delivery failure rather than followed. Must still succeed: `https://hooks.example.com/acme` still registers and still delivers — pin that allow case adjacent to the boundary (RT10). Red-prove each clause separately: (i) submit `http://hooks.example.com/x` and observe the 422 assertion go red if the scheme check is loosened back to `startswith`; (ii) submit `https://127.0.0.1/x` and observe the private-range assertion go red if the range check is removed; (iii) return a 302 to an internal host from `MockTransport` and observe the "redirect not followed" assertion go red if `follow_redirects=True` is restored. Fail loudly: when DNS resolution fails, reject the registration with 422 "hostname could not be resolved" — never admit the URL because the check could not run. Preserve: customers must still be able to register a public HTTPS host behind a CDN, so re-resolve at delivery time rather than pinning the address at registration. Boundary and tie: state the side each range boundary falls on — `10.0.0.0/8` rejected, `9.255.255.255` allowed — and decide explicitly whether IPv6-mapped IPv4 (`::ffff:127.0.0.1`) is rejected (it must be).

### Critical: the signature tests cannot fail for the reason they claim (RT5, RT1(c))
File: tests/webhooks/test_delivery.py — `test_verify_accepts_signature_produced_by_sign`, `test_send_once_posts_the_signed_payload`
What is wrong: `verify` internally calls `sign`, so asserting that `verify` accepts `sign`'s output is an identity that holds for any MAC implementation including a constant, and the `send_once` test only asserts the header `startswith("sha256=")` without ever recomputing the HMAC over the captured body.
What breaks in production: Both defects above — the payload/body serialization mismatch and the unauthenticated timestamp — sit directly under a green suite, so a reviewer reads "verify accepts signature produced by sign" and trusts a signature scheme that no test has ever exercised end to end.
Fix: Add a test with an independently written expected value (RT1(d)): a fixed secret, a fixed payload, a frozen timestamp, and a hex digest computed once by hand from `hmac.new(b"whsec_testsecret", b"1700000000." + b'{"a":1}', hashlib.sha256).hexdigest()` written literally into the assertion; and in the `send_once` test recompute the HMAC over `captured["body"]` with `captured["headers"][TIMESTAMP_HEADER]` and assert it equals the signature header exactly. Must still succeed: a correct implementation passes both — run them against the fixed implementation first. Red-prove each clause separately (execute, do not reason): (i) change `serialize` to `sort_keys=False` and observe the literal-digest assertion go red; (ii) drop the timestamp from the MAC input and observe the same assertion go red for a different reason; (iii) switch `send_once` back to `json=` and observe the recompute-over-captured-body assertion go red. Fail loudly: if the frozen clock fixture is not applied, the test must fail rather than silently use wall-clock time. Preserve: keep the existing wrong-secret rejection test — it is the only deny-side case present. Boundary and tie: choose the fixture payload with two keys in non-sorted insertion order so ordering is observable, and choose values away from zero/defaults (RT1(f)).

### Major: the Redis lock is neither atomic nor reliably released
File: app/webhooks/delivery.py — `_acquire_lock`, `run_worker`
What is wrong: `_acquire_lock` does a `get` then a separate `set` and a separate `expire`, so two workers can both observe an empty key and both proceed, and a crash between `set` and `expire` leaves a TTL-less key; `run_worker`'s `finally` deletes `LOCK_KEY` unconditionally, including a lock a different worker acquired after the TTL expired.
What breaks in production: A crash in the one-line window between `set` and `expire` stops all webhook delivery permanently with no reset path (R38 persisted fail-closed wedge), and in the ordinary case two workers deliver the same batch twice.
Fix: Use a single atomic call — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete Lua script that deletes only when the stored value equals `token`, so a worker cannot delete a lock it does not own. Must still succeed: a single worker still acquires, runs a batch, and releases so the next poll acquires again — pin it against a real Redis or an in-memory fake implementing `set(nx=, ex=)` semantics. Red-prove each clause separately: (i) drop `nx=True` and observe a "second concurrent acquire returns False" assertion go red; (ii) drop `ex=60` and observe a "key has a TTL" assertion go red; (iii) replace the compare-and-delete with a plain `delete` and observe a "foreign lock survives" assertion go red. Fail loudly: when Redis is unreachable, `_acquire_lock` must raise and stop the worker rather than returning `True` and running unlocked. Boundary and tie: state what happens when the TTL expires while work is still in flight — either the lock is renewed on a heartbeat, or the batch must be idempotent by the `(endpoint_id, event_id)` constraint above; say which.

### Major: `run_worker` raises `NameError` when the batch claim fails
File: app/webhooks/delivery.py — `run_worker`
What is wrong: `batch` is bound inside the `try`, but `if not batch` is evaluated after the `finally`, so any exception from `_claim_batch` or `asyncio.gather` leaves `batch` unbound and the handler for the real error is an unrelated `NameError`.
What breaks in production: A transient database error kills the worker loop and masks its own cause in the traceback, so the on-call engineer debugs the wrong failure.
Fix: Initialise `batch: list = []` before the `try`, move the `if not batch: await asyncio.sleep(poll_interval)` inside the `try` after the gather, and wrap the body in `except Exception: log.exception("webhook worker iteration failed"); await asyncio.sleep(poll_interval)` so the loop survives one bad iteration. Must still succeed: a normal non-empty batch still runs without an extra sleep — pin the timing. Red-prove each clause separately: (i) make `_claim_batch` raise and observe an assertion that the loop performed a second iteration go red if the guard is removed; (ii) make `_claim_batch` return an empty list and observe the "slept once" assertion go red if the sleep is removed. Fail loudly: the `except` must log with `log.exception` (stack included) and increment a failure counter, never `pass`. Preserve: the loop must still exit on `CancelledError` — re-raise it above the broad `except`.

### Major: `in_flight` is a non-terminal state with no reset path (R38)
File: app/webhooks/delivery.py — `_claim_batch`
What is wrong: `_claim_batch` flips claimed rows to `in_flight` but only `_finish` ever moves them out, and `_claim_batch` selects `status == "pending"` only, so a worker crash or a redeploy mid-batch strands every claimed row forever.
What breaks in production: A single deploy during a batch permanently drops up to 100 customer webhooks, with no query or job that will ever pick them up again.
Fix: Add a `claimed_at` column and make the claim reclaim stale rows: `filter(or_(status == 'pending', and_(status == 'in_flight', claimed_at < now - timedelta(minutes=5))))`, setting `claimed_at = now` on claim. Must still succeed: a row claimed 10 seconds ago by a live worker is *not* re-claimed by a second worker — pin that allow-side case. Red-prove each clause separately: (i) age a row's `claimed_at` past the threshold and observe the reclaim assertion go red if the `or_` branch is removed; (ii) leave a row fresh and observe the "not reclaimed" assertion go red if the age predicate is dropped. Fail loudly: a row reclaimed more than `MAX_ATTEMPTS` times must go to `failed_permanent` with detail "stale claim exceeded", not loop. Boundary and tie: a row whose `claimed_at` is exactly the threshold is not reclaimed; one microsecond older is — state it and assert both.

### Major: `enqueue_for_event` writes a naive datetime the claim query compares against an aware one
File: app/webhooks/delivery.py — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); migrations/0042_webhook_delivery.sql (`TIMESTAMP`) vs app/webhooks/models.py (`DateTime(timezone=True)`)
What is wrong: `enqueue_for_event` uses naive `datetime.utcnow()` while every other timestamp in the change uses `datetime.now(timezone.utc)`, and the migration declares `TIMESTAMP` without time zone against models declaring `DateTime(timezone=True)`.
What breaks in production: The `next_attempt_at <= now` comparison in `_claim_batch` either raises `TypeError: can't compare offset-naive and offset-aware datetimes` or, once the driver coerces, interprets the naive value in the server's local zone, so deliveries are claimed hours early or late depending on deployment region.
Fix: Use the existing helper the change already provides — `models._now()` — for `next_attempt_at`, and change all six `TIMESTAMP` columns in the migration to `TIMESTAMPTZ` so the storage type matches the model declaration. Must still succeed: a delivery enqueued now is claimable on the next poll — pin it. Red-prove each clause separately: (i) restore `datetime.utcnow()` and observe an assertion that `row.next_attempt_at.tzinfo is not None` go red; (ii) revert one column to `TIMESTAMP` and observe a schema-introspection assertion on that column go red. Fail loudly: reject at write time — add a `CHECK` or a model validator so a naive value cannot be stored silently. Boundary and tie: a row whose `next_attempt_at` equals `now` exactly is claimed (the filter is `<=`) — state it, and note that ties on `next_attempt_at` in the `ORDER BY` have no deterministic resolution until a second key is added (see below).

### Major: `webhooks_enabled` is declared and never consulted (R41)
File: migrations/0042_webhook_delivery.sql — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: The migration adds an org-level feature flag that no code in the change reads — neither `dispatch`, `enqueue_for_event`, `create_webhook_endpoint`, nor `run_worker` — and it is the only backing path a newly added column could have.
What breaks in production: Operators toggling the flag see no behaviour change, and since it defaults to `FALSE` the feature ships enabled for every organization while the control panel says it is off for all of them.
Fix: Consult it at the single narrowest chokepoint — in `enqueue_for_event`, join `Organization` and return `0` when `webhooks_enabled` is false — and make `create_webhook_endpoint` return 403 for a disabled org so the flag is visible at registration too. Must still succeed: an org with the flag TRUE still enqueues one row per matching endpoint — pin that allow case (RT10), since a fix that only denies satisfies everything else. Red-prove each clause separately: (i) set the flag FALSE and observe an assertion that zero rows were inserted go red if the filter is removed; (ii) set it TRUE and observe the "rows inserted" assertion go red if the filter is inverted. Fail loudly: an org row that cannot be loaded must deny (return 0 and log), not default to enabled. Boundary and tie: state the migration ordering — flipping existing orgs to TRUE must be a separate backfill statement, or the deploy silently disables webhooks for everyone the moment this lands.

### Major: `list_deliveries` accepts an unbounded `limit` and orders on a non-unique key (RS3, R57)
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: `Query(50, ge=1)` sets a floor but no ceiling, and the result is ordered by `created_at` alone, which has no uniqueness or total-order guarantee.
What breaks in production: `?limit=100000000` materializes every delivery row and its JSONB payload into memory in one request, and rows sharing a `created_at` — the norm for a batch enqueued in one transaction — come back in an arbitrary order that changes between calls.
Fix: `limit: int = Query(50, ge=1, le=200)` and `.order_by(WebhookDelivery.created_at.desc(), WebhookDelivery.id.desc())`, with `id` also returned so a future keyset cursor has a unique key to carry. Must still succeed: `limit=200` still returns 200 rows and the default 50 still works — pin both. Red-prove each clause separately: (i) request `limit=201` and observe the 422 assertion go red if `le` is removed; (ii) insert three rows with an identical `created_at` and observe a stable-order assertion go red if the `id` tiebreak is removed. Fail loudly: a non-integer `limit` must 422 from FastAPI's own validation, not be coerced. Boundary and tie: `limit=200` is accepted and `201` rejected; among rows tied on `created_at`, the higher `id` sorts first — state both.

### Major: the docs describe a retry and subscription policy the code does not implement (R29)
File: docs/webhooks.md — "Retries", "Registering an endpoint"; app/webhooks/delivery.py — `deliver`, `backoff_for`; app/events/dispatcher.py — `WEBHOOK_EVENT_TYPES`
What is wrong: Four documented claims are false against the same diff — "backoff is exponential with jitter" (`backoff_for` has none, and `test_backoff_grows_exponentially` pins the exact jitter-free values), "a 4xx is permanent and we stop immediately" (`deliver` retries every non-2xx to `MAX_ATTEMPTS`), "only `https://` URLs are accepted" (the scheme check admits `http`), and "an empty `event_types` subscribes the endpoint to every event type we emit" (only the three members of `WEBHOOK_EVENT_TYPES` are ever enqueued).
What breaks in production: Integrators build against the documented contract — retrying a 4xx that will never succeed burns their rate limits, and an endpoint registered with empty `event_types` silently never receives the other event types the platform emits.
Fix: Make the code the authority for each claim and correct the doc where the code is deliberate: add `random.SystemRandom().uniform(0, delay * 0.1)` jitter in `backoff_for` and relax the test to a range assertion; in `deliver`, branch `if 400 <= response.status_code < 500 and status_code != 429: _finish(..., "failed_permanent", ...)` and return; fix the scheme check as in the SSRF finding; and either widen `WEBHOOK_EVENT_TYPES` to the full emitted set derived from `SUBSCRIBERS`/the event catalogue rather than a hand-written list (R42), or change the doc to say empty means "every webhook-eligible event type" and enumerate them. Must still succeed: a 500 and a 429 are still retried and a 200 still marks `delivered` — pin all three. Red-prove each clause separately: (i) return 404 and observe the "one attempt, `failed_permanent`" assertion go red if the 4xx branch is removed; (ii) return 429 and observe the "retried" assertion go red if 429 is folded into the 4xx branch; (iii) remove the jitter and observe a "two consecutive backoffs differ" assertion go red. Fail loudly: an unrecognised status class (1xx, 3xx with redirects disabled) must be recorded as `failed_permanent` with the status in `response_body`, not silently retried forever. Preserve: keep the `MAX_ATTEMPTS == 5` budget and the documented 2/4/8/16 magnitudes — jitter widens, it does not replace them. Boundary and tie: `400` and `499` are permanent, `429` is not, `500` is retried — state each side.

### Major: the delivered payload carries no event identifier, so the documented deduplication is impossible
File: app/webhooks/delivery.py — `send_once`; docs/webhooks.md — "delivery is at-least-once, so deduplicate on `event_id`"
What is wrong: `send_once` posts `delivery.payload` — the raw event payload — with no envelope, so `event_id`, `event_type`, and the delivery id never reach the receiver, while the docs instruct receivers to deduplicate on `event_id`.
What breaks in production: At-least-once delivery combined with no identifier means every retried invoice event is processed twice by the customer, which for payment events is a double-charge or a duplicate ledger entry.
Fix: Wrap the payload in an envelope that the signature covers — `{"id": f"evt_{delivery.event_id}", "type": delivery.event_type, "created_at": <iso>, "data": delivery.payload}` — and add an `X-Acme-Delivery-Id` header; update `docs/webhooks.md` to show the envelope. Must still succeed: the existing `data` contents reach the receiver unchanged — pin `json.loads(body)["data"]["amount_cents"] == 4200` so the fix does not delete what made the feature useful. Red-prove each clause separately: (i) drop `id` from the envelope and observe the "id present and stable across retries" assertion go red; (ii) retry the same delivery and observe the "same id on both attempts" assertion go red if the id is derived from the attempt rather than the event. Fail loudly: a delivery row with a null `event_id` must be finished `failed_permanent`, not sent without an id. Boundary and tie: two deliveries of the same event to two different endpoints share `id` — state that receivers deduplicate per-endpoint and that the delivery id, not the event id, distinguishes attempts.

## Cross-cutting verification

- **Tenancy filter**: `list_webhook_endpoints` filters on `org_id`; `list_deliveries` does not (reported). `enqueue_for_event` correctly scopes by `org_id`. No other query in the diff reads a tenant-owned table.
- **Timezone-aware `now()`**: `models._now`, `_claim_batch`, and `_finish` use `datetime.now(timezone.utc)`; `enqueue_for_event` alone uses `datetime.utcnow()` (reported). `dispatcher.dispatch` uses the aware form.
- **Serialization for signing**: `serialize()` is the only canonicalizer in the change, and `send_once` is the only site that bypasses it (reported). No second producer exists yet — the fix must land before one does.
- **Secret exposure**: `to_dict()` on `WebhookEndpoint` is the only model method leaking the secret; `WebhookDelivery.to_dict` is clean. `send_once`'s header log is the only log site that includes signature material.
- **Status literals**: `'pending'` appears in `models.py` (column default), `delivery.py` (`_claim_batch` filter) and the SQL CHECK; `'in_flight'` in `_claim_batch` and the CHECK; `'delivered'` in `_finish` and the CHECK; `'failed_permanent'` in `_finish` and `STATUSES` but **not** in the CHECK (reported).

## Codebase awareness

- `models._now()` already exists and is the helper `enqueue_for_event`'s `datetime.utcnow()` reimplements — the fix reuses it rather than adding a third spelling.
- `signing.serialize()` already exists and is the canonicalizer `send_once` bypasses by using httpx's `json=` — the fix reuses it rather than introducing a new encoder.
- `hmac` is already imported in `signing.py`, so `compare_digest` needs no new dependency; `secrets` is the stdlib helper `new_signing_secret` reimplements with `random`.
- `session_scope` is the change's existing transaction helper; the detached-instance fix works within it rather than adding a second session manager.
