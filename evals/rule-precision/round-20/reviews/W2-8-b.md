### Critical: the signature is computed over different bytes than the ones sent, so no customer signature will ever verify
File: app/webhooks/delivery.py — `send_once` (`sign(endpoint.signing_secret, delivery.payload)` + `client.post(..., json=delivery.payload)`)
What is wrong: `sign` HMACs `signing.serialize(payload)` = `json.dumps(payload, sort_keys=True)`, which uses the default `", "`/`": "` separators and sorted keys, while httpx's `json=` argument re-serializes the same dict independently with compact `(",", ":")` separators and insertion order, so the digest in `X-Acme-Signature` is over a byte string that never appears on the wire.
What breaks in production: every customer following `docs/webhooks.md` ("HMAC-SHA256 of the raw request body") computes a different digest and rejects 100% of deliveries, so the feature is dead on arrival for every integrator while our own delivery rows are recorded as `delivered`.
Fix: serialize exactly once and send those bytes — in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, pass `content=body` (not `json=`) with the explicit `Content-Type: application/json` header already present, and change `signing.sign` to take the serialized `bytes` rather than the dict so no second serialization can exist. Preserve the properties that made the current code useful: the payload must still arrive as valid JSON and `sort_keys=True` must stay, because that is what makes the digest reproducible for a receiver that re-parses and re-dumps. Pair the deny side with the allow side: add (a) a positive round-trip test that runs the ACTUAL bytes captured by `httpx.MockTransport` through `signing.verify` — not through `sign` again — and asserts it returns True, and (b) a test asserting `captured["body"] == signing.serialize(payload).encode()` byte-for-byte. Red-prove each clause separately by execution: mutation 1 restores `json=delivery.payload` and must redden the byte-equality assertion; mutation 2 flips `sort_keys=False` in `serialize` and must redden the verify assertion with a payload whose insertion order differs from sorted order (e.g. `{"b": 2, "a": 1}` — note the existing `test_verify_accepts_signature_produced_by_sign` uses exactly that payload and stays green under this mutation, which is why it does not cover this). Fail loudly when the check cannot run: if `MockTransport` captures no body (handler never invoked), the test must fail with "transport handler never called", not pass on an absent capture. Boundary and tie: an empty payload `{}` must still produce a body of `b"{}"` and a verifiable signature, not an empty body.

### Critical: the timestamp header is not covered by the signature, so the documented five-minute replay window is unenforceable
File: app/webhooks/signing.py — `sign` (`hmac.new(secret.encode(), serialize(payload).encode(), ...)`)
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign` MACs the body alone and returns `timestamp` as an unauthenticated side value, so `X-Acme-Timestamp` can be rewritten by anyone without invalidating `X-Acme-Signature`.
What breaks in production: an attacker who captures one delivery (from a proxy log, a mis-scoped CDN, or our own INFO log — see the log-hygiene finding) replays it indefinitely by resetting the timestamp header to `now`, and the receiver's freshness check — the only replay defence the docs describe — accepts it, so a captured `invoice.paid` can be re-driven into the customer's ledger any number of times.
Fix: bind the timestamp into the MAC — in `sign`, compute `timestamp = str(int(time.time()))` then `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`, and change `verify` to take the timestamp explicitly (`verify(secret, timestamp, body, signature)`) so a caller structurally cannot omit it; there is no default-timestamp overload, because a defaulted timestamp reintroduces the gap. Preserve what made this useful: the header names and the `sha256=<hex>` wire format stay unchanged, and `docs/webhooks.md`'s stated formula becomes true rather than being edited down to match the weaker code. Pair deny with allow: assert (a) a signature produced at timestamp T verifies when re-checked with T, and (b) the same signature fails when re-checked with `T+1`. Red-prove each clause by execution: mutation 1 drops the `f"{timestamp}."` prefix and must redden (b); mutation 2 makes `verify` recompute its own timestamp from `time.time()` instead of using the passed one and must redden (a) under a frozen-clock fixture. Fail loudly: `verify` must raise on a non-numeric or absent timestamp rather than returning False, so "malformed header" is not spelled the same as "bad signature". Boundary and tie: state that the freshness comparison is `now - timestamp <= 300` inclusive, and that a timestamp in the future by more than the allowed skew is rejected rather than treated as fresh.

### Critical: signature comparison is not constant-time (RS1)
File: app/webhooks/signing.py — `verify` (`return expected == signature`)
What is wrong: the HMAC comparison uses Python's `==`, which short-circuits on the first differing byte, and `docs/webhooks.md` instructs customers to use a constant-time comparison while our own reference implementation does not.
What breaks in production: any caller of `verify` that is reachable by an attacker who can submit candidate signatures and observe latency (an inbound-verification reuse of this helper, or a customer copying it as the documented reference) leaks the expected digest byte-by-byte, letting a forged signature be constructed in ~hundreds of requests per byte.
Fix: replace the comparison with `hmac.compare_digest(expected, signature)`, coercing both to `str` and rejecting non-`str` input with a `TypeError` before the call so an off-type value cannot bypass it. Preserve what made this useful: `verify` must keep returning a plain bool for a well-formed mismatch — do not convert every mismatch into an exception, or callers will start catching broadly and swallow real errors. Pair deny with allow: keep the existing `test_verify_accepts_signature_produced_by_sign` (allow side) and `test_verify_rejects_a_signature_made_with_another_secret` (deny side), and add a case asserting a signature differing only in its final hex character is rejected. Red-prove each clause by execution: mutation 1 reverts to `==` and must redden a `grep`/AST assertion that `compare_digest` appears on the comparison path (a timing test is not reliably red, so the gate must be structural, and it must name itself as such); mutation 2 makes `verify` return `True` unconditionally and must redden the differing-final-character case. Fail loudly: when `signature` is `None` or bytes, `verify` raises a named `TypeError("signature must be str")` rather than returning False, so "unparseable" is distinguishable from "wrong".

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: app/webhooks/signing.py — `new_signing_secret` (`random.choice(_ALPHABET)`)
What is wrong: `random` is a Mersenne Twister seeded from system entropy but fully reconstructible from ~624 observed outputs and not designed to resist prediction, and it is here generating the key that authenticates every outbound webhook; the constant name `SECRET_BYTES = 32` also lies, since it is used as a character count over a 62-symbol alphabet.
What breaks in production: an attacker who obtains their own endpoint's secret (they legitimately can — they register an endpoint) gains samples of the same global generator stream, and can predict other tenants' signing secrets and forge webhooks into their systems, an org-to-org compromise with no audit trail on our side.
Fix: use `secrets` — `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` — and rename nothing until the unit matches: keep `SECRET_BYTES = 32` only because `token_urlsafe` genuinely takes bytes, and delete the now-unused `_ALPHABET`/`random`/`string` imports. Preserve what made this useful: the `whsec_` prefix must stay, because the existing `test_new_signing_secret_has_prefix_and_length` and any customer-side prefix check depend on it. Pair deny with allow: assert (a) a freshly generated secret still starts with `SECRET_PREFIX` and is accepted end-to-end by `sign`/`verify`, and (b) 1000 generated secrets are all distinct. Note the existing length assertion `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` becomes false under `token_urlsafe` (which returns ~43 chars for 32 bytes) — update it to assert a minimum entropy-bearing length (`>= 40`), and do not "fix" it by shrinking the secret back to 32 characters, which would be repairing the test by weakening the key. Red-prove each clause by execution: mutation 1 replaces `secrets.token_urlsafe` with `"whsec_constant"` and must redden the distinctness assertion; mutation 2 drops the prefix and must redden (a). Fail loudly: no fallback to `random` if `secrets` is unavailable — let the import error propagate. Existing secrets minted by the old generator must be treated as compromised and rotated; add a `created_at`-based rotation query rather than silently leaving them in place.

### Critical: the deliveries endpoint has no tenancy check (IDOR), while its two sibling routes in the same file do
File: app/api/routes/settings.py — `list_deliveries` (`.filter(WebhookDelivery.endpoint_id == endpoint_id)`)
What is wrong: the query filters on the caller-supplied `endpoint_id` only and never joins to `WebhookEndpoint.org_id == user.org_id`, so authorization is missing on the one route in the diff that returns another tenant's data.
What breaks in production: any authenticated user enumerates `endpoint_id` and reads every other organization's delivery rows — and `WebhookDelivery.to_dict` exposes `event_type`, `status` and `response_status` for `invoice.paid`/`subscription.updated` events, i.e. a cross-tenant billing-activity feed with no rate limit in front of it.
Fix: scope the query through the endpoint — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the response does not confirm the existence of another org's endpoint id. Cross-cutting: this is the missed site of a pattern the diff already applies correctly twice — `list_api_keys` filters `ApiKey.org_id == user.org_id` and `list_webhook_endpoints` filters `WebhookEndpoint.org_id == user.org_id`; `list_deliveries` is the only new route that dropped it, and `docs/webhooks.md` already asserts the check exists ("for an endpoint belonging to your organization"), which is likely why nobody added it. Preserve what made this useful: an owner must still see their own deliveries — do not fix this by removing the route. Pair deny with allow: assert (a) org A's user gets 200 and the expected rows for its own endpoint, and (b) org B's user gets 404 for that same endpoint id AND receives a zero-length body, not a filtered-but-present list. Red-prove each clause by execution: mutation 1 removes the `org_id` predicate and must redden (b); mutation 2 removes the join entirely and must redden both. Fail loudly: when `user.org_id` is None the handler must 403, never fall through to an unscoped query. Boundary and tie: state that an endpoint owned by the caller's org but soft-deactivated (`active=False`) still returns its historical deliveries, and that a nonexistent id and a foreign id return the identical 404 shape.

### Critical: the list endpoint returns every endpoint's signing secret, contradicting the documented one-time-disclosure guarantee
File: app/webhooks/models.py — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`)
What is wrong: `to_dict()` embeds the raw signing secret, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` discloses every secret on every call — while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret is now returned to every principal with read access to settings, is cached by browsers and API gateways, and lands in access logs and client-side state, so the key that authenticates all outbound webhooks has the blast radius of a read-only listing endpoint — and the documented guarantee that a leaked secret can only come from the customer's own storage is false, which is exactly the claim an incident response would rely on.
Fix: remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` build its 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}`, so disclosure is opt-in at the single call site that is documented to disclose. Preserve what made this useful: creation must still return the secret exactly once — do not fix this by removing it from the create response too, which would leave customers unable to verify anything. Pair deny with allow: assert (a) the 201 body from `POST /webhook-endpoints` contains `signing_secret` and it round-trips through `signing.verify`, and (b) the 200 body from `GET /webhook-endpoints` contains no key whose name matches `secret` and no value starting with `SECRET_PREFIX` — assert on the serialized response text, not on a field list, so a rename does not reopen the hole. Red-prove each clause by execution: mutation 1 restores `signing_secret` in `to_dict()` and must redden (b); mutation 2 strips it from the create response and must redden (a). Fail loudly: if `to_dict()` is ever handed a model with an unexpected extra attribute the test helper must fail rather than skip the scan. Boundary and tie: state the disposition for an endpoint created before this change — its secret has been disclosed repeatedly and must be rotated, not merely hidden going forward.

### Critical: the migration's status CHECK constraint and the code's terminal status do not agree
File: migrations/0042_webhook_delivery.sql — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: the schema permits `'failed'` while `app/webhooks/models.py:STATUSES` and `app/webhooks/delivery.py:deliver` both write `'failed_permanent'`, so the exhaustion path writes a value the constraint rejects.
What breaks in production: every delivery that exhausts `MAX_ATTEMPTS` raises a check-constraint violation inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and because `_claim_batch` only selects `pending` the delivery is never retried and never appears as failed on the customer-facing deliveries page — a permanently invisible stuck row for every hard failure.

Preserve what made this useful: keep the CHECK constraint; do not fix this by dropping it, which would silently admit any status string. Red-prove each clause by execution: mutation 1 removes `'failed_permanent'` from the CHECK and must redden (a) naming that value in the failure output; mutation 2 drops the CHECK and must redden (b). Fail loudly: if the test cannot reach a real Postgres it must error with "constraint test requires a live database", never skip silently — a skipped constraint test is how this defect reached the diff. Boundary and tie: state that `STATUSES` is the single source and the migration is generated from it, and that adding a status requires a migration in the same PR.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `delivery.enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all sharing the same `event_id`, but the index permits exactly one row per `event_id` across the entire table.
What breaks in production: any organization with two or more active endpoints gets an `IntegrityError` on `session.add_all`, which `app/events/dispatcher.py` swallows into a `log.warning`, so those orgs receive zero webhooks with no error surfaced to them or to us — and because the index is global rather than per-org, a single org's event id colliding with another's would fail identically.
Fix: make the index `UNIQUE (endpoint_id, event_id)`, which expresses the actual invariant — at most one delivery of a given event to a given endpoint — and keep it unique, because that pair is what makes the documented "deduplicate on `event_id`" contract enforceable on our side rather than only on the customer's. Preserve what made this useful: do not fix this by dropping uniqueness, which would allow duplicate enqueues on a retried dispatch. Pair deny with allow: assert (a) enqueueing one event for an org with three active endpoints creates exactly three rows, and (b) enqueueing the same `event_id` twice for the same endpoint raises an integrity error rather than creating a fourth row. Red-prove each clause by execution: mutation 1 restores the single-column unique index and must redden (a) with a count of 1; mutation 2 drops uniqueness entirely and must redden (b). Fail loudly: `enqueue_for_event` must return the row count and the dispatcher must compare it against the number of matching endpoints, raising when they differ, so a partial fan-out is not spelled the same as a successful one. Boundary and tie: state the behaviour when an org has zero active endpoints — that is a legitimate zero, not a failure, and must not raise.

### Critical: `time.sleep` inside an async coroutine blocks the entire worker event loop
File: app/webhooks/delivery.py — `deliver` (`time.sleep(delay)`)
What is wrong: `deliver` is an `async def` scheduled by `asyncio.gather`, but its retry backoff uses the blocking `time.sleep`, which halts the event loop rather than yielding.
What breaks in production: one slow endpoint stalls all 100 deliveries in the batch — the full backoff ladder is 2+4+8+16 = 30 seconds of dead loop per failing delivery, so a batch with ten failing endpoints freezes the worker for five minutes, during which no other delivery, no lock refresh, and no health check can run, and the 60-second Redis lock silently expires under it.
Fix: replace with `await asyncio.sleep(delay)`; `asyncio` is already imported in this module. Preserve what made this useful: the backoff ladder itself is correct and must stay — do not fix the stall by shortening or removing the delays, which would turn a blocked loop into a retry storm against the customer's endpoint. Pair deny with allow: assert (a) two concurrent `deliver` calls where the first backs off 2s complete in under ~2.5s wall-clock total, proving they interleaved, and (b) a single delivery that succeeds on its first attempt still returns without sleeping at all. Red-prove each clause by execution: mutation 1 restores `time.sleep` and must redden (a) by roughly doubling the elapsed time — assert on a measured lower bound of concurrency (both coroutines observed mid-flight), not on wall-clock alone, so the test cannot pass on a fast machine for the wrong reason; mutation 2 inserts an unconditional sleep before the first attempt and must redden (b). Fail loudly: if the delay computation yields a non-finite or negative value, raise rather than sleeping zero. Boundary and tie: state that `attempt == MAX_ATTEMPTS` takes the terminal branch and never sleeps, so the last failure is not followed by a pointless 32-second wait.

### Critical: the dispatch lock is a non-atomic check-then-set with a TTL shorter than the work it guards
File: app/webhooks/delivery.py — `_acquire_lock` (`if await redis_client.get(LOCK_KEY): return False` / `set` / `expire`)
What is wrong: the read and the write are separate round-trips, so two workers can both observe an empty key and both "acquire"; the `set` and the `expire` are also separate, so a crash between them leaves a lock with no expiry; and the 60-second TTL is far shorter than a batch's worst case (100 deliveries × up to 5 attempts × a 30-second request timeout plus 30 seconds of backoff).
What breaks in production: the lock provides no mutual exclusion at all under the exact condition it exists for — two or more workers running — so the same delivery rows are claimed and POSTed concurrently, customers receive duplicate `invoice.paid` webhooks, and `_finish` races itself on `attempts`; separately, a crash between `set` and `expire` wedges the whole webhook pipeline permanently with no automatic recovery.
Fix: make acquisition a single atomic operation with the TTL inline — `acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` is unique per worker — and make release conditional on ownership via a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`), so a worker whose lock already expired cannot delete a successor's lock; the current unconditional `await redis_client.delete(LOCK_KEY)` in `run_worker`'s `finally` has exactly that bug. Set `LOCK_TTL_SECONDS` from measured worst-case batch duration and renew it from a background task while the batch runs, rather than picking 60 by inspection. Preserve what made this useful: single-flight dispatch is the point — do not fix this by removing the lock and relying on the DB `status` transition alone, since `_claim_batch` is itself not atomic (see below). Pair deny with allow: assert (a) two concurrent `_acquire_lock` calls yield exactly one `True` — a positive cardinality assertion, `sum(results) == 1`, not merely "not both True" — and (b) after the holder releases, a third call succeeds, so the lock is not a one-shot. Red-prove each clause by execution: mutation 1 restores the get-then-set pair and must redden (a) under a fake Redis that interleaves the two calls; mutation 2 makes release unconditional and must redden a third assertion that a stale holder's release leaves the successor's token intact. The concurrency test must fail if fewer than two acquisition attempts actually ran, so a serialized fake cannot pass it vacuously. Fail loudly: if Redis is unreachable, `_acquire_lock` must raise rather than return `False` — a `False` return is indistinguishable from "someone else holds it" and would silently park every worker forever.

### Critical: `_claim_batch` returns detached ORM instances and its claim is not atomic
File: app/webhooks/delivery.py — `_claim_batch` (`return rows` inside `with session_scope() as session:`)
What is wrong: the rows are returned after the `session_scope` context exits, so with SQLAlchemy's default `expire_on_commit=True` every attribute access in `deliver` (`delivery.attempts`, `delivery.payload`, `delivery.endpoint_id`, `delivery.id`) triggers a refresh on a closed session; separately, the SELECT and the `status = "in_flight"` write are not `SELECT ... FOR UPDATE SKIP LOCKED`, so two workers that both hold the (broken) lock claim the same rows.
What breaks in production: the worker raises `DetachedInstanceError` on the first delivery of every batch, and because `asyncio.gather` is called without `return_exceptions=True` the exception propagates out of the `try`, the `finally` releases the lock, and `if not batch` then raises `NameError` if `_claim_batch` itself failed — so the worker crashes on its first iteration and no webhook is ever delivered.
Fix: detach deliberately by materializing plain data before the session closes — build a frozen dataclass (`ClaimedDelivery(id, endpoint_id, payload, attempts)`) inside the session and return that, so `deliver` cannot touch a live ORM attribute; and make the claim atomic with `.with_for_update(skip_locked=True)` on the query, updating `status` in the same transaction. Also pass `return_exceptions=True` to `asyncio.gather` and log each exception against its delivery id, and initialize `batch = []` before the `try` so the `if not batch` check cannot raise `NameError`. Preserve what made this useful: batching must stay — do not fix this by processing one row per transaction and dropping `BATCH_SIZE`, which would multiply the round-trips this design exists to avoid. Pair deny with allow: assert (a) a claimed batch's fields are readable after the session closes and the deliveries are POSTed, and (b) two concurrent `_claim_batch` calls against the same pending rows return disjoint sets whose union is the full pending set — assert `len(a) + len(b) == total` and `set(a) & set(b) == set()`, both positive cardinality assertions, and fail the test if either call returned zero rows so a serialized run cannot pass it vacuously. Red-prove each clause by execution: mutation 1 returns the ORM rows again and must redden (a) with `DetachedInstanceError` named in the output; mutation 2 removes `skip_locked` and must redden the disjointness assertion. Fail loudly: a row whose `endpoint` no longer exists must route to an explicit `failed_permanent` with a named reason, not to the current `session.get` returning `None` and `send_once` raising `AttributeError` — `_finish` has the same unchecked-`None` bug on `session.get(m.WebhookDelivery, delivery_id)`. Boundary and tie: state that a row with `next_attempt_at` exactly equal to `now` is claimed (the code's `<=` is correct — keep it), and that ties on `next_attempt_at` are broken by `id` (see the ordering finding).

### Critical: any user can register an internal-network URL, and the worker follows redirects to it (SSRF)
File: app/api/routes/settings.py — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`)
What is wrong: the only destination check is that the scheme string begins with `http` and a netloc exists, so `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/`, and any RFC1918 address are all accepted — and `run_worker` builds its client with `follow_redirects=True`, so even a validated public host can 302 the request to an internal one after the check has passed.
What breaks in production: an authenticated tenant turns our delivery worker into a request proxy inside our own network, POSTing attacker-chosen JSON to cloud metadata endpoints and unauthenticated internal services and reading the response body back out through `GET /webhook-endpoints/{id}/deliveries`, since `_finish` stores `response.text` in `response_body`.
Fix: validate against an allowlist of schemes and a denylist of resolved addresses at registration AND at each request. At registration: require `parsed.scheme == "https"` exactly (`startswith("http")` also admits `http+unix` and `httpx`, and `docs/webhooks.md` already promises "Only `https://` URLs are accepted", so the code is the thing that is wrong here), reject a URL with credentials or a non-default port outside {443}, resolve the host and reject any address in a private, loopback, link-local, or reserved range via `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`. At request time: set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a permanent failure with a named reason, which closes the DNS-rebinding and redirect-after-check gap that registration-time validation structurally cannot. Also stop storing the response body verbatim — cap `response_body` at a few hundred characters. Preserve what made this useful: legitimate public HTTPS endpoints on non-standard ports may be a real customer need; if so, allowlist the port explicitly rather than dropping the port check. Pair deny with allow: assert (a) `https://hooks.example.com/acme` registers and delivers successfully, and (b) each of `http://hooks.example.com`, `https://169.254.169.254/`, `https://localhost/`, and a public host that 302s to `http://127.0.0.1/` are each rejected — the last one at delivery time with the delivery marked failed and no request issued to the internal address. Red-prove each clause by execution: mutation 1 restores `startswith("http")` and must redden the plain-`http` case; mutation 2 restores `follow_redirects=True` and must redden the 302 case specifically, asserting the internal host received zero requests, not merely that the delivery failed; mutation 3 removes the private-range check and must redden the metadata-IP case. Fail loudly: if DNS resolution fails or times out, registration must reject with "could not resolve host", never fall through to accepting the URL. Boundary and tie: state the disposition for a host resolving to both a public and a private address (reject — any private answer denies) and for IPv6-mapped IPv4 (`::ffff:127.0.0.1` must be normalized before the range check, or it bypasses it).

### Critical: no test recomputes the HMAC over the bytes actually sent, so the signature primitive is never verified end to end (RT5)
File: tests/webhooks/test_delivery.py — `test_send_once_posts_the_signed_payload`
What is wrong: the test captures the real request but asserts only that the signature header `startswith("sha256=")` and that the timestamp `isdigit()`, never running `captured["body"]` back through `signing.verify` — so the production signing primitive's actual guarantee is untested, and `test_verify_accepts_signature_produced_by_sign` cannot cover it either because `verify` internally calls `sign`, making that assertion an identity that holds for any implementation of `sign`, including one that returns a constant.

What is wrong: `tests/webhooks/test_delivery.py` covers only `signing.*`, `backoff_for`, `MAX_ATTEMPTS`, and `send_once`; the retry loop, the enqueue fan-out, the worker loop, both serializers, and every HTTP route are untested — and several of the Critical findings above (the status-enum mismatch, the unique-index collision, the detached instances, the missing tenancy filter, the secret in `to_dict`) are each detectable by a single test of one of these symbols.
What breaks in production: the whole feature ships on the strength of a suite that exercises the one function that has no database and no branching, so a green CI run carries essentially no information about whether webhooks work.
Fix: add tests in this PR for each listed symbol, with the deny/allow pairs and mutations already specified in the findings above; where a symbol's test genuinely cannot land in this PR, record an Anti-Deferral entry naming worst case, likelihood, and cost-to-fix for that symbol specifically rather than deferring the set as a whole. Preserve what made this useful: the existing signing tests are fine and stay. Pair deny with allow: for each route, at least one success case and one rejection case, with the rejection asserting the guarded mutation did not occur (row count unchanged), not merely the status code. Red-prove by execution: each added test must be shown red against a single mutation of the symbol it covers, one mutation per test, run and observed — not one mutation that reddens the suite. Fail loudly: the route tests must assert the app under test actually mounted the new router; a 404 from an unmounted route would otherwise satisfy several rejection assertions for entirely the wrong reason.

### Minor: `verify` is dead code within this change, and its signature will not survive the timestamp fix
File: app/webhooks/signing.py — `verify`
What is wrong: nothing in the production diff calls `verify` — it exists as a reference implementation for customers and is exercised only by tests, yet it is exported from a production module without a docstring saying so.
What breaks in production: nothing directly, but its being untethered is why its `==` comparison and its missing timestamp argument went unnoticed; a customer copying it inherits both defects.
Fix (advisory): keep it, state in its docstring that it is the customer-facing reference implementation, and make it the function the round-trip test in the RT5 finding calls — that gives it a production-shaped caller and makes future drift visible.

### Minor: `ON DELETE CASCADE` on `webhook_deliveries.endpoint_id` destroys the delivery audit trail
File: migrations/0042_webhook_delivery.sql — `endpoint_id BIGINT NOT NULL REFERENCES webhook_endpoints (id) ON DELETE CASCADE`
What is wrong: deleting an endpoint silently deletes every delivery record for it, including the failure history a customer or a support engineer would consult afterwards.
What breaks in production: a customer who deletes and re-creates an endpoint while debugging loses exactly the evidence they were debugging with, and we lose it too.
Fix (advisory): the `active` flag already exists on `WebhookEndpoint` and appears intended for soft deactivation — if endpoint removal is meant to be soft, no delete route should exist and the cascade is harmless; if a hard delete is planned, change to `ON DELETE RESTRICT` and require deactivation first. This depends on a delete route the change does not contain, so it is a question: is endpoint deletion soft or hard? A soft-delete-only answer closes it.

### Minor: `WebhookEndpoint.to_dict` omits `created_at` while `WebhookDelivery.to_dict` includes its timestamp
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`
What is wrong: the two serializers in the same new file disagree about whether creation time is part of the public shape, and the endpoint one omits it.
What breaks in production: the endpoints listing gives a customer no way to tell which of several similar endpoints they registered when, which is the first thing needed when reconciling a misconfigured integration.
Fix (advisory): add `"created_at": self.created_at.isoformat()` to `WebhookEndpoint.to_dict`, guarding for `None` since the column has a Python-side default but no server default and is nullable in the model.
