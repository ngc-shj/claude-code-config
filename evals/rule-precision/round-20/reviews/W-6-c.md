### Critical: endpoint URL validation admits internal targets, and the delivery client follows redirects into them
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, the `if not parsed.scheme.startswith("http") or not parsed.netloc` guard; `app/webhooks/delivery.py` — `run_worker`, `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check on a customer-supplied URL is a scheme prefix and a non-empty netloc, which I confirmed by execution accepts `http://169.254.169.254/latest/meta-data/`, `http://localhost:8000/x`, `http://[::1]/x` and even `httpfoo://evil`, and `follow_redirects=True` means an endpoint that passes any stricter future check can still redirect the POST to those targets.
What breaks in production: Any authenticated tenant turns the delivery worker into a server-side request forgery agent that POSTs another org's invoice payloads at cloud metadata and internal-only services from inside the trust boundary, with `response_status` returned by `GET /webhook-endpoints/{id}/deliveries` acting as an internal port-scan oracle and `_finish` persisting the internal response body into `webhook_deliveries.response_body`.
Fix: Replace the prefix test with an exact allowlist `parsed.scheme == "https"` (which is what `docs/webhooks.md` already promises), require `parsed.hostname` to be present, resolve it and reject when any resolved address `ipaddress.ip_address(a)` is `is_private`, `is_loopback`, `is_link_local`, `is_reserved` or `is_unspecified`, reject a non-default port outside `{443}` unless an operator allowlist says otherwise, and set `follow_redirects=False` on the client in `run_worker` so a 3xx is recorded as a delivery failure instead of being chased; re-resolve and re-check the address at send time in `send_once` rather than trusting the registration-time result, because DNS rebinding makes the registration-time answer stale (this is the R51 name-vs-object interval). Preserve the allow side explicitly: `https://hooks.example.com/acme` — the URL the docs and `FakeEndpoint` both use — must still register with 201 and must still deliver, and a public address that merely happens to be IPv6 must still be accepted, so the predicate is "private/loopback/link-local/reserved", never "not IPv4". Red-prove each clause by execution as a separate mutation: (i) revert the scheme check to `startswith` and watch the `http://` case flip from 422 to 201; (ii) drop the address classification and watch `https://` DNS pointing at `127.0.0.1` flip from 422 to 201; (iii) set `follow_redirects=True` again and watch a `MockTransport` returning `302 -> http://169.254.169.254/` flip from a recorded failure to a delivered internal fetch — three mutations reddening three different assertions. Fail loudly when the check cannot run: DNS resolution failure, an unparseable host, or an `ip_address` conversion error must reject with 422 naming the reason, never fall through to accept — "could not evaluate" must not be spelled the same as "evaluated and clean". The fix must not be to delete the deliveries listing or the `response_status` field; the feature those serve is real, so keep them and close the request path instead. Boundary and tie: `127.0.0.0/8`, `169.254.0.0/16`, `::1` and `fc00::/7` are on the reject side inclusive of their first and last addresses; a hostname resolving to both a public and a private address is rejected, not accepted on the strength of the public one.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters on a caller-supplied `endpoint_id` alone and never joins to `WebhookEndpoint.org_id == user.org_id`, even though `list_webhook_endpoints` two functions above in the same file already establishes the org-scoping predicate this route needed.
What breaks in production: Any authenticated user enumerates integer `endpoint_id` values and reads every other tenant's delivery rows, and since `to_dict` returns `event_type`, `status` and `response_status` per row, this is a cross-tenant disclosure of billing event activity from a route that requires only a valid session.
Fix: Join the delivery query to `WebhookEndpoint` and filter `WebhookEndpoint.org_id == user.org_id` in the same statement, and return 404 (not 403) when the join yields nothing so the route does not confirm that a foreign `endpoint_id` exists; reuse the same predicate `list_webhook_endpoints` uses rather than writing a second one, so there is one org-scoping expression in the file. Pair the deny side with the allow side: a test where the endpoint belongs to the caller's org must still return the caller's deliveries with the same body it returns today — a fix that 404s unconditionally satisfies the deny assertion and destroys the feature. Red-prove each clause separately by execution: (i) delete the `org_id` filter and watch the foreign-org test flip from 404 to 200 with rows; (ii) change the miss response from 404 to 403 and watch the existence-disclosure assertion redden; the same-org allow test must stay green under both mutations, which is what proves the two clauses are independent. Fail loudly when the check cannot run: if `user.org_id` is `None` or absent, deny with 403 rather than letting `org_id == None` become a SQL `IS NULL` predicate that silently matches nothing or, worse, matches rows with a null owner. Do not fix by removing the deliveries route — the docs advertise it and it is the only inspection surface customers have. Boundary and tie: an endpoint whose row was soft-deleted or deactivated still belongs to its org and stays visible to that org; an endpoint id that exists but belongs to no org is on the deny side.

### Critical: the signed bytes are not the bytes on the wire, and the timestamp is not covered by the signature
File: `app/webhooks/signing.py` — `sign`/`serialize`; `app/webhooks/delivery.py` — `send_once`, `client.post(endpoint.url, json=delivery.payload, headers=headers)`
What is wrong: `sign` computes the HMAC over `json.dumps(payload, sort_keys=True)` while `send_once` hands the dict to httpx's `json=`, which serializes with its own `json.dumps` call that does not pass `sort_keys` — I confirmed by execution that the same three-key payload yields `{"a": 1, "amount_cents": 4200, "b": 2}` signed versus a non-sorted dump on the wire — and the `X-Acme-Timestamp` value is never fed into the MAC at all, though `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`.
What breaks in production: Every customer who implements the documented verification recomputes the MAC over the raw body they received and gets a mismatch, so the integration fails 100% of the time on the first event rather than degrading, and the documented five-minute replay window is unenforceable because an attacker can replay a captured body under any `X-Acme-Timestamp` and the unchanged signature still verifies.
Fix: Serialize once and send exactly those bytes — build `body = serialize(delivery.payload).encode()` in `send_once`, sign `f"{timestamp}.{body.decode()}"` as the docs specify, and POST with `content=body` plus an explicit `Content-Type: application/json` header instead of `json=`, so no second serializer sits between the MAC and the socket; change `sign` to take the already-serialized body rather than the dict, which structurally removes the possibility of a re-serialization drifting from the signed form. Pair deny with allow: the round-trip that must still SUCCEED is `verify(secret, captured_raw_body, captured_timestamp, captured_signature)` over the bytes an actual `httpx.MockTransport` handler received — per R40 this must be actual producer output through the actual consumer, not two independently constructed strings — and per RT1(d) the expected digest in at least one test is written independently with `hmac.new(...).hexdigest()` over a literal body, not obtained by calling `sign` again. Red-prove each clause separately by execution: (i) restore `sort_keys=True` on the signing side only and watch the byte-equality assertion redden; (ii) drop the `f"{timestamp}."` prefix and watch a distinct replay assertion — same body, timestamp advanced six minutes, signature unchanged — flip from reject to accept; (iii) mutate a single payload byte and watch the verification assertion redden; three mutations, three different assertions. Fail loudly when the check cannot run: a payload that is not JSON-serializable must raise at `serialize` and route to `_finish(..., "failed_permanent", ...)` with the reason named, never send an unsigned or partially signed request. Do not fix by relaxing the docs to match the code — the timestamp binding is the replay control, and deleting the claim deletes the control. Boundary and tie: the receiver's window is `abs(now - timestamp) <= 300` seconds with exactly 300 accepted, and two events signed within the same clock second are distinguished by `event_id`, not by the timestamp.

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all carrying the same `event_id`, so the unique index rejects the whole `add_all` the moment an org has two subscribed endpoints — the index expresses a one-row-per-event assumption the producing code contradicts in the same change.
What breaks in production: Any org with a second endpoint gets an `IntegrityError` that the dispatcher's blanket `except Exception: log.warning` swallows, so every webhook for that org is dropped permanently and silently, with only a warning line to show for it and no dead-letter row.
Fix: Change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the actual idempotency key the fan-out implies and which also gives the retry path an upsert target; keep it UNIQUE rather than dropping it, because `docs/webhooks.md` tells customers to deduplicate on `event_id` and a non-unique index would let a re-run of `enqueue_for_event` double-deliver. Pair deny with allow: the case that must still be REJECTED is a second insert of the same `(endpoint_id, event_id)` pair — re-running `enqueue_for_event` for one event must not create a second row for the same endpoint — and the case that must now SUCCEED is one event fanned out to two endpoints of the same org yielding exactly two rows. Red-prove by execution, one mutation per clause: (i) revert the index to `(event_id)` and watch the two-endpoint test redden with an IntegrityError; (ii) drop UNIQUE entirely and watch the re-enqueue test flip from one row to two. Fail loudly when the check cannot run: replace the dispatcher's `except Exception: log.warning` with a handler that re-raises or writes a dead-letter row, so an insert that cannot be evaluated is not spelled the same as an event with no subscribers. Do not fix by removing the per-endpoint fan-out — multiple endpoints per org is the feature. Boundary and tie: an event with zero matching endpoints inserts zero rows and is not an error; an endpoint deleted between enqueue and delivery takes its rows with it via the existing `ON DELETE CASCADE`.

### Critical: the status CHECK constraint rejects the terminal status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` versus `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` `STATUSES`
What is wrong: Three independent declarations of the same status enum disagree — the migration allows `'failed'`, `models.STATUSES` declares `"failed_permanent"`, and `delivery.py` writes `"failed_permanent"` — so the terminal-failure write is the one value the database refuses.
What breaks in production: The first delivery to exhaust `MAX_ATTEMPTS` raises a constraint violation inside `_finish`, the row stays `in_flight` forever with no reaper to reclaim it, and because `_finish` is also the only writer of `attempts` and `response_status` the failure is invisible in the deliveries API.
Fix: Make one declaration authoritative and derive the others from it — keep `models.STATUSES` as the source, change the migration's CHECK to `status IN ('pending','in_flight','delivered','failed_permanent')`, and add a test that asserts the CHECK's member set equals `set(models.STATUSES)` by reading `pg_constraint` (or the migration text) so the two cannot drift again; note this is an R42 class-membership fix, so derive the set from `STATUSES` rather than transcribing four literals a third time. Pair deny with allow: an INSERT of `'failed_permanent'` must now SUCCEED, and an INSERT of `'bogus'` must still be REJECTED — a fix that simply drops the CHECK satisfies the first and abandons the second. Red-prove each separately by execution: (i) revert the CHECK to the old four values and watch the permanent-failure integration test redden with an IntegrityError; (ii) drop the CHECK entirely and watch the `'bogus'` rejection test redden; (iii) append a fifth value to `STATUSES` without touching the migration and watch the set-equality test redden. Fail loudly when the check cannot run: if the sync test cannot read the constraint (no database, introspection unavailable) it must error and name that, not skip — a skipped drift test reports green from having examined nothing. Do not fix by widening the column to unconstrained TEXT; the CHECK is what makes `'failed'`-versus-`'failed_permanent'` a build failure instead of a production one. Boundary and tie: `attempts == MAX_ATTEMPTS` is the terminal case (the code's `attempt >= MAX_ATTEMPTS` already treats the fifth attempt as the last), and a row already `delivered` is never re-transitioned by a late `_finish`.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: The secret is drawn from `random`, the Mersenne Twister generator, whose internal state is recoverable from a few hundred observed outputs — the standard library already provides the correct primitive in `secrets`, so this is a security control reimplemented against a weaker helper (R1, Critical because the duplicated behaviour is itself the control).
What breaks in production: A tenant who registers endpoints repeatedly harvests enough generator output to reconstruct the PRNG state and then predicts other tenants' signing secrets, which lets them forge `X-Acme-Signature` on events delivered to those tenants' endpoints — the signature stops being an authenticity control for everyone, not just for the attacker's own org.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and drop the `random`, `string` and `_ALPHABET` definitions outright rather than leaving them as an unreferenced fallback (R1 clause d); note per R1 clause (b) that this is a behaviour change at the call site — the alphabet becomes URL-safe base64 and the string length becomes ~43 rather than 32 characters for `SECRET_BYTES = 32`, so `test_new_signing_secret_has_prefix_and_length` must be updated to assert an entropy floor (`len(secret) >= len(SECRET_PREFIX) + 32`) instead of an exact length, and any stored-secret column width must be re-checked. Pair deny with allow: existing secrets already issued under the old scheme must still verify, so the change is generation-only and `sign`/`verify` must remain byte-compatible with a `whsec_`-prefixed secret of either alphabet — a fix that rejects legacy secrets breaks every live integration. Red-prove each clause by execution: (i) re-point the function at `random.choice` and watch a test asserting `secrets` is the source (monkeypatch `secrets.token_urlsafe` to a sentinel and assert it appears in the output) redden; (ii) shorten `SECRET_BYTES` to 4 and watch the entropy-floor assertion redden — the current length-equality assertion cannot fail for either mutation, which is exactly why it did not catch this (RT7). Fail loudly when the check cannot run: `secrets` is stdlib and cannot be absent, but if a future config makes `SECRET_BYTES` non-integer the call must raise at import rather than fall back to a default length. Do not fix by keeping `random` and merely lengthening the string — length is not the defect, predictability is. Boundary and tie: `SECRET_BYTES = 32` is the minimum, not the target; two secrets generated in the same microsecond must be independent, which a seeded PRNG does not guarantee and a CSPRNG does.

### Critical: `time.sleep` blocks the event loop inside an async retry loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)` at the end of the `while True` body
What is wrong: A synchronous `time.sleep` inside an `async def` blocks the entire event loop rather than yielding, and it is reached from `asyncio.gather` over a batch of up to `BATCH_SIZE = 100` deliveries.
What breaks in production: One customer endpoint that is down freezes the whole worker process for the full backoff ladder — 2+4+8+16 = 30 seconds per delivery, and with a batch of failing deliveries the loop is blocked for minutes — so every other delivery, every timer, and anything else sharing that loop stalls, and because `LOCK_KEY` expires after 60 seconds a second worker starts claiming while the first is still frozen mid-batch, producing duplicate deliveries.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (`asyncio` is already imported in this module), and move the retry out of the in-process loop entirely: on a retryable failure, write `status="pending"`, `attempts=attempt`, `next_attempt_at=datetime.now(timezone.utc) + backoff_for(attempt)` and return, letting the existing `_claim_batch` scheduler pick the row up — this is what `next_attempt_at` and `backoff_for` were built for and the in-process `while True` currently makes both dead weight. Pair deny with allow: the case that must still SUCCEED is a first-attempt 2xx completing without any sleep at all, and a delivery whose second attempt succeeds must still reach `status="delivered"` with `attempts == 2` — a fix that returns after one attempt satisfies "never blocks" and deletes the retry feature. Red-prove each clause separately by execution: (i) restore `time.sleep` and assert, from a concurrently scheduled `asyncio.sleep(0)` task, that it was not serviced during the backoff — the assertion reddens on the blocking form and passes on the awaiting one; (ii) remove the `next_attempt_at` write and watch the reschedule test redden because the row never becomes due again; (iii) remove the `attempts` write and watch a test that a failing delivery stops after exactly `MAX_ATTEMPTS` total attempts redden by looping forever, so bound that test with a timeout rather than letting it hang. Fail loudly when the check cannot run: if the reschedule write fails, `_finish` must record a terminal status rather than returning silently and leaving the row `in_flight`. Do not fix by shrinking `BATCH_SIZE` or `MAX_ATTEMPTS` — that narrows the window without removing the blocking call. Boundary and tie: `attempt >= MAX_ATTEMPTS` is terminal on the fifth attempt inclusive, and two rows with an identical `next_attempt_at` are both eligible in the same claim rather than one starving.

### Critical: the signature test asserts the header's prefix, never that the signature verifies against the body sent
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test captures both `request.headers` and `request.content` but asserts only `startswith("sha256=")` on the signature and `isdigit()` on the timestamp, so it never recomputes the MAC over `captured["body"]` — the one assertion that would have caught the `sort_keys` divergence and the unsigned timestamp reported above (RT1(d) and RT1(g): no independently written expected value, and no comparison at the serialization boundary the caller sees).
What breaks in production: The signature verification path ships fully green while producing signatures no customer can verify, which is precisely RT5's worse-than-vacuous case — a reviewer reads a passing test named "posts the signed payload" and concludes signing works.
Fix: Add to that test `expected = "sha256=" + hmac.new(SECRET.encode(), f'{captured["headers"][signing.TIMESTAMP_HEADER]}.{captured["body"].decode()}'.encode(), hashlib.sha256).hexdigest()` written inline against the documented construction rather than by calling `signing.sign`, and assert `hmac.compare_digest(captured["headers"][signing.SIGNATURE_HEADER], expected)`; additionally bind `FakeEndpoint`/`FakeDelivery` to the real `WebhookEndpoint`/`WebhookDelivery` types (construct unsaved ORM instances) so a field `send_once` later needs cannot be silently absent from the stub (RT1(a)). Pair deny with allow: keep a passing case with the correct secret, and add the deny case — the same captured body verified against `"whsec_someoneelse"` must fail — because an assertion that only ever sees the matching secret cannot distinguish a real HMAC from a constant. Red-prove each clause separately by execution: (i) add `sort_keys=True` back on one side and watch the new byte-level assertion redden while the old prefix assertion stays green, which is the proof the old assertion was decorative; (ii) drop the timestamp from the signed string and watch the expected-digest assertion redden; (iii) make `sign` return a fixed digest and watch the wrong-secret deny case redden. Fail loudly when the check cannot run: if `captured` is empty because the handler was never invoked, the test must fail on an explicit assertion that the handler ran, not pass through a `KeyError`-free path. Do not fix by deleting the existing prefix and content-type assertions — they are cheap and still catch header-shape regressions. Boundary and tie: an empty payload `{}` must still produce a verifiable signature, and two payloads differing only in key order must produce the same signature only if the wire bytes are also identical.

### Major: `verify` compares signatures with `==` instead of a constant-time primitive
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The signature comparison uses Python's `==`, which short-circuits on the first differing byte, while `hmac.compare_digest` — the stdlib primitive for exactly this — is unused, and `docs/webhooks.md` in the same change instructs integrators to "compare it against your own computation using a constant-time comparison" (RS1; graded Major rather than Critical because the change contains no production call site for `verify`, so today the exposure is to whoever adopts it, including the inbound path this function is evidently staged for).
What breaks in production: The moment `verify` is wired to an inbound endpoint, an attacker measures response-time differences to recover the expected digest byte by byte and forges a valid signature without ever knowing the secret.
Fix: Return `hmac.compare_digest(expected, signature)`, and take the signature as `str` guarded by an explicit type check so a non-string (a dict from a JSON body, per RS3's off-type sink analysis) raises rather than reaching the comparison; update the signature to accept the raw body and timestamp per the R40 fix above so `verify` and `sign` share one construction. Pair deny with allow: `test_verify_accepts_signature_produced_by_sign` must stay green (a correct signature still authenticates) alongside the existing wrong-secret deny case — a fix that returns `False` unconditionally passes every deny test in the file. Red-prove each clause separately by execution: (i) swap `compare_digest` back to `==` and watch a test that asserts `signing.verify.__code__.co_names` contains `compare_digest`, or that monkeypatching `hmac.compare_digest` to a sentinel changes the result, redden; (ii) pass a non-`str` signature and watch the type-check assertion redden. Note that the existing `test_verify_accepts_signature_produced_by_sign` cannot red-prove any of this on its own: it calls `sign` to build the input and `verify` recomputes with `sign`, so it compares two outputs of the same subject and passes even if `serialize` returns `""` (RT1(c)) — replace its expected value with an independently computed digest. Fail loudly when the check cannot run: a `None` or empty-string signature must return `False` explicitly, not raise an unhandled `TypeError` inside `compare_digest` that a caller's broad `except` turns into an accept. Do not fix by deleting `verify` — the docs describe the verification contract and this is the reference implementation of it. Boundary and tie: signatures of unequal length must return `False` without leaking the length through timing, which is what `compare_digest` provides and `==` does not.

### Major: the signing secret is returned on every endpoint listing, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry; consumed by `app/api/routes/settings.py` `list_webhook_endpoints`
What is wrong: One `to_dict` serves both `create_webhook_endpoint` (where returning the secret is intended) and `list_webhook_endpoints` (where it is not), so `GET /v1/settings/webhook-endpoints` hands the secret back on every call while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards" (R25 access-scope, RS4, and R49: the doc claims a control the code does not implement).
What breaks in production: The secret is copied into every client-side cache, browser history entry, proxy log and API-response log that touches the list route, so a read-only credential scoped to settings becomes sufficient to forge signed webhooks, and the incident-response assumption "the secret was disclosed exactly once" is false.
Fix: Remove `signing_secret` from `to_dict` and have `create_webhook_endpoint` build its 201 body as `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the one call site that is entitled to it, so disclosure is opt-in per route rather than default-on in the shared serializer; add a rotation route if read-back was the reason it was there, since the docs already tell customers the value is unrecoverable. Pair deny with allow: the create response must STILL contain the secret (a fix that strips it everywhere breaks onboarding and is the likely lazy outcome), while the list response must not. Red-prove each clause separately by execution: (i) re-add `signing_secret` to `to_dict` and watch an assertion that `"signing_secret" not in list_response[0]` redden; (ii) remove the explicit merge in `create_webhook_endpoint` and watch the assertion that the 201 body contains a `whsec_`-prefixed secret redden — two mutations, two different assertions. Fail loudly when the check cannot run: if the create path cannot read the secret back off the flushed instance it must 500 rather than return a 201 with the field absent, because a client that stores an empty secret fails verification later with no diagnosis. Do not fix by redacting the secret to `"whsec_***"` in the list response — a partial prefix is still a disclosure and it makes the field look present. Boundary and tie: rotation issues a new secret and the old one stops verifying at a named cutover instant; where both are momentarily valid, say which side of that instant an event signed at exactly the cutover falls on.

### Major: the outbound request's signature and timestamp headers are written to the application log
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: The whole header dict is logged at INFO, which includes the freshly computed `X-Acme-Signature` and `X-Acme-Timestamp` for every delivery (RS4: logs are one of the committed-artifact classes the rule names, and a valid signature is exploitable material rather than merely identifying material).
What breaks in production: Anyone with log-read access — a wider set than anyone with database access — replays the exact signed payload to the customer's endpoint indefinitely, and once the timestamp is properly bound into the MAC per the R40 fix the logged pair is a complete, self-contained replay token.
Fix: Log the URL, the delivery id and the header NAMES only — `log.info("POST %s delivery=%s headers=%s", endpoint.url, delivery.id, sorted(headers))` — and if the signature value is needed for support, log a truncated SHA-256 of it rather than the value. Pair deny with allow: the diagnostic value that must be PRESERVED is the ability to correlate a log line to a delivery row and see which headers were sent, so the fix keeps the line and narrows its content rather than deleting the line — deleting it is the R36-shaped non-fix. Red-prove each clause separately by execution: (i) restore the full-dict log and watch an assertion that no emitted record contains the signature value (capture with `caplog`) redden; (ii) drop the delivery id from the format string and watch the correlation assertion redden. Fail loudly when the check cannot run: if `sign` raised and the headers are incomplete, log an explicit failure rather than a line that looks like a normal send. Boundary and tie: an empty header dict logs as an empty list, not as a missing field, so "no headers" and "logging suppressed" are distinguishable.

### Major: `in_flight` has no exit on the failure path and one bad delivery kills the worker
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `deliver` (only `httpx.HTTPError` is caught), `run_worker` (`await asyncio.gather(...)` with no `return_exceptions`)
What is wrong: `_claim_batch` moves rows into `in_flight` and only `_finish` moves them out, but `deliver` catches just `httpx.HTTPError` — a `ValueError` from serialization, a database error inside `_finish`, an ORM error, or a process restart leaves the row `in_flight` forever, and no query anywhere selects `in_flight`, so nothing reclaims it (R38 mode 1: a transient state entered unconditionally and exited only on the success path, with no timeout).
What breaks in production: Billing events stop being delivered with no error surface — the delivery row is neither pending nor delivered nor failed — and because `asyncio.gather` without `return_exceptions=True` propagates the first exception out through `run_worker`'s `while True`, one malformed delivery terminates the worker process and strands the entire claimed batch in `in_flight` at once.
Fix: Give `in_flight` a bounded exit: stamp `updated_at` when claiming, and have `_claim_batch` also reclaim rows where `status == "in_flight" AND updated_at < now - lease_interval` back to `pending`; wrap the body of `deliver` in `try/except Exception` that routes any unexpected exception to `_finish(..., "failed_permanent", ...)` with the exception text so the row always reaches a terminal state; and pass `return_exceptions=True` to `asyncio.gather` so a single failure cannot unwind the worker loop. ### Major: the dispatch lock is acquired non-atomically and expires before a batch can finish
