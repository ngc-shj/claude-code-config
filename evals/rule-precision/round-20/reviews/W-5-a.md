### Critical: the HMAC is computed over bytes that are never sent on the wire
File: app/webhooks/signing.py — `sign` / `serialize`, with app/webhooks/delivery.py — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (sorted keys, `", "`/`": "` separators) while `send_once` transmits the body with `client.post(..., json=delivery.payload)`, which serializes with httpx's own compact `(",", ":")` separators in insertion order, so the signed string and the transmitted body are different byte sequences for any payload with more than one key or any non-empty nesting.
What breaks in production: every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest than we sent, so 100% of deliveries are rejected as forged at the receiver while our side records them `delivered`.
Fix: make the signature and the request body the same bytes by construction — serialize once with `body = serialize(payload).encode()`, sign `f"{timestamp}.".encode() + body`, and send `client.post(endpoint.url, content=body, headers={... "Content-Type": "application/json"})`; never pass `json=` for a signed request. Change `sign` to return `(timestamp, signature, body)` so a caller structurally cannot obtain a signature without the exact bytes it covers. Preserve the sorted-key serialization — it is what makes the signature reproducible for a receiver that re-serializes — and preserve `serialize` as the single definition; do not fix this by loosening the receiver's recipe in the docs. Allow side that must still pass: a delivery whose body is `serialize(payload)` verifies against `signing.verify` and the receiver-side recipe in `docs/webhooks.md`, byte-identical, for a payload with nested dicts, non-ASCII text, and a float. Red-prove each clause separately by execution: (i) revert `content=body` to `json=payload` and observe the new round-trip test go red on a digest mismatch, (ii) remove the `f"{timestamp}."` prefix and observe the timestamp-binding assertion go red, (iii) drop `sort_keys=True` and observe the reordered-keys case go red. Fail loudly when the check cannot run: if `serialize` raises on a non-JSON-serializable payload, `send_once` must raise before any HTTP call and `_finish` must record `failed_permanent` with the serialization error — the delivery must never go out unsigned or with an empty body. Boundary and tie: an empty payload `{}` serializes to `"{}"` and must still be signed (two-byte body, not skipped); two payloads that differ only in key order produce one identical signature by design, and that is the intended tie.

### Critical: the timestamp header is not covered by the signature, so the documented replay window enforces nothing
File: app/webhooks/signing.py — `sign` / `verify`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed", but `sign` feeds only `serialize(payload)` into the MAC and `verify` ignores its timestamp entirely, so the timestamp is attacker-controlled unauthenticated data (R49 — a claim materially stronger than the implementation, on a control other controls are being deferred to).
What breaks in production: anyone who captures one delivery can replay it indefinitely by rewriting `X-Acme-Timestamp` to the current time, and the receiver's freshness check — the only replay defence we told customers to build — passes, so a captured `invoice.paid` can be re-delivered at will.
Fix: bind the timestamp into the MAC as in the previous finding (`mac(secret, f"{ts}.".encode() + body)`) and give `verify` the signature it actually needs: `verify(secret, timestamp, body, signature, *, max_age_seconds=300)` recomputing over `f"{timestamp}."` + the raw body, rejecting when `abs(now - int(timestamp)) > max_age_seconds`, and rejecting a non-integer timestamp. Preserve the documented five-minute window and the documented header names — the fix aligns the code to the doc, it does not relax the doc. Allow side that must still pass: a signature produced 4 minutes 59 seconds ago over the same body still verifies. Red-prove separately by execution: (i) replay a valid signature with the timestamp advanced by one hour and observe the freshness assertion go red if the age check is removed, (ii) flip one byte of the body and observe the digest assertion go red, (iii) pass `X-Acme-Timestamp: "abc"` and observe the malformed-timestamp assertion go red. Fail loudly: a missing or unparseable timestamp must return `False` from `verify` and must raise — never be treated as age zero — and `sign` must refuse to emit a signature when the timestamp cannot be formed. Boundary and tie: age exactly `max_age_seconds` is accepted (`>` rejects, not `>=`); a timestamp exactly equal to now, and one from the future within the window (clock skew), are both accepted, and a future timestamp beyond the window is rejected by the same `abs()` comparison.

### Critical: signature comparison is not constant-time
File: app/webhooks/signing.py — `verify`, line `return expected == signature`
What is wrong: `verify` compares the recomputed digest with the supplied signature using `==`, a short-circuiting byte comparison whose runtime depends on the length of the matching prefix (RS1).
What breaks in production: any caller that can submit candidate signatures against this helper — an inbound-webhook path or a customer-facing verification endpoint that reuses it, which is exactly what a shared `verify` invites — can recover a valid signature byte by byte from response timing, defeating the whole signing scheme.
Fix: `import hmac` is already present; replace the comparison with `hmac.compare_digest(expected, signature)`, and compare on `bytes` (`expected.encode()`, `signature.encode()`) so the comparison is not affected by string interning. Preserve the `sha256=` prefix in the compared value — stripping it to "compare only the hex" would silently accept a signature with a different algorithm tag. Allow side that must still pass: `verify` returns `True` for a signature produced by `sign` over the same secret, payload and timestamp. Red-prove separately by execution: (i) replace `compare_digest` with `==` and observe a test asserting `signing.verify.__code__.co_names` contains `compare_digest` — or a timing-independent unit asserting the helper is used — go red; (ii) corrupt the last hex character and observe the reject assertion go red; (iii) pass a signature of the wrong length and observe `verify` return `False` rather than raise. Fail loudly: `compare_digest` raises `TypeError` on a non-`str`/`bytes` argument — catch nothing; a signature header that is absent must be rejected at the caller before `verify`, not defaulted to `""`, so "no signature supplied" is not spelled the same as "signature did not match". Boundary and tie: two different secrets that produce the same digest for a body is the collision case and is accepted by design (SHA-256 collision resistance is the assumption being relied on); a zero-length supplied signature falls on the reject side.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: the secret is built with `random.choice`, which draws from the Mersenne Twister — a deterministic generator whose full internal state is recoverable from 624 observed outputs and whose default seeding is not required to be cryptographic.
What breaks in production: an attacker who obtains or observes enough secret material (including their own secret, issued from the same process) can predict the signing secrets minted for other organizations and forge deliveries that pass every customer's verification.
Fix: use `secrets` — `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` — and rename the constant to what it now means (`SECRET_BYTES = 32` genuinely being 32 random bytes), updating `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` to assert a minimum entropy-bearing length rather than an exact character count, since `token_urlsafe(32)` yields 43 characters. Preserve the `whsec_` prefix — customers and log scrubbers key on it. Allow side that must still pass: a freshly minted secret still round-trips through `sign`/`verify` and still starts with `SECRET_PREFIX`. Red-prove separately by execution: (i) reseed `random.seed(0)` in a test and assert two successive `new_signing_secret()` calls made under identical seeds are *different* — this goes red against the current `random.choice` implementation and green after the fix; (ii) shorten `SECRET_BYTES` to 4 and observe the minimum-length assertion go red; (iii) drop the prefix and observe the prefix assertion go red. Fail loudly: if `secrets` cannot produce entropy the call raises and endpoint creation must 500 rather than fall back to `random` — there must be no fallback branch. Boundary and tie: two organizations drawing the same secret is a 2^-256 event and is not defended against; the assertion is on length and generator, not uniqueness.

### Critical: the signing secret is readable back from the list endpoint, contradicting the documented contract
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`, consumed by app/api/routes/settings.py — `list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret"` and is the serializer for both `create_webhook_endpoint` (where disclosure is intended) and `GET /v1/settings/webhook-endpoints` (where `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: any principal with read access to settings — a read-scoped API key, a support session, a browser XHR captured in an HAR file, or an APM response-body capture — obtains the HMAC key for every endpoint in the org and can forge arbitrary signed events to the customer's system.
Fix: remove `"signing_secret"` from `to_dict()` so the default serialization is safe, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at the single call site where first-and-only disclosure is the contract; add a rotation route that mints a new secret and returns it once, since removing read-back leaves customers with no recovery path for a lost secret. Preserve the create-time disclosure — deleting it entirely would make the feature unusable, which is not a fix. Allow side that must still pass: `POST /v1/settings/webhook-endpoints` still returns a usable `signing_secret` in its 201 body. Red-prove separately by execution: (i) re-add `"signing_secret"` to `to_dict()` and observe a test asserting `"signing_secret" not in list_response[0]` go red; (ii) delete the explicit merge in the create handler and observe the create-time disclosure assertion go red; (iii) point the rotation route at the old secret and observe the "rotated secret differs from the previous one" assertion go red. Fail loudly: the deliveries and list serializers must raise rather than silently omit if a future field named like a credential is added — assert the exact key set of `to_dict()` in a test, so a new secret-bearing field fails the build instead of leaking. Boundary and tie: the 201 create response is the one place the secret crosses the boundary; a rotation response is the second, and both are excluded from request logging.

### Critical: the deliveries endpoint is not scoped to the caller's organization
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: the query filters only on the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, while both sibling routes added in the same file (`list_api_keys`, `list_webhook_endpoints`) do filter on `user.org_id` — the tenancy pattern was applied to two of three new routes (R3, security-relevant).
What breaks in production: any authenticated user can walk `endpoint_id` from 1 upward and read other organizations' delivery rows, and because `WebhookDelivery.to_dict()` exposes `event_type` and the route exposes the whole row set, this is a cross-tenant disclosure of billing event metadata at scale.
Fix: join through the endpoint and scope by org — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookDelivery.endpoint_id == m.WebhookEndpoint.id).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the endpoint's existence is not disclosed. Preserve the ordering and the `limit` behaviour; the fix is a narrowing of the row set, not a change to the page. Allow side that must still pass: the owning organization still receives its own deliveries for its own `endpoint_id`, in the same order and count as before. Red-prove separately by execution: (i) drop the `org_id` predicate and observe a cross-tenant test — org A calling with org B's `endpoint_id` — go red on the expected 404; (ii) drop the `WebhookEndpoint.id == endpoint_id` predicate and observe the same-org test go red because it now returns another endpoint's rows; (iii) return 403 instead of 404 and observe the enumeration assertion go red. Fail loudly: an `endpoint_id` that does not parse as an integer must 422 at the route signature, and an unresolvable endpoint must 404 — "examined nothing" must not return an empty `200 []`, which is indistinguishable from "your endpoint has no deliveries". Boundary and tie: an endpoint that exists but belongs to another org falls on the 404 side, identically to an endpoint that does not exist; an endpoint the caller owns with zero deliveries returns `200 []`.

### Critical: endpoint URLs are unvalidated against SSRF, and the response body is stored and served back
File: app/api/routes/settings.py — `create_webhook_endpoint`, with app/webhooks/delivery.py — `run_worker` (`follow_redirects=True`) and `_finish` (`row.response_body = detail`)
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plaintext `http://` (docs/webhooks.md says "Only `https://` URLs are accepted"), admits any scheme whose spelling merely begins with `http`, and applies no destination restriction, while the worker follows redirects and `_finish` persists the full response body into a row that `list_deliveries` returns.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or a public URL that 302s there), our worker fetches it from inside the VPC, stores the response, and hands it back through the deliveries API — a full read-SSRF with exfiltration channel, plus every non-redirected delivery leaves the network in cleartext with the signing header attached.
Fix: validate at the schema level with `pydantic.HttpUrl` constrained to `https` only, then resolve the host and reject any address in a private, loopback, link-local, unique-local, or unspecified range using `ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`, rejecting also when the name resolves to multiple addresses of which any is internal; set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure with a message naming the redirect target; and truncate `response_body` to a fixed cap (e.g. 4 KiB) before persisting. Because DNS can be re-resolved between validation and use, pin the delivery to the validated address at request time rather than trusting the earlier check. Preserve the delivery of legitimate public HTTPS endpoints and preserve the stored response prefix — operators need it to debug a customer's 500, so truncate rather than drop it. Allow side that must still pass: `https://hooks.example.com/acme` resolving to a public address is accepted at registration and delivered to unchanged. Red-prove separately by execution: (i) register `http://hooks.example.com` and observe the scheme assertion go red if the `https`-only constraint is removed; (ii) register a hostname resolving to `127.0.0.1` and observe the private-range assertion go red if the address check is removed; (iii) serve a 302 to `http://169.254.169.254/` and observe the no-redirect assertion go red if `follow_redirects=True` is restored; (iv) return a 1 MiB body and observe the truncation-length assertion go red if the cap is removed. Fail loudly: a hostname that does not resolve must be rejected at registration with a message saying resolution failed — never accepted on the assumption it will resolve later — and a resolution failure at delivery time must record a retryable failure naming DNS, not a generic HTTP error. Boundary and tie: `https://` on a public address is the only accepted shape; a host resolving to both a public and a private address falls on the reject side, and an address exactly at the edge of a private block (`10.255.255.255`, `172.31.255.255`) is private and rejected.

### Critical: the unique index on `event_id` alone makes multi-endpoint fan-out impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index permits only one row per `event_id` across the entire table — and it is table-wide, so it also collides across organizations if `event_id` is not globally unique.
What breaks in production: the first customer with two registered endpoints triggers an `IntegrityError` on `session.add_all`, the whole enqueue transaction aborts, the dispatcher's blanket `except Exception` swallows it as a warning, and *no* endpoint receives the event — the failure is silent and total for that customer.
Fix: replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which is also the constraint that actually implements the "deduplicate on `event_id`" guarantee the docs describe (per-endpoint, not per-event), and add `ON CONFLICT (endpoint_id, event_id) DO NOTHING` semantics at the insert so a re-dispatch of the same event is idempotent rather than an abort. Preserve deduplication — do not fix this by dropping uniqueness, which would let a retried dispatch fan out twice. Allow side that must still pass: one event with two active endpoints produces exactly two rows, and re-running `enqueue_for_event` for the same event produces no additional rows. Red-prove separately by execution: (i) restore the single-column index and observe the two-endpoint test go red on `IntegrityError`; (ii) drop the unique index entirely and observe the re-enqueue idempotency test go red with four rows; (iii) remove `DO NOTHING` and observe the re-enqueue test go red on the conflict raising. Fail loudly: a conflict on any *other* constraint must still propagate — `DO NOTHING` must be scoped to the named index, not a bare `ON CONFLICT DO NOTHING` that would also swallow a foreign-key or check violation. Boundary and tie: two different endpoints of the same org sharing one `event_id` is the legal case; the same endpoint twice for one `event_id` is the tie and resolves to one row.

### Critical: the migration's status CHECK constraint does not contain the value the code writes
File: migrations/0042_webhook_delivery.sql — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs app/webhooks/delivery.py — `_finish(delivery.id, "failed_permanent", ...)` and app/webhooks/models.py — `STATUSES`
What is wrong: the database is the strict consumer of a value produced elsewhere in the same change, and the two spellings disagree — the migration says `'failed'`, while both `models.STATUSES` and the only writer in `deliver` say `'failed_permanent'` (R40; R3 — the four-state enum was propagated to the model and not to the schema).
What breaks in production: every delivery that exhausts its retries raises a check-constraint violation inside `_finish`, the update transaction aborts, and the row stays `in_flight` forever — so exhausted deliveries are never marked failed, never surfaced in the deliveries API, and never reclaimed.
Fix: change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive both sides from one definition — have the model column use `Enum(*STATUSES, name="webhook_delivery_status")` and generate the constraint from `STATUSES` so the two cannot drift again. Preserve the constraint; do not fix this by dropping the CHECK, which would trade a loud abort for silent garbage in the status column. Allow side that must still pass: writing each of the four names in `STATUSES` succeeds against the migrated schema. Red-prove separately by execution: (i) write a fifth name and observe the constraint-rejects-unknown-status test go red if the CHECK is dropped; (ii) revert the migration spelling to `'failed'` and observe the exhausted-retries integration test go red on the violation; (iii) add a name to `STATUSES` without regenerating and observe the "constraint set equals `STATUSES`" test go red. Fail loudly: the schema-versus-`STATUSES` equality test must fail the build when the two sets differ, rather than being skipped when a database is unavailable — mark it as requiring the database and error, not skip, when there is none. Boundary and tie: `'failed_permanent'` is the sole terminal failure name; `'failed'` must not remain as an accepted alias, or both spellings will appear in the table.

### Critical: a blocking `time.sleep` inside an async coroutine stalls the whole worker
File: app/webhooks/delivery.py — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered 100-at-a-time by `run_worker`, but it sleeps with the synchronous `time.sleep`, which blocks the event loop rather than yielding it.
What breaks in production: one endpoint that returns 500 blocks every other delivery in the batch — and every other coroutine on that loop — for up to 2+4+8+16 = 30 seconds of sleeping plus up to 5×30 s of request timeout, so a single slow customer serializes the entire dispatcher and the 60-second Redis lock expires mid-batch while the loop is frozen.
Fix: `await asyncio.sleep(delay)` — `asyncio` is already imported — and bound the total time a single delivery may hold a worker slot with `async with asyncio.timeout(DELIVERY_BUDGET_SECONDS)` around the retry loop, recording a terminal `failed_permanent` when the budget is exceeded. Preserve the retry schedule and the number of attempts; the fix changes who waits, not how long. Allow side that must still pass: a delivery that succeeds on its second attempt still waits the full first backoff interval before retrying (assert elapsed wall time under a controlled clock, not merely that it succeeded). Red-prove separately by execution: (i) restore `time.sleep` and observe a concurrency test — two deliveries, one sleeping, asserting the second completes while the first is still in backoff — go red; (ii) remove the timeout wrapper and observe the never-terminating-endpoint test go red by exceeding the budget; (iii) set `BASE_DELAY_SECONDS` to 1 and observe the backoff-interval assertion go red. Fail loudly: an `asyncio.TimeoutError` must be recorded via `_finish` as a terminal state naming the budget, never allowed to escape into `gather` where it cancels sibling deliveries. Boundary and tie: elapsed time exactly equal to the budget is not a timeout (`>` not `>=`); two deliveries whose backoffs expire in the same tick both resume, in no defined order.

### Critical: the dispatch lock is not atomic, has an unprotected TTL window, and is released unconditionally
File: app/webhooks/delivery.py — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does `get` then `set` then `expire` as three separate round trips, so two workers can both observe an empty key and both "acquire"; a crash between `set` and `expire` leaves a key with no TTL; and `run_worker` deletes `LOCK_KEY` in a `finally` without checking that the value still belongs to this worker.
What breaks in production: the no-TTL case wedges the dispatcher permanently — every subsequent worker sees the key, sleeps, and no webhook is ever delivered again, with nothing logged above `poll_interval` noise — and the unconditional delete means that after the 60-second TTL expires mid-batch (see the blocking-sleep finding), worker A deletes worker B's lock and both dispatch concurrently.
Fix: acquire with a single atomic command carrying a unique token and the TTL together — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`) so a worker can only delete its own lock; renew the TTL while the batch is in flight, and set `LOCK_TTL_SECONDS` above the per-delivery budget introduced above so the lease cannot expire under a legitimately slow batch. Preserve the single-dispatcher invariant and preserve the TTL as the crash-recovery path — do not fix the wedge by removing the lock. Allow side that must still pass: a worker whose predecessor exited cleanly acquires the lock on its next poll with no delay. Red-prove separately by execution: (i) replace `set(nx=True)` with `get`+`set` and observe a two-worker concurrent-acquire test go red with both acquiring; (ii) replace the compare-and-delete with a bare `delete` and observe the "worker A does not release worker B's lock" test go red; (iii) omit `ex=` and observe the TTL assertion (`await redis_client.ttl(LOCK_KEY) > 0`) go red. Fail loudly: a Redis error during acquire must raise out of `run_worker` and stop the process rather than being read as "not acquired" and silently spinning, so an unreachable Redis is distinguishable from a held lock; a failed release must log at ERROR with the key and token. Boundary and tie: two workers polling in the same instant — exactly one `SET NX` returns truthy and the other must sleep; a lease whose TTL expires at the exact moment the holder attempts release deletes nothing, and the compare-and-delete returning 0 is the expected, non-error outcome.

### Critical: no test verifies that the signature matches the body that was sent
File: tests/webhooks/test_delivery.py — `test_send_once_posts_the_signed_payload`
What is wrong: the test captures both `request.headers` and `request.content` but asserts only that the signature header *starts with* `sha256=` and that the timestamp *is a digit string*, never recomputing the digest over the captured body — so the one assertion that would catch the producer/consumer byte mismatch is absent, and `signing.verify` is never reached from any wire-shaped body (RT5: the production primitive being claimed is signature verification, and the test's call path does not include it; RT1(c)/(d): the assertions compare the subject's output against the subject's own output rather than against an independently derived expected value).
What breaks in production: the suite is green while every delivery we send is unverifiable by every customer, and the green suite is precisely why the defect ships — a reviewer reading "posts the signed payload" concludes the signature is correct.
Fix: assert the signature against the captured bytes with an independently written expectation — `expected = "sha256=" + hmac.new(SECRET.encode(), captured["headers"][signing.TIMESTAMP_HEADER].encode() + b"." + captured["body"], hashlib.sha256).hexdigest()`, computed in the test from the primitives rather than by calling `signing.sign`, then `assert captured["headers"][signing.SIGNATURE_HEADER] == expected` — and add a round-trip case feeding the captured raw body through `signing.verify` exactly as a customer would. Replace `FakeEndpoint`/`FakeDelivery` with instances of the real `m.WebhookEndpoint` / `m.WebhookDelivery` so the fixture's field set is enforced by the model rather than by a reader. Preserve the existing status-code and content-type assertions. Allow side that must still pass: the correct-secret, correct-body case verifies `True`. Red-prove separately by execution: (i) change `send_once` to post `json=` instead of the signed bytes and observe the digest equality assertion go red; (ii) change `sign` to drop the timestamp prefix and observe the same assertion go red for a different reason named in the output; (iii) swap the secret in the test's expectation and observe the round-trip `verify` assertion go red. Fail loudly: if the mock transport never fires, `captured` is empty and the test must fail with "handler was not invoked" rather than a `KeyError` that reads like a fixture bug. Boundary and tie: a payload with a single key is the case where httpx's and `serialize`'s encodings coincide, so the fixture payload must have at least two keys in non-sorted order and a nested value — otherwise the test passes for the wrong reason.

### Major: ORM instances are used after their session has closed
File: app/webhooks/delivery.py — `_claim_batch` (returns `rows` after the `with session_scope()` block ends), `deliver` (`session.get` for `endpoint` outside the block, then `delivery.attempts` / `delivery.payload` / `delivery.id`)
What is wrong: both helpers hand live ORM objects out past the end of their `session_scope()` block and then read attributes from them, whereas the three routes in `app/api/routes/settings.py` — added in this same change — carefully materialise `to_dict()` *inside* the `with` block, which is the pattern this file does not follow.
What breaks in production: on the standard `expire_on_commit=True` configuration every one of those attribute reads triggers a refresh against a closed session and raises `DetachedInstanceError`, so the worker fails on its first batch and no delivery ever goes out; where it does not raise, `row.status = "in_flight"` in `_claim_batch` and the reads in `deliver` operate on stale values.
Fix: return plain data, not ORM instances — have `_claim_batch` build and return a list of frozen dataclasses (`ClaimedDelivery(id, endpoint_id, attempts, payload, endpoint_url, signing_secret)`) constructed inside the session, joining the endpoint in the same query so `deliver` needs no second lookup, and change `deliver`/`send_once` to take that dataclass. Preserve the `in_flight` marking inside the same transaction as the read (it is what prevents a second claim) and preserve the batch ordering. Allow side that must still pass: a claimed batch of two deliveries is still delivered with the correct URL, secret and payload for each. Red-prove separately by execution: (i) return the ORM rows again and observe an integration test that claims and then delivers go red on `DetachedInstanceError`; (ii) drop the `in_flight` update and observe the "a second `_claim_batch` returns nothing" assertion go red; (iii) join the wrong endpoint and observe the per-delivery URL assertion go red. Fail loudly: a delivery whose endpoint row is missing must be finished as `failed_permanent` naming the missing endpoint, not skipped silently. Boundary and tie: a batch of exactly `BATCH_SIZE` rows is fully claimed; two rows with identical `next_attempt_at` are ordered arbitrarily and both must be claimed in the same batch or neither.

### Major: `in_flight` is a non-terminal state with no reset path
File: app/webhooks/delivery.py — `_claim_batch` (`row.status = "in_flight"`) and `run_worker`
What is wrong: rows leave `in_flight` only through `_finish`, which is reached only on the two normal exits of `deliver`; a worker crash, a SIGTERM during deploy, an exception from `_finish` itself, or a sibling coroutine's exception propagating out of `asyncio.gather` (called without `return_exceptions=True`) leaves rows in `in_flight`, and `_claim_batch` only ever selects `status == "pending"` (R38 mode 1: no failure-exit and no bounded timeout out of the transient state).
What breaks in production: every deploy or crash permanently strands the in-flight batch — up to 100 events per incident — and the rows are invisible to both retry and alerting, so a customer's missing `invoice.paid` is only discovered by the customer.
Fix: add a reaper that returns rows to `pending` when `status = 'in_flight' AND updated_at < now() - interval '<lease>'`, bump `updated_at` at claim time so the lease has a start, cap the reclaim count per row with a `attempts` increment so a poison row eventually reaches `failed_permanent` instead of cycling forever, and pass `return_exceptions=True` to `asyncio.gather` with each exception routed through `_finish`. Preserve `in_flight` as a real state — do not fix this by claiming without marking, which reintroduces double-delivery. Allow side that must still pass: a delivery still in flight *within* its lease is not reclaimed by the reaper while its worker is alive. Red-prove separately by execution: (i) kill a worker mid-batch and observe the "stranded rows return to pending within one lease" assertion go red if the reaper is removed; (ii) remove the `attempts` increment on reclaim and observe the "poison row terminates at MAX_ATTEMPTS" assertion go red by looping; (iii) remove `return_exceptions=True` and observe the "one failing delivery does not cancel its siblings" assertion go red. Fail loudly: the reaper must log at WARN with the reclaimed count and must raise if it cannot run, so "no rows were stranded" is not spelled the same as "the reaper never executed". Boundary and tie: a row whose age is exactly the lease is not yet reclaimed (`<` not `<=`); a row reclaimed at exactly `MAX_ATTEMPTS` goes terminal rather than back to `pending`.

### Major: `run_worker` can raise `NameError` and spin
File: app/webhooks/delivery.py — `run_worker`, `if not batch:` after the `try/finally`
What is wrong: `batch` is assigned inside the `try` but read after the `finally`, so any exception from `_claim_batch` — a database blip, the detached-instance error above — leaves `batch` unbound and the read raises `NameError`, replacing the real error with a misleading one; and if the outer loop is supervised and restarted, the loop then spins at full speed because the `poll_interval` sleep is on the same unreachable path.
What breaks in production: a transient database error surfaces in logs as `NameError: name 'batch' is not defined`, which points investigators at the wrong file while the dispatcher busy-loops against the database.
Fix: initialise `batch: list[ClaimedDelivery] = []` before the `try`, move the `if not batch: await asyncio.sleep(poll_interval)` inside the `try` after the gather, and add `except Exception: log.exception(...); await asyncio.sleep(poll_interval)` around the body so a claim failure backs off instead of spinning. Preserve the fast path — when a batch *is* returned the loop must immediately claim again without sleeping, which is what keeps the queue draining. Allow side that must still pass: with a full batch available the loop performs the next claim with no `poll_interval` delay. Red-prove separately by execution: (i) make `_claim_batch` raise and observe the "the worker logs the original exception and continues" assertion go red against the current code (it reports `NameError`); (ii) remove the backoff in the except branch and observe a "no more than N claims per second under a failing database" assertion go red; (iii) sleep unconditionally and observe the no-delay-on-full-batch assertion go red. Fail loudly: the handler must log the original exception with a traceback and must not swallow `asyncio.CancelledError` — shutdown must remain promptly cancellable. Boundary and tie: an empty batch sleeps, a batch of exactly one does not; the tie is a batch that becomes empty because every row was reclaimed by the reaper, which sleeps.

### Major: the retry policy contradicts the documented one
File: app/webhooks/delivery.py — `deliver` / `backoff_for`, against docs/webhooks.md "Retries"
What is wrong: the docs state that "a 4xx is permanent and we stop immediately" and that backoff is "exponential with jitter", but `deliver` treats every non-2xx identically and retries it to `MAX_ATTEMPTS`, and `backoff_for` returns a deterministic `2**attempt` with no jitter — a divergence the test suite actively pins in place (`test_backoff_grows_exponentially` asserts the exact non-jittered values).
What breaks in production: a customer who returns 401 after rotating credentials, or 410 for a decommissioned endpoint, receives five copies of every event instead of one, and because all deliveries for a burst of events share a start instant they retry in lockstep, hammering a struggling endpoint at synchronized 2/4/8/16-second intervals.
Fix: branch on the status class — `if 400 <= status < 500 and status not in RETRYABLE_4XX: _finish(..., "failed_permanent", ...); return` with `RETRYABLE_4XX = {408, 425, 429}` — and add full jitter to the schedule (`random.uniform(0, 2**attempt)` from a non-cryptographic generator is correct here, unlike for secrets), updating `test_backoff_grows_exponentially` to assert the interval falls within its jitter window rather than an exact value. Preserve the documented attempt ceiling and the documented base intervals as the window's upper bound. Allow side that must still pass: a 500 and a connection error are both still retried to `MAX_ATTEMPTS`, and a 429 is still retried. Red-prove separately by execution: (i) remove the 4xx branch and observe a "one attempt for a 404" assertion go red with five; (ii) add 404 to `RETRYABLE_4XX` and observe the same assertion go red the other way; (iii) remove the jitter and observe a "two deliveries scheduled in the same tick have different next attempt times" assertion go red. Fail loudly: a status the classifier does not recognise (1xx, an out-of-range code) must be treated as retryable and logged at WARN naming the code, never silently dropped into either branch. Boundary and tie: 400 through 499 is the permanent band with the three named exceptions; exactly 400 is permanent and exactly 399 is not, and a 429 arriving on the final attempt still terminates at `MAX_ATTEMPTS`.

### Major: `enqueue_for_event` reimplements the timestamp helper added in the same change, with the opposite awareness
File: app/webhooks/delivery.py — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`) against app/webhooks/models.py — `_now()`
What is wrong: `models._now()` returns `datetime.now(timezone.utc)` and is used as the default for every other timestamp column in the change, and `_claim_batch`/`_finish` both use `datetime.now(timezone.utc)`, but this one call site hand-rolls a *naive* `datetime.utcnow()` for the very column `_claim_batch` compares against an aware value (R1 — a shared helper exists in the same package and was not adopted; the behavioural difference is not accidental, it is a timezone-awareness change).
What breaks in production: comparing a naive and an aware datetime raises `TypeError` in Python and is silently reinterpreted in the local session timezone by the database, so newly enqueued deliveries are either never claimed or claimed at an offset of the server's UTC offset from the intended time.
Fix: import and use `models._now()` (promoting it to `now_utc()` as a public helper in `app/webhooks/models.py`, since it now has a second caller) at this call site and anywhere a delivery timestamp is created; the behavioural difference being adopted is that the value becomes tz-aware, which is what the column and the claim query already assume. Note what the dedup does *not* fix: the migration's column is `TIMESTAMP` without time zone (see the next finding), so adopting the aware helper is necessary and not sufficient — both must change together. Preserve immediate-dispatch semantics: a newly enqueued delivery must still be claimable on the very next poll. Allow side that must still pass: a delivery enqueued now is returned by `_claim_batch` on the next poll, and one with `next_attempt_at` one hour ahead is not. Red-prove separately by execution: (i) restore `datetime.utcnow()` and observe an "enqueued delivery is claimed on the next poll" integration test go red; (ii) set `next_attempt_at` an hour ahead and observe the not-yet-due assertion go red if the `<=` filter is removed; (iii) grep-assert in a test that no `utcnow(` appears in `app/webhooks/` and observe it go red when reintroduced. Fail loudly: a naive datetime reaching the column must raise at the boundary — add a validator rather than letting the driver coerce it. Boundary and tie: `next_attempt_at` exactly equal to `now` is due (`<=`, not `<`); two deliveries with identical `next_attempt_at` are both claimed in the same batch.

### Major: the model declares timezone-aware columns that the migration creates as naive
File: app/webhooks/models.py — `DateTime(timezone=True)` on `created_at` / `next_attempt_at` / `updated_at`, against migrations/0042_webhook_delivery.sql — `TIMESTAMP NOT NULL`
What is wrong: every timestamp column in the migration is `TIMESTAMP` (i.e. `timestamp without time zone`) while the ORM declares `DateTime(timezone=True)` (`timestamptz`), so the mapped type and the physical type disagree for all six columns across both new tables.

Allow side that must still pass: a row written from a process with `TZ=America/New_York` and read from a process with `TZ=UTC` yields the same instant. Fail loudly: the model-versus-schema type comparison must be a test that errors when no database is reachable rather than skipping, so an unrun check is not reported as a pass. Boundary and tie: an instant exactly at a DST transition must round-trip to the same UTC instant; two rows written in the same microsecond tie on `created_at` and their relative order is undefined.

### Major: `organizations.webhooks_enabled` is declared and never read
File: migrations/0042_webhook_delivery.sql — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: the migration adds an org-level kill switch defaulting to `FALSE`, but nothing in the change consults it — `create_webhook_endpoint` accepts registrations regardless, `enqueue_for_event` filters only on `WebhookEndpoint.active`, and the dispatcher gates only on `WEBHOOK_EVENT_TYPES` (R41 — a declared capability with no backing path; the declared path never worked at all).
What breaks in production: operators believe the feature is off by default and that flipping the flag is how it is enabled or disabled, so an incident response that sets `webhooks_enabled = FALSE` to stop a runaway delivery loop has no effect and the deliveries continue.

Wiring it is the better option and the axis is the incident path: deleting removes a kill switch the operations story needs, whereas wiring costs one join. Preserve the `DEFAULT FALSE` semantics if wired — the flag being off must mean no deliveries, not merely no new endpoints. Allow side that must still pass: an org with `webhooks_enabled = TRUE` and one active endpoint still receives its events, and its registration call still returns 201. Red-prove separately by execution: (i) set the flag false and observe the "no delivery rows are created" assertion go red if the join predicate is removed; (ii) set the flag false and observe the 403-on-registration assertion go red if that check is removed; (iii) set the flag true and observe the allow-case assertion go red if the predicate is inverted. Fail loudly: an org row that cannot be loaded must abort the enqueue with a logged error rather than defaulting to enabled — the unresolvable-subject case denies. Boundary and tie: the flag is evaluated at enqueue time, so deliveries already `pending` when it is switched off are governed by the reaper/kill path, and that decision must be stated in the docs.

### Major: only three hardcoded event types ever reach webhooks, contradicting the documented "every event type we emit"
File: app/events/dispatcher.py — `WEBHOOK_EVENT_TYPES`, against docs/webhooks.md "An empty `event_types` subscribes the endpoint to every event type we emit"
What is wrong: fan-out is gated twice — once by a three-element literal set in the dispatcher and again by the endpoint's own `event_types` — and `create_webhook_endpoint` accepts any strings at all in `event_types`, so an endpoint can be registered for an event that structurally can never be delivered (R12: the enum's coverage is defined in one place and consumed in two that do not agree).
What breaks in production: a customer subscribes to an event type we emit but that is absent from this literal, sees a successful 201 and an endpoint listed as `active`, and silently receives nothing — with no error anywhere to attribute it to.

Preserve the empty-list-means-all behaviour. Fail loudly: an event type absent from the registry must be logged at WARN by the dispatcher when a matching endpoint exists, rather than skipped silently. Boundary and tie: `[]` means all; `["invoice.paid"]` for an event of a different type means none; an endpoint listing an eligible and an ineligible type is rejected whole rather than partially accepted.

### Major: enqueue failures are swallowed and the event is lost with no reconciliation
File: app/events/dispatcher.py — `except Exception as exc: log.warning("webhook enqueue failed for event %s: %s", event_id, exc)`
What is wrong: the only code path that ever creates delivery rows is wrapped in a bare `except Exception` that downgrades every failure — including the `IntegrityError` from the `event_id` unique index and any database unavailability — to a WARN line, and nothing in the change re-derives missed deliveries from the persisted `Event` rows afterwards.
What breaks in production: a database hiccup or the unique-index collision means the customer never receives that event and never will, and because the event itself committed successfully there is no signal anywhere that a delivery was owed.
Fix: keep the catch narrow and make the loss recoverable — catch only the exceptions that must not fail the caller, re-raise or alert on the rest, and add a reconciliation job that scans `events` of a webhook-eligible type having no `webhook_deliveries` row for each active endpoint within the last N hours and enqueues them. Preserve the property that a webhook failure does not roll back or fail the event dispatch itself — that is why the try/except exists, and the fix must not make the caller fail. Allow side that must still pass: a successful enqueue still returns the `event_id` to the caller unchanged, and a webhook failure still lets `dispatch` return normally. Red-prove separately by execution: (i) make `enqueue_for_event` raise and observe the "the reconciliation job creates the missing rows" assertion go red if the job is removed; (ii) make it raise and observe the "`dispatch` still returns `event_id`" assertion go red if the except clause is deleted; (iii) narrow the alerting predicate wrongly and observe the "an enqueue failure raises an alert" assertion go red. Fail loudly: the log level must be ERROR with the exception traceback, not WARN with `str(exc)` — an owed-but-undelivered event is not a warning, and `str(exc)` on a database error is frequently empty. Boundary and tie: an event with zero matching endpoints legitimately creates zero rows and must not be flagged by the reconciliation job; an event with one endpoint and zero rows must be.

### Major: full response bodies and signed headers are logged and persisted without bound
File: app/webhooks/delivery.py — `send_once` (`log.info("POST %s headers=%s", endpoint.url, headers)`) and `_finish` (`row.response_body = detail`, fed `response.text`)
What is wrong: the header dict logged at INFO on every attempt includes the `X-Acme-Signature` value, and `_finish` stores the customer's entire unbounded response body into a `TEXT` column that `list_deliveries` reads back.
What breaks in production: log aggregation retains valid signatures for the retention window (a replay primitive, given the timestamp is unsigned), and a customer endpoint that returns a large or sensitive body — an HTML error page containing session data, or a multi-megabyte stack trace — is copied into our database and served back through the API, both bloating rows and importing the customer's data into our breach surface.
Fix: log the URL, delivery id, attempt number and status code only — never the header dict — and truncate the stored body with an explicit cap and marker (`detail[:RESPONSE_BODY_MAX] + "…[truncated]"` with `RESPONSE_BODY_MAX = 4096`), recording the original length in a separate column. Red-prove separately by execution: (i) return a 10 KiB body and observe the "stored length equals the cap plus marker" assertion go red if the truncation is removed; (ii) return a 10-byte body and observe the "stored verbatim, no marker" assertion go red if truncation is applied unconditionally; (iii) grep-assert the log record's message does not contain `SIGNATURE_HEADER` and observe it go red if the header dict is logged again. Fail loudly: a response whose body cannot be decoded must store an explicit `"<undecodable body, N bytes>"` marker rather than an empty string, so "no body" and "unreadable body" are not spelled the same. Boundary and tie: a body of exactly `RESPONSE_BODY_MAX` bytes is stored verbatim with no marker; `RESPONSE_BODY_MAX + 1` is truncated.

### Major: `_finish` dereferences a row it never checks for existence
File: app/webhooks/delivery.py — `_finish`, `row = session.get(m.WebhookDelivery, delivery_id)` followed by `row.status = status`
What is wrong: `session.get` returns `None` for a missing primary key and the next five lines assign attributes on it unconditionally, and the row genuinely can be gone — `webhook_deliveries` has `ON DELETE CASCADE` from `webhook_endpoints`, so a customer deleting an endpoint mid-flight removes rows the worker still holds.
What breaks in production: the resulting `AttributeError: 'NoneType' object has no attribute 'status'` propagates out of `deliver` into `asyncio.gather`, which (called without `return_exceptions=True`) cancels the remaining coroutines in the batch, so one deleted endpoint strands up to 99 unrelated deliveries in `in_flight`.
Fix: guard with `if row is None: log.info("delivery %s vanished before finish (endpoint deleted?)", delivery_id); return`, and pair it with `return_exceptions=True` on the gather so no single delivery can cancel its siblings regardless of cause. Preserve the state write for the normal path — the guard must be a `None` check, not a broad `try/except` that would also swallow constraint violations such as the status CHECK mismatch. Allow side that must still pass: an existing row is still updated with status, attempts, response status, body and `updated_at`, and those five fields are asserted individually. Red-prove separately by execution: (i) delete the row before calling `_finish` and observe the "returns without raising" assertion go red if the guard is removed; (ii) remove one of the five field assignments and observe that field's assertion go red; (iii) restore the bare gather and observe the "a failing delivery does not cancel its siblings" assertion go red. Fail loudly: log the vanished row at INFO with its id — a silent `return` makes "finished" and "row was gone" indistinguishable in the delivery metrics. Boundary and tie: a row deleted between the claim and the finish falls on the no-op side; a row that still exists but whose endpoint was deleted is finished normally, since the delivery row is the subject.

### Major: request parameters are not validated at the schema level
File: app/api/routes/settings.py — `EndpointIn` (`url: str`, `event_types: list[str] = []`) and `list_deliveries` (`limit: int = Query(50, ge=1)`)
What is wrong: the request schema declares `url` as a bare `str` validated afterwards by a `startswith` check inside the handler rather than by the schema, `event_types` accepts arbitrary strings with no membership check, and `limit` carries a lower bound with no upper bound (RS3 — validation belongs at the boundary, not deep in business logic; and a mutable `[]` default on a Pydantic model field is only safe because Pydantic copies it, which is not a property to rely on by accident).

Red-prove separately by execution: (i) request `limit=201` and observe the 422 assertion go red if `le=200` is removed; (ii) request `limit=0` and observe the existing lower-bound 422 assertion go red if `ge=1` is removed; (iii) post a non-URL string and observe the 422 assertion go red if `HttpUrl` is reverted to `str`. ## Cross-cutting verification performed

- **Tenancy filter** — checked all three new routes: `create_webhook_endpoint` and `list_webhook_endpoints` scope on `user.org_id`; `list_deliveries` does not (reported). `enqueue_for_event` scopes on `org_id` correctly.
- **`to_dict` secret exposure** — checked both `to_dict` implementations; only `WebhookEndpoint.to_dict` carries a credential, and it has two call sites, one of which must not disclose it (reported).
- **Naive vs aware datetimes** — `datetime.utcnow()` appears once, in `enqueue_for_event`; `_claim_batch`, `_finish` and `models._now` are all aware (reported as R1). The migration's six timestamp columns are uniformly naive (reported separately).
- **Credential comparison** — `verify` is the only equality comparison on signature-shaped data in the diff (reported as RS1). No other `==` on a secret, token or digest appears.
- **Status enum spelling** — `'failed_permanent'` appears in `models.STATUSES` and in `deliver`; the migration is the only site spelling it `'failed'` (reported).
- **Blocking calls in async code** — `time.sleep` appears once, in `deliver`; `run_worker` and `_acquire_lock` use `await asyncio.sleep`/awaited Redis calls correctly.
- **Session-scope escape** — `_claim_batch` and `deliver` both return or use ORM objects past the `with` block; the three routes in `settings.py` do not (reported as the in-diff contrast).

## Codebase awareness

- `models._now()` already provides the aware-UTC timestamp that `enqueue_for_event` hand-rolls with `datetime.utcnow()` — the helper is in the same package, added by this same change (R1 finding above).
- `signing.serialize()` already defines the canonical wire encoding, and `send_once` bypasses it by delegating serialization to httpx's `json=` parameter — the signature-mismatch Critical is a case of the shared serializer existing and not being used on the path that matters.
- `WebhookEndpoint.to_dict()` is the shared serializer both endpoint routes reuse; the secret-disclosure fix belongs in that one helper rather than at each call site.
- `_finish` is the single terminal-state writer, so the `in_flight` reaper and the `None` guard both belong there rather than being duplicated into `deliver`.
