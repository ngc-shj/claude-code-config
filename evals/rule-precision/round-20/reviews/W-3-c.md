### Critical: Endpoint URL is user-controlled and unrestricted — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `parsed.scheme.startswith("http") or not parsed.netloc`
What is wrong: The only check on a customer-supplied delivery URL is that its scheme starts with `http` and its netloc is non-empty, so `http://169.254.169.254/latest/meta-data/`, `http://10.0.0.5:6379/`, or `httpfoo://…` all pass, and `run_worker` then POSTs to them from inside the network with `follow_redirects=True` (`app/webhooks/delivery.py`).
What breaks in production: Any authenticated tenant turns the delivery worker into a proxy for internal HTTP services and cloud metadata endpoints, and a `302` from a legitimate host reaches the same targets because redirects are followed unconditionally — while `docs/webhooks.md` tells operators "Only `https://` URLs are accepted", which the code does not enforce.
Fix: Replace the `startswith` test with an exact allow-list `parsed.scheme == "https"`; resolve the hostname at registration and at each send, and reject when any resolved address is in a private/loopback/link-local/unique-local/reserved range (`ipaddress.ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast`); set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure. Boundary and tie: the check is on the *resolved addresses*, and an ALL-or-NOTHING rule — a hostname that resolves to both a public and a private address is rejected, and the last resolution before the socket is the one that decides (pin the resolved IP into the request via a custom transport so the DNS answer that passed is the one connected to, closing the rebind window between check and use). Allow side that must still succeed: registering and delivering to `https://hooks.example.com/acme` resolving to a public address stays a 201 and a `delivered` row. Fail loudly: DNS failure, a resolver timeout, or `ip_address` raising must reject the registration with 422 and fail the delivery attempt with an explicit `detail="dns resolution failed"` — never fall through to "no private address found, allow". Preserve: customers must still be able to register any *public* host, so do not fix this by hardcoding a host allow-list. Red-prove separately, by running each: (a) register `http://hooks.example.com` → 422; (b) register `https://127.0.0.1/x` → 422; (c) an endpoint whose server answers `302 Location: http://169.254.169.254/` → delivery marked failed, and assert with a mock transport that no second request was issued.

### Critical: Signature is computed over a different byte string than the one transmitted
File: `app/webhooks/signing.py` — `sign` / `serialize`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys sorted) while the body actually sent is produced independently by `client.post(..., json=delivery.payload)` (httpx's own `json.dumps` — compact separators, insertion order), so the bytes signed are never the bytes on the wire, and `docs/webhooks.md` instructs the receiver to HMAC `raw_request_body` (R40).
What breaks in production: Every customer who implements the documented verification rejects every webhook we send, so the whole feature is a silent total-path failure for any endpoint that actually checks signatures.
Fix: Serialize once and send those exact bytes — build `body = serialize(payload).encode()` in `send_once`, pass `content=body` (not `json=`) to `client.post`, and have `sign` take that same `bytes` argument so a single buffer is both signed and transmitted; keep `Content-Type: application/json` explicit since `content=` no longer sets it. Preserve: the payload must remain a JSON object the receiver can parse, so do not "fix" this by dropping the signature or by loosening the doc to "signature covers an unspecified encoding". Fail loudly: if `serialize` raises on a non-serializable payload, mark the delivery `failed_permanent` with `detail="payload not serializable"` rather than sending an unsigned or partial body. Boundary and tie: byte equality is the contract — an empty payload `{}` must sign and send as the same two bytes, and two payloads differing only in key order must produce the same signature under `sort_keys=True`. Allow side that must still succeed: a receiver recomputing HMAC over the raw body verifies the request. Red-prove by execution: with a `MockTransport` capturing `request.content`, assert `hmac.new(secret, captured, sha256).hexdigest()` equals the sent header, then mutate `send_once` back to `json=payload` and observe that assertion go red.

### Critical: The timestamp header is not covered by the signature
File: `app/webhooks/signing.py` — `sign`, `verify`
What is wrong: `sign` returns a timestamp but HMACs only the payload, and `verify` ignores the timestamp entirely, so `X-Acme-Timestamp` is an unauthenticated attacker-editable field despite `docs/webhooks.md` specifying the signed material as `"{timestamp}.{raw_request_body}"` and the timestamp window as "what stops a captured request from being replayed".
What breaks in production: Anyone who captures one delivery can replay it forever by rewriting the timestamp header to `now`, defeating the only replay control the documentation offers — a duplicated `invoice.paid` webhook is a duplicated downstream side effect.
Fix: Make the signed material `f"{timestamp}.".encode() + body` in `sign`, and change `verify(secret, body, timestamp, signature)` to recompute over the caller-supplied timestamp and additionally reject when `abs(now - int(timestamp)) > 300`; update `send_once` to pass the same timestamp it puts in the header. Boundary and tie: `300` is inclusive-reject-above — a request exactly 300s old is accepted, 301s is rejected; a non-numeric or absent timestamp is rejected, not treated as 0. Fail loudly: `int(timestamp)` raising `ValueError` must return `False` with a distinct reason, never be caught into a generic `True`. Preserve: the timestamp must stay a plain unix-seconds header so receivers can log it. Allow side that must still succeed: a freshly signed request verifies. Red-prove separately, by running each: (a) tamper the timestamp by +1 second on an otherwise valid request → `verify` returns False; (b) set the timestamp 301s in the past → False; (c) valid fresh request → True (this one must stay green).

### Critical: Signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice` over `string.ascii_letters + string.digits`, and `random` is a Mersenne Twister seeded from process state, not a CSPRNG — the standard library already ships the correct helper (`secrets`), so this is a reimplementation of a security control (R1).
What breaks in production: An attacker who observes a few generated secrets, or who can influence process seeding, can predict other tenants' signing secrets and forge webhook deliveries that every receiver accepts as authentic.
Fix: Replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(32)` and delete `random`, `string`, and `_ALPHABET`; rename `SECRET_BYTES` to reflect that it is now an entropy size in bytes, and update the length assertion in `tests/webhooks/test_delivery.py` accordingly. Boundary and tie: 32 bytes is the floor, not a target — assert `>= 32` bytes of entropy rather than an exact string length, since `token_urlsafe` output length is a function of base64 padding. Preserve: the `whsec_` prefix must stay, because it is what lets customers recognise the value in their secret manager. Fail loudly: nothing here may fall back to `random` if `secrets` is unavailable — an ImportError must abort process start. Allow side that must still succeed: `new_signing_secret()` still returns a string that `sign`/`verify` round-trip on. Red-prove by execution: monkeypatch `secrets.token_urlsafe` to a constant and observe the new uniqueness assertion (below) go red; revert and observe it green.

### Critical: Signature comparison in `verify` is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The published verification helper compares an HMAC digest with `==`, which short-circuits on the first differing byte (RS1), even though `docs/webhooks.md` instructs customers to "Compare it against your own computation using a constant-time comparison".
What breaks in production: Any service that reuses this helper on an inbound path leaks digest bytes through response timing, letting an attacker forge a valid signature byte by byte; the module also ships advice it does not itself follow.
Fix: `return hmac.compare_digest(expected, signature)`, guarding the case where `signature` is not `str` by rejecting before the compare rather than letting `compare_digest` raise. Boundary and tie: a signature of the wrong length must return `False` through the same path, not through an early length check that reintroduces the timing channel — `compare_digest` already handles unequal lengths without leaking beyond the length itself. Preserve: the `sha256=` prefix must remain part of the compared string so a caller cannot strip it and match on the hex alone. Fail loudly: a `None` or non-ASCII signature returns `False` with a logged reason, never a `TypeError` that a caller might catch and treat as "unverified but continue". Allow side that must still succeed: `test_verify_accepts_signature_produced_by_sign` stays green. Red-prove by execution: flip one hex character of a valid signature and observe `verify` return False; replace `compare_digest` with `==` under a test that asserts `hmac.compare_digest` is on the call path (e.g. by patching it and asserting it was called) and observe that assertion red.

### Critical: Delivery listing is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`, `.filter(WebhookDelivery.endpoint_id == endpoint_id)`
What is wrong: The query filters on the path parameter alone and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike the sibling `list_webhook_endpoints` immediately above it which does filter on `org_id` — the tenancy predicate present two functions up was not propagated (R3).
What breaks in production: Any authenticated user can enumerate `endpoint_id` values and read other organizations' delivery history — event types, statuses, upstream response codes and schedules — a cross-tenant data disclosure with no audit trail.
Fix: Join the endpoint and filter on both, e.g. `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`, and return 404 (not 403) when the join yields nothing so the endpoint's existence is not disclosed. Cross-cutting: apply the same predicate to every future per-endpoint route; `create_webhook_endpoint` is already correct (it takes `org_id` from `user`), and `list_webhook_endpoints` is already correct — `list_deliveries` is the only missed site in this diff. Boundary and tie: an endpoint that exists but belongs to another org and an endpoint id that does not exist must be indistinguishable — both 404, same body, same timing class. Fail loudly: if `user.org_id` is `None`, raise rather than issuing a query with `org_id IS NULL`. Allow side that must still succeed: the owning org still gets its own deliveries, ordered and limited as before. Red-prove separately, by running each: (a) org A requests org B's endpoint id → 404 and zero rows; (b) org A requests its own endpoint id → 200 with its rows (must stay green).

### Critical: The signing secret is returned by the list endpoint and stored in plaintext
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`
What is wrong: `to_dict` unconditionally includes `signing_secret`, and `list_webhook_endpoints` calls it on every endpoint, so a plain `GET /v1/settings/webhook-endpoints` hands out every secret — directly contradicting `docs/webhooks.md`, which declares "The response is the only place the signing secret appears — it cannot be read back afterwards" (a control claimed stronger than the implementation, R49).
What breaks in production: The shared HMAC key is readable by anyone holding a session for the org and lands in browser history, proxy logs, and API-client caches; because it is also stored unhashed in `webhook_endpoints.signing_secret`, a read-only database leak is a full webhook-forgery capability.
Fix: Drop `signing_secret` from `to_dict`, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the in-memory value it just generated so the create response — and only that response — carries it; add a separate explicit `POST /webhook-endpoints/{id}/rotate-secret` for re-issue rather than making the value readable. Preserve: the create path must keep returning the secret exactly once, because it is the only way a customer can obtain it — do not fix this by removing it everywhere. Boundary and tie: on rotation, both the old and the new secret must verify during an explicit overlap window, and the response must state which is which; outside the window only the new one. Fail loudly: if the create path cannot return the secret (serialization error), the endpoint row must not be committed — a persisted endpoint whose secret nobody holds is unusable. Allow side that must still succeed: `POST /webhook-endpoints` still yields a usable secret in its 201 body. Red-prove separately, by running each: (a) `GET /webhook-endpoints` response JSON contains no `signing_secret` key; (b) `POST /webhook-endpoints` response does contain one (must stay green).

### Critical: Migration CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint enumerates `'failed'` while `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", …)` both use `'failed_permanent'` — the same enum spelled two ways across a strict consumer boundary (R40 / R2).
What breaks in production: The first delivery that exhausts `MAX_ATTEMPTS` raises a `CheckViolation` inside `_finish`, so the row stays `in_flight` forever and the worker's `asyncio.gather` propagates the exception out of `run_worker`, killing the delivery loop for every tenant.
Fix: Change the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))` and derive the SQL list from `models.STATUSES` in a test that asserts the two sets are equal, so the next added status cannot drift. Boundary and tie: the sets must be compared as sets, and the test must fail in both directions — a status in SQL but not in Python is as much a defect as the reverse. Preserve: the CHECK constraint itself must stay; do not fix this by dropping the constraint so the insert succeeds. Fail loudly: if the test cannot locate or parse the migration file, it must fail with "migration not found", not skip. Allow side that must still succeed: inserting each of the four legitimate statuses succeeds. Red-prove separately, by running each: (a) add a bogus status to `STATUSES` only → parity test red; (b) run a delivery to exhaustion against a real database → row lands `failed_permanent` (green after fix, red before).

### Critical: `UNIQUE (event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: One event fans out to one delivery row per matching endpoint (`app/webhooks/delivery.py` `enqueue_for_event` builds `rows` from every active endpoint and calls `session.add_all(rows)`), but the unique index permits only one row per `event_id`.
What breaks in production: Any org with two or more subscribed endpoints gets a unique-violation on the whole `add_all`, which the dispatcher swallows as a warning — so those orgs silently receive no webhooks at all, and the failure is invisible except in logs.
Fix: Make the index `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id, endpoint_id)`, which still gives the idempotency the feature needs (one attempt-chain per event per endpoint) and lets `enqueue_for_event` use an `ON CONFLICT DO NOTHING` upsert so a retried dispatch does not duplicate. Preserve: uniqueness must remain — the point of the index is that a re-dispatched event does not double-deliver, so do not fix this by making the index non-unique. Boundary and tie: two endpoints of the same org for the same event are two distinct rows; the *same* endpoint re-enqueued for the same event is a tie and must be a no-op, not a second row. Fail loudly: an `IntegrityError` that is not the expected conflict must propagate, not be folded into the same "already enqueued" branch. Allow side that must still succeed: a single-endpoint org still gets exactly one row. Red-prove separately, by running each: (a) two active endpoints, one event → two rows; (b) re-run `enqueue_for_event` with the same `event_id` → still two rows, no exception.

### Critical: `time.sleep` inside an async coroutine blocks the event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` for a whole batch, but its retry backoff uses the blocking `time.sleep`, so one retrying delivery freezes the entire loop — the module already imports `asyncio` and uses `await asyncio.sleep` correctly in `run_worker`, so the async primitive is present and simply not used here.
What breaks in production: A single endpoint that returns 500 stalls the whole worker process for up to 2+4+8+16 = 30 seconds per delivery, serialising the batch and blocking the Redis lock heartbeat and every other tenant's deliveries behind it.
Fix: Replace with `await asyncio.sleep(delay)`. Preserve: the backoff itself must stay — the fix is the sleep primitive, not the delay. Boundary and tie: with `attempt` starting at 1, `backoff_for(1) == 2s` and the loop exits at `attempt >= MAX_ATTEMPTS` after 4 sleeps, so the last attempt must not sleep at all; assert that the `MAX_ATTEMPTS`-th failure returns immediately. Fail loudly: a `CancelledError` during the sleep must abandon the attempt and leave the row reclaimable, not be swallowed by the `except httpx.HTTPError` (it is not an `HTTPError`, so confirm it propagates). Allow side that must still succeed: a delivery that succeeds on the first attempt never sleeps. Red-prove separately, by running each: (a) with a mock transport returning 500 twice then 200, assert under `asyncio.wait_for` that a second concurrent coroutine made progress during the backoff — red with `time.sleep`, green with `asyncio.sleep`; (b) assert total sleeps == 4 for a fully failing delivery.

### Critical: Worker uses ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`), `deliver` (`endpoint` used after the `with` block)
What is wrong: Both functions return or retain SQLAlchemy instances past the end of their `session_scope()`, then read `delivery.payload`, `delivery.attempts`, `delivery.id`, `endpoint.url`, and `endpoint.signing_secret` — attributes that are expired on commit and must be refreshed against a live session.
What breaks in production: The first attribute access after the batch is claimed raises `DetachedInstanceError`, which propagates through `asyncio.gather` and out of `run_worker`, so no webhook is ever delivered and the worker exits.
Fix: Stop passing ORM objects across session boundaries — have `_claim_batch` return plain data (`list[DeliveryJob]` frozen dataclasses carrying `id`, `endpoint_id`, `attempts`, `payload`), and have `deliver` load the endpoint's `url` and `signing_secret` into locals inside a session before the first `await`. Preserve: the claim must still flip rows to `in_flight` in the same transaction that reads them, so do not fix this by widening the session to span the HTTP calls (that would hold a DB connection for the full 30s timeout). Boundary and tie: a row whose endpoint was deleted between claim and load must be finished as `failed_permanent` with `detail="endpoint deleted"`, not crash — and a row claimed exactly at the batch limit boundary is either fully claimed or not claimed at all. Fail loudly: `session.get` returning `None` must raise a named error routed to that permanent-failure path rather than dereferencing `None`. Allow side that must still succeed: a normal batch of one pending row is delivered end to end. Red-prove by execution: run `_claim_batch` against a real session and access `rows[0].payload` after the context exits — red today; green after the dataclass conversion.

### Major: `in_flight` is a non-terminal state with no recovery path
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`, `_finish` is the only exit
What is wrong: A row leaves `in_flight` only when `deliver` reaches `_finish`, and `_claim_batch` selects only `status == "pending"`, so any worker crash, restart, deploy, or the lock expiring mid-batch strands rows in `in_flight` forever with no reaper and no timeout (R38 non-terminal transient state).
What breaks in production: Deliveries silently vanish after an ordinary deploy, and because `attempts` and `next_attempt_at` are never written between attempts there is no evidence of how far the chain got.
Fix: Add a `claimed_at TIMESTAMPTZ` column set at claim time, and have `_claim_batch` also select rows where `status = 'in_flight' AND claimed_at < now() - interval '10 minutes'`, resetting them to `pending`; persist `attempts` and the next `next_attempt_at` on every attempt, not only at the terminal state. Boundary and tie: a row whose `claimed_at` is exactly at the 10-minute mark is reclaimed (`<=`), and a reclaimed row keeps its accumulated `attempts` so the reclaim cannot reset the budget to zero and retry forever. Preserve: the claim must still prevent two concurrent workers from taking the same live row, so the reclaim window must exceed `REQUEST_TIMEOUT * MAX_ATTEMPTS`. Fail loudly: if `claimed_at` is NULL on an `in_flight` row (rows written before the migration), reclaim it and log the count explicitly rather than skipping it. Allow side that must still succeed: an actively-being-delivered row is not reclaimed. Red-prove separately, by running each: (a) backdate `claimed_at`, run `_claim_batch`, assert the row returns; (b) a row claimed one second ago is not returned (must stay green); (c) reclaim a row with `attempts=4` and assert the next failure is permanent.

### Major: `run_worker` raises `UnboundLocalError` and exits permanently on any error
File: `app/webhooks/delivery.py` — `run_worker`, `batch` referenced after the `try/finally`
What is wrong: `batch` is assigned inside the `try`, but `if not batch` is read after the block, so if `_claim_batch()` or `asyncio.gather` raises, the `finally` releases the lock and then the unbound `batch` raises `UnboundLocalError`; either exception escapes the `while True` and the coroutine terminates.
What breaks in production: A single transient database error permanently stops all webhook delivery with no restart and no alert, and the original exception is masked by the `UnboundLocalError`.
Fix: Initialise `batch: list = []` before the `try`, and wrap the body in `except Exception: log.exception(...)` followed by `await asyncio.sleep(poll_interval)` and `continue`, so the loop survives; add a consecutive-failure counter that escalates to `log.critical` after N iterations. Preserve: an unrecoverable programming error must still be visible — use `log.exception` so the traceback is not swallowed, and do not fix this by catching and ignoring. Boundary and tie: the counter resets on the first successful iteration; at exactly N consecutive failures it escalates once, not on every subsequent one. Fail loudly: a `CancelledError` must be re-raised, not caught by the broad handler, or shutdown hangs. Allow side that must still succeed: a normal iteration with an empty batch still sleeps `poll_interval` and continues. Red-prove separately, by running each: (a) patch `_claim_batch` to raise, assert the loop runs a second iteration; (b) assert the traceback of the *original* exception appears in the log record.

### Major: Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `_acquire_lock` does a `GET` then a separate `SET` then a separate `EXPIRE`, so two workers can both observe an empty key and both proceed, and the `finally` deletes `LOCK_KEY` without checking ownership, so a worker whose 60-second TTL expired mid-batch deletes the lock a *different* worker now holds.
What breaks in production: Two workers process overlapping batches and the same endpoint receives duplicate POSTs; the 60-second TTL is also far shorter than a batch of 100 deliveries with a 30-second timeout each, so expiry mid-batch is the normal case rather than the edge case.
Fix: Acquire with a single atomic `SET LOCK_KEY <uuid> NX EX 60` and release with a compare-and-delete Lua script that deletes only when the stored value equals this worker's uuid; renew the TTL from a background task while the batch runs, or size the TTL above the worst-case batch duration (`BATCH_SIZE` bounded concurrency × `REQUEST_TIMEOUT`). Preserve: the lock must still be released promptly on a clean exit so a restart is not blocked for a full TTL. Boundary and tie: two workers racing on `SET NX` — exactly one wins, and the loser must sleep rather than proceed; a lock whose TTL expires at the same instant the owner tries to release is a no-op delete, not an error. Fail loudly: a Redis connection error in `_acquire_lock` must return `False` (do not process) and log at error level — an unreachable Redis must never be read as "lock is free". Allow side that must still succeed: a single worker acquires, processes, and releases on every poll. Red-prove separately, by running each: (a) two concurrent `_acquire_lock()` calls against a real Redis → exactly one `True`; (b) worker B's release attempt while A holds the lock → key still present; (c) simulate a Redis error → `False` and no batch claimed.

### Major: Dispatcher swallows webhook enqueue failures with no durable record
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning(...)`
What is wrong: The enqueue runs after the event's `session_scope` has already committed and its failure is caught and logged at `warning` with no persisted marker and no retry, so the event row exists while the webhook rows do not (R9 — fire-and-forget outside the transaction).
What breaks in production: A transient database error or the unique-index violation described above drops the customer's webhooks entirely with the only evidence a warning line, and nothing in the system can later tell which events were never fanned out.
Fix: Enqueue the delivery rows inside the same transaction that writes the `Event` row so both commit or neither does, and leave only the *sending* asynchronous; if the enqueue must stay separate, persist a `webhook_enqueue_pending` marker on the event and add a reconciliation query that re-enqueues events lacking delivery rows. Preserve: a webhook failure must still not roll back the event itself once the marker approach is chosen — name which of the two semantics you want and implement one. Boundary and tie: an event whose org has zero matching endpoints legitimately produces zero delivery rows and must not be mistaken for "not yet enqueued" — record the enqueue as *done with zero rows*, not as absence (an in-band sentinel collision, R55). Fail loudly: log at `error`, not `warning`, and increment a counter a monitor can alert on. Allow side that must still succeed: a normal `invoice.paid` still returns `event_id` and enqueues its rows. Red-prove separately, by running each: (a) patch `enqueue_for_event` to raise, assert the event row is absent (transactional variant) or the marker is set (marker variant); (b) an org with no endpoints → enqueue recorded as complete with zero rows.

### Major: Only three event types ever reach webhooks, contradicting the documented "every event type"
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `docs/webhooks.md` — "An empty `event_types` subscribes the endpoint to every event type we emit"
What is wrong: `dispatch` calls `enqueue_for_event` only when `envelope.type in WEBHOOK_EVENT_TYPES` (three hardcoded strings), while `enqueue_for_event` itself treats an empty `endpoint.event_types` as "all" — so the documented contract is decided by a hardcoded set the customer cannot see and that no test or constant ties to the actual event catalogue (R42 class-membership derivation).

Preserve: an endpoint that subscribed to a specific type must keep receiving only that type. Fail loudly: if the catalogue cannot be enumerated at import time, fail process start rather than defaulting to an empty deliverable set (which would deliver nothing while looking healthy). Allow side that must still succeed: `invoice.paid` still reaches an endpoint that lists it. ### Major: `organizations.webhooks_enabled` is added but never read

### Major: 4xx responses are retried and backoff has no jitter, contradicting the documentation
File: `app/webhooks/delivery.py` — `deliver`, the `if 200 <= response.status_code < 300` branch; `backoff_for`
What is wrong: `docs/webhooks.md` states "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver` treats every non-2xx identically and retries it up to `MAX_ATTEMPTS`, and `backoff_for` returns a pure `2**attempt` with no jitter (R29 — the documented rationale does not match the code).
What breaks in production: A customer endpoint returning 400 or 404 is hammered five times per event, and because every delivery in a batch fails at the same instant their retries are perfectly synchronised, producing a thundering herd against an endpoint that is already unhealthy.
Fix: Branch explicitly — 2xx → `delivered`; 408 and 429 → retryable; other 4xx → `failed_permanent` immediately; 5xx, timeouts and connection errors → retryable — and add full jitter to `backoff_for` (`random.uniform(0, 2**attempt)` via `secrets.SystemRandom` or `random`, which is acceptable here because this value is not security material). Preserve: 5xx and connection errors must keep their five attempts, and the documented 2/4/8/16 must remain the *upper* bound of each step. Boundary and tie: 399 and 400 fall on opposite sides — assert both; 429 is the exception inside the 4xx range and must be asserted separately from 400. Fail loudly: a status code outside 100–599 (a broken proxy) must be treated as permanent with a named detail, not silently retried. Allow side that must still succeed: a 503 followed by a 200 still delivers. Red-prove separately, by running each: (a) mock transport returning 400 → exactly one request issued; (b) returning 429 then 200 → two requests; (c) with jitter, assert the delay is in `(0, 2**attempt]` over repeated draws, then remove the jitter and observe the "two consecutive delays differ" assertion red.
