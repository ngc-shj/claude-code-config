### Critical: deliveries endpoint is not tenant-scoped (IDOR)
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` line
What is wrong: The query filters on the caller-supplied `endpoint_id` only and never joins back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling routes added in the same file (`create_webhook_endpoint`, `list_webhook_endpoints`) do scope by `user.org_id` — the tenancy pattern was added but not propagated to the third route (R3, security-relevant).
What breaks in production: Any authenticated user can enumerate integer `endpoint_id`s and read every other organization's delivery history — event type, delivery status, and the response status we observed from their internal endpoint.
Fix: Change the query to `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` and raise `HTTPException(404)` when the endpoint row does not exist *or* belongs to another org (identical response for both, so the route is not an existence oracle). Preserve the behaviour that makes the route useful: an owner listing their own endpoint must still get the same rows in the same order — pin that with an allow-case test asserting a 200 and the exact delivery ids for the owning user, alongside the deny-case test asserting 404 **and** that the response body contains no delivery ids (RT8: status alone is not the assertion). Red-prove the two clauses with two separate mutations: (i) drop the `org_id` predicate — the deny test must red on the leaked ids, not merely on the status; (ii) drop the `endpoint_id` predicate — the allow test must red because rows from a sibling endpoint of the same org appear. Boundary and tie: an endpoint whose `org_id` equals the caller's is the single admitted case; a soft-deleted or `active=False` endpoint still belongs to its org and must remain readable by its owner, so do not fold `active` into this predicate. If `user.org_id` is absent or `None`, raise rather than letting the comparison evaluate — an unresolvable subject must deny loudly, not match `org_id IS NULL`.

### Critical: the signing secret is returned by the list endpoint on every read
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, key `"signing_secret"`
What is wrong: `to_dict()` embeds the signing secret and is used by `list_webhook_endpoints` as well as by the create route, so the secret is disclosed on every `GET /v1/settings/webhook-endpoints` — directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards"), which is R49 clause 2, a claim stronger than the implementation.
What breaks in production: The HMAC key that authenticates every outbound event is served on a read-only route, so any actor with a read-scoped token, any cached GET response, and any browser devtools log yields the ability to forge signed events to the customer's endpoint.
Fix: Remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held plaintext, so exactly one response carries it. Preserve what made the feature useful: the create response must still contain the secret — pin that with an allow-case test asserting `201` and a `signing_secret` starting with `whsec_`, paired with a deny-case test asserting the list route's payload has no key whose value starts with `whsec_` (assert on the value shape, not on the key name, so a rename does not restore the leak silently). Red-prove separately: (i) re-add the key to `to_dict()` — the list test must red; (ii) drop the explicit merge in the create route — the create test must red. Boundary and tie: the boundary is the single create response; if the create transaction rolls back after the secret was generated, the route must return an error rather than a partial body, and a second create for the same URL mints a distinct secret rather than reusing the first (state this in the docs alongside the rotation story, which the diff currently has no route for).

### Critical: signing secrets are generated with the `random` module, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: `random.choice` draws from a seeded Mersenne Twister, which is not cryptographically secure and whose internal state is recoverable from a modest number of observed outputs.
What breaks in production: An attacker who registers a handful of their own endpoints observes enough generator output to reconstruct the state and predict other tenants' signing secrets, letting them forge `invoice.paid` events into those tenants' systems.
Fix: Replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX`, `import secrets`, and delete the now-unused `random`/`string`/`_ALPHABET` — and rename `SECRET_BYTES` honestly, since the existing test `test_new_signing_secret_has_prefix_and_length` asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which is a *character* count and will red against `token_urlsafe` (32 bytes → 43 chars); update that assertion to `>= len(SECRET_PREFIX) + 43` rather than deleting it, because deleting the assertion is not fixing the test (Remedy Floor 4). Preserve the allow side: the prefix contract other systems match on must still hold — keep the `startswith(SECRET_PREFIX)` assertion, and add one asserting 1000 generated secrets are all distinct. Red-prove separately: (i) revert to `random.choice` seeded with `random.seed(0)` — a new test asserting two secrets generated after identical seeding differ must red; (ii) drop the prefix — the prefix test must red. Fail loudly: `secrets` failing to source entropy raises, and the create route must let that propagate as a 500 rather than falling back to any weaker generator. Boundary: `SECRET_BYTES = 32` is the floor, not a target — assert `>=`, so raising it later does not red the suite.

### Critical: the signature does not cover the timestamp, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`, the `hmac.new(secret.encode(), serialize(payload).encode(), ...)` line
What is wrong: `sign` MACs the payload alone and returns an *unauthenticated* timestamp, while `docs/webhooks.md` instructs receivers that "the signature is the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`" and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed" — the timestamp is attacker-mutable, so that check stops nothing (R49: the control is described as an enforceable boundary but implemented as none).
What breaks in production: An attacker who captures one signed `invoice.paid` request replays it indefinitely by rewriting `X-Acme-Timestamp` to now, and the receiver's documented freshness check accepts it because the signature was never bound to that value.
Fix: Change `sign` to compute `hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` over the exact bytes that will be transmitted (see the next finding — the two fixes must land together), and change `verify` to take the received timestamp and body as parameters instead of re-deriving a fresh timestamp: `verify(secret, timestamp, body, signature, tolerance_seconds=300)`. Preserve the allow side: a request signed now must still verify — pin it with a test that signs, verifies, and asserts `True`, plus a test at `now - 299s` asserting `True`. Red-prove each clause separately: (i) mutate only the timestamp in the header while leaving the signature intact — verification must red; (ii) mutate one byte of the body — verification must red; (iii) set the timestamp to `now - 301s` — verification must red on the tolerance branch specifically, with the failure naming staleness rather than digest mismatch. Fail loudly: a missing or non-integer timestamp header must return "cannot verify" (an explicit rejection), never be defaulted to `now`. Boundary and tie: `now - tolerance` is accepted and `now - tolerance - 1` is rejected (`<=` on the age comparison), and a timestamp in the future beyond a small clock-skew allowance is rejected too — state both in `docs/webhooks.md` in the same edit.

### Critical: the bytes we sign are not the bytes we send, so no customer verification can ever succeed
File: `app/webhooks/delivery.py` — `send_once`, `sign(endpoint.signing_secret, delivery.payload)` paired with `client.post(..., json=delivery.payload, ...)`
What is wrong: `signing.serialize` produces `json.dumps(payload, sort_keys=True)` (keys sorted, `", "` / `": "` separators) while `httpx` serializes the `json=` argument with its own compact, insertion-ordered encoding, so the HMAC is computed over a different byte string than the one placed on the wire — the exact same-team-owns-both-sides divergence R40 describes, and the in-repo tests pass vacuously because `verify` re-invokes `sign` rather than reading the request body.
What breaks in production: Every customer following `docs/webhooks.md` computes the HMAC over the raw request body and gets a mismatch, so 100% of deliveries are rejected as forged — a silent total-path failure that our own `delivered` status will nonetheless report as success.
Fix: Serialize once and send the resulting bytes: `body = serialize(delivery.payload).encode()`, `ts, signature = sign(endpoint.signing_secret, body)`, then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` — change `sign`/`verify` to accept the already-serialized `bytes` so no caller can re-serialize with different options, and delete the `dict`-taking overload rather than leaving both (a second entry point is how the divergence returns). Preserve the allow side and pin it with the round-trip test R40 requires: capture the request via `httpx.MockTransport`, feed `request.content` (the *actual* wire bytes, not the source dict) plus the captured timestamp header into `verify`, and assert `True` — the existing `test_verify_accepts_signature_produced_by_sign` cannot detect this class and must be replaced, not merely supplemented, since it compares `sign` against itself. Red-prove separately: (i) revert `send_once` to `json=delivery.payload` — the round-trip test must red on a digest mismatch; (ii) change `serialize` to `sort_keys=False` while leaving the producer path intact — a test asserting `serialize` is byte-stable across two dicts with the same pairs in different insertion order must red. Fail loudly: a payload containing a non-JSON-serializable value must raise at `serialize` and mark the delivery `failed_permanent` with a named reason, not be silently coerced. Boundary: define the canonical form exactly once (`sort_keys=True`, `separators=(",", ":")`, `ensure_ascii=False`, UTF-8) and document those four options in `docs/webhooks.md` so the receiver can reproduce them.

### Critical: customer-supplied endpoint URL is an unguarded SSRF sink
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; and `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only validation is a `startswith("http")` prefix test — it admits `http://`, admits any scheme spelled `http*` (`httpfoo://`), and applies no host policy at all, so `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:6379/` is an accepted endpoint; `follow_redirects=True` then lets a public-looking URL redirect into the same internal space at delivery time (RS3: an unvalidated externally-supplied value reaching an interpreter — here, the outbound HTTP client), and `docs/webhooks.md` asserts "Only `https://` URLs are accepted", which the code does not do (R49).
What breaks in production: Any tenant turns our delivery worker into a request proxy inside our network — reaching the cloud metadata service, unauthenticated internal admin ports, and Redis — with the HTTP status of each attempt handed back through the deliveries route as an oracle.
Fix: Validate at the schema boundary with a pydantic validator on `EndpointIn.url` that requires `parsed.scheme == "https"` exactly (equality, not `startswith`), a non-empty `hostname`, and no embedded credentials or fragment; reject with 422 naming which clause failed. Add a `_resolve_and_check(host)` helper in `app/webhooks/delivery.py` that resolves the hostname and rejects when any returned address `ip_address(a).is_private or is_loopback or is_link_local or is_reserved or is_multicast`, call it in `send_once` immediately before the POST (registration-time checks alone lose to DNS rebinding), and set `follow_redirects=False` so each hop is a fresh, re-checked delivery decision rather than a client-internal jump. Preserve the allow side: a genuine public HTTPS endpoint must still receive events — pin it with a test that a public-resolving host is accepted at registration and delivered to, so a fix that denies everything does not pass. Red-prove separately: (i) `https://127.0.0.1/x` — registration test must red-to-422 on the address clause; (ii) `http://hooks.example.com/x` — must red-to-422 on the scheme clause; (iii) a MockTransport returning `302` to `http://169.254.169.254/` — the delivery test must show no second request issued. Fail loudly: DNS resolution failing, or `ip_address` raising, must mark the attempt failed with a named reason and *not* proceed — "could not check" must not be spelled the same as "checked and clean". Boundary and tie: a hostname resolving to *both* a public and a private address is rejected (all-must-pass, not any), and IPv6-mapped IPv4 (`::ffff:10.0.0.1`) is normalized before the check.

### Critical: `verify` compares HMACs with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The digest comparison uses Python's short-circuiting `==` rather than a constant-time primitive (RS1).
What breaks in production: This is the reference verifier we ship and, per `docs/webhooks.md`, tell customers to mirror; where it is used server-side for inbound callbacks it leaks the expected digest byte-by-byte to a timing oracle, letting an attacker forge a signature without the secret.
Fix: `return hmac.compare_digest(expected, signature)`, after coercing both operands to `str` (or both to `bytes`) since `compare_digest` raises on mixed types — and coerce by rejecting the wrong type explicitly rather than by casting, so a non-string signature header denies instead of being stringified into a comparison. Update the "Compare it against your own computation using a constant-time comparison" line in `docs/webhooks.md` to name `hmac.compare_digest` so the sample and the prose agree. Preserve the allow side: `test_verify_accepts_signature_produced_by_sign` (in its rewritten, wire-bytes form) must still pass, and add its mirror asserting a signature differing only in the final hex character returns `False`. Red-prove separately: (i) revert to `==` — a test asserting `verify` is invoked through `hmac.compare_digest` (patch it and assert called) must red; (ii) pass `None` as the signature — a test asserting a clean `False`/rejection rather than a `TypeError` escaping to the caller must red. Boundary and tie: signatures of unequal length must return `False`, never raise, and the empty-string signature is a rejection, not a match.

### Critical: the worker uses ORM instances after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside the `session_scope` block) and `deliver` (`endpoint` read outside its `with`)
What is wrong: Both functions read attributes off SQLAlchemy instances after the owning session has committed and closed, and with the default `expire_on_commit=True` every attribute is expired at commit, so `delivery.attempts`, `delivery.payload`, `endpoint.signing_secret` and `endpoint.url` each trigger a refresh on a dead session.
What breaks in production: The worker raises `DetachedInstanceError` on the first delivery of the first batch — the feature never delivers a single event — while the rows it just flipped to `in_flight` stay in that state forever with no reaper.
Fix: Stop returning ORM instances across session boundaries: have `_claim_batch` return a list of plain dataclasses/dicts (`delivery_id`, `endpoint_id`, `event_id`, `attempts`, `payload`) built inside the session, and have `deliver` fetch the endpoint's `url` and `signing_secret` into locals inside a single session block before the HTTP call; `send_once` then takes those two values rather than a model. Preserve the allow side: `test_send_once_posts_the_signed_payload` must still pass against the new signature — update `FakeEndpoint` to the plain-value form rather than deleting the test, and add an integration test that runs `_claim_batch` against a real session and asserts the returned objects are readable *after* the block, since `FakeEndpoint`/`FakeDelivery` are hand-written doubles that structurally cannot exhibit detachment (RT1). Red-prove separately: (i) return the ORM rows from `_claim_batch` again — the integration test must red with `DetachedInstanceError` named in the failure; (ii) move the endpoint read in `deliver` back outside the `with` — the delivery test must red. Fail loudly: `session.get(WebhookEndpoint, endpoint_id)` returning `None` (endpoint deleted between claim and send) must mark the delivery `failed_permanent` with reason `endpoint_deleted`, not raise `AttributeError`. Boundary: a delivery claimed in the same transaction in which its endpoint is deactivated is still sent once — say so, or add the `active` re-check explicitly.

### Critical: the unique index on `event_id` alone makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: The uniqueness is global on `event_id`, but `enqueue_for_event` inserts one row per matching endpoint for a single event, so any org with two subscribed endpoints violates the constraint on `session.add_all`.
What breaks in production: The whole enqueue transaction raises `IntegrityError`, the dispatcher's blanket `except Exception` swallows it as a warning, and *every* webhook for that event is dropped — including the one for the first endpoint — with no delivery row and no retry.
Fix: Replace with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`, which is the constraint the design actually wants — one delivery per (endpoint, event) — and keep it, because it is what makes the documented "deduplicate on `event_id`" contract enforceable at our end rather than only at the customer's. Preserve the allow side: pin a test that enqueuing one event for an org with two active endpoints creates exactly two rows, alongside one asserting a second enqueue of the *same* event for the *same* endpoint does not create a third. Red-prove separately: (i) revert the index to `(event_id)` — the two-endpoint test must red on `IntegrityError`; (ii) drop the index entirely — the re-enqueue test must red on a duplicate row count. Fail loudly: change `enqueue_for_event` to `ON CONFLICT DO NOTHING` semantics (insert per row, or `postgresql.insert(...).on_conflict_do_nothing`) so a redelivery race is absorbed, while any *other* `IntegrityError` still propagates and is recorded rather than swallowed. Boundary: an event with zero matching endpoints inserts zero rows and returns `0` — that is success, not an error, and the dispatcher must not log it as a failure.

### Critical: the `status` CHECK constraint rejects the value the code writes on permanent failure
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`
What is wrong: The constraint allows `'failed'`, while `app/webhooks/delivery.py` writes `"failed_permanent"` and `app/webhooks/models.py` declares `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")` — three spellings of one enum across two files and a migration, never cross-checked (R2/R40).
What breaks in production: Every exhausted-retry delivery raises a `CheckViolation` on commit inside `_finish`, the update rolls back, and the row stays `in_flight` forever — so the permanent-failure path, the one that matters for support, never records anything.
Fix: Change the migration's CHECK list to `('pending', 'in_flight', 'delivered', 'failed_permanent')` and import the enum from a single source — have `models.STATUSES` be the only literal list, and add a test that reads the `CHECK` clause from the migration file and asserts set-equality with `models.STATUSES`, so the two can never drift again (`STATUSES` is currently defined and never referenced anywhere in the diff — the constant exists but nothing consults it). Preserve the allow side: the `delivered` and `pending` transitions must still commit — pin one test per legal status writing and re-reading the row. Red-prove separately: (i) add `"failed"` to `models.STATUSES` — the migration/constant parity test must red; (ii) write `"expired"` from `_finish` — the write test must red with the constraint name in the failure. Fail loudly: `_finish` must assert `status in STATUSES` before the write so an unknown status fails at the call site with a readable message rather than as an opaque DB error at commit. Boundary and tie: `attempts == MAX_ATTEMPTS` is the transition into `failed_permanent` (the current `attempt >= MAX_ATTEMPTS` is right); state that a delivery already `delivered` is never re-transitioned, and make `_finish` a no-op-with-warning if it is.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` times concurrently, but the retry backoff uses the blocking `time.sleep`, which stalls the event loop rather than yielding.
What breaks in production: One failing endpoint freezes the entire process for up to 30 seconds of accumulated backoff (2+4+8+16) per delivery, serializing what was written as concurrent fan-out and stalling every other delivery, the Redis lock refresh, and any other coroutine sharing the loop.
Fix: `await asyncio.sleep(delay)` (`asyncio` is already imported) — but the deeper repair is to stop retrying in-process at all: persist `attempts` and `next_attempt_at = now + backoff_for(attempt)`, set the row back to `pending`, and return, letting the next `_claim_batch` pick it up; the in-loop retry is what makes a worker restart lose all progress (see the `in_flight` finding). Preserve the allow side: the retry *behaviour* must survive the change — pin a test that a delivery failing once and succeeding on the second claim ends `delivered` with `attempts == 2`, so "fix" by removing retries entirely does not pass. Red-prove separately: (i) restore `time.sleep` — a test asserting the loop stays responsive (a concurrently scheduled task completes within the backoff window) must red; (ii) remove the `next_attempt_at` update — the two-claim test must red because the row is re-claimed immediately with the same attempt count. Fail loudly: if `backoff_for` returns a non-positive or absurd delay, raise rather than busy-looping. Boundary and tie: `next_attempt_at <= now` is the claim predicate, so a row scheduled exactly at `now` is claimed in this pass, and two rows sharing a `next_attempt_at` are ordered by primary key (see the ordering finding).

### Critical: the dispatch lock is a non-atomic check-then-set and is released by whoever finishes
File: `app/webhooks/delivery.py` — `_acquire_lock` and the `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` then `set` then `expire` is three round-trips with no atomicity, so two workers both observe an empty key and both "acquire"; a crash between `set` and `expire` leaves a lock with no TTL; and the unconditional `delete` in `finally` removes the key even when the 60-second TTL has already expired and a *different* worker owns it — while `_claim_batch` selects without `FOR UPDATE SKIP LOCKED`, so nothing below the lock prevents double-claiming either.
What breaks in production: The same signed `invoice.paid` event is POSTed twice to a customer endpoint by two workers — and because a batch can hold the lock far longer than its 60-second TTL (up to five 30-second HTTP timeouts plus 30 seconds of backoff), that overlap is the normal case, not a rare race; alternatively one crash wedges dispatch permanently behind a TTL-less key.
Fix: Acquire with a single atomic call carrying a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — and release with a compare-and-delete Lua script that deletes only when the stored value equals `token`, so a worker can never drop another's lock. Independently, make the claim safe on its own: add `.with_for_update(skip_locked=True)` to `_claim_batch`, which is the actual correctness boundary (the Redis lock is at best an optimization, and per R49 should be documented as a best-effort tripwire, not as the mutual-exclusion guarantee). Preserve the allow side: a single worker must still claim and dispatch — pin a test that one worker processes a batch end-to-end, so a fix that always fails to acquire does not pass. Red-prove separately: (i) revert to `get`+`set` and run two acquire calls concurrently — a test asserting exactly one succeeds must red; (ii) revert to the unconditional `delete` and have worker A release after B acquired — a test asserting B's token still holds the key must red; (iii) remove `skip_locked` — a two-session claim test asserting disjoint id sets must red. Fail loudly: a Redis error in `_acquire_lock` must return `False` and log, never be treated as "no lock present, proceed". Boundary and tie: set `LOCK_TTL_SECONDS` above the worst-case batch wall time (`MAX_ATTEMPTS * REQUEST_TIMEOUT` plus total backoff) or renew it mid-batch, and state which side owns the lock at the instant of expiry — with compare-and-delete, neither can corrupt the other.

### Major: `in_flight` is a non-terminal state with no reaper and no persisted progress
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `deliver` (`attempt` is a local, `next_attempt_at` never rewritten)
What is wrong: A row enters `in_flight` at claim time and only leaves it if the same in-process loop reaches `_finish`; `attempts` and `next_attempt_at` are never persisted between retries, so a deploy, an OOM, or any exception outside `httpx.HTTPError` strands the row (R38 non-terminal transient state).
What breaks in production: Every worker restart permanently loses the in-flight batch — up to 100 customer events silently never delivered and never surfaced, since nothing queries for stale `in_flight` rows.
Fix: Persist progress on every attempt (`attempts = attempt`, `next_attempt_at = now + backoff_for(attempt)`, `status = "pending"`) instead of holding it in a local, and add a reaper that resets rows with `status = 'in_flight' AND updated_at < now() - lease_interval` back to `pending` with `attempts` unchanged, running at the top of each `run_worker` pass. Preserve the allow side: a healthy delivery must still terminate — pin a test that a 200 response leaves the row `delivered` and that the reaper does *not* touch a row updated one second ago. Red-prove separately: (i) kill the coroutine between claim and finish — a test asserting the reaper returns the row to `pending` within the lease must red when the reaper is removed; (ii) drop the `attempts` persistence — a test asserting a resumed delivery starts from attempt 2, not 1, must red (otherwise a row retries forever). Fail loudly: a row exceeding `MAX_ATTEMPTS` that the reaper picks up goes to `failed_permanent` with reason `abandoned`, not back to `pending`. Boundary and tie: `updated_at < now() - lease` is exclusive, so a row exactly at the lease edge is left alone this pass and reaped on the next.

### Major: any non-HTTP exception terminates the worker loop entirely
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `deliver` catches only `httpx.HTTPError`, `gather` is called without `return_exceptions=True`, and `run_worker`'s `try` has only a `finally` — so a single DB error, a `DetachedInstanceError`, or a JSON serialization failure propagates out of `while True` and ends the coroutine.
What breaks in production: One malformed payload kills webhook delivery process-wide until someone notices, and every other delivery in that batch is left `in_flight` with no reaper.
Fix: Use `results = await asyncio.gather(..., return_exceptions=True)`, log each returned exception with its `delivery_id`, and wrap the body of the `while True` in `try/except Exception` that logs and continues after a short sleep, so one poisoned row cannot end the loop. Preserve the allow side and what makes failure visible: do not swallow — every caught exception must be logged at `error` with the delivery id, and pin a test asserting the log record is emitted, so "fix by catching" does not become "fix by hiding" (Remedy Floor 4). Red-prove separately: (i) make one `deliver` raise `RuntimeError` — a test asserting the remaining deliveries still complete must red without `return_exceptions`; (ii) make `_claim_batch` raise — a test asserting the loop survives and retries next tick must red without the outer handler. Fail loudly: a run of consecutive failed passes above a threshold should stop the loop with a fatal log rather than spinning silently — name that threshold. Boundary: the very first pass failing is still a retry, not a fatal, so the counter starts at zero and trips at N, not N-1.

### Major: the documentation describes a system the code does not implement
File: `docs/webhooks.md` — the "Registering an endpoint" and "Retries" sections
What is wrong: Four load-bearing claims are false against the diff — "Only `https://` URLs are accepted" (the check is `scheme.startswith("http")`), "it cannot be read back afterwards" (`to_dict` returns the secret on the list route), "backoff is exponential with jitter" (`backoff_for` is `2**attempt` with no jitter, and the shipped test `test_backoff_grows_exponentially` pins the exact non-jittered values), and "a 4xx is permanent and we stop immediately" (`deliver` retries every non-2xx up to `MAX_ATTEMPTS`) — R29/R49, a claim stronger than the implementation.
What breaks in production: Customers size their infrastructure and their own retry handling on these statements, and our on-call reads them as the contract during an incident — a 4xx-returning endpoint gets five times the traffic the docs promise, and thundering-herd retries hit synchronously because the promised jitter does not exist.
Fix: Make the code match the doc where the doc states the better behaviour, and correct the doc where it does not: (a) enforce `scheme == "https"` (covered by the SSRF finding); (b) drop the secret from `to_dict` (covered above); (c) add jitter as `backoff_for(attempt) * uniform(0.5, 1.5)` in a separate `next_delay_for(attempt)` used by the scheduler, keeping the pure `backoff_for` and its existing exact-value test intact so the deterministic base remains testable (Remedy Floor 4); (d) classify responses — `400 <= code < 500 and code not in (408, 429)` → `failed_permanent` immediately, everything else retried. Preserve the allow side: a 500 and a 429 must still retry — pin one test per class (2xx→delivered, 404→failed_permanent on attempt 1, 500→retried, 429→retried). Red-prove separately: (i) make the classifier retry 404 — the permanent test must red; (ii) make it stop on 500 — the retry test must red; (iii) pin jitter bounds and remove the multiplier — the bounds test must red. Boundary and tie: 399 and 400 fall on opposite sides, 499/500 likewise, and `200`/`299` inclusive remain success — state each edge in `docs/webhooks.md` in the same commit.

### Major: the dispatcher's hardcoded event allowlist silently drops subscriptions the API accepts
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; and `app/api/routes/settings.py` — `EndpointIn.event_types`
What is wrong: Delivery is gated on a three-element set literal in the dispatcher, while `create_webhook_endpoint` accepts any `list[str]` without validating it against that set and `docs/webhooks.md` promises an empty `event_types` "subscribes the endpoint to every event type we emit" (R12: the enum group and its call sites are not cross-checked).
What breaks in production: A customer subscribing to any event outside the three literals gets a 201 and then silence forever, with no error anywhere to diagnose it; and the empty-list case delivers only three of our event types despite the documented "every event type".
Fix: Move the allowlist into `app/webhooks/models.py` as `DELIVERABLE_EVENT_TYPES`, import it in both the dispatcher and the route, and reject unknown members at the schema boundary with a 422 naming the unsupported values — so the promise and the enforcement read from one list. Update the doc sentence to "every event type in the supported list" and render that list in the doc from the same constant. Preserve the allow side: an endpoint registered with a supported type, and one registered with `[]`, must both receive matching events — pin both. Red-prove separately: (i) register `["invoice.refunded"]` — the 422 test must red when the validator is removed; (ii) add a type to `DELIVERABLE_EVENT_TYPES` without touching the dispatcher — a parity test asserting the dispatcher gate and the validator read the same object must red if either re-hardcodes a literal. Fail loudly: an event dispatched whose type is *not* in the list and for which some endpoint explicitly subscribed must log at `warning` naming both, rather than passing the `if` silently. Boundary: `[]` means "all supported", and an endpoint subscribed to a type later removed from the list stops receiving without erroring — say which, in the doc.

### Major: `organizations.webhooks_enabled` is added but never consulted
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE;`
What is wrong: The migration adds a per-org kill switch defaulting to `FALSE`, but nothing in the diff reads it — `enqueue_for_event` filters only on `WebhookEndpoint.active`, and no model field or route exposes it (R41: a declared capability with no backing path).
What breaks in production: The feature ships on for every org that registers an endpoint, despite a schema that says it is off by default — and when an incident calls for cutting outbound webhooks for one tenant, the switch operators will reach for does nothing.
Fix: Add `webhooks_enabled` to the `Organization` model and join it into `enqueue_for_event`'s endpoint query (`.join(Organization).filter(Organization.webhooks_enabled.is_(True))`), and make `create_webhook_endpoint` return 409 with a named reason when the caller's org has it false — so the flag governs both enqueue and registration rather than one of the two. Preserve the allow side: an enabled org must still enqueue — pin a test that flipping the flag to `TRUE` produces delivery rows, next to one asserting `FALSE` produces zero rows *and* leaves no partially-written state (RT8: assert the absence of the mutation, not only the count). Red-prove separately: (i) drop the join — the disabled-org test must red on rows appearing; (ii) drop the 409 — the registration test must red. Fail loudly: an org row that cannot be loaded must deny enqueue, not default to enabled. Boundary: the flag is read at enqueue time, so events already enqueued before the flip are still delivered — state that, or drain them explicitly.

### Major: webhook enqueue happens outside the event transaction and its failure is swallowed
File: `app/events/dispatcher.py` — the `try: await webhook_delivery.enqueue_for_event(...) except Exception as exc: log.warning(...)` block
What is wrong: The event row commits in its own `session_scope`, then `enqueue_for_event` opens a second, independent transaction, and any failure between them is downgraded to a `warning` with no retry, no dead-letter, and no bit on the event row recording that fan-out never happened (R9/R5: the "event persisted and its side effect enqueued" invariant is not atomic across the split).
What breaks in production: A transient DB blip between the two transactions loses the webhook for that event permanently and invisibly — `dispatch` still returns the event id as success, and nothing can reconstruct which events were skipped.
Fix: Enqueue inside the same transaction as the event insert (both are DB writes; there is no external call to keep out of the transaction), so the delivery rows and the event commit or roll back together — or, if the split must stay, record the fan-out state on the event row and add a sweeper that enqueues for events with `webhooks_enqueued IS FALSE` older than a minute. Preserve the allow side: `dispatch` must still return the event id and still notify in-process subscribers when enqueue succeeds — pin that, so a fix that makes enqueue failure fatal to the whole dispatch is caught. Red-prove separately: (i) make `enqueue_for_event` raise and assert the event row is absent (atomic variant) or that the sweeper later creates the rows (split variant) — must red without the change; (ii) narrow the `except` to the exception types actually recoverable and assert a `TypeError` from a signature change propagates rather than being logged as a warning — must red against the current blanket `except Exception`. Fail loudly: log at `error` with the event id and increment a counter, never `warning`, and make the metric the thing alerting reads. Boundary: an event with zero subscribed endpoints is a successful enqueue returning 0 and must not be swept repeatedly.

### Major: three new routes ship with no rate limiting and no cap on endpoints per org
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`
What is wrong: None of the new routes carries a rate-limit dependency, and nothing bounds how many endpoints one org may register (RS2).
What breaks in production: One tenant registers thousands of endpoints and every dispatched event fans out into thousands of outbound POSTs from our worker pool — a self-inflicted amplification DoS — while the unauthenticated-adjacent create route mints unbounded secret-bearing rows.
Fix: Attach the project's existing rate-limit dependency to all three routes (the diff shows no such helper, so if none exists this is the question form: which shared limiter do the other routes in `app/api/routes/` use, and does adding it here suffice?), and add a per-org endpoint cap enforced inside the create transaction with `SELECT count(*) ... FOR UPDATE` on the org row, returning 409 naming the limit. Preserve the allow side: a normal tenant creating their first, second, and Nth endpoint must still get 201 — pin the case at `count == limit - 1`. Red-prove separately: (i) create at `count == limit` — the 409 test must red without the cap, and must assert no row was inserted, not only the status; (ii) exceed the rate limit — the 429 test must red without the dependency. Fail loudly: if the counter query fails, deny the create rather than admitting it. Boundary and tie: the cap admits exactly `limit` endpoints (the `limit`-th create succeeds, the `limit + 1`-th is refused), and two concurrent creates at `limit - 1` must not both succeed — which is what the row lock buys.

### Major: `limit` on the deliveries route has a floor but no ceiling
File: `app/api/routes/settings.py` — `list_deliveries`, `limit: int = Query(50, ge=1)`
What is wrong: `ge=1` bounds the parameter from below only, so `?limit=100000000` is accepted and passed straight to `.limit()` (RS3: a request parameter reaching a query without a validated range).
What breaks in production: One request materializes every delivery row for an endpoint — each carrying a JSONB `payload` — into the API process, exhausting memory and blocking the worker that served it.
Fix: Change to `Query(50, ge=1, le=200)` so the framework rejects out-of-range values at the boundary with a 422 rather than deep in the query layer, and add keyset pagination (see the ordering finding) so callers who legitimately need more can still get it — capping without a pagination path removes the feature rather than fixing it (Remedy Floor 4). Preserve the allow side: `?limit=200` must still return 200 with up to 200 rows — pin it beside the `?limit=201` → 422 case. Red-prove separately: (i) remove `le` — the 422 test must red; (ii) remove the pagination cursor — a test fetching page two must red on repeated rows. Fail loudly: a non-integer `limit` must 422, not be coerced. Boundary and tie: 200 is accepted and 201 is refused, and a page ending inside a run of rows sharing `created_at` must not drop the tied rows.

### Major: the signature header is logged at INFO on every delivery attempt
File: `app/webhooks/delivery.py` — `send_once`, `log.info("POST %s headers=%s", endpoint.url, headers)`
What is wrong: The whole header dict — including `X-Acme-Signature` and `X-Acme-Timestamp` — is written to the application log on every attempt.
What breaks in production: Logs are shipped, indexed, and readable by staff and tooling that should not hold delivery credentials; anyone with log access can replay a captured signed request verbatim to the customer's endpoint (and today, with the timestamp unsigned, indefinitely).
Fix: Log the endpoint id, the delivery id, and the header *names* only — `log.info("POST delivery=%s endpoint=%s headers=%s", delivery.id, endpoint.id, sorted(headers))` — and keep the log line, because it is the only trace of an outbound attempt (Remedy Floor 4). Preserve the allow side: the record must still let an operator correlate an attempt with a delivery row — pin a test asserting the emitted record contains the delivery id. Red-prove separately: (i) restore the value-bearing format — a test asserting no emitted log record contains the `sha256=` prefix must red; (ii) drop the delivery id — the correlation test must red. Fail loudly: keep the assertion in the test, not a lint rule that can be suppressed. Boundary: this applies to the failure path too — the `log.warning("delivery %s failed (%s), retrying...")` line interpolates `detail`, which is `response.text` from an attacker-controlled endpoint, so cap and escape it there as well.

### Major: unbounded attacker-controlled response bodies are read into memory and stored
File: `app/webhooks/delivery.py` — `_finish(delivery.id, "delivered", attempt, response.status_code, response.text)` and `detail = f"HTTP {response.status_code}: {response.text}"`
What is wrong: `response.text` is the customer endpoint's full response body with no size limit, and it is both formatted into a log line and written to the `response_body TEXT` column.
What breaks in production: A hostile or misbehaving endpoint returning a multi-gigabyte body OOMs the worker and, short of that, fills the deliveries table and the log pipeline with junk we pay to store.
Fix: Cap the read — set `max_bytes` on the client or read via `response.aiter_bytes()` up to a `MAX_RESPONSE_BYTES` constant (e.g. 8192) — and store `body[:MAX_RESPONSE_BYTES]` with an explicit `"…truncated"` marker so the truncation is visible rather than mistaken for the endpoint's whole reply (Remedy Floor 4: the diagnostic value is what must be preserved). Preserve the allow side: a small body must still be stored verbatim — pin a test that a 20-byte response round-trips unchanged. Red-prove separately: (i) remove the cap and feed a 1 MB MockTransport body — a test asserting the stored value's length is `<= MAX_RESPONSE_BYTES + len(marker)` must red; (ii) remove the marker — a test asserting truncated values are distinguishable from exact-length ones must red. Fail loudly: a body that exceeds the cap mid-stream aborts the read and records `response_truncated`, not a silent partial. Boundary and tie: a body of exactly `MAX_RESPONSE_BYTES` is stored without the marker; `MAX_RESPONSE_BYTES + 1` gets it.

### Major: naive and aware datetimes are mixed, and the migration's column types contradict the models
File: `app/webhooks/delivery.py` — `next_attempt_at=datetime.utcnow()` in `enqueue_for_event`; `migrations/0042_webhook_delivery.sql` — `created_at/next_attempt_at/updated_at TIMESTAMP`
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` while `_claim_batch` compares against an aware `datetime.now(timezone.utc)` and `models._now()` is aware, and the migration declares `TIMESTAMP` (without time zone) for columns the ORM declares as `DateTime(timezone=True)`.
What breaks in production: On any host whose local zone is not UTC, the stored instants and the comparison instant differ by the offset, so freshly enqueued deliveries are either claimed hours late or (with a negative offset) all claimed at once — and the mismatch is invisible in a UTC-configured CI, which is where it will be tested.
Fix: Replace `datetime.utcnow()` with the module-local aware helper — import and call `models._now()` (promote it to a public `now()`), since a UTC-aware "now" helper already exists in this very diff and the delivery module reimplements it with the naive variant (R1) — and change all three columns in the migration to `TIMESTAMPTZ` to match `DateTime(timezone=True)`. Preserve the allow side: an immediately-due delivery must still be claimed on the next pass — pin a test that a row enqueued at `now` is returned by `_claim_batch`. Red-prove separately: (i) restore `datetime.utcnow()` and run the test under `TZ=Asia/Tokyo` — the claim test must red (this is also the CI gap: the suite must run at least one non-UTC job); (ii) revert the column to `TIMESTAMP` — a test asserting a round-tripped value retains its `tzinfo` must red. Fail loudly: add an assertion in `enqueue_for_event` that the value passed is `tzinfo`-aware, so a naive value fails at the write with a named message rather than skewing silently. Boundary and tie: `next_attempt_at <= now` claims a row scheduled exactly now, and rows sharing the instant are ordered by primary key.

### Major: the tests cannot fail for the defects that matter, and most new code has none
File: `tests/webhooks/test_delivery.py` — `test_verify_accepts_signature_produced_by_sign`, and the absent coverage for `enqueue_for_event` / `deliver` / `run_worker` / `_claim_batch` / `_acquire_lock` / the three routes
What is wrong: `verify` is implemented by calling `sign`, so the round-trip test asserts `sign == sign` and is structurally incapable of detecting the signed-bytes-vs-wire-bytes divergence or the missing timestamp binding (RT5: the test's call path does not include the real boundary it claims to cover); meanwhile six new production symbols and all three new routes ship with no test at all (RT6), and `FakeEndpoint`/`FakeDelivery` are hand-written doubles whose attribute access can never exhibit the detached-instance failure the real models do (RT1).
What breaks in production: The suite is green while every customer verification fails, the worker cannot deliver, and the tenancy hole on `list_deliveries` is unexercised — coverage that reads as assurance and provides none.
Fix: Replace the self-referential round-trip with the wire-level one described in the serialization finding (verify against `request.content` captured by `MockTransport`, plus the captured timestamp header), and add, per the RT6 disposition, tests in this same PR for: `enqueue_for_event` fan-out to two endpoints and the empty-`event_types` case; `deliver` on 2xx / 4xx / 5xx / connect-error; `_claim_batch` against a real session asserting the returned objects are usable after the block; `_acquire_lock` under two concurrent callers; and a route-level test per endpoint including the cross-org 404. Preserve the allow side: keep the existing passing assertions (prefix, digest length, backoff values, `MAX_ATTEMPTS`) — they are cheap and pin real contracts; the fix is additive, not a rewrite. Red-prove: for each added test, run the single mutation named in the corresponding finding above and confirm it reds for the reason the failure output states, one mutation per assertion — a suite where one mutation reddens everything has not been red-proved. Fail loudly: mark the DB-backed tests so a missing Postgres fixture errors as "cannot run" rather than being skipped into a green run. Boundary: at minimum, every symbol listed above has one test whose deletion changes the suite result.
