### Critical: `list_webhook_endpoints` returns every endpoint's signing secret
File: app/webhooks/models.py — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`), consumed by app/api/routes/settings.py — `list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally includes the HMAC signing secret and is reused verbatim by the GET listing route, contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: every caller of `GET /v1/settings/webhook-endpoints` — including any read-scoped API key, browser session, proxy log, or client-side cache — receives live secrets that let the holder forge signed events for that organization, and each disclosed secret must be rotated because it is already published.
Fix: Remove `signing_secret` from `to_dict()` and return the secret from exactly one place — construct the 201 body in `create_webhook_endpoint` as `endpoint.to_dict() | {"signing_secret": secret}`, where `secret = new_signing_secret()` is held in a local and passed to the model. Preserve the behaviour that makes the feature usable: the create response must still carry the secret exactly once (do not "fix" this by removing the secret from the create path too, which would make registered endpoints unverifiable). Pin both sides: an allow-case test asserting `POST /v1/settings/webhook-endpoints` response body contains `signing_secret` matching `^whsec_`, and a deny-case test asserting `signing_secret not in` the JSON of every element of the `GET` listing and of `GET .../deliveries`. Red-prove each separately by execution: (i) re-add `"signing_secret"` to `to_dict()` and observe only the deny test red; (ii) drop the `| {"signing_secret": ...}` merge in the create route and observe only the allow test red. Fail loudly where the check cannot run: if `new_signing_secret()` returns a falsy or non-`whsec_`-prefixed value, raise in the route rather than persisting an endpoint, so "no secret generated" is not spelled the same as "secret withheld from the listing". Boundary and tie: the secret is readable for exactly the create response and no other response; two endpoints registered in the same request-second are distinguished by row id, not by secret, so the listing must remain able to identify an endpoint by `id` after the secret is dropped.

### Critical: `list_deliveries` has no tenancy filter — cross-organization read
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` while the two sibling routes added in the same file both filter on `org_id` (`create_webhook_endpoint` sets `org_id=user.org_id`; `list_webhook_endpoints` filters `WebhookEndpoint.org_id == user.org_id`), so the org predicate was propagated to two of three new routes and missed on the third (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` values and read another organization's delivery history — event ids, event types, delivery status and upstream response codes — a cross-tenant data leak reachable with a single integer increment, and `docs/webhooks.md` documents this route as scoped to "an endpoint belonging to your organization", so the gap is silent.
Fix: Join the tenancy predicate into the query — `.join(webhook_models.WebhookEndpoint, webhook_models.WebhookEndpoint.id == webhook_models.WebhookDelivery.endpoint_id).filter(webhook_models.WebhookEndpoint.org_id == user.org_id, webhook_models.WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the join yields nothing, so the response does not disclose whether the id exists. Preserve what the route is for: the owning organization must still get its rows, in `created_at DESC` order, honouring `limit`. Pin both sides and red-prove each by execution: (i) allow — a request from the owning org for an endpoint with 3 deliveries returns 3 rows; mutate by making the filter `org_id != user.org_id` and observe this test red; (ii) deny — a request from a second org for that same `endpoint_id` returns 404 with an empty body; mutate by deleting the `org_id` clause and observe *this* test red and the allow test still green (RT8: the deny test must assert the row payload is absent, not only the status). Fail loudly when the check cannot run: if `user.org_id` is `None`, raise 401 rather than issuing a query with a null-comparing predicate, which in SQL matches nothing and would be indistinguishable from "org has no deliveries". Boundary and tie: an endpoint whose `org_id` equals the caller's is allowed and one that differs is denied; a delivery whose endpoint row has been deleted has no org and must be denied, not orphan-visible.

### Critical: the signature is computed over different bytes than the request body
File: app/webhooks/delivery.py — `send_once` (`sign(endpoint.signing_secret, delivery.payload)` then `client.post(..., json=delivery.payload)`); app/webhooks/signing.py — `serialize`
What is wrong: `serialize()` produces `json.dumps(payload, sort_keys=True)` with Python's default `", "` / `": "` separators, while httpx re-serializes `json=` itself with its own encoder (compact separators, insertion key order), so the MAC covers a byte string the receiver never sees — for the fixture payload `{"id": ..., "type": ..., "amount_cents": ...}` the keys are already out of sorted order, so the two encodings differ today, not only in an edge case (R40: producer wire shape vs strict consumer, same team owning both sides).
What breaks in production: every customer who implements the documented verification — HMAC over the raw request body — computes a different digest and rejects 100% of deliveries, and because the retry loop treats a 4xx as retryable this failure is amplified into 5 attempts per event against every endpoint.
Fix: Send the exact bytes that were signed. Change `serialize` to a canonical encoder — `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")` — have `sign` return that byte string alongside `(timestamp, signature)`, and have `send_once` post it with `content=body` plus an explicit `Content-Type: application/json` header instead of `json=`. Preserve the behaviour the current code gets right: the request must still be valid JSON with the same logical fields, and `Content-Type` must remain `application/json` (do not fix this by dropping canonicalization — the deterministic ordering is what makes third-party verification reproducible). Pin both sides with a round-trip test through the *actual* producer output and the *actual* consumer: capture `request.content` in the `MockTransport` handler and assert `signing.verify(SECRET, captured_body, captured_headers[SIGNATURE_HEADER])` is true (allow side), and assert it is false after flipping one byte of the captured body (deny side). Red-prove each clause by execution: (i) revert `content=` to `json=` and observe the allow assertion red; (ii) drop `sort_keys=True` and observe the allow assertion red for a two-key payload written out of order; (iii) drop the byte-flip assertion and confirm the test still passes, proving that assertion is load-bearing. Fail loudly when the check cannot run: raise from `send_once` if the payload is not JSON-serializable rather than posting an empty body, so "could not encode" is not spelled the same as "encoded to nothing". Boundary and tie: the signed unit is the complete request body including the outermost braces, and two payloads that differ only in key order must produce identical bytes and therefore identical signatures — state that in the doc so a verifier knows re-encoding its parsed object is not safe.

### Critical: the timestamp is not covered by the MAC, so the documented replay window is unenforceable
File: app/webhooks/signing.py — `sign` (`hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`)
What is wrong: `sign` emits a `X-Acme-Timestamp` header but the HMAC input is the payload alone, while `docs/webhooks.md` states the signature is "the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`" — the implementation is weaker than the documented control (R49) and the doc claim is false (R29).
What breaks in production: an attacker who captures one delivery can replay it indefinitely by rewriting the unauthenticated timestamp header to `now`, so the five-minute freshness window the doc says "stops a captured request from being replayed" stops nothing, and a receiver that trusts the doc has silently no replay protection on financial events like `invoice.paid`.
Fix: Bind the timestamp into the MAC — compute `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)` where `body` is the canonical bytes from the finding above, and update `verify` to take `(secret, timestamp, body, signature)` so it recomputes over the same tuple. Preserve the documented header contract: `X-Acme-Timestamp` stays unix seconds and `X-Acme-Signature` stays `sha256=<hex>` (do not fix this by dropping the timestamp header, which would remove the freshness signal entirely). Pin both sides: allow — a signature produced at time T verifies at T+60s; deny — the same body with the timestamp header rewritten to T+3600 fails verification. Red-prove each by execution: (i) remove the `f"{timestamp}."` prefix from `sign` only and observe the deny test go green (i.e. the replay succeeds), which is the mutation that proves the deny test discriminates; (ii) remove the freshness check from the verifier and observe the deny test red. Fail loudly: a non-numeric or absent timestamp header must be a rejection that names itself (`invalid timestamp`), never a skipped freshness check. Boundary and tie: with a 300-second tolerance, a timestamp exactly 300s old is accepted and 301s is rejected, and clock skew is handled by rejecting timestamps more than 300s in the *future* as well — state both edges in `docs/webhooks.md` alongside the corrected preimage.

### Critical: `verify` compares HMAC digests with `==`
File: app/webhooks/signing.py — `verify` (`return expected == signature`)
What is wrong: the signature comparison uses Python's short-circuiting string equality rather than a constant-time primitive (RS1), and this is the reference implementation the project publishes and its own tests exercise.
What breaks in production: an attacker with repeated access to a verifying endpoint can recover a valid signature byte-by-byte from response-time differences, and because this function is the pattern customers copy, the weakness propagates to every receiver.
Fix: Replace the comparison with `hmac.compare_digest(expected, signature)`, guarding for non-ASCII input by encoding both sides first. Preserve the function's contract: it must still return `True` for a signature the local `sign` produced and `False` for one produced with a different secret — the two existing tests (`test_verify_accepts_signature_produced_by_sign`, `test_verify_rejects_a_signature_made_with_another_secret`) are the allow and deny sides and must stay green unchanged. Red-prove by execution: (i) mutate `compare_digest` back to `==` and confirm a timing test over ~10k samples on a first-byte-mismatched vs last-byte-mismatched signature shows a measurable delta while the functional tests stay green — this is what proves the functional tests alone never covered this clause; (ii) mutate `expected` to a constant and observe the deny test red. Fail loudly: if `signature` is not a `str`/`bytes` or lacks the `sha256=` prefix, return `False` via an explicit prefix check that logs the malformed-header case, so "wrong format" is distinguishable from "wrong key". Boundary and tie: `compare_digest` on two equal-length hex digests is the intended path; unequal lengths must reach the same `False` without an early length branch that reintroduces the leak, and two different secrets producing the same digest is a collision the comparison need not disambiguate.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: app/webhooks/signing.py — `new_signing_secret` (`random.choice(_ALPHABET)`)
What is wrong: `random` is the Mersenne Twister PRNG, seeded from a predictable source and fully recoverable from 624 observed outputs, and it is being used to mint the key material for a security control (R1: a security primitive reimplemented with a non-security helper — `secrets` is the stdlib's canonical path and is not used).
What breaks in production: an attacker who registers a handful of their own endpoints observes enough PRNG output to reconstruct the generator state and predict every other tenant's signing secret, letting them forge signed events into any customer's webhook receiver.
Fix: Use `secrets.token_urlsafe(SECRET_BYTES)` and rename the constant to match what it now measures (it currently names bytes but counts 32 alphabet *characters*). Preserve the parts other code depends on: the `whsec_` prefix must remain, since `docs/webhooks.md` and the test suite key on it. Pin both sides: allow — the returned value still starts with `SECRET_PREFIX` and round-trips through `sign`/`verify`; deny — 1000 generated secrets are all distinct and none is reproducible after `random.seed(0)`. Red-prove each by execution: (i) revert to `random.choice` and, with `random.seed(0)` set in the test, observe the deny test red because the secret becomes reproducible — that mutation is the whole point and the current test (`test_new_signing_secret_has_prefix_and_length`) stays green under it, which is the evidence the existing test does not cover this; (ii) drop the prefix and observe the allow test red. Update `test_new_signing_secret_has_prefix_and_length` in the same change, because `token_urlsafe(32)` yields 43 characters, not 32 — the existing length assertion encodes the old constant's meaning. Fail loudly: if `secrets` cannot produce entropy, let the `OSError` propagate and fail the registration request rather than falling back to any weaker generator. Boundary and tie: 32 bytes is the floor, not a target — state the floor at the constant, and note that two endpoints registered in the same instant get independent secrets because the source is not time-seeded.

### Critical: the migration's status CHECK rejects the terminal value the code writes
File: migrations/0042_webhook_delivery.sql — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs app/webhooks/models.py — `STATUSES` and app/webhooks/delivery.py — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the schema allows `'failed'` while both the Python status tuple and the only writer of a permanent failure use `'failed_permanent'`, so the strict consumer (Postgres) rejects the exact value the producer emits (R40); the same drift means `STATUSES` in `models.py` is a third, unenforced copy of the enum (R2).
What breaks in production: every delivery that exhausts its attempts raises a check-constraint violation inside `_finish`, the update rolls back, and the row is left in `in_flight` forever — so failed deliveries are neither retried nor reported, and the `deliveries` listing shows them as permanently in flight.
Fix: Change the CHECK to `status IN ('pending', 'in_flight', 'delivered', 'failed_permanent')` and derive the Python side from one place — build the SQL enum list from `models.STATUSES` in a migration test that asserts the two sets are equal, rather than maintaining three literals. Preserve the constraint itself: do not fix this by dropping the CHECK, which is what makes an unknown status impossible. Pin both sides and red-prove each by execution against a real database, not a mock (a mocked session cannot validate a check constraint): (i) allow — inserting a row and calling `_finish(id, "failed_permanent", 5, 500, "...")` commits and a re-read shows `status == "failed_permanent"`; mutate the CHECK back to `'failed'` and observe this test red with the constraint name in the failure output; (ii) deny — `_finish(id, "gave_up", ...)` raises; mutate by dropping the CHECK entirely and observe *this* test red; (iii) parity — the set-equality test between `STATUSES` and the SQL list; mutate by appending one status to `STATUSES` only and observe it red. Fail loudly: `_finish` must not swallow the `IntegrityError` — let it propagate so a status the schema rejects surfaces as a worker error rather than a silently unchanged row. Boundary and tie: `attempts == MAX_ATTEMPTS` is the terminal boundary (the 5th attempt is the last one made, not the first one skipped), and a row already `delivered` must not be transitioned to `failed_permanent` by a late-arriving retry — add that as a WHERE predicate on the update.

### Critical: the unique index on `event_id` makes fan-out to a second endpoint impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the index is unique on `event_id` alone, but `app/webhooks/delivery.py:enqueue_for_event` inserts one `WebhookDelivery` per matching endpoint for a single `event_id`, so any org with two or more subscribed endpoints violates the index.
What breaks in production: the whole `session_scope` transaction in `enqueue_for_event` rolls back on the second row, the dispatcher's `except Exception` swallows the error into a `log.warning`, and the org receives *zero* webhooks for that event — the more endpoints a customer registers, the fewer they receive.
Fix: Make the index unique on the pair that is actually unique — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)` — which also gives the per-endpoint idempotency the docs promise ("delivery is at-least-once, so deduplicate on `event_id`"; correct that line to name the endpoint too). Preserve the property the unique index was there for: re-enqueuing the same event for the same endpoint must still be rejected rather than duplicating work. Pin both sides and red-prove each by execution: (i) allow — an org with two active endpoints enqueued for one event yields exactly 2 rows and `enqueue_for_event` returns 2; mutate the index back to `(event_id)` and observe this test red with a unique-violation; (ii) deny — calling `enqueue_for_event` twice with the same `event_id` yields 2 rows total, not 4; mutate by dropping the unique index and observe *this* test red. Fail loudly: replace the dispatcher's blanket `except Exception: log.warning(...)` with a path that re-raises (or writes a dead-letter row) on `IntegrityError`, so "could not enqueue" is not spelled the same as "nothing to enqueue" — the current swallow is why this defect is invisible. Boundary and tie: an org with exactly one endpoint is the case the current index accidentally satisfies, which is why the bug survives single-endpoint testing; two endpoints registered with identical URLs are still two distinct rows and must both be delivered.

### Critical: `deliver` and `send_once` read ORM objects after their session has closed
File: app/webhooks/delivery.py — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (`endpoint = session.get(...)` then used after the `with` block), `send_once` (`endpoint.signing_secret`, `endpoint.url`, `delivery.payload`)
What is wrong: both functions return or retain SQLAlchemy instances past the end of their `session_scope`, and under the default `expire_on_commit=True` every subsequent attribute access re-triggers a load on a closed session.
What breaks in production: the worker raises `DetachedInstanceError` on the first attribute read of the first claimed delivery, so no webhook is ever sent — and because `deliver` is invoked through `asyncio.gather` inside `run_worker`'s `try`, the exception surfaces only as a gather failure after the lock is already released.
Fix: Stop passing ORM instances across session boundaries — have `_claim_batch` return plain data (`list[tuple[int, int, dict]]` of `delivery_id, endpoint_id, payload`, or a frozen dataclass), and have `deliver` open one `session_scope` that loads the endpoint's `url` and `signing_secret` into locals before the HTTP call. Preserve the status transition `_claim_batch` performs: the claim must still flip rows to `in_flight` in the same transaction that reads them, otherwise the claim is not a claim. Pin both sides and red-prove each by execution against a real session (a mocked session returns live objects and passes vacuously — this is precisely the RT1 divergence the `FakeEndpoint`/`FakeDelivery` stubs already introduce): (i) allow — `_claim_batch` followed by a read of every returned field succeeds outside the `with` block; mutate by returning the ORM rows again and observe this test red with `DetachedInstanceError`; (ii) allow — after `_claim_batch`, a re-read of the rows shows `status == "in_flight"`; mutate by removing the `row.status = "in_flight"` loop and observe *this* test red. Fail loudly: `deliver` must raise a named error when `session.get(m.WebhookEndpoint, endpoint_id)` returns `None` (a deleted endpoint) rather than reaching `endpoint.signing_secret` and dying on `AttributeError` — the current code has no `None` check in either `deliver` or `_finish`. Boundary and tie: a delivery claimed at exactly `next_attempt_at == now` is included (the filter is `<=`), and two rows sharing the same `next_attempt_at` are ordered arbitrarily today — add `id` as the tie-break so the claim order is total (R57).

### Critical: blocking `time.sleep` inside an async coroutine stalls the whole worker
File: app/webhooks/delivery.py — `deliver` (`time.sleep(delay)`), reached from `run_worker`'s `asyncio.gather`
What is wrong: `deliver` is `async` but sleeps with the blocking `time.sleep` rather than `await asyncio.sleep`, and it retries in-process rather than rescheduling via the `next_attempt_at` column the schema was built for.
What breaks in production: one endpoint that 500s freezes the event loop for 2+4+8+16 = 30 seconds, and a batch of 100 such deliveries serializes into roughly 50 minutes of a fully blocked loop — during which no other delivery, no lock refresh, and no other coroutine in the process makes progress, while the 60-second Redis lock TTL expires and a second worker begins claiming the same rows.
Fix: Delete the in-process `while True` retry loop and make `deliver` a single attempt that persists its outcome — on a retryable failure, write `status="pending"`, `attempts=attempt`, and `next_attempt_at = now + backoff_for(attempt)` with jitter, and let the next poll cycle pick it up; keep `_finish` for the two terminal cases. Preserve the retry semantics the docs promise: at most 5 attempts with roughly 2/4/8/16s spacing, and `_finish(..., "failed_permanent", ...)` once `attempt >= MAX_ATTEMPTS` (do not fix the blocking by simply removing retries). Pin both sides and red-prove each by execution: (i) allow — a handler returning 200 marks the row `delivered` in one pass and schedules nothing; mutate by making the success branch also reschedule and observe this test red; (ii) deny — a handler returning 503 leaves the row `pending` with `attempts == 1` and `next_attempt_at` advanced by ~2s, and the call returns in under 100ms; mutate `await asyncio.sleep` back to `time.sleep` and observe the elapsed-time assertion red, which is the clause that proves the loop is no longer blocked; (iii) a handler returning 503 on the 5th attempt yields `failed_permanent`; mutate `MAX_ATTEMPTS` to 6 and observe it red. Fail loudly: a delivery whose row cannot be re-read for rescheduling must log at error and leave the row `in_flight` for the reaper rather than silently returning. Boundary and tie: `attempt >= MAX_ATTEMPTS` means the 5th attempt is the last one *made*; a row whose `next_attempt_at` is exactly `now` is claimable on this poll, and jitter must never push `next_attempt_at` backwards past `now`.

### Critical: the destination URL is fully attacker-controlled and redirects are followed
File: app/api/routes/settings.py — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`), app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check on a user-supplied destination is that the scheme string starts with `http` and the netloc is non-empty — no host allowlist, no private-range rejection — and the delivery client follows redirects, so even a registration-time host check would be bypassable by a 302 (RS3: an untrusted value reaching a network sink with no semantic guard).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://internal-admin.svc/`, and the worker — running inside the production network with no egress restriction visible in this change — makes the request and stores the response body verbatim in `webhook_deliveries.response_body`, which that tenant then reads back through `GET .../deliveries`; the scheme test also admits `httpx://` and `httpfoo://` because `startswith` is a prefix test on an unbounded string.
Fix: Validate at the boundary and re-validate at the sink. At registration: require `parsed.scheme == "https"` (equality, not `startswith` — `docs/webhooks.md` already states "Only `https://` URLs are accepted", so the code is the thing that is wrong), reject a `netloc` whose resolved addresses include any loopback, link-local, private, or reserved range via `ipaddress.ip_address(...).is_global`, and reject embedded credentials and non-default ports outside an allowlist. At delivery: set `follow_redirects=False` and treat a 3xx as a permanent failure, and re-resolve-and-check the host immediately before connect (the registration-time check and the connect are separated by an attacker-schedulable DNS TTL — R51). Preserve the feature: a genuine public HTTPS endpoint must still be registrable and deliverable, including one on a non-standard port if the allowlist permits it. Pin both sides and red-prove each by execution: (i) allow — `https://hooks.example.com/acme` registers with 201 and delivers; mutate the scheme check to reject all non-443 ports and observe the allow test red; (ii) deny — each of `http://hooks.example.com/`, `httpx://hooks.example.com/`, `https://127.0.0.1/`, `https://169.254.169.254/`, `https://user:pw@host/` returns 422 and, per RT8, asserts no `webhook_endpoints` row was created; mutate `==` back to `startswith` and observe exactly the `httpx://` and `http://` cases red; (iii) redirect — a handler returning 302 to `https://127.0.0.1/` marks the delivery failed and records no body from the redirect target; mutate `follow_redirects` back to `True` and observe it red. Fail loudly: a hostname that does not resolve, or resolution that errors, must be a named rejection at registration, never a skipped check that defers to delivery time. Boundary and tie: a host resolving to both a global and a private address is rejected (any private address in the set denies), and `https` on port 443 is the allowed baseline.

### Major: the Redis lock is not atomic, so two workers claim the same batch
File: app/webhooks/delivery.py — `_acquire_lock` (`if await redis_client.get(LOCK_KEY): return False` then `set` then `expire`), `_claim_batch` (no row-level locking)
What is wrong: the check and the set are two round-trips with no atomicity, the TTL is a third round-trip that leaves a window where the lock is permanent if the process dies between `set` and `expire`, and `_claim_batch`'s `SELECT ... LIMIT 100` takes no row locks, so nothing prevents two workers from selecting and flipping the same rows.
What breaks in production: two workers that pass the check in the same millisecond both deliver every row in the batch, so customers receive duplicate `invoice.paid` events; conversely a worker killed between `set` and `expire` wedges the key forever and all delivery stops until someone deletes it by hand.
Fix: Replace the read-then-write with a single atomic `SET LOCK_KEY <token> NX EX 60`, and release with a Lua compare-and-delete on `<token>` so a worker cannot delete a lock that has since been re-acquired by another (the current unconditional `redis_client.delete(LOCK_KEY)` in the `finally` does exactly that). Independently, make the claim itself safe by adding `.with_for_update(skip_locked=True)` to `_claim_batch` so correctness does not rest on the lock at all. Preserve the throughput the lock exists to allow: a single worker must still claim a full `BATCH_SIZE` in one pass, and the lock must still be released promptly on the success path. Pin both sides and red-prove each by execution: (i) allow — one worker acquires, and after `delete` a second acquires; mutate the release to a no-op and observe this test red; (ii) deny — two concurrent `_acquire_lock` calls yield exactly one `True`; mutate `SET NX` back to get-then-set and observe this test red under a loop of ~1000 concurrent pairs (a serial test passes vacuously — R5's note); (iii) deny — two concurrent `_claim_batch` calls over 10 pending rows return disjoint sets summing to 10; mutate away `skip_locked` and observe it red; (iv) a worker holding a stale token must fail to release; mutate the Lua compare away and observe it red. Fail loudly: if Redis is unreachable, `run_worker` must log at error and refuse to claim rather than treating the failed `get` as "lock free" — the current code's `if await redis_client.get(...)` fails open on an exception path only because the exception escapes; make the refusal explicit and named. Boundary and tie: a lock whose TTL expires at exactly the moment the holder finishes must not have its successor's lock deleted — that is what the token comparison decides.

### Major: `in_flight` is a non-terminal state with no reaper and no timeout
File: app/webhooks/delivery.py — `_claim_batch` (sets `row.status = "in_flight"`), `deliver`, `_finish`
What is wrong: a row leaves `in_flight` only through `_finish` on a success or a permanent-failure path inside the same process; a worker crash, a redeploy, an OOM kill, or the detached-instance error above leaves the row in `in_flight` with nothing anywhere that resets it (R38 non-terminal transient state, persisted rather than in-memory).
What breaks in production: every delivery in flight at the moment of a rolling deploy is orphaned permanently — never retried, never marked failed, and invisible in any "pending" metric — so events are silently lost and the loss scales with deploy frequency.

## Cross-cutting verification

- **Tenancy predicate**: present in `create_webhook_endpoint` (`org_id=user.org_id`) and `list_webhook_endpoints` (`.filter(... .org_id == user.org_id)`), **absent** in `list_deliveries` — the only miss in the file.

- **Event-type list**: `dispatcher.WEBHOOK_EVENT_TYPES` is the only enumeration; `EndpointIn.event_types` does not consult it.
