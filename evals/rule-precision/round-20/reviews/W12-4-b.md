### Critical: the signature is computed over bytes that are never sent
File: `app/webhooks/signing.py` — `serialize` / `sign`, and `app/webhooks/delivery.py` — `send_once` (`client.post(endpoint.url, json=delivery.payload, ...)`)
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default separators, keys reordered) while the request body is produced independently by httpx's `json=` encoder, so the signed string and the transmitted string are different byte sequences for any payload with more than one key or any key not already in sorted order.
What breaks in production: every receiver that verifies the HMAC over the raw request body — which is the only thing a receiver has — computes a different digest and rejects 100% of deliveries, and because no test compares a signature against the actual wire body the failure appears only after customers integrate.
Fix: make the serialized string the single source of the body. In `send_once`, build `body = signing.serialize(delivery.payload).encode()`, sign `body`, and send `client.post(endpoint.url, content=body, headers=...)` with `Content-Type: application/json` set explicitly; never pass `json=` alongside a signature. Add a round-trip test (R40's actual-producer-output-through-actual-consumer requirement) that captures `request.content` from `httpx.MockTransport` and asserts `hmac.new(SECRET.encode(), captured_body, sha256).hexdigest()` equals the digest in the captured `X-Acme-Signature` header, using a payload with unsorted, non-ASCII and nested keys (`{"z":1,"a":{"b":"ü"}}`) so encoder differences are visible.
 - Allow side that must still succeed: `test_send_once_posts_the_signed_payload` must still see a parseable JSON body (`json.loads(captured["body"])["type"] == "invoice.paid"`) and a 200 response — the fix must not turn the body into a non-JSON blob.
 - Red-proof, one mutation per clause, executed: (i) change `serialize` to drop `sort_keys=True` → the byte-identity assertion reddens; (ii) revert `content=` back to `json=` → the same assertion reddens with a digest mismatch; (iii) change `Content-Type` to `text/plain` → the content-type assertion reddens. Three mutations, three distinct failing assertions.
 - Fails loudly when the check cannot run: if `MockTransport` never invokes the handler, `captured` is empty — assert `captured` is non-empty first and fail with "no request captured", so "signed nothing" cannot be spelled the same as "signature matched".
 - Preserve: the payload must stay a JSON object the receiver can parse and the existing `Content-Type: application/json` and `User-Agent` headers must remain.
 - Boundary and tie: an empty payload `{}` signs the two-byte body `{}` and must still produce a 64-hex digest; two payloads that differ only in key order must now produce the same body and therefore the same signature — that equality is the property the fix buys.

### Critical: the signature does not cover the timestamp, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign` (`mac = hmac.new(secret.encode(), serialize(payload).encode(), ...)`) vs `docs/webhooks.md` ("The signature is the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`" … "reject requests whose timestamp is more than five minutes old — that window is what stops a captured request from being replayed")
What is wrong: the implementation HMACs the body alone and returns the timestamp as an unauthenticated side value, so the header the documented anti-replay check reads is attacker-mutable while the signature stays valid.
What breaks in production: anyone who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to the current second, and the customer-side freshness check the docs sell as the replay defence rejects nothing.
Fix: change `sign` to `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` over the exact transmitted body (the same `body` bytes from the previous finding), and change `verify` to take the timestamp explicitly — `verify(secret, timestamp, body, signature)` — recomputing over the same concatenation and additionally rejecting a timestamp outside the tolerance. Declare the control class at the artifact (R49): this is an *enforceable boundary* for message authenticity only once the timestamp is inside the MAC; the freshness bound is a fail-closed check whose absent/unparseable-timestamp case must deny.
 - Allow side: a signature produced now with the correct secret and an in-window timestamp must still verify (`assert verify(SECRET, ts, body, sig)`).
 - Red-proof, executed separately: (i) mutate the MAC input back to `body` only and assert a test that flips one digit of the timestamp still reddens the "tampered timestamp is rejected" assertion; (ii) mutate the tolerance comparison from `<=` to `<` and assert the exactly-300s case reddens; (iii) mutate `verify` to ignore the secret and assert the wrong-secret test reddens.
 - Fails loudly: a non-numeric or missing timestamp must raise/deny with a named reason ("timestamp header absent or unparseable"), never fall through to a signature-only comparison.
 - Preserve: `sign` must keep returning the timestamp it used, so `send_once` sends the same value it signed — do not fix this by dropping the timestamp header.
 - Boundary and tie: a timestamp exactly `300` seconds old is accepted, `301` is rejected; two deliveries signed within the same second produce identical timestamps and that is legal — freshness is not an idempotency key.

### Critical: signing secrets are generated with a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret` (`random.choice(_ALPHABET)`)
What is wrong: `random` is the Mersenne Twister, seeded and shared process-wide and fully predictable from a modest run of observed outputs, so it must not generate key material.
What breaks in production: an attacker who observes or provokes enough `random` output from the same process (any other feature using `random`, or a set of secrets issued in sequence) can reconstruct the generator state and derive other tenants' signing secrets, at which point they can forge webhooks that every customer's verification accepts.
Fix: replace the body with `secrets.token_urlsafe(SECRET_BYTES)` (import `secrets`, drop `random`, `string` and `_ALPHABET`) and rename the constant to reflect that it now really is a byte count. Store the secret hashed or envelope-encrypted at rest if the platform has a key service, since the column is plaintext today.
 - Allow side: `new_signing_secret()` must still start with `whsec_` and must still be accepted end-to-end by `sign`/`verify` — keep a test that signs and verifies with a freshly generated secret.
 - Red-proof, executed separately: (i) mutate the generator back to `random.choice` and red a test asserting `signing` does not import `random` (or asserting the module's RNG is `secrets`); (ii) mutate the prefix and red the prefix assertion; (iii) mutate `SECRET_BYTES` to 4 and red a minimum-entropy assertion on the decoded length. Note the current `test_new_signing_secret_has_prefix_and_length` is red-proof-blind: it stays green if the function returns `"whsec_" + "a"*32`, so it must be strengthened rather than relied on.
 - Fails loudly: if the platform key service is used for at-rest protection and is unreachable, endpoint creation must fail with 503 naming the unavailable dependency — never fall back to writing a plaintext secret.
 - Preserve: the returned value must remain a URL-safe printable string customers can paste into their own secret manager.
 - Boundary and tie: `token_urlsafe(32)` returns 43 characters, so any test asserting `len(secret) == len(prefix) + SECRET_BYTES` must be updated to assert the decoded entropy, not the character count; two secrets generated in the same microsecond must differ (assert on a set of 1000).

### Critical: `list_deliveries` has no organization filter — cross-tenant read
File: `app/api/routes/settings.py` — `list_deliveries` (`.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)`)
What is wrong: the query is scoped only by the caller-supplied `endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate any other organization's delivery history.
What breaks in production: a customer iterating `endpoint_id` reads every other tenant's event types, delivery statuses, response codes and schedule — a tenancy breach that the docs explicitly promise does not exist ("returns the most recent attempts for an endpoint belonging to your organization").
Fix: join and filter on the owner in the query itself — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the route does not leak endpoint existence.
 - Cross-cutting verification (R3): the two sibling routes in the same file, `list_api_keys` (`ApiKey.org_id == user.org_id`) and `list_webhook_endpoints` (`WebhookEndpoint.org_id == user.org_id`), both carry the org predicate; `list_deliveries` is the only new boundary in the diff that dropped it, and `enqueue_for_event` in `app/webhooks/delivery.py` correctly filters `m.WebhookEndpoint.org_id == org_id`. No other unscoped query remains in the diff.
 - Allow side: the owning organization must still receive its own deliveries — pin a test where user A's endpoint is read by user A and returns the rows.
 - Red-proof, executed separately: (i) delete the `org_id` predicate and red the cross-tenant test (user B gets 404, not 200 with rows); (ii) change the not-found response from 404 to 403 and red the existence-non-disclosure assertion; (iii) delete the join and red the "endpoint_id of another org returns empty" assertion. Per RT8, the cross-tenant test must assert both the status AND that the response body carries zero rows, not the status alone.
 - Fails loudly: if `user.org_id` is None or absent, deny with 403 rather than building a query with a null predicate that silently matches nothing or everything.
 - Preserve: the `created_at DESC` ordering and the `limit` behaviour must survive the join.
 - Boundary and tie: an endpoint that exists but belongs to another org and an endpoint that does not exist must be indistinguishable (both 404); deliveries sharing an identical `created_at` are ordered arbitrarily — see the ordering finding below.

### Critical: the migration's status CHECK constraint omits the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` — `STATUSES = ("pending", "in_flight", "delivered", "failed_permanent")`
What is wrong: three independent spellings of the same closed set disagree — the SQL allows `failed`, the model tuple and the delivery code use `failed_permanent` — so the terminal-failure write violates the constraint.
What breaks in production: the first delivery that exhausts its attempts raises an IntegrityError inside `_finish`, which propagates out of `deliver` and out of `asyncio.gather`, killing `run_worker` and leaving the row stuck in `in_flight` — one unreachable customer endpoint stops all webhook delivery for every tenant.
Fix: make `models.STATUSES` the single definition and derive the others from it — change the SQL to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`, replace every bare string literal in `delivery.py` (`"pending"`, `"in_flight"`, `"delivered"`, `"failed_permanent"`) with members of `m.STATUSES` exposed as named constants, and add a test that asserts the constraint's member set equals `set(models.STATUSES)` by parsing the migration file. `STATUSES` already exists in the diff and is imported nowhere — that unused helper is exactly the drift this finding is about (R1/R42: derive the member set from the defining primitive rather than from a hand-copied list).
 - Allow side: writing each of the four legal statuses must still succeed — pin an integration test that inserts one row per member of `STATUSES` and commits.
 - Red-proof, executed separately: (i) remove one member from the SQL CHECK and red the parity test; (ii) add a member to `STATUSES` without touching the SQL and red the same test in the other direction; (iii) re-introduce a bare `"failed"` literal in `_finish` and red an assertion that no status string literal appears outside `models.py`.
 - Fails loudly: if the migration file cannot be found or the CHECK clause cannot be parsed, the parity test must fail with "constraint not located in 0042_webhook_delivery.sql", never skip and report green.
 - Preserve: the constraint must stay a real CHECK — do not fix the mismatch by deleting the constraint or widening it to any TEXT.
 - Boundary and tie: the empty-string status and NULL must both remain rejected; a row already written as `failed` by an earlier deploy needs a backfill statement in the same migration, or the new CHECK fails to validate on an existing table.

### Critical: the unique index on `event_id` alone breaks fan-out to more than one endpoint
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` by itself, but `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`, so the second row of any fan-out violates the index.
What breaks in production: an organization with two subscribed endpoints gets an IntegrityError on commit, the whole `add_all` rolls back so even the first endpoint receives nothing, and the dispatcher's blanket `except Exception` downgrades this total loss to a `log.warning` — silent, permanent, per-event data loss that also contradicts the documented at-least-once contract.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the pair that actually expresses "one delivery of this event to this endpoint" and simultaneously gives the idempotency guarantee the docs promise; keep the plain `status` index and add `(status, next_attempt_at)` for the claim query.
 - Allow side: a fan-out of one event to three endpoints of the same org must insert three rows and commit — pin that; the current behaviour must not merely be replaced by a silent de-duplication.
 - Red-proof, executed separately: (i) revert the index to `(event_id)` and red the three-endpoint fan-out test with an IntegrityError; (ii) insert the same `(endpoint_id, event_id)` twice and red an assertion that the second insert is rejected; (iii) drop the index entirely and red the duplicate-rejection assertion.
 - Fails loudly: `enqueue_for_event` must not swallow the constraint error — on an already-present `(endpoint_id, event_id)` it should use an explicit `ON CONFLICT DO NOTHING`-equivalent and report the count it actually inserted; any other IntegrityError must propagate.
 - Preserve: re-delivery attempts of the same event to the same endpoint must still be possible via the `attempts` counter on the existing row — the uniqueness must not be "fixed" by dropping retry state.
 - Boundary and tie: an event fanned out to zero endpoints inserts zero rows and is not an error; two different events landing on the same endpoint in the same instant are distinct pairs and both must insert.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver` (`time.sleep(delay)`)
What is wrong: a synchronous sleep in an `async def` blocks the thread rather than yielding, and `deliver` is run under `asyncio.gather` for a batch of up to `BATCH_SIZE = 100`.
What breaks in production: one slow endpoint stalls the entire process for 2+4+8+16 = 30 seconds per failing delivery, serialized across the batch, so a batch of failing endpoints wedges the worker (and any co-hosted API) for tens of minutes while the 60-second Redis lock silently expires under it and a second worker starts double-delivering.
Fix: replace the in-loop retry with a rescheduling write and `await asyncio.sleep` for any sleep that remains: on a retryable failure, call `_finish(delivery.id, "pending", attempt, status_code, detail)` with `next_attempt_at = now + backoff_for(attempt)` and return, letting `_claim_batch` pick the row up later — this removes the sleep from the request path entirely and makes retries survive a worker restart. Retain `await asyncio.sleep(poll_interval)` in `run_worker` only.
 - Allow side: a delivery that succeeds on the first attempt must still be marked `delivered` synchronously within the same `deliver` call — pin that path.
 - Red-proof, executed separately: (i) re-introduce `time.sleep` and red a test that asserts `deliver` returns within a bounded wall-clock budget while a second coroutine makes progress concurrently; (ii) mutate the reschedule to leave `status = "in_flight"` and red an assertion that a retryable failure leaves the row claimable; (iii) mutate `next_attempt_at` to `now` and red an assertion that the next attempt is scheduled at least `backoff_for(attempt)` in the future. Bound each test with a timeout so a non-terminating mutation reds instead of hanging.
 - Fails loudly: if `_finish` cannot write the reschedule (DB down), the exception must propagate to a named handler that leaves the row claimable, not be swallowed into a return that marks the delivery done.
 - Preserve: the total attempt budget (`MAX_ATTEMPTS`) and the growing delays must be unchanged in observable effect — the fix moves where the wait happens, it does not remove retries.
 - Boundary and tie: `attempt == MAX_ATTEMPTS` is the last attempt made, not an extra one; a row whose `next_attempt_at` is exactly `now` is claimable (`<=`), and two rows with identical `next_attempt_at` may be claimed in either order.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify` (`return expected == signature`)
What is wrong: the recomputed HMAC is compared with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: any caller of this helper on an inbound path — and it is the module's only public verification primitive, exported and exercised by the shipped tests — leaks digest bytes through response timing, letting an attacker construct a valid signature byte by byte without knowing the secret.
Fix: `return hmac.compare_digest(expected, signature)`, after normalizing both sides to the same type (`str`) and rejecting a `signature` that is not the exact `sha256=<64 hex>` shape before comparing, so a short or absent header cannot be compared at all.
 - Allow side: a correct signature must still verify — keep `test_verify_accepts_signature_produced_by_sign` green (after it is rewritten per the test findings below to compute the expected value independently).
 - Red-proof, executed separately: (i) revert to `==` and red a test asserting the module uses `hmac.compare_digest` (via source inspection or by patching `hmac.compare_digest` and asserting it was called with both operands); (ii) pass a signature of the wrong length and red the shape-rejection assertion; (iii) pass a signature made with another secret and red the rejection assertion.
 - Fails loudly: a `signature` of `None` or a non-string must raise a named `TypeError`/return False with a logged reason, not fall into a comparison that coerces.
 - Preserve: `verify` must keep its boolean contract; do not "fix" the timing leak by removing verification or by comparing only a prefix.
 - Boundary and tie: two signatures of equal length that differ in the last byte must take the same time as two differing in the first; the empty string must be rejected before comparison, not compared.

### Critical: endpoint URL validation permits SSRF, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`), with `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the check accepts any scheme whose name merely begins with `http` and any host at all, and the delivery client then follows redirects, so a customer can register `http://169.254.169.254/…` (or a public URL that 302s there) and have the server POST to internal addresses on their behalf.
What breaks in production: the worker becomes a confused deputy that reaches cloud metadata endpoints, internal admin ports and localhost services, and it carries a valid signature header while doing so; the docs' claim "Only `https://` URLs are accepted" is false, which is a control described as stronger than it is (R49).
Fix: validate with an explicit allowlist rather than a prefix test — require `parsed.scheme == "https"`, require a hostname, resolve it and reject any address in a loopback/link-local/private/reserved range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), reject a non-default port unless it is 443, and bound the URL length. Set `follow_redirects=False` in the delivery client and treat a 3xx as a permanent failure with a named reason, so the resolved-and-checked host is the host actually contacted (re-resolution at connect time is a separate TOCTOU that the allowlist alone does not close — state that limitation at the artifact, and pin the connection to the validated address if the HTTP client supports it). Declare the class: this is a fail-closed verification gate, not an enforceable boundary, and DNS rebinding is a known residual bypass.
 - Allow side: `https://hooks.example.com/acme` on port 443 must still be accepted and must still be delivered to — pin both the 201 on creation and a successful `send_once` against it.
 - Red-proof, executed separately: (i) restore `startswith("http")` and red the `httpx://evil` rejection test; (ii) remove the private-range check and red the `https://127.0.0.1/x` rejection test; (iii) set `follow_redirects=True` and red a `MockTransport` test asserting a 302 to an internal host is not followed.
 - Fails loudly: when DNS resolution fails or times out, creation must return a 422 naming "hostname could not be resolved" — an unresolvable host must not be treated as "no private address found, therefore safe".
 - Preserve: legitimate public HTTPS endpoints behind CDNs with multiple A records must still register; the fix must reject a host only when *every* resolved address is disallowed is the wrong rule — reject when *any* is.
 - Boundary and tie: `100.64.0.0/10` (CGNAT) and IPv6 `::ffff:127.0.0.1` must be rejected; a host resolving to both a public and a private address is rejected.

### Critical: the signing secret is returned by the list endpoint, contradicting its documented write-once property
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict` (`"signing_secret": self.signing_secret`), reached by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict` embeds the long-lived signing secret in every serialization, so `GET /v1/settings/webhook-endpoints` hands it back on demand, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: a documented write-once credential becomes a readable one on a GET route whose responses are the kind of thing that lands in browser caches, proxy logs and support tickets, and every downstream decision made on the strength of the docs' claim (log retention for that route, who may call it, whether the response needs redaction) was made on a false premise.
Fix: remove `signing_secret` from `to_dict`, and return it exactly once from `create_webhook_endpoint` by constructing that one response explicitly (`{**endpoint.to_dict(), "signing_secret": secret}` using the value generated in the handler). Add a rotation route, since removing read-back without a rotation path leaves a customer who loses the secret with no recovery.
 - Cross-cutting verification: `WebhookDelivery.to_dict` in the same file exposes no secret material, and it is the only other `to_dict` in the diff; `list_deliveries` and `list_webhook_endpoints` are the only two read routes returning serialized models.
 - Allow side: creation must still return the secret — pin an assertion that the 201 body contains a `whsec_`-prefixed value.
 - Red-proof, executed separately: (i) re-add the key to `to_dict` and red an assertion that the list response body contains no `whsec_` substring; (ii) remove the explicit merge in the create handler and red the creation-returns-secret assertion; (iii) point the create handler at `to_dict` alone and red the same pair together.
 - Fails loudly: if a serializer ever cannot determine whether a field is secret, the safe default is omission — add the redaction test over the whole response body (substring scan for `whsec_`), so a newly added field carrying the secret reds rather than passing unnoticed.
 - Preserve: the list response must keep `id`, `url`, `event_types` and `active`, which is what the settings UI needs.
 - Boundary and tie: an endpoint created before the change already has a secret in the database — the fix changes only what is serialized, and the response for a zero-endpoint list must remain `[]`, not an error.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` (`if await redis_client.get(LOCK_KEY): return False` then `set` then `expire`) and `run_worker` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: the get-then-set sequence has a window in which two workers both observe an empty key and both proceed, the separate `expire` leaves a permanent lock if the process dies between `set` and `expire`, and the `finally` deletes the key by name without checking the holder token, so a worker whose lock already expired deletes the lock a different worker now holds.
What breaks in production: two workers claim overlapping batches and every customer endpoint receives duplicate POSTs, which the broken `event_id` uniqueness and the absent receiver-side idempotency make indistinguishable from real repeat events.
Fix: acquire with a single atomic call carrying a unique token and a TTL — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so only the holder can release. Add `SELECT ... FOR UPDATE SKIP LOCKED` to `_claim_batch`, because the database, not Redis, is what actually makes the claim exclusive; the lock is then an optimization, not the correctness mechanism.
 - Allow side: a single worker with no contention must still acquire, claim and release on every poll — pin that loop for two iterations.
 - Red-proof, executed separately: (i) revert to get-then-set and red a test that two concurrent `_acquire_lock` calls yield exactly one `True`; (ii) revert the release to an unconditional `delete` and red a test that a stale holder's release leaves the current holder's token in place; (iii) drop `SKIP LOCKED` and red a test that two concurrent `_claim_batch` calls return disjoint id sets. Each concurrency test must fail if it did not actually observe concurrency (assert both coroutines ran), or it passes vacuously (RT4).
 - Fails loudly: if Redis is unreachable, `_acquire_lock` must raise a named error that stops the worker rather than returning `True` and running unguarded, and it must not return `False` forever in silence either — log the refusal by name.
 - Preserve: the 60-second TTL that keeps a crashed worker from wedging the queue must remain; do not fix the release race by removing the expiry.
 - Boundary and tie: a lock whose TTL expires exactly as the holder finishes must not delete a successor's lock — that is what the token comparison decides; two workers presenting the same token is impossible by construction (uuid4).

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`) and `_finish` (only ever called on the success or permanent-failure path of `deliver`)
What is wrong: a row is moved to `in_flight` before delivery and returns to a claimable state only if `deliver` completes, so a worker crash, a `gather` cancellation, or any exception between claim and finish strands the row permanently — `_claim_batch` filters on `status == "pending"` and nothing anywhere sets `in_flight` back (R38, non-terminal transient state).
What breaks in production: every deploy restart, OOM kill or unhandled exception silently and irreversibly drops the deliveries that were in flight, with no operator-visible signal beyond a row that stops moving.
Fix: give the transient state a bounded lease and an explicit reaper — store `claimed_at` when moving to `in_flight`, and in `_claim_batch` also select rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'`, resetting them to `pending` with `attempts` unchanged; log each reclaim at WARNING with the delivery id so the wedge is visible rather than inferred.
 - Allow side: a delivery genuinely in flight for less than the lease must NOT be reclaimed — pin a test that a row claimed 10 seconds ago is invisible to a second `_claim_batch`.
 - Red-proof, executed separately: (i) remove the reaper predicate and red a test that a 10-minute-old `in_flight` row is re-claimed; (ii) mutate the reaper to also reset `attempts` to 0 and red an assertion that the attempt budget is preserved across a reclaim; (iii) mutate the lease to zero and red the "not reclaimed too early" assertion.
 - Fails loudly: if `claimed_at` is NULL on an `in_flight` row (rows written before this change), treat it as expired and reclaim with a log line naming the backfill, rather than leaving it invisible forever.
 - Preserve: `MAX_ATTEMPTS` must still bound total attempts across reclaims — a reaped row must not get an unlimited budget, or an endpoint that always kills the worker becomes an infinite loop.
 - Boundary and tie: a row whose `claimed_at` is exactly at the lease boundary is reclaimed (`<=`); two workers reaping the same row simultaneously is resolved by the same `FOR UPDATE SKIP LOCKED` as the normal claim.

### Major: ORM instances are mutated and read outside the session that loaded them
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` from inside `with session_scope()`) and `deliver` (`endpoint = session.get(...)` used after the `with` block)
What is wrong: both functions hand live ORM instances out of their session scope and then read attributes (`delivery.payload`, `delivery.attempts`, `delivery.id`, `endpoint.url`, `endpoint.signing_secret`) after that session has been committed and closed.

### Major: the worker loop dies on the first exception, and `batch` can be unbound
File: `app/webhooks/delivery.py` — `run_worker` (`try: batch = await _claim_batch(); await asyncio.gather(...) finally: ... ` then `if not batch:`)
What is wrong: there is no `except` anywhere in the loop, so any error from `_claim_batch`, `gather` or Redis propagates out of `run_worker` and terminates the worker; and because `batch` is assigned inside the `try`, a failure in `_claim_batch` makes the post-`finally` `if not batch` raise `UnboundLocalError`, masking the original error.

### Minor: the claim query's ordering key is not a total order and no index supports it
File: `app/webhooks/delivery.py` — `_claim_batch` (`.order_by(m.WebhookDelivery.next_attempt_at).limit(BATCH_SIZE)`) and `migrations/0042_webhook_delivery.sql` (`CREATE INDEX idx_webhook_deliveries_status ON webhook_deliveries (status)`)
What is wrong: `next_attempt_at` ties freely — every row enqueued in the same fan-out gets the identical timestamp — so ordering among ties is undefined and the `LIMIT 100` cut can fall inside a tie group (R57), while the only index is on `status`, leaving the sort unsupported.
What breaks in production: under burst load a tied row can be repeatedly passed over in favour of its siblings while the table grows, and the unindexed sort degrades to a full scan of all pending rows on every poll.
Fix: order on `(next_attempt_at, id)` — `id` is the engine-assigned `BIGSERIAL` and is unique and monotonic by construction, and the caller cannot name it — and add `CREATE INDEX idx_webhook_deliveries_claim ON webhook_deliveries (status, next_attempt_at, id)`.

### Minor: `SECRET_BYTES` counts characters, not bytes
File: `app/webhooks/signing.py` — `SECRET_BYTES = 32`, used as the character count in `new_signing_secret` and asserted as such in `test_new_signing_secret_has_prefix_and_length`
What is wrong: the name states an entropy budget in bytes while the value is a length in alphabet characters, so a reader auditing key strength reads 256 bits where the construction gives at most ~190 (and far less in practice, per the PRNG finding).
What breaks in production: the next person to tune key length will change the number believing it is a byte count, and the shipped test cements the wrong unit by asserting `len(secret) == len(prefix) + SECRET_BYTES`.
Fix: rename to `SECRET_ENTROPY_BYTES` and consume it as the argument to `secrets.token_urlsafe`, updating the test to assert decoded entropy rather than character count.

### Minor: `enqueue_for_event` is declared async but performs only blocking work
File: `app/webhooks/delivery.py` — `enqueue_for_event`
What is wrong: the function is `async def` yet contains no `await`; every statement is a synchronous SQLAlchemy call, so it blocks the event loop for the duration of the query and inserts.
What breaks in production: it is awaited from `dispatch` on the request path, so a slow endpoint query stalls every other coroutine in the process — the same class of problem as the `time.sleep` finding, at smaller scale.
Fix: either make it a plain `def` called via `run_in_executor`/`asyncio.to_thread` from `dispatch`, or move to an async session; whichever is chosen, state it once for the module rather than mixing sync ORM calls into coroutines.

### Minor: there is no way to rotate a secret, deactivate an endpoint, or delete one
File: `app/api/routes/settings.py` — the webhook route group (`create_webhook_endpoint`, `list_webhook_endpoints`, `list_deliveries`)
What is wrong: the model carries an `active` flag and a `signing_secret` but the API exposes only create and read, so neither can ever change once written.
What breaks in production: a customer whose secret leaks has no remediation path short of a support ticket, and an endpoint that starts failing cannot be turned off, so it keeps consuming the worker's attempt budget on every event indefinitely.
Fix: add `PATCH /webhook-endpoints/{id}` (org-scoped, toggling `active` and `event_types`) and `POST /webhook-endpoints/{id}/rotate-secret` returning the new secret exactly once, both filtered by `WebhookEndpoint.org_id == user.org_id` per the tenancy finding above.
