### Critical: the HMAC is computed over different bytes than the body that is actually sent
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, used by `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` while `send_once()` hands the dict to `client.post(..., json=delivery.payload)`, so httpx re-serializes it independently — key order and separators differ, and I confirmed by execution that the same payload yields `{"amount_cents": 4200, "id": "evt_1", "type": "invoice.paid"}` signed versus `{"id": "evt_1", "type": "invoice.paid", "amount_cents": 4200}` (or the compact form on newer httpx) on the wire.
What breaks in production: every receiver that verifies the signature over the raw body it received computes a different digest and rejects 100% of deliveries, so the webhook feature never works for any correctly-implemented customer.
Fix: make the signed bytes and the transmitted bytes the same object — build `body = serialize(payload).encode()` once in `send_once()`, sign that exact byte string, and send it with `client.post(endpoint.url, content=body, headers=headers)` instead of `json=`; `serialize()` already exists and is the shared path `send_once()` currently bypasses, so adopt it rather than adding a second serializer. Preserve the behaviour that made the feature useful: the request must still carry `Content-Type: application/json` and a JSON-parseable body — do not "fix" this by dropping the signature header or by loosening the receiver contract. Deny side: a body mutated by one byte after signing must fail `verify()`. Allow side that must still succeed: `verify(secret, received_raw_body, header)` returns True for an unmodified delivery, and `json.loads(received_raw_body)` still yields the original payload dict. Red-prove each clause separately by executing it, one mutation per clause: (i) revert `content=` to `json=` and observe the round-trip assertion go red; (ii) flip `sort_keys=True` to `False` in `serialize()` on a payload with out-of-order keys and observe the same assertion go red for a different reason; (iii) tamper one byte of the body in the test transport and observe the deny assertion go red. Fail loudly if the check cannot run: if `serialize()` raises (non-JSON-serializable payload), abort the delivery with an explicit `failed_permanent` and a named reason rather than sending an unsigned or partially-signed request.

### Critical: the timestamp header is not covered by the signature, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign()` line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`
What is wrong: `docs/webhooks.md` instructs receivers to verify the HMAC of `"{timestamp}.{raw_request_body}"` and to reject timestamps older than five minutes, but `sign()` MACs the body alone and returns the timestamp as an unauthenticated side value.
What breaks in production: an attacker who captures one delivery can replay it indefinitely by rewriting `X-Acme-Timestamp` to now while leaving the still-valid signature untouched, so the five-minute anti-replay window documented as "what stops a captured request from being replayed" stops nothing.
Fix: change the MAC input to `f"{timestamp}.".encode() + body` in `sign()`, and give `verify()` the signature `verify(secret, timestamp, body, signature)` so the caller must supply the timestamp it received; update `docs/webhooks.md` only if the chosen concatenation differs from the one documented, and keep the documented form as the target rather than rewriting the doc to match the weaker code. Preserve what made this visible: the timestamp must remain sent in its own header so receivers can enforce the window — do not fix by removing the header. Deny side: a signature generated at T with the header rewritten to T+10min must fail verification. Allow side that must still succeed: a delivery verified with its own unmodified timestamp still passes. Boundary and tie: state the window comparison explicitly as `abs(now - ts) <= 300` seconds so a timestamp at exactly 300s is accepted and 301s is rejected, and reject negative skew beyond the same bound so a far-future timestamp cannot buy an extended window. Red-prove separately by execution: (i) verify with a rewritten timestamp → red; (ii) verify with a rewritten body → red; (iii) verify at exactly the 300s boundary → still green.

### Critical: signature comparison is a plain `==`, not constant-time
File: `app/webhooks/signing.py` — `verify()` line `return expected == signature`
What is wrong: the HMAC comparison uses Python's short-circuiting string equality instead of `hmac.compare_digest`, leaking a byte-position-dependent timing signal.
What breaks in production: any caller that uses this shared `verify()` on an inbound path — and it is exported as the reference implementation of the scheme — lets an attacker recover a valid signature byte-by-byte from timing, forging events that appear signed by the real secret.
Fix: replace the body of `verify()` with `hmac.compare_digest(expected, signature)`, comparing `str`/`bytes` of the same type and normalising the `sha256=` prefix before the compare so the prefix mismatch does not short-circuit either. Preserve the behaviour the current code has that matters: a wrong-secret signature must still return False (`test_verify_rejects_a_signature_made_with_another_secret` must stay green) — do not fix by deleting or weakening that assertion. Allow side that must still succeed: `test_verify_accepts_signature_produced_by_sign` stays green. Red-prove by execution, one mutation per clause: (i) make `sign()` return a constant digest and observe the wrong-secret test red; (ii) hand `compare_digest` a `str` and a `bytes` and observe the explicit `TypeError` path surface as a named failure rather than a silent False. Fail loudly if the check cannot run: a malformed `signature` argument (missing `sha256=` prefix, non-hex, wrong length) must return False through an explicit, logged rejection branch that names the reason, so "could not compare" is never spelled the same as "compared and matched".

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret()` line `random.choice(_ALPHABET)`
What is wrong: the secret is drawn from `random`, Python's Mersenne Twister, which is deterministic and whose internal state is recoverable from observed output — I confirmed by execution that seeding reproduces the identical 32-character secret.
What breaks in production: an attacker who learns or reconstructs the generator state (any other `random` consumer in the same process leaks it) can predict the signing secret of every endpoint created nearby in time and forge signed webhooks for those customers, defeating the entire scheme.
Fix: replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and import `secrets` (drop the now-unused `random`, `string` and `_ALPHABET`). Note the constant is misnamed for the current code — `SECRET_BYTES = 32` is used as a *character* count over a 62-symbol alphabet — so with `token_urlsafe` it becomes a true 32-byte entropy quantity and the existing length assertion must be updated to `len(secret) == len(SECRET_PREFIX) + len(secrets.token_urlsafe(SECRET_BYTES))` rather than deleted. Preserve what made the feature usable: the `whsec_` prefix and URL-safe alphabet stay, so existing customer parsers keep working. Allow side that must still succeed: `test_new_signing_secret_has_prefix_and_length` still passes and two consecutive calls still produce parseable secrets. Red-prove separately by execution: (i) add a test asserting 1000 generated secrets are all distinct, then mutate `new_signing_secret` to return a constant and observe it red; (ii) add a test asserting the entropy source by patching `secrets.token_urlsafe` to raise and observing the call propagate rather than silently falling back — a fallback to `random` must not exist. Fail loudly if the check cannot run: no `except` around the generator; if the OS entropy source fails, endpoint creation must 500, never issue a weak secret.

### Critical: `list_deliveries` has no tenancy filter, exposing every organization's webhook payloads
File: `app/api/routes/settings.py` — `list_deliveries()`, the `.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: the query scopes on the caller-supplied `endpoint_id` only, while every sibling handler added in the same file scopes on `user.org_id` (`list_api_keys` filters `ApiKey.org_id == user.org_id`; `list_webhook_endpoints` filters `WebhookEndpoint.org_id == user.org_id`), so this one route omits the pattern its peers apply.
What breaks in production: any authenticated user can enumerate `endpoint_id` and read another tenant's delivery rows — including `event_type`, `response_status` and the delivery history of their invoices — a cross-tenant data breach reachable with a single incrementing integer.
Fix: join to the endpoint and filter on ownership in the same query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the response does not disclose whether the id exists. `docs/webhooks.md` already states this route "returns the most recent attempts for an endpoint belonging to your organization", so the code is the side that is wrong. Preserve what made the route useful: the owner must still get their rows, ordered and limited as before — do not fix by removing the route. Deny side: a request from org B for org A's `endpoint_id` returns 404 **and** returns zero rows. Allow side that must still succeed: a request from the owning org for its own `endpoint_id` still returns its deliveries. Red-prove each clause separately by execution: (i) drop the `org_id` predicate and observe the cross-tenant test red on the row-count assertion; (ii) change 404 to 403 and observe the enumeration-disclosure assertion red. Fail loudly if the check cannot run: if `user.org_id` is absent, the handler must raise rather than fall through to an unscoped query. Cross-cutting: this is the only added route missing the filter — `list_webhook_endpoints` and `enqueue_for_event` both scope by `org_id` — but `create_webhook_endpoint` has the mirror gap of never checking that the caller may create endpoints for `user.org_id` beyond trusting the dependency, which is acceptable only because it writes `user.org_id` rather than reading a supplied one.

### Critical: `list_webhook_endpoints` returns every endpoint's signing secret, contradicting the documented one-time display
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()` includes `"signing_secret": self.signing_secret`; consumed by `app/api/routes/settings.py` — `list_webhook_endpoints()`
What is wrong: the single `to_dict()` is shared by the create route (where returning the secret is intended) and the list route, and `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards", which the list route falsifies.
What breaks in production: the shared secret for every endpoint is readable on demand by anyone holding any credential for the org — including a read-scoped API key or a low-privilege member — turning a one-time-disclosure secret into a permanently harvestable one, and any customer who built on the documented guarantee has mis-scoped their access control.
Fix: remove `signing_secret` from `to_dict()` and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` explicitly at that one call site, so disclosure is opt-in per route rather than default-on. Preserve what made the feature usable: the creating caller must still receive the secret exactly once, and since it is now unreadable a rotation route (`POST /webhook-endpoints/{id}/rotate-secret`, returning the new secret once) is required or customers have no recovery from a leak. Deny side: the list response body must not contain the substring `whsec_`. Allow side that must still succeed: the create response body still contains a `whsec_`-prefixed secret. Red-prove separately by execution: (i) re-add the field to `to_dict()` and observe the list-route assertion red; (ii) delete the explicit merge in the create route and observe the create-route assertion red — two mutations, two different assertions. Fail loudly if the check cannot run: assert on the serialized response body, not on the model, so a future serializer change cannot silently reintroduce the field.

### Critical: any `http*` URL is accepted and the worker follows redirects, giving an authenticated SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint()` line `if not parsed.scheme.startswith("http") or not parsed.netloc`; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the guard adjudicates the URL's surface form rather than the location the HTTP client will actually resolve — I confirmed by execution that `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/` and even `httpz://evil.example` all pass `scheme.startswith("http") and netloc`, and `follow_redirects=True` means even a validated public host can redirect the worker to an internal one.
What breaks in production: a customer registers an endpoint pointing at the cloud metadata service or an internal admin port, and the worker POSTs signed requests there from inside the trust boundary, returning the response body into `response_body` where the attacker reads it back through `list_deliveries` — full read SSRF with an exfiltration channel.
Fix: adjudicate at the rung the runtime uses, not the notation — replace the `startswith` test with an exact `parsed.scheme == "https"` membership check (which is what `docs/webhooks.md` already promises), resolve the hostname to addresses at request time and reject any that is loopback, link-local, private, multicast, or reserved via `ipaddress.ip_address(...).is_global`, set `follow_redirects=False`, and pin the connection to the vetted address so the check cannot be undone by DNS rebinding between validation and use. Preserve what made the feature useful: a legitimate public HTTPS endpoint must still be registerable and deliverable to — do not fix by allowlisting a fixed set of hosts. Deny side: registration of `http://…` and of `https://169.254.169.254/` both 422, and a 302 from a valid endpoint to `http://localhost/` results in a failed delivery with no request issued to localhost. Allow side that must still succeed: `https://hooks.example.com/acme` registers and delivers exactly as today. Red-prove each clause separately by execution: (i) relax the scheme check back to `startswith` → the plaintext-rejection assertion reds; (ii) remove the address check → the metadata-address assertion reds; (iii) set `follow_redirects=True` → the redirect assertion reds. Fail loudly if the check cannot run: DNS resolution failure or an unparseable host must reject the registration and mark the delivery failed with a named reason, never fall through to "no bad address found, allow".

### Critical: the migration's CHECK constraint does not contain the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the code's terminal failure status is `failed_permanent` (also the fourth member of the unused `STATUSES` tuple in `app/webhooks/models.py`), but the migration enumerates `failed`, so the two spellings of the same enum drifted between the three places that declare it.
What breaks in production: the first delivery that exhausts its retries raises a check-constraint violation inside `_finish`, so the row is never marked terminal, the exception escapes `deliver()` into `asyncio.gather` and takes down the worker loop's batch — and the row stays `in_flight` forever.
Fix: change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and make `STATUSES` the single source by having `_finish`, `_claim_batch` and any future writer take their literals from `m.STATUSES` members rather than inline strings — the constant already exists in `models.py` and is currently dead, so this is adopting the shared path, not adding one. Preserve what the constraint was there to do: the DB must still reject an unknown status — do not fix by dropping the CHECK. Deny side: writing `status = 'bogus'` still raises. Allow side that must still succeed: writing each of the four `STATUSES` members commits. Red-prove each separately by execution: (i) write `'failed'` against the corrected constraint → red; (ii) write `'bogus'` → red; (iii) write all four members → green. Cross-cutting: the same three-way drift risk exists for nothing else in the diff, but note the migration's `event_type TEXT` versus the model's `String(100)` is the same class of declaration divergence and should be reconciled to `VARCHAR(100)` in the same change.

### Critical: the unique index on `event_id` makes multi-endpoint orgs undeliverable
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, but the index permits only one row per `event_id` across the whole table.
What breaks in production: any organization with two or more active endpoints subscribed to the same event hits a unique-violation on the second row, the whole `session.add_all` transaction rolls back, and because `app/events/dispatcher.py` wraps the call in `except Exception: log.warning(...)`, that org silently receives *zero* webhooks with only a warning line as evidence.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);`, which is the constraint actually wanted — it preserves the idempotency the original index was reaching for (one delivery per endpoint per event, backing the "deduplicate on `event_id`" contract in `docs/webhooks.md`) while permitting fan-out. Preserve what made the index worth having: duplicate enqueues for the same endpoint and event must still be rejected — do not fix by deleting the uniqueness. Deny side: enqueuing the same `(endpoint_id, event_id)` twice raises. Allow side that must still succeed: one event fanning out to three endpoints of one org inserts three rows and returns 3. Boundary and tie: state explicitly that re-delivery of the same event to the same endpoint is *not* permitted by insert — a manual redelivery must update the existing row's `status`/`next_attempt_at` rather than insert a second one, so the retry path is not accidentally blocked by the new constraint. Red-prove separately by execution: (i) three-endpoint fan-out under the old index → red; (ii) duplicate `(endpoint_id, event_id)` under the new index → red on the uniqueness assertion.

### Critical: ORM instances are used after their session scope has closed
File: `app/webhooks/delivery.py` — `deliver()` (`endpoint` read inside `with session_scope()` then used at `send_once`) and `_claim_batch()` (returns `rows` from inside the `with` block)
What is wrong: both functions read rows inside a `session_scope()` block and then read their attributes after the block exits — `endpoint.signing_secret` and `endpoint.url` in `send_once`, and `delivery.attempts` / `delivery.id` / `delivery.payload` in `deliver` and `run_worker`.
What breaks in production: under SQLAlchemy's default `expire_on_commit=True` every one of those attribute reads issues a refresh on a closed session and raises `DetachedInstanceError`, so the worker throws on the first claimed batch and no webhook is ever delivered; if `session_scope` instead sets `expire_on_commit=False`, the same code silently operates on stale snapshots and `_claim_batch`'s `in_flight` writes race the delivery loop. (The precondition — `session_scope`'s configuration — is not in the diff; what the diff makes true is the use-after-scope, and the fix below is correct under either configuration.)
Fix: extract plain values inside the scope and pass only those out — have `_claim_batch` return a list of dataclasses or tuples `(id, endpoint_id, payload, attempts)` built inside the `with`, and have `deliver` read `url` and `signing_secret` into locals inside its own `with` before calling `send_once`; change `send_once`'s signature to take `url: str, secret: str, payload: dict` so the detached-object hazard is unrepresentable rather than merely avoided. Preserve what made the code useful: `_claim_batch` must still mark the claimed rows `in_flight` in the same transaction that reads them, so a second worker cannot re-claim them. Deny side: a test that asserts `_claim_batch` never returns an object with a `_sa_instance_state`. Allow side that must still succeed: a claimed batch still yields the correct payload bytes to `send_once`, and the rows are `in_flight` in the DB after the call returns. Red-prove separately by execution: (i) return the ORM rows again and observe the no-ORM assertion red; (ii) move the `row.status` assignment outside the `with` and observe the in_flight assertion red. Fail loudly if the check cannot run: if `session.get` returns `None` for the endpoint, `deliver` must mark the delivery `failed_permanent` with a named reason instead of proceeding — see the separate `_finish` finding.

### Critical: `time.sleep` inside an async coroutine blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver()` line `time.sleep(delay)`
What is wrong: the retry backoff uses the blocking `time.sleep` inside an `async def`, in the same module that already imports `asyncio` and correctly uses `await asyncio.sleep(poll_interval)` in `run_worker`.
What breaks in production: one failing endpoint stalls the whole loop for up to 2+4+8+16 = 30 seconds — and because `run_worker` `gather`s up to `BATCH_SIZE` deliveries on that loop, a single slow endpoint blocks all 100 concurrent deliveries and, if the worker shares a process with the API, every inbound HTTP request too.
Fix: replace with `await asyncio.sleep(delay)`; the correct primitive is already used one function below, so this is adopting the existing path, not introducing one. Better still, stop sleeping in-process altogether: set `next_attempt_at = now + backoff_for(attempt)` and `status = 'pending'` via `_finish`, and return — the `next_attempt_at` column and the `_claim_batch` ordering exist precisely to schedule retries, and the current in-process loop leaves them unused. Preserve what made the retry useful: the delivery must still be attempted up to `MAX_ATTEMPTS` times with growing delay, and the final attempt must still land in `failed_permanent`. Deny side: with the endpoint permanently erroring, the row reaches `failed_permanent` with `attempts == 5` and no more requests are issued. Allow side that must still succeed: an endpoint that fails once then succeeds still reaches `delivered` with `attempts == 2`. Boundary and tie: define whether attempt number `MAX_ATTEMPTS` is *attempted* or is the first *not* attempted — the current `if attempt >= MAX_ATTEMPTS` after a failed attempt means 5 attempts happen, and the reschedule rewrite must keep exactly that count, not 4 or 6. Red-prove separately by execution: (i) restore `time.sleep` and assert the loop stays responsive by racing a second coroutine → red; (ii) change `>=` to `>` and observe the attempt-count assertion red.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock()` (`get` then `set` then `expire`) and `run_worker()` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: the check-then-set across three round trips is a TOCTOU window in which two workers both observe an empty key and both "acquire" the lock, and the `finally` deletes the key regardless of whether this worker still owns it.
What breaks in production: two workers claim overlapping batches and deliver every webhook twice; separately, a worker whose batch exceeds the 60-second TTL deletes the lock that a *second* worker legitimately took, cascading into a third concurrent worker — and a crash between `set` and `expire` leaves the lock held forever with zero deliveries until manual intervention.
Fix: acquire with a single atomic conditional write carrying its own expiry and a unique owner token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` — and release with a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock; renew the TTL periodically while the batch runs rather than assuming 60s suffices. Preserve what the lock is for: exactly one worker must still process a batch at a time — do not fix by removing the lock or by widening the TTL to a number that merely hides the overrun. Deny side: a second `_acquire_lock` while the first holds returns False; a release with a stale token deletes nothing. Allow side that must still succeed: after the owner releases, the next `_acquire_lock` returns True. Boundary and tie: state what happens when two workers call `set(nx=True)` in the same instant — Redis serialises them, exactly one gets True, and the loser must sleep rather than proceed. Red-prove each clause separately by execution: (i) drop `nx=True` → the mutual-exclusion assertion reds; (ii) drop the token comparison in release → the stale-release assertion reds; (iii) drop `ex=60` → the crash-recovery assertion (lock auto-expires) reds.

### Major: `in_flight` is a non-terminal state with no reaper
File: `app/webhooks/delivery.py` — `_claim_batch()` sets `row.status = "in_flight"`; no code path returns a row from `in_flight` to `pending`
What is wrong: rows enter `in_flight` on claim and leave only via `_finish` on the success or permanent-failure path inside `deliver`; a worker crash, a pod eviction, an OOM kill, or the constraint violation described above leaves them there, and `_claim_batch` filters on `status == "pending"` so they are never reconsidered.
What breaks in production: every worker restart permanently strands the batch that was in flight — up to 100 events per restart silently never delivered, with the delivery listed to the customer as neither delivered nor failed.
Fix: add a bounded lease rather than a bare state flag — record `claimed_at` (or reuse `updated_at`) when setting `in_flight`, and have `_claim_batch` also select rows where `status = 'in_flight' AND updated_at < now() - interval '5 minutes'`, resetting them to `pending` with `attempts` preserved so the retry budget is not silently refilled. Preserve what `in_flight` is for: a row currently being delivered by a live worker must still not be re-claimed — do not fix by deleting the state or by making `_claim_batch` ignore status. Deny side: a row set `in_flight` one second ago is not re-claimed. Allow side that must still succeed: a row set `in_flight` six minutes ago is re-claimed exactly once and delivered. Boundary and tie: a row at exactly the 5-minute lease edge must fall on one stated side (recommend `<` strictly older, so exactly-5-minutes is not reclaimed) and two workers reclaiming the same expired row must be serialised by the same atomic status transition `_claim_batch` uses. Red-prove separately by execution: (i) remove the age predicate → the stranded-row assertion reds; (ii) remove `attempts` preservation → the retry-budget assertion reds.

### Major: the retry policy retries 4xx, contradicting the documented contract
File: `app/webhooks/delivery.py` — `deliver()`, the branch after `if 200 <= response.status_code < 300`
What is wrong: every non-2xx status falls through to the retry path, but `docs/webhooks.md` states "5xx, timeouts and connection errors are retried; a 4xx is permanent and we stop immediately".
What breaks in production: a customer endpoint returning 401 or 404 — a decommissioned URL, a rotated auth — is hammered 5 times per event across the whole event stream, burning the customer's rate limits and this system's worker capacity, while the documented "stop immediately" behaviour that operators and customers rely on never happens.
Fix: branch explicitly — `if 400 <= response.status_code < 500 and response.status_code not in RETRYABLE_4XX: _finish(delivery.id, "failed_permanent", attempt, response.status_code, detail); return` — with `RETRYABLE_4XX = {408, 429}` declared beside `MAX_ATTEMPTS`, and honour `Retry-After` on 429. Preserve what made the retry loop useful: 5xx, timeouts and connection errors must still be retried up to `MAX_ATTEMPTS` — do not fix by making everything permanent. Deny side: a 404 produces exactly one request and lands in `failed_permanent`. Allow side that must still succeed: a 503 followed by a 200 still lands in `delivered` with `attempts == 2`, and a 429 is still retried. Boundary and tie: name where 400 and 499 fall (both permanent) and where 399 and 500 fall (neither permanent), and say that a response with no status (connection error) takes the retry branch. Red-prove separately by execution: (i) remove the 4xx branch → the single-request assertion reds; (ii) remove 429 from `RETRYABLE_4XX` → the 429-retry assertion reds.

### Major: `_finish` dereferences a row that may not exist
File: `app/webhooks/delivery.py` — `_finish()` lines `row = session.get(m.WebhookDelivery, delivery_id)` then `row.status = status`
What is wrong: `session.get` returns `None` for a missing primary key and the result is used without a check, in a function that is the only writer of every terminal state.
What breaks in production: if the endpoint was deleted (the migration's `ON DELETE CASCADE` on `webhook_endpoints` removes its deliveries) while a delivery was in flight, `_finish` raises `AttributeError` inside `asyncio.gather`, which propagates out of the `try` in `run_worker`, past the `finally` that releases the lock, and kills the worker loop for every tenant.
Fix: guard with `if row is None: log.warning("delivery %s vanished before finish (status=%s)", delivery_id, status); return` so the concurrent-delete case is an explicitly named, logged no-op rather than a crash, and wrap each `deliver(...)` in `run_worker` with `asyncio.gather(..., return_exceptions=True)` plus a logged inspection of the returned exceptions so one bad delivery cannot take down the batch.
