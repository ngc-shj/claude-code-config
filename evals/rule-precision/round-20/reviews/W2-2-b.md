### Critical: the signature is computed over different bytes than the request body, so no receiver can ever verify it
File: `app/webhooks/delivery.py` — `send_once`, with `app/webhooks/signing.py` — `serialize`/`sign`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` while the body actually transmitted is produced independently by `client.post(..., json=delivery.payload)`, so the signed bytes and the wire bytes differ for any payload whose keys are not already in sorted order — the diff's own fixture `{"id": "evt_1", "type": "invoice.paid", "amount_cents": 4200}` signs as `amount_cents,id,type` but is sent in insertion order, and separator/`ensure_ascii` conventions diverge on top of that.
What breaks in production: every customer following `docs/webhooks.md` computes the HMAC over the raw request body and gets a mismatch, so 100% of deliveries are rejected as forged and the entire feature is dead on arrival — while our own delivery records mark them `delivered` because we only look at the 2xx.
Fix: make the serialized bytes the single source for both signing and transport — in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, sign that exact `bytes`, and send it with `client.post(endpoint.url, content=body, headers=headers)` so `Content-Type: application/json` is set explicitly by the existing `headers` dict rather than by httpx's json encoder. Change `sign()` to accept `body: bytes` instead of `dict` so the dict-to-bytes step cannot be repeated at two call sites (this is the R40 "actual producer output through the actual consumer" alignment; do not fix it by dropping `sort_keys=True`, which would leave two independent serializers that merely happen to agree today). **Preserve**: `serialize()` must stay deterministic — canonical key order is what lets a receiver re-serialize if it wants to; the fix must not remove it. **Allow side to pin**: a round-trip test that captures `request.content` from the `MockTransport` handler and asserts `hmac.new(SECRET.encode(), captured_body, sha256).hexdigest()` equals the hex in the sent `X-Acme-Signature` — this must stay green, i.e. the real bytes verify. **Red-prove separately, by execution**: (a) revert `content=body` to `json=delivery.payload` and observe the round-trip assertion red on the body mismatch; (b) mutate one byte of `body` after signing and observe the same assertion red for a different reason (digest mismatch, named in the failure output). **Fail loudly**: if `serialize()` raises (non-JSON-serializable payload), `send_once` must propagate rather than send an unsigned or partially-signed request — an unserializable payload is neither "signed" nor "sent". **Boundary/tie**: for a payload with duplicate-after-normalization keys or a non-string key, `json.dumps` coerces; state that the canonical form is the coerced one and that both signer and any re-serializing receiver see it identically because they see the same bytes.

### Critical: the timestamp header is not covered by the HMAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "is what stops a captured request from being replayed", but `sign()` HMACs the body alone and returns the timestamp as an unauthenticated side value.
What breaks in production: an attacker who captures one delivery can replay it forever by rewriting only the `X-Acme-Timestamp` header — the signature still validates because the timestamp was never signed — so the replay control every customer was told to rely on is not a control at all (R49: a claim stronger than the implementation, escalated to Critical because the doc's five-minute-window instruction is the only replay defence offered and every integrator will have skipped building another).
Fix: make the signed input `f"{timestamp}.".encode() + body` inside `sign()`, so the timestamp is inside the MAC and cannot be edited independently, and update `verify()` to take the timestamp explicitly (`verify(secret, timestamp, body, signature)`) rather than regenerating a fresh `time.time()` — the current `verify()` cannot check an old request at all because it re-derives "now". **Preserve**: `TIMESTAMP_HEADER` must still be sent in the clear so a receiver can read it before verifying; the fix authenticates it, it does not hide it. **Allow side to pin**: a request signed at timestamp T verifies when checked at T+60s with a 300s window. **Red-prove separately, by execution**: (a) flip one digit of the timestamp passed to `verify` while leaving the signature intact and observe the verify assertion red; (b) hold the timestamp constant and flip one byte of the body and observe a *different* assertion red; (c) advance the checking clock to T+301s and observe the freshness assertion red. **Fail loudly**: a request missing or with a non-numeric `X-Acme-Timestamp` must be rejected by the documented receiver algorithm, not treated as timestamp 0 or as "no window to check" — say so explicitly in `docs/webhooks.md`. **Boundary/tie**: state that exactly-300s-old is accepted and 301s is rejected, and that two requests sharing one timestamp are both valid (the timestamp is a freshness bound, not a nonce — dedup is on `event_id`, as the docs already say).

### Critical: signing secrets are generated with a predictable PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice`, i.e. the Mersenne Twister global generator, which is fully reconstructible from a modest number of observed outputs and is not a CSPRNG.
What breaks in production: an attacker who obtains a few secrets (their own registered endpoints — this endpoint is self-service) can recover the generator state and derive other tenants' signing secrets, letting them forge webhooks that every customer's verification accepts as ours.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete the `random`/`string`/`_ALPHABET` imports so the weak generator cannot be reached from this module at all; rename `SECRET_BYTES` accordingly or keep it and document that it is now a byte count rather than a character count. **Preserve**: the `whsec_` prefix and the property that the secret is URL/header-safe — `token_urlsafe` keeps both; do not fix this by shortening or by dropping the prefix that lets support recognise the credential class. **Allow side to pin**: `new_signing_secret()` still starts with `SECRET_PREFIX`, and two consecutive calls differ. **Red-prove separately, by execution**: (a) seed `random.seed(0)` in a test and assert `new_signing_secret()` is *not* reproducible across two seeded runs — this reds against the current implementation and greens after; (b) mutate `SECRET_BYTES` to 4 and observe an entropy-floor assertion (`len(secret) - len(SECRET_PREFIX) >= 32`) red for a reason the output names. Note that the existing `test_new_signing_secret_has_prefix_and_length` cannot fail for either mutation — it asserts a length that `random.choice` satisfies exactly as well, which is why the weak generator shipped. **Fail loudly**: `secrets.token_urlsafe` raising (no OS entropy source) must propagate and fail endpoint creation, never fall back to `random`. **Boundary/tie**: state the minimum accepted secret length as an asserted constant so a later edit that lowers it reds rather than silently weakening every new endpoint; two endpoints colliding on a secret is a 2^-256 event and is not handled.

### Critical: `verify()` compares the MAC with `==`
File: `app/webhooks/signing.py` — `verify`, line `return expected == signature`
What is wrong: the recomputed signature is compared to the supplied one with Python's short-circuiting `==` instead of `hmac.compare_digest` (RS1).
What breaks in production: the byte-by-byte early exit leaks the position of the first differing character, letting a remote caller recover a valid signature one byte at a time — and this is the function `docs/webhooks.md` implicitly holds up as the reference implementation while telling customers to "use a constant-time comparison", so it is the exact control it claims to demonstrate.
Fix: `return hmac.compare_digest(expected, signature)`, with both operands coerced to `str` of equal character class first (`compare_digest` accepts ASCII-only `str`; a non-ASCII header must be rejected before the call, not passed in). **Preserve**: `verify` must keep returning a plain `bool` — callers branch on it; do not "fix" it by raising, which changes every call site's control flow. **Allow side to pin**: a signature produced by `sign` for the same secret, timestamp and body still returns `True`. **Red-prove separately, by execution**: (a) replace `compare_digest` with `==` and assert a test that feeds a signature differing only in its final character still returns `False` — this stays green either way, so it is *not* the proof; the actual proof is (b) a grep-level or AST assertion in the suite that `signing.py` contains no `==` on a value named `signature`/`expected`, mutated by re-introducing `==` and observed red. **Fail loudly**: a `signature` argument of the wrong type or containing non-ASCII must return `False` via an explicit guard that names the rejection in a log line, not raise a `TypeError` out of `compare_digest` that a caller's broad `except` would turn into a skipped check. **Boundary/tie**: equal-length-but-different and different-length inputs both return `False`; state that `compare_digest` does not hide the length difference, so the fix does not claim length-blinding it cannot deliver.

### Critical: `GET /webhook-endpoints` returns every endpoint's signing secret
File: `app/api/routes/settings.py` — `list_webhook_endpoints`, via `app/webhooks/models.py` — `WebhookEndpoint.to_dict`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret` and is used both by the create route (where returning the secret once is intended) and by the list route, directly contradicting `docs/webhooks.md` — "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret becomes permanently readable by anyone holding a read-scoped session or API credential for the org, and it is written into every response log, browser cache and support screenshot of a routine settings fetch — so the credential's blast radius is every actor with read access rather than the one operator who created the endpoint.
Fix: remove `signing_secret` from `WebhookEndpoint.to_dict()` — it is the shared serializer, so the removal is the cross-cutting fix — and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable it already has in hand. **Preserve**: creation must still surface the secret exactly once; a fix that removes it from both paths would make the feature unusable, which is the "do not fix by deleting what made it useful" case. **Allow side to pin**: the create response still contains a `signing_secret` starting with `whsec_`. **Red-prove separately, by execution**: (a) add `signing_secret` back into `to_dict()` and observe a list-route test asserting `"signing_secret" not in response.json()[0]` go red; (b) delete the `{**..., "signing_secret": secret}` merge and observe the create-route test asserting the secret is present go red — two mutations, two different assertions. **Fail loudly**: if `new_signing_secret()` fails, endpoint creation must 5xx rather than persist an endpoint with an empty secret that would then sign with `b""`. **Boundary/tie**: state that a re-created endpoint gets a fresh secret and the old one is not recoverable through any route, so support has no in-band read path either.

### Critical: the deliveries listing has no tenancy predicate
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters on `WebhookDelivery.endpoint_id == endpoint_id` only, with no join back to `WebhookEndpoint.org_id == user.org_id`, while the two sibling routes in the same diff (`list_api_keys`, `list_webhook_endpoints`) both filter on `org_id` — the tenancy pattern exists in this file and was not propagated to the new route (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` and read other organizations' delivery records, and `WebhookDelivery.to_dict()` exposes `event_type` and delivery status — cross-tenant disclosure of another customer's billing event stream.
Fix: join and filter, e.g. `.join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and return 404 (not 403) when the join yields nothing so the route does not confirm the existence of another org's endpoint id. **Preserve**: the ordering and `limit` behaviour must not change — the fix narrows the row set, it does not alter pagination. **Allow side to pin**: a user reading their *own* endpoint's deliveries still gets every row they got before, asserted on a fixture with two orgs where org A sees exactly its own N rows. **Red-prove separately, by execution**: (a) drop the `org_id` filter and observe the cross-tenant test (org B requesting org A's endpoint) go red on a non-empty body; (b) keep the filter but change 404 to 403 and observe the enumeration-response test go red — two clauses, two mutations. **Fail loudly**: when `user.org_id` is `None` or unresolvable the route must deny, never fall through to an unfiltered query. **Boundary/tie**: an endpoint id that exists but belongs to no org (orphan) returns 404, same as a nonexistent id; state that the two are indistinguishable to the caller by design.

### Critical: endpoint URLs are unvalidated against internal targets and the documented https-only rule is not enforced
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, line `if not parsed.scheme.startswith("http") or not parsed.netloc:`
What is wrong: `scheme.startswith("http")` admits `http://`, and also `httpx://`, `http+unix://` and any other scheme with that prefix, while `docs/webhooks.md` states "Only `https://` URLs are accepted"; there is no check on the resolved host at all (RS3 — the boundary check exists but does not decide the property the sink cares about).
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/` or `http://10.0.0.5:6379/`, and our own delivery worker POSTs signed, authenticated-looking requests from inside the VPC to that address on every matching event — a self-service SSRF with an attacker-chosen body, plus plaintext transmission of event payloads for every `http://` endpoint registered.
Fix: replace the prefix test with an exact `parsed.scheme != "https"` rejection, then resolve `parsed.hostname` and reject when every resolved address is not global — `all(ipaddress.ip_address(ai[4][0]).is_global for ai in socket.getaddrinfo(host, None))` — rejecting loopback, link-local, private, CGNAT and reserved ranges, and reject a `parsed.port` outside an explicit allowlist (`None`, 443). Enforce this at registration *and* re-check the resolved address at send time in `send_once`, because DNS can be re-pointed after registration (the same predicate must live in one helper called from both, or it is R1 duplication of a security control). **Preserve**: legitimate public HTTPS endpoints on non-standard ports must still be registrable if the allowlist says so — name the allowlist rather than hardcoding 443 silently, so the fix does not quietly delete a capability customers use. **Allow side to pin**: `https://hooks.example.com/acme` (the docs' own example, and the test file's `FakeEndpoint.url`) still registers and still delivers. **Red-prove separately, by execution**: (a) `http://hooks.example.com/` must 422 — mutate the check back to `startswith("http")` and observe it red; (b) `https://127.0.0.1/x` must 422 — remove the `is_global` test and observe a *different* assertion red; (c) `https://example.com:6379/` must 422 — remove the port allowlist and observe a third assertion red. **Fail loudly**: when `getaddrinfo` raises or returns nothing, reject with 422 and a log line naming "unresolvable host" — "could not check" must not be spelled the same as "checked and clean". **Boundary/tie**: state that a hostname resolving to a mix of global and private addresses is rejected (all-must-be-global, not any), and that the tie between registration-time and send-time resolution is broken in favour of the send-time check denying.

### Critical: the delivery client follows redirects, carrying the signed request to an arbitrary host
File: `app/webhooks/delivery.py` — `run_worker`, `httpx.AsyncClient(timeout=REQUEST_TIMEOUT, follow_redirects=True)`
What is wrong: with `follow_redirects=True`, a customer endpoint answering `307`/`308` makes us re-issue the POST — body, signature header and all — to whatever `Location` it names, defeating any registration-time host check.
What breaks in production: a registered public HTTPS endpoint redirects to `http://169.254.169.254/` or to an internal service and our worker delivers the signed payload there, so the SSRF fix on the registration route above is bypassed by a one-line response from the endpoint owner.
Fix: set `follow_redirects=False`, and in `deliver` treat a 3xx as a non-2xx outcome recorded with `detail = f"HTTP {status}: redirect to {response.headers.get('location')!r} not followed"`. **Preserve**: the ability for a customer to *see* why their redirect-based endpoint fails — the detail string is what makes this diagnosable, so do not fix it by silently dropping 3xx. **Allow side to pin**: a plain `200` from the registered URL still delivers, and a `301` recorded as a failure still produces a delivery row (not an exception). **Red-prove separately, by execution**: (a) set `follow_redirects=True` again and observe a `MockTransport` test asserting the second request never reaches the redirect target go red; (b) remove the 3xx detail line and observe the assertion on `response_body` content go red. **Fail loudly**: a response with no `Location` on a 3xx must still be recorded as a failure naming the missing header, not skipped. **Boundary/tie**: state that 300–399 inclusive is the non-followed band and that 3xx is *permanent* (it is a misconfiguration, not a transient) so it does not consume all five attempts.

### Critical: the migration's status CHECK constraint does not contain the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, against `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` — `STATUSES`
What is wrong: the SQL enumerates `'failed'` while both `models.STATUSES` and the only write site in `delivery.py` use `'failed_permanent'`.
What breaks in production: every delivery that exhausts its attempts raises a check-constraint violation on the terminal write, so the row stays in whatever status it held, the exception escapes `deliver` into `asyncio.gather`, and the batch loop in `run_worker` dies — permanently failing endpoints wedge the whole worker rather than being recorded as failed.
Fix: change the SQL to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive the SQL list from `models.STATUSES` in a test rather than restating it — `STATUSES` is already declared in the diff and currently unused, so the constant exists and the migration reimplemented it (R1/RT3). **Preserve**: the CHECK constraint itself must stay — a fix that drops the constraint to make the write succeed removes the thing that made the drift visible. **Allow side to pin**: an insert with each of the four `STATUSES` values succeeds; a fifth value is rejected by the database. **Red-prove separately, by execution**: (a) revert the SQL to `'failed'` and observe a test that parses the migration's `IN (...)` list and compares it to `models.STATUSES` go red naming the missing member; (b) add a bogus member to `STATUSES` and observe the same test go red from the other direction — the comparison must be a set equality, not a subset check. **Fail loudly**: if the test cannot locate or parse the `CHECK` clause in the migration file, it must fail with "constraint not found", never pass by finding nothing to compare. **Boundary/tie**: state that `STATUSES` is the single ordering-free source and that adding a status requires the same commit to touch both the tuple and a new migration.

### Critical: the unique index on `event_id` allows only one delivery row per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: uniqueness is declared on `event_id` alone, but `enqueue_for_event` inserts one row per matching endpoint for a single `event_id`.
What breaks in production: any organization with two or more active endpoints subscribed to the same event type gets an `IntegrityError` on the second row of the `add_all`, the whole insert rolls back, and the dispatcher's blanket `except Exception` downgrades it to a `log.warning` — so multi-endpoint customers silently receive *no* webhooks at all, with a warning line as the only trace.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — the pair is what "at-least-once, deduplicate on `event_id`" in `docs/webhooks.md` actually means per endpoint. **Preserve**: keep the index unique. It is the idempotency guard that stops a re-dispatched event from double-enqueuing to the same endpoint; a fix that makes it a plain index removes the protection instead of correcting its key. **Allow side to pin**: one event fanned out to two endpoints of the same org inserts two rows and both are delivered; the same `(endpoint_id, event_id)` enqueued twice inserts once. **Red-prove separately, by execution**: (a) revert the index to `(event_id)` and observe a two-endpoint fan-out test go red on the `IntegrityError`; (b) drop `UNIQUE` and observe a re-enqueue test asserting `count == 1` go red — two clauses, two mutations. **Fail loudly**: `enqueue_for_event` must not swallow an `IntegrityError` into a success return; a conflict on the pair is a legitimate no-op that must be counted separately from an insert (use an explicit `ON CONFLICT DO NOTHING` and return the affected count) so "enqueued nothing because it was already there" is distinguishable from "enqueued nothing because it failed". **Boundary/tie**: state that when the same event matches an endpoint twice through overlapping `event_types` entries, the pair index collapses it to one row — that is the intended tie-break, not a dropped delivery.

### Critical: `time.sleep` inside an async coroutine blocks the event loop for the whole retry ladder
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather` for a whole batch, but it retries with the blocking `time.sleep` rather than `await asyncio.sleep`, and the entire 2+4+8+16 = 30s ladder runs inline inside one coroutine.
What breaks in production: one slow endpoint stalls every other delivery in the batch and the loop itself; with `BATCH_SIZE = 100` failing endpoints the worker blocks for ~50 minutes while the 60-second Redis lock TTL expires underneath it, so a second worker claims the same work and every customer receives duplicate deliveries.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` — `asyncio` is already imported — and additionally stop retrying inline: on a retryable failure, call `_finish(delivery.id, "pending", attempt, status_code, detail)` with `next_attempt_at = now + backoff_for(attempt)` and return, letting `_claim_batch` pick it up when due. The persisted `next_attempt_at` column and `backoff_for` already exist in the diff for exactly this and are currently dead — the inline loop reimplements the scheduler the schema provides (R1). **Preserve**: the total attempt budget (`MAX_ATTEMPTS == 5`) and the backoff shape must survive the restructuring; `test_max_attempts_matches_documented_limit` and `test_backoff_grows_exponentially` must stay green unchanged. **Allow side to pin**: a delivery that succeeds on the first attempt still completes without any sleep at all, and a delivery that fails once is picked up by the next poll and succeeds on attempt 2. **Red-prove separately, by execution**: (a) re-introduce `time.sleep` and observe a test asserting `deliver` for a failing endpoint returns within a bounded wall-clock budget go red; (b) omit the `next_attempt_at` advance and observe a test asserting the row is not re-claimable immediately go red; (c) set `MAX_ATTEMPTS` to 6 and observe the documented-limit test go red. Bound every one of these with a hard timeout so a non-terminating mutation reds rather than hangs. **Fail loudly**: if `_finish` cannot write the reschedule, the delivery must not be left in `in_flight`; the failure must be logged at error and the row reset to `pending`. **Boundary/tie**: `next_attempt_at <= now` is the claim predicate — state that a row due at exactly `now` is claimed, and that two rows with identical `next_attempt_at` are ordered by primary key so the batch cut never skips one (see the ordering finding below).

### Major: ORM rows are used after their session has closed, unlike every other query in the diff
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` from inside `with session_scope()`) and `deliver` (`endpoint` read outside the block)
What is wrong: `_claim_batch` returns live `WebhookDelivery` instances out of the `with session_scope()` block and `deliver` fetches `endpoint` inside a block then reads `endpoint.url` / `endpoint.signing_secret` after it — whereas every other query in this diff (`list_api_keys`, `list_webhook_endpoints`, `list_deliveries`, `create_webhook_endpoint`) materializes to dicts *inside* the block, so the diff establishes the pattern and these two sites depart from it.
What breaks in production: on the standard `expire_on_commit=True` configuration every attribute read after the commit re-issues a load on a closed session and raises `DetachedInstanceError`, so `deliver` throws before the first HTTP call and no webhook is ever sent; the deciding fact is `session_scope`'s expiry setting, which the diff does not show — if it disables expiry, the reads succeed but silently serve pre-commit values.
Fix: have `_claim_batch` return plain tuples/dataclasses built inside the block (`(row.id, row.endpoint_id, row.attempts, row.payload)`), and have `deliver` read `endpoint.url` and `endpoint.signing_secret` into locals inside its own `with` block before leaving it — matching the existing pattern rather than introducing a third convention. **Preserve**: `_claim_batch` must keep flipping `status` to `in_flight` inside the transaction; that write is the claim, and returning detached copies must not turn it into a read-only query. **Allow side to pin**: a batch of one claimable row still yields one item whose `payload` equals what was stored, and the row's status in the database is `in_flight` after the call. **Red-prove separately, by execution**: (a) return the ORM rows again and observe the payload assertion red on `DetachedInstanceError`; (b) remove the `row.status = "in_flight"` line and observe a separate assertion on the persisted status go red. **Fail loudly**: if `session.get(m.WebhookEndpoint, ...)` returns `None` (endpoint deleted between enqueue and send), `deliver` must record the delivery as permanently failed with "endpoint removed" rather than raising `AttributeError` — see the `_finish` finding below for the same missing-row hazard. **Boundary/tie**: state that a row claimed at exactly the batch limit boundary is included, and that a row whose endpoint was deactivated after claiming is still finished (not silently dropped) so no row stays `in_flight`.

### Major: the Redis lock is acquired non-atomically and released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `get` then a separate `set`, which two workers can interleave so both believe they hold the lock; the `expire` is a third round-trip, so a crash between `set` and `expire` leaves the key with no TTL; and `run_worker` deletes the key in `finally` without checking it still owns it.
What breaks in production: two workers process the same batch and every customer gets duplicate deliveries, or — after a crash between `set` and `expire` — the untimed lock is never released and webhook delivery stops entirely across the fleet until someone deletes the key by hand.
Fix: acquire with a single atomic call carrying a unique owner token and the TTL together — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)`, returning `False` when it yields `None` — and release with a compare-and-delete Lua script (`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end`) so a worker whose lock already expired cannot delete the successor's. **Preserve**: the 60-second TTL must stay — it is what stops a crashed worker from wedging the queue; the fix moves it into the same command rather than removing it. **Allow side to pin**: a single worker still acquires, works, and releases, and can re-acquire on the next poll. **Red-prove separately, by execution**: (a) revert to `get`-then-`set` and observe a two-concurrent-acquirer test asserting exactly one `True` go red; (b) revert the compare-and-delete to a plain `delete` and observe a test where worker A's lock has expired and worker B holds it, asserting B's key survives A's release, go red; (c) drop `ex=60` and observe a TTL assertion (`ttl(LOCK_KEY) > 0`) go red. **Fail loudly**: if Redis is unreachable, `_acquire_lock` must raise or return `False` and the worker must sleep — never proceed lock-free on the assumption that "no lock found" means "free". **Boundary/tie**: state that the TTL boundary is the tie — a worker still running at T+60s has lost the lock, so it must re-check ownership before each `_finish` write rather than assuming it still holds it.

### Major: a single exception kills the worker permanently and strands rows in `in_flight`
File: `app/webhooks/delivery.py` — `run_worker`, the `try/finally` around `_claim_batch` and `gather`, and `if not batch:` after it
What is wrong: the `try` block has no `except`, so any error from `_claim_batch` or from a delivery propagates out of the `while True` loop and terminates `run_worker`; `batch` is also referenced after the `finally` and is unbound on that path (R38 non-terminal state: `in_flight` is entered on the claim path and left only on success, with nothing anywhere resetting it).
What breaks in production: one transient database blip stops all webhook delivery until the process is restarted, and every row the dead batch had already flipped to `in_flight` is invisible to `_claim_batch` forever — those events are never delivered and never marked failed, so they do not appear in the customer's delivery listing as failures either.
Fix: wrap the batch body in `except Exception: log.exception(...)` and continue the loop; initialize `batch = []` before the `try` so the post-`finally` check is always bound; and add a reclaim path — in `_claim_batch`, also select rows in `in_flight` whose `updated_at` is older than a `STALE_AFTER` constant and reset them to `pending`. **Preserve**: `in_flight` must remain a real claim marker that prevents two workers taking the same row — the reclaim window must be longer than the lock TTL, so the fix does not achieve recovery by deleting the exclusion. **Allow side to pin**: a healthy batch still completes and the loop still sleeps `poll_interval` when there is nothing to do; a row claimed 5 seconds ago is *not* reclaimed. **Red-prove separately, by execution**: (a) make `_claim_batch` raise once and assert the worker is still looping afterwards — revert the `except` and observe it red; (b) delete the `batch = []` initializer and, with `_claim_batch` raising, observe a `NameError` assertion red; (c) age a row's `updated_at` past `STALE_AFTER` and assert it is reclaimed — remove the reclaim clause and observe that assertion red. **Fail loudly**: a row that has been reclaimed more than `MAX_ATTEMPTS` times must go to `failed_permanent` with "stalled" as the detail, so a poison row is visible rather than cycling silently. **Boundary/tie**: state that `updated_at` exactly at the `STALE_AFTER` boundary is reclaimed, and that `STALE_AFTER > 60s` (the lock TTL) so a live worker's rows are never stolen mid-flight.

### Major: 4xx responses are retried, contrary to the documented and correct behaviour
File: `app/webhooks/delivery.py` — `deliver`, and `docs/webhooks.md` — "Retries"
What is wrong: the loop treats every non-2xx identically and retries until `MAX_ATTEMPTS`, while the documentation states "a 4xx is permanent and we stop immediately".
What breaks in production: a customer who removes an endpoint route and starts returning 404, or whose WAF returns 403, has every event retried five times with a signed body, which multiplies our outbound volume against an endpoint that will never accept it and delays the `failed_permanent` signal the customer needs to see in the deliveries listing (R29: the doc is a load-bearing claim that the implementation does not honour).
Fix: after computing `status_code`, branch — `if status_code is not None and 400 <= status_code < 500 and status_code not in RETRYABLE_4XX: _finish(delivery.id, "failed_permanent", attempt, status_code, detail); return` — with `RETRYABLE_4XX = {408, 425, 429}` as a named constant beside `MAX_ATTEMPTS`. **Preserve**: 5xx, timeouts and connection errors must still retry — the docs promise that, and a fix that makes all non-2xx permanent would delete the retry feature. **Allow side to pin**: a 503 followed by a 200 still ends `delivered` with `attempts == 2`; a 429 still retries. **Red-prove separately, by execution**: (a) return 404 and assert `attempts == 1` and status `failed_permanent` — remove the branch and observe it red; (b) return 429 twice then 200 and assert `attempts == 3` — add 429 to the permanent set and observe that assertion red; (c) return 503 five times and assert `failed_permanent` at `attempts == 5`. **Fail loudly**: a response whose `status_code` we could not read (transport error) must take the retry path and be logged as such, never be classified as 4xx by default. **Boundary/tie**: 400 and 499 are permanent, 500 is retryable, and 399 does not reach this branch (see the redirect finding) — state each edge explicitly.

### Major: webhook enqueue failures are swallowed, outside the transaction that persisted the event
File: `app/events/dispatcher.py` — `dispatch`, the `try/except Exception: log.warning(...)` around `enqueue_for_event`
What is wrong: the enqueue runs after the event's `session_scope` has closed and any failure is downgraded to a `WARNING` with no retry, no dead-letter and no marker on the event row, so the event is durably committed while its deliveries are not (R9: fire-and-forget outside the transaction boundary).
What breaks in production: any transient database error, or the `IntegrityError` the `event_id` unique index guarantees for multi-endpoint orgs, drops the webhooks for a billing event permanently — with no queue entry, nothing shows up in the customer's deliveries listing and nothing will ever retry, so the loss is invisible on both sides.
Fix: move the `enqueue_for_event` insert into the same `session_scope` as the `Event` insert so the delivery rows commit atomically with the event they describe, and remove the blanket `except Exception` — a failure must roll the event back and propagate to the caller, who can retry the whole dispatch. If the enqueue genuinely must stay out-of-band, replace the `log.warning` with an outbox row and a reconciliation job, and record the deviation. **Preserve**: `dispatch` must still return `event_id` and must still run the in-process `SUBSCRIBERS` — the fix changes the failure handling, not the fan-out. **Allow side to pin**: a successful dispatch still returns the event id and still creates one delivery row per matching endpoint, and an event type outside `WEBHOOK_EVENT_TYPES` still commits with zero delivery rows and no error. **Red-prove separately, by execution**: (a) make `enqueue_for_event` raise and assert no `Event` row is committed — restore the `except` and observe it red; (b) make it raise and assert the exception reaches `dispatch`'s caller — a second assertion on a different clause. **Fail loudly**: the log line for a rolled-back dispatch must be `log.exception` at error level naming the event type and org, so "webhooks failed" is not spelled the same as the ordinary warning it is today. **Boundary/tie**: state that an event with zero matching endpoints commits successfully with zero rows — the empty fan-out is a success, not a failure, and the fix must not conflate them.

### Major: naive and aware datetimes are mixed across the model, the enqueue path and the migration
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`); `app/webhooks/models.py` — `_now()`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP` columns
What is wrong: `enqueue_for_event` writes a naive `datetime.utcnow()` into a column the model declares as `DateTime(timezone=True)` and that `_claim_batch` compares against an aware `datetime.now(timezone.utc)`, while the migration creates the columns as `TIMESTAMP` (without time zone) — three inconsistent conventions for one column, and `models._now()` already exists as the correct helper the enqueue path did not use (R1).
What breaks in production: PostgreSQL interprets the naive value in the server's `TimeZone` setting, so on any non-UTC server every delivery's `next_attempt_at` is offset by the UTC offset — deliveries either fire hours early (claimed immediately regardless of backoff) or sit unclaimable for hours, and the drift is invisible because both sides look like plausible timestamps.
Fix: call the existing `models._now()` in `enqueue_for_event` instead of `datetime.utcnow()`, and change every `TIMESTAMP` in the migration to `TIMESTAMPTZ` so the storage type matches the `timezone=True` the models declare; `now()` already returns `timestamptz` so the column defaults become lossless. **Preserve**: `created_at`/`updated_at` defaults must keep working without application changes — `TIMESTAMPTZ DEFAULT now()` preserves that. **Allow side to pin**: a delivery enqueued now with a zero backoff is claimable now, on a server whose `TimeZone` is not UTC. **Red-prove separately, by execution**: (a) set the session `TimeZone` to `America/New_York`, enqueue, and assert the round-tripped `next_attempt_at` equals the aware value written — revert to `utcnow()` and observe it red; (b) assert `_claim_batch` returns the row under that same non-UTC session — a second clause with its own mutation. **Fail loudly**: if a naive datetime reaches the model, raise rather than coerce — add an explicit assertion in `_now`'s consumers so "no timezone" is not silently read as UTC. **Boundary/tie**: state that `next_attempt_at <= now` includes equality, so a row due at exactly the poll instant is claimed rather than deferred a full `poll_interval`.

### Major: request headers including the signature are written to the info log on every delivery
File: `app/webhooks/delivery.py` — `send_once`, line `log.info("POST %s headers=%s", endpoint.url, headers)`

### Major: the entire third-party response body is stored unbounded in the database
File: `app/webhooks/delivery.py` — `deliver` (`response.text` passed as `detail`) and `_finish` (`row.response_body = detail`)
What is wrong: whatever the customer's endpoint returns is read fully into memory and written into the `response_body TEXT` column, with no size cap on either side.
What breaks in production: a hostile or merely broken endpoint returning a multi-megabyte body has it stored per attempt for every event, so one endpoint can fill the deliveries table and the worker's memory — and since the same body is echoed into `detail` on failure, it also passes through the log line above.
Fix: cap at read time and at write time — read with `response.text[:RESPONSE_BODY_LIMIT]` behind a named `RESPONSE_BODY_LIMIT = 4096` beside `MAX_ATTEMPTS`, and set `httpx.AsyncClient(..., limits=...)` / use `response.aread()` with an explicit max so a body larger than the cap is never fully buffered. **Preserve**: the stored prefix must still be long enough to diagnose a failure — the fix truncates, it does not stop recording, and it must append a marker like `…[truncated]` so a reader can tell a cap from a short body. **Allow side to pin**: a 12-byte body such as the test's `"ok"` is stored verbatim with no truncation marker. **Red-prove separately, by execution**: (a) return a body of `RESPONSE_BODY_LIMIT + 1` bytes and assert the stored value is exactly `RESPONSE_BODY_LIMIT` characters plus the marker — remove the cap and observe it red; (b) return exactly `RESPONSE_BODY_LIMIT` bytes and assert no marker is appended — a separate clause with its own mutation. **Fail loudly**: a body that cannot be decoded as text must be recorded as `"<binary, N bytes>"`, not raise out of `deliver`. **Boundary/tie**: exactly-at-the-limit is stored untruncated, limit+1 is truncated — state it, because an off-by-one here is what makes the marker assertion flap.
