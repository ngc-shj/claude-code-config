### Critical: the published signature contract and the implemented one are different functions, so every conforming consumer rejects every delivery
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, against `docs/webhooks.md` "Verifying the signature"
What is wrong: the doc tells customers the MAC is `HMAC-SHA256("{timestamp}.{raw_request_body}")`, while `sign()` MACs `json.dumps(payload, sort_keys=True)` with the timestamp not fed into the MAC at all and the byte string signed not being the body `httpx` actually puts on the wire (`client.post(..., json=delivery.payload)` in `delivery.send_once` serializes with its own separators and insertion order, not `sort_keys=True`).
What breaks in production: every customer who implements the documented verification computes a different digest and rejects 100% of deliveries, and because the timestamp is outside the MAC an attacker who captures one request can rewrite `X-Acme-Timestamp` freely, so the documented "reject requests more than five minutes old" replay defence protects nothing.
Fix: make the signed string the exact transmitted bytes. Change `send_once` to build the body once — `body = serialize(delivery.payload).encode()` — pass it as `content=body` (not `json=`) with an explicit `Content-Type: application/json`, and change `sign` to take those bytes: `sign(secret, timestamp, body)` returning `hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`. `verify(secret, timestamp, raw_body, signature)` must take the raw bytes the receiver got, never a re-parsed dict, and must reject when `abs(now - int(timestamp)) > 300`. Deny side and allow side both pinned: a test that mutates one byte of the body, one character of the timestamp header, and a timestamp 301s old must each fail verification, and a test that feeds the *actual* `MockTransport`-captured `request.content` and captured timestamp header back through `verify` must pass — this is the R40 actual-producer-output-through-actual-consumer round trip, and it is what makes the doc's example implementable. Red-prove each clause separately by execution: (i) drop the `f"{timestamp}."` prefix and observe only the timestamp-tamper assertion redden; (ii) revert `content=` to `json=` and observe only the byte-identity assertion redden; (iii) widen the window to 86400 and observe only the staleness assertion redden. Preserve what the current code got right: the payload must still reach the endpoint as JSON with the same fields, and `serialize`'s `sort_keys=True` must stay so the signed bytes are reproducible. Boundary and tie: age exactly 300s is ACCEPTED, 301s rejected, and two deliveries sharing a timestamp are independent — the timestamp is a freshness bound, never an identity, so dedup stays on `event_id` as the doc says.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is 32 characters drawn with `random.choice`, which is the Mersenne Twister — a fully reconstructible generator, and the constant is named `SECRET_BYTES` while it actually counts characters from a 62-symbol alphabet.
What breaks in production: an attacker who observes enough output from the same process (or simply brute-forces the seed) recovers the state and predicts every subsequently issued endpoint secret, at which point they can forge signed webhooks that any customer's verifier accepts as genuine — the entire integrity story of the feature collapses.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and `import secrets`; delete the `random`/`string`/`_ALPHABET` imports so the weak generator cannot be re-reached, and rename nothing else so `SECRET_PREFIX` stays the customer-visible marker. The allow side that must still hold: a freshly issued secret still round-trips through `sign`/`verify` and still starts with `whsec_` — pin that with the existing `test_verify_accepts_signature_produced_by_sign`. Repair the test that currently green-proves the defect: `test_new_signing_secret_has_prefix_and_length` asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which is a character count and will go red on the correct fix; replace it with an assertion on decoded entropy (`len(base64.urlsafe_b64decode(secret[len(SECRET_PREFIX):] + "==")) >= 32`) plus a uniqueness assertion over 1000 draws. Red-prove by execution, one mutation per clause: (i) swap `secrets.token_urlsafe` back to the `random.choice` comprehension and observe the entropy assertion redden; (ii) hardcode a constant return and observe only the uniqueness assertion redden. Fail loudly rather than silently: `secrets` is stdlib, so there is no missing-tool case, but do not add a `try/except ImportError` fallback to `random` — an unavailable CSPRNG must raise, not degrade. Boundary: 32 decoded bytes is the floor, and two secrets that happen to share a prefix are still distinct secrets — comparison is over the whole string.

### Critical: the shipped signature verifier compares digests with `==`
File: `app/webhooks/signing.py` — `verify()`, `return expected == signature`
What is wrong: `verify` is the reference implementation the change ships for signature checking and it compares the expected MAC to the supplied one with a short-circuiting `==`, while `docs/webhooks.md` instructs customers to "compare it against your own computation using a constant-time comparison" — the doc demands of the customer exactly what the shipped helper does not do (RS1; also R49: a claim stronger than the implementation).
What breaks in production: the byte-by-byte early exit leaks the position of the first differing byte through response timing, letting an attacker recover a valid signature one byte at a time against any service that uses this helper on an inbound path, and every internal caller that adopts it inherits the leak.
Fix: `return hmac.compare_digest(expected, signature)` — `hmac` is already imported in this file, so no new dependency and no new helper is warranted (codebase awareness: there is no other comparison helper anywhere in the diff to reuse). Pair deny with allow: keep `test_verify_accepts_signature_produced_by_sign` green (a correct signature must still verify) and keep `test_verify_rejects_a_signature_made_with_another_secret` red-side, and add a case where `signature` is the empty string and one where it is the correct digest with one character changed. Red-prove each separately: (i) revert to `==` and confirm the correctness tests stay green — proving the timing property is NOT test-observable, which is why it must be enforced by the primitive rather than asserted; (ii) return a constant `True` and observe the wrong-secret test redden; (iii) return a constant `False` and observe the accept test redden, which is the clause that stops "always deny" from satisfying the fix. Fail loudly on inputs `compare_digest` cannot handle: a non-`str`/non-`bytes` or non-ASCII `signature` raises `TypeError` inside `compare_digest`; catch it at the call boundary and return `False` explicitly with a log line naming the rejection, so "could not compare" is never spelled the same as "compared and matched". Do not achieve constant time by deleting the comparison or by hashing both sides again — the behaviour to preserve is that a signature from a different secret is rejected.

### Critical: every endpoint read hands back the signing secret, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()`, consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` unconditionally includes `"signing_secret"`, and `GET /v1/settings/webhook-endpoints` returns `[e.to_dict() for e in endpoints]`, while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret that authenticates every outbound webhook is served on a plain list route, so any credential with read scope on settings (a leaked read-only API key, a browser extension reading the console, a support tool, an access log capturing the response) yields signature-forging capability for that organization forever, and the doc's promise means nobody rotates.
Fix: remove `"signing_secret"` from `WebhookEndpoint.to_dict()` and have `create_webhook_endpoint` build its 201 response explicitly as `{**endpoint.to_dict(), "signing_secret": secret}` from the local variable returned by `new_signing_secret()` — the disclosure then lives at exactly one call site instead of in the shared serializer. Pair the sides explicitly: assert that the POST response body still contains a `whsec_`-prefixed `signing_secret` (the feature must stay usable — customers cannot verify anything without receiving it once) and assert that the GET list response for the same endpoint has no `signing_secret` key at all. Red-prove separately: (i) re-add the key to `to_dict()` and observe only the list-route assertion redden; (ii) drop the `**` merge in the create route and observe only the create-route assertion redden. Fail loudly: if the merge is ever reached with `secret is None`, raise rather than emit an endpoint record with a missing secret field — an absent secret must not read as a successful creation. Cross-cutting check performed: `WebhookDelivery.to_dict()` exposes no secret material, and no other serializer in the diff carries a credential, so this is the only member of the class.

### Critical: the deliveries route has no tenancy predicate — any authenticated user can read any organization's delivery history
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: `endpoint_id` comes straight from the path and is used as the sole filter, with no join back to `WebhookEndpoint.org_id == user.org_id` — its two siblings in the very same file, `list_api_keys` and `list_webhook_endpoints`, both scope on `user.org_id`, so the pattern the file already establishes was not propagated to the new route (R3, security-relevant).
What breaks in production: enumerating small integer `endpoint_id` values returns other tenants' delivery records — event ids, event types, delivery status and response codes — a cross-tenant data leak reachable by any valid credential with no privilege escalation required.
Fix: join and scope in one query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id)`. Pair the sides: an owner requesting their own endpoint must still receive their rows (assert the exact row ids, not just a 200), and a user from another org requesting the same `endpoint_id` must receive 404 — and per RT8 the test must assert the *absence of the foreign rows in the body*, not merely the status code, because a route that returns 404 with the rows attached would satisfy a status-only assertion. Red-prove each clause by execution: (i) delete the `org_id` predicate and observe the cross-tenant test redden while the owner test stays green; (ii) change the predicate to `!=` and observe the owner test redden — this is the clause that stops "deny everyone" from passing. Fail loudly on the unresolvable subject: an `endpoint_id` that exists but belongs to another org and one that does not exist at all must both return 404 with the same body, so probing cannot distinguish them. Boundary and tie: an endpoint whose `org_id` is exactly `user.org_id` is IN; a deactivated (`active=False`) endpoint owned by the user is still IN, since delivery history must remain readable after an endpoint is disabled — do not fix by filtering on `active`, which would delete the feature the route exists for. Apply the same predicate to any future per-endpoint route; `list_webhook_endpoints` and `list_api_keys` were checked and are already correctly scoped.

### Critical: customer-supplied URLs are accepted unvalidated and followed through redirects — server-side request forgery
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http") or not parsed.netloc`; and `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: `startswith("http")` admits `http://` and any scheme merely prefixed `http` (`httpx://`, `httpfoo://`), there is no check that the host is publicly routable, and the delivery client follows redirects, so even an initially-clean host can bounce the request anywhere — while `docs/webhooks.md` asserts "Only `https://` URLs are accepted" (R49: the claim is stronger than the check).
What breaks in production: a tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or an internal admin service, or a public host that 302s to one) and the worker POSTs to it from inside the trust boundary on every matching event, turning the webhook fleet into an authenticated internal-network request generator; the plain-`http` case additionally ships the payload in cleartext.
Fix: replace the scheme test with an explicit allow decision — `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)` — then resolve `parsed.hostname` with `socket.getaddrinfo` and reject when **any** returned address satisfies `ipaddress.ip_address(a).is_private or .is_loopback or .is_link_local or .is_reserved or .is_multicast`. Set `follow_redirects=False` on the delivery client and treat a 3xx as a non-retryable failure, since a redirect target is a URL the tenant never registered and therefore never passed the check. Pair the sides: `https://hooks.example.com/acme` (the doc's own example) must still be accepted and must still be delivered to — assert that, or the fix is unmeasured in the direction that gets it reverted. Red-prove one mutation per clause by execution: (i) restore `startswith("http")` and observe only the `http://` rejection redden; (ii) delete the address-class check and observe only the `https://localhost` / `https://[::1]` rejection redden; (iii) set `follow_redirects=True` and observe only the redirect test redden. Fail loudly where the check cannot decide: a hostname that fails to resolve must be **rejected** with a message naming resolution failure, never accepted on the grounds that nothing was found. Boundary and tie: a host resolving to *both* a public and a private address is REJECTED (any private answer denies), and because DNS can be re-pointed after registration the same address-class check must run again in the worker against the connected peer — state in the code comment that registration-time validation alone leaves a DNS-rebinding window open (R49: declare this as a fail-closed gate at both points, not as an enforceable boundary at one).

### Critical: the migration's CHECK constraint does not include the status the code writes on permanent failure
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py` `STATUSES` and `app/webhooks/delivery.py::deliver` writing `"failed_permanent"`
What is wrong: the schema permits `failed` while both the model's `STATUSES` tuple and the only writer, `_finish(delivery.id, "failed_permanent", ...)`, use `failed_permanent` — the two spellings of the same enum were written independently and never reconciled (R40, enum spelling across a strict consumer; the database is the strict consumer here).
What breaks in production: every delivery that exhausts its attempts raises a `CheckViolation` inside `_finish`, the transaction rolls back, the row stays `in_flight` forever and the exception escapes `deliver` uncaught (only `httpx.HTTPError` is handled), killing the worker task — so the first permanently-failing endpoint stops the whole delivery pipeline.
Fix: make one spelling authoritative and derive the other from it. Change the migration to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and add a test that asserts set equality between `models.STATUSES` and the literals parsed out of the migration file, so the pair cannot drift again. Pair the sides: assert that inserting each of the four `STATUSES` values SUCCEEDS (the allow side — a constraint that rejects everything would satisfy a rejection-only test), and that inserting `'bogus'` raises `IntegrityError`. Red-prove separately by execution against a real database, not a mock (RT5 — a mocked session cannot validate a CHECK constraint): (i) remove `failed_permanent` from the migration list and observe only the `failed_permanent` insert redden; (ii) add a fifth value to `STATUSES` and observe only the set-equality test redden. Fail loudly when the check cannot run: if the test cannot obtain a real Postgres connection it must ERROR, not skip — a skipped constraint test reports the same green as a passing one. Boundary: this is a closed enum, so the tie case is a value present in one list and absent in the other, which is exactly what set equality catches in both directions.

### Critical: the unique index on `event_id` makes multi-endpoint organizations fail to enqueue
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint for a single `event_id`, so the uniqueness constraint is on the wrong column — it permits at most one delivery per event across all endpoints.
What breaks in production: as soon as an organization registers a second endpoint (or two orgs' endpoints match one event), `session.add_all(rows)` raises a unique violation, the whole batch is lost, and `dispatch` swallows it as `log.warning("webhook enqueue failed...")` — so the events are silently never delivered to anyone, with the failure visible only as a warning line.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);`, which is also the idempotency guard the doc's "deduplicate on `event_id`" advice implies on the receiving side. Pair the sides: assert that one event fanning out to two endpoints of the same org creates exactly two rows (the allow side — the current schema fails this), and that re-running `enqueue_for_event` with the same `event_id` creates no additional rows for an endpoint that already has one. Red-prove separately: (i) revert to the single-column index and observe only the fan-out test redden; (ii) drop the index entirely and observe only the re-enqueue/duplicate test redden. Fail loudly: `enqueue_for_event` must surface the constraint violation as a distinguishable outcome — catch `IntegrityError` and re-raise a named `WebhookEnqueueConflict` rather than letting it be swallowed by the generic `except Exception` in `dispatch`, so "nothing to enqueue" and "enqueue rejected" are not the same log line. Add the matching index for the read path while here: `list_deliveries` filters `endpoint_id` and orders `created_at desc` with no supporting index. Boundary and tie: two endpoints of the same org for one event are DISTINCT rows; the same (endpoint_id, event_id) twice is one row and the second attempt is a no-op, not an error the caller must handle.

### Critical: the worker uses ORM objects after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (returns `rows` from inside `with session_scope()`), `deliver` (reads `endpoint` and `delivery.attempts`/`.payload`/`.id` after the `with` block)
What is wrong: `_claim_batch` returns `WebhookDelivery` instances after the session that loaded them exits, and `deliver` loads `endpoint` inside a `with session_scope()` then reads `endpoint.signing_secret` and `endpoint.url` outside it — with SQLAlchemy's default `expire_on_commit=True`, every one of those attribute reads triggers a refresh on a detached instance and raises `DetachedInstanceError`.
What breaks in production: the first iteration of `run_worker` raises out of `asyncio.gather`, escapes the `try/finally` (which only releases the Redis lock), and terminates the worker loop — no webhook is ever delivered, and the claimed rows are left stranded in `in_flight`.
Fix: stop passing ORM instances across session boundaries. Have `_claim_batch` return plain data — a list of frozen dataclasses or dicts carrying `id`, `endpoint_id`, `event_id`, `payload`, `attempts` read inside the session — and have `deliver` load the endpoint's `url`/`signing_secret`/`active` into the same kind of value object inside its own short session. Pair the sides: assert that a claimed batch's fields are readable after the session closes (the allow side, which is the whole point) and that a delivery whose endpoint was deleted between claim and send is handled rather than crashing. Red-prove one mutation per clause by execution against a real session — a `FakeDelivery` class with class-level attributes, as the current tests use, cannot exhibit this at all (RT1: the double's shape matches, its lifecycle does not): (i) return the ORM rows instead of the value objects and observe the post-session read redden with `DetachedInstanceError`; (ii) remove the missing-endpoint branch and observe only the deleted-endpoint test redden. Fail loudly: a delivery whose endpoint row is gone must be finished as a named terminal status with a reason, never dropped silently and never retried forever. Preserve what works: the batch must still be claimed atomically in one transaction and still ordered by `next_attempt_at`.

### Critical: a blocking `time.sleep` inside an async coroutine stalls the event loop through the whole retry ladder
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is an `async def` but sleeps with the synchronous `time.sleep`, so the retry backoff blocks the entire event loop rather than yielding — and because `run_worker` fans a batch of up to `BATCH_SIZE = 100` deliveries out through `asyncio.gather`, one slow endpoint freezes all of them.
What breaks in production: a single endpoint returning 500 stalls the loop for 2+4+8+16 = 30 seconds per attempt ladder while `REQUEST_TIMEOUT` is another 30s per try, which exceeds the 60-second Redis lock TTL — the lock expires mid-batch, a second worker claims and re-sends the same deliveries, and if the worker shares a process with the API every request served by that loop hangs too.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` (`asyncio` is already imported in this file — no new helper is needed) and, better, stop looping in-process at all: persist `attempts` and `next_attempt_at = _now() + backoff_for(attempt)`, set the status back to `pending`, and return, letting the next `_claim_batch` pick it up — that is what the `next_attempt_at` column and the ordered claim query already exist for, and it survives a worker restart mid-ladder, which the in-memory loop does not. Pair the sides: assert the retry is actually re-attempted (a delivery that fails once and succeeds on the rescheduled attempt ends `delivered` with `attempts == 2`) and assert that the loop is not blocked (a concurrent coroutine scheduled alongside the retry completes before the retry does). Red-prove separately: (i) restore `time.sleep` and observe only the concurrency assertion redden; (ii) drop the `next_attempt_at` write and observe only the reschedule-ordering assertion redden; (iii) drop the `attempts` write and observe only the attempts-count assertion redden. Fail loudly: bound the ladder — a delivery that has been `in_flight` longer than the lock TTL must be reclaimable, and a negative or absurd `attempt` must raise rather than compute a `timedelta` of `2**attempt` seconds silently. Boundary and tie: `attempt >= MAX_ATTEMPTS` (5) is the last attempt and terminal; a row whose `next_attempt_at` is exactly `now` IS claimable (`<= now`, as written), and ties on that column need the `id` tie-break described below.

### Major: the documented retry semantics are not the implemented ones
File: `docs/webhooks.md` "Retries" vs `app/webhooks/delivery.py` — `deliver` and `backoff_for`
What is wrong: the doc says "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", while `deliver` retries every non-2xx response identically up to `MAX_ATTEMPTS` and `backoff_for` is `timedelta(seconds=2**attempt)` with no jitter term anywhere in the change (R29: a rationale published to customers that the code contradicts).
What breaks in production: a customer who removes an endpoint route and starts returning 404, or rejects with 400, is hammered five times per event instead of once, and because every delivery in a batch computes an identical backoff the whole fleet retries in a synchronized thundering herd against the same host.
Fix: implement what the doc promises rather than editing the doc down, since the doc's semantics are the correct ones — treat `400 <= status < 500` (except `408` and `429`, which are retryable by convention) as immediately terminal with status `failed_permanent`, and add jitter as `delay * random.uniform(0.5, 1.0)` applied to the persisted `next_attempt_at` only, never to the deterministic `backoff_for` the tests pin. Pair the sides: assert a 400 stops at `attempts == 1` with `failed_permanent`, and assert a 500 still retries and can still reach `delivered` — a fix that made everything terminal would satisfy the first assertion alone. Red-prove separately: (i) remove the 4xx branch and observe only the 400-terminal assertion redden; (ii) add `429` to the terminal set and observe only the 429-retries assertion redden; (iii) fix the jitter to a constant and observe only the jitter-spread assertion redden. Fail loudly: a response with no status code at all (transport error) must route to the retryable branch explicitly and be logged as such, not fall through the `if` chain. Preserve the existing `test_backoff_grows_exponentially` parametrization by keeping `backoff_for` pure and applying jitter at the call site. Boundary and tie: `499` is terminal, `500` is retryable, and `429` sits on the retryable side of the 4xx boundary as a named exception.

### Major: the Redis lock is not atomic and is released by whoever finishes, not by whoever holds it
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: acquisition is a `get` followed by a separate `set` and a separate `expire`, so two workers that both read an empty key both proceed; and the release is an unconditional `delete` of a shared key with no ownership token, so a worker whose lock already expired deletes a lock a different worker now holds.
What breaks in production: two workers claim overlapping batches and each customer endpoint receives duplicate POSTs for the same event — tolerable only because the doc promises at-least-once, but combined with the `in_flight` claim not being row-locked it also means both workers write conflicting terminal statuses for the same delivery row.
Fix: acquire with a single atomic call carrying a unique token and a TTL — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock. Independently, make the claim itself safe by adding `.with_for_update(skip_locked=True)` to `_claim_batch`, so correctness does not rest on the lock at all — the lock then becomes a politeness optimization rather than the only guard. Pair the sides: assert a second worker attempting acquisition while the first holds it gets `False` (deny), and assert that after the first releases, the second DOES acquire (allow) — without the second assertion an `_acquire_lock` that always returns `False` passes. Red-prove separately by execution: (i) drop `nx=True` and observe only the mutual-exclusion assertion redden; (ii) drop the token comparison in the release and observe only the "stale holder does not delete the new lock" assertion redden; (iii) drop `skip_locked` and observe only the concurrent-claim disjointness assertion redden. Fail loudly: a Redis connection error inside `_acquire_lock` must propagate as a named failure that stops the loop iteration, not be caught and read as "lock acquired" — an unreachable coordinator must deny. Boundary and tie: a lock whose TTL expires at exactly the moment of release is NOT ours, and the compare-and-delete is what makes that tie safe.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; nothing anywhere sets it back
What is wrong: rows enter `in_flight` at claim time and only leave it through `_finish`, which runs solely on the success or exhaustion paths of `deliver` — a worker crash, a `DetachedInstanceError`, a CHECK violation or a deploy mid-batch leaves the row wedged, and `_claim_batch` only selects `status == "pending"`, so nothing will ever look at it again (R38, non-terminal transient state with no failure-exit and no bounded timeout).
What breaks in production: every worker restart permanently strands up to `BATCH_SIZE` deliveries; the customer never receives those events and no alert fires, because the rows are neither `pending` (so not overdue) nor `failed_permanent` (so not in any failure report).
Fix: add a claim timestamp (`claimed_at`) and a reaper that, on each loop iteration, returns rows with `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` to `pending` with `attempts` unchanged; wrap the per-delivery work in `try/except Exception` so an unexpected error routes to an explicit terminal or requeued state instead of escaping. Pair the sides: assert a stranded row is requeued and subsequently delivered (allow), and assert that a row currently being worked on — `claimed_at` inside the window — is NOT requeued (deny), or the reaper becomes a duplicate-delivery engine. Red-prove separately: (i) delete the reaper and observe only the stranded-row test redden; (ii) set the reaper window to zero and observe only the in-progress-row test redden; (iii) remove the `try/except` and observe only the "unexpected exception does not kill the loop" test redden. Fail loudly: the reaper must log a counted requeue at WARNING with the row ids, so a systematic wedge shows up as a rising number rather than as silence. Boundary and tie: a row whose `claimed_at` is exactly at the window edge is NOT reclaimed (strictly older than the window), and a row reclaimed concurrently by two reapers must be protected by the same `skip_locked` claim as above.

### Major: an unhandled exception anywhere in the batch kills the worker permanently
File: `app/webhooks/delivery.py` — `run_worker`, `await asyncio.gather(*[deliver(client, d) for d in batch])`
What is wrong: `gather` is called without `return_exceptions=True`, `deliver` catches only `httpx.HTTPError`, and the `while True` loop has no exception guard — the `try` block's only companion is a `finally` that releases the lock, so any other exception (`DetachedInstanceError`, `IntegrityError` from the CHECK mismatch, a `None` endpoint) propagates out of `run_worker` and the process's delivery loop stops.
What breaks in production: one malformed delivery takes down webhook delivery for every customer until someone notices the worker is gone, and the sibling deliveries in the same `gather` are abandoned mid-flight with their rows left `in_flight`.
Fix: pass `return_exceptions=True` to `gather`, iterate the results, and route each `Exception` result to `_finish(..., "failed_permanent", ...)` or to a requeue with a logged reason; wrap the loop body in `try/except Exception` that logs and continues after a short sleep so the worker survives transient database or Redis faults. Pair the sides: assert that when one delivery in a batch of three raises, the other two still complete (allow — the whole point), and assert that the raising one is recorded with a terminal or requeued status rather than silently dropped (deny). Red-prove separately: (i) remove `return_exceptions=True` and observe only the "other two complete" assertion redden; (ii) remove the result-routing loop and observe only the "raiser is recorded" assertion redden; (iii) remove the outer `try/except` and observe only the "worker survives a `_claim_batch` failure" assertion redden. Fail loudly rather than quietly: the continue-after-error path must log at ERROR with the exception type, and a configurable consecutive-failure count must stop the worker with a named fatal message — an infinitely retrying worker that never delivers looks identical to a healthy idle one. Do not fix by broadening `deliver`'s `except httpx.HTTPError` into a bare `except Exception` that swallows — the behaviour to preserve is that transport failures retry while programming errors are visible.

### Major: naive/aware datetime mixing, and the migration's column types contradict the model's
File: `app/webhooks/delivery.py` — `enqueue_for_event`, `next_attempt_at=datetime.utcnow()`; `migrations/0042_webhook_delivery.sql` — all five `TIMESTAMP` columns vs `app/webhooks/models.py` `DateTime(timezone=True)`
What is wrong: `enqueue_for_event` writes a naive UTC datetime while `_claim_batch`, `_finish` and the models' `_now()` all produce timezone-aware ones, and every timestamp column is declared `DateTime(timezone=True)` in the model but created as plain `TIMESTAMP` (without time zone) in the migration — so the ORM believes it is round-tripping tz-aware values through a column that discards the offset.
What breaks in production: comparisons between the naive value and `datetime.now(timezone.utc)` are wrong by the server's UTC offset wherever the driver does not silently coerce, so rows either become claimable early or never become claimable, and `WebhookDelivery.to_dict()`'s `next_attempt_at.isoformat()` emits an offset-less string to API consumers who cannot tell what zone it is in.
Fix: change all five columns in the migration to `TIMESTAMPTZ` to match the model, and replace `datetime.utcnow()` with the module's existing `models._now()` — codebase awareness: `models.py` already defines `_now()` returning `datetime.now(timezone.utc)` and uses it as the column default, so `delivery.py`'s three separate inline `datetime.now(timezone.utc)` calls and one `utcnow()` are four reimplementations of one helper (R1); import and use `_now` at all four sites. Pair the sides: assert a delivery enqueued with `next_attempt_at = _now()` IS claimable immediately (allow) and that one enqueued with `_now() + timedelta(minutes=5)` is NOT (deny). Red-prove separately: (i) restore `utcnow()` and, with the process TZ set to a non-UTC zone, observe only the claimability assertion redden; (ii) revert one column to `TIMESTAMP` and observe only the offset-preservation round-trip assertion redden. Fail loudly: reject a naive datetime at the boundary — have `_now`'s callers assert `dt.tzinfo is not None` and raise otherwise, so "no zone" is never read as "UTC". Boundary and tie: `next_attempt_at == now` is claimable (`<= now` in the existing filter), which is the correct and intended side; keep it.

### Major: `_finish` and `deliver` dereference database lookups that can return `None`, and delivery ignores `active`
File: `app/webhooks/delivery.py` — `_finish` (`row = session.get(...)` then `row.status = ...`) and `deliver` (`endpoint = session.get(m.WebhookEndpoint, ...)`)
What is wrong: both call sites assign to attributes of a `session.get` result with no `None` check, and `deliver` never re-reads `endpoint.active` even though `enqueue_for_event` filters on it — the endpoint can be deactivated or deleted between enqueue and delivery, and the migration's `ON DELETE CASCADE` means a deleted endpoint removes the delivery row out from under `_finish`.
What breaks in production: deleting or deactivating a webhook endpoint while deliveries are queued raises `AttributeError: 'NoneType' object has no attribute 'status'` inside the worker, which — per the finding above — takes the worker down; and until it does, events keep being POSTed to an endpoint the customer explicitly turned off.
Fix: guard both lookups — `if row is None: log.warning("delivery %s vanished before finish", delivery_id); return` and, in `deliver`, `if endpoint is None or not endpoint.active: _finish(delivery.id, "failed_permanent", attempt, None, "endpoint inactive or removed"); return`. Pair the sides: assert an active, present endpoint still delivers normally (allow) and assert a deactivated one is finished terminally without any HTTP request being made — assert the transport recorded zero calls, not merely that the status changed (RT8: the guarded side effect, not just the status). Red-prove separately: (i) remove the `None` guard in `_finish` and observe only the deleted-row test redden; (ii) remove the `active` check and observe only the zero-HTTP-calls assertion redden. Fail loudly: the vanished-row path logs at WARNING with the id — a `return` with no log makes a lost delivery indistinguishable from a completed one. Boundary and tie: an endpoint deactivated *during* an in-flight request is allowed to finish that request; the check applies at attempt start, and that is the boundary to state in the comment.

### Major: the signature header is logged on every delivery, and unbounded response bodies are stored and logged
File: `app/webhooks/delivery.py` — `send_once`'s `log.info("POST %s headers=%s", endpoint.url, headers)`; `deliver`'s `_finish(..., response.text)` and `detail = f"HTTP {response.status_code}: {response.text}"`
What is wrong: `headers` at that point contains the computed `X-Acme-Signature` and its timestamp, written at INFO for every single delivery, and the full untruncated response body of a customer-controlled endpoint is both persisted into `response_body` and interpolated into a WARNING log line.
What breaks in production: anyone with log access can replay a captured payload with its still-valid signature — unbounded in time, since the timestamp is not covered by the MAC — and a customer endpoint that returns a multi-megabyte body writes it into the database and the log pipeline on every one of five attempts, exhausting disk and log quota.
Fix: drop `headers` from the log line entirely (log the url, delivery id, and event type — that is what the line is actually for), and truncate stored and logged bodies to a named constant, `MAX_RESPONSE_BODY = 2048`, applied in `_finish` before assignment and in the `detail` construction. Pair the sides: assert the log line still identifies which delivery went where (the operator need it retains) and assert it contains neither `X-Acme-Signature` nor the signature value; assert a 100 KB response body is stored at exactly 2048 characters and a 100-character one is stored unchanged. Red-prove separately: (i) restore `headers=%s` and observe only the no-signature-in-logs assertion redden; (ii) remove the truncation and observe only the long-body assertion redden; (iii) set the truncation to 0 and observe only the short-body-unchanged assertion redden — that clause is what stops "log nothing, store nothing" from passing. Do not fix by deleting the log line or the `response_body` column: the behaviour to preserve is that an operator can still see which endpoint failed and what it said. Boundary and tie: a body of exactly 2048 characters is stored unchanged; 2049 is truncated to 2048, and the truncation must be marked (append `…`) so a body that legitimately ends at the limit is distinguishable from one that was cut.

### Major: webhook enqueue is fire-and-forget after the event transaction has committed, and its failure is swallowed
File: `app/events/dispatcher.py` — the `try/except Exception ... log.warning("webhook enqueue failed for event %s: %s", ...)` block
What is wrong: `enqueue_for_event` runs after the `with session_scope()` that persisted the event has already committed, in its own separate transaction, and any failure — the unique-index violation above, a database blip, a serialization error — is caught by a bare `except Exception` and reduced to a warning with no retry, no dead-letter and no effect on the return value (R9/R4: the dispatch is not atomic with the mutation that occasioned it).
What breaks in production: the event is durably recorded while its deliveries are not, so `docs/webhooks.md`'s "delivery is at-least-once" is false — a transient database error during enqueue silently drops the customer's webhook forever, and the only trace is one WARNING line.
Fix: make enqueue part of the same transaction as the event insert — move the `WebhookDelivery` row creation inside the existing `session_scope()` block in `dispatch`, passing the session down, so the event and its deliveries commit or roll back together; where that is not acceptable, replace the swallow with a durable outbox row written in the same transaction and drained by the worker. Pair the sides: assert that a successful dispatch produces both the `Event` row and the matching `WebhookDelivery` rows (allow), and assert that when delivery-row creation raises, the `Event` row is ALSO absent — the atomicity claim, which the current code fails. Red-prove separately: (i) restore the separate `session_scope` and observe only the rollback assertion redden; (ii) remove the enqueue call and observe only the delivery-rows-created assertion redden. Fail loudly: keep an `except` only for the case where webhooks are structurally unavailable, and make it re-raise after logging at ERROR with the event id — a swallowed enqueue must not be spelled the same as a successful one. Preserve the in-process subscriber behaviour: subscribers still run after the commit and their failures must not roll the event back; only the delivery rows join the transaction.

### Major: `WEBHOOK_EVENT_TYPES` silently overrides what customers were told they could subscribe to, and `event_types` is never validated
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`; `app/api/routes/settings.py` — `EndpointIn.event_types: list[str] = []`
What is wrong: the dispatcher only ever calls `enqueue_for_event` for three hardcoded types, while `create_webhook_endpoint` accepts any list of arbitrary strings with no membership check and `docs/webhooks.md` states that an empty `event_types` "subscribes the endpoint to every event type we emit" — the allowlist and the registration boundary were not synchronized (R18), and the true member-set was never derived from the defining primitive, `SUBSCRIBERS`/the emitted event types (R42).
What breaks in production: a customer subscribes to `invoice.refunded` or mistypes `invoice.payed`, receives a 201, and then silently receives nothing forever with no error anywhere to explain it; and an "empty means everything" endpoint receives only three of the event types the product emits, which is not what the doc promises.
Fix: derive the subscribable set from one place — export `WEBHOOK_EVENT_TYPES` (or better, compute it from the events module's own type registry) and validate `EndpointIn.event_types` against it in `create_webhook_endpoint`, raising 422 naming the unknown values. Then correct the doc, or the gate, so the two agree on what "every event type we emit" means. Pair the sides: assert that registering `["invoice.paid"]` succeeds and that an endpoint so registered actually receives that event end to end (allow), and that registering `["invoice.payed"]` returns 422 with the offending value in the message (deny). Red-prove separately: (i) remove the membership check and observe only the 422 assertion redden; (ii) remove `"invoice.paid"` from the exported set and observe only the successful-registration assertion redden — this clause is what stops an empty allowlist from satisfying the fix; (iii) change the doc's "every event type" wording without changing the gate and observe the doc-vs-constant consistency test redden. Fail loudly when the set cannot be derived: an empty `WEBHOOK_EVENT_TYPES` must make registration fail with a named configuration error, not accept everything. Boundary and tie: an explicitly empty `event_types` means the full derived set at *delivery* time, not the set frozen at registration time — state that, because the two readings differ the moment a new event type ships.

### Major: `webhooks_enabled` is added to the schema and read by nothing
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE;`
What is wrong: the column is created but no code in the change consults it — `create_webhook_endpoint` does not check it before issuing a secret, `enqueue_for_event` filters only on `WebhookEndpoint.active`, and no model in `app/webhooks/models.py` or `app/models/org.py` references it (R41: a declared capability with no backing path).
What breaks in production: an operator who flips `webhooks_enabled = FALSE` to stop a runaway integration sees no change in behaviour — the kill switch that the schema advertises does not exist — and since the default is `FALSE`, the column also reads as "webhooks are off for every existing org" while the feature is in fact on for all of them.
Fix: wire it or drop it, and say which. To wire it: add `webhooks_enabled` to the `Organization` model, check it in `create_webhook_endpoint` (422 when disabled) and in `enqueue_for_event` (join `organizations` and filter), then choose the default deliberately — `TRUE` if the feature ships on, `FALSE` plus a backfill statement in the same migration if it ships gated. Pair the sides: assert that an org with `webhooks_enabled = TRUE` still enqueues normally (allow) and that one with `FALSE` enqueues zero rows and issues zero HTTP requests (deny, asserting the absent side effect and not just a count). Red-prove separately: (i) remove the `enqueue_for_event` filter and observe only the disabled-org assertion redden; (ii) invert the filter and observe only the enabled-org assertion redden. Fail loudly: an org row missing from the join must deny rather than pass — an unresolvable subject is not an enabled one. Boundary: state in the migration comment whether existing orgs are enabled at deploy time; the `DEFAULT FALSE` as written silently disables the feature for the entire existing customer base the moment anything starts reading the column.

### Minor: deliveries are ordered by a wall-clock timestamp with no tie-break
File: `app/api/routes/settings.py` — `list_deliveries`, `.order_by(WebhookDelivery.created_at.desc()).limit(limit)`; `app/webhooks/delivery.py` — `_claim_batch`'s `.order_by(m.WebhookDelivery.next_attempt_at)`
What is wrong: both orderings use timestamps that tie in practice — a fan-out writes every row of one event with the same `created_at` default, and `enqueue_for_event` sets an identical `next_attempt_at` for all of them — so the order among tied rows is undefined (R57).
What breaks in production: the deliveries listing returns rows in an unstable order between calls, and if `limit` is ever paired with an offset or keyset cursor, rows at a page boundary through equal timestamps are skipped or repeated.
Fix: add `id` as the tie-break on both queries — `.order_by(created_at.desc(), id.desc())` and `.order_by(next_attempt_at, id)` — and back them with matching indexes. Boundary and tie: two rows sharing a timestamp are ordered by the engine-assigned `id`, which is unique and monotonic by construction and not caller-nameable, so the page cut through equal timestamps is deterministic.

### Minor: `docs/webhooks.md` describes response fields the delivery serializer does not return
File: `docs/webhooks.md` "Inspecting deliveries" vs `app/webhooks/models.py` `WebhookDelivery.to_dict()`
What is wrong: the doc says the listing includes "the response status we saw and when the next attempt is scheduled", and `to_dict` does return `response_status` and `next_attempt_at` — but `next_attempt_at.isoformat()` will raise `AttributeError` if the column is ever `NULL`, which the model forbids (`nullable=False`) while `_finish` never updates it, so the value shown for a delivered row is the stale time of its last attempt rather than a scheduled one.
