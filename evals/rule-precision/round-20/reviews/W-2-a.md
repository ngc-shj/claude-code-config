### Critical: the signed bytes are not the bytes on the wire, so no receiver can ever verify a delivery
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, with the send site at `app/webhooks/delivery.py` — `send_once()`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys reordered), while `send_once` puts the body on the wire via `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators and insertion order — two different byte strings, so a receiver following `docs/webhooks.md` and HMACing the raw request body computes a digest that never matches the header.
What breaks in production: every outbound webhook is rejected by every correctly implemented customer receiver, and because `deliver()` retries any non-2xx, each event burns all 5 attempts against the customer's endpoint before landing in `failed_permanent`.
Fix: make the signed string and the wire body the same object — in `send_once`, compute `body = serialize(delivery.payload).encode()`, sign that exact byte string, and send it with `client.post(endpoint.url, content=body, headers=headers)` so httpx never re-serializes; keep `serialize()` as the single producer of those bytes so signing and sending cannot diverge again. Preserve the behaviour the current code gets right — the `Content-Type: application/json` header and the payload's field values must be unchanged, so the fix must not switch to a form or bytes content type. Pin both directions with a round-trip test that feeds the *actual* captured `request.content` from the `MockTransport` handler back through `signing.verify(SECRET, ...)` against the *actual* header: the allow case is a valid delivery verifying true, the deny case is the same body with one byte mutated verifying false. Red-prove the two clauses separately by execution: (i) revert `content=body` to `json=delivery.payload` and observe the round-trip assertion red, (ii) flip `sort_keys=True` to `False` in `serialize` with a two-key payload whose insertion order differs from sorted order and observe the same assertion red for a different reason. Route the not-a-verdict outcomes loudly: if the payload is not JSON-serializable, `send_once` must raise a named error before any HTTP call rather than posting an unsigned or partially signed body — "could not serialize" must not be spelled the same as "delivered". Boundary and tie: the comparison is over the complete byte string including the trailing byte, and two payloads that serialize identically are the same signed message by construction, which is the intended behaviour for retries of one delivery.

### Critical: the timestamp is not covered by the HMAC, so the documented replay window is unenforceable
File: `app/webhooks/signing.py` — `sign()` (line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`)
What is wrong: `docs/webhooks.md` states the signature is "the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`" and instructs receivers to "reject requests whose timestamp is more than five minutes old", but the implementation signs the body alone and returns the timestamp as an unauthenticated side value, so an attacker replaying a captured request can rewrite `X-Acme-Timestamp` to now and the signature still verifies.
What breaks in production: a single captured `invoice.paid` delivery can be replayed against the customer's endpoint indefinitely and passes both the signature check and the freshness check the documentation says "stops a captured request from being replayed" — the control the docs describe as closing the replay class does not exist (R49 clause 2).
Fix: include the timestamp in the signed material — build `signed = f"{timestamp}.{serialize(payload)}"` and HMAC that, and change `verify()` to take the timestamp explicitly (`verify(secret, timestamp, payload, signature)`) so a caller cannot forget it; do not fix this by softening the doc, because the freshness window is load-bearing and deleting the claim removes the only instruction receivers have. Preserve the existing header names and the `sha256=` prefix so already-integrated receivers keep parsing. Pair the sides: the allow case is `verify` returning true for a signature produced by `sign` with the timestamp it returned; the deny case is the same body and signature presented with a different timestamp returning false. Red-prove separately by execution: (i) drop the `{timestamp}.` prefix from the signed string and observe the deny-case assertion red, (ii) leave the prefix but have `verify` recompute with a hardcoded timestamp and observe the allow-case assertion red. Fail loudly on the non-verdict cases: a missing or non-numeric timestamp header must raise/return a distinct "cannot verify" rather than `False`, so a receiver cannot read "no timestamp supplied" as "signature mismatch". Boundary and tie: state the window as `now - timestamp <= 300` seconds inclusive at exactly 300, and two deliveries signed in the same second are independent messages distinguished by `event_id`, not by the timestamp.

### Critical: signing secrets are minted from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. Mersenne Twister, which is a predictable generator whose internal state is recoverable from a modest amount of observed output — and `_ALPHABET` is only 62 characters, so the module already has `hmac`/`hashlib` imported for crypto while reaching for the non-crypto RNG here (R1: a shared, correct primitive exists and was reimplemented).
What breaks in production: an attacker who registers a handful of their own endpoints and reads back their own secrets (trivially, via the leak reported below) can reconstruct the generator state and predict other tenants' signing secrets, then forge signed events that those tenants' receivers accept as authentic.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` from the stdlib `secrets` module and delete `_ALPHABET` and the `random` import so the weak generator cannot be reintroduced by a later edit; do not "fix" it by seeding `random` or widening the alphabet, since neither makes the stream unpredictable. Preserve what the current function gets right and what the existing test pins: the `whsec_` prefix must still be present, and the secret must remain a URL-safe ASCII string usable as an HMAC key. Pair the sides: the allow case is `new_signing_secret()` still starting with `SECRET_PREFIX` and being accepted by `sign()`; the deny case is a property test asserting 1000 generated secrets are all distinct and carry at least 256 bits of entropy — note `test_new_signing_secret_has_prefix_and_length` currently asserts `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES`, which `token_urlsafe(32)` breaks (it returns ~43 chars), so update that assertion to a minimum length rather than deleting it. Red-prove separately by execution: (i) revert to `random.choice` with a fixed `random.seed(0)` and observe the distinctness assertion red, (ii) drop the prefix and observe the prefix assertion red. Fail loudly if `secrets` cannot produce entropy — let the `OSError` propagate out of endpoint creation rather than falling back to any other generator, so "no entropy available" cannot be spelled the same as "secret issued". Boundary and tie: the entropy floor is stated as at least 32 bytes of generator output, and two endpoints created in the same request must receive independent secrets, which the fix guarantees because `token_urlsafe` carries no per-call state the caller can pin.

### Critical: HMAC comparison in `verify()` is not constant-time
File: `app/webhooks/signing.py` — `verify()` (line `return expected == signature`)
What is wrong: the recomputed signature is compared to the supplied one with `==`, whose short-circuit on the first differing byte leaks the length of the matching prefix through timing, and `hmac.compare_digest` is already available in this file because `hmac` is imported two lines above (RS1).
What breaks in production: any caller that uses this helper to authenticate an inbound signature — the function is exported and documented as the verification primitive — gives an attacker a byte-at-a-time oracle for forging a valid signature without knowing the secret.
Fix: change the return to `hmac.compare_digest(expected, signature)`, guarding first that `signature` is a `str` so a non-string input raises rather than being compared; keep the function's boolean contract and its existing signature-format tolerance so the two passing tests (`test_verify_accepts_signature_produced_by_sign`, `test_verify_rejects_a_signature_made_with_another_secret`) continue to express what they express. Pair the sides: the allow case is the existing accept test still green; the deny case is the existing wrong-secret test still red-on-forgery, plus a new case where the supplied signature shares a long prefix with the expected one and is still rejected. Red-prove separately by execution: (i) revert `compare_digest` to `==` and observe a test that asserts `verify` is called through `compare_digest` (patch `hmac.compare_digest` with a counting spy) go red, (ii) mutate `expected` to be returned unconditionally true and observe the wrong-secret test go red. Fail loudly when the check cannot run: a `signature` of the wrong type or a non-ASCII value must raise a named `TypeError`/`ValueError` rather than returning `False`, so "malformed input" is not recorded as "signature mismatch". Boundary and tie: `compare_digest` on two equal-length strings is the boundary case that must return true, and unequal lengths must return false without an early exit — which is exactly the property `==` fails to provide.

### Critical: `list_webhook_endpoints` returns the signing secret on every call, contradicting the documented one-time disclosure
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict()` (key `"signing_secret": self.signing_secret`), consumed by `app/api/routes/settings.py` — `list_webhook_endpoints`
What is wrong: `to_dict()` is the single serializer used both by the creation response and by the list endpoint, so the secret is emitted on every `GET /v1/settings/webhook-endpoints`, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the HMAC key for every endpoint is repeatedly served over a GET route and lands in browser caches, proxy logs, API-client history and any downstream telemetry that records response bodies, so anyone with read-only access to the settings API or to those logs can forge signed events for that tenant.
Fix: split the serialization — make `to_dict()` omit `signing_secret` entirely, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": endpoint.signing_secret}` at the single creation site so the secret is emitted exactly once; do not fix this by masking or truncating the value in `to_dict()`, because a partial secret in the list response is still a prefix oracle and the creation response must keep returning the full secret or the feature is unusable. Pair the sides: the deny case is a test asserting `"signing_secret" not in` any element of the `GET /webhook-endpoints` response body; the allow case is a test asserting the `POST` 201 body *does* contain a full, usable secret that `signing.verify` accepts. Red-prove separately by execution: (i) re-add the key to `to_dict()` and observe the GET assertion red, (ii) remove the merge in `create_webhook_endpoint` and observe the POST assertion red. Fail loudly when the check cannot run: if the endpoint row has no secret (a row predating the column, or a null), creation must raise rather than returning a response with the key absent or null, so "no secret issued" is not silently shaped like "secret withheld". Boundary and tie: the boundary is the response object leaving the handler — the secret exists on exactly one response, the 201, and two endpoints created in the same request each carry their own; the cross-cutting check below confirms `WebhookDelivery.to_dict()` has no equivalent leak.

### Critical: `list_deliveries` has no tenant scoping, exposing every organization's delivery payloads
File: `app/api/routes/settings.py` — `list_deliveries` (the `.filter(webhook_models.WebhookDelivery.endpoint_id == endpoint_id)` line)
What is wrong: the query filters on the caller-supplied `endpoint_id` alone and never joins to `WebhookEndpoint` to check `org_id == user.org_id`, even though the sibling handler `list_webhook_endpoints` in the same diff hunk *does* apply exactly that predicate — the pattern was applied to one new route and not the other (R3, security-relevant).
What breaks in production: any authenticated user can enumerate `endpoint_id` values and read other tenants' full webhook payloads, which for the subscribed event types (`invoice.paid`, `invoice.payment_failed`, `subscription.updated`) is billing and subscription data, plus the response bodies those tenants' receivers returned.
Fix: join the delivery query to the endpoint and scope it — `.join(webhook_models.WebhookEndpoint, webhook_models.WebhookEndpoint.id == webhook_models.WebhookDelivery.endpoint_id).filter(webhook_models.WebhookEndpoint.id == endpoint_id, webhook_models.WebhookEndpoint.org_id == user.org_id)` — and return 404 (not 403) when the join yields nothing, so the route does not confirm the existence of another tenant's endpoint id. Preserve the ordering, the `limit`, and the `to_dict()` shape the route already returns, so the fix is not a functional narrowing beyond the tenancy check. Pair the sides: the deny case asserts a user in org A requesting an endpoint owned by org B gets 404 **and** that the delivery query returned zero rows (assert the body is `[]`, not just the status — RT8); the allow case asserts a user in org A requesting their own endpoint still receives their deliveries in `created_at desc` order. Red-prove separately by execution: (i) drop the `org_id` predicate and observe the cross-tenant test go red on the body assertion, (ii) drop the `endpoint_id` predicate and observe the same-tenant test go red because it now returns another endpoint's rows. Fail loudly when the check cannot run: a request whose `user.org_id` is absent must deny rather than fall through to an unfiltered query — an unresolvable subject is a denial, not a skip. Boundary and tie: the boundary is org identity compared for exact equality with no inheritance or parent-org fallback, and an endpoint whose `org_id` matches but which is soft-deleted or inactive still belongs to the caller and must remain readable.

### Critical: the `status` CHECK constraint rejects the terminal status the code actually writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, against `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)` and `app/webhooks/models.py` — `STATUSES`
What is wrong: the migration enumerates `'failed'` while both the model's `STATUSES` tuple and the only write site in `deliver()` use `'failed_permanent'`, so the producer's value is not in the strict consumer's accepted set (R40).
What breaks in production: the first delivery to exhaust its 5 attempts raises an integrity error inside `_finish`, the transaction rolls back, the row stays `in_flight` forever, and the worker's `asyncio.gather` propagates the exception out of `run_worker` — one permanently failing customer endpoint takes down the whole delivery worker.
Fix: change the constraint to `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed_permanent'))` and derive it from the single source — reference `models.STATUSES` in a test that reads the migration file and asserts set equality between the tuple and the parsed `IN (...)` list, so the two cannot drift again. Preserve the constraint itself: do not fix this by dropping the CHECK, because the constraint is what stops an arbitrary status string from being persisted. Pair the sides: the deny case inserts `status='bogus'` and asserts the database rejects it; the allow case walks a delivery through all four legitimate statuses and asserts each write commits. Red-prove separately by execution: (i) revert the constraint to `'failed'` and observe the `failed_permanent` write in the allow case go red, (ii) widen the constraint to no CHECK at all and observe the `'bogus'` deny case go red. Fail loudly when the check cannot run: the drift test must fail explicitly if it cannot locate or parse the `CHECK (status IN ...)` clause in the migration, so "regex found nothing" is not reported as "statuses match". Boundary and tie: set equality in both directions is the boundary — a status in the code but not the constraint and a status in the constraint but not the code are both failures; and note the column is declared `TEXT` here but `String(20)` in the model, which `'failed_permanent'` (16 chars) fits with only 4 characters of headroom.

### Critical: the unique index on `event_id` alone makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness key is `event_id` by itself, but `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint and calls `session.add_all(rows)`, so an org with two active endpoints subscribed to the same event violates the index on the second row.
What breaks in production: any customer who registers more than one endpoint gets an integrity error on `add_all`, which `dispatch()` swallows as a `log.warning`, so *all* deliveries for that event are silently lost — including the first endpoint's, because the whole `session_scope` transaction rolls back.
Fix: replace the index with `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the key that actually expresses the intended invariant — at most one delivery per (endpoint, event), the idempotency guarantee `docs/webhooks.md` relies on when it says "deduplicate on `event_id`". Do not fix this by dropping uniqueness entirely: the constraint is what makes a re-run of `enqueue_for_event` for the same event idempotent, and deleting it converts a hard error into duplicate customer-visible deliveries. Pair the sides: the allow case enqueues one event for an org with two active subscribed endpoints and asserts two rows exist; the deny case enqueues the same `(endpoint_id, event_id)` twice and asserts the second insert is rejected. Red-prove separately by execution: (i) revert the index to `(event_id)` and observe the two-endpoint allow case go red, (ii) drop the index and observe the duplicate deny case go red. Fail loudly when the check cannot run: `enqueue_for_event` must not swallow the integrity error — see the dispatcher finding below; a failed enqueue has to surface as a named failure rather than a zero-row success. Boundary and tie: the tie is exactly the case the current index gets wrong — two rows sharing an `event_id` but differing in `endpoint_id` are legitimate and must both persist; two rows sharing both are the same delivery and the second must be rejected.

### Critical: `time.sleep()` inside an async coroutine blocks the entire event loop during every retry
File: `app/webhooks/delivery.py` — `deliver()` (line `time.sleep(delay)`)
What is wrong: `deliver` is an `async def` scheduled through `asyncio.gather` in `run_worker`, but its retry backoff uses the blocking `time.sleep` rather than `await asyncio.sleep`, so the sleeping coroutine holds the loop thread instead of yielding.
What breaks in production: one failing endpoint stalls the whole worker process — with `BATCH_SIZE = 100` gathered concurrently and a backoff of 2+4+8+16 = 30 seconds per delivery, a batch of failing endpoints serializes into roughly 50 minutes of frozen event loop during which no other delivery, no lock refresh, and no HTTP request makes progress, and the 60-second Redis lock expires mid-batch so a second worker starts duplicating the same rows.
Fix: replace `time.sleep(delay)` with `await asyncio.sleep(delay)` — `asyncio` is already imported at the top of the file — and remove the now-unused `import time`; keep the backoff schedule and the `log.warning` that records each retry, because that log line is the only visibility into repeated failure. Pair the sides: the deny case is a test that runs two `deliver()` coroutines concurrently against a handler that fails once, and asserts wall-clock elapsed time is close to one backoff rather than two (proving they interleaved); the allow case asserts a delivery that succeeds on the second attempt is still marked `delivered` with `attempts == 2`, so the fix did not remove the retry. Red-prove separately by execution: (i) revert to `time.sleep` and observe the concurrency assertion go red on elapsed time, (ii) delete the retry loop's second iteration and observe the `attempts == 2` assertion go red. Fail loudly when the check cannot run: if the delay is not a finite non-negative number, `deliver` must raise rather than sleeping indefinitely — a non-terminating sleep is neither pass nor fail and must be routed to a named refusal. Boundary and tie: state that `attempt >= MAX_ATTEMPTS` is checked *before* sleeping so the fifth attempt terminates without a trailing wait, and two deliveries whose backoff expires in the same instant are independent coroutines with no ordering guarantee between them.

### Critical: ORM instances are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch()` (returns `rows` from inside `with session_scope()`) and `deliver()` (returns `endpoint` from its own `with session_scope()`)
What is wrong: both functions build a list/object inside a `session_scope()` context and return or use it after the block exits, so every subsequent attribute read — `delivery.payload`, `delivery.attempts`, `delivery.id` in `run_worker`/`deliver`, and `endpoint.url`, `endpoint.signing_secret` in `send_once` — touches a detached, expired instance.
What breaks in production: the worker raises `DetachedInstanceError` on the first attribute access of the first claimed row, so no webhook is ever delivered and `run_worker` dies on the exception propagating out of `asyncio.gather`; additionally `_claim_batch`'s `row.status = "in_flight"` mutation commits, so the rows it touched are now unreachable by the next `_claim_batch` (which selects only `pending`) and are permanently stranded.
Fix: stop passing ORM entities across session boundaries — have `_claim_batch` return plain data (`[DeliveryTask(id=r.id, endpoint_id=r.endpoint_id, attempts=r.attempts, payload=r.payload) for r in rows]` built inside the block, via a frozen dataclass), and have `deliver` read the endpoint's `url` and `signing_secret` into locals inside its `session_scope` before using them; keep the `in_flight` marking and the batch ordering, which are what make concurrent claiming safe. Pair the sides: the allow case is an integration test that claims a real persisted row and asserts `send_once` posts to the endpoint's real URL with a signature derived from the real stored secret; the deny case asserts that a row claimed by one call is not returned by an immediately following `_claim_batch` call. Red-prove separately by execution: (i) revert `_claim_batch` to returning ORM rows and observe the allow case go red with `DetachedInstanceError`, (ii) remove the `row.status = "in_flight"` assignment and observe the deny case go red because the row is claimed twice. Fail loudly when the check cannot run: the tests must use a real session against a real database rather than the `FakeEndpoint`/`FakeDelivery` doubles, because a hand-rolled double has no detached state and reports green for a subject it never exercised (RT1) — a test that cannot obtain a database must error, not skip silently. Boundary and tie: the boundary is the `with session_scope()` block — every attribute the caller needs must be read strictly inside it — and two workers claiming at the same instant are separated by the `in_flight` write plus the lock, not by the Python object identity.

### Critical: any `http*` URL is accepted and redirects are followed, giving an authenticated SSRF primitive
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`), with `app/webhooks/delivery.py` — `run_worker` (`httpx.AsyncClient(..., follow_redirects=True)`)
What is wrong: the scheme check is a surface-form prefix test rather than a membership test, so it admits plain `http://` (which `docs/webhooks.md` says is rejected: "Only `https://` URLs are accepted") and any scheme merely *starting* with those four characters, and nothing restricts the host, so `http://169.254.169.254/latest/meta-data/` or `http://127.0.0.1:6379/` is a valid endpoint — while `follow_redirects=True` means even an externally-valid host can bounce the request to an internal one after registration (R47: the string prefix is not the thing the HTTP client interprets; R49: the doc claims a control the code does not implement).
What breaks in production: any authenticated tenant turns the delivery worker into a proxy that issues attacker-shaped POSTs from inside the production network to cloud metadata services and internal APIs, and the response body is written back to `WebhookDelivery.response_body` and served to the attacker through `GET .../deliveries` — a complete request-and-read SSRF.
Fix: replace the prefix test with `if parsed.scheme != "https" or not parsed.hostname:` so the accepted set is exactly the one documented; resolve `parsed.hostname` and reject any address in a private, loopback, link-local, or reserved range before persisting; and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a failed attempt rather than chased. Preserve the feature: legitimate public HTTPS endpoints on non-standard ports and with paths and query strings must still register, and the existing 422 status and `detail` wording stay. Pair the sides: the allow case asserts `https://hooks.example.com/acme` still returns 201 and is delivered to; the deny cases assert `http://hooks.example.com/x`, `httpx://evil`, `https://127.0.0.1/x`, and `https://169.254.169.254/` each return 422 **and** that no `WebhookEndpoint` row was created (assert the mutation, not just the status — RT8). Red-prove separately by execution: (i) revert to `scheme.startswith("http")` and observe the `http://` and `httpx://` deny cases go red, (ii) remove the private-range check and observe the `127.0.0.1` deny case go red, (iii) set `follow_redirects=True` again and observe a redirect-to-internal test go red. Fail loudly when the check cannot run: a hostname that does not resolve, or a resolution that errors or times out, must deny registration with a named "could not verify destination" error — "DNS unavailable" must not be spelled the same as "address is public". Boundary and tie: state that the check is against the resolved address at *delivery* time as well as registration time (a DNS record can be repointed after registration, so the worker must re-check before connecting), and a hostname resolving to both a public and a private address must be rejected, not accepted on the public one.

### Major: full signature headers are logged at INFO on every delivery attempt
File: `app/webhooks/delivery.py` — `send_once()` (line `log.info("POST %s headers=%s", endpoint.url, headers)`)
What is wrong: the `headers` dict interpolated into the log line contains `SIGNATURE_HEADER` and `TIMESTAMP_HEADER`, so a valid signature for a known payload is written to the application log on every attempt.
What breaks in production: anyone with log access — including downstream log shipping and indexing — obtains a valid `(timestamp, signature)` pair which, because the timestamp is not covered by the HMAC (see above), can be replayed against the customer's receiver indefinitely.
Fix: log only the non-sensitive fields — `log.info("POST %s delivery=%s event=%s", endpoint.url, delivery.id, delivery.event_type)` — and never interpolate the headers dict; preserve the operational value the line was added for by keeping the URL and adding the delivery and event identifiers, which are what an operator actually correlates on. Pair the sides: the deny case captures log output for one `send_once` call and asserts neither the signature value nor the secret appears in it; the allow case asserts the endpoint URL and delivery id *do* appear, so the fix did not silence the line. Red-prove separately by execution: (i) restore `headers=%s` and observe the redaction assertion go red, (ii) delete the log call entirely and observe the operator-visibility assertion go red. Fail loudly when the check cannot run: if the log capture fixture records nothing, the test must fail rather than pass on an empty haystack — "examined no log lines" must not read as "found no secret". Boundary and tie: the boundary is any value derived from `signing_secret`, which includes the signature itself and not merely the secret; two attempts for the same delivery produce different signatures and both must be excluded.

### Major: retry policy contradicts the documented policy in two ways
File: `app/webhooks/delivery.py` — `deliver()` (the `if 200 <= response.status_code < 300` branch) and `backoff_for()`
What is wrong: `docs/webhooks.md` states "a 4xx is permanent and we stop immediately" and "backoff is exponential with jitter", but `deliver()` retries every non-2xx status including 4xx, and `backoff_for` returns a deterministic `2**attempt` with no jitter at all.
What breaks in production: a customer endpoint returning 400 or 404 is hammered five times per event instead of once, and because every delivery in a batch shares the same deterministic schedule, retries from a mass failure arrive in synchronized thundering-herd waves at the recovering endpoint.
Fix: branch on the status class in `deliver()` — treat `400 <= status < 500` (excepting 408 and 429, which are retryable by convention) as terminal and call `_finish(..., "failed_permanent", ...)` immediately — and add jitter to `backoff_for` by returning `timedelta(seconds=BASE_DELAY_SECONDS**attempt * random.uniform(0.5, 1.5))` using a documented non-crypto RNG. Preserve the retry behaviour for 5xx, timeouts, and connection errors, which is what makes delivery reliable, and preserve the `MAX_ATTEMPTS` ceiling. Pair the sides: the deny case asserts a 400 response produces exactly one HTTP request and a `failed_permanent` row; the allow case asserts a 503 followed by a 200 produces two requests and a `delivered` row. Red-prove separately by execution: (i) remove the 4xx branch and observe the one-request assertion go red at five requests, (ii) make the 4xx branch also catch 5xx and observe the 503-then-200 allow case go red. Note the jitter change breaks `test_backoff_grows_exponentially`, which asserts exact equality — rewrite it as a bounded-range assertion rather than deleting it, since it is the only pin on the growth curve. Fail loudly when the check cannot run: a response with no status code (a transport-level failure) must route to the existing `httpx.HTTPError` retry path and not fall through the status comparison. Boundary and tie: 400 and 499 are both permanent, 500 is retryable, 408 and 429 are the named exceptions on the permanent side, and two responses with the same status are treated identically regardless of body.

### Major: the Redis lock is not atomic and is released unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock()` and `run_worker()`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` performs a `get` then a separate `set`, so two workers can both observe an empty key and both proceed, and the separate `expire` leaves a window where a crash between `set` and `expire` wedges the lock permanently; `run_worker`'s `finally` then deletes the key by name without checking ownership, so a worker whose 60-second lease already expired deletes the lock a *different* worker now holds.
What breaks in production: two workers process the same claimed batch concurrently, so customers receive duplicate deliveries, and the `attempts` counter and terminal status are written twice from racing transactions.
Fix: make acquisition a single atomic operation with the TTL inline — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token` is a per-worker `secrets.token_hex(16)` — and make release conditional on that token (a compare-and-delete Lua script, or at minimum a `get`-equals-token check before `delete`); preserve the lock's purpose, so do not fix the double-delete by removing the release altogether, which would wedge the worker for 60 seconds after every batch. Pair the sides: the deny case asserts a second `_acquire_lock` call while the first holds the lock returns `False`; the allow case asserts that after the holder releases, the next caller acquires successfully — and that a worker whose token no longer matches does *not* delete the key. Red-prove separately by execution: (i) revert to `get`-then-`set` and observe the mutual-exclusion deny case go red under two concurrent calls, (ii) revert the release to an unconditional `delete` and observe the ownership assertion go red. Fail loudly when the check cannot run: if Redis is unreachable, `_acquire_lock` must return `False` and log a named error rather than raising into `run_worker`'s loop or defaulting to `True` — an unavailable coordinator denies the batch, it does not grant it. Boundary and tie: the lease boundary is that the batch must complete strictly within the 60-second TTL or be refreshed, and two workers presenting different tokens for the same key are resolved by the `nx=True` write, not by read ordering.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch()` (sets `row.status = "in_flight"`) and `_finish()` (only ever writes a terminal status)
What is wrong: `_claim_batch` commits `in_flight` before the HTTP work begins, but nothing returns a row to `pending` — if the worker is killed, the process restarts, `deliver` raises anything other than `httpx.HTTPError` (a `DetachedInstanceError`, an integrity error, a `ValueError` from serialization), or the batch exceeds the 60-second lock lease, the row is stranded in a state `_claim_batch` never selects (R38 non-terminal state).
What breaks in production: webhook deliveries silently vanish with no alert and no operator recovery path — the row sits in `in_flight` forever, the customer never receives the event, and the deliveries API reports a status that looks like work in progress.
Fix: record a claim timestamp alongside the state (`claimed_at`) and widen `_claim_batch`'s predicate to reclaim rows whose `status == 'in_flight'` and whose `claimed_at` is older than a stale threshold (e.g. twice the lock TTL), and wrap each `deliver` call in a `try/except Exception` that routes the row back to `pending` with an incremented `attempts`; preserve the `in_flight` marking itself, since removing it reintroduces double-claiming. Pair the sides: the deny case asserts a row claimed one second ago is *not* reclaimed by a concurrent `_claim_batch`; the allow case asserts a row claimed beyond the stale threshold *is* reclaimed and eventually delivered. Red-prove separately by execution: (i) remove the staleness predicate and observe the reclaim allow case go red; (ii) remove the `claimed_at` freshness bound (reclaim everything `in_flight`) and observe the concurrent deny case go red. Fail loudly when the check cannot run: a row whose `claimed_at` is null must be treated as stale and reclaimed with a warning, not skipped — an unresolvable claim age is a recovery case, not a reason to leave the row stranded. Boundary and tie: state that a row at exactly the stale threshold is reclaimed (inclusive), and two workers reclaiming the same stale row at the same instant are separated by the `in_flight` write under the dispatch lock.

### Major: a failed enqueue is swallowed, so the event commits with no delivery record and nothing retries
File: `app/events/dispatcher.py` — `dispatch()` (the `except Exception as exc: log.warning(...)` around `webhook_delivery.enqueue_for_event`)
What is wrong: the enqueue runs in its own `session_scope` *after* the event transaction has already committed, and any failure — the duplicate-key violation from the `event_id` unique index, a connection error, a serialization failure — is caught and downgraded to a warning while `dispatch` returns the event id as if everything succeeded (R9: fire-and-forget across a transaction boundary, with no compensating path).
What breaks in production: the event is durably persisted but its webhook deliveries are not, and because nothing scans for events lacking delivery rows, the customer permanently misses that event with only a WARNING line as evidence.
Fix: create the delivery rows inside the same `session_scope` as the `Event` insert, so the event and its deliveries commit or roll back together and the enqueue cannot be half-done; where that is not acceptable, keep the separate transaction but add an outbox reconciliation — a periodic query for events of a `WEBHOOK_EVENT_TYPES` type older than N minutes with no `WebhookDelivery` row, re-enqueuing them — and re-raise or increment a monitored counter instead of only logging. Preserve the property the current code was reaching for: a webhook failure must not prevent the event from being recorded or block in-process subscribers, so the fix must not make `dispatch` propagate the exception to its caller without first ensuring the event row is durable. Pair the sides: the deny case makes `enqueue_for_event` raise and asserts that either the event is absent (single-transaction variant) or the reconciliation pass later creates the missing rows, **and** that a monitored failure counter incremented — not merely that `dispatch` returned; the allow case asserts a normal dispatch produces both the event row and one delivery row per subscribed endpoint. Red-prove separately by execution: (i) remove the reconciliation/counter and observe the deny case go red on the counter assertion, (ii) remove the enqueue call and observe the allow case go red on the delivery-row count. Fail loudly when the check cannot run: an enqueue that cannot reach the database must be recorded as a distinct "enqueue unavailable" signal, not as a zero-endpoint success — `enqueue_for_event` returning `0` because no endpoints matched and returning nothing because it failed must not be spelled the same way. Boundary and tie: the boundary is the commit of the `Event` row, and an event dispatched twice with the same `event_id` must produce one delivery per endpoint, which the corrected `(endpoint_id, event_id)` unique index enforces.

### Major: the dispatcher's hardcoded event-type set contradicts the documented subscription model
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`, against `app/api/routes/settings.py` — `EndpointIn.event_types` and `docs/webhooks.md`
What is wrong: `dispatch` only enqueues for three hardcoded types, but the registration API accepts any string in `event_types` and the docs state "An empty `event_types` subscribes the endpoint to every event type we emit" — so `enqueue_for_event`'s own `if not endpoint.event_types` catch-all branch is unreachable for every event outside the hardcoded three (R41: a declared capability whose backing path is structurally always-empty).
What breaks in production: a customer who registers an endpoint with no `event_types`, believing they are subscribed to everything, receives only three event types and has no way to discover the gap; a customer who names any other type receives nothing at all and gets no validation error at registration.
Fix: derive the gate from a single registry rather than a second hardcoded set — expose the emitting side's known webhook-eligible types as one exported constant (e.g. `app/webhooks.WEBHOOK_EVENT_TYPES`) that both `dispatch` and `create_webhook_endpoint` consult, and have `create_webhook_endpoint` return 422 listing the unknown members when `body.event_types` contains a type outside it. Preserve the deliberate narrowing — not every internal event should leave the system — but make it visible: update `docs/webhooks.md` to enumerate the emitted types instead of claiming "every event type we emit". Pair the sides: the deny case asserts registering `event_types=["not.a.real.type"]` returns 422 **and** creates no endpoint row; the allow case asserts registering `["invoice.paid"]` returns 201 and that dispatching `invoice.paid` enqueues a row for it, and that an endpoint with `event_types=[]` receives all three enumerated types. Red-prove separately by execution: (i) remove the membership check and observe the unknown-type deny case go red, (ii) remove one member from the shared registry and observe the empty-`event_types` allow case go red on the missing type. Fail loudly when the check cannot run: if the registry cannot be imported the route must reject registration rather than accepting every string. Boundary and tie: the boundary is exact string membership with no prefix or wildcard matching, and an empty list means "all members of the registry at delivery time", which must be re-evaluated per event rather than expanded at registration.

### Major: `organizations.webhooks_enabled` is added but never read
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: the migration introduces a per-org feature flag defaulting to `FALSE`, but no code in the diff consults it — `create_webhook_endpoint` accepts registrations unconditionally and `enqueue_for_event` filters only on `active` — so the declared gate has no backing path (R41).
What breaks in production: the feature ships enabled for every organization despite a column that says it is off by default, and an operator who flips `webhooks_enabled` to `FALSE` to stop deliveries for an abusive or misconfigured tenant sees no effect at all.
Fix: enforce the flag at both boundaries — `create_webhook_endpoint` returns 403 when the caller's org has `webhooks_enabled` false, and `enqueue_for_event` adds `Organization.webhooks_enabled.is_(True)` to its endpoint query via a join — and add `webhooks_enabled` to the `Organization` model so the column is reachable from Python. Preserve the ability to run the feature: the rollout procedure must set the flag true for enrolled orgs, so the fix must ship with the enabling path, not only the deny path. Pair the sides: the deny case asserts an org with the flag false gets 403 on registration **and** that dispatching an event for it creates zero delivery rows; the allow case asserts an org with the flag true registers successfully and receives delivery rows. Red-prove separately by execution: (i) remove the route check and observe the 403 deny case go red, (ii) remove the join predicate in `enqueue_for_event` and observe the zero-rows deny case go red while the 403 case stays green. Fail loudly when the check cannot run: an org row that cannot be loaded must deny rather than default to enabled — an unresolvable subject is a denial. Boundary and tie: the flag is read at dispatch time, not cached at registration, so an org disabled after registering stops receiving immediately; and an org whose row is missing is treated as disabled.

### Major: naive and timezone-aware datetimes are mixed across the same column
File: `app/webhooks/delivery.py` — `enqueue_for_event` (`next_attempt_at=datetime.utcnow()`) vs `_claim_batch` (`now = datetime.now(timezone.utc)`), and `migrations/0042_webhook_delivery.sql` (`TIMESTAMP`) vs `app/webhooks/models.py` (`DateTime(timezone=True)`)
What is wrong: rows are written with a naive UTC datetime and compared against an aware one, while the migration declares every timestamp column as `TIMESTAMP` (without time zone) and the model declares `DateTime(timezone=True)` — the same column is described three different ways, and the file already contains the correct helper (`models._now()`, which returns `datetime.now(timezone.utc)`) that `enqueue_for_event` does not use.
What breaks in production: depending on driver and column type the comparison in `_claim_batch` either raises `TypeError: can't compare offset-naive and offset-aware datetimes` or silently shifts by the server's UTC offset, so deliveries are claimed hours early or never; `WebhookDelivery.to_dict()` then emits `next_attempt_at.isoformat()` with no offset, so the deliveries API reports ambiguous times to customers.
Fix: use one representation everywhere — change the migration's five timestamp columns to `TIMESTAMPTZ`, replace `datetime.utcnow()` in `enqueue_for_event` with the module's existing `models._now()` helper (making it the single source, per R1), and keep `DateTime(timezone=True)` in the model so all three agree. Preserve the scheduling semantics: `next_attempt_at` set to "now" must still make the row immediately claimable, so the fix must not shift the default forward. Pair the sides: the allow case asserts a row enqueued at `now` is returned by an immediately following `_claim_batch`; the deny case asserts a row with `next_attempt_at` one hour in the future is *not* returned. Red-prove separately by execution: (i) revert `enqueue_for_event` to `datetime.utcnow()` and observe the allow case go red (raise or miss); (ii) invert `_claim_batch`'s comparison to `>=` and observe the future-row deny case go red. Fail loudly when the check cannot run: a naive datetime reaching the comparison must raise a named error rather than being coerced with an assumed offset. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimable (`<=`, inclusive, as written), and two rows sharing the same `next_attempt_at` tie under `ORDER BY next_attempt_at` — see the ordering finding below.

### Major: unbounded `limit` and no total order on the deliveries listing
File: `app/api/routes/settings.py` — `list_deliveries` (`limit: int = Query(50, ge=1)` and `.order_by(WebhookDelivery.created_at.desc())`)
What is wrong: `Query(50, ge=1)` sets a floor but no ceiling, and the ordering key is a wall-clock `created_at` with no unique tiebreaker — deliveries created by a single `session.add_all` in `enqueue_for_event` share an identical `created_at`, so their relative order is undefined (R57).
What breaks in production: `?limit=100000000` streams the whole delivery table including every JSONB payload in one response, and any client paginating on `created_at` silently skips or repeats rows exactly at the batch boundaries where fan-out created ties — the deliveries feed is what customers use to reconcile missed events, so a skipped row reads as an event that was never sent.
Fix: bound the parameter with `Query(50, ge=1, le=200)` and make the ordering total by adding the primary key as the tiebreaker — `.order_by(WebhookDelivery.created_at.desc(), WebhookDelivery.id.desc())` — and, if keyset pagination is added later, carry both values in the cursor; `id` is a `BIGSERIAL` the caller cannot name, so it satisfies the un-forgeable requirement. Preserve the newest-first presentation, which is the useful behaviour, and preserve the default of 50 so existing callers are unaffected. Pair the sides: the allow case asserts `limit=200` succeeds and `limit=50` still returns 50; the deny case asserts `limit=201` returns 422 **and** that the query was not executed. Red-prove separately by execution: (i) remove `le=200` and observe the 422 deny case go red; (ii) remove the `id` tiebreaker and observe a determinism test — insert five deliveries with an identical `created_at`, list twice, assert identical order — go red. Fail loudly when the check cannot run: a non-integer `limit` must 422 rather than falling back to the default. Boundary and tie: 200 is accepted and 201 is rejected, and rows sharing a `created_at` are ordered by descending `id`, so the page cut through equal keys is deterministic.

### Major: `EndpointIn` validates almost nothing, and the URL check sits in the handler rather than the schema
File: `app/api/routes/settings.py` — `EndpointIn` and `create_webhook_endpoint`
What is wrong: `url: str` and `event_types: list[str] = []` accept an unbounded-length URL, an unbounded list of arbitrary strings, and duplicates, and the only real check (`urlparse`) lives in the handler body rather than at the schema level (RS3), while nothing caps how many endpoints one org may register.
What breaks in production: a tenant can persist a multi-megabyte URL or a hundred-thousand-element `event_types` array straight into JSONB and register endpoints without limit, and because `enqueue_for_event` fans out one row per active endpoint per event, that multiplies into unbounded delivery-table growth and worker load for every event the org emits.
Fix: move validation onto the model — `url: HttpUrl` with a `max_length`, `event_types: list[str] = Field(default_factory=list, max_length=20)` with a per-item `max_length`, and a validator that de-duplicates and checks membership against the shared event-type registry (see the dispatcher finding) — and add a per-org endpoint cap enforced in the handler with a 409 when exceeded. Preserve the documented ergonomics: an empty `event_types` must still mean "all emitted types", and the `https`-only rule from the SSRF finding still applies on top of `HttpUrl`. Pair the sides: the deny cases assert an over-length URL, a 21-element `event_types`, and an over-cap registration each return 4xx **and** create no row; the allow case asserts `{"url": "https://hooks.example.com/acme", "event_types": ["invoice.paid"]}` still returns 201 with the row persisted. Red-prove separately by execution: (i) remove `max_length` on `event_types` and observe that deny case go red; (ii) remove the per-org cap and observe the over-cap deny case go red; both must leave the allow case green. Fail loudly when the check cannot run: a body that is not an object must 422 from the schema, never reach the handler. Boundary and tie: state the caps as inclusive (20 event types accepted, 21 rejected; the Nth endpoint accepted, the N+1th rejected), and two concurrent registrations at the cap boundary must be resolved by a database constraint or a locked count, not by two independent reads.

### Major: the new delivery machinery ships almost entirely untested, and the one delivery test cannot fail for the reason it claims
File: `tests/webhooks/test_delivery.py` — the whole file, against `app/webhooks/delivery.py`
What is wrong: of the new production exports — `enqueue_for_event`, `backoff_for`, `_acquire_lock`, `_claim_batch`, `_finish`, `send_once`, `deliver`, `run_worker`, and both `to_dict()` methods — only `send_once` and `backoff_for` are exercised (RT6), and `test_send_once_posts_the_signed_payload` asserts merely that the signature header *starts with* `sha256=` without ever recomputing the HMAC over `captured["body"]`, so it stays green under the signed-bytes-vs-wire-bytes divergence that makes every delivery unverifiable (RT7: the assertion cannot fail for the defect it appears to cover).
What breaks in production: the two highest-consequence defects in this change — the serialization mismatch and the detached-instance failure — both ship with a green suite, and the retry loop, the batch claim, the lock, and the fan-out have no coverage at all, so the first evidence of any of them is customer-reported missing webhooks.
Fix: strengthen the existing assertion to a real round trip — `assert signing.verify(SECRET, captured["timestamp"], json.loads(captured["body"]), captured["headers"][signing.SIGNATURE_HEADER])` computed from the captured bytes, not from a re-serialization — and add tests for `enqueue_for_event` (fan-out count and the `event_types` filter, including the empty-list catch-all), `deliver` (2xx terminal, 4xx terminal, 5xx retried to `MAX_ATTEMPTS`, `attempts` persisted), `_claim_batch` (claims only due `pending` rows, marks them `in_flight`, does not re-claim), and `_acquire_lock` (mutual exclusion). Preserve the existing signing tests, which are the only pins on the secret format and the wrong-secret rejection — do not consolidate them away. Pair the sides throughout: each retry test asserts both the terminal status and the exact request count; each filter test asserts both the endpoint that receives a row and the one that does not. Red-prove each new assertion separately by execution: mutate one production line per assertion — swap `content=` back to `json=`, remove the 4xx branch, change the `_claim_batch` status predicate to `in_flight`, revert `_acquire_lock` to non-atomic — and observe exactly one assertion redden for each, with the failure output naming the reason. Fail loudly when the checks cannot run: replace the `FakeEndpoint`/`FakeDelivery` doubles for the delivery-path tests with real persisted rows, and make the database-backed tests error rather than skip when no database is available — a suite that silently skips its only integration coverage reports "found nothing" where it means "examined nothing" (RT1). Boundary and tie: pin `MAX_ATTEMPTS` at the boundary — attempt 5 is the last one made and no sixth request is issued — and assert two deliveries for the same event but different endpoints are both created and both delivered.

## Cross-cutting verification

- **Tenant scoping**: `list_webhook_endpoints` applies `org_id == user.org_id`; `list_deliveries`, added in the same hunk, does not. That asymmetry inside the diff is the evidence for the IDOR finding — the pattern exists and one of the two new read routes was missed. `enqueue_for_event` is correctly org-scoped.
- **Status vocabulary**: `'failed_permanent'` appears in `models.STATUSES` and in `delivery._finish`; the migration's CHECK is the only site using `'failed'`. No third spelling exists in the diff.
- **Datetime construction**: `models._now()` (aware) is used for four column defaults; `delivery.enqueue_for_event` is the single site using naive `datetime.utcnow()`; `_claim_batch` and `_finish` use aware `datetime.now(timezone.utc)`. One outlier, reported above.
- **Secret serialization**: `WebhookEndpoint.to_dict()` emits `signing_secret`; `WebhookDelivery.to_dict()` was checked and emits no secret-bearing field. The only other secret sink in the diff is the `log.info` in `send_once`, reported separately.
- **URL/scheme adjudication**: the `scheme.startswith("http")` check exists at exactly one site (`create_webhook_endpoint`); the delivery side performs no destination check at all before `client.post`, which is the second half of the SSRF finding.
- **Blocking calls in async code**: `time.sleep` appears once, in `deliver`. All other waits (`run_worker`) correctly use `await asyncio.sleep`.
- **Session-boundary leakage**: both `_claim_batch` and `deliver` return or use ORM objects past their `session_scope`; `enqueue_for_event`, `_finish`, and the three route handlers keep all attribute access inside the block, so the defect is confined to those two functions.
