### Critical: deliveries endpoint is not scoped to the caller's organization (IDOR)
File: `app/api/routes/settings.py` — `list_deliveries`, the `.filter(WebhookDelivery.endpoint_id == endpoint_id)` clause
What is wrong: The query filters on the path-supplied `endpoint_id` only and never joins to `WebhookEndpoint.org_id == user.org_id`, while the sibling handler added in the same diff (`list_webhook_endpoints`) does filter on `org_id` — the tenancy pattern was applied to one new route and not its neighbour (R3).
What breaks in production: Any authenticated user can enumerate integer endpoint ids and read other organizations' delivery rows, whose `to_dict()` exposes `event_id`, `event_type` and response status for events they have no access to.
Fix: Join the tenancy predicate into the query itself rather than checking it separately — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id, ...)` — and return 404 (not 403) for an id that exists under another org so the endpoint does not become an existence oracle. Preserve the behaviour the route is for: the owner's own listing must still return its rows in `created_at DESC` order, so pair the deny fixture with an allow fixture — endpoint owned by `user.org_id` returns its N rows — and pin the boundary case where two orgs' endpoints have adjacent ids (id `k` owned by org A, `k+1` by org B: A gets `k`, and `k+1` returns 404 for A and its rows for B). Red-prove each clause separately by execution: (1) delete the `org_id` predicate → the cross-tenant test must fail; (2) change the 404 to a 403 → the oracle test must fail; (3) delete the join → the owner-allow test must still pass, proving mutation (1) reddened for tenancy and not for an arity error. If `user.org_id` is absent or `None`, raise rather than falling through to an unfiltered query — "no org resolved" must not be spelled the same as "no rows matched".

### Critical: the signing secret is returned on every endpoint read, contradicting the documented one-time-disclosure contract
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, the `"signing_secret": self.signing_secret` entry
What is wrong: `to_dict()` is the single serializer used by both `create_webhook_endpoint` and `list_webhook_endpoints`, so the secret is emitted on every `GET /v1/settings/webhook-endpoints`, while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" (R25 access scope; R49 claim stronger than the implementation).
What breaks in production: The webhook signing key — the only thing distinguishing a genuine callback from a forged one — is readable by any principal with list access to settings and lands in every response log, browser cache and audit trail of that route.
Fix: Split the serializer: keep `to_dict()` secret-free (id, url, event_types, active) and add an explicit `to_dict_with_secret()` used only by the 201 response of `create_webhook_endpoint`; do not fix this by editing the doc sentence, because the one-time-disclosure claim is the property customers' key handling depends on. Preserve the create path's usefulness: the allow case is that the POST response still contains a `signing_secret` a caller can immediately sign with — assert the returned value round-trips through `signing.verify`. Red-prove separately by execution: (1) add `signing_secret` back into `to_dict()` → the list-response test asserting `"signing_secret" not in body[0]` must red; (2) point `create_webhook_endpoint` at `to_dict()` → the create-response test must red; (3) with both reverted, the list test and create test must both pass green, showing the two mutations reddened different assertions. Add a rotation route rather than a read route if customers need the secret again, and make any serializer that cannot determine its disclosure context raise instead of defaulting to including the field.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: `app/webhooks/signing.py` — `new_signing_secret`, `random.choice(_ALPHABET)`
What is wrong: `random` is a Mersenne Twister seeded from predictable state and its output is fully reconstructable from ~624 observed outputs, so the secret is not unpredictable despite the 32-character length the test checks.
What breaks in production: An attacker who can register two endpoints of their own can recover the generator state and derive other organizations' signing secrets, then forge signed events that every customer's verification accepts.
Fix: Replace the body with `secrets.token_urlsafe(SECRET_BYTES)` prefixed by `SECRET_PREFIX`, drop the `random`/`string` imports, and rename `SECRET_BYTES` to mean bytes of entropy rather than output characters (the current constant is compared against `len()` in the test, which conflates the two). Preserve what the current code got right and what the test pins: the returned value must still start with `whsec_` and must still be accepted by `sign`/`verify` — keep that allow assertion. Red-prove each clause by execution: (1) swap `secrets.token_urlsafe` back to `random.choice` → a test asserting `random` is not imported by `signing.py` (or a `unittest.mock.patch("random.seed")` determinism test producing two identical secrets from a fixed seed) must red; (2) drop the prefix → the prefix assertion must red; (3) shorten to 8 bytes → a minimum-entropy assertion (`len(secret) - len(SECRET_PREFIX) >= 32`) must red. State the boundary: the length assertion must be `>=`, not `==`, because `token_urlsafe(32)` yields 43 characters and a `==` test would red on a correct fix; two secrets generated in the same microsecond must differ, so assert `new_signing_secret() != new_signing_secret()`.

### Critical: signature verification uses a variable-time string comparison
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The recomputed MAC is compared with `==`, which short-circuits on the first differing byte (RS1).
What breaks in production: A caller that can submit signatures against a known payload can recover a valid signature byte-by-byte from response-time differences, defeating the only authenticity control on the webhook channel — and because `verify` is the reference implementation shipped in this repo, every internal consumer inherits the flaw.
Fix: Use `hmac.compare_digest(expected, signature)` and normalise both operands to `str` before the call (`compare_digest` raises on mixed str/bytes), so a bytes header does not silently take the exception path. Preserve the allow side: `test_verify_accepts_signature_produced_by_sign` must stay green, and add a case where the payload keys are supplied in a different order to pin that `serialize`'s `sort_keys=True` still makes verification order-independent. Red-prove separately by execution: (1) revert to `==` → a test asserting `signing.verify.__code__.co_names` contains `compare_digest` (or a lint gate on `==` over signature-shaped identifiers) must red; (2) truncate `expected` by one character → the accept test must red; (3) pass a `bytes` signature → the function must raise a named `TypeError` rather than returning `False`, because "could not compare" must not be spelled the same as "did not match". Name the tie: a signature of the wrong length must be rejected, not error, and an empty-string signature must be rejected — `compare_digest` returns False for both, so assert both explicitly.

### Critical: the shipped signature is not the signature the documentation tells customers to compute
File: `app/webhooks/signing.py` — `sign`; `app/webhooks/delivery.py` — `send_once`
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"`, but `sign` MACs only `json.dumps(payload, sort_keys=True)` with the timestamp excluded, and `send_once` transmits the body via `client.post(json=...)` — httpx's own serializer, which uses compact separators and insertion order — so the bytes signed are not the bytes sent (R40, R29).
What breaks in production: Every customer implementing the documented verification fails 100% of deliveries, and because the timestamp is outside the MAC an attacker can rewrite `X-Acme-Timestamp` on a captured request to defeat the five-minute replay window the doc says protects them.
Fix: Make `sign` take the exact bytes that will be transmitted and MAC `f"{timestamp}.{body}"`: change the signature to `sign(secret, body: bytes) -> tuple[str, str]`, have `send_once` compute `body = serialize(delivery.payload).encode()` once and pass `content=body` (not `json=`) to `client.post`, and update `verify` to take the same raw body. Do not fix this by rewriting the doc to describe the current MAC — the timestamp-in-MAC is what makes the replay window enforceable, and that is the behaviour the fix must preserve. Red-prove each clause by execution: (1) drop the timestamp from the MAC input → a test that mutates only the `X-Acme-Timestamp` header of a captured request and asserts `verify` now returns False must red; (2) revert `content=` to `json=` → a round-trip test that feeds the *actual* captured `request.content` through the *actual* `verify` (R40's actual-output-through-actual-consumer requirement, which the existing `test_send_once_posts_the_signed_payload` stops short of by only checking the header prefix) must red; (3) change `sort_keys=True` to `False` → that same round-trip test must stay green, proving the round-trip pins bytes and not key order. Name the boundary: a payload at exactly the timestamp skew limit must be accepted and one second beyond it rejected, and two deliveries signed in the same second with identical payloads must produce identical signatures — document that as intended, since dedup is `event_id`-based.

### Critical: the `status` CHECK constraint rejects the value the code writes on permanent failure
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py` `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: The migration allows `'failed'` while `models.py::STATUSES` and `delivery.py` both use `'failed_permanent'`, so the enum spelling is hardcoded in three places that disagree (R2, R40).
What breaks in production: The first delivery that exhausts its attempts raises an IntegrityError inside `_finish`, the row stays `in_flight` forever, and the worker's `asyncio.gather` propagates the error out of the batch loop — one dead customer endpoint stalls all webhook delivery.
Fix: Make `models.STATUSES` the single source and have the migration derive from it rather than restating it: change the CHECK list to `('pending','in_flight','delivered','failed_permanent')` and add a test that asserts the constraint's allowed set equals `models.STATUSES` by querying `pg_constraint`, so the next added status cannot drift. Preserve the constraint's purpose — do not fix by dropping the CHECK, which would make the mismatch invisible instead of fixed. Red-prove each clause by execution: (1) remove `'failed_permanent'` from the migration list → the constraint-parity test must red; (2) add a bogus `'retrying'` to `STATUSES` without touching the migration → the same test must red in the other direction, proving it is not one-sided; (3) attempt an `INSERT ... status='bogus'` → it must raise, proving the CHECK is still enforcing. Name the tie: `STATUSES` is currently a dead constant that nothing imports — wire `models.py` and `delivery.py` to it (`m.STATUSES`) so the literal exists once, and have the parity test fail loudly (not skip) when no database is reachable.

### Critical: the unique index on `event_id` allows only one delivery row per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint from a single `event_id`, so any organization with two subscribed endpoints violates the uniqueness on flush.
What breaks in production: The second endpoint's insert raises an IntegrityError inside `session_scope`, which rolls back the whole `add_all`, so *neither* endpoint receives the event — and the dispatcher swallows the exception, so the loss is silent.
Fix: Replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id)`, which is the constraint actually wanted: it still gives the idempotency guarantee (a redelivered event never double-enqueues to the same endpoint) that the single-column index was presumably reaching for, so nothing useful is deleted. Add the missing `CREATE INDEX ON webhook_deliveries (endpoint_id, created_at DESC)` that `list_deliveries` needs. Red-prove each clause by execution: (1) revert to the single-column index → a test that enqueues one event to two active endpoints of the same org and asserts two rows exist must red; (2) drop the composite index entirely → a test that enqueues the same `event_id` to the same endpoint twice and asserts one row must red; (3) with both indexes in place, both tests must pass, proving the two mutations reddened different assertions. Name the boundary and the tie: two endpoints of *different* orgs subscribing to the same `event_id` must both get a row, and a re-enqueue of an event whose prior row is already `delivered` must be a no-op rather than an error — use `ON CONFLICT DO NOTHING` and assert the returned count reflects rows actually inserted, since `enqueue_for_event` currently returns `len(rows)` regardless.

### Critical: outbound URL is attacker-chosen with redirect following and no destination policy (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint` URL check; `app/webhooks/delivery.py` — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The only check on a customer-supplied destination is `parsed.scheme.startswith("http") and parsed.netloc`, with no resolution of the host to an address and no private-range denial, and the client then follows redirects, so even a public-looking host can bounce the request into the internal network (R47: the notation is judged, not the address the socket layer will actually connect to).
What breaks in production: A customer registers `http://169.254.169.254/latest/meta-data/` (or a public host redirecting there), the worker POSTs a signed request to the cloud metadata service, and the response body is stored in `response_body` and served back to that customer through `GET .../deliveries`.
Fix: Climb to the interpreter that decides the destination: resolve the hostname with `socket.getaddrinfo` at registration *and* pin the resolved address at send time (a name resolved at check time is not the address connected to — bind the decision to the address, via an `httpx` transport with a fixed resolved IP, rather than re-resolving from the name), reject every result in an `ipaddress` private/loopback/link-local/reserved/multicast range, set `follow_redirects=False` and treat 3xx as a permanent failure, and require scheme `https` exactly (see the scheme finding below). Preserve the feature: the allow case is a genuine public HTTPS endpoint, which must still register and still receive deliveries — pin `https://hooks.example.com/acme` resolving to a public address as an accepted fixture adjacent to the boundary. Red-prove each clause separately by execution: (1) remove the private-range check → a registration test for `http://127.0.0.1/x` must red; (2) set `follow_redirects=True` → a delivery test whose fixture returns a 302 to `http://169.254.169.254/` must red; (3) remove the send-time address pin → a test whose resolver returns a public IP on the first call and a private IP on the second must red. Fail loudly: DNS that does not resolve, resolves to zero addresses, or times out must reject the registration with a named error, never fall through to "no private address found". Name the tie: an address that is both public and in the deny-list overlay denies, and a host resolving to both a public and a private address denies.

### Critical: `time.sleep` inside an async coroutine blocks the whole event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered 100-wide by `run_worker`, but its retry pause is the blocking `time.sleep`, not `await asyncio.sleep`.
What breaks in production: One failing endpoint stalls the entire process for 2+4+8+16 = 30 seconds per delivery — with a full batch of failures the worker (and anything else sharing the loop, including the Redis lock refresh) is frozen for tens of minutes and the 60-second lock TTL expires while the lock holder is still running.
Fix: Replace with `await asyncio.sleep(delay)`. The deeper fix is that in-process retry contradicts the schema this diff adds: `next_attempt_at` and `attempts` exist precisely so a failed attempt is persisted and re-claimed later — rewrite `deliver` to make **one** attempt, then either `_finish(..., "delivered", ...)`, or `_finish(..., "failed_permanent", ...)` when `attempt >= MAX_ATTEMPTS`, or write back `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)`; keep `MAX_ATTEMPTS` and `backoff_for` unchanged so the existing `test_backoff_grows_exponentially` and `test_max_attempts_matches_documented_limit` stay green — the retry semantics are what must be preserved, only their scheduling moves. Red-prove each clause by execution: (1) reinstate `time.sleep` → a test asserting the loop stays responsive (two `deliver` calls gathered against a 1s-delayed transport complete in < 1.5s wall time) must red; (2) drop the `next_attempt_at` write-back → a test asserting a failed delivery is re-claimable only after `backoff_for(1)` must red; (3) drop the `attempts` write-back → a test asserting the fifth claim marks `failed_permanent` must red. Name the boundary: a delivery whose `next_attempt_at` is exactly `now` is claimable (the filter is `<=`), and two deliveries sharing the same `next_attempt_at` must both be claimed within one batch rather than one starving — order by `(next_attempt_at, id)` so the ordering key is total.

### Major: `scheme.startswith("http")` is a prefix match where the URL parser defines the scheme
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, `if not parsed.scheme.startswith("http")`
What is wrong: A prefix test admits any scheme beginning with those four characters (`httpfoo:`, `http+unix:`) and admits plain `http:` even though `docs/webhooks.md` says "Only `https://` URLs are accepted" (R47 surface-form adjudication; R49 claim stronger than the implementation).
What breaks in production: Webhooks carrying customer billing payloads and an HMAC header are sent in cleartext over `http://`, and the doc's https-only promise is false for every customer who reads it.
Fix: Replace the prefix test with exact membership — `if parsed.scheme != "https" or not parsed.hostname` — and validate through Pydantic at the schema boundary instead of inside the handler body (`url: AnyHttpUrl` with a scheme validator), so the check cannot be bypassed by a second call site. Preserve the allow side: `https://hooks.example.com/acme` must still register, and a URL with a non-default port and a path must still register — pin both. Red-prove each clause by execution: (1) restore `startswith` → a test rejecting `httpfoo://x/y` must red; (2) widen the set to `{"http","https"}` → a test rejecting `http://hooks.example.com/acme` must red; (3) remove the `hostname` check → a test rejecting `https:///path` must red. Fail loudly on a URL `urlparse` cannot parse (raise 422 naming the field) rather than letting an empty scheme fall through the negation. Name the tie: uppercase `HTTPS://` must be accepted (urlparse lowercases the scheme — assert it) and `https://` with an empty host must be rejected.

### Major: rows are used after their session closes, so every attribute read is on a detached instance
File: `app/webhooks/delivery.py` — `_claim_batch` return value; `deliver`'s `endpoint` lookup
What is wrong: Both functions exit `session_scope()` before returning/using the ORM objects, so `delivery.payload`, `delivery.attempts`, `endpoint.url` and `endpoint.signing_secret` are read from expired instances — SQLAlchemy expires attributes on commit by default and re-loading requires the closed session.
What breaks in production: The worker raises `DetachedInstanceError` on the first delivery of the first batch, after `_claim_batch` has already committed those rows to `in_flight`, so the batch is both undelivered and unclaimable.
Fix: Stop passing ORM entities across the session boundary: have `_claim_batch` return plain dataclasses/tuples of the fields the sender needs (`id`, `endpoint_id`, `attempts`, `payload`) selected in the same transaction, and have `deliver` receive the endpoint's `url` and `signing_secret` as values loaded in that same query via a join, rather than opening a second session. Preserve the claim semantics: the `status = "in_flight"` write must still commit in the claiming transaction — that is what stops two workers sending the same delivery. Red-prove each clause by execution: (1) return the ORM rows again → a test that claims a batch and reads `payload` after the session closes must red with `DetachedInstanceError`; (2) remove the `in_flight` write → a test asserting a second `_claim_batch` call returns an empty list must red; (3) remove the join and re-open a session for the endpoint → the detached test must red again on `endpoint.url`, proving the two paths are separately covered. Fail loudly when the join finds no endpoint (a deleted endpoint): mark the delivery `failed_permanent` with a named detail rather than skipping it silently.

### Major: `in_flight` is a non-terminal state with no exit for crashes or non-HTTP exceptions
File: `app/webhooks/delivery.py` — `deliver`'s `except httpx.HTTPError`; `_claim_batch`'s `row.status = "in_flight"`
What is wrong: Only `httpx.HTTPError` is caught, so a `json` serialization error, a `DetachedInstanceError`, an OOM kill or a deploy restart leaves rows in `in_flight` permanently, and nothing in the diff ever transitions a stale `in_flight` row back to `pending` (R38 non-terminal transient state).
What breaks in production: Every worker restart permanently strands the in-flight batch — up to 100 customer events per restart are silently never delivered and never reported as failed.
Fix: Add a bounded-lease recovery: record `claimed_at` when a row is set to `in_flight`, and have the worker, before each claim, reset rows where `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` back to `pending` with `attempts` unchanged; broaden `deliver`'s handler to `except Exception` that routes to `_finish(..., "pending"/"failed_permanent", ...)` while re-raising `asyncio.CancelledError`. Preserve the claim's purpose — the reaper must not resurrect a row a live worker is still sending, which is why the lease is longer than `REQUEST_TIMEOUT` and why `attempts` is preserved rather than reset. Red-prove each clause by execution: (1) remove the reaper → a test that inserts an `in_flight` row with `claimed_at` 10 minutes old and asserts the next claim returns it must red; (2) narrow the handler back to `httpx.HTTPError` → a test whose transport raises `ValueError` and asserts the row is not left `in_flight` must red; (3) shorten the lease to zero → a test asserting a row claimed 1 second ago is *not* reaped must red, covering the over-recovery direction. Name the boundary: a row whose `claimed_at` is exactly the lease horizon is reaped (`<=`), and a row reaped while its worker later calls `_finish` must be settled by a conditional update keyed on the claim, so the late writer loses rather than overwriting a newer attempt.

### Major: `run_worker` raises `NameError` when the claim query fails
File: `app/webhooks/delivery.py` — `run_worker`, `if not batch:` after the `try/finally`
What is wrong: `batch` is bound inside the `try`, but the `if not batch` test sits after the `finally`, so any exception from `_claim_batch` or `asyncio.gather` propagates past the lock release into an unbound-name evaluation — and even without that, the exception escapes the `while True` loop entirely because nothing catches it.
What breaks in production: A single transient database error terminates the delivery worker process, and since nothing re-enters the loop the queue drains only when a supervisor restarts the container.

Red-prove each clause by execution: (1) revert `batch` out of the `try` and make `_claim_batch` raise → the test asserting the worker survives one failing iteration must red with `NameError`; (2) remove the `except Exception` → the same test must red with the injected error; (3) catch `BaseException` instead → a test asserting `worker_task.cancel()` completes within one poll interval must red. Fail loudly: the `log.exception` must carry the batch size and the lock state so a wedged loop is diagnosable, and the empty-batch sleep must still happen on the exception path so a hard-failing claim does not become a hot spin.

### Major: `_finish` dereferences a row it never checks for existence

### Major: the dispatcher swallows enqueue failures, so events are silently never delivered
File: `app/events/dispatcher.py` — `dispatch`, `except Exception as exc: log.warning(...)`
What is wrong: A blanket catch downgrades every enqueue failure — including the IntegrityError the unique index guarantees for multi-endpoint orgs — to a warning line, with no retry, no dead-letter and no signal to the caller (R36: suppression as a substitute for a fix; R9: the enqueue runs outside the event's transaction, so a committed event can have no delivery rows).
What breaks in production: Billing events are recorded internally but never reach the customer's endpoint, and because the only trace is a warning at a level most deployments do not alert on, the gap is discovered by the customer.
Fix: Make the enqueue durable rather than best-effort: insert the delivery rows in the *same* `session_scope` as the `Event` row so the event and its fan-out commit atomically, and let a genuine failure propagate to `dispatch`'s caller; if fan-out must stay asynchronous, write an outbox row inside the event transaction and have the worker fan out from it. Narrow the catch to the exceptions that are genuinely recoverable, re-raise the rest, and emit a counter metric so "enqueued zero rows" is observable. Preserve the property the try/except was protecting — a webhook problem must not lose the *event* — by keeping the event write first in the same transaction and making the failure path roll both back rather than committing a half state. Red-prove each clause by execution: (1) restore the blanket catch → a test asserting `dispatch` raises when the delivery insert fails must red; (2) move the delivery insert back into a second session → a test asserting no `Event` row exists after a failed fan-out must red; (3) make the enqueue succeed → the happy-path test asserting `dispatch` returns the event id and N delivery rows exist must stay green, proving (1) and (2) reddened for their own reasons. Name the tie: an org with zero active endpoints must commit the event with zero delivery rows and must not be treated as a failure.

### Major: naive and aware datetimes are mixed, and the migration columns have no time zone
File: `app/webhooks/delivery.py` — `next_attempt_at=datetime.utcnow()` vs `_claim_batch`'s `now = datetime.now(timezone.utc)`; `migrations/0042_webhook_delivery.sql` — `TIMESTAMP NOT NULL` vs `models.py` `DateTime(timezone=True)`
What is wrong: `enqueue_for_event` writes a naive UTC datetime into a column the model declares as `timezone=True` while the migration declares it as `TIMESTAMP` (without time zone), and the claim query compares that column against an aware value — the same `_now()` helper the models module already defines for exactly this purpose is not used (R1: the helper exists in the diff and is bypassed).
What breaks in production: Depending on the server's `TimeZone` setting the comparison either raises `can't compare offset-naive and offset-aware datetimes` or silently shifts every schedule by the local UTC offset, so deliveries are claimed hours early or never.

### Major: the Redis dispatch lock is not atomic and expires before a batch can finish
File: `app/webhooks/delivery.py` — `_acquire_lock`
What is wrong: `get` followed by `set` is a check-then-act with an interval any second worker can act in, the TTL is applied by a separate `expire` call (so a crash between them leaks the lock forever), and the 60-second TTL is shorter than a batch's worst case (100 deliveries × up to 5 attempts × 30s timeout) — while `run_worker`'s `finally` deletes the key unconditionally, including one another worker has since acquired.
What breaks in production: Two workers claim and send the same batch, doubling every customer's webhook traffic, or a crashed worker leaves an un-expiring key and delivery stops entirely until someone deletes it by hand.
Fix: Use a single atomic `SET key <random-token> NX EX <ttl>` and release with a compare-and-delete (Lua `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete the lock it holds — this is R51's handle-not-name shape: the release must be bound to the token acquired, not to the key's name. Size the TTL above the worst-case batch duration and refresh it periodically while the batch runs. Preserve the mutual exclusion the lock exists for — do not fix the expiry problem by removing the TTL, which reintroduces the permanent-wedge failure. Red-prove each clause by execution: (1) revert to `get`-then-`set` → a test racing two `_acquire_lock` coroutines and asserting exactly one succeeds must red; (2) revert to an unconditional `delete` → a test where worker A's release runs after B has acquired, asserting B still holds the lock, must red; (3) remove the TTL → a test asserting an abandoned lock is re-acquirable after the TTL must red. Fail loudly when Redis is unreachable: `_acquire_lock` must raise (and the loop back off) rather than returning `False` forever or `True` without a lock. Name the boundary: a lock whose TTL expires at exactly the moment of the CAS release must not delete a successor's key — the token comparison is what decides the tie.
