### Critical: the HMAC is computed over different bytes than the request body, so no receiver can verify a delivery
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `sign`/`serialize`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (default separators, `ensure_ascii=True`) while the request is sent with `client.post(..., json=delivery.payload)`, which re-serializes the dict itself — different key order, different separators, different escaping — so the signed string and the transmitted body are not the same bytes.
What breaks in production: every customer following `docs/webhooks.md` computes the HMAC over the raw body they received and gets a mismatch, so 100% of deliveries are rejected by every correctly-implemented receiver — the classic R40 silent total-path failure, invisible here because the producer and the shipped `verify()` both re-serialize the dict and agree with each other.
Fix: serialize once and send those exact bytes — in `send_once` compute `body = signing.serialize(delivery.payload).encode("utf-8")`, pass it to `sign()` (see the next finding for the timestamp prefix), and POST with `client.post(endpoint.url, content=body, headers=headers)` instead of `json=`; change `sign(secret, payload)` to `sign(secret, body: bytes)` and `verify(secret, body: bytes, signature)` so neither side can re-serialize. Preserve: the `Content-Type: application/json` header, the `X-Acme-Signature`/`X-Acme-Timestamp` names and the `sha256=` prefix — receivers key on all four, and dropping any of them "fixes" the mismatch by breaking a different contract. Allow side, pinned: a round-trip test that takes the bytes actually captured by `httpx.MockTransport` and feeds them to an independently written verifier (raw `hmac.new(secret, ts + b"." + captured_body, sha256).hexdigest()` written in the test, not a call to `signing.verify`) must still pass, and must use a payload whose natural key order is NOT sorted (e.g. `{"z": 1, "a": {"b": [2, 3]}, "s": "é"}`) so sortedness and non-ASCII escaping are both live. Deny side, pinned: flipping one byte of the captured body must make that verifier return False. Red-prove separately: (i) revert `content=body` to `json=delivery.payload` — the round-trip assertion must red naming the signature comparison, not a decode error; (ii) remove `sort_keys=True` from `serialize` — the cross-language vector test below must red. Fail loudly: `serialize()` must raise on a payload that is not JSON-serializable rather than letting `send_once` fall through to an unsigned or partially-signed request; a delivery that cannot be serialized is `_finish(..., "failed_permanent", ...)` with the reason, never a silent skip. Boundary/tie: state in the doc that the signed string is the byte-for-byte HTTP body, so a receiver that re-parses and re-serializes before verifying is out of contract; two payloads that serialize identically are the same signed message by construction, which is the intended tie.

### Critical: the timestamp is not covered by the signature, so the replay window the docs promise does not exist
File: `app/webhooks/signing.py` — `sign` (line `mac = hmac.new(secret.encode(), serialize(payload).encode(), hashlib.sha256)`)
What is wrong: `docs/webhooks.md` states the signature is the HMAC of `"{timestamp}.{raw_request_body}"` and that rejecting timestamps older than five minutes "stops a captured request from being replayed", but `sign()` MACs only the body, so `X-Acme-Timestamp` is unauthenticated and freely rewritable.
What breaks in production: anyone who captures one delivery — from a proxy log, from the `log.info("POST %s headers=%s", ...)` line below, or from a receiver's own access log — can replay that body forever by setting the timestamp header to the current time, and every customer who implemented only the documented staleness check believes replay is closed (R49: a claim strictly stronger than the implementation, relied on as the boundary, so no customer added the `event_id` dedupe that would actually close it).
Fix: make the signed string `f"{timestamp}.".encode() + body` inside `sign()`, and have `verify(secret, body, timestamp, signature)` take the caller-supplied timestamp so it authenticates the same string; declare the control class explicitly in `docs/webhooks.md` — the timestamp binding is an *enforceable* freshness bound only when combined with the receiver's staleness check, and dedupe on `event_id` remains required because at-least-once delivery legitimately re-sends within the window. Preserve: the header stays unix seconds as a decimal string (customers parse it) and the `sha256=` prefix stays. Allow side, pinned: a delivery signed at `T` and verified at `T + 299s` must still verify; a re-delivery of the same `event_id` inside the window must verify (it is legitimate, not a replay). Deny side, pinned: taking a valid `(body, ts, sig)` triple and substituting `ts+1` must make verification fail. Red-prove separately: (i) drop the `f"{timestamp}."` prefix from `sign` — the timestamp-substitution test reds naming the signature assertion; (ii) leave the prefix in `sign` but omit it in `verify` — the accept test reds, proving the two sides are checked independently rather than by one mirrored round-trip. Fail loudly: `verify()` raises on a non-numeric or absent timestamp rather than returning False, so "the header was missing" is not spelled the same as "the signature was wrong". Boundary/tie: define the window as `now - ts <= 300` inclusive, and say so in the doc; a request at exactly 300s is accepted, at 301s rejected, and clock skew is the receiver's to bound.

### Critical: signing secrets are generated with `random`, which is not cryptographically secure
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister PRNG, which is seeded from a small state and is fully reconstructible from a modest run of its outputs.
What breaks in production: an attacker who obtains a handful of secrets (their own endpoints, created in a loop against the very `POST /v1/settings/webhook-endpoints` route this diff adds) can recover the generator state and derive other tenants' signing secrets, then forge signed webhooks — for `invoice.paid` events, into customers' billing automation.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and delete `random`, `string` and `_ALPHABET`; rename or re-document `SECRET_BYTES = 32` so it means bytes of entropy (it is currently used as a character count, and the test pins that wrong meaning — see the Minor below). Preserve: the `whsec_` prefix and the property that the secret is opaque and URL-safe; customers already store it verbatim, so the fix must not change the prefix. Allow side, pinned: an existing `whsec_`-prefixed secret must continue to sign and verify unchanged (no format gate is introduced that would invalidate secrets already issued). Deny side, pinned: assert `len(set(new_signing_secret() for _ in range(1000))) == 1000` and that no `random.` symbol remains importable from the module. Red-prove separately: (i) restore `random.choice` and assert with `random.seed(0)` that two module-level calls are reproducible — the new test must red on that reproducibility; (ii) shrink `SECRET_BYTES` to 4 and assert the entropy floor test reds. Fail loudly: `secrets.token_urlsafe` raises rather than degrading if the OS entropy source is unavailable — do not wrap it in a `try` that falls back to `random`, which is the exact regression this fix exists to prevent. Boundary/tie: secrets already persisted with the weak generator are not repaired by this change — ship a one-off rotation for every existing `webhook_endpoints` row and tell affected customers, since a rotation is the only thing that removes the exposure.

### Critical: `verify()` compares signatures with `==`, leaking the expected MAC through timing
File: `app/webhooks/signing.py` — `verify` (`return expected == signature`)
What is wrong: the HMAC comparison uses Python's short-circuiting string `==` instead of a constant-time primitive (RS1).
What breaks in production: this function is the reference verifier shipped in the same module customers are pointed at, and any internal endpoint that adopts it lets an attacker recover a valid signature byte-by-byte from response-time differences, turning a forgery that requires the secret into one that requires only patience.
Fix: `return hmac.compare_digest(expected, signature)` (`hmac` is already imported), and keep it constant-time after the byte-oriented refactor above by comparing the raw digests rather than the `sha256=`-prefixed strings — strip the prefix first, rejecting a missing prefix explicitly. Preserve: the function must still return `False` (not raise) for a well-formed but wrong signature, which is what its one existing caller in `tests/webhooks/test_delivery.py` asserts. Allow side, pinned: `test_verify_accepts_signature_produced_by_sign` must still pass, and a second test must assert a signature produced by an *independently written* HMAC expression in the test file also verifies. Deny side, pinned: a signature of the correct length differing only in the last hex character returns False; a signature differing only in the first character also returns False (proving no early exit is being asserted). Red-prove: revert to `==` and run a comparison-count instrumentation test (monkeypatch `hmac.compare_digest` to raise) — it must red naming the missing constant-time call; a timing assertion is not usable as the proof because it is flaky, so the proof is call-path based. Fail loudly: a signature that is not `sha256=<64 hex>` raises `ValueError` rather than silently returning False, so a malformed header is distinguishable from a wrong one. Boundary/tie: `compare_digest` on unequal-length inputs is documented to leak only the length — reject non-64-hex input before comparing so length never varies at the comparison.

### Critical: any endpoint URL is accepted, including internal hosts, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint` (`if not parsed.scheme.startswith("http") or not parsed.netloc`); `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: the only check is that the scheme starts with `http` and a netloc exists, so `http://169.254.169.254/latest/meta-data/`, `http://localhost:6379/`, `http://10.0.0.5/admin` and even `httpfoo://x` all pass, and the worker then POSTs to them following redirects.
What breaks in production: a tenant registers an endpoint pointing at the cloud metadata service or an internal admin API and the worker makes the request from inside the VPC on their behalf — server-side request forgery with the response status and body persisted to `webhook_deliveries.response_body` for later reading; `follow_redirects=True` means even a validated public host can 302 into the same place. `docs/webhooks.md` asserts "Only `https://` URLs are accepted", which the code does not implement (R49), and `startswith` on a scheme is surface-form adjudication where `urlparse` already gives the exact token.
Fix: validate with the library already imported in this file — declare `url: AnyHttpUrl` on `EndpointIn` — then add an explicit egress guard: require `parsed.scheme == "https"` (exact equality, not `startswith`), resolve the host with `socket.getaddrinfo` and reject if any resolved address satisfies `is_private or is_loopback or is_link_local or is_reserved or is_multicast or is_unspecified` via `ipaddress.ip_address`, reject a userinfo component and non-default ports outside `{443}`, and set `follow_redirects=False` on the `AsyncClient`. Because DNS can be re-pointed after registration, repeat the address check in `send_once` immediately before the POST and connect to the checked address. Preserve: registration must still succeed for an ordinary public HTTPS endpoint with a path and query string, and the 422 shape stays so existing clients keep parsing the error. Allow side, pinned: `https://hooks.example.com/acme?x=1` registers and delivers (this is the case a tightening fix silently breaks). Deny side, pinned: each of `http://hooks.example.com`, `httpfoo://x`, `https://127.0.0.1/`, `https://169.254.169.254/`, `https://[::1]/`, and a host whose DNS resolves to `10.0.0.5` is rejected at registration; and a public host that 302s to `http://169.254.169.254/` produces a delivery failure rather than a fetch. Red-prove separately, one mutation per clause: (i) change `==` back to `startswith` — the `httpfoo://` case reds; (ii) drop the private-range check — the `10.0.0.5` case reds; (iii) set `follow_redirects=True` — the redirect case reds; (iv) remove the pre-POST re-resolution — the rebinding case (resolver returning public then private) reds. Fail loudly: when DNS resolution fails or times out, registration returns 422 and delivery is retried as a transient failure — an unresolvable host must never be treated as "no private address found, therefore allowed". Boundary/tie: state which side `0.0.0.0/8`, IPv4-mapped IPv6 (`::ffff:10.0.0.5`) and CGNAT `100.64.0.0/10` fall on — all rejected — and check every address returned by `getaddrinfo`, not the first, since a tie between one public and one private answer must deny.

### Critical: the deliveries endpoint is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only on `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint.org_id == user.org_id`, unlike both sibling routes added in the same file.
What breaks in production: any authenticated user increments `endpoint_id` and reads other organizations' delivery history — event ids, event types, delivery status and schedule — a cross-tenant data leak reachable with no special privilege.
Fix: join and filter, e.g. `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)`, and return 404 (not 403) when the join yields nothing so the endpoint's existence is not disclosed. Preserve: the response shape stays `list[dict]` from `to_dict()` and the ordering/limit behaviour is unchanged for the legitimate caller — narrowing must not turn the owner's own request into an empty list. Allow side, pinned: the owning org's user gets exactly the rows for their endpoint (assert the row ids, not just a non-empty list). Deny side, pinned per RT8: a user from org B requesting org A's `endpoint_id` receives 404 **and** the assertion also checks that no row from org A appears in the body — status alone is the vacuous form. Red-prove: delete the `org_id` clause and confirm the cross-tenant test reds naming the leaked-row assertion, not the status assertion. Fail loudly: when `user.org_id` is absent the handler raises rather than defaulting to an unfiltered query. Boundary/tie: an endpoint whose `active` is False still belongs to its org and must remain readable by its owner — deactivation is not deletion, and the filter is on ownership only.
Cross-cutting (R3): I enumerated all three new routes. `create_webhook_endpoint` sets `org_id=user.org_id` and `list_webhook_endpoints` filters on it; `list_deliveries` is the only miss, and `enqueue_for_event` in `delivery.py` correctly filters `org_id`. No other unscoped tenant query exists in the diff.

### Critical: the unique index on `event_id` alone makes multi-endpoint orgs receive nothing
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` by itself, but `enqueue_for_event` inserts one row per matching endpoint for the same event.
What breaks in production: the moment an organization has two subscribed endpoints, `session.add_all(rows)` raises `IntegrityError`, the dispatcher's blanket `except Exception` swallows it as a `log.warning`, and **all** webhooks for that event are dropped — including the delivery to the first endpoint, which would have succeeded.
Fix: `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id);` and drop the single-column index; keep a non-unique index on `event_id` if the deliveries-by-event lookup is needed. Preserve: the idempotency property the index was reaching for — one delivery per (endpoint, event) — is what makes the docs' "deduplicate on `event_id`" safe, so the replacement must still be UNIQUE, not merely an index. Allow side, pinned: an event fanning out to three endpoints of one org inserts three rows. Deny side, pinned: enqueuing the same `event_id` twice for the same endpoint raises `IntegrityError` (re-delivery must not create a second row). Red-prove separately: (i) drop the UNIQUE keyword — the duplicate-enqueue test reds; (ii) revert to the single-column index — the three-endpoint test reds naming the integrity error. Fail loudly: `enqueue_for_event` must catch `IntegrityError` per row (or use `ON CONFLICT DO NOTHING`) and re-raise anything else, so "already enqueued" is not spelled the same as "the insert failed". Boundary/tie: an event matching zero endpoints inserts zero rows and returns 0 — that is a success, not a failure, and the caller must not treat it as one.

### Critical: the migration's status CHECK constraint does not contain the value the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`; `app/webhooks/delivery.py` — `_finish(delivery.id, "failed_permanent", ...)`
What is wrong: the schema permits `'failed'` while `models.STATUSES` and `deliver()` both use `'failed_permanent'` — the same enum is spelled three times (SQL CHECK, the unused `STATUSES` tuple, bare literals in `delivery.py`) and two spellings disagree.
What breaks in production: the first delivery that exhausts its attempts raises `CheckViolation` inside `_finish`, the exception propagates out of `deliver` through `asyncio.gather` (no `return_exceptions=True`) and terminates `run_worker` permanently, leaving the row wedged in `in_flight` and the whole webhook subsystem stopped until someone restarts it.
Fix: change the CHECK to `status IN ('pending', 'in_flight', 'delivered', 'failed_permanent')`, import `STATUSES` from `app/webhooks/models.py` into `delivery.py` and use `STATUSES` members instead of literals so the third spelling disappears, and add a test that asserts the CHECK's value set equals `models.STATUSES` by reading the constraint from the migrated database. Preserve: `'delivered'` and `'pending'` keep their spellings — existing rows and the `_claim_batch` filter depend on them, and "fixing" this by loosening the CHECK to accept any text would remove the only thing that would have caught the drift. Allow side, pinned: writing each of the four legal statuses succeeds. Deny side, pinned: writing `'failed'` or `'oops'` raises. Red-prove separately: (i) add a fifth literal to `STATUSES` without touching the migration — the set-equality test reds; (ii) revert `_finish` to the literal `"failed"` — the exhausted-attempts integration test reds naming the check violation. Fail loudly: `run_worker` must wrap each iteration and use `asyncio.gather(..., return_exceptions=True)`, logging each exception at ERROR, so one poisoned row cannot silently stop every future delivery. Boundary/tie: a row already persisted as `'failed'` by an earlier build (none exist yet, but the migration is the place to say so) is migrated with an explicit `UPDATE ... SET status = 'failed_permanent' WHERE status = 'failed'` before the CHECK is applied.

### Critical: claimed rows leave their session and are read after it closes
File: `app/webhooks/delivery.py` — `_claim_batch`, `deliver`, `send_once`
What is wrong: `_claim_batch` returns ORM instances after its `session_scope` has exited, and `deliver` then reads `delivery.attempts`, `delivery.payload` and `delivery.id` while `send_once` reads `endpoint.signing_secret` and `endpoint.url` from an instance whose session was closed one statement earlier.
What breaks in production: with SQLAlchemy's default `expire_on_commit=True` every attribute is expired at commit, so the first access raises `DetachedInstanceError` and no webhook is ever delivered; if the project happens to set `expire_on_commit=False`, the objects instead become silently stale snapshots that can never observe another worker's writes.
Fix: stop passing ORM identities across scope boundaries — have `_claim_batch` return plain data (`list[ClaimedDelivery]`, a frozen dataclass carrying `id`, `endpoint_id`, `attempts`, `payload`, and the endpoint's `url` and `signing_secret` read in the same transaction), and change `deliver`/`send_once` to take that dataclass; this also removes the second `session.get(WebhookEndpoint, ...)` round-trip in `deliver`. Preserve: the claim must stay a single transaction that both selects and flips `status` to `in_flight`, which is what stops a second worker taking the same rows; converting to plain data must not split it into two transactions. Allow side, pinned: an end-to-end test that claims a real row from a real (in-memory or containerised) database and delivers it through `httpx.MockTransport` succeeds and marks the row `delivered` — RT5 requires the production `_claim_batch` in the call path, not a hand-built `FakeDelivery`. Deny side, pinned: the same test with the transport returning 500 leaves the row retriable with an advanced `next_attempt_at`. Red-prove separately: (i) return ORM rows from `_claim_batch` again — the end-to-end test reds naming the detached access; (ii) move the `status = "in_flight"` write outside the select's transaction — the concurrent-claim test (two workers, one row) reds on a double claim. Fail loudly: if the claim transaction cannot commit, `_claim_batch` raises and `run_worker` logs and retries — it must not return a partially claimed list. Boundary/tie: rows with `next_attempt_at` exactly equal to `now` are claimed (`<=`), and ties on `next_attempt_at` are broken by `id` so the batch cut is deterministic.
Note on grounding: whether this raises or merely goes stale depends on the `sessionmaker` configuration in `app/db`, which the diff does not show. The defect — objects used outside the scope that owns them — is visible in the diff regardless, and the answer that would close the "raises" half is `expire_on_commit=False` in `app/db.session_scope`.

### Critical: `time.sleep` inside an async coroutine blocks the whole worker
File: `app/webhooks/delivery.py` — `deliver` (`time.sleep(delay)`)
What is wrong: the retry backoff uses the blocking `time.sleep` inside an `async def` that `run_worker` runs under `asyncio.gather`, so the event loop is frozen rather than yielded.
What breaks in production: one endpoint that times out stalls the loop for 2+4+8+16 = 30 s of sleeps plus up to 120 s of request timeouts, during which none of the other 99 deliveries in the batch, and nothing else on that loop, makes progress; the 60 s Redis lock expires mid-batch while the worker is still blocked, so a second worker starts claiming and the `finally: delete(LOCK_KEY)` then deletes the *other* worker's lock.
Fix: remove the in-process retry loop entirely — on a retriable failure, persist `attempts += 1`, `next_attempt_at = now + backoff_for(attempt)` and `status = "pending"`, and return; the existing `_claim_batch`/`next_attempt_at` machinery already is the retry scheduler, so the loop reimplements it in a form that cannot survive a restart. Add jitter (`backoff_for` returning `base * 2**attempt * uniform(0.5, 1.5)`) as `docs/webhooks.md` already claims. Preserve: at most `MAX_ATTEMPTS` total attempts and the `2, 4, 8, 16` order of magnitude — the fix must not silently make deliveries retry forever, and the terminal `failed_permanent` transition stays. Allow side, pinned: a delivery that succeeds on the first attempt performs exactly one POST and is marked `delivered` with `attempts == 1`. Deny side, pinned: a delivery failing five times is `failed_permanent` with `attempts == 5` and exactly five POSTs, and the elapsed wall-clock time of the test is under one second (proving nothing slept in-process). Red-prove separately: (i) restore `time.sleep` — the elapsed-time assertion reds; (ii) remove the `next_attempt_at` write — the reschedule assertion reds; (iii) fix `backoff_for` to a constant — the jitter-range assertion reds. Fail loudly: if the reschedule write fails, the row must not be left `in_flight` — catch, log at ERROR and let the reaper (next finding) recover it, rather than returning as though the retry were scheduled. Boundary/tie: a delivery whose `attempts` already equals `MAX_ATTEMPTS` at claim time is finalised without another POST; the comparison is `attempt >= MAX_ATTEMPTS` and 5 is the last attempt, not the first refusal.

### Major: `in_flight` is a non-terminal state with no timeout and no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` (`row.status = "in_flight"`), `_finish`
What is wrong: rows enter `in_flight` in the claim transaction and leave it only when `_finish` runs on the success or permanent-failure path; a worker crash, a deploy, a `CheckViolation`, or a raised `gather` leaves them there forever with no visibility timeout (R38 shape 1).
What breaks in production: every restart permanently strands whatever was in flight — the deliveries silently never happen and never appear as failures, so the customer sees a missing event with no error anywhere.
Fix: add a `claimed_at TIMESTAMPTZ` column set in the claim transaction, and a reaper that returns rows to `pending` when `claimed_at < now - lease_interval` with `attempts` incremented; make the lease strictly longer than `REQUEST_TIMEOUT` and shorter than the retry backoff floor. Preserve: a delivery genuinely still in flight must not be reclaimed and double-sent beyond the documented at-least-once envelope — the lease bound is what preserves that, so it must be measured against `REQUEST_TIMEOUT`, not guessed. Allow side, pinned: a delivery claimed 1 s ago is not reclaimed. Deny side, pinned: a delivery claimed `lease + 1s` ago is reclaimed exactly once and its `attempts` advances. Red-prove separately: (i) remove the age predicate — the not-yet-expired case reds by being reclaimed; (ii) remove the `attempts` increment — the bounded-retry assertion reds by looping forever, so bound the test with a timeout so absence surfaces as a failure rather than a hang. Fail loudly: a reaper run that cannot read the clock or the table logs at ERROR and exits non-zero rather than reporting "nothing to reap". Boundary/tie: a row at exactly `claimed_at == now - lease` is not yet expired (`<` , not `<=`), and two reapers racing the same row are resolved by making the reset a conditional `UPDATE ... WHERE status = 'in_flight' AND claimed_at < ...` whose affected-row count decides the winner.

### Major: the Redis lock is not atomic, is not owned, and is deleted unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, `run_worker` (`finally: await redis_client.delete(LOCK_KEY)`)
What is wrong: `get`-then-`set` is a check-then-act race, `set` and `expire` are two round-trips so a crash between them leaves a lock with no TTL that no one ever clears, and the `finally` deletes the key without checking that this worker still owns it.
What breaks in production: two workers pass `_acquire_lock` simultaneously and claim overlapping batches (duplicate deliveries), or a crash between `set` and `expire` wedges the subsystem permanently with a lock nothing can release (R38 shape 2 — a persisted fail-closed wedge with no exit).
Fix: acquire with a single atomic command carrying a per-run token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`); renew the TTL while a batch is running, or make `LOCK_TTL` exceed the worst-case batch duration implied by `REQUEST_TIMEOUT`. Preserve: the lock must still expire on its own — replacing the TTL with an explicit release only is what turns a crash into a permanent outage, which is the failure this fix exists to remove. Allow side, pinned: after a normal release the next `_acquire_lock` succeeds immediately. Deny side, pinned: a second concurrent acquire returns False, and a release attempted with a stale token leaves the current holder's key intact. Red-prove separately: (i) drop `nx=True` — the concurrent-acquire test reds; (ii) drop `ex=` — the TTL-expiry test reds (bounded by a fake clock, not a real sleep); (iii) replace compare-and-delete with a plain `delete` — the stale-token test reds. Fail loudly: a Redis error during acquire returns False and logs at ERROR — it must not be swallowed into "lock not held, proceed".
