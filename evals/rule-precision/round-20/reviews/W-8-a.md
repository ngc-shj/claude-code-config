### Critical: `list_deliveries` reads any organization's delivery rows
File: app/api/routes/settings.py — `list_deliveries`
What is wrong: The query filters only on `WebhookDelivery.endpoint_id` and never joins or filters on `org_id`, while its sibling `list_webhook_endpoints` in the same file does filter `WebhookEndpoint.org_id == user.org_id`, so any authenticated user can enumerate integer endpoint ids belonging to other tenants.
What breaks in production: A customer walks `endpoint_id=1..N` and reads every other organization's `event_type`, delivery status and schedule — and `docs/webhooks.md` states the route "returns the most recent attempts for an endpoint belonging to your organization", a claim the code does not implement (R49 clause 2).
Fix: Join the tenancy predicate into the query itself rather than checking it in the handler — `session.query(m.WebhookDelivery).join(m.WebhookEndpoint, m.WebhookDelivery.endpoint_id == m.WebhookEndpoint.id).filter(m.WebhookEndpoint.org_id == user.org_id, m.WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403, which confirms existence) when the endpoint id resolves to no row for this org. Preserve the existing capability the fix must not delete: the owning org must still receive its full ordered, limited list, so pin the allow side with a test asserting owner-org GET returns exactly the rows it created. Red-prove the two clauses separately by execution: (i) delete the `org_id` filter and assert the foreign-org test goes red on row count, (ii) delete the `endpoint_id` filter and assert the owner-org test goes red by returning a second endpoint's rows. Fail loudly rather than silently empty when the check cannot run: an `endpoint_id` that resolves to no row at all must 404, and a `user.org_id` that is `None` must raise, never fall through to an unfiltered query. Boundary and tie: an endpoint owned by the caller's org with zero deliveries returns `[]` with 200 (not 404); an `endpoint_id` shared by no org returns 404; ties on the ordering key are addressed separately below.

### Critical: `verify` compares the signature with `==`
File: app/webhooks/signing.py — `verify`
What is wrong: `return expected == signature` is a short-circuiting byte comparison on an HMAC, so comparison time leaks the length of the matching prefix (RS1).
What breaks in production: An attacker with a signing oracle recovers a valid signature byte by byte and forges accepted webhook payloads against any consumer that adopts this helper for inbound verification.
Fix: Replace the body with `_, expected = sign(secret, payload)` followed by `return hmac.compare_digest(expected, signature)`; `hmac` is already imported in this file so no new dependency is introduced. Guard the non-`str`/`None` `signature` case explicitly — `compare_digest` raises `TypeError` on mixed types — and return `False` only after an explicit `isinstance(signature, str)` check so an off-type input is a loud rejection, not a `TypeError` that some caller catches broadly (Remedy Floor 3). Preserve the allow side: keep `test_verify_accepts_signature_produced_by_sign` green and add a case with a signature differing only in the final character, which must be rejected. Red-prove each clause by execution: (i) restore `==` and assert a new timing-independence unit (or at minimum a `compare_digest`-presence assertion on the module source) goes red, (ii) pass `signature=None` and assert the explicit-type test goes red if the `isinstance` guard is removed. Do not fix by deleting what made the defect visible: `verify` must keep recomputing from `secret` and `payload` rather than accepting a caller-supplied `expected`. Boundary and tie: equal-length equal-value inputs return `True`; unequal-length inputs return `False` without raising, and two distinct secrets producing the same digest is not a case this function may special-case.

### Critical: signing secrets are generated with `random`, not a CSPRNG
File: app/webhooks/signing.py — `new_signing_secret`
What is wrong: `random.choice` draws from the Mersenne Twister, a non-cryptographic generator whose internal state is recoverable from observed output, and this function is the sole source of `WebhookEndpoint.signing_secret`.
What breaks in production: An attacker who registers a few endpoints of their own recovers the generator state and predicts other tenants' signing secrets, which lets them forge webhooks that every customer's verification code accepts as genuine.
Fix: Use the stdlib primitive the file reimplements — `import secrets` and `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` — and delete `random`, `string` and `_ALPHABET`, which no other symbol in the diff uses. Rename or re-document `SECRET_BYTES`: it is currently consumed as a character count, and `token_urlsafe(32)` yields 43 characters from 32 bytes, so `tests/webhooks/test_delivery.py::test_new_signing_secret_has_prefix_and_length` must be updated to assert `len(secret) >= len(SECRET_PREFIX) + 43` rather than deleted — the length assertion is what made the misnomer visible and must be preserved, not dropped (Remedy Floor 4). Pin the allow side: the prefix test must still pass and a freshly minted secret must still be accepted by `sign`/`verify` round-trip. Red-prove separately by execution: (i) revert to `random.choice` seeded with `random.seed(0)` and assert a new "two secrets from a reseeded generator differ" test goes red, (ii) drop the prefix and assert the prefix test goes red. Fail loudly if the check cannot run: `secrets.token_urlsafe` raising on a platform without `os.urandom` must propagate, never fall back to `random`. Boundary and tie: `SECRET_BYTES` at its minimum acceptable value (32) is the floor the assertion pins; two calls returning the identical string is a failure, not a tie to tolerate.

### Critical: the signed timestamp is not part of the signed material, so the documented replay window is unenforceable
File: app/webhooks/signing.py — `sign`, and docs/webhooks.md "Verifying the signature"
What is wrong: `sign` computes `hmac.new(secret, serialize(payload), sha256)` over the payload alone and returns the timestamp beside it unsigned, while the documentation instructs receivers to verify an HMAC of `"{timestamp}.{raw_request_body}"` and says the five-minute timestamp window "is what stops a captured request from being replayed".
What breaks in production: An attacker who captures one delivery can rewrite `X-Acme-Timestamp` to the current second and replay the identical body forever, because the signature does not cover the timestamp — the documented anti-replay control does not exist.
Fix: Change `sign` to build the signed string exactly as documented — `signed = f"{timestamp}.{body}"` where `body` is the byte-identical request body (see the serialization finding below) — return `(timestamp, "sha256=" + hmac.new(secret.encode(), signed.encode(), hashlib.sha256).hexdigest())`, and change `verify` to take the timestamp as a parameter (`verify(secret, timestamp, body, signature)`) plus a `max_age_seconds: int = 300` skew check so the window is enforced by the shipped helper rather than left to prose. Preserve what made the feature useful: `send_once` must keep emitting both headers and the docs' verification recipe must remain literally true after the change. Pin the allow side: a signature generated at `now` verifies; one generated at `now - 299s` still verifies. Red-prove each clause by execution: (i) remove the timestamp from the signed string and assert a "same body, rewritten timestamp is rejected" test goes red, (ii) remove the skew check and assert a `now - 3600s` test goes red, (iii) remove the `compare_digest` and assert the constant-time test goes red. Fail loudly when the check cannot run: a missing, non-numeric or non-integer timestamp header must reject with a named error, never be coerced to `0` or skipped. Boundary and tie: `age == max_age_seconds` exactly is accepted and `age == max_age_seconds + 1` rejected; a timestamp in the future beyond a small tolerance (say 60s) is rejected rather than treated as age zero.

### Critical: the signature is computed over different bytes than the bytes actually sent
File: app/webhooks/delivery.py — `send_once`; app/webhooks/signing.py — `serialize`
What is wrong: `sign` hashes `json.dumps(payload, sort_keys=True)` (default `", "`/`": "` separators, keys reordered) while the request body is produced independently by `client.post(..., json=delivery.payload, ...)`, which uses httpx's own encoding with compact separators and insertion order — producer and strict consumer disagree on the exact byte string (R40).
What breaks in production: Every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest than the one in the header, so 100% of deliveries fail verification and the whole feature is dead on arrival for any correctly-implemented receiver.
Fix: Serialize once and send those exact bytes — in `send_once`, compute `body = signing.serialize(delivery.payload).encode()`, sign `body`, and call `client.post(endpoint.url, content=body, headers=headers)` with the explicit `Content-Type: application/json` header already present, so `json=` never re-encodes. Preserve the behaviour the fix must not delete: the payload must still arrive as valid JSON with the same key/value content, so keep `serialize` as the single definition of the wire form and have both the signer and the sender call it. Pin the allow side with a round-trip test that feeds the *actual* captured request bytes through the *actual* `signing.verify`, asserting it returns `True` (this is the assertion the current test set omits). Red-prove each clause separately by execution: (i) revert `content=body` to `json=delivery.payload` and assert the round-trip test goes red, (ii) change `sort_keys=True` to `False` in `serialize` and assert it goes red again, (iii) mutate one byte of the captured body and assert `verify` returns `False`. Fail loudly when the check cannot run: a payload that is not JSON-serializable must raise before the POST rather than sending an empty body. Boundary and tie: an empty payload `{}` must sign and verify as `{}`; two payloads whose key sets differ only by ordering must produce the same signature, and any payload differing by one byte must not.

### Critical: the unique index on `event_id` makes multi-endpoint fan-out impossible
File: migrations/0042_webhook_delivery.sql — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`

Fail loudly when the check cannot run: `enqueue_for_event` must surface an `IntegrityError` rather than have it absorbed by the caller's broad `except Exception` (see the dispatcher finding). ### Critical: `time.sleep` inside an `async def` blocks the whole event loop
File: app/webhooks/delivery.py — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` (100) at a time in `run_worker`, and its retry backoff calls the synchronous `time.sleep`, which blocks the single event loop thread rather than yielding.
What breaks in production: One failing endpoint stalls the entire worker for up to 2+4+8+16 = 30 seconds per retry chain, serializing all 100 concurrent deliveries behind it and starving the lock's 60-second TTL so a second worker takes over mid-flight.
Fix: Replace `time.sleep(delay)` with `await asyncio.sleep(delay)`; `asyncio` is already imported in this module. Do not fix by deleting the backoff — the delay between attempts is the behaviour that must be preserved. Pin the allow side: a successful first attempt must still return without sleeping at all, and the total wall time of two concurrent failing deliveries must be close to one delivery's, not twice it. Red-prove each clause separately by execution: (i) restore `time.sleep` and assert a test measuring two concurrent `deliver` calls' wall clock reds on the concurrency assertion, (ii) set `BASE_DELAY_SECONDS` to 0 and assert the "backoff was actually awaited" assertion reds. Fail loudly when the check cannot run: if the loop is not running (`deliver` invoked outside an event loop), `asyncio.sleep` raising is the correct loud failure and must not be caught. Boundary and tie: `attempt == MAX_ATTEMPTS` must return without sleeping (no trailing sleep before giving up), and `attempt == MAX_ATTEMPTS - 1` must sleep exactly once more.

### Critical: endpoint registration accepts plaintext and internal targets, and the client follows redirects
File: app/api/routes/settings.py — `create_webhook_endpoint`; app/webhooks/delivery.py — `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: The guard `parsed.scheme.startswith("http")` adjudicates the URL by its surface notation rather than by what the HTTP client will actually resolve and connect to (R47) — it admits `http://`, admits any scheme merely prefixed with `http` such as `httpx://`, and imposes no restriction on the host, while `follow_redirects=True` means even an allowed host can bounce the signed POST to `http://169.254.169.254/`.
What breaks in production: Any authenticated tenant registers `http://10.0.0.5/admin` or a redirector and turns the delivery worker into a server-side request forgery primitive that POSTs attacker-chosen JSON to internal services from inside the VPC, with the signature headers attached.
Fix: Replace the prefix test with an explicit whitelist of the single legitimate shape — `if parsed.scheme != "https" or not parsed.hostname: raise HTTPException(422, ...)` — then resolve the hostname through the interpreter that will actually be used (`socket.getaddrinfo`) and reject every resolved address for which `ipaddress.ip_address(addr).is_private or .is_loopback or .is_link_local or .is_reserved` is true, and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a delivery failure rather than followed. Because DNS can be re-pointed between registration and delivery, repeat the resolved-address check in the worker at connect time via an `httpx` transport hook; declare this control's class per R49 as a fail-closed verification gate, not an enforceable boundary. Preserve what made the feature useful: a legitimate public HTTPS endpoint must still register and receive deliveries — pin that allow side with a test registering `https://hooks.example.com/acme` (resolving to a public address) and asserting 201 plus a successful delivery. Red-prove each clause separately by execution: (i) submit `http://hooks.example.com/x` and assert the scheme test reds if the `!= "https"` check is relaxed to `startswith`, (ii) submit `https://localhost/x` and assert the address test reds if the private-range check is removed, (iii) point a mock endpoint at a 302 to an internal host and assert the redirect test reds if `follow_redirects` is set back to `True`. Fail loudly when the check cannot run: a hostname that fails to resolve must 422 with a named reason, never be admitted as "could not determine, allow". Boundary and tie: `100.64.0.0/10` (carrier-grade NAT) and IPv6 unique-local `fc00::/7` fall on the deny side; a host resolving to both a public and a private address is denied, not admitted on the public one.

### Critical: `GET /webhook-endpoints` returns every signing secret, contradicting the documented contract
File: app/webhooks/models.py — `WebhookEndpoint.to_dict`, `"signing_secret": self.signing_secret`

Pin the allow side with a test asserting the 201 creation response contains `signing_secret` and the 200 list response does not. Red-prove each clause separately by execution: (i) re-add the key to `to_dict` and assert the list-route test reds, (ii) remove the explicit key from the creation handler and assert the creation test reds, (iii) call rotate and assert the old secret no longer verifies a fresh signature. Fail loudly when the check cannot run: `create_webhook_endpoint` must raise if `new_signing_secret()` returns an empty or prefix-only value rather than persisting a blank secret. Boundary and tie: an endpoint created before this change still has a readable secret in the DB and must be covered by a forced rotation, and two endpoints must never be issued the same secret.

### Critical: claimed rows are used after their session closes
File: app/webhooks/delivery.py — `_claim_batch` return value, consumed by `deliver`/`send_once`
What is wrong: `_claim_batch` mutates and returns ORM instances out of its `with session_scope() as session:` block, and `deliver`, `send_once` and `_finish` then read `delivery.payload`, `delivery.attempts` and `delivery.id` outside any session — a pattern that raises `DetachedInstanceError` under SQLAlchemy's default `expire_on_commit=True` once the scope commits and closes; `deliver` repeats the same mistake with `endpoint`, which it loads inside a session and dereferences afterwards.

Preserve the claim semantics that made the batch safe: the `status = "in_flight"` write must still happen in the same transaction as the SELECT. Pin the allow side: an integration test running `_claim_batch` followed by `deliver` against a real session must complete a delivery successfully. Red-prove each clause separately by execution: (i) return the ORM rows again and assert the integration test reds with `DetachedInstanceError`, (ii) move the endpoint dereference back outside the scope and assert it reds separately, (iii) remove the `in_flight` write and assert a "second claim returns the same rows" test reds. Fail loudly when the check cannot run: `session.get(m.WebhookEndpoint, ...)` returning `None` (endpoint deleted between enqueue and delivery) must mark the delivery failed with a named reason, not raise `AttributeError` on `endpoint.url`. Boundary and tie: an empty batch must return `[]` and take the sleep branch; two workers claiming simultaneously is covered by the lock finding below.

### Major: the dispatcher swallows every enqueue failure
File: app/events/dispatcher.py — `except Exception as exc: log.warning(...)` around `webhook_delivery.enqueue_for_event`
What is wrong: A bare `except Exception` around the only call that creates delivery rows converts every failure — the unique-violation above, a DB outage, a bug — into a warning line, and the event's own transaction has already committed so there is no reconciliation path back to the missed enqueue.

### Major: the Redis lock is not atomic and is released by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock`, and `finally: await redis_client.delete(LOCK_KEY)` in `run_worker`
What is wrong: `get` followed by `set` is a check-then-act race with no token, so two workers can both observe an absent key and both proceed, and the unconditional `delete` in `finally` removes a lock the caller may no longer own after the 60-second `expire` fires mid-batch.
What breaks in production: Two workers claim and POST the same deliveries concurrently, doubling every outbound webhook and burning customers' rate limits — the very duplication the `(endpoint_id, event_id)` idempotency key is supposed to bound.
Fix: Acquire atomically with a caller-unique token — `token = uuid4().hex; acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` in one call so TTL and value are set together — and release with a compare-and-delete Lua script (`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end`) so a worker never deletes another's lock. Add `FOR UPDATE SKIP LOCKED` to `_claim_batch`'s query so correctness does not rest on the lock alone. Preserve the useful property: a single worker must still acquire immediately with no added latency. Pin the allow side: one worker acquires, runs a batch, and releases; the next acquisition succeeds. Red-prove each clause separately by execution: (i) revert to `get`+`set` and assert a two-task concurrent-acquire test reds by returning two `True`s, (ii) revert the release to unconditional `delete` and assert a "stale owner does not delete the new lock" test reds, (iii) remove `SKIP LOCKED` and assert the double-claim integration test reds. Fail loudly when the check cannot run: a Redis connection error in `_acquire_lock` must propagate or return `False`, never be treated as "no lock held, proceed". Boundary and tie: a batch running exactly 60 seconds must renew the lease rather than silently lose the lock at the boundary, and two workers presenting the same token is a bug the uuid makes unrepresentable.

### Major: `in_flight` is a non-terminal state with no reset path
File: app/webhooks/delivery.py — `_claim_batch` (`row.status = "in_flight"`), `deliver`'s `while True` loop; app/webhooks/models.py — `WebhookDelivery.attempts`
What is wrong: The retry state machine lives entirely in one process's local `attempt` variable, and `attempts`/`next_attempt_at` are written only at the terminal `_finish` call, so any worker crash, redeploy or unhandled exception leaves rows in `in_flight` that no query ever selects again (R38 clause 1).
What breaks in production: Deliveries wedge permanently after any worker restart, and because `_claim_batch` filters on `status == "pending"` they are invisible to both the retry loop and the customer-facing deliveries listing's status field.
Fix: Persist each attempt instead of looping in memory — on failure, write `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and return, letting the next poll re-claim the row; add a lease column (`claimed_at`) and extend `_claim_batch`'s filter to also re-claim rows where `status == "in_flight" AND claimed_at < now - lease_timeout`. Preserve the retry budget that already works: `MAX_ATTEMPTS` must still cap total attempts at 5 across processes, not per process. Pin the allow side: a delivery that succeeds on the first attempt must reach `delivered` without ever being re-claimed. ### Major: the documented retry semantics are not the implemented ones

What is wrong: The docs promise "backoff is exponential with jitter" while `backoff_for` returns a deterministic `2**attempt` with no jitter (and `test_backoff_grows_exponentially` pins the exact values, so adding jitter would red the suite), and promise "a 4xx is permanent and we stop immediately" while `deliver` retries every non-2xx status including 400 and 404 (R29/R49).
