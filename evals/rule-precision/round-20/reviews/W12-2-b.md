### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`, lines calling `sign(...)` then `client.post(..., json=delivery.payload)`
What is wrong: `sign()` HMACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys sorted) while httpx re-serializes the same dict itself for `json=` (compact separators, insertion order), so the digest in `X-Acme-Signature` is over a byte string the receiver never sees — and `docs/webhooks.md` additionally documents the signed input as `"{timestamp}.{raw_request_body}"`, which no code path ever constructs.
What breaks in production: every customer who implements verification as documented — or as any receiver naturally would, over the raw body — rejects 100% of deliveries, and the timestamp header is unauthenticated, so an attacker who captures one request can replay it forever by rewriting `X-Acme-Timestamp` past the five-minute window the docs say is the replay defence.
Fix: make one byte string authoritative. In `send_once`, build `body = signing.serialize(delivery.payload).encode()` — the helper already in `app/webhooks/signing.py` that `json=` currently bypasses — change `sign()` to take those bytes and HMAC `f"{timestamp}.".encode() + body`, and send `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})` so the transmitted body is that exact object; update `docs/webhooks.md` only if the final wording still matches. Preserve, and do not delete to make this pass: `sort_keys=True` determinism, the `SIGNATURE_HEADER`/`TIMESTAMP_HEADER` names, the `sha256=` prefix, and the existing assertions in `tests/webhooks/test_delivery.py` that pin them. Pin the allow side with a round-trip test that captures `request.content` through `httpx.MockTransport` and asserts `signing.verify(SECRET, request.headers[TIMESTAMP_HEADER], request.content, request.headers[SIGNATURE_HEADER])` is True — a valid delivery must still verify, not merely a tightened one. Red-prove each clause by a separate executed mutation: (i) change `serialize` to `json.dumps(payload)` without `sort_keys` and observe the round-trip assertion redden on a two-key payload; (ii) drop the `f"{timestamp}."` prefix from the signed input and observe a dedicated replay test — same body, timestamp advanced by 400s — flip from reject to accept; (iii) revert `content=body` to `json=delivery.payload` and observe the round-trip assertion redden. Fail loudly where the check cannot run: if `json.dumps` raises `TypeError` on a non-serializable payload, let `send_once` raise a named `PayloadNotSerializable` rather than signing or posting a partial body — "could not serialize" must not be spelled the same as "delivered". Boundary and tie: the receiver's staleness check rejects when `now - timestamp > 300` and accepts at exactly `300`; two payloads that differ only in key order serialize to identical bytes under `sort_keys=True`, so there is no tie to break.

### Critical: signing secrets are generated from a non-cryptographic PRNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built with `random.choice`, the Mersenne Twister generator, whose internal state is recoverable from observed output and is shared across every secret minted by the same process, rather than with `secrets`, the stdlib helper for exactly this.
What breaks in production: an attacker who obtains or observes enough output from that generator can predict the signing secret of endpoints they do not own and forge signed webhook deliveries that the customer's verification accepts as authentic — the signature is the only authenticity control in the whole feature.
Fix: replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and import `secrets`, deleting the `random`, `string`, and `_ALPHABET` module members outright rather than leaving them as an unreferenced fallback (R1(d)). The behavioural difference this introduces at the call site must be stated, not left implicit: `token_urlsafe(32)` returns 43 characters over a 64-symbol alphabet including `-` and `_`, so the secret's length and character set both change, and the existing `test_new_signing_secret_has_prefix_and_length` assertion `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` must be rewritten to the new length rather than deleted — keep an assertion on length, do not drop the test that made the shape visible. Rename `SECRET_BYTES` to say what it now means (bytes of entropy, not characters) so the constant stops lying. Pin the allow side: a secret minted by the new function must still round-trip through `sign`/`verify` for a valid payload, and must still start with `whsec_` so existing stored secrets remain distinguishable. Red-prove each clause separately by execution: (i) substitute a constant return value and observe a uniqueness test over 1000 mints redden; (ii) drop the `SECRET_PREFIX` concatenation and observe the prefix assertion redden; (iii) shorten to `token_urlsafe(4)` and observe a minimum-length assertion redden. Fail loudly: `secrets` is stdlib and cannot be absent, so there is no missing-tool outcome to route — state that explicitly rather than leaving it unenumerated. Boundary and tie: two mints colliding is the failure the uniqueness assertion names; at 32 bytes it is not reachable, and the assertion must be over distinct mints from one process, which is precisely the case `random`'s shared state made likely.

### Critical: `verify()` compares signatures with `==`
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: the signature comparison is Python's short-circuiting string equality rather than `hmac.compare_digest`, so comparison time leaks the length of the matching prefix (RS1), and this is the reference implementation shipped to customers while `docs/webhooks.md` instructs them to "compare it against your own computation using a constant-time comparison".
What breaks in production: an attacker who can submit candidate signatures to any receiver built on this helper recovers the digest byte by byte from response timing and then delivers forged events; the docs simultaneously assert a property the shipped code does not have, so a customer copying it inherits the flaw believing it was reviewed.
Fix: `return hmac.compare_digest(expected, signature)`, and make `verify` take the timestamp and the raw body bytes so it verifies what the wire actually carried rather than re-deriving a fresh timestamp from `time.time()` (which today only works because the timestamp is not in the signed input at all — see the first finding). Preserve the function's public name, its boolean return, and the existing `test_verify_rejects_a_signature_made_with_another_secret` case; do not fix the timing leak by removing `verify` from the module, since it is what the docs point customers at. Pin the allow side: `verify` must still return True for a signature produced by `sign` over the same secret, timestamp and body — assert that explicitly in the same test, so a fix that always denies cannot pass. Red-prove each clause by a separate executed mutation: (i) revert to `==` and observe a test asserting `verify.__code__.co_names` contains `compare_digest`, or an equivalent grep gate, redden; (ii) flip the return to `not hmac.compare_digest(...)` and observe the accept-valid-signature assertion redden; (iii) pass a signature of a different length and confirm the function returns False rather than raising — `compare_digest` requires both operands be str-of-ASCII or bytes, and a non-ASCII `str` raises `TypeError`. Fail loudly on that last case: wrap the call so a `TypeError` from a malformed header returns a named rejection rather than a 500 — "could not compare" must not be spelled the same as "did not match", and must not be spelled the same as an unhandled crash either. Boundary and tie: a signature of the correct length but differing in the final byte must return False, and an empty-string signature must return False rather than short-circuiting to True through any falsy check.

### Critical: `list_deliveries` is not scoped to the caller's organization
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters only `WebhookDelivery.endpoint_id == endpoint_id` from the path, with no join to `WebhookEndpoint.org_id == user.org_id`, while the immediately preceding `list_webhook_endpoints` in the same file does apply exactly that tenancy predicate — the correct pattern is present in the diff and was not propagated to the new route (R3, security-relevant).
What breaks in production: any authenticated user can enumerate integer `endpoint_id` values and read another organization's delivery history — event types, event ids, attempt counts and response statuses — and `docs/webhooks.md` states this route "returns the most recent attempts for an endpoint belonging to your organization", so the asserted tenancy control does not exist.
Fix: join the tenancy predicate into the query — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and return 404 (not 403) when the endpoint exists but belongs to another org, so the route does not become an existence oracle. Enforce it at the handler that touches the data rather than only at a dependency, and audit the sibling routes in the same diff in the same change: `create_webhook_endpoint` correctly stamps `org_id=user.org_id`, `list_webhook_endpoints` correctly filters — `list_deliveries` was the only gap, and that enumeration is the finding's cross-cutting half. Pin the allow side and the deny side together, or the fix is unmeasured in the direction that gets it switched off: a test where the endpoint belongs to the caller's org must still return the rows (not an empty list), and a test where it belongs to another org must return 404 and an empty body. Red-prove each clause by a separate executed mutation: (i) delete the `org_id` filter and observe the cross-tenant test flip from 404 to 200; (ii) invert the filter to `!= user.org_id` and observe the same-org test redden; (iii) change the 404 to a 403 and observe an assertion on the status code redden. Fail loudly when the check cannot run: if `user.org_id` is absent or None the handler must raise rather than fall through to an unfiltered query — a missing tenant must not be spelled the same as "no restriction". Boundary and tie: an endpoint id belonging to the caller's org but with zero deliveries returns `200 []`, which must be distinguishable in the tests from the cross-tenant `404`.

### Critical: every endpoint's signing secret is readable from the list route
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py::list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so `GET /v1/settings/webhook-endpoints` hands back every endpoint's live secret — while `docs/webhooks.md` states "the response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: the secret that authenticates every outbound event is exposed on a routine read route to anyone holding a session or API key for the org, including read-scoped integrations and anything that logs or caches API responses, and the documented containment property that customers rely on when deciding where to store it is false (RS4 Critical — a committed artifact asserting a control over exploitable credential material that the code does not implement).
Fix: remove `signing_secret` from `to_dict()` and add a distinct `to_dict_with_secret()` used only by the 201 response of `create_webhook_endpoint`, so the secret's single exposure is structural rather than conventional; alternatively store only a hash of the secret and return the plaintext solely from the create path. Preserve what made the feature useful: the create response must still carry the plaintext secret, or customers can never configure verification — do not fix this by removing the secret from every response. Pin both sides: a test asserting `"signing_secret" not in` the list-route JSON, and a paired test asserting it IS present exactly once in the create-route JSON. Red-prove each clause by a separate executed mutation: (i) re-add the key to `to_dict()` and observe the list-route absence assertion redden; (ii) switch the create route to the secret-free `to_dict()` and observe the create-route presence assertion redden; (iii) add a third route returning `to_dict_with_secret()` and confirm a repo-wide grep gate for `to_dict_with_secret` call sites reddens — containment over one route is blind to a second call site (RT9's drift-direction clause). Fail loudly: if `signing_secret` is None or empty at create time the route must 500 with a named error rather than returning an endpoint whose secret silently cannot sign. Boundary and tie: an endpoint created before this change already has its secret exposed in whatever consumed the old list route, so the fix must be paired with rotation of every existing `webhook_endpoints.signing_secret` — a pushed secret is compromised, and removing the field does not un-publish it.

### Critical: unvalidated destination URL plus redirect-following makes the worker an SSRF proxy
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker`'s `httpx.AsyncClient(..., follow_redirects=True)`
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plaintext `http://`, admits any scheme merely beginning with those four characters (`httpx://…` passes and then fails at request time), and constrains the host not at all — `http://169.254.169.254/…`, `http://127.0.0.1:6379/…` and RFC 1918 addresses are all accepted — while `follow_redirects=True` lets even a public HTTPS endpoint redirect the request to an internal address (RS3: the unvalidated value reaches an HTTP client sink, and validation sits in the handler body rather than on the `EndpointIn` schema, which is a pydantic model already).
What breaks in production: any customer can make the delivery worker issue authenticated-looking POSTs from inside the production network to cloud metadata services and internal APIs, with `webhook_deliveries.response_status` and the persisted `response_body` acting as the exfiltration oracle; and the plaintext `http://` path sends customer event payloads and their signature across the network in clear, contradicting the docs' "Only `https://` URLs are accepted".
Fix: validate on the schema — declare `url: AnyHttpUrl` on `EndpointIn` so pydantic rejects malformed input before the handler runs — then in the handler require `parsed.scheme == "https"` (exact equality, not `startswith`), resolve the hostname and reject when any resolved address is loopback, link-local, private, reserved, or multicast, and set `follow_redirects=False` on the delivery client so a 3xx is recorded as a failed delivery rather than chased. Because DNS can be re-resolved between check and use, pin the resolved address at send time by connecting to the validated IP with the original Host header, or re-run the address check inside the delivery path; naming the check on the URL string alone leaves an attacker-schedulable interval (R51). Preserve what made the feature useful: legitimate public HTTPS endpoints on non-standard ports must still be accepted — do not fix this with a static allowlist of hostnames. Pin both sides: a test that `https://hooks.example.com/acme` is still created and still delivered to, alongside tests that `http://…`, `https://127.0.0.1/…`, `https://169.254.169.254/…` and a 302 to a private address are each rejected. Red-prove each clause by a separate executed mutation: (i) revert `==` to `startswith` and observe the `httpx://` rejection redden; (ii) delete the private-address check and observe the metadata-address rejection redden; (iii) set `follow_redirects=True` again and observe the redirect test flip from `failed_permanent` to a delivered internal response. Fail loudly: when DNS resolution fails or times out, reject the registration with a named error and mark the delivery attempt failed — "could not resolve" must not be spelled the same as "resolved to nothing suspicious". Boundary and tie: `100.64.0.0/10` (carrier-grade NAT) and IPv6 `::1`/`fc00::/7` fall on the reject side, a hostname resolving to both a public and a private address is rejected, and a host resolving to multiple public addresses is accepted only if every address passes.

### Critical: the delivery status vocabulary disagrees with the migration's CHECK constraint
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py::deliver` writing `"failed_permanent"` and `app/webhooks/models.py::STATUSES`
What is wrong: three copies of the same enum exist — the SQL CHECK, the `STATUSES` tuple in `models.py`, and the string literals in `delivery.py` — and the SQL copy spells the terminal failure `'failed'` while the other two spell it `'failed_permanent'` (R2/R3: a constant duplicated across places, with the copies already diverged in the diff that introduces them).
What breaks in production: the very first delivery that exhausts its attempts raises a CHECK-constraint IntegrityError inside `_finish`, which nothing catches, so the exception escapes `deliver`, propagates out of `asyncio.gather`, kills `run_worker` through the bare `finally`, and leaves that row and every other row in the batch stuck in `in_flight` — one unreachable customer endpoint takes down webhook delivery for all customers.
Fix: make the database the only place the vocabulary is written and derive the rest — define the enum once (a `CHECK` generated from `STATUSES`, or a Postgres enum type referenced by both), and have `delivery.py` use `m.STATUSES` members rather than bare literals. Ship a migration that widens the CHECK to the correct four values before any code writes them, since the table may already exist in an environment where the migration ran. Preserve the distinction the two spellings were reaching for: `failed_permanent` names an exhausted-retries terminal state and must remain distinguishable from a transient failure — do not collapse it to `failed` and lose that, and do not fix this by dropping the CHECK constraint, which is the thing that made the drift visible. Pin both sides: a test that inserting each of the four legitimate statuses SUCCEEDS against a real migrated database, paired with a test that inserting `'bogus'` is rejected — a fix that denies everything satisfies the deny half alone. Red-prove each clause by a separate executed mutation, executed against a real database rather than a mock: (i) revert the CHECK to the old four values and observe the `failed_permanent` insert redden; (ii) remove one member from `STATUSES` and observe a test asserting the CHECK text and `STATUSES` agree redden; (iii) re-introduce a bare literal in `delivery.py` and observe a grep gate over `status = "` redden. Fail loudly: if the migration cannot be applied the test must error with a named message rather than skipping — a suite that skips the database tests reports green while examining nothing. Boundary and tie: `in_flight` is legal in the CHECK but is not a terminal state (see the `in_flight` finding), so the agreement test must assert the full set, not merely that `failed_permanent` is a member.

### Critical: the unique index on `event_id` allows only one delivery per event across all endpoints
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: the uniqueness key is `event_id` alone, but `enqueue_for_event` in `app/webhooks/delivery.py` inserts one row per matching endpoint via `session.add_all(rows)`, so the second row for the same event violates the index.
What breaks in production: the moment an organization registers a second subscribed endpoint, every `enqueue_for_event` call raises on flush, the dispatcher's `except Exception: log.warning(...)` swallows it, and the events are permanently lost — nothing is persisted to retry from, and the only trace is a warning line.
Fix: change the index to `UNIQUE (endpoint_id, event_id)`, which expresses the actual idempotency invariant the docs describe ("delivery is at-least-once, so deduplicate on `event_id`" — per endpoint, not globally), and add the composite index `(status, next_attempt_at)` the claim query in `_claim_batch` actually needs, since `idx_webhook_deliveries_status` alone does not serve `ORDER BY next_attempt_at`. Preserve the deduplication property the single-column index was reaching for: a repeated dispatch of the same event to the same endpoint must still collapse to one row — do not fix this by deleting the unique index. Pin both sides: a test that fanning one event to two endpoints of the same org inserts two rows and both are delivered, paired with a test that enqueuing the same `(endpoint_id, event_id)` twice inserts one row and raises or upserts, not two. Red-prove each clause by a separate executed mutation against a real migrated database: (i) revert to the single-column index and observe the two-endpoint fan-out test redden with an IntegrityError; (ii) drop the unique index entirely and observe the duplicate-enqueue test redden with a row count of 2; (iii) drop the `(status, next_attempt_at)` index and observe an `EXPLAIN`-based or timing-bounded assertion on the claim query redden. Fail loudly: `enqueue_for_event` must let an IntegrityError it did not expect propagate with a named message rather than returning a row count — see the dispatcher-swallow finding, because these two defects compose into silent total loss. Boundary and tie: an event fanned to two endpoints produces two rows with identical `created_at`, which is exactly the tie the `list_deliveries` ordering does not break.

### Critical: `time.sleep()` blocks the event loop inside an async delivery worker
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)` at the bottom of the `while True` loop
What is wrong: `deliver` is `async def` and is run under `asyncio.gather`, but the retry backoff uses the blocking `time.sleep`, and the retry loop is in-process at all — the change already contains the scheduled-retry machinery it reimplements: `backoff_for()`, the `attempts` column, the `next_attempt_at` column, and the `_claim_batch` filter `next_attempt_at <= now` that exists for no other purpose.
What breaks in production: one failing endpoint freezes the entire event loop for 2+4+8+16 = 30 seconds per delivery, and because `time.sleep` blocks the single thread the 100 deliveries gathered in a batch serialize rather than overlap — the worker's throughput collapses to roughly two deliveries a minute, and any other coroutine sharing the process (including the redis lock's own expiry refresh) is frozen with it.
Fix: delete the `while True` loop from `deliver` — attempt once, and on a retryable failure write `attempts = attempt`, `next_attempt_at = now + backoff_for(attempt)`, `status = "pending"` and return, letting `_claim_batch` pick the row up when it is due; that is the path the schema was built for, and it also makes retries survive a worker restart, which the in-process loop cannot (R1(e): the hazard the dedup must also address). Where a sleep is still needed, use `await asyncio.sleep`. Preserve the retry semantics the loop provided: at most `MAX_ATTEMPTS` attempts with the same exponential schedule, and the `failed_permanent` terminal state at exhaustion — do not fix the blocking call by removing retries. Pin both sides: a test that a delivery failing once and succeeding on the second claim ends `delivered` with `attempts == 2`, paired with a test that a delivery failing `MAX_ATTEMPTS` times ends `failed_permanent` and is not re-claimed. Red-prove each clause by a separate executed mutation: (i) reinstate `time.sleep` and observe an assertion that a batch of two failing deliveries completes within a bounded wall-clock redden; (ii) drop the `next_attempt_at` write and observe the second-claim test redden by re-claiming immediately; (iii) drop the `attempts` write and observe the exhaustion test redden by looping forever — bound the loop in the test so this mutation reddens rather than hanging. Fail loudly: if `_finish` cannot write the row (the row was deleted, the connection dropped), raise a named error rather than returning, so a delivery whose outcome was never recorded is not spelled the same as one that succeeded. Boundary and tie: a row whose `next_attempt_at` is exactly `now` is claimed (the filter is `<=`), and `attempt == MAX_ATTEMPTS` is terminal while `attempt == MAX_ATTEMPTS - 1` schedules one more.

### Major: `in_flight` is a non-terminal state with no reset path
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; only `_finish` leaves that state
What is wrong: rows enter `in_flight` at claim time and exit only through `_finish` on the success or exhaustion path inside `deliver`, while `_claim_batch` selects exclusively `status == "pending"` — so a worker restart, a deploy, an OOM kill, or any exception `deliver` does not catch (it catches only `httpx.HTTPError`) strands the row permanently (R38 mode 1: an async transition with no failure-exit and no bounded lease).
What breaks in production: every deploy silently drops the in-flight batch — up to 100 events per restart — and those rows are invisible to both the retry path and any "failed deliveries" view, so the loss is not merely unrecovered but unobservable.
Fix: give the claim a lease instead of a bare status flag — add a `claimed_at TIMESTAMPTZ` column, set it alongside `status = 'in_flight'`, and add a reaper that returns rows with `status = 'in_flight' AND claimed_at < now() - interval '5 minutes'` to `pending` with `attempts` incremented, so the exit is explicit and bounded rather than dependent on the process that claimed them surviving. Wrap `deliver`'s body in `except Exception` that routes to `_finish(..., "pending" or "failed_permanent")` so a non-HTTP exception also exits the transient state. Preserve the property `in_flight` exists for: a row being worked must not be claimed by a second worker — do not fix this by deleting the state, and do not set the lease so short that a slow-but-live delivery is double-sent. Pin both sides: a test that a row claimed and left stranded is returned to `pending` by the reaper after the lease expires, paired with a test that a row claimed 10 seconds ago is NOT reclaimed while its worker is still running. Red-prove each clause by a separate executed mutation: (i) delete the reaper and observe the stranded-row test redden; (ii) set the lease to zero and observe the not-yet-expired test redden by double-claiming; (iii) narrow the `except` back to `httpx.HTTPError` and observe a test that raises `ValueError` inside `send_once` leave the row `in_flight`. Fail loudly: if the reaper itself cannot run — the column is missing, the connection fails — it must log at error and exit non-zero rather than completing quietly, since "reaped nothing" and "examined nothing" are the same log line today. Boundary and tie: a row whose `claimed_at` is exactly the lease boundary is reclaimed (`<=`), and a row reclaimed at `attempts == MAX_ATTEMPTS` goes to `failed_permanent` rather than back to `pending`.

### Major: the dispatch lock is neither atomic nor crash-safe, and the worker dies on the first exception
File: `app/webhooks/delivery.py` — `_acquire_lock` and `run_worker`
What is wrong: `_acquire_lock` does a `get` then a separate `set` then a separate `expire`, so two workers can both observe the key absent and both proceed (a TOCTOU race), and a crash between `set` and `expire` leaves a key with no TTL; separately, `run_worker`'s `try/finally` deletes the lock but re-raises, and `asyncio.gather` without `return_exceptions=True` propagates the first failure out of the loop, so the worker exits permanently on any single bad delivery — and `if not batch:` after the `finally` references a name that is unbound if `_claim_batch` raised.
What breaks in production: two overlapping workers double-deliver every event in the racing window (the claim query has no `FOR UPDATE SKIP LOCKED` either, so both transactions can select the same pending rows), and a single unexpected exception both stops all webhook delivery indefinitely and, in the `set`-without-`expire` case, wedges the lock so a restarted worker never acquires it.
Fix: replace the three calls with one atomic `SET key value NX EX 60` (`redis_client.set(LOCK_KEY, token, nx=True, ex=60)`) and release with a compare-and-delete on a per-worker token so a worker cannot delete a lock a successor acquired after its lease expired; add `FOR UPDATE SKIP LOCKED` to `_claim_batch`'s query so correctness does not rest on the lock alone; wrap the loop body in `try/except Exception: log.exception(...)` and `continue`, initialise `batch = []` before the `try`, and pass `return_exceptions=True` to `gather` with per-result logging. Preserve mutual exclusion: exactly one worker must claim a batch at a time — do not fix the crash by dropping the lock. Pin both sides: a test that a second `_acquire_lock` while the first holds returns False, paired with a test that after release, or after the TTL, the next acquire returns True — a lock that never grants satisfies the first alone. Red-prove each clause by a separate executed mutation: (i) revert to `get`-then-`set` and observe a concurrency test issuing two acquires against a real redis (or a fake honouring `nx`) redden; (ii) drop the `ex=60` and observe a test asserting `ttl(LOCK_KEY) > 0` redden; (iii) remove the `except Exception` around the loop body and observe a test that raises inside `deliver` leave `run_worker` terminated rather than iterating again. Fail loudly: if redis is unreachable, `_acquire_lock` must raise or return False with an error-level log naming the outage rather than returning True — an unavailable lock must never be spelled the same as an uncontended one. Boundary and tie: two workers acquiring at exactly the moment the TTL expires must resolve to one holder, which is what the token compare-and-delete decides; and `poll_interval` sleeping only when `batch` is empty must not busy-loop when `_claim_batch` raises every iteration.

### Major: claimed rows are used after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` returns `rows` from inside `with session_scope()`, consumed by `deliver` and `send_once`; `deliver` likewise returns `endpoint` out of its own `session_scope`
What is wrong: the ORM instances are built and mutated inside the session context and then handed out after it exits, so `deliver`'s reads of `delivery.attempts`, `delivery.id` and `delivery.payload`, and `send_once`'s reads of `endpoint.url` and `endpoint.signing_secret`, all happen on detached instances — under SQLAlchemy's default `expire_on_commit=True` every one of those attributes is expired at commit and raises `DetachedInstanceError` on access.
