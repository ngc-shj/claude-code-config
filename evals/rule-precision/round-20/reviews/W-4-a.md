### Critical: the timestamp header is not covered by the signature, so the documented replay window is unenforceable (R49, R29)

Red-prove separately, by execution: (i) delete the `f"{timestamp}."` prefix from `sign` — the tampered-timestamp test must go red; (ii) change `verify` to ignore its timestamp argument — the same test must go red for the verifier. Fail loudly: a non-numeric or absent timestamp must raise from `verify()` rather than defaulting to `0` or to now. Boundary and tie: state which side the edge falls on — a request whose timestamp is exactly `now - 300s` is ACCEPTED, `now - 301s` rejected, and two requests sharing one timestamp are both valid (the timestamp is not an idempotency key; `event_id` is).

### Critical: signature comparison is not constant time (RS1)

### Critical: the distributed lock is a non-atomic check-then-set and is released by whoever finishes first
File: app/webhooks/delivery.py — `_acquire_lock` and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` does a `get` followed by a separate `set` and `expire`, so two workers can both observe an empty key and both proceed, and the release is an unconditional `delete` of a key the caller may no longer own after the 60-second TTL has elapsed under a batch that can legitimately run far longer.
What breaks in production: two or more workers claim overlapping batches and POST the same events to customer endpoints repeatedly, and because each release deletes the other's lock the mutual-exclusion property is gone permanently rather than for one window — customers see duplicate invoice events with no bound on the duplication factor.
Fix: acquire with a single atomic command carrying a unique owner token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` where `token = secrets.token_hex(16)` — and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only delete its own lock; renew the TTL periodically while the batch runs, or bound the batch's wall-clock to less than the TTL. Preserve, do not delete: the lock must still be released promptly on the success path — do not "fix" this by relying on TTL expiry alone, which would idle the worker for a full TTL after every batch. Allow side to pin: a single worker acquires, processes, releases, and the next `_acquire_lock` succeeds immediately; deny side: with the lock held, a second `_acquire_lock` returns `False`, and a second worker's release with a different token leaves the first worker's key intact. Red-prove separately, by execution: (i) replace the `nx=True` set with the old get-then-set and drive two concurrent acquires against a fake Redis that interleaves at the await point — the mutual-exclusion assertion goes red; (ii) replace the compare-and-delete with a bare `delete` — the foreign-release assertion goes red; (iii) drop the `ex=` argument — the crash-recovery test that asserts the key expires goes red (bound the test's wait so it fails rather than hangs). Fail loudly: if Redis is unreachable, `_acquire_lock` must raise or return `False` and the worker must NOT process a batch unlocked — an unavailable coordinator is a refusal, not a green light. Boundary and tie: a TTL that expires at exactly the moment the owner tries to release is the tie case, and the compare-and-delete makes it a no-op rather than a foreign delete; `LOCK_TTL_SECONDS` must exceed the worst-case batch time (`BATCH_SIZE` × `REQUEST_TIMEOUT`) or be renewed, and that relation belongs in a comment beside the constant.
