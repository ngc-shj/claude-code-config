### Critical: signature is computed over re-serialized JSON, not over the bytes actually sent
File: `app/webhooks/signing.py` — `sign()` / `serialize()`, consumed at `app/webhooks/delivery.py:send_once`
What is wrong: `sign()` MACs `json.dumps(payload, sort_keys=True)` (default `", "` / `": "` separators, keys sorted) while `send_once` transmits `client.post(..., json=delivery.payload)`, which httpx encodes itself with compact separators and insertion order, so the signed bytes and the wire bytes differ for essentially every payload.
What breaks in production: every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest, so 100% of deliveries are rejected as forged and the feature is dead on arrival for all integrators — the classic R40 same-team-owns-both-sides failure, invisible here because no test feeds actual producer output through an actual consumer verification.
Fix: make one byte string authoritative and use it for both MAC and transport. In `signing.py` add `def canonical_body(payload) -> bytes: return json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()`; change `sign(secret, body: bytes)` to MAC that exact `bytes`; in `send_once` build `body = canonical_body(delivery.payload)` once, pass `content=body` (not `json=`) with the explicit `Content-Type: application/json` header already present, and pass the same `body` to `sign`. Delete `serialize()` rather than keeping it as a second spelling of the same operation (R1 clause d) — the whole defect is two encoders for one concept. Preserve: the payload's visible JSON content and the existing `sha256=<hex>` header format must not change, and `verify()` must keep accepting a signature produced by `sign()`. Allow side to pin: a round-trip test that runs a real `httpx.MockTransport`, captures `request.content` verbatim, and asserts `hmac.new(SECRET.encode(), captured_body, sha256).hexdigest()` equals the hex in the captured signature header — that must stay green (this is the assertion the current suite lacks). Red-proofs, one mutation each, applied singly to a scratch copy and executed: (i) drop `separators=(",", ":")` from `canonical_body` → the raw-body assertion reddens naming the digest comparison; (ii) drop `sort_keys=True` with a two-key out-of-order fixture `{"b":2,"a":1}` → the same assertion reddens; (iii) revert `content=body` to `json=payload` → reddens. Fail-loud: if `payload` is not JSON-serializable, `canonical_body` must raise rather than fall back to `str(payload)` — "could not canonicalize" must not be spelled the same as "signed successfully"; `_finish` the delivery `failed_permanent` with that detail. Boundary/tie: two payloads that canonicalize to the identical byte string legitimately produce the identical signature — that is intended and must not be treated as a replay, because replay is decided by the timestamp check below, not by digest uniqueness.

### Critical: the timestamp header is not covered by the HMAC, so the documented replay window is forgeable
File: `app/webhooks/signing.py` — `sign()`, and `docs/webhooks.md` "Verifying the signature"
What is wrong: the doc instructs receivers to MAC `"{timestamp}.{raw_request_body}"` and to reject timestamps older than five minutes, but `sign()` MACs the body alone and returns an unauthenticated `timestamp` alongside, so the value the receiver's freshness check reads is attacker-controlled.
What breaks in production: an attacker who captures one signed request (from a proxy, a customer's access log, or the `log.info("POST %s headers=%s")` line added in `delivery.py:send_once`) can replay it forever by rewriting `X-Acme-Timestamp` to `now`, since the signature still verifies — the five-minute window documented as "what stops a captured request from being replayed" stops nothing (R49: a claim stronger than the implementation).
Fix: bind the timestamp into the MAC. `sign(secret, body: bytes)` computes `timestamp = str(int(time.time()))` and `mac = hmac.new(secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256)`; `verify(secret, timestamp, body, signature)` takes the received timestamp, recomputes over `"{timestamp}.{body}"`, and additionally rejects when `abs(now - int(timestamp)) > TOLERANCE_SECONDS` with `TOLERANCE_SECONDS = 300` defined once in `signing.py` and cited by name in `docs/webhooks.md` (R2: the five minutes currently exists only as prose). Preserve: `sign()` must keep returning `(timestamp, signature)` in that order and the `sha256=` prefix, so `SIGNATURE_HEADER`/`TIMESTAMP_HEADER` wire format is unchanged. Allow side to pin: a signature produced 299 seconds ago still verifies. Red-proofs, one per clause, executed separately: (i) remove `f"{timestamp}."` from the MAC input → a test that verifies a signature against a *different* timestamp must go from red to green, so assert it stays red; (ii) delete the tolerance check → a fixture with `timestamp = now - 3600` must fail; (iii) mutate `TOLERANCE_SECONDS` to `0` → the 299-second allow fixture reddens, proving the allow fixture is boundary-adjacent and not a distant case. Fail-loud: a non-integer, absent, or out-of-range `timestamp` must return `False` from `verify` by an explicit branch that names "unparseable timestamp", never by `int()` raising into a caller that treats an exception as "not our request". Boundary/tie: state the boundary explicitly — a timestamp exactly `TOLERANCE_SECONDS` old is ACCEPTED (`>` not `>=`), and two requests sharing one timestamp are both valid, because the freshness check is not an idempotency guard.

### Critical: signing secrets are generated from `random`, not a CSPRNG
File: `app/webhooks/signing.py` — `new_signing_secret()`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, which is fully reconstructible from ~624 observed outputs and is seeded predictably per process.
What breaks in production: an attacker who legitimately registers a handful of endpoints in the same worker process recovers the generator state and predicts other tenants' signing secrets, letting them mint valid `X-Acme-Signature` headers and inject forged `invoice.paid` events into other customers' systems — the duplicated behaviour here is a security control, which is exactly R1's Critical escalation.
Fix: replace the body with `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and import `secrets`; delete `random`, `string`, and `_ALPHABET` outright rather than leaving them as an unreferenced fallback (R1 clause d). Behavioural differences to state, per R1 clause a: the secret's character set widens to `[A-Za-z0-9_-]` and its *length* becomes ~43 chars for `SECRET_BYTES = 32`, so `SECRET_BYTES` finally means bytes rather than characters as its name always claimed; that is a required change, not an accidental one, because the existing test `len(secret) == len(SECRET_PREFIX) + SECRET_BYTES` encodes the wrong meaning and must be rewritten to assert `>= 32` bytes of entropy via `len(secret) - len(SECRET_PREFIX) >= 40`. Preserve: `whsec_` prefix, so existing customer tooling that pattern-matches the prefix keeps working; already-issued secrets keep validating (this changes generation only, not verification). Allow side to pin: `new_signing_secret()` still returns a value that `sign`/`verify` round-trip successfully, and still starts with `SECRET_PREFIX`. Red-proofs, executed singly: (i) revert to `random.choice` after `random.seed(0)` in the test process → an added test asserting two secrets generated after identical `random.seed(0)` calls DIFFER goes red, which is the only mutation that discriminates a CSPRNG from `random` (a length or prefix assertion cannot, and that is why the shipped tests miss this); (ii) drop the `SECRET_PREFIX` concatenation → the prefix assertion reddens; (iii) set `SECRET_BYTES = 4` → the entropy-length assertion reddens. Fail-loud: none of these paths may swallow an exception — if `secrets` is unavailable the import fails at module load, which is the correct loud failure. Boundary/tie: two calls returning the identical string is a hard failure, not a tolerable collision; assert distinctness across 1000 generations.

### Critical: `list_deliveries` is not scoped to the caller's organization (IDOR)
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters on `WebhookDelivery.endpoint_id == endpoint_id` only, while its sibling `list_webhook_endpoints` three lines above filters on `WebhookEndpoint.org_id == user.org_id` — the org predicate was propagated to one new route and not the other (R3, security-relevant).
What breaks in production: any authenticated user can enumerate integer `endpoint_id` values and read every other tenant's delivery rows, and `WebhookDelivery.to_dict` returns `event_id`, `event_type`, `status`, `attempts` and `response_status` for each — a cross-tenant data leak reachable with a `for id in range(1, 10000)` loop.
Fix: join through the endpoint and scope by org, and distinguish "not yours" from "does not exist" only in the direction that leaks nothing: `session.query(m.WebhookDelivery).join(m.WebhookEndpoint).filter(m.WebhookEndpoint.id == endpoint_id, m.WebhookEndpoint.org_id == user.org_id, ...)`; when the endpoint does not exist *or* belongs to another org, raise `HTTPException(404)` — matching the 404-on-absent pattern the same file already establishes in `get_profile`, which is the shared path this new code should reuse rather than reinvent. Preserve: the ordering, the `limit`, and the `to_dict` response shape must not change; the owner of the endpoint must still see exactly the rows they see today. Allow side to pin (Remedy Floor clause 1 — without this, a fix that 404s everything satisfies every other clause): a test where the caller's org owns `endpoint_id` asserts 200 and a non-empty list containing the seeded delivery id. Deny side per RT8: the cross-org test asserts 404 AND that the response body contains no delivery ids — status alone is vacuous. Red-proofs, one mutation each, executed: (i) delete the `org_id` conjunct → the cross-org test reddens on the body assertion, not merely the status; (ii) delete the `join` → the owner test reddens; (iii) change the 404 to a 403 → the deny test reddens on status, proving it is not merely observing an empty list. Fail-loud: an unauthenticated or org-less principal must be rejected by `current_user` before the query runs; if `user.org_id` is `None` the handler raises rather than querying with `org_id IS NULL`, so "no org resolved" cannot read the same as "no rows". Boundary/tie: an endpoint that was soft-deleted or set `active=False` still belongs to its org and its deliveries remain visible to that org — deactivation is not a scope change.

### Critical: user-supplied endpoint URLs are fetched with redirects followed — server-side request forgery
File: `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`) and `send_once`; destination accepted at `app/api/routes/settings.py:create_webhook_endpoint`
What is wrong: `create_webhook_endpoint` accepts any URL whose scheme starts with `http` and whose `netloc` is non-empty, and the worker then POSTs to it from inside the production network with `follow_redirects=True` and no host, IP-range, or port restriction.
What breaks in production: a customer registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://internal-admin.svc.cluster.local/`, and the response status and body are captured into `webhook_deliveries.response_body` and readable back through `GET /webhook-endpoints/{id}/deliveries` — cloud instance credentials and internal service responses are exfiltrated through a feature that is doing exactly what it was built to do; `follow_redirects=True` additionally defeats any allowlist applied only at registration time, because a public host can 302 to a private one.
Fix: validate the destination at the boundary and again at connect time, since only the second survives DNS rebinding and redirects. (1) In `create_webhook_endpoint`, require `parsed.scheme == "https"` (exact equality, not `startswith`) and reject when `parsed.hostname` resolves to any address in a private, loopback, link-local, or unique-local range (`ipaddress.ip_address(...).is_private or .is_loopback or .is_link_local or .is_reserved`), and when `parsed.port` is set to anything other than 443. (2) Set `follow_redirects=False` on the `httpx.AsyncClient` and treat a 3xx as a permanent failure with a detail naming the redirect target, so a redirect cannot smuggle the request past step (1). (3) Re-run the IP check in `send_once` against the address actually connected to, via an `httpx` transport that pins the resolved address. Preserve: legitimate public HTTPS endpoints on port 443, including those behind CDNs with rotating addresses, must still receive deliveries — that is the behaviour the fix must not delete. Allow side to pin: a delivery to `https://hooks.example.com/acme` resolving to a public address still returns 200 and marks `delivered`. Red-proofs, one per clause, executed separately: (i) revert `parsed.scheme == "https"` to `startswith("http")` → a registration test posting `http://hooks.example.com/` must red; (ii) delete the private-range check → a registration test posting `https://127.0.0.1/` must red; (iii) restore `follow_redirects=True` → a `MockTransport` test whose handler returns a 302 to `http://169.254.169.254/` must red on the assertion that the delivery is `failed_permanent` and that no second request was issued. Fail-loud: DNS resolution failure, a hostname that resolves to zero addresses, or an `ipaddress` parse error must all reject the registration with a message naming the failure — "could not check the host" must not be spelled the same as "host is safe". Boundary/tie: state where the boundary falls — a hostname resolving to BOTH a public and a private address is rejected (any-private, not all-private), and a URL with an explicit `:443` is accepted while `:8443` is not.

### Critical: `_finish` writes a status the migration's CHECK constraint forbids
File: `migrations/0042_webhook_delivery.sql` — `status TEXT NOT NULL CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))`, against `app/webhooks/delivery.py:_finish` and `app/webhooks/models.py:STATUSES`
What is wrong: the Python side uses `failed_permanent` (declared in `models.STATUSES`, written by `_finish`) while the SQL CHECK enumerates `failed` — the enum spelling diverges across the producer/strict-consumer boundary R40 governs, and the schema is the strict consumer here.
What breaks in production: every delivery that exhausts `MAX_ATTEMPTS` raises a `CheckViolation` inside `_finish`'s `session_scope`, the transaction rolls back, the row is left at `in_flight` forever, and the exception escapes `deliver` into an un-guarded `asyncio.gather` — so the first permanently-failing endpoint both loses its own terminal record and takes down the whole worker loop.
Fix: make one definition authoritative and derive the other from it. Keep `STATUSES` in `models.py` as the single source, correct the migration to `CHECK (status IN ('pending','in_flight','delivered','failed_permanent'))`, and add a test that asserts the constraint's accepted set equals `models.STATUSES` by reading `pg_get_constraintdef` from a migrated test database — a literal list re-typed into the test is a second copy of the same defect (R2). Preserve: the three statuses that already agree keep their exact spellings, since any rename would invalidate rows written by an earlier deploy. Allow side to pin: inserting each of the four members of `STATUSES` succeeds. Red-proofs, executed one at a time against a real migrated database: (i) revert the migration literal to `'failed'` → the constraint-equals-`STATUSES` test reddens naming the missing member; (ii) append a fifth member to `STATUSES` only → the same test reddens from the other direction, proving it is not asserting a subset; (iii) insert `'nonsense'` → the insert must red, proving the CHECK is present at all and the test is not passing against an unconstrained column. Fail-loud: if the test cannot reach a migrated database, it must ERROR, not skip — a skipped cross-boundary test reports "examined nothing" as "found nothing", which is precisely how this defect shipped. Boundary/tie: enumerate what happens to rows already stuck at `in_flight` when this lands — the fix must ship a backfill (`UPDATE webhook_deliveries SET status='pending' WHERE status='in_flight' AND updated_at < now() - interval '1 hour'`) or those deliveries stay lost after the constraint is corrected.

### Critical: `UNIQUE (event_id)` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id);`, against `app/webhooks/delivery.py:enqueue_for_event`
What is wrong: `enqueue_for_event` builds one `WebhookDelivery` row per matching endpoint, all carrying the same `event_id`, but the unique index permits exactly one row per `event_id` across the whole table.
What breaks in production: as soon as any organization has two active subscribed endpoints, the `session.add_all` flush raises a unique violation, the entire `session_scope` rolls back, and NO deliveries are enqueued for that event — not one-of-two, zero — while `dispatcher.dispatch` swallows the exception at `except Exception as exc: log.warning(...)` so the event is silently never delivered to anyone.
Fix: change the index to `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (endpoint_id, event_id);` — that is the constraint the code actually needs, and it is also the one that makes the docs' "delivery is at-least-once, so deduplicate on `event_id`" implementable, since it gives per-endpoint idempotency on re-enqueue. Preserve: enqueue must remain idempotent for a retried `dispatch` of the same event to the same endpoint — do not solve this by dropping the unique index entirely, which would trade a hard failure for silent duplicate deliveries. Allow side to pin: enqueuing one event for two endpoints of the same org creates exactly two rows and both are claimable. Red-proofs, one per clause, executed against a migrated database: (i) revert to the single-column index → a test enqueuing one event across two endpoints reddens on the row-count assertion (expects 2, gets a violation); (ii) drop the index altogether → a test calling `enqueue_for_event` twice with the same `(endpoint_id, event_id)` reddens on the assertion that the second call adds no row (it must use `ON CONFLICT DO NOTHING` / `INSERT ... ON CONFLICT` semantics rather than relying on the exception); (iii) enqueue the same `event_id` for endpoints in two DIFFERENT orgs → must succeed, proving the uniqueness is not accidentally org-scoped. Fail-loud: `enqueue_for_event` currently returns `len(rows)` computed BEFORE the flush, so it reports success for rows that were never written — make it flush inside the scope and return the count of rows actually persisted, so "insert rejected" cannot be reported as "enqueued N". Boundary/tie: an endpoint whose `event_types` is `[]` and one that names the type explicitly both match the same event and must produce one row each, not one row total.

### Critical: `time.sleep` inside a coroutine blocks the event loop, and the retry loop bypasses the queue's own scheduling
File: `app/webhooks/delivery.py` — `deliver`, line `time.sleep(delay)`
What is wrong: `deliver` is `async` and is run under `asyncio.gather`, but it retries with the blocking `time.sleep`, and it retries in-process in a `while True` loop instead of rescheduling via the `next_attempt_at` column and `backoff_for` that `_claim_batch` already selects on.
What breaks in production: one failing endpoint stalls the entire single-threaded worker for 2+4+8+16 = 30 seconds during which no other delivery in the gathered batch of up to `BATCH_SIZE = 100` makes progress; the 60-second Redis lock TTL expires mid-batch, a second worker claims the same rows, and a batch with several failing endpoints exceeds the loop's ability to make forward progress at all. The queue's retry machinery — `next_attempt_at`, `backoff_for`, the `status == "pending"` re-claim — is a shared path this in-process loop reimplements (R1), so `next_attempt_at` is written exactly once at enqueue and never advanced.
Fix: delete the `while True` loop and make `deliver` a single attempt. On a 2xx call `_finish(..., "delivered", ...)`. On a retryable failure (connection error, timeout, 5xx, 429) and `attempt < MAX_ATTEMPTS`, write `status="pending"`, `attempts=attempt`, `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` and return — the existing `_claim_batch` filter picks it back up when due. On `attempt >= MAX_ATTEMPTS`, `_finish(..., "failed_permanent", ...)`. Remove the `time` import so the blocking call cannot be reintroduced silently. Add jitter as `backoff_for` already promises in `docs/webhooks.md` ("exponential with jitter"), which the current implementation does not implement: `timedelta(seconds=BASE_DELAY_SECONDS**attempt * (1 + random.SystemRandom().uniform(0, 0.25)))`. Preserve: the total attempt budget stays `MAX_ATTEMPTS = 5` and the base schedule stays ~2/4/8/16s, so the documented customer-facing contract is unchanged; deliveries must still be attempted promptly the first time (`next_attempt_at` at enqueue stays "now"). Allow side to pin: a delivery whose first attempt returns 200 completes with `attempts == 1` and status `delivered`, with no sleep of any kind on that path. Red-proofs, one mutation each, executed under a test-level timeout so a hang surfaces as a failure rather than a wedge: (i) reintroduce `time.sleep(delay)` → a test asserting the coroutine yields (two concurrent `deliver` calls interleave, measured by an ordering list) reddens; (ii) delete the `next_attempt_at` advance → a test asserting the row's `next_attempt_at` moved forward by at least `BASE_DELAY_SECONDS**attempt` reddens; (iii) change `attempt >= MAX_ATTEMPTS` to `>` → a test driving six consecutive failures and asserting exactly five requests were issued reddens. Fail-loud: an exception that is neither `httpx.HTTPError` nor a 2xx/retryable status must not fall through the function — catch `Exception`, `_finish` the row `failed_permanent` with the exception text, and re-raise nothing, so an unclassified error is recorded rather than silently leaving the row `in_flight`. Boundary/tie: state the boundary — attempt number 5 is the LAST attempt (not the last retry), and a delivery whose `next_attempt_at` is exactly `now` is claimable (`<=`, matching the existing filter); two deliveries with the identical `next_attempt_at` may be claimed in either order.

### Critical: `_claim_batch` returns ORM instances after its session has closed
File: `app/webhooks/delivery.py` — `_claim_batch`, and its consumers `deliver` / `send_once`
What is wrong: the rows are loaded and mutated inside `with session_scope() as session:` and then returned out of that block, so by the time `deliver` reads `delivery.attempts`, `delivery.payload` and `delivery.id` the instances are detached and (with SQLAlchemy's default `expire_on_commit=True`) every attribute access raises `DetachedInstanceError`.
What breaks in production: the very first non-empty batch raises inside `asyncio.gather`, and because `run_worker`'s `try` block has only a `finally` and its `while True` has no handler at all, the exception propagates out of `run_worker` and the delivery worker dies permanently — every webhook stops, and the only symptom is a process that exited.
Fix: stop passing ORM identities across session boundaries. Have `_claim_batch` return plain data — a list of frozen dataclasses or dicts carrying `(delivery_id, endpoint_id, event_id, attempts, payload, url, signing_secret)` materialised inside the session by joining `WebhookEndpoint` — and have `deliver`/`send_once` take that value object, which also removes the second `session.get(m.WebhookEndpoint, ...)` round trip in `deliver`. Wrap the batch body in `run_worker` with `except Exception: log.exception(...)` so no single row can terminate the loop, and use `asyncio.gather(..., return_exceptions=True)` so one failing coroutine does not cancel its siblings. Preserve: the claim must remain a claim — rows are still flipped to `in_flight` in the same transaction that reads them, so a second worker cannot re-select them. Allow side to pin: a batch of two claimable rows still yields two delivery attempts and two terminal rows; the worker loop is still running afterwards (assert it processes a second batch). Red-proofs, one per clause, executed: (i) revert `_claim_batch` to returning ORM rows → a test that reads `payload` from the returned value after the scope exits reddens with `DetachedInstanceError`; (ii) remove the `except Exception` in `run_worker` and inject a row whose `endpoint_id` points at a deleted endpoint → a test asserting the worker survives and processes the next batch reddens; (iii) drop `return_exceptions=True` and fail one of two coroutines → a test asserting the other still reached a terminal status reddens. Fail-loud: `deliver` must handle the endpoint being absent explicitly (`session.get` returning `None`) by finishing the delivery `failed_permanent` with detail `"endpoint deleted"`, rather than raising `AttributeError` on `endpoint.signing_secret` — "endpoint gone" and "delivery succeeded" must not be indistinguishable non-events. Boundary/tie: an empty batch must sleep `poll_interval` and continue; note that the current `if not batch:` line sits AFTER the `finally` that releases the lock, so a claim of exactly zero rows still takes and releases the lock every iteration — keep that behaviour explicit rather than accidental.

### Critical: the tests cannot fail for the signing defects they advertise
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`, `test_verify_accepts_signature_produced_by_sign`, `test_new_signing_secret_has_prefix_and_length`, and the `FakeEndpoint`/`FakeDelivery` doubles
What is wrong: three separate blindnesses — the send test asserts only that the signature header *starts with* `sha256=` and never recomputes the MAC over `captured["body"]`, so the body/signature divergence above is invisible; `test_verify_accepts_signature_produced_by_sign` compares `sign(x)` against `verify`'s internal `sign(x)`, an identity true under every implementation including one that ignores the payload entirely (RT1 clause c/d); and the secret test asserts prefix and length, which `random.choice` satisfies exactly as well as a CSPRNG does, so no mutation of the generator can redden it (RT7 shape g(ii) — the proof has no delta on the real subject).
What breaks in production: all four Critical crypto defects above ship behind a green suite that names them — a reviewer reading "posts the signed payload" and "verify accepts signature produced by sign" reasonably concludes signing is covered, which is RT5's "the test name lies" escalated to Critical because the primitive is a security control.
Fix: replace each tautology with an independently-written expected value. (1) In `test_send_once_posts_the_signed_payload`, compute `expected = "sha256=" + hmac.new(SECRET.encode(), f"{captured['headers'][signing.TIMESTAMP_HEADER]}.".encode() + captured["body"], hashlib.sha256).hexdigest()` from the captured raw bytes and assert equality — hand-written in the test, never by calling `signing.sign`. (2) Split the verify test: keep the round-trip but ADD `assert not signing.verify(SECRET, {"a": 2}, signature_for({"a": 1}))`, which is the assertion that pins payload binding and which the current suite lacks entirely. (3) Replace the length assertion with the seeded-generator distinctness assertion described in the CSPRNG fix. (4) Bind `FakeEndpoint`/`FakeDelivery` to the real `WebhookEndpoint`/`WebhookDelivery` types (construct the real model instances, unsaved) so a schema change fails the test rather than passing over a short double (RT1 clause a) — as written `FakeEndpoint` has no `id`, which is why the `deliver` path could never be tested with it. Preserve: the existing green assertions on status code, `content-type`, and the parsed `type` field stay — the fix adds oracles, it does not delete the ones that work. Allow side to pin: with all four Critical fixes applied, every one of these tests passes on unmutated code. Red-proofs, one mutation each, applied singly to a scratch copy created with `mktemp -d` and removed afterwards, with the runner pointed at the copy so the original is not what runs: (i) `sort_keys=True` → `False` in the canonicaliser reddens (1); (ii) make `sign` ignore its `payload` argument reddens (2); (iii) `secrets.token_urlsafe` → `random.choice` reddens (3); (iv) remove a column from `WebhookDelivery` reddens (4). Verify each mutant actually differs (`cmp` exits non-zero) before reading the colour. Fail-loud: if `pytest-asyncio` is not configured the two `@pytest.mark.asyncio` tests currently SKIP silently — add a strict asyncio mode setting so an unconfigured plugin errors the run; a skipped signing test and a passing one must not look the same in CI. Boundary/tie: the equality assertion compares the full hex digest, not a prefix — a comparator that accepts a prefix is how a truncated MAC would survive.

### Major: the signing secret is returned by the list endpoint, contradicting the documented control
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, reached by `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: `to_dict` unconditionally includes `signing_secret`, and `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards" — a control that is claimed and not implemented (R49).

### Major: the Redis lock is a non-atomic check-then-set, and is deleted unconditionally
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `_acquire_lock` performs GET, then SET, then EXPIRE as three separate round trips, so two workers can both observe an empty key and both proceed (R5's read-then-write TOCTOU); and the `finally` deletes `LOCK_KEY` by name with no ownership token, so a worker that overran the 60-second TTL deletes a lock a *different* worker now holds.
What breaks in production: two workers claim overlapping batches and POST the same event to the customer twice or more — tolerable under the documented at-least-once contract only because the docs say to deduplicate, but the same race also has both workers flipping rows to `in_flight` and both writing terminal statuses, so `attempts` and `response_status` reflect whichever finished last.
Fix: replace the three calls with one atomic `SET LOCK_KEY <token> NX EX 60` (`redis_client.set(LOCK_KEY, token, nx=True, ex=60)`) where `token = secrets.token_hex(16)` is unique per acquisition, and release with a compare-and-delete Lua script (`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`) so a worker can only release its own lock. Additionally add `.with_for_update(skip_locked=True)` to `_claim_batch`'s query, so correctness does not depend on the lock at all — the lock becomes an optimisation rather than the only thing preventing double delivery. Preserve: a single worker must still acquire the lock on every iteration with no added latency, and an unheld lock must still be acquirable immediately after release. Allow side to pin: one worker acquires, releases, and re-acquires; and after a crash without release, the next worker acquires once the 60s TTL expires. Red-proofs, one per clause, executed: (i) revert to GET-then-SET and run two concurrent `_acquire_lock` calls → a test asserting exactly one returns `True` reddens (bound the test with a timeout so a wedge surfaces as a failure); (ii) revert the release to an unconditional `delete` → a test where worker A's token has expired and worker B holds the lock, and A releases, reddens on the assertion that B still holds it; (iii) remove `skip_locked` → a test with two sessions claiming concurrently reddens on the assertion that no delivery id appears in both batches. Fail-loud: a Redis connection error inside `_acquire_lock` must return `False` (do not dispatch) and log at error level, never be swallowed into a `True` — the failure direction here is "do not deliver", because delivering unguarded is the harm. Boundary/tie: name the boundary — the TTL is 60s while a batch of `BATCH_SIZE = 100` deliveries at `REQUEST_TIMEOUT = 30.0` can exceed it, so either extend the lock during the batch or set the TTL from `BATCH_SIZE × REQUEST_TIMEOUT`; two workers whose tokens differ never both hold it, which is the tie the compare-and-delete resolves.

### Minor: `SECRET_BYTES` counts characters, not bytes
File: `app/webhooks/signing.py` — `SECRET_BYTES = 32`, used as `range(SECRET_BYTES)` over a 62-character alphabet

### Minor: `webhook_deliveries` lacks the indexes its own queries need, and `webhook_endpoints` lacks one on `org_id`
File: `migrations/0042_webhook_delivery.sql` — `CREATE INDEX idx_webhook_deliveries_status ON webhook_deliveries (status);`
What is wrong: `_claim_batch` filters `status = 'pending' AND next_attempt_at <= now` ordered by `next_attempt_at`, which the single-column low-cardinality `status` index serves poorly; `list_deliveries` filters `endpoint_id`, which has no index (Postgres does not index foreign keys automatically); `enqueue_for_event` and `list_webhook_endpoints` filter `webhook_endpoints.org_id`, also unindexed.

Suggested change: replace the status index with `CREATE INDEX ON webhook_deliveries (next_attempt_at) WHERE status = 'pending';`, and add `CREATE INDEX ON webhook_endpoints (org_id);` plus the `(endpoint_id, created_at DESC, id DESC)` index named in the ordering finding.
