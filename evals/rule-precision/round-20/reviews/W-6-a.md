### Critical: `list_deliveries` has no tenancy filter — any authenticated user reads any org's delivery history
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: the query filters on `WebhookDelivery.endpoint_id == endpoint_id` only, while both sibling endpoints in the same file (`list_api_keys`, `list_webhook_endpoints`) filter on `org_id == user.org_id`, so `user` is read from the dependency and then never used in the query.
What breaks in production: any customer can enumerate `endpoint_id` values and read another organization's event types, delivery statuses and response codes, which is a cross-tenant data leak and a direct contradiction of the docs line "returns the most recent attempts for an endpoint belonging to your organization".
Fix: join the parent row into the same query and scope it — `session.query(WebhookDelivery).join(WebhookEndpoint, WebhookEndpoint.id == WebhookDelivery.endpoint_id).filter(WebhookEndpoint.org_id == user.org_id, WebhookDelivery.endpoint_id == endpoint_id)` — and raise `HTTPException(404)` (not 403, which confirms existence) when `session.get(WebhookEndpoint, endpoint_id)` is None or belongs to another org, so an unresolvable or absent endpoint denies rather than returning an empty 200 that reads identically to "this endpoint has no deliveries". Preserve the existing `order_by(created_at.desc()).limit(limit)` behaviour — narrowing the filter must not become "return nothing". Boundary/tie: an endpoint whose `org_id` equals the caller's org must still return its rows (pin this allow case with a test asserting a non-empty list for the owner), and an endpoint id that exists but belongs to another org must return 404 with zero rows — the two cases must be asserted separately, since a fix that always 404s satisfies the deny test alone. Red-prove each clause independently by execution: (i) revert the `join`/`org_id` filter and confirm the cross-org test goes red; (ii) revert the 404 branch and confirm the "foreign id returns 404" test goes red; (iii) revert the `endpoint_id` filter and confirm the owner test now returns another endpoint's rows and goes red.

### Critical: the signing secret is readable back on every list call
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and `list_webhook_endpoints` returns `[e.to_dict() for e in endpoints]`, so the secret is served on every GET — while `docs/webhooks.md` states "The response is the only place the signing secret appears — it cannot be read back afterwards".
What breaks in production: any credential with read scope on the settings API (a leaked read-only key, a browser session, an integration token) exfiltrates the HMAC key for every endpoint and can then forge webhook deliveries that every customer verifier accepts; this is R49 — a control the docs describe as write-once that is implemented as always-readable, and downstream systems are entitled to trust the documented property.
Fix: drop `signing_secret` from `WebhookEndpoint.to_dict()` so the shared serializer is safe by default, and have `create_webhook_endpoint` return `{**endpoint.to_dict(), "signing_secret": secret}` from the locally held value, which is the only place the plaintext is legitimately disclosed. Do not fix this by deleting the create-time disclosure as well — the secret must still reach the customer exactly once, or the feature is unusable; state that in the change. Store a `signing_secret_hash` alongside if verification-side lookup is ever needed, but that is not required for this fix. Boundary/tie: the create response contains the key and the list response does not — assert both, since removing the field from `to_dict()` alone would silently break registration. Red-prove separately by execution: (i) re-add the key to `to_dict()` and confirm a test asserting `"signing_secret" not in list_response[0]` goes red; (ii) remove the merge in the create handler and confirm a test asserting `create_response["signing_secret"].startswith("whsec_")` goes red.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`
What is wrong: `return expected == signature` compares a MAC with Python's short-circuiting `==` (RS1); `hmac.compare_digest` is the available primitive and is not used anywhere in the diff.
What breaks in production: an attacker who can submit candidate signatures to whatever consumes `verify` recovers the correct digest byte-by-byte from response-time differences and then forges accepted payloads.
Fix: `return hmac.compare_digest(expected, signature)`, with `signature` coerced to `str` and both sides `.encode()`d, and guard the non-string/None case by returning `False` rather than raising. Preserve the accept path: the existing `test_verify_accepts_signature_produced_by_sign` must stay green — a fix that returns `False` unconditionally passes the reject test alone. Red-prove each clause by execution: (i) revert to `==` and confirm a timing-independent equality test still passes (proving the equality test cannot catch this, which is why clause (ii) is needed); (ii) mutate `compare_digest` to `lambda a, b: True` and confirm `test_verify_rejects_a_signature_made_with_another_secret` goes red; (iii) pass a non-string signature and confirm the function returns `False` and logs, rather than raising `TypeError` out of the caller — "could not compare" must not be spelled the same as "did not match". Boundary/tie: a signature of the correct length but differing in the last byte must reject, and an exactly-equal digest must accept.

### Critical: the HMAC does not cover the timestamp the documentation says it covers
File: `app/webhooks/signing.py` — `sign` / `verify`; `docs/webhooks.md` "Verifying the signature"
What is wrong: the docs specify the signature as "the HMAC-SHA256 of `\"{timestamp}.{raw_request_body}\"`", but `sign` computes `hmac.new(secret, serialize(payload), sha256)` over the body alone and merely returns the timestamp beside it, and `verify` discards the timestamp entirely (`_, expected = sign(...)`) so it cannot enforce the documented five-minute replay window.
What breaks in production: every customer who implements the published verification algorithm computes a different digest and rejects 100% of our deliveries (R29/R49 — the documented contract and the implementation are different algorithms), and because the timestamp is unauthenticated an attacker who captures one request can rewrite `X-Acme-Timestamp` to `now` and replay it forever, which is exactly the attack the docs claim the window stops.
Fix: make the signed string the documented one — `mac = hmac.new(secret.encode(), f"{timestamp}.{body}".encode(), hashlib.sha256)` where `body` is the exact byte string transmitted (see the next finding) — and give `verify` the signature `verify(secret, timestamp, body, signature, *, max_age_seconds=300)` that recomputes over `f"{timestamp}.{body}"`, rejects when `abs(now - int(timestamp)) > max_age_seconds`, and rejects when `timestamp` is not an integer string. Do not fix this by relaxing the doc to match the code: the timestamp binding is the replay control, and deleting the claim deletes the control. Fail loudly: a non-integer or absent timestamp must return `False` (not skip the freshness check), and that "cannot evaluate" case must be distinguishable in the caller's log from "digest mismatch". Boundary/tie: a timestamp exactly `max_age_seconds` old is accepted and `max_age_seconds + 1` is rejected — state that in the docs; clock skew in the future is bounded by the same window. Red-prove each clause by execution: (i) drop the `f"{timestamp}."` prefix and confirm a vector test against a hand-computed expected digest goes red; (ii) remove the age check and confirm a test replaying a 10-minute-old timestamp goes red; (iii) feed `timestamp="abc"` and confirm the malformed-input test goes red if the function raises instead of returning `False`. The allow case that must stay green: a freshly signed payload verifies.

### Critical: the bytes that are signed are not the bytes that are sent
File: `app/webhooks/delivery.py` — `send_once`; `app/webhooks/signing.py` — `serialize`
What is wrong: `sign` HMACs `json.dumps(payload, sort_keys=True)` (default separators `", "` / `": "`, keys sorted) while the request body is produced independently by `client.post(..., json=delivery.payload)`, which httpx serializes with compact separators `(",", ":")` and the dict's insertion order — the codebase already has the canonical serializer (`signing.serialize`) and the transmit path does not use it (R40, R1: an existing helper reimplemented by the HTTP client).
What breaks in production: the receiver HMACs the raw body it received, gets a different digest from the one in the header, and every single delivery fails verification — a silent total-path failure that no test in this diff can see, because `test_send_once_posts_the_signed_payload` only checks that the header starts with `sha256=`.
Fix: serialize exactly once and send that byte string — `body = signing.serialize(delivery.payload).encode()`, then `ts, signature = sign(endpoint.signing_secret, body)` (change `sign` to take bytes and stop re-serializing), then `client.post(endpoint.url, content=body, headers={..., "Content-Type": "application/json"})`; delete `json=` from the call so there is one and only one producer of the wire bytes. Pin `serialize` with `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")` so the shape is stated rather than inherited from a default. Do not "fix" this by loosening the receiver's algorithm to re-serialize before hashing — that reintroduces the same divergence at the customer's side. Round-trip test (R40's requirement): feed the ACTUAL captured `request.content` from the `MockTransport` handler through the ACTUAL `signing.verify`, not two independently constructed strings. Boundary/tie: a payload with non-ASCII values and a payload with keys already in sorted order must both round-trip byte-identically. Red-prove each clause by execution: (i) revert `content=body` to `json=delivery.payload` and confirm the round-trip test goes red; (ii) change `separators` back to the default and confirm it goes red; (iii) drop `sort_keys=True` and confirm the reordered-keys test goes red. Allow case: a normal `invoice.paid` payload still POSTs with `Content-Type: application/json` and a 200 still marks the delivery delivered.

### Critical: signing secrets are generated from a non-cryptographic RNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: the secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, which is deterministic and whose full internal state is recoverable from a modest run of outputs; `secrets` is the correct module and is not imported anywhere in the diff.
What breaks in production: an attacker who registers a handful of their own endpoints observes enough generator output to reconstruct the state and predict other tenants' signing secrets, then forges webhooks that every customer's verifier accepts as genuine — the whole authenticity story of the feature collapses.
Fix: `return SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` (importing `secrets`, dropping `random`, `string` and `_ALPHABET` outright rather than leaving them as an unreferenced fallback), and rename `SECRET_BYTES = 32` to mean what it says — bytes of entropy — updating `test_new_signing_secret_has_prefix_and_length` to assert the prefix plus a minimum length rather than an exact character count, since `token_urlsafe` yields ~43 characters for 32 bytes. Preserve the properties the current test pins: the `whsec_` prefix is still present and secrets are still URL-safe printable. Fail loudly rather than silently degrading: do not add a `try: import secrets / except: random` fallback. Boundary/tie: two consecutive calls must differ (assert it — an implementation returning a constant satisfies both prefix and length checks). Red-prove each clause by execution: (i) replace `secrets.token_urlsafe` with a constant and confirm the uniqueness assertion goes red; (ii) drop the prefix and confirm the prefix assertion goes red; (iii) shorten to 8 bytes and confirm the minimum-length assertion goes red.

### Critical: user-supplied endpoint URLs are an unguarded SSRF sink, and redirects are followed
File: `app/api/routes/settings.py` — `create_webhook_endpoint`; `app/webhooks/delivery.py` — `run_worker` (`follow_redirects=True`)
What is wrong: the only check is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plaintext `http://` (the docs say "Only `https://` URLs are accepted"), admits `http://127.0.0.1:6379/`, `http://10.0.0.5/`, and `http://169.254.169.254/latest/meta-data/`, and the worker then POSTs to it from inside the production network with `follow_redirects=True`, so even a legitimately public host can 302 the request onto an internal address (RS3 — an unvalidated boundary value reaching an interpreter, here the HTTP client).
What breaks in production: a customer registers an internal URL, waits for any `invoice.paid` event, and our own worker performs authenticated-by-position requests against internal services or the cloud metadata endpoint, and the delivery record hands the response body back to them via the deliveries API path.
Fix: validate at the schema boundary, not in the handler — give `EndpointIn.url` a `pydantic.HttpUrl`-typed field with a validator that requires `scheme == "https"` exactly (`startswith("http")` also matches `http`, which is the bug) and rejects a host that resolves to any address in `ipaddress` loopback / link-local / private / unique-local / multicast / reserved ranges, resolving every A and AAAA record and rejecting if ANY resolves into those ranges; set `follow_redirects=False` on the `AsyncClient` and treat a 3xx as a permanent failure with a message naming the redirect; and re-check the resolved address at connect time (a custom `httpx` transport or a pinned-IP connect) because DNS can be re-pointed between registration and delivery. Fail loudly: DNS resolution failure at registration must return 422 naming the unresolvable host, never fall through to "allowed". Do not remove the delivery-inspection feature to fix this — the response status must still be recorded. Boundary/tie: `https://hooks.example.com` (public, resolvable) must still register and still deliver — pin that allow case; `169.254.169.255` and `10.255.255.255` are inside the blocked ranges and `9.255.255.255` is outside. Red-prove each clause by execution: (i) restore `startswith("http")` and confirm the `http://` rejection test goes red; (ii) remove the private-range check and confirm the `http://127.0.0.1` test goes red; (iii) set `follow_redirects=True` and confirm a MockTransport test asserting a 302 is recorded as failure goes red.

### Critical: the delivery worker uses ORM rows after their session has closed
File: `app/webhooks/delivery.py` — `_claim_batch` (`return rows` inside `with session_scope()`), consumed by `deliver` / `send_once`
What is wrong: `_claim_batch` returns `WebhookDelivery` instances whose session has already exited the `with` block, and `deliver` then reads `delivery.attempts`, `delivery.id` and `delivery.payload` — with SQLAlchemy's default `expire_on_commit=True` every attribute is expired on commit and the first access on a detached instance raises `DetachedInstanceError`; the same defect is present one line later where `deliver` reads `endpoint = session.get(...)` inside a `with` and dereferences `endpoint.url` / `endpoint.signing_secret` outside it.
What breaks in production: the worker raises on the first claimed row of the first batch and, because `run_worker` has no `except` around the `gather`, the coroutine dies and webhook delivery stops entirely while rows sit in `in_flight` forever.
Fix: stop passing ORM identities across the session boundary — have `_claim_batch` return plain tuples/dataclasses of the fields the send path needs (`id`, `endpoint_id`, `attempts`, `payload`, and the endpoint's `url` and `signing_secret`, fetched in the same query via a join), so `deliver`/`send_once` operate on detached-safe values and every write goes back through `_finish`'s own session. Do not fix this by setting `expire_on_commit=False` globally: that hides the lifetime bug and leaves the worker reading stale values from a committed-away identity map. Fail loudly: `_claim_batch` must raise a named error if the join yields a delivery whose endpoint row is gone, rather than yielding a row with `url=None` that later fails deep inside httpx. Boundary/tie: a batch of exactly `BATCH_SIZE` rows and an empty batch must both be handled — the empty case currently falls to `await asyncio.sleep(poll_interval)` and must keep doing so. Red-prove each clause by execution: (i) write an integration test that runs `_claim_batch` against a real session and asserts `deliver` completes; revert to returning ORM rows and confirm it goes red with `DetachedInstanceError`; (ii) delete an endpoint between claim and send and confirm the named-error test goes red when the guard is removed.

### Critical: the migration's status CHECK constraint rejects the status the code writes
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/models.py:STATUSES` and `app/webhooks/delivery.py:_finish(delivery.id, "failed_permanent", ...)`

Red-prove each clause by execution: (i) write `'failed'` and confirm the rejection test goes red when the CHECK is dropped; (ii) remove `'failed_permanent'` from the CHECK and confirm the exhaust-retries test goes red.

### Critical: the unique index on `event_id` makes fan-out to more than one endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: uniqueness is declared on `event_id` alone, but `enqueue_for_event` builds one row per matching endpoint (`for endpoint in endpoints`) and inserts them with `session.add_all(rows)`, so a single event with two subscribed endpoints violates the index.
What breaks in production: the second and later endpoints of any organization never receive anything — the whole `add_all` raises `IntegrityError`, `dispatch` swallows it as a `log.warning`, and the event is dropped for every endpoint including the first, silently, exactly for the customers who have set up redundancy.
Fix: replace it with `CREATE UNIQUE INDEX idx_webhook_deliveries_endpoint_event ON webhook_deliveries (endpoint_id, event_id)`, which preserves the deduplication property the index was there for (one delivery per event per destination — the property the docs' "deduplicate on `event_id`" depends on) while permitting fan-out. Preserve the idempotency guarantee: a redelivery attempt for the same (endpoint, event) pair must still be rejected, so keep the index UNIQUE rather than dropping it. Fail loudly: `enqueue_for_event` should use an `ON CONFLICT DO NOTHING` insert and log the conflicting pair, so a duplicate enqueue is a recorded no-op rather than an exception that takes the whole batch down. Boundary/tie: two endpoints of the same org for one event → two rows; the same endpoint enqueued twice for one event → one row. Red-prove each clause by execution: (i) enqueue an event for two active endpoints and assert two rows; restore the single-column index and confirm it goes red; (ii) enqueue the same event twice for one endpoint and assert one row; drop the unique index and confirm it goes red.

### Critical: `time.sleep` inside an `async def` blocks the entire event loop
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is a coroutine gathered up to `BATCH_SIZE` times, and its retry pause uses the blocking `time.sleep` rather than `await asyncio.sleep`, while `asyncio` is already imported and used correctly two functions below in `run_worker`.
What breaks in production: one endpoint that is down stalls the process for 2+4+8+16 = 30 seconds per delivery with everything else — including any HTTP server sharing the loop — frozen, and `asyncio.gather` degenerates into strictly serial execution, so a batch of 100 failing deliveries blocks for roughly 50 minutes and exceeds the 60-second Redis lock by three orders of magnitude.
Fix: do not sleep in-process at all — replace the `while True` loop with a single attempt per invocation that persists the outcome, writing `status="pending"`, `attempts=attempt`, and `next_attempt_at = datetime.now(timezone.utc) + backoff_for(attempt)` on a retryable failure and letting the next `_claim_batch` poll pick it up; keep `backoff_for` and `MAX_ATTEMPTS` unchanged so the documented schedule is preserved, and keep the terminal `failed_permanent` write for `attempt >= MAX_ATTEMPTS`. If an in-process retry is genuinely wanted, the minimum change is `await asyncio.sleep(delay)`. Preserve the retry behaviour itself — the fix must not reduce the delivery to a single attempt. Boundary/tie: `attempt == MAX_ATTEMPTS` is terminal and `attempt == MAX_ATTEMPTS - 1` schedules one more try; state which side the boundary falls on in the code. Red-prove each clause by execution: (i) assert the loop yields control by running two failing deliveries concurrently and asserting wall-clock is not the sum of their backoffs — restore `time.sleep` and confirm it goes red; (ii) assert `next_attempt_at` advances by `backoff_for(attempt)` after a 500; remove the write and confirm it goes red; (iii) assert the fifth failure writes `failed_permanent`; change the comparison to `>` and confirm it goes red.

### Major: the Redis lock is acquired non-atomically and expires separately
File: `app/webhooks/delivery.py` — `_acquire_lock`
What is wrong: `get` then `set` then `expire` is a three-round-trip check-then-act, so two workers that both see the key absent both proceed, and a crash between `set` and `expire` leaves a key with no TTL.
What breaks in production: two workers claim overlapping batches and duplicate every delivery in the window, and a single ill-timed crash leaves `webhooks:dispatch:lock` set forever so every worker spins on `asyncio.sleep(poll_interval)` and no webhook is ever delivered again, with no alert because the loop looks healthy.
Fix: make acquisition one atomic command with a TTL and an owner token — `token = secrets.token_hex(16); acquired = await redis_client.set(LOCK_KEY, token, nx=True, ex=LOCK_TTL_SECONDS)` — returning `acquired` and stashing `token` for release; introduce `LOCK_TTL_SECONDS` as a named constant beside `MAX_ATTEMPTS` rather than the inline `60`. Preserve the intended behaviour: exactly one worker proceeds and the others still poll rather than erroring. Fail loudly: a Redis error must propagate or be logged as "lock state unknown → do not claim", never be caught into `return True`, so "cannot check" is not spelled the same as "free". Boundary/tie: when two workers call `set(nx=True)` in the same instant exactly one gets a truthy reply and the loser must sleep, not raise. Red-prove each clause by execution: (i) run two concurrent `_acquire_lock` calls against a real/fake Redis and assert exactly one truthy result — revert to `get`-then-`set` with an `await asyncio.sleep(0)` injected between them and confirm it goes red; (ii) assert `ttl(LOCK_KEY) > 0` immediately after acquisition and confirm it goes red when `ex=` is removed; (iii) the allow case: after the TTL elapses a second worker acquires successfully.

### Major: the lock is released by key, not by ownership, and its TTL is far shorter than a batch
File: `app/webhooks/delivery.py` — `run_worker`, `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: the lock is set with a 60-second expiry while the guarded section processes up to `BATCH_SIZE` deliveries whose retry schedule alone is 30 seconds each, and the `finally` deletes the key unconditionally without checking that this worker still owns it.
What breaks in production: worker A's lock expires mid-batch, worker B acquires and starts a duplicate batch, then worker A finishes and deletes B's lock — so from that point the mutual exclusion is permanently broken and customers receive duplicate deliveries for every event.
Fix: release via a compare-and-delete so only the owner can unlock — a Lua `if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) end` evaluated with the token from the acquisition fix — and renew the lease (`expire` refresh) from a background task while the batch runs, or bound the guarded section so it provably completes inside `LOCK_TTL_SECONDS` (which the per-attempt persistence fix above already achieves by removing in-process sleeping). Preserve the release-on-exception behaviour: the `finally` must still run, it must just be ownership-checked. Fail loudly: if the compare-and-delete reports "not owner", log a warning naming the lock and the token — a silently-lost lease is the signal that the TTL is too short. Boundary/tie: a batch finishing at exactly the TTL must be treated as lost, not as owned. Red-prove each clause by execution: (i) acquire with token A, overwrite the key with token B, run the release, assert the key still holds B — use the unconditional `delete` and confirm it goes red; (ii) assert the normal path does remove the key when the token matches.

### Major: `in_flight` is a non-terminal state with no reaper
File: `app/webhooks/delivery.py` — `_claim_batch` sets `row.status = "in_flight"`; nothing ever moves it back
What is wrong: the only transitions out of `in_flight` are inside `_finish`, which is reached only if the worker survives the whole attempt sequence; a crash, a deploy, a `DetachedInstanceError`, or the check-constraint violation above leaves the row `in_flight` forever, and `_claim_batch` only ever selects `status == "pending"` (R38, non-terminal transient state with no failure exit and no timeout).
What breaks in production: every delivery interrupted by a restart is silently dropped and never retried, contradicting the docs' "delivery is at-least-once", and the rows accumulate invisibly because nothing queries or alerts on them.
Fix: add a `claimed_at TIMESTAMPTZ` column written when a row is moved to `in_flight`, and have `_claim_batch` also select `status == "in_flight" AND claimed_at < now() - interval '5 minutes'`, resetting those rows to `pending` with `attempts` unchanged before claiming; emit a `log.warning` naming the delivery id for each reclaim so a stuck worker is visible rather than merely healed. Preserve the mutual-exclusion property the `in_flight` marker provides — the reclaim window must be longer than the maximum legitimate attempt duration, so the fix must not simply drop the state. Fail loudly: if `claimed_at` is NULL on an `in_flight` row (rows written before this migration), reclaim it and log, rather than skipping it forever. Boundary/tie: a row claimed exactly at the reclaim horizon must not be double-claimed — the comparison must be strict and the reclaim must happen inside the same transaction as the claim. Red-prove each clause by execution: (i) insert an `in_flight` row with an old `claimed_at`, run `_claim_batch`, assert it is returned; remove the reclaim clause and confirm it goes red; (ii) insert one with a fresh `claimed_at` and assert it is NOT returned — this is the allow-side pin that a reclaim-everything implementation would fail.

### Major: webhook enqueue failures are swallowed and the event is reported as dispatched
File: `app/events/dispatcher.py` — `dispatch`, `except Exception as exc: log.warning(...)`
What is wrong: the event row commits in its own `session_scope`, `enqueue_for_event` then opens a second, independent transaction, and any failure of that second transaction is caught by a bare `except Exception` that logs at WARNING and lets `dispatch` return `event_id` as if everything succeeded (R9: the side effect is not atomic with the write it belongs to; R4: the dispatch gap is invisible to the caller).
What breaks in production: a Redis/DB hiccup, the `IntegrityError` from the unique-index defect above, or any bug in `enqueue_for_event` drops the webhook for that event permanently — there is no outbox row, no retry, and no signal beyond a WARNING line, which directly falsifies the docs' "delivery is at-least-once".
Fix: write the delivery rows in the SAME transaction as the `Event` row — move the `enqueue_for_event` body inside the existing `with session_scope() as session:` block and pass the session in, so either both commit or neither does — and let the worker be the only thing that performs I/O. Keep the `try/except` only around genuinely non-transactional work, and narrow it from `Exception` to the specific exception classes that are recoverable, re-raising everything else. Do not fix this by deleting the log line or by making `dispatch` swallow more: the caller must be able to observe the failure. What is wrong: `list_deliveries` filters on `endpoint_id` and orders by `created_at DESC`, and the only indexes are on `status` (very low cardinality) and the unique one on `event_id`, so the listing degrades to a scan-and-sort as the table grows.

## Cross-cutting verification

- **Org scoping**: checked all three new routes. `list_webhook_endpoints` filters on `user.org_id`, matching the pre-existing `list_api_keys`; `list_deliveries` does not (reported Critical). `enqueue_for_event` scopes on `org_id` correctly.
- **Naive vs aware datetimes**: `datetime.utcnow()` appears exactly once (`enqueue_for_event`); `_now()`, `_claim_batch` and `_finish` all use `datetime.now(timezone.utc)` — the single outlier is reported. The migration's `TIMESTAMP` columns are the same divergence on the storage side and are reported separately.
- **Constant-time comparison**: `verify` is the only credential comparison in the diff; no other `==` on a signature or secret exists.
- **Status vocabulary**: the three definitions are `models.STATUSES`, the migration CHECK, and the string literals in `_claim_batch`/`_finish`. `"pending"`, `"in_flight"` and `"delivered"` agree across all three; only `failed_permanent` / `failed` diverges.
- **Serialization**: `signing.serialize` is the only canonical serializer and `send_once` is the only transmit site; the divergence is therefore a single call, not a class.
- **Bare `except Exception`**: appears once (`dispatcher.dispatch`); `deliver` catches the narrow `httpx.HTTPError`, which is correct, though it means a non-`HTTPError` raised by `send_once` escapes the retry loop entirely — covered by the `gather` finding.

## Codebase awareness

- `app/webhooks/models.py` already defines `_now()`; `enqueue_for_event` reimplements it as `datetime.utcnow()` with different semantics (R1).
- `app/webhooks/signing.py` already defines `serialize()`; `send_once` bypasses it by handing the dict to httpx's own JSON encoder (R1/R40).
- `WebhookEndpoint.to_dict()` is the shared serializer for both the create and list routes, which is exactly why including `signing_secret` in it leaks the secret from a route that was never meant to disclose it.
- `app/api/routes/settings.py` already contains the org-scoping pattern (`filter(ApiKey.org_id == user.org_id)`) that `list_deliveries` fails to follow — the correct shape is in the same file, four functions above.
