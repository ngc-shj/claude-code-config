### Critical: `signing_secret` is returned on every read of the endpoint list
File: `app/webhooks/models.py` — `WebhookEndpoint.to_dict`, consumed by `app/api/routes/settings.py:list_webhook_endpoints`
What is wrong: `to_dict()` includes `"signing_secret": self.signing_secret`, and `GET /v1/settings/webhook-endpoints` returns that dict for every endpoint, directly contradicting `docs/webhooks.md` ("The response is the only place the signing secret appears — it cannot be read back afterwards").
What breaks in production: The HMAC key for every endpoint is served on an ordinary read route, so it lands in browser caches, proxy logs, APM response-body capture and any client-side state store, and anyone who reaches that route once can forge signed deliveries indefinitely.
Codebase awareness: the change already demonstrates the correct shape one class down — `WebhookDelivery.to_dict()` deliberately omits `payload` and `response_body`; `WebhookEndpoint.to_dict()` is the single serializer shared by the create and list call sites, which is why the secret leaked from the one place it is legitimate (create) into the one where it is not (list).
Fix: Split the serializer rather than editing the shared one in place — keep `to_dict()` free of `signing_secret` and add `to_dict_with_secret()` used *only* by `create_webhook_endpoint`'s 201 response. Preserve the behaviour that makes the feature usable: the create response must still carry the secret exactly once (clause 4), so pin both directions (clause 1) — a test asserting `POST` response contains a `whsec_`-prefixed `signing_secret`, and a test asserting `GET .../webhook-endpoints` response JSON contains no key named `signing_secret` and no substring `whsec_`. Red-prove each separately (clause 2): mutation A deletes the secret from the create path and reddens only the POST test; mutation B re-adds `signing_secret` to `to_dict()` and reddens only the GET test. Boundary and tie (clause 5): the rule is "secret is emitted on exactly one HTTP status — 201 from the create route"; for an endpoint created and then immediately listed in the same request cycle the list copy is still redacted. Fail loudly (clause 3): if `signing_secret` is unset/None at create time, return 500 rather than a 201 carrying `null` — an endpoint with no key must not be persisted.

### Critical: `list_deliveries` has no tenancy filter (cross-organization read)
File: `app/api/routes/settings.py` — `list_deliveries`
What is wrong: The query filters only `WebhookDelivery.endpoint_id == endpoint_id` and never joins to `WebhookEndpoint` or compares `org_id` to `user.org_id`, while the two sibling routes in the same file (`list_api_keys`, `list_webhook_endpoints`) and `enqueue_for_event` all filter on `org_id`.
What breaks in production: Any authenticated user can enumerate `endpoint_id` values and read another organization's delivery history — event ids, event types, failure statuses and delivery cadence — which is both a tenancy breach and a business-activity leak (`invoice.paid` volume per competitor).
Cross-cutting verification: the org-scoping pattern appears at four sites in this diff (`get_profile`, `list_api_keys`, `list_webhook_endpoints`, `enqueue_for_event`); `list_deliveries` is the only one missing it — R3, security-relevant.
Fix: Resolve the endpoint first and authorize on it, in the same handler that reads the data rather than at any gateway: `endpoint = session.query(WebhookEndpoint).filter(WebhookEndpoint.id == endpoint_id, WebhookEndpoint.org_id == user.org_id).one_or_none()`; if `None`, raise `HTTPException(404)` (404 not 403, so the route does not confirm the existence of other tenants' ids), then filter deliveries by `endpoint.id`. Pair deny with allow (clause 1): pin two tests — the owning user still receives their rows (a fix that returns 404 unconditionally must redden this), and a user in another org receives 404 *and* an empty body. Red-prove separately (clause 2): mutation A drops the `org_id` predicate and reddens only the cross-tenant test; mutation B drops the `endpoint.id` filter and reddens only the owner test. Fail loudly (clause 3): when `user.org_id` is None/unresolvable the handler raises 401 rather than querying with `org_id IS NULL`. Boundary/tie (clause 5): an endpoint that was soft-deleted or has `active=False` still belongs to its org and its deliveries remain readable by that org only.

### Critical: registered webhook URLs are unrestricted, and the client follows redirects (SSRF)
File: `app/api/routes/settings.py` — `create_webhook_endpoint`, with `app/webhooks/delivery.py:run_worker`
What is wrong: Validation is `parsed.scheme.startswith("http") and parsed.netloc`, which admits plain `http://`, admits any host including `localhost`, `169.254.169.254` and RFC1918 addresses, and admits scheme strings that merely begin with `http` — and `httpx.AsyncClient(..., follow_redirects=True)` then chases any 3xx from an otherwise-public host into the same internal space.
What breaks in production: A tenant registers `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or a public host that 302s there) and the delivery worker, running inside the VPC with the org's event payloads, issues authenticated-by-position requests to internal services and writes the response body into `webhook_deliveries.response_body` where the tenant reads it back via the deliveries route.
Fix: Validate at the schema boundary, not in the handler body — give `EndpointIn.url` a Pydantic `HttpUrl`-typed field constrained to `scheme == "https"` (equality, not `startswith`), plus a resolution-time guard in `send_once`: resolve the hostname and reject any address in a private/loopback/link-local/CGNAT range before connecting, and set `follow_redirects=False` so a 3xx is recorded as a delivery failure rather than followed. Do not fix by deleting the feature (clause 4): a customer's public `https://hooks.example.com/acme` must still be accepted and delivered — pin that as the allow case (clause 1) alongside deny cases for `http://`, `https://127.0.0.1/`, `https://169.254.169.254/` and a public host that 302s to a private one. Red-prove each clause separately (clause 2): four mutations — restore `startswith("http")`, remove the private-range check, restore `follow_redirects=True`, and remove the DNS re-resolution — each reddening one distinct assertion. Fail loudly (clause 3): DNS resolution failure or an unresolvable host must be a named delivery error (`status=failed_permanent`, detail `"host did not resolve"`), never a skipped check that proceeds to connect. Boundary/tie (clause 5): state the rule for a host resolving to both a public and a private address — reject if *any* returned address is private; and re-check after redirect suppression so the check-time address is the connect-time address.

### Critical: signing secrets are generated with a non-cryptographic RNG
File: `app/webhooks/signing.py` — `new_signing_secret`
What is wrong: The secret is built from `random.choice(_ALPHABET)`, i.e. the Mersenne Twister, which is a deterministic PRNG whose full internal state is recoverable from a modest run of observed outputs, rather than from the `secrets` module the standard library provides for exactly this.
What breaks in production: An attacker who obtains a handful of secrets (they are handed out on every create, and now also on every list — see the first finding) can reconstruct the generator state and derive the signing secrets of other endpoints, letting them forge deliveries that every customer's verification accepts.
R1 evidence: this reimplements `secrets.token_urlsafe` / `secrets.choice`, both in the stdlib and already reachable — no local helper is being duplicated, but the security-control class makes it Critical. The behavioural difference that must be classified rather than silently dropped: `SECRET_BYTES = 32` is a misnomer — it is a count of alphabet characters (~190 bits over a 62-symbol alphabet), not bytes, and `tests/webhooks/test_delivery.py:test_new_signing_secret_has_prefix_and_length` currently pins that misnomer as if it were the contract.
Fix: Replace the body with `SECRET_PREFIX + secrets.token_urlsafe(SECRET_BYTES)` and rename the constant to `SECRET_ENTROPY_BYTES = 32` so the name states what it measures; delete the `random`, `string` imports and `_ALPHABET` outright rather than leaving them unreferenced (R1 clause d). Preserve what made the feature work (clause 4): the `whsec_` prefix must stay, because it is what lets customers grep their secret managers — pin an allow case asserting the returned value still starts with `SECRET_PREFIX` and still verifies a payload end-to-end through `sign`/`verify`. Pin the deny side (clause 1) as an entropy floor test: 1,000 generated secrets are all distinct and each has ≥ 128 bits of length-implied entropy. Red-prove separately (clause 2): mutation A returns a constant secret and reddens only the distinctness assertion; mutation B truncates to 4 characters and reddens only the length assertion; mutation C drops the prefix and reddens only the prefix assertion. Fail loudly (clause 3): if `token_urlsafe` raises (no OS entropy source), let it propagate — creation must 500, never fall back to `random`. Boundary/tie (clause 5): state that `token_urlsafe(32)` yields a 43-character body, so the length assertion is `>= 43`, not `== SECRET_BYTES`, and update the existing test accordingly instead of deleting it.

### Critical: signature comparison is not constant-time
File: `app/webhooks/signing.py` — `verify`, `return expected == signature`
What is wrong: The MAC comparison uses Python's `==` on `str`, which short-circuits on the first differing byte, in the same module whose own documentation (`docs/webhooks.md`) instructs integrators to "Compare it against your own computation using a constant-time comparison".
What breaks in production: `verify` is the shipped reference verifier and the natural choice for any inbound webhook path built on this module; against a remote attacker it leaks the correct digest byte-by-byte through response timing, allowing a valid signature to be constructed for an arbitrary payload without knowing the secret — and the module telling customers to do the opposite of what it does makes it more likely to be copied verbatim.
Fix: `return hmac.compare_digest(expected, signature)` (`hmac` is already imported). Pair deny with allow (clause 1): the existing `test_verify_accepts_signature_produced_by_sign` must stay green — a `compare_digest` that always returns False satisfies every hardening clause and must be caught by that allow case, so do not delete it (clause 4). Red-prove separately (clause 2): mutation A reverts to `==` and reddens a timing-independence assertion (assert `verify` is called through `compare_digest` by patching `hmac.compare_digest` and asserting it received both operands); mutation B flips the return value and reddens the wrong-secret test. Fail loudly (clause 3): `compare_digest` raises `TypeError` on non-ASCII `str`; wrap the header value in an explicit `isinstance(signature, str)` + ASCII check that returns False with a logged reason, so a malformed header is a named rejection rather than an unhandled 500. Boundary/tie (clause 5): a `signature` of a different length than `expected` must return False, not raise, and the empty string must return False — `compare_digest` leaks length but not content, and that is the accepted boundary.

### Critical: the transmitted body is not the bytes that were signed
File: `app/webhooks/delivery.py` — `send_once`
What is wrong: The signature is computed over `signing.serialize(payload)` (`json.dumps(payload, sort_keys=True)`, default `", "`/`": "` separators) while the request is sent with `client.post(..., json=delivery.payload)`, which re-serializes the dict with httpx's own compact separators and insertion order — two different byte strings for the same dict.
What breaks in production: Every customer who follows `docs/webhooks.md` and HMACs the raw request body computes a different digest than the one in the header, so *every* delivery to *every* endpoint fails verification and the entire feature is inert from the integrator's side — the classic R40 same-team-owns-both-sides failure, invisible here because no test recomputes the MAC over the transmitted bytes.
Codebase awareness: the change already contains the canonical serializer, `signing.serialize`, and `send_once` bypasses it for the wire path while using it for the signing path — the divergence is exactly the helper not being adopted at the second call site.
Fix: Serialize once and send those bytes: `body = signing.serialize(delivery.payload).encode()`, sign `body`, and post with `content=body` plus an explicit `Content-Type: application/json` header (already set). Require the R40 round-trip test rather than two mocked shapes (clause 1 allow side): a test that captures `request.content` from `MockTransport` and asserts `signing.verify_raw(SECRET, captured_body, captured_headers[SIGNATURE_HEADER])` returns True — i.e. actual producer output through the actual consumer routine. Red-prove separately (clause 2): mutation A reverts to `json=` and reddens the round-trip assertion; mutation B changes `sort_keys` and reddens it for a multi-key payload only; mutation C alters one payload byte before sending and reddens it. Preserve (clause 4): the body must remain valid JSON parseable by the existing `json.loads(captured["body"])` assertion — do not "fix" this by dropping that assertion. Boundary/tie (clause 5): fix the encoding explicitly (`ensure_ascii` setting and UTF-8) and state it in the doc, because a payload containing a non-ASCII invoice description is where producer and consumer next diverge.

### Critical: the timestamp is not covered by the MAC, so the documented replay window enforces nothing
File: `app/webhooks/signing.py` — `sign`, and `docs/webhooks.md` "Verifying the signature"
What is wrong: `sign` returns `timestamp` but computes `hmac.new(secret, serialize(payload), sha256)` — the timestamp is never fed into the MAC — while the doc states the signature is "the HMAC-SHA256 of `"{timestamp}.{raw_request_body}"`" and that rejecting old timestamps "is what stops a captured request from being replayed".
What breaks in production: An attacker who captures one delivery can replay it forever by rewriting `X-Acme-Timestamp` to the current second, because the header is unauthenticated and the digest does not change — the replay defence the customer was told to rely on does not exist, and this is R49's Critical case: a control described as an enforceable boundary that is in fact absent, with no other control compensating for it.
Test evidence inside the change: `tests/webhooks/test_delivery.py:test_verify_accepts_signature_produced_by_sign` passes even though `verify` recomputes `sign` with a *fresh* timestamp — a test that could only be green if the timestamp is outside the MAC.
Fix: Make the signed string `f"{timestamp}.{body}"` in `sign`, and give `verify` a `timestamp` parameter plus a `tolerance_seconds: int = 300` staleness check, so the signature and the freshness check are one decision. Pair deny with allow (clause 1): a delivery signed 10 seconds ago still verifies (allow), a delivery replayed with a rewritten timestamp fails (deny), and a delivery replayed with its *original* timestamp 6 minutes later fails (deny). Red-prove each separately (clause 2): mutation A removes the timestamp from the MAC input and reddens only the rewritten-timestamp test; mutation B removes the tolerance check and reddens only the 6-minutes-later test; mutation C sets tolerance to 0 and reddens only the allow test. Fail loudly (clause 3): a missing, non-numeric, or future-dated-beyond-tolerance timestamp returns False with a distinct logged reason — "no timestamp supplied" must not be spelled the same as "timestamp fresh". Boundary/tie (clause 5): a timestamp exactly `tolerance_seconds` old is accepted and `tolerance_seconds + 1` is rejected; state the clock-skew direction so a customer whose clock is 2 minutes fast is not silently rejected. Update `docs/webhooks.md` in the same commit so the documented string and the computed string are one sentence apart.

### Critical: the permanent-failure status is not writable — the DB CHECK constraint rejects it
File: `migrations/0042_webhook_delivery.sql` — `CHECK (status IN ('pending', 'in_flight', 'delivered', 'failed'))` vs `app/webhooks/delivery.py:deliver` writing `"failed_permanent"`
What is wrong: The migration's allowed set ends in `'failed'` while `app/webhooks/models.py:STATUSES` and `_finish(delivery.id, "failed_permanent", ...)` use `'failed_permanent'`, so the terminal write raises `CheckViolation` and its transaction rolls back.
What breaks in production: Every delivery that exhausts its attempts fails to be finalized, the row stays `in_flight` forever, `_claim_batch` only selects `status == "pending"` so it is never retried and never surfaced, and the worker logs a 500-class exception on the exact path operators watch for delivery failures — the failure state is unrepresentable.
Cross-cutting verification: `models.STATUSES` is declared and then used by nothing — neither `_finish`, nor `_claim_batch`'s `"pending"` literal, nor the migration's `CHECK` list; the same enum is written out by hand in three places (R2/R12).
Fix: Make `STATUSES` the single source and generate from it — change the migration's CHECK list to the four values in `models.STATUSES`, and replace the literals in `_finish` and `_claim_batch` with named constants (`STATUS_PENDING`, `STATUS_IN_FLIGHT`, `STATUS_DELIVERED`, `STATUS_FAILED_PERMANENT`) exported from `models.py`. Pair deny with allow (clause 1): pin an integration test that writes each of the four statuses to a real database and succeeds (allow), and one that writes `'bogus'` and raises (deny) — a fix that drops the CHECK constraint entirely satisfies the allow side and must be caught by the deny side (clause 4: do not fix by deleting the constraint that made this visible). Red-prove separately (clause 2): mutation A reverts the migration value to `'failed'` and reddens only the failed-permanent write; mutation B removes the CHECK and reddens only the `'bogus'` test. Fail loudly (clause 3): add a startup assertion that the DB's CHECK list equals `set(STATUSES)` and refuses to boot the worker otherwise, so drift is a named boot failure rather than a per-row exception in an hour. Boundary/tie (clause 5): specify the migration path for rows already written under the old constraint (there are none on a fresh table, so the constraint can be replaced with `ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT`; state that explicitly rather than assuming an empty table).

### Critical: `UNIQUE (event_id)` makes fan-out to a second endpoint impossible
File: `migrations/0042_webhook_delivery.sql` — `CREATE UNIQUE INDEX idx_webhook_deliveries_event ON webhook_deliveries (event_id)`
What is wrong: `enqueue_for_event` inserts one `WebhookDelivery` row per matching endpoint, all carrying the same `event_id`, so the unique index rejects the second row and the whole `session_scope` block fails.
What breaks in production: Any organization with two or more active endpoints subscribed to the same event gets an `IntegrityError` on every such event; `dispatch` swallows it as `log.warning("webhook enqueue failed...")`, so that org silently receives *no* webhooks at all while the product reports the endpoints as active — and `docs/webhooks.md`'s "delivery is at-least-once, so deduplicate on `event_id`" describes the opposite of what the schema permits.
Fix: Change the index to `UNIQUE (endpoint_id, event_id)`, which expresses the actual idempotency invariant (one delivery per endpoint per event) and keeps the deduplication guarantee the doc promises. Pair deny with allow (clause 1): pin a test where one event with two active subscribed endpoints produces exactly two rows (allow — a fix that simply drops the index passes this and must be caught by the deny case), and a test where re-running `enqueue_for_event` for the same `(endpoint_id, event_id)` raises/upserts to one row (deny). Red-prove separately (clause 2): mutation A restores the single-column unique index and reddens only the two-endpoint test; mutation B drops the index and reddens only the re-enqueue test. Fail loudly (clause 3): make `enqueue_for_event` catch `IntegrityError` and re-raise a named `WebhookEnqueueError` — and remove the blanket `except Exception: log.warning` in `dispatch` (see the next finding) so "enqueued nothing" cannot be spelled the same as "enqueued successfully". Preserve (clause 4): keep the `event_id` column indexed for the deduplication lookup — make it a non-unique index rather than deleting it. Boundary/tie (clause 5): state what happens when the same event is re-dispatched after an endpoint is deactivated and reactivated — the `(endpoint_id, event_id)` pair still collides, which is the intended at-most-once-per-endpoint behaviour, and say so.

### Critical: `deliver` blocks the event loop with `time.sleep`, and the retry schedule in the schema is dead code
File: `app/webhooks/delivery.py` — `deliver`, `time.sleep(delay)`
What is wrong: `deliver` is `async def` but sleeps with the blocking `time.sleep`, and it retries in a `while True` loop in-process instead of writing `next_attempt_at = now + backoff_for(attempt)` and returning the row to `pending` — so the `attempts` and `next_attempt_at` columns the migration creates are never used for scheduling.
What breaks in production: One failing endpoint blocks the entire process — up to 2+4+8+16 = 30 seconds per delivery, serialized across a batch of `BATCH_SIZE = 100`, so a single bad endpoint stalls every other org's deliveries for tens of minutes, the 60-second lock TTL expires mid-batch and a second worker claims the same rows, and any restart during the loop loses all retry state because nothing was persisted.
Fix: Delete the in-process retry loop: `deliver` makes exactly one attempt, then either `_finish(..., "delivered", ...)` or — if `attempt < MAX_ATTEMPTS` — writes `status="pending"`, `attempts=attempt`, `next_attempt_at=now + backoff_for(attempt)` and returns, letting `_claim_batch` pick it up when due; replace `time.sleep` with nothing (the sleep is the poller's job) and add jitter inside `backoff_for` as the doc already claims. Preserve what made the feature useful (clause 4): the retry behaviour itself must survive — a delivery that fails twice and succeeds on the third attempt must still end `delivered` with `attempts == 3`; pin that as the allow case (clause 1) alongside the deny case that a permanently-failing delivery reaches `failed_permanent` at exactly `MAX_ATTEMPTS` and is never claimed again. Red-prove separately (clause 2): mutation A restores `time.sleep` and reddens an assertion that a batch of two failing deliveries completes in under one second of wall clock; mutation B stops writing `next_attempt_at` and reddens the reschedule test; mutation C makes `backoff_for` constant and reddens the growth test. Fail loudly (clause 3): an exception that is not `httpx.HTTPError` must not escape `deliver` silently into `asyncio.gather` — catch it, `_finish(..., "failed_permanent", ..., detail=repr(exc))`, and re-raise into a logged handler, so a serialization bug is not indistinguishable from a successful empty batch. Boundary/tie (clause 5): state that `attempt == MAX_ATTEMPTS` is terminal (not `>`), and that two deliveries with an identical `next_attempt_at` are ordered by `id` so neither is starved.

### Critical: the only test of the signature asserts its prefix, not its value
File: `tests/webhooks/test_delivery.py` — `test_send_once_posts_the_signed_payload`
What is wrong: The test asserts `captured["headers"][signing.SIGNATURE_HEADER].startswith("sha256=")` and never recomputes the HMAC over `captured["body"]`, so the production security primitive (the signature actually matching the transmitted bytes) is never on the test's assertion path — RT5/RT7 on a security control.

### Major: `dispatch` swallows every webhook enqueue failure
File: `app/events/dispatcher.py` — `except Exception as exc: log.warning(...)`
What is wrong: The `Event` row is committed in one `session_scope` and `enqueue_for_event` opens a second, unrelated transaction whose every failure — integrity violation, DB unavailability, a bug — is caught by a bare `except Exception` and reduced to a warning.
What breaks in production: The event is durably recorded while its deliveries are not, with no retry, no dead-letter and no queryable trace, so `invoice.paid` webhooks are permanently and silently lost for the affected org, and the recovery path is reconstructing them by hand from the `events` table.
Fix: Use a transactional outbox — insert the `Event` row and its `WebhookDelivery` rows in the *same* `session_scope` so they commit or roll back together, and let the worker be the only thing that reads them. Where that is not possible, narrow the catch to the specific recoverable exception and re-raise everything else. Pair deny with allow (clause 1): a successful dispatch still returns `event_id` and still notifies in-process subscribers (a fix that makes enqueue failures fatal must not break the subscriber path); a failing enqueue must roll back the `Event` insert too, asserted by querying that no event row exists. Red-prove separately (clause 2): mutation A restores the bare `except Exception` and reddens the rollback assertion; mutation B removes the subscriber loop and reddens the allow assertion. Fail loudly (clause 3): if the webhook module cannot be imported or the endpoint query errors, `dispatch` raises with the event type and org in the message — "no endpoints subscribed" (a legitimate zero) must be a distinct, logged outcome from "could not determine endpoints". Preserve (clause 4): keep the `log.warning` line as a warning for the genuine zero-endpoint case; the fix removes the swallow, not the observability. Boundary/tie (clause 5): state the ordering — subscribers currently run *before* the enqueue, so decide and document whether a subscriber raising should also prevent the webhook rows from committing.

### Major: `WEBHOOK_EVENT_TYPES` is a second, narrower subscription domain that silently voids valid subscriptions
File: `app/events/dispatcher.py` — `WEBHOOK_EVENT_TYPES`, with `app/api/routes/settings.py:EndpointIn.event_types`
What is wrong: The dispatcher only enqueues for three hardcoded types, while the create route accepts an arbitrary `list[str]` with no membership check and `enqueue_for_event` treats an empty list as "all events" — two independent definitions of the same set, the narrower one invisible to the API.
What breaks in production: A customer registers `event_types: ["user.created"]`, receives a 201 and an endpoint listed as `active: True`, and never receives a single delivery, with no error anywhere to explain it; `docs/webhooks.md`'s "An empty `event_types` subscribes the endpoint to every event type we emit" is false for every emitted type outside the hardcoded three.
Fix: Export a single `WEBHOOK_EVENT_TYPES` (or a shared enum) from one module, import it in both the dispatcher and the route, and validate `EndpointIn.event_types` against it with a Pydantic validator that returns 422 naming the unknown type and listing the supported set. Pair deny with allow (clause 1): registering `["invoice.paid"]` still returns 201 and still receives deliveries (allow); registering `["user.created"]` returns 422 (deny) — a validator that rejects everything must redden the allow case. Red-prove separately (clause 2): mutation A removes the validator and reddens only the 422 test; mutation B removes a member from the shared set and reddens only the allow test. Fail loudly (clause 3): an empty `event_types` must resolve to the *explicit* current member list at enqueue time, and if that set is empty the create route rejects rather than persisting a subscription to nothing. Preserve (clause 4): keep "empty means all" as the documented convenience — the fix constrains the non-empty case, it does not remove the wildcard. Boundary/tie (clause 5): define what happens to an already-persisted endpoint whose `event_types` contains a value later removed from the set — it must be surfaced in the list response as unsupported, not silently ignored.

### Major: `organizations.webhooks_enabled` is added but read nowhere
File: `migrations/0042_webhook_delivery.sql` — `ALTER TABLE organizations ADD COLUMN webhooks_enabled BOOLEAN NOT NULL DEFAULT FALSE`
What is wrong: The column is created with a default of `FALSE` and no code in the change — not `dispatch`, not `enqueue_for_event`, not the create route — ever reads it; there is also no corresponding attribute on any model in the diff.

### Major: the distributed lock is a check-then-set and can wedge permanently
File: `app/webhooks/delivery.py` — `_acquire_lock`, and `run_worker`'s `finally: await redis_client.delete(LOCK_KEY)`
What is wrong: `get` then `set` then `expire` are three separate round trips, so two workers can both observe the key absent and both proceed; if the process dies between `set` and `expire` the key has no TTL and never expires; and `run_worker` deletes the key unconditionally in `finally` with no ownership token, so a worker whose lock already expired deletes the lock a second worker now holds.
What breaks in production: The benign outcome is duplicate deliveries to customer endpoints (the interleaved-claim race); the malign one is a crash-timed leak that leaves `webhooks:dispatch:lock` set forever, after which every worker's `_acquire_lock` returns False and *all* webhook delivery stops silently until someone deletes the key by hand — R38's persisted fail-closed wedge with no reset path.
Fix: Collapse acquisition into one atomic command with a fencing token — `await redis_client.set(LOCK_KEY, token, nx=True, ex=60)` where `token = uuid4().hex` — and release with a compare-and-delete Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end`) so a worker can only delete the lock it holds. Pair deny with allow (clause 1): a single worker still acquires, processes and releases (allow — a lock that never acquires satisfies every mutual-exclusion assertion and must be caught here); two concurrent workers must produce exactly one claim of a given delivery row (deny). Red-prove separately (clause 2): mutation A reverts to `get`/`set` and reddens only the concurrency test; mutation B removes `ex=60` and reddens a test asserting the key has a positive TTL immediately after acquisition; mutation C replaces the compare-and-delete with a plain `delete` and reddens a test where a stale worker's release leaves the fresh holder's lock intact. Fail loudly (clause 3): if Redis is unreachable, `_acquire_lock` must raise a named error that stops the worker with a log line, never return False in a silent forever-loop that looks identical to "another worker holds it". Preserve (clause 4): keep the TTL — do not fix the double-delete by removing expiry, which reintroduces the wedge. Boundary/tie (clause 5): state what happens when the TTL expires while a batch is still in flight (the batch must be rescheduled, not silently double-delivered) and pick a TTL strictly greater than the worst-case batch duration.

### Major: one transient error terminates the delivery worker

### Major: `in_flight` has no exit on the crash path
