# Extraction ratchet baseline — machine-read by hooks/check-rule-sync.sh (check 9).
#
# A rule row in common-rules.md is a ROUTING SUMMARY. When the procedure is
# large it belongs in rule-details/<ID>.md, which the row points at. This file
# lists the rows that are over the byte ceiling with the whole procedure still
# inline — the ones whose extraction has not happened yet.
#
# It exists because that convention sat in folding.md for a long time with
# nothing measuring it, and a convention nobody measures is a wish. The linter
# enforces the ratchet in both directions:
#
#   - a row over the ceiling with no rule-details/<ID>.md pointer, absent from
#     this file, is drift (no silent growth)
#   - a line here whose row now fits or has been extracted is drift (the list
#     can only shrink)
#   - the annotation must match the row (see below)
#
# So the way to remove a line is to move that rule's procedure into
# rule-details/<ID>.md, not to edit this file.
#
# A first version measured bytes alone. It was the wrong instrument: extracting
# 25 procedures cut the table by 40 KB and moved the over-ceiling count by four,
# because a routing summary for a rule with sub-clauses and a detector to
# describe legitimately costs more than one for a rule without. What the ceiling
# is really asking is whether the full procedure lives somewhere a reader can
# fetch separately — so that, and not the byte count alone, is what is checked.
#
# Column 2 records whether the row names a **Mechanical detection** paragraph,
# in any qualified form. It is the input folding.md consults before letting a
# repeated `Extends` land as still more prose: naming a class is not the same
# act as installing its inspector, and a rule that has absorbed several rounds
# of text while staying `no-inspector` is the signature of that confusion.
#
# What that column does NOT cover: this file lists only over-ceiling rows whose
# procedure is still inline, so the annotation answers for about a sixth of the
# rule set and is silent for the rest — including every extracted rule, which
# names its detector in the detail page rather than in the row. Absence from
# this file is not evidence of a detector. Across the whole set, 16 rules of 74
# have one anywhere.
#
# Format: <rule-id><TAB>inspector|no-inspector   (# comments and blanks ignored)
