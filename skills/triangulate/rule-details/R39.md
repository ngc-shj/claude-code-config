# R39 — Lifecycle secret/metadata zeroization (inverse of R25)

This file contains the full normative procedure for `R39`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R39 | Lifecycle secret/metadata zeroization (inverse of R25) | When state crosses a **lock / background / suspend / sign-out / session-end** lifecycle boundary, every holder of secret material (decryption keys, decrypted plaintext, session tokens, in-memory vault context) AND every externally-visible metadata store seeded from secrets (autofill/suggestion caches, prefilled hints, search indices, OS-surfaced credential identities) MUST have a deterministic clear hooked to that boundary, and the clear MUST NOT race the re-populate path. R25 covers persist→hydrate (does saved data come *back*); R39 is the destroy side — does loaded secret/metadata get *cleared* when the session boundary says it should. A missing clear leaves secrets or secret-derived hints recoverable after the user believes the session ended (post-lock memory dump, post-sign-out autofill hint, suggestion surviving a crash/relaunch window). **Reviewer action**: for each secret holder and each metadata store populated from secrets, confirm a clear is wired to the lock/background/sign-out path; confirm the clear is ordered so a concurrent re-populate (`.task`/async re-register) cannot resurrect it. **Intermediate decode-time plaintext sub-clause**: zeroization is in scope not only at the lifecycle boundary but also for *transient* secret buffers produced while decoding or unwrapping a key — the derived shared-secret bytes, the decrypted plaintext held before import into the platform keystore, the parsed raw key bytes from an encoded key blob. These intermediates are under application control (unlike an opaque platform key object the OS manages) and MUST be overwritten with an explicit zero-fill after the key is imported, even though they never cross a lock/sign-out boundary; otherwise they linger recoverable in a memory dump. **Severity**: Major for secret-derived metadata (defense-in-depth); Critical when long-term key material or live session tokens survive the boundary. | Major (Critical when long-term key material / live tokens survive) |
