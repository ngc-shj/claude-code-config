# RT11 — Test fixture outlives its own run (sandbox escape, or cleanup skipped on the failure path)

This file contains the full normative procedure for `RT11`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| RT11 | Test fixture outlives its own run (sandbox escape, or cleanup skipped on the failure path) | Fires when a test acquires state that can survive the test — a filesystem object, a uniquely-keyed record, an entry in a shared registry or append-only sink — and either the state is created outside the tree the run reclaims, or its release is registered after the assertions rather than at acquisition. Both defects present as a green suite: the leak lands in the *next* run, as a failure that does not name its cause (a uniqueness violation from a key the previous run abandoned, an existence assertion satisfied by an earlier test's record, a stale object making an order-dependent case pass). Two structural causes, and a suite usually has both. (1) **Sandbox scoping**: when the per-test sandbox root IS the subject root, every fixture the test needs *outside* the subject — the "outside the guarded tree" case a containment guard must be given — necessarily lands outside the reclaimed tree, typically in shared system temp under a predictable name. Nest the subject one level inside the sandbox so out-of-subject fixtures stay inside what teardown removes. (2) **Release ordering**: registration placed after the assertions is skipped by the abort-on-failure semantics of every runner, so cleanup runs in exactly the runs that did not need it. Register at the moment of acquisition, in the runner's teardown construct, and include identifiers returned by *production* code — not only ones the test constructed. **Also**: direct every mutable sink the subject touches (log file, recorder, registry, counter) to a per-test location explicitly rather than assuming the scratch-directory pattern covers it, and assert the sink's exact resulting state rather than the presence of a matching entry — a presence assertion is satisfiable by another test's residue. **Reviewer action**: for every test that constructs a path outside its subject root or acquires a globally-unique key, name the directory or teardown that reclaims it when the assertions throw; "the scratch dir is removed afterwards" is the finding when the fixture was never inside it. **Distinct from**: R50 clause (v) (run isolation — a *verification run* mutating the tracked worktree or racing a concurrent job; RT11 is a fixture outliving the run that made it), RT7 shape (g)'s lifetime bound (that clause governs the scratch subject a RED-PROOF acquires, because a proof's destructive statement executes precisely when the guard is absent; RT11 is any fixture in any test — a leaking red-proof subject fires both, and shape (g) is the more specific), RT4 (a race test passing vacuously), R31 (destructive product operations under user intent), R16 (a shared environment is a factor, not the mechanism), R35's manual-test-plan cleanup item (a human procedure ending tidily). | Major; Critical when the leaked state is written to a namespace shared with other principals or other jobs, or when it can make a later run of a security control's test pass for the wrong reason |
