# R29 — Citation, derived-claim, and rationale accuracy (external spec or intra-repo)

This file contains the full normative procedure for `R29`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R29 | Citation, derived-claim, and rationale accuracy (external spec or intra-repo) | When citing an RFC / NIST / OWASP / W3C / FIPS / ISO document, verify all four: (1) the cited section exists in the cited revision, (2) the quoted/paraphrased text actually appears at that section, (3) the revision is disambiguated when the standard has been revised and section numbers have shifted, (4) quoted phrases (in backticks or quotes) appear verbatim in the source; paraphrases are explicitly marked as such. Sources of drift commonly seen: NIST SP 800-63B Rev 3 → Rev 4 renumbered reauthentication sections AND changed AAL2 values; OWASP ASVS 4.0.3 → 5.0 renumbered chapters. **Illustrative past-hallucination patterns** (user-reported from prior reviews; pin revisions and re-verify against the source before citing in new findings): confidently citing a section number where the named topic actually lives elsewhere; quoting wording that does not appear verbatim in the source; omitting the revision when section numbers have shifted between revisions. **Severity**: Major by default (trust damage to future readers — they act on wrong info because the citation looks authoritative). **Escalate to Critical** when the hallucinated citation directly drives a security decision (recommending disabling a control, widening an allowlist, loosening a crypto parameter, raising a session lifetime) — in that case the wrong "authority" causes immediate security regression, not just trust erosion. See "Verify citations, do not fabricate them" in Expert Agent Obligations. **Intra-repo citation and rationale sub-clause (mined extension)**: the four obligations above are written for an EXTERNAL published document, but the same defect arrives from citations nothing external governs — a computed constant, a `file:line` reference, a symbol or helper name, an assertion about what a tool does — and, most costly, from the RATIONALE attached to a conclusion. A rationale is not decoration: it is what licenses the next edit, so a false reason under a TRUE conclusion is a live defect (observed: an invariant justified by "no candidate advanced the maximum, because none was processed", where instrumented execution showed the maximum already advanced at the emitter — the conclusion held, and the variable the false reason pointed at is the one in scope and the natural thing for the next editor to reach for). The same shape appears as a risk acceptance resting on an asserted ecosystem fact that is false, where the true fact *strengthens* the risk the claim was used to discount, and as a "clean" verdict recorded with a rationale that is false, which a later decision then cites as evidence for a claim it does not support. **Do**: verify by EXECUTION every load-bearing claim, not only the conclusion it supports — record the command next to a computed constant, open the cited `file:line`, run the tool whose behaviour is asserted, and re-derive the reason attached to each invariant. Assert round-trips against literals in both directions, never as `f(g(x)) == x`, which two mirrored-wrong implementations satisfy. Verify before the claim enters an append-only surface (a commit message, a PR body, a committed artifact), where correction is expensive or impossible **Derived-claim sub-clause**: the sibling case to the intra-repo one above is a QUANTITATIVE statement about the codebase used to justify a decision — a call-site count, a member cardinality, a coverage or occurrence figure, "only N places do X". It is presented in a frame ("derived from the code") that readers and later rounds treat as verified, exactly as a section number is. Ship the exact command that reproduces the number beside it, or drop the number and argue without it; re-run the command when the claim is restated in a later round rather than carrying it forward. This applies in plans, findings, and deferral justifications alike. Distinct from the Finding Quality Standards Evidence requirement, which asks a finding for the file path and line number of the code it references — a single file:line is not a derivation for a count, and the Evidence requirement does not reach plan claims at all. **Mechanical detection**: pipe the round's committed artifacts (`./docs/archive/review/<plan-name>-*.md`) into `bash ~/.claude/hooks/verify-references.sh --root . --base <ref> --strict`, which classifies every `file:line` those documents cite. Beyond MISSING / OUT-OF-RANGE it reports **SHIFTED** — the cited line still exists and is still in range, but no longer holds the text it held at `<ref>` — which is the rot mode an existence check is blind to and the one this branch's own fixes manufacture. Wired into the Phase 2 Step 2-4 and Phase 3 Step 3-6 gate blocks. **Coverage bound**: `file:line` citations only. A derived NUMBER, an external spec section, a symbol or helper name, an asserted tool behaviour, and above all the RATIONALE attached to a conclusion are all invisible to it, and the hardest case in this rule — a citation that is TRUE but does not reach the conclusion standing on it — is not decidable by any text scan, because the defect is in the inference rather than in the reference. A clean run is evidence about line identity and about nothing else; do not read it as this rule being discharged. | Major (Critical when the hallucinated citation, or an unreproducible codebase-derived figure, drives a security-tightening or security-loosening decision) |
