# R48 — Parallel adjudicators deciding one predicate by different semantics

This file contains the full normative procedure for `R48`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R48 | Parallel adjudicators deciding one predicate by different semantics | Fires when a fix ADDS a check beside an existing one that answers the same question by different semantics, instead of replacing it — lexical versus physically-resolved judgment, pre- versus post-resolution, name-based versus binding-based, a raw-text scan beside a parsed scan, a cached verdict beside a live one. Two adjudicators with different semantics disagree by construction, and the disagreement has both directions at once: the weaker one approves what the stronger would deny (a bypass, whenever its approval is honoured) and denies what the stronger would allow (a false block), with the observed behavior depending on evaluation order rather than on policy. Defence in depth does not license this shape: layers of the SAME semantics are depth, two semantics for one predicate are ambiguity. **Do**: keep exactly ONE adjudicator per predicate — the most authoritative available (R47) — and delete or demote the rest. A demoted check may pre-filter, log, or observe; it must not be able to emit a verdict. Where layering is genuinely wanted, layers must be strictly conjunctive (each may only DENY, none may approve past another) and must share one input-resolution path, so a new input shape cannot reach one layer in a form the other never sees. Adding a defence is an occasion to re-examine the existing one, not only to append to it. **Strict-direction sub-clause** (applies only after the fail-open direction has been ruled out — see the severity column; a pair with both directions is Critical on the fail-open one): the fail-open direction is the one a review looks for, so the *strict* divergence is the one that ships. Where the duplicated predicate sits on a fail-closed path, a derived adjudicator that is stricter than the primary does not reject a value — it rejects the value the primary path *produces*, and the failure is an outage of the flow rather than a finding (a storage constraint tighter than the application validator that owns it; a not-null column for a field legitimately absent over one transport; a length bound below the platform's maximum identifier length). These are not reachable from a test environment, because the configurations that produce them are the ones no test environment creates. Either delete the duplicate and record which adjudicator owns the question, or pin the derived predicate to the upstream one and state "never stricter"; before making a duplicated predicate fail-closed, enumerate the values it can legitimately receive across deployment shapes — absent or empty under an alternate transport, platform-maximum identifiers, values produced by a machine caller rather than an operator. RT10 is the test-time counterpart of this direction; this sub-clause is its design-time obligation. **Reviewer action**: for each guard the diff touches, grep the verdict emission (the deny/allow return or exit, not the helper name) and enumerate every site that decides the same predicate; two verdict sites for one predicate is the finding unless the conjunctive rule is explicit and tested in both directions. **Distinct from**: phase-2's duplicate-implementation check (a reuse concern; R48 is semantic divergence inside a decision), RT9 (one logic in two files drifting over time; R48 is two logics live simultaneously), R43 (one boundary being widened). | Major; Critical when the divergent pair guards a security boundary — the weaker semantics' approval is a fail-open bypass. The strict direction is a SECOND reading, never a softer alternative to the first: it applies only when no input exists on which the weaker semantics approves what the stronger denies. Where both directions are present — the default, per this rule's body — the Critical fail-open reading governs. In the strict-only case: Critical when the divergence takes down a whole flow rather than a single request (first-time sign-in, onboarding, a transport- or deployment-specific path no test environment produces); Major otherwise |
