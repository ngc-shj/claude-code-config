# R53 — Numeric gate threshold set or raised without headroom measurement

This file contains the full normative procedure for `R53`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R53 | Numeric gate threshold set or raised without headroom measurement | Fires when a diff adds or raises a numeric threshold that gates a build: a coverage floor, a performance or bundle-size budget, a warning/error count cap, a complexity or duplication limit, a latency SLO used as a gate. The number is habitually judged by whether it *sounds* right, but the value that decides the gate's behaviour is the DISTANCE between the threshold and the current measurement — that distance decides whom the gate fires on. A threshold set within normal churn of the present value fires on whichever unrelated change happens to cross it rather than on the change that caused the regression, which trains the team to raise it back and disables the floor by attrition. **Do**: (a) measure the current value and record the command that produced it; (b) state the headroom explicitly and set the threshold with slack exceeding observed churn — a floor a few points under a measurement that moves by a few points is a tripwire, not a floor; (c) enrol a specific subject into a stricter per-subject threshold only AFTER the work that lifts it above the line has landed, since enrolling a subject already below the line reds CI on the enrolment commit; (d) prove a per-subject entry actually binds — a path or key that matches nothing applies to nothing and is silently green, which is the RT7 obligation applied to the threshold map's keys. The proving value must be LEGAL for the tool but outside the subject's ACHIEVABLE range (a 100% floor on a subject measured at 80%), never merely out of range for the config schema: most threshold tooling validates its config before evaluating it, so a schema-invalid value reds on rejection — and the rejection message names the offending key too, satisfying a naive "the subject appears in the failure" oracle while proving nothing about whether the key matches a subject. Require the observed failure to name the subject AND its measured value; a config rejection cannot produce a measurement. This is R55's degenerate-oracle obligation applied to R53's own proof. **Distinct from**: R45 (a gate's RUNTIME against the scanned set; R53 is its threshold value), R27 (a numeric range hardcoded in user-facing strings), R33 (the same threshold drifting between duplicate CI configs). | Major; Critical when the un-measured threshold gates a security control's coverage, so the enrolment commit either reds the build or admits an unmeasured subject |
