# R51 — Decision bound to a name, not to the object the operation uses

This file contains the full normative procedure for `R51`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R51 | Decision bound to a name, not to the object the operation uses | Fires when a check and the effectful use it authorizes are separated by an interval in which another principal can act, and the use re-derives its subject from a *name* rather than carrying a handle to the object the check examined — a path validated and then re-opened, a resource id resolved and then re-resolved, an object listed and then addressed again by key. A name is a lookup key, not an identity: every re-resolution is a fresh lookup that anyone with write access to an intermediate component can influence between the two steps, so the object judged and the object acted on need not be the same one. Two properties make this survive the reviews that should catch it. (1) The remedies for the adjacent rules discharge without closing it — consulting the authoritative resolver (R47) fixes the reference's *spelling* and leaves the *interval* open, so R47 reads as satisfied; validating the value (RS3/RS5) happened, with the right criteria, on the right value. (2) The default helpers are unsafe: ordinary existence/stat/open calls follow links, so a check that "looked at the file" looked at whatever the name denoted at that instant. **Do**: carry the decision on a handle, acquired without traversing any component another principal can write — refusing to follow a link on the FINAL component is not enough, because every intermediate directory is still resolved by name during that open and each is a live swap point. Either walk one component at a time from a descriptor for a trusted root (open-relative, refusing links at each step) or use a single-shot resolve that refuses links and confines to a subtree where the platform offers one. Then validate the *descriptor* (type, owner, mode, size ceiling — not the path), and perform every subsequent operation relative to it, naming ONE non-symlink component at a time: a multi-component relative path re-resolves the names in it, which is the very thing the handle was acquired to avoid. Where no handle exists (a remote id, a registry key), the re-check at the instant of use is a narrowing, not a closure — it must be paired with making the guarded operation CONDITIONAL on the checked state (compare-and-swap over every field the check read and every field the write mutates, so a change in the interval aborts the write), and the remaining window declared. Restrictive creation mode on one's own directory does not protect operations that re-traverse the path afterwards, and a shared or world-writable namespace makes the interval attacker-schedulable rather than merely racy. **Reviewer action**: for every validated identifier in the diff, name what runs between validation and use — if anything at all can run, ask which object the use resolves and whether it is the one that was checked. A check-then-act pair on a filesystem path in a shared namespace, and a preview-then-confirm-then-write path whose write predicate omits a field the preview displayed, are the two shapes that recur. **Distinct from**: R5 (the same interval inside a database transaction, closed by transactional scope — R51 is every other store), R47 (which spelling of the name is authoritative; R51 is whether the name is authoritative at all — resolving correctly still leaves the interval after resolution), R46 (name-vs-binding resolved statically inside an analyzer, no interval), R38 clause (2) (the same interval across async suspension points inside ONE principal, remedied by re-checking a superseded-guard at every resume-after-suspension write site; R51 is a second principal re-binding the *name* between the check and the use — a task that crosses await points AND re-derives its subject from a name fires both), R42 (the field set a compare-and-swap must cover is derived per R42; R51 is why it must exist). | Major; Critical when the interval is attacker-schedulable (a namespace another principal can write, an untrusted command running between check and use) or when the re-resolved object is the subject of a privileged or destructive operation |
