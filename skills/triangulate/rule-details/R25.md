# R25 — Persist / hydrate symmetry + access scope

This file contains the full normative procedure for `R25`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R25 | Persist / hydrate symmetry + access scope | When a new field is added to state that crosses process / session / restart boundaries (browser or session storage, DB, file, cache, keychain, secure enclave), both the persist path AND the hydrate path must be updated. Write-only adds cause silent data loss on restart — hard to reproduce in tests that do not cross the boundary. Check: pair save/persist functions with their load/hydrate counterparts and confirm the new field appears on both sides. **Security angle**: for auth tokens, revocation lists, encryption material, consent flags, and audit-trail fields, write-only adds are not "data loss" but silent security downgrade — on restart the system reverts to a pre-policy state (un-revoked tokens appear valid again, consent appears never granted, encryption material missing). Name such fields explicitly when flagging. **Testing obligation**: a round-trip test that crosses a TRUE process / worker / container boundary (new process, cold worker, restarted container) — NOT a same-process in-memory reinstantiation or cache clear — is required. The test must: persist the field → cross the boundary → hydrate → assert the field equals what was persisted. Tests that mock both persist and hydrate in the same process, or that only reinstantiate the in-memory state, cannot catch the symmetry gap. **Access-scope sub-clause (a second axis, orthogonal to presence)**: content symmetry is not sufficient — the item's storage *attributes* must admit every reader. Enumerate the processes and the lifecycle moments that must read the item, then confirm its namespace/access-group/ACL admits all those processes and its availability window admits all those moments (locked device, pre-first-unlock, background/extension context, another container or user). Items read together in one operation must share ONE availability window; a stricter window on either makes the pair's read fail mid-operation. This gap is invisible to a round-trip test run in the *owning* process, where the read always succeeds, and its usual signature is a silent skip rather than a fail-closed error | Major; Critical when the unreadable item is what a security control consults, so the excluded process skips the check rather than failing closed |
