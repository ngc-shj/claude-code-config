# R38 — Async or persisted state machine: non-terminal state, fail-open supersession, persisted fail-closed wedge

This file contains the full normative procedure for `R38`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R38 | Async or persisted state machine: non-terminal state, fail-open supersession, persisted fail-closed wedge | Two failure modes of asynchronous state machines, both surfaced repeatedly in event-loop / background-worker / single-threaded-UI runtimes (browser service workers, mobile lifecycle, any reactive UI). **(1) Non-terminal transient state**: a component / handler enters a transient state (`loading`/`pending`/`in-flight`) and transitions OUT of it ONLY on the success path of an async call (message, fetch, RPC, channel read). When that call rejects, the channel closes, or it neither resolves nor rejects, the machine is wedged in the transient state forever — and if recovery affordances (retry/cancel buttons, error panes) render only in a terminal state, the user has zero escape. Every async transition needs BOTH a failure-terminal path (an explicit `.catch` / error branch that exits the transient state) AND a bounded timeout (the call may hang silently). A *background-triggered* refresh must additionally scope its failure so it cannot clobber an already-good screen into an error state. **Persisted fail-closed sub-clause**: the same no-escape obligation applies to states that are PERSISTED rather than transient — a trust-on-first-use pin, a lockout or quarantine flag, a revocation cache, a tamper marker. Here the wedge survives restart, so it is not cleared by the process dying, and the trigger is usually LEGITIMATE rotation of the pinned material, which the control cannot distinguish from an attack; the fail-closed direction is correct for the security property and simultaneously an unrecoverable denial for every user. A dead mismatch branch — the deny path exists and nothing anywhere clears the state — is the detectable signature. Every persisted fail-closed state needs an explicit exit that stays fail-closed: never automatic and never time-based, initiated by the user or operator, gated behind a confirmation step that names what will be lost and what re-establishing the control requires, and RE-establishing the control rather than disabling it. (Do not route this to R31, which governs the reviewing agent's OWN tool calls, not a product's confirmation UX — the catalog has no rule for the latter today.) Re-entering the same configuration is not an exit — it re-hits the stored state. **The exit must not be reachable by the party the state RESTRAINS, and must not be a step in the flow the state restrains.** Bind this to that reachability property, not to the state's label (R51): every persisted deny state has an actor it restrains, and an exit rendered inside the failing flow hands that actor the clear. Note the predicate is "restrains", never "set it" — a quarantine an automated scanner set has no setting *party* at all, an operator-set lockout must stay clearable by that same operator, and a pin the legitimate first-contact ceremony set is re-pinned by the very user who set it. An in-band "unlock and continue" on a lockout, a self-service "dismiss" on a quarantine marker, and a "reset trust and continue" on a pin are one mechanism, and all three satisfy the explicit / non-automatic / confirmation-gated / re-establishing conditions above while defeating the control — which is exactly why those conditions are not sufficient on their own. Per state class: for an anti-impersonation pin the exit must be OUT-OF-BAND, with the re-established material verified through a channel independent of the one that failed — the mismatch prompt is the attacker's most likely arrival point, so a user who clears it while on the hostile path re-pins the ATTACKER's material in one click. For a lockout, quarantine, or revocation cache, an in-band clear is admissible only when the party initiating it authenticated through a channel the state does not gate (a mailed reset link, an operator console). Note the interaction with RS5, which counts transport pinning/TOFU as MITM mitigation: a pin whose reset is in-band is not the mitigation RS5 is crediting. **(2) Fail-open supersession**: a long multi-step async task that reads-then-writes shared state across several suspension/await points can have a higher-priority authoritative mutation (an explicit user security action — lock, sign-out, token clear, revoke) run *during* its window; if the late-completing task writes back unconditionally it overwrites that mutation — re-deriving a key after an explicit lock, restoring a token after clear. This is fail-OPEN relative to the user's security action. The task MUST re-check a "superseded" guard at EVERY resume-after-suspension write site (not just the entry guard), and the authoritative mutators MUST set that guard. See Extended obligations. **Reviewer action**: enumerate every transient-state producer (failure exit + timeout present?) and every multi-await background writer (superseded guard at each resume point?); for any parse of a suppression/expiry/timer gate value, check the malformed-value fail-direction (Extended obligations Part 2 item 6 — visibility timers fail toward active/visible, access-restriction timers toward restrictive). | Major (non-terminal state; persisted fail-closed state with no reset path) / Critical (fail-open supersession on auth/session/key/token state, or a persisted fail-closed wedge that a legitimate rotation of the pinned material triggers for every user at once) |
