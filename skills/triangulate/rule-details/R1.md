# R1 — Shared utility reimplementation

This file contains the full normative procedure for `R1`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R1 | Shared utility reimplementation | Fires when new code implements behaviour an existing shared helper already provides (retry/backoff, rate limiting, validation, encoding, formatting, pagination, caching). Search for the existing helper before accepting the new implementation. **The obligations below were derived from a panel shown only the defective code, none of whom saw this rule** (`evals/rule-firing/rubrics/R1-merged.md`); the rule previously said only to search first, and the panel found unanimously that adopting the shared helper — the whole of what the rule asks — can leave the call site's real hazard untouched and change its behaviour besides. (a) **Enumerate every behavioural difference between the duplicate and the shared helper, and classify each** as accidental (drop it) or required by this call site (express it as an option on the shared helper); a difference left unclassified is the one that surprises production. (b) **Adopting the shared helper is itself a behaviour change at the call site** — state it. Defaults the duplicate did not have now apply, and where the two coincide today they may coincide only at the current parameter values; say which values the equivalence is scoped to. (c) **Changes to the shared helper are additive and default-preserving**, with the absent-argument path reproducing the pre-change behaviour, so the existing call sites are not moved by a change made for a new one — and that non-regression is evidenced by their tests, not by the assertion that nothing was changed. (d) **Delete the duplicate outright** — not renamed, not left unreferenced, not kept as a wrapper that still contains the logic. (e) **Ask what the duplicate's existence implies about the call site.** A hand-rolled mechanism is often hand-rolled because the author was reasoning about this call site specifically, and the properties that call site needs may be absent from BOTH implementations; deduplicating then yields one copy of an unchanged hazard. Name the failure the dedup does not address, or state that there is none. (f) **Address why the helper was not found** — export path, index visibility, naming, or a mechanical guard — or record that recurrence is accepted and why. **Distinct from**: R2 (a duplicated literal value rather than duplicated behaviour), R3 (a pattern changed in one place and not propagated to its other instances). | Major; Critical when the duplicated behaviour is a security control or the call site's unaddressed hazard is one |

## Why "use the existing helper" alone is insufficient

The panel's statement of the mechanism, on a call site that retried a non-idempotent operation:

> It does not fix the actual hazard. Both the old and new code retry [the non-idempotent operation] on every error class. Deduplicating them yields one copy of the same [exposure] — a tidier diff and an unchanged risk. A fix that stops at deduplication has resolved the stated problem and left the dangerous one in place.

and, on the cost of following the rule literally:

> It turns off nothing and turns *on* [the shared helper's default], the only same-day behavioural change.

Clause (e) exists for the first and clause (b) for the second. Neither is reachable from "search for the existing helper".
