# R54 — Control suspension granted through ambient context state

This file contains the full normative procedure for `R54`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R54 | Control suspension granted through ambient context state | Fires when a routine is permitted to bypass an invariant-enforcing control (append-only or immutability enforcement, row-level security, an audit trigger, a rate limiter, a foreign-key or constraint check) and the grant is expressed by SETTING AN AMBIENT FLAG inside the routine's body — a session or transaction variable, a thread-local, a request-scoped context value, a global "in maintenance" boolean. The grant's lifetime is then the enclosing context, not the operation it was granted for, so every subsequent statement in that transaction / request / thread inherits the exception. The failure needs no attacker: calling the sanctioned routine from a shared cleanup or batch helper silently disarms the control for everything that follows it in the same context. Two properties make it survive review. (1) The obvious test passes — issuing the forbidden operation in the NEXT context observes a fresh ambient state, so a leaking implementation is green. (2) An unregistered ambient variable is settable by any principal, so the "authority" is a convention rather than a boundary, and the control's class declaration (R49) reads as (a) *enforceable boundary* when the implementation is (c) *best-effort tripwire*. **Do**: scope the suspension to the CALL — a declaration on the routine that the runtime saves and restores around invocation, including on the error path — never by setting the flag and relying on the body to unset it, which the error path skips. Test the invariant in the SAME context immediately after the sanctioned call returns. Where the platform offers no call-scoped form, wrap the grant in an explicit acquire/release with the release in the language's finally-equivalent, and state in the control's class declaration that an ambient flag any principal can set bounds nothing — the real bound must be a capability the adversary does not hold. **The remaining six obligations, added because reviewers holding the three above still shipped fixes without them** (`evals/rule-ablation`, `docs/archive/audit/2026-08-04-rule-ablation.md`): (a) **restore the PREVIOUS value, never a hardcoded off/false** — a nested or already-granted outer scope is otherwise ended early by the inner release, which is the same leak inverted; (b) **await the covered work before restoring** — returning the callback's promise un-awaited lets the release run before the work it covers, and a `finally` added to that shape is decoration; (c) **do not mutate state the caller shares** — enter a fresh frame (a nested context store) or, for a connection-scoped setting, guarantee that set, covered work and restore all travel on the same handle, since a sibling task or a pooled checkout otherwise observes or inherits the grant; (d) **a failed restore must abort, not continue** — swallowing it leaves the control off for the remainder with no signal, and it must not mask the callback's own error; (e) **test the throw path**, not only the return path — the release that exists solely for the error case is the one no reviewer exercises; (f) **test nesting or concurrent use** — a naive save/restore on shared state passes both the return-path and throw-path tests and fails only here, so those two tests alone certify the wrong fix. **Distinct from**: R39 (clearing secret material at a lifecycle boundary), R38 clause (2) (an interval across async suspension points inside one principal), R51 (a name re-resolved to a different object), R5/R9 (transaction scope of the guarded work, not of an exception grant). | Major; Critical when the leaked suspension covers an audit, append-only, tenancy, or authorization control, since every statement after the sanctioned call runs unguarded |
