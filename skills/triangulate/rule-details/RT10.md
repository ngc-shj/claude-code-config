# RT10 — Guard tested only on its deny side (no paired allow case, no axis combinations)

This file contains the full normative procedure for `RT10`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| RT10 | Guard tested only on its deny side (no paired allow case, no axis combinations) | Fires when a diff adds or tightens a guard, gate, or validator and its tests exercise only rejected inputs. A deny-only suite pins the guard's strictness and nothing else: a later tightening — including an accidental one from a refactor — stays invisible, and the guard's own dominant failure mode goes unmeasured. Over-blocking is not the safe direction in practice; a guard that denies legitimate work gets disabled, granted a standing escape hatch, or routed around, and the protection leaves with it. A security control needs both halves proven: it refuses the dangerous operation, AND it keeps permitting the legitimate one. **Do**: (1) pair every deny fixture with an ALLOW fixture that is legitimate and *adjacent to the boundary* — the nearest input that must still pass (the benign case that resembles the attack, the ordinary case a hair inside the limit), not a distant obviously-fine case that any broken guard also admits. **Adjacency is symmetric, and is measured against the IMPLEMENTED predicate**: the deny fixture must likewise be the nearest forbidden input — the one differing from a permitted input only in the property under test — and both fixtures are chosen from the decision variable the code actually compares, not from the abstract requirement. A deny fixture derived from the requirement lands far from the implemented boundary, where the too-loose implementation refuses it as well, so the test passes on the defective code; and a coarse mutation proof cannot reveal this, because force-truing the whole predicate reddens the distant case too. Make the check discriminating rather than a paper exercise: enumerate the ONE-STEP loosenings the implementation admits — read off the code, not imagined (exact→prefix→substring, normalised comparison→raw, dropping one conjunct, removing a canonicalisation step, widening the compared container by one level) — and require that at least one of them makes the deny fixture PASS. "Loosen to the weakest reading" without that bound is unfalsifiable in both directions: loosen all the way to always-allow and every fixture qualifies; loosen by a hair and almost none does. Run the loosening as a mutation under RT7 shape (g) rather than arguing it — the same scratch-copy procedure, and a wholesale force-true of the predicate does NOT discharge it, since that is precisely the coarse mutant a distant deny fixture also reddens. Give the ALLOW fixture the mirror test, or the symmetry claimed here is enforced on one side only: enumerate the one-step TIGHTENINGS (substring→prefix→exact, raw→normalised, adding a conjunct or a canonicalisation step, narrowing the compared container by one level) and require at least one to make the allow fixture FAIL. Run the tightening as a real mutation too — the "not on paper" clause governs BOTH directions, and a tightening in particular couples in ways no paper reading yields. An allow fixture surviving every one-step tightening is the distant case in the other direction; (2) where the input has independent axes, cover their COMBINATIONS rather than each axis alone — the escapes that reach review are compound, not single-feature (aliasing plus relative traversal, aliasing plus an environment-derived root, a literal shorthand plus aliasing, an in-scope object resolving out of scope); enumerate the axes explicitly, choose fixtures from the cross-product's boundary cells, and state which cells are deliberately unclaimed so an uncovered cell is not read as a covered one. Illustrative axis set for a path guard (adapt per domain — the obligation is the enumeration, not these values): input form (absolute, relative, shorthand) by normality (plain, doubled separator, dot segment, parent segment) by aliasing (none, directory symlink, leaf symlink, chain) by direction (inside to inside, outside to inside, inside to outside, outside to outside) by subject state (existing, to be created) by expectation (deny, allow). **Distinct from**: RT7 (proves the guard CAN go red; RT10 proves it can still go green for legitimate input), RT8 (assertion completeness within one deny test), R42 (the member-set the guard is applied to; RT10 is the input-space of a single guard). **Mechanical detection (partial)**: `bash ~/.claude/hooks/check-deny-only-guard.sh [base-ref]` flags a changed test file whose assertions are entirely deny-shaped. File-level, TWO file flavors (Jest/Vitest, and bats `$status`); its hook-decision-JSON tokens are scored inside the bats-flavored branch only, so a Jest/Vitest test asserting on decision JSON matches neither grammar. Polarity-scored so a negated token is read as its opposite. It covers only the PAIRING half of clause 1 — that an allow-shaped assertion exists somewhere in the file — and neither whether EITHER fixture is *boundary-adjacent* (a judgment, since it is measured against the predicate the code implements) nor clause 2 (axis combinations) — and it additionally misses: a file holding one covered and one deny-only guard; grammars beyond the three; allow-side lines are not diff-scoped, so deleting a file's only allow assertion produces no fire; a `//` inside a string literal is over-stripped. A clean run means "no file was entirely deny-shaped", never "RT10 is satisfied". | Major; Critical when the guard sits on an operational recovery, deployment, or incident-response path where a false deny blocks remediation |
