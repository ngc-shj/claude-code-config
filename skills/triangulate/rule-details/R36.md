# R36 — Suppression, or any markerless weakening, as substitute for fix

This file contains the full normative procedure for `R36`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| R36 | Suppression, or any markerless weakening, as substitute for fix | Suppressing static-analysis warnings (lint, type checker, security scanner) via comment pragmas or rename-tricks is not an acceptable resolution. Suppression mechanisms vary by tool (illustrative, not exhaustive — searched as separate literal tokens, not a single combined regex, to keep table cells from breaking): `eslint-disable`, `@ts-ignore`, `# type: ignore`, `# noqa`, `@SuppressWarnings`, `//nolint:`, `#[allow(...)]`. Rename-tricks include underscore-prefix renames that mark variables as "intentionally unused" when the code is actually dead. The warning must be addressed at root cause via one of four categories: **(a) dead code** → delete entirely; **(b) rule violation in legitimate code** → restructure to satisfy the rule; **(c) duplicate of an existing helper** → reuse the helper instead of writing new code that requires suppression; **(d) upstream type-stub gap or known linter false-positive** → suppression IS acceptable when accompanied by a written justification placed adjacent to the suppression comment, naming the specific upstream issue, version, or incompatibility (illustrative comment: `// @ts-ignore — upstream issue typescript-eslint/typescript-eslint#1234, fixed in v8`). Bare suppression without a named, grep-able justification is the violation; suppression with a documented justification is acceptable. **Markerless-weakening sub-clause (mined extension)**: the categories above all assume the diff CARRIES A MARKER a reviewer can find — a pragma, an allowlist entry, an underscore rename. A firing detector offers several other responses that cost the author far less, look nearly identical in a diff, and leave nothing to review. Four observed spellings. (a) *Rewording the matched text*: a text- or name-matching gate is satisfied by editing the source it matched, with no behaviour change and no exemption entry — the benign case (a comment spelling out an example value) and the dangerous case (renaming an identifier, aliasing an import, splitting a literal) are indistinguishable in the artifact. (b) *Narrowing the gate's subject* (restricting which lines or files it reads) — often legitimate, but nearly indistinguishable from (c). (c) *Softening the pattern* so the conformant-looking case stops matching. (d) *Suppressing a channel*: running a load-bearing operation with stderr discarded, so a failed load leaves a helper silently absent. Separately, and with NO human suppressing anything at all, an expectation file that is REGENERATED FROM LIVE STATE launders its own regressions — every drift becomes an expected value at the next regeneration, and an audit built on it reports OK against a state where the control has been silently undone (the manual analogue is baselining a violation). **Do**: record which response was chosen and why, as an explicit deviation entry — "the gate fired and the source was edited" is exactly the shape that needs an audit trail, and it is the shape that currently leaves none. A channel suppression is admissible only when paired with a positive post-condition on the operation's result (the symbol is present after sourcing; the output validated after a suppressed probe). A subject narrowing must be shipped with a proof that it creates no hiding place (illustrative: only full-line comments stripped, so an inline marker cannot conceal code). Prefer an explicit, greppable exemption over an invisible rewording whenever the subject genuinely should not match. And pair every regenerable descriptive snapshot with an independent PRESCRIPTIVE rule that refuses to record a violating state, run BEFORE the regeneration, so the regenerated file is trustworthy only because the prescriptive check passed; require diff-stability of any tool whose diff is the review artifact. **Security-category carve-out — the deviation entry records a fix, it never substitutes for one**: for a detector in the security category listed under Severity escalation below (SAST injection, path traversal, SSRF, timing attack, hardcoded-secret, deserialization, crypto misuse, dead-code on auth/authz branches), spellings (a) *rewording the matched text* and (c) *softening the pattern* are NOT admissible resolutions at any price. Those two are the canonical bypasses of a secret detector, a forbidden-API gate, and a SAST rule — splitting a literal across a concatenation, aliasing the flagged import, or trimming the regex turns the gate green with no behaviour change and no defect fixed. The base four categories (a)-(d) above are the only resolutions available there, and the deviation entry documents which one was applied; "the gate fired and we reworded the source, entry filed" is the violation, not the discharge. Spellings (b) and (d) keep their own hard obligations in every category. Detection: enumerate the suppression markers above and run a separate grep for each one across the diff (`git diff --name-only main...HEAD`), then — because the markerless forms match no marker by construction — sweep the diff a second time for a gate/detector definition (pattern, glob, subject list, severity threshold) changed in the same diff as the source it scans, for a `2>/dev/null` or equivalent added to a load-bearing command, and for a regenerated expectation/snapshot/baseline file. Review every hit from both sweeps. **Severity escalation** (matches R29 mechanic): Major by default; **Critical** when the suppressed warning is in a security category — illustrative examples (not exhaustive): SAST injection warnings (SQLi/XSS/command), path-traversal warnings, SSRF warnings, timing-attack warnings, hardcoded-secret detector hits, deserialization-vulnerability warnings, cryptographic-API misuse / weak-cipher detector hits, dead-code warnings on auth/authz branches that may be reachable via alternate code paths. Suppressing a security warning is materially equivalent to disabling the security control. **Mechanical detection**: `bash ~/.claude/hooks/check-suppression.sh [base-ref]` scans diff `+` lines for the suppression markers above and flags Major when the same line carries no justification keyword (URL / issue ref / version pin / "false positive" / "upstream" / etc.). The hook can't tell whether the suppressed rule is in a security category — reviewers escalate to Critical manually based on the rule named in the suppression | Major (Critical when the suppressed warning is in a security category) |
