# RS3 — Input validation at boundaries

This file contains the full normative procedure for `RS3`. The compact row in `../common-rules.md` is only its routing summary.

## Full rule

| ID | Pattern | Procedure | Severity if missed |
|---|---|---|---|
| RS3 | Input validation at boundaries | New request parameters must be validated/sanitized at the schema level, not deep in business logic. **Mechanical detection**: `bash ~/.claude/hooks/check-input-validation.sh [base-ref]` enumerates HTTP mutation boundaries (function names matching `^(handle)?(POST|PUT|PATCH|DELETE)$` — covers NextJS / Hono / Express / SvelteKit-style routes including `handle*` wrappers; read verbs `GET` / `HEAD` / `OPTIONS` are excluded from v1) and classifies each as a validator if the body contains a schema-validation primitive — Zod-style `.parse(` / `.safeParse(`, library factories `z.<type>(` / `Joi.<type>(` / `Yup.<type>(` / `v.<type>(` (valibot) / `t.<type>(` (io-ts), or class-validator decorators `@IsString` / `@IsNumber` / `@ValidateNested` / etc. Non-validation `parse` callsites — `JSON.parse` / `Date.parse` / `Number.parseInt` / `URL.parse` / `crypto.parse` / `jwt.parse` — are skipped. Project-specific validation wrappers (e.g. `parseBody(req, schema)`, `withSchema(...)`, `validateRequest(...)`) MUST be passed via `EXTRA_VALIDATION_PRIMITIVES` env var. **A type assertion is not validation, and its downstream cost is the finding**: a cast/`as`/type-hint applied to a parsed body asserts a shape at compile time and checks nothing at runtime, so an off-type value (an object where a string was declared) flows on untouched. The consequence worth flagging is second-order — every *type-specific* defensive transform downstream (length cap, truncation, trim, normalisation, escaping) degrades to an identity NO-OP on that value, failing open silently because the no-op branch reads as a safe passthrough and the control still appears present in the diff. The no-op set is only ONE of the two consequence classes, and the lesser one: where the off-type value instead reaches an INTERPRETER rather than a sanitizer — a query builder, a comparison on an authentication path, a deep merge/assign, a template — the wrong type is not ignored but assigned the interpreter's own meaning (an operator object standing in for a scalar comparison, a prototype-bearing key in a merge). Enumerate BOTH classes; stopping at the sanitizers walks the review past the sink that matters. **Reviewer action**: for each cast on externally-supplied structured input, treat the value as unvalidated, then derive the value's complete sink set (R42) and ask of each sink what it does with the off-type value rather than whether it exists. Major fires when a NEW non-validating boundary shares a peer group (file/class scope OR cross-file `<dir:parent-of-verb-dir>` for leaf-verb-dir route files — same structural promotion as R4) with ≥1 validating sibling. Auto-suppression: transitive validation (calls another same-file validating boundary), body-edit re-flag (boundary name appears on diff `-` lines), stdlib `parse` collisions. The hook covers HTTP boundaries only; GraphQL / gRPC / message-queue boundaries need manual review. **It does not see either half of the cast sub-clause above**: it decides only whether a schema-validation primitive is present in the boundary body, so it cannot tell a cast from an absent check beyond that, and it never follows the value to its sinks. A clean run leaves the off-type-value question entirely unasked — that half is manual review on every framework | Major; Critical when an unvalidated off-type value can reach a query operator, a credential comparison, an object-merge/assign sink, or a template / HTML-interpolation sink |
